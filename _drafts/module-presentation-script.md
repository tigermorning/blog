## 0. 한 줄 정의 (20초)

**화면:** 맨 위 제목과 한 줄 정의.

**말하기**
> 이번 모듈은 AI 서비스를 사용자에게 내보내는 일이었어요. 한 줄로 줄이면, 서비스를 내보낸다는 건 세 가지 질문에 숫자로 답할 수 있게 만드는 일이에요. 어떤 버전이 나갔는지, 사용자에게 오류가 보였는지, 이전 버전으로 돌릴 수 있는지요.

## 1. 한 장 그림 — 전체 지도 (60초)

**화면:** 지도 그림. 애니메이션이 한 바퀴 도는 동안(21초) 천천히 말해요. 말하는 순서에 맞춰 상자가 지나가요.

**말하기**
> 먼저 숲을 보겠습니다. 왼쪽 «출발»은 설계예요. 코드를 짜기 전에 무엇을 내보낼지 정해요.
> 가운데 «길»은 코드 변경이 사용자에게 가는 여섯 칸이에요. 테스트, staging에 합치기, 이미지 만들기, 시험 서버, main에 합치고 승인, 요청 옮기기예요. 칸 아래 줄은 누가 하는지예요. 테스트는 CI가 자동으로, 합치기와 승인은 사람이, 나머지는 CD가 자동으로 해요. 빨간 상자가 코드 변경이라고 보시면 돼요.
> 오른쪽 «도착»은 실제 서비스(production)예요. Cloud Run 위에서 돌아가요.
> 칸을 지날 때마다 아래 세 질문이 같이 켜져요. 그 칸이 «어떤 버전이 나갔나», «사용자에게 오류가 보였나», «이전 버전으로 돌릴 수 있나» 중 어디에 증거를 쌓는지를 보여 주는 거예요.
> 색은 배운 주제예요. 파랑은 CI/CD, 초록은 Docker, 주황은 배포 전략이에요. 시험 서버 칸은 CI/CD와 Docker가 함께 다뤄서 두 색이 반반이에요.

**참고(말하지 않아도 됨):** 칸과 질문의 연결은 «아홉 개 노드를 한 번에» 블로그 글에 적은 노드 표시로 계산한 값이에요.

## 2. 이 글이 묶은 노드 (20초)

**화면:** 노드 타임라인(63~72). 평소에는 숫자와 주제 이름만 보이고 설명은 가려져 있어요.

**말하기**
> 모두연 노드로는 63번부터 71번까지 아홉 날이에요. 색은 지도와 같아요. 설계 하루, Cloud Run 이틀, CI/CD 이틀, Docker 이틀, 배포 전략 이틀이에요. 72번은 오늘 이 정리 시간이라서 점선으로 표시했어요.

## 3. 주제 구역을 하나씩 짚기 (70초)

**화면 조작:** 타임라인 아래 **둥근 이름표(설계, Cloud Run, CI/CD, Docker, 배포 전략)나 위의 숫자 칸에 마우스를 올리면** 그 주제의 설명이 떠요. 마우스를 구역에서 설명 상자 안으로 옮겨도 닫히지 않아서 링크를 누를 수 있어요. 상자와 구역을 모두 벗어나면 잠시 뒤 사라져요. 처음에는 «마우스를 대 보세요» 안내와 구역이 맥박처럼 깜빡여요(한 번 올리면 멈춰요). **클릭하면 고정**돼서 마우스를 치워도 계속 보여요. 같은 구역을 다시 클릭하면 닫혀요. 설명은 아래 내용 위에 겹쳐 떠서 화면이 밀리지 않아요.

설명 상자에는 «하는 일»(이 주제가 하는 일), «직접 확인한 것»(제가 해 보고 확인한 것), «자세한 글»(노드 링크)이 있어요.

**말하기(주제별 한 문장, 순서대로 올리거나 클릭)**
- 설계: 코드를 짜기 전에 누구에게 어디서 어떻게 쓰게 할지 정해서 문서 한 장으로 남겨요.
- Cloud Run: 코드 폴더를 올리면 공개 주소를 붙여 주는 구글 서비스예요. 서버가 정상이어도 사용자가 답을 못 받을 수 있어서 타임아웃과 로그를 봐요.
- CI/CD: 합쳐 달라는 요청(PR)이 올라오면 CI가 테스트를 자동으로 돌려 깨진 코드를 찾아 주고, 코드가 main에 합쳐지면 CD가 새 버전을 자동으로 올려요. **합치는 건 사람이 해요.** 제 앱에서 일부러 깨뜨린 변경은 테스트 9개 중 3개가 실패했어요. 테스트가 실패하면 합치기를 막는 규칙(브랜치 보호)은 연습용 저장소에서만 걸었고, 도장판에는 없어요.
- Docker: 실행 환경을 적은 설명서, 즉 Dockerfile로 이미지(코드와 실행 환경을 한 꾸러미로 포장한 것)를 만들어요. 시험 서버에서 확인한 이미지는 실제 서비스용으로 다시 만들지 않고 그대로 보내요. 이미지를 두 번 만들면 내용이 달라질 수 있어서 한 번만 만들어요.
- 배포 전략: 새 버전을 요청 0%로 먼저 올려 두고, 준비를 확인한 뒤에만 요청을 옮겨요. — 이게 다음 장 실험이에요.

> 시간이 모자라면 CI/CD와 Docker는 «하는 일»만 말하고 «직접 확인한 것»은 건너뛰세요.
> 마지막에는 고정을 풀어 두세요(같은 구역을 다시 클릭). 다음 내용 위에 상자가 떠 있지 않게요.

## 4. 내 예시 — 배포는 «성공»인데 요청 71건이 실패한 이야기 (80초)

**화면:** 실험 막대 그림(기본 프로브 vs /health 프로브).

**말하기**
> 다섯 주제 중 하나만 깊게 보여 드릴게요. 새 버전이 시작하는 데 30초 걸리는 예제 앱을 일부러 배포하고, 배포하는 동안 같은 주소에 0.2초마다 요청을 보내 실패를 셌어요.
> Cloud Run에는 새 버전이 요청을 받을 준비가 됐는지 확인하는 검사, 스타트업 프로브가 있어요. 앱이 건강한지 묻는 검사를 넓게 헬스체크라고 부르는데, 스타트업 프로브는 그중 새 버전이 시작할 때 하는 헬스체크예요.
> 이 프로브의 설정 두 가지를 비교했어요. 기본 프로브는 포트가 열렸는지만 봐서, 앱이 아직 준비 중인데도 통과시켜 버려요. /health 프로브는 앱의 /health 주소가 200, 정상으로 답할 때까지 기다려요.
> 결과가 이래요. 기본 프로브는 요청 389건 중 71건이 실패했어요. 배포 화면은 «성공»인데도요. 제가 /health 주소로 «진짜 준비됐는가»를 묻도록 바꾸자 283건 중 0건이 실패했어요.
> /health 프로브는 앱이 준비될 때까지 기다리기 때문에 배포가 끝나기까지 더 걸렸어요(약 19초 → 약 62초). 그동안 사용자는 이전 버전을 그대로 썼어요.

## 5. 활용 — 내 앱(도장판)에 세 질문을 대 보기 (60초)

**화면:** 도장판 화면 → GitHub 실행 기록 화면(번호 ①②③) → 비어 있는 곳/다음에 할 일 표.

**말하기**
> 제 앱 도장판은 오늘 할 일 칸 세 개에 도장을 찍는 루틴 앱이에요. 도장이 쌓이면 칸이 하나씩 열려요. 이 앱의 배포 기록은 GitHub에 그대로 남아 있어서, 세 질문을 이 화면에 대 봤어요.
> 1번, 어떤 버전이 나갔나는 배포 실행마다 코드 버전 번호, 커밋이 남아요. 여기서는 1a816a4예요.
> 2번, 사용자에게 오류가 보였나는 합쳐 달라는 요청마다 테스트가 자동으로 돌고, 통과는 초록 체크, 실패는 빨간 엑스로 보여요.
> 3번, 이전 버전으로 돌릴 수 있나는 rollback을 버튼으로 직접 실행해요. 이번에는 38초였어요.
> 비어 있는 곳도 있어요. 테스트(ci)는 칸이 열리는 규칙만 확인하고, 배포한 뒤 화면이 뜨는지나 사진 글자 읽기가 되는지는 자동으로 확인하지 않아요. main에는 보호 규칙이 없어서 테스트가 실패해도 합칠 수 있어요. 공개 범위도 정리가 필요해요. 아래 «다음에 할 일»은 아직 하지 않았어요.
> 정리하면 비어 있는 곳은 «사용자에게 오류가 보였나»에 몰려 있어요. 가장 먼저 자동화할 곳이에요. 감사합니다.

**주의:** 화면의 `1a816a4`와 `rollback #3, 38초`는 GitHub 공개 기록에서 찍은 값이에요. «롤백 24초»는 노드 69 글에서 잰 값으로 다른 측정이라 섞어 말하지 마세요.
