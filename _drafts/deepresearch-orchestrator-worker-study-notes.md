## 완료 — 이해 확인된 내용 (블로그 소재로 쓸 수 있음)

### 1강. 왜 한 명으로는 안 되는가

- **오늘 만들 것**: 질문 하나 던지면 스스로 자료 찾아 읽고 보고서 써 오는 에이전트.
  주제는 한국 근대사, "1894년에 일어난 주요 사건들은?" 같은 질문에 절 나뉘고
  문장마다 근거 붙은 2천 자 넘는 보고서가 나옴.
- **한 명으로 안 되는 이유 둘**:
  1. 물리적: 코퍼스 34건·447,487자(≈22만 토큰). gpt-4o-mini 컨텍스트 창은 12만
     8천 토큰이라 전부 못 넣음. 누군가 원문 읽고 요약만 올려야 함 — 그게 서브에이전트.
  2. 산출물 모양: 절이 셋인 보고서는 절마다 다른 근거 필요. 한 사람이 전부 이고
     쓰면 앞 절만 촘촘하고 뒤로 갈수록 헐거워짐.
- **여섯 노드**: ①기획(목차 짜고 배정) → ②배치(서브에이전트 파견, 여기서 그래프
  갈라짐) → ③조사(서브에이전트가 읽고 씀) → ④점검(빈 칸 찾아 재파견, 루프) →
  ⑤종합(보고서 완성) → ⑥평가(측정).
- **라우팅과의 차이**: 라우팅은 경로가 미리 고정돼 뒤에 뭐가 나올지 예측 가능.
  오케스트레이터-워커는 코디네이터가 그때그때 목차를 즉석에서 짜고 서브에이전트
  결과 보고 재파견 여부를 판단 — 제어가 더 어렵고 자유도 높은 대신 결과물
  퀄리티가 들쭉날쭉할 수 있음.
- **데이터셋**: 한국어 위키백과 한국 근대사(1876~1910) 클러스터. 문서 34건·
  447,487자·내부 링크 428개, CC BY-SA 4.0. 문서끼리 링크로 이어져 있어서
  서브에이전트가 한 건 읽으면 그 링크가 다음 후보가 됨(단, «거문도 사건»은
  내부 링크 0개라 링크로는 못 닿는 유일한 문서). 정답 문서표를 원래 만들어
  뒀었는데, 질문 하나 바뀌면 못 쓰는 잣대라서 교안 만들며 버림 — 14강에서
  정답표 없이 재는 법을 따로 만듦.
- **아이스브레이킹 퀴즈와 내 답**: "세 사람이 리포트 하나를 같이 쓸 때 역할을
  어떻게 나누면 낫고, 어떻게 나누면 나빠지나?" → 분야를 확실히 나누면 낫고
  겹치면 나빠질 것 같은데, 반대로 상대가 뭘 하는지 모르고 내 것만 하면 나빠질
  것 같다는 답. 이게 정확히 이 구조의 핵심 긴장 — 나눠서 고립 작업하면 겹침·
  빈칸이 생기고, 그걸 잡는 게 ④점검 노드(코디네이터가 전체를 보고 재파견).
  라우팅은 애초에 안 겹치게 경로를 고정해서 피하지만, 오케스트레이터-워커는
  자유도 준 대신 사후에 점검 루프로 수습하는 구조.

### 2강. 빈 노드 여섯 개 — 뼈대부터 세우는 이유

- **핵심 태도**: 첫 노드를 완성도 높게 만들면 두 번째 노드 붙일 때 첫 노드를
  다시 뜯게 됨. 그래서 여섯 노드를 전부 "아무 일도 안 하는 빈 함수"로 만들어
  먼저 연결하고 한 바퀴 돌려봄 — 살은 3~14강에서 노드 하나씩 채움.
- **State(TypedDict) 구조**: `question`(질문) · `plan`(목차/배정) ·
  `sections`(서브에이전트가 올린 절 원고) · `visited`((절,문서) — 누가 뭘
  읽었나) · `report`(완성 보고서) · `metrics`(평가 지표) · `log` · `task`(Send로
  한 명에게만 가는 지시) · `prior`(재위임 시 지난 원고).
- **리듀서(`Annotated[list, operator.add]`)**:
  - 리듀서 = "새 값 들어올 때 기존 값이랑 어떻게 합칠지 정하는 규칙". 기본은
    덮어쓰기(새 값이 기존 값을 지움).
  - 조사관 여러 명이 동시에 같은 칸(`sections`)에 쓰면, 덮어쓰기가 기본일 때
    가장 나중에 끝난 조사관 결과만 남고 나머지는 사라짐 — 동시 쓰기 충돌.
  - `operator.add`를 리듀서로 쓰면 `[A] + [B] + [C] = [A,B,C]`처럼 이어 붙임 —
    셋 다 살아남음.
  - 우편함 비유: 리듀서 없는 우편함은 새 편지 오면 예전 편지 버림(마지막
    배달부 것만 남음). 리듀서 있는 우편함은 편지를 나란히 쌓음(전부 남음).
  - 내가 확인한 재진술: "리듀서 없으면 덮어써서 사라지고, 있으면 이어 붙여서
    다 남아" — 맞음.
- **fanout()과 Send**:
  - 보통 조건부 갈림길 함수는 문자열 하나("다음엔 review로")만 돌려줘서 목적지
    하나만 표현 가능. `Send("researcher", {입력값})`은 "이 노드를 이 입력값으로
    하나 새로 실행해라"는 지시서 한 장이라, 실행 전용 데이터까지 들고 다님.
  - `fanout()`이 Send 지시서를 **리스트**로 돌려주면, LangGraph는 리스트 안
    지시서 개수만큼 그 노드를 동시에(병렬로) 띄움.
  - 사슬: `plan()`이 절을 몇 개로 나눴나 → `idxs`(=`plan["배치"]`) 길이 →
    `for i in idxs` 반복 횟수 → 만들어지는 Send 지시서 개수(리스트 길이) →
    동시에 뜨는 조사관 수. 지금(2강 뼈대)은 `plan()`이 절 하나만 만들어서
    조사관 한 명. 5강에서 `plan()`이 LLM으로 절을 셋 만들면 조사관 셋 동시
    실행됨.
  - 조사 카드 비유: 선생님(코디네이터)이 그날 조사할 주제 개수만큼 카드를
    만들어 학생들에게 나눠줌. 카드 한 장 = 학생 한 명 파견. 카드가 몇 장
    생기느냐가 학생이 몇 명 뛰느냐를 그대로 정함.
  - 병렬로 뛰는 조사관들은 서로 뭘 읽는지 모름 — 같은 문서를 둘이 읽는 낭비가
    여기서 생김(6강에서 숫자로 확인 예정). 1강 아이스브레이킹에서 짚은 "상대
    작업 모르면 나빠진다" 문제가 실제로 발생하는 지점.
  - 내가 확인한 재진술: "카드가 몇 장 생기느냐가 학생이 몇 명 뛰느냐를 정해" —
    맞음.
- **실행 검증**: 로컬 파이썬으로 2강 코드 그대로 돌려서 강의 예상 로그와 정확히
  일치 확인함.
  ```
  코퍼스 34건 · 447,487자

  ① 기획   목차 1절 (빈 노드)
  ② 배치   서브에이전트 1명 파견 (빈 노드)
     ③ 조사관   «(빈 절)» 0건 읽고 0자 (빈 노드)
  ④ 점검   1절 중 빈 칸 0개 (빈 노드)
  ⑤ 종합   1절 → 보고서 0자 (빈 노드)
  ⑥ 평가   지표 0개 (빈 노드)
  ```
  여섯 줄이 전부 0 — 앞으로 열두 강에 걸쳐 매번 로그 한 줄만 0에서 벗어나고
  나머지는 그대로인 게 "진도"라는 뜻.
- **`add_conditional_edges` 세 번째 인자 vs 인원수**: `g.add_conditional_edges(
  "dispatch", fanout, ["researcher","review"])`의 세 번째 인자 `["researcher",
  "review"]`는 "갈 수 있는 곳" 목록일 뿐. 실제 몇 명이 가는지는 `fanout()`이
  돌려주는 Send 리스트 길이가 정함 — 목적지 목록(그래프 구조)과 인원수(실행
  시점에 정해짐)는 별개 개념.
- **`g.add_node(name, globals()[name])`**: 노드를 함수 객체가 아니라 이름
  (문자열)으로 찾아 등록. 그래서 지금(2강)은 `researcher`가 빈 껍데기 함수지만,
  9강에서 강의 자료가 같은 이름 `researcher`로 실제 조사 로직을 다시 정의해
  실행하면 `build()` 코드를 한 글자도 안 고쳐도 그래프가 새 버전을 씀. "나중
  강"은 이 커리큘럼의 뒤 회차(9강 등)를 뜻함 — 각 강마다 노드 함수 하나씩
  실제 내용으로 갈아 끼우는 구조.
- **객관식 퀴즈 정답**: "9강에서 `researcher` 함수를 진짜 조사관으로 갈아 끼울
  때 `build()`도 함께 고쳐야 할까?" → 정답은 2번 "고칠 필요 없다. `globals()
  [name]`이 이름으로 찾으므로 같은 이름으로 다시 정의하면 교체된다". 위
  `globals()[name]` 항목과 같은 근거.

### 3강. 라우팅도 GraphRAG도 아닌 이유 — 구조가 정해지는 시점

- **셋 다 "질문 받아 답 찾기"인데, 다른 건 구조가 언제 굳느냐**:
  - 라우팅: **코드 작성 시** 굳음. `if 유형=="환불": return 환불핸들러`처럼
    갈래 목록이 코드 짤 때 이미 확정. 예측 쉽고 쌈.
  - GraphRAG: **인덱싱 시** 굳음. 질문 오기 전에 문서에서 개체·관계 뽑아
    그래프+커뮤니티 요약을 미리 만들어 둠. 질문은 이미 굳은 구조 위를 걸음.
  - 오케스트레이터-워커(오늘 구조): **질문 도착 후** 굳음. 목차 몇 절인지,
    조사관 몇 명인지, 누가 뭘 맡는지 질문마다 새로 정해짐. 늦게 정할수록
    질문에 잘 맞고 비쌈.
- **재사용과 상각 — 인덱싱 값을 언제 뽑는가**: GraphRAG 인덱스는 질문 수로
  나눠짐(재사용 100%). 오케스트레이터-워커는 재사용 0% — 질문마다 목차·
  서브에이전트를 새로 만듦.
  - 숫자: 코퍼스 447,487자 중 질문 하나 푸는 데 모델이 읽는 양이 약
    200,074자(코퍼스의 0.45배). 질문 2.2개만 물어도 코퍼스 전체를 한 번
    통째로 읽는 값이 나감 — GraphRAG 인덱싱이 미리 해두는 일이 바로 그 통독.
  - 가상의 숫자로 원리 확인(강의 수치 아님, 설명용): 인덱싱 100원(1회) +
    질문당 1원 vs 인덱싱 없이 질문당 10원. 질문 1000개면 인덱스 쪽
    (1100원)이 압도적으로 쌈. 질문 10개면 오히려 인덱스 없는 쪽(100원)이
    더 쌈 — 인덱싱에 투자한 100원을 다 못 뽑음("본전 못 뽑는다").
  - **"질문마다 각도가 다르다"의 의미**: 각도 = 질문이 요구하는 "묶는
    기준". 예) "1894년 사건들은?"(시간순) vs "일본과 맺은 조약들은?"
    (종류별) vs "동학농민운동 관련 인물은?"(사건-인물 중심). GraphRAG
    인덱스는 인덱싱할 때 **하나의** 묶는 기준으로 이미 짜여 있어서, 그
    기준과 다른 각도의 질문이 오면 그래프에 원하는 연결이 없어 원문을
    거의 다시 뒤져야 함 — "1원 할인"이 그 질문엔 안 먹히고 사실상 10원에
    가까워짐. 그래서 질문 개수가 많아도 각도가 제각각이면 인덱싱 이득이
    확 줄어듦(상각이 잘 안 됨).
- **컨텍스트 길이를 다루는 방식**: GraphRAG는 이웃 개체+텍스트 조각(Local)
  또는 미리 만든 커뮤니티 요약(Global)을 한 프롬프트에 모아 넣음 — 창 하나로
  해결. 오케스트레이터-워커는 조사관마다 독립된 컨텍스트 창을 가짐 — 원문은
  그 안에서 소화되고 사라지고, 위(코디네이터)로는 원고(요약)만 올라감.
  실측: 코디네이터가 본 글자는 팀 전체가 읽은 글자의 5.0%뿐, 나머지 95.0%는
  조사관 안에서 소비되고 사라짐. "컨텍스트 윈도우를 병렬로 넓힌다"는 게 이 뜻.
- **셋을 한 표로** (강의 원문):

  | | 라우팅 | GraphRAG | 코디네이터+서브에이전트 |
  |---|---|---|---|
  | 구조 굳는 시점 | 코드 작성 시 | 인덱싱 시 | 질문 도착 후 |
  | 갈래 목록 | if/elif에 적힌 것 | 그래프의 이웃과 커뮤니티 | 코퍼스 문서 전체 |
  | 재사용 | 전부 | 인덱스 | 없음 |
  | 질문당 LLM 호출 | 한두 번 | 검색+몇 번 | 29번 안팎 |
  | 근거 모이는 곳 | 한 창 | 한 창 | 조사관마다 따로 |
  | 산출물 | 한 덩어리 답 | 한 덩어리 답 | 절 단위 보고서 |
  | 틀렸을 때 | 잘못된 갈래로 끝 | 인덱스에 없으면 못 찾음 | 읽고 나서 되돌릴 수 있음 |

  마지막 줄이 핵심: 라우팅은 한 번 갈래 고르면 못 돌아옴, GraphRAG는
  인덱싱 때 안 뽑힌 관계를 질문 시점에 못 만듦, 오케스트레이터-워커는
  읽어본 뒤 판단을 바꿀 수 있음(④점검 노드가 이 일을 함).
  - **"29번 안팎"은 이 코퍼스·이 프로젝트 실측값**(보편 상수 아님). 이
    코스가 기본으로 잡은 조사관 인원은 "넷"(커리큘럼 소개, 2강 비용
    안내에서 확인)이라 29번도 그 시나리오에서 나온 값일 가능성이 크지만,
    강의가 명시적으로 밝히진 않음 — **추정, 미확정**으로 남겨둠. 세부
    산출 내역(어느 노드에서 몇 번씩)도 강의가 공개 안 함.
- **Anthropic 인용**: 멀티 에이전트 구조가 단일 에이전트보다 내부 평가에서
  90.2% 나았지만, 토큰은 대화 한 번보다 약 15배 씀. "모든 에이전트가 같은
  맥락을 공유해야 하거나 에이전트 사이 의존이 많은 영역(예: 코딩)엔 안
  맞는다"고 명시(출처: Anthropic "How we built our multi-agent research
  system").
- **판단 기준 두 가지**: ① 코드 짤 때 갈래를 전부 적을 수 있는가 → 되면
  라우팅. ② 같은 자료에 질문이 몇 번 들어오는가 → 수천 번이면 인덱싱
  (GraphRAG)이 이김. 둘 다 아닐 때만 오케스트레이터-워커. 이 두 기준은
  독립적으로 같이 봐야 함 — "질문 많음+답 짧음"이어도 갈래가 코드 짤 때
  다 나열 가능하면 라우팅이 GraphRAG보다 더 간단하고 쌈(그래프 만들 필요
  자체가 없음). GraphRAG가 진짜 필요한 이유는 "질문 많음"이 아니라 자료
  안의 관계를 타고 들어가야 답이 나오는 경우(다단계 추론)이기 때문.
- **"질문 많음+답 짧음"이 오케스트레이터-워커를 배제하는 이유(둘 다 겹침)**:
  1. 재사용 0% + 질문 많음 조합 — 매번 처음부터 다시 계획 짜는 비용이
     질문 수만큼 누적되어 감당 안 됨(위 100원/1원/10원 예시에서 "인덱스
     안 쓰는 쪽"과 같은 처지).
  2. 산출물 모양 — 오케스트레이터-워커는 "절 단위 보고서"를 만드는
     구조(조사관 여러 명이 절을 나눠 씀). 답이 한두 문단이면 애초에 나눌
     절이 없어 이 분업 구조를 쓸 이유가 없음. "나눌 것이 실제로 나뉘어
     있을 때만 나눈다. 오늘 나누는 것은 코퍼스가 아니라 보고서의 절"
     (강의 원문).
- **객관식 퀴즈와 정답**: "사내 문서 50만 자, 하루 3천 건 질문(유형
  제각각, 대부분 한두 문단이면 답 됨) — 어느 구조?" → 정답 2번 GraphRAG.
  근거: 판단기준②(하루 3천 건 = 질문 많음 → 인덱싱 상각 유리) + 산출물
  모양(짧은 답 = 보고서 아님 → 오케스트레이터-워커 배제) + 판단기준①
  (유형 제각각이라 갈래를 코드 짤 때 못 적음 → 라우팅도 배제).
- **주관식(성찰형) 퀴즈 — 실제 프로젝트에 적용**: "본인 프로젝트에서 구조를
  언제 굳혀도 되나? 코드 작성 시점·인덱싱 시점·질문 도착 후 중 어디이고,
  근거는?" (처음엔 건너뛰었다가 별도 세션에서 실제 저장소 코드를 보고 답함)

  **굳혀도 되는 시점 — 판정만 먼저 요약**(질문이 "언제 이미 굳어 있나"가
  아니라 "언제 굳혀도 되나"이므로, 더 늦게 굳혀도 되는데 안 늦추는 게
  아니라 더 늦출 이유가 없다는 뜻으로 읽을 것):

  | 프로젝트·부분 | 굳혀도 되는 시점 | 근거 한 줄 |
  |---|---|---|
  | nk-briefing · 슬롯 배정 | 코드 작성 시 | 슬롯 3개로 고정, 갈래를 코드에 다 적을 수 있음(기준①) — 더 늦출 이유 없음 |
  | nk-briefing · 기사별 워커 파견 | 질문 도착 후 | 그날 후보 기사 수가 매번 달라 코드 작성 시점엔 정할 수 없음 — 더 당길 수가 없음 |
  | lesson-graph-agent | 인덱싱 시 | 코퍼스 63건 고정 + 질문 반복(기준②) — 질문마다 다시 굳히면 상각이 안 됨 |
  | 한국어 교정기 | 코드 작성 시 | 규정·사전 이미 확정. PoC로 "질문 도착 후"(임베딩/LLM)까지 늦춰 실측했지만 이득 없이 손해만 남 |
  | 자막생성기 | 코드 작성 시 | 파이프라인에 분기 자체가 없음 — 굳힐 갈래가 하나뿐이라 시점 논의가 성립 안 함 |
  | 부동산 앱 | 코드 작성 시 | 차별 카테고리 10개, 가이드라인 문서가 갈래를 이미 다 나열해 둠(기준①) |
  | 교안 생성기 · 요지/커리큘럼 | 질문 도착 후(자동화하면) | 범위 선택마다 결과가 완전히 갈려 코드 작성 시점엔 못 굳힘 — 지금은 이 판단을 사람이 대신 내림 |

  아래는 각 판정의 근거를 코드로 확인한 상세.
  - **nk-briefing** (`graph.py`): 한 파이프라인 안에 두 시점이 같이 있음.
    - 슬롯 구조(breaking/deep/tier1)는 **코드 작성 시** 굳음. 매일 같은 세
      슬롯이 반복되고, 슬롯별 진입 규칙(`BODY_MIN`, `DEEP_WINDOW_H`,
      `TIER1_LOOKBACK_D` 등)이 상수로 하드코딩돼 있음. 판단기준①("코드 짤
      때 갈래를 전부 적을 수 있는가")이 그대로 맞음 — 슬롯이 세 개뿐이고
      안 바뀌므로 라우팅이 맞고, 여기에 오케스트레이터를 쓸 이유가 없음.
    - 반면 `report` 노드(기사 한 건당 조사관 한 명, `Send`로 fanout)는
      그날 `select`가 기사를 몇 건 골랐느냐에 따라 매번 워커 수가 달라짐 —
      **질문(그날의 후보 기사 집합) 도착 후** 굳음. 3강의 오케스트레이터-
      워커 정의(카드 개수가 학생 수를 그때그때 정함, 2강)가 그대로 적용됨.
    - 결론: "이 프로젝트는 무슨 구조냐"가 아니라 "이 파이프라인의 어느
      단계가 무슨 구조냐"로 쪼개서 봐야 함 — 슬롯 배정=라우팅, 기사별
      워커 파견=오케스트레이터-워커.
  - **lesson-graph-agent** (`build_graph.py`): 과외 교안 63건에서 개념
    선수관계 그래프를 질문 오기 전에 미리 만들어 둠 — **인덱싱 시** 굳음.
    `app.py`는 이미 만들어진 그래프 위를 걸을 뿐. 판단기준②("같은 자료에
    질문이 몇 번 들어오는가")가 근거: 63건은 고정 코퍼스고, 선수관계 조회·
    추천 질문이 앞으로 반복해서 여러 번 들어올 걸 전제로 만든 도구라 인덱싱
    비용이 상각됨. 전형적인 GraphRAG 사례.
  - **오케스트레이터-워커가 메인 구조인 프로젝트는 아직 없음**: nk-briefing의
    기사별 워커 파견이 가장 가까운 부분 사례일 뿐, 코퍼스가 매번 통째로
    안 바뀌는 한(=재사용 0%를 감당할 만큼 질문이 드문 한) 이 구조를 전면
    도입할 이유가 지금 프로젝트들엔 없다는 뜻이기도 함.
  - **한국어 교정기** (`korean-subtitle-corrector`, `subtitle_corrector/`):
    규정·사전·판례가 이미 확정돼 있는 영역 — **코드 작성 시** 굳음
    (`dictionary/`, `engine/`, `common_errors.py`가 규칙 엔진). PoC
    (`poc/mq2-spacing-retrieval/`)에서 이 자리에 임베딩·로컬 LLM 검색을
    실제로 얹어 실측했고, 둘 다 신경망 안 쓰는 방법(규칙+사전)에 졌음 —
    "이미 맞게 쓴 문장을 망가뜨린 것은 임베딩뿐"이었다는 결과. 판단기준①
    ("갈래를 코드 짤 때 전부 적을 수 있는가")이 실측으로 확인된 사례: 답이
    문서(맞춤법 규정)로 이미 결정돼 있으면 확률적 생성은 강점이 아니라
    약점 — "모를 때 기권할 줄 모른다"는 이 프로젝트 README의 결론이 3강
    판단기준①과 정확히 같은 말.
  - **자막생성기** (`subtitle-tc-generator`): 전사 → 대조 → 번역 → 재분할 →
    스포팅, 순서 고정된 순차 파이프라인 — **코드 작성 시** 굳음. 우선순위
    ("자동 교정 오답 0 > 플래그 건수 감소 > recall")도 코드 시점에 못박힘.
    영상 한 편 안에서 자막 줄 수는 매번 다르지만 그건 반복 횟수일 뿐
    구조(다음에 뭐가 오는지)는 안 바뀜 — 분기가 아예 없어서 라우팅보다도
    더 단순한 경우. "코드 짤 때 갈래를 전부 적을 수 있는가"에서 갈래 자체가
    하나뿐인 극단.
  - **부동산 앱** (`korea-direct-rental`): 유일한 판단 로직은 차별 소지
    문구 감지(`src/lib/guardrails/discrimination.ts`) — 10개 카테고리
    정규식, **코드 작성 시** 굳음. 카테고리가 차별금지 가이드라인 3항("서비스가
    수집하지 않는 정보") 목록을 그대로 가져온 것이라 판단기준① 충족(법령·
    가이드라인이 갈래를 이미 다 나열해 둠). 경고용이라 오탐 허용 — LLM
    분류로 유연하게 갈 이유가 없는 것도 같은 근거(갈래가 이미 고정 목록).
  - **교안 생성기** (`curriculum-autogen`): 특이 사례 — STT 전사(RTZR+로컬
    Whisper 이중 전사)는 **코드 작성 시** 굳은 고정 파이프라인. 근데 요지
    추출과 커리큘럼 작성은 README가 명시하듯 **의도적으로 자동화 안 하고**
    Claude Code 세션에 수동으로 넘김(Claude Console 종량제 과금 이슈로
    `lib/extract.py` 자동호출을 보류한 ADR). 커리큘럼 범위 선택(이번
    수업만/최근 N회/직접 선택)은 매번 달라 결과가 완전히 갈리는, 원래대로면
    **질문 도착 후** 굳어야 할 자리 — 근데 이 프로젝트는 그 판단을 그래프
    자동화 대신 **사람이 코디네이터, Claude Code가 워커**인 수동 구조로
    대체해 둠. 자동화하면 정확히 오케스트레이터-워커 자리라는 뜻이기도 함.
  - **네 프로젝트를 가로질러 보이는 패턴**: 다섯 개 프로젝트(nk-briefing
    포함) 중 코드 작성 시 굳는 부분이 압도적으로 많음 — 답이 이미 문서·
    법령·규정으로 결정돼 있는 도메인이 많기 때문(맞춤법 규정, 차별금지
    가이드라인, TC 생성 순서). 인덱싱 시점은 코퍼스가 고정이고 질문이
    반복될 때만(lesson-graph-agent) 딱 한 번 나옴. 질문 도착 후 굳는
    자리는 지금 전부 "부분 사례"거나(nk-briefing) "사람이 대신 하는 중"
    (curriculum-autogen)이라, 실제로 오케스트레이터-워커를 그래프로 자동화할
    만큼 코퍼스 크고 질문 다양한 프로젝트는 아직 없음.

### 4강. 코디네이터는 무엇을 보고 나누는가 — 퀴즈 대기, 본문만 정리

- **문제**: ①기획 노드(목차 짜고 조사관 배정)를 채울 차례인데, 코디네이터는
  아직 코퍼스를 하나도 안 읽음. 뭘 보여 줄지 잘못 고르면 조사관이 엉뚱한
  문서에 예산(호출 1회)을 씀 — 병렬로 뛰기 때문에 배정 후엔 되돌릴 수 없음.
- **선택지 넷과 비용 대 정확도**:
  1. 제목 34개만 — 가장 쌈. 상식으로 아는 사건(«갑신정변»)은 맞히지만,
     "을사조약 저항"을 물었을 때 «임오군란»(1882년, 무관)을 배정하는 사고가
     실제로 났음.
  2. **제목 + 앞 250자 카드 (강의가 고른 답)** — 코퍼스의 1.9%(8,666자)만
     더 보여주는 값으로 같은 질문에 «을사조약»·«헤이그 특사 사건»·«최익현»
     이 배정됨. 위키백과는 첫 문단이 정의라 잘 맞지만, 머리말이 형식적인
     자료(사내 문서 등)에선 카드가 다 비슷해 보여 무너질 수 있음 — 그때는
     '앞 250자' 대신 '미리 만든 한 줄 요약'으로 재료만 바꾸면 구조는 그대로
     씀.
  3. 한 건 정찰 후 목차 짜기 — 가장 정확하지만 직렬 단계가 하나 늘어 지연
     시간이 통째로 추가되고, 정찰 문서를 잘못 고르면 편향이 목차 전체로
     퍼짐.
  4. 문서 전부 — 447,487자 ≈ 223,743 토큰인데 창은 128,000 토큰이라
     1.7배 초과, 물리적으로 불가능. "왜 서브에이전트가 필요한가"의 반례로만
     기능.
  - 판단: ①은 싸 보여도 배정 실패=예산 손실이라 실은 안 쌈, ③은 정확하지만
    병렬로 벌려던 시간 이득을 직렬 단계로 까먹음, ④는 후보가 아님. ②가
    비용 대비 효과 압도적.
- **배정과 목차 분할은 다른 개념**: 목차 분할=무엇을 "쓸지"의 분할, 배정=
  무엇을 "읽을지"(출발점)의 분할. 병렬 조사관은 서로를 못 봐서 각자
  알아서 고르면 유명 문서 두세 건에 쏠림 — 실측: 배정·구역 둘 다 끄면 중복률
  41.5%, 켜면 19.6%. 코드가 절마다 시작 문서 하나씩 배정하고 겹치면 코드가
  다른 것으로 바꿈.
- **배정은 울타리가 아니라 출발점**: 배정받은 문서가 상관없으면 조사관은
  다음 한 건을 자기 판단으로 고를 수 있어야 함. 울타리로 만들면 코디네이터의
  오판이 그대로 결과가 됨.
- **검증 신호 셋**(⑥평가 노드가 14강에서 metrics로 뽑음): 배정 적중률(기획이
  배정한 시작 문서 중 골든셋 비율), 관련 없음 비율(조사관이 첫 읽기에서
  "관련 없음"으로 돌려준 비율), 최다 문서 편중(인용이 한 문서에 몰렸는가).
  틀렸을 때 증상: 보고서 자체는 멀쩡해 보임 — 엉뚱한 문서를 읽어도 그럴듯한
  절을 써 오므로 질문과 절 제목을 나란히 놓고 봐야 드러남.
- **객관식 퀴즈는 사용자가 건너뜀**(1강·3강과 같은 패턴): "카드 길이를
  250자에서 2,000자로 늘리면?" — 선택지: ①정확해지고 비용 거의 같음
  ②정확해지지만 카드 총량이 코퍼스의 15% 가까이 되어 매 질문마다 그만큼 냄
  ③달라지는 것 없음 ④조사관이 문서를 읽을 필요 없어짐. (참고로
  34건×2,000자=68,000자, 코퍼스 447,487자 대비 15.2%)
- **더 해보기는 5강 코드가 나온 뒤로 미룸**: 이 스텝엔 실행 가능한 셀이 없음
  (Monaco 에디터 확인함, 없음) — `cards()`/`CARD` 상수는 5강 ①기획 노드
  코드에 있음. 5강에서 라이브로 실행함(아래).

### 5강. ① 기획 노드 — 목차를 짜고 조사관을 붙인다 — 실측 완료

- **코드 세 덩어리**: 조사관 명단(`ROSTER`, 5명 — 큰그림·시간순·인물·원인·
  비교 담당), 카드 함수(`cards()`, 4강에서 고른 "제목+앞250자"를 그대로
  구현), `plan` 노드(LLM에 JSON으로 목차·역할·시작문서를 받아 코드로
  검증). 역할은 프롬프트 한 줄일 뿐 별도 코드가 아님 — 같은 문서를 읽어도
  "시간순 담당"이면 날짜를, "인물 담당"이면 사람을 뽑음.
- **키 관리**: `.env → Colab 보안 비밀 → 직접 입력` 순으로 찾고, 못 찾으면
  `assert`로 바로 멈춤. 이유: 이게 없으면 키 없이 여러 섹션을 지나가다
  `plan` 노드에서야 엉뚱한 오류로 죽음 — 잘못된 설정은 쓰기 전에 죽는 게
  나음. `getpass`를 쓰는 이유도 명시됨: `input()`은 키가 노트북 출력에
  그대로 남아 파일째 공유될 위험.
- **구조화 출력 + 코드 검증**: 모델이 JSON으로 목차·역할·시작문서를
  내면, 코드가 역할이 명단에 있는지·시작문서가 실제 문서인지·절끼리
  겹치지 않는지 확인함(`seed if seed in DOCS and seed not in taken else
  ...`). 모델이 "조일수호조규 속약"처럼 그럴듯하지만 없는 제목을 지어낼 수
  있어서, 검증 없이 바로 `DOCS[제목]`에 넣으면 `KeyError`로 터짐. 코드
  검증은 **형식만** 봄 — 배정된 문서가 실존하는지는 확인해도 그게 질문에
  맞는 문서인지는 확인 못함(내용 쪽은 ④점검·⑥평가가 맡음).
- **실측 ①: 강의 코드 그대로 로컬 실행** (`_drafts/step5_plan_verify.py`,
  `PYTHONIOENCODING=utf-8 python _drafts/step5_plan_verify.py`로 재현 가능,
  `~/Documents/openai_key.env`의 실습용 키 사용, gpt-4o-mini 실제 호출):
  ```
  ① 기획   목차 4절 · 원인 담당→«동학 농민 혁명» · 시간순 담당→«청일 전쟁» ·
            인물 담당→«갑오개혁» · 큰그림 담당→«을미사변»
  COST: {'calls': 1, 'sub_chars': 0, 'coord_chars': 8894}
  ```
  검증 신호 셋 확인: ①절 4개(≥2) ②절마다 시작 문서가 서로 다름(동학농민
  혁명·청일전쟁·갑오개혁·을미사변, 겹침 없음) ③배정 문서가 질문("1894년
  주요 사건")의 시대·주제와 맞음(1894~95년 사건들). `coord_chars`
  8,894자는 강의가 말한 카드 총량 8,666자(코퍼스의 1.9%)에 프롬프트
  지시문까지 합친 값이라 근사치가 맞음.
- **실측 ②: "내용 단위로 나눠라" 문장을 지우고 재실행**
  (`_drafts/step5b_no_content_unit.py`, 원본에서 해당 지시문 두 줄만 제거):
  ```
  ① 기획   목차 4절 · 큰그림 담당→«동학 농민 혁명» · 시간순 담당→«청일 전쟁» ·
            인물 담당→«전봉준» · 원인 담당→«갑오개혁»
  절 제목: 1894년 주요 사건 개요 / 사건의 시간적 전개 / 주요 인물의 역할 /
          사건의 원인 분석
  ```
  강의가 예고한 그대로 절 제목이 "개요·시간적 전개·인물의 역할·원인
  분석" — **형식 단위**로 갈라짐(강의 원문의 '개요·연표·인물·인과분석'과
  사실상 같은 패턴). `coord_chars`는 8,894자로 원본과 동일(지시문 두 줄
  삭제분이 카드 총량에 비하면 무시할 만큼 작아서) — 지시문 하나가 비용은
  그대로 두고 **목차의 축**만 바꾼다는 것을 실측으로 확인.
- **객관식 퀴즈 — 실측으로 근거 확인, 정답은 사용자가 직접 고름**: "'목차는
  반드시 내용 단위로 나눠라'를 지우면?" 정답은 ②("목차가 형식 단위가 되고
  조사관들이 같은 문서를 중복해서 읽는다")로 보임 — 위 실측 ②가 정확히 그
  결과를 보여줌(형식 단위 목차 자체를 실제로 관찰함). 다만 문항 선택은
  사용자 몫으로 남겨 둠(1강·3강·4강과 같은 원칙).
- **사용자가 코랩(Colab)에서 직접 돌려 보며 나온 Q&A**:
  - `BASE = os.getcwd()` — 괄호 안에 아무 경로나 못 넣음(인자 없는 함수,
    넣으면 `TypeError`). 로컬 전용으로 쓸 거면 그 줄+`try/except` 블록을
    통째로 지우고 `load_dotenv(r"절대경로")` 한 줄로 대체 가능. 단, 코드가
    찾는 파일명이 `.env` 고정이라 `openai_key.env`처럼 이름이 다르면 `BASE`
    만 바꿔선 안 됨 — `load_dotenv()` 자체를 그 파일 절대경로로 직접 불러야
    함.
  - `load_dotenv(경로)` — 그 경로 파일의 `KEY=값` 줄을 읽어 `os.environ`에
    넣는 함수. 코드에 키를 직접 안 적고 별도 파일로 떼어 놓기 위함.
  - `assert 조건, 메시지` — 조건 거짓이면 그 자리서 `AssertionError`로
    멈춤. 키 없이 넘어가면 몇 셀 뒤 `plan`에서야 엉뚱한 오류로 죽어 원인
    찾기 어려워지므로, 문제 지점에서 바로 죽이는 안전장치.
  - `ROSTER`는 역할 이름→설명 딕셔너리(5개, 코드로 미리 고정). `plan()`이
    이 목록 전체를 프롬프트에 넣어 LLM이 절마다 하나씩 고르게 하고, 코드는
    "그 이름이 ROSTER에 실제로 있는가"만 검증(`role if role in ROSTER
    else "큰그림 담당"`) — 역할을 **누가 고르는지**(LLM)와 **유효성만
    검사하는지**(코드)가 분리돼 있음.
  - `COST`는 호출 횟수·글자 수 세는 카운터(`calls`/`coord_chars`/
    `sub_chars`) — 3강에서 본 "코디네이터가 본 글자는 5%뿐" 같은 수치가
    바로 이 카운터에서 나옴. `일시적오류`는 재시도해도 되는 에러 이름
    목록(RateLimit·APIConnection·Timeout·InternalServer) — 이 중 하나면
    지수 백오프로 재시도, 아니면(키 오류 등) 바로 `raise`해서 시간 낭비
    안 함.
  - `NameError: name 'run' is not defined` — `run()`은 이 5강 셀이 아니라
    2강 뼈대 셀에서 정의됨. 커널이 재시작됐거나 이전 셀을 안 돌리고 이
    셀만 실행하면 남. 해결: 노트북 위에서부터(코퍼스 로드·State·빈
    노드들·`build()`·`run()`) 순서대로 다시 실행.
  - **같은 코드·같은 질문인데 배정 결과가 실행마다 다른 이유**:
    ① `temperature=0`이어도 OpenAI API는 100% 결정적이지 않음(배치 처리·
    부동소수점 연산 등 내부 사정). ② 애초에 "정답 목차"가 하나가 아님 —
    1894년 사건을 4절로 나누는 방법이 여러 갈래라 LLM이 매번 그중 하나를
    고름. 5강 본문이 이미 예고한 내용("같은 질문을 두 번 돌려도 절
    제목과 배정이 달라진다")과 일치. 지금 단계(①기획)는 "뭘 읽을지 계획"만
    세운 것 — `researcher`가 아직 빈 노드라 실제로 읽은 건 하나도 없음
    (다음은 6~9강에서 채움).
  - **자료가 너무 방대해 사람이 눈으로 다 확인 못 할 때**: 4강의 검증
    신호 셋(배정 적중률·관련 없음 비율·최다 문서 편중)이 바로 이 문제의
    답 — 사람이 절 하나하나 안 읽어도 코드가 로그·메타데이터(무엇을
    읽었나, 무엇을 버렸나, 어디에 몰렸나)에서 자동으로 뽑는 숫자로 대체.
    이 프로젝트도 원래 "정답 문서표"(골든셋)를 만들어 뒀다가 버림(1강
    노트) — 질문 하나 바뀌면 못 쓰는 잣대라서. 그래서 14강("⑥ 평가 —
    정답표 없이 재는 법")에서 정답표 없이 코퍼스 자기참조적 지표로 재는
    법을 따로 만듦 — 자료가 방대해 사람이 못 읽는 상황이 정확히 이 설계의
    존재 이유.

### 6강. 얼마나 넓게 나눌까 — 폭과 깊이

- **문제**: 5강까지 기획 노드가 목차(절 수·역할·시작 문서)를 정함. 이제 ②배치
  단계에서 정할 것 둘: **폭**(목차를 절 몇 개로 나눌까=조사관 수) ·
  **깊이**(조사관 한 명이 문서 몇 건까지 읽을까).
- **폭·깊이는 트레이드오프**: 총 읽기량 = 절 수 × 절당 예산으로 고정됨. 절
  4개×절당 3건=12건, 같은 12건을 절 2개로 몰면 한 명이 6건. 폭 늘리면 깊이는
  자동으로 깎임 — 숫자 계산.
- **폭이 좁아지면(절 수 줄면) 스코프도 같이 넓어짐**: 절 수 줄면 조사관 수도
  줄고(절 하나=조사관 한 명), 다뤄야 할 전체 질문은 그대로라 남은 조사관이
  더 넓은 범위를 나눠 맡아야 함. 이때 절당 예산(깊이)은 트레이드오프로
  늘어나지만, 조사관은 그 늘어난 예산을 다양하게 못 쓰고 가장 두꺼운 자료
  하나로 절 전체를 때우는 경향이 생김 — **예산(깊이)이 늘어도 실제 근거
  다양성은 오히려 얕아지는 역설**. 폭↔깊이(숫자 트레이드오프), 폭↔스코프
  (동반 확대), 예산↔실제다양성(역설) — 세 개 다른 관계임을 구분해 확인함.
- **예측 두 가지**(검증은 14강으로 미룸, 지금은 예측만): ①총 예산 같으면
  절을 잘게 나눈 쪽이 낫다(2절×4건 vs 4절×2건 둘 다 8건인데, 절 적은 쪽이
  편중↑·근거↓). ②예산(깊이) 늘리면 읽기량·호출·중복률은 확실히 오르지만
  근거율이 오른다는 보장은 없음.
- **선택지 넷**과 강의가 고른 것: ①2절×4건(좁고 깊게, 절 범위 너무 넓어짐)
  ②3절×3건(균형이지만 배경·전개·결과라는 형식 단위로 갈라져 요약체가 됨)
  ③4절×2건(값 대비 최고지만 만회 기회 없음 — 배정 빗나가면 그 절 그대로
  망함) ④4절×3건(**선택됨** — 절 좁아 근거 붙이기 쉬움+1건 여유로 조사관이
  스스로 만회 가능, 장문 보고서용 자료량 확보. 가장 비쌈).
- **④를 고른 진짜 근거**: "근거율 최고"가 아님(예측②대로면 ③·④ 근거율은
  구별 안 됨) — ④가 사는 건 읽은 문서 수·분량과 배정 실패 시 만회 여유.
  짧고 정확한 답이 목표면 ③이 정답, 장문 보고서가 목표라 ④. 중복률 약점은
  7강의 "남의 구역" 장치를 전제로 감당 가능하다 본 것 — 그 장치 없으면
  ④가 ③보다 나쁜 선택이 됨.
- **검증 신호 넷**(14강에서 실측 예정): 절당 실제 읽기 수(예산 안 쓰고
  멈추면 깊이 늘려도 무효) · 절당 글자 수(목표 미달이면 깊이 부족) · 최다
  문서 편중(절 적을수록 뜀, 예측①의 신호) · 중복률(깊이 늘리면 먼저
  나빠짐). 틀렸을 때 증상: 보고서 길어져 진전처럼 보이지만 같은 자료를
  여러 절이 돌려 쓰는 것뿐 — 편중·중복률을 같이 봐야 드러남.
- **퀴즈 없음**: 이 강엔 객관식/실습 셀이 없음. 예측만 세우고 검증은
  14강으로 명시적으로 미뤄짐.

### 7강. ② 배치 노드 — 팬아웃을 열고 구역을 나눈다

- **채우는 것**: 팬아웃 자체(Send 리스트 돌려주기)는 2강 뼈대에 이미 있음.
  이번에 채우는 건 "각 조사관에게 무엇을 들려 보낼 것인가"— 그리고 6강의
  약점(중복률)을 막는 장치.
- **피하기 목록**: 조사관들은 서로 못 봄(동시 실행). 코디네이터는 누가
  어디서 시작하는지 앎 — A 보낼 때 "B·C·D는 이 문서들 맡았으니 그쪽 말고"
  일러줌. 재위임 바퀴(2바퀴+)에서는 더 강해짐 — 1바퀴 끝나면 누가 뭘
  실제로 읽었는지까지 알아서, 이미 읽힌 문서 전부를 피하라고 줌.
- **코드 네 군데**: `return [Send("researcher", {...}) for i in idxs]` —
  리스트 길이가 인원. `idxs`=`plan["배치"]`, 1바퀴엔 전체 절, 2바퀴엔 빈
  칸인 절만. `남의구역 = {t["시작문서"] for j, t in enumerate(사절) if j
  != i ...}` — 나를 뺀 나머지 절의 배정, 여기에 이미 읽힌 문서 더해서
  `피하기`로 보냄. `"prior": done.get(mine, {})` — 재위임 때 지난 원고
  같이 보냄(처음부터 다시 안 읽음), 1바퀴엔 빈 딕셔너리. `if not idxs:
  return "review"` — 보낼 절 없으면 Send 리스트 대신 노드 이름 문자열
  돌려줌(같은 갈림길 함수가 팬아웃과 그냥 통과를 겸함).
- **구역 분할**: 병렬 워커에게 서로 안 겹치는 범위를 미리 알려주는 것.
  워커끼리 통신 안 하므로 출발 전 나누는 수밖에 없음 — 실측: 안 나누면
  중복률 절반 넘김(6강 41.5%와 같은 수치). 코디네이터가 아는 정보로만
  만듦(파견 시점엔 배정 정보, 재위임 시점엔 지금까지 읽힌 것까지) — 뒤쪽
  바퀴일수록 목록이 정확해짐. 후보 전부 제외되는 상황 대비해 제외 없는
  목록으로 물러나는 길도 있음.
- **구역의 한계**: 낭비(중복)는 줄이지만 품질(근거율)은 안 올림 — 오히려
  중요 문서를 한 조사관만 읽게 만들어 그 사람이 딴 데 정신 팔리면 아무도
  안 읽는 위험 생김. 실측: 중복·편중은 크게 줄었는데 근거율은 거의
  그대로(15강에서 숫자 확인 예정).
- **객관식 퀴즈**(사용자가 건너뜀): "피하기 목록에 다른 조사관이 지금
  읽는 문서를 실시간 반영 가능한가?" — 정답은 3번으로 보임("불가능.
  병렬 실행 중엔 각자 자기 입력만 보고, 결과는 전원 끝난 뒤 합쳐지므로").

### 8강. 서브에이전트에게 무엇을 돌려받을까

- **문제**: 조사관이 문서 읽고 뭘 위로 올릴지가 위층(코디네이터) 할 일을
  정함. 제약: 문서 평균 1만 자 넘음, 최대 58,195자(«흥선대원군») — 원문
  그대로 올리면 코디네이터 창 터짐.
- **선택지 넷**: ①원문 그대로(정보손실 0이지만 격리가 사라져 서브에이전트
  쓸 이유 없어짐, 열두 건이면 약 10만 토큰대라 창 넘음) ②요약 몇 문장만
  (가장 가볍지만 글쓰기가 코디네이터로 몰려 앞 절만 촘촘해짐, D45
  리서처 팀 방식) ③**자기 절 원고+인용+자기신고(선택됨)** ④원고+근거
  원문 발췌(진위 확인 가능하지만 발췌가 곧 원문이라 사실상 ①로 되돌아감).
- **③을 고른 이유**: 산출물이 이미 절로 나뉘어 있어서, 절 쓸 사람=자료
  읽은 사람이면 인용이 정확해짐. 약점은 절 사이 일관성을 아무도 책임 안
  짐(조사관은 남의 절 못 봄) — ⑤종합의 편집자가 절 목록 훑으며 머리말·
  맺음말 쓰는 걸로 일부만 감당, 완전한 해결 아님(12강에서 재론).
- **컨텍스트 격리**: 비싼 원문은 하위 에이전트 안에서만 소비, 위로는
  압축 결과만. 이유는 창이 유한해서(코퍼스 223,743 토큰 vs 창
  128,000 토큰) — 격리 없으면 상한이 창 하나, 격리하면 상한이 조사관
  수만큼 곱해짐. `read_one()`이 문서 받아 요약만 돌려주고 원문은 함수
  밖 안 나감. 실측: 코디네이터가 본 글자는 팀 전체 읽은 글자의 5.0%
  (3강 수치와 동일 근거). 격리는 되돌릴 수 없어서, 요약 프롬프트에
  "관련 없으면 관련 없음이라고만 답하라" 탈출구가 중요 — 어설픈 요약보다
  빈손이 나음(빈손은 로그에 보이지만 잘못된 요약은 안 보임).
- **검증 신호 셋**(14강에서 계산): 격리율(코디네이터가 본 글자÷팀 전체
  읽은 글자, 한 자릿수 %가 정상, 30% 넘으면 무너지는 중) · 절당 인용 수
  (0곳이면 자료 없이 쓴 것) · 허위 인용(0이 아니면 안 읽은 걸 인용).
  셋 다 모델 판정 없이 코드로 셈.
- **격리율과 바퀴 수 — 대화 중 나온 미확정 질문**: 재위임 바퀴가 늘면
  격리율이 떨어지는지 물었을 때, 분자(코디네이터가 본 글자)·분모(팀
  전체 읽은 글자) 둘 다 바퀴마다 커진다는 것까지만 구조적으로 확인,
  ④점검이 빈 칸을 무슨 기준으로 판단하는지 아직 안 배워서(11강 예정)
  단정 못 함으로 남김. 9강에서 `탐색()`이 `prior.get("읽은문서")`로
  이전 바퀴 읽은 것부터 이어간다는 걸 코드로 확인해서, 분모 증가폭이
  재위임 때마다 "새 예산만큼"으로 제한된다는 실마리는 얻음(완전한 답은
  아직 아님).
- **객관식 퀴즈**(사용자가 건너뜀): "문서 세 건 다 '관련 없음'인데 절
  원고 600자 나온 이유는?" — 정답은 2번으로 보임("모델이 자료 없이
  자기 상식으로 썼다. 인용 수 0곳일 것, 그게 유일한 신호").

### 9강. ③ 조사관 — 서브에이전트가 읽고 씁니다 — 코드 실측 완료·이해 확인

- **이 노드가 다른 이유**: 앞 노드들은 한 번 호출하고 끝났는데 이 노드는
  안에 루프가 있음(배정 문서 읽기 → 링크에서 다음 후보 추리기 → 하나
  골라 또 읽기 → 예산 다하면 원고 쓰기). 노드 하나가 작은 에이전트 하나.
  동시에 네 벌 돌고, 네 벌 사이 공유되는 것 없음.
- **Monaco에서 실제 코드 꺼내 대조**(처음엔 강의 설명 텍스트만 읽고
  설명했다가, 사용자가 "코드 봤냐"고 물어서 `window.monaco.editor.
  getModels()`로 실제 코드 확인함 — 강의 산문 설명과 정확히 일치, 특히
  `researcher` 함수가 실제로 15줄이라는 강의 서술까지 맞아떨어짐):
  - **도구 둘**(실습①): `read_one(title, brief)` — 문서 하나 통째로 받아
    "6문장 이내로 간추려라, 관련 없으면 '관련 없음'만 답하라" 시킴(8강
    격리 경계 실제 구현). `후보목록(read, 피하기)` — `쓴것=read∪피하기`
    빼고 읽은 문서들의 링크(`LINKS.get(v,[])`)를 1순위 후보로,
    비면 전체에서, 그것도 비면 `피하기`까지 무시(3단 물러서기).
    `역할문장(t)`, `다음문서(t, read, 피하기)` — 후보 중 LLM이 하나
    고르되, `pick if pick in DOCS and pick not in read else None`으로
    코드가 재검증(5강 패턴과 동일 — LLM이 없는 제목 지어내도 걸러짐).
  - **본체**(실습②): `탐색(t, prior)` — `for _ in range(t["예산"])`로
    예산만큼만 돎(코드가 강제, 모델이 못 어김). 시작문서 우선 읽고
    이후는 `다음문서()`가 고름. `prior.get("읽은문서")`/`prior.get(
    "메모")`로 시작해서 재위임 때 처음부터 다시 안 읽음. `집필(t,
    notes)` — 메모만 근거로 절 씀(6문장 이상 12문장 이하, 600자 이상,
    «문서명» 인용, "자료에 없는 내용은 쓰지 마라" — 8강 본문에 없던
    새 디테일). `researcher(s)` — 위 둘 합쳐 절 원고+읽은문서+인용+
    허위인용(`[c for c in set(인용) if c not in read]`)을 담아 반환.
    `절모음` — 재위임되면 같은 절이 두 번 올라오는데 딕셔너리 키로
    마지막 것만 남김.
- **"예산만큼 반복" 결정 주체 — Q&A로 확인**: 세 층으로 나뉨. ①예산
  숫자 자체(몇 건)는 조사관도 코디네이터도 아니고 사람이 미리 박아둔
  설정값(6강 "4절×3건" 선택, 7강 `설정["절수"]`류 패턴). ②"이 숫자만큼
  반복한다"는 코드(`for range(t["예산"])`)가 강제, 모델이 못 어김.
  ③각 바퀴 "무엇을 읽을지"만 조사관(LLM) 재량. 예외: 후보 바닥나면
  조기 종료되지만 이것도 조사관의 판단이 아니라 `후보목록`이 빈 리스트
  준 결과.
- **"재료를 준비하는 보조 함수" 비유로 확인**: `후보목록`·`역할문장`은
  `ask()` 호출 전에 프롬프트에 넣을 문자열을 만들어줄 뿐, 그 자체로는
  아무것도 "선택"하지 않음 — 진짜 선택은 `ask()` 안에서 LLM이 함. 웨이터가
  메뉴판 갖다주는 것(`후보목록`)과 손님이 메뉴 보고 직접 고르는 것
  (`ask()`)은 다르다는 비유로 확인됨.
- **프런티어 안 통하는 문서**: «거문도 사건»(내부 링크 0개, 1강부터
  나온 사실)은 어느 문서를 읽든 후보에 안 뜸 — 도달 방법은 코디네이터가
  카드 보고 직접 배정하는 것뿐(4강에서 카드를 고른 값을 여기서 받음).
- **노드 안의 에이전트**: 그래프 노드 하나가 그 자체로 작은 에이전트인
  구조. 모든 반복을 바깥 그래프 엣지로 그리면 상태 관리가 감당 안 돼서,
  바깥 그래프=팀 협업/노드 안 루프=개인 작업으로 나눔. 대가: 노드 안
  루프는 LangGraph 체크포인트의 중단점·재시도 보호를 못 받음 — 세
  번째 읽기에서 API 실패하면 그 조사관 작업 전체 날아감. 실제 서비스면
  루프 안에 재시도 직접 넣어야 함.

### 10강. 누가 "부족하다"고 말하는가 — 이해 확인(깊게)

- **문제**: 2강 뼈대에 그려둔 `review → dispatch` 되돌아가는 화살표(바퀴)가
  아직 한 번도 안 탐. 이 화살표 타려면 "이 절 아직 부족하다"는 판단이
  필요 — 그 판단을 누가 내리느냐가 이 강의 결정.
- **함정**: 판단하려면 절 원고(2,800자)를 읽어야 함. 코디네이터가 읽고
  판단하면 정확하지만, 그 순간 8강에서 지킨 격리(코디네이터는 원문 안
  보고 압축 결과만 받는다는 규칙)가 깨짐.
- **선택지 넷**: ①코드 규칙(인용 수 k곳 미만=부족, 결정적·공짜·LLM
  호출 0회지만 뭐가 비었는지는 모름, 겨냥 없는 재위임이 같은 걸 또 읽게
  함) ②**조사관이 스스로 신고(선택됨)** ③코디네이터가 절 원고 읽고
  판단(전체 보는 눈 생기지만 격리 깨짐, 바퀴마다 다시 올라옴)
  ④판정 모델 따로 둠(가장 정확할 수 있지만 판정 자체가 또 하나의 못
  믿을 단계 — 이 교안은 "재현 가능한 숫자로만 실험" 원칙 때문에 채점을
  코드로만 하기로 정함, 또 다른 LLM 판단을 끼우는 걸 거부).
- **②를 고른 이유**: 뭐가 비었는지 문장으로 얻는 유일한 공짜 선택지.
  ①은 그 문장 자체를 못 줌, ③④는 비싸게 삼. ①을 완전히 버리진 않음
  — 인용 0곳 규칙은 ⑥평가 지표로 남김. 구현은 9강 `집필()`의 `충분`/
  `부족` 필드(추가 호출 없이 원고 쓰는 호출에 필드만 얹음).
- **②의 약점 — 실제 사례**: 모델이 자기 일 후하게 평가. 실측: 재위임
  일어난 절은 질문당 평균 **0.4개뿐**. 실제로 "여섯 문장 이상 열두 문장
  이하를 못 채웠다"를 부족 사유로 적은 조사관 있었음 — 근거가 아니라
  형식(글자 수 규칙)을 부족의 뜻으로 오해한 사례. "충분하다고 신고했는데
  실제로 빈" 경우는 실시간으로 못 잡고 ⑥평가의 '읽고 안 쓴 문서'·편중이
  사후에 잡음.
- **절제 실험(질문 8개)**: 루프 켜면 근거율 45.7%→51.1%, 편중
  29.2%→25.8%(둘 다 좋아짐). 대신 호출 25.2회→26.8회(소폭 증가). 루프가
  값을 하려면 두 조건 — 첫 바퀴로 다 못 봐야 하고, 둘째 바퀴가 남은 걸
  겨냥해야 함. 이 코퍼스는 34건이라 첫 바퀴에 열두 건 보면 이미 많이
  본 셈이라 루프 여지가 작음(효과가 크지 않은 이유).
- **검증 신호 셋**: 재위임된 절 수(0에 가까우면 신고 자체가 안 일어나
  루프가 있으나 마나) · 재위임 전후 절 길이·인용 변화(그대로면 새로
  읽은 게 글에 안 반영) · 2바퀴에서 새로 읽은 문서 수(0이면 후보가
  다 막힘). ③조사관 로그를 1바퀴/2바퀴로 나눠 비교하면 보임.
- **틀렸을 때 증상**: 로그는 바쁜데 결과 그대로 — 2바퀴가 1바퀴와 같은
  후보로 같은 선택 하기 때문. 지시에 '무엇이 비었는지'가 안 들어가면
  반드시 이렇게 됨.
- **주관식(성찰형) 퀴즈 — 사용자와 깊은 Q&A로 확인**: "재위임 켜면
  근거율·편중 좋아지는데 호출도 는다. 이 거래를 받아들일지 판단하려면
  뭘 더 알아야 하나?" 사용자가 "무조건 켜야 하는 거 아니냐"고 역질문 →
  반론 넷으로 답함: (1) 5.4%p가 체감상 큰 건지 작은 건지 강의가 안
  알려줌 — 45.7%가 이미 충분한 수준이면 이득이 거의 없을 수 있음.
  (2) 늘어나는 건 호출 수뿐 아니라 응답 지연(한 바퀴 더 도는 시간)도
  포함 — 실시간 서비스면 이게 더 아플 수 있음. (3) 이 결과는 34건짜리
  코퍼스에 한정 — 코퍼스가 훨씬 크면 첫 바퀴로 다 못 보는 게 확실해져서
  루프 효과가 더 클 수 있음, 즉 "켜야 하나"의 답은 코퍼스 규모에 따라
  달라짐. (4) 재위임된 절 수 검증 신호가 왜 있는지 생각하면, 예산
  받고도 0건 읽는 실패 케이스가 섞여 있을 수 있음 — 평균 수치는 이런
  실패까지 포함한 값이라 "항상 좋아진다"는 아님. 결론: 방향은 맞지만
  "그 정도 이득이 이 프로젝트의 비용·지연을 감수할 값인가"는 강의 밖의
  정보(품질 기준, 서비스 요구사항, 코퍼스 규모)가 있어야 답할 수 있는
  질문 — 강사가 정답을 안 준 이유이기도 함.

### 11강. ④ 점검 노드 — 빈 칸을 찾아 다시 보냅니다 — 본문+코드 실측 완료

- **채우는 것**: 2강 뼈대에 그려둔 `review → dispatch` 되돌아가는 화살표(바퀴)를
  실제로 켜는 노드. 10강에서 "부족" 신고를 조사관 자기신고로 정했으므로,
  `review`가 할 일은 그 신고를 모아 빈 칸 목록만 만드는 것 — **LLM 호출이
  한 번도 없는 노드**. 코디네이터가 하는 일이 이 지점에선 판단이 아니라
  집계와 배차라는 것을 그대로 보여줌.
- **처리하는 것 셋**: ①재위임으로 같은 절이 두 번 올라왔을 때 마지막 것만
  세기 ②바퀴 상한을 지켜 무한 루프 막기 ③다시 보낼 때 무엇이 비었는지
  지시문에 실어 겨냥해 주기.
- **코드 세 군데**(강의 설명 그대로, Monaco에서 원문 대조 확인):
  - `latest[sec["절"]] = sec` — `sections`엔 리듀서(2강)가 붙어 있어 재위임된
    절이 두 벌 쌓이는데, 딕셔너리 키로 절 이름을 써서 마지막(최신) 원고만
    남김.
  - `if not 설정["재위임"] or wheel >= 설정["최대바퀴"]: gaps = []` — 종료
    조건이 둘. 설정으로 끄거나 바퀴를 다 썼거나, 둘 중 하나만 걸려도 멈춤
    (**이중 통제**). 모델의 "부족" 신고만으로는 못 멈춤 — 완벽을 요구받으면
    모델은 언제까지고 부족하다 말할 수 있어서, 내용 기준(빈 칸 없음)과
    예산 기준(바퀴 소진) 둘을 같이 둠. 예산 기준을 코드에서 먼저(바깥에)
    검사하고, 멈춘 이유를 `종료` 키로 상태에 남김 — 예산으로 멈춘 것과
    내용이 충분해서 멈춘 것은 완전히 다른 사건이라 로그로 구별 못 하면
    안 됨.
  - `newtoc[i]["지시"] = f"... (재위임: 지난번에 «...»를 읽었지만 {부족}. 그
    빈 칸을 겨냥해 아직 안 본 문서를 찾아라)"` — **겨냥**. 이 문장이 없으면
    2바퀴가 1바퀴와 같은 후보로 같은 선택을 함(더 해보기 2번이 정확히 이걸
    확인시키는 실험).
- **바퀴 상한이 "혹시 몰라서"가 아니라 반드시 필요한 이유**: '부족'인데
  후보 문서가 하나도 안 남은 절은 조사관이 0건을 읽고 같은 신고를 반복함 —
  두 기준(내용·예산) 중 예산 쪽이 안 걸리면 이 조합에서 무한 루프가 남.
- **더 해보기 셋**(코드 직접 실행은 미착수, 방향만 확인): ①`최대바퀴`를
  4로 올리면 근거율·호출 수가 곧 평평해짐(34건짜리 코퍼스라 볼 것이
  금방 떨어짐) ②재위임 지시에서 "(재위임: …)" 부분을 빼면 2바퀴가 1바퀴와
  거의 같은 문서를 고름 — 겨냥 없는 재위임은 예산만 태움 ③"충분" 판정을
  자기신고 대신 규칙(인용 5곳 미만이면 부족)으로 바꾸면 재위임되는 절이
  훨씬 늘어남 — 10강 선택지 ①을 직접 구현하는 실험.
- **객관식 퀴즈**(정답 2번으로 추정, 로컬 실측 케이스2가 뒷받침 — 문항
  선택은 1강·3강·4강과 같은 원칙으로 사용자 몫): "`latest[sec["절"]] = sec`
  로 절 이름을 키로 덮어쓰는 이유는?" → "`sections`에 리듀서가 붙어 있어
  재위임된 절이 두 벌 쌓이는데, 최신 원고만 써야 하므로".
- **로컬 실측**(`_drafts/step11_review_verify.py`, 강의 코드 그대로 옮겨
  LLM 없이 가상 state 4개로 검증, `PYTHONIOENCODING=utf-8 python
  _drafts/step11_review_verify.py`로 재현 가능):
  1. 4절 중 2절이 "부족" 신고 → `배치`(gaps)가 정확히 그 두 절의 인덱스,
     지시문에 부족 사유가 그대로 실림, 충분 신고한 절은 지시문 안 바뀜,
     바퀴가 1→2로 오름 — 전부 확인.
  2. 2바퀴에서 같은 절이 `sections`에 두 벌(1바퀴 부족 원고 + 2바퀴 충분
     원고) 쌓인 상황 재현 → `latest` 딕셔너리가 마지막(2바퀴, 충분) 것만
     남겨 gaps가 0으로 나옴 — 리듀서 덧붙임+키 덮어쓰기 조합이 실제로
     "최신 원고만 본다"로 이어지는 것을 실측.
  3. 바퀴=3, 최대바퀴=3인 상태에서 절 하나가 여전히 "부족"이어도 →
     `종료`가 "바퀴 소진"으로 강제 종료, `배치`는 빈 리스트 — 내용
     기준을 예산 기준이 덮어씀을 확인.
  4. `설정["재위임"]=False`로 끄면 전부 "부족"이어도 → `종료`가 "루프
     없음"으로 즉시 종합행 — 스위치 자체가 내용 판단보다 우선함을 확인.
  - 네 케이스 모두 `assert`로 통과 확인(스크립트 실행 로그로 검증됨).
- **모두연 실습 환경 실행은 못함**: "실습 시작" 확인 후 "수강 환경
  연결하고 있어요" 스피너가 2분 넘게 안 풀려 포기 — `review()`가 LLM
  호출 없는 순수 함수라는 점을 이용해 로컬로 대체함. 그래서 강의가 예고한
  "② 줄이 두 번 찍히는" 전체 그래프 실행 로그(1바퀴 전원 파견 → 2바퀴
  일부 재파견)는 아직 실측 못함 — review 노드 자체의 로직은 확인됐지만
  ②배치~⑤종합까지 이어진 전체 파이프라인의 실제 실행 로그는 남은 일.

## 주의 (gotcha)

- 모두연 실습 셀은 그 스텝이 "진행 중" 상태로 안 바뀌면 잠겨서(`진행전인
  스탭인 경우 실습을 진행할 수 없습니다`) 코드를 못 돌림 — 스텝 상단
  "진행 중 학습으로 이동" 버튼을 눌러서 풀 것
- 모두연 실습 셀은 Monaco 에디터라서 `get_page_text`/`read_page`로 코드
  내용이 안 잡힘 — `window.monaco.editor.getModels()`로 꺼낼 것
  (`page-code-extraction` 스킬 참고). 긴 셀은 `.getValue().slice(a,b)`로
  나눠 받을 것 — 한 번에 요청하면 도구 응답이 중간에서 잘림
- Windows 터미널에서 `!pip install ... # 주석`처럼 셸 줄 끝에 인라인 `#`
  주석을 달면 에러 남(`Invalid requirement: '#'`) — bash와 달리 Windows
  셸은 `#`를 주석으로 안 봄. 주석은 pip 줄 앞으로 뺄 것
- Windows 터미널에서 파이썬 스크립트를 직접 돌리면 한글·특수문자에서
  `UnicodeEncodeError: 'cp949' codec ...` 날 수 있음 —
  `PYTHONIOENCODING=utf-8` 붙여서 실행할 것. 주피터 노트북 자체(브라우저
  렌더링)는 이 문제 없음
- `jupyter.exe`는 더블클릭용이 아니라 터미널에서 `jupyter notebook`으로
  띄우는 서버 — 더블클릭하면 콘솔이 반짝하고 닫혀서 안 켜지는 것처럼 보임.
  VS Code면 `Ctrl+Shift+P` → "Jupyter: Create New Jupyter Notebook"이 더 쉬움
- VS Code에서 `Ctrl+P`로 "Jupiter"(오타)를 치면 무관한 venv 안 스텁 파일이
  열릴 수 있음(예: `site-packages/.../PyMeeus/pymeeus/Jupiter.pyi` — 행성
  목성 클래스). 파일 경로가 `venv/Lib/site-packages/...`로 시작하면 잘못
  열린 것 — 저장하지 말고 닫을 것
