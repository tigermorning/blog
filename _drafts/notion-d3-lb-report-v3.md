# 신서연 — 서비스 배포 전략 1일차: 로드밸런서로 무중단 배포 구성하기

## 한눈에 보기

- **문제**: 자동 배포를 하면 새 버전이 하루에도 여러 번 나간다. 새 버전으로 바뀌는 그 몇 초 동안 사용자가 오류를 보거나, 방금 나눈 대화가 사라질 수 있다.
- **원인**: ① server가 한 벌뿐이면 교체하는 동안 요청을 받을 곳이 없다. ② 대화와 약속을 container 메모리에만 두면, 요청이 다른 server로 가거나 container를 다시 시작할 때 보이지 않거나 사라진다.
- **해결**: server를 두 벌(blue, green) 두고 앞에 Nginx load balancer를 세워서, 설정 한 줄과 reload로 요청이 가는 방향만 바꾼다(블루그린). 대화는 server 밖에 둔다(DB).
- **실습**: 내 루틴 도장 앱 이미지로 blue, green, Nginx를 띄워 전환, 롤백, server 하나가 멈추는 실험을 하고 추가 과제 3개도 해 봤다. 결과는 「오늘의 미션」에 있다.

---

## 오늘의 주제

**서비스를 끄지 않고 새 버전으로 바꾸는 법, 그리고 그때 사용자가 하던 일이 이어지게 하는 법.**

## 오늘의 목표

- 무중단 배포가 지켜야 하는 두 조건과 availability, SPOF, 이중화, 무상태가 무엇인지 설명한다. (1, 2, 6절)
- 롤링, 블루그린, 카나리 배포의 차이와 drain, 롤백이 필요한 이유를 설명한다. (2절)
- Nginx가 reverse proxy와 load balancer로 하는 일을 설정 파일(proxy_pass, upstream, 규칙, zone)로 읽는다. (3절)
- 설정 한 줄과 reload로 블루그린 전환과 롤백을 하고, 비율(weight)을 정하는 방법을 이해한다. (4절)
- server 하나가 멈췄을 때 누가 먼저 알아채는지(헬스체크), 연결 대기 시간이 사용자에게 미치는 영향, Nginx 자신이 단일 장애점인 이유를 설명한다. (5절)
- 대화를 DB에 두면 어느 쪽으로 전환해도 이어지는 이유와, DB를 함께 쓸 때 생기는 위험을 설명한다. (6절)

## 흐름으로 이해하기

### 1. 무엇이 문제인가: 무중단 배포의 두 조건

새 버전으로 바뀌는 순간 사용자에게는 두 가지 일이 생길 수 있다. 요청이 끊기거나, 하던 일이 사라진다. 이 두 가지는 서로 다른 조건이고, 이를 가능하게 하는 것도 다르다.

▶그림: fig-1-두조건.gif◀

| 확인할 것 | 해당하는 용어 | 이를 가능하게 하는 것 |
| --- | --- | --- |
| 요청이 끊기지 않음 | 무중단 배포 (zero-downtime deployment) | load balancer, 블루그린, 헬스체크, 그레이스풀 셧다운 (2~5절) |
| 하던 일이 이어짐 | 무상태 (stateless) | 상태를 server 밖의 DB에 두기 (6절) |

- 요청이 하나도 실패하지 않았는데도 사용자가 방금 나눈 대화가 사라졌다면, 사용자에게는 서비스가 끊긴 것과 똑같다. 그래서 무중단이라고 하려면 위 표의 두 가지, 곧 “요청이 끊기지 않음”과 “하던 일이 이어짐”을 둘 다 만족해야 한다.
- 무중단의 정도는 availability로 말한다. availability는 1년 중 서비스를 쓸 수 있었던 시간의 비율이고, 낮을수록 1년 동안 서비스가 멈추는 시간이 길다(노드 2장). 아래 그림처럼 99%는 1년에 약 3.65일, 99.9%는 약 8.8시간, 99.99%는 약 53분, 99.999%는 약 5분 멈추는 수준이다.

▶그림: figA-availability.gif◀

### 2. server를 어떻게 바꿔야 끊기지 않나

server가 한 벌뿐이면 그 server를 교체하는 동안 요청을 받을 곳이 없다. 그래서 같은 일을 하는 server를 여러 벌 두고, 요청을 어디로 보낼지를 앞에서 정한다.

#### 2-1. 이중화와 단일 장애점(SPOF)

이중화는 같은 일을 하는 것을 하나 더 두는 것이다. SPOF(단일 장애점)는 그것 하나만 고장 나도 전체가 멈추는 부분이다. server가 한 대뿐이면 그 server가 SPOF이고, 두 대를 두면 한 대가 고장 나도 다른 한 대가 받는다. 이중화에는 두 가지 방식이 있다.

| 방식 | 뜻 | 평소 처리 속도 |
| --- | --- | --- |
| 액티브-스탠바이 | 한 대가 일하고 한 대는 기다리다가, 일하던 쪽이 멈추면 넘겨받는다 | 빨라지지 않는다. 기다리는 한 대는 평소에 일하지 않기 때문이다 |
| 액티브-액티브 | 두 대가 모두 요청을 받는다 | 요청을 나눠 처리하므로 같은 시간에 더 많은 요청을 처리할 수 있어 빨라질 수 있다. 다만 요청 하나가 끝나는 데 걸리는 시간이 줄어드는 것은 아니다 |

이중화의 목적은 어느 쪽이든 고장 나도 멈추지 않는 것이다. (액티브-액티브의 처리 속도는 노드에는 없고 일반적인 설명이다.)

#### 2-2. 새 버전으로 바꾸는 세 가지 방식

server가 여러 벌이면 새 버전을 올리는 방법도 달라진다. load balancer는 여러 server에 요청을 나눠 보내는 장치이고, 아래 세 방식은 모두 load balancer가 요청 보내는 곳을 바꾸는 방법이다(노드 2장).

▶그림: fig-2-배포방식.gif◀

| 방식 | 뜻 |
| --- | --- |
| 롤링 (rolling update) | server를 한 대씩 돌아가며 새 버전으로 바꾼다. 바꾸는 동안 이전 버전과 새 버전이 함께 요청을 받는다 |
| 블루그린 (blue-green) | server 묶음을 두 벌 두고, 새 쪽을 다 준비한 뒤 방향을 한 번에 바꾼다 |
| 카나리 (canary) | 새 버전에 일부 요청만 먼저 보내 보고, 괜찮으면 비율을 올린다 |

- drain(드레이닝)은 server 한 대를 뺄 때 그 server로 새 요청은 끊고 하던 요청은 끝까지 마치게 한 뒤 끄는 동작이다. 배포 방식의 이름이 아니라, 롤링처럼 server를 하나씩 빼는 방식의 한 단계로 쓰이는 부품이다(노드 3장: 빼고, 업데이트하고, 헬스체크를 통과하면 다시 넣기).
- 블루그린이나 카나리에서도 이전 server를 끌 때는 같은 「하던 요청 마무리」가 필요하다. 그레이스풀 셧다운은 끄는 server 쪽에서 하던 요청을 마친 뒤 끄는 것으로, 노드는 drain과 거의 같은 뜻으로 쓴다.
- 배포 방식을 설명하는 도식에서 “Cloud Run 기본 배포는 롤링이 아니라, 새 리비전이 준비되면 트래픽을 한꺼번에 넘기는 방식”이라는 설명을 봤지만 그림 설명일 뿐이고 내가 문서로 확인하지는 못했다. Cloud Run 문서 요약에는 요청을 “최신의 정상 리비전으로 가능한 한 빨리” 보낸다고 적혀 있다.

#### 2-3. 롤백과 blue를 끄지 않는 이유

오늘 실습에서는 blue에서 v1 프로그램이, green에서 v2 프로그램이 돈다고 보고 전환한다. 블루그린은 실제 배포 방식의 이름이고, blue와 green은 실습에서 붙인 container 이름표다(왜 하필 그 색인지는 노드에 없다).

- 롤백은 데이터를 되돌리는 것이 아니라, 어느 버전의 프로그램이 요청을 받게 할지를 이전으로 되돌리는 것이다. 되돌릴 수 있는 것은 blue를 끄지 않고 계속 돌려 두기 때문이다.
- 전환한 직후 blue를 바로 끄면 두 가지를 잃는다. blue가 처리하던 요청이 끊기고(그레이스풀 셧다운을 지키지 못함), 롤백할 곳도 사라진다.
- 이전 버전을 언제 꺼야 하는지는 노드가 오늘 정하지 않았다고 밝힌다. 구체적인 시간은 노드에 없다.
- 식당의 보수공사로 빗대면, 영업 중에 주방을 닫고 고치는 것이 아니라 옆에 새 주방(green)을 지어 두고 손님을 옮기는 것이다. 새 주방에 문제가 있으면 옛 주방(blue)으로 손님을 다시 옮기면 되니, 옛 주방은 한동안 불을 꺼서는 안 된다.

### 3. 요청이 갈 곳은 누가 정하나: Nginx

방향을 바꾸는 장치가 Nginx다. Nginx는 web server, reverse proxy, load balancer 세 역할을 하는 프로그램이고, 오늘 실습에서는 설정 파일 한 벌이 요청의 길을 정한다.

#### 3-1. 배포할 때와 요청이 올 때는 서로 다른 시간이다

이 노드의 내용을 CI/CD와 이어서 보면, 일이 일어나는 시점이 두 층으로 나뉜다.

| 시점 | 일어나는 일 | 이 보고서에서 |
| --- | --- | --- |
| 배포할 때 (코드를 push할 때마다 한 번) | CI/CD가 테스트와 빌드를 거쳐 새 버전을 올리고, 요청이 가는 방향을 새 버전 쪽으로 바꾼다 | 8절 |
| 요청이 올 때 (사용자가 쓰는 동안 계속) | Nginx 설정이 요청을 server로 넘긴다 | 3절 |

배포의 마지막 단계는 새 버전을 올린 뒤, 앞으로 오는 요청을 어느 server로 보낼지 바꾸는 일이다. 오늘 실습에서는 그 “어느 server”가 Nginx 설정 파일의 upstream 안에 적힌 server 줄이었고, 줄을 고친 뒤 reload하는 일을 사람이 했다. Cloud Run에서는 이 일을 플랫폼이 대신 한다(8절).

▶그림: fig-4-배포와요청.gif◀

#### 3-2. 설정 한 벌로 보는 요청의 길

그렇다면 요청이 올 때 그 줄은 어떻게 쓰일까? 사용자는 Nginx 주소 하나만 알고, 요청은 Nginx 설정 파일에 적힌 순서대로 길을 지난다. 아래가 오늘 실습의 설정이고, 3-3부터 3-6까지는 이 설정의 각 부분을 요청이 지나는 순서대로 설명한다.

```
listen 80                          ← 80번 포트로 요청이 들어온다
location /                         ← 모든 경로 / 의 요청을
  proxy_pass http://active_app     ← active_app 이라는 이름의 목록으로 대신 넘기고
upstream active_app { ... }        ← 그 목록 안에서
  server blue:8080; server green:8080;   ← 규칙(round robin 등)으로 한 곳을 고른다
  zone active_app 64k;             ← 고르는 순서를 worker process들이 함께 센다
```

▶그림: fig-3-Nginx길.gif◀

#### 3-3. 요청을 대신 받아 넘기는 proxy

proxy는 요청을 대신 받아 다른 곳에 넘기고, 응답도 대신 받아 돌려주는 중간 창구다. 사용자 쪽에 서면 forward proxy(나가는 요청을 대신 보냄), server 쪽에 서면 reverse proxy(들어오는 요청을 대신 받음)다. 오늘 실습에서는 `proxy_pass` 줄이 reverse proxy 동작을 지정한다.

▶그림: figP-proxy.gif◀

- blue와 green에는 `-p`로 포트를 열지 않았다. 그래서 내 컴퓨터에서 server에 직접 들어갈 수 없고, 같은 network의 Nginx만 요청을 넘길 수 있다.

#### 3-4. 넘겨받을 server의 목록, upstream

upstream은 Nginx가 요청을 넘겨받을 server들을 적어 둔 목록 블록이다. `proxy_pass http://active_app;`의 `active_app`이 이 블록의 이름이다. server가 한 줄이면 reverse proxy, 여러 줄이면 load balancer로 동작한다. 줄이 여러 개일 때 Nginx는 요청이 올 때마다 그중 한 곳을 고르는데, 두 가지를 본다. 하나는 줄 끝에 붙인 옵션이다. weight는 몫이라서 `weight=3`인 server는 기본값 1인 server보다 요청을 3배 받고, backup은 예비라서 다른 server가 모두 안 될 때만 쓴다. 다른 하나는 최근의 실패 기록이다. 어떤 server에 보낸 요청이 실패하면 Nginx는 잠시(기본 10초) 그 server를 후보에서 빼고 다른 server로 보낸다.

▶그림: figU-upstream.gif◀

| 옵션 | 뜻 | 기본값 (Nginx 문서) |
| --- | --- | --- |
| `weight=3` | 다른 server보다 3배 | 1 |
| `backup` | 다른 server가 모두 빠졌을 때만 요청을 받음 | 일반 server |
| `max_fails=1` | `fail_timeout` 안에 이 횟수만큼 실패하면 server를 뺌 | 1 |
| `fail_timeout=10s` | 실패를 세는 기간이자 server를 빼 두는 기간 | 10초 |

#### 3-5. 목록에서 한 곳을 고르는 규칙

어느 server로 보낼지는 정해 둔 규칙을 따른다(노드 3장).

| 규칙 | 보내는 방식 | 쓰는 때 |
| --- | --- | --- |
| round robin | 1번, 2번, 3번, 다시 1번처럼 순서대로 | server 성능이 비슷할 때. 가장 단순함 |
| least connections | 지금 처리 중인 요청이 가장 적은 server로 | 요청마다 처리 시간이 크게 다를 때. LLM 응답처럼 몇 초에서 수십 초 |
| weight | 정해 둔 비율대로 | 성능이 다른 server를 섞을 때, 카나리 배포 |
| IP hash | 같은 사용자는 늘 같은 server로 | server가 사용자 상태를 기억할 때 |

공항 보안 검색대로 빗대면 이렇다. 안내 직원이 load balancer이고 검색 레인이 server다. round robin은 레인에 한 명씩 차례로 보내는 것, weight는 신형 레인에 3명을 보낼 때 구형 레인에 1명을 보내는 것, least connections는 줄이 가장 짧은 레인으로 보내는 것, IP hash는 같은 승객을 늘 같은 레인으로 보내는 것이다.

- hash는 입력 값을 정해진 계산식에 넣어 일정한 범위의 값으로 바꾸는 것이고, 같은 입력은 항상 같은 결과가 나온다. IP hash는 사용자의 IP를 hash한 값으로 server를 고르므로 같은 IP는 늘 같은 server로 간다.
- IP hash는 server가 사용자 상태를 기억할 때 쓰는 임시방편이다. 상태가 server 안에 있으면 다른 server로 가는 순간 그 상태를 볼 수 없으니, 같은 사용자를 늘 같은 server에 붙여 두는 것이다. 하지만 그 server가 멈추거나 새 버전으로 바뀌면 붙어 있던 사용자들의 상태도 함께 사라지고, 한 server에 사용자가 몰려도 다른 server로 나눌 수 없다(노드 3장). 상태를 DB에 두면(6절) 어느 server로 가도 되므로 이런 장치가 필요 없다.

#### 3-6. 고르는 순서를 함께 세는 zone

round robin이나 weight로 나누려면 Nginx가 「방금 어디로 보냈으니 다음은 어디」를 기억해야 한다. 이 기억이 「다음 차례」 카운터다. Nginx는 요청을 받는 일꾼(worker process)을 여러 개 띄우는데, 이 실습의 Nginx에는 worker process가 8개 있었다. worker process는 서로 메모리를 나눠 쓰지 않아서, `zone`이 없으면 일꾼마다 자기 카운터를 따로 세고 각자 처음부터 시작한다. `zone`은 upstream 블록 안의 설정 한 줄(`zone <이름> <크기>`)이고, 이 카운터와 실패 기록을 모든 worker process가 공유하는 메모리에 두게 한다(노드 3장).

▶그림: fig10-zone.gif◀

이 차이를 직접 재 봤다. blue 3 : green 1로 설정하고 요청을 하나씩 48번 보내 응답한 쪽을 순서대로 적었다(B는 blue, G는 green, 각각 한 번씩 측정).

| 설정 | 응답 순서 | 읽는 법 |
| --- | --- | --- |
| zone 있음 | `BBGBBBGBBBGBBBG…` | blue 3번에 green 1번씩, 처음부터 규칙대로 |
| zone 없음 | `BBBBBBBBBGBBBGBBBG…` | 처음 9번이 모두 blue이고, 그 뒤에야 규칙대로 |

요청이 많아지면 비율은 비슷해진다(150건 측정에서 zone 있음 75% 대 25%, 없음 76% 대 24%). 차이는 요청을 몇 개 안 보냈을 때 같은 server로만 가는 것처럼 보이는 데서 드러난다. 이 현상의 정확한 원인(일꾼마다 카운터가 따로라는 것)은 노드 설명과 이 측정의 모양이 맞아떨어진다고 본 것이고, Nginx 내부 코드로 확인한 것은 아니다.

### 4. 방향을 바꾸는 방법과 비율 정하기

#### 4-1. 방향 바꾸기: reload

upstream의 server 줄을 `blue`에서 `green`으로 고친 뒤 `nginx -t`로 문법을 검사하고 `nginx -s reload`로 적용한다. reload는 Nginx를 다시 시작하지 않고 설정만 바꿔 끼운다.

▶그림: fig5-reload와재시작.gif◀

| | reload | 재시작 (`docker restart blue`) |
| --- | --- | --- |
| 대상 | Nginx의 설정 | container 전체 |
| 처리 중이던 요청 | 이전 worker process가 마무리하고, 새 worker process가 새 설정으로 다음 요청부터 받음 | 노드에 설명 없음 |
| 메모리 | 영향 없음 | 비워짐 (6절에서 약속이 사라짐) |

- 문법이 틀린 설정으로 reload하면 Nginx는 새 설정을 적용하지 않고 이전 설정으로 계속 동작한다(Nginx 공식 문서). 서비스는 끊기지 않지만, 요청은 계속 이전 설정의 server(예: blue)로 간다. 방향을 바꿨다고 생각했는데 실제로는 바뀌지 않은 상태가 되는 것이다. 그래서 reload 전에 `nginx -t`로 먼저 검사해서, 이 실패를 reload 전에 바로 확인한다.
- reload는 Cloud Run의 리비전과 다르다. reload는 Nginx가 설정을 다시 읽는 일이고, 리비전은 배포할 때마다 생기는 버전 기록이다.

#### 4-2. 비율은 어떻게 정하나: weight

weight는 server마다 보내는 요청의 몫이다. 값은 설정 파일의 숫자라서 운영자가 정한다. 기본값은 1이고, Nginx 문서에는 값이 숫자여야 한다는 것만 있고 정수 여부나 최소·최대값 같은 제한은 적혀 있지 않다. 아래 그림은 green이 새 버전이라고 가정했을 때 새 버전이 받는 요청의 비율이다.

▶그림: fig4-가중치.gif◀

| 가중치 (blue : green) | green이 받는 요청 | 의미 |
| --- | --- | --- |
| 3 : 1 | 25% | 노드의 실습 예시 (내 실습에서 150건 중 green 25%) |
| 9 : 1 | 10% | 카나리: 일부에게만 시험 |
| 99 : 1 | 1% | 카나리: 아주 일부 |

**비율은 보통 어떻게 정하나?**

- 정해진 목록은 없고 운영자가 정하지만, 정하는 기준이 있다.
- 기준 ① 성능이 다른 server를 섞을 때는 성능에 비례해서 정한다(노드 3장).
- 기준 ② 카나리 배포는 작게 시작해서 단계적으로 올린다. 노드는 새 버전에 1%나 10%만 먼저 보낸다고 한다. 도구마다 단계 예시는 다르다. Cloud Deploy 문서의 canary 예시는 25%, 50%, 75%이고, Argo Rollouts 문서의 예시는 10%와 20%이다. 하나로 정해진 표준은 아니고, 대체로 단계마다 지표를 확인하고 잠깐 멈춘 뒤 올린다(문서의 예시일 뿐 권고가 아니다).
- 99 : 1의 “99”와 가용성 99%의 “99”는 겹쳐 보이지만 서로 다른 말이다. 가용성은 1년 중 쓸 수 있었던 시간의 비율이고, weight는 요청을 나눠 보내는 몫이다. 다만 새 버전을 1%에만 먼저 보내면 문제가 있어도 영향받는 사용자가 적으니 배포 위험을 줄여 가용성을 지키는 데 간접적으로 도움이 된다(이 연결은 내 해석이다).

### 5. server나 Nginx가 멈추면 요청은 어떻게 되나

#### 5-1. 고장 난 server를 누가 먼저 알아채나: 헬스체크

수동 헬스체크(무료 Nginx)에서는 사용자의 요청이 먼저 실패하고, 능동 헬스체크에서는 load balancer가 먼저 알아챈다.

▶그림: fig2-헬스체크.gif◀

| | 능동 헬스체크 | 수동 헬스체크 |
| --- | --- | --- |
| 알아채는 방법 | 몇 초마다 `/health`로 먼저 물어봄 | 실제 요청이 실패한 것을 보고 앎 |
| 먼저 알아채는 쪽 | load balancer | 사용자의 요청 |
| 사용자가 겪는 실패 | 확인 주기 사이에 간 요청 정도 | 알아채는 데 쓰인 요청과 그 요청이 실패하기까지 기다린 시간 |
| 지원 | HAProxy, 클라우드 load balancer, 유료 NGINX Plus | 무료 Nginx를 포함한 대부분 |

#### 5-2. 연결 대기 시간은 짧을수록 좋은가

`proxy_connect_timeout`은 Nginx가 server에 연결되기를 기다리는 시간이다. 짧으면 고장 난 server를 빨리 포기해서 빠르지만, 너무 짧으면 정상인데 조금 느린 server까지 실패로 판정한다.

▶그림: fig3-대기시간.gif◀

- 노드 5장에서 `proxy_connect_timeout`의 기본값은 60초다. server가 아예 응답하지 않으면 그 60초가 지나야 실패로 보고 다른 server로 넘기므로, 그동안 그 server 차례의 사용자는 멈춘 화면을 본다.
- 1초로 줄이면 실패가 거의 없어지지만, green 차례였던 요청은 1초쯤 늦게 응답한다. 그래서 정상일 때 걸리는 시간보다는 넉넉하게, 그러나 60초보다는 훨씬 짧게 잡는다. 구체적인 숫자는 노드에 없다.

▶그림: figT-시간표.gif◀

#### 5-3. Nginx 한 대가 단일 장애점인 이유

SPOF의 눈으로 Nginx를 보자. 사용자는 Nginx 주소 하나만 알고 모든 요청을 그 Nginx로 보내므로, Nginx가 한 대뿐이면 Nginx가 멈출 때 뒤의 server(blue, green)가 멀쩡해도 요청이 들어가지 못한다. 그래서 Nginx 한 대가 단일 장애점이다.

▶그림: fig7-SPOF.gif◀

- 해결은 Nginx도 두 대로 두고 가상 IP 하나를 함께 쓰는 것이다. 평소에는 주 Nginx가 그 주소를 갖고 있다가, 멈추면 예비가 넘겨받는다. 사용자는 같은 주소로 접속하니 바뀐 줄 모른다. 이것이 2-1에서 본 액티브-스탠바이 이중화다.

### 6. 전환하니 대화가 사라진 이유와 해결: 무상태

#### 6-1. 상태가 container 메모리에 있었다

노드 5장에서 blue가 받을 때 “내일 아침 8시에 물 마시라고 알려 줘”를 보내면 약속이 만들어진다. 그다음 순서는 이렇다.

1. green으로 전환하면 약속이 보이지 않는다(blue 안에는 그대로 있다).
2. blue로 돌아오면 다시 보인다.
3. `docker restart blue`를 하면 메모리가 비워져 약속이 진짜로 사라진다.

▶그림: fig5-1-메모리와DB.gif◀

원인은 약속을 container의 메모리에만 두었기 때문이다. 상태는 server가 요청 사이에 기억해 둔 정보이고, container의 메모리는 프로그램의 변수와 같아서 container마다 따로 있고 다시 시작하면 비워진다. 이 노드에서 「server」는 공간을 빌려주는 컴퓨터가 아니라 프로그램이 실제로 돌고 있는 것(container)이고, 기억을 오래 맡아 두는 곳은 DB다.

- 처음에 “방향을 바꾸면 사라진다”고 이해했던 것은 정확하지 않았다. 정확히는 새 방향에서는 안 보일 뿐이고, 재시작하거나 새 버전으로 교체할 때 진짜로 사라진다.
- 무상태는 server가 대화·약속 같은 사용자 정보를 요청과 요청 사이에 자기 안(메모리)에 남겨 두지 않고 DB에 맡기는 구조다. 그래서 어느 server가 다음 요청을 받아도 같은 DB를 읽어 하던 일이 이어진다. 이렇게 상태를 자기 안에 두지 않는 server가 무상태 server다.
- 롤백이 약속을 복원해 주는 것은 아니다. 오늘 5장에서 blue로 돌아오자 약속이 다시 보인 것도 롤백이 약속을 복원해서가 아니라, blue를 끄지 않아 blue의 메모리에 약속이 그대로 있었기 때문이다. 롤백은 프로그램 버전을 되돌릴 뿐이라 server 안에 사용자 정보가 없어도 된다(2-3).
- 식당으로 빗대면, 직원이 주문을 머릿속에만 기억하면 직원을 바꾸는 순간 주문이 사라지고, 주문을 게시판(DB)에 적어 두면 누가 바뀌어도 이어진다. 노드의 “무상태여야 server를 마음대로 늘리고, 빼고, 새 버전으로 바꿀 수 있다”가 이 뜻이다.

#### 6-2. DB를 붙인 뒤 새로 생기는 위험

DB는 하나인데 server는 두 벌이라, 두 버전이 같은 DB를 함께 쓰게 된다. 한쪽 버전이 테이블 구조를 바꾸면 다른 쪽이 바로 영향을 받는다.

▶그림: fig5-2-열이름변경.gif◀

| | DB 붙이기 전 | DB 붙인 뒤 |
| --- | --- | --- |
| 기억이 있는 곳 | blue와 green이 각자의 메모리 | blue와 green이 같은 DB |
| 두 버전의 영향 | 서로 영향 없음 | 한쪽이 테이블 구조를 바꾸면 다른 쪽이 영향받음 |
| 대화 | 전환하면 안 이어짐 | 이어짐 |

식당으로 빗대면, 두 주방이 같은 주문 게시판을 쓰는데 새 주방이 게시판의 “메뉴” 칸 이름을 “음식”으로 바꾸면, 아직 일하고 있는 옛 주방은 주문을 읽지 못한다. 전환 중에는 두 버전이 함께 일하고, 롤백해도 DB는 이미 바뀐 상태라서 문제가 남는다. 그래서 DB를 바꿀 때는 두 server가 같은 버전인지 확인하는 것이 아니라, 옛 버전과 새 버전이 모두 읽을 수 있는 상태로만 바꾼다. 방법은 세 번에 나누는 것이다.

1. 새 칸 “음식”을 추가만 한다. 옛 칸 “메뉴”는 그대로라서 옛 버전은 계속 동작한다.
2. 두 칸을 함께 쓰는 새 버전을 배포한다. 전환도 롤백도 안전하다.
3. 옛 버전이 모두 내려가 더 이상 롤백할 일이 없을 때 옛 칸 “메뉴”를 지운다.

칸을 먼저 늘리고(확장) 나중에 줄이는(축소) 이 순서를 확장-축소 패턴(expand and contract)이라고 한다(일반적인 패턴 설명이고, 노드에서 확인한 것은 아니다).

- Supabase 익명 로그인은 가입 없이도 사용자마다 고유한 ID를 만들어 주는 기능이다. 이 ID를 기준으로 RLS(행 단위 접근 제한. 표의 행마다 누가 읽고 쓸 수 있는지 정해 두는 규칙)를 걸어 두면, 각 사용자는 자기 행만 읽고 쓸 수 있다. 그래서 브라우저에는 publishable key를 둔다. 이 키로는 RLS가 허용한 범위만 할 수 있어서 화면에 노출돼도 피해가 제한된다. 반면 secret key는 RLS를 건너뛰어 모든 사용자의 데이터를 읽고 쓸 수 있으므로, 브라우저에는 절대 두지 않고 server에서만 쓴다(노드 6장 설명을 풀어 쓴 것이고, Supabase 문서로 다시 확인하지는 않았다).

### 8. 내 프로젝트에서 이 일은 어디서 일어나고 있었나

#### 8-1. 배포 파이프라인의 마지막 칸

내 `deploy.yml`은 main에 push하면 위에서 아래로 자동 실행되는 다섯 칸이고, 마지막 칸 「Cloud Run 배포」 안에서 이전 버전이 새 버전으로 교체된다. 오늘 노드는 이 교체가 사용자에게 안 끊기게 하는 원리다.

▶그림: fig6-파이프라인.gif◀

- 노드 1장은 “Dockerfile로 이미지를 만들 수 있는 상태에서 시작”한다고 하고, 노드 실습은 Google Cloud 없이 내 컴퓨터의 Docker로만 한다. GitHub Actions도 Cloud Run도 실습에는 나오지 않는다.
- CI/CD 1일차에 만든 파이프라인이 “main에 합치면 자동 배포”까지였다면, 오늘은 그 마지막 칸이 사용자에게 안 끊기게 하는 원리다.

#### 8-2. Cloud Run이 대신 해 주던 일

▶그림: fig8-CloudRun대응.gif◀

- 문서에 따르면 Cloud Run은 container를 실행하는 완전 관리형 플랫폼이고, 서비스는 안정적인 주소 하나로 요청을 받으며 무상태 container 인스턴스를 쓴다. 새 리비전에 트래픽 1%만 보내 보는 점진적 롤아웃도 지원한다.
- 리비전은 배포할 때마다 생기고, container 이미지와 환경변수·메모리 제한 같은 설정으로 이루어지며, 만든 뒤에는 수정할 수 없다(설정을 바꾸면 새 리비전).
- scale to zero는 요청이 없으면 인스턴스가 0개까지 줄고 새 요청이 오면 새로 만드는 것이다. 그러면 인스턴스 메모리의 대화도 같이 사라지니 DB가 필요하다(이 연결은 내 추론이다).
- 내 기록에는 CI/CD 1일차에 일부러 nginx 설정 오류를 넣은 PR #5를 배포했을 때 리비전 00003이 시작에 실패했고, 사용자는 00002를 계속 받았으며, PR #6으로 되돌리니 00004가 떴다고 적혀 있다. 새 버전이 못 뜨는 동안 이전 버전이 받는다는 점은 오늘 배운 블루그린과 같은 모양이다. 다만 Cloud Run이 그렇게 동작하는 내부 규칙은 읽은 문서에 없어서 확인하지 못했다.

#### 8-3. 내 도장 앱은 load balancer 뒤에 있나

- 도장 앱은 `index.html` 한 파일을 내주는 FastAPI 서버이고(`app/main.py`에 `/`, `/health`, `/api/ocr`), main에 머지하면 Cloud Run에 자동 배포된다(README, deploy.yml). 앞단에 직접 만든 load balancer는 보이지 않는다.
- 이 서버는 이미 무상태다. 사용자 데이터는 브라우저의 `localStorage`에 있고 server에는 요청 사이에 남기는 정보가 없다(`index.html`). 그래서 6절의 “전환하니 약속이 사라짐”은 이 앱에서 그대로 일어나지 않고, 실습에서는 메모리에 약속을 저장하는 경로를 임시로 얹어서 재현했다.
- 1일차 Dockerfile(커밋 `cbe14b1`)의 첫 줄은 `FROM nginxinc/nginx-unprivileged:alpine`이었고, 지금 Dockerfile은 `python:3.13-slim-bookworm` 위에 FastAPI를 올린다. 컨테이너 안의 Nginx는 파일을 내주는 web server였고, 오늘 실습의 Nginx와는 다른 쓰임이다.

### 9. 실습 준비: Docker 이미지 찾기와 기본 명령

노드 4장의 `nginx:1.27-alpine`처럼 이미지 이름은 노드와 Dockerfile에 이미 있다. 직접 찾을 때는 hub.docker.com에서 `nginx`를 검색하거나 `docker search nginx`를 쓰고, Claude에게 요청해도 된다(노드에도 「코딩 에이전트에게 맡길 때」 프롬프트가 있다. 이름과 tag는 직접 확인한다).

- 이미지는 container를 실행하는 데 필요한 파일, 바이너리, 라이브러리, 설정을 담은 변경 불가(immutable) 패키지이고, Docker Hub가 기본 저장소다(Docker 문서).
- `docker run`은 문서에 「필요하면 이미지를 pull하고 container를 시작」한다고 되어 있고, 기본값(`--pull missing`)에서는 내 컴퓨터에 없을 때만 받는다. Nginx를 설치하는 것이 아니라 Nginx가 든 이미지를 받아 container로 실행하는 것이다.

| 명령 | 하는 일 |
| --- | --- |
| `docker search nginx` | Docker Hub에서 이미지 검색 (결과: `nginx` OFFICIAL [OK], STARS 21410 외 4건) |
| `docker pull nginx:1.27-alpine` | 이미지 내려받기 |
| `docker run -d --name bg-nginx -p 8080:80 nginx:1.27-alpine` | 이미지로 container 실행 |
| `docker images` | 내 컴퓨터의 이미지 목록 |
| `docker ps` | 실행 중인 container 목록 |
| `docker logs blue` | container 로그 |
| `docker exec bg-nginx nginx -t` | 실행 중인 container 안에서 명령 실행 |
| `docker stop` / `start` / `restart green` | 멈춤 / 시작 / 재시작 |
| `docker rm -f blue green` | container 삭제 |
| `docker network create bg-lab` | container끼리 이름으로 찾는 network 만들기 |

## 오늘의 미션

### 실습 환경

- 노드는 `friend-agent:local` 이미지를 쓰지만 이 컴퓨터에는 없고, 템플릿 폴더 루트에도 Dockerfile이 없었다. 그래서 내 루틴 도장 앱 이미지 `routine-stamp:local`로 같은 구성을 만들었다. 저장소의 `app/main.py`는 고치지 않았다.
- blue와 green을 구별하는 방법이 노드와 다르다. 노드는 환경변수 `K_REVISION`, `BANNER`와 `/version`을 쓰지만 이 앱에는 `/version`이 없어서, 이미 있는 환경변수 `OCR_ENABLED`(blue는 false, green은 true)를 바꾸고 `/health`의 `ocr_enabled` 값으로 응답한 쪽을 구별했다.
- 노드의 요청 확인 스크립트(`watch_requests.py`)는 `/version`만 요청하게 고정되어 있어서, 같은 방식(0.2초마다 요청, 2초 안에 답이 없으면 실패, 응답한 쪽별 집계)으로 `/health`를 요청하는 `watch_health.py`를 따로 만들어 썼다. 실습용 파일은 모두 저장소 밖 `~/bluegreen-tools`와 `~/bluegreen-lab`에 있다.
- 이 컴퓨터에는 실습 시작 전에 이미 `bg-nginx` 컨테이너가 떠 있었다(설정 폴더가 비어 있어 요청에 응답하지 못하던 상태, 누가 만들었는지는 확인하지 않았다). 지우지 않고 설정 파일만 넣어 이어서 썼다.
- Docker 29.9.2, Docker Compose v5.6.1.

### 새로 알게 된 것

- 「요청이 안 끊김」과 「하던 일이 이어짐」은 다른 검사이고, 무상태는 뒤쪽을 가능하게 하는 조건이다.
- proxy는 요청을 넘기는 동작이고, upstream은 넘겨받을 server의 목록이며, `proxy_pass`가 upstream의 이름으로 둘을 잇는다.
- 무료 Nginx는 수동 헬스체크라서 고장을 사용자가 먼저 겪는다. 대기 시간(기본 60초)이 길수록 그 비용이 커진다.
- 블루그린의 롤백이 빠른 이유는 이전 버전을 끄지 않고 남겨 두기 때문이다. 롤백은 프로그램 버전을 되돌리는 것이지 데이터를 되돌리는 것이 아니다.
- 멈춘 컨테이너는 Docker의 이름 찾기에서 빠져서, 그 이름을 upstream에 둔 채로는 Nginx 설정 검사가 실패한다.
- `zone`은 worker process들이 「다음 차례」를 함께 세게 해서, 요청이 적을 때도 규칙대로 나뉘게 한다.
- DB를 붙이는 순간 코드만이 아니라 테이블 구조를 바꾸는 순서까지 신경 써야 한다.
