앞 편에서 만든 앱은 내 노트북이 켜져 있고 개발 서버가 돌 때만 내 폰에서 움직여요. 친구에게 보내려면 앱 파일을 누가 어디서 만들고, 폰에는 어떻게 들어가며, 스토어에 올리려면 무엇을 준비해야 할까요? 이 글은 Expo의 클라우드 빌드로 앱 파일을 만들어 내 폰에 설치하는 데까지 가고, 스토어에 올리기 전에 점검할 것을 정리해요. 마지막에는 내가 만들고 싶은 앱을 직접 만들어 폰에 올려 보는 과제가 있어요. 이 글의 명령과 순서는 학습 자료를 정리한 것이고, 제가 직접 빌드까지 해 본 것은 아니에요. 제 앱에 적용해 본 결과는 «내 앱에 적용해 보기» 절에 따로 적었어요.

빌드가 필요한 이유 — 폰은 소스 코드를 그대로 받지 못해요

폰이 소스 코드 폴더를 그대로 설치하지 못하는 이유는 세 가지예요. 폰의 CPU는 사람이 쓴 코드를 바로 실행하지 못해서 기계가 실행하는 형식으로 바꾸는 컴파일1이 필요하고, 운영체제는 정해진 형식의 앱 파일만 설치하고, 개발자의 키로 만든 서명2이 없는 파일은 설치를 거부해요. 이 셋을 차례로 하는 과정이 빌드예요. 웹은 브라우저가 받은 JavaScript를 그 자리에서 실행하므로 설치할 앱 파일 자체가 없어요.

네이티브 앱은 이 셋을 플랫폼 회사가 만든 도구로 해요.

두 플랫폼은 언어도 도구도 달라서, 네이티브로 만들면 같은 앱을 두 번 만들고 두 번 빌드해요.

비유로 먼저 — 앞 편의 칠판과 교과서를 이어서

앞 편의 학교 수업 비유를 이어 가요. 아래 장면은 Expo Go(왼쪽)와 빌드한 앱(오른쪽)을 나란히 놓았어요. ①은 원고(화면 코드)를 고칠 때, ②는 학교 사무실의 기록(데이터)을 고칠 때를 눌러 보세요.

학교에는 공용 바인더가 미리 만들어져 있어요. 표지와 고리 같은 부품은 완성돼 있어서 낱장만 끼우면 되고, 노트북 책상(개발 서버)이 낱장(내 코드)을 계속 보내 줘요. 이것이 Expo Go예요. 책상이 꺼지면 낱장이 오지 않고, 바인더에 없는 특수 부품(Expo Go에 없는 네이티브 라이브러리)은 쓸 수 없어요.

다른 학생에게 줄 책은 외주 인쇄소(EAS)가 한 권으로 만들어요. 접수창구는 원고(저장소 파일)만 받고 서랍 속 메모(.env)는 받지 않아요. 낱장을 묶고(번들), 표지와 부품을 찍고(컴파일), 제본해서(앱 파일) 검정 도장(서명)을 찍고, 도장은 인쇄소 금고(Expo 계정)에 보관돼요. 책에는 고유 번호(ISBN)가 붙는데 이것이 패키지 이름이라 한 번 올리면 못 바꿔요. 뒤표지에는 학교 사무실 위치(EXPO_PUBLIC_ 값)가 인쇄돼 책을 가진 누구나 읽을 수 있으니, 비밀번호는 적으면 안 돼요.

제본된 책의 낱장은 굳어서 원고를 고치면 책을 새로 찍어야 하고, 그때마다 인쇄 의뢰 횟수(무료 플랜의 월 빌드 횟수)를 한 번 써요. 반면 출석과 성적은 책을 펼 때마다 학교 사무실(백엔드)에서 받아 와요. 그림의 ②를 누르면 서랍에서 서류가 두 책으로 날아가는 것이 이 일이에요. 그래서 사무실 기록을 고치는 일은 책을 다시 찍을 필요가 없어요.

핵심 한 줄: 공용 바인더는 낱장만 갈아 끼우면 바로 바뀌지만, 한 권으로 제본한 책은 찍는 순간 내용이 굳어서 고치려면 새로 찍어야 해요.

다만 비유가 끊기는 점이 있어요. 학교는 새 교과서를 한꺼번에 나눠 줄 수 있지만 앱은 사용자가 직접 업데이트해야 하고, 인쇄소는 책만 만들 뿐 학생에게 나눠 주는 제출과 심사는 스토어에서 따로 거쳐요.

전체 흐름 — 코드가 앱 파일이 되기까지

Expo 앱은 내 코드(TypeScript)와 화면·카메라 같은 기기 기능을 맡는 네이티브 부분으로 나뉘어요. 내 코드는 JavaScript로 실행되므로 컴파일하지 않고 Metro가 번들 하나로 묶기만 하고, 컴파일이 필요한 건 네이티브 부분뿐이에요.

개발할 때 쓰는 Expo Go는 자주 쓰는 네이티브 부분을 Expo 팀이 미리 컴파일·서명해 스토어에 올려 둔 앱이에요. 그래서 노트북은 번들만 보내면 되고, 컴파일도 서명도 없으니 코드를 저장하면 몇 초 안에 화면이 바뀌어요. 대신 Expo Go에 없는 네이티브 라이브러리는 못 쓰고, 앱 이름과 아이콘도 Expo Go의 것이고, 개발 서버가 꺼지면 앱도 멈춰요.

EAS 서버가 받는 것은 저장소에 있는 파일뿐이라, 커밋하지 않은 .env의 값은 빌드에 들어가지 않아요. 빌드가 실패하면 빌드 로그에서 어느 단계에서 멈췄는지부터 봐요. 패키지 설치에서 멈췄다면 package.json의 버전 충돌을, 네이티브 컴파일에서 멈췄다면 네이티브 라이브러리나 app.json 설정을 먼저 의심해요.

버전 번호 두 개와 업데이트

앱 파일에는 번호가 둘 붙어요. 사용자에게 보이는 버전(app.json의 version, 예: 1.0.0)과, 스토어가 파일을 구분하는 빌드 번호(안드로이드 versionCode, iOS buildNumber)예요. 스토어는 이미 올린 빌드 번호와 같거나 작은 파일을 받지 않으니, 올릴 때마다 빌드 번호가 커져야 해요.

바꾼 것Expo Go개발용 빌드preview 빌드(설치한 앱)
화면·문구·동작(JavaScript)저장하면 반영저장하면 반영다시 빌드

웹은 배포하면 모든 사용자가 새 버전을 쓰지만 앱은 사용자가 업데이트해야 바뀌어요. 그래서 앱을 내놓은 뒤에는 옛 화면이 새 백엔드를 부르는 상황을 늘 생각하고, 앱이 쓰는 API의 응답 모양은 옛 앱이 못 읽게 함부로 바꾸지 않아요.

빌드 프로필과 설정값 — eas.json, 서명 키, 패키지 이름

어떤 앱 파일을 어떻게 만들지는 저장소의 eas.json에 프로필3로 적어요. 모바일 템플릿에는 둘이 있어요.

프로필만드는 파일쓰는 곳
previewAndroid APK, 내부 배포(internal distribution)설치 링크로 내 폰이나 팀원 폰에 바로 설치
productionAndroid AAB, iOS 스토어용 파일. 빌드할 때마다 빌드 번호를 자동으로 올림스토어에 제출

서명 키. 스토어는 처음 올린 앱 파일의 서명 키를 기억해 두고, 그 뒤에는 같은 키로 서명한 파일만 같은 앱의 새 버전으로 받아요. 키를 잃어버리면 업데이트를 못 하고, 남에게 넘어가면 누가 내 앱인 척 올릴 수 있어서 시크릿처럼 다뤄야 해요. EAS는 처음 빌드할 때 키를 만들어 Expo 계정에 보관하고 빌드마다 꺼내 써요. 그래서 키 파일이 내 노트북이나 저장소에 생기지 않고, 템플릿의 .gitignore에도 키 파일 형식(*.jks, *.p12, *.p8)을 막아 뒀어요.

빌드에 들어가는 설정값. 개발할 때는 .env의 EXPO_PUBLIC_API_URL(백엔드 주소)을 개발 서버가 읽어 앱에 넣어 줘요. 그런데 .env는 커밋하지 않는 파일이라 빌드할 때 클라우드로 올라가지 않아요. 그래서 빌드에 쓸 값은 eas.json 프로필의 env에 따로 적어요. 빠뜨리면 빌드는 성공하는데 설치한 앱에서 «백엔드 주소가 비어 있습니다»가 떠요. EXPO_PUBLIC_ 값은 앱 파일 안에 그대로 들어가므로 공개돼도 되는 값(백엔드 주소)만 넣고, LLM API 키나 Supabase secret key는 넣지 않아요. 템플릿은 Supabase 주소와 publishable key를 백엔드의 /api/config에서 받아 오게 만들어 뒀어요.

앱 이름과 패키지 이름. app.json의 name은 홈 화면에 보이는 이름이고, android.package와 ios.bundleIdentifier는 스토어와 폰이 앱을 구분하는 이름이에요. 보통 kr.회사이름.앱이름처럼 도메인을 뒤집은 모양으로 지어요. 같은 패키지 이름의 앱은 한 폰에 하나만 설치되고, 스토어에 한 번 올린 패키지 이름은 바꿀 수 없어요(바꾸면 완전히 다른 앱이 돼요). 템플릿의 com.example.harufriend를 그대로 두면 같은 이름으로 만든 다른 사람의 앱과 부딪혀요.

첫 빌드 — 내 Android 폰에 설치하기

실습은 Android 폰 기준이에요. 아이폰은 스토어 밖에서 앱을 설치하는 길이 막혀 있어서(유료 애플 개발자 계정에 그 기기를 미리 등록해야 해요), 아이폰만 있다면 Expo Go로 확인하고 빌드한 앱은 Android 폰을 가진 사람과 짝을 지어 짝의 폰에 설치해 봐요. 먼저 상태를 확인해요. Node.js(이 글의 템플릿은 20 이상으로 안내했고, 앞 편의 SDK 58은 22.13 이상을 요구해요), 템플릿으로 만든 내 저장소와 설치된 패키지, .env의 백엔드 주소, Expo Go에서 도는 앱, 무료 Expo 계정이 있어야 해요.

실행: 로컬 터미널 — 모바일 저장소 폴더에서

node -v
npm -v
npx expo-doctor

빌드하기 전에 세 가지를 정해 파일에 적어요. 앱 이름(예: 하루친구 지수), 다른 사람과 겹치지 않는 패키지 이름(예: kr.study.harufriend.jisu, 영문 소문자·숫자·점만), 빌드에 넣을 백엔드 주소예요.

  1. app.json의 name을 내 앱 이름으로 바꿔요.
  2. app.json의 android.package와 ios.bundleIdentifier를 내 패키지 이름으로 바꿔요. 두 값은 같게 둬요.
  3. eas.json의 preview와 production 프로필 env에 있는 EXPO_PUBLIC_API_URL을 내 백엔드 주소로 바꿔요(끝에 / 없이).
  4. npx expo start로 Expo Go에서 다시 열어 그대로 도는지 확인해요. app.json을 바꾼 뒤에는 개발 서버를 껐다 켜요.

코딩 에이전트에게 맡길 때는 바뀌는 줄이 이 다섯 값뿐인지 실행 전에 봐요. 패키지 이름은 에이전트가 임의로 짓지 않고 내가 정한 값이 들어갔는지 확인해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

app.json 의 name 을 [앱 이름], android.package 와 ios.bundleIdentifier 를 [패키지 이름] 으로 바꿔 줘.
eas.json 의 preview 와 production 프로필 env 의 EXPO_PUBLIC_API_URL 을 [백엔드 주소] 로 바꿔 줘.
다른 줄은 바꾸지 말고, 바꾸기 전과 후를 나란히 보여 줘.

이제 빌드해요. eas 명령은 설치하지 않고 npx eas-cli@latest로 그때그때 최신 버전을 받아 써요. login으로 내 Expo 계정에 로그인하고, build:configure로 이 저장소를 내 Expo 프로젝트로 연결해요(app.json에 프로젝트 ID가 추가돼요). 로그인은 브라우저나 터미널에서 내가 직접 하고, 비밀번호를 에이전트 대화에 붙이지 않아요.

실행: 로컬 터미널 — 모바일 저장소 폴더에서. 무료 플랜의 빌드 횟수를 한 번 써요

npx eas-cli@latest login
npx eas-cli@latest build:configure

# 클라우드에서 Android APK를 만든다. 처음이면 서명 키를 만들지 묻는다 → Yes
npx eas-cli@latest build --profile preview --platform android

빌드 명령을 승인하기 전에 프로필이 preview, 플랫폼이 android인지 봐요. 무료 플랜은 월 빌드 횟수가 정해져 있어서(2026년 10월 기준 월 30회, 낮은 우선순위 대기열) 타입 검사나 설정 검사에서 걸러질 실수로 빌드 한 번을 쓰지 않게 npx tsc --noEmit과 npx expo-doctor를 먼저 돌려요.

명령은 프로젝트를 올린 뒤 빌드 페이지 주소를 보여 줘요. 무료 플랜은 대기열이 길어 시작까지 몇 분에서 수십 분이 걸릴 수 있고, 시작한 뒤에도 10분 안팎이 걸려요. 터미널을 기다리지 않아도 서버에서 계속 진행되고, 끝나면 설치 링크와 QR 코드가 나와요. 처음 빌드에서 서명 키를 만들겠다고 답했다면 빌드 페이지의 Credentials 항목에 키가 Expo 계정에 보관된 것으로 나오고, 내 노트북에는 키 파일이 생기지 않았는지도 확인해요.

  1. 폰으로 설치 링크를 열거나 QR을 찍어 APK를 내려받아요.
  2. «출처를 알 수 없는 앱» 설치를 허용할지 물으면 이번만 허용해요. Play 프로텍트가 «인식하지 못하는 앱»이라고 경고하면 내용을 읽고 그래도 설치를 골라요. 스토어를 거치지 않은 앱이라 나오는 경고예요.
  3. 홈 화면에 내가 정한 앱 이름으로 앱이 생겼는지 보고, 노트북의 개발 서버를 끈 상태에서 앱을 열어 캐릭터를 만들고 메시지를 보내 답이 오는지 봐요.

개발 서버를 꺼도 앱이 열리고 대화가 되는 건 내 코드가 앱 파일 안에 번들로 들어 있고 앱이 직접 백엔드로 요청을 보내기 때문이에요. 처음 열면 Expo Go에서 만든 캐릭터와 대화가 안 보이는데, 설치한 앱은 Expo Go와 저장 공간이 따로라 새 게스트로 로그인하기 때문이에요(데이터가 사라진 게 아니라 다른 사용자가 된 거예요). 문구 하나를 고쳐 보면 Expo Go에서는 저장하자마자 바뀌지만 설치한 앱은 그대로예요. 반영하려면 다시 빌드해야 하고 그때마다 빌드 횟수를 하나 써요.

아이폰, 그리고 스토어에 올리는 빌드

아이폰에서 빌드한 앱을 직접 실행해 보려면 맥에 Xcode를 설치하고 아이폰을 케이블로 연결해 맥에서 빌드해 설치해요. 무료 애플 계정으로도 되지만 7일 뒤에 열리지 않아 다시 설치해야 하고 아이폰 설정에서 개발자 모드를 켜야 해요. 맥이 있는 사람만 쓸 수 있는 방법이라 아이폰 사용자는 Expo Go 확인이 기본이에요.

실행: 로컬 터미널 — 맥과 Xcode가 있고 아이폰을 케이블로 연결했을 때만(선택)

# 처음이면 아이폰에서 '이 컴퓨터를 신뢰' 를 누른다
npx expo run:ios --device

# 개발 서버 없이도 열리는 앱으로 설치할 때 (번들을 앱 안에 넣는다)
npx expo run:ios --device --configuration Release

run:ios는 기본으로 개발용 구성으로 빌드해서 설치한 앱이 노트북의 개발 서버에서 코드를 받아 와요. 노트북 없이 도는지 보려면 --configuration Release를 붙여요. 이 명령이 만드는 ios/ 폴더는 app.json으로 언제든 다시 만들 수 있으므로 커밋하지 않고 직접 고치지도 않아요.

오늘 만든 APK는 링크로 내 폰이나 팀원 폰에 설치해 보는 용도예요. 구글 플레이는 새 앱을 APK가 아니라 AAB4로만 받아요. AAB는 스토어가 받아 사용자 기기에 맞는 APK로 나눠 내려보내는 형식이라 폰에 바로 설치할 수 없어요. 그래서 스토어에 올릴 빌드는 production 프로필로 만들어요.

실행: 로컬 터미널 — 개발자 계정이 있을 때. 빌드 횟수를 써요

# Google Play에 올릴 AAB
npx eas-cli@latest build --profile production --platform android

# App Store에 올릴 iOS 빌드 (유료 Apple 개발자 계정 필요)
npx eas-cli@latest build --profile production --platform ios

production 빌드에도 프로필 env에 적은 백엔드 주소가 들어가요. 스토어에 올릴 앱이라면 staging이 아니라 운영 백엔드 주소를 넣어야 하므로, 실행 전에 프로필 이름과 이 주소를 함께 확인해요.

빌드 상태와 로그는 expo.dev에서도 보지만 코딩 에이전트에게 물어도 돼요. 에이전트는 로그인해 둔 EAS CLI의 build:list, build:view 명령으로 목록·상태·설치 링크를 조회해요. 조회는 빌드를 새로 시작하지 않아 횟수를 쓰지 않아요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

npx eas-cli@latest 로 내 Expo 계정에서 가장 최근 Android 빌드의 상태, 걸린 시간, 설치 링크를 알려 줘.
실패했다면 로그에서 실패한 단계와 원인이 되는 줄을 찾아 설명해 줘. 다시 빌드하기 전에 무엇을 고칠지 먼저 알려 주고, 빌드는 새로 시작하지 마.

스토어로 가는 길 — 테스트 단계와 출시 준비 점검

스토어에 올리려면 개발자 계정이 필요해요. 구글 플레이 계정은 등록비를 한 번 내고, 애플 계정은 해마다 회비를 내요. 계정이 있으면 앱을 만들고 production 빌드를 올린 뒤 테스트 단계를 거쳐 공개해요. 테스트 단계에 올린 앱은 저절로 공개되지 않고, 다음 단계로 넘기는 버튼을 사람이 누르고 필요한 심사를 통과해야 넘어가요.

스토어단계알아 둘 것
구글 플레이내부 테스트 → 비공개 테스트 → 프로덕션내부 테스트는 등록한 테스터(최대 100명)만 참여 링크로 받아요. 첫 파일은 Play Console 웹에서 직접 올려요. 자동 제출(EAS Submit)에는 구글 서비스 계정 키 파일(JSON)이 필요한데 유출되면 그 계정으로 무엇이든 할 수 있어 연습에서는 만들지 않아요
애플TestFlight(내부 테스터 → 외부 테스터) → App Store팀원은 내부 테스터로 바로 받고, 외부 테스터에게는 베타 심사를 거쳐요

2023년 11월 이후 만든 개인 구글 개발자 계정은 테스터 12명 이상이 14일 동안 비공개 테스트를 해야 프로덕션 출시를 신청할 수 있어서, 하루 이틀에 정식 출시까지 가기는 어려워요. 스토어에 한 번 올린 패키지 이름과 번들 ID는 바꿀 수 없고 빌드를 올린 앱은 콘솔에서 지워지지 않고 남는 경우가 많으니, 연습으로 올릴 때도 이름을 정해 두고 끝나면 테스트 트랙을 일시중지하거나 테스터를 빼서 정리해요.

스토어는 앱이 사용자 데이터를 어떻게 다루는지와 앱 안에서 무엇을 파는지를 심사하고, AI 서비스 앱은 AI가 만든 콘텐츠를 어떻게 다루는지가 더해져요. 에이전트 서비스 앱을 기준으로 출시 전에 점검할 항목은 이래요.

항목스토어가 보는 것에이전트 서비스 앱에서
개인정보처리방침어떤 데이터를 모으고 어디에 보내는지 적은 공개 주소대화·캐릭터·기억·약속을 저장하고 대화를 외부 LLM API로 보낸다는 점을 적어야 함 (아직 없음)
데이터 안전(구글)·개인정보(애플) 항목수집 데이터 종류와 제3자 전송 여부외부 LLM API로 보내는 대화도 제3자 전송에 해당
계정과 데이터 삭제앱 안에서 계정·데이터를 지울 수 있는지백엔드에는 전체 삭제 API(DELETE /api/data)가 있지만 앱 화면에는 버튼이 없음
AI 생성 콘텐츠 신고부적절한 AI 답을 사용자가 신고할 수 있는지답마다 신고 버튼이 필요함 (아직 앱에 없음)
AI임을 밝히기사람인 척하지 않는지캐릭터가 사람이라고 주장하지 않고 화면에 AI 캐릭터임을 표시
앱 안 판매디지털 상품을 앱 안에서 팔면 스토어 결제를 써야 함AI 크레딧을 앱 안에서 팔면 스토어 결제 정책이 적용됨. 결제는 웹에서 하고 앱에서는 사용만 하는 구조로 나누는 경우가 많음
연령 등급내용에 맞는 등급 설문사용자 내용과 AI 답이 섞이므로 설문에 그대로 답함

표의 «아직 없음»은 출시 전에 채울 일이에요. 스토어 정책은 자주 바뀌므로 실제로 올릴 때는 구글 플레이 정책 센터와 애플 App Review 지침의 최신 내용을 다시 확인해요. 코딩 에이전트에게 «앱이 사용자에게서 받아 어디로 보내는 데이터를 표로 정리해 줘»라고 시키면 출발점을 얻어요. 다만 백엔드에서 데이터가 어디로 가는지는 앱 코드만으로 알 수 없으니, «모른다»고 나온 칸은 백엔드 저장소를 보고 직접 채워요.

내 앱에 적용해 보기 — 루틴 도장은 빌드 전에 무엇이 비었나

저는 앞 편에서 만든 루틴 도장 앱(도장판·진동·폰 안 저장, 손글씨 메모 사진을 글자로 읽어 일정으로 넣기, 캘린더)에 이 글의 점검 항목을 적용해 봤어요. 이 앱을 EAS로 빌드하지는 않았어요. 제 폰이 iPhone이라 Android용 APK를 직접 깔 수 없고, iPhone용 빌드는 유료 애플 개발자 계정이나 맥이 있어야 해서, 오늘은 Expo Go로만 확인했어요. 아래는 설정 파일과 코드를 읽어 확인한 것이고, 앱을 새로 실행해 확인한 것은 아니에요.

점검 항목내 앱의 현재 상태빌드하려면
eas.json없어요build:configure로 만들고 preview 프로필이 Android를 APK로 만드는지 확인해요
패키지 이름app.json에 android.package와 ios.bundleIdentifier가 없어요(앱 이름 name은 있어요)내 별칭이 들어간 이름을 빌드 전에 정해 두 값을 같게 둬요
빌드에 들어갈 값글자 읽기 서버 주소(EXPO_PUBLIC_OCR_SERVER_URL) 하나를 쓰는데 .env는 저장소에 없어요빌드에 쓸 값이니 eas.json 프로필 env에 적어야 해요. 지금 서버는 내 노트북에서만 닿아서, 그대로 넣으면 다른 폰에서는 글자 읽기가 안 돼요
시크릿코드와 설정에서 키·토큰은 못 찾았어요(키워드 검색 기준이고 전수 검사는 아니에요)빌드 전에 한 번 더 검색해요
권한 문구사진첩·카메라 권한 문구가 «글자 읽기»만 말해요. 같은 권한을 칸 안 증거 사진에도 써요실제 쓰임에 맞게 app.json에서 고쳐요(고치면 다시 빌드해야 해요)

출시 점검 표에 적용해 보면 이래요. 개인정보처리방침은 사진을 외부 서버로 보내고 카메라·사진첩 권한을 쓰므로 필요한데 아직 없어요. 로그인이 없어 계정 삭제는 해당 없지만, 칸·일정·증거를 하나씩 지우는 기능은 있고 전체 초기화는 못 찾았어요. 결제·구독 코드가 없어 앱 안 판매도 해당 없어요. AI 답 신고와 AI임 표시는 글자 읽기 서버가 생성형 AI를 쓰는지에 달려 있는데, 서버는 다른 저장소라 이 앱의 코드만으로는 판단할 수 없어서 확인 못 함으로 남겼어요.

나쁜 선택 vs 좋은 선택 — 같은 인쇄 의뢰, 같은 상황

나쁜 선택좋은 선택
사무실 주소를 .env에만 적고 인쇄소에 원고를 보낸다 → 인쇄소는 커밋된 파일만 받으므로 주소가 빠진 책이 나오고, 펴 보니 «백엔드 주소가 비어 있습니다»예요. 빌드에 쓸 값은 eas.json 프로필의 env에 적는다 → 인쇄소가 받는 원고 안에 주소가 들어가 책이 처음부터 사무실에 연결돼요.
샘플 패키지 이름(com.example.harufriend)을 그대로 쓴다 → 같은 샘플을 쓴 다른 사람의 앱과 부딪히고, 한 번 올린 이름은 못 바꿔요. 내 별칭이 들어간 이름(kr.study.harufriend.jisu)을 빌드 전에 정한다 → 처음부터 내 앱으로 알아볼 수 있어요.
타입 검사도 설정 검사도 없이 곧바로 빌드를 누른다 → 걸러질 오류로 월 빌드 횟수를 쓰고 대기열에서 몇십 분을 기다려요. npx tsc --noEmit과 npx expo-doctor를 먼저 돌린다 → 빌드는 통과한 상태에서만 눌러요.

이 글에 나온 숫자 — 빌드 전에 확인할 것

앞 절들의 한도와 조건을 모은 표예요. 요금과 정책은 바뀌므로 실제로 쓰기 전에 공식 문서로 다시 확인해요.

이럴 때 의심하세요 — 빌드한 앱을 처음 열 때

이 문제들은 «Expo Go에서는 됐는데 설치한 앱에서만 안 돼요»라는 모습으로 먼저 나타나요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
설치한 앱을 열자 «백엔드 주소가 비어 있습니다»가 떠요. Expo Go에서는 잘 됐어요 eas.json의 preview 프로필 env에 있는 EXPO_PUBLIC_API_URL. 와이파이나 Expo Go 버전은 범인이 아니에요 내 백엔드 주소가 들어 있는지 봐요. 고친 뒤 다시 빌드해야 반영돼요. 빌드 프로필과 설정값 절을 보세요.
버튼 문구를 고쳤는데 Expo Go는 바로 바뀌고 설치한 앱은 그대로예요 설치한 앱 안의 번들 — 빌드한 시점의 코드가 고정돼 있어요 백엔드에서 화면을 받아 오는 게 아니므로 다시 빌드해서 새 설치 링크로 설치해요. 백엔드를 다시 배포해도 바뀌지 않아요.
같은 패키지 이름의 다른 앱이 설치돼 있다고 하거나, 올릴 이름이 이미 쓰인다고 해요 app.json의 android.package·ios.bundleIdentifier가 com.example.harufriend 그대로인지 내 별칭이 들어간 이름으로 바꾸고 두 값을 같게 둬요. 스토어에 올리기 전에만 바꿀 수 있어요.

app.json 의 name, android.package, ios.bundleIdentifier 와 eas.json 의 모든 프로필 env 값을 표로 보여 줘.
시크릿처럼 보이는 값이 있으면 표시만 해 줘. 아직 코드는 고치지 마.

직접 해보기 — 내 앱을 만들어 폰에 올리기

템플릿 앱을 빌드해 설치해 봤다면, 이번에는 내가 만들고 싶던 앱을 Expo로 새로 만들어 같은 길을 끝까지 가 봐요. 아이디어가 없다면 산책 기록, 냉장고 유통기한 메모, 영수증 가계부처럼 사진이나 위치 같은 기기 기능을 하나만 쓰는 작은 앱이 하루 안에 끝내기 좋아요. 코드는 에이전트에게 맡겨도 되지만 화면 목록과 데이터가 오는 곳은 내가 먼저 정해요.

단계할 일끝났다는 확인
0. 앱 계획아래 계획 표를 내 앱으로 채워 docs/app-plan.md에 둠표만 보여 주고 옆 사람에게 1분 안에 설명함
1. 화면 만들기npx create-expo-app@latest로 새 프로젝트를 만들고 표의 화면을 만듦Expo Go에서 모든 화면을 오가고 npx tsc --noEmit과 npx expo-doctor가 오류 없이 끝남
2. 기기 기능 하나카메라·위치·로컬 알림 중 하나를 붙임정한 때에 권한 창이 뜨고, 거부해도 앱이 멈추지 않음
3. 빌드와 설치preview 프로필로 Android 빌드노트북의 개발 서버를 끈 상태에서 설치한 앱이 Expo Go에서와 같이 돎
4. 출시 준비 점검표위 점검 표를 docs/store-readiness.md에 옮겨 내 앱 기준으로 채움모든 항목에 «있음/없음»이 적혀 있고, 빈칸 하나를 실제로 채움

빌드는 무료 플랜의 월 횟수를 쓰므로 1~2단계는 Expo Go로만 확인하고 빌드는 3단계에서 한 번에 해요.

앱이 하는 일 한 문장산책한 날의 사진과 장소를 남기고 목록으로 다시 본다
화면 목록기록 목록, 새 기록, 기록 보기
데이터가 오는 곳과 저장폰 안 저장소(@react-native-async-storage/async-storage). 서버 없음. 앱을 지우면 기록도 사라짐
기기 기능과 Expo Go 지원카메라(expo-image-picker), 위치(expo-location). 둘 다 Expo Go에서 됨

데이터를 어디에 둘지가 가장 큰 결정이에요. 폰 안에만 두면 서버가 필요 없지만 앱을 지우거나 폰을 바꾸면 데이터도 사라지고, 서버에 두면 백엔드가 있어야 해요. 하루 안에 끝내려면 화면은 세 개 이하, 데이터는 폰 안 저장이나 이미 있는 백엔드로 정하는 편이 안전해요. 기기 기능이 Expo Go에서 되는지는 각 라이브러리 문서 위쪽의 «Included in Expo Go» 표시로 확인해요. 완성한 뒤 짝에게 보여 줄 때는 «이 화면의 데이터는 어디서 오는가»와 «코드를 고치면 설치한 앱에 반영하려면 무엇을 해야 하는가»를 물어봐 달라고 해요. 보여 주기 전에는 앱 코드와 eas.json에 시크릿이 없는지, .env와 서명 키 파일이 저장소에 없는지 한 번 더 봐요.

참고로 Expo Go에서 카메라 권한 창을 확인한 뒤 빌드해 설치하면 권한 창의 앱 이름과 문구가 달라 보여요. Expo Go에서는 Expo Go의 문구가 뜨고, app.json에 적은 내 앱의 권한 설명은 빌드한 앱에서만 보이기 때문이에요. 출시 전에 이 문구를 app.json에서 정해요.

  1. 컴파일(compile) — 사람이 쓴 코드를 기계가 실행하는 형식으로 바꾸는 일이에요. ↩
  2. 서명(signing) — 개발자만 가진 키로 앱 파일에 «누가 만들었고 중간에 바뀌지 않았다»는 표시를 남기는 일이에요. ↩
  3. 프로필 — eas.json에 이름을 붙여 적어 둔 «어떤 앱 파일을 어떻게 만들지»의 설정 묶음이에요. ↩
  4. AAB(Android App Bundle) — 구글 플레이에 올리는 형식으로, 스토어가 사용자 기기에 맞는 APK로 나눠 내려보내므로 폰에 직접 설치할 수 없어요. ↩
