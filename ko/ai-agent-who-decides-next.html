반복 업무, AI에게 맡겨도 될까 — 다음 행동을 누가 정하는가 (1)

2026. 9. 1.

※ 이 글은 모두의연구소 학습 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

메일함은 줄지 않는데, AI에게 맡겨도 되는 걸까

아침에 메일함을 열면 비슷한 문의가 쌓여 있어요. 배송은 언제 오는지, 결제는 왜 실패했는지, 반품은 어디로 보내는지를 확인하고, 내용을 읽어 담당 팀에 전달한 뒤, 같은 내용을 표에 다시 옮겨요. 점심이 가까워져도 메일은 줄지 않고요. 이쯤 되면 자연스레 "이거 AI가 대신 해주면 안 될까"라는 생각이 들어요.

자동화는 늘 시간을 돌려주고 실수를 줄이겠다고 약속해왔어요. 실제로 규칙이 분명한 반복은 잘 맡길 수 있어요. 문제는 맡긴 일이 예외를 만났을 때예요. 잘못 분류된 문의가 엉뚱한 팀으로 전달될 수 있고, 멈춰야 할 작업이 계속 실행될 수도 있어요. 나중엔 결과만 남고 왜 그런 선택이 이어졌는지 찾기 어려워지고요.

그래서 먼저 정해야 할 건 "AI를 쓸지 말지"가 아니었어요. 무엇을 맡기고, 어디에서 멈추게 하며, 문제가 생기면 무엇을 확인할지를 정하는 게 먼저였어요. 그리고 이 판단은 결국 하나의 질문에서 시작하더라고요. "다음 행동을 누가 정하는가."

같은 "에이전트"라는 이름 아래, 서로 다른 통제 방식

opencode, Claude Code, Antigravity 같은 도구에 저장소를 살펴보고 수정안을 만들어 달라고 맡기는 장면을 떠올려봐요. 도구는 파일을 읽고, 명령을 실행하고, 테스트 결과를 확인한 뒤 다음 행동을 스스로 고를 수 있어요. 화면에는 최종 수정안만 보이지만, 그 사이 어떤 파일을 먼저 열었는지, 어느 명령을 택했는지, 실패 뒤 왜 다시 시도했는지는 빠르게 지나가버려요.

이 찜찜함은 도구를 잘못 쓴 탓이 아니었어요. 같은 "에이전트"라는 이름 아래 서로 다른 통제 방식이 섞여 있기 때문이에요. 다음 행동을 정하는 주체는 크게 셋으로 나뉘어요.

  • 사람이 하나씩 시킴: 사람이 다음 행동을 직접 정해요.
  • 고정 그래프가 순서를 정함: 미리 연결해 둔 그래프가 정해진 순서와 조건에 따라 움직여요.
  • 모델이 다음을 고름: 앞선 결과를 읽은 모델이 사용할 도구와 다음 경로를 스스로 골라요.

고객 문의를 분류해 담당 팀에 알리는 업무로 비교해보면 감이 와요. 사람이 메일을 읽고 기준을 적용해 알림을 보낸다면 사람의 판단이 다음 행동을 정해요. 수신·분류·담당 팀 찾기·알림 발송을 미리 연결하고 조건을 정해뒀다면 고정 그래프가 순서를 정해요. 반면 내용이 모호한 문의에서 모델이 조회 도구를 쓸지, 추가 정보를 요청할지, 후보를 다시 찾을지를 고른다면 모델이 다음 행동을 정하는 거고요.

세 경우 모두 화면에는 "담당 팀에 알림을 보냈다"는 같은 결과만 남을 수 있어요. 그런데 원인을 찾는 방식은 완전히 달라요. 사람이 골랐다면 입력과 판단 기준을 되짚으면 되고, 고정 그래프가 골랐다면 어느 조건에서 다른 경로로 갔는지 확인하면 돼요. 모델이 골랐다면 얘기가 조금 더 복잡해져요 — 제공한 도구, 관측한 결과, 반복 한도, 승인 규칙을 함께 확인해야 해요.

운전대에서 자동 조향 장치로, 다시 조수에게로

선택권이 이동하는 모습은 운전대가 손에서 자동 조향 장치로, 다시 상황을 해석하는 조수에게로 넘어가는 모습과 닮아 있어요. 목적지는 같아도 뭔가 잘못됐을 때 브레이크를 확인할 자리는 매번 달라지고요.

사람이 대화창에서 하나씩 요청하는 경우엔 조사·파일·코드·연결 도구를 자유롭게 쓸 수 있지만, 실행 경로와 권한의 경계가 어디에 표시되는지는 제품마다 달라요. 입력한 내용이 어떤 연결 도구와 외부 서비스로 전달되는지, 실행 기록을 어디까지 볼 수 있는지를 그때그때 확인해야 해요.

고정 그래프가 순서를 정하는 경우엔 여러 도구와 단계를 연결한 경로가 화면에 그대로 보여요. 트리거·노드·분기·실행 이력이 눈에 보이는 길로 남죠. 다만 그래프 가운데 모델을 하나 끼워 넣는다고 전체가 곧바로 "모델 주도"로 바뀌는 건 아니에요. 모델이 판단하는 범위와 그 앞뒤의 연결, 실행 권한을 나눠서 봐야 해요.

모델이 다음 도구를 고르는 경우엔 저장소·터미널·테스트처럼 개발 환경의 실제 도구를 다뤄요. 어느 경로가 읽기 전용인지, 변경과 외부 통신은 어디서 승인하는지, 테스트 결과가 다음 선택에 다시 반영되는지를 확인해야 하고요.

중요한 건 이 세 국면이 서로 등을 돌린 제품 목록이 아니라는 점이에요. 하나의 도구 안에서도 국면마다 선택 주체가 달라질 수 있어요. 대화창에 연결 기능이 붙을 수도 있고, 고정 그래프 한가운데 모델 판단이 들어갈 수도 있고, 코딩 에이전트에도 사람이 승인하는 절차가 함께 있을 수 있거든요.

Anthropic이 나누는 워크플로와 에이전트

Anthropic은 Building effective agents에서 코드 경로가 미리 정해진 경우를 워크플로, 모델이 과정과 도구 사용을 동적으로 이끄는 경우를 에이전트로 구분해요. 이 구분은 어느 쪽이 더 낫다는 뜻이 아니에요. 고정 경로는 검토와 재현에 유리하고, 동적 선택은 예외가 많은 업무에서 도움이 돼요. 대신 모델에 선택을 더 맡길수록 비용과 오류가 쌓일 가능성도 커지니, 도구 권한·반복 한도·사람이 멈추는 지점을 더 분명히 정해둬야 해요.

정리하면 이 세 국면을 자동화·워크플로·에이전트라는 말로 부를 수 있어요. 자동화는 규칙이 분명한 반복을 맡기고, 워크플로는 여러 단계를 사람이 설계해 연결하고, 에이전트는 판단이 필요한 곳에서 모델이 다음 행동을 골라요. 다음 글에서는 이 구분의 출발점이 되는 자동화와 워크플로의 구조를 좀 더 자세히 들여다볼게요 — "이게 규칙인지 아닌지"를 가려내는 실제 기준부터요.
