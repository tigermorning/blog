1. GitHub Pages가 뭔가요?

3편에서 GitHub에 올려둔 파일은, 링크를 눌러도 "코드가 적힌 문서"로 보일 뿐 웹페이지처럼 열리지는 않아요. 파일이 웹페이지로 보이려면 그 파일을 24시간 켜져 있는 컴퓨터(서버)에 올려두고, 누가 주소를 칠 때마다 대신 내어주는 곳이 있어야 하거든요. 이렇게 "내 파일을 맡아뒀다가 방문자에게 내어주는 일"을 호스팅(hosting)이라고 해요. 손님을 맞는 주인을 뜻하는 host에서 온 말이에요.

GitHub Pages는 그 호스팅을 GitHub이 무료로 해주는 기능이에요. 서버를 따로 빌리거나 돈을 낼 필요 없이, 저장소 안에 index.html 파일 하나만 있으면 GitHub이 그 내용을 실제 웹사이트로 인터넷에 공개해줘요. 원래 웹사이트를 하나 띄우려면 24시간 켜져 있는 컴퓨터를 빌리고, 그 컴퓨터에 파일을 옮기고, 주소와 연결하는 설정까지 따로 해야 해요. GitHub Pages는 이미 파일을 올려둔 저장소가 있다는 이유만으로 그 과정을 통째로 건너뛰게 해주는 셈이라, 서버라는 걸 한 번도 다뤄본 적 없는 저한테는 정말 큰 문턱 하나가 사라진 거였어요. 물론 공짜인 만큼 할 수 없는 것도 있어요. 회원가입 정보를 저장하거나 결제를 처리하는 것처럼 데이터베이스가 필요한 기능은 GitHub Pages만으로는 못 만들어요. 하지만 저처럼 글을 쓰고 보여주기만 하면 되는 블로그에는 이 정도로 충분하고도 남았어요.

2. 저장소 이름을 특별하게 짓기

공개해준다고 하니 다음 궁금증은 자연스럽게 "그래서 주소가 뭐가 되는데?"였어요. 이 주소는 제가 마음대로 정하는 게 아니라 저장소 이름에 따라 자동으로 결정돼요.

저장소 이름결과 주소
내깃허브아이디.github.io (정확히 이 형태)루트 주소로 바로 공개 — 예: tigermorning.github.io
그 외 이름 (예: hello-aiffel)주소 뒤에 저장소 이름이 붙음 — 예: tigermorning.github.io/hello-aiffel/

참고: 저장소 이름은 나중에 바꿀 수도 있어요. 저는 처음에 tigermorning.github.io로 만들었다가 blog로 이름을 바꿨는데, 그 순간 주소도 tigermorning.github.io/blog/로 자연스럽게 바뀌었어요. 삭제하고 새로 만든 게 아니라, GitHub 저장소 Settings에서 이름만 바꾼 것이라 커밋 기록도 그대로 유지돼요.

이 이름 규칙이 처음엔 이상하게 느껴졌는데, 이유를 알고 나니 납득이 됐어요. 아이디마다 내아이디.github.io라는 주소는 세상에 딱 하나뿐이잖아요. 그래서 GitHub은 "저장소 이름을 그 주소와 똑같이 지으면 그 계정의 대표 사이트로 쓰겠다는 뜻"으로 약속해둔 거예요. 나머지 저장소들은 그 대표 주소 아래에 방처럼 하나씩 들어가고요. 대표 자리는 계정당 하나뿐이지만, 아래 방은 얼마든지 만들 수 있는 셈이에요.

3. index.html 파일 만들기

주소가 정해졌으면, 이제 그 주소로 들어왔을 때 보여줄 내용이 있어야겠죠. 그 역할을 하는 파일이 index.html이에요. 저장소 맨 위(루트, 폴더를 열자마자 보이는 첫 층)에 이 이름의 파일이 있으면 GitHub이 그걸 홈페이지 첫 화면으로 인식해요. 이름이 정해져 있는 이유는 간단해요. 방문자가 tigermorning.github.io처럼 파일 이름 없이 주소만 쳤을 때 서버가 "그럼 뭘 보여주지?" 하고 찾는 기본 파일 이름이, 웹에서는 예전부터 index.html로 약속되어 있거든요.

🎨 바이브 코딩으로: Claude에게 "간단한 인사말이 담긴 index.html 파일을 만들어줘"라고 말하면 알아서 만들어줘요.

🔍 궁금하다면: 실제로 어떤 내용일까?

아주 기본적인 형태는 이런 모습이에요.

실행: 로컬 파일 + 브라우저 — VS Code Live Server 등

<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>내 이름</title>
</head>
<body>
  <h1>안녕하세요!</h1>
</body>
</html>

<h1> 태그 사이의 글자가 화면에 큰 제목으로 보이는 부분이에요. 이 글자만 원하는 내용으로 바꿔도 이미 나만의 홈페이지가 완성돼요.

꺾쇠괄호로 된 부분을 태그(tag)라고 하는데, 옷에 붙은 이름표처럼 글자에 "이건 큰 제목이다", "이건 문단이다" 하고 이름표를 달아주는 표시예요. 대부분 <h1>로 열고 </h1>로 닫는 짝을 이루고, 브라우저는 그 짝 사이의 글자를 이름표에 맞는 모양으로 그려줘요. 그래서 태그는 그대로 두고 사이의 글자만 바꾸면 안전해요. 참고로 <head> 안은 방문자 눈에는 안 보이는 정보(문서 제목, 문자 설정)를 적는 자리이고, 화면에 실제로 보이는 내용은 전부 <body> 안에 들어갑니다.

4. 커밋 → push → 몇 분 기다리기

파일을 만들었으면 다음은 3편에서 한 것과 똑같아요. 기록을 남기고(commit), GitHub로 올려보내면(push) 돼요. 저장소 이름을 내깃허브아이디.github.io로 지었다면 GitHub Pages를 위해 따로 해줄 일은 없어요. 저장소에 새 파일이 올라오는 그 순간이 곧 "이 내용으로 사이트를 다시 만들어라"라는 신호가 되거든요. hello-aiffel처럼 다른 이름으로 지었다면 처음 한 번만, 저장소 Settings → 왼쪽 메뉴 Pages에서 배포할 브랜치를 main으로 골라 저장해 두면 그다음부터는 똑같아요. 무료 계정은 공개(Public) 저장소에서만 Pages를 켤 수 있어요.

🎨 바이브 코딩으로: Claude에게 "이 파일 커밋하고 push해줘"라고 말하면 끝이에요.

다만 push가 끝나자마자 사이트가 뜨는 건 아니에요. GitHub이 그 신호를 받고 페이지를 만드는 데 보통 1~2분, 길면 10분까지 걸려요. 그 사이에 접속하면 404 에러가 뜰 수 있는데, 404는 "그런 주소의 파일을 못 찾았다"는 뜻으로 웹에서 오래전부터 쓰이는 오류 번호예요. 여기서는 고장이 아니라 아직 준비가 안 끝났다는 신호에 가까우니, 조금 기다렸다가 다시 새로고침(강력 새로고침: Ctrl+Shift+R)해보면 돼요. 고쳤는데도 계속 예전 화면이 보인다면 아래 글을 참고하세요.

내 사이트 주소가 정확히 뭔지, 공개가 끝났는지 헷갈릴 땐 저장소 Settings → 왼쪽 메뉴 Pages로 들어가보면 돼요. 준비가 끝났으면 그 화면 위쪽에 완성된 주소가 그대로 적혀 있어요. 저는 이 화면에 주소가 뜨는 걸 보고서야 "진짜로 인터넷에 올라갔구나" 싶었어요.

참고 글 캐시(Cache)가 뭔가요?

이럴 때 의심하세요 — push했는데 사이트가 기대와 다르게 보일 때

GitHub Pages 문제는 거의 전부 주소창에 사이트 주소를 친 순간 만나요. 그런데 화면에 보이는 건 404 하나, 예전 화면 하나뿐이라 원인이 여럿이어도 겉모습이 같아요. 그래서 파일을 다시 만지기 전에 GitHub 쪽 화면부터 열어 보는 게 순서예요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "회원가입 기능 넣어 줘", "댓글 달 수 있게 해 줘", "방문자 수 세어 줘" — 그 데이터가 어디에 저장되는지 Claude에게 물어봐요
이런 증상이 보이면먼저 열어 볼 자리확인 방법
push하자마자 사이트 주소로 들어가니 404가 떠요 파일이 아니라 저장소의 Actions 탭이에요. Pages를 만드는 실행 기록(pages build and deployment)이 맨 위에 올라와 있어요 그 줄 앞이 노란 동그라미면 아직 만드는 중이라 기다리면 돼요. 초록 체크로 바뀐 뒤 Ctrl+Shift+R로 새로고침해요. 초록인데도 404면 다음 줄로 가요
몇 분을 기다려도 계속 404예요. 또는 내가 만든 화면 대신 README 내용이 떠요 Settings → Pages 화면과 저장소 첫 화면의 파일 목록이에요. 방금 고친 글자는 대개 범인이 아니에요 Pages 화면에 완성된 주소가 없고 배포할 브랜치를 고르는 칸이 비어 있으면, 거기서 main을 골라 저장해요. 주소가 있다면 그 주소와 내가 친 주소를 맞춰 보고(저장소 이름이 아이디.github.io가 아니면 끝에 /저장소이름/이 붙어요), index.html이 폴더 안이 아니라 맨 위 층에 소문자 이름으로 있는지 봐요
고치고 push했는데 몇 분이 지나도 예전 화면이 그대로예요 먼저 GitHub 저장소 페이지에서 그 파일을 열어 봐요. 거기도 예전 내용이면 사이트가 아니라 push 문제예요 저장소에는 새 내용이 있으면 브라우저가 들고 있던 예전 파일(캐시)이에요. 시크릿 창으로 같은 주소를 열어 새 화면이 보이면 그거예요. 저장소도 예전 내용이면 3편의 이 줄을 봐요
글자 몇 개만 고쳤는데 화면에 h1> 같은 꺾쇠 글자가 그대로 보이거나, 그 아래 내용이 전부 큰 제목 글씨가 됐어요 index.html에서 방금 고친 줄 근처의 태그 짝이에요. 태그 하나의 <나 닫는 </h1>이 지워졌을 가능성이 커요 GitHub 저장소의 커밋 기록에서 방금 커밋을 누르면 지운 줄은 빨갛게, 새로 쓴 줄은 초록으로 보여요. 빨간 줄에만 있고 초록 줄에서 사라진 꺾쇠가 있으면 되살려요
AI가 넣어 준 가입·댓글 기능이 내 화면에서는 되는데, 다른 컴퓨터나 시크릿 창에서 들어가면 그 기록이 하나도 없어요 AI가 데이터를 저장하는 코드예요. localStorage가 들어간 줄이면 방문자 각자의 브라우저에만 저장돼요. server.js 같은 서버 파일이 생겼다면 GitHub Pages는 그 파일을 실행하지 않아요 Claude에게 "이 기능의 데이터는 어디에 저장돼?"라고 물어요. 여러 사람이 같은 기록을 봐야 하는 기능이면 GitHub Pages만으로는 안 되고 서버와 데이터베이스가 필요해요 (백엔드가 왜 필요한가)

마지막 줄은 에러가 안 나서 제일 늦게 알아요. 내 브라우저에서 테스트하면 늘 잘 되니까요. 그래서 이런 기능은 증상을 기다리지 말고, 부탁한 직후에 저장 위치부터 물어봐요.

홈페이지를 만든 뒤 검색에 잘 걸리게 하고 싶다면 아래 글도 함께 읽어보세요.

참고 글 블로그 검색 노출(SEO) 기초

여기까지가 Git·GitHub·GitHub Pages의 기본 흐름 전체예요. 준비물조차 없던 컴퓨터에서 시작해서, 이제는 실제로 인터넷에 공개된 내 홈페이지를 갖게 됐어요. 다음 5편에서는 조금 더 나아가서, 글을 미리 써두면 자동으로 하루 몇 개씩 예약 발행되는 시스템(GitHub Actions)을 만들어볼게요.
