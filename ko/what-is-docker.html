도커(Docker)란 무엇인가 — 이미지와 컨테이너, 상자에 뭘 담느냐

2026. 9. 8.

※ 이 글은 같이 공부하는 분들과 나눈 대화에서 출발해, 제 나름의 언어로 정리한 것입니다.

도커는 프로그램과 그 프로그램이 돌아가는 데 필요한 환경을 통째로 상자 하나에 담아, 어느 컴퓨터에서든 같은 조건으로 실행하게 해 주는 도구다.

왜 이 글을 쓰게 됐나

"도커는 주로 어디에 쓰나요?"라는 질문에 누군가 "서비스 배포요"라고 답했고, 다른 분이 이렇게 받았어요 — "주 사용처가 딱 정해져 있진 않아요. 컨테이너에 뭘 담느냐에 따라 그 컨테이너의 역할이 바뀌듯이, 컴퓨터의 컨테이너도 똑같아요."

이 말이 정확해요. 도커는 "배포 도구"가 아니라 담는 그릇이에요. 안에 웹 서버를 담으면 웹 서버가 되고, 데이터베이스를 담으면 데이터베이스가 되고, 실험용 파이썬 환경을 담으면 실험실이 돼요. 그래서 "도커로 뭘 하나요"라는 질문은 "상자로 뭘 하나요"만큼이나 답이 넓어요.

제가 이 블로그에서 도커를 여러 번 스쳐 지나갔는데 — n8n 직접 띄워보기에서 "Docker로 옮기기"를 시키고, 벤치마크 10문항 로컬 평가에서는 "Docker 없이 돌린다"를 전제로 설명했어요 — 정작 도커가 무엇인지는 한 번도 제대로 풀지 않았더라고요. 이 글이 그 자리예요.

비유 — 남의 집 부엌과 밀키트

요리사 한 명이 자기 주방에서는 늘 같은 맛을 내요. 그런데 친구 집 부엌에서 같은 요리를 하면 맛이 달라져요. 그 집엔 쓰던 간장이 없고, 팬 크기가 다르고, 불 세기도 달라요. 매번 "여기선 왜 안 되지"를 처음부터 다시 겪어요.

밀키트는 이걸 다르게 풀어요. 손질된 재료, 계량된 양념, 조리법을 한 상자에 다 담아서 보내요. 그 상자만 있으면 어느 집 부엌에서 뜯든 같은 맛이 나와요. 그 집에 간장이 있든 없든 상관없어요 — 필요한 건 상자 안에 다 들었으니까요.

밀키트에서는도커에서는
냉장고에 든 포장 그대로의 밀키트 상자 (아직 요리 아님)이미지1 — 아직 실행 안 된 정지 상태의 덩어리
상자를 뜯어 불에 올린 상태컨테이너2 — 실제로 돌고 있는 것
같은 밀키트 세 상자를 동시에 조리이미지 하나로 컨테이너를 여러 개 띄우기
상자 안의 재료·양념·조리법 전부프로그램 + 필요한 라이브러리 + 설정 파일 전부
남의 집 부엌 (간장 없음, 팬 다름)내 컴퓨터의 운영체제와 설치된 프로그램 버전
다 먹고 냄비 씻으면 그 집 부엌은 원래대로컨테이너를 지우면 내 컴퓨터엔 흔적이 안 남음

핵심 한 줄: 도커가 고정하는 건 "요리"가 아니라 부엌 조건이에요 — 무엇을 만드느냐가 아니라, 어디서 만들어도 같아지게 하는 쪽이에요.

다만 여기서 비유가 끊기는 점이 둘 있어요. 하나는 밀키트는 먹으면 없어지지만 컨테이너는 도는 동안 결과물이 쌓인다는 거예요 — 데이터베이스라면 저장된 데이터가 그 안에 생기죠. 그래서 아래에서 볼 "볼륨"이 필요해요. 다른 하나는 컨테이너가 부엌 설비를 아예 안 쓰는 건 아니라는 거예요. 불과 가스는 그 집 것을 써요 — 도커도 컴퓨터의 핵심 부분(커널3)은 빌려 씁니다. 이게 뒤에 나올 "가상 머신과의 차이"의 뿌리예요.

또 하나의 비유 — 옛날 CD 이미지와 가상 드라이브

대화에서 이런 비유도 나왔어요. 예전에 CD를 통째로 파일 하나로 떠 놓은 이미지 파일(.iso)을 가상 드라이브에 "꽂아서" 실물 CD 없이 실행하던 프로그램들이 있었죠. 그 파일은 그냥 있을 땐 아무것도 안 해요. 꽂아야 비로소 돌아가요.

도커도 똑같아요. 이미지를 내려받기만 하면 아무 일도 안 일어나요. 실행해서 컨테이너로 만들어야 그때부터 돌아가요. "도커 이미지 받았는데 왜 아무것도 안 되죠?"의 답이 여기 있어요. 다만 이 비유도 한 지점에서 끊겨요 — CD 이미지는 읽기 전용 디스크를 흉내 내는 것뿐이지만, 컨테이너 안에서는 프로그램이 실제로 실행돼요.

전체 흐름 — 이미지가 만들어져서 컨테이너로 도는 길

읽는 법: ①은 왼쪽에서 오른쪽으로 한 방향 흐름이고, 점선은 "데이터가 컨테이너 밖으로 빠져나가 저장된다"는 뜻이에요. ②는 아래가 하드웨어, 위로 갈수록 사람이 쓰는 프로그램인 층 그림이에요. 왼쪽에는 붉은 칸(게스트 OS)이 앱마다 하나씩 있고 오른쪽에는 그 층이 아예 없다는 게 이 그림의 전부예요.

그래서 도커는 무엇이 아닌가

제가 제일 헷갈렸던 부분이에요. "환경을 고정해 준다"는 도구가 이미 여러 개 있는데, 그것들과 도커가 같은 물건인 줄 알았거든요. 아니었어요 — 고정해 주는 범위가 다 달라요.

도구무엇을 고정하나도커와 뭐가 다른가
파이썬 가상환경 (venv·conda)그 프로젝트가 쓰는 파이썬 패키지 목록과 버전운영체제와 시스템 프로그램은 그대로 내 컴퓨터 것 — 다른 컴퓨터로 가면 여전히 달라짐
런타임 버전 관리자 (nvm 등), Bun 같은 실행기자바스크립트 실행기의 버전격리가 없음. 같은 운영체제 위에서 그냥 버전만 바꿔 끼우는 것
가상 머신4 (VirtualBox 등)운영체제를 통째로커널까지 따로 띄움 → 무겁고 부팅도 오래 걸림
도커프로그램 + 라이브러리 + 파일 구조 전부커널만은 내 컴퓨터 것을 빌려 씀 → 가상 머신보다 가볍고 빨리 뜸

대화에서 "알게 모르게 도커 비슷한 걸 많이 써 봤을 거예요, Bun 같은 거요"라는 말이 나왔는데, 여기서 한 번 갈라 두는 게 좋아요. Bun은 자바스크립트를 실행하는 프로그램이지 컨테이너가 아니에요. 겹치는 건 "환경을 통째로 고정한다"는 감각이지, 하는 일이 아니에요. 위 표에서 보듯 고정하는 범위가 서로 다르고, 도커만 유일하게 격리까지 해요.

실제로 어디에 쓰나

"뭘 담느냐가 역할을 정한다"는 말을 구체적인 장면으로 바꿔 보면 이래요.

상황상자에 담는 것도커를 쓰는 이유
만든 서비스를 서버에 올릴 때웹 서버 + 내 코드내 컴퓨터에서 되던 게 서버에서도 그대로 됨
데이터베이스가 필요할 때PostgreSQL 등내 컴퓨터에 직접 설치하지 않고도 씀 — 안 쓰면 지우면 끝
자동화 도구를 띄울 때n8n 같은 프로그램운영체제마다 다른 설치 과정을 건너뜀 (n8n 셀프 호스팅에서 실제로 해 본 것)
실험·테스트실험용 파이썬 환경, 벤치마크 문제망가뜨려도 컨테이너만 지우면 내 컴퓨터는 그대로
여러 사람이 같은 조건에서 채점채점 코드 + 필요한 도구 전부실행 환경 차이가 점수에 섞이지 않음 (벤치마크 로컬 평가에서 다룬 지점)

테스트·실험에 특히 유리한 이유가 마지막 두 줄이에요. 뭔가 설치했다 지웠다를 반복하다 보면 내 컴퓨터가 알 수 없는 상태로 더러워지는데, 컨테이너 안에서는 그럴 일이 없어요.

써 보기 — 명령 네 개면 감이 와요

도커를 설치했다는 전제로, 실제 명령이 어떻게 생겼는지만 보고 갈게요. 지금 따라 치지 않아도 괜찮아요 — "이미지를 받는다 / 컨테이너로 띄운다 / 뭐가 도는지 본다" 이 세 동작이 나뉜다는 것만 보면 돼요.

먼저 이미지를 받아 컨테이너로 띄우는 명령이에요. -p는 컨테이너 안의 포트5를 내 컴퓨터 쪽으로 연결하라는 뜻이에요. 이걸 안 하면 컨테이너는 잘 돌아도 브라우저로 들어갈 문이 없어요.

실행: 로컬 터미널 — 도커가 설치돼 있어야 해요

docker run -p 5678:5678 n8nio/n8n

지금 뭐가 도는지, 어떤 이미지를 갖고 있는지 확인하는 명령이에요.

실행: 로컬 터미널

docker ps
docker images

docker ps는 지금 도는 컨테이너, docker images는 내려받아 둔 이미지를 보여줘요. 둘이 다른 목록이라는 게 이미지와 컨테이너가 다른 것이라는 증거예요.

그리고 데이터를 지키려면 볼륨6을 붙여야 해요. -v가 "컨테이너 안 이 폴더는 컨테이너 밖에 저장해 달라"는 뜻이에요.

실행: 로컬 터미널

docker run -p 5678:5678 -v n8n_data:/home/node/.n8n n8nio/n8n

내 프로그램을 이미지로 만들 때는 "무엇을 담을지" 적은 목록 파일을 하나 써요. 이 파일 이름이 Dockerfile이에요.

실행: 프로젝트에 Dockerfile로 저장 — docker build 명령이 이 파일을 읽어요

FROM python:3.12
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "main.py"]

읽어 보면 밀키트 상자를 싸는 순서 그대로예요 — 어떤 바탕에서 시작할지(FROM), 어디에 풀지(WORKDIR), 뭘 넣을지(COPY), 뭘 미리 설치해 둘지(RUN), 뜯었을 때 뭘 실행할지(CMD).

나쁜 선택 vs 좋은 선택

부엌 비유를 이어서 — "데이터베이스를 도커로 띄워 며칠 작업했다".

나쁜 선택좋은 선택
볼륨 없이 docker run만으로 띄우고 며칠 데이터를 쌓았다. 정리한다고 컨테이너를 지웠다 → 안에 있던 데이터가 통째로 사라진다. 밀키트를 조리한 냄비를 통째로 버린 것과 같아요. 컨테이너는 "지우면 흔적이 안 남는다"는 게 장점인데, 그게 그대로 위험이 되는 지점이에요. 처음부터 -v로 볼륨을 붙여 데이터가 컨테이너 밖에 저장되게 했다 → 컨테이너를 지우고 새 버전 이미지로 다시 띄워도 데이터는 그대로 붙는다. 상자는 갈아도 냄비 속 내용물은 따로 그릇에 옮겨 둔 셈이에요.

초보자가 도커에서 가장 크게 다치는 자리가 여기예요. "컨테이너 안의 것은 언제든 사라질 수 있다"를 기본값으로 놓고, 남아야 하는 건 반드시 볼륨으로 빼세요.

자원이 부족할 때

같은 대화에서 이런 이야기도 나왔어요 — 책 실습을 하는데 절반 이상이 메모리 부족으로 실패해서, 모델을 점점 작은 것으로 낮추다 보니 품질이 떨어지더라는 거예요.

여기서 두 가지를 갈라 두면 좋아요.

도커 자체는 가상 머신보다 가볍지만 공짜는 아니에요. 위 그림 ②에서 층이 하나 적다는 게 "자원을 안 쓴다"는 뜻은 아니에요. 컨테이너 안에서 도는 프로그램은 결국 내 컴퓨터의 메모리와 CPU를 씁니다. 특히 윈도우·맥에서는 도커가 내부적으로 리눅스 환경을 하나 띄워 두고 쓰기 때문에, 그 몫이 추가로 나가요.

하지만 AI 실습이 메모리 부족으로 실패하는 주된 이유는 도커가 아니라 모델 크기예요. 모델이 메모리에 들어가는지를 계산하는 법은 KV 캐시와 VRAM — 내 컴퓨터에 들어갈지 계산하기에, 크기를 줄이면서 품질을 덜 잃는 방법은 양자화 — 정밀도를 깎아도 왜 멀쩡할까에 정리해 뒀어요. 그리고 "내 컴퓨터에서 돌리느냐 API로 부르느냐"를 아예 다른 축으로 놓고 보는 관점이 로컬이냐 API냐는 틀린 질문 — 세 갈래와 품질 격차예요.

정리하면 — 도커는 "환경이 달라서 안 되는 문제"를 푸는 도구지, "내 컴퓨터가 작아서 안 되는 문제"를 푸는 도구가 아니에요. 두 문제를 섞으면 엉뚱한 데서 답을 찾게 돼요.

직접 해보기

설치까지 갔다면 이 순서로 감을 잡아 보세요. 목표는 "이미지와 컨테이너가 다른 것"을 눈으로 확인하는 것이에요.

할 것: ⓐ 가벼운 이미지를 하나 받고 docker images로 목록에 뜨는지 본다. ⓑ 이때 docker ps를 쳐 본다 — 비어 있어야 정상이에요. 이미지는 받았지만 아직 아무것도 안 돌고 있으니까요. ⓒ 그 이미지를 실행하고 다시 docker ps를 친다.
확인할 것: ⓑ와 ⓒ 사이에 docker images 결과는 그대로인데 docker ps 결과만 바뀐다는 것.
한 걸음 더: 컨테이너를 지운 뒤 docker images를 다시 쳐 보세요. 이미지는 그대로 남아 있어요 — 밀키트 상자를 하나 조리해 먹었다고 냉장고의 다른 상자가 없어지지 않는 것과 같아요.

함께 읽으면 좋은 글
