비유 — 시식 담당이 되돌린다

지난 편의 그 저녁 주방이에요. 내보내기 전에 시식 담당이 맛을 봐요. 기준에 못 미치면 조리사에게 되돌리면서 무엇이 부족한지 적어 보내요. 조리사는 그 메모를 보고 고쳐요. 세 번을 넘기면 더 붙들지 않고 사장님을 불러요.

비유 속 요소원래 개념
시식 담당이 조리사에게 — "간이 약해요"라고 적어서 되돌리기⑤ 평가자 — 되돌아가는 선에 피드백을 실어야 다음 바퀴가 달라져요
세 번 넘으면 사장님 호출정상 출구 — 상한에만 맡기지 않고 그래프 안에 출구를 그려요

핵심 한 줄: 시식 담당이 정하는 건 바퀴 수뿐이에요 — 조리사가 제멋대로 새 메뉴로 바꿔 버리는 장면은 없고, 그게 바로 에이전트와의 차이예요.

이 상황엔 어떤 패턴?

"노트 초안을 LLM이 쓰고, 다른 LLM이 '용어 정의 있는가, 예시 있는가' 기준으로 채점해서 통과 못하면 피드백 주고 다시 쓰게 해야 한다. 단, 무한 반복은 막아야 한다." 가장 적합한 패턴은?

  1. 프롬프트체이닝 — 쓰기 → 채점을 한 번만 순서대로 잇는다
  2. 평가자-최적화자 — 채점 결과로 되돌아가 다시 쓰기를 반복, 횟수 상한을 둔다
  3. 라우팅 — 채점 결과 종류별로 다른 담당에게 보낸다
  4. 오케스트레이터-워커 — 채점 기준 개수만큼 워커를 부른다

문제를 쪼개면: 핵심 단서는 "통과 못하면 되돌아가 다시 쓴다" — 앞으로만 흐르는 체이닝과 다른 순환 구조예요. "무한 반복은 막아야 한다"는 말은 라운드 상한이 필요하다는 신호고요.

2번인 이유: 생성(LLM) → 평가 → 기준 못 넘으면 되돌아가 재작성, 기준을 넘거나 상한에 닿으면 정상 출구로. 평가자-최적화자의 정의 그대로예요.

다른 선택지가 아닌 이유:

  • 1(체이닝): 앞으로만 흐르고 되돌아가는 선이 없어요. 한 번 떨어지면 그걸로 끝이라 "다시 쓰게" 요구를 못 채워요.
  • 3(라우팅): 채점 결과는 "종류"가 아니라 "통과/불합격"이라는 이분 판정이고, 다른 담당한테 가는 게 아니라 같은 작성자한테 되돌아가요 — 분기가 아니라 순환이에요.
  • 4(오케스트레이터-워커): 채점 기준은 몇 개든 실행 전에 고정이에요. "기준 개수"와 "반복해서 다시 쓰기"는 다른 축인데, 이 질문은 반복 쪽이에요.

한 줄로: 평가자-최적화자 = "기준 넘을 때까지 되돌아가 고쳐 쓴다. 상한 없이는 위험."

전체 흐름

상자와 선은 제가 미리 다 그렸어요. 실행할 때 정해지는 건 바퀴 수뿐이에요.

통과할 때까지 고쳐 쓰기

앞의 넷은 데이터가 앞에서 뒤로만 흘렀어요. 이번엔 처음으로 되돌아가는 순환이 생겨요. 한 LLM 호출이 결과를 만들고, 다른 호출이 평가해서 피드백을 주고, 기준을 넘을 때까지 반복해요. 순환에는 2편에서 본 위험이 따라와요. 끝나지 않을 수 있다는 거요. 3편의 무한 반복 실험에서는 되돌아가는 동안 State가 하나도 안 바뀌어서 영원히 돌았는데, 이 패턴은 매 바퀴 초안을 고쳐 쓰니 그 점은 달라요. 대신 고쳐 써도 기준을 영영 못 넘을 수 있어서 상한은 여전히 필요해요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요 (LLM 자리는 규칙으로 흉내 냈어요)

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

MAX_ROUNDS = 3
RULES = ["용어 정의", "예시"]

class Draft(TypedDict):
    text: str
    feedback: str
    rounds: int
    passed: bool

def evaluate(state: Draft):                  # 실제로는 LLM 평가자 자리
    missing = [r for r in RULES if r not in state["text"]]
    return {"passed": not missing,
            "feedback": f"빠진 것: {missing}" if missing else "통과",
            "rounds": state["rounds"] + 1}

def optimize(state: Draft):                  # 실제로는 LLM 작성자 자리
    missing = [r for r in RULES if r not in state["text"]]
    return {"text": state["text"] + f" +{missing[0]}"}

def hand_over(state: Draft):                 # 상한에 닿으면 사람에게 넘기는 정상 출구
    return {"feedback": state["feedback"] + " (사람에게 넘김)"}

def decide(state: Draft) -> str:
    if state["passed"]:
        return "통과"
    if state["rounds"] >= MAX_ROUNDS:
        return "포기"
    return "재작성"

b = StateGraph(Draft)
b.add_node("evaluate", evaluate)
b.add_node("optimize", optimize)
b.add_node("hand_over", hand_over)
b.add_edge(START, "evaluate")
b.add_conditional_edges("evaluate", decide,
                        {"통과": END, "재작성": "optimize", "포기": "hand_over"})
b.add_edge("optimize", "evaluate")
b.add_edge("hand_over", END)
g = b.compile()

for step in g.stream({"text": "리듀서는 값을 합친다.", "rounds": 0}):
    print(step)

{'evaluate': {'passed': False, 'feedback': "빠진 것: ['용어 정의', '예시']", 'rounds': 1}}
{'optimize': {'text': '리듀서는 값을 합친다. +용어 정의'}}
{'evaluate': {'passed': False, 'feedback': "빠진 것: ['예시']", 'rounds': 2}}
{'optimize': {'text': '리듀서는 값을 합친다. +용어 정의 +예시'}}
{'evaluate': {'passed': True, 'feedback': '통과', 'rounds': 3}}
  • 반복 상한은 그래프 안에. 상한에 닿으면 GraphRecursionError로 멈추는데, 이건 예외(실행을 그 자리에서 끊는 에러)라서 그동안 고쳐 온 중간 결과가 다 날아가요(바로 아래에서 직접 확인해요). 게다가 langgraph 1.2 이후의 기본 상한은 25가 아니라 10007스텝이라(3편에서 직접 확인), 기본값만 믿으면 멈추기 전에 호출 요금부터 쌓여요. 그래서 rounds를 세다가 hand_over로 빠지는 정상 종료 경로를 두고, recursion_limit은 이중 안전망으로 남겨요.
  • stream()과 invoke() — invoke()는 끝날 때까지 기다렸다가 최종 State만 줘요. stream()은 스텝이 끝날 때마다 "어느 노드가 무엇을 바꿨는지"를 하나씩 내보내요. 루프가 몇 바퀴 돌았는지, 피드백이 어떻게 바뀌었는지는 stream()으로만 보여요. 디버깅엔 stream(), 서비스에서 결과만 필요하면 invoke()예요.
  • 비용은 곱절로 늘어요. 한 바퀴에 생성 1번 + 평가 1번이니, 3바퀴면 6번이에요. 바퀴를 늘리면 품질이 정말 오르는지 재 보고 상한을 정해요.

상한에만 맡기면 왜 결과를 못 받을까

"예외라서 결과가 날아간다"는 말이 처음엔 잘 와닿지 않았어요. 그래서 채점이 늘 불합격을 주는 최악의 경우를 두 가지 방식으로 돌려 봤어요. A는 멈추는 걸 recursion_limit에만 맡기고, B는 위 코드처럼 rounds를 세다가 3이 되면 hand_over로 빠지는 정상 출구를 둬요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import GraphRecursionError

class Draft(TypedDict):
    text: str
    rounds: int

def evaluate(state: Draft):                 # 늘 불합격을 주는 채점 (최악의 경우를 흉내)
    return {"rounds": state["rounds"] + 1}

def optimize(state: Draft):
    return {"text": state["text"] + " +고침"}

def hand_over(state: Draft):
    return {"text": state["text"] + " (사람에게 넘김)"}

def build(decide, with_exit):
    b = StateGraph(Draft)
    b.add_node("evaluate", evaluate)
    b.add_node("optimize", optimize)
    b.add_edge(START, "evaluate")
    if with_exit:
        b.add_node("hand_over", hand_over)
        b.add_conditional_edges("evaluate", decide, ["optimize", "hand_over"])
        b.add_edge("hand_over", END)
    else:
        b.add_conditional_edges("evaluate", decide, ["optimize"])
    b.add_edge("optimize", "evaluate")
    return b.compile()

# A. 멈추는 걸 recursion_limit에만 맡긴다
a = build(lambda s: "optimize", with_exit=False)
result = "아직 아무것도 안 들어옴"
try:
    result = a.invoke({"text": "초안", "rounds": 0}, {"recursion_limit": 8})
except GraphRecursionError as e:
    print("A 에러:", type(e).__name__)
print("A result:", result)

# B. rounds를 세다가 3이 되면 hand_over로 빠지는 정상 출구를 둔다
b = build(lambda s: "hand_over" if s["rounds"] >= 3 else "optimize", with_exit=True)
print("B result:", b.invoke({"text": "초안", "rounds": 0}, {"recursion_limit": 8}))

처음 보는 문법 둘만 짚을게요. lambda s: ...는 한 줄짜리 이름 없는 함수라서 여기서는 라우터 역할을 해요. try: 아래에서 에러가 나면 프로그램이 멈추는 대신 except 아래 줄로 넘어가요.

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

A 에러: GraphRecursionError
A result: 아직 아무것도 안 들어옴
B result: {'text': '초안 +고침 +고침 (사람에게 넘김)', 'rounds': 3}

핵심은 result = a.invoke(...) 한 줄이에요. =는 오른쪽 일이 끝까지 성공해야 왼쪽 result에 값을 넣어요. A는 채점과 수정이 번갈아 8번 돈 뒤 한도에 걸려, invoke가 결과를 돌려주기 전에 에러로 끝났어요. 그래서 result에는 처음에 넣어 둔 "아직 아무것도 안 들어옴"이 그대로 남았고, 네 번이나 고친 초안은 받을 길이 없어요. B는 세 번째 채점에서 hand_over로 빠져 평범하게 끝났고, 고쳐 온 초안을 그대로 받았어요.

A가 멈춘 지점도 눈여겨볼 만해요. 노드마다 실행 횟수를 따로 세어 보니 채점 4번, 수정 4번, 모두 8번 실행한 뒤 멈췄어요. 노드는 두 종류뿐인데 한도 8에서 멈췄다는 건, recursion_limit이 노드 개수가 아니라 실행된 단계 수를 센다는 뜻이에요. 한도는 invoke()에 두 번째 값으로 {"recursion_limit": 8}처럼 넘겨서 얼마든지 바꿀 수 있고요.

중요꼭 기억할 것

되돌아가는 선이 있는 그래프를 recursion_limit 하나로만 멈추게 하면 안 돼요. 한도에 닿으면 GraphRecursionError라는 예외로 끝나서, 그때까지 만든 중간 결과를 하나도 돌려받지 못해요. 그래서 반복 횟수를 State에 세다가 정해 둔 횟수에서 "사람에게 넘기기" 같은 정상 출구로 빠지게 그래프 안에 그려 두고, recursion_limit은 그 설계가 실패했을 때를 대비한 비상용으로만 남겨요.

여기서 꼭 봐야 할 장면이 있어요. 성의 없는 노트 초안을 이 루프에 넣었더니, 평가 규칙("용어 정의가 있나", "예시 코드가 있나" 등)을 채우는 쪽으로 고쳐 쓰는 동안 주제가 LangGraph 리듀서에서 자바스크립트 reduce로 옮겨 가 버렸어요. 평가자는 규칙 목록만 채우는 방향으로 글을 바꿀 뿐, 원래 무엇을 지켜야 했는지는 몰라요. 그래서 "무엇을 잃으면 안 되는가"를 체이닝 편의 게이트처럼 코드 검사로 걸어 두는 게 필요해요.

평가 기준이 흐리면 피드백이 "더 좋게 써 보세요" 수준으로 겉돌고 반복해도 안 나아져요. 규칙부터 구체적으로 적는 게 먼저예요. 그리고 평가자가 결정적일 수 있다면 그편이 훨씬 나아요. 코드를 쓰게 하고 테스트를 돌려 실패 메시지를 피드백으로 돌려주는 루프가 대표적이에요. LLM이 채점하는 방식의 장단점은 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge에서, 에이전트 여럿이 같은 모양을 만드는 경우는 네 가지 구조의 비평-수정에서 봤어요.

나쁜 선택 vs 좋은 선택 — 평가 기준을 정할 때

노트 초안을 통과할 때까지 고쳐 쓰는 같은 루프로, 평가 기준을 어떻게 적었는지 비교해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 평가 기준을 "좋은 학습 노트로 써라" 한 문장으로 뭉뚱그렸어요.

무슨 일이 생기나: 평가자가 매번 다른 이유로 퇴짜를 놓아요. 바퀴가 상한까지 다 돌아도 안 나아지고, "더 좋게 써 보세요" 수준의 뜬 피드백만 쌓여요. 게다가 규칙 목록이 없으니 "무엇을 잃으면 안 되는가"도 안 지켜져서 주제가 옆길로 새기 쉬워요.		 무엇을 했나: 기준을 RULES = ["용어 정의", "예시"]처럼 항목별로 구체적으로 적었어요. 지켜야 할 용어(예: LangGraph)가 남아 있는지도 코드 게이트로 같이 걸었어요.

무슨 일이 생기나: 피드백이 "빠진 것: ['예시']"처럼 구체적이라 다음 바퀴가 실제로 나아져요. 몇 바퀴에 통과하는지도 실행마다 비교할 수 있고, 주제가 옆길로 새면 게이트가 바로 잡아요.

정리하면 평가자-최적화자에서 물을 건 하나예요. "기준이 규칙으로 적을 만큼 구체적인가?" 그렇지 않다면 바퀴 수만 늘어날 뿐, 되돌아가는 구조 자체가 문제를 못 풉니다.

이 글에 나온 숫자

무엇의 숫자인가값알아 둘 것
평가 루프를 3바퀴로 막았을 때의 호출 수최대 6번바퀴마다 생성 1 + 평가 1이에요. 통과할 때까지 돌리면 끝을 모르니, 바퀴 수를 먼저 정하고 시작하는 쪽이 안전해요
반복을 강제로 끊는 기본 상한
recursion_limit		10007스텝
(langgraph 1.2 기준)		1.0.0은 25, 1.1.0은 10000이었어요. 저는 8로 낮춰 GraphRecursionError를 일부러 내 봤고요. 기본값에 맡기면 요금이 먼저 도착해요 (상한에만 맡기면)

내 파이프라인에 대입하면 — 비유가 안 맞는 것도 코드로는 못 걸러요

코드로 못 재는 기준이 이 블로그에도 있어요 — "그 비유가 이 편 내용에 맞는가"예요. 안 맞는 비유는 없느니만 못해요, 독자가 개념 대신 비유를 외우게 되니까요. 이건 글자 수나 링크 개수처럼 세어서는 판정이 안 나요. 그래서 다 쓴 글을 다시 읽고 통과·반려를 내는 단계를 두고, 반려면 어디가 왜 안 맞는지를 함께 본문 쓰기로 되돌려요. 이유를 안 붙이면 3편의 그 반복이 돼요.

바퀴마다 호출이 두 번씩 늘어나니 몇 바퀴까지인지가 필요하고, 그 수에 닿았을 때도 그때까지의 최선 원고를 들고 정상 출구로 나가야 해요. 예외로 끝나면 세 바퀴 돈 원고가 통째로 사라지거든요.

실제 코드에 대입하면 — 전사가 실패하면 한 번 더, 안 되면 있는 그대로

자막·타임코드 생성기의 전사 단계에 한 바퀴짜리 평가자-최적화자가 있어요. 말소리가 있는 구간은 따로 세어 두는데, 전사가 내놓은 세그먼트 수가 그 90%에 못 미치면 전사가 실패했다고 보고 한 번 더 돌려요.

제 저장소 코드 — checker/generate.py의 재시도 부분이에요(알림 문구는 줄여서 옮겼어요)

SUSPECT_RATIO = 0.9
if transcript_cache is None and speech and len(segments) < len(speech) * SUSPECT_RATIO:
    retry_segments = transcribe(video, ...)
    if len(retry_segments) > len(segments):
        segments = retry_segments
    else:
        say("다시 돌려도 나아지지 않았습니다 — 이번 결과를 그대로 씁니다. ...")

여기서 볼 게 else예요. 다시 돌려도 안 나아졌을 때 예외를 던지지 않고 그때까지의 결과를 들고 정상 출구로 나가요. 위에서 말한 상한에 닿았을 때도 최선을 들고 나가야 한다가 이 else 한 줄이에요. 여기서 예외로 끝내면 몇십 분 걸린 전사가 통째로 사라지거든요.

다만 판정하는 쪽이 모델이 아니라 개수 비교예요. 그래서 "전사가 틀렸다"는 못 잡아요 — 엉뚱한 말로 받아썼어도 개수만 맞으면 통과해요. 그게 이 편의 평가자를 LLM으로 두는 이유이고, 동시에 그렇게 바꿨을 때 판정이 매번 달라질 수 있다는 값을 치르는 자리예요.

이럴 때 의심하세요

증상이 아직 없어도, AI에게 "통과할 때까지 고쳐 쓰게 해 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
평가 루프가 한참 돌다가 GraphRecursionError로 끝나고, 그동안 고쳐 온 초안이 하나도 안 남아요. 결과를 담을 변수가 비어 있어요 되돌아가는 선을 고르는 라우터 함수예요. "통과"와 "재작성" 말고 사람에게 넘기기 같은 세 번째 return이 있는지, 바퀴 수를 세는 칸을 매 바퀴 올리는지 봐요 채점이 늘 불합격을 주게 잠깐 바꿔 stream()으로 돌려요. 바퀴 수 칸이 오르다가 정해 둔 수에서 출구 노드로 빠지면 괜찮고, 에러로 끝나면 출구가 없는 거예요 (상한에만 맡기면 왜 결과를 못 받을까)
바퀴가 돌수록 평가 규칙은 하나씩 채워지는데, 마지막 초안을 읽어 보면 원래 주제가 사라졌어요. 리듀서 설명이 자바스크립트 reduce 이야기로 옮겨 간 식이에요 stream() 출력에서 바퀴마다 바뀐 초안이에요. 평가 규칙 목록에 "채울 것"만 있고 "잃으면 안 되는 것"은 없는지도 봐요 고쳐 쓴 초안마다 주제 핵심 용어(예: LangGraph)가 남아 있는지 코드로 검사하는 게이트를 루프 안에 걸어요. 다만 이런 게이트는 글자만 봐서, 용어가 남아 있어도 설명이 틀린 건 못 잡아요 (체이닝 편의 게이트 줄)

첫 줄은 시험 삼아 넣은 초안으로는 잘 안 보여요. 몇 바퀴 안에 통과해 버리면 출구가 없어도 멀쩡히 끝나거든요. 루프를 만든 직후에 늘 불합격인 채점으로 한 번 돌려 보는 게 가장 싼 확인이에요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — LangGraph 코드가 있는 프로젝트 폴더에서

이 프로젝트에서 앞 노드로 되돌아가는 선이 있는 곳을 전부 찾아서 표로 보여 줘. 아직 코드는 고치지 마.
1. 바퀴 수를 세는 State 칸, 라우터 함수가 돌려줄 수 있는 이름 전부
2. 상한에 닿았을 때 빠지는 출구 노드가 있는지, recursion_limit 설정값
3. 평가 기준(규칙 목록이나 평가 프롬프트)에 원래 주제나 핵심 용어를 지키는지 확인하는 항목이 있는지

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 다른 편의 같은 목록은 1편 · 2편 · 3편 · 4편 · 6편 · 7편 · 8편 · 9편에 있어요.

  • 반복은 상한에만 맡기지 말고 정상 출구를 그래프 안에
  • 에이전트로 옮기는 근거는 기록으로 확인한 실패 모습
  • 패턴은 내 일의 모양에 대 보고, 가장 단순한 것부터

어떤 모양을 고를까

다섯 모양을 한 표로 정리하면 이래요.

패턴이럴 때그래프의 핵심치르는 값
① 프롬프트 체이닝단계에 순서가 있고 중간 점검이 필요할 때일렬 노드 + 코드 게이트단계 수만큼 기다리는 시간(지연 시간1)이 늘어요
② 라우팅입력 종류마다 전혀 다른 프롬프트나 모델이 필요할 때분류 노드 + 점선 조건부 엣지분류가 틀리면 뒤가 다 틀려요
③ 병렬화하위 작업이 서로 독립이고 개수를 미리 알 때실선 팬아웃 + 리듀서시간은 줄지만 호출 수만큼 요금은 그대로예요
④ 오케스트레이터-워커하위 작업의 개수와 내용이 입력마다 달라질 때계획 노드 + Send 복제계획 품질이 상한이고, 비용을 미리 알 수 없어요
⑤ 평가자-최적화자기준이 뚜렷하고 피드백을 반영하면 나아질 때생성·평가 사이 되돌아가는 선바퀴마다 비용이 곱해지고, 상한이 필수예요

표를 실제 요구에 대 볼게요. "회의록을 받아, 거기서 나온 할 일 개수만큼(3개일 수도 10개일 수도 있다) 할 일마다 담당자 배정 초안을 만든다." 요약하고, 할 일을 뽑고, 배정하는 순서가 있어 보여서 ① 체이닝을 떠올리기 쉬워요. 하지만 체이닝은 단계가 고정이라 마지막 단계 한 번에 할 일을 몰아서 처리하게 되고, 할 일마다 따로 초안을 만드는 구조가 아니에요. ③ 병렬화는 처리 노드 개수를 미리 알아야 하는데 할 일 개수는 회의록마다 달라요. ② 라우팅은 여러 갈래 중 하나만 고르니 할 일 여러 개를 동시에 다루지 못해요. 답은 ④ 오케스트레이터-워커예요.

그럼 언제 워크플로를 넘어 에이전트로 가야 할까요. 기준은 하나예요. 필요한 단계의 조합을 개발자가 미리 늘어놓을 수 없을 때. 사내 문서로 퀴즈를 만드는 일은 경로가 뻔하니 워크플로가 낫고, "이 저장소의 버그를 찾아 고쳐 줘"는 어떤 파일을 몇 번 읽을지 경우의 수가 끝이 없으니 도구를 쥔 자율 에이전트가 필요해요. 대신 비용을 미리 계산할 수 없고, 같은 입력에 다른 길로 가서 테스트가 어렵고, 틀렸을 때 어디가 틀렸는지 짚기 어려워요. 그래서 워크플로로 먼저 해 보고, 안 된다는 증거가 나왔을 때만 옮겨요.

"워크플로로는 안 된다"는 증거는 어떤 모습일까

"증거가 나왔을 때만"이라는 말은, 뒤집으면 그 증거를 알아볼 수 있어야 한다는 뜻이에요. 구체적인 모습은 각자 적어 봐야 하는데, 아래는 제가 떠올린 신호예요. 기준이 "필요한 단계의 조합을 미리 늘어놓을 수 없을 때"였으니, 증거도 결국 미리 그린 길로는 감당이 안 되는 장면이에요. LangSmith 같은 실행 기록에서 이런 모습이 되풀이되면 신호로 봐요.

  • 갈래를 계속 덧대고 있어요. 새로운 종류의 입력이 올 때마다 라우터에 갈래를 하나씩 더하고, 예외를 처리하는 노드가 끝없이 늘어나요. 길을 미리 다 그릴 수 없다는 뜻이에요.
  • 중간 결과를 보고 다음 걸음을 바꿔야 해요. 실패한 건을 모아 보니 "한 번 더 조회했어야 했는데 그래프에 그 길이 없어서" 틀린 경우가 대부분이에요. 몇 번, 어떤 순서로 조회할지가 매번 달라요.
  • 계획 한 번으로 끝나지 않아요. 오케스트레이터가 처음 짠 계획대로 워커를 돌렸는데, 결과를 보고 계획을 다시 짜야 하는 일이 잦아요. ④ 오케스트레이터-워커는 계획을 한 번만 세우는 모양이에요.
  • 사람이 자주 끼어들어 길을 바꿔 줘요. 흐름이 막힐 때마다 사람이 "이번엔 이걸 먼저 해"라고 손으로 경로를 바꿔 주고 있다면, 그 판단을 LLM에게 맡길 후보예요.

칩 후옌(Chip Huyen)의 글 Agents는 에이전트가 실패하는 모습을 계획 오류·도구 오류·효율 문제로 나눠 정리해요. 에이전트로 옮긴 뒤 무엇을 지켜봐야 하는지 알고 싶을 때 이어서 읽기 좋아요.

중요꼭 기억할 것

에이전트로 옮기는 근거는 "더 똑똑해 보여서"가 아니라 기록으로 확인한 실패 모습이어야 해요. 갈래가 끝없이 늘어나거나, 중간 결과에 따라 다음 걸음이 매번 달라져 고정된 길로는 실패하는 일이 되풀이될 때가 그 증거예요. 에이전트는 비용을 미리 알 수 없고 테스트와 원인 찾기가 어려운 만큼, 증거 없이 먼저 가지 않아요.

내 일에는 어떤 모양이 맞을까 — 고르는 질문 순서

여기서 첫 질문으로 돌아가 볼게요. 1편에서 적어 본 '맡기고 싶은 반복 작업'과 그 조회·행동 목록을 다시 꺼내, 다섯 모양 중 무엇이 맞는지 골라 보는 거예요. 저는 위 표를 질문 순서로 바꿔서 위에서부터 차례로 물어요.

  1. 할 일의 단계와 순서가 늘 같고, 단계 사이에 확인할 게 있나? → ① 프롬프트 체이닝
  2. 들어오는 입력의 종류에 따라 처리 방법이 완전히 달라지나? → ② 라우팅
  3. 서로 독립인 일을 여러 개 동시에 할 수 있고, 그 개수를 미리 아나? → ③ 병렬화
  4. 그 개수를 입력을 받아 봐야 알 수 있나? → ④ 오케스트레이터-워커
  5. 좋고 나쁨의 기준이 뚜렷하고, 피드백대로 고쳐 쓰면 나아지나? → ⑤ 평가자-최적화자
  6. 필요한 단계의 조합을 아예 미리 늘어놓을 수 없나? → 그때만 에이전트

한 가지 일에 여러 모양이 섞여도 돼요. 첫 편 예시였던 식당 예약 변경에 대 보면, 할 일은 늘 "예약 찾기 → 빈자리·수수료 확인 → 예약 바꾸기 → 확인 문자" 순서라 ① 프롬프트 체이닝이 뼈대예요. 빈자리가 없으면 멈추는 코드 게이트를 확인 단계 뒤에 두고, 되돌리기 어려운 '예약 바꾸기' 앞에는 사람의 확인을 끼워요. 그런데 문의가 예약 변경·취소·불만으로 섞여 들어온다면 맨 앞에 ② 라우팅을 붙여 종류별로 나눠 보내요.

중요꼭 기억할 것

패턴은 이름을 외우는 게 아니라 내 일의 모양에 대 보는 것이에요. 순서가 정해져 있나, 종류별로 갈리나, 개수를 미리 아나, 고쳐 쓰면 나아지나를 차례로 묻고, 맞는 것 중 가장 단순한 모양을 골라요. 여러 모양을 섞어도 되지만, 길을 미리 그릴 수 있는 한 워크플로로 먼저 해요.

직접 해보기

  1. 기준을 흐리게 해 보기 — 바꿀 것: 평가 규칙을 "좋은 학습 노트로 써라" 한 문장으로 바꿔요. 측정할 것: 바퀴 수가 몇 번에 끝나는지, 매번 같은지. 비교할 것: 기준을 항목별로 적어 뒀을 때와 대 봐요. 기준이 흐리면 평가자가 매번 다른 이유로 퇴짜를 놓아 바퀴만 늘어요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.

다음은

다섯 패턴은 이걸로 다 봤어요. 다음 편부터는 배운 패턴을 한 프로젝트에 모아요. 매일 아침 AI 소식을 모아 다섯 건을 고르고, 요약하고, 원문과 대조한 뒤 디스코드로 보내는 뉴스레터 에이전트를 여섯 편에 걸쳐 만들어요. 기사를 묶음으로 나눠 고르는 자리에 ③ 병렬화가, 고른 기사 수만큼 요약을 펼치는 자리에 ④의 Send가, 요약을 원문과 대조하는 자리에 ⑤의 평가자가 들어가요.

함께 읽으면 좋은 글

  • 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업 — 오케스트레이터-워커를 여러 에이전트 구조 가운데 하나로 놓고 본 글이에요.
  • 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge — ⑤의 평가자를 LLM으로 둘 때의 한계를 다룬 글이에요.
  • 나눠서 얻는 것과 잃는 것 — 일을 여러 갈래로 나눌 때 치르는 비용을 다룬 글이에요.
