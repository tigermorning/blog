이 시리즈에서 저는 각 OCR, 객체탐지 도구가 어디에서 왔고 어떤 기술을 이어받았는지부터 따라갔어요. Tesseract는 특징 기반 OCR에서 LSTM 행 인식으로 발전한 로컬 엔진이고, PaddleOCR은 탐지·방향 판별·인식을 조립하는 도구 상자였고, PaddleOCR-VL은 문서 구조를 복원하려는 VLM이고, Claude·ChatGPT는 더 넓은 질문을 받는 범용 멀티모달 제품이었어요. 사진에서는 최초 YOLO 공동 연구와 Darknet, 이후 갈라진 계보, 그리고 실습에 쓴 Ultralytics YOLO가 서로 다른 주체의 공헌임을 구분했고, 동시에 박스·마스크·관절점이라는 출력 차이와 Redmon이 제기한 사생활 문제를 실제 사용 카드로 연결했어요.

중요한 건 유명세가 아니라 연결된 사실들

중요한 건 도구의 유명세가 아니라 만든 주체, 입력, 출력 자료형, 검증 방법, 실패와 사회적 영향이 서로 연결되어 있다는 사실이었어요.

각 도구의 출처와 개발 주체를 밝힌 뒤, 실제 결과에서는 어떤 답을 주는지, 무엇과 대조할 수 있는지, 실패했을 때 누가 결정하는지를 기록하는 것 — 이게 이 시리즈 전체가 가르쳐준 습관이었어요. 오늘은 추론만 실행했고, 학습(fine-tuning)은 반복되는 도메인 실패와 권리가 확인된 라벨 데이터가 있을 때 검토하면 됐어요.

넘긴 것은 노동, 남은 것은 결정

처음 떠올렸던 문서와 사진을 다시 보면, 이제 "AI로 읽어주세요"라고 한 덩어리로 넘기기 전에 질문을 나눌 수 있게 됐어요. 글자와 좌표가 필요하면 OCR 엔진, 표와 수식의 구조가 중요하면 문서 VLM, 열린 질문을 빠르게 시험하려면 범용 VLM, 위치와 경계와 자세가 필요하면 각각 탐지·분할·포즈 가중치를 고르면 됐어요.

코딩 에이전트에게는 설치와 연결, 반복 실행, 파일 저장과 UI 조립을 맡길 수 있어요. 하지만 같은 입력을 썼는지, 모델을 몰래 바꾸지 않았는지, 결과가 원문 어디에서 왔는지, 틀리면 누가 확인할지는 사람이 정해야 했어요. 그래서 이 시리즈의 결론은 도구 선택으로 끝나지 않아요. 읽고 보는 노동은 위임할 수 있지만, 그 결과를 믿기로 한 결정은 위임되지 않는다. 원본 해시, 모델·버전, 원시 결과, [UNCLEAR]와 실패 기록이 그 결정을 감당하는 최소한의 근거였어요.

오늘 다룬 능력들은 성격이 하나로 묶여요. 전부 파일 안에 이미 들어 있는 것을 찾아내는 일이었어요. 글자를 읽어내고, 상자를 그려 짚어주고, 픽셀을 칠해 경계를 선언하는 일 모두 원본 어딘가를 가리켰어요. 원본에 대조할 근거가 남아 있고, 사람이 합의한 기준으로 정답지를 만들어 평가할 수 있었어요. 다음 시간에는 이 구조가 깨지는 자리로 갈 예정이에요 — 원본에 없던 픽셀을 만들어내는 이미지 생성이에요. 직접 대조할 원본 정답이 없으면 맞았다 틀렸다를 따지는 방식 자체가 달라지고, 던져야 할 질문도 바뀌어요.

이럴 때 의심하세요 — 문서·사진 처리를 코딩 에이전트에게 맡긴 뒤

에이전트에게 설치와 반복 실행을 맡기면, 사람이 정해야 할 몫이 작업 도중에 조용히 바뀌어요. 설치가 막히면 다른 모델로 돌리고, 비교가 느리면 이미지를 줄여서 돌려요. 끝에는 "완료했어요"라는 말만 남아서, 결과를 다시 따져 볼 때가 돼서야 드러나요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
에이전트가 "설치 에러를 해결했어요"라고 한 뒤로, 결과의 모양이 달라졌어요. 예를 들어 Markdown 표로 나오던 결과가 줄글 문자열로 나와요 에이전트가 고친 코드에서 모델을 불러오는 줄과 try/except 안이에요. 에러가 나면 다른 모델로 넘어가게 짜여 있는지 봐요. 대화 기록에서 "대신", "대체", "우회" 같은 말도 찾아봐요 결과 한 건마다 어떤 모델과 버전으로 만들었는지 적혀 있는지 봐요. 안 적혀 있으면 바뀌기 전후를 가를 수 없으니, 비교보다 기록을 먼저 넣게 해요. 표에서 본 것처럼 도구가 바뀌면 답의 자료형과 실패 유형이 같이 바뀌어요
두 도구를 비교했더니 한쪽이 훨씬 잘 읽었어요. 그런데 그쪽만 따로 설치해 돌린 코드였어요 두 도구를 부르기 직전의 코드예요. 한쪽에만 크기 줄이기, 자르기, 흑백 바꾸기 같은 전처리가 들어갔는지, 넘긴 파일이 같은 폴더의 같은 파일인지 봐요 두 실행에 들어간 파일의 해시(파일 내용으로 만든 지문 같은 값)를 맞춰 봐요. Windows는 certutil -hashfile 파일이름 SHA256, macOS는 shasum -a 256 파일이름이에요. 원본 파일의 해시가 같아도 전처리가 다르면 같은 입력이 아니니, 전처리 줄도 같이 봐요
지난달 뽑은 결과를 두고 "이 값 어디서 나왔어요?"라는 질문을 받았는데, 결과 파일에 값만 있고 무엇으로 언제 만들었는지가 없어요 결과를 저장하는 JSON·CSV 파일의 칸이에요. 원본 해시, 모델·버전, 원시 결과(가공 전 응답), 실행일이 한 건에 같이 있는지 봐요 하나라도 없으면 그 결과를 왜 믿었는지 되짚을 수 없어요. 다시 돌려도 모델이 바뀌었을 수 있어서 같은 답이 나온다는 보장이 없거든요. 지금부터 돌리는 결과에 네 칸을 같이 남기게 해요

세 줄 모두 결과만 봐서는 티가 안 나요. 결과를 보고서에 옮기거나 다른 사람에게 넘기기 직전에 한 번 확인해요. 결과표에 빈칸이 하나도 없어서 오히려 이상한 경우는 VLM 편의 첫 줄에서 확인해요.

에이전트가 짠 처리 코드는 길고 여러 파일에 나뉘어 있어서, 고치기 전에 무엇이 기록되고 어디서 모델이 바뀔 수 있는지부터 보여 달라고 해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 문서나 사진을 처리하는 프로젝트 폴더에서

이 프로젝트에서 OCR·VLM·탐지·분할 같은 모델로 문서나 사진을 처리하는 곳을 전부 찾아서 표로 보여 줘. 아직 코드는 고치지 마.
1. 파일 이름, 줄 번호, 부르는 모델 이름과 버전
2. 에러가 나면 다른 모델이나 다른 방법으로 넘어가는 코드(try/except 등)가 있는지, 있다면 무엇으로 넘어가는지
3. 모델에 넘기기 전에 이미지 크기 줄이기·자르기·색 바꾸기 같은 전처리를 하는 줄
4. 결과를 저장할 때 원본 해시, 모델·버전, 원시 결과, 실행일 중 무엇을 같이 남기고 무엇이 빠져 있는지
