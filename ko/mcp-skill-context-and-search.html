어디에 쓰나
여러 MCP 서버를 한 호스트에 붙일 때 · 도구 검색이 안 보인다고 설정이 고장 났다 오해할 때 · 코드 안에서 필요한 필드만 추려 반환하고 싶을 때 · 문맥 사용량 표시를 해석할 때

지난 편에서 업무 기록을 읽는 통로 하나를 뚫었어요. 이 방식이면 문서 검색도, 달력 조회도, 다른 팀 기록도 같은 식으로 붙일 수 있겠구나 싶었죠. 그래서 몇 개 더 붙여 봤는데, 여기서 좀 의외의 장면을 만났어요.

수업에서 보여 준 캡처가 그 장면이에요. 사용자가 입력한 건 ping 한 마디, AI도 짧게 답했어요. 대화는 두 줄이 전부인데 화면 오른쪽 숫자는 Context 138,233 tokens · 69% used였어요. 옆에는 연결된 서버 이름들(달력·문서·스프레드시트 등)이 죽 나열돼 있고요.

여기서 제가 제일 먼저 확인해야 했던 건 "그 13만 토큰이 전부 MCP 도구 설명이냐"는 거예요. 아니에요. 호스트1의 기본 지시, 프로젝트 규칙, 도구 안내 등 말풍선 바깥에서 함께 들어가는 정보가 섞여 있어요. 그러니 이 숫자를 "도구를 붙였더니 13만 토큰이 되었다"로 읽으면 틀려요. 다만 대화가 짧다고 문맥이 작은 건 아니다는 사실만큼은 이 화면이 확실히 보여 줘요.

이번 편은 그 부담이 어디서 생기는지 갈라 보고, Claude Code와 OpenCode가 같은 문제를 각각 어떻게 푸는지까지 봐요.

비유 — 회의실에 들어가기 전 책상 위

2편에서 회사 대표번호와 전화 교환대를, 3편에서 자료실 직원을 이야기했죠. 이번엔 그 회사의 회의실 안이에요.

저는 지금 회의실에 앉아 있고, 앞에 담당자 한 명이 있어요. 제가 할 말은 딱 한 줄이에요. "첫 주 업무 기록 좀 보여 주세요." 그런데 담당자 책상 위에는 이미 회사 전 부서의 업무 매뉴얼 100권이 쌓여 있어요. 회의 전에 "혹시 필요할지 모르니" 전부 올려 둔 거예요. 아직 한 마디도 안 했는데 책상은 이미 꽉 찼죠.

더 좋은 방법이 있어요. 책상엔 부서명과 한 줄 소개만 적힌 색인 카드 한 장만 두고, 제 요청을 듣고 나서 필요한 두 권만 꺼내 오는 거예요. 100권을 없애는 게 아니라 가져오는 시점을 미루는 거죠.

그런데 여기서 끝이 아니에요. 담당자가 자료실에 다녀왔는데, 제가 "첫 주"라고 안 하고 그냥 "우리 팀 기록"이라고 했다면 1년치 서류 뭉치를 실어 와요. 매뉴얼을 안 펼쳐서 아낀 자리를, 이번엔 서류 뭉치가 다 차지해요. 책상을 채우는 방법이 두 가지인 거예요.

담당자 책상 위의 유한한 공간문맥2 — 모델이 이번 답을 만들 때 함께 읽는 정보 전체

핵심 한 줄: 책상을 채우는 건 안 펼칠 매뉴얼과 너무 많이 실어 온 서류 두 가지고, 이 둘은 치우는 방법이 서로 달라요.

다만 여기서 비유가 끊기는 점이 하나 있어요. 진짜 책상은 치우지 않으면 어제 그대로지만, 문맥은 그렇지 않아요. 컨텍스트 창은 왜 유한한가에서 정리했듯이 문맥은 매 요청마다 새로 채워지는 작업대예요. 그래서 "지난번에 한 번 읽혔으니 이번엔 안 읽어도 되겠지"가 성립하지 않아요.

대화창 밖에서 함께 읽히는 것들

문맥(context)은 모델이 이번 응답 하나를 만들 때 참고하라고 함께 건네받는 정보예요. 사용자와 AI가 주고받은 말이 여기 들어가지만, 대화창에 보이는 문장만 들어가는 건 아니에요. 화면에 안 보이는 재료가 여럿 같이 실려요.

모델 입력에 들어갈 수 있는 것이번 실습에서는무엇 때문에 늘어나나
시스템·프로젝트 지시에이전트의 작업 방식, 프로젝트 규칙 문서지침이나 설정을 추가할수록
요청·대화 이력"첫 주 기록 읽어 줘"와 그 이전 질문·답변들같은 대화를 길게 이어 갈수록
도구 정의get_weekly_records의 이름·설명·입력 규칙도구를 추가하거나 상세 정의를 읽을수록
실행 결과조회된 주차 정보와 업무 기록 목록더 많은 자료를 가져올수록
읽은 자료팀 보고 기준 문서, 참조한 프로젝트 파일새 파일과 참조 자료를 읽을수록

이 다섯 재료는 컨텍스트 창은 왜 유한한가에서 "하나의 적재함을 나눠 쓴다"고 정리했던 그 재료들과 같은 얘기예요. 그 글의 예산표에 "도구 설명 — 지금 과업에서 쓰지 않는 도구는 노출을 뺀다"는 줄이 있었는데, 이번 편은 그 한 줄을 실제 기능으로 구현하면 어떻게 생겼는가에 대한 이야기예요.

한 가지 더. 호스트가 이 모든 걸 항상 원문 그대로 보내는 건 아니에요. 필요한 항목만 고르거나, 오래된 대화를 요약해 넣거나, 읽는 시점을 뒤로 미룰 수 있어요. 그러니 "화면에 있는 것 = 모델이 읽은 것"도 아니고, "연결된 것 = 지금 다 읽히는 중"도 아니에요.

여기서 토큰6도 한 번 짚고 갈게요. 토큰은 모델이 글자를 나누는 조각이고, 단어나 글자와 정확히 일치하지 않아요. AI 토큰이란 무엇인가에서 처음 다뤘고, 토큰과 컨텍스트 — 활용가가 보는 비용과 한계에서는 같은 뜻의 한국어 문장이 영어보다 토큰을 훨씬 많이 먹는다는 걸 실제로 세어 봤어요. 그래서 화면의 69% used는 절대 진리가 아니라 그 환경이 그 모델 기준으로 표시한 사용 비율로 읽으면 돼요 — 정확한 한도와 계산 방식은 모델마다 다르거든요.

도구 정의 · 호출 입력 · 실행 결과 — 셋은 다른 정보예요

부담이 어디서 생기는지 보려면 먼저 같은 도구를 둘러싼 세 가지 정보를 갈라 둬야 해요. 이걸 뭉뚱그리면 "도구를 줄여야 하나?" 같은 엉뚱한 결론으로 가요.

get_weekly_records라는 이름만 봐도 주간 기록과 관련된 기능이겠거니 짐작은 돼요. 그런데 어느 주를 읽을지 어떻게 지정하는지, 어떤 값이 돌아오는지는 이름만으로 알 수 없죠. 이 사용 안내의 묶음을 도구 정의라고 해요 — 1편에서 "이름 · 설명 · 입력 스키마" 세 부분으로 처음 뜯어봤던 그것이에요.

정보이번 실습에서의 내용언제 필요한가
도구 정의이름은 get_weekly_records, 가상 팀의 업무 기록을 읽음, week라는 문자열 입력을 받음모델이 기능을 고르고 입력을 만들 때
호출 입력{"week": "week-one"}첫 주 기록을 읽어 달라고 실행을 요청할 때
실행 결과첫 주의 팀 정보 · 보고 기준일 · 업무 기록 4건실제 기록을 받아 내용을 이해할 때

이 구분은 제가 지어낸 게 아니라 MCP 메시지 자체에 이미 있어요. 2편에서 본 tools/list(도구의 이름·설명·입력 스키마를 알아오는 요청)와 tools/call(쓸 도구와 인자를 전달하는 요청)이 각각 첫 줄과 둘째 줄에 대응해요.

그리고 MCP가 "모든 정의를 매번 모델에게 한꺼번에 읽혀라"라고 강제하지는 않아요. 이게 이번 편의 출발점이에요. 서버 연결 → 도구 정의 발견·로드 → 도구 호출 → 결과 읽기를 별개의 단계로 보면, 어느 단계를 미룰 수 있는지가 보이거든요. 4편에서 "연결됐다"와 "호출됐다"를 굳이 갈라 뒀던 이유가 여기서 한 번 더 쓰여요.

실행 전의 부담과 실행 후의 부담

이제 부담을 두 종류로 나눠 볼게요. 수업에서 든 가상 수치 예시가 이해에 좋아요(실제 측정값이 아니라 감을 잡으려고 만든 숫자예요).

도구가 100개 있고 각 정의가 평균 500토큰이라면, 전부 미리 실을 때 100 × 500 = 약 50,000토큰이에요. 그런데 이번 요청에 실제로 필요한 도구가 두 개뿐이라면? 검색 안내에 1,000토큰 + 찾은 두 도구의 정의 1,000토큰 = 약 2,000토큰이면 돼요. 나머지 98개의 상세 설명은 이번 대화에서 한 번도 안 펼치는 거죠.

여기까지가 한 종류예요. 이제 다른 상황을 보세요. 찾은 도구의 설명은 짧은데, 실행했더니 1년치 업무 기록이 수천 줄 돌아오는 경우요. 정의를 나중에 읽는 기능을 아무리 켜 놔도 커진 실행 결과 자체는 조금도 작아지지 않아요.

구분무엇이 문맥을 차지하나어느 쪽으로 손대야 하나
실행 전의 부담이번에 쓰지도 않을 도구들의 상세 설명관련 정의만 필요한 시점에 읽는 방식
실행 후의 부담실제로 가져온 데이터가 너무 많음조회 기간·항목을 좁히거나, 결과에서 필요한 부분만 추려 전달

이 구분이 왜 중요하냐면, 증상이 비슷해 보여도 처방이 정반대이기 때문이에요. "문맥이 꽉 찼다"는 같은 화면을 보고 실행 전 부담을 줄이는 기능만 켜면, 원인이 실행 후 부담이었을 때 아무것도 안 바뀌어요.

여기서 3편에서 만든 서버를 다시 보면 재밌어요. 우리 서버는 week를 입력받아 해당 주의 파일 하나만 돌려줘요. 그때는 "허용된 값만 받으려고" 그렇게 만든 거였는데, 결과적으로 실행 후 부담을 설계 단계에서 미리 잘라 둔 셈이에요. 도구를 만들 때 "무엇을 돌려줄 것인가"를 좁게 잡는 일이 나중에 문맥 문제로 돌아온다는 뜻이죠.

덧붙여, 실행 후 부담은 요금·속도 문제만도 아니에요. 길게 넣어도 안 읽힐 수 있다에서 봤듯이 실었다는 사실과 읽혔다는 사실은 다르거든요. 수천 줄을 밀어 넣으면 정작 중요한 한 줄이 가운데 묻힐 수 있어요.

전체 흐름 그림 — 미리 다 읽히기 vs 찾아서 읽기

지연 로딩(deferred loading)은 쓸 때까지 상세 내용을 불러오는 시점을 미루는 것이에요. 기능을 없애거나 서버를 끄는 것과는 완전히 다른 얘기예요 — 100권은 창고에 그대로 있고, 책상에 언제 올리느냐만 바뀌어요.

읽는 법: 두 줄은 같은 일을 하는 서로 다른 순서예요. 첫 칸을 비교하는 게 핵심이에요 — ①은 요청을 듣기도 전에 100개를 다 실었고, ②는 요청을 듣고 나서 두 개만 실어요. 그리고 아래 괄호 두 개를 보세요. ②가 줄여 주는 건 왼쪽 괄호뿐이에요. 오른쪽 칸(결과)은 두 줄에서 크기가 똑같아요. 마지막 줄도 중요해요 — ②에는 검색이라는 단계가 하나 늘어나요. 그래서 도구가 두세 개뿐인 환경에서는 오히려 손해일 수도 있어요.

Anthropic의 Tool Search 설명도 같은 얘기를 해요. 많은 도구의 상세 정의를 처음부터 다 주는 대신 필요할 때 발견해서 읽는 방식을 소개하면서, 동시에 검색 단계가 추가되므로 도구 수가 적을 때와 많을 때의 이점이 다를 수 있다고 단서를 달아 뒀어요. 이 단서를 빼고 "무조건 절약된다"로 읽으면 안 돼요.

Claude Code의 Tool Search — 찾고 나서 읽는다

Tool Search7는 필요한 도구를 먼저 찾고, 그 도구의 상세 정의를 그다음에 불러오는 기능이에요. 연결된 도구가 존재한다는 정보와, 실제 호출에 필요한 상세 사용법을 나눠서 다루는 거죠.

요청 하나를 예로 네 장면을 따라가 볼게요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

MCP로 week-one 업무 기록을 읽고, 어떤 자료를 가져왔는지 알려 줘.
  • 첫째, 할 일을 이해해요. 모델은 요청을 받았지만 아직 업무 기록을 읽지는 않았어요.
  • 둘째, 필요한 도구를 찾아요. 여기서 검색이 한 일은 '조회할 수단 찾기'예요. 화면에 get_weekly_records가 등장해도 TASK-101부터 TASK-104까지 읽었다는 뜻이 아니에요.
  • 셋째, 찾은 도구의 상세 정의를 불러와요. 필요한 정의를 문맥에 넣는 걸 흔히 로드8(load)한다고 해요. 이 단계에서 "week-one이라는 값을 써야 한다"는 설명을 읽고 입력을 맞춰요.
  • 넷째, 실제로 호출하고 기록을 받아요. {"week": "week-one"}이 오가고 자료가 돌아와요.

둘째와 넷째를 헷갈리는 게 이 기능에서 제일 흔한 오해예요. 구분하는 법은 간단해요 — 돌아온 게 도구의 사용법이면 검색, 실제 업무의 내용이면 호출이에요.

그리고 이 흐름을 따라가다 보면 3편에서 함수 설명(docstring)에 "week-one 또는 week-two"라고 적어 둔 게 왜 중요했는지 다시 보여요. 검색 기능이 생겨도, 도구가 무슨 일을 하는지 잘 설명해 두는 건 여전히 우리 몫이에요. 설명이 부실하면 검색으로 못 찾거나, 찾아도 엉뚱한 입력을 만들어요.

여기서 한 가지 함정이 있어요. AI가 터미널에서 설정값을 바꿨다고 해서, 이미 돌고 있는 모든 세션이 동시에 바뀌지는 않아요. 4편 트러블슈팅 표 마지막 줄의 "실행 중인 프로세스는 새 소스를 다시 읽어야 한다"와 같은 종류예요. 지금 보고 있는 세션과 새로 실행하는 세션을 구분하지 않으면, 안 바뀐 화면을 몇 번이고 다시 확인하게 돼요.

검색이 안 보였다고 고장 난 건 아니에요

같은 대화에서 둘째 주 기록을 이어서 요청했는데, 이번엔 검색 장면이 안 나올 수 있어요. 저는 처음에 "설정이 풀렸나?" 했는데 아니었어요. 가능한 이유가 몇 가지 있어요.

  • 이미 찾아 둔 정의를 그대로 재사용했을 수 있어요 — 같은 도구를 또 찾을 이유가 없으니까요. (대화가 압축돼 발견 정보가 정리되고 나면 다시 검색해요.)
  • 설정을 auto로 뒀다면, 정의 분량이 기준에 못 미쳐 그냥 미리 로드했을 수 있어요. 이번 실습처럼 도구가 한 개뿐이면 충분히 있을 수 있는 일이에요.

검색이 안 보였다는 관찰과 기능이 고장 났다는 결론은 다른 얘기예요. 관찰을 결론으로 바로 승격시키면 멀쩡한 설정을 뒤집어엎게 돼요.

도구는 찾았는데 실제 호출에서 오류가 났다면, 오류 내용을 읽어요. 예를 들어 "지원하지 않는 주차"라는 응답이라면 서버가 요청을 받고 입력을 검사하는 단계까지 도달한 거예요 — 3편의 WEEK_FILES 허용 검사가 돌았다는 뜻이죠. 이건 연결 실패와 완전히 다른 상태예요.

마지막으로 절약 효과를 해석하는 기준 하나. 도구 하나만 연결한 상태에서 큰 절약률이 나오도록 억지로 만들 필요는 없어요. 검색 자체에 과정이 추가되니까 도구가 적으면 전체 시간이 더 빨라진다고 단정할 수도 없고요. 그리고 여기가 핵심인데 — Tool Search는 정의를 언제 읽을지를 돕고, 자료의 범위를 정하는 건 우리 몫이에요. 필요 없는 주차까지 다 가져오면 정의를 아껴도 데이터가 문맥을 채워요.

OpenCode의 Code Mode — 코드로 도구를 부른다

OpenCode를 쓰는 경우에도 같은 자료를 읽을 수 있어요. 다만 Code Mode9를 켜면 실행 기록에 익숙한 도구 이름 대신 execute가 먼저 나타날 수 있어요. 처음 보면 "내 도구가 사라졌나?" 싶은데, 바뀐 건 모델이 도구를 호출하는 방식일 뿐이에요. 3편에서 만든 Python 서버와 JSON 자료는 그대로 써요.

Code Mode에서는 모델이 도구 호출을 담은 짧은 JavaScript 코드를 만들고, OpenCode가 정해진 범위 안에서 그 코드를 실행해요. 제가 서버를 새 언어로 다시 짜는 게 아니에요.

목록과 검색, 그리고 네임스페이스

V1의 Code Mode는 처음 제공할 도구 안내에 분량을 정해 두고, 그 안에 들어가는 도구 정의를 보여 줘요. 그래서 일부 도구가 빠진 목록이 나올 수 있어요. 그때 모델은 검색으로 필요한 도구의 경로와 입력 규칙을 확인할 수 있어요. 여기서의 검색은 새 도구를 설치하는 게 아니라 이미 연결된 도구 가운데 쓸 것을 찾는 과정이에요.

그러면 이름이 겹칠 때가 문제예요. 여러 서버에 search라는 도구가 다 있다고 상상해 보세요. 어느 서버의 검색인지 구분할 이름이 필요하죠. 서버별로 도구를 묶어 둔 이름 공간을 네임스페이스10(namespace)라고 해요. 우리 실습에서는 weekly-records라는 묶음 아래에 get_weekly_records가 있어요 — 4편에서 등록한 서버 이름이 여기서 이렇게 쓰여요.

상황실행 경로
처음 주어진 안내에 필요한 도구와 입력 규칙이 이미 보임안내를 읽고 바로 호출
도구 목록이 일부만 보이고 필요한 도구가 빠져 있음도구 검색 → 반환된 경로·입력 확인 → 호출

그래서 여기서도 같은 주의가 붙어요. 검색이 없었다는 이유만으로 설정 실패라고 판단하지 마세요. 첫 줄의 경우일 수 있어요.

실행 기록 따라가기

실행: 코딩 에이전트에 붙여넣기 — OpenCode 등

weekly-records MCP에서 week-one 기록을 읽어 줘.

V1 소스에서 바깥쪽 도구 이름은 execute이고, 그 안의 호출이 MCP 클라이언트를 통해 원래 서버로 전달돼요. 다섯 걸음으로 적으면 이래요.

  • 저: "week-one 기록을 읽어 줘"
  • 모델: execute에 도구 호출 코드를 전달
  • OpenCode: 그 안의 내부 호출을 MCP 요청으로 전달
  • weekly-records: get_weekly_records가 자료를 읽어 반환
  • OpenCode: 코드 실행 결과를 모델에게 전달

모델이 만드는 코드는 이렇게 생겼어요.

개념 설명용 코드 — 모델이 내부에서 만드는 코드를 사람이 읽기 좋게 옮긴 것이에요

const result = await tools["weekly-records"].get_weekly_records({ week: "week-one" });
return result;

한 조각씩 뜯어볼게요.

  • tools — 실행 환경에 제공된 도구 모음이에요.
  • ["weekly-records"] — 그중 주간 기록 서버 묶음을 가리키는 네임스페이스예요.
  • get_weekly_records(...) — 실제 조회예요. 3편에서 만든 그 함수요.
  • { week: "week-one" } — 서버에 보낼 입력이에요. 2편에서 본 tools/call의 인자와 같은 내용이 여기 들어가요.
  • await11 — 결과가 도착할 때까지 기다린다는 뜻이에요. 파이썬 코드 눈으로 읽기의 async/await 설명과 같은 개념이에요.
  • return — 코드 실행에서 얻은 값을 바깥으로 돌려줘요. 이 값이 모델에게 가요.

여기서 중요한 건 이 코드는 OpenCode 쪽에서 돌고, 실제 Python 함수는 MCP 서버에서 돈다는 점이에요. 두 실행 위치가 다른 거죠. 확인은 4편과 똑같이 해요 — 전달한 주차와 결과의 week를 맞춰 보고, 원본 data/week-one.json의 업무 ID 네 개가 반환 자료에도 다 있는지 보세요.

여기가 Code Mode에서 제일 흥미로웠던 부분이에요. 이렇게 물어봐요.

실행: 코딩 에이전트에 붙여넣기 — OpenCode 등

week-one 기록에서 blocker가 적힌 항목의 ID와 막힌 이유만 보여 줘.

blocker는 업무 진행을 막는 사유를 담는 필드예요. 값이 null이면 사유가 기록되어 있지 않은 거고요(4편에서 deployed_at과 owner의 null을 대조할 때 본 그 null이에요).

Code Mode에서는 도구로 받은 결과를 코드 안에서 살펴보고 필요한 부분만 반환할 수 있어요. 전체 기록을 받았더라도 모델에게 전달되는 최종 값은 고른 ID와 사유뿐일 수 있다는 뜻이에요. 아까 그림의 오른쪽 괄호(실행 후의 부담)에 손을 대는 방법이 여기서 하나 생기는 거예요.

다만 두 가지 단서가 붙어요.

  • V1 v1.18.29의 호스트 소스는 MCP의 구조화된 결과12가 있으면 그걸 쓰고, 없으면 텍스트 내용을 전달하는 경로를 가져요. 텍스트를 객체처럼 취급하면 필드를 못 찾아요 — result.records 같은 접근이 빈손으로 돌아오는 상황이 여기서 나와요.
  • 전체 기록을 모델에 다 전달한 뒤 답변만 짧게 만드는 것과 코드 안에서 골라 짧게 전달하는 것은 완전히 다른 상태인데, 결과 문장의 길이만으로는 구분이 안 돼요. 둘 다 답은 두 줄로 나오거든요. 그래서 실행 기록을 같이 봐야 해요.

마지막으로 이것도 짚어 둘게요. OpenCode는 여러 제공자의 모델을 쓸 수 있고, 모델마다 코드 생성과 도구 호출 능력이 달라요. "설정 예시를 확인했다"와 "내 모델 조합에서 호출에 성공했다"는 각각 따로 확인해야 해요.

두 앱을 나란히 — 같은 문제, 다른 해법

둘 중 뭐가 더 낫냐는 질문이 자연스럽게 나오는데, 도구 하나짜리 실습으로 성능 우열이나 절감률을 판정하지는 않을게요. 대신 어느 부담을 어디서 건드리는가로 갈라 보면 성격 차이가 뚜렷해요.

결과를 줄이는 방법도구 입력으로 범위를 좁히는 건 우리 설계 몫입력으로 좁히거나, 코드 안에서 필요한 필드만 골라 반환
검색이 안 보일 때이미 로드된 정의 재사용, 또는 auto 기준 미달로 미리 로드처음 안내 목록에 그 도구가 이미 들어 있었을 수 있음
우리가 만든 서버는그대로 씀그대로 씀

표 마지막 줄이 제일 마음에 들었어요. 두 방식 다 3편에서 만든 Python 서버를 손대지 않아요. 호스트가 도구를 어떻게 알아내고 어떻게 부르는지는 호스트 쪽 사정이고, 서버는 2편의 MCP 규칙만 지키면 되니까요. 프로토콜을 사이에 두는 구조의 이점이 여기서 실감 나요.

나쁜 선택 vs 좋은 선택 — 회의실 책상 위에서

나쁜 선택좋은 선택
회의 시작 전에 전 부서 매뉴얼 100권을 책상에 다 올려 둔다 = 연결된 도구 전부의 상세 정의를 처음부터 문맥에 싣는다 → 아직 한 마디도 안 했는데 책상이 꽉 차고, 정작 펼쳐야 할 두 권을 놓을 자리가 없다. 부서명과 한 줄 소개만 적힌 색인 카드를 두고, 요청을 듣고 두 권만 꺼내 온다 = 발견용 안내만 두고 검색으로 찾은 도구의 정의만 로드한다 → 책상에 올라가는 건 실제로 쓸 두 권뿐이다.
자료실에 "우리 팀 기록 전부 주세요"라고 부탁한다 = 조회 범위를 안 좁히고 1년치를 통째로 가져온다 → 매뉴얼을 아껴 비운 자리를 서류 뭉치가 그대로 채운다. 정의를 미루는 기능으로는 이건 안 줄어든다. "첫 주 것만, 그중 막힌 건의 번호와 사유만" 부탁한다 = week 입력으로 주차를 좁히고, 필요한 필드만 추려 전달한다 → 실행 후의 부담까지 같이 줄어든다.
색인 카드를 뒤지는 장면이 안 보였으니 색인 제도가 고장 났다고 결론짓는다 = 실행 기록에 검색이 안 보여 기능이 꺼졌다고 단정한다 → 멀쩡한 설정을 뒤집어엎고, 원인은 다른 데 있었으므로 증상도 그대로다. "안 보였다"는 관찰과 "고장 났다"는 결론을 갈라 둔다 → 이미 로드된 정의를 재사용한 건지, 분량 기준에 못 미쳐 미리 실린 건지부터 확인한다.

증상마다 먼저 볼 곳이 다르다

도구를 많이 연결한 환경을 다룰 때 제일 중요한 태도는 "문맥이 크다"를 하나의 증상으로 뭉치지 않는 것이에요. 관찰한 상황마다 봐야 할 데가 달라요.

관찰한 상황먼저 살펴볼 곳
대화를 거의 하지 않았는데 많은 도구 설명이 이미 제공됨필요한 도구 정의만 불러오는 기능이 켜져 있는지
한 번의 조회에서 수천 줄의 원자료가 반환됨조회 범위와 반환할 항목 — 도구 설계 쪽
같은 대화에서 여러 작업을 오래 이어감남아 있는 대화·파일·결과와 호스트의 문맥 관리
도구는 발견했는데 인증 만료 오류가 반환됨해당 서비스의 인증 상태와 서버 오류
비슷한 이름의 다른 기능을 호출함발견한 도구 설명과 실제 호출 입력

넷째 줄이 이 표의 이유예요. 인증이 만료된 상황에서는 도구 설명을 덜 읽게 해도 접근 권한이 돌아오지 않아요. 문맥을 줄이는 기능은 문맥 문제만 풀어요. 어느 단계에서 문제가 생겼는지에 맞춰 방법을 고르는 게 출발점이에요.

내 환경이 실제로 어떤지 궁금하면 이렇게 물어봐요. 뒷줄이 특히 중요해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

지금 연결된 MCP 도구가 어떻게 AI에게 알려지는지 확인해 줘.
실제로 확인한 내용과 추정은 구분해 줘.

"확인한 내용과 추정을 구분해 줘"를 안 붙이면 그럴듯한 설명이 한 덩어리로 와요. 이건 4편에서 AI의 진단을 결론이 아니라 확인할 지점을 좁혀 주는 힌트로 썼던 것과 같은 태도예요.

그리고 한 가지 안심할 점. 이번 실습처럼 도구가 적으면 처음부터 도구 설명이 다 제공될 수도 있어요. 그게 정상이에요. 절감 효과를 보겠다고 필요도 없는 서버를 잔뜩 설치할 필요는 전혀 없어요.

직접 해보기

이번 연습의 목적은 절약률을 재는 게 아니라 두 부담을 눈으로 구분하는 것이에요.

① 같은 요청을 범위만 바꿔 두 번 해보기. 먼저 "우리 팀 업무 기록 읽어 줘"라고만 하고, 다음엔 "첫 주 기록만 읽어 줘"라고 해 보세요. 실행 기록에 돌아온 자료의 양을 나란히 놓고 보세요. 답변 문장 길이는 비슷해도 실어 온 서류 뭉치의 두께가 다를 수 있어요.

② 검색 장면이 나오는지 두 번 확인하기. 새 대화에서 첫 주를 요청하고, 이어서 같은 대화에서 둘째 주를 요청해 보세요. 두 번째에 검색이 안 나온다면 왜 안 나왔는지를 한 줄로 적어 보세요 — 재사용인지, 애초에 미리 실렸는지요. 안 보였다는 관찰을 결론으로 바꾸지 않는 연습이에요.

③ 일부러 필드를 골라 달라고 해보기. Code Mode를 쓸 수 있다면 "blocker가 적힌 항목의 ID와 사유만"을 요청하고, 실행 기록에서 모델에게 실제로 전달된 값이 전체 기록인지 추려진 값인지 확인해 보세요. 둘 다 최종 답은 두 줄로 나올 테니, 답변만 보고는 절대 구분 못 한다는 걸 여기서 체감하게 돼요.

여기까지 오면 통로도 뚫렸고, 그 통로가 문맥을 어떻게 쓰는지도 봤어요. 그런데 아직 안 정한 게 하나 있어요. TASK-102는 '개발 완료'인데, 이걸 우리 팀 주간보고의 '완료'에 넣어도 되나요? 이건 도구가 정해 줄 수 없는, 우리 팀만의 판정 기준이에요. 그리고 이런 기준은 매주 반복돼요. 그 반복되는 판단을 어디에 적어 두는가 — 다음 편의 Skill 이야기예요.

  1. 호스트(host) — 내가 대화하는 AI 앱으로, 모델 사용과 서버 연결·실행 허용을 관리하는 쪽이며 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
  2. 문맥(context) — 모델이 이번 응답 하나를 만들 때 참고하도록 함께 건네받는 정보 전체로, 대화창에 보이는 문장만 들어가는 것은 아니에요. ↩
  3. 문맥 창(context window) — 모델이 한 번의 요청에서 다룰 수 있는 정보의 범위이며, 컨텍스트 창은 왜 유한한가에서 이사 트럭 적재함 비유로 처음 다뤘어요. ↩
  4. 도구 정의(tool definition) — 도구의 이름·설명·입력 규칙을 묶은 사용 안내로, 도구 하나가 호출되기까지에서 처음 다뤘어요. ↩
  5. 지연 로딩(deferred loading) — 기능을 없애는 것이 아니라, 상세 내용을 실제로 쓸 때까지 불러오는 시점을 미루는 방식. ↩
  6. 토큰(token) — 모델이 글자를 나누는 조각으로 단어나 글자와 정확히 일치하지 않으며, AI 토큰(Token)이란 무엇인가에서 처음 다뤘어요. ↩
  7. Tool Search — Claude Code에서 필요한 도구를 먼저 검색해 찾은 뒤 그 도구의 상세 정의만 문맥에 불러오는 기능. ↩
  8. 로드(load) — 필요한 정의나 자료를 모델이 읽을 수 있도록 문맥에 실어 넣는 일. ↩
  9. Code Mode — OpenCode에서 모델이 도구 호출을 담은 짧은 JavaScript 코드를 만들고 앱이 그 코드를 정해진 범위 안에서 실행하는 방식. ↩
  10. 네임스페이스(namespace) — 이름이 겹치지 않도록 서버나 묶음별로 도구를 담아 두는 이름 공간. ↩
  11. await — 결과가 도착할 때까지 기다린다는 뜻의 문법으로, 파이썬 코드 눈으로 읽기의 async/await 절에서 처음 다뤘어요. ↩
  12. 구조화된 결과(structured content) — 도구가 돌려준 값이 항목별로 나뉜 형태로 와서 records 같은 필드를 코드로 바로 꺼낼 수 있는 상태. ↩
