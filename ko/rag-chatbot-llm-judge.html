답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge

2026. 8. 28.

리허설에서 모두콘 자료와 관계없는 "내일 날씨 알려줘" 같은 질문을 일부러 넣었어요. 근거가 되는 자료가 없는 질문이에요. 보려던 건 세 가지예요. 챗봇이 확인할 근거가 없다고 말하는지, 날씨 정보를 지어내지 않는지, 빈 출처를 꾸며내지 않는지요. 대화가 그냥 멈춘 것처럼 보이는 결과와, 자료의 경계가 실제로 작동한 결과는 달라요. 답변 본문과 출처 칩(답변 아래에 붙는 출처 표시 단추)을 함께 읽어야 구별된다는 걸 오늘 배웠어요.

1. 출처 칩만으로는 부족하다

모두콘 챗봇의 답변은 검색된 근거를 바탕으로 만들어져요. 하지만 출처 칩이 보인다고 해서 답변 전체가 근거에 충실하다고 할 수는 없어요. 그래서 질문·검색 근거·생성 답변을 함께 읽는 별도 평가자를 답변 뒤에 둬요. 이 평가자가 모델의 답을 완전히 객관적으로 증명해 주는 건 아니에요. 근거성·환각(근거 없이 지어낸 틀린 답, 첫 글)·인용·정당한 거부를 같은 화면에서 지켜보게 해 주는, 공부용 측정 장치예요. 평가자는 답변을 다시 쓰거나 감추지 않아요. 어떤 기준에서 통과했는지, 어떤 점이 불확실했는지를 판정 배지(작은 결과 표시)와 짧은 평어로 남겨요.

2. 여섯 필드로 판정을 데이터 구조로 읽기

판정 프롬프트(평가자에게 주는 지시 글)는 평가 기준을 "좋아 보인다" 같은 인상으로 두지 않아요. JSON(항목 이름과 값을 짝지어 적는 데이터 형식)의 칸과 판단 대상을 분명히 적어요. 특히 근거 없는 질문에 답을 꾸며내지 않고 "없다"고 말한 경우는 실패가 아니에요. refusal:true로 따로 분리해야 해요. 그래야 챗봇이 무엇이든 답하는 도구가 아니라, 확인할 수 있는 자료 안에서만 답하는 안내 도구가 돼요. 아래 코드는 평가자에게 주는 지시문의 예이고, 읽기만 해도 돼요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

당신은 RAG 챗봇 답변의 평가자입니다. 아래 [질문], [근거자료], [답변]을 읽고 다음 기준으로 JSON만 출력합니다.
grounded: 답변 내용이 근거자료에서 나왔는가 (true/false)
noHalluc: 근거에 없는 사실을 지어내지 않았는가 (true/false)
cited: 답변 안에 근거 조각의 [ID] 표시가 있는가 (true/false)
refusal: 근거에 답이 없어서 '없다'고 답한 경우 true, 그 외 false
score: 0-100 정수 (grounded·noHalluc·cited 반영)
comment: 한두 문장 평어 (한국어)
출력 형식: {"grounded":bool,"noHalluc":bool,"cited":bool,"refusal":bool,"score":int,"comment":"..."} — JSON 외 텍스트 금지.

[질문] …
[근거자료] …
[답변] …
필드뜻true/false의 의미
grounded답변이 검색 근거에서 나왔는지true는 근거에 닿았음, false는 근거 밖 진술이 있음
noHalluc없는 사실을 만들지 않았는지true는 지어낸 사실 없음, false는 환각 가능성
cited답변 안 [ID] 인용 여부true는 추적 가능한 표기 있음, false는 출처 연결 빠짐
refusal근거 부재를 정직하게 거부했는지true는 정당한 거부, false는 답변했거나 다른 이유로 거부
score세 핵심 기준을 반영한 정수 점수높으면 기준 충족 많음, 낮으면 다시 읽을 대상
comment한국어 한두 문장 평어긍정 평어는 통과 근거, 부정 평어는 확인할 결함

3. 로컬 자기평가의 한계까지 함께 기록한다

로컬(내 컴퓨터 안) 엔진에서는 답변을 만든 qwen3.5:2b 모델에게 같은 질문·근거·답변을 다시 보내요. 이때 세 가지를 지정해요. 답을 한 글자씩 흘려보내는 방식(스트리밍)은 꺼요. 모델이 속으로 생각하는 출력(사고 출력)도 꺼요. 형식은 JSON, 온도는 0으로 해요. 온도 0은 같은 입력에는 거의 같은 답을 내게 하는 설정이에요. 아래 한 줄은 그 설정이고, 읽기만 해도 돼요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

stream:false, think:false, format:"json", options:{temperature:0}

이 경로는 외부 API 키 없이 브라우저에서 로컬 Ollama(내 컴퓨터에서 모델을 돌려 주는 프로그램)를 불러 평가해요. 그래서 키 발급이나 서버 준비보다 판정 결과가 생성 결과와 어떻게 붙는지에 집중할 수 있어요. 다만 답변 모델과 평가 모델이 같은 2B 모델이라서, 이 평가는 독립 심사가 아니에요. 세밀한 사실 차이나 빠진 문맥을 거칠게 판정할 수 있어요. 이 한계를 화면과 기록에서 숨기지 않아야 해요. 이 판정을 믿고 쓰려면 함께 챙길 것이 세 가지예요.

  • 점수 체계 방어 — 모델이 가끔 5점 만점처럼 score를 돌려주면 score ≤ 5일 때 (score/5)×100으로 바꿔 100점 만점에 맞춰요.
  • 실패 방어 — JSON을 읽지 못하거나(파싱 실패) 호출이 실패하면 judgeError 배지만 남겨요. 이미 만든 답변과 화면(UI)은 그대로 둬요.
  • 사람 피드백과 대조 — 사람의 좋아요·싫어요가 판정 배지와 같은 방향이면, 자동 기준과 실제 사용 경험이 일단 맞은 거예요. 어긋나면 판정 기준이 놓친 유용함이나 사용자가 놓친 근거가 있는지, 답변·출처·평어와 함께 다시 읽어요.

4. 실습 — 근거 없는 질문에서 정당한 거부 확인하기

직접 해 보는 순서예요.

  1. 모두콘 챗봇에 "내일 날씨 어때?"를 넣어요. 만들어진 문장이 모르는 정보를 채워 넣지 않는지 먼저 읽어요.
  2. 답변 아래 판정 배지를 봐요. refusal:true와 grounded, noHalluc, cited, score, comment가 어떤 조합으로 나오는지 살펴요. 정당한 거부는 품질 낮은 침묵이 아니에요. 근거의 경계를 지킨 답변이라는 걸 확인해요.
  3. 질문 원문, 답변의 핵심 문장, 판정 배지와 평어를 실습 기록에 함께 적어요. 점수 하나만 남기지 말고 판정이 나온 맥락을 같이 남겨요.

이 실습에서 확인하려는 건 날씨를 알아내는 능력이 아니에요. 벡터스토어(숫자로 바꾼 자료를 모아 둔 곳)에 없는 정보를 만났을 때 검색·생성·판정이 각각 어느 선에서 멈추는지예요. refusal:true가 안 보이거나 근거 없는 정보가 만들어지면, 답변 문장만 고치지 마세요. 검색 근거와 프롬프트에서 "근거가 없을 때"를 다루는 갈래를 먼저 열어 원인을 기록해요.

정리

평가자를 만드는 일이 곧 답변을 만드는 일이에요. 판정 배지가 자동 채점 도구라 해도, 배지의 true와 false가 실제 답변·근거 청크와 맞는지는 결국 내가 다시 확인해야 해요. 이게 오늘의 결론이었어요. 심판을 다른 모델로 바꿔도 이 확인은 여전히 필요해요. 정답지가 불완전하면 심판이 맞는 답을 감점하는 일이 GraphRAG 채점 편에서 실제로 나왔어요. 다음 편에서는 이 판정 필드를 근거로 삼아요. 프롬프트와 검색 설정을 바꿔 가며, 스스로 세운 루브릭(채점 기준표)으로 실험해요.

이럴 때 의심하세요 — 판정 배지가 붙었는데 믿기 어려울 때

판정 배지는 화면에 항상 뭔가를 보여줘요. 그래서 이 단계의 문제는 "배지가 안 뜬다"가 아니에요. "배지는 뜨는데 배지와 답변이 서로 다른 말을 한다"는 모습으로 나타나요. 아래 네 줄이 그 어긋남을 짚는 자리예요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
답변 아래 출처 칩은 붙어 있는데, 칩을 눌러 원문을 읽으면 답변에 나온 날짜나 이름이 그 문서에 없다 판정 프롬프트가 아니라, 그 답변에 넘어간 근거 청크의 text와 답변 문장 두 개를 나란히 놓는 자리다 답변의 문장을 하나씩 근거 text에서 찾아본다. 못 찾는 문장이 있으면 칩이 있어도 근거 밖 진술이다. 칩은 "이 조각을 넘겼다"는 표시일 뿐 "그 조각대로 썼다"는 표시가 아니다
판정 배지가 거의 늘 통과로만 나온다. 사람이 읽으면 틀린 답인데도 점수가 높다 판정을 부르는 코드에서 지정한 모델 이름이다. 답변 생성에 쓴 모델과 같은지 본다 같은 모델이면 독립 심사가 아니라 자기평가라, 세밀한 사실 차이나 문맥 누락을 거칠게 넘긴다. 판정을 믿기 전에 몇 건은 사람이 직접 근거와 대조하고, 이 한계를 화면과 기록에 함께 남긴다
점수 칸에 4나 5처럼 작은 값이 섞여 들어와, 같은 표 안에 92점짜리와 4점짜리가 같이 남는다 판정 JSON을 받아 score를 저장하는 줄이다 score ≤ 5인 값이 있는지 센다. 모델이 5점 만점으로 답한 것이니 (score/5)×100으로 환산하고, 환산했다는 사실도 기록에 같이 남겨 나중에 두 체계가 다시 섞이지 않게 한다
답변은 멀쩡히 다 나왔는데 그 아래가 통째로 비거나 화면이 깨진다. 콘솔에 JSON 파싱 오류가 남아 있다 판정 응답을 JSON으로 읽는 부분과 그 주변의 오류 처리다. 생성 쪽 코드는 범인이 아니다 — 답변은 이미 잘 나왔다 파싱 실패와 호출 실패를 모두 잡아 judgeError 배지만 남기고, 이미 생성된 답변과 출처 칩은 그대로 두는지 본다. 판정은 뒤에 덧붙이는 층이라 실패해도 답변까지 무너뜨리면 안 된다

증상이 없어도, 판정을 처음 붙인 날에는 근거 없는 질문("내일 날씨 어때?") 하나를 일부러 넣어 보세요. refusal:true가 안 뜨면 배지가 제대로 도는 게 아니라 통과 도장만 찍고 있는 것일 수 있어요.

한 걸음 더: 여기서 만든 심사위원을 "답변"이 아니라 "에이전트의 행동 기록"에 적용하면 어떻게 되는지 다룬 글이 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정이에요. evidence_quote를 필수 칸으로 두어 인용 없는 점수를 막는 방법이 나와요.
