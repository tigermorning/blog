답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge

2026. 8. 28.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

리허설에는 모두콘 자료와 관계없는 "내일 날씨 알려줘" 같은 무근거 질문을 일부러 넣었다. 챗봇이 확인할 근거가 없다는 문장을 남기고, 날씨 정보를 지어내지 않으며, 빈 출처를 꾸며내지 않는지를 보는 사례다. 대화가 중단된 것처럼 보이는 결과와 자료 경계가 실제로 작동한 결과는 다르다 — 답변 본문과 출처 칩을 함께 읽어야 구별된다는 걸 오늘 배웠다.

1. 출처 칩만으로는 부족하다

모두콘 챗봇의 답변은 검색된 근거를 바탕으로 생성되지만, 출처 칩이 보인다는 사실만으로 답변 전체가 근거에 충실하다고 판정할 수는 없다. 그래서 질문·검색 근거·생성 답변을 함께 읽는 별도 평가자를 답변 뒤에 배치한다. 이 평가는 모델이 자기 문장을 완전히 객관적으로 증명한다는 장치가 아니라, 근거성·환각·인용·정당한 거부를 같은 화면에서 관찰하게 만드는 교육적 계측 장치다. 평가자는 답변을 다시 쓰거나 감추지 않고, 어떤 기준에서 통과했거나 불확실했는지를 판정 배지와 짧은 평어로 남긴다.

2. 여섯 필드로 판정을 데이터 구조로 읽기

판정 프롬프트는 평가 기준을 모호한 칭찬이나 인상으로 남기지 않고, JSON 필드와 판단 대상을 명시한다. 특히 근거 없는 질문에 답을 꾸며내지 않고 "없다"고 말한 경우는 실패가 아니라 refusal:true로 따로 분리해야, 챗봇이 무엇이든 답하는 도구가 아니라 확인 가능한 자료 안에서만 답하는 안내 도구가 된다.

당신은 RAG 챗봇 답변의 평가자입니다. 아래 [질문], [근거자료], [답변]을 읽고 다음 기준으로 JSON만 출력합니다.
grounded: 답변 내용이 근거자료에서 나왔는가 (true/false)
noHalluc: 근거에 없는 사실을 지어내지 않았는가 (true/false)
cited: 답변 안에 근거 조각의 [ID] 표시가 있는가 (true/false)
refusal: 근거에 답이 없어서 '없다'고 답한 경우 true, 그 외 false
score: 0-100 정수 (grounded·noHalluc·cited 반영)
comment: 한두 문장 평어 (한국어)
출력 형식: {"grounded":bool,"noHalluc":bool,"cited":bool,"refusal":bool,"score":int,"comment":"..."} — JSON 외 텍스트 금지.

[질문] …
[근거자료] …
[답변] …
필드뜻true/false의 의미
grounded답변이 검색 근거에서 나왔는지true는 근거에 닿았음, false는 근거 밖 진술이 있음
noHalluc없는 사실을 만들지 않았는지true는 지어낸 사실 없음, false는 환각 가능성
cited답변 안 [ID] 인용 여부true는 추적 가능한 표기 있음, false는 출처 연결 빠짐
refusal근거 부재를 정직하게 거부했는지true는 정당한 거부, false는 답변했거나 다른 이유로 거부
score세 핵심 기준을 반영한 정수 점수높으면 기준 충족 많음, 낮으면 다시 읽을 대상
comment한국어 한두 문장 평어긍정 평어는 통과 근거, 부정 평어는 확인할 결함

3. 로컬 자기평가의 한계까지 함께 기록한다

로컬 엔진에서는 답변 생성에 쓴 qwen3.5:2b에게 같은 질문·근거·답변을 다시 보내되, 스트리밍을 끄고 사고 출력도 끄며 JSON 형식과 온도 0을 지정한다.

stream:false, think:false, format:"json", options:{temperature:0}

이 경로는 외부 API 키 없이 브라우저의 로컬 Ollama 호출로 평가를 수행하므로, 키 발급이나 서버 구성보다 판정 결과가 생성 결과와 어떻게 붙는지에 집중할 수 있다. 다만 답변 모델과 평가 모델이 같은 2B 모델이라, 이 평가는 독립 심사가 아니다. 세밀한 사실 차이나 문맥 누락을 거칠게 판정할 수 있다는 한계를 화면과 기록에서 숨기지 않아야 한다. 모델이 간혹 5점 만점처럼 score를 반환하면 score ≤ 5일 때 (score/5)×100으로 환산해 점수 체계의 오해를 방어하고, JSON 파싱이나 호출이 실패하면 judgeError 배지만 남긴 채 이미 생성된 답변과 UI는 유지한다. 사람의 좋아요·싫어요 표시가 판정 배지와 같은 방향이면 자동 기준과 사용 경험이 일단 맞물린 사례로 읽고, 어긋나면 판정 기준이 놓친 유용성 또는 사용자가 놓친 근거를 답변·출처·평어와 함께 다시 읽는다.

4. 실습 — 근거 없는 질문에서 정당한 거부 확인하기

모두콘 챗봇에 "내일 날씨 어때?"를 넣고, 생성된 문장이 모르는 정보를 채워 넣지 않는지 먼저 읽는다. 답변 아래 판정 배지에서 refusal:true와 grounded, noHalluc, cited, score, comment가 어떤 조합으로 나타나는지 관찰하며, 정당한 거부가 낮은 품질의 침묵이 아니라 근거 경계를 지킨 답변임을 확인한다. 질문 원문, 답변의 핵심 문장, 판정 배지와 평어를 실습 기록에 함께 적어, 점수 하나만 남기지 않고 판정이 나온 맥락을 보존한다.

이 실습에서 확인하려는 건 날씨를 알아내는 능력이 아니라, 벡터스토어에 없는 정보를 발견했을 때 검색·생성·판정이 각각 어떤 경계에서 멈추는가다. refusal:true가 안 보이거나 근거 없는 정보가 생성되면, 답변 문장만 고치기보다 검색 근거와 프롬프트의 근거 부재 분기를 먼저 열어 원인을 기록한다.

정리

평가자를 만드는 일이 곧 답변을 만드는 일이다. 판정 배지가 자동 채점 도구라 해도, 배지의 true와 false가 실제 답변·근거 청크와 잘 맞는지는 결국 내가 다시 확인해야 한다는 게 오늘의 결론이었다. 다음 편에서는 이 판정 필드를 근거로, 프롬프트와 검색 설정을 바꿔가며 스스로 세운 루브릭으로 실험하는 단계로 넘어간다.

한 걸음 더: 여기서 만든 심사위원을 "답변"이 아니라 "에이전트의 행동 기록"에 적용하면 어떻게 되는지 다룬 글이 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정이에요. evidence_quote를 필수 칸으로 두어 인용 없는 점수를 막는 방법이 나와요.
