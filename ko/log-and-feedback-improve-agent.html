한눈에 — 다섯 단계는 이어지는 순서예요

이 글의 다섯 단계는 앞 단계의 결과가 다음 단계의 재료가 되는 순서예요. 그림 속 트레이스1는 메시지 하나를 처리한 단계별 기록이고, 피드백2은 사용자가 남긴 반응이에요.

비유로 먼저 — 식당 주방의 장부와 의견 카드

이 시리즈는 (11) 로그에는 200만 찍혔는데 사용자는 엉뚱한 답을 봤다에서 세운 식당 주방 비유를 끝까지 써요. 한 달 영업이 끝난 뒤 사장이 손에 든 것을 떠올려 보세요. 계산대 장부에는 팔린 주문이 하나도 빠짐없이 적혀 있고 주문마다 어느 레시피 판으로 만들었는지 번호가 붙어 있지만, 손님이 맛있게 먹었는지는 적혀 있지 않아요. 맛은 두 군데서 짐작할 수 있어요. 테이블에 둔 "별로예요" 카드는 손님이 직접 쓰지만 쓰는 사람이 적고 불만이 있는 손님이 더 자주 써요. 카드를 안 써도 손님이 "아니, 그게 아니라"라고 다시 말하거나 같은 주문을 또 넣는 것으로 불만을 읽을 수 있어요. 그래서 사장은 카드가 꽂힌 주문서부터 열어 보고, 같은 문제가 정말 몇 번 있었는지는 장부 전체를 훑어 세요.

비유 속 요소원래 개념
계산대 장부 — 모든 주문이 남음, 만족 여부는 없음로그·트레이스 — 모든 대화가 남지만 사용자가 만족했는지는 안 적힘
"별로예요" 카드 — 손님이 직접 씀, 쓰는 사람이 적음명시적 피드백 — 눌러서 남긴 반응
손님이 "아니, 그게 아니라"라고 다시 말함, 같은 주문을 또 넣음암묵적 피드백 — 행동에서 읽는 반응(정정, 같은 질문 재전송)
카드가 꽂힌 주문서부터 열어 봄어느 트레이스부터 읽을지 정하는 데 피드백을 씀
같은 문제가 몇 번 있었는지 장부 전체에서 셈반복 횟수는 전체 로그에서 셈
어느 레시피 판으로 만든 주문인지 적힌 표시version·release — 배포 버전별로 나눠 비교하는 기준

핵심 한 줄: 로그는 "무슨 일이 있었나"를 빠짐없이 알려 주고, 피드백은 "어디부터 읽을까"를 알려 주지만, 둘 다 "무엇이 문제인가"를 대신 말해 주지는 않아서 사람이 읽고 세어야 해요.

다만 비유가 끊기는 점이 있어요. 식당 사장은 "별로예요" 카드를 쉽게 받지만, 제 서비스 «루틴 도장»에는 그 카드(좋아요·별로예요 버튼)가 아직 없어요. 그래서 이 글의 실제 사례는 카드 없이 장부와 손님의 말투만으로 문제를 찾아요.

다섯 단계 — 단계마다 남길 근거가 정해져 있어요

다섯 단계가 하는 일과 남기는 근거는 위 그림이 보여 준 그대로예요. 그림을 보기 어렵거나 한 단계만 찾아 읽고 싶다면 표로 펼쳐 보세요.

▼ 다섯 단계를 표로 보기 (그림과 같은 내용)
단계하는 일남길 근거
1. 모으기쌓인 트레이스를 확인하고, 모자라면 직접 대화해서 만듦트레이스 수, 피드백 수
2. 찾기별로예요, 정정한 턴, 짧게 끊긴 세션, 느리거나 비싼 답, 오류를 걸러 읽고 후보를 3개 이상 찾음후보마다 트레이스 링크와 반복 횟수
3. 고르기빈도·영향·고치는 비용을 비교해 하나를 고름비교표와 고른 이유
4. 고치기문제 트레이스와 정상 대화로 데이터셋을 만들고, 한 가지만 바꿔 전후 비교실험 결과, PR
5. 확인하기배포 뒤 데이터셋에 없는 새 대화를 보내고 version으로 나눠 비교버전별 트레이스와 판단

단계마다 지킬 것은 네 가지예요.

  • 이상한 답 하나로 문제를 정하지 않아요. LLM의 답은 매번 달라서 같은 현상이 다른 트레이스에도 있는지 세어 봐요.
  • 데이터셋에는 문제 항목과 정상 항목을 같이 넣어요. 정상 항목이 없으면 고친 뒤 원래 잘 되던 대화가 나빠진 걸 놓쳐요.
  • 한 번에 한 가지만 바꾸고, 실험 전에 내보낼 기준을 숫자로 먼저 적어요. 결과를 본 뒤 기준을 정하면 조금이라도 나아진 쪽으로 기울어요.
  • 확인할 때는 데이터셋과 똑같은 문장 대신 표현을 바꾼 새 대화를 보내요. 데이터셋에 맞춰진 것과 정말 나아진 것을 가르려는 거예요.

  • 운영 서버(Cloud Run)에는 아직 올리지 않았어요. 고친 코드를 로컬에서 release=v2-fix 이름표를 붙여 돌려 버전별로 비교했어요.

왜 ①이 원인이 "한도"라고 봤을까요? 빈 답 16개 모두 답 쓰기 단계의 출력 토큰이 정확히 450이었고, 거부나 오류가 없었어요. 같은 요청을 API로 직접 보내 보니 응답이 thinking 블록(보이는 글자 0)과 text 블록(26자)이었고 중단 이유는 max_tokens였어요. 한도를 1500으로 올리자 정상 종료했고 출력은 778토큰, 보이는 글은 204자였어요. 즉 모델이 답하기 전에 하는 숨은 생각이 같은 토큰 한도를 먹어서, 한도가 작으면 글이 나오기 전에 멈춘 거예요(제가 확인한 건 이 모델·이 설정에서예요).

4. 고치기 — 데이터셋, 기준 먼저, 한 가지씩

빈 답 16턴(문제 항목)과 비지 않고 잘 끝난 16턴(정상 항목)으로 데이터셋4 32개를 만들었어요. 그리고 실험 전에 기준 5개를 적어 뒀어요: ① 문제 항목 빈 답 1개 이하, ② 정상 항목은 전부 정상, ③ 한도에 걸려 끊긴 답 2개 이하, ④ 응답 시간 p905이 기준선의 1.5배 이하, ⑤ 모드가 바뀐 항목 4개 이하.

  • B는 실패한 시도예요. 가장 빠르고 쌌지만, 정상 항목이던 연구 수치 질문(«작게 시작하면 성공률이 몇 퍼센트 올라가요?»)이 «근거를 못 찾았어요»에서 숫자가 든 조언으로 바뀌어 숫자 검사에 걸렸어요. 정상 항목이 나빠졌으니 기준 ②를 못 지켰고, 그래서 채택하지 않았어요.
  • 기준선을 다시 돌리니 문제 항목 16개 중 13개만 또 비었어요. LLM은 같은 입력에도 답이 달라서, 같은 조건에서 다시 돌린 기준선과 비교해야 해요.

데이터셋에 없는 새 대화 12개(45턴)를 표현과 주제를 바꿔 지어서, 옛 동작과 고친 동작에 같은 방식으로 보냈어요. 트레이스에 버전 이름표(release)를 붙여 Langfuse에서 나눠 셌어요.

처음 67턴(옛 코드)6016 (27%)32 (53%)5.6 / 6.5초$0.01519
새 대화, 옛 코드389 (24%)17 (45%)4.8 / 5.9초$0.01422
새 대화, 고친 코드380 (0%)0 (0%)4.9 / 7.1초$0.01493

같은 새 대화에서 빈 답이 9건에서 0건이 됐어요. 대가는 p90이 5.9 → 7.1초(+20%), 비용이 한 턴 평균 +5%예요. 읽을 때 주의할 점도 있어요. 대화마다 앞 답이 달라서 두 버전이 똑같은 입력을 받은 건 아니고, 표본은 38턴이라 «앞으로 0건»이라는 뜻은 아니에요. 그리고 ③ 퀘스트 빈칸은 이번에 안 고쳤기 때문에 새 대화에서도 그대로였어요(퀘스트 5턴 모두 빈칸). 그게 다음 차례예요.

나쁜 선택 vs 좋은 선택 — "답이 이상할 때가 있어요"라는 말을 들었을 때

나쁜 선택좋은 선택
눈에 띈 답 하나를 보고 지시문을 고친다 → 그 답은 좋아졌는데, 사실 더 자주 일어나던 빈 답 16건은 그대로예요. 고친 뒤 "나아졌다"는 증거도 없어요. 대화를 모아 문제 후보를 5개 뽑고 횟수를 센 뒤, 비교표로 하나를 골라요. 문제·정상 항목 데이터셋에 기준을 먼저 적고 고친 뒤, 새 대화를 버전별로 나눠 확인해요 → 빈 답이 9건에서 0건이 된 것도, 생각 끄기가 정상 항목을 망친 것도 숫자로 보였어요.

식당으로 말하면, 왼쪽은 손님 한 분의 말만 듣고 레시피를 바꾸는 것이고, 오른쪽은 장부 전체를 훑어 가장 자주 틀리고 영향이 가장 큰 메뉴부터 고치고 판 번호별로 손님 반응을 비교하는 거예요.

이럴 때 의심하세요 — 서비스를 연 직후와 고친 직후

이 문제들은 서버 로그가 아니라 "사용자가 본 것"에서 먼저 나타나요. 증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "이 답 이상하니까 지시문 고쳐 줘" — 같은 현상이 다른 트레이스에 몇 번 있는지부터 센다.
  • "모델을 바꿔 줘" — 답 쓰기 단계의 출력 토큰과 한도가 같이 바뀌었는지 본다.
이런 증상이 보이면먼저 열어 볼 자리확인 방법
사용자 화면에 답이 통째로 비어 있는데 서버 로그는 POST /api/chat 200이에요. 트레이스의 답 쓰기 단계(generate-reply)의 출력 토큰과 reply_chars. 모드 고르기·카드 선택 단계는 범인이 아닌 경우가 많아요. 출력 토큰이 한도 숫자(예: 450)와 정확히 같고 글자 수가 0이면 한도 문제를 의심해요. 코드의 한도 상수를 찾아 올려 보고, 같은 대화를 다시 보내 달라진 점을 봐요. 모델이 바뀌면 한도가 부족해질 수 있어요(직접 해 본 기록).
이상한 답을 하나 보고 바로 고치고 싶어져요. 같은 단계의 다른 트레이스 전체(기간·환경으로 거른 목록). 같은 현상이 몇 번인지 세어 적어 봐요. 1~2번이면 후보 목록에 올려만 두고, 자주 나오는 것부터 비교표에 넣어요.
"고쳤어요"라고 하는데 어디가 나아졌는지 숫자가 없어요. 실험 전에 적어 둔 기준 문서와 데이터셋의 정상 항목. 기준이 실험 뒤에 적혔다면 믿지 않아요. 정상 항목이 나빠진 곳이 있는지, 새 대화로 버전별 숫자를 나눠 다시 봐요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

내 서비스에서 답을 만드는 단계의 최대 출력 토큰(max_tokens) 설정을 모두 찾아서
파일·줄 번호로 보여 줘. 모델을 바꿔 쓰는 경로가 있으면 경로마다 따로 보여 줘.
아직 코드는 고치지 마.

이 글에 나온 숫자 — 내 서비스 기록을 읽을 때 비교할 값

위 «직접 해 본 기록»에서 잰 값 중 자기 서비스를 볼 때도 기준이 되는 것만 모았어요. 모두 이 PC에서 Claude(claude-sonnet-5-5, 지어낸 대화)로 2026-11-09에 잰 값이라 모델·설정이 다르면 달라져요.

무엇의 숫자인가값알아 둘 것
답 쓰기 단계의 출력 토큰 한도(고치기 전)450이 값에 정확히 걸린 트레이스가 문제 후보의 단서였어요. 한도가 숨은 생각까지 포함하는 모델이면 보이는 글이 이보다 훨씬 짧아져요.
고친 뒤 한도1500이 설정에서 한도에 닿은 답이 0개였어요(이 모델 기준).
한도에 닿은 답의 비율(옛 코드)60턴 중 32 (53%)빈 답 16 + 끊김 16. 반 넘게 한도에 걸리면 한도 자체를 의심해요.
같은 입력을 다시 돌린 기준선의 빈 답16개 중 13개LLM은 같은 입력에도 답이 달라서, «고치기 전»도 한 번 더 돌려 기준선으로 써요.
한도를 올린 뒤 p90 시간 변화6.0 → 8.5초(데이터셋 재생), 5.9 → 7.1초(새 대화)답이 느려지는 비용도 같이 적어야 «내보낼 만한가»를 판단할 수 있어요.
새 대화에서 빈 답9건(24%) → 0건표본 38턴이라 «0건 유지»는 보장이 아니에요.

직접 해보기 — 내 서비스에서 한 바퀴

  1. 최근 트레이스를 20개 이상 모아요. 모자라면 사용자 유형을 바꿔 가며 20턴 이상 직접 대화해 만들어요(실제 개인정보는 쓰지 않아요).
  2. "답이 비었다·정정했다·같은 질문을 또 했다·너무 느리다·오류가 났다"로 걸러 읽고 후보를 3개 이상 적어요. 후보마다 횟수와 트레이스 링크를 같이요.
  3. 빈도·영향·고치는 비용 표를 만들고 하나를 골라요. 고르지 않은 이유도 한 줄씩 적어요.
  4. 문제 항목과 정상 항목을 같은 수로 모아 데이터셋을 만들고, 고치기 전에 내보낼 기준을 숫자로 적어요.
  5. 한 가지만 바꿔 같은 데이터셋으로 돌리고, 기준을 못 지키면 그 시도는 «실패한 시도»로 남기고 다른 변형을 시도해요.
  6. 배포 후 표현을 바꾼 새 대화를 보내고 버전별로 나눠 세요. 나아지지 않았다면 그 결과와 이유를 적는 것도 완료예요.
  1. 트레이스 — 사용자 메시지 하나를 처리하는 동안 거친 단계들을 한 묶음으로 남긴 기록이에요((11)에서 자세히 다뤘어요). ↩
  2. 피드백 — 사용자가 답에 남긴 반응으로, 좋아요·별로예요 같은 명시적인 것과 정정·재질문처럼 행동에서 읽는 암묵적인 것이 있어요. ↩
  3. Langfuse — 에이전트가 한 일을 트레이스로 모아 보고 점수·데이터셋·실험까지 다루는 관측 도구예요((11) 참고). ↩
  4. 데이터셋 — 같은 문항 묶음으로 고치기 전과 후를 비교하려고 모아 둔 입력 목록이에요((12) 참고). ↩
  5. p90 — 응답 시간을 짧은 것부터 줄 세웠을 때 90% 지점의 값으로, 열 번 중 아홉 번은 이 시간 안에 끝난다는 뜻이에요. ↩
