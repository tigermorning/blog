MVP는 완벽이 아니라 하나는 끝까지 되는 것 — 메인 퀘스트 착수기

2026. 8. 28.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

지금까지 배운 조각(PRD·화면·데이터베이스·배포)을 하나로 모아 "내 서비스"를 만드는 메인 퀘스트가 시작됐다. 첫 시간에 나온 경고가 인상 깊었다 — "지민"이라는 가상의 학습자가 첫 프롬프트에 "회원가입, 게시판, 댓글, 알림까지 한 번에 다 만들어줘"를 넣었다가 AI가 뭘 먼저 손대야 할지 갈피를 못 잡고 뒤엉킨 사례였다. 오늘은 이 실패를 안 밟는 법을 배웠다.

1. MVP — 부끄럽지 않으면 너무 늦게 낸 것

MVP(Minimum Viable Product, 최소 기능 제품)는 "완벽한 작은 버전"이 아니라 "하나는 끝까지 되는 버전"이다. 링크드인 창업자 Reid Hoffman의 말이 이 마인드셋을 요약한다.

"부끄럽지 않다면, 첫 버전을 너무 늦게 낸 것이다."

기능을 다 갖췄지만 하나도 완성 안 된 상태보다, 기능은 하나뿐이지만 처음부터 끝까지 실제로 동작하는 상태가 낫다는 뜻이다. 화면은 예쁜데 저장이 안 되는 것보다, 화면은 투박해도 저장 버튼을 누르면 진짜로 저장되는 쪽을 고른다.

2. 다섯 재료 레시피

메인 퀘스트를 완성하는 다섯 재료가 이렇게 정리됐다.

재료뜻
PRDProduct Requirements Document, 무엇을 왜 만드는지 적은 한 장짜리 문서
하네스AI 에이전트가 작업하는 작업대(터미널·Node.js·npm·git 등 도구 묶음)
화면 + 목업데이터실제 데이터 없이도 화면이 돌아가게 하는 가짜 데이터
저장(DB 또는 Supabase)새로고침해도 안 사라지는 진짜 저장소
배포남도 접속할 수 있는 웹 주소로 내보내기

같이 나온 용어집도 정리해 둔다 — MVP(최소 기능 제품), 목업데이터(임시 가짜 데이터), CRUD(Create·Read·Update·Delete, 데이터를 다루는 네 기본 동작), 하네스(에이전트의 작업 환경), 환경변수(코드에 안 적고 따로 관리하는 비밀값), 커밋(작업 상태를 저장하는 기록점), 배포(웹에 실제로 올리는 것). PRD를 쓰는 여덟 개 자기 질문은 이미 RAG 챗봇 PRD 편에서 다뤘던 것과 같은 틀이라 여기선 되풀이하지 않는다.

3. 제출 루브릭 — 착수할 때부터 채점 기준을 본다

Main Quest 01 제출물은 네 가지다 — 배포 링크, PRD 문서, 저장소 링크, 회고. 채점은 가중치 다섯 기준으로 나뉜다.

기준비중
도메인 연결성 — 내 도메인 문제와 실제로 맞닿아 있는가25%
기능 완성도 — 만든 기능이 끝까지 동작하는가25%
AI 활용도 — AI를 얼마나 효과적으로 썼는가20%
회고 깊이 — 무엇을 배우고 무엇이 남았는지15%
발표·시연 — 실제로 보여줄 수 있는가15%

기능 완성도와 AI 활용도를 합치면 45%다. 화려한 기능 개수보다 "적게 만들고 끝까지 되게 하기"가 채점 구조 자체에 박혀 있다는 뜻이다.

4. 막혔을 때 — AI와 만들어 나가는 네 가지 규율

실습이 길어질수록 결국 부딪히는 문제는 기능이 아니라 "AI가 같은 버그를 못 고치고 빙빙 도는" 순간이다. 이때를 위한 네 규율.

  1. 한 번에 하나만 — 프롬프트 하나에 여러 개를 요구하면 몇 개는 맞고 몇 개는 틀려 디버깅이 더 어려워진다. 버그 하나 고치고 확인하고 다음으로.
  2. 작동하면 저장(커밋) — 바뀔 때마다가 아니라 작동할 때마다 저장한다. 뭔가 깨지면 마지막으로 잘 되던 지점으로 되돌리면 된다.
  3. 막히면 되돌리고 리셋한다 — 랜덤하게 이것저것 바꾸라고 시키는 대신, 5~10번마다 "지금까지 뭐가 됐고 뭐가 남았고 지금 문제는 뭐다"로 AI의 초점을 다시 맞춘다.
  4. 이해 못 한 코드는 배포하지 않는다 — 시제품 단계에선 다 수락해도 괜찮지만, 남에게 내보낼 거라면 무엇을 하는 코드인지 알아야 한다. Veracode의 2025 GenAI 코드 보안 보고서는 조사한 AI 생성 코드 표본의 약 45%가 보안 결함으로 나왔다고 보고했다(해당 연구의 표본·기준에서 나온 수치).

둠 루프(doom loop) — 마지막 10%의 늪

"거의 다 됐는데" 버그 하나가 안 잡히고, AI는 "고쳤다"는데 실제론 안 고쳐지고, 프롬프트를 더 넣을수록 멀쩡하던 기능까지 깨지는 상황에 이름이 붙어 있었다 — 둠 루프. 대화가 길어지며 맥락이 오염되고, AI에겐 "무엇이 무엇에 의존하는지"의 지도가 없어 원인이 아니라 증상만 계속 땜질하기 때문에 생기는 구조적 문제다. 빠져나오는 법은 규율 3번의 실전판이다 — 같은 프롬프트를 반복하지 말고 한 발 물러서 전체 그림을 다시 보자고 시키기, 마지막으로 작동하던 지점으로 되돌린 뒤 새 대화로 다시 시작하기, "로그인 시스템 고쳐줘" 대신 "로그인 폼이 데이터를 제대로 보내는지부터 확인하자"처럼 문제를 잘게 쪼개기. 막힘이 30분을 넘기면 더 파기 전에 멈추고 되돌리는 쪽이 대개 더 빠르다.

고무 오리에게 설명하기

개발자들 사이의 오래된 방법 — 러버덕 디버깅(rubber duck debugging). 막힐 때 책상 위 고무 오리 인형에게 코드를 한 줄씩 소리 내어 설명하면, 설명하다가 스스로 답을 찾는 경우가 많다. 원리는 심리학의 '자기 설명 효과' — 머릿속에선 슬쩍 넘어가던 당연한 전제가 말로 옮기는 순간 빈틈을 드러낸다. 바이브 코딩에서는 AI가 그 고무 오리 역할을 한다. 막혔을 때 "지금 뭘 하려는 거고, 무엇까지 됐고, 어디서 막혔는지"를 처음부터 또박또박 적어 AI에게 설명하는 것만으로 문제의 상당 부분이 스스로 보인다.

5. 오늘의 회고 질문

마무리 시간에 던져진 세 질문을 그대로 옮겨 둔다 — 나중에 프로젝트를 되짚을 체크포인트로 쓸 만하다.

  • 오늘 "자르기"가 가장 아까웠던 기능은? 그래도 자른 이유는?
  • 막혔을 때 나를 가장 도와준 규율(한 번에 하나 / 작동하면 저장 / 막히면 리셋 / 이해한 것만 배포)은?
  • 완성까지, 지금 가장 겁나는 부분은 무엇인가?

정리

메인 퀘스트의 핵심은 기능을 많이 넣는 게 아니라 범위를 잘라내는 용기였다. PRD로 방향을 정하고, 다섯 재료로 하나씩 쌓고, 막히면 네 규율로 다시 초점을 맞추고, 둠 루프가 보이면 파고들지 말고 되돌린다 — 완벽한 버전이 아니라 부끄러워도 끝까지 동작하는 버전을 먼저 낸다.
