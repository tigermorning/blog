1편에서 맡길 일을, 2편에서 화면과 모델 연결을 정했어요. 그런데 이런 요청이 들어왔다고 해 볼게요.

실습 폴더의 안내문을 읽고 준비물을 정리해 줘.

모델이 파일 읽기를 요청하고, 하네스가 내용을 돌려주고, 모델이 답을 씁니다. 여기까지는 쉬워요. 그런데 파일이 없으면 어떻게 하죠? 읽는 대신 수정하겠다고 하면 바로 실행해도 될까요? 같은 요청을 계속 반복하면 언제 끝내야 할까요?

기능 목록으로는 이 셋이 정해지지 않아요. 이번 편은 요청이 들어온 뒤 완료될 때까지의 흐름과 지금 어느 단계인지를 나타내는 상태를 설계합니다. 아직 코드는 안 써요.

비유 — 은행 창구의 전광판

은행에 갔다고 해 볼게요. 번호표를 뽑고 앉으면 벽에 붙은 전광판에 지금 내 순서가 어디쯤인지 떠요. 대기 중, 처리 중 같은 글자로요.

창구에 앉으면 직원이 이체 화면을 돌려 보여 줘요. "수취인과 금액 확인하시고 서명해 주세요." 제가 서명하기 전까지 돈은 나가지 않아요. 여기서 서명은 지금 화면에 뜬 이 이체 한 건에 대한 동의지, "앞으로 내 계좌에서 뭐든 빼도 좋다"는 뜻이 아니에요.

제가 "아니요, 금액이 틀렸네요"라고 하면 어떻게 될까요. 이체는 안 됩니다. 그리고 직원이 같은 화면을 다시 들이밀거나, 이름만 바꿔 '송금'이라는 다른 메뉴로 몰래 처리하면 그건 사고예요.

마지막으로 창구에는 마감 시간이 있어요. 서류가 계속 부족해서 다섯 번을 왔다 갔다 하다 보면, 창구는 "오늘은 여기까지입니다"라고 멈춰요. 이때 전광판에 완료가 뜨면 안 되죠. 마감으로 중단이라고 떠야 맞아요.

벽에 붙은 전광판 글자상태1 — 사용자와 프로그램이 공유하는 현재 단계

창구 마감 시간반복 횟수·시간 상한
"마감으로 중단"이라는 안내제한에 도달한 종료를 완료와 구별해 표시

핵심 한 줄: 전광판에 완료가 떴는데 창구에서는 아직 서류를 기다리고 있다면, 잘못된 건 창구가 아니라 전광판이에요.

다만 비유가 끊기는 점이 있어요. 은행 창구는 마감이 지나면 진짜로 문을 닫지만, 반복 상한은 "작업이 끝난다"는 보장이 아니에요. 끝없이 도는 상황을 다루기 위한 장치일 뿐, 상한 안에 답이 나온다는 약속은 어디에도 없어요.

전체 흐름 — 정상 경로와 실패 경로를 같은 그림에서

읽는 법: 실선은 정상 경로, 점선은 실패·거절 경로예요. 같은 그림을 손가락으로 두 번 따라가 보세요 — 한 번은 실선만, 한 번은 점선만요.

정상 경로를 먼저 따라가면 이래요. 모델의 도구 요청과 실제 도구 실행은 서로 다른 단계예요. 모델은 무엇을 하고 싶은지 표현하고, 하네스가 그걸 검사한 뒤 실행합니다. 모델이 "파일을 읽었습니다"라고 답한 것만으로 실제 읽기가 일어난 게 아니에요.

이제 같은 그림에서 실패 경로를 따라가요. 여기서 갈리는 게 하나 있어요.

  • 계속할 수 있는 오류 — "파일이 없습니다"는 모델에게 전달하면 다른 경로를 찾아볼 수 있어요.
  • 작업을 끝내야 할 오류 — 인증 오류로 모델 연결 자체가 안 되면, 도구 결과를 더 보내 봐야 해결되지 않아요.

이 둘을 구별해 두는 게 이번 편의 절반이에요.

상태 — 사용자가 무엇을 알 수 있어야 하나

상태는 터미널이면 짧은 출력으로, 웹이면 화면 표시로 드러내요. 이름은 제 제품에 맞게 정하면 됩니다.

상태 예뜻사용자가 알 수 있어야 할 내용
준비아직 실행하지 않음어떤 작업을 요청할 수 있는지
실행 중모델 호출 또는 도구 처리가 진행됨현재 진행 단계
승인 대기사용자 판단 없이는 다음 행동을 하지 않음승인할 구체적인 변경
완료정한 종료 조건을 만족함결과와 수행한 작업
실패 · 중단더 진행할 수 없거나 정책상 멈춤이유와 이미 수행한 범위

내부 단계를 전부 별도 화면 상태로 만들 필요는 없어요. 모델 대기와 도구 실행을 같은 "실행 중"으로 묶어 표시하되 기록에서만 구별해도 됩니다. 중요한 건 두 가지예요 — 멈춰 있는데 완료라고 표시하지 않기, 승인을 기다리면서 이유를 숨기지 않기.

승인과 거절 — 거절 다음도 설계에 들어가요

D06에서는 승인받을 행동과 보여 줄 정보를 정해요. 코딩 작업이라면 수정할 파일과 변경 내용을 보여 준 뒤 적용을 승인받는 방식이죠. 이때 승인은 "앞으로 모든 파일을 바꿔도 좋다"가 아니라 제시한 그 변경에 대한 허용이에요.

거절했을 때의 동작도 정해야 해요. 두 갈래가 있어요.

  • 작업 전체를 멈춘다 — 가장 단순하고 예측 가능해요.
  • 변경하지 않았다는 결과를 모델에게 전달한다 — 읽기만으로 가능한 답변을 쓰게 할 수 있어요.

어느 쪽을 고르든 같은 변경을 계속 다시 요청하거나, 거절된 행동을 다른 도구 이름으로 실행하는 흐름은 허용하지 않습니다. 앞의 비유에서 '이름만 바꿔 송금 메뉴로 처리'하던 그 장면이요.

그리고 한 층 더 앞에 두는 규칙이 있어요. 작업 범위 밖의 경로 접근은 승인을 묻기 전에 거절하도록 설계할 수 있어요. 이건 승인 여부의 문제가 아니라 애초에 제품이 허용하지 않은 행동이니까요. "승인 버튼이 있으니 무엇이든 요청할 수 있다"는 구조와, "허용한 범위 안에서 추가 확인을 받는다"는 구조는 완전히 달라요. 이 경계 감각은 안전하게 쓰고 평가하기 — 권한·회귀·과제 제출 (3)과 덜어내기와 경계 긋기 (4)에서 다뤘던 내용과 이어져요.

나쁜 선택 vs 좋은 선택

같은 은행 창구에서, 마감 시간이 되었을 때의 두 가지 안내예요.

나쁜 선택좋은 선택
무엇을 했나: 반복 상한에 도달하자 루프를 빠져나오면서 그때까지 모델이 쓴 마지막 문장을 최종 답변으로 출력하고, 상태를 완료로 찍었어요.

무슨 일이 생기나: 사용자는 정리가 끝난 줄 알고 그 요약을 회의에 그대로 씁니다. 실제로는 파일 세 개 중 하나만 읽은 상태였고요. 중단을 완료로 표시한 순간, 기록은 남아 있어도 아무도 안 봐요.		 무엇을 했나: 상한에 도달하면 "제한에 도달해 중단"이라는 별도 상태로 끝내고, 이미 읽은 자료 목록과 적용한 변경이 있으면 그 사실도 함께 남겼어요.

무슨 일이 생기나: 사용자가 "덜 끝났다"는 걸 즉시 알아요. 상한을 올릴지, 요청을 쪼갤지, 다른 파일부터 볼지 판단할 재료가 남습니다.

반복을 끝내는 조건

모델이 계속 도구를 요청하면 프로그램도 계속 실행할 수 있어요. 그래서 종료 조건을 "모델이 최종 답변을 냈을 때" 하나에만 맡기지 않아요. 함께 정할 것은 이래요.

  • 반복 횟수의 상한
  • 대기 시간의 상한
  • 같은 실패가 반복될 때의 처리

구체화하면 이런 문장이 나와요. 이건 정답이 아니라 예시예요 — 자기 도구와 사용 장면에 맞게 다시 정합니다.

파일을 못 찾으면 모델이 다른 경로를 한 번 확인할 수 있게 하자.
권한 밖 경로는 실행하지 말고, 반복 제한에 도달하면 이유를 보여 주고 멈추자.

작업과 세션 — 다른 단위예요

두 단어가 자주 뒤섞이는데, 이렇게 갈라요.

  • 작업(task) — 사용자의 요청 하나를 처리하는 실행 단위.
  • 세션(session)2 — 이어지는 대화 맥락을 묶는 단위.

안내문을 정리한 뒤 "그중 내일 필요한 것만 골라 줘"라고 물으면, 그건 새 작업이지만 같은 세션이에요.

D07에서는 첫 버전의 저장 범위를 골라요. 프로그램이 켜져 있는 동안에만 대화를 유지할 수도 있고, 메시지와 기록을 파일에 저장해 재시작 후 이어갈 수도 있어요. 메모리만 쓰는 선택도 괜찮지만, 종료하면 대화가 사라진다는 한계를 사용자에게 분명히 알려야 해요. 그리고 대화 저장과 변경한 파일의 이전 버전 복원은 별개 기능이에요 — 대화를 저장한다고 파일이 되돌아가지 않아요.

취소 버튼이나 실행 중 중단 명령은 D09의 선택 확장이에요. 안 넣기로 했다면 "미뤘다"고 기록하고, 넣기로 했다면 표시만 바꾸는지 실행 중인 프로세스도 정리하는지까지 설계해야 해요. 그리고 사용자 거절, 반복 상한으로 인한 중단, 사용자가 누른 취소는 서로 다른 사건이니 하나로 뭉뚱그리지 않습니다.

직접 해보기

개발 도우미에게 흐름을 그려 달라고 요청할 때, 실패 경로를 처음부터 같이 요구하는 게 요령이에요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

우리가 정한 작업이 끝날 때까지의 흐름을 그려 줘. 도구 실패와 승인 거절 때도 어떻게 되는지 같이 보자.
  1. 바꿀 것 — 상황 세 개를 자기 그림에 대입해요. ①정상적인 읽기 작업 ②파일을 찾지 못한 작업 ③코드 변경을 거절한 작업.
  2. 측정할 것 — 각 경우의 마지막 상태 이름과 사용자에게 보여 줄 문장을 소리 내어 말할 수 있는지 봐요. 말이 막히는 칸이 설계의 빈틈이에요.
  3. 비교할 것 — 정상 경로에만 있고 실패 경로에는 없는 안내가 있는지 찾아요. 대개 "왜 멈췄는지"가 빠져 있어요.

이 세 가지 상황을 우리 흐름에 대입해서 빈틈을 찾아 줘. 합의한 상태와 종료 조건을 문서에 반영해 줘.

마지막으로 못 박아 둘 것 하나. 그림에 화살표가 있다는 사실이 동작이 구현됐다는 뜻은 아니에요. 여기서 만든 건 나중에 "실제 실행이 이 흐름을 지켰는가"를 대조할 기준이에요. 다음 편에서는 이 상태들이 주고받을 값의 모양 — 인터페이스를 정합니다.

함께 읽으면 좋은 글

  • 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동 — 반복이 끝나지 않는 문제를 처음 본 글이에요.
