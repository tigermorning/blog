도구를 하나씩 부르는 대신 코드를 쓴다 — CodeAct 논문 읽기

원문: Executable Code Actions Elicit Better LLM Agents (arXiv, 2024.02.01 · Wang, Chen, Yuan 외)

2026. 9. 2.

※ 이 글은 위 논문을 제 나름의 언어로 쉽게 풀어 정리한 것입니다.

전에 봤던 ReAct 루프는 "생각하고 → 행동하고 → 결과를 관찰하고 → 다시 생각한다"를 반복하는 순환이었어요. 그리고 도구를 실제로 설계할 때는 그 "행동" 한 번을 보통 정해진 스키마에 맞춘 JSON 형식으로 적었고요. 이번 논문은 그 "행동을 적는 형식" 자체를 건드려요 — JSON이나 자유 텍스트 대신, 파이썬 코드 자체를 행동으로 쓰면 어떻게 되는가를 실험한 논문이에요.

1. 문제의식 — 행동을 적는 형식도 형식이다

지금까지 에이전트가 도구를 부르는 방식은 크게 두 갈래였어요. 하나는 자유 텍스트로 "재고를 조회해줘"처럼 문장으로 적고 하네스가 그 문장에서 의도를 다시 해석하는 방식, 다른 하나는 스키마에 맞춘 JSON으로 {"tool": "check_stock", "sku": "A-17"}처럼 구조화해서 적는 방식이에요. 둘 다 한 턴에 도구 하나를 부르는 게 기본 단위예요.

문제는 할 일이 "도구 하나를 한 번 부르기"보다 복잡해질 때 생겨요. 파일 10개를 똑같은 방식으로 처리해야 한다면 JSON 방식으로는 도구 호출을 10번 반복해야 하고, "A가 실패하면 B를 대신 시도한다" 같은 조건 분기도 매 턴 모델이 처음부터 다시 판단해야 해요. 논문 저자들은 이런 반복 작업에서 코드로 for문 하나를 쓰면 같은 일을 최대 30% 더 적은 행동 수로 끝낼 수 있다고 말해요 — 프로그래밍 언어가 원래 갖고 있던 반복·조건·변수라는 도구를, 행동 형식에도 그대로 가져오자는 게 이 논문의 출발점이에요.

2. CodeAct란 무엇인가 — 행동 자체가 파이썬 코드

논문은 에이전트 루프를 에이전트·사용자·환경 세 역할로 정의해요. 매 턴마다 에이전트는 사용자나 환경으로부터 관찰(입력)을 받고, 필요하면 생각을 거쳐 행동(출력)을 내놓아요. CodeAct에서는 이 행동이 전부 파이썬 코드예요. 그리고 그 코드를 실제로 실행한 결과 — 정상적인 출력이든, 에러 메시지든 — 를 그대로 다음 관찰로 돌려받아요. JSON 방식이 "무엇을, 어떤 값으로 부를지"만 적는다면, CodeAct는 "그 호출들을 어떤 순서와 논리로 엮을지"까지 코드 문법으로 적는 셈이에요.

3. 자기 디버깅 — 에러 메시지를 보고 스스로 고친다

이 네 번째 기준(자동 피드백)이 실제로 어떻게 작동하는지, 논문이 든 예시가 인상적이었어요. Mistral-7B 기반 에이전트가 표 데이터를 내려받는 작업을 맡았는데, 처음 시도한 pandas 코드가 에러를 내요. 그런데 에이전트는 그 에러 메시지를 다음 관찰로 그대로 받아서, 사람이 개입하지 않아도 코드를 스스로 고쳐서 다시 실행하고, 이어서 scikit-learn으로 모델을 학습시키고 matplotlib로 그래프까지 그려요. 논문은 이걸 "자동 오류 메시지를 통해 LLM 에이전트가 자율적으로 실수에서 개선될 수 있다"고 설명해요.

이게 가능한 이유는 파이썬 같은 프로그래밍 언어가 원래 "무엇이 왜 실패했는지"를 에러 메시지라는 형태로 표준화해서 돌려주기 때문이에요. JSON이나 텍스트 행동에서는 이런 실패 이유를 하네스나 사람이 별도로 만들어서 챙겨줘야 하는데, 코드 행동에서는 언어 자체가 이미 그 일을 하고 있는 셈이에요.

4. 실험 — 숫자로 확인하기

주장을 확인하려고 논문은 오픈소스·폐쇄소스 합쳐 17개 모델을 두 벤치마크로 평가해요. 하나는 도구 하나만 정확히 부르면 되는 API-Bank(원자적 호출), 다른 하나는 이 논문이 새로 만든 M3ToolEval — 웹 탐색·금융·여행 계획 등 5개 도메인에 걸친 82개 과제를, 최대 10턴 동안 여러 도구를 조합해서 풀어야 하는 벤치마크예요.

반대로 도구 여러 개를 조합해야 하는 M3ToolEval에서는 격차가 뚜렷해요. GPT-4-1106은 텍스트 대비 20.7%포인트 더 높은 성공률을, 그것도 2.1턴 더 적게 써서 달성했어요. 다만 이 개선은 GPT-4·Claude 같은 강한 모델에서 크게 나타났고, 오픈소스 최고 모델(Lemur-70B)은 코드 행동을 써도 13.4%에 머물렀어요 — 코드로 행동을 적는 형식 자체가 성능을 만드는 게 아니라, 그 코드를 제대로 활용할 만큼 모델이 코드를 잘 이해하고 있어야 한다는 조건이 여기서 드러나요.

5. 이 능력, 오픈소스 모델에도 옮길 수 있을까 — CodeActInstruct

그래서 저자들은 오픈소스 모델을 코드 행동에 맞춰 직접 미세조정하는 데이터셋 CodeActInstruct를 만들어요. HotpotQA(정보 검색)·MATH·APPS(소프트웨어 도구)·WikiTable(외부 메모리)·ALFWorld(로봇 계획) 다섯 도메인에서 총 7,139개 다중턴 상호작용, 1,058만 토큰을 모았어요.

이때 그냥 성공한 궤적을 다 모으지 않고 두 기준으로 걸러요. 첫째는 Code-as-Actions — 코드 행동 형식을 따르지 않은 궤적은 뺀다는 기준이고, 둘째가 더 흥미로운데 Self-Improving — "처음엔 틀렸지만 이어지는 상호작용에서 스스로 고쳐낸 궤적만" 골라냈다는 기준이에요. 3장에서 본 자기 디버깅 능력을 모델이 배우게 하려고, 아예 학습 데이터 단계에서부터 "실패 → 자기수정" 패턴만 의도적으로 뽑은 거예요. GPT-3.5·Claude·GPT-4로 궤적을 만들고 성공 여부로 걸러서 최종적으로 GPT-4 궤적 411개, GPT-3.5·Claude 궤적 6,728개가 남았어요.

이 데이터로 Mistral-7B를 미세조정한 CodeActAgent는, 훈련에 쓴 도메인과 같은 성격의 평가(MINT, in-domain)에서 57.4%를 냈어요 — 미세조정 전 Mistral Instruct(18.8%)는 물론 GPT-3.5-turbo(33.9%)보다도 높아요. 기존 에이전트 데이터셋과 비교해도 FireAct 대비 119%, AgentInstruct 대비 24% 상대적으로 높은 성능이에요. 그러면서도 일반 능력(MMLU 지식 QA, HumanEval 코드 생성, GSM8K 수학)은 베이스 모델과 비슷하거나 오히려 살짝 올랐어요 — 에이전트 능력을 넣느라 원래 능력을 깎아먹지 않았다는 뜻이에요.

재미있는 건 전이 실험이에요. CodeActAgent는 코드로만 훈련받았는데, 텍스트 행동을 요구하는 MiniWob++(훈련에 없던 도메인)에서도 25.5%를 냈어요 — 텍스트 행동 전용으로 훈련한 AgentLM(24.6%)과 비슷한 수준이에요. "코드로 배운 조합·수정 능력이 다른 행동 형식에도 어느 정도 옮겨간다"는 조건부 결론이지만, 코드 행동이 그저 하나의 트릭이 아니라 더 일반적인 능력을 길러준다는 근거로 저자들은 이 결과를 들어요.

6. 한계와 조건 — 저자가 스스로 남긴 것

  • 오픈소스-GPT4 격차 — M3ToolEval에서 오픈소스 최고(Lemur-70B 13.4%)와 GPT-4-1106(74.4%) 사이 격차가 여전히 크다고 논문이 직접 밝혀요.
  • 할루시네이션은 그대로 남는다 — 코드 행동도 LLM이 변수 안 내용을 상상해서 지어내는 고질적 문제를 없애주지 않아요.
  • 샌드박스 보안 — 행동이 실제로 실행되는 코드인 이상, 그 코드를 어디까지 격리된 환경(샌드박스, 실제 시스템과 분리된 실행 공간)에서 돌릴지가 새로운 위험 요소가 돼요. 실행 권한을 어디까지 열어줄지는 AI가 짠 코드를 실제로 실행시킬 때 반드시 확인해야 할 지점과 같은 고민이에요.
  • 이상 현상 — Llama-2 기반 CodeActAgent는 M3ToolEval에서 기대만큼 개선되지 않는 예외 사례가 있었다고 부록(Appendix H)에 남겨뒀어요.
  • 실험 조건 — 위 수치들은 모두 예시 없이 바로 묻는 zero-shot 설정, 최대 10턴 제한이라는 조건 아래에서 나온 값이에요.

마무리

이 논문을 한 줄로 요약하면, "행동을 어떤 형식으로 적을지"도 에이전트 설계에서 결정해야 할 몫 중 하나라는 거예요. JSON은 여전히 안전하고 예측 가능한 선택이고(특히 도구 하나만 정확히 불러야 하는 상황), 코드는 여러 도구를 조합하거나 실패를 스스로 고쳐야 하는 복잡한 작업에서 강점을 보여요. MCP로 도구를 표준화하는 흐름과, 이 논문처럼 행동 형식 자체를 코드로 바꾸는 흐름은 서로 다른 층의 이야기지만, 결국 둘 다 "에이전트가 도구와 어떻게 대화하게 만들 것인가"라는 같은 질문을 겨누고 있다는 점에서 함께 봐 둘 만해요.
