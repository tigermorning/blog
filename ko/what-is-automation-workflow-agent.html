자동화·워크플로·에이전트, 뭐가 다를까 (1)

2026. 9. 1.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

아침에 메일함을 열면 비슷비슷한 문의가 쌓여 있어요. 배송이 언제 오는지, 결제가 왜 실패했는지, 반품은 어디로 보내는지 확인하고 담당 팀에 전달한 뒤 표에 옮겨 적어요. 이쯤 되면 "이거 AI한테 맡기면 안 될까" 싶은데, 막상 찾아보면 자동화·워크플로·에이전트라는 비슷해 보이는 말이 잔뜩 나와서 뭐가 뭔지 헷갈려요. 이 셋을 가르는 기준은 딱 하나였어요. 다음에 뭘 할지 누가 정하느냐.

내비게이션으로 갈라보기

운전으로 비유하면 셋의 차이가 확 와닿아요.

  • 자동화 = 버스 노선. 정류장과 순서가 미리 정해져 있고, 그대로만 움직여요. "이 조건이면 이렇게 한다"는 규칙이 처음부터 끝까지 고정돼 있어요.
  • 워크플로 = 내비게이션이 그려주는 경로. 갈림길마다 조건에 따라 이 길 저 길로 갈라지긴 하는데, 그 갈림길과 조건은 전부 사람이 미리 그려둔 지도 안에 있어요. 화면에 경로가 선으로 그대로 보이니까, 어디서 왜 이 길로 갔는지 되짚기도 쉬워요.
  • 에이전트 = 자율주행. 지금 상황(도로 상태, 신호)을 보고 그때그때 판단해서 다음 행동을 스스로 골라요. 유연하지만, 왜 그 판단을 했는지 되짚으려면 그 순간 뭘 보고 뭘 근거로 골랐는지까지 다 확인해야 해요.

목적지는 같아도 뭔가 잘못됐을 때 "어디를 봐야 하는지"가 완전히 달라요. 버스 노선이 잘못됐으면 노선표를 고치면 되고, 내비 경로가 이상하면 어느 갈림길 조건이 잘못됐는지 확인하면 돼요. 그런데 자율주행이 이상한 선택을 했다면, 그 순간 무슨 정보를 봤고 어떤 도구를 쓸 수 있었고 왜 그렇게 판단했는지까지 다 들여다봐야 해요. 그래서 AI에게 일을 맡기는 정도가 커질수록, "얼마나 마음대로 하게 둘지"와 "사람이 언제 멈춰 세울지"를 더 분명히 정해둬야 했어요.

중요한 건 이 셋이 딱 잘라 나뉜 별개의 도구가 아니라는 거예요. 하나의 서비스 안에서도 부분마다 다를 수 있어요. 대화창으로 AI와 얘기하다가 필요할 때만 미리 만들어둔 자동화를 불러 쓸 수도 있고, 내비게이션(워크플로) 안에 자율주행 판단(에이전트)이 한 조각 끼워져 있을 수도 있어요.

이게 "규칙"인지 아닌지 가려내는 법

그러면 내 업무는 버스 노선(자동화)으로 될까, 아니면 사람 판단(에이전트)이 필요할까? 간단한 시험이 있어요. 일을 설명할 때 "무조건", "항상", "매번"이라는 말을 자연스럽게 쓸 수 있으면 규칙이 선명한 거예요. "새 문의가 오면 무조건 접수 번호를 붙인다", "매일 아침 무조건 어제 매출을 표에 옮긴다" 같은 건 조건과 결과를 그대로 적을 수 있어요.

반대로 "친절하게 답한다"나 "중요한 메일부터 본다"에는 사람의 판단이 끼어 있어요. 헷갈릴 땐 낯선 동료에게 이 일을 가르친다고 상상해보면 돼요. 동료가 "이 경우엔 어떻게 해요?"라고 물었을 때 제 입에서 "그건 알아서 해주세요"가 나온다면, 그 부분은 아직 규칙이 아니에요. 자동화는 빈틈을 알아서 메워주는 마술이 아니라, 빈틈까지 다 적어 둔 조리법처럼 작동하거든요.

실제 도구로 보면 이렇게 갈려요

이 세 갈래가 실제 서비스로는 어떻게 보이는지 궁금해서 몇 개를 훑어봤어요.

도구어떤 느낌인가
Zapier, Make노코드로 "이런 일이 생기면 → 이렇게 한다"를 미리 연결해두는 서비스예요. 버스 노선에 가까워요. 실행 횟수나 연산량으로 요금이 매겨져요.
n8n, Node-RED화면에 노드(동그란 블록)를 선으로 이어서 흐름을 직접 그려요. 내비게이션 지도처럼 어느 길로 갔는지, 뭘 주고받았는지가 눈에 다 보여서 배우기 좋아요. 소스가 공개돼 있어서 나중에 내 컴퓨터에 직접 띄워볼 수도 있어요.
Claude Code 같은 코딩 에이전트파일을 읽고 명령을 실행하고 다음에 뭘 할지 스스로 골라요. 자율주행 쪽이에요. 강력한 만큼, 어디까지 권한을 줄지 사람이 더 신경 써야 해요.

n8n으로 직접 흐름 하나 만들어봤어요

말로만 들으면 감이 안 와서, n8n으로 제일 짧은 흐름을 직접 만들어봤어요. Manual Trigger(내가 버튼 눌러야 시작하는 출발점)와 HTTP Request(인터넷 어딘가에 요청을 보내는 노드) 두 개만 화면에 놓고 선으로 이었어요. HTTP Request 주소에는 로그인 없이도 볼 수 있는 위키백과 요약 API 주소를 넣었고요.

실행 버튼을 누르니 두 노드가 선을 따라 차례로 움직였고, 실행 기록을 열어보니 위키백과가 돌려준 진짜 응답 — 제목, 설명, 관련 링크 같은 것들 — 이 그대로 찍혀 있었어요. 화면의 선 하나하나가 "다음엔 이 노드로 간다"는 정해진 경로였고, 그 경로를 따라간 결과가 기록으로 고스란히 남는다는 걸 눈으로 확인한 순간이었어요. 다만 노드 몇 개를 이었다고 아무 업무나 맡겨도 되는 건 아니에요 — 연결한 서비스가 어디까지 손댈 수 있는지, 실패하면 어디에 기록이 남는지, 사람이 다시 확인할 지점이 있는지는 매번 따로 챙겨야 했어요.

정리하면 이래요. 자동화는 정해진 노선을 반복하고, 워크플로는 미리 그려둔 지도 안에서 갈림길을 타고, 에이전트는 그때그때 상황을 보고 스스로 다음 행동을 골라요. 내 업무가 "무조건·항상·매번"으로 설명되면 자동화나 워크플로로 충분하고, 매번 다른 판단이 필요하면 에이전트 쪽으로 가되 어디까지 맡길지 권한과 멈출 지점을 더 분명히 정해둬야 해요.

모두의연구소 "AI Agent 파헤치기" 커리큘럼 노드는 전체 7강인데, 이 글은 그중 앞 3강(다음 행동을 누가 정하는가 / 규칙과 그래프 / n8n 실습)을 묶어 정리했어요. 나머지 4강(코딩 에이전트에게 같은 흐름 맡기기, 워크플로에서 에이전트 쓰기, 판정, 셀프 호스팅)은 다음 글에서 이어가요.

한 걸음 더: "다음 행동을 누가 정하느냐"라는 이 기준 하나로 같은 버그를 세 번 고쳐 보며 기록을 비교한 글이 같은 버그를 세 방식으로 — 기준선·워크플로·오케스트레이션 실행이에요. 한 에이전트(자율주행), 파이썬 코드(내비 경로), 리드 모델(지휘자)이 정하는 세 실행을 Claude Agent SDK 코드로 나란히 놓아요.
