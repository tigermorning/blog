오케스트레이터-워커란 중앙 LLM(오케스트레이터)이 전체 작업을 쪼개 워커에게 동적으로 나눠 주고 결과를 다시 모으는, 그래서 워커를 몇 개 부를지가 실행 중에야 정해지는 워크플로다.

위에서 아래로 갈수록 개발자가 미리 정해 두는 것이 줄고, LLM이 실행 중에 정하는 것이 늘어요. 그래도 다섯 다 워크플로예요. 갈 수 있는 길 자체는 전부 개발자가 미리 그려 뒀거든요.

비유 — 헤드셰프가 메뉴 수를 정한다

그 주방의 저녁, 단체 손님이 들어와요. 인원이 몇인지, 뭘 못 먹는 사람이 있는지는 주문서를 봐야 알아요. 헤드셰프가 주문서를 읽고 그 자리에서 메뉴 수를 정해요. "오늘은 다섯 접시." 그리고 요리사마다 쪽지를 한 장씩 건네요. 쪽지에는 자기가 맡은 요리 하나만 적혀 있고, 다른 요리사가 뭘 하는지는 안 적혀 있어요. 다 만들어지면 한 상에 모아 내보내요.

비유 속 요소원래 개념
헤드셰프가 주문서를 읽고 그 자리에서 메뉴 수를 정하기오케스트레이터 — 하위 작업의 개수를 LLM이 실행 중에 정해요
요리사마다 건네는 쪽지 한 장 (자기 것만 적혀 있음)Send — 워커는 전표(State) 전체가 아니라 자기 쪽지만 받아요 (아래)
다 만들어진 접시를 한 상에 모으기신서사이저 — 워커 결과를 리듀서로 모아 합치는 노드

핵심 한 줄: 헤드셰프가 정하는 건 접시 수뿐이에요 — 요리사가 제멋대로 새 동선을 만드는 장면은 없고, 그게 바로 에이전트와의 차이예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 요리사는 쪽지만 받아도 옆을 힐끗 보고 눈치껏 맞추지만, Send로 불린 워커는 정말 자기 쪽지 말고는 아무것도 못 봐요. 필요한 정보는 쪽지에 전부 적어 보내야 해요.

이 상황엔 어떤 패턴?

"사용자가 올린 회의록을 받아, 그 회의록에서 나온 액션 아이템 개수만큼(3개일 수도 10개일 수도 있다) 각각의 담당자 배정 초안을 만들어야 한다." 가장 적합한 패턴은?

  1. 프롬프트 체이닝 — 회의록 요약 → 액션 아이템 추출 → 담당자 배정을 순서대로 잇는다
  2. 병렬화 — 액션 아이템 처리 노드 여러 개를 미리 만들어 두고 동시에 실행한다
  3. 오케스트레이터-워커 — 액션 아이템의 개수를 실행 전에 알 수 없으므로 Send로 워커를 동적으로 생성한다
  4. 라우팅 — 회의록의 종류를 분류한 뒤 알맞은 처리 경로 하나로 보낸다

문제를 쪼개면: 회의록을 받는다 → 액션 아이템을 뽑는다 → 개수는 매번 다르다 → 각각에 대해 담당자 배정 초안을 만든다. 여러 작업이 순서로 연결된 것처럼도 보이지만, 핵심은 "몇 개가 나올지 실행 전엔 모른다"예요.

3번인 이유: 하위 작업의 개수가 입력을 받아 봐야 정해져요. 회의록에서 할 일을 뽑는 계획 단계(오케스트레이터)가 개수를 정하고, Send로 할 일마다 워커를 하나씩 불러 담당자 초안을 써요. "개수를 미리 아나?" 한 질문이 병렬화와 오케스트레이터-워커를 가르는 갈림길이에요.

다른 선택지가 아닌 이유:

  • 1(체이닝): 체이닝은 단계가 고정이라, 마지막 단계 한 번에 할 일을 몰아서 처리하게 돼요. 할 일마다 따로 초안을 만드는 구조가 아니에요.
  • 2(병렬화): 처리 노드 개수를 미리 알아야 하는데, 할 일 개수는 회의록마다 달라요.
  • 4(라우팅): 여러 갈래 중 하나만 고르는 모양이라, 할 일 여러 개를 동시에 다루지 못해요.

한 줄로: 오케스트레이터-워커 = "개수가 입력을 받아 봐야 정해진다."

전체 흐름

몇 갈래일지 LLM이 정한다

병렬화에는 숨은 전제가 있었어요. 하위 작업(나눠 맡길 일 하나하나)의 개수와 종류를 개발자가 코드를 쓸 때 이미 알아야 해요. 평가 축이 셋이라 검사 노드도 셋을 미리 그렸죠. 주방으로 치면 검사 담당 셋을 영업 전에 동선표에 그려 둔 거예요.

그런데 단체 예약이 들어오면 사정이 달라요. 손님 수를 봐야 메뉴가 몇 개일지 정해지니, 요리사가 몇 명 필요할지 영업 전에는 몰라요. 학습 가이드도 같아요. "이 주제로 가이드를 만들어 줘, 섹션 수는 알아서"라고 하면 섹션이 3개일 수도 7개일 수도 있어요. 그렇다고 영업 중에 동선표에 조리대를 새로 그려 넣을 수도 없어요. 노드를 등록하는 add_node는 compile() 전에만 부를 수 있거든요.

그래서 요리사 자리는 동선표에 하나만 그려 두고, 헤드셰프가 메뉴를 정한 다음 "이 쪽지 들고 요리사 한 명 더!"를 메뉴 수만큼 외쳐요. 이 외침이 Send예요.

개념 설명용 코드 — 아래 전체 코드에서 한 줄만 떼어 뜯어본 거예요

Send("cook", {"dish": d})
     ^^^^^^  ^^^^^^^^^^^
     (1)     (2)
# (1) 부를 노드 이름   (2) 그 요리사에게만 건넬 쪽지

아래 코드의 assign은 메뉴 목록에서 요리를 하나씩 꺼내(for d in state["menu"]) Send를 하나씩 만들어 목록으로 돌려줘요. 메뉴가 셋이면 Send도 셋이고, 같은 cook 노드가 쪽지를 한 장씩 들고 세 번 동시에 돌아요. 보통 라우터는 "다음은 이 노드" 하고 이름 하나를 돌려주는데, 여기서는 Send 목록을 돌려줘서 "이 노드를 이 쪽지로 N번"이라고 지시하는 거예요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class Party(TypedDict):
    guests: int
    menu: list
    plates: Annotated[list, operator.add]   # 워커들의 결과를 모으는 칸

class CookInput(TypedDict):                  # 요리사 한 명이 받는 전용 쪽지
    dish: str

def plan(state: Party):                      # 실제로는 LLM이 메뉴 수를 정하는 자리
    menu = ["전", "잡채", "갈비", "나물", "떡", "식혜"][: state["guests"] // 2]
    return {"menu": menu}

def assign(state: Party):
    return [Send("cook", {"dish": d}) for d in state["menu"]]   # 메뉴 수만큼 요리사 복제

def cook(state: CookInput):
    return {"plates": [f"{state['dish']} 완성"]}

def serve(state: Party):
    return {}

b = StateGraph(Party)
b.add_node("plan", plan)
b.add_node("cook", cook)
b.add_node("serve", serve)
b.add_edge(START, "plan")
b.add_conditional_edges("plan", assign, ["cook"])
b.add_edge("cook", "serve")
b.add_edge("serve", END)
g = b.compile()

for n in (6, 12):
    out = g.invoke({"guests": n, "plates": []})
    print(n, "명 →", len(out["plates"]), "접시:", out["plates"])

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

6 명 → 3 접시: ['전 완성', '잡채 완성', '갈비 완성']
12 명 → 6 접시: ['전 완성', '잡채 완성', '갈비 완성', '나물 완성', '떡 완성', '식혜 완성']

같은 그래프인데 한 번은 요리사가 3명, 한 번은 6명 불렸어요. draw_mermaid()로 찍어 보면 cook 노드는 여전히 하나고 plan -.-> cook 점선 하나뿐이에요. 그림에는 요리사 자리가 하나, 실행할 때 필요한 만큼 불려 나오는 거예요. 요리사들이 돌려준 plates는 리듀서(operator.add)를 단 칸이라, 세 명이 동시에 적어도 에러 없이 한 목록으로 모여요(③ 병렬화의 그 장치예요). 이렇게 펼쳐서 각자 처리하고 하나로 모으는 구조를 맵-리듀스1라고도 불러요.

요리사는 전표를 못 봐요 — 쪽지만 받아요

여기서 가장 중요한 성질이 있어요. Send로 불린 요리사는 주방의 전표(State) 전체를 받는 게 아니라 자기 쪽지만 받아요. 확인하려고 cook이 받은 걸 찍고, 쪽지에 없는 손님 수(guests)까지 읽어 보게 했어요.

실행: 로컬 파이썬 — 위 코드에서 cook 함수와 맨 아래 실행 줄만 이렇게 바꿔요

def cook(state: CookInput):
    print("요리사가 받은 것:", dict(state))
    print("손님 수를 읽으면:", state["guests"])   # 쪽지에 없는 칸을 읽어 본다
    return {"plates": [f"{state['dish']} 완성"]}

try:
    g.invoke({"guests": 6, "plates": []})
except Exception as e:
    print("에러:", type(e).__name__, e)

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

요리사가 받은 것: {'dish': '전'}
요리사가 받은 것: {'dish': '잡채'}
요리사가 받은 것: {'dish': '갈비'}
에러: KeyError 'guests'

요리사 셋이 받은 건 요리 이름 하나짜리 쪽지뿐이었고, 손님 수를 읽으려는 순간 KeyError로 멈췄어요. cook의 타입을 Party로 바꿔 적어도 결과는 같았어요. 타입 힌트는 표시일 뿐이고, 실제로 들어오는 건 Send에 담은 딕셔너리 그대로거든요.

왜 이렇게 만들었을까요? 요리사 셋이 동시에 서로 다른 요리를 맡아야 하는데, 전표의 한 칸에는 값을 하나만 적을 수 있어요. "지금 만들 요리" 칸을 전표에 두면 세 명에게 서로 다른 값을 줄 수가 없죠. 그래서 한 명씩 개인 쪽지를 주는 거예요.

중요꼭 기억할 것

Send("노드 이름", {...})의 두 번째 인자(괄호 안에 넣는 두 번째 값)는 그 워커 실행 한 번에만 건네는 전용 상태예요. 이 쪽지는 전표(State)에 옮겨 적히지 않고 그 워커에게만 가요. 워커가 받는 건 이 딕셔너리 그대로라서, 메인 State의 다른 칸(주제, 섹션 목록 등)은 볼 수 없어요. 워커가 알아야 하는 건 전부 이 쪽지에 담아 줘야 해요. 워커가 쓴 결과는 쪽지가 아니라 워커의 반환값으로 따로 돌아와 리듀서가 단 칸에 모여요.

"LangGraph의 리듀서와 병렬 실행"이라는 주제를 주고 프롬프트에 "섹션은 3~5개"라는 범위만 줬더니 오케스트레이터가 5개를 골랐어요. 그런데 결과물을 읽어 보면 한계가 드러나요.

  • 지어내기 — 쪽지에 섹션 제목만 받은 워커는 주제가 LangGraph라는 걸 몰라요(바로 위에서 본 성질이에요). 그래서 'LangGraph의 리듀서' 대신 학습 데이터에 훨씬 흔한 자바스크립트 Redux의 useReducer를 설명해 버렸어요. 해법은 프롬프트를 다듬는 게 아니라 주제와 근거 노트를 쪽지에 같이 넣어 주는 것이에요. Send("write_section", {"section": s, "topic": state["topic"]})처럼요.
  • 중복 — 계획할 때 섹션의 경계를 안 그어 주면 워커 두 명이 거의 같은 내용을 써요. "이 섹션에서 다루지 않을 것" 칸을 쪽지에 넣는 식으로 막아요.
  • 격리 — 워커끼리는 서로 뭘 썼는지 몰라요.

병렬화와 뭐가 다른가

두 패턴은 실행될 때 여러 갈래로 갈라졌다가 한곳에 모이는 모양이 닮았어요(개념도로 그리면 거의 같고, draw_mermaid() 그림에서는 오케스트레이터-워커의 워커 노드가 하나뿐이지만요). 차이는 갈래가 몇 개인지 누가, 언제 정하느냐 하나예요.

비교 항목③ 병렬화④ 오케스트레이터-워커
갈래 수를 정하는 쪽개발자LLM(오케스트레이터)
정하는 때코드를 쓸 때, compile() 전실행 중에, 입력을 본 뒤
그래프 모양갈래마다 노드를 미리 그려 둠워커 노드 하나 + Send로 필요한 만큼 불러냄
주방에서검사 담당 셋을 동선표에 미리 그려 둠헤드셰프가 그날 메뉴 수를 보고 요리사를 부름

대가도 분명해요. 계획이 나쁘면 아래 워커 전부가 나빠지고(단일 실패 지점2), 워커 수를 LLM이 정하니 비용도 미리 알 수 없어요. 오케스트레이터가 섹션 20개를 계획하면 호출이 21번이에요. 그래서 state["menu"][:4](목록에서 앞의 4개만 남기기)처럼 워커 수에 상한을 두고, 잘린 게 있으면 결과에 표시해 둬요.

중요꼭 기억할 것

병렬화와 오케스트레이터-워커의 가장 큰 차이는 하위 작업의 개수와 종류를 누가, 언제 정하느냐예요. 병렬화는 개발자가 코드를 쓸 때 고정해서 노드를 미리 그려 두고, 오케스트레이터-워커는 LLM이 실행 중에 정해서 Send로 워커를 불러내요.

그래서 "평가 축 3개로 노트 검수하기"처럼 어떤 입력이 와도 할 일이 늘 같은 작업에 오케스트레이터-워커를 쓰면, 얻는 것 없이 대가만 커져요. 계획용 LLM 호출이 한 번 더 들어 비용과 기다리는 시간이 늘고, 계획이 틀리면(축을 둘만 만들거나 엉뚱한 축을 넣으면) 검수 전체가 망가지고, 실행마다 축이 달라져 결과를 서로 비교할 수도 없어요. 미리 알 수 있는 건 미리 정해 두는 게 맞아요.

이 모양은 코딩(몇 개 파일을 어떻게 고칠지 요청마다 다름)이나 여러 출처 검색에 잘 맞아요. 멀티 에이전트 네 가지 구조에서 본 오케스트레이터-워커가 에이전트 여럿의 이야기라면, 여기서는 한 그래프 안의 LLM 호출로 같은 모양을 만든 거예요.

나쁜 선택 vs 좋은 선택 — 신메뉴를 세 기준으로 검사할 때

주방에서 신메뉴를 낼 때마다 맛·온도·모양 세 가지로 검사하는 흐름을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: "유연해 보여서" 오케스트레이터-워커로 짰어요. 헤드셰프 역할 LLM이 매번 접시를 보고 검사 항목을 정한 뒤 Send로 검사원을 불러요.

무슨 일이 생기나: 계획 호출이 매번 1번 더 들고, 어떤 날은 항목이 4개로 늘고 어떤 날은 '모양'이 빠져요. 요금은 들쑥날쑥하고, 메뉴끼리 점수를 비교할 수도 없어요.		 무엇을 했나: 검사 항목이 항상 셋이니 병렬화로 짰어요. 노드 셋을 고정하고 checks 칸에 리듀서를 달았어요.

무슨 일이 생기나: 호출은 늘 3번이고 비용이 예측돼요. 같은 기준의 점수가 쌓이니 메뉴끼리 비교도 돼요. 반대로 "회의록에서 나온 할 일 개수만큼 담당자 초안 만들기"처럼 개수가 입력마다 다를 때가 오케스트레이터-워커의 자리예요.

이 글에 나온 숫자

무엇의 숫자인가값알아 둘 것
같은 그래프가 만드는 워커 수입력에 따라 3개 또는 6개Send로 갈라지는 구조라 코드는 그대로인데 입력만 바꿔도 호출 수가 달라져요. 그래프만 보고 요금을 계산할 수 없다는 뜻이에요
섹션 20개를 계획했을 때의 호출 수21번오케스트레이터 1 + 워커 20이에요. 프롬프트에 범위를 안 주면 몇 개를 고를지도 모델이 정해요. "3~5개"처럼 상한을 적어 두는 게 요금 통제의 전부예요

내 파이프라인에 대입하면 — 이 시리즈가 열 편이 된 이유

정리할 원문 열두 단원을 받았을 때 글이 몇 편이 될지는 읽어 보기 전엔 몰라요. 먼저 전체를 훑어 목차를 정하는 단계가 오케스트레이터고, 각 편을 실제로 쓰는 단계가 워커예요. 병렬화 편과 그림이 닮았지만 갈림점은 하나 — 거기선 검사가 셋이라고 적어 뒀고, 여기선 편 수를 적어 둘 수가 없어요. 이 시리즈가 이렇게 여러 편으로 나뉜 것도 그렇게 정해졌어요.

그리고 위의 워커는 쪽지만 받는다가 여기서 아주 구체적으로 걸려요. 각 편을 쓰는 쪽은 그 편이 시리즈에서 몇 번째인지 몰라요. 편 번호, 앞뒤 편의 제목, 시리즈 전체 목록을 쪽지에 직접 담아 보내야 해요. 안 담아 주면 편마다 시리즈 이름이 조금씩 달라지고, 맨 아래 목록의 편 수가 서로 안 맞아요. 이 글 맨 아래 목록이 어느 편에서 봐도 같은 이유예요.

실제 코드에 대입하면 — 자막이 몇 개 나올지는 코드가 모르는데, 그래도 아직 ④가 아니에요

이 편은 교정기 말고 자막·타임코드 생성기(subtitle-tc-generator) 쪽을 볼게요. 교정기는 자막 한 줄을 받아 한 줄을 돌려주는 도구라 개수가 변하는 자리가 없어요. ④를 보려면 하나가 여럿이 되는 도구가 필요해서 바꿔요. 이 도구는 영상 하나를 받아 전사 → 대조 → 재분할 → 스포팅으로 초벌 자막을 내요(번역은 따로 붙는 다른 갈래예요).

먼저 결론부터. 전사한 덩어리 하나가 자막 몇 개로 갈릴지를 코드에 적을 수가 없어요. 그런데도 이 편의 기준으로 보면 아직 워크플로예요. 위의 "개수를 누가, 언제 정하나"에서 언제만 실행 때로 옮겨졌고, 누가는 그대로 코드거든요 — 자막 하나에 담기는 글자 수는 규정(한 줄 한계 × 줄 수)이 정하고, 덩어리에 글자가 몇 개인지는 영상이 정해요. LLM은 이 계산에 안 끼어요. 이 갈림점이 얼마나 좁은지가 여기서 보여요.

제 저장소 코드 — checker/resplit.py의 resplit_all()에서 나누는 부분이에요. events가 전사 덩어리 목록이고, out이 최종 자막 목록이에요

out: list[Event] = []
for ev in events:
    pieces = resplit(ev, max_chars_per_cue, ...)   # 덩어리 하나 → 조각 여러 개
    out.extend(pieces)
    if origins is not None:
        origins.extend([ev.index] * len(pieces))
for i, ev in enumerate(out, 1):                    # 1번부터 번호 다시 매기기
    ev.index = i
return out

append가 아니라 extend인 게 요지예요. 하나 넣으면 하나 나오는 게 아니라 몇 개 나올지 모르는 것을 쏟아 붓는 자리라서요. 마지막 두 줄이 결과를 하나로 접는 부분이고요. 그리고 위의 워커는 쪽지만 받는다가 여기서 아주 구체적으로 걸려요. 번호를 다시 매기는 순간 앞 단계가 "여기 봐야 한다"고 표시해 둔 번호가 엉뚱한 자막을 가리켜요. 셋째 자막을 가리키던 표시가, 앞의 자막 하나가 셋으로 갈리면 전혀 다른 대사에 붙어요. origins라는 목록이 따로 있는 게 그래서예요 — 새 자막마다 원래 번호가 무엇이었는지를 같이 들고 가요. 워커에게 쪽지로 담아 보내야 하는 정보가 실제로는 이런 모양이에요.

이럴 때 의심하세요

이 편의 모양은 돌려 보기 전에는 몇 번 부를지 모르는 구조라, 문제도 입력에 따라 나타났다 사라져요. 짧은 입력으로 시험할 땐 멀쩡하다가, 섹션이 많이 나오는 주제가 들어온 날 요금으로 드러나요.

증상이 아직 없어도, AI에게 "섹션 수는 알아서 정해서 나눠 써 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
에러는 없는데, 워커가 쓴 섹션 몇 개가 주제와 다른 이야기를 해요. LangGraph의 리듀서를 물었는데 Redux의 useReducer를 설명하는 식이에요 워커를 부르는 Send("워커 이름", {...}) 줄의 두 번째 값이에요. 워커 프롬프트의 문장은 대개 범인이 아니에요. 워커는 이 딕셔너리 말고는 아무것도 못 보거든요 워커 함수 첫 줄에 print(dict(state))를 넣어 워커가 받은 쪽지를 찍어 봐요. 섹션 제목만 있고 주제나 근거 노트가 없으면, 그 칸을 Send 쪽지에 더 담아요 (요리사는 전표를 못 봐요)
워커 노드에서 KeyError: '칸 이름'으로 멈춰요. 그 칸은 메인 State에 분명히 있고, 트레이스백 맨 아래 During task with name '...'에는 워커 이름이 찍혀요 같은 Send 줄이에요. 워커 함수의 타입 힌트를 전체 State로 바꿔 적어도 들어오는 건 쪽지 그대로라 소용없어요 에러에 찍힌 칸 이름이 Send 쪽지 딕셔너리에 있는지 봐요. 없으면 그 칸을 쪽지에 담아 보내요 (꼭 기억할 것)
코드는 그대로인데 입력에 따라 한 번 돌리는 요금이 몇 배씩 들쑥날쑥해요. API 사용량 화면에 한 번 돌린 것치고 호출이 수십 건 찍혀요 오케스트레이터가 만든 계획 목록의 길이와, 그 목록으로 Send를 만드는 줄이에요. 목록을 자르는 상한([:4] 같은)이 있는지, 오케스트레이터 프롬프트에 "3~5개" 같은 범위가 있는지 봐요 계획 목록의 len()을 찍어요. 호출 수는 오케스트레이터 1번 + 목록 길이만큼이에요. 상한을 두고, 잘린 항목이 있으면 결과에 표시해요 (병렬화와 뭐가 다른가)

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — LangGraph 코드가 있는 프로젝트 폴더에서

이 프로젝트의 LangGraph 코드에서 아래를 찾아 표로 보여 줘. 아직 코드는 고치지 마.
1. Send(...)를 쓰는 곳마다: 파일 이름과 줄 번호, 쪽지 딕셔너리에 담는 열쇠 목록, 그 워커 함수가 state["..."]로 읽는 열쇠 목록, 그리고 읽는데 쪽지에 없는 열쇠
2. Send 목록을 만드는 계획 목록에 개수 상한이 있는지, 오케스트레이터 프롬프트에 개수 범위가 적혀 있는지

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 다른 편의 같은 목록은 1편 · 2편 · 3편 · 4편 · 6편 · 7편 · 8편에 있어요.

  • Send로 불린 워커는 자기 쪽지만 봐요
  • 병렬화와 오케스트레이터-워커는 "개수를 누가, 언제 정하나"로 갈려요

직접 해보기

  1. 범위를 빼 보기 — 바꿀 것: 오케스트레이터 프롬프트에서 "3~5개"라는 범위를 지워요. 측정할 것: 같은 입력으로 여러 번 돌렸을 때 계획된 섹션 수와 총 호출 수. 비교할 것: 범위가 있을 때와 대 봐요. 호출 수가 열려 있다는 게 숫자로 보여요.
  2. 쪽지에 덜 적어 보기 — 바꿀 것: Send로 넘기는 쪽지에서 필드 하나를 빼요. 측정할 것: 워커가 그 정보를 State에서 가져올 수 있는지. 비교할 것: 에러가 나는지, 아니면 조용히 엉뚱한 결과가 나오는지 확인해요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.

이번 편까지 데이터는 앞에서 뒤로만 흘렀어요. 다음 편은 처음으로 되돌아가는 순환이 생겨요 — 통과할 때까지 고쳐 쓰는 평가자-최적화자예요.

함께 읽으면 좋은 글

  • 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업 — 오케스트레이터-워커를 여러 에이전트 구조 가운데 하나로 놓고 본 글이에요.
  • 나눠서 얻는 것과 잃는 것 — 일을 여러 갈래로 나눌 때 치르는 비용을 다룬 글이에요.
  • 요약을 세 칸으로 받고 원문과 대조한다 — 고른 기사 수만큼 Send로 요약 워커를 펼치는 실전 예예요.
  1. 맵-리듀스(map-reduce) — 일을 여러 갈래로 펼쳐 각각 처리한 뒤 결과를 하나로 접는 데이터 처리 방식이에요. ↩
  2. 단일 실패 지점(single point of failure) — 그 한 곳이 잘못되면 시스템 전체 결과가 망가지는 지점이에요. ↩
