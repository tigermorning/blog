이제 조각이 다 모였어요 — 화면, 그리고 네트워크·백엔드·보안·배포. 마지막으로 이 조각들을 실제로 어떻게 잇는지가 남았어요. 여기가 초보가 가장 많이 헤매는 지점이라고 해서 저도 긴장하며 봤는데, 다행히 순서만 알면 훨씬 수월했어요.

가장 안정적인 순서 — 목업에서 진짜로

순서는 이래요. 먼저 지난 시리즈에서 만든 "가짜 데이터로 도는 화면"을 출발점으로 삼고, 그다음 그 화면이 부를 창구(엔드포인트)를 백엔드에 만들고, 마지막으로 가짜 데이터를 실제 호출로 교체해요. 여기서 결정할 게 하나 있는데, "앱 전체를 한 번에 시킬까, 나눠 시킬까"예요. 통째로 한 프롬프트에 다 시키는 건 초보에게 거의 항상 실패한다고 해요 — AI의 집중력과 기억에도 한계가 있거든요. 대신 "데이터 모양 → API → 화면"처럼 작게 쪼개서 시키면 실수를 훨씬 일찍 잡을 수 있었어요.

흐름을 정리하면, 목업으로 화면을 잘 만들어두면 백엔드는 정말 "한 겹 덧입히기"가 돼요. 화면이 가짜 데이터를 불러오던 한 줄을, 진짜 서버에 요청하는 한 줄로 바꾸기만 하면 화면 코드는 거의 그대로거든요. 첫 글에서 봤던 그 장면 — 친구가 링크를 열 수 있고, 새로고침해도 데이터가 남는 것 — 이 바로 이 과정의 끝에서 이뤄지는 거예요.

연결에서 실제로 겪는 문제들

연결 단계는 실무자들이 "바이브가 죽는 순간"이라고 부를 만큼 문제가 몰려요. 가장 큰 원흉은 계약 불일치예요. 프론트가 기대하는 데이터 모양과 백엔드가 주는 모양이 서로 다른 건데, AI를 쓰면 오히려 심해질 수 있어요 — 양쪽에 "얼추 맞는" 걸 따로 만들다 보니 서서히 어긋나는 거예요. 화면에 undefined가 뜨거나, 기대와 달리 한 겹 더 감싸인 응답이 오는 게 이 증상이에요. 처방은 나중에 맞추는 게 아니라, 주고받을 데이터를 처음부터 문서로 적어두고 그걸 기준으로 양쪽을 짜는 것이었어요.

두 번째는 로딩·에러 상태 누락이에요. 데이터가 오기 전 화면이 깜빡이거나, 서버가 오류를 줘도 앱이 멈춘 듯 보이는 증상인데, 모든 호출을 로딩/성공/에러 세 상태로 나눠 각각 화면을 준비해두면 해결돼요. 세 번째는 지난 글에서 본 CORS·주소·환경변수 문제예요. 다른 주소 간 요청이 막히거나 "로컬에선 됐는데" 하는 그 문제들이 사실 배포 문제이기도 하지만, 동시에 프론트-백엔드 연결 문제이기도 했어요. 처방도 그때와 같아요 — 백엔드가 내 프론트 주소를 허용하고, 주소는 환경변수로 관리하기. 실제로 겪으면 콘솔에 has been blocked by CORS policy 같은 빨간 글씨가 떠요 — 이건 서버가 거부한 게 아니라 브라우저가 스스로 응답을 버린 거예요. 응답에 Access-Control-Allow-Origin: 내프론트주소 헤더가 없으면 브라우저가 그 응답을 화면에 넘겨주지 않거든요. 이 검문 과정만 따로 떼어 번외편에 정리했어요.

연결을 매끄럽게 하는 전략

가장 강력한 전략은 주고받을 데이터를 문서로 남기고 시작하는 거예요. 어떤 창구(엔드포인트)가 있고, 각 요청·응답이 어떤 JSON 모양인지 적은 문서(API 명세)를 만들어두면, 계약 불일치가 근본적으로 사라져요. AI에게는 이렇게 요구하면 돼요 — "엔드포인트 목록과 각 요청/응답 예시(JSON)를 명세 문서로 만들어줘. 앞으로 이 문서를 기준으로 프론트와 백엔드를 짜자." 기능이 바뀌면 코드보다 이 문서를 먼저 고치는 습관을 들이면, 프론트와 백엔드가 늘 같은 문서를 보게 되니 서로 어긋날 일이 없어요.

두 번째 요령은 한 기능씩 끝까지 만드는 거예요("수직 슬라이스"라고 부르더라고요). "화면 전부 먼저, 서버 전부 나중에"처럼 층으로 나누면 AI가 다른 층을 몰라서 추측하다 틀리기 쉬워요. 대신 "회원가입 한 기능"을 화면-API-저장까지 하나로 완성하고 바로 테스트하는 게 훨씬 안정적이었어요. 그 밖에 프론트와 백엔드 코드를 같은 대화·같은 저장소에 두면 AI가 양쪽 모양을 맞추기 수월하고, 목업을 실제로 바꿀 때는 "지금 화면이 쓰는 가짜 데이터를 방금 만든 실제 API 호출로 바꿔줘. 문서의 요청/응답 모양은 그대로 유지하고, 로딩과 에러 처리도 함께 넣어줘"라고 요구하면 됐어요. 그리고 매 단계마다 커밋을 남겨서 되돌아갈 체크포인트를 만드는 것도 중요했어요 — AI는 확신에 차서 멀쩡한 걸 망가뜨리기도 하니까요.

내보내기 전 마지막 점검

AI는 보안이 나빠서가 아니라 프롬프트에 보안이 없었기 때문에 "일단 돌아가는" 코드를 만들어요 — 목표가 '작동'이지 '안전'이 아니었으니까요. 그래서 내보내기 전에 꼭 두 가지를 확인해야 해요. 하나는 프론트에만 검증하고 백엔드 검증을 빼먹는 것이에요. 앞서 다룬 "프론트는 못 믿는다" 원칙처럼, 공격자는 화면을 안 거치고 API를 직접 부를 수 있으니 서버에서 입력을 반드시 다시 검증해야 해요. 다른 하나는 하드코딩된 주소나 키 노출이에요. localhost 주소를 코드에 박으면 배포에서 깨지고, API 키를 프론트 코드에 넣으면 개발자 도구로 다 보여요. 특히 NEXT_PUBLIC_이나 VITE_ 접두사가 붙은 값은 "브라우저에 공개"라는 뜻이라, 비밀값엔 절대 쓰면 안 돼요. 이걸 근본적으로 막는 방법은 브라우저가 키를 아예 안 드는 것 — 대신 중간에 프록시 서버를 하나 세워서 키는 그 서버만 들고 있게 하는 거예요. 이 구조는 번외편에 따로 정리했어요. 배포 전에는 AI에게 "이 코드 전체를 하드코딩된 비밀값, 서버 입력 검증 누락, CORS 설정, 인증 취약점 관점으로 점검해줘"라고 한 번 더 시켜보는 습관이 든든했어요.

연결 부담 자체를 줄이는 길도 있었어요. 프론트·백엔드·DB를 한 묶음으로 다루는 스타터(예: Next.js 풀스택 + Supabase)를 쓰면, 둘이 한 프로젝트 안에 있어서 CORS나 주소 불일치 같은 문제가 애초에 줄어들어요. 다만 만능은 아니에요 — 앞서 본 RLS처럼 보안 설정을 안 켜면 남의 데이터가 노출될 수 있으니, 편리함과 함께 점검은 여전히 사람의 몫이었어요.

여기까지가 화면 뒤에서 일어나는 일들의 전체 그림이었어요. 서버가 왜 필요한지에서 시작해서, 주소가 화면이 되는 여정, 백엔드가 실제로 하는 일과 지켜야 할 보안, 세상에 내보내는 배포, 그리고 이 모든 걸 잇는 연결까지 — 여섯 편에 걸쳐 정리해봤어요. 다음엔 이 백엔드가 다루는 데이터베이스 이야기로 이어져요.

이럴 때 의심하세요 — 화면과 서버를 이은 뒤 어딘가 어긋날 때

연결 단계의 문제는 대부분 "각자는 멀쩡하다"는 모습으로 나타나요. 화면만 보면 화면이, 서버만 보면 서버가 잘 돌아서, AI에게 한쪽만 보여 주면 멀쩡한 쪽을 고치기 쉬워요. 그래서 먼저 둘 사이에 실제로 오간 요청을 봐요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
배포한 사이트에서 데이터가 안 와요. 네트워크 탭에서 그 요청을 눌러 보면 요청 주소가 http://localhost:3000/...이에요 화면 코드에서 fetch에 넘긴 서버 주소예요. 에디터 전체 검색에 localhost를 넣어 봐요 주소를 코드에 직접 적은 곳을 환경변수 하나로 모아서, 개발할 때는 localhost, 배포 때는 배포한 서버 주소가 들어가게 해 달라고 해요. 이 주소는 비밀값이 아니라 공개 접두사를 써도 괜찮아요. 넣은 뒤엔 화면 쪽도 새로 배포해야 해요 (배포 편의 이 줄)
어제까지 되던 화면이, AI에게 서버 쪽만 고쳐 달라고 한 뒤 일부 칸에 undefined가 뜨거나 비어요 주고받을 데이터를 적어 둔 명세 문서예요. 그런 문서가 아예 없다면 그것부터 원인 후보예요 응답의 칸 이름과 모양을 화면 코드가 읽는 이름과 맞춰 봐요 (목업 편의 이 줄). 어긋난 곳을 찾으면 코드보다 문서를 먼저 고치고, AI에게 문서 기준으로 양쪽을 맞춰 달라고 해요
서버가 꺼져 있거나 느릴 때 화면이 아무 안내 없이 빈 채로 멈춰 있어요. 고장인지 기다리는 중인지 알 수가 없어요 fetch를 부르는 코드 주변이에요. 로딩 중 표시와, 실패했을 때 보여 줄 문구를 다루는 줄(catch 같은)이 있는지 봐요 서버를 켜 둔 터미널을 잠깐 끄고 화면을 새로고침해 봐요. 에러 안내가 안 나오면 에러 상태가 빠진 거예요. 느릴 때는 네트워크 탭 위쪽의 속도 제한 메뉴를 느린 쪽으로 바꾸고 로딩 표시가 보이는지 봐요
.env에 VITE_OPENAI_KEY처럼 공개 접두사와 비밀 키 이름이 한 줄에 붙어 있어요 .env 파일과 배포 플랫폼 환경변수 화면의 이름 목록이에요. Supabase 공개(anon) 키처럼 처음부터 공개용으로 만든 키는 예외지만, 그 대신 RLS가 켜져 있어야 해요 배포한 사이트에서 개발자 도구를 열고 Ctrl + Shift + F로 그 키 값의 앞 몇 글자를 검색해 봐요. 나오면 누구나 볼 수 있는 상태라 키를 새로 발급받고 프록시 서버 뒤로 옮겨요. 안 나와도 아직 안 불러온 파일에 있을 수 있어서, 비밀 키에 공개 접두사가 붙어 있다는 것만으로 옮길 이유가 돼요
한 번에 크게 시켰더니 AI는 "완성했어요"라는데 여러 기능이 동시에 안 되고, 하나를 고치면 다른 게 망가져요 마지막 커밋 이후 바뀐 파일 목록이에요. 터미널의 git status나 에디터의 소스 제어 칸에서 봐요 바뀐 파일이 수십 개면 원인을 좁히기 어려운 상태예요. 지금 상태를 커밋으로 남겨 두고, 기능 하나를 화면-API-저장까지 끝낼 때마다 돌려 보고 커밋해요 (커밋 편의 이 줄)

저장 버튼을 눌러도 아무 일이 없다면 표보다 먼저 요청이 나가기는 하는지 봐요. 안 나가면 목업 편의 이 줄, 나갔는데 실패했다면 상태 숫자, CORS 에러라면 CORS 편의 이 줄이에요.

배포 전 점검을 AI에게 맡길 때도 먼저 목록으로 보여 달라고 해요. "점검해 줘"라고만 하면 AI가 알아서 고치다가 멀쩡한 연결까지 건드릴 수 있어요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 화면과 서버 코드가 있는 프로젝트 폴더에서

배포 전에 이 프로젝트의 화면-서버 연결을 점검하려고 해. 아래 네 가지를 찾아서 한 곳마다 파일 이름과 줄 번호를 표로 보여 줘.
1) 화면 코드에 localhost나 서버 주소를 직접 적은 곳
2) VITE_나 NEXT_PUBLIC_ 같은 공개 접두사가 붙었는데 이름이나 쓰임새로 봐서 비밀 키로 보이는 환경변수 (값은 보여 주지 마)
3) fetch 같은 서버 호출 중에 로딩 표시나 에러 처리가 없는 곳
4) 화면 코드가 읽는 응답의 칸 이름과 서버 코드가 돌려주는 칸 이름이 서로 다른 곳
