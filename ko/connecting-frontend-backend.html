AI로 프론트-백엔드 연결하기

2026. 7. 20.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

← 이전 편 배포, 무료 호스팅, 그리고 집 컴퓨터를 서버로 쓰기

이제 조각이 다 모였어요 — 화면, 그리고 네트워크·백엔드·보안·배포. 마지막으로 이 조각들을 실제로 어떻게 잇는지가 남았어요. 여기가 초보가 가장 많이 헤매는 지점이라고 해서 저도 긴장하며 봤는데, 다행히 순서만 알면 훨씬 수월했어요.

가장 안정적인 순서 — 목업에서 진짜로

순서는 이래요. 먼저 지난 시리즈에서 만든 "가짜 데이터로 도는 화면"을 출발점으로 삼고, 그다음 그 화면이 부를 창구(엔드포인트)를 백엔드에 만들고, 마지막으로 가짜 데이터를 실제 호출로 교체해요. 여기서 결정할 게 하나 있는데, "앱 전체를 한 번에 시킬까, 나눠 시킬까"예요. 통째로 한 프롬프트에 다 시키는 건 초보에게 거의 항상 실패한다고 해요 — AI의 집중력과 기억에도 한계가 있거든요. 대신 "데이터 모양 → API → 화면"처럼 작게 쪼개서 시키면 실수를 훨씬 일찍 잡을 수 있었어요.

흐름을 정리하면, 목업으로 화면을 잘 만들어두면 백엔드는 정말 "한 겹 덧입히기"가 돼요. 화면이 가짜 데이터를 불러오던 한 줄을, 진짜 서버에 요청하는 한 줄로 바꾸기만 하면 화면 코드는 거의 그대로거든요. 첫 글에서 봤던 그 장면 — 친구가 링크를 열 수 있고, 새로고침해도 데이터가 남는 것 — 이 바로 이 과정의 끝에서 이뤄지는 거예요.

연결에서 실제로 겪는 문제들

연결 단계는 실무자들이 "바이브가 죽는 순간"이라고 부를 만큼 문제가 몰려요. 가장 큰 원흉은 계약 불일치예요. 프론트가 기대하는 데이터 모양과 백엔드가 주는 모양이 서로 다른 건데, AI를 쓰면 오히려 심해질 수 있어요 — 양쪽에 "얼추 맞는" 걸 따로 만들다 보니 서서히 어긋나는 거예요. 화면에 undefined가 뜨거나, 기대와 달리 한 겹 더 감싸인 응답이 오는 게 이 증상이에요. 처방은 나중에 맞추는 게 아니라, 주고받을 데이터를 처음부터 문서로 적어두고 그걸 기준으로 양쪽을 짜는 것이었어요.

두 번째는 로딩·에러 상태 누락이에요. 데이터가 오기 전 화면이 깜빡이거나, 서버가 오류를 줘도 앱이 멈춘 듯 보이는 증상인데, 모든 호출을 로딩/성공/에러 세 상태로 나눠 각각 화면을 준비해두면 해결돼요. 세 번째는 지난 글에서 본 CORS·주소·환경변수 문제예요. 다른 주소 간 요청이 막히거나 "로컬에선 됐는데" 하는 그 문제들이 사실 배포 문제이기도 하지만, 동시에 프론트-백엔드 연결 문제이기도 했어요. 처방도 그때와 같아요 — 백엔드가 내 프론트 주소를 허용하고, 주소는 환경변수로 관리하기.

연결을 매끄럽게 하는 전략

가장 강력한 전략은 주고받을 데이터를 문서로 남기고 시작하는 거예요. 어떤 창구(엔드포인트)가 있고, 각 요청·응답이 어떤 JSON 모양인지 적은 문서(API 명세)를 만들어두면, 계약 불일치가 근본적으로 사라져요. AI에게는 이렇게 요구하면 돼요 — "엔드포인트 목록과 각 요청/응답 예시(JSON)를 명세 문서로 만들어줘. 앞으로 이 문서를 기준으로 프론트와 백엔드를 짜자." 기능이 바뀌면 코드보다 이 문서를 먼저 고치는 습관을 들이면, 프론트와 백엔드가 늘 같은 문서를 보게 되니 서로 어긋날 일이 없어요.

두 번째 요령은 한 기능씩 끝까지 만드는 거예요("수직 슬라이스"라고 부르더라고요). "화면 전부 먼저, 서버 전부 나중에"처럼 층으로 나누면 AI가 다른 층을 몰라서 추측하다 틀리기 쉬워요. 대신 "회원가입 한 기능"을 화면-API-저장까지 하나로 완성하고 바로 테스트하는 게 훨씬 안정적이었어요. 그 밖에 프론트와 백엔드 코드를 같은 대화·같은 저장소에 두면 AI가 양쪽 모양을 맞추기 수월하고, 목업을 실제로 바꿀 때는 "지금 화면이 쓰는 가짜 데이터를 방금 만든 실제 API 호출로 바꿔줘. 문서의 요청/응답 모양은 그대로 유지하고, 로딩과 에러 처리도 함께 넣어줘"라고 요구하면 됐어요. 그리고 매 단계마다 커밋을 남겨서 되돌아갈 체크포인트를 만드는 것도 중요했어요 — AI는 확신에 차서 멀쩡한 걸 망가뜨리기도 하니까요.

내보내기 전 마지막 점검

AI는 보안이 나빠서가 아니라 프롬프트에 보안이 없었기 때문에 "일단 돌아가는" 코드를 만들어요 — 목표가 '작동'이지 '안전'이 아니었으니까요. 그래서 내보내기 전에 꼭 두 가지를 확인해야 해요. 하나는 프론트에만 검증하고 백엔드 검증을 빼먹는 것이에요. 앞서 다룬 "프론트는 못 믿는다" 원칙처럼, 공격자는 화면을 안 거치고 API를 직접 부를 수 있으니 서버에서 입력을 반드시 다시 검증해야 해요. 다른 하나는 하드코딩된 주소나 키 노출이에요. localhost 주소를 코드에 박으면 배포에서 깨지고, API 키를 프론트 코드에 넣으면 개발자 도구로 다 보여요. 특히 NEXT_PUBLIC_이나 VITE_ 접두사가 붙은 값은 "브라우저에 공개"라는 뜻이라, 비밀값엔 절대 쓰면 안 돼요. 배포 전에는 AI에게 "이 코드 전체를 하드코딩된 비밀값, 서버 입력 검증 누락, CORS 설정, 인증 취약점 관점으로 점검해줘"라고 한 번 더 시켜보는 습관이 든든했어요.

연결 부담 자체를 줄이는 길도 있었어요. 프론트·백엔드·DB를 한 묶음으로 다루는 스타터(예: Next.js 풀스택 + Supabase)를 쓰면, 둘이 한 프로젝트 안에 있어서 CORS나 주소 불일치 같은 문제가 애초에 줄어들어요. 다만 만능은 아니에요 — 앞서 본 RLS처럼 보안 설정을 안 켜면 남의 데이터가 노출될 수 있으니, 편리함과 함께 점검은 여전히 사람의 몫이었어요.

여기까지가 화면 뒤에서 일어나는 일들의 전체 그림이었어요. 서버가 왜 필요한지에서 시작해서, 주소가 화면이 되는 여정, 백엔드가 실제로 하는 일과 지켜야 할 보안, 세상에 내보내는 배포, 그리고 이 모든 걸 잇는 연결까지 — 여섯 편에 걸쳐 정리해봤어요. 다음엔 이 백엔드가 다루는 데이터베이스 이야기로 이어져요.
