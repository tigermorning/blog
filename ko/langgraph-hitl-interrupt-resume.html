멈췄다가 사람 답을 받아 잇는다 — interrupt·resume·체크포인터 (1)

2026. 9. 28.

HITL(Human-in-the-Loop)1이란 되돌릴 수 없는 실행 직전에 에이전트를 멈추고, 사람의 답을 받은 뒤 그 지점부터 이어서 실행하게 만드는 장치다.

  • 정확도를 아무리 올려도 사고 건수가 안 줄어들 때. 하루 200건을 처리하는 AI의 정확도가 95%든 99%든 남는 오류가 있고, 그 몇 건이 큰 금액이면 손해는 그대로예요. 이럴 때 정확도를 더 다듬는 대신 실행 직전에 멈추는 자리를 따로 둬요.
  • 환불 집행, 메일 자동 발송, 문서 자동 반영처럼 한 번 나가면 되돌리기 힘든 자동화에 승인 문턱 하나를 끼워 넣을 때.
  • 대기 중인 승인 건이 프로그램을 껐다 켜도 사라지지 않게, 나중에 다시 확인해도 이어서 처리되게 만들 때.

정확도로는 안 풀리는 문제

자료를 모으고 분류하고 초안을 만드는 데까지는 결과가 틀려도 다시 하면 돼요. 문제는 그 결과를 실제로 내보내는 순간이에요. 환불금을 계좌로 보내거나, 고객에게 메일을 발송하거나, 문의를 종결하는 일은 한 번 실행되면 되돌리기 어려워요.

AI가 아무리 정확해져도 100%에는 못 닿아요. 정확도 95%인 AI에게 하루 200건을 맡기면 매일 10건이 확인 없이 잘못 나가고, 정확도를 99%로 올려도 2건은 남아요. 그 2건이 31만 원짜리 환불이거나 잘못된 고객 안내라면, 정확도가 올라간 것과 상관없이 손해는 그대로예요. 프롬프트를 아무리 다듬어도 이 계산 자체가 사라지지는 않아요 — 판단을 정확하게 만드는 노력과는 별개로, AI가 틀렸을 때 결과가 나가기 전에 막을 자리가 따로 필요해요.

선택지는 셋이에요. 사람이 결과를 모두 확인하면 가장 안전하지만 200건이면 200번을 봐야 해 자동화의 의미가 거의 없어요. 전부 자동으로 내보내면 빠르지만 잘못된 결과를 막을 방법이 없어요. 그래서 위험한 건에서만 멈추고 사람 확인을 받은 뒤 나머지는 자동으로 이어가는 세 번째 방식이 필요해요 — 200건 중 위험한 20건만 사람에게 가고 나머지 180건은 자동으로 끝나면, 자동화 속도는 유지하면서 큰 사고는 사람이 막을 수 있어요. 이 방식을 HITL(Human-in-the-Loop)이라고 불러요.

HITL을 만들려면 두 가지가 필요해요. 하나는 일을 하던 중 멈췄다가 사람의 답을 받아 이어서 실행하는 기능이고, 다른 하나는 어떤 건에서 멈출지 정하는 기준이에요. 이 편은 앞의 것 — 멈추고 이어가는 기능을 다뤄요. 기준을 정하고 검증하는 법은 다음 편이에요.

비유 — 옷가게 환불 접수대

온라인 옷가게의 상담 AI가 환불 요청을 받아요. 대부분은 AI 혼자 판단해서 끝내지만, 금액이 크거나 판정이 애매한 건은 접수대 뒤 매니저에게 쪽지를 한 장 건네고 답을 기다려요. 매니저가 자리를 비웠어도 접수대 장부에 "이 손님 건은 여기까지 처리했다"고 적혀 있으니, 나중에 매니저가 돌아와 답만 주면 그 손님 건은 처음부터가 아니라 멈춘 자리부터 다시 이어져요.

비유 속 요소원래 개념
매니저에게 건네는 쪽지 내용(요청, 금액, 통과시키면 벌어질 일)interrupt(...)에 담는 값 — 이 쪽지가 곧 승인 화면 내용이 돼요
매니저가 쪽지에 적어 돌려주는 답(승인/반려)Command(resume=답)으로 되돌아오는 값
접수대 장부 — 어느 손님 건이 어디까지 처리됐는지 적어 둠체크포인터2
손님마다 다른 접수번호thread_id3 — 이 번호로 손님 건이 서로 안 섞여요

핵심 한 줄: 매니저가 몇 시간 자리를 비웠어도 장부만 있으면 그 손님 건부터 그대로 이어갈 수 있다는 게 이 구조의 전부다.

전체 흐름

실선은 코드 한 줄로 이미 정해진 길(add_conditional_edges)이고, 점선은 사람을 기다리는 자리예요. 담당자가 답을 줄 때까지 오른쪽 실행(execute/reject)은 시작조차 안 해요.

멈추고 이어가는 두 함수 — interrupt와 resume

환불이라면 판정을 시도하고(review) → 승인 여부에 따라 → 집행하거나(execute) 반려하는(reject) 단계로 나눠요. review 안에서 사람에게 물어야 할 순간에 interrupt(...)를 부르면 에이전트는 그 자리에서 멈추고, 괄호 안에 넣은 값이 담당자에게 그대로 전달돼요 — 이게 곧 승인 화면 내용이에요. 담당자가 Command(resume=답)으로 답을 넣으면, 처음부터가 아니라 멈춰 있던 자리부터 이어져요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요(이 글은 langgraph 1.2.11 기준)

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command
from typing_extensions import TypedDict

class RefundCase(TypedDict):
    request: str
    amount: int
    decision: str
    paid: int

def review(state: RefundCase):
    answer = interrupt({
        "요청": state["request"],
        "금액": f'{state["amount"]:,}원',
        "통과시키면": f'{state["amount"]:,}원이 계좌로 나갑니다',
    })
    return {"decision": answer}

def execute(state: RefundCase):
    return {"paid": state["amount"]}

def reject(state: RefundCase):
    return {"paid": 0}

def route(state: RefundCase):
    return "execute" if state["decision"] == "approve" else "reject"

b = StateGraph(RefundCase)
b.add_node("review", review)
b.add_node("execute", execute)
b.add_node("reject", reject)
b.add_edge(START, "review")
b.add_conditional_edges("review", route, ["execute", "reject"])
b.add_edge("execute", END)
b.add_edge("reject", END)

app = b.compile(checkpointer=InMemorySaver())   # 체크포인터 없으면 interrupt를 못 써요

config = {"configurable": {"thread_id": "R3"}}
out = app.invoke(
    {"request": "코트를 한 달 입었는데 어깨 솔기가 터졌습니다.", "amount": 310000},
    config,
)
print("돈이 나갔는가:", out.get("paid", 0) > 0)
print(out["__interrupt__"])

개념 설명용 코드 — 위 코드를 실제로 돌려서 확인한 출력이에요

돈이 나갔는가: False
[Interrupt(value={'요청': '코트를 한 달 입었는데 어깨 솔기가 터졌습니다.', '금액': '310,000원', '통과시키면': '310,000원이 계좌로 나갑니다'}, id='6bd5f669...')]

review가 끝나기도 전에 실행이 멈췄고, execute는 아직 시작도 안 했어요(paid가 없어서 False). 담당자에게는 interrupt에 넣은 세 줄(요청·금액·통과시키면)이 그대로 보여요. 이제 같은 config(같은 thread_id)로 답을 넣어 이어가요.

실행: 로컬 파이썬 — 위 코드 바로 아래에 이어서 실행해요

out2 = app.invoke(Command(resume="approve"), config)
print(out2)

개념 설명용 코드 — 위 코드를 실제로 돌려서 확인한 출력이에요

{'request': '코트를 한 달 입었는데 어깨 솔기가 터졌습니다.', 'amount': 310000, 'decision': 'approve', 'paid': 310000}

같은 그래프, 같은 요청인데 담당자가 넣은 한 단어("approve")로 결과가 갈렸어요. resume="reject"로 다시 돌리면 route가 reject로 갈라져 paid가 0으로 남아요 — 실제로 다른 손님 건(9,000원)에 reject를 넣어 확인해도 paid: 0이 그대로 나와요.

체크포인터 — 멈춘 자리를 기억하는 장부

interrupt로 멈추면 실행은 그 자리에서 함수가 반환된 것과 같아요. 나중에 resume으로 이어가려면 지금까지 어떤 값이 계산됐고 다음에 어느 단계를 실행할지 어딘가 남아 있어야 하는데, 이걸 저장하는 부품이 체크포인터예요. 단계 하나가 끝날 때마다 그 시점의 상태와 다음 단계 이름을 기록해요(기록 한 건 = 체크포인트). get_state로 가장 최근 체크포인트를, get_state_history로 쌓인 전체를 볼 수 있어요.

실행: 로컬 파이썬 — 멈춘 직후에 이어서 실행해요

snap = app.get_state(config)
print("values:", snap.values)
print("next:", snap.next)

개념 설명용 코드 — 위 코드를 실제로 돌려서 확인한 출력이에요

values: {'request': '코트를 한 달 입었는데 어깨 솔기가 터졌습니다.', 'amount': 310000}
next: ('review',)

멈춘 직후엔 저장된 값이 요청 두 칸뿐이고 decision·paid는 아직 없어요. next에는 "review"가 적혀 있어요 — 재개하면 여기서부터라는 뜻이에요. resume="approve"로 이어가서 끝난 뒤 같은 걸 다시 찍어 보면 values에 decision·paid가 추가되고 next는 빈 값(())이에요 — 더 실행할 단계가 없다는, 곧 처리가 끝났다는 뜻이에요. 승인 대기 목록을 만든다면 next가 안 비어 있는 건만 골라내면 돼요.

중요꼭 기억할 것

체크포인터가 없으면 interrupt를 아예 쓸 수 없어요. 멈춘 뒤 이어갈 근거(다음 단계·지금까지의 값)를 어디에도 남기지 않기 때문이에요. compile(checkpointer=...)로 반드시 지정해야 해요.

주의 — 멈춘 단계는 처음부터 다시 실행돼요

재개할 때 에이전트는 interrupt가 있던 줄의 다음 줄부터 이어가지 않아요. 멈췄던 단계(review) 전체를 처음부터 한 번 더 실행해요. 실행 중이던 함수의 중간 상태는 저장하지 못해서 이렇게 설계됐어요. 그래서 멈추기 직전에 "고객님 요청을 검토 중입니다" 문자를 보내는 코드를 같이 넣어 두면, 재개할 때 그 줄도 다시 실행돼 고객이 같은 문자를 두 번 받아요. 직접 만들어서 돌려 봤어요.

개념 설명용 코드 — review 노드 맨 위에 문자 발송을 넣고 SENT 리스트에 기록만 하도록 바꾼 버전이에요

SENT = []

def review_bad(state: RefundCase):
    SENT.append(f"검토 중 문자 발송: {state['request'][:10]}")   # interrupt보다 위에 둔 부작용
    answer = interrupt({"금액": state["amount"]})
    return {"decision": answer}

# ... 그래프를 review_bad로 구성한 뒤 ...
app.invoke({"request": "코트 환불", "amount": 310000}, config)
app.invoke(Command(resume="approve"), config)
print("문자 발송 기록:", SENT)

개념 설명용 코드 — 위 코드를 실제로 돌려서 확인한 출력이에요

문자 발송 기록: ['검토 중 문자 발송: 코트 환불', '검토 중 문자 발송: 코트 환불']

딱 한 번 요청했는데 문자는 두 번 기록됐어요 — 한 번은 멈추기 전, 한 번은 재개할 때 review가 처음부터 다시 실행되면서예요. 원칙은 하나예요. 사람에게 묻는 단계 안에서, 묻기 전에 바깥으로 나가는 동작(문자·메일·로그·외부 API 호출)을 두지 말 것. 알림이 필요하면 review 밖의 별도 단계로 분리해요.

중요꼭 기억할 것

resume으로 재개하면 멈춘 노드는 이어서가 아니라 처음부터 다시 실행돼요. 그 노드 안에 있는 부작용(발송·기록·외부 호출)은 재개할 때마다 한 번씩 더 일어나요.

나쁜 선택 vs 좋은 선택 — 환불 접수대의 알림 문자

환불 요청이 들어오면 접수 확인 문자를 보내고, 금액이 크면 매니저 승인을 받은 뒤 집행하는 흐름을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: review 노드 맨 위에서 "검토 중입니다" 문자를 보내고, 그 아래에서 interrupt로 멈췄어요.

무슨 일이 생기나: 매니저가 승인해서 재개되는 순간 review가 처음부터 다시 실행되며 문자가 한 번 더 나가요. 손님은 같은 문자를 두 번 받고, 원인을 찾으려 해도 interrupt 자체는 멀쩡히 동작해서 눈치채기 어려워요.		 무엇을 했나: 문자 발송을 review 밖, interrupt를 거치지 않는 별도 단계(요청이 들어온 직후 한 번만 실행되는 노드)로 옮겼어요.

무슨 일이 생기나: review가 몇 번을 재실행되든 문자는 접수 시점에 이미 한 번만 나간 뒤라 다시 나가지 않아요. 재개가 몇 번 걸리든(다시 판정 요청 등) 안전해요.

정확도만으로는 왜 부족한지, 그리고 대기 건을 어디에 저장해야 하는지를 가늠할 때 쓰는 숫자예요.

무엇의 숫자인가값알아 둘 것
정확도 95%/99% AI가 하루 200건을 처리할 때 남는 오류10건 / 2건정확도를 5%p 더 올려도 오류가 0이 되지는 않는다는 계산의 근거예요. 자기 업무의 건수·정확도로 다시 계산해 보면 사람 확인 자리가 왜 필요한지 가늠할 수 있어요
InMemorySaver의 저장 위치메모리(프로세스 안)프로그램을 껐다 켜면 대기 중이던 건이 사라져요. 실습에는 충분하지만, 사람 답을 몇 시간~며칠 기다려야 하는 운영에는 부족해요
SqliteSaver·PostgresSaver의 저장 위치파일 / 데이터베이스재시작해도 대기 건이 남아요. 여러 서버가 함께 써야 하면 PostgresSaver 쪽이에요

이럴 때 의심하세요 — HITL 그래프가 이상하게 돌 때

이 편의 구조는 실행이 중간에 끊겼다가 나중에 이어진다는 게 핵심이라, 문제도 재개하는 순간이나 여러 건이 동시에 대기할 때 드러나요.

증상이 아직 없어도, AI에게 "승인받고 나서 실행하는 구조로 만들어 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
승인 후 실행됐는데, 고객이 같은 안내 문자나 메일을 두 번 받았다는 문의가 들어와요 interrupt(...)를 호출하는 노드 안에서, 그 호출보다 위에 있는 줄들이에요. interrupt 자체의 동작은 대개 범인이 아니에요 그 줄들이 문자·메일 발송, 로그 기록, 외부 API 호출 같은 부작용을 일으키는지 봐요. 있으면 재개할 때마다 한 번씩 더 실행돼요 — 그 부작용을 노드 밖으로 옮겨요 (멈춘 단계는 처음부터 다시 실행돼요)
서버를 재시작했더니 어제부터 기다리던 승인 건이 통째로 사라졌어요. 담당자가 분명 확인 안 했다는데 목록에 없어요 compile(checkpointer=...)에 넘긴 체크포인터 종류예요 InMemorySaver를 쓰고 있는지 봐요. 맞으면 파일이나 DB에 저장하는 체크포인터로 바꾸고, 재시작 후에도 get_state(config)가 같은 값을 돌려주는지 확인해요 (체크포인터가 없으면 interrupt를 못 써요)
여러 건이 동시에 대기 중일 때, A 건에 준 승인 답이 엉뚱하게 B 건에 반영돼요 invoke에 넘기는 config의 thread_id예요 건마다 다른 thread_id를 쓰는지 확인해요. 같은 값이 재사용되고 있으면 요청 하나당 고유 번호(주문번호 등)로 바꿔요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — LangGraph 코드가 있는 프로젝트 폴더에서

이 프로젝트의 LangGraph 코드에서 아래를 찾아 표로 보여 줘. 아직 코드는 고치지 마.
1. interrupt(...)를 호출하는 노드마다: 파일 이름과 줄 번호, 그 호출보다 위에 있는 줄 중 부작용(발송·기록·외부 호출)이 있는지
2. compile(checkpointer=...)에 어떤 체크포인터를 쓰고 있는지
3. invoke를 호출하는 곳마다 thread_id를 어떻게 만들어 넣는지, 같은 값이 재사용될 여지가 있는지

직접 해보기

  1. 부작용을 앞으로 옮겨 보기 — 바꿀 것: review 안에서 interrupt 호출보다 위에 리스트에 기록을 남기는 줄을 넣어요. 측정할 것: resume 후 그 기록이 몇 번 남는지. 비교할 것: 같은 기록을 review 밖으로 옮겼을 때와 횟수를 대 봐요.
  2. 체크포인터를 바꿔 보기 — 바꿀 것: InMemorySaver를 파일 기반 체크포인터로 바꿔요. 측정할 것: 파이썬 프로세스를 새로 띄운 뒤에도 get_state(config)가 같은 값을 돌려주는지. 비교할 것: 메모리 버전은 재시작 후 어떻게 되는지 적어 둬요.

정답은 하나가 아니에요. 자기 조건(요청 건수, 담당자 응답 속도)에서 직접 돌려 보고 기록으로 비교하는 게 요령이에요.

함께 읽으면 좋은 글

  • 흐름을 그림으로 짠다 — LangGraph의 State·Node·Edge (2) — 이 글의 체크포인터가 저장하는 그 State가 무엇인지 먼저 보는 글이에요.
  • 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건 (3) — "승인 대기"를 하네스의 정식 상태 하나로 다룬 글로, 거절 뒤 우회 실행을 막는 감각이 이 글의 재실행 문제와 이어져요.
  1. HITL(Human-in-the-Loop) — 자동화의 마지막 실행 직전에 사람의 확인·승인을 끼워 넣는 설계를 말해요. ↩
  2. 체크포인터(checkpointer) — 멈춘 시점의 상태와 다음에 실행할 단계를 저장해 뒀다가 나중에 그대로 복원하는 장치예요. ↩
  3. thread_id — 동시에 여러 건이 대기할 때 그중 한 건을 가리키는 고유 값이에요. ↩
