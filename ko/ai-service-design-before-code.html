AI 기능을 서비스로 설계한다는 것 — 코딩 에이전트에게 맡기기 전에 정할 것 (1)

2026. 10. 20.

※ 이 글은 모두의연구소 학습 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

AI 기능을 서비스로 설계한다는 것은, 코딩 에이전트에게 개발을 맡기기 전에 누가·언제·어디서 쓰는지와 키·데이터·실패를 어디에 둘지를 사람이 먼저 정해 문서로 남기는 일이다.

어디에 쓰나
  • AI에게 앱을 만들어 달라고 부탁하려는 순간. 부탁한 문장에 없는 것은 AI가 가장 빨리 돌아가는 쪽으로 정해 버려요.
  • 만든 기능을 동료에게 보여 줬더니 "나도 써 보게 주소 좀 줘"라는 말이 돌아왔을 때
  • 회사에서 쓰는 도구로 만들려는데 "회사 문서를 외부 AI에 보내도 되나요?"에서 막혔을 때

코딩 에이전트1에게 부탁하면 AI 기능 하나는 하루가 안 걸려 만들어져요. 어려운 건 그다음이에요. 만든 기능을 동료나 고객이 계속 쓰게 만드는 일은 훨씬 오래 걸려요. 주소를 공유해도 며칠 뒤에는 접속하는 사람이 없고, 회사 안에서 쓰려 하면 위의 "외부 AI에 보내도 되나요?"라는 질문에서 막혀요. 외부에 공개했더니 모르는 사람이 내 API 키2 비용으로 기능을 호출하는 일도 있어요.

앞의 문제들은 코드를 못 짜서가 아니라 "어떻게 쓰게 할지"를 정하지 않아서 생겨요. 몇 주 뒤 어느 파일을 고쳐야 할지 모르는 문제는 "코드를 어떻게 나눠 둘지"를 정하지 않아서 생기고요. 그래서 코드를 짜기 전에 정해 둘 것을 순서대로 적어 두는 일을 이 글에서는 설계라고 불러요. 이 시리즈는 만든 AI 기능을 다른 사람이 쓰게 하는 데까지를 다루고, 1편은 코드를 짜기 전, 2편은 서버에 올리는 순간이에요.

비유로 먼저 — 식당을 열기 전에 사장이 정할 것

식당을 연다고 해 볼게요. 요리사(코딩 에이전트)에게 "식당 하나 열어 줘"라고만 말하면 요리는 금방 나와요. 그런데 누가 손님인지, 홀에서 받을지 배달할지, 주문이 몰리면 번호표를 줄지, 금고 열쇠를 어디에 둘지는 말하지 않았으니 요리사가 가장 빨리 열 수 있는 쪽으로 정해요. 열쇠가 카운터 위에 놓이는 식으로요. 개업 전에 사장인 내가 정할 것을 적어 두는 일이 설계예요. 이 시리즈는 비유를 이 식당 하나로만 쓸게요.

비유 속 요소원래 개념
사장(나)이 요리사에게 — "식당 열어 줘"라고 부탁내가 코딩 에이전트에게 — 앱 개발을 요청
어떤 손님이 언제 오는지 적기사용 맥락3 — 대상 사용자, 필요한 시점, 기기와 도구
홀에서 팔지, 배달할지, 도시락으로 팔지 정하기제공 채널4 — 기성 AI 도구·메신저 봇·웹앱
바로 내주는 메뉴 · 번호표를 받아 나중에 부르는 메뉴동기 처리·비동기 처리5
주문이 틀렸을 때의 사과·재조리 절차, 주방장이 나가기 전에 한 번 확인하는 단계AI 오류 대응 — 폴백 응답6, 휴먼 인 더 루프7

핵심 한 줄: 요리사에게 맡기기 전에 사장이 정해 둘 것을 적어 두면, 요리사가 제멋대로 채운 빈칸이 나중에 사고로 돌아오지 않는다.

다만 여기서 비유가 끊기는 점이 있어요. 식당 손님은 가게 앞까지 와야 하지만, 서비스는 주소만 알면 누구든 부를 수 있어요. 그리고 AI 기능은 요청 한 번마다 비용이 나가요. 그래서 "누가 부를 수 있는가"와 "비용을 어디까지 허용하는가"는 식당 비유에 없는 항목으로 따로 정해야 해요.

전체 흐름 — 설계는 이 순서로 정해요

읽는 법: 윗줄은 왼쪽에서 오른쪽으로 읽고, ④에서 아랫줄 ⑤로 내려와 다시 오른쪽으로 읽어요. 아랫줄 끝의 ⑧에서 정하지 않은 항목이 나오면 점선을 따라 앞으로 돌아가요. 설계는 한 번에 끝나는 순서표가 아니라, 빈칸을 찾으며 앞뒤로 오가는 일이에요.

중요꼭 기억할 것

부탁한 문장에 없는 부분은 에이전트가 가장 빨리 돌아가는 방법으로 채워요. 설계는 그 빈칸을 코드 전에 사람이 채우는 일이고, 그림은 빈칸을 눈에 보이게 만드는 도구일 뿐이에요.

정할 것은 네 덩어리 — 그리고 한 장으로 모아요

위 흐름의 윗줄과 아랫줄을 네 덩어리로 묶으면 이래요. 이 넷을 한 장에 모은 문서를 PRD13라고 불러요.

덩어리정하는 것정하지 않으면
① 쓰이는 장면과 제공 방식누가·언제·어떤 기기에서 쓰는지, 어떤 통로로 내보낼지주소만 공유해 놓고, 쓰는 사람이 서서히 사라져요
② 처리 방식과 출력 형식바로 답할지 접수하고 나중에 알릴지, 결과를 어떤 모양으로 줄지긴 작업에서 화면이 멈추거나 결과를 잃어요
③ AI가 틀렸을 때의 대응어떤 오류가 날 수 있고 사용자에게 어떻게 보일지틀린 답이 그대로 사용자에게 가요
④ 구조무엇이 무엇을 부르는지, 무엇을 어디에 저장하는지, 키를 어디에 두는지에이전트가 빈칸을 제멋대로 채워요

① 쓰이는 장면과 제공 방식 — 사용자는 이미 쓰는 도구 안에서 살아요

사용자는 하루 대부분을 이미 쓰는 도구 안에서 보내요. 회사라면 업무 메신저·메일·문서 도구이고, 개인이라면 휴대폰 메신저·노트 앱이에요. 별도 주소로 접속해야 하는 기능은 처음엔 쓰이다가 사용률이 빠르게 떨어져요. 그래서 제공 방식을 정하기 전에, 이 기능이 필요한 순간을 먼저 적어요. 아래는 "강의 필기를 넣으면 복습 노트와 퀴즈를 만들어 주는 기능"을 예로 든 표예요.

항목물어볼 것예 (필기 → 복습 노트)
대상 사용자누가 쓰나하루 7시간 강의를 듣고 노트 앱에 필기하는 수강생
필요한 시점언제 필요한가강의 직후, 다음 날 아침 강의 전
사용 중인 기기와 도구그때 무엇을 들고 있나직후에는 노트북의 노트 앱, 다음 날 아침에는 휴대폰
결과를 받은 뒤의 다음 작업결과로 무엇을 하나노트 앱에 저장하고 다음 날 퀴즈를 푼다
현재 방식지금은 어떻게 하나필기를 다시 읽으며 30분쯤 정리하고, 대부분 미룬다

표를 채우면 요구사항이 저절로 보여요. 복습 노트는 노트북 앞에서 만들지만 퀴즈는 다음 날 휴대폰으로 풀어요. 그러니 결과가 휴대폰에서 다시 열 수 있는 곳에 남아야 해요. 노트북에서만 열리는 화면이나 대화가 금방 밀려 올라가는 단체 대화방은 이 요구사항에 안 맞아요.

직접 확인하지 못한 칸은 "가정"이라고 적어 두고, 인터뷰와 자료 조사로 하나씩 줄여요. 인터뷰에서는 기능을 설명하지 말고 그 작업을 마지막으로 한 순간을 물어요("어제 강의 끝나고 필기는 어떻게 정리했어요?"). "이런 기능이 있으면 쓰시겠어요?"는 묻지 않아요. 대부분 "네"라고 답해서 판단 근거가 안 돼요. 사람을 만나기 어려우면 비슷한 서비스의 별점 2~3점 후기를 읽어요. 별점 1점에는 결제나 오류 불만이 많고, 2~3점에 "이건 좋은데 이게 불편하다"는 구체적인 사용 장면이 많아요.

제공 채널은 여러 가지이고, 오른쪽으로 갈수록 직접 정할 수 있는 범위와 개발 부담이 함께 커져요.

채널좋은 점한계
기성 AI 도구Claude 프로젝트·GPTs 같은 기존 서비스에 지침과 문서를 설정해 공유해요. 코드가 없어 몇 시간이면 내보내요사용자가 그 도구의 계정이 있어야 하고, 화면·저장·접근 범위는 도구가 정한 대로예요
메신저 봇사용자가 이미 있는 대화방 안에서 쓰고, 정해진 시각에 먼저 말을 걸 수 있어요대화가 밀려 올라가 결과를 보관하기 어렵고, 운영자 한 명의 키로 비용이 나가요
웹앱화면·로그인·데이터·과금을 모두 직접 정해요개발·배포·운영을 전부 맡아야 해요

그래서 실무에서는 기성 AI 도구로 먼저 확인하고, 필요가 생길 때 오른쪽으로 옮기는 경우가 많아요. 옮길 때는 대개 셋 중 하나예요. 도구 계정이 없는 사람도 써야 할 때, 사용량과 비용을 직접 관리해야 할 때, 결과를 메신저나 사내 시스템에 자동으로 연결해야 할 때예요. 처음부터 웹앱을 만들면 사용자가 정말 쓰는지 확인하기도 전에 몇 주를 써요.

② 처리 방식과 출력 형식 — 기다리는 시간에 맞춰요

일반 웹 서비스는 요청에 1초 안에 답해요. AI 호출은 짧은 답도 몇 초가 걸리고, 긴 녹음이나 문서 여러 개를 다루면 몇 분이 걸려요. 그래서 처리 시간과 사용자가 결과를 필요로 하는 때에 맞춰 처리 방식을 골라요.

방식어떻게 돌아가나어울리는 경우
동기 처리요청하고 끝날 때까지 기다렸다가 같은 자리에서 답을 받아요강의 한 번 분량의 필기 요약처럼 몇 초면 끝나는 일
비동기 처리접수했다는 응답을 먼저 주고, 뒤에서 처리한 뒤 완료를 알려요. 상태 표시와 알림 통로를 함께 정해요2시간짜리 강의 녹화 요약처럼 오래 걸리는 일. 동기로 하면 사용자가 화면을 못 떠나고 연결이 끊기면 결과를 잃어요
스케줄 실행사용자 요청 없이 정해진 시각에 돌아요매주 같은 형식으로 필요한 주간 보고 초안

출력 형식도 함께 정해요. AI에게 "요약해 줘"라고만 하면 매번 길이와 순서가 달라서, 사용자가 받을 때마다 필요한 부분을 다시 찾아 정리해야 해요. 결과를 받은 뒤의 다음 작업에 맞춰 항목·순서·길이·값이 없을 때의 표기를 정해요. 다음 날 휴대폰으로 퀴즈를 푼다면 퀴즈는 휴대폰 화면에서 읽을 수 있는 길이여야 하고, 정답은 문제와 따로 있어야 해요.

③ AI가 틀렸을 때의 대응 — 없앨 수 없으니 장치를 둬요

AI는 그럴듯한 오류를 내요. 필기에 없는 설명을 개념 정의에 덧붙이거나, 퀴즈의 정답을 틀리게 적는 식이에요. 이런 오류는 없앨 수 없으니, 사용자에게 그대로 전달되지 않게 대응 장치를 둬요.

장치하는 일예
출처 표시답마다 근거의 위치를 붙여요"정의: … (필기 12번째 줄)"
휴먼 인 더 루프사람이 확인한 뒤에 내보내요단체 대화방에 올리기 전에 봇 운영자가 퀴즈를 확인해요
폴백 응답실패하거나 확신이 없을 때 정해 둔 안내를 줘요"담당자를 녹음에서 찾지 못했어요. 직접 입력해 주세요"
에스컬레이션확실하지 않은 것은 사람 담당에게 넘겨요정답이 불확실한 문제는 운영자에게 보내요
피드백과 되돌리기사용자가 틀렸다고 알리고 이전 상태로 돌릴 수 있게 해요"틀려요" 버튼. 모인 평가는 나중에 품질을 재는 데이터가 돼요

다섯 가지를 다 넣을 필요는 없어요. 오류의 영향도가 클수록 많이 넣어요. 혼자 보는 복습 노트라면 출처 표시 하나로 충분하지만, 여럿이 보는 대화방에 올라가는 퀴즈는 사람 확인까지, 틀리면 여러 사람이 잘못 외우게 되는 내용은 에스컬레이션까지 넣어요. 장치가 늘수록 사용자가 확인할 단계도 늘어나니 편의성과 함께 따져요. 표로 적을 때 "사용자에게 보이는 문구" 칸은 실제로 나갈 문장으로 써요. "오류가 발생했습니다"보다 다음에 무엇을 하면 되는지 알 수 있는 문장이 좋아요.

코드 없이 확인하기 — 만들기 전에 사람이 대신해 봐요

여기까지 정한 것은 모두 가정이에요. 코드를 짠 뒤에 채널이 틀렸다는 걸 알면 이미 며칠을 쓴 뒤예요. 그래서 코드 없이 확인해요. 방법은 둘이에요. 하나는 오즈의 마법사 테스트로, 시스템이 하는 일을 사람이 뒤에서 대신해요. 다른 하나는 기성 AI 도구 프로토타입으로, 지침·출력 형식·오류 규칙을 AI 도구의 프로젝트에 설정해 써 보게 해요.

  • 짝과 역할을 나눠요. 한 명은 참여자, 한 명은 진행자예요. 15분씩 역할을 바꿔 두 번 해요.
  • 진행자는 상황 하나만 알려 줘요. "방금 오전 강의가 끝났고 점심 먹으러 가는 길이에요. 오늘 배운 내용을 복습해 두고 싶어요." 사용법은 설명하지 않아요.
  • 진행자는 정해 둔 출력 형식대로 직접 응답하고, 테스트 중에는 돕지 않아요.
  • 노트에는 말보다 행동을 적어요. 처음 한 행동, 멈추거나 질문한 지점, 결과를 받은 직후의 행동, 수정한 부분, 요청 사항이에요. "좋네요"라고 하면서 결과의 절반을 지우고 다시 쓰는 사람도 있어요.

같은 문제가 두 사람에게서 나오면 바꾸고, 한 사람에게서만 나오면 기록해 두었다가 파일럿에서 다시 확인해요. 지침을 고쳐도 해결되지 않는 요구(예: 다음 날 틀린 문제만 다시 풀고 싶다)는 그 채널의 한계예요. 이런 요구가 반복되면 다음 채널로 옮길 후보로 적어 둬요.

④ 구조 — 빈칸을 드러내는 세 장의 문서

웹앱을 고르면 화면·서버·저장·AI 호출을 모두 직접 설계해야 해요. 기성 AI 도구에서는 도구가 대신 정해 주던 것들이에요. 코딩 에이전트에게 맡기면 이 설계도 에이전트가 하는데, 요청에 없는 부분은 가장 빨리 동작하는 방법으로 채우기 쉬워요.

요청에 없던 것에이전트가 고르기 쉬운 방법나중에 드러나는 문제
API 키 위치화면(클라이언트) 코드에 그대로 적어요브라우저 개발자 도구로 키가 보여서, 남이 내 비용으로 호출해요
데이터 저장소서버 메모리나 브라우저 저장소에 담아요서버를 다시 켜거나 기기를 바꾸면 데이터가 사라져요
데이터 소유자정하지 않아요다른 사용자의 데이터를 읽거나 고칠 수 있어요
외부 API 실패 처리처리하지 않아요AI 응답이 늦거나 실패하면 화면이 멈추거나 빈 데이터가 저장돼요
코드 나누기한 파일에 모두 써요기능 하나를 고치다 관계없는 기능이 함께 깨져요

어느 것도 처음 화면이 뜰 때는 드러나지 않아요. 사용자가 늘거나, 다시 배포하거나, 기능을 고칠 때 드러나요. 그래서 코드를 쓰기 전에 아래 세 문서로 구조를 적어 둬요.

  • 시퀀스 다이어그램 — 사용자 동작 하나가 처리되는 동안 구성 요소 사이에 오가는 호출을 시간 순서로 그려요. 요청은 실선, 응답은 점선, 조건에 따라 갈리는 곳은 alt 상자로 표시해요.
  • 아키텍처 다이어그램 — 시스템을 이루는 구성 요소와 그 사이의 호출 관계를 그려요. 서버 안은 책임 하나에 모듈 하나씩 나눠 두면, 시세 조회를 고칠 때 그 모듈만 열면 돼요.
  • 데이터 모델 — 저장하는 것마다 생성 시점, 소유자, 저장소, 보존 기간을 적은 표예요. 화면에 보이는 것과 저장되는 것은 달라요. AI 초안은 화면에 보여도 저장하지 않기로 할 수 있고, 알림 작업은 화면에 안 보여도 처리될 때까지 저장돼요.

그리는 순서는 시퀀스가 먼저예요. 사용자 동작 하나에서 출발하니 앞에서 정한 쓰이는 장면·처리 방식과 그대로 이어지고, 그리고 나면 필요한 구성 요소와 저장할 데이터가 함께 드러나요. 예를 들어 "명함 사진을 올리면 연락처로 정리해 주는 앱"의 시퀀스를 그리면 이런 것이 처음 보여요.

  • AI 호출은 몇 초가 걸리고 호출마다 비용이 나가요. 사용자가 버튼을 여러 번 누르면 비용도 그만큼 늘어요. → 타임아웃과 실패 시의 폴백을 정하고, 요청 중에는 버튼을 막아요.
  • "연락처가 바뀌면 수백 명에게 알린다"를 등록 요청 안에서 처리하면 사용자가 오래 기다려요. → 알림은 작업 큐에 등록만 하고 바로 응답해요.

데이터 모델의 소유자 칸은 인가14로 이어져요. 연락처의 소유자가 사용자라면, 수정·삭제 요청이 올 때마다 서버는 요청한 사람이 그 소유자인지 검사해야 해요. 보존 기간 칸은 개인정보와 저장 비용으로 이어져요. 기간을 정하지 않으면 탈퇴한 사용자의 사진이 계속 남고 저장 비용도 계속 나가요.

다 그렸으면 위 표의 다섯 항목(API 키 위치, 데이터 저장소, 데이터 소유자, 외부 API 실패 처리, 코드 나누기)을 내 설계에서 모두 정했는지 점검해요. 정하지 않은 항목은 에이전트가 대신 정하게 되는 항목이에요. 마지막으로 에이전트에게 설계를 보여 주되, 고치게 하지 말고 빠진 곳을 질문으로만 다섯 개 이내로 받아요. 결정은 내가 하고, 에이전트는 놓친 곳을 찾는 데 써요. 에이전트의 질문이 항상 맞는 것은 아니니, 동의하지 않는 질문은 이유를 한 줄 적어 둬요.

PRD 한 장 — 접근 제어·데이터 처리·비용까지

문서로 묶기 전에 남은 요구사항 세 가지를 정해요. 외부에 공개한다면 이용 약관과 개인정보 처리 방침에 들어갈 항목이고, 회사 안에서 쓴다면 보안 담당자가 가장 먼저 묻는 항목이에요.

항목정할 것정하지 않으면
접근 제어공개, 링크 공유, 회원 인증, 사내 계정 가운데 어디까지 열지주소가 퍼져 모르는 사람이 내 비용으로 기능을 불러요
데이터 처리AI 제공사로 보내는 데이터, 저장하는 데이터, 보존 기간사용자가 올린 자료나 다른 사람의 개인정보가 동의 없이 외부로 나가요
비용누가 부담하는지(운영자 키·사용자 키), 사용자별·월별 한도사용량이 늘수록 비용이 늘고, 멈출 방법이 없어요

세 항목은 서로 이어져 있어요. 공개로 열면 비용 한도가 꼭 필요하고, 개인정보가 들어가는 기능이면 회원 인증과 소유자 기준 인가가 필요해요. 첫 공개는 파일럿으로 해요. 이름을 댈 수 있는 몇 명과 기간을 정하고, 성공 지표를 숫자로 적어 그 결과로 넓힐지 정해요("스터디원 4명, 1주, 정리 시간 30분에서 5분 이내"처럼요). PRD의 칸 구성과 쓰는 요령은 PRD를 스스로에게 묻기와 내 하네스의 사용자와 미완성 PRD에서 다뤘어요.

내 자막 도구에 적용해 보니 — 그림이 아니라 구조가 목적이었어요

저는 영상과 대사 스크립트로 자막이 화면에 뜨고 지는 시각(TC)을 잡고 자막 초벌을 만드는 도구를 만들고 있어요. 이 도구에 위 순서를 그대로 적용해 봤더니, 코드를 한 줄도 안 건드렸는데 이런 것이 드러났어요.

  • 제공 방식. 웹앱을 가정하고 그렸더니 서버·로그인·작업 큐가 줄줄이 따라 나왔어요. 그런데 이 도구가 다루는 영상은 외부 서버에 올릴 수 없어요. 그래서 내 컴퓨터에서 도는 설치형으로 정하고, 웹 전용 요소를 모두 걷어냈어요.
  • 순서. 코드는 글자를 받아 적는 일부터 시작하는데, 실제 작업 순서는 자막이 뜨고 지는 시각을 정하는 일이 먼저였어요. 둘을 나란히 놓고 보니 어긋난다는 걸 알았어요.
  • 말. "재분할"이라는 한 단어가 줄을 바꾸는 일과 시각을 바꾸는 일 두 가지를 가리키고 있었어요. 설계에는 줄바꿈만 남겼어요.

제가 얻은 건 그림 자체가 아니라, 그림을 그리다 걸린 이런 빈칸들이에요. 아직 못 한 것도 있어요. 사람과 함께 해 보는 사용성 테스트는 아직 안 했고, 자동 판정 기준에 최신 코드가 닿는지도 다시 재지 못했어요. 설계 문서가 있으니 이것들이 "비어 있다"는 것은 분명히 보여요.

나쁜 선택 vs 좋은 선택 — 요리사에게 앱을 맡길 때

식당으로 치면 사장이 신입 요리사에게 가게를 맡기는 장면이에요. 아래는 상황을 가정한 예시예요.

나쁜 선택좋은 선택
"명함 사진을 올리면 연락처로 정리해 주는 앱 만들어 줘"라고만 부탁한다 → 에이전트가 가장 빨리 돌아가는 방법으로 AI 호출용 키를 화면 코드에 적고 연락처를 서버 메모리에 둔다. 공개한 뒤 키가 노출되고, 서버를 다시 켜자 연락처가 사라진다 시퀀스와 데이터 모델 표를 붙이고 점검 다섯 항목(키는 서버에만, 저장 위치·소유자·보존 기간, AI 실패 시 안내 문구)을 함께 부탁한다. 끝나면 설계와 다른 곳을 찾아 달라고 한다 → 키는 서버에만 있고, 연락처는 사용자별로 저장되며, AI가 실패해도 안내가 뜬다

이 글에 나온 숫자 — 설계를 점검할 때 쓰는 기준값

이 글의 방법을 내 기능에 적용할 때 다시 보게 되는 값만 모았어요. 인터뷰와 사용성 테스트를 몇 분, 몇 번 하는지, 점검 항목이 몇 개인지처럼요. 모두 방법을 소개한 쪽이 제시한 값이고, 내 상황에 맞춰 조정할 수 있어요.

무엇의 숫자인가값알아 둘 것
사용자 인터뷰 길이10분대상 사용자에 가장 가까운 한 사람에게 "그 작업을 마지막으로 한 순간"을 물어요. 기능 설명과 "쓰시겠어요?"는 빼요
후기 조사별점 2~3점 후기 20개쯤구체적인 불편이 많은 구간이에요. 비슷한 내용이 두 곳 이상에서 나오면 "가정"을 "리서치"로 바꿔요
사용성 테스트15분씩, 역할을 바꿔 2번같은 문제가 두 사람에게서 나오면 바꾸고, 한 사람이면 기록해 파일럿에서 다시 봐요
AI 오류 대응 장치5가지출처 표시·사람 확인·폴백·에스컬레이션·피드백. 영향도가 클수록 많이 넣고, 다 넣을 필요는 없어요
구조 점검 항목5개API 키 위치·데이터 저장소·소유자·외부 API 실패 처리·코드 나누기. 정하지 않은 항목은 에이전트가 정해요
설계 리뷰 질문다섯 개 이내에이전트에게 설계를 고치게 하지 말고 빠진 곳만 질문으로 받아요

이럴 때 의심하세요 — AI 기능을 서비스로 내놓은 뒤에

설계에서 빠뜨린 것은 코드 줄보다 청구서, 사라진 데이터, 남의 화면에 보이는 내 정보처럼 사고의 모습으로 먼저 나타나요. 아래 증상이 보이면 코드를 더 짜기 전에 이 자리를 열어 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "이 앱에서 AI를 부르게 해 줘" — AI 키가 화면 코드에 적혔는지
  • "사용자가 입력한 걸 저장해 줘" — 저장 위치가 서버 메모리나 브라우저인지, 소유자 검사가 있는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
공개한 뒤 모르는 요청이 보이거나 AI 사용 요금이 갑자기 늘었어요 API 키를 읽거나 적어 둔 곳. 그리고 내 서비스를 브라우저로 열었을 때의 개발자 도구(F12) 네트워크 탭이에요 요청 내용이나 화면 코드에 키가 보이면 서버로 옮기고 그 키는 폐기해 다시 발급받아요. 누가 부를 수 있는지와 비용 한도도 함께 정해요(PRD 한 장)
서버를 다시 켜면 데이터가 사라지고, 기기를 바꾸면 내 내용이 없어요 데이터를 담는 줄이에요. 서버 안의 변수(메모리)나 브라우저 저장소에 담고 있지 않은지 봐요 앱을 껐다 켠 뒤에도 데이터가 남는지 확인해요. 남겨야 하는 것은 서버 밖의 저장소로 옮기고 데이터 모델에 "저장소" 칸을 채워요
다른 사람 화면에 내 데이터가 보여요 데이터를 읽거나 고치는 요청을 처리하는 곳에서 "요청한 사람이 소유자인지" 검사하는 줄이에요 내가 만든 테스트 계정 두 개로, 한 계정의 항목 번호를 다른 계정에서 열어 봐요. 열리면 소유자 검사가 빠진 거예요
AI 호출이 느릴 때 화면이 멈추거나 빈 값이 저장돼요 AI를 부르는 줄 근처의 대기 시간 제한과 실패 처리예요 키를 일부러 틀리게 넣고 한 번 호출해 봐요. 안내 문구가 뜨는지, 빈 데이터가 저장되지 않는지 봐요
기능 하나를 고쳤더니 관계없는 기능이 깨져요 한 파일에 여러 책임이 섞여 있는 곳이에요 에이전트에게 파일마다 하는 일을 표로 정리시키고, 한 파일에 둘 이상이 섞인 곳을 찾아요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이 프로젝트에서 아래 세 가지를 찾아 파일·줄 번호로 표로 보여 줘. 아직 코드는 고치지 마.
1. API 키를 읽거나 적어 둔 모든 곳 (화면 코드에 들어 있는 것이 있으면 따로 표시)
2. 데이터를 저장하는 모든 곳 (메모리, 브라우저 저장소, 파일, 데이터베이스 구분)
3. 외부 API(AI 호출 포함)를 부르는 곳과 각각의 실패 처리 여부
항목마다 왜 그렇게 봤는지 한 줄씩 적어 줘.

함께 보기

  • Cloud Run에 소스를 배포한다는 것 — 코드 폴더 하나가 공개 주소가 되기까지 (2) — 이 글에서 정한 설계를 실제 서버에 올리는 순간을 따라가요.
  • 바이브 코딩의 첫 문장 — PRD를 스스로에게 묻기 (2) — PRD의 칸을 스스로에게 묻는 질문으로 채워 가는 연습이에요.
  • 맡길 일부터 적는다 — 내 하네스의 사용자와 미완성 PRD (1) — 사용자와 미완성 PRD를 먼저 적는 흐름이에요.
  • 프록시 서버란 무엇인가 — API 키를 대신 들어주는 서버 — 키를 화면 코드에 넣지 않으려면 왜 서버를 거쳐야 하는지 보여요.
  • 로컬이냐 API냐는 틀린 질문 — 세 갈래 — AI를 어디서 돌릴지 고를 때의 갈림길이에요.
  1. 코딩 에이전트 — 터미널이나 편집기 안에서 코드를 읽고 고치고 실행까지 해 주는 AI 프로그램으로, AI 에이전트란 무엇인가에서 처음 다뤘어요. ↩
  2. API 키 — 외부 서비스(AI 제공사 등)를 쓸 자격을 증명하는 비밀 문자열로, 쓴 만큼 내 계정으로 요금이 붙어요. API란 무엇인가에서 API 자체를 다뤘어요. ↩
  3. 사용 맥락 — 사용자가 언제 어떤 기기와 도구를 쓰고 있을 때 이 기능이 필요한지를 가리키는 말이에요. ↩
  4. 제공 채널 — 만든 AI 기능을 사용자에게 건네는 통로로, 기성 AI 도구·메신저 봇·웹앱처럼 여러 가지가 있어요. ↩
  5. 동기·비동기 처리 — 동기는 요청한 쪽이 끝날 때까지 기다렸다가 답을 받는 방식이고, 비동기는 접수만 먼저 받고 처리는 뒤에서 하는 방식이에요. ↩
  6. 폴백 응답 — AI 호출이 실패했거나 확신이 없을 때 대신 내보내려고 미리 정해 둔 안내 문구예요. ↩
  7. 휴먼 인 더 루프 — AI가 만든 결과를 내보내기 전에 사람이 한 번 확인하는 단계를 두는 설계로, 멈출 기준을 정하고 승인 화면을 설계한다에서 자세히 다뤘어요. ↩
  8. 오즈의 마법사 테스트 — 시스템이 하는 일을 사람이 뒤에서 대신하면서, 아직 만들지 않은 기능을 사용자가 써 보게 하는 테스트예요. ↩
  9. 시퀀스 다이어그램 — 구성 요소를 가로로 놓고 요청(실선)과 응답(점선)을 위에서 아래로 시간 순서대로 그린 그림이에요. ↩
  10. 아키텍처 다이어그램 — 시스템을 이루는 구성 요소와 그 사이의 호출 관계를 한 장에 그린 그림이에요. ↩
  11. 데이터 모델 — 시스템이 저장하는 것마다 언제 생기고 누구 것이며 어디에 얼마나 두는지를 적은 표예요. ↩
  12. 시크릿(secret) — API 키처럼 밖에 드러나면 안 되는 값으로, 코드나 화면에 적지 않고 서버 쪽 안전한 곳에 둬요. ↩
  13. PRD(제품 요구사항 문서) — 무엇을 누구를 위해 만들고 어떻게 동작해야 하는지 적어 구현과 확인의 기준으로 삼는 문서예요. ↩
  14. 인가(authorization) — 로그인한 사람이 어떤 데이터를 보고 고칠 수 있는지를 따지는 일로, 소유자가 아니면 막는 검사를 말해요. ↩
