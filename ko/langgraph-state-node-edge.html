LangGraph는 LLM 앱이 일하는 순서를 공용 메모(State)·작업 칸(Node)·이동 선(Edge) 세 가지로 그려 두면 그 그림대로 실행해 주는 파이썬 프레임워크다.

오늘부터 "에이전트 팀 꾸리기"라는 새 모듈이 시작됐어요. 첫 주제가 LangGraph였어요. "노드를 선으로 잇는다"는 설명만 들으면 이미지 생성할 때 쓰는 ComfyUI와 비슷해 보이는데, 다루는 대상도 잇는 방법도 달라요(아래 표). 제 기록을 뒤져 보니 LangGraph는 멀티 에이전트 실험 때 후보로만 검토하고 쓰지 않았던 도구였어요.

이번 편에서는 LangGraph가 무엇이고 어디 집 식구인지, 그리고 흐름 그림을 만드는 세 가지 재료로 일직선 흐름과 갈림길·반복까지 만들어 봐요. 이 편의 코드는 전부 API 키 없이 돌아가요. 그 갈림길을 여러 문제로 밀어붙이고 LLM에게 도구를 쥐여 주는 루프는 다음 편에서, 흐름의 대표적인 모양 다섯 가지는 3편에서 이어서 봅니다.

절이 많아 보이지만, 전부 질문 하나를 각도만 바꿔 되묻는 거예요. "다음 걸음을 누가 정하나." 개발자가 코드에 미리 박아 둔 순서를 따라가느냐, 아니면 LLM이 매번 스스로 고르느냐는 질문이요. 워크플로와 에이전트를 가르는 것도 이 질문이고, n8n과 LangGraph가 갈라지는 것도, 뒤에서 직접 그을 add_conditional_edges 한 줄이 하는 일도 전부 이 질문의 다른 얼굴이에요. 읽다가 길을 잃으면 "지금은 이 질문의 어느 면을 보고 있나"로 되돌아오면 돼요.

그 각도들이 어떤 순서로 나오는지 미리 지도를 그려 둘게요.

코드로 먼저 보기 — while문 뭉치를 세 조각으로 뜯기

낱말 설명에 들어가기 전에, LangGraph가 손에 쥐여 주는 게 정확히 뭔지 코드로 먼저 볼게요. 위 '왜 배우나'에 적은 "흐름을 while문과 if문으로만 짜면"이 무슨 뜻인지부터요. 파이썬 코드가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 와도 좋아요.

국을 끓이는 일을 시킨다고 해 볼게요. 간을 보고, 싱거우면 소금을 넣고, 다시 간을 봐요. 세 번 넣으면 완성이고, 다섯 번을 봐도 안 되면 사람을 불러요. 평범한 파이썬으로 쓰면 이래요.

개념 설명용 코드 — LangGraph 없이 짜면 어떤 모양인지 보여 주려고 적은 코드예요

salt, tries, result = 0, 0, ""       # 소금 숟가락 수 · 간 본 횟수 · 결과

while True:
    tries += 1                       # 간을 본다
    if salt >= 3:                    # 간이 맞으면 내보내고 끝
        result = "완성"
        break
    if tries >= 5:                   # 다섯 번 봐도 안 되면 사람을 부르고 끝
        result = "셰프 호출"
        break
    salt += 1                        # 싱거우니 소금 한 숟갈, 그리고 다시 위로

열한 줄짜리라 아직은 읽을 만해요. 문제는 이 코드 안에서 성격이 다른 세 가지가 한 덩어리로 엉켜 있다는 거예요.

  • 값을 담는 부분 — salt, tries, result 세 변수요. 지금은 셋이지만 단계가 늘면 이 목록도 같이 늘고, 각각이 어느 줄에서 바뀌는지는 코드를 전부 훑어야 알 수 있어요.
  • 일을 하는 부분 — tries += 1(간 보기), salt += 1(소금 넣기)처럼 실제로 뭔가를 하는 줄이요.
  • 길을 정하는 부분 — while, if, break요. "다음에 어디로 갈지"를 이 세 낱말이 나눠 맡고 있어요. 출구가 두 개(break 두 번)라는 사실도 코드를 끝까지 읽어야 보이고요.

단계가 열 개로 늘면 이 엉킴이 바로 문제가 돼요. "지금 어느 갈래에 있나"를 알려면 들여쓰기를 눈으로 따라가야 하고, 중간에 "사람이 한 번 검토" 같은 단계를 끼우려면 if문 뭉치를 다시 짜야 해요. LangGraph가 하는 일은 이 셋을 억지로 떼어 놓는 것이고, 떼어 낸 세 조각에 붙인 이름이 이 글 제목의 State·Node·Edge예요.

LangGraph의 재료한 줄로 말하면위 while문 코드에서는
State (상태)모든 단계가 함께 읽고 쓰는 값 한 묶음이에요흩어져 있던 salt·tries·result 세 변수
Node (노드)일 한 가지만 하는 평범한 파이썬 함수예요. 길은 신경 쓰지 않아요tries += 1, salt += 1처럼 실제로 뭔가 하는 줄
Edge (엣지·선)어느 노드 다음에 어느 노드로 갈지를 미리 그어 둔 선이에요. 일은 하지 않아요while·if·break가 뒤섞여 맡고 있던 역할

이렇게 점(노드)과 선(엣지)으로 이뤄진 구조를 컴퓨터 쪽에서 그래프1라고 불러요. LangGraph라는 이름이 여기서 나왔어요. 위 코드를 그래프로 다시 짜면 아래 직접 만들기 ②의 열몇 줄이 되는데, 줄 수는 오히려 늘어나요. 대신 이런 게 생겨요.

  • 길만 따로 그림이 돼요. 선을 코드로 적어 뒀으니 아래 흐름 그림처럼 그려 볼 수 있고, draw_mermaid() 한 줄로 기계가 대신 그려 주기도 해요.
  • 길만 따로 고칠 수 있어요. 노드 함수는 그대로 두고 선 몇 줄만 바꿔서 순서를 바꾸거나 단계를 끼워 넣어요.
  • 값이 사라지지 않아요. 다섯 단계 전에 적어 둔 값도 State에 그대로 남아 있어요(아래 합치기 규칙).
  • 누가 길을 정했는지가 보여요. 선의 종류가 곧 답이라, 이 글을 관통하는 그 질문에 코드가 직접 답해 줘요(아래 표).

그래서 이 글의 나머지는 이 세 조각을 하나씩 뜯어보는 과정이에요. 그럼 낱말부터 정리하고 갈게요.

먼저 낱말 정리 — 에이전트와 워크플로

"에이전트"라는 말은 사람마다 떠올리는 게 달라요. 강의는 칩 후옌(Chip Huyen)과 Anthropic의 정의를 합쳐서 이렇게 잡았어요. 목표를 받으면 스스로 계획을 세우고, 행동하고, 그 결과를 보고 다음 행동을 정하는 LLM 시스템. 여기에 세 가지 재료가 있어요.

  • 환경 — 데이터베이스, 외부 API, 파일처럼 에이전트가 건드릴 바깥세상.
  • 행동 — 환경에 손을 대는 수단이에요. 실무에서는 도구(tool)라고 불러요. 에이전트가 할 수 있는 일의 한계는 쥔 도구 목록이 정해요.
  • 계획 — 어떤 도구를 어떤 순서로 쓸지 정하는 판단이에요.

중요1강에서 짚은 내용

에이전트에게 맡길 일을 떠올렸다면, 그 일에 필요한 것을 조회와 행동 두 목록으로 나눠 적어 보세요. 조회는 바깥세상을 읽기만 하는 일이고, 행동은 바깥세상을 실제로 바꾸는 일이에요(위 목록의 '행동'은 도구 전체를 가리켰지만, 여기서는 바깥을 바꾸는 도구만 가리키는 좁은 뜻이에요). 이 두 목록을 합친 게 곧 그 에이전트가 쥘 도구 목록이에요.

식당 예약 변경을 맡긴다면 조회는 "예약 내역 찾기 · 원하는 시간에 빈자리 확인 · 변경 수수료 확인"이고, 행동은 "예약 바꾸기 · 확인 문자 보내기"예요. 굳이 나누는 이유는 위험이 달라서예요. 조회는 틀려도 다시 하면 되지만, 행동은 한 번 하면 되돌리기 어려워요. 사람의 확인 같은 안전장치를 붙일 자리가 바로 행동 목록이에요(아래 표의 '환경 변경').

그런데 여기서 중요한 질문이 하나 남아요. 그럼 도구를 어떤 순서로 쓸지는 누가 정하나요? "조회하고, 판단하고, 답을 써라"를 개발자가 코드에 박아 두면 워크플로2, 매 단계 LLM이 스스로 고르게 두면 좁은 뜻의 에이전트예요. 이 기준은 자동화·워크플로·에이전트, 뭐가 다를까에서 내비 경로와 자율주행에 빗대 처음 다뤘던 것과 같아요.

처음 배울 때는 겉으로 보이는 차이를 기준으로 착각하기 쉬워요. 아래 넷은 기준이 아니에요.

  • LLM을 몇 번 부르는지 — 워크플로도 LLM을 여러 번 불러요. 3편의 프롬프트 체이닝은 LLM 호출 여러 번을 순서대로 이은, 가장 전형적인 워크플로예요.
  • 도구를 쓰는지 — 워크플로의 노드도 도구를 쥘 수 있어요. 바로 아래에서 볼 'LLM에 도구를 붙인 한 덩어리'는 워크플로와 에이전트가 함께 쓰는 기본 부품이에요.
  • 모델이 큰지 작은지 — 같은 모델로 둘 다 만들 수 있어요. 오히려 워크플로 안에서 쉬운 단계는 작고 싼 모델로, 어려운 단계는 큰 모델로 나눠 보내기도 해요.
  • 무엇으로 만들었는지 — n8n은 워크플로 자동화 도구, LangGraph는 에이전트 프레임워크로 카테고리부터 달라요. 하지만 카테고리는 그 제품이 무엇을 하려고 만들어졌느냐의 이야기라서, 3편의 다섯 패턴은 LangGraph로 그렸는데도 전부 워크플로예요. 두 도구의 차이는 아래에서 따로 비교해요.

그래서 3편의 라우팅처럼 LLM이 입력을 읽고 갈래를 골라도, 고를 수 있는 갈래를 개발자가 미리 다 그려 뒀다면 여전히 워크플로예요. LLM이 판단을 하느냐가 아니라, 그 판단이 움직일 수 있는 길을 누가 그려 뒀느냐를 봐요.

중요2강에서 짚은 내용

워크플로와 에이전트를 가르는 기준은 하나예요. 다음에 갈 길을 누가 정하나. 개발자가 코드로 길을 미리 다 그려 뒀으면 워크플로, LLM이 매 단계 스스로 정하면 에이전트예요. LLM을 몇 번 부르는지, 도구를 쓰는지, 모델이 큰지는 기준이 아니에요. 셋 다 워크플로와 에이전트 양쪽에 똑같이 나타날 수 있어서 둘을 가르지 못해요.

Anthropic은 "가장 단순한 방법으로 시작하고, 자율성이 꼭 필요하다는 증거가 있을 때만 복잡도를 더하라"고 권해요. 정해진 길을 따르면 결과를 예측할 수 있고, 비용을 통제할 수 있고, 틀렸을 때 어디가 틀렸는지 바로 찾을 수 있으니까요.

모든 그래프의 노드 하나하나는 증강된 LLM3이라고 보면 이해가 쉬워요. LLM 본체에 검색·도구·메모리가 붙은 한 덩어리요. 붙이는 도구는 크게 셋이에요.

도구 종류하는 일주의할 점
지식 증강실제 DB나 문서를 찾아 와서 모델이 모르는 최신 정보를 채워요 (RAG가 대표예요)없는 걸 지어내는 할루시네이션4을 줄이는 게 목적이에요
메모리이전 대화를 요약하거나 찾아서 다시 꺼내요컨텍스트 창이 유한해서 필요해요
환경 변경메일 보내기, 결제 취소처럼 바깥세상을 진짜로 바꿔요되돌리기 어려우니 사람의 승인(HITL5) 같은 안전장치가 필요해요

LangGraph는 어느 집 식구인가 — LangChain·LangSmith

LangGraph배선 — 부품을 어떤 순서로 돌릴지, 분기·반복·상태StateGraph — 흐름 그림(그래프)을 짜는 틀이라 직접 만들기 ①부터 계속 써요

LangSmith관측 — 실행 기록과 평가를 보여 주는 웹 서비스이 시리즈 코드에는 안 나와요. 코드가 아니라 설정 몇 줄로 켜는 서비스라 3편에서 켜 봐요

LangChain은 프롬프트 세 경로 직접 실행해보기에서 메시지 객체를 넘기는 모습으로 한 번 봤어요. 초기 LangChain의 "체인"은 prompt | model | parser처럼 한 줄로만 흐르는 파이프라인이었어요. 되돌아가는 반복이나 갈림길, 중간 상태 저장에 약해서 2024년에 LangGraph가 따로 나왔고, 지금은 LangChain의 에이전트 기능도 속으로는 LangGraph 위에서 돌아가요.

패키지 이름이 여러 개인 이유도 이거예요. 기본 자료형은 langchain-core, 모델 회사별 연결은 langchain-openai·langchain-anthropic·langchain-google-genai, 외부 서비스 연동 모음은 langchain-community에 들어 있어요. 한 가지 주의할 게 있어요. 옛날 자료에 나오는 LLMChain, AgentExecutor, initialize_agent는 1.0부터 langchain-classic이라는 별도 패키지로 빠졌어요. 검색해서 찾은 코드가 import 에러를 내면 버전부터 의심해 보세요.

그럼 수많은 프레임워크6(CrewAI, AutoGen, Claude Agent SDK…) 중에 왜 LangGraph였을까요. 강의가 든 이유는 셋이에요.

  • 모델 회사에 묶이지 않아요 — OpenAI든 Anthropic이든 Google이든, 노드 안에서 부르는 모델만 바꾸면 나머지 그래프는 그대로예요.
  • 흐름을 감추지 않아요 — 어느 단계 다음에 어디로 갈지를 프레임워크가 알아서 정해 주는 게 아니라, State·Node·Edge로 개발자가 한 줄씩 적어요. 손이 더 가는 대신 안 적은 길로는 절대 안 가요. 이 성질이 바로 아래에서 다시 나와요.
  • 관측을 붙이기 쉬워요 — 코드를 고치지 않고 환경 변수 몇 줄만 넣으면 실행 기록이 LangSmith에 남아요(3편에서 켜 봐요).

제 기록 하나를 고쳐 적어요 — "결정 주체가 가려진다"는 말

방금 "흐름을 감추지 않는다"를 장점으로 적었는데, 저는 예전에 정반대로 적어 뒀어요. 그래서 여기서 한 번 고치고 갈게요.

멀티 에이전트 실험 때 저는 "LangGraph 같은 범용 프레임워크를 쓰면 다음 행동을 누가 정하는지가 프레임워크 안에 가려진다"고 적고, 그 실험 도구로 Claude Agent SDK를 골랐어요. 여기서 "누가 정하는지"란 바로 위에서 본 그 질문이에요. 한 걸음이 끝난 뒤 다음에 뭘 할지를 개발자가 코드에 박아 둔 규칙이 정하느냐, LLM이 정하느냐요. 그 실험에서 제가 비교하려던 게 정확히 그 차이였으니, 그게 안 보이는 도구는 쓸 수 없다고 판단한 거예요. 안 써 보고 내린 판단이었고요.

막상 배워 보니 반대였어요. State·Node·Edge로 직접 그린 그래프는 그 결정 주체를 선 하나하나로 드러내는 쪽이었어요. 선의 종류가 곧 답이거든요.

코드에 적은 선이 걸음을 정한 건
add_edge("add_salt", "taste")
— 고정 엣지		개발자예요. "소금을 넣었으면 무조건 다시 간을 본다"를 제가 못 박아 둔 선이라, LLM이 끼어들 자리가 없어요
add_conditional_edges("taste", judge, [...])
— 조건부 엣지		두 번째 자리에 앉힌 judge예요. 그게 if문으로 짠 함수면 규칙이 정하는 거고(아래 직접 만들기 ②), 그 자리에 모델을 앉히면 LLM이 정하는 거예요(다음 편의 직접 만들기 ③)

선을 한 줄씩 전부 제 손으로 적어야 하니, 거꾸로 그 줄만 보면 누가 정하는지가 그대로 보여요. 가려지기는커녕 코드가 그 답을 적어 놓고 있는 셈이에요.

그럼 제가 걱정했던 "가려짐"은 어디서 생길까요. create_agent 같은 미리 만들어진 부품을 쓸 때예요. 이 함수 한 줄을 부르면 "모델에게 묻는다 → 모델이 부탁한 도구를 실행한다 → 결과를 들고 다시 모델에게 묻는다"는 반복이 이미 배선된 채로 나와요. 몇 줄로 에이전트가 완성되니 편한데, 그 반복은 선으로 보이지 않고 중간에 "사람이 검토" 같은 제 노드를 끼워 넣을 수도 없어요. 다음 편에서 이 부품을 한 번 쓰고, 같은 걸 손으로 조립해서 나란히 비교해 봐요. 아래 n8n 비교표의 'LLM 판단 범위' 줄에서 n8n의 AI Agent 노드를 두고 "칸 안의 반복은 봉인돼 있다"고 적은 것과 똑같은 상황이고요.

정리하면, 가려지느냐 아니냐는 프레임워크 이름이 아니라 그 안에서 직접 그리느냐 완제품을 가져다 쓰느냐로 갈려요. 도구 이름만 보고 판단한 게 제 실수였어요.

헷갈리기 쉬운 이웃들

LangGraph와 헷갈리기 쉬운 것들도 정리해 둘게요. ComfyUI·n8n·Flowise·Dify는 노드를 선으로 잇는 생김새가 닮았고, GraphRAG는 이름에 graph가 들어가서 헷갈려요. 여기부터 다음 절(n8n 비교)까지는 "이건 LangGraph가 아니다"를 갈라 두는 자리라, 이 도구들을 들어 본 적 없다면 주방 비유 절로 건너뛰었다가 나중에 돌아와도 돼요.

헷갈리는 것정체LangGraph와 다른 점
ComfyUI이미지·영상 생성 AI를 노드 상자로 이어 돌리는 화면 도구 (이미지 생성 도구 고르기의 세계예요)마우스로 이어요. 다루는 대상도 텍스트 LLM이 아니라 그림 생성이에요
n8n노코드 워크플로 자동화 도구 (IF 노드로 갈림길 만들기)셋 중 생김새가 가장 닮았지만 카테고리가 달라요. 바로 아래에서 따로 봐요
FlowiseLangChain의 부품(모델·메모리·도구·벡터 저장소)을 화면에서 상자로 놓고 이어 돌리는 오픈소스 도구"LangChain을 마우스로 조립하는 그림판"이에요. 개발자가 코드 대신 화면으로 그릴 때 써요. 최근 판(Agentflow)은 공유 State와 되돌림 선까지 지원해서 넷 중 LangGraph에 제일 가까워요
Dify지식베이스(문서 넣고 검색), 프롬프트 편집기, 워크플로 화면, 배포·로그·권한까지 한 덩어리로 묶은 LLM 앱 제작 플랫폼LangChain을 안 쓰고 자체 엔진이에요. 노드가 "LLM 호출·문서 검색·HTTP 요청·반복"처럼 업무 단위라서 쓰는 느낌은 n8n에 가깝고, 챗봇을 웹 앱이나 API로 바로 내놓는 데 강해요. 저는 아직 안 써 봐서 문서를 읽고 정리한 거예요
GraphRAG문서에서 뽑은 개체와 관계를 지식 그래프로 저장해 검색하는 기법여기서 graph는 지식의 구조예요. LangGraph의 graph는 실행 순서고요. 이 모듈 뒤쪽에서 배워요

n8n과는 뭐가 다른가 — 워크플로 도구와 에이전트 프레임워크

위 표에서 가장 헷갈리는 게 n8n이에요. 둘 다 노드를 선으로 잇고, 둘 다 LLM을 부를 수 있고, 둘 다 갈림길을 만들 수 있어요. 그래서 "화면으로 그리면 n8n, 코드로 쓰면 LangGraph" 정도로만 구분하기 쉬운데, 둘은 애초에 카테고리가 달라요. n8n은 워크플로 자동화 도구고, LangGraph는 에이전트를 만드는 프레임워크예요. 닮은 데가 많아서 오히려 이 차이가 잘 안 보여요.

비교 항목n8nLangGraph
카테고리워크플로 자동화 도구 — 자동화·워크플로·에이전트 글의 도구 표에서 내비 경로 쪽에 놓았던 도구예요에이전트 프레임워크 — 위에서 본 CrewAI·AutoGen·Claude Agent SDK와 같은 줄이에요
만든 목적"메일이 오면 표에 옮기고 슬랙에 알린다"처럼 사람이 정해 둔 순서를, 메일 도착이나 매일 아침 9시 같은 시작 신호(트리거)가 올 때마다 그대로 되풀이하기LLM이 도구 결과를 보고 다음 행동을 고르는 반복을, State를 들고 끝날 때까지 통제하며 돌리기
흐름 짜는 방식브라우저 화면에서 노드를 끌어다 선으로 이어요파이썬 코드로 State·Node·Edge를 적어요
노드가 보는 데이터컨베이어 벨트예요. 앞 노드가 내보낸 결과(항목 묶음)가 다음 노드의 입력이 되고, 노드는 기본적으로 바로 앞 노드 결과만 봐요. 다섯 칸 전 값이 필요하면 그 노드를 이름으로 지목해 꺼내 오거나 Set 노드로 계속 들고 다녀야 해요화이트보드예요. State 하나를 모든 노드가 통째로 읽고, 고칠 칸만 돌려줘요. 다섯 칸 전 노드가 적어 둔 값도 State에 그대로 있어요(아래 State 합치기 규칙)
반복(루프)돼요. Loop Over Items 노드로 항목마다 돌리거나, IF 노드의 출력을 앞 노드로 되돌려 이으면 돼요. 다만 벨트라서 바퀴마다 앞 노드 결과만 넘어오고, "지금까지 모은 것"은 따로 들고 다녀야 해요조건부 엣지로 앞 노드에 되돌려요(아래 직접 만들기 ②). 바퀴마다 쌓이는 값은 State 합치기 규칙이 알아서 이어 붙여요
외부 서비스 연결자주 쓰는 서비스는 미리 만들어진 노드가 있어서, 노드를 고르고 화면에서 계정만 연결하면 돼요서비스가 프로그램용으로 열어 둔 창구(API)를 부르는 함수를 직접 짜서 도구로 붙여요
LLM 판단 범위사람이 그린 흐름 속 AI Agent 노드 한 칸이에요. 칸 안에서는 LLM이 도구를 고르지만, 칸 밖의 순서는 화면에 그린 선을 따라가요. 칸 안의 도구 고르기 반복은 봉인돼 있어서, 그 반복 중간에 "검토" 같은 내 노드를 끼울 수는 없어요그래프 전체를 LLM이 다음 걸음을 고르는 루프로 짤 수도 있고(다음 편의 직접 만들기 ③), 규칙으로 못 박을 수도 있어요(직접 만들기 ①·②)
시작 문턱코드 없이 시작할 수 있어요코드를 읽고 쓸 줄 알아야 해요

그렇다고 n8n으로는 판단하는 AI를 아예 못 넣는 건 아니에요. AI Agent 노드로 흐름 한가운데에 판단을 한 조각 끼울 수 있어요(IF 노드 vs AI Agent 노드). 반대로 LangGraph로 그렸다고 다 에이전트인 것도 아니고요. 제품의 카테고리와 그걸로 만든 시스템의 종류가 따로라는 건 앞의 '기준이 아니에요' 목록 네 번째 항목('무엇으로 만들었는지')에서 짚은 그대로예요.

LangGraph가 n8n보다 어려운 이유도 표에 다 들어 있어요. 코드를 읽어야 하고, 외부 서비스를 직접 가져다 붙여야 하거든요. 예를 들어 "결과를 슬랙으로 보내기" 한 단계가 n8n에서는 Slack 노드를 놓고 계정을 연결하면 끝나요. LangGraph에서는 Slack의 API 설명서를 찾아 읽고, 메시지를 보내는 파이썬 함수를 짜고, Slack에서 받은 비밀 키를 .env에 넣고, @tool로 감싸 모델에 쥐여 줘야 해요(도구를 쥐여 주는 과정은 다음 편의 직접 만들기 ③에서 봐요). 위에서 본 langchain-community에 이미 만들어진 연동이 있기도 하지만, 그걸 찾아 불러와 그래프에 잇는 것도 코드로 해요. 대신 그만큼 반복 횟수 상한, 특정 도구 앞의 사람 승인, State 칸 하나하나를 원하는 대로 통제할 수 있어요.

그래서 앞에서 본 Anthropic의 권고, "가장 단순한 방법으로 시작하라"는 n8n과 LangGraph 중에 고를 때도 통해요. 정해진 순서로 여러 서비스를 잇는 일이 대부분이라면 n8n으로 끝나는지부터 보고, LLM이 매번 다음 걸음을 골라야 하거나 흐름을 코드로 세밀하게 통제해야 할 때 LangGraph로 가는 순서예요.

비유 — 식당 주방의 주문 전표와 동선표

식당 주방을 떠올려 볼게요. 주문이 들어오면 전표 한 장이 주방을 돌아요. 접수대 직원은 전표에 메뉴를 옮겨 적고, 화구 담당은 조리를 마쳤다고 자기 칸에만 체크해요. 다른 사람이 적은 칸은 건드리지 않아요.

전표가 다음에 어느 조리대로 갈지는 벽에 붙은 동선표가 정해요. "손질대 다음은 화구." 동선표 중간에는 갈림길도 있어요. 검수대 직원이 맛을 보고, 싱거우면 전표를 화구 담당에게 되돌려 보내고, 간이 맞으면 홀로 내보내요. 영업을 시작하기 전에 사장님이 이 동선표를 확정해 둬요.

비유 속 요소원래 개념
주방을 도는 전표 한 장State — 노드들이 함께 읽고 쓰는 공용 데이터
조리대 직원이 자기 칸에만 체크하기부분 업데이트7 — 노드는 바꾼 키만 돌려주고 나머지는 그대로 남아요

핵심 한 줄: 요리를 잘하는 건 조리대(노드)의 몫이고, 전표가 어디로 갈지는 동선표(엣지)가 정해요 — LangGraph는 그 동선표를 코드로 쓰는 도구예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 직원은 동선표에 없어도 눈치껏 옆 조리대를 도와주지만, 그래프는 선이 없는 곳으로는 절대 가지 않아요. 그리고 검수대(라우터)는 다음 목적지를 고르는 일만 해요. 전표에 값을 적는 건 노드가 반환값으로 하는 일이에요. 라우터가 전표에 직접 적으려 하면 무슨 일이 생기는지는 다음 편에서 직접 해 봤어요.

전체 흐름 — 간 맞추기 그래프 한 장

아래에서 직접 만들 두 번째 예제를 그림으로 먼저 볼게요. 맨 앞에서 while문으로 봤던 바로 그 간 맞추기를, 이번에는 세 조각으로 뜯어 그린 모습이에요. 읽는 법: 실선은 앞 노드가 끝나면 항상 지나가는 선이고, 점선은 라우터가 여러 갈래 중 하나만 고르는 선이에요. add_salt에서 taste로 올라가는 실선이 "다시 간 보기", 즉 반복이에요. 반복이 끝나는 출구가 두 개(serve, call_chef)라는 점도 눈여겨보세요.

직접 만들기 ① — LLM 없이 일직선 그래프

개념 설명보다 한 번 돌려 보는 게 빨라요. 먼저 설치예요. 강의 교안은 langgraph 1.2, langchain-core 1.6, langchain 1.4, langchain-openai 1.6에서 검증됐고, 제가 오늘 새로 설치한 버전도 같은 줄기(1.2.11·1.6.2·1.4.0·1.6.2)였어요. 파이썬 코드 자체가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 편해요.

실행: 로컬 터미널 — 가상 환경을 켠 상태에서 한 번만

pip install -U langgraph langchain langchain-openai

첫 그래프는 LLM 없이, 손님이 쉼표로 적은 주문을 메뉴 목록으로 정리하고 접시 수를 세는 두 단계짜리예요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Ticket(TypedDict):          # ① State: 전표에 어떤 칸이 있는지 선언
    order: str      # 손님이 적은 주문 원문
    dishes: list    # 정리된 메뉴 목록
    count: int      # 접시 수
    log: str        # 어느 조리대를 거쳤는지

def take_order(state: Ticket):    # ② Node: 전표를 받아 바꾼 칸만 돌려준다
    dishes = [d.strip() for d in state["order"].split(",") if d.strip()]
    return {"dishes": dishes, "log": state["log"] + " > 접수"}

def count_dishes(state: Ticket):
    return {"count": len(state["dishes"]), "log": state["log"] + " > 집계"}

builder = StateGraph(Ticket)
builder.add_node("take_order", take_order)      # 이름이 곧 엣지의 주소
builder.add_node("count_dishes", count_dishes)
builder.add_edge(START, "take_order")           # ③ Edge: 순서를 잇는다
builder.add_edge("take_order", "count_dishes")
builder.add_edge("count_dishes", END)
graph = builder.compile()

print(graph.invoke({"order": " 김치찌개,  계란말이 ,공기밥 ", "log": "시작"}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수 > 집계'}

출력을 세 재료 순서대로 읽어 볼게요.

  • State — Ticket은 TypedDict9로 전표의 칸을 미리 적어 둔 거예요. take_order는 dishes와 log만 돌려줬는데 order가 사라지지 않았죠. LangGraph가 반환된 딕셔너리를 기존 State에 합쳐 주기 때문이에요. 칸이 스무 개로 늘어도 노드는 자기 관심사만 다루면 되니, 노드를 따로 만들고 따로 시험하기 쉬워요.
  • Node — 그냥 파이썬 함수예요. 문자열을 다듬어도, DB를 조회해도, LLM을 불러도, 심지어 다른 그래프를 실행해도 돼요. add_node("이름", 함수)에 적은 이름이 엣지를 이을 때의 주소가 돼요.
  • Edge — START는 입구, END는 출구예요. invoke()에 넘긴 딕셔너리가 첫 State가 되어 START에서 출발하고, END에 닿는 순간의 State 전체가 반환값이에요.

log가 계속 뒤에 붙은 건 노드가 직접 +로 이어 붙였기 때문이에요. 여러 노드가 동시에 같은 칸에 쓰면 이 방식이 깨지는데, 그 문제와 해결책(리듀서)은 3편 병렬화에서 봐요.

합치기 규칙 확인하기 — 안 돌려준 칸, 아직 없는 칸

강의에는 "State 병합 규칙을 직접 확인하기"라는 연습 문제가 있었어요. 코드를 조금 바꾸고, 돌리기 전에 결과를 먼저 예상한 뒤 실행해서 맞춰 보는 문제였어요. 저는 처음에 무엇을 확인하라는 건지부터 헷갈려서, 위의 전표 예제에 그대로 옮겨 두 가지를 돌려 봤어요.

확인 ① — 돌려주지 않은 칸은 어떻게 될까

count_dishes의 반환값에서 log를 빼서 return {"count": len(state["dishes"])}만 남겨요. 나머지 코드는 위와 같아요. 돌리기 전에 먼저 예상해 보세요. 마지막 log는 None이 될까요, 빈 문자열이 될까요, 아니면 그대로일까요?

개념 설명용 코드 — 위처럼 반환값 한 줄만 바꿔 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수'}

log는 지워지지 않고 take_order가 적어 둔 '시작 > 접수'에서 멈춰 있어요. 반환값에서 키를 뺀다는 건 "이번엔 이 칸을 건드리지 않는다"는 뜻이지, State에서 지우라는 뜻이 아니에요. 주방으로 치면 집계 담당이 '거쳐 간 조리대' 칸에 아무것도 적지 않고 전표를 넘긴 거예요. 그 칸에는 앞사람이 적은 글씨가 그대로 남아요.

중요3강에서 짚은 내용

노드가 돌려준 칸만 새 값으로 바뀌고, 돌려주지 않은 칸은 이전 값 그대로 남아요(부분 업데이트). 그래서 노드는 전표 전체를 다시 적어 돌려줄 필요 없이 자기가 바꾼 칸만 돌려주면 돼요. 안 돌려준 칸이 None으로 비워진다, 전표에서 지워진다, 전체를 안 돌려줬으니 에러가 난다 — 이렇게 착각하기 쉬운데 셋 다 아니에요.

확인 ② — 순서를 뒤집으면

이번에는 count_dishes를 take_order보다 먼저 돌려요. 바꿀 곳은 엣지 세 줄뿐이에요.

builder.add_edge("count_dishes", "take_order")

시점전표에 있는 칸일어난 일
invoke() 직후order, log입력으로 넣은 두 칸뿐이에요

"Ticket에 dishes라고 적어 뒀잖아?" 싶을 수 있어요. 확인하려고 첫 노드가 받은 State의 키를 찍어 봤더니 ['log', 'order'] 두 개뿐이었어요. dishes와 count는 None이나 빈 리스트로 들어 있던 게 아니라 아예 없었어요. TypedDict는 전표 양식에 칸 이름을 인쇄해 두는 것일 뿐, 칸을 미리 만들거나 기본값을 채워 두지 않아요. 여기서 주방 비유도 끊겨요. 종이 전표라면 빈칸을 보고 "아직 안 적혔네" 하고 넘어가겠지만, 파이썬은 없는 칸을 읽으려는 순간 그 자리에서 멈춰요.

그래서 노드마다 읽는 칸과 만드는 칸을 나눠 보면 순서가 저절로 정해져요.

노드읽는 칸 (먼저 있어야 하는 것)만드는 칸
take_orderorder, log — 둘 다 입력으로 처음부터 있어요dishes, log
count_dishesdishes, log — dishes는 take_order가 돌려줘야 생겨요count, log

take_order는 맨 처음에 돌아도 필요한 게 다 있고, count_dishes는 반드시 take_order 뒤에 와야 해요. 그리고 LangGraph는 "이 노드가 dishes를 필요로 하니 take_order부터 돌리자" 같은 판단을 해 주지 않아요. 엣지로 정한 순서 그대로 실행할 뿐이라서, 값을 만드는 노드가 그 값을 읽는 노드보다 앞에 오도록 잇는 건 사람의 몫이에요. 참고로 add_node 두 줄의 순서만 바꿔 보면 결과가 원래와 똑같이 나와요. 노드를 등록하는 순서는 실행 순서와 상관없어요.

에러를 없애려고 state["dishes"]를 state.get("dishes", [])로 바꾸는 방법도 떠올릴 수 있어요. .get()은 키가 없으면 에러를 내는 대신 뒤에 준 기본값을 돌려주는 딕셔너리 메서드예요. 엣지는 뒤집힌 그대로 두고 이것만 바꿔서 돌려 봤어요.

개념 설명용 코드 — 순서를 뒤집은 채 .get()으로만 바꿨을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 0, 'log': '시작 > 집계 > 접수'}

에러는 사라졌지만 메뉴는 셋인데 접시 수가 0이에요. 프로그램이 멈추지 않으니 틀린 줄도 모르고 넘어가기 쉬워요. 뒤집힌 흔적은 log의 순서(집계 > 접수)에만 남아요. KeyError는 "순서가 틀렸다"고 알려 주는 신호예요. 신호를 끄지 말고 엣지를 고치는 게 맞아요.

정리하면 두 줄이에요. 노드가 돌려주지 않은 칸에는 앞의 값이 그대로 남고(확인 ①), 한 번도 누가 쓴 적 없는 칸은 남아 있을 앞의 값 자체가 없어요(확인 ②). State에 선언된 칸이 곧 지금 존재하는 칸은 아니에요.

직접 만들기 ② — 갈림길과 되돌아가는 선

실제 시스템은 일직선으로 끝나지 않아요. "간이 맞으면 내보내고, 싱거우면 소금을 넣고 다시 맛본다" 같은 갈림길이 필요하죠. 맨 앞의 while문 코드와 하는 일이 똑같은 예제인데, 이번에는 값(State)·일(Node)·길(Edge)을 따로 떼어 적어요. 위 흐름 그림을 그대로 코드로 옮기면 이래요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Pot(TypedDict):
    salt: int       # 넣은 소금 숟가락 수
    tries: int      # 간을 본 횟수
    result: str

def taste(state: Pot):     return {"tries": state["tries"] + 1}
def add_salt(state: Pot):  return {"salt": state["salt"] + 1}
def serve(state: Pot):     return {"result": "완성"}
def call_chef(state: Pot): return {"result": "셰프 호출"}

def judge(state: Pot) -> str:      # 라우터: 전표를 읽고 다음 노드 이름만 돌려준다
    if state["salt"] >= 3:
        return "serve"
    if state["tries"] >= 5:
        return "call_chef"         # 다섯 번 봐도 안 되면 사람을 부르는 출구
    return "add_salt"

builder = StateGraph(Pot)
for name, fn in [("taste", taste), ("add_salt", add_salt),
                 ("serve", serve), ("call_chef", call_chef)]:
    builder.add_node(name, fn)
builder.add_edge(START, "taste")
builder.add_conditional_edges("taste", judge, ["serve", "add_salt", "call_chef"])
builder.add_edge("add_salt", "taste")      # 되돌아가는 선 = 반복
builder.add_edge("serve", END)
builder.add_edge("call_chef", END)
graph = builder.compile()

print(graph.invoke({"salt": 0, "tries": 0}))
print(graph.get_graph().draw_mermaid())    # 그래프 구조를 글자 도식으로

개념 설명용 코드 — 제 화면에 찍힌 출력에서 결과 줄과 화살표 줄만 옮겼어요

{'salt': 3, 'tries': 4, 'result': '완성'}

__start__ --> taste;
add_salt --> taste;
taste -.-> add_salt;
taste -.-> call_chef;
taste -.-> serve;
call_chef --> __end__;
serve --> __end__;

add_conditional_edges(출발 노드, 라우터 함수, 목적지 목록)이 핵심이에요. taste가 끝나면 judge()를 부르고, 돌려받은 문자열을 노드 이름으로 보고 그리로 가요. 간을 네 번 보고 소금을 세 번 넣은 뒤 serve로 빠졌네요.

  • 목적지를 딕셔너리로도 줄 수 있어요. {"통과": "serve", "보류": "add_salt"}처럼 주면 라우터가 한국어 라벨을 돌려주고 LangGraph가 노드 이름으로 번역해 줘요. 노드 이름은 영문으로, 라벨만 한국어로 두는 절충이에요.
  • 조건부 엣지 하나로 분기와 반복을 다 만들어요. 이미 지나온 노드로 돌아가는 선을 그으면 그게 반복이에요.
  • 그림으로 확인하기. draw_mermaid()는 Mermaid12 문법 글자를 돌려줘요. -->는 실선(항상 가는 길), -.->는 점선(조건에 따라 고르는 길)이에요. 목적지를 리스트로 줘서 라벨이 노드 이름과 같으면 화살표 라벨이 생략되고, 딕셔너리로 다른 라벨을 주면 화살표 위에 라벨이 찍혀요. draw_mermaid_png()는 그림 파일로 바로 그려 주지만, 기본 설정은 외부 렌더링 서비스를 부르니 인터넷이 필요해요.

반복에는 늘 따라오는 위험이 있어요. 끝나지 않을 수 있다는 거예요. judge가 항상 "add_salt"만 돌려주게 바꾸고 graph.invoke(입력, {"recursion_limit": 6})으로 돌려 보니, 여섯 스텝에서 GraphRecursionError가 나며 멈췄어요. 그럼 상한을 안 주면 어디서 멈출까요? 예전 자료에는 기본 25스텝이라고 나오는데, 제가 설치한 langgraph 1.2.11의 소스 코드를 열어 보니 기본값이 10007이었어요. 버전별로 받아 보니 1.0.0은 25, 1.1.0은 10000, 1.2.0은 10007이었어요. 기본 상한이 알아서 일찍 끊어 줄 거라고 기대하면 안 된다는 뜻이에요(다음 편의 무한 반복 실험에서 직접 봐요). 게다가 상한에 걸려 멈추는 건 예외라서 그때까지 만든 중간 결과를 못 받아요. 그래서 위 코드처럼 tries를 세다가 call_chef로 빠지는 정상 출구를 그래프 안에 두는 게 기본이고, recursion_limit은 그 설계가 실패했을 때를 대비한 두 번째 안전망이에요. 그 두 번째 안전망도 기본값에 맡기지 말고 직접 적어 두는 게 좋아요. 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건에서 "중단을 완료로 표시하지 말라"고 했던 것과 같은 이야기예요.

나쁜 선택 vs 좋은 선택 — 간 맞추기 반복을 설계할 때

같은 주방에서, 검수대가 싱거운 요리를 화구로 되돌리는 반복을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 검수대에서 화구로 돌아가는 선만 긋고, 끝나는 조건은 "간이 맞으면" 하나만 뒀어요. 멈추는 건 LangGraph의 기본 상한에 맡겼고요.

무슨 일이 생기나: 소금통이 빈 날엔 간이 영원히 안 맞아요. 지금 langgraph(1.2 이후)의 기본 상한은 10007스텝이라, 간 보기와 소금 넣기를 5천 번씩 되풀이한 뒤에야 GraphRecursionError로 끊겨요. 간 보기가 LLM 호출이었다면 그 요금은 다 나갔고, 중간 결과는 예외와 함께 사라져요. 왜 멈췄는지도 결과에 안 남아요.		 무엇을 했나: 전표에 tries 칸을 두고, 다섯 번을 넘기면 call_chef 노드로 빠지는 정상 출구를 그래프에 그렸어요. recursion_limit은 두 번째 안전망으로만 남겼어요.

무슨 일이 생기나: 몇 번 만에 끝나든 결과가 정상적으로 돌아오고, result 칸에 "셰프 호출"이 남아서 덜 끝났다는 사실이 드러나요. 상한을 올릴지, 재료를 바꿀지 판단할 재료가 생겨요.

함께 읽으면 좋은 글

  • 자동화·워크플로·에이전트, 뭐가 다를까 — "다음 행동을 누가 정하나"라는 기준을 처음 세운 글이에요.
  • 코딩 에이전트에게 흐름을 맡기고, IF 노드로 갈림길 만들기 — 규칙으로 가르는 갈림길을 n8n 화면에서 만든 글이라, 이 편의 조건부 엣지와 나란히 보면 좋아요.
  • 같은 버그를 세 방식으로 — 기준선·워크플로·오케스트레이션 실행 — 같은 기준을 Claude Agent SDK 코드로 비교한 실험이에요.
  1. 그래프(graph) — 점(노드)과 그 점들을 잇는 선(엣지)으로 이뤄진 구조를 가리키는 말로, LangGraph에서는 이 점이 일하는 단계이고 선이 실행 순서예요. ↩
  2. 워크플로(workflow) — 실행 경로를 개발자가 코드로 미리 정해 둔 LLM 시스템으로, 자동화·워크플로·에이전트 글에서 내비 경로에 빗대 처음 다뤘어요. ↩
  3. 증강된 LLM(augmented LLM) — LLM 본체에 검색·도구·메모리를 붙여 모르는 정보를 가져오거나 바깥세상을 바꿀 수 있게 만든 기본 단위예요. ↩
  4. 할루시네이션(hallucination) — 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 현상이에요. ↩
  5. HITL(Human-in-the-Loop) — 되돌리기 어려운 행동 앞에서 사람의 승인을 받도록 흐름 중간에 사람을 끼워 두는 설계예요. ↩
  6. 프레임워크(framework) — 매번 반복되는 뼈대 코드를 미리 짜 둔 틀이라서, 개발자는 빈칸만 채우면 되는 개발 도구 묶음이에요. ↩
  7. 부분 업데이트(partial update) — 노드가 State 전체가 아니라 바꾼 칸만 돌려주면 LangGraph가 나머지 칸은 그대로 두고 합쳐 주는 방식이에요. ↩
  8. 라우터 함수 — State를 읽고 다음에 갈 노드의 이름(또는 라벨)만 돌려주는 함수예요. ↩
  9. TypedDict — 딕셔너리에 어떤 이름의 칸이 어떤 자료형으로 들어가는지 미리 적어 두는 파이썬 타입 힌트 문법으로, 칸을 실제로 만들거나 기본값을 채워 주지는 않아요(합치기 규칙 확인하기에서 직접 확인해요). ↩
  10. 트레이스백(traceback) — 에러가 났을 때 파이썬이 그 지점까지 거쳐 온 함수 호출 경로를 차례로 적어 보여 주는 기록으로, 맨 아래 줄이 실제로 일어난 에러예요. ↩
  11. KeyError — 딕셔너리에 없는 키를 d["키"]처럼 대괄호로 꺼내려 할 때 파이썬이 내는 에러예요. ↩
  12. Mermaid — 글자로 적은 도형 설명을 다이어그램으로 그려 주는 문법으로, GitHub나 Notion에 붙여 넣으면 바로 그림이 돼요. ↩
