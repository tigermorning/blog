LangGraph는 LLM 앱이 일하는 순서를 공용 메모(State)·작업 칸(Node)·이동 선(Edge) 세 가지로 그려 두면 그 그림대로 실행해 주는 파이썬 프레임워크다.

오늘부터 "에이전트 팀 꾸리기"라는 새 모듈이 시작됐어요. 첫 주제가 LangGraph였어요. "노드를 선으로 잇는다"는 설명만 들으면 이미지 생성할 때 쓰는 ComfyUI와 비슷해 보이는데, 다루는 대상도 잇는 방법도 달라요(아래 표). 제 기록을 뒤져 보니 LangGraph는 멀티 에이전트 실험 때 후보로만 검토하고 쓰지 않았던 도구였어요.

이번 편에서는 LangGraph가 무엇이고 어디 집 식구인지, 그리고 그래프를 만드는 세 가지 재료와 도구 루프까지를 다뤄요. 흐름의 대표적인 모양 다섯 가지는 다음 편에서 이어서 봅니다.

먼저 낱말 정리 — 에이전트와 워크플로

"에이전트"라는 말은 사람마다 떠올리는 게 달라요. 강의는 칩 후옌(Chip Huyen)과 Anthropic의 정의를 합쳐서 이렇게 잡았어요. 목표를 받으면 스스로 계획을 세우고, 행동하고, 그 결과를 보고 다음 행동을 정하는 LLM 시스템. 여기에 세 가지 재료가 있어요.

  • 환경 — 데이터베이스, 외부 API, 파일처럼 에이전트가 건드릴 바깥세상.
  • 행동 — 환경에 손을 대는 수단이에요. 실무에서는 도구(tool)라고 불러요. 에이전트가 할 수 있는 일의 한계는 쥔 도구 목록이 정해요.
  • 계획 — 어떤 도구를 어떤 순서로 쓸지 정하는 판단이에요.

그런데 여기서 중요한 질문이 하나 남아요. 그 순서는 누가 정하나요? "조회하고, 판단하고, 답을 써라"를 개발자가 코드에 박아 두면 워크플로1, 매 단계 LLM이 스스로 고르게 두면 좁은 뜻의 에이전트예요. 이 기준은 자동화·워크플로·에이전트, 뭐가 다를까에서 내비 경로와 자율주행에 빗대 처음 다뤘던 것과 같아요.

처음 배울 때는 겉으로 보이는 차이를 기준으로 착각하기 쉬워요. 아래 넷은 기준이 아니에요.

  • LLM을 몇 번 부르는지 — 워크플로도 LLM을 여러 번 불러요. 다음 편의 프롬프트 체이닝은 LLM 호출 여러 번을 순서대로 이은, 가장 전형적인 워크플로예요.
  • 도구를 쓰는지 — 워크플로의 노드도 도구를 쥘 수 있어요. 바로 아래에서 볼 'LLM에 도구를 붙인 한 덩어리'는 워크플로와 에이전트가 함께 쓰는 기본 부품이에요.
  • 모델이 큰지 작은지 — 같은 모델로 둘 다 만들 수 있어요. 오히려 워크플로 안에서 쉬운 단계는 작고 싼 모델로, 어려운 단계는 큰 모델로 나눠 보내기도 해요.
  • 무엇으로 만들었는지 — n8n은 워크플로 자동화 도구, LangGraph는 에이전트 프레임워크로 카테고리부터 달라요. 하지만 카테고리는 그 제품이 무엇을 하려고 만들어졌느냐의 이야기라서, 다음 편의 다섯 패턴은 LangGraph로 그렸는데도 전부 워크플로예요. 두 도구의 차이는 아래에서 따로 비교해요.

그래서 다음 편의 라우팅처럼 LLM이 입력을 읽고 갈래를 골라도, 고를 수 있는 갈래를 개발자가 미리 다 그려 뒀다면 여전히 워크플로예요. LLM이 판단을 하느냐가 아니라, 그 판단이 움직일 수 있는 길을 누가 그려 뒀느냐를 봐요.

Anthropic은 "가장 단순한 방법으로 시작하고, 자율성이 꼭 필요하다는 증거가 있을 때만 복잡도를 더하라"고 권해요. 정해진 길을 따르면 결과를 예측할 수 있고, 비용을 통제할 수 있고, 틀렸을 때 어디가 틀렸는지 바로 찾을 수 있으니까요.

모든 그래프의 노드 하나하나는 증강된 LLM2이라고 보면 이해가 쉬워요. LLM 본체에 검색·도구·메모리가 붙은 한 덩어리요. 붙이는 도구는 크게 셋이에요.

도구 종류하는 일주의할 점
지식 증강실제 DB나 문서를 찾아 와서 모델이 모르는 최신 정보를 채워요 (RAG가 대표예요)없는 걸 지어내는 할루시네이션3을 줄이는 게 목적이에요
메모리이전 대화를 요약하거나 찾아서 다시 꺼내요컨텍스트 창이 유한해서 필요해요
환경 변경메일 보내기, 결제 취소처럼 바깥세상을 진짜로 바꿔요되돌리기 어려우니 사람의 승인(HITL4) 같은 안전장치가 필요해요

계산은 코드에게 — 단순한 함수도 좋은 도구인 이유

강의가 짚어 준 설계 원칙 한 줄이 기억에 남아요. LLM이 약한 계산과 정밀 작업은 코드에 맡기고, LLM은 "언제 어떤 코드를 부를지" 판단하는 데 집중시킨다. 그래서 달력, 시간대 변환기, 단위 변환기처럼 단순한 함수도 훌륭한 도구가 돼요. 위 표의 세 종류가 바깥에서 정보를 가져오거나 바깥을 바꾸는 도구라면, 이쪽은 LLM이 약한 계산을 대신 해 주는 도구예요.

처음엔 "오늘부터 100일 뒤가 무슨 요일인지 정도는 LLM이 그냥 풀면 되지 않나" 싶었어요. 그런데 LLM에게 직접 맡길 때와 함수로 뺄 때를 나란히 놓으면 차이가 분명해요.

비교 항목LLM이 직접 계산하면함수 도구로 빼면
정확한가계산을 하는 게 아니라 앞 글자들 다음에 올 그럴듯한 조각을 이어 쓰는 방식이라, 월말·윤년이 끼는 날짜나 자릿수가 긴 곱셈에서 틀린 답을 자신 있게 내놓을 수 있어요파이썬으로 "2026년 9월 11일 + 100일"을 계산하는 한 줄(date(2026, 9, 11) + timedelta(days=100))이면 언제 돌려도 2026-12-20(일요일)이 나와요
매번 같은가답을 확률적으로 뽑아서 같은 질문에도 실행마다 답이 달라질 수 있어요같은 입력엔 언제나 같은 결과가 나와요
지금 기준인가누가 알려 주지 않으면 오늘 날짜를 모르고, 학습이 끝난 뒤에 바뀐 서머타임 같은 시간대 규칙도 몰라요실행되는 순간의 컴퓨터 시계를 읽고, 시간대 규칙도 업데이트로 갱신되는 자료를 따라요
틀렸을 때 찾을 수 있나머릿속 계산이라 어디서 틀렸는지 흔적이 남지 않아요도구에 무엇을 넣고 무엇을 받았는지가 메시지로 남아요(직접 만들기 ③에서 봐요). 함수는 테스트 코드로 따로 검사할 수도 있어요

정리하면 LLM은 "날짜 계산이 필요하니 이 도구를 이 값으로 부르자"까지만 판단하고, 계산은 코드가 맡아요. 이 역할 분담이 뒤에서 조립할 도구 루프의 출발점이에요. 다만 도구를 늘릴수록 모델이 읽어야 할 도구 설명도 함께 쌓이니(도구가 많아지면 생기는 문맥 부담 — Tool Search와 Code Mode), 틀리면 곤란한 계산부터 빼는 게 순서예요. 둘의 차이는 글 끝 직접 해보기 2번에서 재 볼 수 있어요.

LangGraph는 어느 집 식구인가 — LangChain·LangSmith

강의 코드를 보면 import 줄에 langchain_과 langgraph가 섞여 나와요. 둘은 경쟁 관계가 아니라 같은 회사(LangChain Inc.)가 역할을 나눠 만든 제품이에요. 표의 오른쪽 칸은 이 글의 코드에서 각 제품을 어떤 이름으로 만나게 되는지예요.

이름맡은 일이 글 코드에서 만나는 이름
LangChain부품 — 모델 연결, 메시지 형식, 도구 정의, 문서 로더, 벡터스토어ChatOpenAI — OpenAI 모델을 부르는 부품
@tool — 파이썬 함수를 모델이 쓸 수 있는 도구로 바꾸는 표시
둘 다 직접 만들기 ③에서 나와요
LangGraph배선 — 부품을 어떤 순서로 돌릴지, 분기·반복·상태StateGraph — 흐름 그림(그래프)을 짜는 틀이라 직접 만들기 ①부터 계속 써요
ToolNode — 모델이 부탁한 도구를 대신 실행해 주는 노드로, 직접 만들기 ③에서 나와요
LangSmith관측 — 실행 기록과 평가를 보여 주는 웹 서비스이 글 코드에는 안 나와요. 코드가 아니라 설정 몇 줄로 켜는 서비스라 다음 편에서 켜 봐요

LangChain은 프롬프트 세 경로 직접 실행해보기에서 메시지 객체를 넘기는 모습으로 한 번 봤어요. 초기 LangChain의 "체인"은 prompt | model | parser처럼 한 줄로만 흐르는 파이프라인이었어요. 되돌아가는 반복이나 갈림길, 중간 상태 저장에 약해서 2024년에 LangGraph가 따로 나왔고, 지금은 LangChain의 에이전트 기능도 속으로는 LangGraph 위에서 돌아가요.

패키지 이름이 여러 개인 이유도 이거예요. 기본 자료형은 langchain-core, 모델 회사별 연결은 langchain-openai·langchain-anthropic·langchain-google-genai, 외부 서비스 연동 모음은 langchain-community에 들어 있어요. 한 가지 주의할 게 있어요. 옛날 자료에 나오는 LLMChain, AgentExecutor, initialize_agent는 1.0부터 langchain-classic이라는 별도 패키지로 빠졌어요. 검색해서 찾은 코드가 import 에러를 내면 버전부터 의심해 보세요.

그럼 수많은 프레임워크5(CrewAI, AutoGen, Claude Agent SDK…) 중에 왜 LangGraph였을까요. 강의가 든 이유는 셋이에요. 특정 모델 회사에 묶이지 않고, 흐름을 블랙박스로 감추지 않고 State·Node·Edge로 개발자가 직접 그리게 하고, 환경 변수 몇 줄로 LangSmith 관측을 붙일 수 있다는 점이요.

여기서 제 기록 하나를 고쳐 적어야겠어요. 멀티 에이전트 실험 때는 "LangGraph를 쓰면 다음 행동을 누가 정하는지가 프레임워크 안에 가려진다"고 보고 Claude Agent SDK를 골랐어요. 막상 배워 보니 직접 그린 그래프는 오히려 그 결정 주체를 선 하나하나로 드러내는 쪽이었어요. 가려지는 건 뒤에 나오는 create_agent 같은 미리 만들어진 부품을 쓸 때예요.

LangGraph와 헷갈리기 쉬운 것들도 정리해 둘게요. ComfyUI와 n8n은 노드를 선으로 잇는 생김새가 닮았고, GraphRAG는 이름에 graph가 들어가서 헷갈려요.

헷갈리는 것정체LangGraph와 다른 점
ComfyUI이미지·영상 생성 AI를 노드 상자로 이어 돌리는 화면 도구 (이미지 생성 도구 고르기의 세계예요)마우스로 이어요. 다루는 대상도 텍스트 LLM이 아니라 그림 생성이에요
n8n노코드 워크플로 자동화 도구 (IF 노드로 갈림길 만들기)셋 중 생김새가 가장 닮았지만 카테고리가 달라요. 바로 아래에서 따로 봐요
GraphRAG문서에서 뽑은 개체와 관계를 지식 그래프로 저장해 검색하는 기법여기서 graph는 지식의 구조예요. LangGraph의 graph는 실행 순서고요. 이 모듈 뒤쪽에서 배워요

n8n과는 뭐가 다른가 — 워크플로 도구와 에이전트 프레임워크

위 표에서 가장 헷갈리는 게 n8n이에요. 둘 다 노드를 선으로 잇고, 둘 다 LLM을 부를 수 있고, 둘 다 갈림길을 만들 수 있어요. 그래서 "화면으로 그리면 n8n, 코드로 쓰면 LangGraph" 정도로만 구분하기 쉬운데, 둘은 애초에 카테고리가 달라요. n8n은 워크플로 자동화 도구고, LangGraph는 에이전트를 만드는 프레임워크예요. 닮은 데가 많아서 오히려 이 차이가 잘 안 보여요.

비교 항목n8nLangGraph
카테고리워크플로 자동화 도구 — 자동화·워크플로·에이전트 글의 도구 표에서 내비 경로 쪽에 놓았던 도구예요에이전트 프레임워크 — 위에서 본 CrewAI·AutoGen·Claude Agent SDK와 같은 줄이에요
만든 목적"메일이 오면 표에 옮기고 슬랙에 알린다"처럼 사람이 정해 둔 순서를, 메일 도착이나 매일 아침 9시 같은 시작 신호(트리거)가 올 때마다 그대로 되풀이하기LLM이 도구 결과를 보고 다음 행동을 고르는 반복을, State를 들고 끝날 때까지 통제하며 돌리기
흐름 짜는 방식브라우저 화면에서 노드를 끌어다 선으로 이어요파이썬 코드로 State·Node·Edge를 적어요
외부 서비스 연결자주 쓰는 서비스는 미리 만들어진 노드가 있어서, 노드를 고르고 화면에서 계정만 연결하면 돼요서비스가 프로그램용으로 열어 둔 창구(API)를 부르는 함수를 직접 짜서 도구로 붙여요
LLM 판단 범위사람이 그린 흐름 속 AI Agent 노드 한 칸이에요. 칸 안에서는 LLM이 도구를 고르지만, 칸 밖의 순서는 화면에 그린 선을 따라가요그래프 전체를 LLM이 다음 걸음을 고르는 루프로 짤 수도 있고(직접 만들기 ③), 규칙으로 못 박을 수도 있어요(직접 만들기 ①·②)
시작 문턱코드 없이 시작할 수 있어요코드를 읽고 쓸 줄 알아야 해요

그렇다고 n8n으로는 판단하는 AI를 아예 못 넣는 건 아니에요. AI Agent 노드로 흐름 한가운데에 판단을 한 조각 끼울 수 있어요(IF 노드 vs AI Agent 노드). 반대로 LangGraph로 그렸다고 다 에이전트인 것도 아니고요. 제품의 카테고리와 그걸로 만든 시스템의 종류가 따로라는 건 앞의 '기준이 아니에요' 목록에서 짚은 그대로예요.

LangGraph가 n8n보다 어려운 이유도 표에 다 들어 있어요. 코드를 읽어야 하고, 외부 서비스를 직접 가져다 붙여야 하거든요. 예를 들어 "결과를 슬랙으로 보내기" 한 단계가 n8n에서는 Slack 노드를 놓고 계정을 연결하면 끝나요. LangGraph에서는 Slack의 API 설명서를 찾아 읽고, 메시지를 보내는 파이썬 함수를 짜고, Slack에서 받은 비밀 키를 .env에 넣고, @tool로 감싸 모델에 쥐여 줘야 해요(도구를 쥐여 주는 과정은 아래 직접 만들기 ③에서 봐요). 위에서 본 langchain-community에 이미 만들어진 연동이 있기도 하지만, 그걸 찾아 불러와 그래프에 잇는 것도 코드로 해요. 대신 그만큼 반복 횟수 상한, 특정 도구 앞의 사람 승인, State 칸 하나하나를 원하는 대로 통제할 수 있어요.

그래서 앞에서 본 Anthropic의 권고, "가장 단순한 방법으로 시작하라"는 n8n과 LangGraph 중에 고를 때도 통해요. 정해진 순서로 여러 서비스를 잇는 일이 대부분이라면 n8n으로 끝나는지부터 보고, LLM이 매번 다음 걸음을 골라야 하거나 흐름을 코드로 세밀하게 통제해야 할 때 LangGraph로 가는 순서예요.

비유 — 식당 주방의 주문 전표와 동선표

식당 주방을 떠올려 볼게요. 주문이 들어오면 전표 한 장이 주방을 돌아요. 접수대 직원은 전표에 메뉴를 옮겨 적고, 화구 담당은 조리를 마쳤다고 자기 칸에만 체크해요. 다른 사람이 적은 칸은 건드리지 않아요.

전표가 다음에 어느 조리대로 갈지는 벽에 붙은 동선표가 정해요. "손질대 다음은 화구." 동선표 중간에는 갈림길도 있어요. 검수대 직원이 맛을 보고, 싱거우면 전표를 화구 담당에게 되돌려 보내고, 간이 맞으면 홀로 내보내요. 영업을 시작하기 전에 사장님이 이 동선표를 확정해 둬요.

그리고 이 식당에는 도구 호출 글에서 본 홀 직원도 있어요. 홀 직원이 창고 조회 쪽지를 적어 주방에 넘기면, 쪽지를 실제로 처리하는 건 창고 담당이에요.

핵심 한 줄: 요리를 잘하는 건 조리대(노드)의 몫이고, 전표가 어디로 갈지는 동선표(엣지)가 정해요 — LangGraph는 그 동선표를 코드로 쓰는 도구예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 직원은 동선표에 없어도 눈치껏 옆 조리대를 도와주지만, 그래프는 선이 없는 곳으로는 절대 가지 않아요. 그리고 검수대(라우터)는 다음 목적지를 고르는 일만 해요. 전표에 값을 적는 건 노드가 반환값으로 하는 일이에요. 라우터가 전표에 직접 적으려 하면 무슨 일이 생기는지는 아래에서 직접 해 봤어요.

전체 흐름 — 간 맞추기 그래프 한 장

아래에서 직접 만들 두 번째 예제를 그림으로 먼저 볼게요. 읽는 법: 실선은 앞 노드가 끝나면 항상 지나가는 선이고, 점선은 라우터가 여러 갈래 중 하나만 고르는 선이에요. add_salt에서 taste로 올라가는 실선이 "다시 간 보기", 즉 반복이에요. 반복이 끝나는 출구가 두 개(serve, call_chef)라는 점도 눈여겨보세요.

직접 만들기 ① — LLM 없이 일직선 그래프

개념 설명보다 한 번 돌려 보는 게 빨라요. 먼저 설치예요. 강의 교안은 langgraph 1.2, langchain-core 1.6, langchain 1.4, langchain-openai 1.6에서 검증됐고, 제가 오늘 새로 설치한 버전도 같은 줄기(1.2.11·1.6.2·1.4.0·1.6.2)였어요. 파이썬 코드 자체가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 편해요.

실행: 로컬 터미널 — 가상 환경을 켠 상태에서 한 번만

pip install -U langgraph langchain langchain-openai

첫 그래프는 LLM 없이, 손님이 쉼표로 적은 주문을 메뉴 목록으로 정리하고 접시 수를 세는 두 단계짜리예요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Ticket(TypedDict):          # ① State: 전표에 어떤 칸이 있는지 선언
    order: str      # 손님이 적은 주문 원문
    dishes: list    # 정리된 메뉴 목록
    count: int      # 접시 수
    log: str        # 어느 조리대를 거쳤는지

def take_order(state: Ticket):    # ② Node: 전표를 받아 바꾼 칸만 돌려준다
    dishes = [d.strip() for d in state["order"].split(",") if d.strip()]
    return {"dishes": dishes, "log": state["log"] + " > 접수"}

def count_dishes(state: Ticket):
    return {"count": len(state["dishes"]), "log": state["log"] + " > 집계"}

builder = StateGraph(Ticket)
builder.add_node("take_order", take_order)      # 이름이 곧 엣지의 주소
builder.add_node("count_dishes", count_dishes)
builder.add_edge(START, "take_order")           # ③ Edge: 순서를 잇는다
builder.add_edge("take_order", "count_dishes")
builder.add_edge("count_dishes", END)
graph = builder.compile()

print(graph.invoke({"order": " 김치찌개,  계란말이 ,공기밥 ", "log": "시작"}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수 > 집계'}

출력을 세 재료 순서대로 읽어 볼게요.

  • State — Ticket은 TypedDict8로 전표의 칸을 미리 적어 둔 거예요. take_order는 dishes와 log만 돌려줬는데 order가 사라지지 않았죠. LangGraph가 반환된 딕셔너리를 기존 State에 합쳐 주기 때문이에요. 칸이 스무 개로 늘어도 노드는 자기 관심사만 다루면 되니, 노드를 따로 만들고 따로 시험하기 쉬워요.
  • Node — 그냥 파이썬 함수예요. 문자열을 다듬어도, DB를 조회해도, LLM을 불러도, 심지어 다른 그래프를 실행해도 돼요. add_node("이름", 함수)에 적은 이름이 엣지를 이을 때의 주소가 돼요.
  • Edge — START는 입구, END는 출구예요. invoke()에 넘긴 딕셔너리가 첫 State가 되어 START에서 출발하고, END에 닿는 순간의 State 전체가 반환값이에요.

log가 계속 뒤에 붙은 건 노드가 직접 +로 이어 붙였기 때문이에요. 여러 노드가 동시에 같은 칸에 쓰면 이 방식이 깨지는데, 그 문제와 해결책(리듀서)은 다음 편 병렬화에서 봐요.

합치기 규칙 확인하기 — 안 돌려준 칸, 아직 없는 칸

강의에는 "State 병합 규칙을 직접 확인하기"라는 연습 문제가 있었어요. 코드를 조금 바꾸고, 돌리기 전에 결과를 먼저 예상한 뒤 실행해서 맞춰 보는 문제였어요. 저는 처음에 무엇을 확인하라는 건지부터 헷갈려서, 위의 전표 예제에 그대로 옮겨 두 가지를 돌려 봤어요.

확인 ① — 돌려주지 않은 칸은 어떻게 될까

count_dishes의 반환값에서 log를 빼서 return {"count": len(state["dishes"])}만 남겨요. 나머지 코드는 위와 같아요. 돌리기 전에 먼저 예상해 보세요. 마지막 log는 None이 될까요, 빈 문자열이 될까요, 아니면 그대로일까요?

개념 설명용 코드 — 위처럼 반환값 한 줄만 바꿔 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수'}

log는 지워지지 않고 take_order가 적어 둔 '시작 > 접수'에서 멈춰 있어요. 반환값에서 키를 뺀다는 건 "이번엔 이 칸을 건드리지 않는다"는 뜻이지, State에서 지우라는 뜻이 아니에요. 주방으로 치면 집계 담당이 '거쳐 간 조리대' 칸에 아무것도 적지 않고 전표를 넘긴 거예요. 그 칸에는 앞사람이 적은 글씨가 그대로 남아요. 강의의 객관식 퀴즈도 바로 이 질문이었어요. 노드가 한 칸만 돌려주면 나머지 칸은 어떻게 되냐는 건데, 보기 중 'None으로 초기화된다', 'State에서 삭제된다', '에러가 난다'는 모두 틀리고 '이전 값을 그대로 유지한다'가 답이에요.

확인 ② — 순서를 뒤집으면

이번에는 count_dishes를 take_order보다 먼저 돌려요. 바꿀 곳은 엣지 세 줄뿐이에요.

실행: 로컬 파이썬 — 위 일직선 그래프 코드에서 builder.add_edge 세 줄만 이렇게 바꿔요

builder.add_edge(START, "count_dishes")
builder.add_edge("count_dishes", "take_order")
builder.add_edge("take_order", END)

한 문장으로 옮기면 "count_dishes가 dishes를 꺼내려 했는데 전표에 그 칸이 없었다"예요. 왜 없었는지는 전표를 단계마다 따라가 보면 보여요.

시점전표에 있는 칸일어난 일
invoke() 직후order, log입력으로 넣은 두 칸뿐이에요
count_dishes 차례order, logdishes를 읽으려는데 아직 아무도 안 만들어서 에러로 멈춰요
take_order 차례—실행될 기회조차 없어요

"Ticket에 dishes라고 적어 뒀잖아?" 싶을 수 있어요. 확인하려고 첫 노드가 받은 State의 키를 찍어 봤더니 ['log', 'order'] 두 개뿐이었어요. dishes와 count는 None이나 빈 리스트로 들어 있던 게 아니라 아예 없었어요. TypedDict는 전표 양식에 칸 이름을 인쇄해 두는 것일 뿐, 칸을 미리 만들거나 기본값을 채워 두지 않아요. 여기서 주방 비유도 끊겨요. 종이 전표라면 빈칸을 보고 "아직 안 적혔네" 하고 넘어가겠지만, 파이썬은 없는 칸을 읽으려는 순간 그 자리에서 멈춰요.

그래서 노드마다 읽는 칸과 만드는 칸을 나눠 보면 순서가 저절로 정해져요.

노드읽는 칸 (먼저 있어야 하는 것)만드는 칸
take_orderorder, log — 둘 다 입력으로 처음부터 있어요dishes, log
count_dishesdishes, log — dishes는 take_order가 돌려줘야 생겨요count, log

take_order는 맨 처음에 돌아도 필요한 게 다 있고, count_dishes는 반드시 take_order 뒤에 와야 해요. 그리고 LangGraph는 "이 노드가 dishes를 필요로 하니 take_order부터 돌리자" 같은 판단을 해 주지 않아요. 엣지로 정한 순서 그대로 실행할 뿐이라서, 값을 만드는 노드가 그 값을 읽는 노드보다 앞에 오도록 잇는 건 사람의 몫이에요. 참고로 add_node 두 줄의 순서만 바꿔 보면 결과가 원래와 똑같이 나와요. 노드를 등록하는 순서는 실행 순서와 상관없어요.

에러를 없애려고 state["dishes"]를 state.get("dishes", [])로 바꾸는 방법도 떠올릴 수 있어요. .get()은 키가 없으면 에러를 내는 대신 뒤에 준 기본값을 돌려주는 딕셔너리 메서드예요. 엣지는 뒤집힌 그대로 두고 이것만 바꿔서 돌려 봤어요.

개념 설명용 코드 — 순서를 뒤집은 채 .get()으로만 바꿨을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 0, 'log': '시작 > 집계 > 접수'}

에러는 사라졌지만 메뉴는 셋인데 접시 수가 0이에요. 프로그램이 멈추지 않으니 틀린 줄도 모르고 넘어가기 쉬워요. 뒤집힌 흔적은 log의 순서(집계 > 접수)에만 남아요. KeyError는 "순서가 틀렸다"고 알려 주는 신호예요. 신호를 끄지 말고 엣지를 고치는 게 맞아요.

정리하면 두 줄이에요. 노드가 돌려주지 않은 칸에는 앞의 값이 그대로 남고(확인 ①), 한 번도 누가 쓴 적 없는 칸은 남아 있을 앞의 값 자체가 없어요(확인 ②). State에 선언된 칸이 곧 지금 존재하는 칸은 아니에요.

직접 만들기 ② — 갈림길과 되돌아가는 선

실제 시스템은 일직선으로 끝나지 않아요. "간이 맞으면 내보내고, 싱거우면 소금을 넣고 다시 맛본다" 같은 갈림길이 필요하죠. 위 흐름 그림을 그대로 코드로 옮기면 이래요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Pot(TypedDict):
    salt: int       # 넣은 소금 숟가락 수
    tries: int      # 간을 본 횟수
    result: str

def taste(state: Pot):     return {"tries": state["tries"] + 1}
def add_salt(state: Pot):  return {"salt": state["salt"] + 1}
def serve(state: Pot):     return {"result": "완성"}
def call_chef(state: Pot): return {"result": "셰프 호출"}

def judge(state: Pot) -> str:      # 라우터: 전표를 읽고 다음 노드 이름만 돌려준다
    if state["salt"] >= 3:
        return "serve"
    if state["tries"] >= 5:
        return "call_chef"         # 다섯 번 봐도 안 되면 사람을 부르는 출구
    return "add_salt"

builder = StateGraph(Pot)
for name, fn in [("taste", taste), ("add_salt", add_salt),
                 ("serve", serve), ("call_chef", call_chef)]:
    builder.add_node(name, fn)
builder.add_edge(START, "taste")
builder.add_conditional_edges("taste", judge, ["serve", "add_salt", "call_chef"])
builder.add_edge("add_salt", "taste")      # 되돌아가는 선 = 반복
builder.add_edge("serve", END)
builder.add_edge("call_chef", END)
graph = builder.compile()

print(graph.invoke({"salt": 0, "tries": 0}))
print(graph.get_graph().draw_mermaid())    # 그래프 구조를 글자 도식으로

개념 설명용 코드 — 제 화면에 찍힌 출력에서 결과 줄과 화살표 줄만 옮겼어요

{'salt': 3, 'tries': 4, 'result': '완성'}

__start__ --> taste;
add_salt --> taste;
taste -.-> add_salt;
taste -.-> call_chef;
taste -.-> serve;
call_chef --> __end__;
serve --> __end__;

add_conditional_edges(출발 노드, 라우터 함수, 목적지 목록)이 핵심이에요. taste가 끝나면 judge()를 부르고, 돌려받은 문자열을 노드 이름으로 보고 그리로 가요. 간을 네 번 보고 소금을 세 번 넣은 뒤 serve로 빠졌네요.

  • 목적지를 딕셔너리로도 줄 수 있어요. {"통과": "serve", "보류": "add_salt"}처럼 주면 라우터가 한국어 라벨을 돌려주고 LangGraph가 노드 이름으로 번역해 줘요. 노드 이름은 영문으로, 라벨만 한국어로 두는 절충이에요.
  • 조건부 엣지 하나로 분기와 반복을 다 만들어요. 이미 지나온 노드로 돌아가는 선을 그으면 그게 반복이에요.
  • 그림으로 확인하기. draw_mermaid()는 Mermaid11 문법 글자를 돌려줘요. -->는 실선(항상 가는 길), -.->는 점선(조건에 따라 고르는 길)이에요. 목적지를 리스트로 줘서 라벨이 노드 이름과 같으면 화살표 라벨이 생략되고, 딕셔너리로 다른 라벨을 주면 화살표 위에 라벨이 찍혀요. draw_mermaid_png()는 그림 파일로 바로 그려 주지만, 기본 설정은 외부 렌더링 서비스를 부르니 인터넷이 필요해요.

반복에는 늘 따라오는 위험이 있어요. 끝나지 않을 수 있다는 거예요. judge가 항상 "add_salt"만 돌려주게 바꾸고 graph.invoke(입력, {"recursion_limit": 6})으로 돌려 보니, 여섯 스텝에서 GraphRecursionError가 나며 멈췄어요. 그럼 상한을 안 주면 어디서 멈출까요? 예전 자료에는 기본 25스텝이라고 나오는데, 제가 설치한 langgraph 1.2.11의 소스 코드를 열어 보니 기본값이 10007이었어요. 버전별로 받아 보니 1.0.0은 25, 1.1.0은 10000, 1.2.0은 10007이었어요. 기본 상한이 알아서 일찍 끊어 줄 거라고 기대하면 안 된다는 뜻이에요(아래 무한 반복 실험에서 직접 봐요). 게다가 상한에 걸려 멈추는 건 예외라서 그때까지 만든 중간 결과를 못 받아요. 그래서 위 코드처럼 tries를 세다가 call_chef로 빠지는 정상 출구를 그래프 안에 두는 게 기본이고, recursion_limit은 그 설계가 실패했을 때를 대비한 두 번째 안전망이에요. 그 두 번째 안전망도 기본값에 맡기지 말고 직접 적어 두는 게 좋아요. 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건에서 "중단을 완료로 표시하지 말라"고 했던 것과 같은 이야기예요.

갈림길 더 밀어붙이기 — 세 갈래, 라벨, 일부러 만든 무한 반복

강의에는 조건부 엣지 실습 뒤에 "더 해보기" 문제가 세 개 붙어 있었어요. 처음엔 강의 코드를 통째로 베껴 넣었더니 실행은 되는데, 무엇을 확인했는지는 하나도 남지 않았어요. 50줄 가운데 문제마다 실제로 바뀌는 건 두세 줄뿐인데, 그 두세 줄이 나머지 속에 묻혀 버렸거든요. 그래서 합치기 규칙 확인하기 때처럼 한 번에 몇 줄만 바꾸고, 돌리기 전에 결과를 먼저 예상한 뒤 실행하는 식으로 다시 풀었어요.

세 문제가 왜 필요한지부터 짚을게요. 갈래를 늘리는 건 다음 편의 라우팅(입력 종류마다 다른 담당에게 보내기)의 뼈대이고, 되돌아가는 선은 다음 편의 평가자-최적화자(통과할 때까지 고쳐 쓰기)의 뼈대예요. 여기서는 LLM 없이 글자 수로만 가르지만, 실제로는 라우터 자리에 LLM의 판단이 들어가는 경우가 많아요.

출발점 — 노트 분량 검사 그래프

강의 예제는 학생이 올린 공부 노트를 받아, 복습 문제를 낼 만큼 내용이 충분한지 가르는 그래프였어요. 60자보다 짧으면 보강해 달라고 보류하고, 아니면 출제 대기열로 보내요. 구조는 그대로 두고 코드를 제 식으로 줄여 다시 짰어요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Note(TypedDict):
    text: str       # 올라온 노트 원문
    verdict: str    # 판정 결과

def receive(state: Note):
    print(f"[receive] {len(state['text'])}자 노트 접수")
    return {}                          # 바꾸는 칸이 없으면 빈 딕셔너리

def triage(state: Note) -> str:        # 라우터: 글자 수만 보고 다음 노드 이름을 돌려준다
    if len(state["text"].strip()) < 60:
        return "flag_too_short"
    return "accept"

def flag_too_short(state: Note): return {"verdict": "보류 — 60자 미만이라 보강 필요"}
def accept(state: Note):         return {"verdict": "출제 가능"}

builder = StateGraph(Note)
builder.add_node("receive", receive)
builder.add_node("flag_too_short", flag_too_short)
builder.add_node("accept", accept)
builder.add_edge(START, "receive")
builder.add_conditional_edges("receive", triage, ["flag_too_short", "accept"])
builder.add_edge("flag_too_short", END)
builder.add_edge("accept", END)
graph = builder.compile()

for text in ["State는 딕셔너리다.",
             "State는 노드들이 함께 쓰는 딕셔너리다. 노드는 바꾼 칸만 돌려주고, 나머지 칸은 LangGraph가 그대로 남겨 둔다.",
             "State는 딕셔너리다. " * 250]:        # 같은 문장 250번 = 3500자짜리 긴 노트
    out = graph.invoke({"text": text})
    print(" →", out["verdict"])

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

[receive] 69자 노트 접수

3500자짜리 노트도 '출제 가능'이에요. 갈래가 둘뿐이라 짧지만 않으면 무조건 통과예요. 문항 하나로는 다 덮을 수 없는 긴 노트를 걸러 낼 길이 그래프에 아예 없는 거예요. 첫 문제는 여기서 출발해요.

① 세 번째 갈래 — 너무 긴 노트는 쪼개기

3000자를 넘는 노트는 따로 빼서 1000자씩 쪼개기로 해요. 바꿀 곳은 네 군데예요. ⓐ 조각을 담을 칸, ⓑ 라우터의 판단 하나, ⓒ 새 노드 둘, ⓓ 목적지 목록의 이름 하나요.

실행: 로컬 파이썬 — 위 코드에서 이 부분만 더하거나 바꿔요

class Note(TypedDict):
    text: str
    verdict: str
    parts: list     # ⓐ 새 칸: 쪼갠 조각

def triage(state: Note) -> str:
    n = len(state["text"].strip())
    if n < 60:
        return "flag_too_short"
    if n > 3000:                       # ⓑ 판단 하나 추가
        return "flag_too_long"
    return "accept"

def flag_too_long(state: Note): return {"verdict": "분할 필요 — 3000자 초과"}   # ⓒ 새 노드 둘
def split_note(state: Note):
    t = state["text"]
    return {"parts": [t[i:i + 1000] for i in range(0, len(t), 1000)]}     # 1000자씩 자르기

builder.add_node("flag_too_long", flag_too_long)
builder.add_node("split_note", split_note)
builder.add_conditional_edges("receive", triage,
                              ["flag_too_short", "accept", "flag_too_long"])   # ⓓ 기존 줄을 이걸로 바꿔요
builder.add_edge("flag_too_long", "split_note")    # 판정 다음엔 항상 쪼개기
builder.add_edge("split_note", END)

# 맨 아래 for 문: 목록은 그대로 두고 print 줄만 이렇게 바꾼 뒤, 그래프 그림을 찍는 줄을 더해요
    print(" →", out["verdict"], "| 조각 길이:", [len(p) for p in out.get("parts", [])])
print(graph.get_graph().draw_mermaid())

flag_too_long과 split_note를 둘로 나눈 데는 이유가 있어요. 목적지를 리스트로 주면 라우터가 돌려준 글자가 곧 노드 이름이어야 해요. 그래서 "flag_too_long"을 돌려주려면 같은 이름의 노드가 있어야 하고, 그 노드가 판정을 적은 뒤 실선을 따라 split_note로 넘겨요. 출력 줄의 .get("parts", [])는 앞에서 본 대로, 짧은 노트처럼 parts 칸이 아예 생기지 않은 경우에 빈 목록을 대신 쓰려는 거예요.

개념 설명용 코드 — 제 화면에 찍힌 출력에서 긴 노트의 결과와 화살표 줄만 옮겼어요

[receive] 3500자 노트 접수
 → 분할 필요 — 3000자 초과 | 조각 길이: [1000, 1000, 1000, 500]

__start__ --> receive;
flag_too_long --> split_note;
receive -.-> accept;
receive -.-> flag_too_long;
receive -.-> flag_too_short;
accept --> __end__;
flag_too_short --> __end__;
split_note --> __end__;

receive에서 나가는 점선이 셋이 됐어요. 목적지 목록에 이름을 더하는 만큼 갈래가 늘어나요. 그리고 flag_too_long --> split_note는 실선이에요. 라우터가 고르는 길은 점선, 판정 뒤에 무조건 가는 길은 실선이라는 게 그림에 그대로 드러나요.

이름을 한 군데라도 안 맞추면 어떻게 되는지도 일부러 틀려 봤어요.

무서운 건 첫 번째예요. 테스트 삼아 짧은 노트와 보통 노트만 넣어 보면 아무 문제 없이 돌아가다가, 긴 노트가 처음 들어오는 날에야 터져요. 게다가 트레이스백 맨 아래에 During task with name 'receive'라고 찍혀서 receive 노드를 의심하게 되는데, 범인은 receive에 붙어서 도는 라우터예요. 라우터가 돌려줄 수 있는 이름과 목적지 목록이 한 글자도 다르지 않은지는 사람이 맞춰야 해요.

② 라벨 붙이기 — 화살표에 이유 적기

이번엔 라우터가 노드 이름 대신 "보류"·"통과"·"분할" 같은 라벨을 돌려주게 하고, 목적지를 리스트 대신 딕셔너리로 줘요. 딕셔너리는 "이 라벨이 오면 이 노드로"라는 번역표예요.

실행: 로컬 파이썬 — ①까지 고친 코드에서 라우터와 add_conditional_edges 줄만 바꿔요

def triage(state: Note) -> str:
    n = len(state["text"].strip())
    if n < 60:
        return "보류"                  # 노드 이름 대신 라벨을 돌려준다
    if n > 3000:
        return "분할"
    return "통과"

builder.add_conditional_edges("receive", triage,
    {"보류": "flag_too_short", "통과": "accept", "분할": "flag_too_long"})   # 라벨 → 노드 이름 번역표

개념 설명용 코드 — 제 화면에 찍힌 draw_mermaid() 출력 중 점선 세 줄이에요

receive -. &nbsp;통과&nbsp; .-> accept;
receive -. &nbsp;분할&nbsp; .-> flag_too_long;
receive -. &nbsp;보류&nbsp; .-> flag_too_short;

판정 결과는 ①과 똑같은데, 점선 화살표 가운데에 라벨이 끼어들었어요. &nbsp;는 HTML에서 띄어쓰기 한 칸을 뜻하는 기호라서, 이 글자를 GitHub나 Notion에 붙여 그림으로 그리면 화살표 위에 '보류', '통과', '분할'만 보여요. ①에서 화살표에 라벨이 없었던 건 라벨과 노드 이름이 같아서 생략됐기 때문이에요. 노드 이름은 영문으로 두고, 사람이 읽을 라벨만 한국어로 다는 절충이에요.

여기서 두 가지에 걸려 넘어지기 쉬워요.

  • 갈림길을 두 번 붙이기. 주피터나 Colab처럼 코드를 칸 단위로 나눠 돌리는 노트북에서, 원래 코드를 이미 돌린 뒤 바뀐 add_conditional_edges 한 줄만 새 칸에 붙여 실행하면 ValueError: Branch with name `triage` already exists for node `receive`가 나요. 같은 builder의 같은 출발 노드에 같은 라우터로 갈림길을 두 번 붙였다는 뜻이에요. builder = StateGraph(Note)부터 다시 만드는 칸 전체를 돌려야 해요.
  • 번역표에 없는 라벨. 라우터가 번역표에 없는 "합격"을 돌려주게 해 봤더니, ①의 첫 번째 실수와 같은 KeyError: '합격'이 났어요. 라벨을 바꿀 땐 라우터와 딕셔너리를 같이 고쳐요.

③ 일부러 무한 반복 — 되돌아가는데 아무것도 안 바뀌면

flag_too_short에서 END로 가던 선을 receive로 돌려요. 짧은 노트를 '다시 접수'시키는 거예요. 돌리기 전에 예상해 보세요. 13자 노트를 넣으면 몇 번 만에 끝날까요?

실행: 로컬 파이썬 — ②까지 고친 코드에서 엣지 한 줄을 바꾸고, 맨 아래 for 문을 이 한 줄로 바꿔요

builder.add_edge("flag_too_short", "receive")    # END로 가던 선을 처음으로 되돌린다

graph.invoke({"text": "State는 딕셔너리다."}, {"recursion_limit": 6})

끝나지 않아요. receive가 세 번 찍혔고, 그 사이사이 flag_too_short도 세 번 돌았어요(출력하는 줄이 없는 노드라 안 보일 뿐이에요). 이 그래프처럼 노드가 한 줄로 이어서 돌 때는 노드 한 번 실행이 스텝 하나라서, 3 + 3 = 6스텝에서 끊긴 거예요(여러 노드가 한 스텝에 동시에 도는 경우는 다음 편 병렬화의 슈퍼스텝에서 봐요). draw_mermaid()를 찍어 보면 flag_too_short --> receive;라는 실선이 새로 생겨 있어요.

그런데 위의 간 맞추기 그래프도 되돌아가는 선이 있었는데 그건 끝났잖아요. 차이는 한 바퀴 돌 때마다 State가 바뀌느냐예요. 간 맞추기에서는 add_salt가 돌 때마다 salt를 1씩 올려서 언젠가 3에 닿아요. 여기서는 되돌아가는 동안 text를 고치는 노드가 하나도 없어요. 똑같은 13자 노트를 똑같은 라우터가 똑같이 판정하니, 몇 바퀴를 돌아도 같은 길이에요. 되돌아가는 선이 의미가 있으려면 소금이든, 시도 횟수든, 고쳐 쓴 초안이든 매 바퀴 무언가가 달라져야 해요.

recursion_limit을 빼고 기본값으로 돌려 봤더니 receive가 5,004번, flag_too_short가 5,003번 돈 뒤에야 10007스텝에서 멈췄어요. 이 노드들이 LLM을 부르는 노드였다면 호출이 만 번 가까이 쌓였을 거예요. 아래 '나쁜 선택 vs 좋은 선택'의 정상 출구가 왜 필요한지 이 숫자가 말해 줘요.

덤 — 라우터가 전표에 직접 적으면?

강의 주관식 퀴즈는 이거였어요. "triage()는 State를 읽기만 했는데, 라우터 안에서 State를 고치려 하면 무슨 문제가 생길까?" 처음엔 답을 못 적었어요. 그래서 라우터에서 전표를 고치는 방법 세 가지를 직접 해 봤어요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Note(TypedDict):
    text: str
    verdict: str
    history: list   # 거쳐 간 곳 기록

def receive(state: Note): return {"history": ["receive"]}
def accept(state: Note):
    print("accept가 받은 verdict:", state.get("verdict"), "| history:", state["history"])
    return {}

def triage(state: Note) -> str:
    state["verdict"] = "라우터가 적은 판정"   # 실험 1: 칸에 새 값 적기
    state["history"].append("router")        # 실험 2: 리스트 안을 직접 고치기
    return "accept"

builder = StateGraph(Note)
builder.add_node("receive", receive)
builder.add_node("accept", accept)
builder.add_edge(START, "receive")
builder.add_conditional_edges("receive", triage, ["accept"])
builder.add_edge("accept", END)
print(builder.compile().invoke({"text": "아무 노트"}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

accept가 받은 verdict: None | history: ['receive', 'router']
{'text': '아무 노트', 'history': ['receive', 'router']}

실험 3은 라우터 본문을 return {"verdict": "라우터가 적은 판정"} 한 줄로 바꿔서, 노드처럼 딕셔너리를 돌려주게 한 거예요. 세 결과를 모으면 이래요.

라우터 안에서 한 일결과왜 그런가
실험 1 — state["verdict"] = ...로 칸에 새 값 적기사라짐. 다음 노드도, 최종 결과도 verdict가 없어요라우터가 받는 State는 매번 새로 만든 딕셔너리(전표 사본)라서, 사본에 적은 글씨는 원본으로 안 가요
실험 2 — state["history"].append(...)로 리스트 안을 고치기남음. 'router'가 끼어들었어요사본의 리스트 칸이 원본과 같은 리스트를 가리키고 있어서, 그 안을 고치면 원본까지 바뀌어요. LangGraph가 받아 준 변경이 아니라 새어 들어간 거예요
실험 3 — {"verdict": ...} 딕셔너리를 돌려주기멈춤. TypeError: unhashable type: 'dict'13라우터의 반환값은 목적지 목록에서 이름을 찾는 열쇠로 쓰이는데, 딕셔너리는 열쇠가 될 수 없는 자료형이에요

퀴즈의 답을 제 말로 적으면 이래요. 라우터의 반환값은 '다음에 갈 곳'으로만 해석되고, State에 옮겨 적는 통로는 노드의 반환값뿐이다. 그래서 라우터에서 적은 값은 사라지거나(실험 1), 기록 없이 몰래 새어 들어가거나(실험 2), 목적지를 못 찾고 멈춰요(실험 3). 제일 위험한 건 실험 2예요. 되는 것처럼 보여서 믿고 쓰게 되는데, 문자열이나 숫자 칸은 제자리에서 고칠 방법이 없어서 결국 실험 1처럼 새 값을 적게 되고, 그 값은 조용히 사라지거든요. 판정 결과를 남기고 싶으면 판정을 적는 노드를 따로 두면 돼요. 세 번째 갈래 문제의 flag_too_long이 딱 그런 노드예요.

세 문제에서 남은 것

문제바꾼 곳확인한 것
① 세 번째 갈래라우터에 판단 하나, 목적지 목록에 이름 하나, 노드 둘갈래는 필요한 만큼 늘릴 수 있어요. 대신 라우터가 돌려줄 이름과 목적지 목록은 사람이 맞춰야 해요
② 라벨라우터의 반환값, 목적지를 리스트에서 딕셔너리로라벨이 노드 이름과 다르면 그림의 화살표에 갈래의 이유가 적혀요
③ 무한 반복선 하나를 END에서 receive로되돌아가는 선은 매 바퀴 State가 바뀌어야 끝나요. 상한은 기본값에 맡기지 말고 직접 걸어요
덤 — 라우터 퀴즈라우터 안에서 State 고치기적은 값은 사라지거나 몰래 새어 들어가요. 전표에 적는 건 노드의 일이에요

직접 만들기 ③ — 도구를 쥐여 주는 루프

이제 진짜 LLM을 넣어요. 여기서부터는 OpenAI API 키14가 필요해요. 키를 넣는 방법은 세 가지예요.

  • 내 컴퓨터 — 프로젝트 폴더의 .env 파일에 OPENAI_API_KEY=sk-...를 적고 from dotenv import load_dotenv; load_dotenv()로 읽어요. .env는 절대 깃에 올리지 않아요 (AI 코드 보안 기초에서 다룬 비밀 관리 그대로예요).
  • Colab — 왼쪽 열쇠 아이콘(보안 비밀)에 등록하고 google.colab.userdata로 읽어요.
  • 임시 — os.environ["OPENAI_API_KEY"] = "sk-..."로 직접 넣어요. 노트북 파일에 키가 그대로 남으니 저장하거나 공유하기 전에 꼭 지워요.

모두의연구소 강의 화면의 코드 셀에서 돌린다면 첫 번째 방법이 적힌 그대로는 안 통해요. 코드가 내 컴퓨터가 아니라 강의 서버에서 돌기 때문이에요. 제가 한참 막혔던 과정은 아래 '강의 화면에서 API 키 넣기'에 따로 적어 뒀어요.

도구는 함수에 @tool을 붙여 만들어요. 여기서 제일 중요한 건 독스트링15이에요. LangChain이 독스트링과 타입 힌트를 읽어 JSON 스키마16를 만들고, 모델은 우리 파이썬 코드가 아니라 이 스키마만 봐요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요 (호출마다 요금이 조금 나가요)

from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

@tool(parse_docstring=True)
def get_recipe(dish: str) -> str:
    """요리 한 접시에 들어가는 재료와 양을 알려 준다. 만들 수 있는지 답하기 전에 먼저 호출한다.

    Args:
        dish: 요리 이름. 예: "계란말이"
    """
    return {"계란말이": "계란 3개", "두부조림": "두부 1모"}.get(dish, "레시피 없음")

@tool(parse_docstring=True)
def check_stock(item: str) -> str:
    """창고에 재료가 몇 개 남았는지 조회한다.

    Args:
        item: 재료 이름. 예: "계란"
    """
    return f"{item} {({'계란': 4, '두부': 0}).get(item, 0)}개"

TOOLS = [get_recipe, check_stock]
llm = ChatOpenAI(model="gpt-4o-mini").bind_tools(TOOLS)   # 모델에게 메뉴판을 건넨다

def agent(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(TOOLS))                 # 요청서를 실제로 실행하는 노드
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)   # tool_calls가 있으면 "tools", 없으면 END
builder.add_edge("tools", "agent")                        # 결과를 들고 다시 모델에게
graph = builder.compile()

result = graph.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})
for m in result["messages"]:
    m.pretty_print()

한 줄씩 짚어 볼게요.

  • parse_docstring=True — 이걸 빼면 독스트링의 Args: 설명이 스키마에 안 들어가요. 성실하게 써 두고도 모델에게 전달이 안 되는 셈이라 꼭 확인할 값이에요. 제 컴퓨터에서 get_recipe의 스키마를 찍어 보니 "dish": {"description": "요리 이름. 예: \"계란말이\"", "type": "string"}처럼 타입 힌트는 type이, Args:는 description이 돼 있었어요.
  • MessagesState — messages 칸 하나짜리 미리 만들어진 State예요. 새 메시지가 오면 덮어쓰지 않고 뒤에 쌓이게 설정돼 있어서 대화 기록을 따로 관리할 필요가 없어요.
  • bind_tools는 도구를 실행하지 않아요. 모델 응답의 tool_calls 칸에 "이 도구를 이 값으로 불러 달라"는 요청만 담겨요. 실제 실행은 ToolNode가 하고, 결과를 ToolMessage로 메시지 목록에 붙여요.
  • tools_condition — 마지막 메시지에 tool_calls가 있으면 "tools"를, 없으면 END를 돌려주는 미리 만들어진 라우터예요.

실행하면 이런 순서로 흘러가요. 사용자 질문을 받은 모델은 답 대신 레시피와 재고를 알려 달라는 도구 요청을 내놓고(모델에 따라 두 개를 한 번에 요청하기도, 하나씩 부르기도 해요), ToolNode가 두 함수를 실행해 "계란 3개", "계란 4개"를 붙이고, 다시 불려 온 모델이 그걸 읽고 "한 접시만 가능하다"는 최종 답을 써요. 더 부를 도구가 없으니 tools_condition이 END를 돌려주고 끝나요.

강의 실습에서도 똑같은 장면이 나왔어요. 노트 조회 도구와 출제 가능 판정 도구를 쥐여 주고 "이 노트로 문제를 낼 수 있나" 물었더니, 모델이 먼저 조회를 불러 208자·4문장이라는 값을 받고, 그 숫자를 그대로 판정 도구의 인자로 넣었어요. 개발자가 "조회한 뒤 판정하라"고 코드에 순서를 박지 않았는데도요. 이렇게 관찰과 행동을 번갈아 하며 다음 행동을 스스로 정하는 게 ReAct17 루프예요. 도구 결과라는 확실한 기준을 받아 오니 모델 기억에만 기대는 것보다 지어낼 여지가 줄어들어요.

이 agent ↔ tools 루프는 너무 자주 쓰여서 한 줄짜리 부품도 있어요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요, 위 코드의 TOOLS를 그대로 써요

from langchain.agents import create_agent

agent = create_agent("openai:gpt-4o-mini", tools=TOOLS)
agent.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})

이 부품의 draw_mermaid()를 찍어 보면 노드 이름만 model·tools로 다를 뿐, 손으로 조립한 것과 같은 모양이었어요. 그럼 왜 굳이 손으로 만들었을까요. 실무에서는 도구 호출 횟수에 상한을 두거나, 특정 도구를 부르기 전에 사람의 승인을 받는 식으로 흐름을 고치고 싶어져요. 단순한 도구 루프 하나면 create_agent, 흐름을 통제해야 하면 직접 그리는 쪽이 유리해요.

나쁜 선택 vs 좋은 선택 — 간 맞추기 반복을 설계할 때

같은 주방에서, 검수대가 싱거운 요리를 화구로 되돌리는 반복을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 검수대에서 화구로 돌아가는 선만 긋고, 끝나는 조건은 "간이 맞으면" 하나만 뒀어요. 멈추는 건 LangGraph의 기본 상한에 맡겼고요.

무슨 일이 생기나: 소금통이 빈 날엔 간이 영원히 안 맞아요. 지금 langgraph(1.2 이후)의 기본 상한은 10007스텝이라, 간 보기와 소금 넣기를 5천 번씩 되풀이한 뒤에야 GraphRecursionError로 끊겨요. 간 보기가 LLM 호출이었다면 그 요금은 다 나갔고, 중간 결과는 예외와 함께 사라져요. 왜 멈췄는지도 결과에 안 남아요.		 무엇을 했나: 전표에 tries 칸을 두고, 다섯 번을 넘기면 call_chef 노드로 빠지는 정상 출구를 그래프에 그렸어요. recursion_limit은 두 번째 안전망으로만 남겼어요.

무슨 일이 생기나: 몇 번 만에 끝나든 결과가 정상적으로 돌아오고, result 칸에 "셰프 호출"이 남아서 덜 끝났다는 사실이 드러나요. 상한을 올릴지, 재료를 바꿀지 판단할 재료가 생겨요.

① 코드는 내 컴퓨터가 아니라 강의 서버에서 돌아요

모두의연구소 강의 화면에서 셀의 [실행] 버튼을 누르면, 코드는 제 노트북이 아니라 강의 쪽 서버에 떠 있는 주피터에서 돌아요. 화면 아래 막대의 '상세보기'를 누르면 수강 환경 패널에 인스턴스 상태(RUNNING)와 커널19 종류(python3)가 보여요. 그러니 제 컴퓨터 폴더에 .env를 만들어 봐야 서버는 그 파일을 볼 수 없어요. 강의 안내의 "프로젝트 폴더에 .env"는 원래 내 컴퓨터에 주피터를 설치해 돌리는 경우의 이야기였어요.

그럼 서버의 어느 폴더일까요. load_dotenv()를 인자 없이 부르면, 주피터 안에서는 지금 작업 폴더20부터 .env를 찾고, 없으면 한 단계씩 상위 폴더로 올라가며 찾아요. python-dotenv 소스의 find_dotenv() 함수가 그렇게 짜여 있어요. 그래서 셀에 한 줄만 넣어 보면 답이 나와요.

실행: 모두의연구소 강의 화면 코드 셀 — 강의 서버의 주피터에서 돌아요

import os
print(os.getcwd())   # 지금 작업 폴더

제 화면에는 /home/jovyan이 찍혔어요. jovyan은 주피터를 서버에 띄울 때 흔히 쓰는 기본 사용자 이름이고, 이 경로는 그 사용자의 집 폴더예요. .env는 여기, 즉 /home/jovyan/.env에 두면 돼요.

② 파일은 강의 화면의 터미널에서 만들었어요

강의 화면 아래 막대의 터미널 아이콘을 누르면 같은 서버의 터미널이 열려요. 거기서 이렇게 쳤어요.

실행: 모두의연구소 강의 화면 터미널 — 코드 셀과 같은 강의 서버예요

cd /home/jovyan
cat > .env

cat > .env를 치면 커서만 깜빡이며 입력을 기다려요. 여기에 OPENAI_API_KEY=sk-... 한 줄을 붙여 넣고(= 앞뒤에 공백 없이), Enter를 누른 다음 Ctrl+D를 누르면 저장되고 프롬프트가 돌아와요. Ctrl+V로 안 붙으면 Ctrl+Shift+V나 마우스 오른쪽 클릭을 써요. 확인은 두 줄로 했어요.

실행: 모두의연구소 강의 화면 터미널

ls -a             # 이름이 점(.)으로 시작하는 숨김 파일까지 보여 줘요
cut -c1-18 .env   # 파일의 앞 18글자만 보여 줘요

두 번째 줄에 OPENAI_API_KEY=sk-가 나오면 형식이 맞아요. 키 전체를 화면에 띄우지 않고 형식만 보는 요령이라, 터미널 화면을 캡처해 질문할 때도 키가 새지 않아요.

③ 파일을 만들었는데도 '비어 있음' — 조용히 넘어간 두 함정

파일을 만들고 강의의 키 설정 셀을 다시 돌렸는데도 "키 설정 여부: 비어 있음"이 그대로였어요. 셀의 뼈대는 이랬어요.

개념 설명용 코드 — 강의 키 설정 셀에서 흐름만 남기고 줄여 옮겼어요

import os
try:
    from dotenv import load_dotenv
    load_dotenv()
except ImportError:
    pass    # 함정 1: 설치가 안 돼 있어도 조용히 넘어가요

os.environ.setdefault("OPENAI_API_KEY", "")  # 함정 2: 키가 없으면 빈 값을 넣어 둬요
print("키 설정 여부:", "설정됨" if os.environ.get("OPENAI_API_KEY") else "비어 있음")

원인을 가리려고 같은 셀 맨 아래, try 밖에 진단 코드를 붙여 돌렸어요. 키 자체는 화면에 찍지 않아요.

실행: 모두의연구소 강의 화면 코드 셀 — 키 설정 셀 맨 아래에 붙여요

from dotenv import find_dotenv, load_dotenv
print("찾은 경로:", repr(find_dotenv(usecwd=True)))
print("로드 결과:", load_dotenv("/home/jovyan/.env", override=True))
print("키 길이:", len(os.environ.get("OPENAI_API_KEY", "")))

첫 줄에서 바로 ModuleNotFoundError: No module named 'dotenv'가 났어요. .env를 읽어 주는 python-dotenv 패키지가 강의 서버에 아예 없었던 거예요. 강의 셀은 except ImportError: pass로 이 에러를 삼켜서, 파일을 한 번도 읽지 않고 넘어가고 있었어요. 이 진단 코드는 다른 원인일 때도 쓸모가 있어요. 로드 결과가 False면 파일이 비었거나 형식이 틀린 거고, 키 길이가 0보다 크면 키가 들어간 거예요.

설치는 터미널이 아니라 셀에서 했어요.

실행: 모두의연구소 강의 화면 코드 셀 — 설치가 끝나면 이 줄은 지워요

%pip install python-dotenv

맨 앞의 %는 파이썬 문법이 아니라 주피터 전용 명령이라는 표시예요. %pip로 깔면 지금 셀을 돌리는 커널과 같은 파이썬 환경에 설치돼요. 터미널의 pip는 커널과 다른 환경에 깔릴 수도 있거든요. 제 경우엔 python-dotenv 1.2.3이 설치됐고, "커널을 재시작해야 할 수도 있다"는 안내가 떴지만 재시작 없이도 됐어요.

두 번째 함정은 setdefault 줄이에요. "키가 없으면 빈 문자열이라도 넣어 둔다"는 뜻이라, 셀을 처음 돌린 순간 OPENAI_API_KEY 자리에 빈 값이 들어가 버렸어요. 그런데 load_dotenv()는 기본값이 override=False라서 이미 있는 환경 변수21는 덮어쓰지 않아요. 빈 값도 "이미 있는" 걸로 치니까, .env를 만든 뒤 셀을 다시 돌려도 빈 값이 그대로 남아요. 해결책은 둘 중 하나예요.

  • load_dotenv()를 load_dotenv(override=True)로 바꿔요. .env의 값이 이미 있는 값을 이기게 해요.
  • 커널을 재시작해요. 환경 변수는 커널이 도는 동안만 메모리에 있어서, 재시작하면 빈 값도 같이 사라져요.

저는 override=True로 바꾸고 설치까지 마친 뒤 셀을 다시 돌려 "설정됨"을 봤어요. 거꾸로 말하면 커널을 재시작할 때마다 키도 사라지니, 재시작 뒤엔 키 설정 셀부터 다시 돌려야 해요. 수강 환경이 초기화되면 설치한 패키지도 사라질 수 있으니 그땐 %pip install부터 다시 하고요.

④ 남의 서버에 키를 두어도 될까

여기까지 오고 나니 "내 키를 강의 서버에 그냥 넣어도 되나?" 싶었어요. OpenAI를 부르는 코드가 그 서버에서 도니까, 어떤 방법을 쓰든 키는 결국 그 서버에 가야 해요. 다만 .env로 두면 키가 남의 서버 디스크에 저장된다는 건 알고 넣어야 해요. 다른 수강생이 볼 가능성은 낮지만, 서버를 운영하는 쪽은 기술적으로 접근할 수 있어요. 그래서 방법을 이렇게 골랐어요.

나쁜 선택좋은 선택
무엇을 했나: 평소 쓰던 키를 os.environ["OPENAI_API_KEY"] = "sk-..."로 셀에 직접 적었어요.

무슨 일이 생기나: 셀 내용은 저장돼서 다음에 열어도 그대로 있고, 실행 기록이나 제출물에 남을 수도 있어요. 키가 새면 내 계정 요금으로 누군가 계속 쓸 수 있는데, 한도가 없으니 피해가 어디서 멈출지 몰라요.		 무엇을 했나: 이 강의에만 쓸 키를 새로 만들어 사용 한도를 작게 걸고, 터미널의 cat > .env로 파일에만 넣었어요. 셀에는 load_dotenv()만 남겼어요.

무슨 일이 생기나: 셀에도, 터미널 명령 기록에도 키가 보이지 않아요(기록에는 cat > .env 명령만 남고 붙여 넣은 내용은 안 남아요). 새더라도 한도에서 멈추고, 강의가 끝나면 그 키만 폐기(revoke)하면 정리돼요.

디스크에도 남기기 싫다면 실행할 때마다 키를 입력받는 방법이 있어요. 키가 커널 메모리에만 있다가 재시작하면 사라지는 대신, 재시작할 때마다 다시 입력해야 해요. 강의 화면 셀에서 입력창이 뜨는지는 제가 확인하지 못했으니, 안 뜨면 .env 쪽으로 가면 돼요.

실행: 모두의연구소 강의 화면 코드 셀 — 입력창이 뜨는 환경에서만 돼요

비밀값을 코드와 떼어 두는 원칙은 AI가 짠 백엔드 코드에서 반드시 확인할 것들에서 다룬 것과 같아요. 장소가 내 컴퓨터에서 남의 서버로 바뀌었을 뿐이에요. 막힌 순서대로 한 표에 모으면 이래요.

보이는 증상원인해결
내 컴퓨터에 .env를 만들었는데 안 읽혀요강의 화면 셀은 강의 서버에서 돌아요print(os.getcwd())로 서버 폴더를 확인하고 거기에 만들어요 (제 경우 /home/jovyan)
파일이 있는데 에러 없이 "비어 있음"python-dotenv가 설치돼 있지 않은데 except ImportError: pass가 에러를 삼켰어요try 밖에서 import해 확인하고, 셀에서 %pip install python-dotenv
설치한 뒤에도 "비어 있음"setdefault가 넣은 빈 값을 override=False가 못 덮어써요load_dotenv(override=True)로 바꾸거나 커널 재시작
잘 되다가 다시 "비어 있음"커널을 재시작해서 메모리의 키가 사라졌어요키 설정 셀부터 다시 돌려요 (환경이 초기화됐다면 %pip install부터)

직접 해보기

  1. 독스트링 망가뜨리기 — 바꿀 것: get_recipe의 독스트링을 """조회.""" 한 단어로 줄여요(Args:가 없으면 parse_docstring=True가 오류를 내니 함께 지워요). 측정할 것: 같은 질문에 모델이 그 도구를 부르는지, 인자는 맞는지. 비교할 것: 원래 독스트링일 때와 도구 호출 순서. 도구가 안 불리면 프롬프트보다 독스트링부터 의심하는 습관이 생겨요.
  2. 계산을 도구로 빼기 — 바꿀 것: "재고로 몇 접시까지 되는지" 나눗셈을 하는 도구를 하나 더해요. 측정할 것: 재고를 7개, 11개로 바꿔 가며 답이 맞는지. 비교할 것: 같은 질문을 도구 없이 물었을 때 계산이 틀리는 빈도.
  3. 도구 호출 횟수에 상한 걸기 — 바꿀 것: agent 노드에서 메시지 목록의 ToolMessage 개수를 세다가 5개를 넘으면 도구를 붙이지 않은 모델로 마무리하게 해요. 측정할 것: 상한에 걸렸을 때 최종 답에 그 사실이 드러나는지. 이게 create_agent 대신 직접 그리는 이유를 몸으로 느끼는 실험이에요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.

함께 읽으면 좋은 글

  • 자동화·워크플로·에이전트, 뭐가 다를까 — "다음 행동을 누가 정하나"라는 기준을 처음 세운 글이에요.
  • 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동 — 오늘 조립한 루프의 뿌리예요.
  • 도구 하나가 호출되기까지 — 정의·파싱·구조화 요청 — bind_tools와 ToolNode 사이에서 무슨 일이 일어나는지 더 자세히 봐요.
  • 같은 버그를 세 방식으로 — 기준선·워크플로·오케스트레이션 실행 — 같은 기준을 Claude Agent SDK 코드로 비교한 실험이에요.
  1. 워크플로(workflow) — 실행 경로를 개발자가 코드로 미리 정해 둔 LLM 시스템으로, 자동화·워크플로·에이전트 글에서 내비 경로에 빗대 처음 다뤘어요. ↩
  2. 증강된 LLM(augmented LLM) — LLM 본체에 검색·도구·메모리를 붙여 모르는 정보를 가져오거나 바깥세상을 바꿀 수 있게 만든 기본 단위예요. ↩
  3. 할루시네이션(hallucination) — 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 현상이에요. ↩
  4. HITL(Human-in-the-Loop) — 되돌리기 어려운 행동 앞에서 사람의 승인을 받도록 흐름 중간에 사람을 끼워 두는 설계예요. ↩
  5. 프레임워크(framework) — 매번 반복되는 뼈대 코드를 미리 짜 둔 틀이라서, 개발자는 빈칸만 채우면 되는 개발 도구 묶음이에요. ↩
  6. 부분 업데이트(partial update) — 노드가 State 전체가 아니라 바꾼 칸만 돌려주면 LangGraph가 나머지 칸은 그대로 두고 합쳐 주는 방식이에요. ↩
  7. 라우터 함수 — State를 읽고 다음에 갈 노드의 이름(또는 라벨)만 돌려주는 함수예요. ↩
  8. TypedDict — 딕셔너리에 어떤 이름의 칸이 어떤 자료형으로 들어가는지 미리 적어 두는 파이썬 타입 힌트 문법으로, 칸을 실제로 만들거나 기본값을 채워 주지는 않아요(합치기 규칙 확인하기에서 직접 확인해요). ↩
  9. 트레이스백(traceback) — 에러가 났을 때 파이썬이 그 지점까지 거쳐 온 함수 호출 경로를 차례로 적어 보여 주는 기록으로, 맨 아래 줄이 실제로 일어난 에러예요. ↩
  10. KeyError — 딕셔너리에 없는 키를 d["키"]처럼 대괄호로 꺼내려 할 때 파이썬이 내는 에러예요. ↩
  11. Mermaid — 글자로 적은 도형 설명을 다이어그램으로 그려 주는 문법으로, GitHub나 Notion에 붙여 넣으면 바로 그림이 돼요. ↩
  12. ValueError — 값의 자료형은 맞지만 그 내용이 허용되지 않을 때 파이썬이 내는 에러로, 여기서는 목적지 목록에 적힌 노드 이름이 그래프에 없다는 뜻이에요. ↩
  13. TypeError — 그 자리에 쓸 수 없는 자료형의 값이 들어왔을 때 파이썬이 내는 에러예요. ↩
  14. API 키 — 유료 AI 서비스를 내 계정으로 부를 때 쓰는 비밀 문자열이라, 남에게 보이면 내 요금으로 남이 쓸 수 있어요. ↩
  15. 독스트링(docstring) — 파이썬 함수 맨 위에 적는 설명 문자열로, LangChain은 이것을 읽어 모델에게 보낼 도구 설명을 만들어요. ↩
  16. JSON 스키마 — 데이터가 어떤 칸과 자료형을 가져야 하는지 적은 규칙서로, 도구 호출 글에서 메뉴판의 '주문 규칙'에 빗댔던 입력 스키마가 이것이에요. ↩
  17. ReAct(Reasoning + Acting) — 생각과 행동을 번갈아 하며 관찰 결과로 다음 행동을 정하는 루프로, ReAct 루프 글에서 그 뿌리를 다뤘어요. ↩
  18. LLM의 답은 확률적이라 같은 질문도 실행할 때마다 도구 호출 순서나 메시지 수가 달라질 수 있어서, 이 값은 강의 실습의 한 번 실행 결과로만 읽어야 해요. ↩
  19. 커널(kernel) — 주피터에서 셀 코드를 받아 실제로 실행하며 그동안 만든 변수를 메모리에 들고 있는 프로그램이라 재시작하면 그 값이 모두 사라지고, 도커 글에 나온 운영체제의 커널과는 이름만 같아요. ↩
  20. 작업 폴더(current working directory) — 프로그램이 파일 이름만 받았을 때 기준으로 삼는 '지금 있는 폴더'로, 호스트에 연결하고 첫 도구 호출 확인하기에서 처음 다뤘어요. ↩
  21. 환경 변수(environment variable) — 코드 바깥에 "이름=값" 꼴로 적어 두고 프로그램이 이름으로 읽어 가는 설정값으로, 인증 코드와 MCP 서버 글에서 처음 다뤘어요. ↩
