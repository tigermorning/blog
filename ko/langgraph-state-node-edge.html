← 이전 편 다음에 어느 코드가 실행될까 — LangGraph와 워크플로·에이전트 (1)

LangGraph로 흐름을 짠다는 건 값을 담는 State, 일을 하는 함수인 Node, 어느 Node 다음에 어느 Node를 실행할지 정하는 Edge 세 가지를 따로 적어 하나로 합치는 일이다.

8단계 › 에이전트 팀 꾸리기 — LangGraph — 2번째 글 (전 7편)
뭐를 할 수 있나
State·Node·Edge로 그래프 하나를 직접 만들어 돌리고, 노드가 돌려준 값이 전표에 어떻게 합쳐지는지 미리 예상하고, 조건부 엣지로 갈림길과 되돌아가는 반복을 넣을 수 있어요.
왜 배우나
흐름을 while문과 if문으로만 짜면 단계가 몇 개만 늘어도 "지금 어느 갈래에 있는지, 값이 어디서 덮어써졌는지"를 코드만 보고는 알기 어려워져요.
왜 중요한가
끝나는 조건이 없는 반복은 API 호출이 멈추지 않아서 요금이 계속 나가요. 그래프로 그려 두면 되돌아가는 선이 눈에 보이고, 상한을 걸 자리도 분명해져요.
어디에 쓰나
강의 노트를 정리하는 여러 단계 파이프라인 · 조건에 따라 다른 처리로 보내는 분기 · 검사에 떨어지면 다시 하는 반복

1편에서는 밑그림만 봤어요. LangGraph가 while문 뭉치를 값(State)·일하는 함수(Node)·다음에 어느 함수를 실행할지(Edge) 세 조각으로 뜯는 도구라는 것, 그리고 그 다음에 실행할 함수를 누가 고르느냐가 워크플로와 에이전트를 가른다는 것까지요. 이번 편에서는 그 세 조각으로 실제 그래프를 만들어 돌려 봐요. 점과 선으로 이뤄진 이 구조를 왜 그래프라고 부르는지도 1편에 적어 뒀어요.

이번 편의 코드는 전부 API 키 없이 돌아가요. LLM은 한 번도 안 부르고, 길은 전부 규칙이 골라요. 라우터 자리에 모델을 앉히는 건 4편이에요. 파이썬 코드 자체가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 편해요.

순서는 이래요. 주방 비유로 세 낱말에 자리를 잡아 주고 → 흐름 그림 한 장을 먼저 보고 → 일직선 그래프를 하나 만들고 → 그 그래프를 일부러 깨뜨려 State 합치기 규칙을 확인하고 → 조건부 엣지로 갈림길과 반복을 넣어요.

비유 — 식당 주방의 주문 전표와 동선표

1편에서 무대만 세워 둔 그 주방으로 돌아갈게요. 이번에는 주방 안에서 전표가 도는 모습이에요. 주문이 들어오면 전표 한 장이 주방을 돌아요. 접수대 직원은 전표에 메뉴를 옮겨 적고, 화구 담당은 조리를 마쳤다고 자기 칸에만 체크해요. 다른 사람이 적은 칸은 건드리지 않아요.

전표가 다음에 어느 조리대로 갈지는 벽에 붙은 동선표가 정해요. "손질대 다음은 화구." 동선표 중간에는 갈림길도 있어요. 검수대 직원이 맛을 보고, 싱거우면 전표를 화구 담당에게 되돌려 보내고, 간이 맞으면 홀로 내보내요. 영업을 시작하기 전에 사장님이 이 동선표를 확정해 둬요.

비유 속 요소원래 개념
주방을 도는 전표 한 장State — 노드들이 함께 읽고 쓰는 공용 데이터
조리대 직원이 자기 칸에만 체크하기부분 업데이트1 — 노드는 바꾼 키만 돌려주고 나머지는 그대로 남아요
전표 양식에 미리 인쇄된 칸 이름 (아직 아무도 안 적은 칸 포함)State 선언 — 어떤 칸이 있을 수 있는지만 정해요. 칸의 값은 어떤 노드가 돌려줘야 비로소 생겨요 (아래에서 직접 확인)
조리대 하나 (접수대·화구·검수대)Node — State를 받아 딕셔너리를 돌려주는 평범한 파이썬 함수

사장님이 영업 전에 동선표를 확정하기compile() — 설계한 그래프를 실행 가능한 객체로 바꿔요

핵심 한 줄: 요리를 잘하는 건 조리대(노드)의 몫이고, 전표가 어디로 갈지는 동선표(엣지)가 정해요 — LangGraph는 그 동선표를 코드로 쓰는 도구예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 직원은 동선표에 없어도 눈치껏 옆 조리대를 도와주지만, 그래프는 선이 없는 곳으로는 절대 가지 않아요. 그리고 검수대(라우터)는 다음 목적지를 고르는 일만 해요. 전표에 값을 적는 건 노드가 반환값으로 하는 일이에요. 라우터가 전표에 직접 적으려 하면 무슨 일이 생기는지는 3편에서 직접 해 봤어요.

전체 흐름 — 간 맞추기 그래프 한 장

아래에서 직접 만들 두 번째 예제를 그림으로 먼저 볼게요. 1편에서 while문으로 봤던 바로 그 간 맞추기를, 이번에는 세 조각으로 뜯어 그린 모습이에요. 읽는 법: 실선은 앞 노드가 끝나면 항상 지나가는 선이고, 점선은 라우터가 여러 갈래 중 하나만 고르는 선이에요. add_salt에서 taste로 올라가는 실선이 "다시 간 보기", 즉 반복이에요. 반복이 끝나는 출구가 두 개(serve, call_chef)라는 점도 눈여겨보세요.

직접 만들기 ① — LLM 없이 일직선 그래프

개념 설명보다 한 번 돌려 보는 게 빨라요. 먼저 설치예요. 강의 교안은 langgraph 1.2, langchain-core 1.6, langchain 1.4, langchain-openai 1.6에서 검증됐고, 제가 오늘 새로 설치한 버전도 같은 줄기(1.2.11·1.6.2·1.4.0·1.6.2)였어요. 파이썬 코드 자체가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 편해요.

실행: 로컬 터미널 — 가상 환경을 켠 상태에서 한 번만

pip install -U langgraph langchain langchain-openai

첫 그래프는 LLM 없이, 손님이 쉼표로 적은 주문을 메뉴 목록으로 정리하고 접시 수를 세는 두 단계짜리예요.

붙여넣는 자리가 위와 달라요. pip install은 터미널 명령이라 PowerShell 창에 그대로 치면 되지만, 실행: 로컬 파이썬이 붙은 아래 블록은 파이썬 문법이에요. 같은 PowerShell 창에 붙이면 'from' 키워드는 이 언어 버전에서 지원되지 않습니다 같은 오류가 나요. 블록 전체를 graph1.py 같은 파일로 저장하고, 터미널에서 python graph1.py로 돌리면 돼요. 파이썬 대화형 창에 한 줄씩 붙이는 방법도 있지만, class나 def처럼 들여쓴 덩어리가 중간 빈 줄에서 끊겨서 파일로 저장하는 쪽이 편해요.

실행: 로컬 파이썬 — 터미널이 아니라 .py 파일에 저장해서 python 파일이름.py로 실행해요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Ticket(TypedDict):          # ① State: 전표에 어떤 칸이 있는지 선언
    order: str      # 손님이 적은 주문 원문
    dishes: list    # 정리된 메뉴 목록
    count: int      # 접시 수
    log: str        # 어느 조리대를 거쳤는지

def take_order(state: Ticket):    # ② Node: 전표를 받아 바꾼 칸만 돌려준다
    dishes = [d.strip() for d in state["order"].split(",") if d.strip()]
    return {"dishes": dishes, "log": state["log"] + " > 접수"}

def count_dishes(state: Ticket):
    return {"count": len(state["dishes"]), "log": state["log"] + " > 집계"}

builder = StateGraph(Ticket)
builder.add_node("take_order", take_order)      # 이름이 곧 엣지의 주소
builder.add_node("count_dishes", count_dishes)
builder.add_edge(START, "take_order")           # ③ Edge: 순서를 잇는다
builder.add_edge("take_order", "count_dishes")
builder.add_edge("count_dishes", END)
graph = builder.compile()

print(graph.invoke({"order": " 김치찌개,  계란말이 ,공기밥 ", "log": "시작"}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수 > 집계'}

출력을 세 재료 순서대로 읽어 볼게요.

  • State — Ticket은 TypedDict3로 전표의 칸을 미리 적어 둔 거예요. take_order는 dishes와 log만 돌려줬는데 order가 사라지지 않았죠. LangGraph가 반환된 딕셔너리를 기존 State에 합쳐 주기 때문이에요. 칸이 스무 개로 늘어도 노드는 자기 관심사만 다루면 되니, 노드를 따로 만들고 따로 시험하기 쉬워요.
  • Node — 그냥 파이썬 함수예요. 문자열을 다듬어도, DB를 조회해도, LLM을 불러도, 심지어 다른 그래프를 실행해도 돼요. add_node("이름", 함수)에 적은 이름이 엣지를 이을 때의 주소가 돼요.
  • Edge — START는 입구, END는 출구예요. invoke()에 넘긴 딕셔너리가 첫 State가 되어 START에서 출발하고, END에 닿는 순간의 State 전체가 반환값이에요.

log가 계속 뒤에 붙은 건 노드가 직접 +로 이어 붙였기 때문이에요. 여러 노드가 동시에 같은 칸에 쓰면 이 방식이 깨지는데, 그 문제와 해결책(리듀서)은 6편 병렬화에서 봐요.

합치기 규칙 확인하기 — 안 돌려준 칸, 아직 없는 칸

강의에는 "State 병합 규칙을 직접 확인하기"라는 연습 문제가 있었어요. 코드를 조금 바꾸고, 돌리기 전에 결과를 먼저 예상한 뒤 실행해서 맞춰 보는 문제였어요. 저는 처음에 무엇을 확인하라는 건지부터 헷갈려서, 위의 전표 예제에 그대로 옮겨 두 가지를 돌려 봤어요.

확인 ① — 돌려주지 않은 칸은 어떻게 될까

count_dishes의 반환값에서 log를 빼서 return {"count": len(state["dishes"])}만 남겨요. 나머지 코드는 위와 같아요. 바꾸기 전과 후를 나란히 두면 이래요.

개념 설명용 코드 — 위 일직선 그래프에서 count_dishes의 반환값 한 줄만 나란히 둔 거예요

# 바꾸기 전 — 칸 두 개를 돌려준다
return {"count": len(state["dishes"]),        # 조각 A: 접시를 세어 count 칸에 적는다
        "log":   state["log"] + " > 집계"}     # 조각 B: log 칸의 글자 뒤에 " > 집계"를 잇는다

# 바꾼 뒤 — 칸 하나만 돌려준다
return {"count": len(state["dishes"])}        # 조각 A만 남았다 (조각 B가 통째로 사라짐)

조각 A와 조각 B는 서로 아무 상관이 없어요. B를 지워도 접시를 세는 A는 그대로 돌아요. 돌리기 전에 먼저 예상해 보세요. 마지막 log는 None이 될까요, 빈 문자열이 될까요, 아니면 그대로일까요?

개념 설명용 코드 — 위처럼 반환값 한 줄만 바꿔 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수'}

log는 지워지지 않고 take_order가 적어 둔 '시작 > 접수'에서 멈춰 있어요. 반환값에서 키를 뺀다는 건 "이번엔 이 칸을 건드리지 않는다"는 뜻이지, State에서 지우라는 뜻이 아니에요. 주방으로 치면 집계 담당이 '거쳐 간 조리대' 칸에 아무것도 적지 않고 전표를 넘긴 거예요. 그 칸에는 앞사람이 적은 글씨가 그대로 남아요.

여기서 "집계가 빠졌다"를 "집계를 안 했다"로 읽기 쉬워요. 두 출력의 칸을 하나씩 맞대 보면 아니라는 게 보여요.

전표의 칸바꾸기 전log를 뺀 뒤
count
접시 수		33 — 그대로예요
log
거쳐 간 조리대		'시작 > 접수 > 집계''시작 > 접수'

접시를 세는 일은 그대로 했어요. count에 찍힌 3이 그 증거예요. 안 붙은 건 log 문자열 끝의 " > 집계" 네 글자뿐이에요.

log 칸은 이 프로그램이 실제로 쓰는 값이 아니라서 이런 일이 가능해요. 어느 노드를 거쳤는지 사람이 눈으로 확인하려고 만들어 둔 메모 칸이거든요. Ticket에서 log 줄을 지우고 두 노드에서도 log를 다 빼 보면, count는 여전히 3으로 나와요. 접시를 세는 데 메모는 필요 없으니까요. 손님에게 나가는 건 접시 수지 조리대 목록이 아닌 것과 같아요 — 다만 나중에 전표만 봐서는 "집계 담당이 이 전표를 봤나?"를 알 수 없게 돼요.

중요꼭 기억할 것

노드가 돌려준 칸만 새 값으로 바뀌고, 돌려주지 않은 칸은 이전 값 그대로 남아요(부분 업데이트). 그래서 노드는 전표 전체를 다시 적어 돌려줄 필요 없이 자기가 바꾼 칸만 돌려주면 돼요. 안 돌려준 칸이 None으로 비워진다, 전표에서 지워진다, 전체를 안 돌려줬으니 에러가 난다 — 이렇게 착각하기 쉬운데 셋 다 아니에요.

확인 ② — 순서를 뒤집으면

이번에는 count_dishes를 take_order보다 먼저 돌려요. 바꿀 곳은 엣지 세 줄뿐이에요.

실행: 로컬 파이썬 — 위 일직선 그래프 코드에서 builder.add_edge 세 줄만 이렇게 바꿔요

builder.add_edge(START, "count_dishes")
builder.add_edge("count_dishes", "take_order")
builder.add_edge("take_order", END)

이런 에러 기록을 트레이스백4이라고 해요. 처음 보면 겁나지만 맨 아래부터 거꾸로 읽으면 금방 풀려요.

  • KeyError: 'dishes' — 무슨 일이 났는지예요. 딕셔너리에서 'dishes'라는 키를 꺼내려 했는데 없었다는 KeyError5예요.
  • During task with name 'count_dishes' — 어느 노드에서 났는지예요. LangGraph가 덧붙여 주는 줄이에요.

  • 중간의 langgraph 줄들 — 그래프 엔진 내부를 지나간 경로라서, 처음엔 건너뛰어도 돼요.

한 문장으로 옮기면 "count_dishes가 dishes를 꺼내려 했는데 전표에 그 칸이 없었다"예요. 왜 없었는지는 전표를 단계마다 따라가 보면 보여요.

시점전표에 있는 칸일어난 일
invoke() 직후order, log입력으로 넣은 두 칸뿐이에요
count_dishes 차례order, logdishes를 읽으려는데 아직 아무도 안 만들어서 에러로 멈춰요
take_order 차례—실행될 기회조차 없어요

"Ticket에 dishes라고 적어 뒀잖아?" 싶을 수 있어요. 여기가 이 편에서 제일 걸리는 자리라, State가 실제로 무엇인지부터 한 계단 내려가 볼게요.

State는 그냥 파이썬 딕셔너리예요. 딕셔너리는 이름표가 붙은 서랍장이라고 보면 돼요. 값을 넣는 순간 그 이름의 서랍이 생겨요. 안 넣으면 서랍이 비어 있는 게 아니라 서랍 자체가 없어요. 그리고 Ticket처럼 TypedDict로 적어 둔 칸 이름은 "이 서랍장에는 이런 이름표를 쓸 겁니다"라고 적어 둔 목록일 뿐이에요. 목록을 적는다고 서랍이 생기지는 않아요. LangGraph 없이 파이썬만으로 확인할 수 있어요.

실행: 로컬 파이썬 — 그래프 없이 이 다섯 줄만 따로 돌려 봐도 돼요

t: Ticket = {"order": "김치찌개,계란말이", "log": "시작"}

print(list(t.keys()))    # 실제로 만들어진 칸
print(t.get("dishes"))   # 없는 칸을 .get()으로 꺼내면
print(t["dishes"])       # 없는 칸을 대괄호로 꺼내면

개념 설명용 코드 — 위 세 줄을 실행했을 때 제 화면에 찍힌 출력이에요

['order', 'log']
None
KeyError: 'dishes'

Ticket에 칸 이름을 넷 적어 뒀는데 실제로 있는 건 둘뿐이에요. dishes와 count는 None이나 빈 리스트로 들어 있던 게 아니라 아예 없어요. 그리고 invoke()에 넘긴 딕셔너리가 곧 시작 State라서, 그래프도 서랍 두 개짜리로 출발해요. 순서를 뒤집은 그래프에서 첫 노드가 받은 State의 키를 찍어 봤더니 정말 ['log', 'order'] 두 개였어요.

여기서 주방 비유도 끊겨요. 종이 전표는 칸이 인쇄돼 있어서 "칸은 있는데 아직 안 적혔다"가 가능해요. 딕셔너리에는 그 중간 상태가 없어요 — 있거나, 아예 없거나 둘뿐이에요. 그리고 없는 칸을 대괄호로 읽으려 하면 파이썬은 빈 값을 주는 대신 그 자리에서 멈춰요. 위 출력의 None과 KeyError가 그 차이예요.

그래서 노드마다 읽는 칸과 만드는 칸을 나눠 보면 순서가 저절로 정해져요.

노드읽는 칸 (먼저 있어야 하는 것)만드는 칸
take_orderorder, log — 둘 다 입력으로 처음부터 있어요dishes, log
count_dishesdishes, log — dishes는 take_order가 돌려줘야 생겨요count, log

take_order는 맨 처음에 돌아도 필요한 게 다 있고, count_dishes는 반드시 take_order 뒤에 와야 해요. 그리고 LangGraph는 "이 노드가 dishes를 필요로 하니 take_order부터 돌리자" 같은 판단을 해 주지 않아요. 엣지로 정한 순서 그대로 실행할 뿐이라서, 값을 만드는 노드가 그 값을 읽는 노드보다 앞에 오도록 잇는 건 사람의 몫이에요. 참고로 add_node 두 줄의 순서만 바꿔 보면 결과가 원래와 똑같이 나와요. 노드를 등록하는 순서는 실행 순서와 상관없어요.

에러를 없애려고 state["dishes"]를 state.get("dishes", [])로 바꾸는 방법도 떠올릴 수 있어요. .get()은 키가 없으면 에러를 내는 대신 뒤에 준 기본값을 돌려주는 딕셔너리 메서드예요. 바꾸는 자리는 count_dishes 함수 안, len() 괄호 속 한 군데예요.

실행: 로컬 파이썬 — 엣지는 뒤집힌 그대로 두고 count_dishes의 이 줄만 바꿔요

# 바꾸기 전
def count_dishes(state: Ticket):
    return {"count": len(state["dishes"]), "log": state["log"] + " > 집계"}
#                        ^^^^^^^^^^^^^^^^ 없는 칸을 대괄호로 읽어서 KeyError

# 바꾼 뒤
def count_dishes(state: Ticket):
    return {"count": len(state.get("dishes", [])), "log": state["log"] + " > 집계"}
#                        ^^^^^^^^^^^^^^^^^^^^^^^ 칸이 없으면 [] 를 대신 준다

같은 줄의 state["log"]는 그대로 둬요. log는 invoke()에 넣어 준 칸이라 처음부터 있거든요. .get()은 실제로 없는 칸에만 필요해요. 그리고 기본값 []를 빼고 state.get("dishes")라고만 쓰면 None이 돌아오고, len(None)에서 이번엔 TypeError가 나요. len()에 넘길 값이니 빈 리스트를 줘야 해요. 이렇게 바꿔서 돌려 봤어요.

개념 설명용 코드 — 순서를 뒤집은 채 .get()으로만 바꿨을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 0, 'log': '시작 > 집계 > 접수'}

에러는 사라졌어요. 그런데 출력이 앞뒤가 안 맞아 보여요. 같은 전표에 메뉴는 셋(dishes)인데 접시 수는 0(count)이라고 적혀 있거든요. 엣지가 뒤집혀 있으니 count_dishes가 먼저 돈다는 걸 시간 순서로 따라가면 풀려요.

실행 시점dishes 칸count 칸log 칸
출발없음없음'시작'
count_dishes없음 — .get이 []를 대신 줘요len([]) = 0'시작 > 집계'
take_order메뉴 셋이 이제야 생겨요0 그대로'시작 > 집계 > 접수'

count_dishes는 딱 한 번만 돌아요. 셀 때는 아무것도 없어서 0을 적었고, 그 뒤에 메뉴가 생겼다고 누가 다시 세어 주지 않아요. 그래서 마지막 전표에 "메뉴 셋 + 접시 수 0"이 나란히 남아요.

그리고 순서가 뒤집혔다는 단서는 log에만 남아요. '시작 > 집계 > 접수' — 집계가 접수보다 앞에 찍혀 있죠. count: 0만 봐서는 "주문이 비어 있었나?" 싶지, 순서 문제인 줄은 몰라요.

여기가 이 확인 문제의 핵심이에요. 바꾸기 전에는 KeyError가 나면서 프로그램이 멈췄어요. 멈추면 당장은 성가시지만, 덕분에 "count_dishes가 dishes를 못 찾았다 = 순서가 틀렸다"를 그 자리에서 알았어요. .get은 그 멈춤만 없애요. 순서는 여전히 틀린 채로 프로그램이 끝까지 돌고, 답만 조용히 틀려요. 시끄럽다고 화재경보기 배터리를 뺀 것과 같아요 — 소리는 멎었지만 불은 그대로예요. 고칠 자리는 엣지 세 줄이에요.

정리하면 두 줄이에요. 노드가 돌려주지 않은 칸에는 앞의 값이 그대로 남고(확인 ①), 한 번도 누가 쓴 적 없는 칸은 남아 있을 앞의 값 자체가 없어요(확인 ②). State에 선언된 칸이 곧 지금 존재하는 칸은 아니에요.

직접 만들기 ② — 갈림길과 되돌아가는 선

실제 시스템은 일직선으로 끝나지 않아요. "간이 맞으면 내보내고, 싱거우면 소금을 넣고 다시 맛본다" 같은 갈림길이 필요하죠. 1편의 while문 코드와 하는 일이 똑같은 예제인데, 이번에는 값(State)·일(Node)·길(Edge)을 따로 떼어 적어요. 위 흐름 그림을 그대로 코드로 옮기면 이래요.

맨 끝에 print가 두 줄인 게 눈에 띌 거예요. 첫 줄은 결과를, 둘째 줄의 draw_mermaid()는 다 만든 그래프의 모양을 글자로 돌려받는 거예요. 바로 위 문장이 "흐름 그림을 코드로 옮긴다"였는데, 이건 그 반대 방향이에요 — 코드로 그린 길이 원래 그리려던 그림과 같은지 되돌려 받아 맞춰 보는 거죠.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Pot(TypedDict):
    salt: int       # 넣은 소금 숟가락 수
    tries: int      # 간을 본 횟수
    result: str

def taste(state: Pot):     return {"tries": state["tries"] + 1}
def add_salt(state: Pot):  return {"salt": state["salt"] + 1}
def serve(state: Pot):     return {"result": "완성"}
def call_chef(state: Pot): return {"result": "셰프 호출"}

def judge(state: Pot) -> str:      # 라우터: 전표를 읽고 다음 노드 이름만 돌려준다
    if state["salt"] >= 3:
        return "serve"
    if state["tries"] >= 5:
        return "call_chef"         # 다섯 번 봐도 안 되면 사람을 부르는 출구
    return "add_salt"

builder = StateGraph(Pot)
for name, fn in [("taste", taste), ("add_salt", add_salt),
                 ("serve", serve), ("call_chef", call_chef)]:
    builder.add_node(name, fn)
builder.add_edge(START, "taste")
builder.add_conditional_edges("taste", judge, ["serve", "add_salt", "call_chef"])
builder.add_edge("add_salt", "taste")      # 되돌아가는 선 = 반복
builder.add_edge("serve", END)
builder.add_edge("call_chef", END)
graph = builder.compile()

print(graph.invoke({"salt": 0, "tries": 0}))
print(graph.get_graph().draw_mermaid())    # 그래프 구조를 글자 도식으로

개념 설명용 코드 — 제 화면에 찍힌 출력에서 결과 줄과 화살표 줄만 옮겼어요

{'salt': 3, 'tries': 4, 'result': '완성'}

__start__ --> taste;
add_salt --> taste;
taste -.-> add_salt;
taste -.-> call_chef;
taste -.-> serve;
call_chef --> __end__;
serve --> __end__;

add_conditional_edges(출발 노드, 라우터 함수, 목적지 목록)이 핵심이에요. taste가 끝나면 judge()를 부르고, 돌려받은 문자열을 노드 이름으로 보고 그리로 가요. 간을 네 번 보고 소금을 세 번 넣은 뒤 serve로 빠졌네요.

  • 목적지를 딕셔너리로도 줄 수 있어요. {"통과": "serve", "보류": "add_salt"}처럼 주면 라우터가 한국어 라벨을 돌려주고 LangGraph가 노드 이름으로 번역해 줘요. 노드 이름은 영문으로, 라벨만 한국어로 두는 절충이에요.
  • 조건부 엣지 하나로 분기와 반복을 다 만들어요. 이미 지나온 노드로 돌아가는 선을 그으면 그게 반복이에요.
  • 그림으로 확인하기. 엣지를 add_edge 네 줄과 add_conditional_edges 한 줄로 흩어 적고 나면 전체 모양이 한눈에 안 들어와요. 그래서 draw_mermaid()로 되돌려 받아 보는 거예요. 출력의 아랫부분 일곱 줄이 그 결과인데, 실선과 점선만 봐도 어디가 항상 가는 길이고 어디가 갈림길인지 바로 보여요. draw_mermaid()가 돌려주는 건 Mermaid6 문법 글자를 돌려줘요. -->는 실선(항상 가는 길), -.->는 점선(조건에 따라 고르는 길)이에요. 목적지를 리스트로 줘서 라벨이 노드 이름과 같으면 화살표 라벨이 생략되고, 딕셔너리로 다른 라벨을 주면 화살표 위에 라벨이 찍혀요. draw_mermaid_png()는 그림 파일로 바로 그려 주지만, 기본 설정은 외부 렌더링 서비스를 부르니 인터넷이 필요해요.

반복에는 늘 따라오는 위험이 있어요. 끝나지 않을 수 있다는 거예요. judge가 항상 "add_salt"만 돌려주게 바꾸고 graph.invoke(입력, {"recursion_limit": 6})으로 돌려 보니, 여섯 스텝에서 GraphRecursionError가 나며 멈췄어요. 그럼 상한을 안 주면 어디서 멈출까요? 예전 자료에는 기본 25스텝이라고 나오는데, 제가 설치한 langgraph 1.2.11의 소스 코드를 열어 보니 기본값이 10007이었어요. 버전별로 받아 보니 1.0.0은 25, 1.1.0은 10000, 1.2.0은 10007이었어요. 기본 상한이 알아서 일찍 끊어 줄 거라고 기대하면 안 된다는 뜻이에요(3편의 무한 반복 실험에서 직접 봐요). 게다가 상한에 걸려 멈추는 건 예외라서 그때까지 만든 중간 결과를 못 받아요. 그래서 위 코드처럼 tries를 세다가 call_chef로 빠지는 정상 출구를 그래프 안에 두는 게 기본이고, recursion_limit은 그 설계가 실패했을 때를 대비한 두 번째 안전망이에요. 그 두 번째 안전망도 기본값에 맡기지 말고 직접 적어 두는 게 좋아요. 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건에서 "중단을 완료로 표시하지 말라"고 했던 것과 같은 이야기예요.

나쁜 선택 vs 좋은 선택 — 간 맞추기 반복을 설계할 때

같은 주방에서, 검수대가 싱거운 요리를 화구로 되돌리는 반복을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 검수대에서 화구로 돌아가는 선만 긋고, 끝나는 조건은 "간이 맞으면" 하나만 뒀어요. 멈추는 건 LangGraph의 기본 상한에 맡겼고요.

무슨 일이 생기나: 소금통이 빈 날엔 간이 영원히 안 맞아요. 지금 langgraph(1.2 이후)의 기본 상한은 10007스텝이라, 간 보기와 소금 넣기를 5천 번씩 되풀이한 뒤에야 GraphRecursionError로 끊겨요. 간 보기가 LLM 호출이었다면 그 요금은 다 나갔고, 중간 결과는 예외와 함께 사라져요. 왜 멈췄는지도 결과에 안 남아요.		 무엇을 했나: 전표에 tries 칸을 두고, 다섯 번을 넘기면 call_chef 노드로 빠지는 정상 출구를 그래프에 그렸어요. recursion_limit은 두 번째 안전망으로만 남겼어요.

무슨 일이 생기나: 몇 번 만에 끝나든 결과가 정상적으로 돌아오고, result 칸에 "셰프 호출"이 남아서 덜 끝났다는 사실이 드러나요. 상한을 올릴지, 재료를 바꿀지 판단할 재료가 생겨요.

이 글에 나온 숫자 — 글을 덮은 뒤에도 쓸 것

이 편에서 다른 코드를 짤 때도 그대로 쓰이는 숫자만 모아 뒀어요. 예제가 몇 바퀴 돌았는지 같은 실행 기록은 본문에 있는 그대로가 전부라 여기 옮기지 않았어요. 둘 다 버전을 타는 숫자라, 코드가 설명대로 안 움직이면 여기부터 보면 돼요.

함께 읽으면 좋은 글

  • 다음에 어느 코드가 실행될까 — LangGraph와 워크플로·에이전트 — 이 편의 세 낱말이 어디서 나왔는지, 왜 이 도구인지를 다룬 앞 편이에요.
  • 파이썬 코드 눈으로 읽기 — 이 편의 코드가 낯설 때 먼저 보면 좋은 글이에요.
  • 코딩 에이전트에게 흐름을 맡기고, IF 노드로 갈림길 만들기 — 규칙으로 가르는 갈림길을 n8n 화면에서 만든 글이라, 이 편의 조건부 엣지와 나란히 보면 좋아요.
  • 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건 — "중단을 완료로 표시하지 말라", 즉 반복의 정상 출구를 설계하는 이야기를 먼저 다룬 글이에요.
  1. 부분 업데이트(partial update) — 노드가 State 전체가 아니라 바꾼 칸만 돌려주면 LangGraph가 나머지 칸은 그대로 두고 합쳐 주는 방식이에요. ↩
  2. 라우터 함수 — State를 읽고 다음에 갈 노드의 이름(또는 라벨)만 돌려주는 함수예요. ↩
  3. TypedDict — 딕셔너리에 어떤 이름의 칸이 어떤 자료형으로 들어가는지 미리 적어 두는 파이썬 타입 힌트 문법으로, 칸을 실제로 만들거나 기본값을 채워 주지는 않아요(합치기 규칙 확인하기에서 직접 확인해요). ↩
  4. 트레이스백(traceback) — 에러가 났을 때 파이썬이 그 지점까지 거쳐 온 함수 호출 경로를 차례로 적어 보여 주는 기록으로, 맨 아래 줄이 실제로 일어난 에러예요. ↩
  5. KeyError — 딕셔너리에 없는 키를 d["키"]처럼 대괄호로 꺼내려 할 때 파이썬이 내는 에러예요. ↩
  6. Mermaid — 글자로 적은 도형 설명을 다이어그램으로 그려 주는 문법으로, GitHub나 Notion에 붙여 넣으면 바로 그림이 돼요. ↩
