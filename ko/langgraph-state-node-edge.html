LangGraph는 LLM 앱이 일하는 순서를 공용 메모(State)·작업 칸(Node)·이동 선(Edge) 세 가지로 그려 두면 그 그림대로 실행해 주는 파이썬 프레임워크다.

오늘부터 "에이전트 팀 꾸리기"라는 새 모듈이 시작됐어요. 첫 주제가 LangGraph였는데, 솔직히 이름을 처음 봤을 때는 이미지 생성할 때 쓰는 ComfyUI랑 헷갈렸어요. 둘 다 "노드를 선으로 잇는다"는 말이 나오거든요. 제 기록을 뒤져 보니 LangGraph는 멀티 에이전트 실험 때 후보로만 검토하고 쓰지 않았던 도구였어요.

이번 편에서는 LangGraph가 무엇이고 어디 집 식구인지, 그리고 그래프를 만드는 세 가지 재료와 도구 루프까지를 다뤄요. 흐름의 대표적인 모양 다섯 가지는 다음 편에서 이어서 봅니다.

먼저 낱말 정리 — 에이전트와 워크플로

"에이전트"라는 말은 사람마다 떠올리는 게 달라요. 강의는 칩 후옌(Chip Huyen)과 Anthropic의 정의를 합쳐서 이렇게 잡았어요. 목표를 받으면 스스로 계획을 세우고, 행동하고, 그 결과를 보고 다음 행동을 정하는 LLM 시스템. 여기에 세 가지 재료가 있어요.

  • 환경 — 데이터베이스, 외부 API, 파일처럼 에이전트가 건드릴 바깥세상.
  • 행동 — 환경에 손을 대는 수단이에요. 실무에서는 도구(tool)라고 불러요. 에이전트가 할 수 있는 일의 한계는 쥔 도구 목록이 정해요.
  • 계획 — 어떤 도구를 어떤 순서로 쓸지 정하는 판단이에요.

그런데 여기서 중요한 질문이 하나 남아요. 그 순서는 누가 정하나요? "조회하고, 판단하고, 답을 써라"를 개발자가 코드에 박아 두면 워크플로1, 매 단계 LLM이 스스로 고르게 두면 좁은 뜻의 에이전트예요. 이 기준은 자동화·워크플로·에이전트, 뭐가 다를까에서 내비 경로와 자율주행에 빗대 처음 다뤘던 것과 같아요.

Anthropic은 "가장 단순한 방법으로 시작하고, 자율성이 꼭 필요하다는 증거가 있을 때만 복잡도를 더하라"고 권해요. 정해진 길을 따르면 결과를 예측할 수 있고, 비용을 통제할 수 있고, 틀렸을 때 어디가 틀렸는지 바로 찾을 수 있으니까요.

모든 그래프의 노드 하나하나는 증강된 LLM2이라고 보면 이해가 쉬워요. LLM 본체에 검색·도구·메모리가 붙은 한 덩어리요. 붙이는 도구는 크게 셋이에요.

도구 종류하는 일주의할 점
지식 증강실제 DB나 문서를 찾아 와서 모델이 모르는 최신 정보를 채워요 (RAG가 대표예요)없는 걸 지어내는 할루시네이션3을 줄이는 게 목적이에요
메모리이전 대화를 요약하거나 찾아서 다시 꺼내요컨텍스트 창이 유한해서 필요해요
환경 변경메일 보내기, 결제 취소처럼 바깥세상을 진짜로 바꿔요되돌리기 어려우니 사람의 승인(HITL4) 같은 안전장치가 필요해요

강의가 짚어 준 설계 원칙 한 줄이 기억에 남아요. LLM이 약한 계산과 정밀 작업은 코드에 맡기고, LLM은 "언제 어떤 코드를 부를지" 판단하는 데 집중시킨다. 달력 계산이나 단위 변환 같은 단순한 함수도 훌륭한 도구가 되는 이유예요.

LangGraph는 어느 집 식구인가 — LangChain·LangSmith

강의 코드를 보면 import 줄에 langchain_과 langgraph가 섞여 나와요. 둘은 경쟁 관계가 아니라 같은 회사(LangChain Inc.)가 역할을 나눠 만든 제품이에요.

이름맡은 일이 글에서 쓰는 곳
LangChain부품 — 모델 연결, 메시지 형식, 도구 정의, 문서 로더, 벡터스토어ChatOpenAI, @tool
LangGraph배선 — 부품을 어떤 순서로 돌릴지, 분기·반복·상태StateGraph, ToolNode
LangSmith관측 — 실행 기록과 평가를 보여 주는 웹 서비스다음 편에서 켜 봐요

LangChain은 프롬프트 세 경로 직접 실행해보기에서 메시지 객체를 넘기는 모습으로 한 번 봤어요. 초기 LangChain의 "체인"은 prompt | model | parser처럼 한 줄로만 흐르는 파이프라인이었어요. 되돌아가는 반복이나 갈림길, 중간 상태 저장에 약해서 2024년에 LangGraph가 따로 나왔고, 지금은 LangChain의 에이전트 기능도 속으로는 LangGraph 위에서 돌아가요.

패키지 이름이 여러 개인 이유도 이거예요. 기본 자료형은 langchain-core, 모델 회사별 연결은 langchain-openai·langchain-anthropic·langchain-google-genai, 외부 서비스 연동 모음은 langchain-community에 들어 있어요. 한 가지 주의할 게 있어요. 옛날 자료에 나오는 LLMChain, AgentExecutor, initialize_agent는 1.0부터 langchain-classic이라는 별도 패키지로 빠졌어요. 검색해서 찾은 코드가 import 에러를 내면 버전부터 의심해 보세요.

그럼 수많은 프레임워크5(CrewAI, AutoGen, Claude Agent SDK…) 중에 왜 LangGraph였을까요. 강의가 든 이유는 셋이에요. 특정 모델 회사에 묶이지 않고, 흐름을 블랙박스로 감추지 않고 State·Node·Edge로 개발자가 직접 그리게 하고, 환경 변수 몇 줄로 LangSmith 관측을 붙일 수 있다는 점이요.

여기서 제 기록 하나를 고쳐 적어야겠어요. 멀티 에이전트 실험 때는 "LangGraph를 쓰면 다음 행동을 누가 정하는지가 프레임워크 안에 가려진다"고 보고 Claude Agent SDK를 골랐어요. 막상 배워 보니 직접 그린 그래프는 오히려 그 결정 주체를 선 하나하나로 드러내는 쪽이었어요. 가려지는 건 뒤에 나오는 create_agent 같은 미리 만들어진 부품을 쓸 때예요.

이름 때문에 헷갈리기 쉬운 것들도 정리해 둘게요.

이름정체LangGraph와 다른 점
ComfyUI이미지·영상 생성 AI를 노드 상자로 이어 돌리는 화면 도구 (이미지 생성 도구 고르기의 세계예요)마우스로 이어요. 다루는 대상도 텍스트 LLM이 아니라 그림 생성이에요
n8n노코드 자동화 도구 (IF 노드로 갈림길 만들기)화면에서 그려요. LangGraph는 같은 발상을 파이썬 코드로 써요
GraphRAG문서에서 뽑은 개체와 관계를 지식 그래프로 저장해 검색하는 기법여기서 graph는 지식의 구조예요. LangGraph의 graph는 실행 순서고요. 이 모듈 뒤쪽에서 배워요

비유 — 식당 주방의 주문 전표와 동선표

식당 주방을 떠올려 볼게요. 주문이 들어오면 전표 한 장이 주방을 돌아요. 접수대 직원은 전표에 메뉴를 옮겨 적고, 화구 담당은 조리를 마쳤다고 자기 칸에만 체크해요. 다른 사람이 적은 칸은 건드리지 않아요.

전표가 다음에 어느 조리대로 갈지는 벽에 붙은 동선표가 정해요. "손질대 다음은 화구." 동선표 중간에는 갈림길도 있어요. 검수대 직원이 맛을 보고, 싱거우면 전표를 화구 담당에게 되돌려 보내고, 간이 맞으면 홀로 내보내요. 영업을 시작하기 전에 사장님이 이 동선표를 확정해 둬요.

그리고 이 식당에는 도구 호출 글에서 본 홀 직원도 있어요. 홀 직원이 창고 조회 쪽지를 적어 주방에 넘기면, 쪽지를 실제로 처리하는 건 창고 담당이에요.

비유 속 요소원래 개념
주방을 도는 전표 한 장State — 노드들이 함께 읽고 쓰는 공용 데이터
조리대 직원이 자기 칸에만 체크하기부분 업데이트6 — 노드는 바꾼 키만 돌려주고 나머지는 그대로 남아요
조리대 하나 (접수대·화구·검수대)Node — State를 받아 딕셔너리를 돌려주는 평범한 파이썬 함수
동선표의 화살표 "손질대 다음은 화구"Edge — add_edge(A, B), A가 끝나면 B로
검수대 직원이 전표를 보고 화구 담당에게 되돌리거나 홀로 내보내기조건부 엣지 — 라우터 함수7가 State를 읽고 다음 노드 이름을 돌려줘요
주문 접수 창구 / 홀로 나가는 창구START / END
사장님이 영업 전에 동선표를 확정하기compile() — 설계한 그래프를 실행 가능한 객체로 바꿔요
홀 직원이 적어 주방에 넘기는 창고 조회 쪽지 / 창고 담당이 쪽지대로 조회하기모델이 내놓는 도구 호출 요청(tool_calls) / 그 요청을 실제로 실행하는 ToolNode

핵심 한 줄: 요리를 잘하는 건 조리대(노드)의 몫이고, 전표가 어디로 갈지는 동선표(엣지)가 정해요 — LangGraph는 그 동선표를 코드로 쓰는 도구예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 직원은 동선표에 없어도 눈치껏 옆 조리대를 도와주지만, 그래프는 선이 없는 곳으로는 절대 가지 않아요. 그리고 검수대(라우터)는 다음 목적지를 고르는 일만 해요. 전표에 값을 적는 건 노드가 반환값으로 하는 일이에요.

전체 흐름 — 간 맞추기 그래프 한 장

아래에서 직접 만들 두 번째 예제를 그림으로 먼저 볼게요. 읽는 법: 실선은 앞 노드가 끝나면 항상 지나가는 선이고, 점선은 라우터가 여러 갈래 중 하나만 고르는 선이에요. add_salt에서 taste로 올라가는 실선이 "다시 간 보기", 즉 반복이에요. 반복이 끝나는 출구가 두 개(serve, call_chef)라는 점도 눈여겨보세요.

직접 만들기 ① — LLM 없이 일직선 그래프

개념 설명보다 한 번 돌려 보는 게 빨라요. 먼저 설치예요. 강의 교안은 langgraph 1.2, langchain-core 1.6, langchain 1.4, langchain-openai 1.6에서 검증됐고, 제가 오늘 새로 설치한 버전도 같은 줄기(1.2.11·1.6.2·1.4.0·1.6.2)였어요. 파이썬 코드 자체가 낯설다면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 편해요.

실행: 로컬 터미널 — 가상 환경을 켠 상태에서 한 번만

pip install -U langgraph langchain langchain-openai

첫 그래프는 LLM 없이, 손님이 쉼표로 적은 주문을 메뉴 목록으로 정리하고 접시 수를 세는 두 단계짜리예요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Ticket(TypedDict):          # ① State: 전표에 어떤 칸이 있는지 선언
    order: str      # 손님이 적은 주문 원문
    dishes: list    # 정리된 메뉴 목록
    count: int      # 접시 수
    log: str        # 어느 조리대를 거쳤는지

def take_order(state: Ticket):    # ② Node: 전표를 받아 바꾼 칸만 돌려준다
    dishes = [d.strip() for d in state["order"].split(",") if d.strip()]
    return {"dishes": dishes, "log": state["log"] + " > 접수"}

def count_dishes(state: Ticket):
    return {"count": len(state["dishes"]), "log": state["log"] + " > 집계"}

builder = StateGraph(Ticket)
builder.add_node("take_order", take_order)      # 이름이 곧 엣지의 주소
builder.add_node("count_dishes", count_dishes)
builder.add_edge(START, "take_order")           # ③ Edge: 순서를 잇는다
builder.add_edge("take_order", "count_dishes")
builder.add_edge("count_dishes", END)
graph = builder.compile()

print(graph.invoke({"order": " 김치찌개,  계란말이 ,공기밥 ", "log": "시작"}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

{'order': ' 김치찌개,  계란말이 ,공기밥 ', 'dishes': ['김치찌개', '계란말이', '공기밥'], 'count': 3, 'log': '시작 > 접수 > 집계'}

출력을 세 재료 순서대로 읽어 볼게요.

  • State — Ticket은 TypedDict8로 전표의 칸을 미리 적어 둔 거예요. take_order는 dishes와 log만 돌려줬는데 order가 사라지지 않았죠. LangGraph가 반환된 딕셔너리를 기존 State에 합쳐 주기 때문이에요. 칸이 스무 개로 늘어도 노드는 자기 관심사만 다루면 되니, 노드를 따로 만들고 따로 시험하기 쉬워요.
  • Node — 그냥 파이썬 함수예요. 문자열을 다듬어도, DB를 조회해도, LLM을 불러도, 심지어 다른 그래프를 실행해도 돼요. add_node("이름", 함수)에 적은 이름이 엣지를 이을 때의 주소가 돼요.
  • Edge — START는 입구, END는 출구예요. invoke()에 넘긴 딕셔너리가 첫 State가 되어 START에서 출발하고, END에 닿는 순간의 State 전체가 반환값이에요.

log가 계속 뒤에 붙은 건 노드가 직접 +로 이어 붙였기 때문이에요. 여러 노드가 동시에 같은 칸에 쓰면 이 방식이 깨지는데, 그 문제와 해결책(리듀서)은 다음 편 병렬화에서 봐요.

직접 만들기 ② — 갈림길과 되돌아가는 선

실제 시스템은 일직선으로 끝나지 않아요. "간이 맞으면 내보내고, 싱거우면 소금을 넣고 다시 맛본다" 같은 갈림길이 필요하죠. 위 흐름 그림을 그대로 코드로 옮기면 이래요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Pot(TypedDict):
    salt: int       # 넣은 소금 숟가락 수
    tries: int      # 간을 본 횟수
    result: str

def taste(state: Pot):     return {"tries": state["tries"] + 1}
def add_salt(state: Pot):  return {"salt": state["salt"] + 1}
def serve(state: Pot):     return {"result": "완성"}
def call_chef(state: Pot): return {"result": "셰프 호출"}

def judge(state: Pot) -> str:      # 라우터: 전표를 읽고 다음 노드 이름만 돌려준다
    if state["salt"] >= 3:
        return "serve"
    if state["tries"] >= 5:
        return "call_chef"         # 다섯 번 봐도 안 되면 사람을 부르는 출구
    return "add_salt"

builder = StateGraph(Pot)
for name, fn in [("taste", taste), ("add_salt", add_salt),
                 ("serve", serve), ("call_chef", call_chef)]:
    builder.add_node(name, fn)
builder.add_edge(START, "taste")
builder.add_conditional_edges("taste", judge, ["serve", "add_salt", "call_chef"])
builder.add_edge("add_salt", "taste")      # 되돌아가는 선 = 반복
builder.add_edge("serve", END)
builder.add_edge("call_chef", END)
graph = builder.compile()

print(graph.invoke({"salt": 0, "tries": 0}))
print(graph.get_graph().draw_mermaid())    # 그래프 구조를 글자 도식으로

개념 설명용 코드 — 제 화면에 찍힌 출력에서 결과 줄과 화살표 줄만 옮겼어요

{'salt': 3, 'tries': 4, 'result': '완성'}

__start__ --> taste;
add_salt --> taste;
taste -.-> add_salt;
taste -.-> call_chef;
taste -.-> serve;
call_chef --> __end__;
serve --> __end__;

add_conditional_edges(출발 노드, 라우터 함수, 목적지 목록)이 핵심이에요. taste가 끝나면 judge()를 부르고, 돌려받은 문자열을 노드 이름으로 보고 그리로 가요. 간을 네 번 보고 소금을 세 번 넣은 뒤 serve로 빠졌네요.

  • 목적지를 딕셔너리로도 줄 수 있어요. {"통과": "serve", "보류": "add_salt"}처럼 주면 라우터가 한국어 라벨을 돌려주고 LangGraph가 노드 이름으로 번역해 줘요. 노드 이름은 영문으로, 라벨만 한국어로 두는 절충이에요.
  • 조건부 엣지 하나로 분기와 반복을 다 만들어요. 이미 지나온 노드로 돌아가는 선을 그으면 그게 반복이에요.
  • 그림으로 확인하기. draw_mermaid()는 Mermaid9 문법 글자를 돌려줘요. -->는 실선(항상 가는 길), -.->는 점선(조건에 따라 고르는 길)이에요. 목적지를 리스트로 줘서 라벨이 노드 이름과 같으면 화살표 라벨이 생략되고, 딕셔너리로 다른 라벨을 주면 화살표 위에 라벨이 찍혀요. draw_mermaid_png()는 그림 파일로 바로 그려 주지만, 기본 설정은 외부 렌더링 서비스를 부르니 인터넷이 필요해요.

반복에는 늘 따라오는 위험이 있어요. 끝나지 않을 수 있다는 거예요. judge가 항상 "add_salt"만 돌려주게 바꾸고 graph.invoke(입력, {"recursion_limit": 6})으로 돌려 보니, 여섯 스텝에서 GraphRecursionError가 나며 멈췄어요. LangGraph는 기본으로 25스텝에서 이렇게 끊어 줘요. 다만 이건 예외로 멈추는 거라 그때까지 만든 중간 결과를 못 받아요. 그래서 위 코드처럼 tries를 세다가 call_chef로 빠지는 정상 출구를 그래프 안에 두는 게 기본이고, recursion_limit은 그 설계가 실패했을 때를 대비한 두 번째 안전망이에요. 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건에서 "중단을 완료로 표시하지 말라"고 했던 것과 같은 이야기예요.

직접 만들기 ③ — 도구를 쥐여 주는 루프

이제 진짜 LLM을 넣어요. 여기서부터는 OpenAI API 키10가 필요해요. 키를 넣는 방법은 세 가지예요.

  • 내 컴퓨터 — 프로젝트 폴더의 .env 파일에 OPENAI_API_KEY=sk-...를 적고 from dotenv import load_dotenv; load_dotenv()로 읽어요. .env는 절대 깃에 올리지 않아요 (AI 코드 보안 기초에서 다룬 비밀 관리 그대로예요).
  • Colab — 왼쪽 열쇠 아이콘(보안 비밀)에 등록하고 google.colab.userdata로 읽어요.
  • 임시 — os.environ["OPENAI_API_KEY"] = "sk-..."로 직접 넣어요. 노트북 파일에 키가 그대로 남으니 저장하거나 공유하기 전에 꼭 지워요.

도구는 함수에 @tool을 붙여 만들어요. 여기서 제일 중요한 건 독스트링11이에요. LangChain이 독스트링과 타입 힌트를 읽어 JSON 스키마12를 만들고, 모델은 우리 파이썬 코드가 아니라 이 스키마만 봐요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요 (호출마다 요금이 조금 나가요)

from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

@tool(parse_docstring=True)
def get_recipe(dish: str) -> str:
    """요리 한 접시에 들어가는 재료와 양을 알려 준다. 만들 수 있는지 답하기 전에 먼저 호출한다.

    Args:
        dish: 요리 이름. 예: "계란말이"
    """
    return {"계란말이": "계란 3개", "두부조림": "두부 1모"}.get(dish, "레시피 없음")

@tool(parse_docstring=True)
def check_stock(item: str) -> str:
    """창고에 재료가 몇 개 남았는지 조회한다.

    Args:
        item: 재료 이름. 예: "계란"
    """
    return f"{item} {({'계란': 4, '두부': 0}).get(item, 0)}개"

TOOLS = [get_recipe, check_stock]
llm = ChatOpenAI(model="gpt-4o-mini").bind_tools(TOOLS)   # 모델에게 메뉴판을 건넨다

def agent(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(TOOLS))                 # 요청서를 실제로 실행하는 노드
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)   # tool_calls가 있으면 "tools", 없으면 END
builder.add_edge("tools", "agent")                        # 결과를 들고 다시 모델에게
graph = builder.compile()

result = graph.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})
for m in result["messages"]:
    m.pretty_print()

한 줄씩 짚어 볼게요.

  • parse_docstring=True — 이걸 빼면 독스트링의 Args: 설명이 스키마에 안 들어가요. 성실하게 써 두고도 모델에게 전달이 안 되는 셈이라 꼭 확인할 값이에요. 제 컴퓨터에서 get_recipe의 스키마를 찍어 보니 "dish": {"description": "요리 이름. 예: \"계란말이\"", "type": "string"}처럼 타입 힌트는 type이, Args:는 description이 돼 있었어요.
  • MessagesState — messages 칸 하나짜리 미리 만들어진 State예요. 새 메시지가 오면 덮어쓰지 않고 뒤에 쌓이게 설정돼 있어서 대화 기록을 따로 관리할 필요가 없어요.
  • bind_tools는 도구를 실행하지 않아요. 모델 응답의 tool_calls 칸에 "이 도구를 이 값으로 불러 달라"는 요청만 담겨요. 실제 실행은 ToolNode가 하고, 결과를 ToolMessage로 메시지 목록에 붙여요.
  • tools_condition — 마지막 메시지에 tool_calls가 있으면 "tools"를, 없으면 END를 돌려주는 미리 만들어진 라우터예요.

실행하면 이런 순서로 흘러가요. 사용자 질문을 받은 모델은 답 대신 레시피와 재고를 알려 달라는 도구 요청을 내놓고(모델에 따라 두 개를 한 번에 요청하기도, 하나씩 부르기도 해요), ToolNode가 두 함수를 실행해 "계란 3개", "계란 4개"를 붙이고, 다시 불려 온 모델이 그걸 읽고 "한 접시만 가능하다"는 최종 답을 써요. 더 부를 도구가 없으니 tools_condition이 END를 돌려주고 끝나요.

강의 실습에서도 똑같은 장면이 나왔어요. 노트 조회 도구와 출제 가능 판정 도구를 쥐여 주고 "이 노트로 문제를 낼 수 있나" 물었더니, 모델이 먼저 조회를 불러 208자·4문장이라는 값을 받고, 그 숫자를 그대로 판정 도구의 인자로 넣었어요. 개발자가 "조회한 뒤 판정하라"고 코드에 순서를 박지 않았는데도요. 이렇게 관찰과 행동을 번갈아 하며 다음 행동을 스스로 정하는 게 ReAct13 루프예요. 도구 결과라는 확실한 기준을 받아 오니 모델 기억에만 기대는 것보다 지어낼 여지가 줄어들어요.

이 agent ↔ tools 루프는 너무 자주 쓰여서 한 줄짜리 부품도 있어요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요, 위 코드의 TOOLS를 그대로 써요

from langchain.agents import create_agent

agent = create_agent("openai:gpt-4o-mini", tools=TOOLS)
agent.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})

이 부품의 draw_mermaid()를 찍어 보면 노드 이름만 model·tools로 다를 뿐, 손으로 조립한 것과 같은 모양이었어요. 그럼 왜 굳이 손으로 만들었을까요. 실무에서는 도구 호출 횟수에 상한을 두거나, 특정 도구를 부르기 전에 사람의 승인을 받는 식으로 흐름을 고치고 싶어져요. 단순한 도구 루프 하나면 create_agent, 흐름을 통제해야 하면 직접 그리는 쪽이 유리해요.

나쁜 선택 vs 좋은 선택 — 간 맞추기 반복을 설계할 때

같은 주방에서, 검수대가 싱거운 요리를 화구로 되돌리는 반복을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 검수대에서 화구로 돌아가는 선만 긋고, 끝나는 조건은 "간이 맞으면" 하나만 뒀어요. 멈추는 건 LangGraph의 기본 상한(25스텝)에 맡겼고요.

무슨 일이 생기나: 소금통이 빈 날엔 간이 영원히 안 맞아요. 25스텝째에 GraphRecursionError로 끊기는데, 그때까지 LLM을 부른 요금은 나갔고 중간 결과는 예외와 함께 사라져요. 왜 멈췄는지도 결과에 안 남아요.		 무엇을 했나: 전표에 tries 칸을 두고, 다섯 번을 넘기면 call_chef 노드로 빠지는 정상 출구를 그래프에 그렸어요. recursion_limit은 두 번째 안전망으로만 남겼어요.

무슨 일이 생기나: 몇 번 만에 끝나든 결과가 정상적으로 돌아오고, result 칸에 "셰프 호출"이 남아서 덜 끝났다는 사실이 드러나요. 상한을 올릴지, 재료를 바꿀지 판단할 재료가 생겨요.

  • 모델 이름 gemini-1.5-flash는 이미 서비스가 끝난 모델이라 지금 쓰는 모델 이름으로 바꿔야 해요.
  • 날씨는 미국 기상청 API를 불러서 미국 지명만 돼요. 지명 변환에는 Google Maps 키도 필요해요.
  • 주석 처리된 MemorySaver·thread_id 줄이 바로 9/22 주제(상태 지속성)예요. 살릴 때는 import 경로를 지금 방식인 langgraph.checkpoint.memory로 바꿔야 해요.

직접 해보기

  1. 독스트링 망가뜨리기 — 바꿀 것: get_recipe의 독스트링을 """조회.""" 한 단어로 줄여요(Args:가 없으면 parse_docstring=True가 오류를 내니 함께 지워요). 측정할 것: 같은 질문에 모델이 그 도구를 부르는지, 인자는 맞는지. 비교할 것: 원래 독스트링일 때와 도구 호출 순서. 도구가 안 불리면 프롬프트보다 독스트링부터 의심하는 습관이 생겨요.
  2. 계산을 도구로 빼기 — 바꿀 것: "재고로 몇 접시까지 되는지" 나눗셈을 하는 도구를 하나 더해요. 측정할 것: 재고를 7개, 11개로 바꿔 가며 답이 맞는지. 비교할 것: 같은 질문을 도구 없이 물었을 때 계산이 틀리는 빈도.
  3. 도구 호출 횟수에 상한 걸기 — 바꿀 것: agent 노드에서 메시지 목록의 ToolMessage 개수를 세다가 5개를 넘으면 도구를 붙이지 않은 모델로 마무리하게 해요. 측정할 것: 상한에 걸렸을 때 최종 답에 그 사실이 드러나는지. 이게 create_agent 대신 직접 그리는 이유를 몸으로 느끼는 실험이에요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.

함께 읽으면 좋은 글

  • 자동화·워크플로·에이전트, 뭐가 다를까 — "다음 행동을 누가 정하나"라는 기준을 처음 세운 글이에요.
  • 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동 — 오늘 조립한 루프의 뿌리예요.
  • 도구 하나가 호출되기까지 — 정의·파싱·구조화 요청 — bind_tools와 ToolNode 사이에서 무슨 일이 일어나는지 더 자세히 봐요.
  • 같은 버그를 세 방식으로 — 기준선·워크플로·오케스트레이션 실행 — 같은 기준을 Claude Agent SDK 코드로 비교한 실험이에요.
  1. 워크플로(workflow) — 실행 경로를 개발자가 코드로 미리 정해 둔 LLM 시스템으로, 자동화·워크플로·에이전트 글에서 내비 경로에 빗대 처음 다뤘어요. ↩
  2. 증강된 LLM(augmented LLM) — LLM 본체에 검색·도구·메모리를 붙여 모르는 정보를 가져오거나 바깥세상을 바꿀 수 있게 만든 기본 단위예요. ↩
  3. 할루시네이션(hallucination) — 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 현상이에요. ↩
  4. HITL(Human-in-the-Loop) — 되돌리기 어려운 행동 앞에서 사람의 승인을 받도록 흐름 중간에 사람을 끼워 두는 설계예요. ↩
  5. 프레임워크(framework) — 매번 반복되는 뼈대 코드를 미리 짜 둔 틀이라서, 개발자는 빈칸만 채우면 되는 개발 도구 묶음이에요. ↩
  6. 부분 업데이트(partial update) — 노드가 State 전체가 아니라 바꾼 칸만 돌려주면 LangGraph가 나머지 칸은 그대로 두고 합쳐 주는 방식이에요. ↩
  7. 라우터 함수 — State를 읽고 다음에 갈 노드의 이름(또는 라벨)만 돌려주는 함수예요. ↩
  8. TypedDict — 딕셔너리에 어떤 이름의 칸이 어떤 자료형으로 들어가는지 미리 적어 두는 파이썬 타입 힌트 문법이에요. ↩
  9. Mermaid — 글자로 적은 도형 설명을 다이어그램으로 그려 주는 문법으로, GitHub나 Notion에 붙여 넣으면 바로 그림이 돼요. ↩
  10. API 키 — 유료 AI 서비스를 내 계정으로 부를 때 쓰는 비밀 문자열이라, 남에게 보이면 내 요금으로 남이 쓸 수 있어요. ↩
  11. 독스트링(docstring) — 파이썬 함수 맨 위에 적는 설명 문자열로, LangChain은 이것을 읽어 모델에게 보낼 도구 설명을 만들어요. ↩
  12. JSON 스키마 — 데이터가 어떤 칸과 자료형을 가져야 하는지 적은 규칙서로, 도구 호출 글에서 메뉴판의 '주문 규칙'에 빗댔던 입력 스키마가 이것이에요. ↩
  13. ReAct(Reasoning + Acting) — 생각과 행동을 번갈아 하며 관찰 결과로 다음 행동을 정하는 루프로, ReAct 루프 글에서 그 뿌리를 다뤘어요. ↩
  14. LLM의 답은 확률적이라 같은 질문도 실행할 때마다 도구 호출 순서나 메시지 수가 달라질 수 있어서, 이 값은 강의 실습의 한 번 실행 결과로만 읽어야 해요. ↩
