코딩 에이전트에게 흐름을 맡기고, IF 노드로 갈림길 만들기 (2)

← 이전 편 자동화·워크플로·에이전트, 뭐가 다를까

1편에서는 n8n 화면에서 Manual Trigger와 HTTP Request 두 노드를 직접 선으로 이어봤어요. 이번엔 세 가지를 더 해봤어요. 같은 흐름을 화면 대신 코딩 에이전트에게 맡겨보고, 그 흐름 안에 AI의 판단을 한 조각 끼워보고, 마지막으로 "내 업무는 어디까지 맡겨도 될까"를 판정하는 기준까지 만들어봤어요.

같은 흐름, 이번엔 코딩 에이전트에게 맡겨봤어요

맡긴다는 말은 명령을 대신 실행하는 데서 끝나지 않아요. 결과와 실행 기록을 누가 확인했는지도 함께 정해야 해요. 화면에서 5분쯤 걸릴 일을 에이전트가 30초 만에 끝내도, 그 속도만으로 결과를 믿지는 않았어요.

n8n 화면의 Settings → n8n API에서 API 키를 먼저 발급받아요. 이 키로 워크플로 목록 조회·생성·삭제, 실행 기록 조회를 할 수 있어요. 터미널에서는 설치 없이 npx @n8n/cli로 CLI를 바로 써요.

npx @n8n/cli config set-url https://n8n.vibemakers.kr
npx @n8n/cli config set-api-key <발급한 API 키>
npx @n8n/cli workflow list

공식 스킬을 전역 설치하면 코딩 에이전트가 CLI로 할 수 있는 작업 범위(조회·생성·활성화·실행 기록 확인 등)를 미리 알게 돼요.

npx @n8n/cli skill install --global

여기서 중요한 건 CLI 명령 자체가 아니라, 에이전트에게 요청하는 순서였어요. 한 요청 안에 이 네 단계를 못 박아뒀어요.

  1. 먼저 workflow list로 이 인스턴스에 잘 연결됐는지 확인한다.
  2. Manual Trigger → HTTP Request 흐름의 정의를 wf.json으로 만들되, 생성 명령을 실행하기 전에 JSON의 노드와 연결을 먼저 보여준다.
  3. 확인했다는 답을 받은 뒤에만 workflow create --file=wf.json으로 생성한다.
  4. 생성 뒤에는 실행 기록을 찾아 상태코드와 원 응답을 보여준다.

짧은 JSON 한 줄이 외부로 나가는 진짜 요청으로 이어진다고 생각하면, 그 JSON을 검토하는 순간 은근한 긴장감이 생겨요. 그래서 두 노드의 이름과 URL, 연결을 눈으로 다 확인한 뒤에만 생성을 승인했어요. 생성 뒤에도 화면에서 같은 이름의 워크플로와 실행 기록을 열어 노드와 연결을 다시 대조했고요. CLI에는 새 수동 실행을 시작하는 명령이 없어서, Manual Trigger 워크플로의 첫 실행만큼은 화면에서 눌렀어요. 그다음부터는 execution list와 execution get <실행 ID>로 에이전트가 기록을 찾아 상태코드와 원 응답을 보여줄 수 있었어요.

에이전트는 CLI 호출과 워크플로 생성·조회를 맡고, 저는 생성 결과와 실행 근거를 확인하는 쪽을 맡았어요. 이 구분이 결국 업무를 어디까지 맡길지 판단하는 근거가 됐어요.

한 걸음 더: n8n은 CLI 말고 MCP 서버도 제공해요. 인스턴스 설정에서 켜면 execute_workflow·test_workflow로 워크플로 실행까지 에이전트에게 맡길 수 있어요 — CLI엔 새 수동 실행을 시작하는 명령이 없다는 앞의 한계와 대비되는 부분이에요. MCP 연결의 구체적인 절차는 이 글에서 다루지 않았어요.

워크플로 안에 판단을 한 조각 끼워봤어요 — AI Agent 노드

화면에서 만든 HTTP Request 흐름 뒤에 AI Agent 노드를 연결했어요. 이 노드가 도구를 부르고 결과를 되돌려받는 방식은 에이전트가 도구를 쥔다는 것 — 모델·하네스·루프에서 다룬 하네스 구조와 같은 그림이에요. 이 노드에는 두 가지를 따로 연결해요. Chat Model은 도구가 가져온 정보를 바탕으로 문장을 만드는 역할이고, Tool(여기선 앞서 만든 HTTP Request 흐름)은 모델이 아직 모르는 사실을 읽어오는 역할이에요. 이 둘을 구분해두면, AI가 새 사실을 찾은 순간과 이미 받은 사실의 형식만 바꾼 순간을 구별할 수 있어요.

첫 질문은 도구 없이는 답할 수 없는 걸로 골랐어요. "N8n 문서의 제목과 설명은 무엇인가"라고 물으니, 모델이 공개 API의 원 응답에서 title과 description을 읽어와 답했어요. 실행 기록에는 도구 호출과 그 결과가 그대로 남아서, 답변의 근거가 어디서 왔는지 되짚을 수 있었어요.

이어서 "방금 받은 제목과 설명을 한 문장으로 정리해 줘"라고 물었어요. 이건 이미 받은 정보를 새 문장으로 바꾸는 요청이라, 새 사실을 찾을 이유가 없었어요. 실제로 같은 대화 맥락에서는 새 도구 호출이 생기지 않았고요. 두 답변 다 그럴듯해 보이지만, 하나는 정보를 가져온 답변이고 하나는 표현만 바꾼 답변이라 서로 다른 일을 하고 있었던 거예요.

IF 노드 vs AI Agent 노드 — 언제 뭘 쓸까

여기까지는 입력이 들어오면 항상 같은 순서로 노드를 실행했어요. 실제 업무에서는 받은 값의 상태에 따라 다음 행동이 달라져야 할 때가 있어요. n8n의 IF 노드는 정해진 조건을 검사해서 실행 경로를 true/false로 나눠줘요.

HTTP Request와 AI Agent 사이에 IF 노드를 끼워, "응답에 title과 description이 모두 있는가"를 조건으로 걸어봤어요.

HTTP Request
  ↓
IF: title과 description이 모두 있는가?
 ├─ true  → AI Agent → 한 문장 요약
 └─ false → 확인 필요 기록 또는 담당자 검토

이 분기는 AI의 판단이 아니에요. 같은 입력에는 언제나 같은 결과를 내는, 명시적인 규칙이에요. 필드가 비어 있는지, 상태코드가 200인지, 점수가 기준 이상인지처럼 조건을 정확히 표현할 수 있을 때는 IF 노드가 알맞아요. 실행 기록에서도 어떤 조건이 참이었고 어느 경로가 실행됐는지 그대로 확인할 수 있고요. 반대로 입력 문장의 의도를 해석하거나, 지금 정보로 답할 수 있는지 스스로 판단하고 필요한 도구를 골라야 하는 일에는 AI Agent 노드가 맞아요.

구분IF 노드AI Agent 노드
판단 기준미리 작성한 조건입력의 의미와 현재 맥락
같은 입력의 결과항상 같은 경로로 분기모델·도구 결과에 따라 달라질 수 있음
알맞은 업무값·상태·수치 검사의도 해석·도구 선택·요약
확인할 기록조건 결과와 실행 경로도구 호출, 도구 결과, 최종 답변

둘은 서로를 대신하지 않아요. 그래서 실제 흐름에서는 명시적인 부분은 IF 노드에, 해석이 필요한 부분은 제한된 도구를 가진 AI Agent에 나눠 맡기고, 실행 기록에서 분기 조건과 도구 호출을 함께 확인해요. 그래야 무엇이 규칙에 따른 결과이고 무엇이 AI의 판단에 따른 결과인지 구별할 수 있어요.

범용성은 에이전트에게 모든 권한을 주는 데서 생기지 않아요. 허용된 도구 안에서 다음 행동을 선택할 수 있게 하는 데서 생겨요. 처음에는 공개 데이터를 읽기만 하는 도구만 연결하고 호출 횟수와 처리 범위를 작게 제한했어요. 발송·수정·삭제처럼 외부 상태를 바꾸는 도구가 필요하다면, 사람의 승인이나 별도의 IF 조건을 통과한 뒤에만 실행하도록 경계를 둬야 해요.

내 업무, 도입할까 보류할까 거절할까

화면·CLI·에이전트에서 같은 흐름의 실행 기록을 본 경험을 업무 판단으로 옮기려면, 도구의 인상이 아니라 관찰한 사실에서 선택을 시작해야 해요. 중요한 건 무엇을 맡길지뿐 아니라 어디까지 맡기고 무엇을 계속 확인할지도 함께 정하는 일이에요.

  • 도입 — 필요한 기능·책임 범위·확인 절차가 업무 조건 안에서 확인됐을 때.
  • 보류 — 쓸모는 보이지만 안전성·권한·운영 조건처럼 아직 확인하지 못한 사실이 남았을 때.
  • 거절 — 확인한 위험이나 비용이 업무 목적과 맞지 않아, 현재 조건에서는 맡기지 않기로 정했을 때.

이걸 한 쪽짜리 판정문으로 적어봤어요. 안전하게 쓰고 평가하기 — 권한·회귀·과제 제출에서 다룬 평가 기준과 같은 결의, "도구를 켜기 전에 뭘 확인했는지 남긴다"는 생각이에요. 검토할 업무는 한 문장으로, 확인한 사실과 미확인 사실은 분리해서 적어요.

항목판정문 예시
검토할 업무매일 오전 공개 API에서 정보를 읽어 담당자용 세 줄 요약을 만든다
확인한 사실실행 기록에 상태코드와 원 응답이 남는다
미확인 사실데이터 보관 위치, 쓰기 권한 범위
판정보류
재검토 조건운영 환경과 보관 위치를 확인하면 다시 검토

"고객 지원 자동화"처럼 뭉뚱그려 쓰면 입력과 확인 범위가 넓어져요. "매일 오전 새로 들어온 공개 문의를 읽고 담당자가 확인할 세 줄 요약을 만든다"처럼 좁혀 쓰면 읽는 대상, 결과를 받는 사람, 사람이 확인하는 지점이 드러나요. 같은 업무라도 어떤 경우엔 실행 기록만으로 충분한 근거가 되지만, 다른 경우엔 보관 위치나 권한 범위가 먼저 확인돼야 해요. 그 차이는 도구를 좋아하는 정도가 아니라 무엇을 관찰했고 무엇이 아직 비어 있는지에서 나와요. 그래서 판정문은 결론만 적는 문서가 아니라, 관찰 근거의 차이를 비교하는 기록이 돼요.

1편의 비유를 다시 가져오면, 화면에서 흐름을 만드는 건 내비게이션 지도를 그리는 일이었고, 그 지도를 코딩 에이전트에게 맡기는 건 지도를 대신 그려줄 사람을 고용하는 일에 가까웠어요. 고용한 사람이 아무리 빨라도, 지도를 그리기 전에 보여달라고 하고 다 그린 뒤에도 제가 직접 대조하는 절차는 그대로 남겨뒀어요. 맡기는 범위가 넓어질수록 확인 지점도 같이 늘려야 한다는 1편의 결론이, CLI로 위임하고 IF/AI Agent 노드를 나눠 쓰고 판정문을 쓰는 이 모든 과정에 그대로 이어졌어요.
