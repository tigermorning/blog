PRD를 건네는 것부터 — 코드를 쓰기 전에 정할 것

이번에는 완성된 앱의 코드를 따라 치지 않아요. PRD1를 코딩 에이전트에게 넘기고, 내 선택에 맞는 앱을 함께 만들어요. 건네는 건 앱이나 실행 프로그램이 아니라 설계 문서 묶음이에요. 코딩 에이전트에서 이 묶음을 푼 폴더를 열고 PRD.md부터 읽게 해요. 다만 PRD를 건넸다고 앱이 저절로 완성되지는 않아요. 실제 조사와 이미지 생성까지 연결해 실행해 봐야 해요.

PRD가 요구하는 흐름은 지난 편의 일곱 단계예요. 단순히 문구를 한 번 만들어 보여 주는 화면과 다른 점이 하나 있어요. 사용자가 자료나 방향을 고르는 자리에서는 작업을 멈춰서 기다리고, 답을 받은 뒤 앞선 제작을 이어 가야 해요.

첫 요청은 짧게 시작해요. 아래 요청은 PRD를 끝까지 읽게 하고, 아직 정하지 않은 것을 구현 전에 먼저 묻게 해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — PRD.md가 들어 있는 폴더를 연 상태에서

PRD.md를 끝까지 읽고 이 카드뉴스 앱을 함께 만들어 줘. 구현하기 전에 아직 정하지 않은 것을 2~3개씩 물어봐 줘. 선택지마다 추천과 이유를 보여 주고, 내가 답한 결정은 DECISIONS.md에 기록해 줘.

첫 질문에서 정하는 건 구현 언어(Python·TypeScript·Rust 중 내가 다루고 싶은 것)와 실행 엔진2, 검색 수단을 내 계정에서 실제로 쓸 수 있는지, 카드 비율, 결과를 보관할 위치예요. 잘 모르겠으면 이렇게 선택지별 차이를 설명하게 해요.

작은 흐름부터 연결하기

결정을 기록했다면 화면과 서버의 연결부터 확인해요. 웹 화면은 서버에 API3로 요청해요. 예를 들어 주제를 보내면 프로젝트가 만들어지고, 조사를 시작하면 작업 ID가 돌아오고, 화면은 그 ID에 해당하는 진행 상태를 보여 줘요. PRD 속 API 표는 초안이라서, 코딩 에이전트가 고른 언어에 맞게 입력·출력과 오류를 API_SPEC.md에 다시 정리하게 해요.

그다음 순서는 한 번에 완성을 요청하지 않고 작은 흐름을 실행해 보고, 관찰한 문제를 다음 요청에 담는 것이에요(지시 → 생성 → 판단 → 재지시의 반복이에요).

  1. 화면 연결 — 주제 입력, 후보 선택, 질문 답변까지만 먼저 만들고 모의 데이터4를 화면에 보여 줘요. 서버를 켠 뒤 브라우저에서 안내받은 주소(기본은 http://127.0.0.1:8765, 포트가 이미 쓰이면 안내받은 다른 포트)를 열어요.
  2. 실제 엔진 연결 — 실제 조사와 '답변 뒤 이어 가기'를 연결해요.
  3. 제작 연결 — 이미지는 별도 작업자로 한 장을 실제로 만들어 파일을 열어 본 뒤 전체 카드로 넓혀요.
  4. 수정·내보내기 — 글자 배치, 부분 수정, 내려받기를 연결하고 ACCEPTANCE.md의 조건을 하나씩 확인해요(완료 조건을 미리 적어 두는 방식이에요).

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 1번 단계, 결정을 DECISIONS.md에 기록한 뒤

비유 — 주문서에 '손님 답변 대기' 도장 찍기

이 시리즈는 비유를 하나만 써요. 지난 편에서 세운 식당 주방 그대로예요. 손님은 카드뉴스를 만드는 사용자이고, 받는 사람은 그 카드뉴스를 읽을 사람이에요.

주방이 요리하다가 손님에게 물어야 할 일이 생겼어요. "이 도시락을 받으실 분이 누구예요?" 주방은 질문과 선택지를 적고 주문서에 '손님 답변 대기' 도장을 찍은 뒤, 그 접시에는 손대지 않고 기다려요. 손님이 자리를 비워도 주문서에 질문과 지금까지 한 일이 적혀 있으니 괜찮아요. 손님이 답하면 도장을 '조리 중'으로 바꾸고 같은 주문서로 이어서 요리해요. 정전이 나면 요리사 머릿속에 있던 진행 상황은 사라지지만, 주문서에 적힌 건 남아서 거기서부터 다시 시작할 수 있어요.

핵심 한 줄: 기다리는 동안 요리사의 기억이 아니라 주문서가 일을 붙잡고 있어야, 손님이 몇 시간 뒤에 답해도 같은 요리를 이어 갈 수 있다.

다만 여기서 비유가 끊기는 점이 있어요. 식당에서는 직원이 바뀌어도 새 직원이 주문서를 읽고 이어 가지만, 앱에서는 한 엔진의 세션 ID를 다른 엔진이 쓸 수 없어요. 엔진을 바꾸면 앱이 저장해 둔 자료·선택·현재 원고를 새 엔진의 시작 맥락으로 넘겨야 해요.

실행 엔진 고르기 — 앱 안에서 조사와 원고를 맡길 도구

웹앱이 맡는 일은 주제와 자료를 받고, 진행 상황과 질문을 보여 주는 것이에요. 자료 조사와 카드 원고 작성은 실행 엔진이 맡아요. 사용할 수 있는 하나를 고르면 되고, 셋을 모두 설치하거나 연결할 필요는 없어요. 엔진 연결은 웹 서버가 SDK7를 쓰거나 설치된 CLI8를 실행하는 기능이에요. 브라우저가 직접 명령을 실행하는 구조가 아니에요.

선택앱에서 연결하는 방식앞선 대화를 이어 가는 방식
Claude Agent SDK코드에서 query()를 호출하고 메시지를 받아요저장한 세션 ID를 options.resume에 전달해요
Claude CLI서버에서 claude -p를 실행하고 JSON 결과를 읽어요--resume에 해당 프로젝트의 세션 ID를 전달해요
OpenCode CLI서버에서 opencode run --format json을 실행하고 JSON 이벤트를 읽어요--session에 해당 프로젝트의 세션 ID를 전달해요

고르는 기준은 이래요. SDK는 앱 안에서 질문 처리를 연결하기 좋고, CLI는 익숙한 실행 도구를 서버에서 부르는 방법이에요. 이어 가기에서 조심할 점이 하나 있어요. CLI의 --continue는 가장 최근 세션을 고르기 때문에, 프로젝트가 여러 개면 다른 프로젝트의 대화로 이어질 수 있어요. 그래서 앱이 저장한 명시적인 ID로 이어 가게 해요. 이미지 제작은 이 엔진 선택과 별개로 이미지 작업자(Antigravity CLI)에게 맡기고, 이 단계에서는 이미지 요청과 돌아온 파일을 카드에 연결할 자리만 마련해 둬요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 엔진 이름을 대괄호 자리에 넣어서

실행 엔진을 [Claude Agent SDK]로 연결해 줘. 필요한 질문은 웹에서 답하고 같은 제작을 이어 가게 해 줘. 엔진을 호출하는 부분은 따로 분리해 줘.

연결을 구현한 뒤에는 'AI 최신소식 카드뉴스를 만들어 줘'라는 요청이 내가 고른 엔진으로 실제로 전달되는지까지 확인해요.

질문을 기다리는 상태 — 저장할 것과 두 가지 전달 방식

앱이 보관할 것은 엔진의 답변만이 아니에요. 어느 제작인지, 무엇을 기다리는지, 사용자가 무엇을 골랐는지까지 저장해야 해요. 구체적으로는 카드뉴스 프로젝트와 제작 실행의 ID, 고른 엔진과 세션 ID, 현재 단계, 질문과 선택지, 사용자 답변, 지금까지 만든 원고예요. 그래야 브라우저를 새로고침해도 대기 중인 질문을 다시 보여 줄 수 있어요.

읽는 법: 위쪽 세 상자는 작업의 상태이고 왼쪽에서 오른쪽으로 흘러요. 점선은 그 상태가 바뀔 때마다 아래 저장소에 적는다는 뜻이에요. 맨 아래 두 줄은 화면을 다시 열 때와 서버를 다시 켤 때 무엇이 남는지 적은 거예요.

코딩 에이전트에게는 이 상태 전환을 이렇게 요청해요.

질문이 생기면 제작 상태를 waiting_for_user로 저장하고, 질문과 선택지를 웹 화면에 보여 줘. 답변을 받기 전에는 다음 제작 단계로 넘어가지 마. 답변을 제출하면 같은 제작 실행의 상태를 다시 running으로 바꾸고, 저장해 둔 답변과 엔진 세션을 연결해서 이어 가게 해 줘. 새로고침해도 질문이 남는지, 제출 버튼을 두 번 눌러도 중복 실행되지 않는지 확인해 줘.

질문을 앱으로 끌어올리는 두 가지 방법

SDK와 CLI는 질문을 전달하는 방법이 달라서 구분해 구현해요. 아래는 코딩 에이전트가 구현할 때 확인하는 내용이고, 사용하는 사람은 "내가 고른 엔진의 질문이 화면에 나타나고, 답한 뒤 이어지는가"를 보면 돼요.

  • Claude SDK — SDK에는 사용자에게 질문하는 기능(AskUserQuestion)이 있어요. TypeScript에서는 canUseTool, Python에서는 can_use_tool이라는 콜백9에서 질문을 받아 웹으로 보내요. 사용자가 고른 답을 콜백에 되돌려 주면 대기하던 SDK 실행이 이어져요. 웹 화면과 답변 저장은 여전히 앱이 만들어야 해요. 콜백은 원래 질문과 사용자 답을 SDK가 요구하는 모양으로 반환해야 해서, 고른 언어의 공식 예제를 확인해요.
  • CLI — 앱이 정한 need_input이라는 약속을 써요. 필요한 정보가 없으면 엔진이 "질문이 필요하다"는 구조화된 결과를 돌려주고, 앱이 그걸 검증해 질문 화면으로 바꿔요. 아래는 공식 CLI 필드가 아니라 이 앱에서 정할 수 있는 예시예요.

개념 설명용 코드 — 이 앱이 정할 수 있는 약속의 예시예요. 직접 실행하는 코드가 아니에요

{
  "status": "need_input",
  "question_id": "audience-001",
  "version": 1,
  "question": "누구를 위한 카드뉴스인가요?",
  "options": ["AI 입문자", "업무에 AI를 쓰는 사람"],
  "multi_select": false
}

question_id는 질문이 새로 만들어질 때마다 구분하는 값이고, version은 "어느 버전의 질문에 대한 답인가"를 확인하는 값이에요. 프로젝트 ID와 함께 저장해 두고, 이미 답한 질문이나 지난 버전의 답으로 새 작업을 시작하지 않게 해요.

이 결과를 돌려준 CLI 프로세스는 끝날 수 있어요. 그래도 웹앱은 제작을 완료로 표시하지 않고 waiting_for_user로 남겨 둬요. 사용자가 답하면 저장한 세션 ID로 다음 CLI 호출을 시작하면서 질문과 답을 함께 넘겨요. 같은 제작과 같은 대화를 이어 가는 것이지, 같은 운영체제 프로세스가 계속 살아 있다는 뜻이 아니에요. 두 엔진의 원시 출력은 서로 달라서(Claude CLI는 session_id, OpenCode는 줄마다 이벤트가 나오고 세션 필드가 sessionID, 텍스트는 part.text) 앱은 필요한 내용을 꺼낸 뒤 자기가 정한 need_input 또는 완료 결과로 해석해요. 잘못된 출력을 완료로 처리하면 안 돼요.

CLI 출력 형식을 검사하고, 질문과 답변을 해당 세션의 다음 입력으로 넘겨 줘. 형식이 맞지 않는 출력은 완료로 처리하지 마.

새로고침과 서버 재시작은 다르다

브라우저를 새로고침해도 서버의 작업은 살아 있을 수 있어요. 그런데 서버를 다시 시작하면 메모리에서 기다리던 SDK 콜백은 사라져요. 그래서 앱은 질문·답변·현재 단계를 저장해 두고, 재시작 뒤에는 중단된 상태임을 보여 준 다음 저장된 맥락으로 실행을 재개하거나 다시 시도하게 만들어야 해요. 세션 ID만 저장한다고 화면 상태와 작업이 자동으로 복구되지는 않아요. 이 '멈춘 자리를 저장해 두고 이어 가는' 원리는 HITL 1편의 체크포인터와 같은 생각이고, 껐다 켜도 사라지지 않게 하려면 파일이나 DB에 저장해야 한다는 점도 같아요.

직접 검증하기 — 다섯 가지 상황

코딩 에이전트에게 아래 상황을 다시 만들어 보게 하고, 나도 브라우저에서 직접 확인해요. 인증을 일부러 망가뜨리는 대신 테스트용 모의 오류로 실패 경로를 확인할 수 있어요.

다시 만들 상황기대하는 결과
독자 질문이 나온 뒤 새로고침같은 프로젝트의 질문과 선택지가 남고, 답하기 전에는 제작이 시작되지 않아요
같은 답변을 두 번 제출작업을 한 번만 시작하고, 중복 답변은 다시 실행하지 않아요
이전 질문 화면에서 뒤늦게 답변지난 질문임을 알리고, 현재 작업을 덮어쓰지 않아요
생성 실패 뒤 재시도실패 원인을 보여 주고, 확정한 기획과 성공한 카드 결과는 그대로 둬요
서버를 다시 시작한 뒤 프로젝트 열기저장한 질문·결과가 복원되고, 중단된 작업은 재개하거나 다시 시도할 수 있어요

관찰은 입력·조작 / 기대 결과 / 실제 결과 / 수정 뒤 결과 네 칸으로 남겨요. 모의 오류로 확인한 항목과 실제 엔진으로 확인한 항목은 구별해서 적어요. 연결한 뒤에는 독자를 고르게 하는 요청으로 질문 표시 → 대기 → 답변 → 제작 계속을 확인하고, 프로젝트를 하나 더 열어 질문과 세션이 섞이지 않는지도 봐요.

3. 서버를 다시 시작한 뒤 중단된 작업을 감지해 보여 주는 코드가 있는지

직접 해보기

  1. 질문 뒤 새로고침 — 바꿀 것: 화면 연결 단계(모의 데이터)에서 질문이 뜬 뒤 새로고침해요. 측정할 것: 질문·선택지·고른 후보가 그대로인지. 비교할 것: 저장 항목을 일부러 하나 빼고 다시 해서 무엇이 사라지는지.
  2. 같은 답 두 번 제출 — 바꿀 것: 답 제출 버튼을 빠르게 두 번 눌러요. 측정할 것: 작업이 몇 번 시작됐는지. 비교할 것: 중복 방지를 넣기 전과 후.

정답은 하나가 아니에요. 어떤 엔진을 고르든 위 다섯 상황을 내 앱에서 직접 재현해 보고 결과를 네 칸으로 적는 게 요령이에요.

확인 범위 — 읽은 것과 못 읽은 것

  • 이 글은 PRD를 건네는 순서와 엔진 연결 방식, 질문 전달·재개에 대한 설명 글을 읽고 재구성한 것이에요. 제가 앱을 만들거나 엔진을 연결해 돌려 본 것이 아니에요.
  • SDK·CLI의 호출 방식(query(), options.resume, claude -p --resume, opencode run --format json --session, AskUserQuestion)은 설명 글이 정리한 내용을 옮긴 것이고, 공식 문서를 직접 열어 대조하지는 않았어요. 구현 전에는 고른 엔진의 공식 문서를 확인해요.
  • 설계 문서 묶음(PRD 원문 포함)과 참고 구현의 설치 조건, 실행 검증 기록은 읽지 못했어요.

다음은

3편에서는 이 앱에 'AI 최신소식'을 넣어 실제 카드뉴스 한 편을 만들고 검수하는 기준, 그리고 이 흐름을 내가 자주 하는 작업으로 바꿔 확장하는 법을 다뤄요.

함께 읽으면 좋은 글

  • 멈췄다가 사람 답을 받아 잇는다 — interrupt·resume·체크포인터 (1) — 멈춘 자리를 저장했다가 이어 가는 원리를 코드로 확인한 글이에요.
  • 멈출 기준을 정하고 승인 화면을 설계한다 — 개입률·놓침·헛멈춤 (2) — 대기 건을 보관하고 응답 종류를 늘리는 운영 규칙을 다룬 글이에요.
  • 얇게 한 번 관통시키기 — 첫 구현과 막힌 지점 찾기 (6) — 작은 흐름 하나를 끝까지 관통시켜 막히는 자리를 찾는 방식이에요.
  • 목업 데이터와 REST API — 서버 없이 화면부터 만들 때 쓰는 가짜 데이터를 다룬 글이에요.
  1. PRD(Product Requirements Document) — 만들 앱이 무엇을 해야 하는지 요구사항을 적은 문서로, PRD를 스스로에게 묻는 글에서 처음 다뤘어요. ↩
  2. 실행 엔진 — 완성된 앱이 자료 조사나 원고 작성 같은 AI 작업을 시킬 때 서버가 부르는 도구로, 앱을 만들 때 쓰는 코딩 에이전트와는 역할이 달라요. ↩
  3. API — 웹 화면이 서버에 요청하고 답을 받는 약속된 통로로, API란 무엇인가에서 처음 설명했어요. ↩
  4. 모의 데이터 — 아직 없는 서버 응답과 같은 모양으로 미리 만든 가짜 데이터로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  5. waiting_for_user — 작업이 사용자의 답을 기다리는 중임을 나타내려고 앱이 정해 둔 상태 이름으로, 실행 흐름과 상태에서 다룬 '상태'의 한 종류예요. ↩
  6. 세션 — 앞선 대화와 작업 맥락을 이어 가기 위한 단위이고, 세션 ID는 그 단위를 구별하는 값이에요. ↩
  7. SDK — 내 코드에 연결해 쓰는 개발 도구 묶음이에요. ↩
  8. CLI — 터미널에 명령을 쳐서 실행하는 도구예요. ↩
  9. 콜백 — 어떤 일이 생겼을 때 대신 불러 달라고 미리 맡겨 둔 함수예요. ↩
