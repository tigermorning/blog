분모란 실제로 시도하기로 약속한 문항 수이며, 실행 오류나 미완료가 있다고 줄이지 않는 값이다.

하네스를 고친 뒤 열 문제 중 네 문제를 풀었다고 해 볼게요. 이전엔 세 문제였고요. 개선됐다고 말하고 싶어져요.

그런데 이전 실행에서 모델이 달랐거나, 한 문제는 필요한 로컬 프로그램이 실행되지 않았거나, 새 실행에 시간을 더 줬다면? 무엇이 점수를 바꿨는지 알 수 없어요. 이번 마지막 편은 결과를 정직하게 모으고, 바꾼 부분의 효과만 비교하고, 다시 실행할 수 있는 형태로 제출하는 이야기예요.

비유 — 영수증 잃어버린 가계부

이번 달 가계부를 씁니다. 30일 중 20일치는 영수증이 있고, 10일치는 영수증을 잃어버렸어요.

여기서 두 가지 유혹이 와요. 첫째, 잃어버린 10일치를 0원으로 적는 것이에요. 칸이 비어 있으면 보기 싫으니까요. 그러면 이번 달 지출 총액이 실제보다 훨씬 적게 나와요. 게다가 다음 달과 비교할 때 "이번 달은 아꼈네"라는 사실이 아닌 결론까지 따라옵니다.

둘째, 기록한 20일만 놓고 하루 평균을 내는 것이에요. 20으로 나누면 숫자는 깔끔하죠. 하지만 그건 "영수증이 남은 날의 평균"이지 "이번 달의 하루 평균"이 아니에요.

그리고 비교할 때 함정이 하나 더 있어요. "지난달보다 카드값이 줄었다"고 말하려면 다른 조건이 같아야 해요. 그런데 지난달엔 이사를 했고, 이번 달엔 카드를 바꿨고, 재택근무도 시작했다면? 줄어든 이유를 하나로 지목할 수 없어요.

이번 달 30일분모 — 고정 10문항 (또는 10×반복 횟수)

가계부 첫 장의 "기준: 카드 A, 4인 가구"run-metadata.json — 실행 조건 기록

핵심 한 줄: 모르는 지출을 0원으로 적는 순간, 그 가계부는 이번 달을 설명하지 못해요.

다만 비유가 끊기는 점이 있어요. 가계부는 영수증을 다시 찾으면 채울 수 있지만, 모델이 사용량을 반환하지 않은 실행은 나중에 되살릴 수 없어요. 그래서 '알 수 없음'이 영구적인 기록이 됩니다.

네 가지 상태 — 다 세지만 다 다르게

실행 중에도 결과를 볼 수 있어요. 채점이 끝날 때마다 jobs/실행이름/scoreboard/에 HTML·CSV·JSON이 갱신돼요. 모니터를 켠다고 평가를 다시 실행하거나 채점 파일을 바꾸지는 않아요 — 같은 결과 파일을 따로 읽어 보여 줄 뿐이에요.

이 실행의 점수 모니터를 켜 줘. 아직 안 끝난 문제와 실행 오류도 빠짐없이 보이게 해 줘.

보고서의 kind도 확인해요. 제 하네스의 실행은 agent_evaluation이에요. 개발자가 참고 구현으로 채점 경로를 점검한 grader_self_check 결과가 있다면 그건 별도의 진단 자료이고, 제 에이전트 성능 비교에는 넣지 않습니다.

나쁜 선택 vs 좋은 선택

같은 가계부를 정리하는 두 가지 방식이에요.

나쁜 선택좋은 선택
무엇을 했나: 성공 3, 실패 4, 실행 오류 2, 미완료 1이 나왔어요. 오류 2개는 "제 코드 문제가 아니라 환경 문제"라서 빼고 3/8 = 37.5%로 적었어요.

무슨 일이 생기나: 환경 문제를 지운 채 성능이 올라 보여요. 게다가 다음 실행에서 그 환경 문제가 고쳐지면 분모가 또 달라져서 두 실행을 비교할 수 없게 됩니다.		 무엇을 했나: 분모를 10으로 고정하고 3/10 = 30%로 적었어요. 그리고 오류 2건의 원인을 따로 한 줄씩 기록했고요.

무슨 일이 생기나: 숫자는 낮지만 다음 실행과 그대로 비교돼요. 오류를 고쳐서 다음에 5/10이 나오면, 그 개선이 어디서 왔는지도 기록에 남아 있어요.

원칙은 하나예요. 오류와 실패는 원인이 다르지만, 둘 다 약속한 실행 기회 안에서 성공한 결과는 아니므로 분모에서 빼지 않아요. 그리고 모든 실행이 끝났는데 결과가 없으면 계속 미완료로 숨기지 않고 오류로 표시합니다.

반복 실행을 썼다면 모니터의 --attempts도 같은 값으로 지정해요. 실행 메타데이터와 다르면 분모를 임의로 바꾸지 못하도록 오류가 납니다. 같은 문제에서 예상보다 많은 결과나 중복 시행이 발견되면, 좋은 결과만 골라 쓰지 않고 그 문제를 오류로 표시합니다.

그리고 중간 문제를 풀고 쉬운 문제에서 실패할 수도 있어요. 공식 난도 분류가 모든 모델·환경의 성공 순서를 보장하지는 않아요.

실패한 시행 읽기

점수 표에서 문제를 하나 골랐다면, 그 시행 폴더의 두 파일을 같이 봐요.

  • agent/events.jsonl — 어떤 도구가 언제 성공하거나 실패했는지. (JSONL은 한 줄마다 JSON 기록 하나를 저장하는 형식이에요.)
  • agent/sessions/trial.json — 모델이 어떤 인수를 넣었고 어떤 결과를 받아 다음 행동을 골랐는지.

파일 형식을 외우기보다 개발 도우미에게 "이 시행의 흐름을 설명해 줘"라고 요청해도 돼요. 다만 세션에 남은 도구 결과는 출력 제한을 적용한 뒤의 내용이에요 — 7편의 16,000자 한도가 적용된 거라, 프로세스의 모든 출력이 무제한 보관된 파일이 아니에요.

verifier 폴더의 검사 결과와 대조하면 모델이 주장한 완료와 실제 채점이 어디서 갈렸는지 보여요. 그리고 이 파일들에는 문제 내용이 포함되므로 공개 배포 예제나 다른 평가의 입력에 섞지 않습니다.

하나만 바꾸는 비교 실험

baseline은 기준 실행, improved는 변경한 하네스로 수행할 실행의 이름이에요. 이름을 improved라고 붙였다고 개선이 확인된 건 아니에요.

읽는 법: 아래 그림에서 왼쪽 목록은 두 실행에서 똑같이 유지할 것이고, 오른쪽 하나만 바꿉니다. 왼쪽에서 하나라도 함께 바뀌면 비교가 아니라 다른 실험이 돼요.

가설은 실행 기록에서 나와요. 예를 들어 긴 명령 출력 때문에 다음 행동에 필요한 오류 문장이 묻혔다면, 그 근거를 읽고 출력 전달 방식을 바꾸는 가설을 세울 수 있어요. 반대로 기록에서 그런 손실이 확인되지 않았다면 그 원인을 확정하지 않습니다.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

긴 명령 출력에서 오류 위치를 찾기 어려워 보여. 전달 방식 하나만 바꾸고 같은 조건으로 비교하자.

이 감각은 내 불편을 가설로 — 개선 실험 설계와 제출 (6)과 같아요. 다른 점은 이번엔 고칠 대상이 제 소스코드라는 것이고요.

그리고 원본 solution/이나 숨겨진 채점 코드를 읽어 정답에 맞추는 방식으로 개선하지 않아요. 문제 설명, 하네스가 실제로 수행한 명령과 결과, 공개 가능한 채점 상태를 근거로 일반적인 실패 원인을 찾습니다. 풀이·채점 내용을 보고서나 Skill·프롬프트에 넣으면 평가 결과를 해석할 수 없게 돼요.

제품 기능도 함께 봐요

벤치마크 점수가 제 제품 기능을 증명하지는 않아요. 평가 연결부는 시행별 작업 복사본 안의 파일 변경과 Python 실행을 사전 허용으로 처리하니까요. 3편에서 정한 승인·거절 정책은 별도 기능 검증으로 확인해야 해요.

확인 대상함께 볼 근거구별할 판단
자료 처리원문, 도구가 읽은 내용, 최종 답변읽기 성공 vs 내용 정확성
코드 수정수정 전후 파일, 실제 검사 출력변경 적용 vs 요구 충족

벤치마크문제별 실행 기록과 채점 결과에이전트 주장 vs 독립 판정
개선 효과두 버전의 조건·소스·전체 결과의도한 개선 vs 관찰된 차이

실패를 찾았을 때는 "다시 잘 만들어 줘"라고 요청하기 전에 어디의 약속이 어긋났는지 봐요. 요구가 분명한데 코드가 안 지켰다면 구현 오류고, 요구 자체가 모호했다면 기대 동작부터 정해야 해요.

예를 들어 "거절했는데 파일이 저장된" 상황이라면 이렇게 추적해요. (가정한 예이고, 실제로 이런 결과가 난다는 뜻은 아니에요.)

수정 때문에 다른 동작이 망가지지 않았는지 확인하는 걸 회귀 검사3라고 해요. 거절 처리를 고쳤더니 승인한 변경도 적용되지 않는다면 새 문제가 생긴 거예요. 그리고 벤치마크 점수가 올라도 기존 제품 기능이 깨졌다면 함께 해결하거나 남은 문제로 명시합니다.

또 하나. 요구를 고치는 것과 실패를 숨기는 것을 구별해요. 거절 후 파일을 바꾸는 코드에 맞춰 "거절해도 저장될 수 있다"고 명세를 바꾸면 사용자의 의도를 버린 것이에요. 반면 애초에 필요 없던 재시작 복원을 후속으로 미루기로 정했다면, 그 선택을 기록하고 화면에서도 복원한다고 주장하지 않도록 맞추는 것은 적절합니다.

모르는 것은 모른다고 적기

EXPERIMENT_REPORT.md는 예시 성적표가 아니라 실행 후 채우는 양식이에요. 기준과 개선의 통과·실패·오류·미완료, 시간·토큰·비용을 실제 결과로 채웁니다.

여기서 가계부 비유가 다시 나와요. 토큰이나 비용이 기록되지 않았다면 0으로 쓰지 않고 '알 수 없음'으로 둬요. 보고서는 모든 시행에서 값이 알려졌을 때만 총합을 표시하고, 일부만 알려지면 부분 합계와 관측 수를 함께 보여 줍니다. 가격표로 비용을 추산했다면 공식 청구값과 구별하고 단가·날짜·계산 방법을 적어요.

실행 조건도 함께 기록해요 — 모델 이름, 문제 커밋, manifest 해시, 소스 버전, 실행 한도, 그리고 로컬 이식 경로이므로 운영체제·Python 버전·사용한 패키지와 작업 경로 조건까지요. execution_mode는 local-port, hostlimits는 unrestricted로 남는데, 마지막 값은 "별도의 OS 격리나 CPU·메모리 제한을 적용하지 않았다"는 뜻이지 실행 시간·출력 길이의 프로그램 제한과는 다른 층이에요.

그리고 커밋과 해시가 있다고 모든 환경이 완전히 같다는 뜻은 아니에요. 같은 OS·Python 버전이어도 CPU·메모리·다른 프로그램의 부하가 같다고 보장할 수 없어요. 특히 Ollama를 로컬에서 돌리면 장치 자원의 영향을 받으니, 기기와 동시에 실행한 작업도 실험 기록에 남깁니다.

마지막으로 실제 측정이 없다면 NOT_RUN 또는 '미측정'이라고 정직하게 적어요. 다만 이건 실험을 완료했다는 뜻이 아니에요. 모의 검사만 했다면 실행 가능한 연결을 점검한 단계이고 실제 평가가 남아 있는 거예요. 환경 오류로 막혔다면 어느 단계가 막혔는지 증거와 함께 남기고, 어려운 문제에서 못 푼 실패와 환경조차 실행 못 한 상태를 구분합니다.

이 열 문제로 알 수 있는 것의 한계

같은 열 문제를 보며 반복해서 개선하면, 이 문제들은 개발용 평가 집합의 성격을 갖게 돼요. 이미 개선 판단에 써 버린 문제들이라는 뜻이에요.

그래서 이 안에서 좋아졌다는 결과를 "처음 보는 모든 작업에서도 우수하다"는 결론으로 넓히지 않아요. 일반화 성능을 보려면 개선에 사용하지 않은 문제와 별도 평가 계획이 필요해요. 이번 보고서에는 우선 이 고정된 열 문제에서 확인한 변화와 한계를 충실히 적습니다.

그리고 원본 검증기가 모든 올바른 해법과 잘못된 해법을 완벽히 가른다고 보장하지도 않아요. 검증기에 포함된 사례, 특정 파일 이름·출력 형식에 대한 가정, 검사 범위의 한계가 있어요. 반대로 점수를 올리려고 검증기의 기대값을 수정하거나 참고답안을 에이전트에 제공하면 비교의 의미 자체가 사라집니다. 검증기 결함이 의심되면 원본 실패 기록을 보존하고 별도 이슈로 설명해요.

다시 실행할 수 있는 제출물

다른 사람이 설명만 믿지 않고 직접 실행해 볼 수 있게 실제 소스를 제출해요. 묶을 것은 이래요.

  • 실제 실행 프로젝트와 두 버전의 소스, 의존성 설정·잠금 파일, README.md
  • PRD.md, DECISIONS.md, INTERFACES.md, ACCEPTANCE.md
  • IMPLEMENTATION_PLAN.md와 작성한 EXPERIMENT_REPORT.md
  • 고정 benchmark/tasks.json과 기준·개선의 설정, run-metadata.json
  • 두 실행의 원본 시행 결과와 하네스 실행 기록
  • 두 실행의 10문항 전체를 담은 trials.csv, report.json, index.html
  • 개선 가설, 변경 내용, 좋아진 점과 나빠진 점, 남은 한계

다른 언어로 구현했다면 로컬 평가 어댑터와 실행 방법도 남겨요. 어댑터는 원본 작업 지시·시행별 폴더·실행 한도를 제 프로그램에 전달하고 결과·상태·지표를 평가기 계약으로 돌려주는 연결부예요. 제공된 Python 평가 진입점에서 제 프로그램을 부르는 얇은 연결을 만들어도 되지만, 모델·도구 반복을 수행하는 주체는 제출한 하네스여야 해요. 작업 디렉터리, 종료 코드, 출력 파싱, 시간 초과 때의 정리, 사용량 미관측 처리도 설명하고요. 제 프로그램이 반환한 성공 문구를 독립 pytest의 채점 결과로 대체하지 않습니다.

그리고 제출용 묶음은 실행 폴더 전체를 무조건 압축해서 만들지 않아요.

  • jobs/<실험이름>/source/ 안의 benchmark/upstream/에는 내려받은 원본 문제·자료·풀이·테스트가 들어 있어요. 재현을 위해 로컬에는 그대로 두되, 제출용 복사본에서는 이 원문을 제외합니다. .benchmark-cache/도 제외하고요.
  • 시행별 작업 폴더와 verifier/에도 원본 픽스처나 경로를 옮긴 테스트가 들어갈 수 있으니 같은 기준으로 확인해요.
  • 보존할 것: 제 구현·변경 내용, 시행별 result.json, 하네스 이벤트 기록, 채점 결과 XML·표준 출력·오류 출력, 실행 메타데이터, 집계 보고서.

로그 안에 원본 자료나 정답·검사 코드가 그대로 들어갔다면 제출용 사본에서 그 부분을 가리고 위치와 이유를 남겨요. 다만 원문을 제외한다는 이유로 실패 시행이나 불리한 점수 행을 삭제하지 않습니다.

제출용 파일 목록에는 제외 경로와 이유, 그리고 고정 원본의 주소·커밋·파일 해시와 다시 자료를 준비하는 방법을 적어요. 원본 전체를 포함해 계산한 소스 해시는 정리본의 해시와 다를 수 있으니, 원래 실행 메타데이터를 덮어쓰지 말고 무엇을 제외했는지 따로 설명합니다. API 키·토큰·개인 자료가 기록에 들어가지 않았는지도 마지막으로 확인해요.

기준 실행과 개선 실행을 비교해 줘. 좋아진 문제와 나빠진 문제를 모두 찾고,
코드 변경과 연결되는 근거를 실험 보고서에 남겨 줘.
  1. 바꿀 것 — 실패 기록에서 반복되는 문제를 하나 고르고, 변경 하나를 정해 improved 실행을 돌려요.
  2. 측정할 것 — 두 보고서 모두에 고정 열 문제의 행이 전부 있는지 확인해요. 실패·오류·미완료 행을 삭제해 통과율을 올리지 않고, 시도하지 않은 문제도 빠진 이유와 상태가 드러나야 해요.
  3. 비교할 것 — 점수가 올랐다면 어떤 문제에서 바뀌었는지, 내려갔다면 새 방식이 불리했던 조건을 찾아요. 차이가 작거나 반복 결과가 들쭉날쭉하면 확실한 우월성이라고 단정하지 않습니다.

마지막으로, 처음의 사용자 이야기와 최종 결과를 나란히 놓아 보세요. 사용자가 요청을 넣는 자리, 허용한 작업 범위, 변경을 확인하는 방식, 실패를 보여 주는 방식이 1편에서 적은 요구와 이어지는지요.

이번 과제의 성취는 높은 숫자 하나가 아니에요. 쓸 기능을 명세로 정하고, 실행 결과를 보고 명세와 구현을 조정하고, 무엇을 바꿨고 어떤 조건에서 어떤 결과를 관찰했는지 검증 가능한 형태로 설명하는 것이에요.

그리고 여기서 시리즈가 닫혀요. 이번엔 모델 요청·도구 실행·결과 반환의 반복을 제 소스에서 직접 구현했어요. 다음 단계는 이미 제공되는 실행 엔진(MCP나 에이전트 SDK 같은 것들)을 앱의 구성 요소로 조립하는 쪽이에요. 어느 방식을 쓰든 사용자가 원하는 동작을 실제 근거로 확인하는 책임은 그대로 남습니다.
