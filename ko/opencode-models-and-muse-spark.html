2026. 9. 8.

※ 이 글은 같이 공부하는 분들과 나눈 대화에서 출발해, 공식 문서와 공개된 자료를 직접 확인하고 제 나름의 언어로 정리한 것입니다.

opencode의 모델 목록이 긴 이유는 쓸 수 있는 모델이 수백 개여서가 아니라, 몇 안 되는 모델이 제공자·버전·요금 티어·추론 강도라는 네 축으로 곱해져 나열되기 때문이다.

이 글을 읽기 전에

뭐를 할 수 있나
opencode의 수백 줄짜리 모델 목록을 제공자·버전·요금 티어·추론 강도 네 축으로 나눠 읽을 수 있게 되고, 새 모델이 목록에 안 보일 때 캐시 갱신부터 순서대로 해결할 수 있어요. 무료·저가 요금제가 사실 내 코드를 학습 데이터로 내주는 조건이라는 것도 구분해서 고를 수 있어요.
왜 배우나
목록이 길다고 "쓸 수 있는 모델이 수백 개"라고 오해하면 정작 중요한 선택(이 폴더의 코드를 학습에 내줘도 되는지)을 놓치고, 요금이 싸다는 이유만으로 요금 티어를 고르게 돼요.
왜 중요한가
업무 코드가 든 폴더를 열어 둔 채 무료 티어를 고르면 그 코드와 설정이 학습 재료로 넘어가고, 한 번 보낸 데이터는 되돌릴 방법이 없어요.
어디에 쓰나
/models 목록에서 원하는 모델 찾기 · 연습 폴더와 업무 폴더에 각각 다른 요금 티어(Contributor Free vs Standard) 지정하기 · 새 모델이 안 보일 때 opencode upgrade → --refresh → 캐시 삭제 순서로 확인하기 · opencode.json에 기본 모델 고정해 두기.

먼저, opencode가 뭔가요

opencode는 터미널1 안에서 도는 AI 코딩 도구예요. 제가 AI 코딩 도구 고르기 — 터미널이냐 편집기냐 클라우드냐에서 나눠 본 네 부류 중 터미널형에 해당해요. 채팅창에 말하듯 시키면 그게 내 프로젝트 폴더의 파일을 직접 읽고 고치는 물건이라고 보면 돼요.

이런 도구를 통틀어 하네스(harness)라고 불러요 — 모델 자체가 아니라, 모델을 붙들어 놓고 파일을 읽히고 명령을 돌리게 만드는 껍데기예요(맡길 일부터 관찰까지 — 하네스 보는 법에서 자세히 다뤘어요). opencode의 특징은 이 껍데기가 어떤 회사의 모델에도 붙는다는 점이에요. Claude를 쓰든 GPT를 쓰든 Gemini를 쓰든, 껍데기는 그대로예요.

그래서 처음 켜면 겁이 나요. /models를 눌렀을 때 나오는 목록이 수백 줄이거든요. 이 글은 그 목록을 읽는 법에 관한 거예요.

비유 — 기차표 예매 화면

서울에서 부산까지 가려고 예매 앱을 열었다고 해볼게요. 실제로 그 시간대에 부산으로 가는 열차는 서너 편밖에 없어요. 그런데 검색 결과는 수십 줄이 뜹니다.

왜냐면 같은 열차 한 편이 여러 번 나오거든요. 코레일 앱에서 산 것, 여행사 사이트에서 산 것, 역 창구에서 산 것이 각각 다른 줄로 보이고, 거기에 일반운임·조기할인·청소년할인이 또 갈라지고, 일반실과 특실이 다시 갈라져요. 열차는 넷인데 줄은 마흔 줄이 되는 거예요.

목록이 길어 보이는 이유이 네 축이 서로 곱해지기 때문

핵심 한 줄: 목록의 길이는 "쓸 수 있는 모델이 몇 개인가"가 아니라 "내가 골라야 할 축이 몇 개인가"를 보여주는 거예요.

다만 여기서 비유가 끊기는 점은 — 기차는 어느 예매처에서 사든 앉는 좌석이 똑같지만, AI 모델은 어느 제공자를 거치느냐에 따라 실제로 달라질 수 있어요. 컨텍스트 한도3를 제공자가 더 좁게 잘라 놓기도 하고, 속도가 다르기도 하고, 무엇보다 내 코드가 어떻게 취급되는지가 달라요. 이 마지막 항목은 아래에서 따로 볼게요.

모델 이름 읽는 법

opencode에서 모델 하나를 가리키는 이름은 제공자/모델이름 형식이에요. 슬래시 앞이 "어느 창구로 사느냐", 뒤가 "무슨 열차냐"인 셈이죠. 여기에 추론 강도를 고르는 # 꼬리표가 붙을 수 있어요.

공식 문서가 못 박아 둔 규칙이 하나 있어요 — 제공자 이름에는 /와 #이 들어갈 수 없고, 모델 이름에는 #이 들어갈 수 없어요. 그래서 첫 번째 슬래시까지가 항상 제공자, 마지막 #부터가 항상 변형으로 안전하게 잘라 읽을 수 있어요.

전체 흐름 — 이름 해부와 목록이 만들어지는 길

읽는 법: 위쪽 두 상자는 모델 이름 한 줄을 조각으로 자른 것이고, 아래 화살표는 왼쪽 세 곳에서 모은 정보가 내 컴퓨터에 저장된 캐시4 파일 하나를 거쳐 화면 목록이 된다는 뜻이에요. 화면에 없는 모델은 "존재하지 않는 모델"이 아니라 "이 캐시가 아직 모르는 모델"일 때가 많아요.

Muse Spark 1.3이 뭐길래

제가 이 글을 쓰게 된 계기가 이거예요. 같이 공부하는 분이 "1.3이 컨텍스트 용량이 훨씬 커서 1.3 쓰는 게 낫다"고 했는데, 제 목록엔 1.3이 없었거든요.

Muse Spark 1.3은 Meta가 2026년 9월 2일에 낸 코딩용 모델이에요. 자기네 코딩 도구인 Muse Code와 Meta Model API에 먼저 올렸고, opencode에서는 아래에서 설명할 Contributor 계열로 쓸 수 있어요.

Meta가 내세운 건 두 가지예요. 하나는 1M 토큰 컨텍스트 창 — 한 번의 대화에 담아 둘 수 있는 분량이 아주 크다는 뜻이에요. 다른 하나는 같은 일을 더 적은 걸음으로 끝낸다는 거예요. 1.2와 비교해 도구 호출5 횟수가 약 20%, 쓰는 토큰이 약 25% 줄었다고 발표했어요.

여기서 제가 헷갈렸던 걸 짚고 갈게요. "컨텍스트가 커진 덕분에 좋아진 게 아니에요." 공개된 설명을 보면 1.3의 개선은 학습·튜닝에서 온 것이지 컨텍스트 창을 늘려서 생긴 게 아니에요. 컨텍스트가 크다는 것과 그 큰 컨텍스트를 꽉 채워 쓰는 게 좋다는 건 아예 다른 얘기고요 — 창을 채울수록 중간에 넣은 정보를 놓치기 쉬워진다는 건 중간이 사라진다 — Lost in the Middle과 컨텍스트 부패에서, 그래서 예산처럼 관리해야 한다는 건 컨텍스트 창 예산 세우기에서 다뤘어요.

표 아래 단서: 20%·25%라는 감소 폭은 Meta가 자기 모델을 자기 기준으로 잰 값이에요. 독립 기관이 검증한 수치가 아니니 "내 작업에서도 그만큼 줄어든다"로 읽으면 안 돼요. 이런 근거 등급 구분은 결과와 궤적을 함께 본다 — 평가 루프와 일곱 하네스 비교에서 다뤘어요.

가장 중요한 축 — 요금 티어는 사실 데이터 정책이에요

비유의 "운임제"에 해당하는 축인데, 이건 그냥 싸고 비싼 문제가 아니라서 따로 봐야 해요.

티어가격내 프롬프트와 결과물이
Standard$1.25 / $4.25 per 100만 토큰모델 개선에 쓰이지 않음
Contributor$0.10 / $0.20 per 100만 토큰다음 모델 학습에 쓰임 (그 대가로 할인)
Contributor Free$0학습에 쓰임 + 언제 사라질지 모름

즉 무료 티어는 "공짜"가 아니라 내가 친 코드와 프롬프트를 학습 재료로 내주고 그 값으로 받는 것이에요. 이름에 contributor가 들어간 게 그 뜻이고요.

그리고 여기서 한 번 더 갈라 읽어야 할 게 있어요 — "학습에 쓰지 않는다"와 "남지 않는다"는 다른 말이에요. Standard를 골라도 그건 학습에 안 쓴다는 약속이지, 로그가 아예 없다는 뜻이 아니에요. 이 구분은 데이터는 어디에 남는가에서 여섯 가지 확인 항목으로 정리해 뒀어요.

나쁜 선택 vs 좋은 선택

같은 상황 — "무료 모델이 있길래 반가워서 바로 골랐다".

나쁜 선택좋은 선택
회사에서 맡은 사내 프로젝트 폴더를 열어 둔 채 contributor-free 모델을 골랐다 → 그 폴더의 코드·설정·주석·고객 이름까지 전부 모델 학습 재료로 넘어간다. 나중에 알아채도 이미 보낸 건 되돌릴 방법이 없다. 연습용 빈 폴더를 하나 만들고 거기서만 contributor-free를 쓴다 → 공짜로 성능을 체감해 보되, 넘어가는 건 어차피 남에게 보여도 되는 연습 코드뿐이다. 업무 저장소에서는 opencode.json의 기본 모델을 Standard 계열로 따로 지정해 둔다.

기차표 비유로 돌아가면 — 조기할인표가 싸다고 좋은 게 아니라, 그 표에 붙은 조건(환불 불가·날짜 변경 불가)을 읽고 골라야 하는 것과 같아요.

1.3이 목록에 안 보일 때

제 경우가 이랬어요. 강사님 화면엔 있는데 제 화면엔 없었죠. 앞의 그림에서 본 캐시가 원인일 때가 대부분이에요. opencode는 매번 인터넷에서 목록을 새로 받지 않고, 예전에 받아 둔 목록 파일을 재사용하거든요. 새 모델이 나온 지 며칠 안 됐으면 그 파일이 아직 모르는 거예요.

위에서부터 순서대로 해보세요. 앞 단계에서 해결되면 뒤는 안 해도 돼요.

1단계 — opencode 자체를 최신으로 올린다. 새 제공자·새 모델을 알아보는 코드가 프로그램 안에 들어 있어서, 프로그램이 낡으면 캐시를 지워도 소용없어요.

실행: 로컬 터미널

opencode upgrade

2단계 — 모델 목록을 새로 받는다. 갱신 플래그를 붙여 실행하면 캐시를 다시 채워요.

실행: 로컬 터미널

opencode --refresh

3단계 — 캐시 파일을 직접 지운다. 지워도 다음 실행 때 알아서 다시 만들어지니 안전해요.

실행: 로컬 터미널

rm ~/.cache/opencode/models.json

4단계 — 로그인 상태를 확인한다. opencode 안에서 /connect를 쳐서 제공자 연결을 확인하고, /models에서 목록을 다시 봐요. 무료 모델만 보고 싶으면 목록에서 "free"로 걸러 보면 돼요.

5단계 — 이름을 직접 지정해서 켠다. 목록에 안 떠도 이름을 정확히 주면 붙는 경우가 있어요.

실행: 로컬 터미널

opencode -m opencode/muse-spark-1-3-contributor-free

매번 치기 귀찮으면 프로젝트 폴더에 설정 파일로 못 박아 둘 수 있어요. opencode는 시작할 때 이 파일을 읽어서 기본 모델을 정해요.

실행: 프로젝트 폴더에 opencode.json으로 저장 — opencode가 시작할 때 자동으로 읽어요

{
  "model": "opencode/muse-spark-1-3-contributor-free"
}

여기까지 했는데도 없다면, 그 모델이 무료 풀에서 빠진 것일 수 있어요. 무료 목록은 고정이 아니라 계속 돌아가요 — 종료 날짜를 예고하지 않는다는 게 명시돼 있고요. 어제 있던 게 오늘 없는 건 제 설정이 잘못돼서가 아닐 수 있다는 뜻이에요.

알아두면 좋은 것 — Zen이라는 창구

모델 이름 앞에 붙는 opencode/가 뭔지 궁금하셨을 거예요. 이건 opencode Zen이라는 게이트웨이6예요. opencode 팀이 직접 테스트해 본 모델만 모아 놓은 창구라고 보면 돼요.

이게 편한 이유는 계정을 하나만 만들면 되기 때문이에요. 원래는 Anthropic에 가입해서 키 받고, OpenAI에 가입해서 키 받고, Google에도 가입해서… 이걸 다 해야 하는데, Zen은 그 창구를 하나로 합쳐 줘요. 여러 회사 모델을 한 계정으로 쓰고 청구서도 한 장이에요.

대신 대가도 있어요. 요청이 한 곳을 더 거치니 그만큼 중간에 낀 사람이 하나 늘어나는 셈이고, Zen이 골라 넣은 모델만 쓸 수 있어요. 이 "중간에 하나 더 끼우는" 구조 자체가 무엇인지는 프록시 서버란 무엇인가에 정리돼 있어요.

참고로 Zen에는 결제 정보 없이 쓸 수 있는 무료 구간이 따로 있는데, 하루 요청 수 같은 제한이 걸려 있어요. 유료로 넘어가면 쓴 만큼 내는 방식이고요.

축이 넷이라 어렵게 느껴지지만, 처음엔 이 순서로만 결정하면 돼요.

순서결정할 것초보자 기본값
①어느 창구로 살 것인가 (제공자)이미 쓰는 구독이 있으면 그것(Claude Pro/Max, ChatGPT Plus, GitHub Copilot). 없으면 Zen 하나로 시작
②이 폴더의 코드를 학습에 내줘도 되나연습 폴더 → Contributor 무료도 OK / 업무·과제 폴더 → Standard
③어떤 모델목록 위쪽의 코딩용 대형 모델 하나만 정해 두고, 비교는 나중에
④추론 강도 변형(#high 등)안 건드림. 기본값이 대부분 맞아요

제일 흔한 실수는 ③부터 고민하는 거예요. 모델 이름을 비교하느라 하루를 쓰기 전에, ②를 먼저 정해 두는 게 훨씬 중요해요 — ③은 나중에 한 줄 고쳐서 바꿀 수 있지만, ②는 이미 보낸 데이터를 되돌릴 수 없거든요.

직접 해보기

연습 폴더를 하나 만들고 이걸 재보세요. "어느 모델이 더 똑똑한가"가 아니라 "같은 일에 얼마를 쓰는가"를 보는 연습이에요.

바꿀 것: 모델 하나만. 프롬프트와 폴더 내용은 고정.
시킬 것: 짧은 과제 하나 — 예를 들어 "이 폴더의 HTML 파일에서 제목만 뽑아 목록 파일로 만들어 줘".
잴 것: ⓐ 끝날 때까지 걸린 시간, ⓑ 도구 호출 횟수(에이전트가 파일을 몇 번 읽고 몇 번 고쳤는지), ⓒ 세션 사용량 화면에 뜬 토큰 수.
비교할 것: 같은 과제를 두 모델로 각각 두 번씩(총 네 번). 한 번씩만 재면 그날 운을 재게 돼요.

이렇게 재 보면 "좋은 모델"이 아니라 "내 과제에 싼 모델"이 보여요. 비용을 이런 식으로 다루는 관점은 AI에게 컴퓨터를 맡길 때 — 권한, 로컬 모델, 토큰 비용에 더 있어요.

함께 읽으면 좋은 글

한 걸음 더: 여기서 "제공자"라고 부른 축이 사실은 세 개의 독립된 결정(사용자 화면 / 내 프로그램이 도는 컴퓨터 / 모델이 도는 컴퓨터) 중 하나라는 이야기는 어디서 돌리고 무엇에 연결할까 — 플랫폼·언어·모델 제공자에 있어요.

한 걸음 더: 토큰이 왜 돈이 되는지, 왜 대화가 길어질수록 비싸지는지는 토큰과 컨텍스트 창, 그리고 비용에서 봐요.

한 걸음 더: opencode 같은 터미널 도구가 처음이라 명령어 자체가 낯설다면 터미널 연습부터 보고 오시면 편해요.

다음 편 → 혼자 일하던 에이전트를 팀으로 — Sisyphus와 오케스트레이션 플러그인 (2)
  1. 터미널 — 컴퓨터에 글자로 명령을 쳐 넣는 창으로, 자세한 구조는 터미널·셸·커널·프롬프트에 있어요. ↩
  2. 제공자(provider) — 모델을 실제로 돌려 주고 요금을 청구하는 회사나 창구를 뜻하며, 고르는 기준은 플랫폼·언어·모델 제공자에 정리돼 있어요. ↩
  3. 컨텍스트 창 — 모델이 한 번에 볼 수 있는 글자 분량의 상한으로, 토큰과 컨텍스트 창, 그리고 비용에서 다뤘어요. ↩
  4. 캐시 — 매번 다시 받지 않으려고 받아 둔 것을 잠시 저장해 두는 자리로, 개념은 브라우저 캐시란 무엇인가와 같아요. ↩
  5. 도구 호출 — 모델이 파일 읽기·명령 실행 같은 동작을 스스로 요청하는 것으로, 한 번의 호출이 어떻게 오가는지는 도구 하나가 호출되기까지에 있어요. ↩
  6. 게이트웨이 — 여러 회사의 모델을 하나의 창구로 모아 대신 중계해 주는 서비스예요. ↩
