도구 하나가 호출되기까지 — 정의·파싱·구조화 요청 (1)

2026. 9. 7.

※ 이 글은 모두의연구소 학습 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

도구 호출은 AI가 직접 파일을 읽는 일이 아니라, 모델이 "이 기능을 이 값으로 실행해 달라"는 요청서 한 장을 만들어 내놓고 프로그램이 그 요청서를 대신 실행하는 일이다.

"AI가 파일을 읽는다"는 말 뒤에서 실제로 일어나는 일 — 도구 정의 전달, 모델의 구조화된 호출 요청 생성, 파서가 그 요청을 읽어내는 과정, 실행 결과 반환 — 을 단계별로 구분해서 볼 수 있게 돼요.

금요일 오후에 이런 부탁을 받았다고 해 볼게요. "이번 주 프로젝트 진행 상황을 정리해 주세요. 다음 주에 누가 뭘 챙겨야 하는지도요." 저는 AI 도구를 열었어요. 문장을 다듬고 보고서 모양을 잡는 건 AI가 잘해요. 그런데 빠진 게 하나 있어요. 우리 팀에서 이번 주에 실제로 무슨 일이 있었는지예요. 누가 어떤 기능을 만들었는지, 배포까지 끝났는지, 다른 팀 답변을 기다리는 중인지는 제 부탁 문장 안에 들어 있지 않아요.

이 시리즈는 그 빈칸을 메우는 과정이에요. 먼저 기록을 읽는 통로를 만들고, 그다음 읽어 온 내용을 우리 팀 기준에 맞춰 보고서로 바꿔요. 실습 자료는 실제 회사 기록이 아니라 가상 제품팀의 업무 기록이고, 첫째 주와 둘째 주가 준비돼 있어요.

사실 "에이전트1가 도구를 쓴다"는 이야기 자체는 이 블로그에서 이미 두 번 다뤘어요. 에이전트가 도구를 쥔다는 것에서 모델·하네스·루프의 역할을 나눠 봤고, 도구를 실제로 설계하기에서 도구 정의서와 스키마를 직접 써 봤어요. 이번 시리즈는 그 개념 위에서 MCP2라는 구체적인 규칙으로 실제 서버를 만들어 붙이는 실습이에요. 그러니 1편인 이 글은 "그 실습에 들어가기 전에, 도구 호출 한 번 안에서 정확히 무슨 일이 일어나는가"를 느리게 뜯어보는 편이에요.

비유 — 식당 홀 직원과 주방

동네 식당에 들어가서 "매콤한 거 하나 주세요"라고 말해요. 홀 직원은 그 말을 듣고 주문표에 메뉴 이름과 옵션을 적어 주방에 넘겨요. 요리는 주방이 해요. 홀 직원이 주문표를 적었다고 해서 그 순간 음식이 만들어진 건 아니죠. 그리고 홀 직원이 뭘 적을 수 있는지는 메뉴판이 정해요. 메뉴판에는 음식 이름과 한 줄 설명, 그리고 "맵기는 1~3단계 중에 고르세요" 같은 주문 규칙만 적혀 있어요. 메뉴판 안에 음식이 들어 있는 건 아니에요.

핵심 한 줄: 메뉴판(도구 정의)에는 음식이 들어 있지 않고, 주문표(호출 요청)는 아직 음식이 아니에요 — 요리는 주방(프로그램)이 따로 해요.

다만 여기서 비유가 끊기는 점은 이거예요. 사람인 홀 직원은 "매콤한 거"가 애매하면 손님에게 되물어요. 모델은 되묻지 않고 그냥 하나를 골라 적어 버릴 수도 있어요. 그래서 뒤에서 "형식은 맞는데 손님이 원한 게 아닌 주문표"를 따로 이야기해요.

기록을 전달하는 두 장면

가장 먼저 떠오르는 방법은 파일 내용을 대화창에 그대로 붙여 넣는 거예요. 기록이 몇 줄이고 한 번만 정리하면 된다면 이걸로 충분해요. 읽을 자료를 제가 직접 건네줬으니 바로 같이 볼 수 있어요.

그런데 다음 주에도 같은 일을 맡는다면요? 게다가 "지난주와 이번 주를 비교해 줘"라는 요청까지 들어와요. 기록이 파일 하나에 있으면 찾아 붙이면 되지만, 공유 표나 여러 프로젝트에 흩어져 있으면 자료를 모으는 작업부터 매번 반복돼요.

그래서 AI에게 "필요한 주의 기록을 가져오는 기능"을 쥐여 줘요. 저는 보고 싶은 주를 말하고, 프로그램이 그 주의 기록을 읽고, AI는 읽어 온 기록을 바탕으로 답해요. 여기서 생긴 진짜 변화는 AI가 더 그럴듯한 문장을 쓰게 된 게 아니에요. 대화 밖의 자료를 실제로 가져오는 동작이 생겼다는 거예요.

실행할 기능과 모델에게 줄 설명은 다른 것

개발자가 "주 이름을 받으면 그 주의 기록을 읽어서 돌려주는 함수4"를 준비했다고 해 볼게요. 이름은 get_weekly_records, 전달하는 입력은 어떤 주를 읽을지 나타내는 week이고, 첫째 주를 읽을 때 넣을 값은 week-one이에요.

여기서 제가 처음에 헷갈렸던 지점이 있어요. 함수 코드를 만드는 일과, 모델이 그 기능을 쓸 수 있게 만드는 일은 이어져 있지만 같은 단계가 아니에요. 컴퓨터에 파일을 하나 저장했다고 해서 모델이 그 안의 함수를 자동으로 아는 게 아니거든요. 모델에게는 쓸 수 있는 기능의 이름·설명·입력 규칙을 따로 건네줘야 해요. 이렇게 모델이 사용을 요청할 수 있도록 제공한 기능을 도구(tool)라고 불러요.

이번 도구의 안내를 사람이 읽기 좋게 펼치면 이래요.

항목내용모델이 이걸로 하는 일
이름get_weekly_records어떤 기능을 요청할지 구별한다
설명지정한 주의 가상 제품팀 업무 기록을 읽는다주간 진행 상황을 묻는 요청에 이 기능이 필요한지 판단한다
입력 항목week어떤 주를 조회할지 값을 채운다
입력 형식글자로 된 값(문자열5)이며 반드시 필요함값의 모양과 필수 여부를 확인한다
준비된 주week-one, week-two실습에서 조회할 수 있는 자료의 범위를 안다

입력 항목과 형식을 정한 이 규칙을 입력 스키마(input schema)라고 해요. '스키마'라는 말이 낯설다면 여기서는 "이 기능을 실행하려면 어떤 값을 어떤 모양으로 제출해야 하는지 적은 규칙"으로 읽으면 돼요. 주 이름은 숫자가 아니라 글자로 전달하는데, 프로그래밍에서 이런 글자 자료를 문자열(string)이라고 불러요. 실제 도구 정의는 사람이 읽는 표가 아니라 프로그램이 읽을 수 있는 형식으로 전달되는데, 대개 목업 데이터와 REST API에서 처음 봤던 JSON6 모양이에요. 대충 이런 느낌이에요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

{
  "name": "get_weekly_records",
  "description": "지정한 주의 가상 제품팀 업무 기록을 읽습니다",
  "input_schema": {
    "type": "object",
    "properties": {
      "week": { "type": "string" }
    },
    "required": ["week"]
  }
}

표에서 본 다섯 줄이 그대로 들어 있는 게 보이실 거예요. "type": "string"이 "글자 값", "required": ["week"]가 "반드시 필요함"이에요. 여기까지가 도구 정의서와 스키마 편에서 손으로 써 봤던 그 내용이 실제 파일에서 어떤 모양인지예요.

그리고 하나 더. 주 이름의 형식을 지키는 일과 올바른 주를 고르는 일은 달라요. week-two는 형식에 완벽히 맞는 값이지만, 제가 첫째 주를 물었는데 이 값이 들어갔다면 엉뚱한 자료를 읽게 돼요. 그래서 나중에는 "호출이 실행됐는가"와 함께 "어떤 입력으로 실행됐는가"도 같이 봐요.

마지막으로, 도구의 설명은 조회 기능의 사용법이지 업무 기록 자체가 아니에요. "기록을 읽을 수 있다"는 안내만 받은 상태에서는 TASK-102의 개발이 끝났는지 모델은 아직 몰라요. 실제 내용은 조회한 뒤에 도착해요. 메뉴판을 봤다고 음식을 먹은 게 아닌 것처럼요.

모델의 요청이 만들어지는 지점

제가 "첫째 주 기록을 읽고 진행 상황을 알려 줘"라고 쳤어요. AI 앱은 제 요청과 쓸 수 있는 도구의 설명을 함께 모델에게 넘겨요. 모델은 그걸 받아서 응답을 만드는데, 이 응답은 두 갈래일 수 있어요. 저에게 보여 줄 문장일 수도 있고, 도구 이름과 입력을 담은 호출 요청일 수도 있어요.

도구 사용을 지원하는 모델은 이런 구조화된 요청을 출력할 수 있어요. '구조화'란 프로그램이 이름과 입력을 구별해서 읽을 수 있도록 정해진 항목으로 표현한다는 뜻이에요. 산문 한 덩어리가 아니라 칸이 나뉜 주문표인 거죠.

개념 설명용 코드 — 오가는 내용을 사람이 읽기 좋게 펼친 것이에요

모델에게 전달 —
  사용자 요청: 첫째 주 기록을 읽고 진행 상황을 알려 줘.
  도구 안내: get_weekly_records는 지정한 주의 업무 기록을 읽음
  필요한 입력: week
  준비된 값: week-one, week-two

모델이 생성한 호출 요청 —
  사용할 도구: get_weekly_records
  이번 입력: week = week-one

덕분에 개발자가 매번 사용자 문장에서 '첫째 주'라는 말을 찾아 week-one으로 바꾸는 조건문을 손으로 짜지 않아도 돼요. 도구 설명과 대화를 받은 모델이 이번에 필요한 도구와 입력을 스스로 출력하는 단계가 있고, 그다음 프로그램이 그 요청을 받아 실제 실행으로 연결해요.

여기서 꼭 짚고 갈 게 있어요. 여기까지는 "이 도구를 이 값으로 실행해 달라"는 요청이 만들어진 것뿐이에요. 아직 업무 기록을 읽은 결과는 없어요. 모델이 그 요청을 출력했다고 해서 파이썬 함수가 모델 안에서 돌아간 게 아니에요. 다음 단계는 제가 쓰는 애플리케이션 — AI와 대화하고 도구를 연결하는 프로그램 — 이 이어가요. 앱이 호출 요청을 연결된 도구 쪽으로 보내고 결과를 받아요. 이번 실습에서는 별도로 도는 파이썬 프로그램이 파일 읽는 일을 맡아요.

모델의 출력에서 도구 호출을 읽어 내는 과정

모델이 만든 표현을 프로그램이 "도구 호출"로 읽으려면 그 표현의 규칙을 알아야 해요. 파싱(parsing)7은 정해진 규칙에 따라 내용을 읽고 각 항목을 구분해 내는 과정이고, 그 일을 하는 프로그램을 파서(parser)라고 해요. 도구 호출 파서는 모델 출력에서 도구 이름과 입력을 뽑아내요. 주방장이 홀 직원의 손글씨 주문표를 읽어 "메뉴는 이거, 옵션은 이거"로 나누는 일이에요.

이 규칙은 모델을 제공하는 서비스(제공자, provider)와 세부 모델에 따라 달라질 수 있어요. 다만 "제공자마다 반드시 고유한 파서가 하나씩 있다"는 뜻은 아니에요. 서로 다른 모델이 같은 표현 규칙을 공유할 수도 있고, 반대로 같은 제공자의 모델이라도 계열이나 버전이 바뀌면 다른 처리가 필요할 수 있어요.

넣는 쪽에도 규칙이 있어요. 모델에 대화와 도구 설명을 넣을 때는 모델이 학습한 형식에 맞춰 배치하는데, 이 배치 규칙을 채팅 템플릿(chat template)8이라고 해요. 정리하면 이래요.

하는 일대화와 도구 설명을 모델이 익숙한 배치로 정리출력에서 도구명·입력을 뽑아냄
어긋나면모델이 도구가 있다는 걸 제대로 못 알아봄모델이 호출을 잘 냈어도 프로그램이 못 읽음

둘 다 그 모델의 도구 표현 방식에 맞아야 해요. 모델에 따라 도구 호출을 특별한 시작·종료 표시로 감싸기도 하고, JSON처럼 항목 이름과 값을 짝지어 적기도 해요. 예를 들어 {"week":"week-one"}은 week라는 항목의 값이 week-one이라는 뜻이에요. 파서는 호출 구간을 찾아 그 안의 도구명과 입력을 꺼내고, 응답이 조금씩 나눠 도착할 때는 필요한 조각을 모아 가며 읽기도 해요.

이 얘기가 실제로 손에 닿는 순간이 있어요. 모델을 직접 돌리고 외부 프로그램의 요청에 응답하는 일을 서빙(serving)9이라고 하는데, 직접 운영할 때 쓰는 서빙 소프트웨어인 vLLM에서는 자동 도구 선택을 켤 때 --tool-call-parser로 모델에 맞는 파서를 지정해요. 공식 문서는 Qwen2.5에 hermes를, Qwen3-Coder에 qwen3_xml을 안내해요. 같은 Qwen 계열이라도 세부 모델에 따라 달라지는 사례예요.

앱이 받는 호출과 MCP로 보내는 요청

다행히 대부분의 경우 저는 파서를 직접 만지지 않아요. API10는 프로그램끼리 요청과 응답을 주고받도록 정해 둔 접점인데, 모델 제공자의 API를 쓰는 앱은 보통 모델의 원래 출력 표시를 직접 해석하지 않고 서비스가 이미 정리해 준 호출 항목을 받아요. 예를 들어 Claude API는 사용자 정의 도구를 요청할 때 tool_use라는 응답 블록에 도구의 name과 input을 담아 줘요.

개념 설명용 코드 — 앱이 받는 응답의 모양만 보여주는 예시예요

{
  "type": "tool_use",
  "name": "get_weekly_records",
  "input": { "week": "week-one" }
}

이건 앱이 받는 공개 응답 형식이지, Claude 내부의 특수 표시나 파서 구현을 보여주는 게 아니에요. 같은 API 응답 형식을 여러 모델이 함께 쓸 수도 있고요.

첫째 주 조회 요청 하나에서 각 부분이 맡는 일을 늘어놓으면 이래요. 앱이 MCP를 통해 별도 조회 프로그램에 연결하는 경우예요.

부분무엇인가첫째 주 요청에서 하는 일
모델의 출력 표현모델이 생성하는 도구 호출 표시와 입력 표현조회 도구와 week-one을 골라 표현한다
서빙 쪽 도구 호출 파서모델의 표현 규칙을 읽는 쪽도구명과 입력을 읽어 서비스의 호출 구조로 정리한다
제공자 API의 구조화된 호출앱에 공개된 응답 항목Claude의 tool_use처럼 앱이 읽을 수 있는 호출을 전달한다
앱의 연결 처리 (어댑터11)제공자별 응답과 실제 도구를 잇는 부분호출을 읽고 연결된 조회 도구로 보낼 요청을 준비한다
MCP 메시지앱과 도구 제공 프로그램 사이의 공통 형식tools/call 요청에 도구명과 입력을 담아 보낸다

여기서 헷갈리기 쉬운 걸 하나 못 박고 갈게요. 어댑터가 제공자 API의 응답을 읽는 일과, 서빙 파서가 모델의 출력 표시를 해석하는 일은 서로 다른 위치의 작업이에요. 그리고 MCP도 모델 출력의 특수 표시를 읽는 파서가 아니에요. MCP의 tools/call은 도구 제공 프로그램에 "이걸 실행해 달라"고 요청하는 메시지이고, 그 안에 name과 arguments가 들어가요. MCP가 왜 필요한 표준인지는 MCP — AI를 내 데이터에 꽂는 USB-C에서 처음 다뤘어요.

제가 Claude Code나 OpenCode에서 지원되는 제공자 API를 쓸 때는 이런 처리를 앱과 서비스가 맡으니 모델별 파서를 직접 설정할 일이 없어요. 반대로 직접 운영하는 vLLM 서버를 붙인다면 서버 쪽의 모델·템플릿·파서 조합이 맞는지 확인할 일이 생겨요.

이 편에서 제가 제일 오래 붙잡고 있던 대목이에요. "잘 됐다"는 말 안에 사실 세 가지가 섞여 있어요.

무엇이 성공했나뜻이걸로 알 수 없는 것
파싱 성공모델 출력에서 도구명과 입력을 읽어 냈다그 도구가 실제로 돌았는지
실행 성공조회 프로그램이 요청을 처리하고 결과를 돌려줬다읽어 온 게 내가 원한 자료인지
의미가 맞는 호출사용자가 원한 주와 도구를 골랐다—

제가 첫째 주를 부탁했는데 모델이 week-two를 출력했다면, 파싱도 성공이고 실행도 성공이지만 제 요청에는 맞지 않아요. 파서는 모델이 고른 입력을 읽어 줄 뿐, 그 선택이 제 의도와 맞는지까지 보장하지 않아요. 주방은 주문표대로 정확히 요리했는데 손님이 시킨 게 아닌 상황이죠.

입력이 아예 애매한 경우도 있어요. 대화에 아무 주 정보가 없는데 "진행 상황을 알려 줘"라고만 하면, 어떤 주의 기록이 필요한지 먼저 되묻는 답변이 적절할 수 있어요. 실제 모델이 무엇을 골랐는지는 호출 기록으로 확인해요. 문장을 자연스럽게 이해하는 능력과 사용자의 의도를 정확히 맞히는 일이 항상 같지는 않으니까요.

전체 흐름 — 요청에서 답변까지

읽는 법: 세로 점선 네 개가 각각 사용자·AI 앱·모델·조회 프로그램이에요. 화살표는 번호 순서대로 왼쪽에서 오른쪽으로, 다시 되돌아오며 오가요. 눈여겨볼 곳은 두 군데예요. 첫째, 모델은 ③에서 요청만 내놓고 ④의 실행에는 관여하지 않아요. 둘째, 가운데 AI 앱이 모든 화살표를 거쳐 가요 — 모델과 조회 프로그램은 서로 직접 말하지 않아요. 이 그림은 한 번의 조회로 답할 수 있는 요청을 그린 설명용 순서도이고, 실제 에이전트는 필요한 자료에 따라 ②~⑥을 여러 번 반복하기도 해요.

프로그램이 모델에게 건네는 건 이런 조회 결과예요. "팀 전체 업무가 모두 순조롭다" 같은 최종 평가가 아니에요. 모델은 도착한 기록을 읽고 요청에 맞게 답변을 구성해요. 예를 들면 이렇게요.

"로그인 안내 문구 개선은 코드 작성이 끝났고 다음 배포를 기다리고 있습니다. 담당자는 지우이며, 기한은 9월 7일입니다."

이 문장에서 '다음 배포를 기다린다'는 말은 도구 설명이 아니라 실제로 반환된 업무 메모에서 왔어요. 어느 기록에서 어느 문장이 나왔는지 짚어 보면, "AI가 자료를 활용했다"는 말이 구체적으로 뭘 뜻하는지 손에 잡혀요.

한편 '개발 완료'를 우리 팀 주간 보고서에서 최종 '완료'로 분류할지는 아직 별개의 문제예요. 코드를 다 만든 것과 사용자가 쓰는 환경에 배포한 것은 서로 다른 사건이니까요. AI는 일반적인 요약을 잘하고, 별도 지침 없이도 "개발 완료, 배포 대기"를 정확히 표현할 수 있어요. 그렇지만 우리 팀이 어떤 항목을 완료 건수에 넣는지는 팀의 약속을 알아야 판단할 수 있어요. 이건 이 시리즈 뒤쪽의 Skill과 팀 규칙 편에서 다뤄요.

나쁜 선택 vs 좋은 선택 — 주문표를 확인할 때

나쁜 선택좋은 선택
get_weekly_records 함수를 파일로 잘 만들어 저장해 두고 "이제 AI가 쓰겠지" 하고 넘어간다 → 메뉴판에 안 올린 음식이라 모델은 그런 기능이 있는 줄도 모르고, 그냥 그럴듯한 문장을 지어낸다. 함수를 만든 뒤 이름·설명·입력 스키마를 도구 정의로 따로 만들어 모델에게 전달한다 → 모델이 "이 요청에는 이 기능이 필요하다"고 판단할 근거가 생긴다.

나중에 실제로 연결 실습을 할 때는 AI의 문장만 읽고 끝내지 않고 도구명·입력·반환된 기록을 함께 볼 거예요. 호출 요청을 처리한 뒤 그 결과를 모델에게 다시 전달하는 것 — 이게 도구 사용의 한 차례 흐름이에요.

같은 기능을 여러 앱에 연결하려면

여기까지 오니 조회 기능 하나의 흐름이 보여요. 개발자가 기능을 준비하고, 모델은 설명을 받아 호출을 요청하고, 프로그램이 실행 결과를 돌려줘요. 그러면 같은 조회 기능을 Claude Code에서도 OpenCode에서도 쓰려면 어떻게 해야 할까요?

도구 사용 기능 자체는 MCP가 나오기 전에도 있었어요. 개발자가 모델이 받는 도구 설명 형식에 맞추고, 돌아온 호출 요청을 읽고, 실제 서비스에 연결하고, 결과를 다시 보내는 부분을 직접 작성할 수 있었어요. 다만 앱이나 서비스의 연결 방식이 달라지면 그때마다 맞추는 작업이 또 생겼죠.

다음 편에서는 이 중 도구를 제공하는 프로그램과 AI 앱 사이에 공통 규칙을 두는 방법을 봐요. 그 규칙이 MCP예요. 방금 살펴본 모델의 요청 · 프로그램의 실행 · 결과 전달을 기억해 두면, MCP가 맡는 부분과 제가 직접 구현할 업무 기능을 구별하기가 훨씬 쉬워져요.

직접 해보기

코드 없이 종이에 하는 연습이에요. 제 업무 중에 "AI가 대신 조회해 줬으면" 싶은 것 하나를 고르고 네 줄을 적어요. ① 기능 이름을 영어 소문자로 뭐라고 붙일까(get_weekly_records처럼), ② 설명 한 줄 — 모델이 이 설명만 읽고 "지금 이게 필요한지" 판단할 수 있게 쓸 수 있나, ③ 입력 항목은 몇 개이고 각각 어떤 모양인가(글자? 숫자? 필수인가?), ④ 입력값이 형식은 맞는데 의미가 틀릴 수 있는 경우는 뭔가. 특히 ④를 채워 보면 "파싱 성공 ≠ 의미가 맞는 호출"이 왜 따로 있는지 손에 잡혀요.

  1. 에이전트 — 목표를 받아 스스로 도구를 골라 쓰며 여러 단계를 이어 가는 AI 프로그램으로, AI 에이전트란 무엇인가에서 처음 다뤘어요. ↩
  2. MCP — AI 앱과 도구 제공 프로그램이 서로 연결되는 방식을 하나로 정해 둔 공통 규칙으로, MCP — AI를 내 데이터에 꽂는 USB-C에서 처음 다뤘어요. ↩
  3. 입력 스키마 — 어떤 기능을 실행하려면 어떤 값을 어떤 모양으로 제출해야 하는지 적어 둔 규칙으로, 도구를 실제로 설계하기에서 도구 정의서와 함께 다뤘어요. ↩
  4. 함수 — 이름을 붙여 다시 실행할 수 있도록 묶어 둔 코드 한 덩어리. ↩
  5. 문자열(string) — 숫자가 아니라 글자로 이루어진 자료를 프로그래밍에서 부르는 이름. ↩
  6. JSON — 설정이나 데이터를 "이름: 값" 꼴로 중괄호 안에 적는 형식으로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  7. 파싱(parsing) — 정해진 규칙에 따라 내용을 읽고 각 항목을 구분해 내는 과정이며, 그 일을 하는 프로그램을 파서(parser)라고 불러요. ↩
  8. 채팅 템플릿(chat template) — 대화와 도구 설명을 모델이 학습한 형식에 맞춰 배치하는 규칙. ↩
  9. 서빙(serving) — 모델을 실행해 두고 외부 프로그램의 요청에 응답하도록 운영하는 일. ↩
  10. API — 프로그램끼리 요청과 응답을 주고받도록 정해 둔 접점으로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  11. 어댑터(adapter) — 서로 다른 형식 사이를 맞춰 주는 연결 부분. ↩
