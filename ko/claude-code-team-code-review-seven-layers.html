Claude Code 팀 — AI 코드 리뷰 일곱 겹

2026. 11. 02.

※ 이 글은 한국어 해설 영상 "앤트로픽 Claude Code 팀이 공개한 AI 코드 리뷰 7겹 — PR은 2배 늘리고 되돌림은 40% 줄인 방법"(AgentOS, 9분 22초)을 보고 핵심만 제 나름의 언어로 줄인 것입니다. 해설 영상의 원문은 앤트로픽 엔지니어링 글 「How the Claude Code team does code review」(Addy Osmani, Morgan Westlee Lunt, Qing Wang, 2026-10-15)이고, 원문도 함께 읽어 영상이 줄인 대목은 "원문에 따르면"으로 덧붙였어요.

Claude Code 팀의 코드 리뷰는 "사람이 이 코드를 읽었나" 대신 "이 변경에서 무엇이 잘못될 수 있고 어느 검사가 그걸 잡나"를 묻는 일곱 겹의 체이고, 읽는 일은 대부분 기계가 맡고 사람의 시간은 위험한 변경과 빠른 되돌리기에 쓴다.

이 글을 읽기 전에

어디쯤인가
AI 시대 스크랩 — 단독 글이에요. PR 병목 고치기의 "브레이크 세 겹"을 실제 회사가 일곱 겹으로 굴린 사례로 읽어도 돼요.
이런 게 궁금했다면
  • 에이전트가 PR을 하루에 수십 개씩 올리면 사람은 그걸 다 읽어야 할까요?
  • 리뷰 에이전트를 붙였더니 작성 에이전트와 끝없이 주고받기만 하는데, 어디서 끊어야 할까요?
읽고 나면 할 수 있는 것
  • 내 저장소의 변경을 위험도 세 등급으로 나누고 등급마다 사람 승인 수를 정할 수 있어요.
  • AI 리뷰에 라운드 상한과 "새로 바뀐 부분만 다시 보기" 규칙을 걸 수 있어요.
모르면 이런 일이 생겨요
  • 리뷰 에이전트와 작성 에이전트가 밤새 수십 라운드를 돌며 옛날 버그만 계속 찾아요. 언제 의심하나 ↓
  • 각자 검사를 통과한 PR 두 개를 합쳤는데 main이 깨져요. 언제 의심하나 ↓
어디에 쓰나
  • 코딩 에이전트에게 PR을 맡기기 시작한 팀이나 1인 저장소. 어디까지 자동으로 합치고 어디서 사람이 볼지 정할 때 써요.
  • CLAUDE.md·REVIEW.md 같은 지시 파일에 무엇을 적을지 정할 때

원문에 따르면 Claude Code 코드의 약 90%를 Claude가 써요. 앤트로픽 사내 모노레포1에 하루에 합쳐지는 변경은 올해 5월 약 2,500건에서 9월 3만 건을 넘었어요. 사람이 한 줄씩 읽을 수 없는 양이에요. 그런데 Claude Code 팀은 6월부터 9월까지 합친 PR2이 두 배 넘게 늘었는데도 되돌려야 했던 비율은 40% 넘게 줄었다고 해요. 해설 영상은 첫 화면에서 이렇게 못 박아요. 리뷰를 없앤 게 아니다.

중요세 줄 요약

  1. 질문을 바꾼다. "사람이 읽었나"가 아니라 "무엇이 잘못될 수 있고, 그걸 자동 검사와 사람 중 누가 잡나"를 묻는다.
  2. 겹을 쌓는다. PR 전 검증부터 되돌리기까지 일곱 겹이 서로 다른 문제를 잡고, 사람이 판단하는 겹은 위험도별 승인 하나다.
  3. 놓치면 검사를 고친다. 리뷰가 놓친 문제는 "그때 모델 앞에 무엇이 없었나"를 물어 CLAUDE.md·스킬·새 검사로 옮긴다.

1. 질문 바꾸기 — 사람이 읽었나 대신 무엇이 잘못될 수 있나

예전 리뷰는 길 끝의 관문이었어요. 코드를 짜고, PR을 올리고, 동료를 기다려요. 해설 영상은 지금 이 팀의 리뷰를 글을 쓰는 동안 계속 돌아가는 맞춤법 검사에 빗대요. 사람이 보기 전에 대부분의 변경은 이미 Claude가 한 번 이상 리뷰하고 고친 상태예요.

이 팀이 아끼려는 건 사람의 시간과 주의력이에요. 사람 시간은 두 가지예요. 리뷰하는 시간, 그리고 나쁜 코드가 망가뜨린 걸 고치는 시간. 앞의 것을 줄였는데 뒤의 것이 늘면 아낀 게 아니라 옮긴 거예요. 그래서 목표는 이래요.

  • 목표: PR 대부분을 사람 최대 한 명(그 한 명이 작성자 본인이어도 됨)만 거쳐 합친다.
  • 가드레일: 되돌림 비율과 장애 비율이 예전보다 나빠지지 않는다.

여러 겹의 체 — 한 장으로는 다 못 거른다

해설 영상이 쓰는 비유예요. 고운 가루를 거를 때 체 한 장으로 다 거르려 하지 않고 눈 크기가 다른 체를 여러 장 겹쳐요. 한 장에 구멍이 있어도 다음 장이 받아요. 모든 체의 구멍이 한 줄로 맞아 끝까지 빠져나가는 알갱이는 드물고, 그래도 빠져나간 건 맨 아래 받침이 받아요.

비유 속 요소원래 개념
체 한 장검사 하나(자동 검사, AI 리뷰, 보안 리뷰, 사람 승인…)
체마다 다른 눈 크기겹마다 잡는 문제와 놓치는 문제가 다름
끝까지 빠져나간 알갱이모든 겹을 통과한 버그
맨 아래 받침기능 플래그3·되돌리기·단계적 배포

핵심 한 줄: 한 겹을 완벽하게 만드는 대신, 서로 다른 구멍을 가진 겹을 여러 장 쌓고 맨 아래에 받침을 둔다.

다만 여기서 비유가 끊기는 점이 있어요. 체는 가만히 있지만 이 팀의 겹은 놓친 문제를 먹고 자라요. 장애가 나면 어느 겹이 잡았어야 했는지 따지고, 그 겹을 고쳐요.

이 블로그의 PR 병목 고치기가 세운 브레이크는 자동 검사·자동 리뷰·사람 리뷰 세 겹이었어요. Claude Code 팀의 일곱 겹은 그 앞에 "PR 전 검증"을, 사이에 "보안 리뷰"를, 뒤에 "머지 큐·배포"와 "되돌리기"를 더 끼운 모양이에요.

전체 흐름 — 변경 하나가 지나는 일곱 겹

변경 하나가 개발자 노트북에서 사용자에게 닿기까지 지나는 겹이에요. 해설 영상에 따르면 원문 도표에서 사람이 판단하는 칸으로 표시된 건 다섯 번째 위험도별 승인 하나이고, 나머지는 자동 검사와 복구 쪽이에요.

겹 1·2 PR 전 검증과 필수 자동 검사 — 다 했다는 말 대신 실행 결과

첫 겹은 PR이 생기기도 전에 시작돼요.

  • 스스로 돌려 볼 수단을 준다. 테스트, 빌드, 디자인과 비교할 스크린샷처럼 Claude가 직접 실행해 볼 수 있는 걸 주고, "다 했어요" 대신 실행 결과를 보여 달라고 해요.
  • 빈 맥락에서 다시 본다. 그다음 맥락이 비어 있는 서브에이전트가 변경분을 다시 리뷰해요. 원문에 따르면 버그 찾기, 변경 단순화, 끝까지 동작 점검을 하는 사내 스킬도 이 단계에서 써요.
  • 같은 지적은 근원을 고친다. 리뷰어가 같은 걸 세 번 지적하면 세 번 고치는 대신 스킬을 고치거나, 린트 규칙을 만들거나, 지시 파일을 고쳐요.

Claude Code를 만든 보리스 체르니(Boris Cherny)는 Claude에게 스스로 검증할 수단을 주는 것이 아마 가장 중요한 일이라며, 그러면 최종 결과가 두세 배 좋아진다고 추정했어요.

지시 파일은 둘이에요.

파일누가 쓰나무엇을 적나
CLAUDE.md프로젝트 팀프로젝트가 무엇인지, 스택과 관례, 목표와 비목표, 에이전트가 돌릴 검사. 짧게 두고 다른 문서를 가리켜요
REVIEW.md코드 오너4자기 영역에서 실패가 어떤 모습인지(문서라면 "거짓말하기", 설정이라면 "엉뚱한 곳으로 보내기"), 이름만 보고 추측하지 말고 파일과 줄 번호를 근거로 대라는 요구

원문에 따르면 REVIEW.md에는 사소한 지적의 개수 제한, 건너뛸 경로, 그리고 "지적이 몇 개인지로 시작하고 문제가 없으면 없다고 분명히 말하는 요약"도 적어요.

두 번째 겹은 익숙한 필수 자동 검사예요. 린트, 타입 검사, 모든 플랫폼의 테스트, 빌드. 평범한 CLI PR 하나가 사람이 보기 전에 수십 개 검사를 거치기도 해요. PR 템플릿은 어떻게 테스트했는지, 위험은 무엇인지, 어떻게 되돌리는지를 묻고, 그 칸은 Claude가 채워도 서명은 변경을 요청한 사람이 해요.

겹 3 AI 코드 리뷰 — 지적을 거르는 투표

세 번째 겹은 모든 PR에 붙는 AI 리뷰예요. 사람보다 Claude가 먼저 봐요. 변경분을 저장소 전체와 PR의 의도에 비춰 읽고, 이 변경이 문제를 풀었는지, 시스템에 맞는지, 다른 걸 깨뜨리지 않는지 물어요. 원문에 따르면 버그 수정이면 근본 원인을 찾았는지도 봐요.

리서치 프리뷰를 시작했을 때 실질적인 리뷰 코멘트를 받는 사내 PR 비율이 16%에서 54%로 올랐어요. 1,000줄이 넘는 PR은 대부분 지적을 받고, 작은 PR은 대부분 지적 없이 통과해요.

해설 영상이 "흥미롭다"고 짚는 건 지적을 거르는 방식이에요.

  • 찾기와 거르기를 나눈다. 여러 에이전트가 동시에 버그를 찾고, 다른 에이전트 그룹이 지적 하나하나에 투표해요. 충분히 많이 "진짜"라고 동의해야만 PR에 올라가요. 스타일이나 정리 수준의 지적은 버려요. 원문에 따르면 이 거름 규칙은 자기네 PR로 A/B 테스트를 해 본 뒤에 남겼어요.
  • 꼬리표를 단다. 남은 지적엔 중요·사소함·원래 있던 문제 중 하나가 붙어요. 이 PR이 만든 버그가 아니면 작성자 잘못처럼 보이지 않게 하려는 거예요.
  • 모든 지적에 답한다. 고치거나, 이유를 달고 닫아요. 밤사이 에이전트가 수정을 가져가는 경우가 많아서, 작성자가 아침에 오면 PR이 이미 한 라운드를 더 돈 상태예요.

원문에 따르면 이 리뷰는 제품으로도 나와 있어요. Team·Enterprise 플랜의 Code Review for Claude Code와, 로컬에서 돌리는 가벼운 /code-review 명령이에요. 저장소마다 Quick·Standard·Deep 세 단계로 깊이를 정하고, 놓친 버그 하나의 값이 비싼 곳에 Deep을 써요.

밤새 50라운드 — 끝나지 않는 리뷰와 바뀐 네 가지

그런데 바로 이 구조에서 문제가 터졌어요. 작성도 에이전트, 리뷰도 에이전트면 지적하고 고치고 또 지적하고 또 고치는 일이 끝없이 이어질 수 있어요. 실제로 CLI 쪽 PR 하나가 밤새 리뷰와 수정을 50라운드 넘게 돌았어요. 작성자가 멈출 때까지요.

리뷰어가 계속 지적한 부분을 git blame5으로 따져 보니 약 59%가 리뷰어의 첫 리뷰 때부터 이미 있던 코드였어요. 새 버그는 거의 못 찾고, 옛날 버그를 라운드마다 몇 개씩 더 찾고 있었던 거예요.

노이즈 문제이기도 해요. 사람은 사소한 지적을 몇 초 만에 넘기지만 에이전트는 그걸 고쳐요. 고치면 커밋이 하나 더 생기고, 커밋이 생기면 리뷰가 한 번 더 돌아요. 팀은 라운드마다 뭔가 새로 걸리니까 여러 라운드를 기본으로 돌리는 데 익숙해져 있었다고, 스스로 일을 키웠다고 인정해요. 그래서 네 가지를 바꿨어요.

  1. 라운드 상한. 3라운드가 넘으면 리뷰어가 작성자에게 한발 물러서서 접근 자체를 다시 생각하라고 해요.
  2. 새로 바뀐 부분만. 처음 몇 번 이후엔 새 변경분만 다시 봐요.
  3. 버그 유형 단위. 한 줄이 아니라 버그의 유형을 짚어서, 같은 유형을 한 번에 다 고치게 해요.
  4. 반복 금지. 이미 올린 지적은 다시 올리지 않아요.

리뷰어 자체도 이렇게 다듬어요.

  • 장애가 곧 평가 세트. 과거에 장애를 낸 PR(원문에 따르면 그 뒤의 앞으로 고치기·되돌리기 PR까지)을 모으고, 그 코드를 잘 아는 엔지니어가 버그와 위치를 확인해요. 리뷰어를 매일 이 세트에 돌리고, 프롬프트든 도구든 모델이든 리뷰어를 바꾸면 전체 세트로 다시 채점해요. 원문에 따르면 점수가 오르면 남기고 아니면 버려요.
  • 노이즈도 잰다. 지적마다 사람이 어떻게 반응했는지(고쳤다, 틀렸다고 했다, 의도한 거라고 했다, 상관없다고 했다)로 나눠요. 원문에 따르면 깨끗하다고 알려진 PR에도 돌려서 엉뚱한 보고가 얼마나 나오는지 세고, 우선순위는 진짜 버그 잡기가 먼저, 라운드 줄이기가 그다음이에요.
  • 원문에 따르면 리뷰 에이전트는 밤마다 기존 코드에도 돌아서 옛날 버그를 다른 데서 터지기 전에 잡아요.

겹 4·5 보안 리뷰와 위험도별 승인 — 등급은 작성자가 아니라 변경이 정한다

네 번째 겹은 보안 리뷰예요. 버그 리뷰든 보안 리뷰든 열린 지적이 하나라도 있으면 머지가 안 돼요. 오탐이면 짧은 이유를 달고 닫으면 되고, 나중 커밋이 문제를 고치면 지적은 저절로 풀려요. 원문에 따르면 도구는 오픈소스 security review GitHub Action과 /security-review 명령이에요.

다섯 번째 겹에서 드디어 사람이 등장해요. 문서 수정과 자동 업데이터 변경은 위험이 다르니까 리뷰도 달라요.

여기에 규칙 네 개가 붙어요.

  1. 등급은 변경이 정한다. 작성자가 아니라 분류기가 변경을 읽고 등급을 고르고, 두 번째 분류기가 그래도 사람이 필요한지 한 번 더 물어요. 오너가 민감하다고 적어 둔 경로와 CI 워크플로 파일은 무조건 사람이 봐요.
  2. 가벼운 길은 신뢰 목록 작성자만. 원문에 따르면 신뢰 목록은 주로 그 저장소를 맡은 팀이고, 그 밖의 작성자는 사람 승인이 하나 더 필요해요. 에이전트의 승인은 절대 사람의 승인으로 치지 않아요.
  3. 지시한 사람이 필수 리뷰어. 에이전트가 쓴 PR이면 그 에이전트에게 지시한 사람이 필수 리뷰어 중 한 명이에요. 직접 타이핑한 것과 똑같이 책임져요.
  4. 승인은 그 커밋에만. 시스템이 보증할 수 없는 새 커밋(에이전트의 새 푸시, 사람이 손으로 푼 충돌)이 들어오면 승인을 다시 받아야 해요.

겹 6·7 머지 큐·단계적 배포·되돌리기 — 느려지는 대신 빨리 고친다

다 통과한 PR 두 개가 동시에 들어오면 어떻게 될까요? PR A도 B도 모든 검사를 통과했는데, 둘이 합쳐지는 순간 main이 깨질 수 있어요. 각자는 예전 main 위에서 테스트됐거든요. 해설 영상은 각자는 탑에 잘 맞는데 동시에 올리면 탑이 기우는 블록 두 개에 빗대요.

  • 머지 큐6. 변경을 최신 main 위에 얹은 상태로 모든 검사를 다시 돌려요. 따로 통과한 두 PR이 합쳐져 main을 깨뜨릴 수 없어요.
  • 직원이 먼저. 합친 뒤에도 바로 모두에게 가지 않아요. 새 기능은 보통 플래그 뒤에 숨겨 앤트로픽 직원들이 먼저 쓰고, 워낙 많이 써서 사용자보다 먼저 문제를 찾는 경우가 많대요.
  • 채널을 나눠 배포. 공개 배포는 latest 채널이 먼저, stable 채널이 그 뒤를 따라가요.

마지막 일곱 번째 겹은 빨리 알아채고 빨리 되돌리기예요. 플래그는 배포 없이 끌 수 있어요. 장애 대응 담당을 일주일씩 돌아가며 맡고, 장애가 나면 어느 겹이 잡았어야 했는지를 따져요. 한계도 밝혀요. 되돌림·사고 수치가 늘면 자동으로 사람 승인을 더 받게 하는 장치(원문 표현으로 circuit breaker)는 아직 없고, 원문에 따르면 엔지니어들은 사람 없이 합치는 변경이 더 늘기 전에 그걸 원해요.

원문이 전한 한 동료의 말이 이 겹의 이유예요. 속도를 늦추면 오류율이 떨어지긴 하지만, 그건 대부분 모든 일을 덜 해서라는 거예요. 이 팀은 느려지는 대신 문제를 알아채고 고치는 속도를 올리는 쪽을 골랐어요.

사람이 남는 곳 — 다섯 가지와 "네가 합쳤으면 네가 고친다"

그럼 일곱 겹에서 사람은 뭘 할까요? 원문은 다섯 가지를 꼽아요.

사람의 일무엇을 하나
만들지 말지 정하기방향·취향·범위. 원문에 따르면 리뷰 병목을 풀었다는 팀도 다른 팀이 보낸 변경에는 "이걸 해야 하나"를 묻는 사람 리뷰를 남겨 둬요
위험한 코드 리뷰결제, 자동 업데이터, CI 워크플로
설계 리뷰다른 사람들이 따라 할 패턴을 정하는 변경
증거 읽기테스트 출력, 실행한 명령과 결과, 스크린샷, 리뷰어의 지적. 검사를 다 통과했어도 어디가 빈틈인지 말할 수 없으면 승인 버튼만 누르지 말고 코드를 직접 읽는 리뷰를 요청해요
결과에 대한 책임누가 타이핑했든 배포되는 모든 변경에는 책임지는 사람이 한 명 있어요

문화 규칙도 하나 있어요. "네가 합쳤으면, 네가 고친다." 작거나 중간 크기의 변경이 문제를 일으키면 보통 합친 사람이 고쳐요. 가혹하지 않은 이유는 변경이 작아서 되돌리기 쉽고, 플래그·되돌리기·단계적 배포로 대부분의 실수가 몇 분 안에 풀리기 때문이에요. 탓하는 것도 아니에요. 장애 리뷰는 사람이 아니라 시스템을 봐요.

코드 리뷰엔 원래 역할이 하나 더 있었어요. 동료의 변경을 읽으며 팀 전체가 코드를 이해하는 거예요. 기계가 대부분 읽으면 그건 어떻게 할까요? 이 팀은 필요할 때 Claude에게 딱 그 부분만 설명하는 글을 써 달라고 해요. 몇 분이면 되고 오늘의 코드를 그대로 반영해요. 한 줄짜리 문구 수정을 리뷰하며 배우는 것보다, 지금 고치려는 모듈의 설명서 한 편이 훨씬 많이 가르쳐 준다는 거예요. 원문에 따르면 그 부분을 그림으로 보여 주는 작은 아티팩트를 만들게 하는 사람도 있어요.

내 팀에 옮기는 순서 — PR 전 · PR · 승인 · 합친 뒤

해설 영상 8:20의 네 칸 화면과 원문 "Adopting this on your team"을 합쳐 옮겼어요.

해설 영상이 원문 끝에서 뽑은 요약은 이래요. 리뷰가 뭔가를 놓치면 그때 모델 앞에 무엇이 없었는지를 묻고, 그 답을 CLAUDE.md나 스킬이나 새 검사에 넣는다. 사람이 더 열심히 읽는 게 아니라 같은 실수가 다음엔 저절로 걸리게 만드는 거예요. PR 병목 글의 retro가 하는 일과 같은 방향이에요. 목표는 그대로예요. 변경 하나에 드는 사람 시간은 줄이고, 되돌림은 예전보다 늘리지 않는 것.

나쁜 선택 vs 좋은 선택 — 리뷰 에이전트가 작성 에이전트와 맞물릴 때

작성 에이전트가 올린 PR에 리뷰 에이전트를 붙여 밤새 돌리기로 한 장면이에요.

나쁜 선택좋은 선택
리뷰어가 낸 지적을 작성 에이전트가 전부 고치게 하고, 고칠 때마다 PR 전체를 다시 리뷰한다 → 사소한 지적도 커밋이 되고 커밋마다 리뷰가 돌아, 아침에 보면 수십 라운드째 옛날 버그를 하나씩 고치고 있다. 투표로 걸러 스타일·정리 지적은 버리고, 3라운드가 넘으면 접근을 다시 생각하게 하고, 그 뒤엔 새 변경분만 보며 같은 버그 유형은 한 번에 고치게 한다 → 대부분 한두 라운드에 끝나고, 원래 있던 문제는 꼬리표를 달아 따로 다룬다.

겹이 하나 빠지거나 겹끼리 맞물려 헛돌면 증상으로 먼저 보여요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
리뷰 봇과 작성 에이전트가 밤새 수십 라운드를 주고받았는데 PR이 아직 안 끝났어요 PR의 리뷰 라운드 수, 지적이 가리키는 줄의 작성 시점 지적된 줄을 git blame으로 봐서 이 PR 전부터 있던 코드면 "원래 있던 문제"로 따로 빼요. 라운드 상한과 새 변경분만 다시 보기를 걸어요(밤새 50라운드)
각자 초록불이던 PR 두 개를 합쳤더니 main 빌드가 깨졌어요 두 PR이 테스트된 기준 커밋(base). 둘 다 예전 main 위였는지 머지 큐를 켜서 최신 main 위에 얹은 상태로 검사를 다시 돌린 뒤에만 합쳐지게 해요(머지 큐)
승인받은 뒤 에이전트가 새 커밋을 푸시했는데 그대로 합쳐졌어요 브랜치 보호 설정의 "새 커밋이 오면 승인 해제" 항목, 봇 승인이 필수 승인으로 세어지는지 새 커밋이 오면 승인을 풀고, 봇 승인은 필수 승인 수에서 빼요(규칙 네 개)

실행: 저장소 루트의 REVIEW.md 뼈대 — 원문이 REVIEW.md에 넣으라고 한 항목을 옮긴 예시

# REVIEW.md — (영역 이름) 리뷰 기준

## 이 영역에서 실패는 이런 모습이다
- (예: 문서) 코드와 다른 내용을 사실처럼 적는다
- (예: 설정) 요청을 엉뚱한 곳으로 보낸다

## 지적 규칙
- 이름만 보고 추측하지 말고 파일과 줄 번호를 근거로 댄다
- 사소한 지적(nit)은 최대 3개까지만 올린다
- 이 PR 전부터 있던 문제는 "원래 있던 문제"로 표시한다

## 건너뛸 경로
- (예: 생성된 파일, 벤더 코드)

## 요약 형식
- 첫 줄은 지적 개수로 시작한다
- 문제가 없으면 "문제 없음"이라고 분명히 쓴다

사소한 지적 3개는 제가 예시로 둔 값이에요. 원문은 개수를 제한하라고만 하고 숫자는 밝히지 않았어요.

함께 보기

  • PR 병목 고치기 — 에이전트 PR을 사람이 다 읽지 않아도 되는 조건 — 자동 검사·자동 리뷰·사람 리뷰 세 겹과 one-way door 기준, 반복 지적을 검사로 옮기는 retro가 이 글의 일곱 겹·위험도별 승인·"모델 앞에 무엇이 없었나"와 이어져요.
  • 합치기 전에 테스트하고 내보내기 전에 먼저 본다 — CI 테스트와 staging 환경 (5) — 필수 자동 검사와, 모두에게 내보내기 전에 먼저 보는 단계의 기본이에요.
  • AGENTS.md와 캐싱 경제학 (5) — CLAUDE.md를 짧게 두고 다른 문서를 가리키라는 이유와 이어져요.
  • 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정 (4) — 리뷰어를 바꿀 때마다 평가 세트로 다시 채점하고 오르면 남기는 방식과 같은 질문이에요.
  • 켄트 벡 — 기능 사이에서 멈춰 여지를 되찾는 법 — 에이전트가 쏟아내는 변경을 사람 쪽에서 감당하는 또 다른 시각이에요.
  1. 모노레포 — 회사의 여러 프로젝트 코드를 저장소 하나에 모아 둔 방식이에요. ↩
  2. PR(pull request) — 내가 고친 코드를 본래 코드에 합쳐 달라고 올리는 요청이에요. 리뷰와 검사가 이 단위로 돌아요. ↩
  3. 기능 플래그 — 새 기능을 코드에는 넣어 두고 켜고 끄는 스위치로 감싸 두는 방법이에요. 배포를 다시 하지 않고도 끌 수 있어요. ↩
  4. 코드 오너 — 저장소의 특정 경로를 책임지는 사람이나 팀이에요. GitHub에서는 CODEOWNERS 파일로 정하고, 그 경로가 바뀌면 리뷰를 요구할 수 있어요. ↩
  5. git blame — 파일의 줄마다 마지막으로 바꾼 커밋과 시점을 보여 주는 git 명령이에요. 어떤 줄이 이번 PR에서 생겼는지, 그 전부터 있었는지 가릴 때 써요. ↩
  6. 머지 큐 — 합칠 PR을 줄 세운 뒤, 앞선 PR까지 반영된 최신 main 위에서 검사를 다시 돌리고 통과한 것만 차례로 합치는 장치예요. ↩
