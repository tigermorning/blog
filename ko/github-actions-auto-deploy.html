앞의 세 편에서는 서비스를 설계하고 Cloud Run에 소스를 배포한 뒤 운영하면서 생기는 일을 봤어요. 그때마다 배포(만든 앱을 사람들이 쓸 수 있게 올리는 일)는 제가 명령을 쳐서 했어요. 이번에는 도장판 앱으로 해 봤어요. 이름은 routine-stamp-trial이고, index.html 하나로 된 작은 앱이에요. Cloud Run에 비공개 서비스로 올라가 있어요. 목표는 이거였어요. "main에 머지1하면 저절로 배포된다." 코드를 고칠 때마다 사람이 배포 명령을 치면 빼먹거나 실수하기 쉬우니까요. 풀어야 할 질문은 세 가지였어요.

  • 로봇(GitHub Actions2)에게 어떻게 일을 시킬까?
  • 비밀 키 파일 없이 어떻게 Google Cloud에 들어갈까?
  • 고장 난 코드가 들어오면 어떻게 될까?

이 글에서 "로봇"은 GitHub이 대신 일해 주는 컴퓨터(GitHub Actions의 러너3)를 뜻해요. 비유는 1편부터 쓰던 식당을 이어 써요.

노드 핵심 5줄 — 이번 글 전체를 먼저 요약하면

  • 워크플로4는 GitHub이 로봇에게 시키는 일 목록이에요(.github/workflows 폴더에 적어요). 언제(이벤트)와 무엇을(일)을 적는 기능이라 배포 전용이 아니에요. PR 점검(hello)도 배포(deploy)도 같은 기능이고, 이벤트와 일만 달라요.
  • main에 머지되면 로봇이 자동으로 배포한다.
  • 열쇠 파일 없이 일회용 신분증(WIF5)으로 Google Cloud에 들어간다.
  • 고장 난 배포는 손님에게 안 나가고, Revert6로 되돌린다.
  • 감사 로그7로 누가 배포했는지 확인할 수 있다.

비유로 먼저 — 사장이 직접 상자를 들고 가던 가맹점 배송을 포장 로봇에게

1편부터 이어 온 식당으로 말해 볼게요. 사장인 내가 밀키트 상자를 만들 때마다 직접 들고 가맹점(서비스)에 가서 진열한다고 해요. 그러면 바쁜 날 한 번 빼먹기 쉬워요. 그래서 "본점 장부(main)에 새 레시피가 올라오면 포장 로봇이 알아서 상자를 만들어 가맹점에 진열한다"는 규칙을 적어 줬어요. 문제는 로봇이 가맹점 본부 건물에 들어갈 때예요. 사장 열쇠를 로봇에게 복사해 주면, 열쇠가 새는 순간 아무나 들어와요. 그래서 열쇠 대신 "본점 장부에서 온 로봇에게만 그때그때 발급하는 일회용 방문증"을 썼어요.

핵심 한 줄: 사람이 하던 배포를 로봇에게 맡기되, 열쇠를 복사해 주지 말고 "내 저장소에서 온 로봇"임을 확인하는 일회용 방문증만 쓰게 한다.

한 줄 정리 사람이 하던 배포를 로봇에게 맡기되, 열쇠 대신 "내 저장소에서 온 로봇"임을 확인하는 일회용 방문증만 쓰게 해요.

다만 여기서 비유가 끊기는 점이 있어요. 컴퓨터에서는 로봇을 부르는 것도 "장부에 올라오는 순간"이라는 이벤트(일이 생겼다는 신호)예요. PR을 열 때처럼 다른 이벤트에도 같은 로봇 기능을 쓸 수 있어요. 사람이 손으로 실행 버튼을 눌러도 돼요.

머지부터 새 리비전8까지를 한 장으로 먼저 보면 이래요. 아래에서 ②~⑤를 하나씩 풀어요. 사람이 명령을 치는 칸은 없어요.

과정 1. 로봇에게 일 시키기 — PR #1, hello.yml

먼저 배포가 아닌 연습용 워크플로 hello.yml을 만들었어요. .yml은 일 목록을 적는 설정 파일이에요. PR을 열거나 손으로 실행하면 로봇이 세 칸을 차례로 확인해요.

일부러 첫 칸에 exit 1(실패로 끝내라는 명령)을 넣어 실패시켰어요. 그러면 뒤 칸은 건너뛰어요. 원인을 되돌리고(Revert) 다시 통과시킨 뒤 머지했어요. 이 연습으로 "PR → 검사 → 머지" 흐름과, 실행 기록에 event 값(pull_request, push)이 찍힌다는 것을 확인했어요.

과정 2. 열쇠 없이 들어가는 길 — WIF

GitHub 로봇이 Google Cloud에 배포하려면 신분이 필요해요. 키 파일(비밀번호 역할을 하는 파일)을 만들면 새어 나갈 위험이 있어요. 그래서 일회용 신분증(토큰)을 보여 주고 임시 권한을 받는 방식(Workload Identity Federation)을 썼어요. 구성은 이래요.

  • 사원증(서비스 계정9)을 역할별로 3개로 나눴어요. 배포용(소스 배포 + API 사용 역할만), 빌드용(빌드 역할만), 실행용(프로젝트 역할 없음)이에요.
  • 문은 3개예요. 접수처(풀), 규칙표(공급자: 내 저장소에서 온 신분증만 통과), 출입 명단(배포용 사원증을 빌려도 되는 대상)이에요.
  • 저장소 변수 5개(GCP_PROJECT_ID, WIF_PROVIDER, DEPLOY_SA, BUILD_SA, RUNTIME_SA)만 등록했고, 키 파일과 비밀 값은 저장소에 넣지 않았어요.

과정 3. 첫 자동 배포 — PR #3, #4

▼ 자세히 보기

Dockerfile(앱을 상자에 담는 설계도)과 deploy.yml을 PR #3으로 머지했어요. Dockerfile은 nginx-unprivileged10로 index.html을 서빙해요(손님 화면으로 내보내요). deploy.yml은 main에 push되면 동작하고, 권한은 contents: read와 id-token: write만 있어요. 로봇이 문 두 개를 통과하고 포장해서 올리자 리비전 00001(배포 한 번마다 생기는 버전)이 생겼어요. README만 바꾼 PR #4도 같은 길로 리비전 00002를 만들었어요. 배포는 --no-allow-unauthenticated로 비공개를 유지했어요. 권한 줄은 이런 모양이에요.

아래 두 줄은 로봇이 가질 권한을 적은 부분이에요. 읽기만 해도 돼요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

# deploy.yml 의 권한 블록(줄만 발췌)
permissions:
  contents: read    # 저장소의 코드를 읽기만 한다
  id-token: write   # 일회용 신분증(토큰)을 발급받는다

실패와 복구 — 일부러 고장 내 보기 (PR #5 → #6)

고장 난 코드가 손님에게 나가는지 확인하려고 PR #5에서 일부러 틀린 nginx 설정(웹 서버의 설정)을 넣었어요. 새 리비전 00003은 시작하지 못했어요(Cloud Run 로그: unknown directive "cache_expiry_minutes" in default.conf:5). 그래도 손님은 계속 00002를 받았어요. 다만 main에는 고장 난 코드가 남아 있어요. 그래서 PR #6(Revert)으로 되돌렸어요. 그러자 새 리비전 00004가 정상으로 시작했어요.

과제로 내 프로젝트에 적용해 보기

과제 1. 기능 하나 넣고 자동 배포 (PR #7)

화면 맨 아래에 "배포된 커밋 번호"를 보여 주는 기능을 골랐어요. index.html에 COMMIT 자리를 두고, 로봇이 배포 직전에 머지 커밋 번호(7자리)로 바꿔 넣게 했어요. PR #7을 머지하자 사람이 배포 명령을 치지 않았는데 리비전 00005가 생겼고, 화면에 v 076c27a가 떴어요. 이 번호가 머지 기록의 번호와 같다는 것으로 "방금 머지한 코드가 나갔다"를 확인했어요.

과제 2. 다른 저장소에서 배포 시도

공개 저장소 wif-reject-test를 만들어 같은 워크플로를 돌려 봤어요. 로봇이 신분증을 내밀자 규칙표에서 unauthorized_client: rejected by the attribute condition으로 거절됐고, 배포 단계는 실행되지 않았어요. 새 서비스는 생기지 않았고 기존 리비전도 그대로였어요. 내 저장소 이름이 조건으로 걸려 있어서 다른 저장소는 같은 파일을 복사해도 못 들어간다는 것을 확인했어요.

과제 3. 누가 배포했는지 감사 로그로 추적

Cloud Run 활동 감사 로그(누가 무엇을 했는지 남는 기록)를 읽기 전용으로 조회했어요. 손으로 배포한 기록은 내 Google 계정으로 남아 있어요. 자동 배포 기록은 배포용 사원증(서비스 계정)으로 남아 있어요. 그 뒤쪽 delegation 정보에는 내 저장소 이름과 refs/heads/main이 함께 찍혀 있었어요. 즉 "어느 계정"뿐 아니라 "어느 저장소의 어느 브랜치에서 온 로봇"까지 추적돼요.

과제 4. GitHub Actions 대신 다른 것을 썼다면?

내가 만든 파이프라인의 조각(누가 일하나, 무엇이 깨우나, 권한, 승인·롤백)을 기준으로 대안을 대 봤어요. 표의 "문서 확인"은 공식 문서에서 읽은 내용이고, "내 해석"은 문서를 내 프로젝트에 대 본 추정이라 실제로 해 보지는 않았어요.

▼ 자세히 보기
  • 서비스 이름을 따로 지었어요. 같은 프로젝트에 이미 있던 다른 서비스를 덮어쓰지 않으려고요.
  • 기본 서비스 계정의 비밀 값 읽기 권한은 지우지 않았어요. 같은 프로젝트의 다른 서비스가 쓸 수 있어서 지우면 깨질 수 있다고 판단했어요.
  • 배포 실패를 일부러 한 번 겪었어요. 실패가 사용자에게 안 나가고 Revert로 되돌려진다는 것을 눈으로 보려고요.

배운 점

  • 자동 배포의 핵심은 "로봇이 일하는 규칙"과 "로봇에게 빌려주는 최소한의 권한"을 분리해서 보는 것이에요.
  • 비밀 키 파일이 없어도 "어느 저장소에서 온 신분증인가"를 조건으로 걸면 안전하게 들어갈 수 있어요.
  • 배포가 실패해도 Cloud Run은 이전 리비전으로 손님을 받아서 사용자는 모르지만, main에 남은 고장은 Revert로 직접 치워야 해요.
  • 감사 로그에는 계정뿐 아니라 어느 저장소·브랜치에서 왔는지가 남아서 "누가 배포했나"를 끝까지 추적할 수 있어요.
  • 방법을 고를 때는 "무엇이 더 좋은가"보다 "내 서비스에 필요한 것(승인, 단계, 저장소 위치)이 무엇인가"가 기준이에요.

이럴 때 의심하세요 — 자동 배포가 고장 나거나 거절될 때

자동 배포 문제는 코드를 읽어서는 보이지 않아요. 배포 로그의 한 줄 문장이나 화면이 안 바뀌는 모습으로 먼저 나타나요. 여기서 막히는 게 정상이에요. 아래 증상이 보이면 코드를 고치려 들기 전에 이 자리를 열어 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "자동 배포를 만들어 줘" — 서비스 계정 키 파일을 만들거나 저장소에 비밀 값을 넣는 줄이 생겼는지, 권한 블록이 contents: read와 id-token: write를 넘는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
머지했는데 새 리비전이 시작하지 못했어요 (Cloud Run 로그에 unknown directive "cache_expiry_minutes" in default.conf:5 같은 문장이 보여요) Cloud Run 로그와, 문장이 가리키는 설정 파일 줄(이 글에서는 nginx의 default.conf 5번째 줄)이에요. 손님이 오류를 보는 것이 아니라 이전 리비전이 계속 받고 있어요 서비스 주소가 이전 리비전으로 열리는지 먼저 봐요. 그다음 main에 남은 고장 코드를 Revert PR로 되돌리고 새 리비전이 정상으로 시작하는지 봐요. 실패와 복구
로봇이 Google Cloud에서 거절돼요 (unauthorized_client: rejected by the attribute condition) WIF의 규칙표(공급자) 조건이에요. 내 저장소 이름이 조건으로 걸려 있어서, 다른 저장소나 복사한 파일은 이 문에서 막혀요. 배포 단계는 실행되지 않고 기존 리비전은 그대로예요 지금 돌린 저장소가 조건에 적힌 내 저장소가 맞는지 먼저 봐요. 맞는데도 막히면 세 문(접수처·규칙표·출입 명단)을 순서대로 확인해요. 과정 2
"이 배포를 누가 했는지 모르겠어요" Cloud Run 활동 감사 로그예요. 자동 배포 기록은 배포용 사원증(서비스 계정)으로 남고, 그 뒤쪽 delegation 정보에 저장소 이름과 refs/heads/main이 찍혀요 읽기 전용으로 조회해서 계정과 delegation 정보를 같이 읽어요. 과제 3

  • "Cloud Build 트리거로 바꿨다면 열쇠 없이 들어가기 단계가 줄었을 가능성"은 추정이에요.

  • 배포한 AI 서비스가 말없이 틀리는 순간 (3) — Cloud Run 로그에서 원인을 찾는 순서를 봐요.

  1. 머지(merge) — 합쳐 달라고 올린 요청(PR)의 고친 내용을 main 브랜치에 합치는 일이에요. ↩
  2. GitHub Actions — GitHub 저장소에 일이 생길 때(코드가 올라올 때 등) 정해 둔 작업을 자동으로 실행해 주는 기능이에요. ↩
  3. 러너(runner) — GitHub Actions의 작업을 실제로 대신 실행해 주는 컴퓨터예요. ↩
  4. 워크플로(workflow) — 언제(이벤트)와 무엇을(일)을 적어 .github/workflows 폴더에 두는 GitHub Actions의 일 목록 파일이에요. ↩
  5. WIF(Workload Identity Federation) — 키 파일 대신 일회용 신분증(토큰)을 보여 주고 Google Cloud의 임시 권한을 받는 방식이에요. ↩
  6. Revert — 이미 합쳐진 변경을 취소하는 변경을 새 PR로 만들어 되돌리는 일이에요. ↩
  7. 감사 로그 — Google Cloud에서 누가 어떤 작업을 했는지 남기는 기록이에요. ↩
  8. 리비전 — 이미지와 설정을 함께 적은 Cloud Run의 배포 기록으로, 2편에서 다뤘어요. ↩
  9. 서비스 계정 — 사람이 아니라 프로그램이 Google Cloud에 들어갈 때 쓰는 신분이에요. ↩
  10. nginx — 웹 서버 프로그램으로, 여기서는 index.html을 화면에 내보내는 역할이에요. ↩
  11. Cloud Build — Google Cloud 안에서 코드를 받아 이미지를 만들고 배포 작업을 돌리는 서비스예요. ↩
  12. Cloud Deploy — 릴리스를 환경 단계별로 나르며 승인과 롤백 기능을 갖췄다고 문서에 나온 Google Cloud의 배포 서비스예요. ↩
  13. Argo CD — 쿠버네티스 클러스터 안에서 Git 저장소의 상태에 맞춰 배포를 동기화하는 도구예요. ↩
