13편까지 채운 그래프를 돌리면 로그 다섯 줄 중 앞의 두 줄(① 수집, ② 선별)에만 숫자가 찍혀요. 뒤 세 줄은 아직 0이에요. 지금 결과물은 기사 제목과 링크 다섯 개라, 받는 사람 입장에서는 링크 목록일 뿐이에요. 이번 편에서는 링크마다 원문 본문을 가져와 읽을 만한 요약으로 바꾸는 ③ 취재 노드와, 그 요약이 원문을 벗어나지 않았는지 확인하는 ④ 검수 노드를 채워요. 12편에서 본문이 600자 넘게 뽑히는지부터 확인한 이유가 여기서 쓰여요. 본문이 없으면 모델은 제목만 보고 요약을 지어내거든요.

비유 — 칸 나눈 도시락과 그 시식 담당

11편부터 이어 온 주방이에요. 매일 아침 "오늘의 한 상" 다섯 접시를 내요. 재료 상자 다섯 개가 골라지면 헤드셰프가 상자마다 요리사를 한 명씩 부르며 9편의 그 쪽지를 건네요. 쪽지에는 자기 상자 하나만 적혀 있어요. 요리사는 요리를 한 그릇에 비벼 담지 않고 칸 나눈 도시락에 담아요. 재료로 만든 칸 둘, 주방이 따로 곁들인 양념 칸 하나예요. 완성된 도시락은 완성 선반에 차례로 쌓여요. 그러면 10편의 시식 담당이 도시락마다 재료 칸만 재료 상자와 대 보고, 통과한 것만 내보낼 보온함에 옮겨요. 떨어진 건 장부에 적고 버려요.

비유 속 요소원래 개념
헤드셰프가 요리사마다 — 상자 하나만 적힌 쪽지 건네기fan_report가 report 노드에게 — Send("report", {"item": 기사 하나})를 기사 수만큼
요리사가 도시락에 — 재료 칸 둘 + 양념 칸 하나로 나눠 담기report가 LLM에게서 — headline·summary(원문을 옮김) + why(해석)로 나눠 받기
요리사들이 완성 선반에 — 도시락을 올리면 쌓이기만 함워커들이 drafted 칸에 — 리듀서 operator.add가 합쳐요
시식 담당이 재료 상자와 — 재료 칸만 대 보기verify가 원문과 — headline·summary만 대조, why는 빼요
시식 담당이 통과한 도시락을 — 선반이 아니라 내보낼 보온함에 옮기기verify가 통과분을 — 리듀서 없는 새 칸 verified에 담아요

핵심 한 줄: 한 그릇에 비벼 담으면 어느 맛이 재료에 없는 맛인지 가려낼 수 없으니, 대 볼 수 있는 칸과 대 볼 게 없는 칸을 처음부터 나눠 담아요.

다만 여기서 비유가 끊기는 점은, 사람 시식 담당은 실수가 드물지만 이 편의 검수도 LLM이라 멀쩡한 요약을 떨어뜨리거나 틀린 요약을 통과시킬 수 있다는 거예요.

전체 흐름 — 이번 편이 채우는 ③·④

세로 점선 왼쪽은 후보를 모아서 한 번에 보는 구간, 오른쪽은 한 건씩 처리하는 구간이에요. report는 그림에 하나지만 실행할 때 기사 수만큼 불려 나와요. 아래쪽 강조색 점선은 후보가 0건인 날 report를 건너뛰는 길이에요. 이 길이 없으면 무슨 일이 생기는지는 아래에서 직접 확인했어요.

요약을 어떤 칸으로 받을까

코드보다 먼저 정할 게 있어요. 요약을 어떤 모양으로 받느냐예요. "요약해 줘"라고만 하면 문단 하나가 와요. 읽기엔 멀쩡하지만, 한 덩어리로 받는 순간 다음 단계에서 할 수 있는 일이 확 줄어요.

뉴스레터 카드 한 장에 필요한 건 셋이에요. 카드 제목(headline), 세 문장 요약(summary), 그리고 "국내 개발팀에게 왜 중요한가" 한 문장(why). 이 셋은 성질이 달라요.

칸담기는 내용무엇과 대조하나
headline원문 내용을 짧게 옮김원문 — 원문에 있는 말인지 볼 수 있어요
summary원문 내용을 세 문장으로 옮김원문
why독자 관점의 해석대조 대상 없음 — 원문 어디에도 "국내 개발팀에게"는 안 적혀 있어요

이 셋을 한 문단으로 받았다고 해 볼게요. 뒤에서 "이 문단이 원문에 근거하나?"를 물으면 why 부분은 원문에 없으니 매번 불합격이에요. 그렇다고 기준을 느슨하게 하면 진짜로 지어낸 문장도 같이 통과해요. 한 덩어리 안에서는 둘을 구분할 방법 자체가 없어요. 그래서 출력 모양을 정하는 일은 형식 문제가 아니라 "나중에 무엇을 자동으로 검사할 수 있을지"를 미리 정하는 일이에요.

생성 결과를 받는 방법은 넷쯤 떠올릴 수 있어요. 아래로 갈수록 검증은 쉬워지지만 비싸지거나 자유도가 줄어요.

받는 방법얻는 것포기하는 것
① 자유 텍스트 한 덩어리가장 자유롭고 프롬프트가 짧아요. 사람이 읽고 다듬어 보내는 뉴스레터라면 이걸로 충분해요어디까지 사실이고 어디부터 해석인지 코드가 몰라요. 검사도, 한 부분만 다시 쓰기도 막혀요
② 검증 방법이 다르면 칸을 나눈다 (고른 것)칸마다 다른 검사를 걸 수 있고, 불합격 사유도 칸 단위라 어디를 고칠지 분명해요칸이 늘수록 출력이 길어져 비용·지연이 늘고, 모델의 주의가 흩어져 칸 하나하나의 품질이 떨어질 수 있어요
③ 문장마다 근거 구절까지 함께근거를 못 대는 문장이 곧 환각이라 검증이 분명해요출력이 길어지고, 요약이 원문 표현에 묶여요. 모델이 근거 구절 자체를 지어낼 수 있어서 결국 문자열 확인이 또 필요해요
④ 요약·왜 중요한지·분류를 따로 호출프롬프트가 단순해 지시를 잘 지키고, 단계마다 모델을 달리 쓸 수 있어요호출 수만큼 비용·지연이 곱해지고, 앞 결과를 뒤에 실어 보내야 해서 토큰도 늘어요

②를 고른 이유는 뒤에 검수 단계가 있어서예요. 검수가 없으면 ①로 충분해요. ③은 "세 문장으로 건조하게"라는 요구와 부딪히고, ④는 다섯 건에 호출 열다섯 번이라 과해요. 조건이 달라지면 다른 선택지가 맞는 답이에요. 무엇을 포기했는지 알고 고르면 돼요.

칸을 나누는 기준은 하나로 정리돼요. "이 칸은 무엇과 대조할 수 있나." 원문과 대조하는 칸, 정해진 목록과 대조하는 칸(토픽 분류 같은 것), 대조할 대상이 없는 칸(해석)은 성질이 다르니 나눠요. 13편에서 선별 결과에 사건 라벨(event)을 따로 뽑은 것도 같은 이유였어요.

기사 세 건만 먼저 요약해 보기

그래프에 넣기 전에, 기사 세 건으로 세 칸 요약이 어떻게 나오는지부터 봐요. 칸 정의는 pydantic1 모델로 적고, 구조화 출력2으로 그 모양 그대로 받아요. 앞 편까지의 셀을 먼저 실행해 둔 노트북에서 이어 가요. API 키를 넣는 방법은 13편과 5편에 있어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — OpenAI API 키 필요, 결과는 실행마다 달라요

import feedparser, requests, trafilatura
from openai import OpenAI
from pydantic import BaseModel, Field

client = OpenAI()
UA = {"User-Agent": "Mozilla/5.0 (newsletter-agent)"}

class Draft(BaseModel):        # ← 방금 정한 세 칸
    headline: str = Field(description="20자 내외의 한국어 헤드라인")
    summary:  str = Field(description="세 문장 요약. ~합니다체, 과장 없이 건조하게")
    why:      str = Field(description="국내 개발팀에게 왜 중요한지 한 문장")

SYS = ("당신은 국내 개발팀을 위한 AI 뉴스레터 기자입니다.\n"
       "아래 기사 본문을 읽고 헤드라인·요약·왜 중요한지를 쓰세요.\n"
       "'주목된다·기대를 모은다' 같은 기자체 표현은 쓰지 마세요.")

feed = feedparser.parse(requests.get(
    "https://techcrunch.com/category/artificial-intelligence/feed/",
    headers=UA, timeout=20).content)

for e in feed.entries[:3]:
    downloaded = trafilatura.fetch_url(e.link)
    body = trafilatura.extract(downloaded) if downloaded else None
    if not body or len(body) < 600:          # ← 12편에서 정한 본문 기준선
        continue
    out = client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": SYS},
                  {"role": "user", "content": body[:6000]}],
        response_format=Draft).choices[0].message.parsed
    print("─" * 66)
    print("원문:", e.title[:60], f"(본문 {len(body)}자)")
    print("  헤드라인:", out.headline)
    print("  요약    :", out.summary[:120], "…")

response_format=Draft가 "이 세 칸 모양으로 답하라"는 지시예요. 돌아온 답은 out.headline처럼 칸 이름으로 바로 꺼내요.

중요꼭 기억할 것

프롬프트와 칸 설명에 "한국어"라고 적어도 그건 요청이지 보장이 아니에요. 영어 본문을 넣으면 모델이 입력 언어를 따라가 영어로 쓸 수 있고, 더 세게 강조하거나 더 큰 모델로 바꿔도 확률만 달라져요. 영어 소스를 빼는 건 뉴스레터를 망치는 길이고요. 지켜졌는지 출력만 보고 확인할 수 있는 규칙(한글이 있나)은 코드로 검사하고, 어기면 다시 요청하거나 번역 단계로 보내요.

여기서 칸 나누기의 원칙 하나가 더 보여요. 스키마가 보장하는 건 칸이 채워진다는 것이지 내용이 지시를 지켰다는 게 아니에요. headline 설명에 "한국어"라고 적었는데 영어가 들어온 게 증거예요. 7편에서 Literal이 형식만 막아 준다고 한 것과 같은 이야기예요. 형식은 스키마가, 내용은 검사가 맡아요. 그리고 쓰지도 검사하지도 않을 칸은 "있으면 좋을 것 같아서" 넣지 않아요. 출력 비용만 늘거든요.

원문의 사실을 옮기는 요약은 temperature=0으로 불러요. 올리면 단위 같은 사실이 바뀔 수 있어요. 다만 0도 같은 답을 약속하지 않고, 사실이 빠지는 것도 못 막아요. 결과가 매번 같다고 가정하거나 0을 검수 대신으로 믿지 말고, 사실 확인은 검수에 맡겨요.

기사 수만큼 펼치기 — Send로 취재 노드 채우기

앞의 두 노드는 같은 이름의 함수를 다시 정의하는 것으로 끝났어요. 취재는 조금 달라요. 기사마다 본문을 가져오고 LLM을 한 번씩 부르니, 한 건씩 차례로 하면 다섯 배 걸려요. 게다가 몇 건일지는 실행해 봐야 알아요. 선별이 세 건을 넘길 수도, 다섯 건을 넘길 수도 있어요.

개수를 실행해 봐야 아는 일을 동시에 돌리는 장치가 9편의 Send였어요. 조건부 엣지 함수가 노드 이름 대신 Send 목록을 돌려주면, 그 개수만큼 같은 노드가 불려 나와요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 위 셀까지 실행해 둔 노트북에서 이어 가요, OpenAI API 키 필요

from langgraph.types import Send

class ReportIn(TypedDict):                     # 워커가 받는 것은 기사 하나뿐
    item: dict

def extract_body(url):
    d = trafilatura.fetch_url(url)
    return trafilatura.extract(d) if d else None

def draft(body):
    return client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": SYS},
                  {"role": "user", "content": body[:6000]}],
        response_format=Draft).choices[0].message.parsed

def fan_report(s: dict):                      # 기사 수만큼 워커를 펼친다
    return [Send("report", {"item": it}) for it in s["picked"]] or "verify"   # ← 0건이면 verify로

def report(s: ReportIn) -> dict:               # ③ 취재 — 기사 한 건을 맡는다
    it = s["item"]
    body = extract_body(it["url"])
    if not body or len(body) < 600:            # ← 12편에서 정한 본문 기준선
        return {"drafted": [],
                "log": [f"③ 취재   제외 {it['source']} · 본문 {len(body or '')}자"]}
    d = draft(body)
    return {"drafted": [{**it, "body": body[:6000], **d.model_dump()}],
            "log": [f"③ 취재   {it['source']} · 본문 {len(body)}자"]}     # ← 성공해도 한 줄

def build():                                   # 엣지 한 줄이 팬아웃으로 바뀐다
    g = StateGraph(Brief)
    for name in ("collect", "select", "report", "verify", "publish"):
        g.add_node(name, globals()[name])
    g.add_edge(START, "collect")
    g.add_edge("collect", "select")
    g.add_conditional_edges("select", fan_report, ["report", "verify"])   # ← 고정 엣지 대신
    g.add_edge("report", "verify")
    g.add_edge("verify", "publish")
    g.add_edge("publish", END)
    return g

for line in run()["log"]:
    print(line)

바뀐 건 select 뒤의 엣지 한 줄과 report 함수뿐이에요. State도, 앞뒤 노드도 그대로예요. 짚을 곳은 셋이에요.

  • 리듀서가 여기서 값을 해요. 다섯 워커가 각자 {"drafted": [한 건]}을 돌려주면, 11편에서 drafted에만 붙여 둔 리듀서가 한 목록으로 합쳐요. 리듀서가 없으면 동시에 같은 칸에 쓰다가 8편의 InvalidUpdateError가 나요.
  • 워커는 기사 하나만 알아요. Send의 두 번째 값 {"item": 기사 하나}가 워커가 받는 전부예요(9편에서 확인한 성질). 다른 기사가 뭔지, 몇 건 처리됐는지 몰라요. 대신 워커 하나를 떼어 시험하기 쉽고 서로 간섭하지 않아요.
  • 본문이 모자라면 빈 목록을 돌려줘요. 다섯 건을 골랐어도 네 건만 요약될 수 있고, 빠진 사실은 로그에 남아요. 그런 날은 네 건만 내보내요. 모자란다고 다시 긁어 오지 않아요.

"0건이면 verify로", "성공해도 한 줄" 주석을 단 두 줄은 빠뜨려도 에러가 안 나는 자리예요. report의 성공 쪽 return에 "log"가 없으면 잘 요약된 기사가 로그에서 사라지고, fan_report 끝에 or "verify"가 없으면 후보가 0건인 날 뒤 노드가 하나도 안 돌아요. 두 줄을 빼고 돌린 결과는 아래 가짜 실행에 있어요.

어디서부터 펼칠까 — 팬아웃 경계

여러 벌로 펼칠 수 있는 구간과 없는 구간의 경계를 팬아웃3 경계라고 부를게요. 이 파이프라인에서는 선별이 끝난 지점이에요. 앞은 모아서 한 번에, 뒤는 한 건씩이에요.

경계를 잘못 그으면 결과가 조용히 달라져요. 선별을 기사별로 펼쳤다고 해 봐요. 워커마다 자기 기사 하나만 보고 "중요하다"고 답하니, "다섯 건 고르기"가 기사마다 따로 점수 매기기로 바뀌어요. 13편에서 점수 대신 한 화면 비교를 고른 이유가 통째로 사라지는데, 프로그램은 잘 돌고 결과만 달라져요. 반대로 펼칠 수 있는데 안 펼치면 시간만 몇 배 들고요.

경계를 찾는 질문은 하나예요. "이 단계는 다른 항목을 봐야 답할 수 있나?" 봐야 하면 경계 앞(모아서), 안 봐도 되면 경계 뒤(펼침)예요. 중복 판정·상대평가·건수 상한은 앞, 본문 추출·요약·원문 대조는 뒤예요. 경계는 보통 한 곳이고, 거기서 Send를 한 번 써요.

펼치면 시간은 줄지만 비용은 안 줄어요. 다섯 건이면 토큰도 다섯 배 그대로예요. 동시 호출이 많으면 요청 한도에 걸려 429 응답이 오기도 해서, 후보가 수십 건인 단계를 무심코 펼치면 안 돼요. 한 갈래가 실패했을 때의 처리를 안 정해 두면 그 건만 조용히 빠진 채 합쳐지니, 빠진 건수를 로그에 남겨요.

중요꼭 기억할 것

어느 단계를 한 건씩 펼칠지는 "이 단계는 다른 항목을 봐야 답할 수 있나"로 정해요. 봐야 하는 단계(중복 판정·상대평가)를 펼치면 에러 없이 결과만 틀려지고, 안 봐도 되는 단계(본문 추출·요약)를 안 펼치면 시간만 늘어요. 펼쳐도 비용은 그대로라 요청 한도와 빠진 건수 기록을 같이 챙겨요.

매끄럽다고 맞는 건 아니다 — 검수

요약은 매끄럽게 나와요. 그런데 매끄러운 것과 정확한 것은 달라요. 모델이 지어낸 문장(환각4)도 똑같이 매끄럽거든요. 사람이 매일 다섯 건을 원문과 대조하면 확실하지만, 그럼 자동화한 의미가 없어요. 기계가 할 검사가 필요해요.

먼저 떠오르는 방법 — 요약의 숫자를 원문에서 찾기

숫자는 환각이 가장 티 나는 자리고, 문자열 비교라 비용도 들지 않아요. 요약에 나온 숫자를 뽑아 원문에 있는지 세어 봤어요. 예문은 가상의 회사·투자사·수치로 만들었어요. 영어 기사를 한국어로 요약한 상황이고, 요약에는 틀린 내용이 없어요.

검사는 시킨 대로 정확히 돌았어요. 2와 4500은 정말로 원문 어디에도 없어요. 그런데 요약은 틀리지 않았어요. "two months"가 "2개월"이 된 건 영어는 낱말로, 한국어는 숫자로 적어서고, "$45 million"이 "4500만 달러"가 된 건 단위 체계를 바꿔 적어서예요. 번역과 단위 환산을 환각으로 잡은 오탐5이 두 건이에요. 영어 기사를 한국어로 요약하는 한 거의 매번 이렇게 떨어져요.

반대쪽 구멍도 있어요. 3이 통과한 건 "3억"이 맞아서가 아니라 $300이라는 글자 안에 3이 들어 있어서예요. 궁금해서 요약의 "약 3억 달러"를 틀린 값인 "약 30억 달러"로 바꿔 다시 돌렸더니, 30도 300 안에 들어 있어서 틀린 숫자가 그대로 통과했어요(원문에 없는 숫자 목록이 ['2', '4500'] 그대로였어요). 맞는 숫자는 떨어뜨리고 틀린 숫자는 통과시킨 거예요. temperature 실험의 실제 요약에서도 같은 구멍이 보여요. 30인치를 30피트로 바꾼 요약을 위 코드에 넣었더니 원문에 없는 숫자가 []로 나와 합격이었어요. 6과 30은 원문에도 있고, 바뀐 건 숫자가 아니라 단위 부호였으니까요.

그렇다고 "숫자 검사는 쓸모없다"는 결론은 성급해요. 정규식에 버그가 있는 것도 아니고, 검사가 틀린 것도 아니에요. 대조하는 방식이 틀렸어요. 문자열 "4500"과 "45 million"은 다르지만 값은 같아요. 글자를 비교하는 한 이건 안 풀려요. 한국어 요약을 포기하면 오탐은 사라지지만 뉴스레터의 목적을 버리는 거고, 숫자 칸을 검사에서 빼면 환각이 가장 잘 드러나는 자리를 버리는 거예요. 필요한 건 뜻을 비교하는 대조예요.

중요꼭 기억할 것

숫자 대조가 "2개월"과 "4500만 달러"를 환각으로 잡았다면, 검사는 정상으로 돌았고 문자열 일치라는 대조 방식이 번역·단위 환산을 못 다룬 것이에요. 정규식 버그가 아니고(그 숫자들은 정말 원문에 없어요), 한국어 요약을 포기하거나 숫자를 검사에서 빼는 건 답이 아니에요. 원문과 요약의 뜻을 견주는 대조로 바꿔요.

무엇으로 확인할까 — 네 가지 방법

요약이 원문을 벗어나지 않았는지 확인하는 방법을 늘어놓으면 이래요. 아래로 갈수록 정확하지만 비싸요.

확인 방법얻는 것포기하는 것
① 검수 안 함비용 0. 사람이 매일 읽는 작은 발행물이면 현실적이에요틀린 정보가 나가도 아무도 몰라요. 뉴스레터는 신뢰가 전부라 오보 한 번이 구독 해지로 이어져요
② 규칙 검사 (숫자·고유명사 대조)비용 0, 늘 같은 판정(결정론적6). 같은 언어끼리는 잘 들어요번역·단위 환산을 전부 오탐해요. "업계 최초로" 같은 숫자 없는 과장은 못 잡아요
③ LLM 대조 (고른 것)뜻을 비교해서 번역·환산은 통과시키고 숫자 없는 과장도 잡아요호출 비용·지연이 들고, 판정 자체가 확률적이라 검사하는 쪽도 틀릴 수 있어요
④ 근거 문장 함께 출력분명하게 판정하면서 뜻도 다뤄요출력이 길어지고, 근거 구절을 지어낼 수 있어 문자열 확인이 또 필요해요. 요약의 자유도가 크게 줄어요

입력이 영어와 한국어로 섞여 있으니 ②는 구조적으로 오탐이 나요. ④는 앞에서 칸을 정할 때 이미 접었고("세 문장으로 건조하게"와 부딪혀요), ①은 신뢰가 전부인 물건에서 위험해요. 그래서 ③이에요.

그리고 범위를 좁혀요. 대조는 headline과 summary만 하고 why는 검수에서 빼요. 칸을 나눠 둔 값이 여기서 나와요. why는 해석이라 원문 근거가 있을 수 없고, 대조하면 매번 불합격이거든요.

검수 노드 — 생성과 분리된 호출로

검수는 모델이 만든 결과물을 원본과 대조해 통과·불합격을 매기는 별도 단계예요. 10편 평가자-최적화자의 평가자 자리이고, 불합격한 것만 다시 쓰게 하면 그 루프가 돼요. 생성 단계에 "정확하게 쓰세요"라고 적는 것만으로는 부족해요. 프롬프트는 요청이지 보장이 아니니까요. 그리고 판정은 생성과 분리된 호출에 맡겨요. 방금 쓴 쪽에게 "네가 쓴 게 맞아?"라고 물으면 대체로 맞다고 답하거든요. LLM에게 채점을 맡길 때의 한계는 LLM-as-a-Judge 글에서 따로 다뤘어요.

검수 출력도 칸으로 받아요. 합격 여부(ok)와 문제 부분(problems)이에요. 어디가 문제인지 알아야 나중에 그 부분만 고칠 수 있으니, 앞에서 세운 칸 나누기 원칙이 검수 출력에도 그대로 적용돼요.

불합격한 요약은 어떻게 할까요. 그 자리에서 지적을 붙여 다시 쓰게 하면 한 건을 건지지만 호출이 늘고 재시도 이력이 노드 안에 숨어요. 취재 노드로 되돌아가는 엣지를 그리면 그래프에 보이긴 하지만, 다섯 건 중 한 건 때문에 단계 전체가 한 번 더 돌아요. 저는 버리고 로그에 남기는 쪽을 골랐어요. 발행 규칙이 "검수를 통과한 만큼 그대로"로 단순해지거든요. 본문이 없어 빠지든 검수에서 떨어지든 결과는 "그날은 네 건"이고, 로그에 남으면 충분해요. 되돌아가는 길을 붙이는 순간 "언제까지 다시 시도하나"를 정해야 하고, 재시도 횟수·비용 상한·중복 누적이 줄줄이 따라와요.

검수는 취재와 달리 펼치지 않았어요. 펼칠 수도 있지만, 다섯 건이면 한 노드 안에서 차례로 도는 게 단순하고 동시 호출도 줄어요. 펼칠 수 있다고 늘 펼칠 필요는 없어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 위 셀까지 실행해 둔 노트북에서 이어 가요, OpenAI API 키 필요

class Verdict(BaseModel):
    ok:       bool      = Field(description="요약이 원문에 근거하면 true")
    problems: list[str] = Field(description="근거 없는 부분. 없으면 빈 목록")

SYS_CHECK = ("요약이 원문에서 뒷받침되는지 판정하세요.\n"
             "헤드라인과 요약만 보고 판단하고, 번역이나 단위 환산은 문제가 아닙니다.")

def check(d):
    user = (f"[원문]\n{d['body'][:5000]}\n\n"
            f"[헤드라인]\n{d['headline']}\n\n[요약]\n{d['summary']}")
    return client.chat.completions.parse(
        model="gpt-4.1-mini", temperature=0,
        messages=[{"role": "system", "content": SYS_CHECK},
                  {"role": "user", "content": user}],
        response_format=Verdict).choices[0].message.parsed

class Brief(TypedDict):                        # State에 칸을 하나 더한다
    hours:     int
    collected: list
    picked:    list
    drafted:   Annotated[list, operator.add]
    verified:  list                            # ← 검수를 통과한 것
    log:       Annotated[list, operator.add]

INIT = {**INIT, "verified": []}

def verify(s: dict) -> dict:                  # ④ 검수 — 빈 노드를 갈아 끼운다
    kept, dropped = [], []
    for d in s["drafted"]:
        (kept if check(d).ok else dropped).append(d)
    return {"verified": kept,                  # 리듀서 없는 새 칸에 담는다
            "log": [f"④ 검수   {len(s['drafted'])} → {len(kept)}건"
                    + (f" · 불합격 {[x['source'] for x in dropped]}" if dropped else "")]}

for line in run()["log"]:
    print(line)

이 셀을 돌리면 로그에 ④ 검수 N → M건 줄이 생기고, 떨어진 게 있으면 뒤에 출처가 붙어요. 몇 건이 떨어질지는 실행마다 달라요.

걸림돌이 하나 있었어요. drafted에는 리듀서가 붙어 있어요. 워커 결과를 합치려고 붙인 건데, 검수는 반대로 줄이는 일이에요. operator.add가 붙은 칸에 통과분만 돌려주면 줄지 않고 기존 목록 뒤에 이어 붙어서 오히려 늘어나요. 그래서 통과분은 verified라는 새 칸에 담아요. 합치는 칸과 줄이는 칸을 나눈 거예요. State에 칸이 하나 늘었지만 노드는 자기가 바꾼 칸만 돌려준다는 규칙 덕분에 다른 노드는 하나도 안 고쳤어요. verified를 읽는 건 15편의 발행 노드예요. 그 전까지 ⑤ 줄은 11편의 빈 노드가 drafted 건수를 세서, 검수 뒤 숫자보다 클 수 있어요.

class Brief를 다시 정의하는 셀도 꼭 실행해야 해요. build()는 부를 때마다 그 순간의 Brief로 그래프를 짜서 새 칸이 들어가는데, 이 셀을 빠뜨리면 에러 없이 verified가 사라져요. 이것도 아래 가짜 실행에서 확인했어요.

비용도 적어 둘게요. 기사마다 생성 1번 + 검수 1번이라 호출이 두 배예요. 불합격을 다시 쓰게 했다면 한 건에 3번이고, 재시도 상한이 없으면 비용을 통제할 수 없어요. 그리고 검수도 LLM이라 틀려요. 멀쩡한 요약을 떨어뜨리기도, 진짜 환각을 통과시키기도 해요. 검수가 주는 건 정확성 보장이 아니라 틀릴 확률이 줄어드는 것이에요. 이 둘을 헷갈리면 검수를 믿고 다른 안전장치를 빼게 돼요.

검수가 제대로 도는지는 결과물만 봐서는 몰라요. 검수가 고장 나도 아무 증상이 없거든요. 불합격 0건, 모든 게 매끄럽게 발행돼요. 12편에서 본 조용한 실패가 검사 장치 자체에서도 일어나는 거예요. 그래서 실행마다 불합격 건수를 세어 두고, 그 수가 계속 0이면 좋은 소식이 아니라 확인할 신호로 봐요. 가장 확실한 확인은 요약에 없는 숫자를 손으로 넣은 요약이 check에서 떨어지는지 보는 거예요. 반대로 불합격이 너무 많으면 기준이 과하거나 취재 프롬프트가 잘못된 거고, 다시 써도 계속 떨어진다면 요약이 아니라 본문 추출이 원인일 수 있어요. 기록을 어디에 쌓는지는 16편에서 다뤄요.

왜 중요한가 칸은 검수 안 해도 괜찮을까

괜찮지 않아요. 위험해요. why는 독자가 "이걸 읽을까 말까"를 판단하는 칸인데, "업계 판도를 바꿀" 같은 과장이나 원문에 없는 사실이 섞여도 지금 구조에서는 아무것도 거르지 않아요. 원문과 대조할 수 없다는 게 검사하지 않아도 된다는 뜻은 아니에요. 줄이는 방법은 여럿이에요.

  1. 정의를 바꿔 대조할 수 있게 만들어요. why 칸 설명을 "요약에 있는 내용만 근거로, 새 사실은 더하지 말 것"으로 바꾸면 대조 대상이 원문 대신 summary가 돼요. 그러면 검수에 넣을 수 있어요.
  2. 규칙 검사를 걸어요. why에 나온 숫자·고유명사가 summary에 있는지 봐요. 둘 다 한국어라 앞에서 실패한 문자열 대조가 여기서는 잘 들어요.
  3. 형식을 묶어요. 한 문장, 길이 상한, "최초·혁신적" 같은 단정 표현 금지 목록을 둬요.
  4. 발행 화면에서 해석임을 표시해요. 사실 줄과 따로 떨어진 줄에 두면 독자가 둘을 구분해요.
  5. 가끔 사람이 표본을 읽어요. 자동 검사로 못 잡는 과장은 이 방법밖에 없어요.

중요꼭 기억할 것

원문과 대조할 수 없는 해석 칸(why)을 검수에서 뺐다고 그 칸이 안전한 건 아니에요. 과장이나 원문에 없는 사실이 그대로 나가요. 그래서 "요약에 있는 내용만 근거로"라고 정의를 바꿔 대조 대상을 summary로 만들고, 같은 언어끼리의 숫자·고유명사 대조, 형식 제약, 발행 화면에서 해석 표시, 사람의 표본 확인을 겹쳐 위험을 줄여요.

키 없이 그래프만 돌려 보기 — 가짜 함수로 확인한 네 가지

나쁜 선택 vs 좋은 선택 — 요약을 받아 검수할 때

같은 주방에서, 영어 기사 다섯 건을 한국어 요약으로 받아 원문과 대 보는 상황이에요.

나쁜 선택좋은 선택
무엇을 했나: "헤드라인과 요약, 왜 중요한지를 써 줘"라고 해서 한 문단으로 받고, 그 문단 전체에 요약의 숫자가 원문에 있는지 문자열로 대조했어요.

무슨 일이 생기나: "왜 중요한가" 문장은 원문에 없어서, "2개월"·"4500만 달러"는 번역·환산이라서 거의 매일 불합격이에요. 불합격을 줄이려 기준을 풀면 "30억 달러" 같은 틀린 숫자도 통과하고, 문단 어디가 문제인지 몰라 "다시 써"밖에 못 해요.		 무엇을 했나: headline·summary·why 세 칸으로 받고, 원문을 옮긴 두 칸만 생성과 분리된 LLM 호출로 뜻을 대조했어요. 한글 여부는 코드로 따로 세고, why는 "요약에 있는 내용만 근거로"라고 정의했어요.

무슨 일이 생기나: 번역·환산은 통과하고 근거 없는 문장은 칸 이름과 함께 걸려요. 떨어진 건 빼고 로그에 남기니, 그날 몇 건이 왜 빠졌는지 다음 날 볼 수 있어요.

증상이 아직 없어도, AI에게 "기사마다 동시에 요약하게 해 줘"나 "검수 통과한 것만 남겨 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
프롬프트와 칸 설명에 "한국어"라고 적었는데, 영어 기사의 헤드라인·요약이 영어로 나와요. 한국어 기사는 멀쩡해요 프롬프트 문장이 아니라, 요약을 받은 직후 결과를 검사하는 코드가 있는지예요. 프롬프트를 더 세게 고치는 건 범인을 잡는 자리가 아니에요 re.search(r"[가-힣]", 요약)으로 한글이 있는지 세어, 없으면 다시 요청하거나 번역 단계로 보내요 (한국어라고 두 번 적었는데)
후보가 없던 날 실행 로그가 ② 선별 줄에서 끝나고 ③④⑤ 줄이 하나도 없어요. 에러는 없고, "오늘은 없음" 알림도 안 와요 Send 목록을 돌려주는 함수(fan_report)의 return과, add_conditional_edges의 갈 수 있는 곳 목록이에요 선별이 빈 목록을 돌려주게 잠깐 바꿔 돌려요. ④ 줄이 안 찍히면 목록이 빌 때 돌려줄 노드 이름(or "verify")이 없는 거예요 (가짜 실행 2번)
요약이 다 된 날인데 로그에 ③ 취재 줄이 없거나 "제외" 줄만 있어요 워커 노드(report)의 성공 쪽 return 딕셔너리에 "log"가 있는지예요. 실패 쪽만 로그를 남기는 경우가 흔해요 본문 길이를 넉넉하게 준 가짜로 돌려 ③ 줄 수가 기사 수와 같은지 봐요 (가짜 실행 1번)
검수 줄은 4 → 3건인데 뒤에서 세면 7건이고, 떨어뜨린 기사가 발행 목록에 섞여 있어요 검수 노드의 return이 어느 칸에 쓰는지, 그 칸에 Annotated[list, operator.add]가 붙어 있는지예요. 검수 모델은 범인이 아니에요 줄이는 결과는 리듀서 없는 새 칸(verified)에 담고, 뒤 노드가 그 칸을 읽는지 확인해요 (가짜 실행 3번)
검수 로그는 멀쩡히 찍혔는데 결과에 verified가 없거나, 발행 노드에서 KeyError: 'verified'가 나요 노트북에서 class Brief를 다시 정의한 셀을 실행했는지, 그 뒤에 run()(안에서 build())을 다시 불렀는지예요 Brief.__annotations__를 찍어 verified가 있는지 봐요. 없으면 재정의 셀부터 다시 실행해요 (가짜 실행 4번)
