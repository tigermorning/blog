직접 Ollama로 로컬 LLM 돌려보기

2026. 8. 6.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

← 이전 편 KV 캐시와 VRAM — 내 컴퓨터에 들어갈지 계산하기

여기까지는 계산이었어요. 파라미터 수에 바이트를 곱하고, 양자화로 나누고, KV 캐시를 더해서 "이 모델은 내 그래픽카드에 들어간다"는 숫자를 얻었죠. 그런데 숫자는 거짓말을 하지 않지만 전부를 말해주지도 않아요. 들어가긴 들어가는데 답변이 한 글자씩 뚝뚝 끊겨 나오는지, 사람이 타자 치는 속도보다 빠른지는 계산식이 알려주지 않아요. 그건 손으로 만져봐야 알았어요.

설치는 십 분이면 끝난다 — Ollama

로컬에서 모델을 돌리는 도구는 여럿이지만 Ollama를 썼어요. 모델 가중치를 내려받고, 하드웨어에 맞는 추론 엔진을 골라 붙이고, 채팅 인터페이스와 HTTP API까지 한 번에 얹어주는 프로그램이에요. 원래 CUDA 버전을 맞추고 GGUF 파일 경로를 지정하고 컴파일 옵션을 고르는 일이었는데, 그 전부를 명령어 한 줄 뒤로 숨겨놨어요. 자주 쓰는 명령은 ollama pull(내려받기), ollama run(대화 시작), ollama list(받아둔 목록), ollama ps(지금 메모리에 올라간 모델과 크기), ollama stop(내리기) 정도였어요. 이 중 ollama ps는 나중에 아주 중요해지는데, 모델이 GPU에 온전히 올라가 있는지 자리가 모자라 CPU로 밀려났는지를 알려주는 유일한 창구이기 때문이에요.

설치나 하드웨어 확인처럼 환경이 다 다른 단계는 코딩 에이전트에게 맡기는 게 정확했어요. "이 머신의 OS, GPU, VRAM, RAM을 조사해서 표로 보여주고, 공식 배포 경로로만 설치하고, GPU 가속이 실제로 되는지 판정해줘"처럼 목적과 조건만 주면, 에이전트가 제 환경에 맞춰 명령을 만들어 실행했어요.

실험 1 — 크기 사다리를 올라가며 같은 질문 던지기

처음부터 큰 모델을 받으면 안 됐어요. 순서는 항상 작은 것부터였어요. Ollama 공식 라이브러리에는 회사들이 가중치를 공개한 모델이 크기별 태그로 올라와 있는데, 사다리가 촘촘한 계열 하나를 골라 0.8B부터 27B까지 단계별로 받았어요. 테스트 질문은 네 종류였어요 — 사실 확인형(짧고 정답이 분명한 질문, 작은 모델도 곧잘 맞혀요), 다단계 추론형(조건 여러 개를 동시에 만족시켜야 하는 문제, 여기서 크기가 갈리기 시작해요), 지시 준수형(JSON처럼 출력 형식을 엄격히 요구, 작은 모델은 내용은 맞혀도 형식을 자주 흘려요), 지구력형(긴 입력과 긴 출력을 함께 요구, 답이 길어질 때 품질이 유지되는지 봐요).

결과를 관찰하면서 배운 게 몇 가지 있었어요. 크기가 커질수록 eval rate(초당 생성 토큰 수)는 대역폭에 비례해 느려졌지만, 사실 확인형에서는 크기 차이가 거의 안 보였어요. 크기의 진짜 값어치는 다단계 추론과 지시 준수에서 드러났어요. 특히 지시 준수형은 에이전트를 만들 때 가장 중요한 지점이었는데, JSON 한 글자가 어긋나면 파이프라인 전체가 멈추기 때문이에요. 그리고 "큰 모델은 무조건 느리다"는 늘 맞지는 않았어요 — 앞서 본 MoE 구조는 전체 파라미터가 커도 토큰 하나를 만들 때는 일부 전문가만 깨우기 때문에, 용량에서 짐작하는 것보다 훨씬 빠르게 돌았어요.

실험 2 — 같은 모델을 4비트와 8비트로 나란히 돌리기

양자화를 눈으로 확인할 차례였어요. 같은 모델의 q4_K_M 태그와 q8_0 태그를 둘 다 받아서, ollama list로 실제 디스크 점유량이 페이지에 표시된 용량과 일치하는지 대조했어요. 그다음 같은 프롬프트를 온도 0, 같은 seed로 두 버전에 넣어 응답을 비교했어요(온도와 seed를 고정한 이유는, 답이 갈렸을 때 그게 양자화 때문인지 그냥 뽑기 운 때문인지 가르기 위해서였어요).

결과는 예상과 비슷했어요. 용량과 속도는 두 배가량 벌어졌는데, 품질 차이는 짧은 질문에서 거의 안 보였어요. 차이가 드러나는 곳은 길고 조건이 많은 추론, 그리고 드물게 등장하는 고유명사나 숫자를 정확히 기억해야 하는 자리였어요. 그래서 실무의 기본값은 4비트이고, 8비트는 "이 작업에서 4비트가 실제로 틀리는 것을 확인했을 때" 올리는 선택지라는 게 납득이 갔어요.

실험 3 — 컨텍스트를 늘려 메모리가 어디로 가는지 보기

가장 중요한 실험이었어요. 앞에서 계산으로 배운 KV 캐시 함정을 실제로 재봤어요. 재미있었던 건, num_ctx(컨텍스트 창 설정)만 키우고 짧은 문장을 넣었을 땐 메모리가 전혀 안 늘었다는 거예요. 창을 넓게 열어둔 것일 뿐 채운 게 없었기 때문이에요. 진짜 변수는 실제로 밀어 넣는 입력 토큰 수였어요. 실측해보니 토큰 하나당 캐시가 정직하게 선형으로 늘었고, 7만 토큰을 밀어 넣으면 답을 한 글자도 쓰기 전에 2분 넘게 기다려야 했어요. 긴 문서를 통째로 붙여넣는 습관의 값이 여기 있었어요.

결과를 확인하는 명령이 ollama ps였어요. PROCESSOR 열에 100% GPU가 찍히면 전부 GPU에 올라간 것이고, 예를 들어 48%/52% CPU/GPU처럼 찍히면 계산의 절반 가까이가 CPU 쪽으로 밀려났다는 뜻이에요. 중요한 건 이 값이 절반을 넘는 순간이 아니라 처음으로 0을 벗어나는 순간이었어요. 1퍼센트만 밀려나도 그 층은 매 토큰마다 시스템 메모리를 왕복하기 때문에, 속도는 그 지점에서 이미 꺾여요.

Ollama Cloud — 이름은 정직하지만 조심할 것

Ollama 자체가 제공하는 클라우드 실행도 있었어요. 태그 뒤에 -cloud를 붙이면 명령어와 인터페이스는 그대로인 채 실제 연산만 Ollama의 데이터센터에서 수행돼요. 노트북에서는 절대 못 돌릴 크기의 모델을 같은 도구로 만져볼 수 있다는 점에서 유용했지만, 눈여겨볼 게 있었어요. 로컬 도구로 알고 쓰던 그 명령어에, 똑같은 모양으로 원격 경로가 딸려 있다는 점이에요. 블로그에서 명령어를 복사해 붙이거나 모델 목록에서 무심코 하나 고르는 순간, 데이터가 기기를 벗어나요. 알아채는 방법도 하나 익혀뒀어요 — 클라우드 모델은 ollama signin으로 계정 로그인이 필요하니, 로그인을 묻는다면 그건 밖으로 나가는 길이라는 뜻이었어요. 다음 글에서는 이렇게 직접 겪어본 로컬 모델의 한계를 바탕으로, 로컬과 API 중 무엇을 고를지 판단하는 세 갈래의 선택지를 볼게요.
