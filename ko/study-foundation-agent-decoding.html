이 책이 "설계 패턴" 32가지 틀을 쓰는 이유는? 신입사원 매뉴얼 비유가 짚는 것은?

모범답

GenAI를 실서비스에 넣으면 같은 문제(문체 이탈, 환각, 내부 지식 부재)가 반복된다. 그때마다 바닥부터 고민하지 말고, 이미 검증된 해법을 "문제 → 해법 → 예시 → 고려사항" 형태로 찾아 쓰라는 게 이 책의 구성이다. 회사가 신입사원을 뽑을 때마다 "자주 겪는 문제 대응 매뉴얼"을 서랍에서 꺼내주는 것과 같다.

직접 검증해볼 것

저장소의 06_basic_rag 폴더를 열어, "문제 → 해법 → 예시 → 고려사항"이라는 발제 템플릿이 실제 코드 구성에도 그대로 나타나는지 확인해보라(README와 노트북 순서).

확인 포인트: 32개 패턴 폴더가 전부 00_introduction부터 32_guardrails까지 책의 패턴 번호·이름과 1:1로 매칭돼 있다 — "패턴집" 구조가 텍스트뿐 아니라 저장소 폴더 구조 자체로 구현돼 있는 셈이다. 사내 문서를 모르는 모델이 휴가 규정을 지어내는 사고가 나면, 바로 이 06_basic_rag가 "질문에 답하기 전 실제 문서를 먼저 찾아보게" 만드는 해법의 실행 가능한 코드다.

F2

시스템 프롬프트와 사용자 프롬프트는 뭐가 다른가?

모범답

시스템 프롬프트는 "너는 이런 역할, 이런 태도로 답해"라고 한 번 정해두는 규칙이고, 사용자 프롬프트는 그때그때 실제로 부탁하는 내용이다. prompt라는 말 자체가 연극 무대에서 배우에게 다음 대사를 귀띔해주는 "프롬프터"에서 왔다.

직접 검증해볼 것

위 F3·A1·L1의 모든 예제 코드를 다시 훑어보라 — Agent(MODEL_ID, system_prompt="...")와 agent.run_sync("...")가 각각 몇 번씩 나오는지, 그 둘에 들어가는 문자열의 성격이 어떻게 다른지 비교해보라.

확인 포인트: system_prompt엔 "You are an inventory manager who orders just in time", "You are an expert on art history" 처럼 매번 안 바뀌는 역할·태도가 들어가고, run_sync(...)엔 재고 데이터·그림 설명처럼 그때그때 바뀌는 실제 요청이 들어간다 — 책 세 노트북 모두 이 구분을 코드로 그대로 지킨다. 쇼핑몰 챗봇을 짠다면 "환불 정책"은 system_prompt에, "3번 주문 환불해주세요"는 run_sync 인자로 가야 한다는 뜻이고, 이 구분이 무너지면(예: 정책을 매 요청마다 반복 삽입) 토큰 낭비와 관리 부담이 커진다.

F3

제공업체 API를 직접 호출하는 것과 LLM 비종속적 프레임워크를 쓰는 것, 차이는?

모범답

제공업체 API 직접 호출은 그 회사가 정한 창구 양식에 딱 맞춰 코드를 짜야 한다. 프레임워크는 "채용 대행사"처럼 여러 회사의 양식 차이를 대신 흡수해준다 — 회사 이름표만 바꿔 끼워도 같은 방식으로 모델을 부를 수 있다.

📓 examples/00_introduction/building_on_apis.ipynb 
## 직접 호출
import anthropic
client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
completion = client.messages.create(
    model="claude-3-7-sonnet-latest",
    system="You are an expert Python programmer.",
    max_tokens=1024, temperature=0.3,
    messages=[{"role": "user", "content": [{"type": "text",
        "text": "Write code to find the median of a list of integers."}]}]
)
print(completion.content[0].text)

## PydanticAI 프레임워크
from pydantic_ai import Agent
agent = Agent('anthropic:claude-3-7-sonnet-latest',
              system_prompt="You are an expert Python programmer.")
result = agent.run_sync("Write code to find the median of a list of integers.")
print(result.data)
직접 검증해볼 것

이 저장소를 클론해서 두 셀을 그대로 돌려보고, PydanticAI 쪽 모델 문자열을 'anthropic:claude-3-7-sonnet-latest'에서 'google-gla:gemini-2.0-flash'로만 바꿔 재실행해보라(prompt_engineering.ipynb가 이미 이 제미나이 모델로 같은 Agent(...) 패턴을 쓴다). anthropic.Anthropic() 직접 호출 쪽도 같은 방식으로 바꿀 수 있는지 코드를 보고 확인해보라.

확인 포인트: PydanticAI 쪽은 문자열 한 줄만 바꾸면 나머지 Agent(...)·run_sync(...) 코드가 그대로 재사용된다. 반면 anthropic.Anthropic() 직접 호출 쪽은 클라이언트 클래스 자체(anthropic.Anthropic → 구글 SDK의 다른 클래스)와 messages.create의 인자 형식까지 다 바꿔야 한다 — "이름표만 바꾸면 된다"는 비유가 코드 레벨에서 정확히 어디까지 사실인지 이 저장소로 직접 확인되는 지점이다.

모범답

00_introduction/의 세 노트북과 15_adapter_tuning/의 keys.env 요구사항을 서로 비교해보라 — 전자는 어떤 키가 필요하고, 후자는 어떤 키·라이선스·하드웨어가 필요한가?

확인 포인트: 00_introduction 쪽은 ANTHROPIC_API_KEY/GEMINI_API_KEY만 있으면 노트북이 어떤 컴퓨터에서든 바로 돈다 — 가중치 자체는 한 번도 로컬에 안 내려온다. 반대로 15_adapter_tuning은 HuggingFace HF_TOKEN과 Gemma 라이선스 동의, 그리고 NVIDIA L4 32GB GPU가 명시적으로 필요하다 — 가중치가 공개(오픈웨이트)돼 있어도 내 컴퓨터/노트북 GPU로는 못 돌리는 실제 사례다. 회사 기밀 문서를 다루는 도구라면 데이터가 API로 안 나가는 로컬/사내 호스팅이 우선이지만, "오픈웨이트=쉽게 로컬 실행 가능"이 아니라는 걸 이 README의 GPU 사양이 그대로 보여준다.

F6

프런티어·증류·오픈웨이트·로컬호스팅, 네 등급은 뭐로 나뉘고 비용과는 어떤 관계인가?

모범답

블라인드 테스트(LMArena)로 매겨진 순위 기준 네 등급 — 프런티어(최고 성능, 가중치 비공개) · 증류(가볍고 저렴) · 오픈웨이트(가중치 공개) · 로컬호스팅(그중 크기가 작아 개인 컴퓨터에서도 돌아감). 성능·비용 그래프는 두 축 모두 로그 눈금이라 등급 하나만 내려가도 비용은 크게 줄어든다(예: 제미나이 플래시는 제미나이 프로보다 약 20배 저렴).

직접 검증해볼 것

lmarena.ai/leaderboard에 직접 들어가서 지금 시점 상위권 모델과, 같은 회사의 경량(증류) 모델 순위·이름을 나란히 적어보라. F3·D1의 예제가 쓴 claude-3-7-sonnet-latest는 어느 급인지도 찾아보라.

확인 포인트: 리더보드는 계속 바뀌므로 등수 자체을 외울 필요는 없다 — 확인할 건 순위표 상단(프런티어)과 같은 회사의 경량 라인업(하이쿠·플래시류)이 항상 같이 존재한다는 구조다. 예제 노트북이 쓴 claude-3-7-sonnet-latest는 프런티어와 경량 사이의 "중간급" 모델이다 — 실무에서 노트북을 그대로 복사해 쓰기 전에, 지금 하려는 작업(문의 분류처럼 쉬운 것 vs 계약서 리스크 분석처럼 어려운 것)에 이 모델 등급이 과한지 부족한지부터 리더보드로 확인하는 습관이 실제 비용을 좌우한다.

A · 에이전트형 AI (1.3)
A1

"자율성"이 정확히 뭔가? 재고 관리 예시로 설명하면?

모범답

"재고가 100개 밑이면 300개 주문해"처럼 세세한 규칙을 사람이 미리 프로그래밍하지 않고, "재고 부족 없게 적시에 주문해줘"라는 목표만 주는 것. 에이전트는 최근 판매량·배송 기간을 스스로 살펴보고 필요 수량을 계산해서 이유까지 설명한다. 규칙 자체를 에이전트가 그때그때 만들어낸다는 게 핵심이다.

📓 examples/00_introduction/agentic_ai.ipynb — 책의 재고 예시 원본 코드 
@dataclass
class InventoryItem:
    name: str
    quantity_on_hand: int
    weekly_quantity_sold_past_n_weeks: [int]
    weeks_to_deliver: int

@dataclass
class Reorder:
    name: str
    quantity_to_order: int
    reason_to_reorder: str

items = [
    InventoryItem("itemA", 300, [50, 70, 80, 100], 2),
    InventoryItem("itemB", 100, [70, 80, 90, 70], 2),
    InventoryItem("itemC", 200, [80, 70, 90, 80], 1)
]

agent = Agent(f"anthropic:{MODEL_ID}",
              system_prompt="You are an inventory manager who orders just in time.",
              result_type=list[Reorder])

result = agent.run_sync(f"Identify which of these items need to be reordered this week.\n{items}")
print(result.data)
직접 검증해볼 것

"재고가 100개 밑이면 300개 주문"류 규칙이 코드 어디에도 없다는 걸 직접 확인하라 — if문을 찾아봐라. 그다음 InventoryItem에 실제로 없는 필드(예: 재입고 리드타임이 아니라 "공급업체명")를 하나 추가하고 시스템 프롬프트는 그대로 둔 채 재실행해보라.

확인 포인트: 재주문 규칙을 만드는 if문은 정말 없다 — 판단은 전부 system_prompt 한 줄과 result_type=list[Reorder](출력 형식 강제)에서 나온다. 필드를 추가해도 코드 수정 없이 에이전트가 알아서 그 정보를 판단에 반영하려 시도하는지, 아니면 무시하는지가 "자율성"의 한계를 실제로 보여준다 — 목표·출력형식만 정해주고 판단 로직 자체는 프롬프트+모델에 위임했다는 뜻이다.

A2

에이전트에게 기대되는 네 가지 능력과, 이게 순환 구조라는 말은 무슨 뜻인가?

모범답

① 목표 지향성(반응만 안 하고 목표를 향해 움직임) ② 계획 및 추론(단계를 스스로 쪼갬) ③ 인지 및 행동(데이터를 읽고 외부 함수를 호출함) ④ 적응 및 학습(결과를 다음 판단에 반영함). 이 넷이 인지→계획→행동→적응→다시 인지로 한 바퀴 돌 때마다, 다음 판단이 이전 결과를 반영해 조금씩 나아진다.

직접 검증해볼 것

A1의 agentic_ai.ipynb를 다시 보라 — @agent.tool 데코레이터나 실제 주문 API 호출 코드가 있나? items 데이터가 어디서 오는지도 확인하라(실시간 재고 시스템 조회인가, 그냥 파이썬 변수인가).

확인 포인트: 없다. items는 노트북 안에 하드코딩된 파이썬 리스트고, agent.run_sync(...)는 그 텍스트를 프롬프트에 그대로 박아 넣을 뿐이다. 즉 이 예제는 ②계획·추론(수량 계산·이유 설명)까지만 구현됐고, ③인지·행동(실제 재고 DB 조회, 진짜 주문 API 호출)은 빠져 있다 — 책의 4대 능력 표에서 "인지 및 행동"이 코드로 채워지는 건 7장 도구 호출 패턴(21_tool_calling)부터다. 이 노트북만 보고 "완전한 에이전트"라 생각하면 안 되는 지점이 바로 여기다.

A3

비결정성과 환각은 둘 다 "AI가 틀리는 문제"처럼 보이는데, 원인이 어떻게 다른가?

모범답

비결정성은 모델이 후보마다 매긴 점수(로짓)를 확률로 바꿔 그 확률대로 뽑기 때문에 생긴다 — 1등이 뽑힐 확률이 제일 높아도 2등이 가끔 뽑힐 수 있다. 계산이 틀린 게 아니라 원래 설계(창의성을 위한 의도적 무작위성)다.

환각은 확률 뽑기와 무관하게, 모델에게 애초에 "사실인지 확인하는 절차"가 없어서 생긴다. 실제 데이터가 없어도 문법·맥락상 그럴듯한 답의 점수가 높으면 그냥 뽑아버린다.

직접 검증해볼 것

D1의 온도 반복문(for T in [0, 0.2, 0.5, 0.8, 1.0]: ...)을 T=0 한 줄만 남겨서 똑같이 3번 재실행해보라. 그다음 실전에서 환각을 줄이려면 온도를 낮추는 것 말고 뭘 손봐야 하는지 생각해보라.

확인 포인트: 책 저장소 출력 기록을 보면 T=0에서 5번을 돌려도 "The trade war caused significant disruptions to global supply chains..."로 토씨까지 똑같은 문장이 나온다 — 비결정성이 거의 사라진 걸 직접 확인할 수 있다. 하지만 이 문장이 사실인지(실제로 그 무역전쟁이 공급망을 어떻게 얼마나 무너뜨렸는지) T값과는 전혀 무관하다 — 온도는 "얼마나 다양하게 뽑을지"만 건드릴 뿐, "그 내용이 진짜인지"는 건드리지 못한다. 환각을 줄이려면 디코딩 설정이 아니라 3장 RAG 패턴처럼 답하기 전에 실제 문서를 찾아보게 하는 절차 자체를 바꿔야 한다.

D · 세밀한 디코딩 제어 (1.4)
D1

로짓·소프트맥스·온도(T)는 각각 뭘 하는 개념인가?

모범답

모델의 마지막 계층은 다음 단어 후보마다 로짓(순위용 원점수)을 매긴다. 소프트맥스는 이 로짓을 0~100% 확률로 바꾸는 계산이다. 온도(T)는 이 확률을 재분배하는 손잡이 — T를 0에 가깝게 두면 1등만 거의 항상 뽑히고(안전, 뻔함), T를 높이면 순위 낮은 후보도 뽑힐 기회가 생긴다(창의적, 위험도 커짐).

📓 examples/00_introduction/building_on_apis.ipynb 
for T in [0, 0.2, 0.5, 0.8, 1.0]:
    agent = Agent('anthropic:claude-3-7-sonnet-latest',
                  model_settings={"temperature": T},
                  system_prompt="Complete the sentence.")
    result = agent.run_sync("The trade war caused")
    print(T, ":  ", result.data)
0 : The trade war caused significant disruptions to global supply chains, leading to increased prices for consumers... 0.5 : ...(더 길어짐) Many manufacturers were forced to reconsider their production strategies... 1.0 : ...(가장 길고 표현 다양) accelerated shifts in international trade patterns and renewed debates about economic nationalism...
직접 검증해볼 것

이 반복문을 코드 생성 프롬프트("Write code to find the median of a list of integers.")로 바꿔서, T=0과 T=1.0 각각 3번씩 돌려 결과가 얼마나 다른지 비교해보라.

확인 포인트: 원본 출력 기록을 보면 T가 오를수록 문장 길이 자체가 늘고 표현이 다양해진다(T=0은 한 문장, T=1.0은 세 문장 이상). 코드 생성처럼 정답이 하나인 작업에 T를 높이면, 다양해지는 게 "창의성"이 아니라 "일관성 붕괴"로 나타난다 — 그래서 코드 생성은 T를 0~0.3, 자유 서술은 0.7~1.0로 잡는 게 실전 기준이다.

D2

상위K 표집과 상위P 표집은 둘 다 "안전장치"라는데, 방식은 어떻게 다른가?

모범답

상위K는 점수 순으로 줄 세운 뒤 고정된 개수 K개만 남기고 나머지는 후보에서 아예 제외한다. 상위P는 개수를 미리 안 정하고, 누적 확률이 P(예: 90%)를 넘는 지점까지만 후보로 남긴다 — 남는 후보 개수가 상황(점수 분포)에 따라 달라진다. 목적은 둘 다 같다 — 말이 안 되는 단어가 뽑힐 가능성을 미리 잘라내는 것.

📓 examples/00_introduction/building_on_apis.ipynb 
for top_k in [1, 10, 100]:
    agent = Agent('anthropic:claude-3-7-sonnet-latest',
                  model_settings={"temperature": 0.95, "top_k": top_k},
                  system_prompt="Complete the sentence.")
    result = agent.run_sync("The spaceship")
    print(top_k, ":  ", result.data)
1 : The spaceship zoomed through the vast expanse of space... 10 : The spaceship glided silently through the vast emptiness of space... 100 : The spaceship soared through the starry expanse, its gleaming hull reflecting...
직접 검증해볼 것

저장소의 apply_top_p(probs, top_p) 함수(순수 파이썬, API 호출 없이 로컬에서 바로 실행됨)를 logits 딕셔너리에 top_p=0.3, 0.8로 각각 돌려서 몇 개 단어가 살아남는지 직접 세어보라.

확인 포인트: logits = {"the": 5.2, "a": 3.8, "an": 2.1, "this": 1.5, "that": 0.9}처럼 1등·2등에 확률이 몰린 뾰족한 분포에서는 top_p=0.3만 줘도 the·a 정도만 남고 나머지는 확률 0으로 잘린다. 고객 응대 챗봇처럼 정확한 답 하나가 중요한 경우 top_p를 낮게(0.1~0.3) 잡는 이유가, 이 함수를 직접 돌려서 "몇 개가 남는지" 눈으로 세어보면 왜 그런지 체감된다 — top_k=1이 그리디 선택과 동일해지는 것도 위 출력에서 확인 가능하다.

D3

빔 탐색은 뭘 해결하고, 실전에서 잘 안 보이는 이유는?

모범답

한 단어씩만 골라나가면 당장은 그럴듯해도 문장 전체로는 어색해질 수 있다. 빔 탐색은 유망한 문장 경로 여러 개(흔히 3~5개, 빔 너비)를 동시에 몇 단어씩 미리 그려본 뒤, 전체 문장 점수가 가장 높은 경로를 최종으로 고른다.

직접 검증해볼 것

D1·D2에서 쓴 model_settings={"temperature": ..., "top_k": ...}에 "beam_width": 5를 추가해서 실행해보라. 그리고 PydanticAI의 ModelSettings 정의에 실제로 그런 필드가 있는지 확인해보라.

확인 포인트: 이 책 저장소의 어떤 노트북에도 beam이라는 단어 자체가 등장하지 않는다(직접 저장소를 grep해도 안 나온다). Anthropic·PydanticAI 모두 대화형 API에 빔 탐색 옵션을 열어주지 않기 때문이다 — 경로 여러 개를 동시에 추적하는 연산이 실시간 대화 응답 속도와 안 맞아서다. 실제로 빔 탐색이 쓰이는 곳은 번역기·자막 생성기처럼 문장 전체 정확도가 실시간성보다 중요한 로컬 추론 파이프라인(허깅페이스 transformers의 generate(num_beams=5) 등) 쪽이다 — 즉 "없다"는 사실 자체가 실전 API 설계를 보여주는 증거다.

D4

반복 벌점과 길이 벌점은 각각 뭘 조절하나?

모범답

반복 벌점은 같은 단어·문구 반복을 막는다(빈도 벌점: 반복할수록 더 깎음 / 출현 벌점: 한 번 나오면 그다음부터 항상 같은 만큼 깎음). 길이 벌점은 문장 길이를 조절한다(최소 길이 벌점: 너무 일찍 못 끝내게 / 최대 길이 벌점: 특정 길이 넘으면 끊음 / 길이 정규화 벌점: 무조건 짧은 답만 선호하지 않게).

직접 검증해볼 것

D1·D2와 똑같은 model_settings 딕셔너리에 "frequency_penalty": 1.0을 넣고 앤트로픽 모델로 실행해보라. 에러가 나는지, 조용히 무시되는지 직접 확인하라.

확인 포인트: temperature·top_k·top_p는 실제로 동작하지만, 앤트로픽 Claude API에는 반복 벌점 파라미터 자체가 없다(오픈AI·구글 Gemini API엔 있다). D1·D2 코드로 직접 이 셋을 넣어보고 안 되는 걸 확인하는 게, "회사마다 지원이 다르다"는 걸 문서만 읽는 것보다 확실하게 체감하는 방법이다. 실전 우회책은 온도·top_p로 분포를 넓히거나, 시스템 프롬프트에 "같은 표현을 반복하지 말라"는 지시를 직접 넣는 것이다.

L · 학습 방법 — 컨텍스트 내 학습과 사후훈련 (1.5~1.6)
L1

퓨샷 학습에서 모네 그림 예시 하나로 전혀 다른 르누아르 그림까지 맞히는 게, 왜 "지식 주입"이 아니라는 증거인가?

모범답

모델은 르누아르 그림 정보를 예시에서 받은 적이 없다. 모네 그림 예시 하나가 가르친 건 "설명 → 작품·화가·연도·의의" 순서(패턴)뿐이고, 실제 내용은 모델이 사전훈련 때부터 이미 알던 지식이다. 즉 퓨샷 학습은 새 지식을 넣는 게 아니라, 이미 아는 지식을 원하는 형식으로 꺼내 쓰게 하는 것이다.

📓 examples/00_introduction/prompt_engineering.ipynb 
## few-shot
agent = Agent(MODEL_ID, system_prompt=
    "You are an expert on art history. I will describe a painting. You should identify it")

result = agent.run_sync("""
Example:
Description: shows two small rowboats in the foreground and a red Sun.
Answer:
   Painting: Impression, Sunrise
   Artist: Claude Monet
   Year: 1872
   Significance: Gave the Impressionist movement its name...

Description: The painting shows a group of people eating at a table under
an outside tent. The men are wearing boating hats.
""")
print(result.output)
직접 검증해볼 것

이 셀의 예시(모네)는 그대로 두고, 마지막 Description만 실존하지 않는 그림 — "보라색 하늘 아래 로봇 세 대가 체스를 두는 그림"으로 바꿔 재실행해보라. 모델이 "모르겠다"고 하는지, 아니면 형식만 맞춰 그럴듯하게 지어내는지 확인하라.

확인 포인트: 십중팔구 모델은 "모른다"고 하는 대신 형식(Painting/Artist/Year/Significance)은 정확히 맞춘 채 존재하지 않는 화가·연도를 지어낸다 — 퓨샷이 가르친 게 "형식"뿐이라는 걸 역으로 증명하는 동시에, 이게 바로 환각(A3)이 실제로 발생하는 순간이다. 사내 전용 코드명처럼 모델이 사전훈련 때 못 본 사실은 예시를 아무리 늘려도 진짜로 못 맞히고, 대신 그럴듯한 형식으로 지어낼 위험만 커진다 — 그래서 이런 지식은 프롬프트에 직접 넣어주거나(RAG) 사후훈련시켜야 한다.

examples/15_adapter_tuning/README.md를 열어 "Step 4"를 찾아보라 — 실행에 어떤 하드웨어가 필요하다고 적혀 있나? 그리고 messages.jsonl의 각 줄이 표의 어느 데이터 모양(순수 텍스트 / 질문-모범답 쌍 / 비교 데이터)에 해당하는지 확인하라.

L3

LoRA는 왜 쓰고, 파국적 망각은 왜 생기나?

모범답

LoRA는 수천억 개 매개변수 전체를 다시 훈련하는 대신, 원본은 그대로 두고 작은 "추가 메모" 층만 새로 학습시킨다(포스트잇 비유). 학습 파라미터 최대 1만 배, GPU 메모리 최대 3배까지 줄면서도 성능은 전체 재훈련과 비슷하다.

파국적 망각은 좁은 데이터로 너무 집중해서 재훈련하면 원래 잘하던 다른 일을 잊어버리는 현상이다. 컴퓨터 파일과 달리, 모델의 가중치는 여러 능력이 같은 숫자 자리를 겹쳐서 공유하기 때문에 생긴다 — 누가 "이 능력 버려"라고 결정한 게 아니라, 좁은 데이터의 오차를 줄이려 가중치를 계속 밀어붙이는 계산 과정에서 다른 능력이 걸려 있던 같은 숫자까지 원치 않게 같이 바뀌는 것이다.

📓 examples/15_adapter_tuning/3_adapter_tuning.ipynb 
from peft import LoraConfig

peft_config = LoraConfig(

    lora_dropout=0.05,

    bias="none",
    target_modules="all-linear",
    task_type="CAUSAL_LM",
    modules_to_save=[
        "lm_head",
        "embed_tokens",
    ],
)
직접 검증해볼 것

r=16이 뭘 뜻하는지, 그리고 modules_to_save=["lm_head", "embed_tokens"]가 왜 굳이 명시돼 있는지 peft 공식 LoRA 문서에서 찾아보라.

확인 포인트: r은 LoRA 어댑터(포스트잇 층)의 랭크 — "포스트잇에 몇 줄까지 적을 수 있는지"에 해당하는 크기다. 이 방사선 이미지 캡션 예제에서 저자들은 lm_head·embed_tokens(출력·입력 임베딩 층)까지 modules_to_save로 일반 파라미터로 함께 학습되도록 명시했는데, 이건 Gemma가 원래 모르던 방사선 용어·토큰을 새로 익혀야 해서다 — 반대로 이 층까지 건드리면서 좁은 데이터로만 오래 학습시키면 파국적 망각이 더 쉽게 생긴다. 즉 "특정 고객사 스타일만 파고들다 다른 업무가 이상해졌다"는 시나리오의 실제 원인 후보 하나가 바로 이 modules_to_save 설정과 에폭 수(num_train_epochs)다 — 코드에서 직접 확인 가능한 지점이다.

한 장 지도로 정리하면 — 채용(1.2)·배치(1.3)·조율(1.4)·즉석교육(1.5)·정식재교육(1.6). 회사가 신입사원을 기초 모델로 데려와(F), 목표만 주고 판단을 맡기고(A), 판단의 과감함을 손잡이로 조절하고(D), 예시나 재훈련으로 가르치는(L) 순서 그대로다. 위 16개 문답에서 막힌 지점이 있었다면, 그 칸으로 돌아가 원문을 다시 읽어보면 된다.
