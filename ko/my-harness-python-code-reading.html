먼저 목적을 분명히 해 둘게요. 함수를 전부 외우거나 같은 파일 구성을 재현하는 게 목표가 아니에요. 이 예제의 결정은 Python·로컬 CLI·파일 세션 저장이고, 제가 다른 언어나 플랫폼을 골랐다면 그대로 바꿀 필요도 없어요. 모델 연결·도구 실행·상태·검증을 어떻게 나눴는지를 제 설계와 대조하려고 읽습니다.

비유 — 신문사 편집국의 자리 배치

신문 기사 한 꼭지가 지면에 실리기까지, 편집국에서는 자리마다 맡은 일이 달라요.

취재기자는 "다음에 누구를 만날지, 무엇을 더 확인할지"를 판단해요. 외신 번역 담당은 영어·중국어로 들어온 자료를 편집국이 쓰는 한 가지 형식으로 바꿔 넘겨요. 자료실 사서는 과거 기사 원본을 꺼내 주는데, 아무 서랍이나 열어 주지는 않아요 — 열람 규칙이 따로 있죠. 그리고 데스크는 기사를 읽고 사실이 맞는지 확인해요. 기자가 "확인했습니다"라고 말한 것과, 데스크가 원본과 대조한 것은 다른 일이에요.

여기서 자리 배치의 묘가 드러나요. 번역 담당이 중국어에서 스페인어로 바뀌어도, 자료실 열람 규칙은 그대로예요. 만약 번역 담당이 바뀌었다고 자료실 규칙까지 고쳐야 한다면, 그건 두 자리가 섞여 있다는 뜻이에요.

다만 비유가 끊기는 점이 있어요. 편집국은 사람이 서로 말로 조율하지만, 코드는 자료형으로만 조율해요. 그래서 "무엇을 주고받는가"를 4편에서 미리 정해 두지 않으면, 자리를 아무리 나눠도 결국 섞입니다.

반복의 중심 — 세 조각만 읽어도 돼요

코드 전체를 읽을 필요는 없어요. 세 조각이면 흐름이 잡혀요. Python 문법이 낯설면 파이썬 코드 눈으로 읽기 — 함수·변수·반복·오류·async를 옆에 두고 보세요.

①모델을 부르는 곳이에요.

개념 설명용 코드 — 실제 파일에서 흐름만 보이게 뽑아낸 조각이라, 이것만으로는 실행되지 않아요

reply = await self.provider.complete(
    messages, self.backend.definitions
)

messages는 지금까지의 대화이고, definitions는 쓸 수 있는 도구 설명이에요. await2는 모델 응답을 기다리는 지점이고요. 이런 비동기 실행을 쓰면 기다리는 작업에 취소와 시간 제한을 걸 수 있어요. 그리고 이 줄이 중요한 이유가 하나 더 있어요 — 이건 다른 에이전트 제품에 반복을 맡기는 호출이 아니라, 모델 API를 직접 부르는 호출이에요.

②응답을 담는 자료형이에요.

개념 설명용 코드 — 자료형의 모양만 보여 주는 조각이에요

@dataclass(frozen=True)
class ToolRequest:
    id: str
    name: str
    arguments: dict[str, Any] | str

id는 4편의 호출 ID예요 — 요청과 결과를 짝지어 줘요. name은 어느 도구인지, arguments는 그 도구의 입력이고요. 이렇게 타입이 적힌 자료형을 쓰면 각 부분이 주고받는 값이 눈에 보여요. 다만 타입 표기만으로 실행 검사가 끝나지는 않아요. 그래서 루프에서는 JSON을 해석하고, 도구의 JSON Schema3로 인수를 다시 검사합니다.

③도구를 실제로 실행하는 곳이에요.

개념 설명용 코드 — 검사 후 실행이라는 순서만 보여 주는 조각이에요

validated = ToolRequest(request.id, request.name, arguments)
async with asyncio.timeout(self.limits.tool_timeout_seconds):
    result = await self.backend.execute(validated)

등록된 도구인지와 인수 형식을 확인한 다음에 백엔드4가 실제 작업을 해요. 여기서 백엔드는 그냥 "요청을 받아 실행하는 쪽"이라는 뜻이에요. 일상 사용에서는 승인받은 파일·명령 실행이고, 로컬 평가에서는 별도 작업 복사본의 파일 처리와 Python 실행이에요. 그리고 작업 복사본은 운영체제 격리를 뜻하지 않아요.

결과를 대화에 추가하면 바깥 반복이 다시 모델을 불러요. 도구 요청이 없는 텍스트를 받으면 반환하고, 한도나 오류에 도달하면 다른 상태로 끝나요. 3편에서 그린 흐름이 그대로 코드가 된 거예요. 다만 실제 함수에는 인수 오류·결과 ID 검사·기록·중단 처리가 더 있으니, 위 발췌만 보고 전체 구현이라고 생각하면 안 돼요.

루프란 무엇인가 — 그리고 그 루프를 누가 짜는가

위에서 "바깥 반복"이라는 말을 썼는데, 이 반복(루프)이 정확히 무엇인지 한 번 짚고 갈게요. 하네스라는 말의 알맹이가 사실상 이거예요.

모델 API를 한 번 부르면 딱 한 번의 왕복이 일어나요. 내가 글을 보내면 모델이 글을 돌려줘요. 그게 전부예요 — 모델은 제 컴퓨터의 파일을 열지도, 명령을 실행하지도 않아요. 그럴 능력이 없어서가 아니라, 모델이 할 수 있는 건 "이 도구를 이런 인수로 써 주세요"라고 말하는 것까지이기 때문이에요. 실제로 파일을 여는 건 제 프로그램이에요.

그래서 에이전트처럼 굴게 하려면 이 왕복을 여러 번 이어 붙여야 해요. 그 이어 붙이는 반복이 루프예요.

개념 설명용 코드 — 위 세 조각이 어떻게 한 바퀴로 이어지는지만 보여 주는 뼈대예요

while True:
    reply = 모델_호출(messages, tools)      # ① 지금까지의 대화를 통째로 보낸다
    if not reply.tool_requests:            # ② 도구 요청이 없으면
        return reply.text                  #    거기서 끝낸다
    for req in reply.tool_requests:        # ③ 요청된 도구를 내 프로그램이 실행하고
        result = 도구_실행(req)
        messages.append(result)            # ④ 그 결과를 대화 뒤에 붙인다
                                           #    → 다시 ①로 돌아간다

①이 앞에서 본 provider.complete(...), ③이 backend.execute(...)예요. ④에서 결과를 대화에 붙이는 게 핵심이에요 — 모델은 매번 기억이 없는 상태로 시작하기 때문에, 지난 왕복의 내용을 대화에 계속 쌓아서 통째로 다시 보내 줘야 앞뒤가 이어져요.

그리고 while True라고 썼지만 실제로는 무한히 돌면 안 돼요. 언제 빠져나올지가 3편에서 정한 종료 조건이고, 그게 없으면 같은 도구를 계속 부르며 토큰만 쓰는 상태에 빠져요. 루프를 짠다는 건 사실상 "언제 멈출지를 정한다"는 뜻이에요.

생각-행동-관찰을 반복한다는 이 발상 자체는 새 것이 아니에요. 그 뿌리는 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동에 있어요. 위 코드는 그 발상이 실제 코드로 앉은 모습이고요.

이 루프를 누가 짜느냐 — 네 갈래

여기서 갈림길이 하나 생겨요. 이 루프를 내가 짤 수도 있고, 이미 짜여 있는 걸 받아 쓸 수도 있어요. 두 가지를 따로 물어보면 정리가 돼요 — 루프(하네스)를 누가 주는가, 그리고 그게 도는 컴퓨터를 누가 대는가.

이 시리즈에서 읽고 있는 하네스는 ①이에요. 앞에서 "이건 다른 에이전트 제품에 반복을 맡기는 호출이 아니라 모델 API를 직접 부르는 호출"이라고 한 게 그 뜻이었어요.

SDK가 두 개라 생기는 혼동

이름이 비슷해서 헷갈리는데, 이건 서로 다른 두 개예요.

무엇패키지 이름주는 것
모델 API용 SDKanthropic / @anthropic-ai/sdkAPI를 편하게 부르는 껍데기. 루프는 안 줌 (위 ①·②)
Claude Agent SDKclaude-agent-sdk / @anthropic-ai/claude-agent-sdk코딩 에이전트 한 벌을 통째로. 루프 + 내장 도구 + 권한·세션·서브에이전트 (위 ③)

"SDK를 쓰면 API 역할이 아니라 에이전트로 동작한다"는 설명을 들었다면, 그건 아래쪽을 가리키는 말이에요. 위쪽 SDK를 설치했다고 에이전트가 되지는 않아요 — 그건 여전히 왕복 한 번을 대신 부쳐 주는 우편 창구고, 루프는 제가 짜야 해요. 뒤쪽은 코딩 에이전트 제품 하나를 라이브러리 형태로 가져다 쓰는 것에 가까워요. 실제로 2편에서 본 오케스트레이션 플러그인을 다른 도구로 옮겨 놓은 것들이 이 방식으로 만들어져요.

주의할 게 하나 더 있어요. ②의 "도구 실행기"는 일반 API SDK 안에 들어 있는 보조 기능이라 ③과 이름이 헷갈리기 쉬운데, 둘은 달라요 — ②는 내가 정의한 도구만 돌려 주고 내장 도구도 파일 접근도 없어요. ③은 파일과 명령을 다루는 도구가 처음부터 들어 있고요.

그러면 왜 ①을 하나

③이나 ④를 쓰면 훨씬 빨리 굴러가요. 그런데 이 시리즈가 ①을 읽는 이유가 있어요 — 루프를 남이 짜 주면, 그 안에서 어떤 결정이 일어나는지가 안 보여요. 도구 인수를 언제 검사하는지, 실패한 도구 결과를 어떻게 돌려주는지, 몇 번째에서 멈추는지가 전부 남의 판단으로 정해져 있어요. 그게 나쁘다는 게 아니라, 그 판단이 무엇인지 아는 사람과 모르는 사람이 갈린다는 뜻이에요.

한 바퀴를 직접 짜 보고 나면 ③·④를 쓸 때도 "지금 저 안에서 ①~④ 중 어디가 도는 중이구나"가 보여요. 반대 순서로는 잘 안 보이고요.

제공자 차이는 어디서 흡수되나

  • OpenAIProvider — Responses API를 써요. 모델의 function_call과 실제 결과인 function_call_output을 call_id로 연결해요. store=False로 요청하면서도 다음 요청에 필요한 출력 항목과 추론 관련 항목은 보존해요. 텍스트만 남기고 나머지 응답을 버리지 않는다는 뜻이에요.
  • OllamaProvider — OpenAI 호환 경로를 가정하지 않고 네이티브 /api/chat을 써요. 도구 호출 입력과 결과를 그 형식으로 변환하고, 호출 ID가 없는 응답에는 내부 ID를 붙여요. 이건 Ollama 서버가 발급한 ID가 아니라 하네스가 만든 것이라, 기록에서도 그렇게 구분해 설명해야 해요.

두 어댑터가 모두 구현돼 있어도 제 첫 검증은 고른 제공자 하나부터 하면 돼요. 추가 제공자를 평가할지는 D08의 선택에 맞춥니다.

기본 한도 — 숫자와 그 숫자가 뜻하지 않는 것

이 구현이 정해 둔 기본 한도예요. 제 하네스에 그대로 쓰라는 값이 아니라, "한도는 이런 항목들로 갈린다"는 견본으로 보세요.

항목기본값측정 조건 / 단서
모델 호출 횟수12회작업 하나 기준
도구 호출 횟수30회작업 하나 기준

표 아래에 단서를 두 개 답니다. 첫째, 여기서 말하는 문자 한도는 모델의 토큰 한도와 같지 않아요. 토큰이 무엇인지는 토큰과 컨텍스트 — 활용가가 보는 비용과 한계와 컨텍스트 창은 왜 유한한가에서 다뤘어요. 둘째, 이건 대화를 자동으로 요약해 주는 기능이 아니에요. 길어지면 그냥 중단합니다.

세션 저장과 지표

세션은 .harness/sessions/에 저장돼요. 도구 요청과 각 결과를 중간중간 저장하고, 임시 파일을 다 쓴 뒤 교체하는 방식으로 저장 중 파일이 깨질 위험을 줄여요. 다만 같은 세션을 여러 프로세스가 동시에 쓰는 설계는 아니에요. 재개할 때 제공자·모델·주소·작업 폴더가 다르면 새 이름을 요구합니다.

중단돼서 결과가 없는 요청은 repair_pending이 오류 결과로 종결해요. 여기서 중요한 한계가 하나 있어요. 파일 변경과 세션 저장이 하나의 거래처럼 묶여 있지 않아요. 그러니 실행 여부가 불확실한 작업을 자동으로 반복하지 말고, 실제 파일을 확인해야 해요. 그리고 대화 파일에는 자료 내용이 남을 수 있으니 공개 저장소에 넣지 않습니다.

지표5(metrics)는 실행을 서로 비교할 수 있게 남기는 수치예요. 모델·도구 호출 수, 도구 오류 수, 경과 시간, 보고된 입력·출력 토큰이 남아요.

나쁜 선택 vs 좋은 선택

지표를 읽는 두 가지 방식이에요.

나쁜 선택좋은 선택
무엇을 했나: 실행 기록에 usage_known=False가 붙어 있고 토큰 수가 비어 있길래, 보고서에 토큰 0, 비용 0원이라고 적었어요. 그리고 상태가 completed이니 성공으로 세었고요.

무슨 일이 생기나: "이 방식이 비용이 안 든다"는 사실이 아닌 결론이 보고서에 남아요. 게다가 completed는 모델이 텍스트를 반환했다는 상태일 뿐인데 업무 정답으로 셈해서, 실제 정확도보다 높은 숫자가 나옵니다.		 무엇을 했나: usage_known=False면 토큰·비용을 '알 수 없음'으로 두고, completed는 "모델이 답을 반환함"으로만 기록했어요. 정답 여부는 별도 채점 결과에서 가져왔고요.

무슨 일이 생기나: 숫자가 비어 보여서 아쉽지만, 나중에 다른 실행과 비교할 때 왜곡이 안 생겨요. 모르는 건 모른다고 적혀 있으니 채워 넣을 지점도 분명해요.

이 원칙 하나만 가져가도 돼요. usage_known=False일 때 숫자 0을 "무료" 또는 "실제로 안 씀"으로 해석하지 않는다.

같은 루프를 평가에 연결하기

평가 경로에서는 local_agent.py의 LocalBenchmarkTools를 같은 Agent에 연결해요. 읽기·쓰기 도구와 run_python을 주고, 일반 CLI의 run_command는 뺍니다.

개념 설명용 코드 — 같은 Agent에 평가용 도구를 갈아 끼우는 구조만 보여 주는 조각이에요

result = await Agent(
    provider,
    LocalBenchmarkTools(workspace, options["command_timeout"]),
    limits,
    trace,
    SYSTEM,
).run(instruction + "\n\nLocal task working directory (relative to workspace): "
      + options.get("task_cwd", "."))

이 연결에서 모델의 판단 루프는 기존 Agent가 그대로 맡고, 실행 범위와 도구 목록만 평가용 백엔드가 정해요. 앞 그림에서 오른쪽 자리를 갈아 끼운 거죠.

모델이 Python 코드를 실행하려면 먼저 작업 폴더에 .py 파일을 만든 뒤 파일 경로와 인수 목록으로 요청해야 해요. 임의 셸 명령을 받는 방식과 구별되는 지점이에요.

그리고 정책 하나가 여기서 달라져요. 평가 작업 복사본 안의 변경은 사전 허용된 동작으로 다뤄요. 매번 승인을 묻지 않는다는 뜻이죠. 하지만 그 허용이 사용자 컴퓨터의 다른 파일 접근까지 뜻하지는 않아요. 로컬 CLI의 "매번 확인" 승인 방식과 평가의 자동 실행 정책은 서로 다른 정책이라는 걸 기억해 두세요.

execution.py는 실행할 Python 파일의 경로를 검사하고 출력과 시간을 제한해요. 출력이 상한을 넘으면 프로세스를 종료하면서도 파이프를 계속 비워 무한 대기를 줄여요. POSIX에서는 원래 프로세스 그룹을 종료하고 Windows에서는 자식 프로세스를 직접 종료하고요. 다만 별도 세션으로 벗어난 자식까지 가두는 운영체제 샌드박스는 아니에요.

원본 문제와 채점은 어디서 오나

여기부터는 다음 편의 예고편이에요. 이 하네스의 평가 문제는 자체 제작이 아니에요. Terminal-Bench Pro의 고정 커밋에서 원본 난도 쉬움 2개·중간 4개·어려움 4개를 골라, 원래 컨테이너의 절대 경로를 로컬 작업 폴더로 옮겨 실행하는 구성이에요.

benchmark_source.py는 목록에 기록된 저장소 커밋과 파일별 크기·SHA2566을 확인해요. 내려받은 파일이 약속한 원본과 같은지 보려는 거예요. 원본의 /app, /protected, /home/user 같은 경로는 작업 폴더 안의 대응 위치로 바뀌고, 작업 지시와 채점 코드에도 같은 경로 규칙을 적용해야 해요.

그리고 grading.py가 원본 tests/test_outputs.py를 pytest로 실행해요. 여기서 이 시리즈 전체를 관통하는 규칙이 다시 나옵니다. 모델이 "완료했다"고 말한 문장을 점수로 쓰지 않아요. 원본 검사가 실제 산출물을 확인한 결과를 씁니다. 검사 실행 오류나 시간·출력 한도 초과도 기록해야 하고요.

다만 채점 파일을 작업 폴더 밖에 두는 건 일반 파일 도구에 노출하지 않기 위한 구조일 뿐이에요. 호스트에서 실행되는 Python 코드가 다른 파일을 못 읽게 보장하는 장치는 아니에요. 그리고 원본 정답과 채점 파일을 내 하네스의 입력이나 개선 프롬프트에 넣지 않는다는 평가 규칙도 함께 지킵니다.

직접 해보기

실제 모델 없이도 돌릴 수 있는 검사부터 해 봐요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

하네스 자체 검사를 돌리고, 실제 모델 평가와 구별해서 결과를 설명해 줘.

그다음 하네스에 직접 요청을 보내 봅니다. 실습용 work/meeting.txt는 가상의 독서 모임 자료이고, 시작 시각은 오후 3시, 준비물은 책 한 권과 필기구예요 — 기대 결과를 이미 알고 있는 상태로 시작하는 거죠.

실행: 내가 만든 하네스의 입력창에 붙여넣기 — 개발 도우미가 아니라 하네스 프로그램이에요

영수증 계산의 테스트를 실행하고 잘못된 부분을 고쳐 줘. 테스트는 바꾸지 말고 다시 확인해 줘.
  1. 바꿀 것 — 이 구현의 파일 목록 옆에 내 설계의 결정 ID를 적어 봐요. 짝이 없는 칸이 나오면 그게 제 설계에서 아직 안 정한 것이거나, 이 예제가 제 요구에 없는 기능을 가진 자리예요.
  2. 측정할 것 — LocalTools가 상대 경로·숨김 경로·링크를 검사하고 쓰기를 승인받는지 실제로 확인해요. 그리고 run_command는 셸 해석 없이 인수 목록으로 실행하지만, 승인한 코드 자체는 사용자 권한을 갖는다는 점도 같이 확인하세요.
  3. 비교할 것 — 제 하네스와 이 예제가 다르게 판단하는 지점을 하나 찾아 이유를 적어요. 다르다고 틀린 게 아니에요 — 다른 결정을 했으면 다른 게 맞아요.

여기까지 읽었다면 제품의 요청·실행 루프와 평가의 문제 준비·채점 경로를 구별할 수 있어요. 다만 경로 이식 코드가 있다는 사실만으로 모든 원본 과제가 로컬에서 검증되었다고 단정하지 않습니다. 실제 열 문제의 실행 성공과 점수는 다음 편에서 직접 만들어 봅니다.

함께 읽으면 좋은 글

  • 파이썬 코드 눈으로 읽기 — 함수·변수·반복·오류·async — await와 데이터클래스가 낯설면 여기부터요.
  • 토큰과 컨텍스트 — 활용가가 보는 비용과 한계 — 문자 한도와 토큰 한도가 왜 다른지요.
  • 행동을 좁히고 문맥을 고른다 — 행동 포맷과 컨텍스트 관리 (2) — 도구 출력을 자르는 선택이 결과에 미치는 영향이요.
  1. pytest — 테스트 함수의 조건을 실행해 성공과 실패를 모아 보고하는 Python 테스트 도구예요. ↩
  2. await — 시간이 걸리는 작업의 결과를 기다리는 지점을 표시하는 Python 표기로, 기다리는 동안 취소나 시간 제한을 걸 수 있게 해 줘요. ↩
  3. JSON Schema — 주고받는 JSON 데이터에 어떤 항목이 필요하고 값의 종류가 무엇인지 정한 규칙으로, 도구를 실제로 설계하기에서 다뤘어요. ↩
  4. 백엔드(backend) — 여기서는 하네스의 도구 요청을 받아 실제 작업을 수행하는 부분을 가리키는 말이에요. ↩
  5. 지표(metrics) — 여러 실행을 서로 비교할 수 있도록 남기는 수치로, 호출 수·오류 수·경과 시간·보고된 토큰 등이 들어가요. ↩
  6. SHA256 — 파일 내용에서 계산해 내는 고정 길이 식별값으로, 받은 파일이 기록해 둔 원본과 같은지 확인할 때 써요. ↩
