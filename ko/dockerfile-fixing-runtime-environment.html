비유로 먼저 — 사장 집 주방에만 있던 특수 칼

2편에서 사장인 내가 본사에 레시피 폴더를 보내면, 본사의 자동 포장 라인이 레시피를 읽고 필요한 재료와 도구를 챙겨 밀키트 상자를 만들어 줬어요. 그런데 이번 메뉴는 사장 집 주방에 있는 특수 칼이 있어야 만들어져요. 사장은 집에서 연습할 때 그 칼을 써 와서 몰랐지만, 레시피에는 "특수 칼 필요"라는 말이 어디에도 없어요. 포장 라인은 레시피에 적힌 것만 챙기니, 상자에는 칼이 빠져요. 가맹점에서 주문이 들어오고 나서야 "칼이 없어요"가 터지고요. 해결은 간단해요. 사장이 상자 조립 설명서를 직접 써서, 특수 칼까지 설명서에 적어 보내면 돼요.

다만 여기서 비유가 끊기는 점이 있어요. 밀키트는 뜯으면 없어지지만, 이미지는 그대로 남아 있고 같은 이미지로 컨테이너를 몇 개든 띄울 수 있어요. 컨테이너를 지워도 이미지는 안 지워져요. 아래에서 직접 확인해요.

Dockerfile · 이미지 · 컨테이너 — 셋의 관계를 한 장으로

이 글에서 가장 헷갈리는 것이 이 셋의 관계예요. 한 줄로 먼저 말하면 이래요. Dockerfile은 글자로 쓴 설명서, 이미지는 그 설명서대로 만들어 봉한 결과물, 컨테이너는 그 결과물을 실행한 것이에요. 아래 그림에서 개수에 주목해 보세요. 같은 Dockerfile로 빌드를 두 번 하면 이미지가 두 개 생기고, 이미지 하나로 컨테이너를 여러 개 띄울 수 있어요.

읽는 법: 왼쪽에서 오른쪽으로 읽어요. 점선 화살표는 명령을 실행하면 만들어지는 방향이에요. 깜박이는 칸은 지금 돌고 있는 컨테이너고, 이미지와 Dockerfile은 깜박이지 않아요. 돌고 있는 것은 컨테이너뿐이라는 뜻이에요.

전체 흐름 — Dockerfile을 써서 production까지

읽는 법: 윗줄은 왼쪽에서 오른쪽으로, ④에서 아랫줄로 내려와 오른쪽에서 왼쪽으로 읽어요. 강조색 테두리는 Dockerfile이 쓰이는 단계(① 쓰기, ④·⑦ 빌드)고, 맨 왼쪽 점선 상자는 이 구조의 한계예요. 배포 흐름 자체는 2편에서 만든 그대로고, 바뀐 것은 빌드할 때 buildpacks 대신 Dockerfile이 쓰인다는 점뿐이에요.

서버에서만 실패한다 — 화면은 결과이고 원인은 로그에 있어요

한 줄 정리 화면의 안내는 결과만 말해 주고, 원인은 로그의 오류 줄에서 찾아요.

OCR을 켜는 스위치는 환경변수7 OCR_ENABLED예요. 기본값이 꺼짐이고, 꺼져 있을 때 사진을 보내면 서버가 "꺼져 있습니다"(404)로 거절해요. 사진을 읽는 코드는 pytesseract라는 파이썬 라이브러리를 쓰는데, 이 라이브러리는 직접 글자를 읽지 않아요. 운영체제에 설치된 tesseract 프로그램을 불러 쓰는 래퍼(wrapper)8예요. 그래서 requirements.txt로 라이브러리를 설치하는 것만으로는 부족해요. tesseract 프로그램과 한국어 글자 데이터를 시스템 패키지(운영체제에 까는 프로그램 묶음)로 따로 깔아야 해요.

먼저 내 컴퓨터에서 확인했어요. 프로그램을 깔기 전에 서버를 켜고 사진을 보내면 500 "사진에서 글자를 읽는 프로그램이 서버에 없습니다."가 나와요. tesseract를 설치하고(설치 후 tesseract --list-langs에 kor가 보이면 한국어 데이터까지 된 거예요) 같은 사진을 보내면 200과 함께 6줄이 읽혀요. 여기까지가 "내 컴퓨터에서는 된다"예요.

이제 staging에서 같은 기능을 켜 봤어요. 서비스 환경변수를 하나 더하는 명령이에요.

실행: 로컬 터미널 — staging 서비스에만 환경변수를 하나 더하고 새 리비전이 하나 생겨요. production은 건드리지 않아요

gcloud run services update 서비스이름-staging --region us-central1 --update-env-vars OCR_ENABLED=true

실행하기 전에 두 가지를 확인해요. 서비스 이름이 staging 것인지, 그리고 옵션이 --update-env-vars(기존 값은 두고 추가)인지예요. --set-env-vars를 쓰면 기존 환경변수가 통째로 바뀌어서 다른 값이 사라져요.

켠 뒤 같은 사진을 보내니 500 "사진에서 글자를 읽는 프로그램이 서버에 없습니다."가 나왔어요. 이 안내는 결과만 말해 줘요. 원인은 Cloud Run 로그에서 찾았어요. 로그 탭에서 심각도를 오류로 거르고 보니, 같은 시각에 두 줄이 있었어요.

  • 요청 로그: POST …/api/ocr, 상태 코드 500 (Cloud Run이 요청마다 자동으로 남기는 접수대 기록)
  • 컨테이너 로그: "tesseract 프로그램을 찾을 수 없습니다. 실행 환경에 tesseract 가 설치되어 있지 않습니다." (앱이 직접 남긴 줄. 원인은 여기)

여기서 짚을 것이 둘 있어요.

  • 서비스는 정상으로 시작했어요. 앱은 시작할 때 tesseract를 확인하지 않고, 사진 요청이 들어와 프로그램을 부르는 순간에야 없다는 것을 알게 돼요. 그래서 배포는 성공으로 끝났고 다른 기능은 멀쩡해요. 3편의 "서버 기록은 정상인데 사용자는 실패"와 같은 종류예요.
  • CI가 못 잡는 이유도 같은 곳에 있어요. CI는 코드를 올리면 자동으로 시험을 돌려 주는 장치예요. 이 시험이 도는 GitHub 러너(자동 실행 서버)와 staging 이미지는 서로 다른 환경이에요. 그래서 러너에서 통과했다고 staging에 tesseract가 있다는 뜻은 아니에요. 이 앱에서 CI가 돌린 테스트는 기존 칸 열림 일정 테스트였어요. OCR을 아예 건드리지 않았으니, 테스트 통과가 OCR이 서버에서 되는지는 알려 주지 못했어요.

왜 빠졌는지도 빌드 로그에서 보였어요. buildpacks는 .python-version을 읽고 파이썬 3.13을, requirements.txt를 읽고 라이브러리를 준비했어요. 하지만 tesseract는 저장소 어디에도 적혀 있지 않아요. 내 컴퓨터에 설치한 기록은 내 컴퓨터에만 남고 저장소로 들어오지 않았으니까요. 환경을 내가 정하려면 이미지를 만드는 방법 자체를 적어 저장소에 넣어야 하고, 그 파일이 Dockerfile이에요.

읽는 법: 세로로 한 칸씩 비교해요. 첫째, 둘째 줄(파이썬, 라이브러리)은 세 곳이 같아서 문제가 없어요. 셋째 줄만 buildpacks 이미지에서 빠져 있고, 그 때문에 맨 아래 결과가 500이 돼요.

실행: 로컬 터미널 — Docker Desktop을 켠 상태에서. 처음 실행할 때 이미지를 내려받아요(이 이미지는 183MB)

# --rm: 컨테이너가 멈추면(안에서 돌던 명령이 끝나면) 자동으로 지운다
docker run --rm python:3.13-slim-bookworm python --version
docker run --rm python:3.13-slim-bookworm sh -c "command -v tesseract || echo 'tesseract 없음'"

첫 줄은 Python 3.13.17이 나왔어요. 컨테이너 안의 파이썬은 내 컴퓨터의 파이썬(3.14)이 아니라 이미지 안의 것이에요. 둘째 줄은 "tesseract 없음"이에요. 공식 파이썬 이미지에도 tesseract는 없으니, 그 위에 설치하는 줄을 Dockerfile에 넣어야 해요.

컨테이너끼리는 파일을 나누지 않는다는 것도 확인했어요.

실행: 로컬 터미널 — 컨테이너 note-a는 일부러 남겨 두고, 마지막에 지워요

docker run --name note-a python:3.13-slim-bookworm sh -c "echo 메모 > /tmp/note.txt && cat /tmp/note.txt"
docker run --rm python:3.13-slim-bookworm sh -c "cat /tmp/note.txt || echo '파일 없음'"
docker rm note-a

첫 컨테이너는 "메모"를 출력했고, 같은 이미지로 띄운 둘째 컨테이너는 "파일 없음"이었어요. 파일은 첫 컨테이너 안에서만 생긴 변경이고 이미지는 바뀌지 않았기 때문이에요. 컨테이너를 지운 뒤에도 이미지 목록에는 그대로 남아 있었어요(docker ps -a로 끝난 컨테이너 포함 목록, docker images로 이미지 목록). 컨테이너 안에서 일을 마치고 끝난 컨테이너는 상태가 Exited (0)로 보이고, 괄호의 0은 문제없이 끝났다는 종료 코드예요.

컨테이너마다 네트워크도 따로예요. 안쪽에서 8000번 포트10로 기다려도 내 컴퓨터의 8000번과는 이어져 있지 않아요. 둘을 잇는 것이 docker run의 -p 바깥:안쪽이에요.

실행: 로컬 터미널 — 내 컴퓨터의 9000, 9001번 포트를 잠깐 써요. 끝나면 지워요

docker run -d --name web-a -p 9000:8000 python:3.13-slim-bookworm python -m http.server 8000
docker run -d --name web-b -p 9001:8000 python:3.13-slim-bookworm python -m http.server 8000
docker ps
docker run -d --name web-c -p 9000:8000 python:3.13-slim-bookworm python -m http.server 8000
docker rm -f web-a web-b web-c

docker ps(돌고 있는 것만 보여 줘요)에는 두 컨테이너가 Up 상태로, 포트 칸에 0.0.0.0:9000->8000/tcp처럼 보였어요. 브라우저로 localhost:9000과 localhost:9001은 열렸고(상태 200), localhost:8000은 열리지 않았어요. 브라우저는 컨테이너 밖에서 오는 손님이라 앞 숫자(바깥 포트)로 들어가고, 뒤 숫자는 컨테이너 안쪽 번호예요. 이미 쓰는 9000번으로 하나 더 띄우려 하면 Bind for 0.0.0.0:9000 failed: port is already allocated 오류가 나요. 여러 개를 띄울 때는 안쪽 포트는 같게 두고 바깥 포트만 바꿔요.

컨테이너는 실행 직후 사라질까 — 아니요, 지우거나 --rm을 줬을 때만이에요

"컨테이너는 실행하면 바로 사라진다"고 오해하기 쉬워요. 짧은 명령(python --version)은 순식간에 끝나서 그렇게 보이지만, 컨테이너는 시작 명령(컨테이너 안에서 처음 실행한 프로그램)이 끝나면 같이 멈출 뿐이고 저절로 지워지지는 않아요. --rm을 줬을 때만 멈추는 순간 자동으로 지워져요. 1회용 컨테이너로 직접 재 봤어요.

한 일결과
docker run --rm 이미지 python --version"Python 3.13.17"을 출력한 뒤 docker ps -a가 빈 목록. 명령이 끝나 컨테이너가 멈추는 순간 --rm이 실제로 지웠어요

정리하면 이래요.

  • 끝났다고 사라지지 않아요. --rm이 없으면 Exited로 남고, docker ps는 돌고 있는 것만 보여 주니 docker ps -a로 봐야 보여요.
  • 컨테이너 안의 파일은 컨테이너가 있는 동안 남아요. 멈췄다 다시 켜도 그대로예요. 컨테이너를 지우면 사라지고, 같은 이미지로 새로 띄우면 처음 상태예요.
  • 이미지는 컨테이너가 남아 있는 한 못 지워요. 멈춘 컨테이너도 이미지를 쓰고 있다고 봐요. 컨테이너를 먼저 지워야 이미지를 지울 수 있어요.
  • 서버에서도 같은 구조예요. Cloud Run에서 새 리비전을 배포하면 새 컨테이너로 시작하니, 컨테이너 안에만 둔 데이터는 사라져요. 남겨야 할 데이터는 컨테이너 밖(데이터베이스 등)에 둬요.

Exited (137)은 멈추라는 요청을 1초 안에 못 받아 강제로 끝낸 것으로 보이는데, 숫자의 정확한 뜻은 확인하지 못했어요.

Dockerfile 한 줄씩 읽기 — 위에서 아래로 쌓이는 이미지

▼ 자세히 보기

Dockerfile에는 베이스 이미지, 설치할 시스템 패키지와 라이브러리, 코드를 둘 곳, 실행할 사용자와 시작 명령을 적어요. 코딩 에이전트에게 쓰게 해도 돼요. 다만 에이전트는 요청받은 대로 파일을 쓸 뿐, 파이썬 버전을 고정할지, root로 실행할지 같은 판단을 대신 정해 주지 않아요. 그래서 무엇을 넣을지는 요청문에 직접 적어요. 이 앱에서 쓴 파일이에요.

실행: 프로젝트에 Dockerfile로 저장 — 저장소 맨 위 폴더에 이 이름 그대로 두면 Cloud Run 소스 배포가 읽어요

FROM python:3.13-slim-bookworm

RUN apt-get update \
    && apt-get install -y --no-install-recommends tesseract-ocr tesseract-ocr-kor \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home appuser
USER appuser

CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8080}"]
줄하는 일
FROM python:3.13-slim-bookworm공식 파이썬 3.13 이미지(Debian bookworm 기반의 작은 버전)에서 시작해요
RUN apt-get ... tesseract-ocr tesseract-ocr-kor시스템 패키지 tesseract와 한국어 데이터를 설치하고, 마지막에 내려받은 패키지 목록을 지워 이미지 크기를 줄여요
WORKDIR /app이후 명령을 실행하고 파일을 둘 폴더예요
COPY requirements.txt . 와 RUN pip install라이브러리 목록만 먼저 복사해 설치해요
COPY . .나머지 코드를 복사해요. .dockerignore에 적힌 파일은 빠져요
RUN useradd 와 USER appuserroot 권한이 없는 일반 사용자(non-root)11 appuser를 만들어 그 사용자로 실행해요
CMD [...]컨테이너가 시작할 때 실행할 명령이에요. ${PORT:-8080}은 PORT 값이 있으면 그 값, 없으면 8080이에요

이 파일로 빌드하면 줄이 하나씩 쌓이는 모습이 로그에 그대로 찍혀요. docker history 이미지이름으로 쌓인 레이어도 볼 수 있어요. 줄 하나가 만든 파일 변경 묶음이 레이어(layer)예요.

읽는 법: 아래 칸이 먼저 쌓이고 위 칸이 나중에 쌓여요. 같은 줄 오른쪽의 숫자는 그 레이어의 크기와 만드는 데 걸린 시간이에요. 칸이 하나씩 떨어져 쌓이는 모습은 빌드가 위에서 아래로 진행되는 순서(Dockerfile의 위쪽 줄부터)와 같아요.

쌓인 순서Dockerfile 줄레이어 크기걸린 시간

2RUN apt-get ... tesseract94.9MB24.1초
3WORKDIR /app8.19kB0.1초
4COPY requirements.txt .12.3kB0.1초
5RUN pip install52.5MB9.9초

크기가 있는 것은 파일을 실제로 설치하는 줄이고, USER나 CMD처럼 설정만 하는 줄은 0B예요. 서버에 없던 tesseract 설치 레이어가 가장 크고(94.9MB), 가장 오래 걸려요(24.1초). 우리 코드와 index.html은 152kB밖에 안 돼요. 이 숫자들이 줄 순서를 정하는 근거가 돼요. 오래 걸리고 잘 안 바뀌는 설치를 위에, 자주 바뀌는 코드 복사를 아래에 두는 거예요. requirements.txt만 먼저 복사하는 것도 같은 이유예요.

한 가지 더, Procfile과 .python-version은 buildpacks가 시작 명령과 파이썬 버전을 정할 때 쓰던 파일이에요. 저장소에 Dockerfile이 생기면 시작 명령은 CMD 줄이, 파이썬 버전은 FROM 줄이 정해요. 두 파일을 지우지 않아도 되지만 값이 다르면 헷갈리니 같은 버전인지 한 번 확인해요.

에이전트가 쓴 파일 검토하기 — 다섯 가지 기준

에이전트가 쓴 파일이든 직접 쓴 파일이든 아래 다섯 가지를 확인해요. 줄 순서나 표현이 조금 달라도 괜찮고, 표의 각 줄이 하는 일이 들어 있는지를 봐요. 하나라도 걸리면 그 부분만 고쳐 달라고 다시 요청해요.

확인할 것이유
베이스 이미지와 파이썬 버전이 고정되어 있는가 (python:latest가 아닌가)고정하지 않으면 빌드할 때마다 다른 버전이 들어와 결과가 달라질 수 있어요
tesseract와 한국어 데이터를 설치하는 줄이 있는가서버에 없던 바로 그것이에요
.dockerignore에 .env가 들어 있는가빠지면 COPY . .이 API 키가 든 파일을 이미지에 넣어요
실행 명령이 PORT 환경변수를 쓰는가Cloud Run은 정해 준 포트로 요청을 보내므로, 다른 포트를 리슨(포트를 열고 요청을 기다리는 것)하면 시작에 실패해요
non-root 사용자로 실행하는가앱에 문제가 생겨도 컨테이너 안에서 할 수 있는 일이 줄어요

예를 들어 에이전트가 세 가지를 이렇게 써 왔다고 해 봐요. FROM python:latest로 시작하고, 마지막 줄을 포트 8000으로 고정한 CMD로 쓰고, USER 줄을 뺐어요. 그러면 세 가지가 걸려요. 버전이 고정되지 않았고, 포트가 PORT와 어긋나 시작에 실패할 수 있고, root로 실행돼요. 세 줄 모두 고쳐 달라고 해요.

왜 root가 아니라 appuser로 실행하나요?

짧은 답은 문제가 생겨도 할 수 있는 일을 줄이려고예요. 서버 앱은 요청을 받아 처리만 하면 되는데 root11로 실행하면 그 이상의 일(시스템 파일 바꾸기, 프로그램 설치, 자기 코드 고치기)도 할 수 있어요. 앱에 버그가 있거나 누가 외부 입력으로 앱을 뚫는 일이 생겨도, 앱이 appuser로 돌고 있으면 그 사용자가 가진 권한만큼만 피해가 나요. 필요한 권한만 주는 이 원칙을 최소 권한이라고 해요.

이 Dockerfile에서는 설치(apt-get, pip install)에 권한이 필요해요. 그래서 root일 때 설치를 끝내고, 그 뒤에 USER appuser로 바꿔요. 그 아래 줄과 컨테이너 실행은 모두 appuser예요. 실제로 어떻게 다른지 직접 해 봤어요(2026.10.28, 직접 실행). 같은 이미지(routine-stamp:pdf)를 기본(appuser)과 --user root로 덮어써서 같은 세 가지 일을 시켜 봤어요.

컨테이너 안에서 해 본 일appuser (기본)root (--user root)
시스템 폴더 /etc에 파일 쓰기거부성공
앱 코드 폴더 /app에 파일 쓰기거부성공
apt-get update (프로그램 설치를 시도)거부성공

읽는 법: 위쪽 두 줄만 봐도 차이가 보여요. 앱이 자기 코드 폴더(/app)조차 못 고치니, 뚫려도 코드를 바꿔치기하기 어려워요. 이 표는 이 이미지에서 해 본 세 가지만 보여 줘요. 컨테이너 밖(내 컴퓨터)까지 피해가 번지는 경로나 실제 침입 시도는 시험하지 않았고, 읽기 권한도 비교하지 않았어요.

docker build -t routine-stamp:local .

# -p: 내 컴퓨터 8080 포트를 컨테이너 8080 포트에 연결, -e: 환경변수 전달
docker run --rm -p 8080:8080 -e OCR_ENABLED=true routine-stamp:local

첫 빌드는 53초가 걸렸고 이미지는 385MB였어요. 컨테이너를 띄우고 같은 사진을 보내니 200, 앞에서 내 컴퓨터의 tesseract가 읽은 것과 같은 6줄이 나왔어요. 그리고 이미지 안을 직접 들여다봤어요. 이미 돌고 있는 컨테이너 안에서 명령을 실행하는 것이 docker exec예요.

실행: 로컬 터미널 — 읽기만 하는 확인 명령이라 이미지는 바뀌지 않아요

docker exec 컨테이너이름 ls -a /app
docker exec 컨테이너이름 whoami
docker image ls routine-stamp:local

/app에는 app, index.html, requirements.txt, Procfile이 있고 node_modules, tests, package.json은 없었어요(.dockerignore가 뺀 것으로 보여요). 실행 사용자는 appuser였어요. 컨테이너 안 tesseract --list-langs에는 eng, kor, osd가 나왔어요. 이 확인에서 한계도 하나 있어요. 이 폴더에는 .env 파일이 애초에 없어서, .dockerignore의 .env 줄이 실제로 막았는지는 이번에 증명하지 못했어요. 확인하려면 임시 .env를 만들어 다시 빌드해 봐야 해요.

API 키는 이미지에 넣지 않고 실행할 때 건네는 것이 원칙이에요. 로컬에서는 --env-file .env로 내 컴퓨터의 .env 값을 컨테이너 환경변수로 넘기고, .env 파일 자체는 .dockerignore 덕분에 이미지에 들어가지 않아요. 이미지는 저장소에 올라가 여러 곳에서 내려받아 실행되는 파일이라, 안에 든 값은 이미지를 받은 누구나 꺼내 볼 수 있기 때문이에요. 이 앱은 키가 필요 없어서 이 부분은 직접 실행해 보지 않았어요. 또 --env-file은 값을 감싼 따옴표를 지워 주지 않으니, .env의 값은 따옴표 없이 적어요.

그리고 로컬에서 만든 이 이미지는 서버에 올리지 않아요. 서버용 이미지는 배포 과정에서 같은 Dockerfile로 다시 만들어요. 내 컴퓨터와 서버의 CPU 아키텍처12가 다를 수 있고, 내 컴퓨터에서 만든 이미지는 누가 언제 어떤 코드로 만들었는지 기록이 남지 않기 때문이에요.

레이어 캐시 — 같은 빌드가 53초에서 2초로

빌드할 때 Docker는 위에서부터 내려오며 내용이 바뀌지 않은 줄은 이전 빌드의 레이어를 다시 쓰고(레이어 캐시), 처음 바뀐 줄부터 아래를 새로 만들어요. 같은 폴더를 네 번 빌드하며 직접 재 봤어요.

읽는 법: 세 열을 비교해요. 첫째 열은 처음이라 전부 새로 만들고, 둘째 열은 바뀐 것이 없어 전부 재사용해요. 셋째 열은 이미지에 들어가는 코드 파일을 바꿨기 때문에 점선 아래의 두 줄만 다시 만들어요. Dockerfile 파일은 위에서 아래로 한 줄씩 실행돼요(그림 4는 쌓이는 모습이라 거꾸로, 아래가 먼저이고 위가 나중이에요). 어느 줄을 바꾸면 그 줄과 그 뒤에 실행되는 줄은 모두 다시 실행되고(빨간 칸), 그 앞 줄은 지난 결과를 그대로 써요(재사용). 예를 들어 tesseract 를 설치하는 apt 줄(7단계 중 2번째)을 바꾸면 2~7번, 6단계가 모두 새로 실행돼요.

2차는 바뀐 것이 없으니 모든 단계를 건너뛰고 2.1초에 끝났어요. 4차는 이미지에 들어가는 코드 파일을 바꿨더니 COPY . .부터 아래만 다시 만들고(아래의 useradd도 함께 다시 실행돼요), 24초짜리 tesseract 설치와 pip install은 건너뛰어 3.5초에 끝났어요. 코드 한 줄을 고칠 때마다 설치를 처음부터 하지 않는 이유가 이 숫자예요.

3차는 제가 예상과 달라 당황한 장면이에요. README.md를 바꿨는데 COPY . .까지 CACHED였어요. 원인은 제가 .dockerignore에 README.md를 넣어 둔 것이었어요. 이미지 안 /app에도 README.md가 없다는 것을 컨테이너에서 확인했어요. .dockerignore에 적힌 파일은 빌드에 보내지 않으니, 바꿔도 Docker 눈에는 바뀐 것이 없어요. 그래서 이미지에 실제로 들어가는 파일(app/__init__.py)로 다시 확인했어요. 두 파일 모두 확인 뒤 git checkout으로 되돌렸어요.

이 캐시를 로컬 docker build에서 직접 본 것이고, 서버(Cloud Build)의 배포 빌드에서도 같은 캐시가 쓰이는지는 확인하지 못했어요.

같은 자동 배포로 올리기 — 고칠 곳은 한 군데예요

Cloud Run의 소스 배포는 올라온 코드에 Dockerfile이 있으면 buildpacks 대신 그 Dockerfile로 이미지를 만들어요. 그래서 Dockerfile과 .dockerignore를 커밋해 staging 브랜치로 PR을 보내면 돼요. 배포 워크플로(GitHub Actions의 자동 배포 설정)는 한 군데만 고쳤어요. buildpacks로 배포한 서비스에는 기능이 하나 켜져 있어요. Google이 관리하는 베이스 이미지를 최신 보안 패치로 자동으로 바꿔 주는 기능이에요. 이 기능은 Dockerfile로 만든 이미지에는 쓸 수 없어요. 그래서 그대로 배포하면 Missing required argument [--clear-base-image] 오류로 멈춘다고 해요. 이 오류는 미리 옵션을 넣고 배포해서 직접 보지는 못했어요. 이제 베이스 이미지는 FROM 줄이 정하니, 배포 단계의 flags: 줄 끝에 --clear-base-image를 붙여 그 기능을 껐어요. 대신 베이스 이미지의 보안 패치는 FROM 줄을 바꾸고 다시 빌드할 때 들어와요.

실행: .github/workflows/deploy.yml 설정 파일에 붙여넣기 — GitHub Actions가 이 파일을 읽어요. 다른 줄은 바꾸지 말고 flags: 줄 끝에 한 단어만 더해요

--clear-base-image

올라가는 파일은 두 번 걸러져요. 소스 배포가 코드를 올릴 때 .gcloudignore에 적힌 파일을 빼고, 빌드할 때 COPY . .이 .dockerignore에 적힌 파일을 다시 빼요. 두 파일 모두 .env를 빼고 있는지 커밋 전에 확인해요. 이 앱은 Node 테스트용 package.json과 node_modules(25MB)도 서버에 필요 없어서 두 파일에서 뺐어요.

실행: 로컬 터미널 — 새 브랜치에서 세 파일만 커밋하고 push한 뒤 PR을 만들어요. 커밋 대상에 .env가 없는지 먼저 확인해요

git switch -c add-dockerfile
git add Dockerfile .dockerignore .github/workflows/deploy.yml
git commit -m "Dockerfile로 실행 환경 정하기"
git push -u origin add-dockerfile
gh pr create --base staging --title "Dockerfile 추가" --body "tesseract와 한국어 데이터를 포함한 실행 환경"

CI가 통과하고 머지하자 staging 배포가 돌았어요. 두 군데서 확인했어요.

  • GitHub의 Actions 탭: 배포 워크플로가 성공(test와 deploy)했는지 봐요.
  • Google Cloud의 Cloud Build 기록(이미지를 만든 과정의 로그): 가장 최근 빌드 로그에 Step 1/11 : FROM python:3.13-slim-bookworm과 Step 2/11 : RUN apt-get … tesseract-ocr tesseract-ocr-kor가 찍혀 있었어요. 처음 배포 때 찍혔던 google.python.runtime(buildpacks의 파이썬 단계)은 0건이었어요. 이번 빌드는 buildpacks가 아니라 Dockerfile로 진행됐다는 증거예요.

이어서 staging에 같은 사진을 보냈어요. 앞에서 staging에 직접 넣어 둔 OCR_ENABLED=true는 자동 배포가 기존 환경변수를 지우지 않고 합치는 방식이라 그대로 남아 있었어요. 결과는 200, 로컬 컨테이너와 같은 6줄이에요. 서버 코드는 한 줄도 안 바꿨는데, Dockerfile 하나로 500이 200이 됐어요.

staging에서 확인했으니 production으로 갔어요. staging에서 main으로 PR을 보내 CI를 통과시키고 머지했더니, production 배포는 승인 대기에서 멈췄어요. production 환경에 승인자를 지정해 둔 설정이에요. GitHub의 Actions 화면에서 배포를 승인하자 배포가 진행되어 성공했어요. production에는 OCR_ENABLED가 아직 없었어요. 그래서 처음에는 기능이 꺼진 채 시작했어요(/health가 ocr_enabled: false). 환경변수를 더해 켜자 같은 사진이 같은 6줄로 읽혔어요. 내 컴퓨터, 로컬 컨테이너, staging, production에서 같은 결과가 나온 거예요.

같은 Dockerfile이면 같은 이미지일까 — 그렇지 않아요

한 줄 정리 같은 Dockerfile로 따로 만든 두 이미지는 이미지 ID가 달랐고, staging에서 확인한 이미지와 production에 나간 이미지는 별개의 이미지예요.

그런데 staging과 production은 같은 Dockerfile로 이미지를 따로 만들었어요. 같은 파일이면 같은 이미지가 나오는지 캐시 없이 두 번 빌드해 비교했어요.

실행: 로컬 터미널 — 캐시를 안 쓰니 tesseract를 두 번 내려받고 한 번에 50초쯤 걸려요. 끝나면 두 이미지를 지워요

docker build --no-cache -t routine-stamp:try-a .
docker build --no-cache -t routine-stamp:try-b .
docker image inspect --format "{{.Id}}" routine-stamp:try-a routine-stamp:try-b
docker run --rm --entrypoint pip routine-stamp:try-a freeze
docker rmi routine-stamp:try-a routine-stamp:try-b

결과는 이랬어요. 두 빌드는 48초, 49초가 걸렸고 이미지 ID는 서로 달랐어요. 하지만 이미지 안의 파이썬 패키지 18개는 두 이미지에서 한 줄도 다르지 않았고, tesseract 패키지 버전(tesseract-ocr 5.3.0-2, 한국어 데이터 1:4.1.0-2)도 같았어요. 이미지 ID는 이미지 내용 전체로 계산한 값이라 작은 차이만 있어도 달라지고, 두 이미지의 생성 시각은 약 49초 차이가 났어요. 그 시각 차이가 ID가 다른 직접 원인인지까지는 제가 확인하지 못했어요. 두 빌드 사이가 1분도 안 돼서 패키지가 같았지만, 며칠 간격으로 빌드하면 그 사이 새로 나온 버전이 들어가 목록까지 달라질 수 있어요. 이건 직접 확인한 것이 아니에요.

그래서 오늘의 마무리는 이래요. 실행 환경은 Dockerfile 한 파일에 적혔고 네 곳에서 같은 결과가 나왔지만, staging에서 확인한 이미지와 production에 나간 이미지는 같은 파일로 따로 만든 별개의 이미지예요. 확인한 것과 나간 것이 같다고 말하려면 이미지를 한 번만 만들어 두 환경에 보내야 해요. 이 글에서는 거기까지 가지 않았어요. 남은 숙제가 둘 더 있어요. 하나는 지금 production에서 도는 이미지가 어느 커밋으로 만든 것인지 이름만 보고 알기 어렵다는 점이에요. 다른 하나는 이미지 크기가 385MB라 배포할 때마다 쌓이는 저장 공간을 아직 관리하지 않았다는 점이에요.

Dockerfile은 어디에 저장되나 — 단계마다 다른 곳에 있어요

▼ 자세히 보기

소스 배포는 GCP(Cloud Run)의 기능이고, GitHub는 코드를 보관하고 배포를 자동으로 시키는 쪽이에요. 같은 Dockerfile이 단계마다 다른 곳에 있어요.

단계어디에
① 작성할 때내 컴퓨터의 프로젝트 폴더
② 커밋·push 뒤GitHub 저장소의 맨 위 폴더 (README.md, index.html과 같은 위치). 원본이에요
③ 배포하는 순간GCP의 임시 저장소(Cloud Storage)에 폴더가 zip으로 올라가요
④ 빌드 중Cloud Build의 작업 폴더. 빌드 로그에 inflating: /workspace/Dockerfile이 찍혀요
⑤ 빌드 결과Artifact Registry에 이미지로 저장돼요 (Dockerfile 파일이 아니라 결과물이에요)
⑥ 이미지 안COPY . . 때문에 /app/Dockerfile 사본도 같이 들어 있어요

Dockerfile은 반드시 저장소 맨 위 폴더에 Dockerfile이라는 이름으로 두어야 소스 배포가 찾아요. 다른 폴더에 두거나 이름을 바꾸면 buildpacks로 빌드되어 tesseract가 다시 빠질 수 있어요. 이 부분은 직접 시험해 보지 않았어요.

이미지 안에서 .env 파일이 보여요, 또는 키 값이 이미지에 들어갔을까 불안해요 .dockerignore의 .env 줄과 .gcloudignore예요. COPY . . 줄이 폴더 전체를 복사하니, 빼지 않은 파일은 모두 이미지로 들어가요 docker run --rm 이미지 ls -a /app으로 파일 목록을 봐요. .env가 보이면 .dockerignore를 고쳐 다시 빌드하고, 그 이미지는 다른 곳에 올리지 말고 지워요. 키를 이미 올렸다면 키를 새로 발급받는 것까지 생각해요

  8. 래퍼(wrapper) 라이브러리 — 자기가 일을 하지 않고 다른 프로그램을 대신 불러 주는 라이브러리예요. ↩
  9. 리비전과 인스턴스 — 리비전은 이미지와 설정을 함께 적은 버전이고 인스턴스는 그 리비전으로 실행 중인 컨테이너로, 2편에서 다뤘어요. ↩
  10. 포트(port) — 한 컴퓨터에서 여러 프로그램이 네트워크를 함께 쓸 때 들어온 연결을 어느 프로그램에 줄지 정하는 번호예요. ↩
  11. non-root 사용자 — 운영체제 전체를 바꿀 수 있는 최고 권한(root)이 없는 일반 사용자예요. ↩
  12. CPU 아키텍처 — amd64나 arm64처럼 CPU가 실행할 수 있는 명령의 형식이에요. ↩
