프롬프트 체이닝이란 큰 작업을 순서가 정해진 단계로 쪼개 차례차례 진행하고, 단계 사이의 통과 여부는 LLM이 아니라 코드가 판단하게 하는 워크플로다.

어디쯤인가

  • 코드 게이트와 LLM 게이트를 겹쳐 씁니다. "용어가 빠졌나"처럼 규칙으로 적을 수 있는 건 코드로, "처음 배우는 사람이 이해할 수 있나"처럼 뜻을 읽어야 하는 건 LLM으로요.

  • 코드 게이트가 글자만 봅니다. 틀린 설명도 용어가 들어 있으면 통과하고, 뜻이 맞아도 State를 state로 적으면 떨어져요. 언제 의심하나 ↓
  • 이 범위로 끝나는 일을 굳이 에이전트로 만들면, 얻는 것 없이 불확실성만 사게 됩니다.
어디에 쓰나
  • 초안을 쓰고 검사하고 다듬는 파이프라인을 단계로 쪼개 만들기
  • 되돌리기 어려운 실행 앞에 사람 확인이나 코드 검사를 끼우기

여기까지 2편에서 세 재료로 그래프를 만들고, 3편에서 갈림길을 밀어붙이고, 4편에서 라우터 자리에 모델을 앉혀 봤어요. 이번 편부터는 그렇게 그은 선들이 이름 붙은 모양으로 다시 나와요. 다섯 가지인데, 자율성을 조금씩 늘려 가는 순서로 한 편에 하나씩 봐요. 모두 LLM을 여러 번 부르고, 뒤로 갈수록 개수나 반복 여부를 LLM이 정하는데도 에이전트가 아닌 이유는 1편에서 정리한 기준 그대로예요. 호출 횟수나 도구 사용 여부가 아니라, 갈 수 있는 길을 개발자가 미리 다 그려 뒀는가가 기준이거든요.

위에서 아래로 갈수록 개발자가 미리 정해 두는 것이 줄고, LLM이 실행 중에 정하는 것이 늘어요. 그래도 다섯 다 워크플로예요. 갈 수 있는 길 자체는 전부 개발자가 미리 그려 뒀거든요.

비유 — 코스 요리와 검수대

1편의 주방으로 다시 가 볼게요. 점심엔 코스 요리가 나가요. 손질, 조리, 플레이팅을 순서대로 하되 단계 사이에 검수대가 있어서 덜 된 접시는 다음 단계로 못 넘어가요.

비유 속 요소원래 개념
코스를 순서대로 내고, 단계 사이 검수대가 덜 된 접시를 막기① 프롬프트 체이닝 — 순서대로 잇는 노드 + 코드로 검사하는 게이트1

핵심 한 줄: "누가 무엇을 언제 할지"가 동선표에 미리 그려져 있어요 — 요리사가 알아서 동선을 바꾸는 장면은 없고, 그게 바로 에이전트와의 차이예요.

이 상황엔 어떤 패턴?

"사용자가 올린 구어체 녹취록을 받아서 (1) 학습자용 3문장 노트로 다듬고, (2) 다듬는 동안 핵심 용어(State, 리듀서)가 빠지지 않았는지 확인하고, (3) 통과하면 그 노트에서 학습 목표 문장을 뽑아야 한다." 가장 적합한 패턴은?

  1. 라우팅 — 노트 종류를 분류해서 담당 처리로 보낸다
  2. 병렬화 — 노트 다듬기와 목표 뽑기를 동시에 돌린다
  3. 프롬프트 체이닝 — 다듬기 → 검사 → 목표뽑기를 순서대로 잇는다
  4. 오케스트레이터-워커 — 문장 개수만큼 워커를 부른다

문제를 쪼개면: 다듬기 → 검사 → 목표뽑기, 순서가 고정이에요. 뒷단계가 앞단계 결과를 필요로 하고, 순서를 바꾸면 말이 안 돼요. 다듬기 전의 원본에서 목표를 뽑을 수는 없으니까요.

3번인 이유: 단계 사이에 자연스러운 순서가 있고, 중간 확인(검사)을 끼울 자리가 있어요. 체이닝의 정의 그대로예요.

다른 선택지가 아닌 이유:

  • 1(라우팅): 모든 입력이 같은 세 단계를 거쳐요. 종류별로 다른 길로 갈 지점이 없어요.
  • 2(병렬화): 다듬기가 끝나야 목표뽑기가 가능해요. 동시에 돌리면 다듬어지지 않은 원본에서 목표를 뽑아 버려요. 서로 독립인 작업이 아니에요.
  • 4(오케스트레이터-워커): 하위 작업의 개수가 입력마다 바뀌지 않아요. 노트 한 개당 항상 딱 세 단계예요.

한 줄로: 프롬프트 체이닝 = "앞 단계 결과 없이는 뒷단계를 할 수 없다."

전체 흐름

단계 사이에 게이트 두기

큰 작업을 순서가 정해진 여러 단계로 쪼개고, 각 단계의 LLM 호출이 앞 단계의 결과를 받아 처리하는 모양이에요. 여기서 만들 파이프라인은 구어체 녹취를 받아 (1) 학습자가 읽을 3문장 노트로 다듬고, (2) 다듬는 동안 핵심 용어가 사라지지 않았는지 파이썬 문자열 검사로 확인하고, (3) 통과하면 학습 목표 문장을 뽑아요.

개념 설명용 코드 — State 선언과 LLM 노드 함수는 생략한 뼈대예요

KEY_TERMS = ["State", "리듀서"]               # 다듬는 동안 사라지면 안 되는 용어

def gate_check(state) -> str:                  # 게이트: LLM이 아니라 코드가 검사한다
    missing = [t for t in KEY_TERMS if t not in state["note"]]
    return "pass" if not missing else "fail"

builder.add_edge(START, "polish_note")         # LLM ①: 녹취를 3문장 노트로
builder.add_conditional_edges("polish_note", gate_check,
                              {"pass": "write_objectives", "fail": "fix_note"})
builder.add_edge("fix_note", "write_objectives")   # 보정한 뒤엔 다시 검사하지 않고 다음 단계로
builder.add_edge("write_objectives", END)      # LLM ②: 학습 목표 뽑기

"이걸 한 번에 시키면 안 되나?" 싶은데, 한 호출로 몰면 세 가지 문제가 생겨요.

  • 요구가 많으면 모델이 일부를 흘려요. 셋을 시켰는데 둘만 하거나, 학습 목표에 집중하다 노트에서 용어를 빠뜨려요.
  • 어디서 틀렸는지 알 수 없어요. 단계를 쪼개 두면 중간 결과가 State에 남아서 result["note"]만 꺼내 봐도 어느 단계까지 멀쩡했는지 보여요.
  • 중간에 끼어들 틈이 없어요. 단계 사이가 열려야 그 틈에 우리 코드를 끼울 수 있어요.

LLM의 출력은 확률적이라 같은 프롬프트에도 결과가 달라요. 그 사이에 결정적2인 코드 검사를 끼우면 전체 시스템의 신뢰도가 올라가요. 앞 편에서 날짜 계산을 LLM 대신 함수에 맡기던 것과 같은 이유예요. 다만 이 게이트는 누락만 잡아요. 용어가 들어 있기만 하면 그 용어를 틀리게 설명해도 통과해요. 이게 실제로 어떤 모습인지는 아래에서 노트 두 개로 확인해요.

하나 더. Anthropic 원문 그림은 게이트에서 떨어지면 그냥 종료하는데, 저는 보정 노드로 보냈어요. 어느 쪽이 맞는지는 상황에 달렸어요. 학습 자료를 배포하는 일이라면 용어가 뭉개진 노트를 내보내느니 멈추고 사람을 부르는 게 나을 수도 있어요.

보정 노드를 뒀더라도 화살표는 여전히 앞으로만 가요. 위 코드에서 fix_note 다음은 게이트가 아니라 write_objectives거든요. 그러니 보정한 노트가 진짜 고쳐졌는지는 아무도 다시 안 봐요. 일부러 그렇게 뒀어요. 게이트로 되돌리면 통과할 때까지 도는 바퀴가 생기고, 그건 체이닝이 아니라 ⑤ 평가자-최적화자예요. 되돌아가는 선이 있느냐 없느냐가 두 모양이 갈리는 지점이에요. 되돌리려면 몇 바퀴까지 돌지도 같이 정해야 하는데, 그 이야기는 그 편에서 해요.

맞는 일: 단계에 자연스러운 순서가 있고, 단계마다 품질을 중간 확인할 수 있는 작업. 안 맞는 일: 단계끼리 독립적이면 병렬화가, 어떤 단계를 밟을지가 입력마다 다르면 라우팅이 나아요.

게이트가 못 보는 것 — 결정적 검사의 한계

체이닝을 이야기할 때 빠지지 않는 단서가 하나 있어요. 결정적인 계산에도 한계가 있다는 거예요. 처음엔 무슨 말인지 감이 안 왔는데, 위 gate_check의 검사 줄에 노트 두 개를 직접 넣어 보니 바로 보였어요.

실행: 로컬 파이썬 — 아무 환경 OK, 따로 설치할 것 없어요

KEY_TERMS = ["State", "리듀서"]

note_a = "리듀서는 State에서 오래된 값을 지워 주는 기능이다."
note_b = "state의 한 칸에 값이 여럿 오면 리듀서가 합치는 법을 정한다."

for note in [note_a, note_b]:
    missing = [t for t in KEY_TERMS if t not in note]
    print("통과" if not missing else f"실패 (누락: {missing})")

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

통과
실패 (누락: ['State'])

판정이 거꾸로 나왔어요.

  • 틀린 설명이 통과했어요. note_a에는 두 용어가 다 들어 있으니 게이트를 지나가요. 그런데 리듀서는 값을 지우는 장치가 아니라, 같은 칸에 여러 값이 들어올 때 어떻게 합칠지 정하는 장치예요(병렬화 편에서 봐요). 게이트는 글자가 있는지만 볼 뿐, 그 글자가 들어간 문장이 맞는 말인지는 몰라요.
  • 맞는 설명이 떨어졌어요. note_b는 뜻이 맞는데 State를 소문자 state로 적었어요. 파이썬의 in은 대소문자까지 똑같아야 같은 글자로 쳐서 "State가 빠졌다"며 떨어뜨려요. 사람이라면 같은 말로 읽었을 텐데요.

앞 편에서 날짜 계산을 함수에 맡긴 것처럼, 결정적인 검사는 정해 둔 규칙 안에서는 절대 흔들리지 않아요. 대신 규칙 밖의 일은 아예 못 봐요. 그래서 검사를 이렇게 나눠 맡겨요.

흔한 실수표기만 달라도 떨어뜨리고, 틀린 내용도 글자만 맞으면 통과시켜요기준이 흐리면 "더 좋게 써 보세요" 같은 뜬 피드백만 나와요

둘은 서로를 대신하는 게 아니라 겹쳐 쓰는 관계예요. "용어가 빠지지 않았나"처럼 확실하게 걸 수 있는 건 코드로 걸고, 그 위에 뜻을 보는 검사를 얹어요. 평가자-최적화자 편에서 LLM 평가자를 따라 고쳐 쓰다가 주제가 엉뚱하게 흘러간 장면이 나오는데, 그때 "무엇을 잃으면 안 되는가"를 붙잡아 주는 것도 결국 이 코드 게이트예요.

게이트를 두는 진짜 이유와, 코드로 못 하는 검사

중요꼭 기억할 것

게이트를 두는 이유는 하나예요. 답이 매번 조금씩 달라지는 LLM 단계들 사이에 늘 같은 판정을 내리는 코드 검사를 끼워서, 틀린 중간 결과가 다음 단계로 흘러가지 못하게 막는 거예요. 한 단계의 실수가 뒤 단계 전체로 번지기 전에 문 앞에서 끊는 셈이에요.

반대로 게이트가 호출 수나 시간을 줄여 주지는 않아요. 검사에서 떨어지면 보정 노드가 LLM을 한 번 더 부르니 호출은 오히려 늘 수 있고, 여러 단계를 동시에 돌려 시간을 줄이는 건 병렬화의 일이에요. 다음에 실행할 함수를 LLM에게 스스로 고르게 하는 것도 게이트가 아니라 에이전트 쪽 이야기고요.

그런데 바로 위에서 본 것처럼 코드 게이트는 규칙으로 적을 수 있는 것만 봐요. "처음 배우는 사람이 이해할 수 있는 노트인가?"를 검사하고 싶다면요? 이건 어떤 단어가 들어 있는지로는 판단할 수 없어요. 용어를 풀어 설명했는지, 설명 순서가 자연스러운지 같은 뜻을 읽어야 알 수 있어서 if문 규칙으로는 못 적어요.

중요꼭 기억할 것

뜻을 읽어야 하는 검사는 LLM을 게이트로 써서 만들어요. 평가 기준을 프롬프트에 구체적으로 적고, LLM이 "통과/실패"와 그 이유를 정해진 형식으로 답하게 한 뒤, 그 답으로 조건부 엣지를 갈라요. 실패하면 그 이유를 보정 노드에 넘겨 다시 고치게 하고요. "정해진 형식"은 라우팅 편의 구조화 출력이 맡아요. 이렇게 하면 '늘 같은 판정'은 포기하는 대신 뜻을 볼 수 있어요. 그래서 둘 중 하나를 고르는 게 아니라, 확실하게 걸 수 있는 건 코드 게이트로 먼저 걸고 그 위에 LLM 게이트를 얹어요.

채점하는 LLM도 틀릴 수 있다는 한계는 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge에서 다뤘고, 떨어진 이유를 되돌려 고쳐 쓰는 반복은 평가자-최적화자 편으로 이어져요.

나쁜 선택 vs 좋은 선택 — 세 요구를 한 번에 시킬 때

같은 파이프라인으로, 다듬기·용어 확인·목표 뽑기 세 가지를 어떻게 시켰는지 비교해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: "녹취를 3문장 노트로 다듬고, 핵심 용어를 지키고, 학습 목표도 뽑아 줘"를 프롬프트 하나에 다 넣어 한 번에 호출했어요.

무슨 일이 생기나: 모델이 학습 목표를 뽑는 데 집중하다 노트에서 용어 하나를 흘려요. 세 가지가 한 응답에 섞여 있어서 어디서부터 틀렸는지 result 하나만 봐서는 알 수 없고, 중간에 검사를 끼울 자리도 없어요.		 무엇을 했나: 다듬기 → 게이트(코드) → 목표뽑기로 단계를 쪼갰어요. 게이트는 용어 목록이 노트에 남아 있는지만 확인해요.

무슨 일이 생기나: 용어가 빠지면 그 자리에서 바로 잡히고 보정 노드로 돌아가요. state["note"]를 찍어 보면 다듬기 단계까지는 멀쩡했는지, 어디서부터 틀렸는지 바로 보여요.

정리하면 체이닝에서 물을 건 하나예요. "이 요구들 사이에 순서가 있고, 그 사이에 확인할 게 있나?" 그렇다면 한 호출에 몰아넣지 말고 단계로 쪼개야 해요.

이 글에 나온 숫자

무엇의 숫자인가값알아 둘 것
용어 두 개로 통과/실패를 가른 노트 두 개를 검사했을 때2건 중 2건 판정이 뒤집힘글자만 보는 게이트라 뜻이 맞아도 표기(State vs state)가 다르면 떨어지고, 뜻이 틀려도 글자만 들어 있으면 통과해요 (게이트가 못 보는 것)

내 파이프라인에 대입하면 — 이 블로그도 체이닝으로 쓰여요

이 블로그의 모든 글은 본문을 같은 순서로 써요. 한 줄 정의 → 이 글을 읽기 전에 박스 → 비유 → 흐름 그림 → 나쁜 선택 vs 좋은 선택 → 숫자 표 → 용어 각주. 앞 칸을 채워야 뒤 칸을 채울 수 있는 한 줄이에요. 이 글도 그 순서대로 여기까지 왔어요.

사이에 두는 게이트도 있는데, 코드로 되는 검사와 안 되는 검사가 갈려요.

게이트가 보는 것코드로 검사되나
"지난 글"·"이전 편" 같은 가리키는 말이 든 문단에 링크가 있는가돼요 — 찾아서 세면 끝
표의 열 이름이 한 글자짜리 낱말 하나로만 돼 있지 않은가돼요 — 글자 수를 재면 끝
그 비유가 이 편 내용에 실제로 맞는가안 돼요 — 읽어 봐야 알아요

맨 아래 칸이 위의 게이트가 못 보는 것에 해당해요. 그래서 평가자-최적화자 편의 평가자가 필요해져요.

실제 코드에 대입하면 — 교정기의 스물네 규칙이 순서대로 이어져요

교정기(korean-subtitle-corrector)에 이 패턴이 그대로 들어 있어요. 줄 하나를 고치는 함수가 규칙 스물네 개를 순서대로 통과시켜요. 앞 규칙이 고친 결과를 뒤 규칙이 받는 한 줄이에요. 순서가 장식이 아니에요 — 저장소에 제가 적어 둔 이유가 있어요. 말줄임표를 먼저 온점 세 개로 통일해야, 그 뒤의 마침표 규칙이 ...을 문장 종결 마침표로 오인하지 않아요. 순서를 뒤집으면 말줄임표가 문장 끝으로 오해받아 지워져요.

사이에 둔 게이트도 있어요. 규칙 하나가 끝날 때마다 verify_edit()라는 관문이 "이 규칙이 바꾸겠다고 선언한 것만 실제로 바뀌었는가"를 봐요. 선언 안 한 낱말이 바뀌었으면 그 규칙의 결과를 통째로 버리고 원문을 그대로 써요. 이건 코드로 되는 검사예요 — 문자열 둘을 대 보면 끝이니까요. 반면 1편에서 말한 되/돼는 읽어 봐야 갈려요. 그래서 그 자리에만 모델을 붙였어요. 위의 게이트가 못 보는 것이 실제로 갈리는 선이 여기예요.

다만 관문이 모든 규칙 뒤에 있는 건 아니에요. 라우팅 편에서 볼 자막 구두점 규칙 다섯 개에는 안 달려 있어요. 그 규칙들은 부호만 건드린다고 보고 통과시킨 건데, 게이트를 어디에 두고 어디에 안 둘지도 결국 사람이 정한 선이라는 뜻이에요.

이럴 때 의심하세요

이 편의 실수는 대부분 에러 없이 결과만 틀려요. 게이트가 틀린 노트를 통과시켜도 그래프는 끝까지 멀쩡히 돌아요. 그래서 끝까지 돌았다고 넘어가지 말고 결과 칸을 직접 열어 봐야 해요.

증상이 아직 없어도, AI에게 "게이트를 달아 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
게이트 판정과 내가 읽은 판정이 거꾸로예요. 통과한 노트를 읽어 보니 설명이 틀렸거나, 뜻이 맞는 노트가 계속 보정 노드로 가요 게이트 함수의 검사 줄이에요. t not in state["note"]처럼 글자가 들어 있는지만 보는 줄이면, 뜻은 처음부터 안 봐요 판정이 이상했던 노트를 그 검사 줄에 직접 넣어 돌려 봐요. State와 state처럼 표기만 달랐다면 비교 전에 둘 다 .lower()로 맞추고, 틀린 설명이 통과한 거라면 코드 게이트로는 못 잡으니 LLM 게이트를 얹어요 (게이트가 못 보는 것)

이 편의 문제는 대부분 게이트 함수의 검사 줄과, 그 줄이 실제로 보는 State 칸이 서로 멀리 떨어져 있어서 생겨요. 에이전트에게 맡길 때는 고치기 전에 게이트마다 무엇을 보는지 한 표로 보여 달라고 해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — LangGraph 코드가 있는 프로젝트 폴더에서

이 프로젝트에서 조건부 엣지로 쓰이는 게이트 함수를 전부 찾아서 표로 보여 줘. 아직 코드는 고치지 마.
1. 게이트 함수 이름과, 검사하는 State 칸
2. 그 검사가 "글자가 있는지"만 보는지, "뜻"까지 보는지(LLM을 부르는지)
3. 실패했을 때 가는 곳 — 보정 노드인지, 그냥 종료인지

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 복습할 때 이것부터 보면 돼요. 다른 편의 같은 목록은 1편 · 2편 · 3편 · 4편에 있어요.

  • 게이트는 LLM 단계 사이에서 틀린 중간 결과를 막는 코드 검사
  • 뜻을 읽어야 하는 검사는 LLM을 게이트로

직접 해보기

  1. 게이트 규칙 하나 더 달기 — 바꿀 것: KEY_TERMS에 용어를 하나 더 추가해요. 측정할 것: 원래는 통과하던 노트가 이제 실패로 바뀌는지. 비교할 것: 규칙이 늘수록 통과 기준이 어떻게 더 까다로워지는지 봐요.
  2. 게이트를 LLM으로 바꿔 보기 — 바꿀 것: gate_check를 "이 노트는 처음 배우는 사람이 이해할 수 있나?"를 묻는 LLM 호출로 바꿔요. 측정할 것: 같은 노트 열 개에 대한 판정이 실행마다 같은지. 비교할 것: 코드 게이트의 '항상 같은 판정'과 대 봐요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.
