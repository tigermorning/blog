모르면 이런 일이 생겨요
  • 원인을 안 찾고 경로 검사를 통째로 꺼버리면 그 순간엔 되는 것처럼 보여요. 실제 원인은 모델이 절대 경로를 보냈는데 하네스가 상대 경로만 처리한 것이었고, 권한 경계만 사라진 채 남아요.
  • 최종 답이 그럴듯하다는 이유로 성공이라 하면, 도구가 아예 실행 안 됐는데도 통과로 세게 돼요. 읽기가 실행됐나 / 결과가 다음 요청에 들어갔나 / 답이 원문과 맞나를 따로 봐야 해요.
  • 모든 실패를 프롬프트나 모델 성능 탓으로 묶으면, 실제로는 결과 반환 코드가 빠진 건데 모델만 계속 바꾸게 돼요.
  • 검사 코드도 내 컴퓨터의 프로세스로 돌아요. 파일 도구를 폴더로 제한해도 검사 프로세스 전체가 그 안에 갇히는 건 아니에요.
어디에 쓰나
  • 모의 응답으로 도구 요청과 결과 연결을 먼저 확인하고, 그다음 실제 모델로 같은 작업을 돌릴 때요.
  • 정상 경로가 되면 같은 날 없는 파일·범위 밖 경로도 같이 확인할 때요.
  • "이제 됩니다" 대신 이전 실패가 사라진 결과와 제한이 유지된 결과 둘을 나란히 남길 때요.
  • 기록이 없으면 먼저 기록만 붙이고, 기록 추가와 문제 수정을 한 번에 섞지 않을 때요.

여기까지 오면 문서에 사용자와 작업, 실행 범위, 상태, 인터페이스, 완료 조건이 다 들어 있어요. 이제 코드를 씁니다.

그렇다고 계획한 화면과 도구를 한 번에 다 만들어 달라고 요청하지는 않아요. 먼저 작은 요청 하나가 실제 모델과 도구를 거쳐 사용자에게 돌아오는 경로를 완성합니다.

비유 — 물 한 컵을 먼저 흘려 보기

새 건물에 수도를 놓는다고 해 볼게요. 정수장에서 온 물이 건물 배관을 지나, 계량기를 거쳐, 주방 수도꼭지에서 나와야 해요.

한 가지 방법은 구간마다 완벽하게 짓는 것이에요. 배관을 층마다 촘촘히 깔고, 계량기를 여러 개 달고, 수도꼭지를 방마다 붙여요. 그러고 마지막 날 밸브를 엽니다. 그런데 물이 안 나와요. 어디가 문제인지 알려면 이제 전 구간을 뒤져야 해요.

다른 방법은 얇은 관 하나를 정수장부터 주방 꼭지까지 먼저 잇고, 물 한 컵을 흘려 보는 거예요. 꼭지 하나, 관 하나뿐이라 초라해 보여요. 그런데 이 한 번으로 이음매·수압·계량기 방향이 다 확인돼요. 그 뒤에 관을 굵히고 꼭지를 늘리면 돼요.

그리고 물이 안 나올 때도 방법이 있어요. 계량기가 도는지, 관 중간 밸브가 열렸는지, 꼭지가 막혔는지를 순서대로 봐요. "물이 안 나와요"라고만 말하면 아무도 못 고쳐요.

비유 속 요소원래 개념
정수장 → 배관 → 계량기 → 수도꼭지모델 연결 → 도구 실행 → 실행 기록 → 화면 출력
얇은 관 하나로 물 한 컵수직 구현 — 작은 요청 하나를 끝까지 관통
구간별로 완벽히 짓고 마지막에 잇기도구 열 개를 만든 뒤 마지막에 연결하는 방식
수압 시험용 물모의 응답1 — 상황을 내가 정해 주는 테스트 데이터
실제로 마시는 물실제 모델로 같은 작업을 수행한 결과
계량기·밸브·꼭지를 순서대로 점검막힌 단계를 좁혀 가는 디버깅

핵심 한 줄: 관을 다 깔기 전에 물 한 컵을 끝까지 흘려 보면, 이음매가 어긋난 자리가 그때 드러나요.

다만 비유가 끊기는 점이 있어요. 수도는 물이 나오면 대체로 끝이지만, 하네스는 "답이 나왔다"가 끝이 아니에요. 나온 답이 원문과 맞는지까지 봐야 해요. 수압 시험은 통과했는데 물맛이 이상한 상황이 실제로 자주 생깁니다.

여기서 다시 못 박아 둘 게 있어요. 여기서 구현하는 건 내가 설계한 하네스예요. Claude Code나 OpenCode는 코드를 쓰고 검토하는 협업 도구로 쓰되, 완성한 제품의 모델·도구 반복 전체를 그 CLI에 대신 맡기지 않습니다. 이 구분이 흐려지면 나중에 "무엇을 만들었는지" 자체가 흐려져요.

실행 환경과 키

IMPLEMENTATION_PLAN.md에 필요한 파일·의존성·실행 방법을 적게 해요. Python, TypeScript, Rust는 쓰는 패키지와 실행 명령이 다르니, 모두에게 같은 명령을 강제하기보다 내가 고른 언어에 맞는 방법을 문서에 남깁니다.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

내가 선택한 언어로 실행 환경을 준비하고, 설치와 실행 방법을 README에 적어 줘. 필요한 패키지의 역할도 설명해 줘.

"설치 끝났습니다"라는 말만 듣고 넘어가지 말고, 프로그램을 실제로 실행해 입력을 받거나 준비 상태를 표시하는지 봐요. 모델을 붙이기 전에 단순한 실행 경로부터 확인하면, 나중에 환경 문제와 모델 문제를 나누기가 쉬워집니다.

모델 인증 정보는 소스코드와 분리해요. 발급받은 API 키는 프로그램이 읽도록 정한 환경 변수2나 비밀정보 설정 경로에 넣습니다. 그리고 키를 채팅 요청, PRD, 검사 결과, 화면 캡처에 붙이지 않아요.

환경 변수에서 초보자가 제일 자주 걸리는 지점이 이거예요. 환경 변수는 앱을 실행하는 그 프로세스에 전달돼야 해요. 다른 터미널 창에서 값을 설정하고, 이미 돌고 있는 앱이 알아서 알게 될 거라고 기대하면 안 됩니다. 설정 확인과 오류 메시지도 구현 항목이에요.

그리고 하나 더. 키가 없는 경우를 임의의 예제 응답으로 대신 성공 처리하지 않습니다. Ollama를 골랐다면 로컬 서비스와 선택 모델이 준비돼 있는지 확인하고요.

첫 수직 구현

실습 파일에는 직접 눈으로 확인할 수 있는 짧은 내용을 넣어요. 예를 들어 가상의 모임 안내문에 준비물 두 가지와 시작 순서를 적는 식이죠. 키나 실제 개인 자료가 필요하지 않습니다.

순서는 이래요.

  1. 모의 응답으로 도구 요청과 결과 연결을 먼저 확인해요. 잘못된 인자나 반복 호출 같은 조건을 재현하기 좋아요. 다만 이건 실제 모델이 그 도구를 골랐다는 증거는 아니에요.
  2. 그다음 실제 모델로 같은 읽기 작업을 수행합니다.

결과를 볼 때는 최종 답이 그럴듯하다는 이유만으로 성공으로 판단하지 않아요. 세 가지를 따로 확인해요.

  • 파일 읽기 도구가 실제로 실행되었는가
  • 반환한 내용을 다음 모델 요청에 연결했는가
  • 답변이 원문과 맞는가

이게 A01·A02의 증거가 됩니다.

실패 경로도 같은 날 확인하기

정상 동작 하나가 연결되면, 같은 경로에 잘못된 입력을 넣어 봐요. 없는 파일, 허용 폴더 밖 경로, 잘못된 도구 인자요. 모델이 계속 요청하는 상황은 모의 응답으로 만들어 합의한 상한에서 멈추는지 봅니다.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

정상 읽기는 됐어. 없는 파일과 범위 밖 경로도 확인하고, 실패를 성공처럼 표시하는 곳이 없는지 봐 줘.

여기서 문제를 발견하면 어느 단계의 문제인지 분리해서 고쳐요. 도구 이름이 맞아도 인자가 틀릴 수 있고, 프로그램 실행이 성공해도 모델이 내용을 잘못 해석할 수 있어요. 그리고 구현 중에 계약을 바꿔야 한다면 코드만 바꾸지 말고 INTERFACES.md와 완료 조건도 함께 갱신합니다.

코드 변경과 검사로 넓히기

다음은 5편에서 정한 검증 사례를 실제 파일로 만들 차례예요. 작은 결함이 있는 실습 코드와, 그 동작을 확인하는 검사를 준비합니다.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

내가 선택한 언어로 작은 결함 코드와 테스트를 준비해 줘. 정해 둔 기대 동작을 기준으로 수정 전 실패부터 확인하자.

여기서 다시 강조할 게 있어요. 기대하는 동작은 수정 전에 정해요. 생성된 코드가 우연히 통과하도록 기대값을 바꾸면 검증의 의미가 사라집니다.

그다음 하네스에 기능을 붙이는데, 실습 코드는 아직 안 고쳐요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

우리 하네스에 변경 제안·승인·테스트 기능을 구현해 줘. 실습 코드는 아직 고치지 마.

그리고 이제 제가 만든 하네스를 따로 실행해서, 그 프로그램의 입력창에 요청을 넣어요. 이 구분이 이번 편에서 제일 중요한 대목이에요.

실행: 내가 만든 하네스의 입력창에 붙여넣기 — 개발 도우미가 아니라 방금 만든 내 프로그램이에요

이 실습 코드의 문제를 찾아 고쳐 줘. 변경을 먼저 보여 줘.

확인할 것은 개발 도우미가 파일을 고친 기록이 아니라, 제가 만든 하네스의 변경 제안 화면·승인 화면·도구 실행 기록이에요. 그리고 두 가지를 각각 검사해요 — 승인하면 지정 검사가 실행되는지, 거절하면 파일이 그대로인지.

검사 도구에는 정한 실행 대상과 시간 제한을 적용해요. 편하게 시키려고 임의 셸 명령 전체를 열어 버리면 D05에서 정한 범위를 바꾸는 거예요. 권한을 넓혀야 한다면 이유와 영향을 먼저 결정합니다.

그리고 꼭 알아 둘 한계가 있어요. 검사 코드도 내 컴퓨터의 프로세스로 실행돼요. 파일 도구가 폴더를 제한하더라도, 검사 프로세스 전체가 그 폴더 안에 격리되는 건 아니에요. 그래서 이 실습에서는 확인 가능한 작은 실습 코드만 실행하고, 신뢰할 수 없는 코드를 실행하려면 별도의 운영체제 격리 설계가 필요합니다. AI가 짠 백엔드 코드에서 반드시 확인할 것들에서 짚은 감각과 같은 결이에요.

나쁜 선택 vs 좋은 선택

수도꼭지에서 물이 안 나올 때의 두 가지 대응이에요.

나쁜 선택좋은 선택
무엇을 했나: 읽기 요청은 오는데 파일 내용이 안 돌아와서, 경로 검사를 통째로 끄고 아무 경로나 읽게 바꿨어요. 그랬더니 동작해서 "해결"이라고 적었어요.

무슨 일이 생기나: 진짜 원인은 모델이 절대 경로를 보냈고 하네스가 상대 경로만 처리하고 있었던 것이었어요. 원인은 그대로인 채 권한 경계만 사라졌어요. 나중에 A05(경로 이탈 거절)가 실패하고, 그때는 왜 껐는지 기억도 안 나요.		 무엇을 했나: 먼저 실행 기록을 붙여 어느 단계까지 진행됐는지 봤어요 — 도구 요청은 왔고, 인자 검사에서 걸렸더군요. 그 자리에서 경로 정규화만 고쳤어요.

무슨 일이 생기나: 권한 경계는 그대로 남고 실패했던 입력만 통과해요. 그리고 같은 실패가 다시 생기는지 확인할 검사도 한 줄 늘었습니다.

막힌 지점 좁히기

"에이전트가 안 돼요"는 진단이 아니에요. 모델 연결 문제인지, 도구가 실행되지 않은 건지, 실행 결과를 잘못 해석한 건지 알 수 없거든요.

그래서 기대 결과를 이미 아는 아주 작은 요청부터 씁니다. 실습 파일에 모임 시작: 오후 3시라고 적고, 만든 하네스에 그 파일의 시작 시간을 물어봐요. 답이 없거나 틀리면, 같은 요청을 반복하기 전에 어디까지 진행됐는지 봅니다.

직접 해보기

  1. 바꿀 것 — 작은 읽기 작업 하나를 실제 모델로 끝까지 관통시키고, 그다음 변경 제안·승인·검사 실행으로 넓혀요.
  2. 측정할 것 — 수정 후에는 실패했던 입력을 그대로 다시 실행해요. 그다음 정상 읽기와 권한 거절 같은 가까운 사례도 확인하고요.
  3. 비교할 것 — "이제 됩니다"라는 설명 대신, ①이전 실패가 사라졌고 ②지켜야 할 제한도 유지된 실행 결과 두 개를 나란히 남겨요.

단계마다 구현 계획에 확인한 결과와 남은 문제를 적어 둡니다. 다음 편에서는 같은 설계의 Python 구현을 열어, 지금 만든 설계가 코드의 어디에 앉는지 대조해 봅니다.
