비유로 먼저 — 영업 중인 식당 옆에 새 주방을 짓는 일

사장인 내가 영업 중인 식당의 주방을 새로 고치고 싶어요. 영업 중에 주방 문을 닫고 고치면 그 시간 동안 주문을 못 받아요. 그래서 옆에 새 주방(green)을 지어 두고, 준비가 끝나면 홀 안내 직원이 손님을 새 주방으로 안내하는 방향만 바꿔요. 새 주방에 문제가 있으면 옛 주방(blue)으로 손님을 다시 보내면 되니, 옛 주방은 한동안 불을 꺼서는 안 돼요. 그런데 한 가지가 더 있어요. 주방 직원이 주문을 머릿속에만 기억하면, 손님을 새 주방으로 옮기는 순간 주문이 사라져요. 주문을 게시판(DB)에 적어 두어야 누가 바뀌어도 이어져요.

다만 여기서 비유가 끊기는 점이 있어요. 식당의 새 주방은 사람이 지어야 하지만, 이번 실습의 green은 같은 이미지에서 컨테이너 하나를 더 띄운 것이라 몇 초면 생겨요. 그리고 blue와 green이라는 색이 왜 하필 그 색인지는 제가 읽은 자료에 없어요. 실습에서 붙인 이름표로만 알고 있어요.

전체 흐름 — 사용자는 입구 하나, 방향은 Nginx가

글 전체를 한 장으로 먼저 보면 이래요. 사용자는 Nginx 주소 하나만 알고, Nginx 설정이 요청을 blue로 보낼지 green으로 보낼지 정해요. 두 서버는 같은 DB를 보고 있어서, 어느 쪽으로 가도 대화가 이어져요.

무엇이 문제인가 — 무중단에는 서로 다른 조건이 두 개 있어요

새 버전으로 바뀌는 순간 사용자에게는 두 가지 일이 생길 수 있어요. 요청이 끊기거나, 하던 일이 사라지거나예요. 이 두 가지는 서로 다른 조건이고, 이를 가능하게 하는 것도 달라요.

확인할 것해당하는 용어이를 가능하게 하는 것
요청이 끊기지 않음무중단 배포 (zero-downtime deployment)로드밸런서, 블루그린, 헬스체크5, 그레이스풀 셧다운6 (아래 두 번째~네 번째 절)
하던 일이 이어짐무상태 (stateless)상태를 서버 밖의 DB에 두기 (여섯 번째 절)

요청이 하나도 실패하지 않았는데도 사용자가 방금 나눈 대화가 사라졌다면, 사용자에게는 서비스가 끊긴 것과 똑같아요. 그래서 무중단이라고 하려면 위 표의 두 가지를 둘 다 만족해야 해요.

무중단의 정도는 가용성(availability)7으로 말해요. 가용성이 낮을수록 1년 동안 서비스가 멈추는 시간이 길어요. 아래 값은 가용성별로 1년 중 멈추는 시간의 기준이에요.

서버를 어떻게 바꿔야 끊기지 않나 — 두 벌을 두고, 방향을 앞에서 정해요

서버가 한 벌뿐이면 그 서버를 교체하는 동안 요청을 받을 곳이 없어요. 그래서 같은 일을 하는 서버를 여러 벌 두고, 요청을 어디로 보낼지를 앞에서 정해요.

이중화와 단일 장애점

이중화8는 같은 일을 하는 것을 하나 더 두는 것이고, 단일 장애점(SPOF)9은 그것 하나만 고장 나도 전체가 멈추는 부분이에요. 서버가 한 대뿐이면 그 서버가 SPOF이고, 두 대를 두면 한 대가 고장 나도 다른 한 대가 받아요. 이중화에는 두 가지 방식이 있어요.

방식뜻평소 처리량 (같은 시간에 처리하는 요청 수)
액티브-스탠바이한 대가 일하고 한 대는 기다리다가, 일하던 쪽이 멈추면 넘겨받아요늘지 않아요. 기다리는 한 대는 평소에 일하지 않기 때문이에요
액티브-액티브두 대가 모두 요청을 받아요늘어나요. 두 대가 요청을 나눠 처리하므로 같은 시간에 더 많은 요청을 처리할 수 있어요

이중화의 목적은 어느 쪽이든 고장 나도 멈추지 않는 것이에요. 표의 처리량은 같은 시간에 몇 건을 처리하느냐이고, 요청 하나가 끝나는 데 걸리는 시간(응답 시간)과는 달라요. 액티브-액티브는 처리량을 늘릴 뿐 응답 시간을 줄여 주지는 않아요. (이 부분은 일반적인 설명이고, 제가 직접 확인한 것은 아니에요.)

고가용성은 보통 세 단계로 이뤄요. ① 이중화: 예비를 둬요. ② 장애 감지: 어느 쪽이 고장 났는지 알아채요(다섯 번째 절의 헬스체크). ③ 장애 조치(failover): 고장이 감지되면 요청 방향을 예비 쪽으로 자동으로 바꿔요. 이중화만 해 두고 감지와 전환이 사람 손에 달려 있으면, 사람이 오기 전에 이미 멈춰 있을 수 있어요. 예비가 고장 난 쪽과 같은 건물·같은 전원에 있으면 함께 멈추니, 위치를 나누는 것도 중요해요. (이 단락은 같은 모듈을 듣는 다른 분의 보고서를 참고한 일반적인 설명이고, 제가 직접 확인한 것은 아니에요.)

새 버전으로 바꾸는 세 가지 방식

서버가 여러 벌이면 새 버전을 올리는 방법도 달라져요. 아래 세 방식은 모두 로드밸런서가 요청 보내는 곳을 바꾸는 방법이에요.

방식뜻
롤링 (rolling update)10같은 일을 하는 서버 여러 대를 한 대씩 새 버전으로 교체해요. 한 대를 빼서(drain11) 바꾸고, 헬스체크를 통과하면 다시 넣는 일을 반복해요. 바꾸는 동안은 옛 버전 서버와 새 버전 서버가 동시에 켜져 있고, 로드밸런서가 요청을 그 둘에 나눠 보내요. 그래서 요청마다 옛 버전이 받을 수도, 새 버전이 받을 수도 있어요. 모든 서버를 바꾸고 나면 모두 새 버전이에요
블루그린 (blue-green)지금 쓰는 서버 묶음(blue)과 같은 크기의 새 묶음(green)을 따로 띄워 준비해요. 헬스체크로 green이 정상인지 확인한 뒤 요청 방향을 blue에서 green으로 한 번에 바꿔요. 어느 순간에도 한 묶음만 요청을 받고, blue는 롤백을 위해 남겨 둬요
카나리 (canary)12새 버전 서버를 소수만 띄워 일부 요청(예: 1%, 10%)만 새 버전으로 보내 봐요. 문제가 없으면 비율을 단계적으로 올려 가요. 올리는 동안 옛 버전은 나머지 요청을 받아요
  • drain(드레이닝)은 로드밸런서 쪽에서 하는 일이에요. 서버 한 대를 요청 보내는 목록에서 뺄 때, 그 서버로 새 요청은 더 보내지 않고 이미 받은 요청은 끝까지 마치게 한 뒤 꺼요. 서버를 하나씩 빼는 롤링의 매 단계에서 쓰이는 부품이에요.
  • 그레이스풀 셧다운은 서버 쪽에서 하는 일이에요. 끄라는 신호를 받은 서버가 새 요청은 받지 않고 하던 요청을 마친 뒤 스스로 종료해요. drain과 목적(하던 요청을 끊지 않기)이 같아서 두 말을 거의 같은 뜻으로 쓰기도 하지만, 정확히는 drain은 로드밸런서가, 그레이스풀 셧다운은 서버가 해요. 세 방식 모두 서버를 목록에서 뺄 때는 이 마무리가 필요해요. 롤링은 교체할 때마다, 블루그린은 전환한 뒤 옛 묶음을 끌 때, 카나리는 새 버전이나 옛 버전 서버를 빼거나 끌 때 필요해요. 카나리에서 비율만 올릴 때는 서버를 빼지 않으므로 필요하지 않아요.
  • 방향을 바꾸는 방법으로 DNS 주소를 바꾸는 길도 있지만, 사용자 기기와 중간 서버가 옛 주소를 한동안 기억해서 바로 바뀌지 않아요. 그래서 전환은 로드밸런서 쪽에서 해요. (일반적인 설명이고, 같은 모듈을 듣는 다른 분의 보고서를 참고했어요. 제가 직접 확인한 것은 아니에요.)
  • 배포 방식을 그린 도식에서 "Cloud Run 기본 배포는 롤링이 아니라, 새 리비전이 준비되면 트래픽을 한꺼번에 넘기는 방식"이라는 설명을 봤지만 그림 설명일 뿐이고 제가 문서로 확인하지는 못했어요. Cloud Run 문서 요약에는 요청을 "최신의 정상 리비전으로 가능한 한 빨리" 보낸다고 적혀 있어요.

DB 호환성옛 버전과 새 버전이 같은 DB를 모두 읽을 수 있게 해요새 버전이 테이블 구조를 바꾸면 옛 버전이 읽지 못하고, 롤백해도 같은 문제가 남아요

롤백과 blue를 끄지 않는 이유

실습에서는 blue에서 v1 프로그램이, green에서 v2 프로그램이 돈다고 보고 전환했어요. 블루그린은 실제 배포 방식의 이름이고, blue와 green은 실습에서 붙인 컨테이너 이름표예요.

  • 롤백은 데이터를 되돌리는 것이 아니라, 어느 버전의 프로그램이 요청을 받게 할지를 이전으로 되돌리는 것이에요. 되돌릴 수 있는 것은 blue를 끄지 않고 계속 돌려 두기 때문이에요.
  • 전환한 직후 blue를 바로 끄면 두 가지를 잃어요. blue가 처리하던 요청이 끊기고(그레이스풀 셧다운을 지키지 못함), 롤백할 곳도 사라져요.
  • 이전 버전을 언제 꺼야 하는지는 제가 읽은 자료가 정하지 않았어요. 구체적인 시간은 없어요.

요청이 갈 곳은 누가 정하나 — Nginx

방향을 바꾸는 장치가 Nginx13예요. Nginx는 웹 서버, 리버스 프록시14, 로드밸런서 세 역할을 하는 프로그램이고, 이번 실습에서는 설정 파일 한 벌이 요청의 길을 정해요.

배포할 때와 요청이 올 때는 서로 다른 시간이에요

CI/CD와 이어서 보면, 일이 일어나는 시점이 두 층으로 나뉘어요.

시점일어나는 일
배포할 때 (코드를 push할 때마다 한 번)CI/CD가 테스트와 빌드를 거쳐 새 버전을 올리고, 요청이 가는 방향을 새 버전 쪽으로 바꿔요
요청이 올 때 (사용자가 쓰는 동안 계속)Nginx 설정이 요청을 서버로 넘겨요

배포의 마지막 단계는 새 버전을 올린 뒤, 앞으로 오는 요청을 어느 서버로 보낼지 바꾸는 일이에요. 이번 실습에서는 그 "어느 서버"가 Nginx 설정 파일의 upstream 안에 적힌 server 줄이었고, 줄을 고친 뒤 reload하는 일을 제가 직접 했어요. Cloud Run에서는 이 일을 플랫폼이 대신 해요(뒤의 「내 프로젝트에서는」 절).

설정 한 벌로 보는 요청의 길

사용자는 Nginx 주소 하나만 알고, 요청은 Nginx 설정 파일에 적힌 순서대로 길을 지나요. 아래는 실습 설정을 줄여 적은 거예요. 각 부분은 이어서 하나씩 설명해요.

개념 설명용 코드 — 설정의 구조만 보여 주려고 줄여 적은 거라 그대로 저장해서 쓰는 파일이 아니에요

listen 80                          ← 80번 포트로 요청이 들어온다
location /                         ← 모든 경로 / 의 요청을
  proxy_pass http://active_app     ← active_app 이라는 이름의 목록으로 대신 넘기고
upstream active_app { ... }        ← 그 목록 안에서
  server blue:8080; server green:8080;   ← 규칙(round robin 등)으로 한 곳을 고른다
  zone active_app 64k;             ← 고르는 순서를 worker process들이 함께 센다

요청을 대신 받아 넘기는 proxy

proxy는 요청을 대신 받아 다른 곳에 넘기고, 응답도 대신 받아 돌려주는 중간 창구예요. 사용자 쪽에 서면 forward proxy(나가는 요청을 대신 보냄), 서버 쪽에 서면 리버스 프록시(들어오는 요청을 대신 받음)예요. 실습에서는 proxy_pass 줄이 리버스 프록시 동작을 지정해요. blue와 green에는 -p로 포트를 열지 않았어요. 그래서 내 컴퓨터에서 서버에 직접 들어갈 수 없고, 같은 네트워크의 Nginx만 요청을 넘길 수 있어요.

넘겨받을 서버의 목록, upstream

upstream15은 Nginx가 요청을 넘겨받을 서버들을 적어 둔 목록 블록이에요. proxy_pass http://active_app;의 active_app이 이 블록의 이름이에요. server가 한 줄이면 리버스 프록시, 여러 줄이면 로드밸런서로 동작해요. 줄이 여러 개일 때 Nginx는 요청이 올 때마다 그중 한 곳을 고르는데, 두 가지를 봐요. 하나는 줄 끝에 붙인 옵션이에요. weight는 몫이라서 weight=3인 서버는 기본값 1인 서버보다 요청을 3배 받고, backup은 예비라서 다른 서버가 모두 안 될 때만 써요. 다른 하나는 최근의 실패 기록이에요. 어떤 서버에 보낸 요청이 실패하면 Nginx는 잠시(기본 10초) 그 서버를 후보에서 빼고 다른 서버로 보내요.

옵션뜻기본값 (Nginx 문서)
weight=3다른 서버보다 3배1
backup다른 서버가 모두 빠졌을 때만 요청을 받음일반 서버
max_fails=1fail_timeout 안에 이 횟수만큼 실패하면 서버를 뺌1
fail_timeout=10s실패를 세는 기간이자 서버를 빼 두는 기간10초

목록에서 한 곳을 고르는 규칙

어느 서버로 보낼지는 정해 둔 규칙을 따라요.

규칙보내는 방식쓰는 때
round robin1번, 2번, 3번, 다시 1번처럼 순서대로서버 성능이 비슷할 때. 가장 단순해요
least connections지금 처리 중인 요청이 가장 적은 서버로요청마다 처리 시간이 크게 다를 때. LLM 응답처럼 몇 초에서 수십 초 걸릴 때예요
weight정해 둔 비율대로성능이 다른 서버를 섞을 때, 카나리 배포
IP hash같은 사용자는 늘 같은 서버로서버가 사용자 상태를 기억할 때

식당 홀로 빗대면 안내 직원이 로드밸런서이고 주방이 서버예요. round robin은 손님을 주방에 한 팀씩 차례로 보내는 것, weight는 새 주방에 세 팀을 보낼 때 옛 주방에 한 팀을 보내는 것, least connections는 지금 주문이 가장 적게 밀린 주방으로 보내는 것, IP hash는 같은 단골을 늘 같은 주방으로 보내는 것이에요.

  • hash는 입력 값을 정해진 계산식에 넣어 일정한 범위의 값으로 바꾸는 것이고, 같은 입력은 항상 같은 결과가 나와요. IP hash는 사용자의 IP를 hash한 값으로 서버를 고르므로 같은 IP는 늘 같은 서버로 가요.
  • IP hash는 서버가 사용자 상태를 기억할 때 쓰는 임시방편이에요. 상태가 서버 안에 있으면 다른 서버로 가는 순간 그 상태를 볼 수 없으니, 같은 사용자를 늘 같은 서버에 붙여 두는 거예요. 하지만 그 서버가 멈추거나 새 버전으로 바뀌면 붙어 있던 사용자들의 상태도 함께 사라지고, 한 서버에 사용자가 몰려도 다른 서버로 나눌 수 없어요. 상태를 DB에 두면(여섯 번째 절) 어느 서버로 가도 되므로 이런 장치가 필요 없어요.

고르는 순서를 함께 세는 zone

round robin이나 weight로 나누려면 Nginx가 "방금 어디로 보냈으니 다음은 어디"를 기억해야 해요. 예를 들어 blue 3 : green 1이면 숫자 0, 1, 2일 때는 blue로, 3일 때는 green으로 보내고, 다음에는 다시 0으로 돌아가요. 이 숫자가 "다음 차례" 카운터이고, 요청이 하나 지나갈 때마다 숫자를 한 칸씩 올려 가며 적는 것이 "센다"는 말의 뜻이에요. Nginx는 요청을 받는 일꾼(worker process)16을 여러 개 띄우는데(이 실습의 Nginx에는 8개가 있었어요), 일꾼들은 서로의 메모리를 볼 수 없어요. 그래서 zone이 없으면 일꾼마다 자기 공책에 카운터를 따로 적고 각자 0부터 시작하므로, 일꾼이 바뀔 때마다 "이번에도 blue 차례"라고 보고 같은 서버로 몰릴 수 있어요. zone은 이 카운터와 실패 기록을 모든 일꾼이 함께 보는 칠판(공유 메모리)에 적게 하는 설정 한 줄(zone <이름> <크기>)이에요. 참고로 일꾼이 여러 명인 이유는, 요청 하나에 일꾼 한 명이 붙어 끝날 때까지 기다리면 요청이 1만 개일 때 일꾼도 1만 명이 필요하기 때문이에요. Nginx는 일꾼 몇 명이 여러 요청을 번갈아 맡는 방식(이벤트 기반)을 써요. (이 마지막 설명은 같은 모듈을 듣는 다른 분의 보고서를 참고한 일반적인 설명이고, 제가 직접 확인한 것은 아니에요.)

이 차이를 직접 재 봤어요. blue 3 : green 1로 설정하고 요청을 하나씩 48번 보내 응답한 쪽을 순서대로 적었어요(B는 blue, G는 green, 각각 한 번씩 측정).

설정응답 순서읽는 법
zone 있음BBGBBBGBBBGBBBG…blue 3번에 green 1번씩, 처음부터 규칙대로
zone 없음BBBBBBBBBGBBBGBBBG…처음 9번이 모두 blue이고, 그 뒤에야 규칙대로

요청이 많아지면 비율은 비슷해져요(150건 측정에서 zone 있음 75% 대 25%, 없음 76% 대 24%). 차이는 요청을 몇 개 안 보냈을 때 같은 서버로만 가는 것처럼 보이는 데서 드러나요. 이 현상의 정확한 원인(일꾼마다 카운터가 따로라는 것)은 배운 설명과 이 측정의 모양이 맞아떨어진다고 본 것이고, Nginx 내부 코드로 확인한 것은 아니에요.

방향을 바꾸는 방법과 비율 정하기 — reload와 weight

방향 바꾸기: reload

upstream의 server 줄을 blue에서 green으로 고친 뒤 nginx -t로 문법을 검사하고 nginx -s reload로 적용해요. reload17는 Nginx를 다시 시작하지 않고 설정만 바꿔 끼워요.

실행: 로컬 터미널 — Nginx 컨테이너(이름 bg-nginx) 안에서 실행하는 형태예요

docker exec bg-nginx nginx -t
docker exec bg-nginx nginx -s reload
reload재시작 (docker restart blue)
대상Nginx의 설정컨테이너 전체
처리 중이던 요청이전 worker process가 마무리하고, 새 worker process가 새 설정으로 다음 요청부터 받아요제가 읽은 자료에 설명이 없어요
메모리영향 없음비워져요 (여섯 번째 절에서 약속이 사라져요)
  • 문법이 틀린 설정으로 reload하면 Nginx는 새 설정을 적용하지 않고 이전 설정으로 계속 동작해요(Nginx 공식 문서). 서비스는 끊기지 않지만, 요청은 계속 이전 설정의 서버(예: blue)로 가요. 방향을 바꿨다고 생각했는데 실제로는 바뀌지 않은 상태가 되는 거예요. 그래서 reload 전에 nginx -t로 먼저 검사해서, 이 실패를 reload 전에 바로 확인해요.
  • reload는 Cloud Run의 리비전과 달라요. reload는 Nginx가 설정을 다시 읽는 일이고, 리비전은 배포할 때마다 생기는 버전 기록이에요.
  • reload는 설정(안내판)만 바꾸고 컨테이너는 관리하지 않아요. 방향을 바꾼 직후 blue를 끄면 blue가 처리하던 요청이 끊기고 롤백할 곳도 사라지므로, blue는 한동안 켜 둬요.
  • Nginx는 설정을 읽을 때 컨테이너 이름(blue, green)을 IP 주소로 바꿔 기억해요. 컨테이너를 지웠다 다시 띄우면 IP가 바뀔 수 있어서 reload로 이름을 다시 찾게 해야 해요. 반대로 이름 자체가 사라져도 문제가 돼요. 이번 실습에서 green 컨테이너를 멈춘 채 설정을 검사하자 host not found in upstream "green:8080" 오류로 nginx -t가 실패했어요.

비율은 어떻게 정하나: weight

weight는 서버마다 보내는 요청의 몫이고, 값은 설정 파일의 숫자라서 운영자가 정해요. 기본값은 1이고, Nginx 문서에는 값이 숫자여야 한다는 것만 있고 정수 여부나 최소·최대값 같은 제한은 적혀 있지 않아요. 아래는 green이 새 버전이라고 가정했을 때 새 버전이 받는 요청의 비율이에요.

가중치 (blue : green)green이 받는 요청의미
3 : 125%배운 실습 예시 (제 실습에서 150건 중 green 25%)
9 : 110%카나리: 일부에게만 시험
99 : 11%카나리: 아주 일부

비율은 보통 어떻게 정하나? 정해진 목록은 없고 운영자가 정하지만, 정하는 기준이 있어요.

  • 기준 ① 성능이 다른 서버를 섞을 때는 성능에 비례해서 정해요.
  • 기준 ② 카나리 배포는 작게 시작해서 단계적으로 올려요. 새 버전에 1%나 10%만 먼저 보낸다고 배웠어요. 도구마다 단계 예시는 달라요. Cloud Deploy 문서의 canary 예시는 25%, 50%, 75%이고, Argo Rollouts 문서의 예시는 10%와 20%예요. 하나로 정해진 표준은 아니고, 대체로 단계마다 지표를 확인하고 잠깐 멈춘 뒤 올려요(문서의 예시일 뿐 권고가 아니에요).
  • 99 : 1의 "99"와 가용성 99%의 "99"는 겹쳐 보이지만 서로 다른 말이에요. 가용성은 1년 중 쓸 수 있었던 시간의 비율이고, weight는 요청을 나눠 보내는 몫이에요. 다만 새 버전을 1%에만 먼저 보내면 문제가 있어도 영향받는 사용자가 적으니 배포 위험을 줄여 가용성을 지키는 데 간접적으로 도움이 돼요(이 연결은 제 해석이에요).

연결 대기 시간은 짧을수록 좋은가

proxy_connect_timeout은 Nginx가 서버에 연결되기를 기다리는 시간이에요. 짧으면 고장 난 서버를 빨리 포기해서 빠르지만, 너무 짧으면 정상인데 조금 느린 서버까지 실패로 판정해요.

  • 이 값의 기본값은 60초예요. 서버가 아예 응답하지 않으면 그 60초가 지나야 실패로 보고 다른 서버로 넘기므로, 그동안 그 서버 차례의 사용자는 멈춘 화면을 봐요.
  • 1초로 줄이면 실패가 거의 없어지지만, green 차례였던 요청은 1초쯤 늦게 응답해요. 그래서 정상일 때 걸리는 시간보다는 넉넉하게, 그러나 60초보다는 훨씬 짧게 잡아요. 구체적인 숫자는 제가 읽은 자료에 없어요.

Nginx 한 대가 단일 장애점인 이유

단일 장애점의 눈으로 Nginx를 보면, 사용자는 Nginx 주소 하나만 알고 모든 요청을 그 Nginx로 보내요. 그래서 Nginx가 한 대뿐이면 Nginx가 멈출 때 뒤의 서버(blue, green)가 멀쩡해도 요청이 들어가지 못해요. Nginx 한 대가 단일 장애점이에요. 해결은 Nginx도 두 대로 두고 가상 IP 하나를 함께 쓰는 거예요. 평소에는 주 Nginx가 그 주소를 갖고 있다가, 멈추면 예비가 넘겨받아요. 사용자는 같은 주소로 접속하니 바뀐 줄 몰라요. 이것이 앞에서 본 액티브-스탠바이 이중화예요.

전환하니 대화가 사라진 이유와 해결 — 무상태

상태가 컨테이너 메모리에 있었어요

blue가 받을 때 "내일 아침 8시에 물 마시라고 알려 줘"를 보내면 약속이 만들어져요. 그다음 순서는 이래요.

  1. green으로 전환하면 약속이 보이지 않아요(blue 안에는 그대로 있어요).
  2. blue로 돌아오면 다시 보여요.
  3. docker restart blue를 하면 메모리가 비워져 약속이 진짜로 사라져요.

원인은 약속을 컨테이너의 메모리에만 두었기 때문이에요. 상태는 서버가 요청 사이에 기억해 둔 정보이고, 컨테이너의 메모리는 프로그램의 변수와 같아서 컨테이너마다 따로 있고 다시 시작하면 비워져요. 이 글에서 "서버"는 공간을 빌려주는 컴퓨터가 아니라 프로그램이 실제로 돌고 있는 것(컨테이너)이고, 기억을 오래 맡아 두는 곳은 DB예요.

  • 처음에 "방향을 바꾸면 사라진다"고 이해했던 것은 정확하지 않았어요. 정확히는 새 방향에서는 안 보일 뿐이고, 재시작하거나 새 버전으로 교체할 때 진짜로 사라져요.
  • 무상태는 서버가 대화·약속 같은 사용자 정보를 요청과 요청 사이에 자기 안(메모리)에 남겨 두지 않고 DB에 맡기는 구조예요. 그래서 어느 서버가 다음 요청을 받아도 같은 DB를 읽어 하던 일이 이어져요. 이렇게 상태를 자기 안에 두지 않는 서버가 무상태 서버예요.
  • 롤백이 약속을 복원해 주는 것은 아니에요. blue로 돌아오자 약속이 다시 보인 것도 롤백이 약속을 복원해서가 아니라, blue를 끄지 않아 blue의 메모리에 약속이 그대로 있었기 때문이에요. 롤백은 프로그램 버전을 되돌릴 뿐이라 서버 안에 사용자 정보가 없어도 돼요.
  • 식당으로 빗대면, 직원이 주문을 머릿속에만 기억하면 직원을 바꾸는 순간 주문이 사라지고, 주문을 게시판(DB)에 적어 두면 누가 바뀌어도 이어져요. "무상태여야 서버를 마음대로 늘리고, 빼고, 새 버전으로 바꿀 수 있다"가 이 뜻이에요.

DB는 하나인데 서버는 두 벌이라, 두 버전이 같은 DB를 함께 쓰게 돼요. 한쪽 버전이 테이블 구조를 바꾸면 다른 쪽이 바로 영향을 받아요.

식당으로 빗대면, 두 주방이 같은 주문 게시판을 쓰는데 새 주방이 게시판의 "메뉴" 칸 이름을 "음식"으로 바꾸면, 아직 일하고 있는 옛 주방은 주문을 읽지 못해요. 전환 중에는 두 버전이 함께 일하고, 롤백해도 DB는 이미 바뀐 상태라서 문제가 남아요. 그래서 DB를 바꿀 때는 두 서버가 같은 버전인지 확인하는 것이 아니라, 옛 버전과 새 버전이 모두 읽을 수 있는 상태로만 바꿔요. 방법은 세 번에 나누는 것이에요.

  1. 새 칸 "음식"을 추가만 해요. 옛 칸 "메뉴"는 그대로라서 옛 버전은 계속 동작해요.
  2. 두 칸을 함께 쓰는 새 버전을 배포해요. 전환도 롤백도 안전해요.
  3. 옛 버전이 모두 내려가 더 이상 롤백할 일이 없을 때 옛 칸 "메뉴"를 지워요.

칸을 먼저 늘리고(확장) 나중에 줄이는(축소) 이 순서를 확장-축소 패턴(expand and contract)이라고 해요. (일반적인 패턴 설명이고, 제가 실습에서 확인한 것은 아니에요.)

이번 모듈의 Supabase 실습에서는 익명 로그인과 RLS18, 두 종류의 키가 나와요. Supabase 익명 로그인은 가입 없이도 사용자마다 고유한 ID를 만들어 주는 기능이에요. 이 ID를 기준으로 RLS를 걸어 두면 각 사용자는 자기 행만 읽고 쓸 수 있어요. 그래서 브라우저에는 publishable key를 둬요. 이 키로는 RLS가 허용한 범위만 할 수 있어서 화면에 노출돼도 피해가 제한돼요. 반면 secret key는 RLS를 건너뛰어 모든 사용자의 데이터를 읽고 쓸 수 있으므로, 브라우저에는 절대 두지 않고 서버에서만 써요. (배운 설명을 풀어 쓴 것이고, Supabase 문서로 다시 확인하지는 않았어요.)

지금까지의 조각을 한 장에 모으면 — 네 조각은 맡은 일이 달라요

무중단 배포는 네 조각으로 이뤄요. 네 조각은 같은 급의 조건 네 개가 아니라 서로 맡은 일이 달라요. 첫 절의 두 조건으로 나누면, "요청이 끊기지 않음"은 이중화(서버를 여러 벌 둠)와 블루그린(새 쪽을 준비해 두고 방향만 바꿈)이 이루고, Nginx는 그 방향을 실제로 바꾸는 장치예요. "하던 일이 이어짐"은 무상태가 이뤄요. 서비스가 돌고 있는 동안에는 네 조각이 모두 동시에 갖춰져 있고, 배포하는 순간에만 방향 바꾸기가 한 번 일어나요.

배포 파이프라인의 마지막 칸

제 deploy.yml은 main에 push하면 위에서 아래로 자동 실행되는 다섯 칸이고, 마지막 칸 「Cloud Run 배포」 안에서 이전 버전이 새 버전으로 교체돼요. 이번 글은 이 교체가 사용자에게 안 끊기게 하는 원리예요.

  • 이번 실습은 Dockerfile로 이미지를 만들 수 있는 상태에서 시작하고, Google Cloud 없이 내 컴퓨터의 Docker로만 해요. GitHub Actions도 Cloud Run도 실습에는 나오지 않아요.

Cloud Run이 대신 해 주던 일

  • 문서에 따르면 Cloud Run은 컨테이너를 실행하는 완전 관리형 플랫폼이고, 서비스는 안정적인 주소 하나로 요청을 받으며 무상태 컨테이너 인스턴스를 써요. 새 리비전에 트래픽 1%만 보내 보는 점진적 롤아웃도 지원해요.

새로 알게 된 것

  • proxy는 요청을 넘기는 동작이고, upstream은 넘겨받을 서버의 목록이며, proxy_pass가 upstream의 이름으로 둘을 이어요.
  • 무료 Nginx는 수동 헬스체크라서 고장을 사용자가 먼저 겪어요. 대기 시간(기본 60초)이 길수록 그 비용이 커져요.
  • 블루그린의 롤백이 빠른 이유는 이전 버전을 끄지 않고 남겨 두기 때문이에요. 롤백은 프로그램 버전을 되돌리는 것이지 데이터를 되돌리는 것이 아니에요.
  • 멈춘 컨테이너는 Docker의 이름 찾기에서 빠져서, 그 이름을 upstream에 둔 채로는 Nginx 설정 검사가 실패해요.
  • zone은 worker process들이 "다음 차례"를 함께 세게 해서, 요청이 적을 때도 규칙대로 나뉘게 해요.
  • DB를 붙이는 순간 코드만이 아니라 테이블 구조를 바꾸는 순서까지 신경 써야 해요.

  1. 무중단 배포(zero-downtime deployment) — 새 버전으로 바꾸는 동안에도 사용자의 요청이 실패하지 않게 하는 배포 방식이에요. ↩
  2. 로드밸런서(load balancer) — 들어오는 요청을 여러 서버에 나눠 보내는 장치예요. ↩
  3. 블루그린(blue-green) 배포 — 지금 쓰는 서버 묶음과 새 묶음을 따로 준비해 두고 요청 방향을 한 번에 바꾸는 배포 방식이에요. ↩
  4. 무상태(stateless) — 서버가 사용자의 대화 같은 정보를 요청과 요청 사이에 자기 안에 남기지 않는 구조예요. ↩
  5. 헬스체크(health check) — 서버가 요청을 받을 수 있는 상태인지 확인하는 검사로, 이 글에서는 /health 주소로 물어봐요. ↩
  6. 그레이스풀 셧다운(graceful shutdown) — 끄라는 신호를 받은 서버가 새 요청은 받지 않고 하던 요청만 마친 뒤 종료하는 방식이에요. ↩
  7. 가용성(availability) — 1년 중 서비스를 쓸 수 있었던 시간의 비율이에요. ↩
  8. 이중화 — 하나가 고장 나도 서비스가 멈추지 않도록 같은 일을 하는 것을 하나 더 두는 일이에요. ↩
  9. 단일 장애점(SPOF) — 그것 하나만 고장 나도 서비스 전체가 멈추는 부분이에요. ↩
  10. 롤링(rolling update) — 서버를 한 대씩 돌아가며 새 버전으로 바꾸는 배포 방식이에요. ↩
  11. drain — 서버를 요청 보내는 목록에서 뺄 때 새 요청은 끊고 이미 받은 요청은 끝까지 마치게 하는 일이에요. ↩
  12. 카나리(canary) 배포 — 새 버전에 일부 요청만 먼저 보내 보고 문제가 없으면 비율을 올리는 배포 방식이에요. ↩
  13. Nginx — 웹 서버, 리버스 프록시, 로드밸런서 역할을 하는 프로그램으로, 컨테이너 하나로 띄워 쓸 수 있어요. ↩
  14. 리버스 프록시(reverse proxy) — 서버 앞에서 들어오는 요청을 대신 받아 서버에 넘기고 응답도 대신 돌려주는 중간 창구예요. ↩
  15. upstream — Nginx가 요청을 넘겨받을 서버들을 적어 둔 설정 블록이에요. ↩
  16. worker process — Nginx 안에서 요청을 실제로 받아 처리하는 일꾼 프로세스로, 서로 메모리를 나눠 쓰지 않아요. ↩
  17. reload — Nginx를 다시 시작하지 않고 설정 파일만 다시 읽어 바꿔 끼우는 일이에요. ↩
  18. RLS(Row Level Security) — 표의 행마다 누가 읽고 쓸 수 있는지 정해 두는 데이터베이스 규칙이에요. ↩
