Node.js·npm 설치 확인 (2)

2026. 7. 13.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

← 이전 편 Claude Code 개발 환경 세팅 (1)

1편에서 Node.js·npm·uv·Git·터미널이 왜 필요한지는 이해했는데, 다시 생각해보니 이상한 점이 있었어요. 저는 그 도구들이 실제로 제 컴퓨터에 어떻게 들어왔는지 하나도 몰라요. Claude Code한테 "이거 설치해줘"라고 말만 했을 뿐이니까요. 수업 자료에 이 부분에 대한 추가 설명이 마침 나와 있었는데, AI가 만들어준 결과를 그냥 받아쓰기만 하는 것보다는 그 원리를 이해하는 게 더 중요하다는 생각이 들어서, 두 가지를 조금 더 짚어보고 싶었어요. 첫째, AI에게 맡겼을 때 뒤에서 정확히 무슨 일이 일어나는지. 둘째, 손으로 직접 설치했다면 어떤 과정을 거쳤을지.

Node.js와 npm은 대체 "언제" 실행되는 거야?

1편에서 저는 Node.js를 "화구", npm을 "재료 창고"라고 비유했어요. 그런데 비유만으로는 부족했어요. 구체적으로 어느 순간에 이것들이 실제로 켜지는지가 궁금했거든요. 그래서 "Next.js로 랜딩페이지 하나 만들어줘"라고 AI에게 부탁했을 때, 뒤에서 실제로 무슨 일이 일어나는지 순서대로 뽑아봤어요. (Next.js는 Node.js 위에서 돌아가는, 웹사이트를 만들 때 쓰는 유명한 도구 묶음이에요. 랜딩페이지는 광고나 링크를 누른 사람이 "착지"하는 소개용 한 장짜리 페이지를 말하고요. 둘 다 지금 당장 외울 필요는 없고, 그냥 "제법 규모 있는 웹 프로젝트 하나"라고 읽으셔도 돼요.)

  1. 제가 요청: "Next.js로 랜딩페이지 하나 만들어줘"
  2. npm이 처음 등장: AI가 npx create-next-app을 실행해요. npx는 "창고에서 도구를 잠깐 빌려와 한 번 쓰고 돌려주는" 명령이에요. 이때 npm 창고에서 Next.js 뼈대 도구를 꺼내와서, package.json 같은 실제 파일들을 만들어줘요. package.json은 이 프로젝트의 재료 주문서예요 — 어떤 코드 조각이 몇 번 버전으로 필요한지가 적혀 있어요.
  3. npm이 두 번째로 등장: npm install을 실행해요. 방금 만들어진 그 주문서를 npm이 읽고, 적힌 재료를 전부 인터넷에서 다운로드해서 node_modules라는 폴더에 채워 넣어요. 이 폴더가 이 프로젝트 전용 재료 창고인 셈이에요.
  4. 여기서 Node.js가 처음으로 실제 가동돼요: npm run dev를 실행하면, 이 순간 Node.js가 진짜로 웹서버를 켜요. 웹서버는 "이 주소의 페이지 주세요"라는 요청을 받아서 페이지를 만들어 돌려주는 프로그램이에요. 이건 한 번 실행하고 끝나는 게 아니라, localhost:3000이라는 주소에서 계속 켜진 채로 대기하고 있어요. (localhost는 "다른 어디도 아닌 지금 이 컴퓨터"를 가리키는 주소예요. 그러니까 아직 인터넷에 공개된 게 아니라, 제 컴퓨터 안에서만 열리는 페이지예요.)
  5. 제가 브라우저로 그 주소에 접속하면, 그 순간 Node.js가 제 요청을 실시간으로 처리해서 실제 페이지를 화면에 응답해줘요.

이제 확실히 답할 수 있어요. npm은 "재료를 준비하는 그 잠깐의 순간"에만 실행돼요 — 프로젝트를 처음 만들 때, 그리고 재료를 설치할 때요. Node.js는 그 이후로 "계속 켜져서 실제로 일하는 엔진"이에요 — 개발 서버가 켜져 있는 동안 내내, 누가 접속할 때마다 그 자리에서 응답을 만들어내요. 제 블로그가 지금까지 이 과정이 한 번도 없었던 이유는, 이미 완성된 HTML을 그냥 보여주기만 하는 정적 사이트라서 이 다섯 단계 자체가 필요 없었던 거예요.

만약 손으로 직접 설치했다면 (참고)

여기까지가 첫 번째 궁금증, "AI에게 맡겼을 때 뒤에서 무슨 일이 일어나는가"였어요. 이제 두 번째 궁금증 차례예요. 그럼 제가 손으로 직접 설치했다면 어떤 과정을 거쳤을까요? 마침 수업 자료에 그 방법이 자세히 나와 있었어요. 나중에 직접 해볼 일이 생기거나, AI가 설치해둔 방식이 이상하게 느껴질 때 비교해볼 기준이 될 것 같아서 참고로 정리해둘게요.

Node.js와 npm은 "nvm"으로 관리한다

nvm(Node Version Manager)은 Node.js 자체를 하나만 딱 고정해서 설치하는 게 아니라, 여러 버전을 넣어두고 필요할 때마다 골라서 쓸 수 있게 해주는 관리자예요. 왜 이렇게 복잡하게 하냐면, 프로젝트마다 필요한 Node.js 버전이 다를 수 있어서예요 — 한 프로젝트의 Node.js가 다른 프로젝트를 덮어쓰면 안 되니까요.

더 실용적인 이유도 있어요. Node.js를 시스템 깊은 곳에 직접 설치하면, npm으로 뭔가를 전역 설치(npm install -g — 특정 프로젝트 안이 아니라 컴퓨터 어디서나 쓸 수 있게 까는 것)할 때 "이 폴더에 쓸 권한이 없다"는 EACCES 에러가 나서 관리자 권한을 따로 붙여야 하는 경우가 많다고 해요. 시스템 폴더는 아무나 못 건드리게 잠겨 있으니까요. nvm은 잠긴 시스템 폴더가 아니라 제 계정 폴더 안에서 관리되기 때문에, 이 권한 문제를 대부분 피할 수 있어요.

Windows에서 주의할 점: 윈도우용 nvm(nvm-windows)은 이름만 같을 뿐, 원래 맥·리눅스용 nvm과는 완전히 다른 별도의 프로그램이라고 해요. 그래서 인터넷에서 본 nvm 명령어가 윈도우에서 그대로 안 통하는 경우가 있어요. 대표적으로 윈도우용에는 --lts라는 줄임 옵션이 없어서, 버전 번호를 직접 찾아 적어줘야 해요. (LTS는 Long Term Support의 줄임말로, "오래 관리해주기로 약속된 안정 버전"이라는 뜻이에요. 특별한 이유가 없으면 이걸 쓰는 게 안전해요.)

uv, Git, Claude Code

  • uv: 공식 설치 문서의 명령어로 깔아요. (윈도우는 공식 문서의 PowerShell 명령을 그대로 씁니다.)
  • Git: Git 공식 다운로드 페이지에서 운영체제에 맞는 걸 받아요.
  • Claude Code: 공식 문서 기준으로, 윈도우 PowerShell에서는 irm https://claude.ai/install.ps1 | iex를 써요. Node.js 22 이상이 있다면 npm install -g @anthropic-ai/claude-code로도 설치할 수 있어요 (제가 실제로 이 방법으로 설치했었어요). (참고로 macOS/Linux, 그리고 윈도우 안에서 리눅스를 돌리는 WSL 환경에서는 curl -fsSL https://claude.ai/install.sh | bash를 써요.)

한 가지 헷갈릴 수 있는 부분: Claude Code는 파이썬 패키지가 아니라서 uv tool install로 설치하지 않아요. uv는 파이썬 프로젝트·도구 전용이고, Claude Code는 npm(자바스크립트 창고) 쪽에 있는 도구예요 — 1편에서 정리했던 "창고마다 취급 언어가 다르다"는 얘기가 여기서도 그대로 적용돼요.

공식 문서를 기준으로 삼는 이유도 짚어두고 싶어요. 버전은 계속 바뀌기 때문에, 지금 이 글에 적힌 명령어도 나중에는 최신이 아닐 수 있어요. 설치 명령을 복사하기 전에, 그 링크가 진짜 공식 문서인지, 버전 태그가 최신인지 한 번 확인하는 습관이 필요해요.

curl -fsSL 주소 | bash, 이 줄은 대체 뭘 하는 걸까

위에서 잠깐 본 curl -fsSL https://claude.ai/install.sh | bash 같은 줄은 macOS·Linux·WSL 세계에서 아주 흔한 설치 방법이에요. 한 조각씩 풀어보면 이래요. curl은 "URL(인터넷 주소)에서 자료를 가져오는" 프로그램이에요. 브라우저 주소창에 링크를 치면 화면에 페이지가 뜨는 것처럼, curl은 그 자리를 화면 없이 터미널에서 대신해줘요. -fsSL은 옵션 네 개를 붙여 쓴 거예요 — 실패하면 조용히 끝내고(f), 진행률 표시줄 없이 조용히 받고(s), 그래도 에러는 보여주고(S), 링크가 다른 주소로 넘어가면 따라가라(L)는 뜻이에요. 마지막의 | bash가 핵심이에요. |(파이프)는 "왼쪽 결과를 오른쪽 프로그램에 그대로 넘겨라"는 뜻이라, curl이 인터넷에서 받아온 설치 스크립트 글자를 화면에 보여주는 대신 곧바로 bash(셸)에 넘겨서 받자마자 바로 실행시켜요. 파일로 저장하고 열어보는 단계를 건너뛰는 거예요.

편리한 만큼 조심할 점도 있어요. 파일로 먼저 받아서 내용을 확인하는 절차 없이 곧바로 실행하는 방식이라, 내가 신뢰하는 출처(공식 문서에 적힌 진짜 주소)에서만 이 방식을 써야 해요. 링크 하나로 남이 보낸 걸 그대로 실행하는 셈이라, 출처가 불분명한 curl 설치 명령을 보면 먼저 그 스크립트 내용을 열어 읽어보는 게 안전해요.

WSL이 뭐길래 윈도우에서 리눅스 명령을 쓰나

WSL(Windows Subsystem for Linux)은 윈도우 컴퓨터 안에 리눅스라는 다른 운영체제를 통째로 따로 설치하지 않고도, 그 리눅스 환경을 윈도우 안에서 그대로 돌려주는 마이크로소프트의 공식 기능이에요. 많은 개발 도구(특히 오늘 본 curl ... | bash 계열 설치법)가 macOS·Linux를 기준으로 먼저 나오고 윈도우 지원은 나중에 따라오는 경우가 많은데, WSL을 켜두면 윈도우에서도 그 macOS·Linux용 명령어를 그대로 쓸 수 있어요. 컴퓨터를 재부팅해서 다른 운영체제로 넘어가는 게 아니라, 윈도우를 켠 채로 리눅스 터미널 창 하나를 더 여는 것에 가까워요.

윈도우의 창고, winget과 choco

1편에서 npm은 자바스크립트용, uv는 파이썬용 재료 창고라고 했는데, 이건 특정 프로그래밍 언어의 코드 조각을 받는 창고였어요. winget과 choco(Chocolatey)는 그보다 한 단계 위, 윈도우 운영체제 자체에 프로그램을 설치하는 창고예요. 마우스로 설치 파일을 내려받아 더블클릭하는 대신, 터미널에 winget install 한 줄로 프로그램을 설치·업데이트·삭제할 수 있어요. winget은 마이크로소프트가 윈도우에 기본으로 넣어둔 창고이고, choco는 그보다 먼저 나온 커뮤니티 주도 창고예요. 두 창고에 똑같은 프로그램이 다 있는 경우도 많고, 한쪽에만 있는 경우도 있어서, 실무에서는 둘 다 알아두고 상황에 맞게 골라 써요. 예를 들어 Git이나 Node.js도 이 창고들로 명령 한 줄에 설치할 수 있는데, 오늘 이 글에서는 각 공식 사이트에서 직접 받는 방법을 썼어요.

"설치했다"는 말, 그대로 믿어도 될까 — 그리고 오류를 AI에게 설명하는 법

AI에게 맡기든 손으로 직접 깔든, 두 경우 모두 마지막에 똑같이 해야 하는 일이 하나 남아요. "설치됐습니다"라는 말을 그대로 믿지 않고, 터미널에서 직접 버전을 물어보는 것이에요. AI가 "설치 완료"라고 답했다고 해서 정말 됐다는 보장은 없거든요. Windows라면 PowerShell을 새로 하나 열고 아래를 한 줄씩 쳐봐요.

pwd
node --version
npm --version
uv --version
git --version
claude --version

숫자가 나오면 설치된 거예요. 반대로 PowerShell에서 'node' 용어가 cmdlet, 함수, 스크립트 파일 또는 실행할 수 있는 프로그램 이름으로 인식되지 않습니다라는 긴 빨간 글씨가 뜨면, 아직 안 된 거예요. (맥·리눅스 터미널에서는 같은 상황에 command not found라고 짧게 나와요. 같은 뜻이에요.) 저는 오늘 이 확인 과정에서 계속 걸렸어요 — 분명히 설치했는데 새 터미널에서는 안 잡히는 일이 반복됐거든요(그 이야기는 1편에 자세히 적어뒀어요).

그런데 헤매고 나서 보니, 그 실패 화면 자체가 오늘의 진짜 학습 자료였어요. 제가 AI에게 "안 돼요"라고만 말했을 때는 AI도 저처럼 감으로 짚을 수밖에 없었어요. 그런데 "node --version을 쳤더니 이런 빨간 글씨가 나왔다"고 화면 그대로 붙여넣으니, 원인 후보가 단번에 좁혀졌어요. 그러니까 오류 화면은 치워야 할 실패가 아니라, AI에게 건네줄 단서였던 거예요. 그렇다면 그 단서를 어떤 모양으로 건네야 가장 잘 통할까요?

그 단서는 이런 틀에 맞춰서 AI에게 건네는 게 좋아요. 핵심은 환경, 실행한 명령, 실제 출력을 분리해서 주는 거예요.

나는 Windows 환경에서 웹 개발 작업대를 설정하고 있어.
터미널에서 아래 명령을 실행했어.

명령: node --version
출력: [여기에 실제 오류 메시지 붙여넣기]

내 목표는 Node.js와 npm 버전을 확인하는 거야.
원인을 추정하지 말고, 내가 먼저 확인할 순서 3가지만 알려줘.

이 요청문이 "오류가 났어요"보다 나은 이유를 한 줄로 정리하면: AI가 추측할 부분을 최대한 없애줘서, 바로 다음 행동으로 넘어갈 수 있게 해주기 때문이에요. "안 돼요"는 AI도 저처럼 감으로 짚어야 하지만, 환경·명령·출력을 정확히 주면 AI가 그 자리에서 원인 후보를 좁힐 수 있어요. 오늘 저와 AI가 PATH 문제를 결국 찾아낸 것도, 매번 실제 에러 메시지와 명령어를 그대로 붙여넣었기 때문이었어요.

오늘 최종으로 확인한 것들

  • pwd → 정상, 현재 위치 확인됨
  • node --version → v24.18.0
  • npm --version → 11.16.0
  • uv --version → 0.11.28
  • git --version → 2.55.0
  • claude --version → 2.1.207

이 숫자들이 바로 나오기까지 새 창을 여러 번 열고 닫고, 재시작하고, 원인을 찾아 헤맨 하루였어요. 그래도 결국 여섯 개 다 숫자가 나오는 걸 눈으로 확인했다는 게, 오늘 제일 뿌듯한 부분이에요. 처음 시작할 때는 "설치해줘"라는 말 한마디로 끝날 줄 알았는데, 막상 겪어보니 그 한마디 뒤에 npm이 두 번 실행되는 순서가 있었고, nvm이 권한 문제를 피하려고 계정 폴더 안에서 조용히 버전을 관리해주고 있었고, 오류가 났을 땐 화면 그대로 붙여넣는 게 감으로 짚는 것보다 훨씬 빨랐다는 사실까지 하나씩 딸려 나왔어요. 다음에 새 도구를 또 설치할 일이 생기면, 이번처럼 버전 확인 명령부터 먼저 쳐볼 것 같아요.
