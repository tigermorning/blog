1편에서 "나누면 좋아진다"는 기대와 "비용만 는다"는 회의를 봤고, 그 판정은 남의 발표가 아니라 직접 실행한 기록으로만 할 수 있다고 했어요. 이번 편이 그 실행이에요. 같은 고장 난 장치를 세 개의 작업대로 옮겨 가며 고치되, 다음 행동을 정하는 주체만 바꿔요. 문제, 모델, 저장소 준비 방식, 채점 방식은 세 실행에 똑같이 둬요.

이번 편에는 파이썬 코드가 세 덩어리 나와요. 파이썬을 모르셔도 괜찮아요. 코드는 "쓰는" 게 아니라 "읽고 넘어가는" 그림이고, 각 덩어리 아래에 한 줄씩 한국어로 풀어 둘게요. 그래도 낯설면 파이썬 코드 눈으로 읽기를 먼저 보고 오면 전부 풀려요. 변수·함수·async·딕셔너리 같은 말이 거기 있어요.

세 실행의 차이 — 다음 행동을 누가 정하는가

자동화·워크플로·에이전트, 뭐가 다를까에서 셋을 가르는 기준이 딱 하나, "다음에 뭘 할지 누가 정하느냐"라고 했었죠. 이번 실험은 바로 그 기준으로 세 실행을 만들어요.

실행다음 행동을 정하는 주체구성턴 예산
기준선 실행(A)에이전트 하나한 세션이 탐색과 수정을 모두 함최대 25턴
워크플로 실행(B)파이썬 코드읽기 전용 locator가 보고서를 쓰고, fixer가 새 세션에서 수정. 순서는 코드가 고정locator 12턴 + fixer 18턴
오케스트레이션 실행(C)리드 모델리드 세션에 locator를 서브에이전트로 등록. 부를지 말지, 어떻게 쓸지는 리드가 결정최대 40턴

여기서 턴은 모델이 한 번 생각하고 도구를 한 번 부르는 왕복 한 사이클이에요. 표의 마지막 열을 보면 세 실행의 턴 예산이 서로 달라요. 이건 나중에 숫자를 읽을 때 계속 따라다니는 단서라서 지금 미리 적어 둬요.

B와 C의 차이는 오케스트라에 빗대면 선명해요. 워크플로 실행(B)은 악보에 연주 순서가 미리 고정돼 있어서 locator 다음에 fixer가 반드시 연주해요. 오케스트레이션 실행(C)은 지휘자(리드 모델)가 연주 중 상황을 보고 다음 순서를 정해요. locator를 부를 수도, 안 부를 수도 있어요.

문제 다섯 건 — 정답 없이 테스트로만 확인한다

대상은 벤치마크 문제 다섯 건이에요. SWE-bench는 실제 오픈소스 저장소의 이슈를 에이전트에게 고치게 하고 테스트로 채점하는 벤치마크이고, Terminal-Bench는 터미널 안에서 끝내야 하는 과제 모음이에요. 원문은 GitHub 저장소 SunCreation/d035-agent-lab에 모여 있어요.

git clone https://github.com/SunCreation/d035-agent-lab.git   # 저장소를 내 컴퓨터로 통째로 복사
  • sympy-24909 — 접두사에 단위를 곱하면 결과가 1이 되어 단위가 사라져요. milli * W는 정상이라면 밀리와트가 남아야 해요.
  • sympy-24213 — 가속도에 시간을 곱한 값과 속도를 더하면 같은 차원인데도 ValueError가 나요. 차원은 길이·시간·속도처럼 물리량의 종류를 뜻해요.
  • sympy-24152 — 텐서곱(두 연산 대상을 짝지어 결합하는 연산)의 인수에 덧셈이 섞였을 때 expand(tensorproduct=True)가 두번째 인수까지 전개하지 못해요.

저장소의 tasks/ 폴더에는 문제별로 원문 이슈, 확인용 테스트 패치, 기준 커밋 정보가 들어 있어요. 정답 패치는 없어요. 무엇을 맞혔는지는 오직 테스트 실행으로만 확인해요. SymPy 세 문제는 공식 도커 평가가 아니라 경량 평가예요. 저장소를 특정 커밋(커밋은 저장소의 한 시점 스냅샷이에요)으로 고정해 받고, 에이전트가 수정한 복사본에 테스트 패치를 적용해 대상 테스트만 실행해요. 이것도 나중에 결론의 범위를 정할 때 다시 나오는 단서예요.

왜 Claude Agent SDK인가 — 조건을 고정하기 가장 쉬운 길

같은 문제를 자동으로 고치는 방법은 여럿이에요. 대화형 CLI(Claude Code, opencode)를 셸 스크립트에서 여러 번 부를 수도 있지만, 사람의 조작과 셸 환경이 끼어들어 조건을 고정하고 재현하기 어려워요. Messages API를 직접 부르면 도구 실행기·권한 승인·기록 형식을 전부 내가 만들어야 해서 실험보다 기반 공사에 시간이 가요. LangGraph 같은 범용 프레임워크는 그 프레임워크의 문법을 익혀야 하고, 정작 오늘 비교하려는 "다음 행동의 결정 주체"가 프레임워크 안에 가려져요.

그래서 이 실험은 Claude Agent SDK(claude-agent-sdk, SDK는 어떤 서비스를 코드에서 부를 수 있게 묶어 둔 개발용 도구 모음이에요)로 실행해요. Claude Code의 도구 실행, 권한, 세션 기록, 서브에이전트 정의, 구조화 출력을 파이썬 코드에서 그대로 쓸 수 있어요. (SDK의 query()를 처음 부르는 모습은 프롬프트 세 경로 직접 실행해보기에서 봤어요.) 실험 폴더에는 전용 가상 환경(프로젝트 전용으로 파이썬과 부품을 따로 담아 두는 작은 방, 폴더 이름이 .venv)을 만들어요. 시스템 파이썬에 바로 설치하면 프로젝트끼리 부품이 섞이고, 최근 리눅스에서는 전역 설치 자체가 막히기도 하거든요.

기준선 실행(A) — 한 에이전트가 끝까지

실험 스크립트 arms.py의 핵심은 query()를 한 번 부르는 도우미 함수예요. 턴을 다 써서 SDK가 오류를 던져도, 실험에서는 그게 "턴 소진"이라는 관측 결과일 뿐이라 예외로 죽지 않고 남은 상태를 그대로 채점해요.

async def _run_once(prompt, options):
    """(마지막 ResultMessage, 오류문) 반환."""
    last = None
    try:
        async for m in query(prompt=prompt, options=options):
            t = getattr(m, "subtype", None) or type(m).__name__
            if t == "result" or type(m).__name__ == "ResultMessage":
                last = m
    except Exception as e:
        return last, f"{type(e).__name__}: {str(e)[:200]}"
    return last, None

if arm == "A":
    msg, err = await asyncio.wait_for(_run_once(
        f"Fix this bug:\n\n{problem}",
        ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=25,
                           system_prompt=SYS_A,
                           permission_mode="bypassPermissions")), 1500)
    if err:
        extra["error"] = err

읽는 법이에요. 위 절반의 _run_once는 "AI에게 한 번 물어보고, 돌아온 메시지 중 마지막 결과만 챙기되, 중간에 오류가 나도 죽지 말고 오류 문장을 같이 돌려줘라"는 함수예요(한 줄씩 풀어 읽은 표는 파이썬 코드 눈으로 읽기 10번에 있어요). 아래 절반이 이번 실행의 본체고요.

워크플로 실행(B) — 코드가 순서를 고정한다

건물 보수 현장을 떠올려 보세요. 구조조사팀이 먼저 균열을 살펴 보고서를 넘기고, 시공팀은 그 보고서를 바탕으로 보수해요. B는 이 순서와 인계 내용을 현장이 아니라 파이썬 코드가 미리 고정하는 구성이에요. locator는 읽기와 검색만 하고 파일 경로·함수 이름·진단을 구조화된 보고로 남겨요. 그 보고를 받은 fixer가 새 세션에서 수정해요.

loc, err_loc = await asyncio.wait_for(_run_once(
    f"Bug report:\n\n{problem}\n\nLocate the likely cause.",
    ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=12,
                       system_prompt=SYS_B_LOCATE,
                       permission_mode="bypassPermissions",
                       allowed_tools=["Read", "Grep", "Glob"])), 900)
if err_loc:
    extra["locator_error"] = err_loc
locate_report = (getattr(loc, "result", "") or "").strip()
extra["locate_report"] = locate_report[:2000]

msg, err = await asyncio.wait_for(_run_once(
    f"Bug report:\n\n{problem}\n\n"
    f"Locator report from a previous agent:\n{locate_report}\n\n"
    "Apply the minimal fix.",
    ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=18,
                       system_prompt=SYS_B_FIX,
                       permission_mode="bypassPermissions")), 1200)

    extra["error"] = err

읽을 지점은 하나예요. 첫 호출의 결과에서 보고서를 꺼내 변수에 담고, 두번째 호출은 그 변수의 내용을 프롬프트로 받아요. 두 세션이 같은 대화를 공유하는 게 아니라, 코드가 정한 보고서만 다음 단계로 건너가요. allowed_tools=["Read", "Grep", "Glob"]이 locator를 읽기 전용으로 묶는 부분이고요.

이 분리는 역할 이름을 늘리는 일이 아니에요. 비교 대상은 탐색 결과가 다음 단계로 전달되는지, 탐색 담당이 파일을 고치지 않는지, 수정 담당이 그 근거를 실제로 쓰는지예요. 그리고 B의 숫자는 두 호출의 기록이 합쳐진 값이에요. A의 25턴과 B의 12+18턴을 같은 예산으로 읽으면 안 돼요.

오케스트레이션 실행(C) — 리드가 부를지 정한다

C에도 같은 읽기 전용 locator가 있어요. 다른 점은 ClaudeAgentOptions의 agents={"locator": ...}로 이 locator를 리드 세션에 제공만 한다는 거예요. 리드는 부를지 말지, 받은 내용을 어떻게 쓸지를 스스로 정하고, 최종 수정도 직접 해요.

elif arm == "C":
    locator = AgentDefinition(
        description="Read-only locator: finds the likely cause of a bug "
                    "in this repo. Cannot edit files.",
        prompt=SYS_B_LOCATE,
        tools=["Read", "Grep", "Glob"],
    )
    msg, err = await asyncio.wait_for(_run_once(

        ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=40,
                           system_prompt=SYS_C,
                           permission_mode="bypassPermissions",
                           agents={"locator": locator},
                           forward_subagent_text=True)), 1500)

바이브 코딩으로 돌리기 — 요약이 아니라 명령과 파일을 받는다

대화 횟수, 걸린 시간을 찾아 정리하고, 실행한 명령과 결과 파일 경로도
보여 줘.  # 참고사항으로 위 코드 제공

인스턴스 준비와 채점까지 똑같이 만들 필요는 없어요. "한 문제를 한 에이전트가 처리하고 결과 파일을 남긴다"는 구조만 같으면 돼요. 다만 위임한 뒤에 에이전트의 요약을 결과로 받아들이지 말고, 실제로 실행된 명령과 실제로 생긴 결과 파일을 함께 확인해요. C를 돌릴 때는 "리드가 locator를 실제로 불렀는지 기록에서 확인해 알려 줘"까지 부탁에 넣어요.

# 가상 환경의 파이썬으로 arms.py 실행. 뒤의 두 단어가 "어느 실행, 어느 문제"
.venv/bin/python arms.py A sympy__sympy-24909
.venv/bin/python arms.py B sympy__sympy-24909
.venv/bin/python arms.py C sympy__sympy-24909

# 세 실행을 한 번에 (쉼표로 나열)
.venv/bin/python arms.py A,B,C

# cat = 파일 내용을 화면에 그대로 출력
cat runs/C-sympy__sympy-24909/result.json
cat runs/C-sympy__sympy-24909/changes.diff

윈도우라면 .venv/bin/python 대신 .venv\Scripts\python이에요. changes.diff의 diff는 "고치기 전과 후의 차이"를 줄 단위로 적은 파일이에요. 앞에 -가 붙은 줄은 지워진 줄, +가 붙은 줄은 새로 들어간 줄이에요.

러너는 이미 result.json이 있는 실행을 건너뛰어요. 다시 돌리기 전에 기존 결과가 있는지 확인하세요. 같은 파일을 덮어쓰고 나면 이전 기록과 무엇이 달라졌는지 비교할 길이 없어져요.
