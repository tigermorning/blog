CORS란 무엇인가 — 다른 주소끼리 대화할 때 브라우저가 하는 검문

2026. 8. 28.

※ 이 글은 모두의연구소(모두연) 학습 자료를 제 나름의 말로 다시 정리한 글이에요.

※ 순순팩토리와의 미팅에서 나온 질문에 답하려고, "화면 뒤에서 일어나는 일들" 시리즈에서 한 줄로만 스쳐 지나갔던 내용을 번외로 정리했습니다.

CORS는 다른 주소에서 온 응답을 화면 코드에 넘겨도 되는지 브라우저가 검사하는 규칙이다 — 서버가 허용 주소를 헤더에 적어 줘야 통과한다.

  • 배포 전에 열어둔 문을 다시 좁히는 점검을 할 때요.

앞선 글에서 프록시 서버를 세워 키를 숨겼어요. 그런데 브라우저 콘솔(브라우저가 오류를 보여 주는 창)에 이런 빨간 글씨가 뜬 적 있나요? Access to fetch at '...' from origin '...' has been blocked by CORS policy. CORS(코르스)는 서로 다른 주소 사이에 요청을 주고받을 때 브라우저가 지키는 검사 규칙이에요. 저는 처음엔 서버가 요청을 거부한 줄 알았어요. 그런데 사실은 브라우저가 스스로 응답을 버린 거였어요.

검문소를 통과하는 여권

여행자가 국경 검문소를 지나는 장면에 비유하면 이해하기 쉬워요. 그 나라(서버)가 "이 국적은 들여보내도 됨"이라고 미리 도장을 찍어 둬야 해요. 그래야 여행자(브라우저)가 통과할 수 있어요. 컴퓨터에서는 이 도장이 서버가 응답에 붙이는 헤더(응답 맨 위에 붙는 안내 줄)예요.

국경에서는CORS에서는
여행자브라우저
여행자의 국적지금 접속한 우리 사이트 주소(origin, 출처)
여행자가 들어가려는 나라프록시 서버가 있는 다른 주소
그 나라가 "이 국적은 들여보내도 됨"이라고 찍어 둔 도장서버가 응답에 붙이는 Access-Control-Allow-Origin 헤더
도장이 없거나 국적이 다르면 국경 스스로 여행자를 돌려보냄헤더가 없거나 우리 주소와 다르면 브라우저가 응답을 버림 — 서버는 응답을 이미 다 만들어 보냈는데도요

핵심 한 줄: 막는 쪽은 서버가 아니라 브라우저예요 — 서버는 허용 주소를 헤더로 적어 줄 뿐이에요.

실제로 겪으면 이렇게 생겼다

예를 들어 우리 게임이 https://cheesecake.pages.dev에, 프록시 서버가 https://cheesecake-proxy.onrender.com에 따로 있다고 해봐요. 서버 쪽에서 헤더를 안 챙기면 이렇게 돼요. 아래는 서버 코드 일부이고, 읽기만 해도 돼요. res.json(result) 줄이 서버가 화면에 답을 돌려주는 곳이에요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

// server.js — 허용 헤더 없음
app.post('/api/npc-line', async (req, res) => {
  // ... SAM 호출 ...
  res.json(result); // ← 이대로면 브라우저가 응답을 버림
});

헤더를 붙이면 통과해요. 아래 코드는 답을 돌려주기 전에 "이 주소에서 온 요청은 괜찮아요"라는 헤더를 한 줄 붙여요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

// server.js — 허용 헤더 추가
app.post('/api/npc-line', async (req, res) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://cheesecake.pages.dev');
  // ... SAM 호출 ...
  res.json(result);
});

Express를 쓴다면 cors 패키지(남이 만들어 둔 코드 묶음)로 더 짧게 쓸 수도 있어요. app.use(cors({ origin: 'https://cheesecake.pages.dev' })) 한 줄이면 이후 모든 응답에 자동으로 이 헤더가 붙어요.

개발할 때 편하다고 열어둔 문, 배포할 때는 잠그기

로컬(내 컴퓨터 안)에서 테스트할 때는 origin: '*'(전체 허용)로 열어두는 게 편해요. 그래서 그대로 두고 싶어져요. 하지만 이 상태로 배포하면 우리 프록시 주소만 알면 아무 사이트나 우리 API 키(서비스를 쓰는 비밀번호 같은 값)를 공짜로 빌려 쓸 수 있게 돼요. 프록시를 세운 이유가 애초에 키를 지키려는 거였어요. CORS를 전체 허용으로 두면 문 하나를 다시 열어두는 셈이에요. 배포 환경을 다룬 글에서처럼, 개발할 때 편하던 설정을 실제 서비스(production)에 그대로 들고 가면 안 돼요. 그 대표적인 예가 이거예요.

여기까지가 프론트-백엔드(화면 쪽과 서버 쪽) 연결에서 자주 걸리는 두 가지, 키 숨기기(프록시)와 검문 통과시키기(CORS)였어요. 둘 다 원래 시리즈에서 한 줄로만 스쳐 지나갔던 것들이에요. 실제로 겪어보면 이 정도 분량이 되더라고요.

이럴 때 의심하세요 — 화면과 서버를 이은 뒤 데이터가 안 올 때

AI에게 화면과 서버 연결을 맡기면 CORS는 거의 한 번은 만나요. 화면 주소와 서버 주소가 다르면 똑같이 검문을 받아요. 로컬에서도 마찬가지예요. localhost:5173과 localhost:3000처럼 포트(주소 끝에 붙는 번호)만 달라도 검문을 받아요. 배포 뒤에도 같아요. 증상은 보통 "서버는 멀쩡한데 화면만 비어 있다"로 나타나요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
화면에 데이터가 안 나오고 콘솔에 ... has been blocked by CORS policy가 떠요. 그런데 서버 로그(서버가 남긴 기록)에는 에러가 없어요. 요청이 처리됐다고 찍혀 있거나, 보낸 적 없는 OPTIONS 요청만 한 줄 와 있어요. 이건 브라우저가 본 요청 전에 보내는 사전 확인이에요. 여기서 막히면 본 요청은 아예 안 가요 서버 코드가 아니라 서버가 돌려준 응답의 헤더예요. 브라우저 개발자 도구의 네트워크(Network) 탭에서 그 요청을 눌러 봐요 응답 헤더에 Access-Control-Allow-Origin이 있는지 봐요. 없으면 헤더를 안 붙인 거고, 있다면 에러 문장의 from origin '...' 주소와 한 글자씩 맞춰 봐요. http와 https, 포트 번호, 끝의 / 하나만 달라도 통과 못 해요
로컬에서는 되던 호출이 배포한 사이트에서만 CORS 에러로 막혀요 서버의 허용 주소 설정이에요. cors({ origin: ... })나 setHeader('Access-Control-Allow-Origin', ...) 줄이요 허용 주소가 http://localhost:...로 남아 있는지 봐요. 개발할 때 쓰던 주소 그대로라면, 배포한 사이트 주소(예: https://cheesecake.pages.dev)로 바꿔야 해요
에러는 하나도 없어요. 대신 내 사이트 방문자에 비해 API 사용량이나 요금이 이상하게 많아요 같은 허용 주소 설정이에요. 특히 origin: '*'이거나, 괄호 안이 빈 app.use(cors())인지 봐요 — 괄호가 비어 있으면 전체 허용이에요 전체 허용이면 우리 사이트 주소 하나로 좁혀요. 다만 CORS는 브라우저만 검문해서, 누군가 브라우저 밖의 스크립트로 프록시를 직접 부르는 건 못 막아요. 좁혔는데도 사용량이 계속 튀면 원인이 CORS가 아닌 거예요

세 번째 줄이 제일 놓치기 쉬워요. 앞의 둘은 화면이 깨져서 알게 돼요. 전체 허용은 모든 게 잘 돌아가서 아무도 안 열어 보거든요. 그래서 증상을 기다리지 말고 배포하기 직전에 한 번 확인해요.

아래 글은 코드가 아니라 코딩 에이전트에게 보내는 부탁이에요. 그대로 붙여넣으면 CORS 설정이 어디 있는지 표로 정리해 줘요. 직접 해 보는 거예요.

이 프로젝트의 서버 코드에서 CORS 설정을 전부 찾아 줘. cors( 호출과 Access-Control-Allow-Origin 헤더를 붙이는 줄이 대상이야.
한 곳마다 파일 이름, 줄 번호, 허용 주소(* / localhost / 실제 사이트 주소 중 무엇인지)를 표로 보여 주고,
개발할 때와 배포할 때 허용 주소가 달라지게 되어 있는지도 알려 줘. 아직 코드는 고치지 마.
