지난 편에서 호스트·클라이언트·서버라는 세 역할을 나눠 봤어요. 그때 "서버는 제 노트북에서 도는 작은 파이썬 프로그램 하나"라고만 말하고 넘어갔는데, 이번 편이 바로 그 파일을 여는 편이에요. 파일 이름은 weekly_records_server.py고요.

먼저 걱정 하나를 덜고 시작할게요. JSON-RPC 메시지를 직접 조립하거나, 표준 입력으로 들어온 글자를 한 줄씩 읽어 해석하는 코드는 제가 쓰지 않아요. 그건 공식 MCP Python SDK1가 맡아요. 제가 쓰는 건 딱 하나, "주 이름을 받아 그 주의 기록 파일을 읽어 돌려주는 함수"예요. 지난 편에서 봤던 get_weekly_records가 그거죠.

그래서 이번 편의 코드에서 볼 곳은 세 군데예요. ① 자료가 어디 있는지 정하는 곳, ② 입력을 검사하고 파일을 읽는 곳, ③ 그 함수를 도구로 공개한다고 표시하는 곳. 지난 편 마지막에 "다음 편 코드에서 이 세 곳을 찾아보라"고 했던 게 이거예요.

비유 — 자료실 신입 직원의 첫 근무

지난 편에서 회사 대표번호에 전화를 걸어 자료실로 내선이 이어지는 장면을 봤어요. 이번엔 그 자료실 안쪽으로 들어가 볼게요.

자료실에 새 직원이 들어왔어요. 이 직원의 책상 바로 옆에는 전용 캐비닛이 붙어 있어요. 책상을 어디로 옮기든 캐비닛도 같이 따라오게 붙여 뒀죠. 직원이 하는 일은 아주 단순해요. 창구에서 요청서가 넘어오면 손글씨를 다듬어 읽고(WEEK-ONE 처럼 대문자로 크게 쓰거나 뒤에 빈칸을 남겨도 알아봅니다), 벽에 붙은 취급 대장에서 그 주차가 있는지 확인하고, 있으면 해당 서랍의 서류철을 꺼내 고치지 않고 그대로 복사해 창구로 넘겨요. 대장에 없는 주차면 "그 주는 취급하지 않습니다"라고 반려하고요.

그리고 자료실 문 밖에는 안내판이 있어요. 이 직원이 맡는 일 중에서 안내판에 이름이 올라간 것만 바깥 사람이 요청할 수 있어요. 안내판에 안 올린 일은 자료실 안에서만 도는 내부 작업이고요.

핵심 한 줄: 제가 만드는 건 "요청서를 다듬어 읽고 옆 캐비닛에서 서류를 꺼내 그대로 복사해 주는 직원"이고, 통화 예절과 창구 운영은 이미 SDK가 하고 있어요.

다만 여기서 비유가 끊기는 점이 하나 있어요. 사람 직원이라면 "week-three요"라는 요청에 "아, 첫째 주 말씀이시죠?"라고 알아서 고쳐 주기도 하죠. 그런데 이 함수는 절대 그러지 않아요. 공백을 지우고 대소문자를 맞추는 것까지는 하지만, 내용을 추측해서 다른 값으로 바꾸는 일은 하지 않아요. 여기가 "다듬기"와 "추측"을 가르는 선이에요.

전체 흐름 그림 — 요청 하나가 파일까지 갔다 오는 길

읽는 법: 가운데 큰 상자가 파일 하나예요. 그 안에 함수가 둘 들어 있는데, 굵은 테두리로 그린 위쪽만 바깥에 공개돼요. 공개 여부를 가르는 건 함수 위에 붙은 @mcp.tool() 한 줄이에요. 아래쪽 상자의 ①~⑤가 실제로 일이 일어나는 순서고, ②와 ④에서 조건이 어긋나면 ⑤까지 못 가고 중간에 멈춰요. 오른쪽 자료 상자로 가는 화살표가 파일을 실제로 읽는 유일한 지점이고요. 왼쪽 클라이언트와 서버 사이를 오가는 화살표는 지난 편에서 본 tools/call과 그 응답인데, 그 통신은 제가 짜는 코드가 아니라 SDK가 처리해요.

먼저 원자료부터 — 무엇을 읽어 올 건가

코드보다 자료를 먼저 보는 게 순서예요. 실습 자료 묶음을 내려받아 압축을 풀면 폴더가 이렇게 생겼어요.

개념 설명용 코드 — 실습 폴더의 구조를 보여주는 그림이에요

mcp-skill-practice/
  pyproject.toml
  uv.lock
  .python-version
  requirements.txt        (예전 설치 방식과의 호환 참고용)
  .venv/                  (환경 준비 때 자동으로 생김)
  weekly_records_server.py
  data/
    week-one.json
    week-two.json

여기서 지금 당장 기억할 관계는 하나예요. weekly_records_server.py와 data 폴더는 같은 층에 나란히 있어요. 나중에 나올 코드가 이 관계를 그대로 전제하니, 파일을 여기저기 옮기지 않는 게 좋아요.

가상의 제품팀 첫째 주 기록 파일은 이렇게 생겼어요. 실제 파일에는 업무가 네 개인데, 지난 편에서 봤던 TASK-102 한 건만 남기고 잘라 왔어요.

개념 설명용 코드 — 실습 자료로 이미 들어 있는 파일의 내용이에요

{
  "week": "week-one",
  "team": "가상 제품팀",
  "period_start": "2026-08-31",
  "report_date": "2026-09-04",
  "records": [
    {
      "id": "TASK-102",
      "title": "로그인 안내 문구 개선",
      "owner": "지우",
      "status": "개발 완료",
      "due_date": "2026-09-07",
      "deployed_at": null,
      "verification": "미실시",
      "blocker": null,
      "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
    }
  ]
}

이 형식이 목업 데이터와 REST API에서 처음 봤던 JSON2이에요. 중괄호 { } 안에 "week": "week-one"처럼 이름과 값이 짝지어 들어가는데, 이름 쪽을 키, 거기 붙은 내용을 값이라고 불러요. records의 값은 대괄호 [ ]로 묶인 목록이고요. 한 주에 업무가 여러 개니까, 업무 한 개씩을 객체로 만들어 목록에 담아 둔 거예요.

null은 그 자리에 값이 없다는 표현이에요. deployed_at이 null이면 배포일이 아직 안 들어 있다는 뜻이죠. 이 자료를 파이썬으로 읽으면 null은 None이 돼요 — 이름만 다르고 뜻은 같아요. (None이 낯설다면 파이썬 코드 눈으로 읽기의 값 종류 표를 한번 훑고 오세요.)

TASK-102를 다시 보면 상태는 '개발 완료'인데 배포일은 없고 확인은 '미실시'예요. 어긋나 보이죠. 도구가 할 일은 이 어긋남을 정리해 주는 게 아니라 그대로 가져오는 거예요. 도구가 알아서 "완료 한 건"으로 요약해 버리면, 나중에 우리 팀 기준으로 판정할 때 쓸 근거가 사라져요. 그 판정 이야기는 시리즈 뒤쪽의 Skill 편 몫이에요.

실습 폴더의 파이썬 환경 — uv가 대신 챙기는 것

코드를 돌리려면 파이썬과 MCP 패키지4가 필요해요. 패키지는 다른 개발자가 만들어 배포해 둔 기능 묶음이에요. 이번 실습에서는 파이썬 실행 환경과 패키지를 함께 관리해 주는 uv3를 써요. 첨부된 폴더는 이미 uv 프로젝트로 준비돼 있어서, uv init이나 uv add를 다시 칠 필요는 없어요.

파일 세 개가 각각 다른 질문에 답하고 있어요.

파일어떤 질문에 답하나손으로 고치나
pyproject.toml"우리 코드에 무엇이 필요한가" — 필요한 패키지와 파이썬 버전의 조건사람이 적는 파일
uv.lock"그 조건을 만족하는 패키지들을 어떤 버전 조합으로 깔 것인가" — 확정된 버전과 설치 정보도구가 만드는 파일 — 손대지 않음
.python-version"이 프로젝트에서 어느 파이썬을 고를 것인가" — 여기서는 3.13 계열한 줄짜리 지정 파일

pyproject.toml에서 실제로 눈여겨볼 건 몇 줄뿐이에요.

실행: pyproject.toml 파일에 적어 두는 내용 — uv가 이 파일을 읽어 환경을 준비해요

requires-python = ">=3.10"

dependencies = [
    "mcp[cli]==2.1.1",
]

[tool.uv]
package = false

한 줄씩 풀면 이래요. requires-python = ">=3.10"은 파이썬 3.10 이상이면 된다는 하한선이에요. dependencies는 이 코드가 곧바로 필요로 하는 패키지, 즉 직접 의존성5 목록이고요. mcp가 패키지 이름, 대괄호 안의 cli는 터미널에서 mcp 명령을 쓸 수 있게 해 주는 추가 기능, ==2.1.1은 버전을 딱 이걸로 고정한다는 뜻이에요. package = false는 이번 실습 코드를 설치 가능한 패키지로 빌드하지는 않겠다는 설정이고요.

여기서 숫자 두 개가 헷갈리기 쉬워요. >=3.10은 허용 범위고, .python-version의 3.13은 그 범위 안에서 이번에 실제로 고를 값이에요. uv는 조건에 맞는 파이썬을 찾아 쓰고, 컴퓨터에 없으면 알아서 내려받기도 해요.

같이 들어 있는 requirements.txt는 예전 설치 방식과의 호환을 위한 참고 자료예요. 이번 실습에서 환경 준비의 기준은 pyproject.toml과 uv.lock이에요.

가상환경 — 프로젝트마다 따로 쓰는 방

가상환경6은 프로젝트마다 설치할 패키지를 분리해 두는 공간이에요. 컴퓨터 전체의 파이썬에 이것저것 설치하면 프로젝트끼리 버전이 부딪히니까, 프로젝트 폴더 안에 작은 방을 하나 만들어 거기에만 넣는 거예요. uv는 기본 설정에서 pyproject.toml 옆에 .venv 폴더를 자동으로 만들어요. (이 개념은 파이썬 코드 눈으로 읽기의 "파일 실행과 가상 환경"에서 조금 더 풀어 뒀어요.)

환경 준비는 터미널에 명령을 치는 대신 코딩 에이전트에게 맡겨도 돼요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이 폴더를 uv로 실행할 수 있게 준비해 줘. Python과 MCP 버전도 확인해 줘.

uv 자체가 아직 없다면 "내 운영체제에 uv를 설치하고 실습 환경을 준비해 줘"라고 부탁하면 돼요. 준비가 끝났다는 답변에서 실행된 파이썬의 위치를 꼭 한 번 보세요. macOS·리눅스에서는 .venv/bin/python, 윈도우에서는 .venv\Scripts\python.exe를 가리키고 있어야 해요.

이걸 굳이 확인하는 이유가 있어요. .venv 안에 패키지를 깔아 놓고 호스트가 컴퓨터의 다른 파이썬을 실행해 버리면, "분명히 설치했는데 mcp를 찾을 수 없다"는 오류가 나요. 다음 편에서 호스트에 서버를 등록할 때 실습 폴더를 지정하고 uv run --locked로 실행하게 만드는 것도 이 환경을 확실히 쓰게 하려는 거예요.

코드 읽기 ① — 자료가 어디 있는지 정하는 곳

이제 weekly_records_server.py를 위에서부터 뜯어볼게요. 맨 앞 여섯 줄이에요.

    "week-two": "week-two.json",
}

import는 다른 곳에 정의된 기능을 가져오는 문법이에요("남이 만들어 둔 도구 상자를 꺼내 온다"고 읽으면 돼요 — 파이썬 코드 눈으로 읽기의 6번에서 다뤘어요). json은 JSON을 파이썬 자료로 읽는 데, Path는 파일 위치를 다루는 데, Any는 잠시 뒤 나올 반환값 설명에 써요. 이 셋은 파이썬에 이미 들어 있어서 따로 설치할 필요가 없어요. 설치가 필요한 건 MCP 관련 기능뿐이에요.

WEEK_FILES는 주차 이름과 파일 이름을 짝지어 둔 딕셔너리7예요. 위에서 본 JSON 객체처럼 키로 값을 찾는 파이썬 자료 구조죠. WEEK_FILES["week-one"]을 읽으면 "week-one.json"이 나와요. 비유의 취급 대장이 바로 이거예요.

여기서 이미 하나 정해진 게 있어요. 두 주차를 대장에 적어 뒀으니 이 도구는 아무 파일 경로나 받는 조회 기능이 아니에요. week-three가 들어와도 비슷한 이름의 파일을 추측해서 열지 않고, "우리가 취급하는 주차인가"부터 검사할 수 있어요.

Path(__file__).with_name("data") — 캐비닛을 책상에 붙여 두기

줄 하나가 낯설게 생겼는데, 두 조각으로 나누면 간단해요.

  • __file__ — 지금 이 파이썬 파일 자신의 경로예요. 파이썬이 알아서 채워 주는 값이라 제가 적을 게 없어요.
  • .with_name("data") — 그 경로의 마지막 이름만 갈아 끼워요. weekly_records_server.py 자리를 data로 바꾸는 거죠.

그래서 코드가 /Users/student/mcp-skill-practice/weekly_records_server.py에 있다면 DATA_DIR은 /Users/student/mcp-skill-practice/data가 돼요. 코드 파일이 어디로 옮겨지든 캐비닛은 항상 그 옆인 셈이에요.

왜 이렇게까지 하냐면, 지난 편에서 봤듯이 호스트가 서버 프로세스를 직접 띄우기 때문이에요. 호스트가 어느 폴더에서 그 명령을 실행할지는 제가 정하지 않아요. 그런데 코드에 그냥 data/week-one.json이라고 적으면, 파이썬은 그걸 "실행 당시의 현재 폴더 기준"으로 찾아요. 현재 폴더가 다른 곳이면 파일을 못 찾죠.

나쁜 선택 vs 좋은 선택 — 자료실 직원에게 캐비닛을 알려 줄 때

나쁜 선택좋은 선택
"자료는 지금 서 있는 자리 옆 캐비닛에 있어"라고 알려 준다 = 코드에 open("data/week-one.json")이라고 적는다 → 내 터미널에서 실습 폴더에 들어가 실행할 때는 잘 되다가, 호스트가 다른 폴더에서 서버를 띄우는 순간 "그런 파일이 없다"로 실패한다. "자료는 네 책상 옆 캐비닛에 있어"라고 알려 준다 = Path(__file__).with_name("data")로 코드 파일 기준 위치를 만든다 → 호스트가 어느 폴더에서 시작하든 코드 옆의 data를 정확히 찾는다.
요청받은 주차 이름을 그대로 파일 이름에 이어 붙여 아무 파일이나 연다 → week-three든 엉뚱한 경로든 그때그때 다른 실패가 나고, 뭘 열려다 실패했는지도 알기 어렵다. WEEK_FILES라는 허용 목록을 먼저 두고, 없는 주차면 raise ValueError로 즉시 반려한다 → 실패가 한 지점에서 같은 모양으로 일어나고, 메시지에 쓸 수 있는 값까지 적어 줄 수 있다.

코드 읽기 ② — 입력을 다듬고 검사하는 곳

드디어 함수예요. 첫 세 줄만 먼저 볼게요.

개념 설명용 코드 — 함수의 앞부분만 잘라 온 발췌예요

def load_weekly_records(week: str) -> dict[str, Any]:
    selected_week = week.strip().lower()
    if selected_week not in WEEK_FILES:
        raise ValueError("week는 week-one 또는 week-two를 사용하세요.")

함수는 이름을 붙여 다시 실행할 수 있게 묶어 둔 작업 덩어리예요. def로 정의를 시작하고, 괄호 안의 week로 입력을 받아요. 함수·들여쓰기·return이 처음이라면 파이썬 코드 눈으로 읽기의 2번을 먼저 보고 오면 이 아래가 훨씬 편해요.

첫 줄에 낯선 표시가 둘 붙어 있어요. 이게 타입 힌트8예요.

표시읽는 법
week: str"들어오는 week는 문자열이다"
-> dict[str, Any]"돌려주는 건 딕셔너리인데, 키는 문자열이고 값의 종류는 여러 가지일 수 있다"

여기서 오해하기 쉬운 게 하나 있어요. 힌트를 적었다고 파이썬이 모든 호출의 자료형을 자동으로 검사해 주지는 않아요. 이름 그대로 힌트라서, 코드를 읽는 사람과 편집기·검사 도구에게 알려 주는 표시예요. 그런데 이번 서버에서는 이 힌트가 한 가지 일을 더 해요 — 잠시 뒤에 볼 텐데, MCP SDK가 이 힌트를 읽어서 지난 편의 입력 스키마를 자동으로 만들어 주거든요.

둘째 줄은 정규화9예요. strip()은 문자열 앞뒤의 빈칸을 지우고, lower()는 영문을 소문자로 바꿔요. 그래서 " WEEK-ONE "이 "week-one"이 돼요. 점(.)이 이어 붙은 건 "앞의 결과에 다음 동작을 또 적용한다"는 뜻이고요.

다시 못 박자면, 정규화는 같은 값을 다르게 적은 것을 하나로 모으는 일이지 다른 값을 비슷한 값으로 고치는 일이 아니에요. week-three는 week-one이 되지 않아요.

셋째·넷째 줄이 허용 검사예요. if selected_week not in WEEK_FILES:는 "다듬은 값이 취급 대장에 없다면"이라는 뜻이고, 그럴 때 raise ValueError(...)로 작업을 중단하면서 "값이 적절하지 않다"는 오류10를 알려요. 괄호 안의 문장이 그대로 사람에게 보이는 메시지고요. 조용히 빈 값을 돌려주지 않고 여기서 확실히 멈추는 것이 핵심이에요.

코드 읽기 ③ — 파일을 열고, 확인하고, 그대로 돌려주기

검사를 통과했으니 이제 서랍을 열 차례예요.

개념 설명용 코드 — 함수 안쪽의 두 줄만 잘라 온 발췌예요

    with (DATA_DIR / WEEK_FILES[selected_week]).open(encoding="utf-8") as file:
        data = json.load(file)

한 조각씩 풀어 볼게요.

조각무슨 일을 하나
WEEK_FILES[selected_week]대장에서 이번 주차의 파일 이름을 꺼낸다 — "week-one.json"
DATA_DIR / 파일이름여기서 /는 나눗셈이 아니라 경로 뒤에 이름을 이어 붙이는 연산이다 — .../data/week-one.json
.open(encoding="utf-8")그 파일을 연다. encoding11은 글자를 어떤 방식으로 해석할지 정하는 것으로, 한글이 깨지지 않게 UTF-8을 지정했다
with ... as file:열린 파일을 file이라는 이름으로 쓰는 범위를 만들고, 그 범위를 벗어날 때 파일을 알아서 닫는다
json.load(file)파일에 적힌 JSON 텍스트를 파이썬 자료로 바꾼다

with가 왜 있는지 한 줄 더 붙일게요. 파일은 열었으면 닫아야 하는데, 중간에 오류가 나면 닫는 줄까지 못 갈 수 있어요. with는 어떻게 끝나든 닫아 준다는 약속이에요. 서랍을 열고 자리를 뜰 때 자동으로 닫히는 장치가 달린 셈이죠.

바뀐 결과의 대응 관계는 이래요. 바깥 객체는 딕셔너리, records의 배열은 목록(리스트), null은 None이 돼요.

그리고 읽었다고 바로 돌려주지 않아요. 겉장 확인이 남았어요.

개념 설명용 코드 — 함수의 마지막 다섯 줄이에요

    if not isinstance(data, dict) or not isinstance(data.get("records"), list):
        raise ValueError("주간 데이터는 records 목록이 있는 객체여야 합니다.")
    if data.get("week") != selected_week:
        raise ValueError("요청한 주차와 데이터의 week가 다릅니다.")
    return data

isinstance(data, dict)는 "data가 딕셔너리인가"를 묻는 거예요. data.get("records")는 records에 붙은 값을 읽되, 그 키가 없으면 오류 대신 None을 돌려줘요. 그래서 파일에 records가 아예 없어도 여기서 프로그램이 죽지 않고, 다음 검사로 자연스럽게 넘어가요.

여기 숨어 있는 파이썬 규칙이 하나 더 있어요. or는 앞 조건이 참이면 뒤 조건을 아예 계산하지 않아요. 그래서 data가 딕셔너리가 아니어서 앞 조건이 참이 되면, 딕셔너리가 아닌 자료에 .get()을 부르는 일 자체가 일어나지 않아요. 순서를 이렇게 짜 둔 게 우연이 아니에요.

두 번째 검사는 파일 안의 week와 내가 요청한 주차가 같은지 봐요. 파일 이름은 첫째 주인데 안에 둘째 주 자료가 들어 있다면, 그대로 보고서에 쓰면 틀린 숫자가 나가니까요. 파일 이름을 믿지 않고 내용을 한 번 더 대조하는 거예요.

마지막 return data가 호출한 쪽에 결과를 돌려줘요. 화면에 글을 쓰는 print(data)와는 완전히 다른 일이에요. 지난 편에서 "화면에 보여 주는 것과 요청한 쪽에 돌려주는 것은 다른 일"이라고 갈라 뒀던 그 지점이 여기예요. SDK가 호스트에 전달할 수 있는 건 반환값이지 화면에 찍힌 글자가 아니에요.

코드 읽기 ④ — 함수를 도구로 공개하는 곳

지금까지 본 load_weekly_records는 그냥 평범한 파이썬 함수예요. 여기서 중요한 사실 하나. 같은 파일에 있다고 해서 모든 함수가 AI에게 공개되지는 않아요. 공개할 것을 따로 표시해 줘야 해요.

실행: weekly_records_server.py 파일로 저장 — 다음 편에서 호스트가 uv run으로 이 파일을 실행해요

from mcp.server import MCPServer

mcp = MCPServer("weekly-records")

@mcp.tool()
def get_weekly_records(week: str) -> dict[str, Any]:
    """week-one 또는 week-two의 가상 팀 업무 기록을 읽습니다.

    반환값은 주차, 팀 이름, 기간 시작일, 보고 기준일, 업무 기록 목록입니다.
    파일을 수정하지 않으며 완료·진행·위험 판정이나 보고서 작성은 하지 않습니다.
    """
    return load_weekly_records(week)

네 부분으로 나눠 볼게요.

① MCPServer("weekly-records")는 도구들을 제공할 서버 객체를 하나 만들어요. weekly-records는 서버 이름이고, 그 아래 만드는 get_weekly_records는 그 서버가 제공하는 도구 이름이에요. 이름이 두 층이라는 게 지난 편의 tools/call과 도구 이름 관계와 똑같아요.

② 함수 위에 붙은 @mcp.tool()이 데코레이터12예요. @로 시작해 함수 바로 위 줄에 붙이는 문법인데, "바로 아래 함수에 이런 성격을 더한다"는 표시예요. 여기서는 이 함수를 서버의 도구로 등록한다는 뜻이고요. load_weekly_records에는 이 표시가 없죠 — 그래서 바깥에 도구로 공개되지 않아요. 비유의 안내판이 정확히 이 한 줄이에요.

③ 함수 안 맨 위의 삼중 따옴표 문자열이 docstring13, 즉 함수 설명문이에요. 보통 파이썬에서는 사람이 읽는 주석 비슷한 역할인데, 여기서는 그게 그대로 모델이 읽는 도구 설명이 돼요. 지난 편 표에서 봤던 "보고서 작성이나 판정은 하지 않는다"는 문장이 어디서 온 건지 여기서 밝혀지는 거죠. 설명을 대충 쓰면 모델이 도구를 엉뚱한 때 부르게 되고, 명확히 쓰면 안 부를 때를 알아요.

④ 몸통은 return load_weekly_records(week) 한 줄뿐이에요. 공개용 함수는 얇게 두고, 실제 일은 아까 만든 내부 함수에 맡겨요. 이렇게 나눠 두면 조회 로직을 고칠 때 도구 정의를 건드리지 않아도 되고, 반대로 도구 설명만 다듬을 때 조회 코드를 건드리지 않아도 돼요.

한 번의 조회가 지나가는 길을 한 줄로 다시 적으면 이래요.

개념 설명용 코드 — 흐름만 화살표로 적은 것이에요

MCP에 공개된 get_weekly_records(week)
  → 내부 조회 함수 load_weekly_records(week)
  → data/week-one.json
  → 파이썬 딕셔너리
  → MCP 응답

입력 스키마는 제가 안 써요

지난 편에서 도구 정의에 들어가는 입력 스키마를 봤죠. 이번 도구의 것은 이렇게 생겼어요.

개념 설명용 코드 — SDK가 만들어 주는 규칙을 사람이 읽기 좋게 펼친 것이에요

{
  "type": "object",
  "properties": { "week": { "type": "string" } },
  "required": ["week"]
}

그런데 이 JSON을 제가 어디에도 적지 않았어요. SDK가 함수의 이름·docstring·타입 힌트를 읽어서 만들어 줘요. 아까 "타입 힌트는 파이썬이 자동 검사해 주지 않는다"고 했던 그 힌트가, 여기서는 스키마를 만드는 재료로 실제로 쓰이는 거예요. LangGraph에서 Literal 힌트 한 줄이 모델의 답을 정해 둔 값 몇 개로 묶는 것도 같은 원리예요(다섯 가지 흐름 모양의 라우팅).

그래서 입력이 잘못됐을 때 어디서 걸리는지가 두 층으로 갈려요.

보낸 입력어디서 걸리나왜
{"week": "week-one"}안 걸림 — 첫째 주 자료 반환스키마도 맞고 허용 목록에도 있음
{"week": "WEEK-ONE "}안 걸림 — 첫째 주 자료 반환공백 제거와 소문자 변환으로 다듬어짐
{"week": "week-three"}내 코드의 WEEK_FILES 검사문자열이라는 조건은 맞지만 취급하는 주차가 아님
{"week": 1}SDK의 입력 검증스키마가 요구한 문자열이 아님
{} (week 생략)SDK의 입력 검증required에 있는 항목이 빠짐

입력의 모양을 검사하는 일과, 우리 업무에서 허용하는 값인지 검사하는 일은 서로 다른 역할이에요. 앞의 것은 SDK가 스키마로, 뒤의 것은 제가 WEEK_FILES로 해요. 지난 편에서 "형식은 맞는데 의미가 틀린 호출"이라고 불렀던 게 표의 세 번째 줄이고, 그 검사를 맡는 코드가 드디어 이번 편에 나온 거예요.

실행해 봐도 아무 일이 안 일어나요

파일이 준비됐으니 한번 돌려보고 싶죠. 터미널에서 이렇게 칠 수 있어요.

실행: 로컬 터미널

uv run --locked python weekly_records_server.py

그런데 아무 일도 안 일어나요. 오류도 안 나고, 서버가 켜졌다는 표시도 없어요. 고장이 아니에요. 첨부된 완성 예제에는 서버를 직접 시작하는 코드가 없거든요. 이 명령은 함수와 서버 객체를 정의하고 파일 끝에 도달해 그냥 끝나요.

참고로 uv run은 "이 프로젝트의 환경으로 뒤의 명령을 실행하라"는 뜻이고, --locked는 "uv.lock에 확정된 버전 조합을 그대로 쓰고, 잠금 파일을 새로 갱신하지 말라"는 뜻이에요.

그럼 서버는 언제 도느냐 — 다음 편에서 호스트가 띄워요. 별도 터미널에 서버를 계속 켜 두고 거기에 접속하는 방식이 아니라, 호스트가 필요할 때 mcp run으로 이 파일의 서버 객체를 찾아 프로세스를 시작하는 방식이에요. 지난 편의 stdio 설명에서 "교환대가 자료실 직원을 옆방에 직접 앉힌다"고 했던 그 방식이죠.

그래서 하나만 미리 못 박고 갈게요. stdio 연결에서는 표준 출력이 MCP 메시지가 오가는 통로예요. 디버깅하려고 넣은 print()도 같은 통로로 나가기 때문에 통신을 깨뜨릴 수 있어요. 서버에서 진단 내용을 남길 때는 표준 오류14로 보내는 로그를 써요. 지난 편에서 print("...", file=sys.stderr)를 미리 봐 뒀던 게 이 코드 파일 얘기였어요.

직접 해보기

이번엔 종이 대신 실제 파일을 여는 연습이에요. 셋 다 5분이면 돼요.

① 캐비닛을 떼어 보기. data 폴더를 다른 곳으로 잠깐 옮기고 도구를 불러 보세요. 어떤 오류가 나는지, 그 오류 메시지에 어떤 경로가 찍히는지 보면 DATA_DIR이 실제로 무엇을 가리키고 있었는지가 눈으로 확인돼요. 확인했으면 원래 자리로 되돌리는 것도 잊지 마세요.

② 대장에 한 줄 더 적어 보기. WEEK_FILES에 "week-three": "week-three.json"을 추가하되 파일은 만들지 마세요. 그러면 week-three 요청이 이제 허용 검사는 통과하고 파일 열기에서 실패해요. 같은 요청이 다른 지점에서 걸리는 걸 보면, 검사가 왜 여러 층인지 손에 잡혀요.

③ 안내판을 떼어 보기. @mcp.tool() 한 줄을 잠깐 지웠다가 다음 편에서 호스트에 연결해 보세요. 함수는 파일에 그대로 있는데 도구 목록에서는 사라져요. "코드에 있다"와 "도구로 공개돼 있다"가 다른 상태라는 걸 이보다 빨리 체감하는 방법은 없어요.

세 실험 다 정상 동작을 확인하는 게 아니라 실패하는 모습을 보는 것이 목적이에요. 어디서 어떻게 실패하는지 미리 봐 두면, 다음 편에서 호스트 연결이 안 될 때 어디부터 볼지 알게 돼요.

  1. SDK(Software Development Kit) — 특정 기능을 개발할 때 필요한 코드와 도구를 미리 모아 둔 꾸러미로, 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
  2. JSON — 설정이나 데이터를 "이름: 값" 꼴로 중괄호 안에 적는 형식으로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  3. uv — 파이썬 실행 환경과 패키지 설치를 함께 관리해 주는 도구. ↩
  4. 패키지(package) — 다른 개발자가 만들어 배포해 둔, 가져다 쓸 수 있는 기능 묶음. ↩
  5. 의존성(dependency) — 내 코드가 돌아가려면 함께 설치돼 있어야 하는 다른 패키지. ↩
  6. 가상환경(virtual environment) — 프로젝트마다 패키지를 따로 담아 두어 버전 충돌을 막는 공간으로, 파이썬 코드 눈으로 읽기의 .venv 설명에서 처음 다뤘어요. ↩
  7. 딕셔너리(dictionary) — 중괄호 안에 "이름표: 값" 짝을 담아 이름으로 값을 찾는 파이썬 자료 구조로, 파이썬 코드 눈으로 읽기의 값 종류 표에서 처음 다뤘어요. ↩
  8. 타입 힌트(type hint) — 함수가 받는 값과 돌려주는 값의 종류를 코드에 적어 두는 표시로, 파이썬이 자동으로 검사해 주는 장치는 아니에요. ↩
  9. 정규화(normalization) — 같은 값을 다르게 적은 것들을 하나의 표준 모양으로 맞추는 처리. ↩
  10. 예외(exception) — 프로그램이 계속 진행할 수 없는 상황을 알리며 작업을 중단시키는 신호로, ValueError는 그중 "값이 적절하지 않다"는 종류예요(파이썬 코드 눈으로 읽기의 오류 잡기 참고). ↩
  11. 인코딩(encoding) — 글자를 컴퓨터가 저장하는 숫자로 바꾸는 방식이며, UTF-8은 한글을 포함한 대부분의 문자를 담을 수 있는 표준 방식이에요. ↩
  12. 데코레이터(decorator) — 함수 바로 위에 @로 붙여 그 함수에 성격이나 등록 처리를 더하는 파이썬 문법. ↩
  13. docstring — 함수 첫 줄에 삼중 따옴표로 적는 설명문으로, MCP 서버에서는 이것이 그대로 도구 설명이 돼요. ↩
  14. 표준 오류(stderr) — 프로그램이 진단·오류 문구를 내보내는, 표준 출력과는 별개인 통로로, 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
