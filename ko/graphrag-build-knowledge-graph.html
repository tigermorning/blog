비유 — 직원에게 카드를 읽혀 연결판을 만든다

20편의 연결판을 이제 실제로 만들어요. 레시피 카드가 수백 장이라 사람이 핀을 꽂을 수는 없으니, 새로 온 직원에게 맡깁니다. 직원은 카드를 한 장씩 읽고 "이 요리에 이 재료", "이 조리사가 이 요리" 같은 실을 이어요.

그냥 맡기면 세 가지 사고가 나요. "이 요리는 사장님 조카가 좋아한다" 같은, 아무도 물을 일 없는 실까지 이어요. 한 카드에 같이 적힌 두 요리를 괜히 이어 버려요. 같은 재료를 어떤 카드에선 "굴소스", 어떤 카드에선 "굴 소스"로 꽂아서 핀이 둘이 돼요.

그래서 먼저 실의 종류를 정해 주고, 끝나면 같은 재료 핀을 하나로 합치고, 냉장고 칸마다 붙어 있는 라벨("해산물 칸")처럼 이미 정리된 정보는 직원 대신 규칙으로 옮겨 적어요.

"굴소스"·"굴 소스" 핀을 하나로 합치기정규화 — 표기가 다른 같은 대상을 한 노드로

라벨을 보고 실을 기계적으로 옮겨 적기규칙 추출 — 정규식으로 분류에서 삼중항 만들기
"손님이 물을 질문 목록"에 필요한 실이 다 있나 세기기준 삼중항 커버리지

핵심 한 줄: 직원은 넓게 읽지만 가끔 틀리고, 라벨은 좁지만 틀리지 않아요. 연결판은 둘을 합쳐야 완성돼요.

전체 흐름

읽는 법: 위아래 두 길이 같은 문서에서 출발해 가운데서 만나요. 위쪽이 비용의 거의 전부를 쓰고, 아래쪽은 공짜예요. 합치는 자리에서 정규화를 딱 한 번 하는 게 중요한데, 이유는 병합 절에서 봐요.

먼저 아무 제약 없이 뽑아 본다

LangChain의 LLMGraphTransformer1는 문단을 주면 노드와 관계를 뽑아 돌려주는 도구예요. 위키백과 《기생충》 문서 앞 5,000자를 넣고 아무 조건 없이 뽑아 봤어요.

개념 설명용 코드 — 제가 2026-09-18에 gpt-4.1-mini로 뽑았을 때 나온 관계 일부예요

노드 40 · 관계 39 · 135초
관계 종류: 수상상 5 · 후보상 3 · 구성원 3 · 과외학생 2 · 배우자 2 · 관련영화 2 · 감독작품 2 …

(기생충) --[감독]--> (봉준호)
(기생충) --[초청영화제]--> (제72회 칸 영화제)
(기생충) --[비교영화]--> (가장 따뜻한 색, 블루)
(기택) --[구성원]--> (기우)
(기우) --[과외학생]--> (박 사장)
(박 사장) --[딸]--> (다혜)

한 문서에서도 관계가 수십 개 나와요. 그런데 대부분 쓸 데가 없어요. 문제가 세 가지로 보여요.

  • 물을 일 없는 관계가 들어와요. "기우가 박 사장의 과외 선생"은 이 문서 안에서만 뜻이 있고 다른 영화와 절대 이어지지 않아요.
  • 틀린 관계가 섞여요. (기생충, 비교영화, 가장 따뜻한 색, 블루)는 두 영화가 칸 황금종려상 이야기를 하는 같은 문단에 나왔다는 이유로 생겼어요. 개수로는 몇 개 안 되지만 정확히 "같은 시상식 수상작"을 물을 때 엉뚱한 후보를 내놓아요.
  • 같은 것이 흩어져요. 관계 이름부터 "수상상"·"감독작품"·"감독"처럼 제멋대로라, 문서마다 다른 이름이 생겨요.

관계 이름만 정해 주면 더 나빠질 수도 있어요

그럼 허용할 노드 종류(영화·사람·영화제·회사·장르)와 관계 이름(연출·출연·수상·제작) 넷만 정해 주면 어떨까요. 같은 5,000자로 다시 뽑았어요.

개념 설명용 코드 — 같은 날 같은 모델로, 관계 이름 넷만 허용했을 때예요

노드 39 · 관계 39 · 15초
관계 종류: 출연 21 · 연출 12 · 수상 4 · 제작 2

(기생충) --[출연]--> (2019년)
(기생충) --[출연]--> (대한민국)
(기생충) --[제작]--> (봉준호)
(기생충) --[출연]--> (제72회 칸 영화제)
(기우) --[연출]--> (민혁)
(박 사장) --[연출]--> (다혜)

개수는 거의 그대로인데 관계가 뜻을 잃었어요. 뽑고 싶은 사실은 그대로인데 허용된 이름이 넷뿐이니, 모델이 "개봉 연도"를 출연에, "과외"를 연출에 욱여넣었어요. 방향도 제각각이라 봉준호는 기생충을 연출한 게 아니라 기생충이 봉준호를 "제작"했어요.

관계를 이름이 아니라 (출발 타입, 관계, 도착 타입) 삼중항으로 주면 이 문제가 막혀요. ("Person", "ACTED_IN", "Film")이라고 주면 "출연"의 출발은 사람, 도착은 영화로 고정되니 (기생충, 출연, 2019년) 같은 조합이 들어설 자리가 없어져요.

중요꼭 기억할 것

allowed_relationships에 이름만 주면 방향도, 양쪽 끝의 타입도 정해지지 않아요. 삼중항으로 줘야 방향과 양끝 타입이 고정되고, 그래야 모델이 사실을 아무 이름에나 욱여넣지 못해요.

스키마는 질문에서 거꾸로 정한다

흔한 실수는 "일단 많이 뽑아 두자"예요. 그런데 그래프가 답할 수 있는 질문의 범위는 관계의 종류가 정해요. 노드를 아무리 늘려도 관계가 세 종류면 세 종류의 질문밖에 못 풀어요.

그래서 순서를 뒤집어요. 답하고 싶은 질문 → 필요한 관계 → 스키마. 골든셋 15문항이 요구하는 관계를 세면 이래요.

관계필요한 횟수어떤 질문에 쓰나
ACTED_IN13같은 배우의 다른 작품
DIRECTED12같은 감독의 다른 작품
WON_AWARD5같은 시상식 수상작
HAS_GENRE4비슷한 장르
SET_IN3같은 배경 (조선 등)
HAS_THEME · PRODUCED_OR_DISTRIBUTED_BY각 1같은 소재 · 배급사

이걸 바탕으로 노드 타입 일곱(Film·Person·Genre·Theme·Award·Organization·Location)과 허용 삼중항 여덟을 정했어요. 수상은 영화도 사람도 받으니 WON_AWARD만 출발 타입이 둘이에요.

개념 설명용 코드 — 스키마 정의 부분만 떼어 왔어요. 전체는 아래 직접 해 보기에 있어요

REL_TRIPLES = [
    ("Person", "DIRECTED", "Film"),       # 같은 감독의 다른 작품
    ("Person", "ACTED_IN", "Film"),       # 같은 배우의 다른 작품
    ("Film",   "HAS_GENRE", "Genre"),     # 비슷한 장르
    ("Film",   "HAS_THEME", "Theme"),     # 비슷한 소재
    ("Film",   "SET_IN", "Location"),     # 같은 배경
    ("Film",   "WON_AWARD", "Award"),     # 같은 시상식 수상작
    ("Person", "WON_AWARD", "Award"),     # 수상 경력 있는 감독·배우
    ("Film",   "PRODUCED_OR_DISTRIBUTED_BY", "Organization"),
]

여기서 정직하게 짚을 게 있어요. 평가에 쓸 골든셋을 보고 스키마를 정하면 반칙 아닌가요? 방향 자체는 반칙이 아니에요. 답할 질문에서 필요한 관계를 거꾸로 정하는 건 요구사항을 정하는 정상적인 절차예요. 문제는 같은 15문항이 설계 입력이자 성적표를 겸한다는 데 있어요. 필요하다고 이미 아는 관계를 넣어 뒀으니 뒤에 나올 커버리지 숫자는 실제보다 후하게 나와요. 실무라면 질문을 설계용과 평가용으로 나누고, 평가용에는 스키마가 못 덮는 질문을 일부러 섞어요. 15문항은 나누기엔 너무 작아서 여기서는 나누지 않았어요.

스키마로 안 전해지는 것 — 지침을 글로 적는다

스키마는 "무엇을" 뽑을지는 말해 주지만 "어떻게" 뽑을지는 못 말해요. 그래서 추출 프롬프트에 지침을 아홉 줄 붙였어요. 이런 지침은 처음부터 완벽하게 쓰는 게 아니라, 결과를 보고 틀린 것을 하나씩 막으면서 쌓여요.

개념 설명용 코드 — 지침 아홉 줄 중 사고를 가장 많이 막은 세 줄이에요

4. Award 노드는 시상식/영화제 이름만 쓴다. (대종상, 청룡영화상, 칸 영화제)
   부문 이름을 Award 노드로 만들지 마라. 부문은 category 속성에 넣는다.
   '송강호가 기생충으로 대종상 남우주연상을 받았다'
     -> 송강호 -WON_AWARD-> 대종상 { category: "남우주연상", work: "기생충" }
6. ACTED_IN 에는 character(배역 이름)를 채운다.
9. 글 맨 앞의 [문서 제목] 이 이 문서가 다루는 대상이다.
   배역 목록처럼 작품 이름이 본문에 없는 부분에서는, 그 배역들이 [문서 제목] 의 작품에 속한다.

중요꼭 기억할 것

"대종상 남우주연상"을 "대종상"과 별개 노드로 만들면, 《기생충》이 받은 상과 다른 영화가 받은 상이 서로 다른 점에 붙어요. 그러면 "《기생충》이 상을 받은 시상식에서 수상한 다른 영화" 같은 질문의 길이 끊겨요. 부문은 점이 아니라 선에 붙은 속성으로 둬야 같은 시상식 노드로 모여요.

제목을 본문 앞에 직접 써 넣는다

문서를 2,400자 청크로 자르면, 배역 목록만 있는 청크가 생겨요. 그 청크만 본 모델은 이 목록이 어느 영화 것인지 몰라서 짐작해요. 그래서 청크마다 앞에 두 줄을 붙였어요.

개념 설명용 코드 — 모델이 실제로 받는 청크 앞부분이에요

[문서 제목] 기생충 (영화)
[문서 유형] Film

(여기부터 본문 청크)

중요꼭 기억할 것

문서 제목을 Document.metadata에 넣어 두면 안심이 되지만, LLMGraphTransformer는 metadata를 프롬프트에 넣지 않아요. 모델이 봐야 하는 정보는 본문 글자로 넣어야 모델 눈에 들어가요.

돌리기 전에 비용부터 센다

문서 80건을 앞 6,000자까지만 쓰고(20편에서 본 길이 분포 때문이에요) 2,400자로 자르니 청크가 168개예요. LLM을 168번 부른다는 뜻이에요. 부르기 전에 tiktoken2으로 토큰을 세면 몇 초 만에 규모가 나와요.

개념 설명용 코드 — 제가 돌리기 전에 센 추정과, 돌린 뒤 실제로 청구된 토큰이에요

추정: 본문 167,635토큰 + 청크당 프롬프트 850토큰 × 168 = 입력 약 310,000
실제: 입력 471,883 · 출력 216,849 · 8개 동시 호출로 214초 · 실패 청크 0

추정보다 입력이 16만 토큰 많았어요. 본문 말고도 스키마·허용 삼중항 목록·지침 아홉 줄이 청크마다 통째로 다시 붙기 때문인데, 실측으로 나눠 보면 그게 청크당 약 1,800토큰이었어요. 추정에 넣은 850의 두 배예요. 이 오버헤드는 청크 수에 그대로 곱해지니, 청크를 잘게 자를수록 비싸져요.

출력도 커요. 삼중항 2,383개를 JSON으로 받으니 21만 토큰이었고, 출력 단가가 입력보다 비싸서 금액은 출력 쪽이 더 컸어요. gpt-4.1-mini 요금으로 계산하면 추출 한 번에 약 0.54달러예요.

그래서 두 가지를 지켰어요. 처음엔 문서 5건만 넣고 돌려 지침이 먹는지 확인했어요(제가 실제로 한 건 《기생충》 청크 2개로 한 번). 그리고 결과를 파일로 캐시해서, 다시 돌리면 LLM을 부르지 않게 했어요. 뒤 단계를 수십 번 고쳐 돌려도 추출비는 한 번만 나가요.

나쁜 선택좋은 선택
새 직원에게 레시피 카드 수백 장을 한꺼번에 주고 "관계를 다 이어 줘"라고 한다 → 다음 날 아침 쓸 데 없는 실이 가득한 판과 야근 수당 청구서가 같이 온다. 판을 고치려면 처음부터 다시 시켜야 한다 손님이 물을 질문 목록에서 필요한 실 여덟 종류를 먼저 정하고, 카드 두 장으로 시험해 본 뒤 전부 맡긴다. 결과는 판 사진으로 남겨 둔다 → 뒤 작업을 몇 번이고 다시 해도 카드를 다시 읽힐 필요가 없다

뽑힌 것을 눈으로 본다

관계별 개수만 보고 넘어가면 안 돼요. 《기생충》 문서에서 나온 것을 열어 보면 이래요.

개념 설명용 코드 — 실제 추출 결과 중 앞부분이에요

(봉준호) --[DIRECTED]--> (기생충)
(봉준호) --[ACTED_IN]--> (기생충)         ← 틀림
(한진원) --[ACTED_IN]--> (기생충)         ← 틀림 (공동 각본가)
(기생충) --[WON_AWARD]--> (골든 글로브상) {'category': '외국어영화상'}
(송강호) --[ACTED_IN]--> (기생충) {'character': '김기택'}
(최우식) --[ACTED_IN]--> (기생충) {'character': '김기우'}

부문이 category로, 배역이 character로 들어간 걸 보면 지침이 먹었어요. 그런데 봉준호와 공동 각본가 한진원이 출연자로도 들어갔어요. 스키마에 "각본" 관계가 없으니 가장 가까운 칸에 넣은 거예요. 이런 오류는 통계로는 안 보이고 눈으로 열어야 보여요.

관계를 이름이 아니라 삼중항으로 줬고 strict_mode=True3로 스키마 밖 결과를 버리게 했는데도 방향은 가끔 뒤집혀 들어와요. 그래서 다음 편의 조회 함수는 선의 방향을 무시하고 양쪽을 다 봐요.

중요꼭 기억할 것

그래프는 방향을 저장하지만(DiGraph), 이웃을 찾을 때는 방향을 무시해요. LLM 추출은 같은 사실을 문서마다 반대 방향으로 저장하는 일이 잦아서, 한쪽 방향만 보면 멀쩡히 있는 사실을 못 찾아요.

정규화 — 같은 대상을 한 점으로

추출이 끝났다고 그래프가 완성된 게 아니에요. 지금 상태로는 길이 자주 끊겨요. 문서 제목은 동음이의를 가르려고 "기생충 (영화)"처럼 괄호를 달지만, 본문과 LLM은 그냥 "기생충"이라고 부르거든요. 처리할 건 세 가지예요.

  • 표기 흔들림 합치기 — "베를린 국제 영화제"와 "베를린국제영화제"처럼 공백·중점만 다른 이름
  • 한정어 괄호 합치기 — "기생충 (영화)"와 "기생충"
  • 개체가 아닌 것 버리기 — "영화"·"배우" 같은 일반명사, 장소 칸에 들어온 연도

여기에 함정이 있어요. 괄호를 무조건 지우면 안 돼요. "괴물 (2006년 영화)"처럼 같은 제목의 다른 작품을 가르는 괄호도 있지만, "김윤석 (1968년)"처럼 동명이인을 가르는 괄호도 있어요. 뒤쪽까지 지우면 다른 두 사람이 한 점이 되고, 그 점을 지나는 모든 길이 오염돼요.

그래서 타입을 같이 봐요. 영화·사람·회사·시상식은 고유명사(개체), 장르·소재·장소는 보통명사(속성)로 묶고, 이름이 같아도 이 두 계열은 절대 합치지 않아요. 실제로 이 데이터에는 영화 《괴물》과 장르 "괴물"이 둘 다 있었어요. 합치지 않은 결과 그래프에는 괴물과 괴물 (Genre)가 따로 남아요.

중요꼭 기억할 것

영화 《괴물》과 장르 "괴물"을 한 점으로 합치면, 장르가 괴물인 모든 영화가 영화 《괴물》과 2홉으로 이어져요. "《괴물》과 비슷한 영화"를 물으면 괴수 영화가 전부 튀어나오는 엉뚱한 추천이 생겨요.

조사를 떼는 규칙도 조심해야 해요. 끝 글자만 보고 "은·는·이·가"를 떼면 《올드보이》가 "올드보"가, 《도리화가》가 "도리화"가 돼요. 그래서 이름 전체에는 조사를 떼지 않고, 《》 같은 닫는 기호 바로 뒤에 붙은 것만 조사로 보고 떼요.

개념 설명용 코드 — 정규화 함수가 무엇을 하는지 찍어 본 출력이에요

《기생충》은        → clean=기생충            norm=기생충
기생충 (영화)       → clean=기생충 (영화)     norm=기생충
괴물 (2006년 영화)  → clean=괴물 (2006년 영화) norm=괴물
황금 종려상         → clean=황금 종려상       norm=황금종려상

clean은 기호와 조사만 떼고 괄호는 남겨요. 비교할 때 쓰는 열쇠 norm에서만 괄호와 공백을 지워요. 같은 열쇠를 가진 표기들 중 가장 많이 나온 것을 대표 이름으로 고르고요.

개념 설명용 코드 — 실제로 한 점으로 합쳐진 표기들이에요 (모두 45건)

'버닝'              ← ['버닝', '버닝 (2018년 영화)']
'Cj엔터테인먼트'     ← ['Cj엔터테인먼트', 'Cj 엔터테인먼트', 'CJ 엔터테인먼트']

이 목록은 자동으로 처리하고 끝낼 게 아니라 사람이 한 번 훑어볼 목록이에요. 표기 흔들림이면 합치는 게 맞지만 동명이인이면 절대 합치면 안 되니까요. 실무에서는 이걸 표로 내보내 담당자가 "합칠 것·둘 것"을 표시해요. 자동으로 처리하되 위험한 자리만 사람에게 보여 주는 것, 이게 사람 확인 단계(HITL, Human-in-the-loop)의 가장 작은 모양이에요.

위키 분류로 보강한다 — 규칙은 좁지만 정확하다

20편에서 본 "분류:" 줄을 여기서 써요. 위키 편집자가 손으로 단 태그라 형식이 고정돼 있어서, 정규식 몇 줄로 삼중항이 나와요.

시상식 이름만은 정규식으로 잘라 내지 않았어요. "대한민국 영화대상 수상자"를 패턴으로 자르면 "대한민국"을 시상식으로 뽑는 사고가 나거든요. 시상식처럼 목록이 정해진 것은 규칙이 아니라 사전으로 다루는 게 정확해요. 알려진 시상식 이름 목록을 두고, 분류 문자열 안에서 가장 긴 이름부터 찾아 맞췄어요.

이렇게 LLM을 한 번도 안 부르고 삼중항 331개가 나왔어요. 관계별로는 이래요.

중요꼭 기억할 것

규칙으로는 ACTED_IN을 한 건도 못 뽑아요. 영화 문서의 분류에도, 배우 문서의 분류에도 출연 관계는 적혀 있지 않고 본문 서술에만 있어요. 그래서 출연은 LLM의 몫이에요. 골든셋이 가장 많이 요구하는 관계가 바로 이것(13개)이었죠.

규칙 결과가 늘 상식과 맞지는 않아요. 《기생충》에는 "대한민국의 재난 영화" 분류가 실제로 달려 있어서 (기생충, HAS_GENRE, 재난)이 생겼어요. 규칙은 모델처럼 지어내지는 않지만, 원본 태그를 그대로 믿는다는 한계는 있어요.

합치고, 출처를 남긴다

LLM 결과를 바탕으로 하고 규칙에만 있는 선을 더했어요. 같은 선이 양쪽에서 나오면 규칙 쪽을 더 믿어서 신뢰도를 1.0으로 올리고, 출처를 rule+llm으로 적었어요. 선마다 origin(llm·rule·rule+llm)을 남겨 두면 나중에 "이 답의 근거는 사람이 단 태그에서 왔나, 모델 추측에서 왔나"를 보여 줄 수 있고, 틀린 사실을 발견했을 때 어느 단계가 만들었는지 되짚을 수 있어요.

여기서 정규화는 두 결과를 합친 뒤에 한 번 해야 해요. 따로따로 하면 LLM이 뽑은 "기생충"과 문서 제목에서 온 "기생충 (영화)"가 각자의 대표 이름을 가져서, 두 그래프가 겹치지 않고 나란히 쌓이기만 해요.

필요한 사실이 다 들어왔나 센다

골든셋에는 문항마다 정답에 꼭 필요한 삼중항이 적혀 있으니, 그게 그래프 안에 몇 개 있는지 세면 돼요. 이 기준 삼중항 커버리지는 문자열 비교만으로 계산해서 비용이 0이에요. 비용이 안 드는 자를 먼저 만들어 두면 실험을 마음껏 돌릴 수 있어요.

총점보다 관계별 칸이 중요해요. 규칙은 장르·배경·수상처럼 형식이 고정된 관계를 LLM 없이 다 잡았고, LLM은 규칙이 원리적으로 못 채우는 출연을 다 잡았어요. 서로 다른 구멍을 메웠기 때문에 합치니 100%가 됐어요. 다만 위에서 짚었듯 스키마를 이 15문항에서 역산했으니, 이 100%는 "이 질문들에 대해서는"이라는 조건이 붙은 숫자예요.

여기서 가져갈 원칙은 이거예요. 형식이 고정된 곳은 규칙으로 싸고 정확하게, 자유 서술만 LLM으로. 전부 LLM에 맡기는 것도, 전부 규칙으로 짜는 것도 최선이 아니에요.

쓰기 전에 네 가지를 점검한다

문서 검색은 결과가 이상하면 원문을 읽어 바로 알아채지만, 그래프는 틀린 선 하나가 조용히 엉뚱한 경로를 만들어도 겉으로는 그럴듯해요. 그래서 그래프를 쓰기 전에 네 가지를 습관처럼 봐요. 넷 다 모델 호출 없이 몇 초면 끝나고, 이상이 보이면 대개 스키마나 추출 지침으로 돌아가 고칠 자리를 가리켜요.

점검무엇을 보나이상 신호

중요꼭 기억할 것

그래프가 서로 이어지지 않은 덩어리 여러 개로 나뉘어 있으면, 다른 덩어리에 있는 두 대상 사이에는 어떤 경로도 없어요. 탐색을 아무리 깊게 해도 못 건너가요. 덩어리가 많다면 탐색이 아니라 정규화(같은 대상이 두 점으로 갈렸나)나 스키마(잇는 관계가 빠졌나)를 먼저 봐요.

④ 눈으로 보기

전체를 그리면 털뭉치가 되니, 한 대상 주변 1~2홉만 잘라(nx.ego_graph) 그려요. 관계마다 색을 다르게 칠하면 "왜 이 영화 옆에 이 사람이 붙어 있지?" 같은 선이 통계보다 먼저 눈에 띄어요. 《기생충》 주변을 그리면 공동 각본가 한진원이 출연 선으로 붙어 있는 게 바로 보여요. 위에서 본 추출 오류예요. 봉준호의 틀린 출연 선은 그림에 없는데, 같은 두 점 사이에는 선을 하나만 두도록 짜서 먼저 들어온 감독 선만 남았기 때문이에요. 고친 게 아니라 우연히 가려진 거라, 이런 규칙이 무엇을 조용히 버리는지도 알고 있어야 해요. 그래서 그래프 그림은 예쁘게 만드는 작업이 아니라 디버깅 도구예요.

실행: 로컬 파이썬 — 아무 환경 OK — matplotlib 필요. 한글이 네모로 나오면 한글 폰트를 등록해요

ego = nx.ego_graph(G.to_undirected(), "기생충", radius=1)   # 기생충과 바로 이웃만

중요꼭 기억할 것

관계의 종류가 곧 그래프가 답할 수 있는 질문의 범위예요. 스키마에 없는 관계는 아무리 탐색을 잘해도 답이 안 나오고, 이름만 준 관계는 엉뚱한 사실로 채워져요. 그래서 스키마 설계는 데이터 작업이 아니라 이 제품이 무엇에 답할지 정하는 일이에요. 뽑기 전에 ① 답할 질문 목록에서 필요한 관계를 거꾸로 세고, ② 관계를 (출발, 관계, 도착)으로 고정하고, ③ 뽑은 뒤 위의 네 가지 점검으로 스키마가 의도대로 먹었는지 확인해요.

from langchain_openai import ChatOpenAI
from langchain_core.documents import Document
from langchain_experimental.graph_transformers import LLMGraphTransformer

REL_TRIPLES = [("Person", "DIRECTED", "Film"), ("Person", "ACTED_IN", "Film"),
               ("Film", "HAS_GENRE", "Genre"), ("Film", "WON_AWARD", "Award")]

tf = LLMGraphTransformer(
    llm=ChatOpenAI(model="gpt-4.1-mini", temperature=0, timeout=120, max_retries=3),
    allowed_nodes=["Film", "Person", "Genre", "Award"],
    allowed_relationships=REL_TRIPLES,          # 삼중항으로 — 방향이 고정된다
    relationship_properties=["category", "character"],
    strict_mode=True,
    additional_instructions="개체 이름은 원문 표기 그대로. Award 노드는 시상식 이름만, 부문은 category 속성에.",
)

title = "기생충 (영화)"
body = open("input/cinephile_kb_80/docs/기생충_(영화).md", encoding="utf-8").read()[:2400]
doc = Document(page_content=f"[문서 제목] {title}\n[문서 유형] Film\n\n{body}")
for r in tf.convert_to_graph_documents([doc])[0].relationships:
    print(f"({r.source.id}) --[{r.type}]--> ({r.target.id})", r.properties or "")

  2. [문서 제목] 두 줄을 지우고 다시 돌려요. 배역이 여전히 《기생충》에 붙는지 비교해요.
  3. allowed_relationships를 ["DIRECTED", "ACTED_IN", "HAS_GENRE", "WON_AWARD"] 이름 목록으로 바꿔 돌려요. 선이 엉뚱한 칸에 들어가는지 보세요.

이럴 때 의심하세요 — LLM으로 관계를 뽑은 뒤

추출의 실패는 에러로 안 보여요. 추출은 "완료"를 찍고, 문제는 나중에 에이전트가 엉뚱한 답을 낼 때 처음 드러나요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "문서에서 관계를 뽑아 그래프로 만들어 줘" — 관계를 이름 목록으로 줬는지, (출발, 관계, 도착)으로 줬는지
  • "문서 전체 돌려서 그래프 만들어 줘" — 돌리기 전에 청크 수와 토큰을 셌는지, 결과를 파일로 남기는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
"영화가 연도에 출연했다", "영화가 감독을 제작했다" 같은 말이 안 되는 선이 보인다 추출기에 넘긴 allowed_relationships 값 이름 목록이면 (출발 타입, 관계, 도착 타입) 삼중항으로 바꾸고 strict_mode를 켠다. 선을 무작위로 스무 개 뽑아 눈으로 읽어 봐요 — 이름만 준 스키마
어떤 배우가 나오지도 않은 영화의 출연자로 답에 등장한다 그 선의 source(어느 문서에서 나왔나)와, 그 문서의 청크 앞부분 청크 맨 앞에 문서 제목이 글자로 들어가 있는지 본다. metadata에만 있으면 모델은 못 봐요 — 제목 헤더 절
"같은 시상식 수상작"이나 "같은 감독의 다른 작품"을 물으면 한두 편만 나오거나 아무것도 안 나온다 그 시상식·감독 이름으로 그래프 노드를 검색한 결과. 비슷한 이름의 노드가 여럿인지 정규화 열쇠(공백·괄호를 지운 이름)가 같은 노드끼리 묶어 본다. 부문 이름이 시상식 노드로 들어갔는지도 본다 — 정규화 절
추출 한 번에 예상보다 몇 배 많은 요금이 나왔다 API 사용량 화면의 입력·출력 토큰, 그리고 청크 수 입력 토큰을 청크 수로 나눠 청크당 오버헤드를 본다. 지침이 길수록 청크마다 곱해져요. 다음부터는 5건으로 먼저 돌린다 — 비용 절

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이 프로젝트에서 LLM으로 관계(삼중항)를 뽑는 코드를 찾아서, (1) 허용 관계를 어떤 형태로 넘기는지,
(2) 청크에 문서 제목이 본문 글자로 들어가는지, (3) 추출 결과를 파일로 캐시하는지를 파일·줄 번호로 보여 줘.
그리고 추출된 삼중항 중 무작위 20개를 출력하는 방법을 알려 줘. 아직 코드는 고치지 마.

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 다른 편의 같은 목록은 1편 · 20편에 있어요.

  • 관계는 이름이 아니라 (출발, 관계, 도착)으로 준다
  • 수상 부문은 노드가 아니라 선의 속성으로
  • 모델이 볼 정보는 metadata가 아니라 본문 글자로
  • LLM 추출은 방향이 뒤집히니 이웃은 양쪽을 본다
  • 이름이 같아도 개체와 속성은 합치지 않는다
  • 분류 규칙으로는 출연을 못 뽑는다
  • 다른 덩어리 사이에는 길이 없다
  • 관계의 종류가 곧 답할 수 있는 질문의 범위

다음 편에서는 이 그래프를 들고 LangGraph로 에이전트를 조립해요. 질문 종류에 따라 세 갈래로 나눠 답하게 할 거예요.

더 해보기 — 완성한 그래프를 눈으로 직접 보기

지금까지는 그래프를 노드 수·엣지 수 같은 숫자로만 봤어요. 그런데 그래프를 만들면서 제일 재미있는 순간은 사실 완성된 그래프가 실제로 어떤 모양인지 눈으로 보는 것이에요.

matplotlib으로 그리면 그림 한 장이 그대로 굳어요(정적 시각화) — 노드가 몇백 개만 넘어도 점이 서로 겹쳐서 뭐가 뭔지 안 보이고, 확대도 안 돼요. 반면 plotly5 같은 라이브러리로 그리면 브라우저 안에서 마우스 휠로 확대·이동하고, 점에 마우스를 올리면 이름이 뜨고, 범례를 눌러 특정 종류(배우만, 영화만)를 껐다 켰다 할 수 있어요 — 이런 걸 동적 시각화라고 불러요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이 프로젝트에서 방금 만든 그래프(삼중항 파일 또는 networkx 그래프)를 찾아서,
plotly로 인터랙티브 네트워크 시각화를 만들어 줘.
노드는 타입별로 색을 다르게 하고, 마우스를 올리면 이름과 연결 수가 보이게 해 줘.
결과는 HTML 파일로 저장해서 브라우저로 열어 볼 수 있게 해 줘.

마우스 휠로 그 자리에서 바로 확대되는 매끄러운 느낌이나, 노드끼리 서로 밀고 당기며 자리 잡는 물리 시뮬레이션 느낌을 더 원하면, 같은 부탁에서 plotly 대신 pyvis6를 써 달라고 하면 돼요.

  1. LLMGraphTransformer — LangChain의 실험 패키지(langchain-experimental)에 든 도구로, 문서를 주면 LLM을 불러 노드와 관계를 뽑아 줘요. ↩
  2. tiktoken — OpenAI 모델이 글을 몇 토큰으로 세는지 모델 호출 없이 계산해 주는 파이썬 라이브러리예요. ↩
  3. strict_mode — 허용한 노드 타입과 관계 밖의 결과를 추출기가 버리게 하는 설정이에요. ↩
  4. 차수(degree) — 한 노드에 붙은 선의 개수로, 들어오는 선과 나가는 선을 합쳐 세요. ↩
  5. plotly — 파이썬으로 확대·호버·범례 토글이 되는 인터랙티브 그래프를 그려서 HTML로 내보내는 시각화 라이브러리예요. ↩
  6. pyvis — 네트워크 그래프를 물리 시뮬레이션(노드끼리 밀고 당기며 자리 잡기)으로 그려 주는 파이썬 라이브러리로, vis-network.js를 감싸고 있어요. ↩
