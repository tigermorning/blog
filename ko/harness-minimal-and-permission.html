2편과 3편이 계속 "무언가를 더하는" 이야기였다면, 이번 편은 방향이 반대예요. 더 많은 기능이 항상 더 좋은 하네스를 뜻한다면 작은 루프가 살아남을 이유가 없겠죠. 얼마나 덜어내도 되는지, 그리고 반대로 무엇을 실행할 수 있는지 경계는 어떻게 그어야 하는지를 함께 봐요.

미니멀 — 작은 루프도 조건 아래에서는 작동한다

미니멀 기능은 "적게 넣는 것"을 목표로 삼지 않아요. 과업을 끝낼 수 있는 가장 작은 루프의 조건을 찾는 거예요. 기능 하나를 덜면 문맥 비용과 설정 부담은 줄지만, 필요한 행동이나 안전 경계까지 함께 빠질 수 있거든요.

mini-swe-agent는 SWE-agent 팀이 만든 실험용 최소 에이전트예요. 스스로 "100줄 에이전트"라 소개하고, Bash만 쓰고 셸 상태와 선형 이력만 단순하게 다뤄요. README는 SWE-bench Verified에서 74% 초과를 보고하는데, 이건 자체 보고이고 모델과 측정 시점이 고정돼 있지 않아요. pi는 개발자 한 명(Mario Zechner)이 만든 미니멀 코딩 에이전트로, read·write·edit·bash 네 도구와 1,000토큰 미만의 시스템 프롬프트(모델이 매 요청마다 가장 먼저 읽는 전역 안내문)만으로 설계됐어요. 저자 스스로도 "모델이 좋아질수록 복잡한 하네스가 덜 필요할 수 있다"는 가설이라고 밝혀요 — 즉 둘 다 아직 독립 학술 검증을 거치지 않은 설계 가설이에요.

SWE-agent의 풍성한 ACI와 mini-swe-agent의 100줄 Bash 루프는 단순히 기능 수만 다른 비교가 아니에요. 전자는 모델이 쓸 행동과 관측을 인터페이스로 정교하게 만들고, 후자는 그 가운데 지금 모델에서는 줄어들 수 있는 부분이 있는지 물어요. 같은 모델·과업을 고정하지 않으면 이 차이를 "하네스 효과"라고 말할 수 없다는 게 중요한 전제고요.

이 둘의 관계는 공구함에 빗대면 더 잘 잡혀요. 칼·가위·드라이버가 다 붙은 스위스 나이프(SWE-agent의 풍부한 ACI)는 만능처럼 보이지만, 실제로는 나사 하나 박는 날에 그냥 일자 드라이버 하나(pi의 4도구, mini-swe-agent의 Bash 하나)만 있어도 충분한 경우가 많아요. 만능 나이프가 늘 좋은 것도 아니에요 — 무겁고, 원하는 날을 펼치는 데 시간이 걸리죠. 하네스에서는 그 무게가 토큰·설정·충돌 규칙으로 나타나요. 그러니까 이 비교는 "기능이 몇 개냐"의 싸움이 아니라, 오늘 이 과업에 필요한 공구 하나가 무엇인지 고르는 판단이에요. 예를 들어 로그 파일에서 오류 줄만 골라 정리하는 스크립트를 짠다면, 풍부한 ACI는 파일 뷰어로 100줄씩 넘겨보고 검색 도구로 찾고 lint 피드백까지 받아가며 정교하게 접근하고, pi식 최소 루프는 read로 읽고 write로 스크립트를 쓰고 bash로 실행해본 뒤 실패하면 edit으로 한 줄 고쳐 재실행하는 것만으로 끝까지 가요. 반대로 컨텍스트 관리가 병목인 긴 이력, 외부 격리로 안 풀리는 권한 요구, 복잡한 다단계 리팩터링처럼 가벼움보다 안전이나 정확성이 더 중요한 과업이라면, 최소 루프는 눈 쌓인 산을 작은 배낭 하나로 오르는 격이라 실패해요.

흥미롭게도 상용 도구에서도 같은 방향이 관찰돼요. Anthropic 소속 개발자 Thariq Shihipar는 Claude 블로그에서, Claude Code의 시스템 프롬프트에서 80% 이상을 제거하는 스트레스 테스트를 거쳤는데도 코딩 평가에서 측정 가능한 손실이 없었다고 밝혔어요. 과거 최악의 시나리오를 막으려던 규칙이 모델이 개선된 뒤엔 필요 없어졌고, 서로 충돌하는 지시가 오히려 과잉 제약이 됐다는 거예요. 다른 사례에서는 멀티에이전트 하네스의 sprint 구조를 없애고 평가를 실행 끝 한 번으로 줄이기도 했어요. 이건 "미니멀이 항상 정답"이라는 뜻이 아니라, 현재 모델이 스스로 해내는 일을 스트레스 테스트해서 불필요한 장치를 덜어낸 관찰이에요.

권한·보안 — 무엇을 실행할 수 있는지 먼저 경계 짓기

파일을 읽는 능력, 명령을 실행하는 능력, 외부 메시지를 받는 능력은 서로 다른 위험을 만들어요. (이전에 다룬 "매번 확인 / 자동 승인" 같은 승인 방식의 기본 감각이 여기서 더 깊어져요.) 이 셋을 같은 "권한"으로 뭉뚱그리면 안 되는 이유가 있어요 — 실패하는 방식이 전혀 다르거든요. 파일 읽기가 잘못되면 정보가 새어나가는 유출 위험이고, 명령 실행이 잘못되면 시스템 자체가 망가지는 파괴 위험이고, 외부 메시지를 그대로 믿으면 에이전트의 의도 자체가 뒤틀리는 조종 위험이에요. 경계를 안 나누면 "읽기만 허용했는데 어느새 쓰기까지 되는" 식으로, 입력 하나가 도구 전체 권한으로 곧장 이어져요. 권한·보안 기능은 이 세 입구를 각각 다른 문으로 나누는 일이에요.

  • Spotlighting 연구는 외부 입력의 출처를 구분하는 변환을 적용했을 때, 공격 성공률이 50% 초과에서 2% 미만으로 내려갔다고 보고했어요. 다만 이건 저자 실험 조건의 수치라, 모든 문서·모든 공격에 같은 방어가 보장되진 않아요.
  • ToolEmu 연구는 36개 고위험 도구·144개 사례를 만들어 안전성을 에뮬레이션으로 평가했는데, 최고 성능의 에이전트도 23.9% 실패했다고 보고했어요. 안전 장치가 있어도 도구 사용의 위험이 완전히 사라지진 않는다는 뜻이에요.
  • CaMeL(DeepMind)은 권한·데이터 흐름·제어 흐름을 구조적으로 분리해서, 외부 입력이 민감한 도구를 직접 제어하지 못하게 하는 설계예요. AgentDojo는 공격 성공률과 과업 완수율을 함께 재는 벤치마크인데, 많이 막을수록 안전해 보이지만 과업 자체를 못 끝낼 수도 있다는 걸 짚어줘요.

여러 채널에서 상시 대기하는 오픈소스 에이전트 OpenClaw는 이 경계를 실제 설정으로 보여줘요. Discord·Slack·Telegram 같은 채널 메시지를 Gateway가 받고, 세 가지 설정으로 범위를 좁혀요.

설정정하지 않으면정하면
pairing처음 보는 발신자의 메시지가 신뢰된 입구인지 확인할 수 없음짝이 맞은 발신자의 메시지만 정해진 세션으로 라우팅
allowFrom채널 접근 규칙만으로는 허용 발신자가 명시적으로 좁혀지지 않음목록 밖 발신자의 메시지는 에이전트 실행으로 이어지지 않음
그룹 멘션 요구일반 대화도 처리 대상과 섞일 수 있음에이전트를 부른 메시지만 처리, 나머지는 무시

이 세 문이 실제로 어떻게 겹쳐 작동하는지, Slack 채널에서 "배포 스크립트 실행해줘"라는 같은 요청을 두 가지 설정으로 비교해보면 감이 와요. 경계가 없는 경우라면, 누구든 채널에 메시지를 보내면 Gateway가 그대로 받아 에이전트가 곧장 bash deploy.sh를 실행해요. 그룹 대화의 잡담도 호출로 섞여 들어가고, 만약 채널에 올라온 외부 문서 안에 숨은 지시가 있다면 그것도 그대로 실행될 수 있어요. 세 경계를 적용한 경우는 이래요. 먼저 pairing된 발신자의 메시지만 Gateway를 통과하고, 그중에서도 allowFrom에 등록된 사람만 처리되고, 그룹 대화에서는 "@에이전트 배포해줘"처럼 멘션된 메시지만 라우팅돼요. 여기까지 통과해도 bash deploy.sh는 도구 권한 규칙에서 "승인 대기"로 걸려 실행 전에 사람이 화면에서 한 번 확인해야 하고, 승인된 뒤에도 격리 환경(Docker 컨테이너) 안에서만 파일·네트워크에 닿아요. 같은 한 줄 요청인데, 경계 다섯 개(발신자 확인 셋 + 실행 전 승인 + 실행 후 격리)를 통과해야 실제로 배포가 이뤄지는 거예요.

이 셋은 발신자와 호출을 가르는 경계지, 도구가 허용된 뒤 실행 피해를 가두는 격리 환경과는 다른 층이에요. 그 격리 층은 도구별 설정에서 또 확인해야 해요. Claude Code의 권한 모드는 어떤 도구 행동을 자동으로 허용하고 어떤 행동을 승인 대상으로 둘지 정하고, opencode의 allow·ask·deny 규칙은 도구·행동별로 허용·확인·거부를 정해요(같은 행동에 여러 규칙이 맞으면 마지막 매치가 적용되고, 에이전트별 규칙이 전역 규칙보다 우선해요).

여기서 꼭 구분해야 할 게 있어요. 권한은 누가 무엇을 허용할지를 묻고, 격리는 허용된 실행의 피해를 어디에 가둘지를 물어요. 도구 안의 권한 규칙은 실행 전 판단을 다루고, Docker 컨테이너 같은 외부 격리 환경은 실행된 프로세스가 닿는 파일·네트워크 범위를 제한해요. 하나가 다른 하나를 대신하지 않아요. 실제로 pi는 내장 권한 체계 없이 실행 사용자 권한으로 도구를 실행하고 격리는 Docker 같은 외부 환경에 맡기는 설계인 반면, Claude Code는 권한 규칙을 도구 안에 둬서 허용·승인을 먼저 다뤄요. 같은 위험을 없애는 단일 해법이 아니라, 권한 판단과 실행 환경을 서로 다르게 배치한 답인 거예요.

권한 설정은 "안전하다"는 선언으로 끝나지 않아요. 같은 과업에서 허용 규칙을 하나 바꾸고, 처리된 요청 수·승인 횟수·막힌 정상 작업·의도하지 않은 도구 호출을 함께 기록해야 다음 설정을 바꿀 근거가 생겨요. 권한을 촘촘히 할수록 공격을 덜 받는다고 바로 결론 내리지 않고, 정상 작업을 막은 비율도 함께 봐야 하는 이유예요.

여기까지 일곱 기능 중 다섯을 봤어요. 다음 편에서는 나머지 하나 — 평가 루프 — 를 보고, 지금까지 나온 일곱 개 실제 하네스(Claude Code, opencode, Aider, pi, OpenClaw, Hermes, SWE-agent)를 기능 지도 위에 한 번에 올려 비교해요.
