"회의록을 읽고 정리했습니다"라는 답변이 화면에 떴어요. 하네스가 완성된 걸까요?

아직 몰라요. 모델이 파일을 읽지 않고 답했을 수도 있고, 읽기는 했지만 원문에 있는 담당자를 빠뜨렸을 수도 있어요. 코드 수정도 마찬가지예요. 파일 내용이 바뀌었다는 사실만으로는 부족하고, 의도한 오류를 고쳤는지를 검사해야 하죠.

이번 편은 구현에 앞서 그 판단 기준을 씁니다. 이걸 완료 조건 또는 인수 기준1이라고 불러요.

비유 — 입주 전 사전점검

새 집에 들어가기 전에 사전점검이라는 걸 해요. 하루 날을 잡아 집을 돌면서 하자를 찾는 절차예요.

여기서 잘하는 사람과 못하는 사람이 갈리는 지점이 있어요. 못하는 사람은 집에 들어가서야 볼 것을 생각해요. 그러면 눈에 띄는 것만 보게 돼요. 벽지 얼룩처럼 튀는 건 잡지만, 붙박이장 문이 끝까지 닫히는지, 싱크대 아래 배수가 새지 않는지는 그냥 지나쳐요.

잘하는 사람은 집에 들어가기 전에 체크리스트를 만들어 가요. "모든 문을 여닫아 본다", "물을 5분 틀어 놓고 아래를 본다" 같은 항목이요. 그리고 항목마다 미리 정한 기대가 있어요 — 문은 끝까지 닫혀야 하고, 물은 새지 않아야 하고요.

현장에서 시공사 담당자가 "다 확인했습니다, 문제없습니다"라고 말할 수 있어요. 그 말은 제 체크리스트의 항목이 아니에요. 제가 문을 직접 여닫아 봐야 그 칸이 채워져요.

그리고 칸을 채우는 방식이 네 가지예요. 아직 안 해 봄, 확인했고 기대대로임, 확인했는데 기대와 다름, 그리고 이 집엔 해당 없음(발코니가 없는 집에서 '발코니 배수' 항목처럼요). 여기서 제일 위험한 게 마지막이에요. 확인하기 귀찮다고 '해당 없음'으로 넘기면 체크리스트 전체가 의미를 잃어요.

핵심 한 줄: 체크리스트는 집에 들어가기 전에 만들어야 해요 — 보고 나서 만들면 이미 본 것만 적게 되니까요.

다만 비유가 끊기는 점이 있어요. 사전점검은 하자를 다 잡으면 끝이지만, 검사를 다 통과했다고 모든 결함이 없다는 뜻은 아니에요. 검사하지 않은 경계 조건은 그대로 한계로 남습니다. 이건 뒤에서 다시 나와요.

전체 흐름 — 기대는 어디서, 실제는 어디서

읽는 법: 위쪽 줄은 구현하기 전에 만드는 것이고, 아래쪽 줄은 구현한 뒤에 생기는 것이에요. 둘은 오른쪽 끝에서만 만나요. 아래 줄에서 위 줄로 올라가는 화살표가 없다는 게 이 그림의 핵심이에요.

점선이 이 그림의 전부예요. 모델이 우연히 내놓은 답을 기대값으로 복사하면, 잘못된 동작도 통과하게 만들 수 있어요. 기대는 원문에서 나와야 하고, 실제는 실행에서만 나옵니다.

한 칸 채워 보기

가상 회의록에 "수진이 금요일까지 홍보 초안을 작성한다"라고 적어 뒀다고 해 볼게요. 그러면 이렇게 나눠 적어요.

기록할 내용예시
준비한 자료담당자와 마감이 명시된 작은 가상 회의록
사용자 행동홍보 초안의 담당자와 마감을 찾아 달라고 요청
기대 결과실제 파일을 읽고, 수진·금요일을 근거와 함께 전달
실제 결과실행 후 읽기 기록과 최종 답변을 확인해 기록

정답 문장 표현까지 고정할 필요는 없어요. "담당 수진, 마감 금요일"과 같은 뜻이면 문장이 달라도 통과예요. 반면 없는 담당자를 만들었거나 금요일을 행사 날짜로 잘못 해석했다면 내용 기준을 충족하지 못한 거예요.

모의 모델 — 만들 수 있는 상황과 만들 수 없는 상황

모델에게 "도구를 세 번 호출해 줘"라고 부탁해도 정확히 그 응답이 온다는 보장이 없어요. 그런데 "반복 한도에 도달하면 멈추는가" 같은 검사는 그 상황을 반드시 만들어야 하죠.

그래서 모의 모델2을 씁니다. 모델 대신 준비한 응답을 순서대로 돌려주는 테스트용 구성이에요. 그런데 이게 무엇을 증명하고 무엇을 증명 못 하는지가 헷갈리기 쉬워요.

검사확인하는 것이 검사만으로 알 수 없는 것
A02 — 모의 도구 호출인수 검사, 실제 도구 연결, 결과 반환, 종료실제 모델의 도구 선택 능력
A06 — 반복하는 모의 응답합의한 한도에서 멈추는지실제 모델이 반복할 빈도
A01 — 실제 모델의 자료 작업실제 연결과 읽기, 최종 답의 근거 일치다른 모든 자료에서도 같은 품질인지

모의 검사는 요청을 정확히 만들 수 있으니, 결과가 엉뚱한 요청에 붙거나 끝나지 않는 버그를 찾기에 좋아요. 다만 이 결과를 "실제 모델 연결 성공"으로 기록하면 안 됩니다.

반대로 실제 모델 검사는 인증·통신·응답 형식·도구 실행·내용 품질을 한꺼번에 보여 줘요. 그래서 파일 읽기는 성공했는데 요약이 틀렸다면 두 사실을 나눠 기록해요. A01의 완료 기준이 "근거에 맞는 결과까지"라면, 연결 성공만으로 항목 전체를 통과시키지 않습니다.

코드 변경의 합격선 — 기대값은 규칙에서 계산해요

A03은 작은 결함이 있는 코드를 대상으로 해요. 여기서 픽스처3(fixture)는 검사를 반복할 수 있게 준비해 둔 입력·파일·상태예요. 민감한 실제 프로젝트 대신, 결함과 기대 동작을 이해할 수 있는 작은 코드를 준비합니다.

강의의 예를 그대로 가져와 볼게요. "참가자별 비용과 장소 고정 비용을 합한다"는 함수인데, 장소비를 인원수만큼 중복 계산하는 결함이 있어요.

항목값 (원)계산 근거
참가자 1인당 비용5,000비용 규칙에서 정한 단가
참가자 수2명이 검사 입력
장소 고정 비용100,000인원과 무관하게 1회
기대 합계110,0005,000 × 2 + 100,000
결함이 있는 함수의 현재 출력210,000장소비를 2번 더함 — 기대값이 아님

표 아래 단서를 하나 붙여요. 기대값 110,000원은 함수의 출력이 아니라 비용 규칙에서 계산한 값이에요. 함수의 현재 출력(210,000)을 기대값 칸에 적는 순간, 이 검사는 결함을 영원히 통과시킵니다.

A03에는 다음 연결이 드러나야 해요.

  1. 변경 전 검사에서 의도한 결함이 드러난다.
  2. 에이전트가 제안한 변경 내용을 확인한다.
  3. 합의한 승인 절차 뒤 변경을 적용한다.
  4. 같은 검사를 다시 실행하고 결과를 확인한다.
  5. 요청과 무관한 변경이나 검사 기대값 조작이 없는지 본다.

그리고 사람이 정답 코드를 넣어 검사가 통과한 것과 에이전트가 변경을 찾아 완료한 것은 구별해 기록해요.

나쁜 선택 vs 좋은 선택

같은 사전점검에서, 붙박이장 문 항목을 채우는 두 가지 방식이에요.

나쁜 선택좋은 선택
무엇을 했나: A04(변경 거절)를 검사하면서, 하네스가 "변경을 취소했습니다"라고 출력한 것을 보고 PASS로 적었어요.

무슨 일이 생기나: 실제로는 승인 확인보다 쓰기가 먼저 실행되는 경로가 있어서 파일은 이미 바뀐 상태였어요. 거절 문구는 그 뒤에 출력된 거고요. 나중에 진짜 작업 폴더에서 같은 일이 벌어져야 알게 됩니다.		 무엇을 했나: 거절 전후의 파일 내용을 대조하는 것을 A04의 관찰 항목으로 적어 뒀어요.

무슨 일이 생기나: 첫 실행에서 바로 FAIL이 나요. 거절 문구는 맞는데 파일이 달라졌으니까요. 고칠 곳이 프롬프트가 아니라 실행 코드의 승인 검사라는 것도 같이 드러납니다.

같은 원칙이 A05에도 적용돼요. 임시 작업 폴더 밖에 가상 파일을 두고, 경로 이탈 요청이 코드의 검사에서 거절되는지 확인해요. 진짜 개인 파일로 시험할 필요는 전혀 없고요. 그리고 모델이 우연히 그 요청을 하지 않았다는 관찰만으로 경로 제한이 구현됐다고 판단하지 않습니다.

A07의 오류 상황도 갈라요. 도구 인수가 잘못됐다면 실패를 모델에게 돌려주고 수정 기회를 줄 수 있어요. API 연결 자체가 실패했다면 사용자에게 실패를 표시해야 하고요. 어느 경우에도 성공한 작업처럼 기록하지 않습니다.

상태 네 가지 — DEFERRED를 도피처로 쓰지 않기

상태의미
NOT_RUN계획했지만 아직 실행하지 않음
PASS실행 증거가 기대 결과를 충족함
FAIL실행했지만 기대 결과를 충족하지 못함
DEFERRED합의한 선택 범위에 따라 미룸

공통 필수 항목이 어렵다는 이유로 DEFERRED로 바꾸지 않아요. 실패 원인과 남은 구현을 기록합니다. 반면 이런 경우는 DEFERRED가 정당해요.

  • D07에서 영속 저장을 선택하지 않았다면 → 재시작 복원에 해당하는 A09를 미룸
  • D08에서 추가 제공자를 미뤘다면 → A10을 미룸

둘 다 결정 ID를 함께 적어야 나중에 "왜 안 했지?"에 답할 수 있어요.

A08(같은 세션의 후속 요청)은 선택한 대화 유지 범위에 맞게 검증해요. 앱이 실행 중일 때 이어지는 대화와 앱을 껐다 켠 뒤 파일에서 복원하는 대화는 다른 기능이에요. 저장하지 않기로 했다면 재시작 후 이어진다고 설명해서는 안 됩니다.

직접 해보기 — Given · When · Then

마지막으로 D01의 사용자 이야기에서 정상 사례 하나와 실패 사례 하나를 직접 골라 ACCEPTANCE.md의 학생 추가 항목에 적어요. 형식은 이래요.

  • Given — 준비: 어떤 자료와 상태에서 시작하는지
  • When — 행동: 사용자가 무엇을 요청하거나 결정하는지
  • Then — 관찰: 무엇을 확인하면 기대한 동작이라고 볼지

예를 들면요.

  • 정상 사례 — 담당자가 적힌 자료를 준비하고(Given), 할 일 정리를 요청하면(When), 실제 근거와 담당자를 함께 제시한다(Then).
  • 실패 사례 — 담당자가 없는 자료에서(Given), 담당자 확인을 요청하면(When), 사람 이름을 만들지 않고 미정이라고 표시한다(Then).

내 작업에서 정상 사례 하나와 실패 사례 하나를 골랐어. 기대 결과가 모호하지 않은지 같이 검토해 줘.
  1. 바꿀 것 — A01~A12를 자기 시나리오와 연결하고, 학생 추가 항목 두 개를 Given·When·Then으로 씁니다.
  2. 측정할 것 — 각 항목에 대해 "이게 통과하면 내가 원한 일이 된다고 말할 수 있는가"를 스스로 물어요. 못 하겠으면 기대 결과가 아직 모호한 거예요.
  3. 비교할 것 — 증거 칸이 비어 있는지 확인해요. 아직 실행 안 했으니 비어 있는 게 정상이에요. 좋은 검사 계획을 세웠다는 이유로 PASS를 적지 않습니다.

실제 검증 기록에는 코드 버전, 제공자와 모델, 입력 자료, 도구 실행 결과, 최종 답과의 대조를 남길 계획을 세워 둬요. 인증 키와 개인 자료는 증거에 넣지 않습니다.
