이 글은 10번 글을 발표 시간에 맞게 줄인 글이에요. 10번 글은 아홉 편 전체를 표와 계산으로 꼼꼼히 정리해서 길어요. 이 글은 다섯 장면만 말하고, 그중 한 가지 실험만 깊게 보여 줘요. 막히면 여기서 막히는 게 정상이에요. 아홉 날 동안 새 말이 정말 많이 나왔으니까요. 모르는 말은 쪽 아래 풀이를 봐요.

비유로 먼저 — 밀키트 상자를 가맹점에 보내는 본사

내가 본사이고, 밀키트 상자는 새 코드예요. 가맹점은 사용자가 쓰는 실제 서비스예요. 처음에는 사장이 상자를 직접 들고 갔지만, 이제는 배송 로봇이 가요. 가맹점은 영업 중이라서 새 상자를 뒤쪽 진열대에 먼저 차려 두고, 손님 안내만 새 진열대로 돌려요.

비유 속 일컴퓨터에서 실제로 하는 일
사장이 상자를 직접 들고 가요사람이 배포 명령을 직접 쳐요 (수동 배포)
배송 로봇이 가요코드를 합치면 GitHub Actions가 자동으로 배포해요
검수대에서 상자를 열어 봐요CI2 테스트가 깨진 코드를 막아요
뒤쪽 진열대에 먼저 차려 둬요새 버전을 요청 0%로 먼저 올려 둬요
손님 안내만 돌려요준비를 확인한 뒤에 요청을 새 버전으로 옮겨요

핵심 한 줄: 상자를 보내는 일은 포장, 검수, 시식, 안내 교체가 이어진 한 줄이에요. 비유가 끊기는 곳도 있어요. 손님은 진열대가 바뀌는 걸 눈으로 보지만, 서비스 사용자는 바뀐 줄도 몰라요. 그래서 «사용자가 오류를 봤는지»는 눈이 아니라 숫자로 세어야 해요.

한 장 그림 — 아홉 날을 다섯 장면과 세 질문으로

위 줄은 다섯 장면이에요. 아래 줄은 그 장면들이 답해 주는 세 가지 질문이에요.

정리 — 다섯 장면, 한 문장씩

아홉 날을 다섯 장면으로 묶었어요. 각 장면에서 쉬운 말로 한 문장과, 제가 직접 본 것 하나만 적었어요. 자세한 과정은 오른쪽 열의 글에 있어요. 첫 장면(10월 19일 설계)과 둘째 장면의 값은 이번에 본문을 다시 읽지 않고, 10번 글의 표에 적어 둔 내용만 옮겼어요.

장면한 문장제가 본 것더 읽기
① 설계
10.19		코드를 짜기 전에 «누가, 어디서, 어떻게 쓰는지»를 사람이 먼저 정해 문서(PRD) 한 장으로 남겨요.코드 없이 프로토타입(시제품)으로 먼저 확인한 뒤, 구조 그림과 PRD 한 장으로 정리했어요.(1)
② Cloud Run1
10.20~21		코드 폴더를 올리면 공개 주소가 생겨요. 서버가 정상이라고 해도 손님이 답을 못 받을 수 있어서 타임아웃과 로그를 봐요.새 버전과 옛 버전 사이로 요청을 옮겨 보고, API 키를 Secret Manager에 연결하고, 로그 세 종류를 찾아 읽었어요.(2) (3)
③ CI/CD
10.22~23		코드를 합치면 서비스가 저절로 바뀌고, 합치기 전에 테스트가 깨진 코드를 막아요.일부러 깨뜨린 PR #9에서 테스트 9개 중 3개가 실패했고, main에 직접 push하는 건 GH006으로 거절됐어요.(4) (5)
④ Docker
10.26~27		실행 환경을 Dockerfile3이라는 파일에 적고, 시험한 이미지를 다시 만들지 않고 그대로 내보내요.이미지의 sha256 지문으로 «같은 이미지인가»를 확인했고, 롤백은 24초, 복구는 36초가 걸렸어요.(6) (7)
⑤ 배포 전략
10.28~29		새 버전을 요청 0%로 먼저 올려 두고, 준비가 됐는지 확인한 뒤에만 요청을 옮겨요.기본 확인 방식에서는 요청 389건 중 71건이 실패했고, /health 확인 방식에서는 283건 중 0건이 실패했어요.(8) (9)

이 표에서 눈에 띄는 건, 다섯 장면 모두 «말로는 안전하다고 하지만 숫자로 보여 주는» 방식이라는 점이에요. 실패한 테스트 개수, 이미지 지문, 실패한 요청 수가 전부 그래요.

내 예시 — 배포는 "성공"인데 요청 71건이 실패한 이야기

다섯 장면 중 발표에서 한 가지만 깊게 말한다면 이 실험이에요. 새 버전이 시작하는 데 30초가 걸리는 예제 앱을 일부러 배포했어요. 배포하는 동안 같은 주소에 0.2초마다 요청을 보내 실패한 건수를 세었어요.

Cloud Run에는 새 버전이 요청을 받을 준비가 됐는지 확인하는 스타트업 프로브4가 있어요. 기본 프로브는 «문이 열렸는가(포트가 열렸는가)»만 봐요. 그래서 앱이 아직 준비 중인데도 통과시켜요. 제가 /health 주소로 «진짜 준비됐는가»를 묻도록 바꾸자 결과가 달라졌어요.

실패를 없애는 대가도 있었어요. 배포가 약 19초에서 약 62초로, 약 43초 더 걸렸어요. 이 값도 한 번 잰 값이에요.

나쁜 선택 vs 좋은 선택 — 배포가 끝난 뒤 "괜찮은가"를 확인할 때

나쁜 선택좋은 선택
배포 화면이 초록색이니 괜찮다고 보고 확인을 끝내요. → 기본 프로브는 문만 열리면 통과시켜서, 요청 389건 중 71건이 실패했어요. 배포 명령은 «성공»이었어요. 배포하는 동안 같은 주소에 요청을 보내 실패 건수를 세요. → /health 프로브로 바꿔 요청 283건 중 0건 실패를 확인했어요.

확장 — "무중단"에 숫자를 붙이면 하루에 몇 번 배포할 수 있나

실험에서 실패한 시간이 약 29초(15:11:07~15:11:36)였는데, 이게 긴지 짧은지 기준이 없었어요. 그래서 가용성5 숫자를 기준으로 삼아 계산해 봤어요. 1년은 8,760시간이에요.

가용성 목표1년에 멈춰도 되는 시간계산
99.9%약 8.8시간8,760시간 × 0.1% = 8.76시간
99.99%약 53분8,760시간 × 0.01% ≈ 52.6분

여기에 제가 세운 가정을 더해요. «배포마다 29초 동안 모든 요청이 실패하고, 하루에 한 번 배포한다»고 해 볼게요. 이건 실제 측정이 아니에요. 실제로는 요청의 약 18%만 실패했으니 훨씬 보수적인 가정이에요.

배포 횟수1년에 잃는 시간99.9% 허용량(8.76시간)과 비교
하루 1번29초 × 365 = 10,585초 ≈ 2.9시간약 34%를 배포가 써요
하루 3번약 8.8시간허용량을 거의 다 써서, 다른 사고가 나면 바로 목표를 넘어요

제가 얻은 해석: 배포 한 번의 실패가 작아 보여도 횟수를 곱하면 가용성 예산을 크게 써요. 그래서 /health 프로브는 «배포가 43초 늦어지는 대가»로 배포가 많아져도 예산을 쓰지 않는 구조를 사 오는 일이에요. 이 해석은 계산에서 나온 추정이고, 실제 서비스의 가용성은 사용자가 몰리는 시간이나 다른 장애까지 포함해 따로 재야 해요.

활용 — 내 앱(도장판)에 세 질문을 대 보기

제 앱은 칸이 열리는 루틴 도장 앱이에요. 앞 글들에서 제가 스스로 «비어 있다»고 적어 둔 곳을 세 질문 아래에 모았어요. 오른쪽 열은 제안이고, 아직 하나도 하지 않았어요.

질문지금 있는 것비어 있는 곳다음 한 걸음(제안)
무엇이 나갔나화면 아래 커밋 7자리, 머지 기록GitHub Pages가 저장소 전체를 공개해서 tests/와 package.json도 보여요.공개 범위를 정리하고, 시험한 이미지의 지문을 배포 기록에 남기기
사용자는 괜찮았나테스트 9개, /health와 /version 확인/health와 /version만 봐서 앱의 답이 이상해졌는지는 몰라요.배포 뒤 대표 질문 몇 개를 보내 규칙을 어겼는지 세는 스크립트 만들기

표를 만들고 보니 비어 있는 칸이 «사용자는 괜찮았나»에 몰려 있었어요. 자동 도구는 «서비스가 떠 있는가»는 잘 보는데, «답이 맞는가»는 사람이 보고 있다는 뜻이에요.

이럴 때 의심하세요 — 배포가 끝났는데 안심이 안 될 때

이런 증상이 보이면먼저 열어 볼 자리확인 방법
배포가 초록색으로 끝났는데 사용자가 오류를 봤다고 해요. Cloud Run의 스타트업 프로브 설정(문만 보는 기본값인지, /health 주소인지) 배포하는 동안 0.2초마다 요청을 보내 실패 건수를 세요. 실패가 배포 직후 몇십 초에 몰려 있으면 프로브를 의심해요.
테스트는 전부 통과했는데 «이제 안전하다»고 생각하고 있어요. 테스트가 가짜 AI를 쓰는지, 실제 서비스에 요청을 보내는지 테스트는 «코드가 깨졌는가»를 막아 줘요. «사용자가 괜찮았는가»는 배포 중 요청 세기와 실제 답 확인이 따로 필요해요.

확인 범위와 해 보지 못한 것

  • 이 글의 숫자는 10번 글과, 거기에 적힌 4·5·6·7·8·9번 글의 측정값에서 옮겼어요. 이번에 글 본문을 다시 열어 확인한 건 각 글의 한 줄 정의와 각주 풀이예요.
  • 설계(1번)와 운영(2·3번)의 값은 본문을 다시 읽지 않았어요. 10번 글의 표에 적힌 내용만 옮겼어요.
  • 가용성 계산은 제가 세운 가정(배포마다 29초, 모든 요청 실패, 하루 1번 또는 3번)에서 나온 산술이에요. 실제 서비스에서 잰 값이 아니에요.
  • 활용 표의 «다음 한 걸음»은 제안이고 아직 하지 않았어요. 9번 글의 실험은 staging에서만 했고, production에서 승인과 전환까지 돌려 보지는 못했어요.
  • 발표 순서와 «장마다 1분»은 제 제안이에요. 실제 발표를 해 본 결과가 아니에요.
  1. Cloud Run — Google Cloud가 제공하는 서비스로, 컨테이너 이미지를 받아 실행하고 공개 주소를 붙여 줘요. Cloud Run에 소스를 배포한다는 것에서 처음 다뤘어요. ↩
  2. CI(지속적 통합) — 코드를 합칠 때마다 서버가 테스트를 자동으로 돌리는 것이에요. CI 테스트와 staging 환경에서 다뤘어요. ↩
  3. Dockerfile — 이미지를 어떻게 만들지 위에서 아래로 한 줄씩 적은 파일로, 실행 환경을 코드처럼 저장소에 남겨요. Dockerfile로 실행 환경 정하기에서 다뤘어요. ↩
  4. 스타트업 프로브(startup probe) — 새 인스턴스가 요청을 받을 준비가 됐는지 Cloud Run이 확인하는 검사예요. Cloud Run으로 무중단 배포하기에서 다뤘어요. ↩
  5. 가용성 — 서비스가 정상으로 답한 시간의 비율이에요. 로드밸런서로 무중단 배포 구성하기의 가용성 표에서 다뤘어요. ↩

"AI 서비스로 내놓기" 시리즈

(1) AI 기능을 서비스로 설계한다는 것 — 코딩 에이전트에게 맡기기 전에 정할 것 (2) Cloud Run에 소스를 배포한다는 것 — 코드 폴더 하나가 공개 주소가 되기까지 (3) 배포한 AI 서비스가 말없이 틀리는 순간 — 타임아웃, 인스턴스, 비용, 로그 (4) 코드를 머지하면 서비스가 저절로 바뀌는 길 — GitHub Actions로 자동 배포하기 (5) 합치기 전에 테스트하고 내보내기 전에 먼저 본다 — CI 테스트와 staging 환경 (6) 로컬에서는 되는데 서버에서만 안 되는 이유 — Dockerfile로 실행 환경 정하기 (7) 시험한 이미지와 내보낸 이미지가 같다는 증거 — 이미지를 한 번만 만들어 그대로 보내기 (8) 새 버전으로 바뀌는 몇 초 동안 — 로드밸런서로 무중단 배포 구성하기 (9) 배포하는 동안 사용자는 오류를 봤을까 — Cloud Run으로 무중단 배포하기 (10) 아홉 개 노드를 한 번에 — AI 서비스를 프로덕션에 올리기까지 돌아보기

(11) 발표용 한 장 요약 — 코드를 사용자에게 내보내는 아홉 날을 다섯 장으로 (이 글)
