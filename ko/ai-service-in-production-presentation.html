하는 일 코드를 짜기 전에, 누구에게 어디서 어떻게 쓰게 할지 정해서 문서(PRD) 한 장으로 남겨요.

직접 확인한 것 코드 없이 프로토타입(시제품)으로 먼저 확인한 뒤, 구조 그림과 PRD 한 장으로 정리했어요.

자세한 글 노드 63 · AI 기능을 서비스로 설계한다는 것

Cloud Run 노드 64·65 · 10.20~21

하는 일 Cloud Run은 코드 폴더를 올리면 공개 주소를 붙여 주는 구글 서비스예요. 서버가 정상이라고 해도 사용자가 답을 못 받을 수 있어서, 타임아웃과 로그를 봐요.

직접 확인한 것 새 버전과 옛 버전 사이로 요청을 옮겨 보고, API 키를 Secret Manager에 연결하고, 로그 세 종류를 찾아 읽었어요.

CI/CD 노드 66·67 · 10.22~23

하는 일 CI는 합쳐 달라는 요청(PR)이 올라올 때마다 서버가 테스트를 자동으로 돌려 깨진 코드를 찾아 줘요. CD는 코드가 main에 합쳐지면 새 버전을 서비스에 자동으로 올려요. 코드를 합치는 건 사람이 해요.

직접 확인한 것 내 앱(도장판)에서 일부러 깨뜨린 변경(PR #9)은 테스트 9개 중 3개가 실패했어요. 테스트가 실패하면 합치기를 막는 규칙(브랜치 보호)은 연습용 템플릿 저장소에서만 걸어 봤고, 거기서 main에 직접 올리는 것(push)이 GH006으로 거절됐어요. 도장판 main에는 이 규칙이 없어요.

자세한 글 노드 66 · 코드를 머지하면 서비스가 저절로 바뀌는 길 · 노드 67 · 합치기 전에 테스트하고 내보내기 전에 먼저 본다

Docker 노드 68·69 · 10.26~27

하는 일 실행 환경을 적은 설명서(Dockerfile)로 이미지(코드와 실행 환경을 한 꾸러미로 포장한 것)를 만들고, 시험한 이미지를 다시 만들지 않고 그대로 내보내요. 설계 문서와는 달라요.

직접 확인한 것 이미지의 sha256 지문으로 «같은 이미지인가»를 확인했고, 롤백은 24초, 복구는 36초가 걸렸어요.

자세한 글 노드 68 · 로컬에서는 되는데 서버에서만 안 되는 이유 · 노드 69 · 시험한 이미지와 내보낸 이미지가 같다는 증거

배포 전략 노드 70·71 · 10.28~29

하는 일 새 버전을 요청 0%로 먼저 올려 두고, 준비가 됐는지 확인한 뒤에만 요청을 옮겨요.

직접 확인한 것 기본 확인 방식에서는 요청 389건 중 71건이 실패했고, /health 확인 방식에서는 283건 중 0건이 실패했어요. (아래 «내 예시»)

자세한 글 아홉 개 노드를 한 번에 — AI 서비스를 프로덕션에 올리기까지 돌아보기

내 예시 — 배포는 "성공"인데 요청 71건이 실패한 이야기

새 버전이 시작하는 데 30초가 걸리는 예제 앱을 일부러 배포하고, 배포하는 동안 같은 주소에 0.2초마다 요청을 보내 실패를 셌어요.

확장 — "무중단"에 숫자를 붙이면 하루에 몇 번 배포할 수 있나

실험에서 실패한 시간이 약 29초(15:11:07~15:11:36)였는데, 이게 긴지 짧은지 기준이 없었어요. 그래서 가용성 (정상으로 답한 시간의 비율) 숫자를 기준으로 삼아 계산해 봤어요. 1년은 8,760시간이에요.

가용성 목표1년에 멈춰도 되는 시간계산
99.9%약 8.8시간8,760시간 × 0.1% = 8.76시간
99.99%약 53분8,760시간 × 0.01% ≈ 52.6분

여기에 제가 세운 가정을 더해요. «배포마다 29초 동안 모든 요청이 실패하고, 하루에 한 번 배포한다»고 해 볼게요. 이건 실제 측정이 아니라 단순하게 만든 가정이에요. 실제 측정에서는 전체 389건 중 71건(약 18%)이 실패했어요.

제가 얻은 해석: 배포 한 번의 실패가 작아 보여도 횟수를 곱하면 가용성 예산을 크게 써요. 그래서 /health 프로브는 «배포가 43초 늦어지는 대가»로 실패를 줄이는 선택이에요. 이번 측정에서는 실패가 0건이었어요.

활용 — 내 앱(도장판)에 세 질문을 대 보기

제 앱 도장판은 도장을 모을수록 칸이 하나씩 열리는 루틴 앱이에요. 세 질문을 대 보면, 이미 갖춘 것과 비어 있는 것이 보여요. «다음에 할 일»은 아직 하지 않았어요.

무엇이 나갔나사용자는 괜찮았나되돌릴 수 있나
✔ 지금은화면 아래에 코드 버전 번호(커밋) 일곱 자리가 보여요.칸이 열리는 일정을 시험하는 테스트 9개가 있고, 서비스가 살아 있는지(/health) 확인해요.되돌리는 요청(Revert PR)과 버튼 한 번 롤백이 있어요. 롤백은 24초 걸렸어요.
✖ 비어 있는 곳GitHub Pages가 저장소 전체를 공개해서 시험 파일(tests 폴더)까지 보여요.살아 있다는 것까지만 알아요. 도우미가 엉뚱한 답을 하는지는 사람이 물어봐야 알아요.main 브랜치(서비스가 되는 코드 줄기)에 보호 규칙이 없어서, 테스트가 실패해도 합칠 수 있어요.
➜ 다음에 할 일공개할 파일만 남기도록 공개 범위를 정리해요.배포 뒤 대표 질문 몇 개를 자동으로 보내, 규칙을 어긴 횟수를 세요.테스트를 통과해야만 합치도록 main에 필수 검사를 걸어요.

정리하면 비어 있는 곳은 «사용자는 괜찮았나»에 몰려 있어요. 서비스가 떠 있는지는 기계가 확인하지만, 답이 맞는지는 아직 사람이 확인해요. 가장 먼저 자동화할 곳이에요.

알아 둘 점

  • 실험값은 모두 한 번씩 잰 값이고, 시험용(staging) 서비스에서만 해 봤어요. 실제 서비스(production)에서 승인과 전환까지 돌려 보지는 못했어요.
  • 가용성 계산은 제가 세운 가정(배포마다 29초, 모든 요청 실패, 하루 1번 또는 3번)에서 나온 산술이에요. 실제 서비스의 가용성은 다른 장애까지 포함해 따로 재야 해요.
