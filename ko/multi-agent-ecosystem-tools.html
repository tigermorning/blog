컨텍스트가 끊기는 문제 — Agent Teams

Claude Code의 Agent Teams는 첫 문제를 겨냥한 실험적 기능이에요. 서브에이전트는 결과를 리드에게 돌려주고 끝나지만, 팀원(teammate)은 각자 컨텍스트 창을 가진 독립 세션으로서 서로에게 직접 메시지를 보내고, 공유 작업 목록에서 다음 일을 스스로 가져가요. 두 팀원이 같은 작업을 동시에 잡지 않도록 파일 잠금이 막아 주고요. 공식 문서가 드는 사례 하나는 원인이 불분명한 버그를 두고 팀원 다섯이 각자 다른 가설을 맡아 서로 반박하게 하는 조사예요. 한 에이전트가 첫 가설에 묶이는 일을 팀원 사이의 반박으로 푸는 발상이죠. settings.json(Claude Code의 설정 파일, 프로젝트의 .claude/ 폴더나 홈 폴더의 ~/.claude/에 있어요)의 env 항목에 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS를 "1"로 넣어 켜요. env는 환경 변수, 곧 프로그램이 시작할 때 읽는 "이름=값" 설정이에요.

대가는 셋이에요. 팀원 하나가 곧 Claude 세션 하나라 토큰이 팀원 수에 비례해 늘고, 한 세션에 팀은 하나이며 팀원이 다시 팀을 만들 수 없고, 대화형 세션에서만 팀원이 만들어져요. 3편의 arms.py처럼 SDK(코드에서 서비스를 부르는 개발용 도구 모음)로 돌리는 실행에서는 켜 두어도 서브에이전트로 돌아가니 지금 실험에 바로 끼울 수는 없어요. 이 도구를 붙이면 바뀌는 조건은 다음 행동을 정하는 주체예요. 리드 하나가 아니라 팀원들이 함께 정하니, C와 나란히 놓으려면 같은 문제로 기준선을 다시 세워야 해요.

locator를 파일 하나로 옮기기 — 서브에이전트 정의 파일

3편의 locator는 arms.py 안에서 agents={"locator": ...}로 파이썬 코드가 정의했어요. 같은 역할을 터미널에서 쓰는 코딩 에이전트에는 마크다운 파일 하나로 정의할 수 있고, Agent Teams의 팀원도 이 정의 파일에서 띄워요. 그래서 역할을 파일로 적어 두면 서브에이전트로도 팀원으로도 같은 정의를 써요. (파일로 규칙을 외워 두는 발상 자체는 스킬과 규칙 파일에서 봤어요.)

Claude Code의 서브에이전트는 프로젝트의 .claude/agents/ 폴더에 두는 마크다운이에요. 프로젝트 폴더에 두면 저장소와 함께 버전 관리되어 팀이 같은 정의를 쓰고, ~/.claude/agents/(~/는 내 홈 폴더)에 두면 내 모든 프로젝트에서 써요. 파일 머리의 YAML(설정을 "이름: 값" 꼴로 적는 형식)에서 name과 description은 필수이고, tools로 도구를 제한하고, model과 maxTurns로 모델과 턴 예산을 정해요. 머리 아래 본문이 그 에이전트의 시스템 프롬프트가 돼요.

---
name: locator
description: 버그 보고를 받아 원인이 있는 파일 경로·함수 이름·진단을 구조화된 보고로 남긴다. 파일을 고치지 않는다.
tools: Read, Grep, Glob
model: haiku
maxTurns: 12
---

당신은 읽기 전용 탐색 담당입니다. 저장소를 읽고 검색만 하며, 결과는
파일 경로 · 함수 또는 클래스 이름 · 한 문단 진단의 세 항목으로 보고합니다.

tools에 Read·Grep·Glob만 적으면 파일을 고치는 도구는 빠지니, 3편에서 allowed_tools로 건 읽기 전용 제한과 같은 뜻이에요. Claude는 요청과 description을 견줘 이 서브에이전트에 맡길지 스스로 정하고, 반드시 맡기려면 프롬프트에 @agent-locator라고 불러요. 파일을 저장하면 몇 초 안에 반영되지만, agents 폴더를 처음 만들었을 때는 세션을 다시 시작해야 해요.

OpenCode는 오픈소스 코딩 에이전트 CLI예요. 정의 파일은 .opencode/agents/ 또는 ~/.config/opencode/agents/에 두고, 파일 이름이 곧 에이전트 이름이에요. mode가 primary면 Tab 키로 바꿔 가며 직접 대화하는 주 에이전트, subagent면 주 에이전트가 필요할 때 부르거나 사용자가 @이름으로 부르는 보조 에이전트예요. 도구 제한은 permission으로 선언해요.

---
description: 버그 보고를 받아 원인이 있는 파일 경로·함수 이름·진단을 구조화된 보고로 남긴다. 파일을 고치지 않는다.
mode: subagent
model: anthropic/claude-haiku-4-5
permission:
  edit: deny
  bash: deny
---
당신은 읽기 전용 탐색 담당입니다. 저장소를 읽고 검색만 하며, 결과는
파일 경로 · 함수 또는 클래스 이름 · 한 문단 진단의 세 항목으로 보고합니다.

이걸 locator.md로 저장하면 @locator로 부를 수 있어요. 모델은 "공급자/모델 ID" 꼴로 적고, ID는 설치한 OpenCode의 모델 목록에서 확인해 맞춰요. OpenCode에는 읽기 전용 탐색용 explore 서브에이전트가 이미 들어 있어서, 보고 포맷을 정해 줄 필요가 없다면 그냥 그걸 불러도 돼요.

재현이 안 되는 문제 — Workflows

3편에서 locator 다음 fixer를 부르는 순서는 사람이 파이썬으로 적었어요. Claude Code의 Workflows는 그 파이썬을 Claude가 자바스크립트로 쓰게 하고, 실행을 맡는 런타임이 스크립트를 백그라운드에서 돌려요. 반복과 분기는 스크립트에 적히고 중간 결과는 스크립트 변수에 머물며, Claude의 컨텍스트에는 최종 결과만 들어와요. 공식 문서는 서브에이전트·스킬·팀·워크플로를 "다음에 실행할 것을 누가 정하는가"로 나눠요. A·B·C를 가른 물음과 같죠. 워크플로 실행(B)을 수십 개 에이전트 규모로 키운 게 이 제품이에요.

재현 장치가 눈에 띄어요. 실행마다 스크립트와 각 에이전트의 결과가 세션 디렉터리에 남고, 같은 세션에서 다시 띄우면 이미 끝난 에이전트는 저장된 결과를 돌려주고 프롬프트가 달라진 에이전트부터 다시 실행해요. 스크립트 안에서 현재 시각이나 난수를 쓰면 오류를 내는데, 다시 돌렸을 때 같은 호출이 같은 순서로 반복되게 하려는 거예요. 3편의 러너가 result.json이 있으면 건너뛴 것과 같은 발상을 런타임이 강제하는 셈이에요. 대가는 실행 중에 사람이 끼어들 수 없다는 점이에요. 단계 사이에 승인이 필요하면 워크플로를 단계마다 따로 나눠야 해요. 한 실행이 에이전트 25개나 150만 토큰을 넘으면 경고가 뜨지만 알림일 뿐 멈추지는 않아요. 바뀌는 조건은 역시 다음 행동의 주체이고, B와 같은 층이라 B의 파이썬을 이 스크립트로 옮겨 같은 문제를 돌리면 B와 바로 견줄 수 있어요.

모델을 나눌 수 없는 문제 — oh-my-claudecode

1편에서 Anthropic의 멀티 에이전트 시스템이 채팅의 약 15배 토큰을 썼다는 수치를 봤어요 [벤더]. 워커가 늘수록 비용이 따라 늘지만, 워커마다 필요한 능력은 달라요. oh-my-claudecode는 Claude Code 위에서 도는 커뮤니티 오케스트레이션 프레임워크로(GitHub 스타 38,000 이상, 커뮤니티 자체 수치), 겨냥하는 지점이 역할별 모델 배분이에요. 단순 조회에는 Haiku, 표준 구현에는 Sonnet, 설계와 깊은 분석에는 Opus를 고르는 3단 배분이 기본이고, 그 위에 에이전트마다 어느 모델을 붙일지 적어 두는 표가 따로 있어요. 실행 모드 중 ralph는 검증이 통과할 때까지 수정을 반복해요. 4편에서 judge.py가 "검증_성실성"으로 물었던 것, 곧 끝났다고 말하기 전에 실제로 확인했는가를 도구가 강제하는 장치예요.

대가는 비교가 어려워지는 것이에요. 프레임워크가 자체 에이전트 정의와 프롬프트를 끼워 넣기 때문에 결과 차이가 모델 배분에서 왔는지 프레임워크의 프롬프트에서 왔는지 가르기 어렵고, 판이 빠르게 바뀌는 커뮤니티 프로젝트라 문서와 실제 동작이 다를 수 있어요. 바뀌는 조건은 모델이에요. 4편의 고정 조건 표에 "역할별 모델" 열을 추가하고, 그 열이 같은 실행끼리만 비용을 견줘야 해요.

상태가 안 보이는 문제 — herdr

에이전트가 셋을 넘어가면 어느 창이 일하고 있고 어느 창이 승인을 기다리며 멈춰 있는지 눈으로 좇기 어렵고, 노트북 터미널을 닫으면 돌아가던 작업이 함께 사라져요. herdr는 이 문제를 겨냥한 오픈소스 런타임이에요. 백그라운드 서버가 에이전트 CLI의 터미널을 소유하기 때문에 터미널을 닫거나 컴퓨터를 다시 켜도 작업이 이어지고, 다른 터미널이나 원격 접속으로 다시 붙을 수 있어요. 각 창에 작업 중(working)·대기(blocked)·유휴(idle) 세 상태가 표시되어 멈춘 에이전트를 바로 찾고, Claude Code뿐 아니라 다른 회사의 코딩 에이전트 CLI 20여 종을 같은 화면에 놓을 수 있어요. 한 에이전트가 다른 에이전트의 창을 띄운 뒤 그쪽이 입력을 기다리며 멈출 때까지 기다리는 동작도 지원하고요.

herdr가 푸는 건 관측과 보존이지 결과 판정이 아니에요. 창이 유휴로 바뀌었다는 표시는 실행이 끝났다는 뜻일 뿐 테스트가 통과했다는 뜻이 아니니, result.json과 judge.py 층은 그대로 필요해요. 이 도구는 비교 조건을 바꾸지 않아요. 전사로 사후에 읽던 실행 상태를 실행 중에 화면으로 보게 해 주는 층이라, 기준선을 다시 세우지 않고 지금 실험 위에 그대로 얹을 수 있어요.

Agent Teams와 Workflows는 "다음 행동을 누가 정하는가"를, oh-my-claudecode는 "어느 모델이 그 행동을 하는가"를, herdr는 "그 행동을 어디서 지켜보는가"를 바꿔요. 2편 끝에서 잠깐 언급한 A2A는 이 격자 바깥에서 소유자가 다른 에이전트를 잇는 층이고요. 조율이나 모델 층이 바뀌면 기준선을 다시 세워야 하지만, 비교하는 방법은 그대로예요. 조건을 고정하고, 기록을 남기고, 같은 방식으로 읽는 일은 도구가 바뀌어도 바뀌지 않아요. 이 도구들 중 하나를 붙일 때도 4편의 채택·축소·폐기를 같은 순서로 판정해요.

지금 내 작업에서 가장 아픈 문제 하나를 위 표의 왼쪽 열에서 골라 보세요. 그 도구를 붙였을 때 4편의 "고정·조작·측정" 표에서 어느 칸이 바뀌는지 한 줄로 적고, 기준선을 다시 세워야 하는지(조율·모델 층) 아니면 그대로 얹어도 되는지(관측 층) 표시해요. 도구 이름에 끌려 붙이는 게 아니라, 문제에서 출발해 조건 변화를 먼저 적는 습관이 이 시리즈에서 남기고 싶은 전부예요.

"멀티 에이전트, 나눌까 말까" 시리즈

(1) 나누면 좋아질까 — 멀티 에이전트의 득실과 판정표 (2) 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업 (3) 같은 버그를 세 방식으로 — 기준선·워크플로·오케스트레이션 실행 (4) 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정
