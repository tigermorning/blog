1편에서 일곱 가지 병목 질문과 관찰 카드를 봤으니, 이번엔 그 가운데 앞 두 가지 — 행동 포맷과 컨텍스트 관리 — 를 실제 연구와 도구 사례로 깊이 들어가 봐요. 두 기능 다 "숫자 하나로 우열을 가른다"기보다, 어떤 조건에서 얼마나 차이가 났는지를 조건과 함께 읽는 게 핵심이었어요.

행동 포맷 — 자유 문장 대신 좁은 문법

모델이 수정할 내용을 정확히 알고 있어도, 그걸 표현하는 방식이 애매하면 작업은 실패해요. "이 함수 고쳐줘"라는 자유 문장은 대상 경계·기존 내용·교체 내용을 모델이 다시 추정해야 하지만, 찾을 내용과 바꿀 내용을 묶은 편집 블록이나 실행 가능한 코드라는 문법은 다음 행동의 형태를 미리 좁혀 놔요.

이게 실제로 차이를 만드는지 세 사례로 봤어요.

  • SWE-agent는 프린스턴 연구진이 만든 연구용 코딩 에이전트예요. 모델 전용 인터페이스(ACI)가 일반 셸보다 나을 수 있다는 가설을 SWE-bench Lite에서 검증했는데, 기준 해결률 18.0%가 편집 기능을 빼면 10.3%로 떨어졌어요. 다만 이건 이 벤치마크·이 구현의 결과라, 모든 모델·모든 도구에 같은 폭의 차이가 난다고 일반화할 순 없어요. (Yang et al., NeurIPS 2024, arXiv:2405.15793)
  • CodeAct는 행동을 JSON 도구 호출 대신 실행 가능한 파이썬 코드 한 덩어리로 쓰게 하는 연구예요. 여러 파일 줄 수를 세는 일을 도구 호출 방식은 열기·세기를 여러 번 왕복하지만, 코드 방식은 for 루프 하나로 끝내요. 17개 LLM에서 기존 형식 대비 최대 +20%p를 보고했지만, 세션을 복원하는 기능의 효과까지 잰 건 아니에요. (Wang et al., ICML 2024, arXiv:2402.01030)
  • Aider는 터미널에서 파일을 편집하고 변경을 자동으로 git 커밋해 주는 오픈소스 도구예요. 파일 전체를 다시 쓰게 하는 whole 포맷과, 바꿀 부분만 search-replace 블록으로 적게 하는 diff 포맷 둘을 제공해요. 자체 벤치마크(133개 Exercism 과업, 실패 뒤 테스트 오류 앞 50줄을 재투입)에서 GPT-3.5는 whole 46%, diff 30%로 갈렸어요.

그런데 여기서 재밌는 반전이 있었어요. 같은 벤치마크에서 GPT-4는 whole과 diff의 차이가 거의 없었고, Aider는 그래도 비용 때문에 diff를 유지한다고 밝혔어요. 즉 포맷이 항상 결과를 가르진 않아요 — 모델이 포맷 차이를 충분히 흡수하는 조건, 변경 범위가 아주 작은 조건에서는 다른 실패 원인이 더 클 수 있어요. 그래서 "이 포맷이 정답"이라고 외우기보다, 내 모델·내 과업에서 대상 파일을 처음 맞힌 횟수와 테스트 통과 여부를 직접 재보는 게 맞는 순서였어요.

컨텍스트 관리 — 넓은 창보다 고르는 기준

문맥 창이 크면 한 번에 읽을 수 있는 기록은 늘어나요. 그런데 창이 넓다는 사실만으로 지금 과업에 필요한 정보가 저절로 눈앞에 놓이진 않아요. 긴 실행에서는 명령 결과·오류 메시지·중간 판단이 계속 쌓이고, 처음엔 중요했던 단서도 새 관측에 밀려 찾기 어려워져요. 컨텍스트 관리는 정해진 토큰 예산 안에 무엇을 넣고, 빠진 정보는 어디서 다시 찾을지를 정하는 일이에요.

SWE-agent 연구진은 최근 관측 다섯 개만 자세히 남기고 과거는 축약하는 조건과, 전체 이력을 다 남기는 조건을 비교했어요. 결과는 18.0% 대 15.0% — 최근 다섯 개 조건이 3.0%p 높았어요. 같은 과업·같은 모델에서 관측을 고르는 방식도 결과를 바꾼다는 뜻인데, 다섯 개가 모든 과업에서 항상 최적이라는 의미는 아니에요.

저장소 전체를 넣는 대신 구조부터 고르는 방법도 있어요. Aider의 repo map이 대표적이에요. 어떤 클래스·함수가 어디서 정의되고 어디서 참조되는지를 목록으로 만들고, 정의·참조가 많을수록 중요하다고 순위를 매겨 기본 1천 토큰 예산 안에서 골라 넣어요. 모델은 파일 전체가 아니라 이 지도를 보고 필요한 파일만 편집 요청에 첨부해요. RepoCoder라는 연구도 비슷한 문제를 다른 각도에서 풀었는데, 검색으로 찾은 코드 조각만 쓰기보다 그 조각의 이웃 문맥(같은 파일의 앞뒤 정의)을 함께 읽을 때 더 정확했다고 해요.

대화 자체를 나누는 방법도 있어요. Claude Code는 이전에 다룬 서브에이전트(작업을 나눠 맡는 보조 AI)가 좁은 문맥에서 조사를 맡고 결과만 메인 대화로 돌려줘요. opencode는 에이전트별로 대화 문맥과 실행 단계를 아예 분리하고, 에이전트별 steps 상한을 둬서 한 대화가 끝없이 관측을 쌓지 않게 해요.

여기서 하나 짚을 반전이 있어요. "문맥은 무조건 줄이는 게 좋다"고 단정하면 안 돼요. RAG와 long-context를 비교한 연구는, 예산이 충분할 때는 long-context(원문을 그대로 다 넣는 방식)가 평균 성능에서 일관되게 RAG보다 높았고, RAG의 장점은 오히려 비용이었다고 보고했어요. (Li et al., EMNLP 2024 Industry, arXiv:2407.16833) 그러니 문맥이 넘칠 때 무조건 먼저 버릴 게 아니라, 이 과업이 원문 전체가 필요한 과업인지 비용 때문에 압축이 필요한 과업인지를 같은 자리에서 판단해야 해요.

이번 두 기능은 결국 "지금 이 실행에서 무엇을 하고 무엇을 봤는지"를 다루는 기능이었어요. 그런데 이번 실행에서 버린 정보 중에는 다음 과업에서 다시 쓸 경험도 섞여 있어요. 다음 편에서는 그 경험을 어떻게 자산으로 남기고, 실패는 또 어떻게 다음 시도에 반영하는지를 봐요.
