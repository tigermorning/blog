행동 포맷 — 자유 문장 대신 좁은 문법

모델(AI 프로그램)이 무엇을 고칠지 정확히 알고 있어도, 그걸 표현하는 방식이 애매하면 작업은 실패해요. 두 가지 부탁 방식을 나란히 놓아 볼게요.

나쁜 선택좋은 선택
"이 함수 고쳐줘"라는 자유 문장으로 부탁했어요 → 대상 경계·기존 내용·교체 내용을 모델이 다시 추정해야 해요. 찾을 내용과 바꿀 내용을 묶은 편집 블록(또는 실행 가능한 코드)으로 부탁했어요 → 다음 행동의 형태가 미리 좁혀져요.

이게 실제로 차이를 만드는지 세 사례로 봤어요.

  • SWE-agent는 프린스턴 연구진이 만든 연구용 코딩 에이전트예요. 모델 전용 인터페이스(ACI)1가 일반 셸보다 나을 수 있다는 가설을 SWE-bench Lite2에서 확인했어요. 기준 해결률은 18.0%였는데, 편집 기능을 빼니 10.3%로 떨어졌어요. 벤치마크(같은 문제로 점수를 매기는 시험)와 구현이 이 조건일 때의 결과예요. 모든 모델과 도구에서 같은 폭으로 차이가 난다고 말할 수는 없어요. (Yang et al., NeurIPS 2024, arXiv:2405.15793)
  • CodeAct는 행동을 JSON3 도구 호출 대신 실행 가능한 파이썬 코드 한 덩어리로 쓰게 하는 연구예요. 예를 들어 여러 파일의 줄 수를 세는 일을 생각해 봐요. 도구 호출 방식은 "열기, 세기"를 여러 번 주고받아요. 코드 방식은 for 루프(같은 일을 되풀이하는 코드) 하나로 끝내요. 17개 LLM(거대 언어 모델)에서 기존 형식보다 최대 +20%p(퍼센트 점수끼리의 차이)를 보고했어요. 하지만 세션(대화 한 판)을 복원하는 기능의 효과까지 잰 건 아니에요. (Wang et al., ICML 2024, arXiv:2402.01030)
  • Aider는 터미널에서 파일을 편집하고 변경을 자동으로 git 커밋(변경 내용을 기록으로 남기는 일)해 주는 오픈소스(만든 코드를 누구나 볼 수 있게 공개한) 도구예요. 편집 포맷이 둘 있어요. whole은 파일 전체를 다시 쓰게 해요. diff는 바꿀 부분만 search-replace 블록(찾을 내용과 바꿀 내용을 짝지은 덩어리)으로 적게 해요. 자체 벤치마크(133개 Exercism 과업, 실패 뒤 테스트 오류 앞 50줄을 재투입)에서 GPT-3.5는 whole 46%, diff 30%로 갈렸어요.

그런데 여기서 반전이 있었어요. 같은 벤치마크에서 GPT-4는 whole과 diff의 차이가 거의 없었어요. Aider는 그래도 비용 때문에 diff를 유지한다고 밝혔어요. 그러니 포맷이 항상 결과를 가르지는 않아요. 모델이 포맷 차이를 충분히 받아넘기는 조건이 있어요. 바꾸는 범위가 아주 작은 조건에서는 다른 실패 원인이 더 클 수도 있어요. 그래서 "이 포맷이 정답"이라고 외우지 마세요. 내 모델과 내 과업에서 대상 파일을 처음 맞힌 횟수와 테스트 통과 여부를 직접 재 보는 게 맞는 순서였어요.

컨텍스트 관리 — 넓은 창보다 고르는 기준

문맥 창이 크면 한 번에 읽을 수 있는 기록은 늘어나요. 하지만 창이 넓다고 지금 필요한 정보가 저절로 눈앞에 놓이지는 않아요. 긴 실행에서는 명령 결과, 오류 메시지, 중간 판단이 계속 쌓여요. 처음엔 중요했던 단서도 새 관측(도구가 돌려준 결과)에 밀려 찾기 어려워져요.

컨텍스트 관리는 정해진 토큰4 예산 안에 무엇을 넣고, 빠진 정보는 어디서 다시 찾을지를 정하는 일이에요. 그 방법으로 세 가지를 봤어요.

  • 최근 관측만 자세히 남기기. SWE-agent 연구진은 최근 관측(1편에서 본, 도구가 돌려준 결과) 다섯 개만 자세히 남기고 과거는 줄이는 조건과, 전체 이력을 다 남기는 조건을 비교했어요. 결과는 18.0% 대 15.0%로, 최근 다섯 개 조건이 3.0%p 높았어요. 같은 과업과 같은 모델에서도 관측을 고르는 방식이 결과를 바꾼다는 뜻이에요. 다섯 개가 모든 과업에서 최적이라는 뜻은 아니에요.
  • 구조부터 고르기. 저장소(프로젝트 파일 묶음) 전체를 넣는 대신 Aider의 repo map을 써요. 먼저 어떤 클래스·함수가 어디서 정의되고 어디서 쓰이는지를 목록으로 만들어요. 많이 쓰일수록 중요하다고 순위를 매겨요. 그중 기본 1천 토큰 예산 안에서 골라 넣어요. 모델은 파일 전체가 아니라 이 지도를 보고, 필요한 파일만 편집 요청에 붙여요. RepoCoder라는 연구도 비슷한 문제를 풀었어요. 검색으로 찾은 코드 조각만 쓰기보다, 그 조각의 이웃 문맥(같은 파일의 앞뒤 정의)을 함께 읽을 때 더 정확했다고 해요.
  • 대화 자체를 나누기. Claude Code는 이전에 다룬 서브에이전트(작업을 나눠 맡는 보조 AI)가 좁은 문맥에서 조사를 맡고 결과만 메인 대화로 돌려줘요. opencode는 에이전트별로 대화 문맥과 실행 단계를 아예 분리하고, 에이전트별 steps 상한(한 대화에서 밟을 단계 수의 한도)을 둬서 한 대화가 끝없이 관측을 쌓지 않게 해요.

대표 행동조사를 맡긴 서브에이전트 결과로 메인 대화가 다음 행동을 정함에이전트별 steps 상한으로 관측이 무한히 쌓이지 않게 함

여기서 짚을 반전이 하나 더 있어요. "문맥은 무조건 줄이는 게 좋다"고 단정하면 안 돼요. RAG(필요한 문서 조각만 찾아 LLM에게 넣어 주는 방법)와 long-context를 비교한 연구가 있어요. 예산이 충분할 때는 long-context(원문을 그대로 다 넣는 방식)가 평균 성능에서 일관되게 RAG보다 높았어요. RAG의 장점은 오히려 비용이었다고 보고했어요. (Li et al., EMNLP 2024 Industry, arXiv:2407.16833)

그러니 문맥이 넘칠 때 무조건 먼저 버리지 마세요. 이 과업이 원문 전체가 필요한 과업인지, 비용 때문에 줄여야 하는 과업인지를 같은 자리에서 따져요.

이럴 때 의심하세요 — AI가 엉뚱한 곳을 고치거나 문맥을 줄인 뒤 헤맬 때

행동 포맷과 문맥의 문제는 "모델이 멍청하다"는 느낌으로 먼저 와요. 그래서 모델을 바꾸기 전에, AI가 어떤 형식으로 고치라는 요청을 받았는지와 그때 무엇을 보고 있었는지부터 봐요. 둘 다 바뀐 파일과 대화 기록에 남아 있어요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
"이 함수 고쳐 줘"라고 했는데 바뀐 곳이 비슷하게 생긴 다른 함수예요. 또는 한 줄만 바꾸면 될 파일이 통째로 다시 쓰여 있어요 모델 성능보다 방금 바뀐 내용이에요. 터미널에 git diff를 넣으면 마지막 커밋 뒤로 줄마다 무엇이 빠지고 들어갔는지 나와요. 내 요청 문장이 대상을 하나로 짚었는지도 같이 봐요 요청에 지금 있는 줄을 그대로 붙이고 "이 줄들을 이렇게 바꿔 줘"로 짝지어 다시 부탁해요. 그렇게 해서 제자리를 맞히면 모델보다 형식 문제였어요. 다만 붙인 줄이 파일 내용과 한 글자라도 다르면 짝지은 요청도 엇나갈 수 있어요
더 싼 모델이나 로컬 모델로 바꾼 뒤부터 수정이 적용되지 않았다는 메시지나 엉뚱한 편집이 잦아져요. 같은 요청이 큰 모델에서는 됐어요 쓰는 도구의 편집 형식 설정이에요. Aider라면 --edit-format으로 파일 전체 다시 쓰기(whole)와 바꿀 부분만 적기(diff)를 고를 수 있어요. 어느 형식이 잘 맞는지는 모델마다 달라요 작은 수정 과업 몇 개를 두 형식으로 똑같이 돌려, 처음에 맞는 파일을 고쳤는지와 테스트가 통과했는지를 세어 봐요. Aider 벤치마크에서 GPT-3.5는 두 형식이 46% 대 30%로 갈렸지만 GPT-4는 거의 같았어요. 남의 표보다 내 모델로 잰 숫자로 골라요
토큰을 아끼려고 파일 일부나 요약만 넘겼더니, 답이 그 밖의 코드와 안 맞아요. 이미 있는 함수를 새로 만들거나 없는 이름을 불러요 모델에게 실제로 넘어간 내용이에요. 내가 붙여넣은 조각, 또는 조사를 맡긴 서브에이전트가 돌려준 요약이요. 요약에는 결론만 있고 근거가 된 파일 이름은 빠져 있기 쉬워요 같은 질문에 관련 파일 전체와, 그 함수를 부르는 이웃 파일을 한 번 같이 넣어 봐요. 그때 맞게 답하면 모델보다 덜어 낸 문맥 탓이에요. 원문을 다 넣으면 비용이 늘어서, 계속 그렇게 할지는 이 과업에 원문이 꼭 필요한지 보고 정해요

긴 작업에서 앞서 정한 조건을 잊는 증상은 토큰 글의 이 줄, 같은 명령을 끝없이 되풀이하는 증상은 같은 글의 이 줄에서 확인해요.

엉뚱한 곳이 고쳐졌다면 곧바로 다시 고치게 하지 말고, 바뀐 자리와 AI가 읽은 범위부터 펼쳐 보게 해요. 형식이 문제였는지 문맥이 문제였는지가 거기서 갈려요. 아래 글은 직접 해 보는 요청문이에요. 방금 수정을 끝낸 그 대화에 그대로 붙여 넣으면, AI가 바뀐 곳과 읽은 파일을 정리해 보여 줘요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 방금 수정을 끝낸 그 대화에서

방금 네가 한 수정을 내가 확인할 수 있게 보여 줘. 아직 되돌리거나 새로 고치지는 마.
1. 바뀐 파일 이름과 줄 번호, 줄마다 무엇이 바뀌었는지 (git diff 기준)
2. 내가 요청한 대상(함수·줄)과 실제로 바뀐 곳이 같은지. 요청 밖에서 바뀐 줄이 있다면 따로 표시
3. 수정하기 전에 네가 읽은 파일 목록과, 파일마다 전체를 읽었는지 일부만 읽었는지(요약만 받았다면 그렇다고)

이번 두 기능은 결국 "지금 이 실행에서 무엇을 하고 무엇을 봤는지"를 다루는 기능이었어요. 그런데 이번 실행에서 버린 정보 중에는 다음 과업에서 다시 쓸 경험도 섞여 있어요. 다음 편에서는 그 경험을 어떻게 자산으로 남기고, 실패는 또 어떻게 다음 시도에 반영하는지를 봐요.

  1. ACI — 모델이 파일을 찾고 고칠 때 쓰는 전용 명령 모음과 그 결과 화면을 말해요. ↩
  2. SWE-bench Lite — 실제 프로그램의 고장 사례(이슈)를 AI에게 풀게 하고 점수를 매기는 시험 문제 모음인 SWE-bench의 한 갈래예요. ↩
  3. JSON — 이름과 값을 짝지어 적는, 프로그램끼리 주고받기 좋은 글자 형식이에요. ↩
  4. 토큰 — AI가 글을 읽고 쓸 때 세는 글자 조각 단위로, AI 토큰(Token)이란 무엇인가에서 다뤘어요. ↩
