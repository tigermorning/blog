같은 "반복 업무 도구"인데 화면이 전혀 다른 이유

반복 업무를 덜어 줄 도구를 검색하면 화면마다 전혀 다른 세계가 펼쳐져요. ChatGPT나 Claude 같은 대화창에서는 말로 요청을 건네고, 대화 맥락을 바탕으로 다음 행동이 정해져요. 답이 곧바로 돌아오는 장면은 친숙하지만, 그 판단이 어떤 연결을 거쳤는지는 대화창 밖에서 따로 살펴야 하고요.

Zapier는 널리 쓰이는 노코드 자동화 서비스예요. 수천 개 앱을 "트리거(이런 일이 일어나면) → 액션(이렇게 한다)" 규칙으로 미리 연결해요. 연결한 앱 수와 실행 횟수(task) 기준으로 이용료가 달라지니 비용과 실행 기록을 함께 봐야 해요. Make(옛 Integromat)는 흐름을 그래프처럼 그리는 시각적 시나리오 편집기예요. 필터·반복·에러 처리 분기를 시나리오 안에서 조립하고, 연산량(operation) 단위로 비용이 매겨져요. 이 둘은 다음 행동을 사람이 미리 정한 규칙이 대신 수행한다는 점에서 같은 층에 놓이지만, n8n에서는 그 그래프를 내 눈으로 직접 들여다보고 나중엔 직접 띄워볼 수도 있다는 점이 달라요.

도구방식과금 단위
Zapier노코드, 앱 간 트리거·액션 규칙task(실행 횟수)
Make시각적 시나리오 편집기, 필터·반복·분기operation(연산량)
n8n그래프형, 노드와 선으로 흐름 확인, 셀프 호스팅 가능도구·플랜에 따라 다름

n8n이나 Node-RED 같은 그래프형 도구에서는 노드와 선이 다음 행동과 데이터 이동 경로를 화면에 그대로 드러내요. 코드를 쓰거나 코딩 에이전트에게 일을 맡기는 방식에서는 코드·터미널·저장소가 그 역할을 나눠 가지고요. 더 세밀한 규칙을 정할 수 있지만, 흐름과 기록을 한 화면에서 다 보기는 어려울 수 있어요. 이 스펙트럼을 훑고 나면 다음 행동을 누가 정하는지, 그 과정이 어디까지 보이는지, 무엇에 비용이 붙는지를 비교할 수 있게 돼요.

왜 하필 n8n인가

관찰 도구로 n8n을 고른 이유가 있었어요. n8n은 2019년 베를린에서 시작한 워크플로 자동화 도구예요. 이름은 노드(node)와 오토메이션(automation)을 합친 nodemation에서 왔는데, 노드를 잇는 그래프가 곧 실행되는 구조 자체가 이름의 출발점이에요. 화면에서 노드라 부르는 블록을 연결해 흐름을 그리면 그 그래프가 그대로 돌아가요. 메일·폼·스프레드시트·채팅 같은 외부 서비스와 공개 API를 노드로 묶을 수 있고, 실행할 때마다 어느 노드가 무엇을 주고받았는지 기록이 남아요. 그래프가 화면에 그대로 보이니 흐름과 데이터 이동을 눈으로 따라갈 수 있고, 그만큼 관찰 학습에 알맞았어요.

성장세도 눈에 띄었어요. 2025년 한 해에만 GitHub 별이 11만 개 넘게 늘었고, 월간 활동 사용자가 170만 명을 넘었대요. AI 에이전트 노드를 앞세워 빠르게 커뮤니티를 넓히는 중이고요. 사용 규모가 곧 신뢰라는 뜻은 아니지만, 많은 사람이 같은 도구로 흐름을 만들고 기록을 남긴다는 건 배운 내용을 강의 밖에서도 써먹을 생태계가 있다는 뜻이었어요. n8n은 소스 코드가 공개된 fair-code 방식이라 나중에 내 컴퓨터나 서버에 직접 띄워볼 수도 있어요. 클라우드 서비스가 문을 닫아도 내 환경에서 흐름을 계속 돌릴 수 있다는 뜻이에요.

Manual Trigger와 HTTP Request로 첫 흐름 만들기

실습에서는 마련된 n8n 인스턴스에 계정을 만들어 접속한 뒤, 새 워크플로 화면에서 Manual Trigger와 HTTP Request 두 노드를 찾아 연결했어요. Manual Trigger는 Execute Workflow로 실행할 때만 흐름을 시작하니, 첫 실행의 출발점이 눈앞에 보여요. HTTP Request의 주소에는 인증 없이 읽을 수 있는 위키백과 요약 API(https://en.wikipedia.org/api/rest_v1/page/summary/N8n)를 넣었고요. 두 노드를 이은 뒤 실행하면, 그래프로 설계한 흐름이 공개 API를 읽고 결과를 돌려줘요.

실행이 끝나면 실행 목록에서 방금 흐름의 기록을 열어봐요. HTTP Request 노드의 출력에는 HTTP 상태 코드와 서버가 돌려준 원 응답이 함께 보이는데, 여기서 title, description, timestamp, content_urls 필드를 확인할 수 있었어요. 선으로만 보이던 흐름이 실제 데이터를 가져왔다는 사실을 기록으로 확인하는 순간이었어요. 실행 기록은 워크플로 전체가 한 번 실행된 단위라, 노드 화면과 실행 한 건은 구별해서 봐야 한다는 것도 새로 알았고요.

이 연결 방식은 설문 폼 응답을 스프레드시트로 옮기는 흐름, 정해진 시각에 공개 API를 읽어 요약을 남기는 흐름, 새 메일이나 폼 접수를 감지해 알리는 흐름으로도 넓힐 수 있어요. 다만 화면에 노드가 있다는 사실과 실제 업무를 맡겨도 된다는 판단은 같지 않다는 걸 기억해야 했어요. 연결할 서비스의 권한, 실패 뒤에 남는 기록, 사람이 다시 확인할 지점을 함께 살펴야 진짜 업무에 쓸 수 있어요.

이렇게 그래프에서 확인한 질문들 — 다음 행동을 누가 정하는가, 실행이 어디에 기록되는가, 원 응답은 어디에 보이는가 — 을 코드와 터미널로 옮겨 비교하는 게 다음 순서예요. 같은 흐름을 코딩 에이전트에게 맡기면 규칙과 기록이 어디에 남는지 비교해보는 4강부터, 워크플로 안에서 에이전트를 쓰는 5강, 내 업무의 어디까지를 맡길지 판정하는 6강, n8n을 직접 셀프 호스팅해보는 7강까지 아직 네 개의 강의가 더 남아 있어요. 이어서 정리해볼게요.

"자동화에서 에이전트까지" 시리즈

(1) 반복 업무, AI에게 맡겨도 될까 — 다음 행동을 누가 정하는가 (2) 자동화와 워크플로 — 규칙을 정하고 그래프를 잇는다

(3) 그래프형 워크플로 도구를 직접 관찰하다 — n8n 실습 (이 글)
