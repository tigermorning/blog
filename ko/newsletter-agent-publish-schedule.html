비유 — 완성된 한 상을 손님 앞에 내보낸다

앞의 네 노드는 모두 프로그램 안에서 끝나는 일이었어요. 수집을 두 번 돌려도, 요약을 다시 써도 바깥에서는 아무 일도 일어나지 않아요. 발행은 달라요. 요청을 보내는 순간 다른 사람의 휴대전화에 알림이 뜨고, 이미 뜬 메시지는 거둬들일 수 없어요.

11편부터 이어 온 그 주방이 매일 아침 "오늘의 한 상"을 내기로 했죠. 장보기를 다시 하든 접시를 다시 담든 주방 안의 일은 손님이 몰라요. 그런데 한 상이 홀로 나가 손님 테이블에 놓이면 끝이에요. 그래서 사장님은 영업 준비 중에는 쟁반에 올려 보기만 하고 홀로 내보내지 않아요. 재료가 영 없던 날에도 손님에게 "오늘은 한 상이 없습니다"라고 알려요. 서빙 직원이 "아까 갔었나?" 싶어 같은 접시를 한 번 더 들고 나가면, 손님 앞에는 같은 접시가 두 개 놓여요.

핵심 한 줄: 내보내기는 되돌릴 수 없으니, 무엇이 나갈지 먼저 보고, 나갔는지 정확히 알고, 없는 날에도 없다고 알려야 해요.

다만 여기서 비유가 끊기는 점이 있어요. 식당은 손님이 눈앞에 있어 반응이 보이지만, 디스코드로 보낸 메시지는 누가 읽었는지 알 수 없어요. 그리고 뒤에 나오는 "매일 아침 정해진 시각에 저절로 돌리기"는 주방에 맞는 장면이 없어서, 그 절은 비유 없이 그대로 설명할게요.

전체 흐름

그림을 읽는 법이에요. 맨 위 줄은 GitHub 쪽에서 매일 한 번씩 벌어지는 일이고, 가운데 점선 상자는 그중 python run.py 한 단계 안에서 도는 우리 그래프예요. 이번 편에서 새로 생기는 건 오른쪽 아래 두 갈래(DRY_RUN)와 맨 위 줄 전체예요. 선별이 0건인 날 곧장 검수로 가는 강조색 점선은 14편에서 그어 뒀는데, 그 선이 왜 필요한지는 이 편의 발행에서 드러나요.

어디로 보낼까 — 네 갈래 중 디스코드 웹훅

규칙부터 정했어요. 검수를 통과한 만큼 그대로 보낸다. 다섯 건이 통과하면 다섯 건, 세 건이면 세 건이에요. 0건인 날에도 "오늘은 조용합니다" 한 줄은 보내요. 아무것도 안 보내면 받는 쪽에서는 소식이 없는 날인지 프로그램이 죽은 날인지 알 수가 없거든요.

남은 건 "어디로"예요. 매일 아침 휴대전화에 알림이 떠야 만들었다는 실감이 나니까, 오늘 안에 받아 볼 수 있는 경로를 골랐어요. 위로 갈수록 제대로 된 뉴스레터에 가깝지만 시작하기까지 오래 걸려요.

그렇다고 ③이 이메일보다 낫다는 뜻은 아니에요. 실제 구독자에게 보내는 뉴스레터라면 ①이 맞아요. 그래도 ③으로 시작해도 되는 건, 무엇을 어떤 모양으로 보내나, 한도를 넘으면 어떻게 하나, 실패를 어떻게 아나가 경로와 상관없이 같기 때문이에요. 나중에 ①로 바꿀 때 고칠 곳은 publish 노드 하나예요.

웹훅 주소 받기

웹훅1은 받는 쪽이 미리 발급해 준 주소예요. 그 주소로 데이터를 보내면 받는 쪽에서 무언가가 일어나요. 디스코드라면 채널에 메시지가 올라와요. 주소는 3분이면 받아요. 메뉴 이름은 앱 언어 설정에 따라 달라서 영어 이름을 같이 적었어요.

  1. 디스코드 왼쪽 서버 목록 맨 아래 +(서버 추가, Add a Server) → 직접 만들기(Create My Own) → 나와 친구들을 위한 서버(For me and my friends). 이름은 아무거나 괜찮아요.
  2. 서버 안에 채널을 하나 만들거나(예: #브리핑) 기본으로 있는 채널을 써요.
  3. 채널 이름 옆 톱니바퀴(채널 편집, Edit Channel) → 왼쪽 메뉴 연동(Integrations) → 웹후크(Webhooks) → 새 웹후크(New Webhook).
  4. 이름을 "편집실" 정도로 바꾸고 웹후크 URL 복사(Copy Webhook URL)를 눌러요. https://discord.com/api/webhooks/숫자/긴문자열 모양이에요.
  5. OpenAI 키를 넣었던 방법 그대로 DISCORD_WEBHOOK_URL이라는 이름의 환경변수2로 넣어요. 로컬 주피터라면 .env에 한 줄, Colab이라면 보안 비밀(열쇠 아이콘)에 하나 더해요. 키를 넣는 방법과 함정은 13편의 키 설정 셀과 .env가 안 읽혔던 네 겹의 이유 (5)에 있어요.

이 주소는 그 자체가 열쇠예요. 웹훅 주소에는 따로 비밀번호가 없어서, 주소를 아는 사람은 누구나 그 채널에 글을 올릴 수 있어요. 노트북 셀에 주소를 적은 채 공유하면 안 되는 이유예요. 새어 나갔다면 되돌리는 방법은 하나예요. 디스코드에서 그 웹후크를 지우고 새로 만들어요. 셀에 적은 키가 어디에 남는지는 5편의 의심 표에서 봤어요.

한 줄 보내 보기 — 204는 성공이다

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 디스코드 웹훅 주소 필요, OpenAI API 키 없이 돌아가요. 실제로 채널에 올라가요

import os, requests

WEBHOOK = os.environ.get("DISCORD_WEBHOOK_URL", "")    # .env나 보안 비밀로 넣어 둔 값
assert WEBHOOK, "환경변수 DISCORD_WEBHOOK_URL 을 먼저 설정하세요"
r = requests.post(WEBHOOK, json={"content": "편집실 연결 확인 ✅"}, timeout=20)
print(r.status_code, r.text or "(본문 없음)")

requests.post는 주소로 데이터를 실어 보내는 요청(POST)을 보내요. json=에 넘긴 파이썬 사전은 JSON3 글자로 바뀌어 실려 가요. 디스코드가 알아듣는 가장 단순한 모양이 {"content": "보낼 문장"}이에요.

개념 설명용 코드 — 성공했을 때 찍히는 모양이에요

204 (본문 없음)

처음 보면 멈칫하는 숫자예요. 응답에 붙는 세 자리 숫자를 HTTP 상태 코드4라고 하는데, 2로 시작하면 성공이에요(읽는 법은 도메인·포트·HTTPS — 주소가 화면이 되기까지의 상태 코드 절에 있어요). 그중 204는 "잘 처리했고, 돌려줄 내용은 없다"는 뜻이에요. 디스코드 웹훅은 기본적으로 메시지를 올리고 이 204를 돌려줘요. 채널을 열어 보면 문장이 올라와 있고, 그게 파이프라인의 출구가 열렸다는 표시예요. 주소 끝에 ?wait=true를 붙이면 디스코드가 메시지가 저장된 걸 확인한 뒤 그 메시지 내용을 담아 200으로 답해 줘요.

본문이 비었다고 실패로 보면 안 돼요. 그렇게 오해하고 한 번 더 보내면 같은 메시지가 채널에 두 번 떠요. 웹훅은 "아까 받은 거네" 하고 걸러 주지 않거든요. 요청 한도에 걸린 거라면 204가 아니라 429가 와요. 그리고 디스코드가 늘 200을 주는 것도 아니에요. 주소가 틀렸거나 웹후크가 지워졌으면 401이나 404, 보낸 JSON 모양이 규격에 안 맞으면 400이 와요. 429일 때는 응답 본문에 몇 초 뒤에 다시 보내라는 값이 들어 있어요.

중요꼭 기억할 것

웹훅 응답이 204에 본문이 비어 있으면 성공이에요 — 메시지는 채널에 올라갔고, 돌려줄 내용이 없을 뿐이에요. 빈 본문을 실패로 보고 다시 보내면 중복 발송이 돼요. 실패는 숫자로 구분해요. 주소가 틀리면 401·404, 한도는 429, JSON 규격 위반은 400이에요.

카드로 나눠 담기 — embed와 dry-run

여기부터는 14편까지의 셀을 먼저 실행해 둔 노트북에서 이어 가요.

content는 글 한 덩어리라서, 기사 다섯 건을 이어 붙이면 읽기 힘든 글자 벽이 돼요. 디스코드에는 embed5라는 카드가 있어요. 제목·본문·링크·출처를 칸마다 나눠 담는 틀이에요. 14편에서 요약을 headline·summary·why 세 칸으로 나눠 받은 게 여기서 값을 해요. 헤드라인은 카드 제목, 요약은 본문, "왜 중요한가"는 본문 아래 강조 줄로 들어가요.

카드에는 한도가 있어요. 메시지 하나에 카드 10장, 제목 256자, 본문 4096자, 모든 카드의 글자를 합쳐 6000자예요. 하나라도 넘으면 디스코드가 400으로 거절하고 아무것도 올라가지 않아요. 그래서 보내기 전에 코드에서 잘라요.

또 하나, 보내지 않고 무엇을 보낼지만 출력하는 스위치를 둬요. 이걸 dry-run6이라고 불러요. 매일 도는 물건에서는 필수예요. 프롬프트를 고칠 때마다 채널에 시험 발행이 쌓이면 곤란하잖아요. 아래 셀의 기사 두 건은 모양을 보여 주려고 지어낸 가상 예시예요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키도 웹훅 주소도 없이 돌아가요 (dry_run=True라 보내지 않아요)

import json, os, requests

COLORS = {"모델·API": 0x0B6E77, "도구·프레임워크": 0x4C7C9C,
          "정책·규제": 0x8F5606, "사례·적용": 0x2E7D5B, "연구": 0x6A4A9C}
DEFAULT = 0x5F7476
TITLE_MAX, DESC_MAX, EMBED_MAX, TOTAL_MAX = 256, 4096, 10, 5800   # 6000에서 여유를 둔다

def build_embeds(run_id, lead, articles):
    if not articles:                                   # 조용한 날에도 한 장은 보낸다
        return [{"title": f"🗞️ {run_id}", "color": DEFAULT,
                 "description": "오늘은 조용합니다."}]
    embeds = [{"title": f"🗞️ {run_id} · AI 브리핑", "description": lead, "color": DEFAULT}]
    for i, a in enumerate(articles, 1):
        desc = a["summary"]
        if a.get("why"):
            desc += f"\n\n💡 **{a['why']}**"
        embeds.append({
            "title":       f"{i}. {a['headline']}"[:TITLE_MAX],
            "description": desc[:DESC_MAX],
            "url":         a["url"],
            "color":       COLORS.get(a.get("topic", ""), DEFAULT),
            "footer":      {"text": f"{a['source']} · {a['when']}"},
        })
    total = lambda es: sum(len(e.get("title", "")) + len(e.get("description", ""))
                           + len(e.get("footer", {}).get("text", "")) for e in es)
    dropped = 0
    while len(embeds) > EMBED_MAX or total(embeds) > TOTAL_MAX:
        embeds.pop()                                   # 뒤에서부터 덜어낸다
        dropped += 1
    if dropped:                                        # 덜어냈으면 흔적을 남긴다
        print(f"[한도] 카드 {dropped}장을 빼고 {len(embeds) - 1}장만 보냅니다")
    return embeds

def send(run_id, lead, articles, webhook=None, dry_run=True):
    payload = {"username": "편집실", "embeds": build_embeds(run_id, lead, articles)}
    if dry_run:
        print(f"[dry-run] embed {len(payload['embeds'])}개 · "
              f"{len(json.dumps(payload, ensure_ascii=False))}자 — 보내지 않음")
        print(json.dumps(payload["embeds"][-1], ensure_ascii=False, indent=2)[:400])
        return False
    if not webhook:
        raise RuntimeError("DRY_RUN이 0인데 DISCORD_WEBHOOK_URL이 비어 있어요")
    try:
        r = requests.post(webhook, json=payload, timeout=20)
    except requests.RequestException as e:             # 에러 문장에 웹훅 주소가 섞여 로그에 남지 않게
        raise RuntimeError(f"발행 요청 실패: {type(e).__name__}") from None
    if r.status_code not in (200, 204):                # 실패는 조용히 넘기지 않는다
        raise RuntimeError(f"발행 실패 {r.status_code} {r.text[:120]}")
    print("발행: 성공", r.status_code)
    return True

  • embed 3개는 머리말 카드 한 장에 기사 카드 두 장이에요. 기사가 다섯 건이면 여섯 장이라 한도 10장까지 여유가 있어요.
  • 찍힌 카드는 마지막 카드, 즉 두 번째 기사예요. 코드가 embeds[-1]을 찍거든요. 파이썬에서 [-1]은 "맨 뒤"라는 뜻이에요. 첫 기사 카드를 보고 싶으면 [1]로 바꾸면 돼요([0]은 머리말이에요).
  • 칸 배치를 보면 헤드라인은 title로, 요약은 description으로, "왜 중요한가"는 그 아래 💡 굵은 줄로 들어갔어요. 요약을 한 덩어리 문단으로 받았다면 이렇게 나눠 담을 수 없어요.
  • color가 5012636이에요. 디스코드는 색을 16진수 글자가 아니라 정수로 받아요. 코드에 적은 0x4C7C9C(도구·프레임워크 색)를 파이썬이 정수로 바꾼 값이에요. 파이썬으로 계산해 보면 0x0B6E77은 749175예요.
  • dry_run=True를 False로 바꾸면 실제로 채널에 올라가요. 그때 응답이 200·204가 아니면 RuntimeError로 실행을 멈춰요. 실패를 조용히 넘기면 나중에 "실패했는데 아무도 모르는" 날이 생기거든요(돌았는지 확인하는 세 겹에서 이어져요).
  • 연결이 끊기거나 시간이 초과되면 requests가 내는 에러 문장에는 웹훅 주소의 경로가 토큰까지 그대로 들어가요. 제가 닫힌 포트로 보내 보니 에러 문장에 /api/webhooks/…/토큰이 찍혔어요. 공개 저장소의 Actions 로그는 누구나 볼 수 있고, 주소 일부만 찍히면 GitHub가 가려 주지 않을 수 있어요. 그래서 except로 받아 에러 종류만 남기고 다시 던져요.

한도를 넘으면 어떻게 되는지도 돌려 봤어요. 요약이 1500자씩인 기사 다섯 건을 넣었더니 [한도] 카드 2장을 빼고 3장만 보냅니다가 찍히고 embed는 4개(머리말 + 기사 세 장)가 됐어요. 코드는 뒤에서부터 카드를 덜어내요. 순서가 중요도 순이니 덜 중요한 기사가 먼저 빠지는 거예요. 다만 덜어낸 기사는 아무 에러 없이 사라져요. 그래서 dropped를 세어 한 줄을 찍게 해 뒀어요. 이 줄이 없으면 로그만 봐서는 몇 장이 빠졌는지 알 수 없어요.

발행 노드 — 마지막 빈 노드를 채운다

11편에서 세운 빈 노드 가운데 publish 하나가 남았어요. build()가 노드를 이름으로 찾아 붙이니까, 같은 이름으로 함수를 다시 정의하고 run()만 다시 부르면 끼워져요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — OpenAI API 키 필요 (앞 노드들이 LLM을 불러요). DRY_RUN을 안 넣었으면 디스코드엔 안 보내요

from datetime import datetime, timedelta, timezone

KST = timezone(timedelta(hours=9))              # 받는 사람이 읽는 시각은 한국 시각

def make_lead(arts):
    if not arts:
        return ""
    srcs = ", ".join(dict.fromkeys(a["source"] for a in arts))
    return f"오늘은 {len(arts)}건을 골랐습니다. ({srcs})"

def publish(s: dict) -> dict:                 # ⑤ 발행 — 마지막 빈 노드를 갈아 끼운다
    arts = [{"headline": a["headline"], "summary": a["summary"], "why": a["why"],
             "url": a["url"], "source": a["source"], "topic": a.get("event", ""),
             "when": a["at"].astimezone(KST).strftime("%m-%d %H:%M")} for a in s["verified"]]
    today = datetime.now(KST).strftime("%Y-%m-%d")
    sent  = send(today, make_lead(arts), arts,
                 webhook=os.environ.get("DISCORD_WEBHOOK_URL"),
                 dry_run=os.environ.get("DRY_RUN", "1") == "1")   # 기본은 보내지 않음
    label = f"{len(arts)}건" if arts else "조용합니다"
    return {"log": [f"⑤ 발행   {label} · {'보냄' if sent else 'dry-run'}"]}

for line in run()["log"]:
    print(line)

실행하면 로그 마지막 줄이 ⑤ 발행 N건 · dry-run 모양으로 찍혀요. 몇 건인지와 앞 줄들의 숫자는 그날 뉴스와 모델 답에 따라 실행마다 달라요. 이제 다섯 단계 로그가 모두 0이 아닌 숫자로 채워졌어요. 파이프라인이 끝까지 이어진 거예요. 짚을 곳은 다섯이에요.

  • 보낼지 말지는 State가 아니라 설정이에요. 기사 목록처럼 실행하면서 바뀌는 값이 아니라, "이번 실행이 시험인가 진짜인가"를 정하는 값이라 환경변수 DRY_RUN으로 뺐어요. 기본값은 "1"(보내지 않음)이에요. 실수로 보내는 쪽보다 실수로 안 보내는 쪽이 덜 나빠서요. 노트북에서 정말 보내려면 os.environ["DRY_RUN"] = "0"을 먼저 실행해요.
  • 필요한 칸만 골라 새로 담아요. verified의 기사에는 원문 본문(body)처럼 발행에 안 쓰는 칸도 들어 있어요. 통째로 넘기면 6000자 한도를 넘기기 쉽고, 무엇을 내보내는지도 흐려져요.
  • 시각은 한국 시각으로 바꿔 찍어요. 12편의 at은 UTC 기준이라 그대로 strftime하면 카드 아래 시각이 9시간 이르게 찍혀요. datetime.now()도 Colab이나 GitHub 서버처럼 UTC로 도는 곳에서는 UTC 시각이라, 한국 아침 7시 반에 돌면 제목 날짜가 전날로 나와요. 그래서 KST를 직접 넘겨요.
  • 지금은 카드가 전부 기본색으로 나와요. topic 자리에 a.get("event", "")를 넣었지만, 13편의 사건 라벨(event)은 모델 답(Pick)에만 있고 picked에 담기는 기사 사전에는 붙지 않아요. 그래서 빈 문자열이 들어가고 COLORS.get은 기본색을 돌려줘요. 라벨을 기사에 붙여 넘겨도 "A사 추론 모델 공개" 같은 자유 문장이라 COLORS의 다섯 이름과는 맞지 않아요(제가 자유 문장으로 COLORS.get을 해 봐도 기본색이었어요). 토픽별 색을 쓰려면 선별 단계에서 다섯 토픽 중 하나를 고르게 하는 칸이 따로 필요해요.
  • 모자라도 그대로 보내요. 검수에서 두 건이 떨어져 세 건이면 세 건만 보내요. 다섯을 채우려고 다시 수집하거나 기준을 낮추는 길을 붙이면 "언제까지 다시 시도할까"를 정해야 하고, 재시도 횟수·비용 상한이 줄줄이 따라와요. 14편에서 불합격 요약을 버리고 로그에 남기기로 한 것과 같은 판단이에요.

조용한 날의 "오늘은 조용합니다"가 정말 나가려면, 고른 기사가 0건인 날에도 그래프가 publish까지 가야 해요. 그 길은 14편에서 깔아 뒀어요. fan_report는 고른 기사 수만큼 Send를 만들고(Send는 9편에서 본, 같은 노드를 여러 벌 띄우는 쪽지예요), 목록이 비면 or "verify"로 곧장 검수로 보내요. 그 줄이 없으면 다음에 실행할 노드가 하나도 없어 그래프가 ② 줄에서 에러 없이 끝난다는 건 14편의 가짜 실행에서 봤어요. 여기서는 14편까지의 코드에 이 편의 발행 노드를 끼우고, LLM과 네트워크 자리를 가짜 함수로 바꿔 수집이 0건인 날을 돌려 봤어요.

{
  "title": "🗞️ 2026-09-14",
  "color": 6255734,
  "description": "오늘은 조용합니다."
}
① 수집   24시간 창 · 0건
② 선별   0 → 0건
④ 검수   0 → 0건

빈 검수를 거쳐 발행까지 가서, 머리말 한 장짜리 "오늘은 조용합니다" 카드를 만들었어요. ③ 줄이 없는 건 워커가 한 번도 불리지 않았기 때문이에요. [dry-run] 줄이 로그보다 먼저 찍힌 건 send가 그래프가 도는 도중에 출력하고, 로그 줄은 run()이 끝난 뒤에 한꺼번에 찍기 때문이에요. 노트북을 파이썬 파일로 옮길 때 fan_report의 or "verify"나 add_conditional_edges 목록의 "verify"가 빠지면 이 카드가 안 나가요(14편의 같은 증상 줄). 옮긴 뒤에도 0건으로 한 번 돌려 봐요.

중요꼭 기억할 것

매일 도는 발행은 보낼 게 없는 날에도 무언가를 보내야 해요. "소식이 없어서 조용한 날"과 "프로그램이 죽어서 조용한 날"은 받는 사람 눈에 똑같아 보이지만, 앞쪽은 "오늘은 조용합니다"가 오고 뒤쪽은 아무것도 안 와요. 그러려면 0건인 날에도 그래프가 발행 노드까지 가는 길이 실제로 있는지, 기사 0건으로 한 번 돌려 확인해요.

웹훅은 어떤 방식인가

여기까지 쓴 웹훅을 한 발 물러서 볼게요. 웹훅은 미리 받아 둔 주소로 HTTP 요청을 보내면, 그쪽 시스템에서 무언가 일어나는 방식이에요. 상대 서비스의 사용법(API)을 따로 배우거나, 토큰을 발급받거나, 권한을 설정할 필요가 없어요. 주소와 requests 한 줄이면 돼요. 그래서 알림·배포 완료 통지·모니터링처럼 한 방향으로 알리는 일에 잘 맞아요.

인증 헤더가 없는데 어떻게 아무나 못 쓰게 할까요. 받는 쪽이 발급한 주소 안에 식별자와 비밀 토큰이 함께 들어 있어요. 그 주소로 보낼 수 있다는 것 자체가 인증이에요. 그래서 주소가 곧 비밀번호고, 저장소에 올리거나 노트북에 적어 공유하면 누구나 글을 쓸 수 있어요. 되돌리는 방법은 지우고 다시 만드는 것뿐이에요.

방향도 짚어 둘게요. 코딩 에이전트에게 흐름을 맡기고, IF 노드로 갈림길 만들기 (2)의 n8n Webhook 트리거는 우리가 주소를 열어 두고 요청을 받는 쪽이었어요. 여기서는 디스코드가 열어 둔 주소로 우리가 보내는 쪽이에요. 구조는 같아요. 주소를 발급한 쪽이 받고, 주소를 아는 쪽이 보내요. 그 글에서 받는 쪽 주소에 인증과 호출 제한을 걸라고 한 것도, 이번에 보내는 쪽이 주소를 비밀로 지켜야 하는 것도 같은 이유예요.

알아 둘 성질이 둘 더 있어요. 웹훅에는 중복 방지가 없어요. 같은 내용을 두 번 보내면 두 번 떠요. 나중에 "보냈는지 모르겠으니 한 번 더" 하는 재시도를 붙이면 그게 바로 중복 발송이에요. 그리고 짧은 시간에 많이 보내면 429가 와요. 여러 메시지로 쪼개 보낸다면 사이에 간격을 둬요.

매일 아침 저절로 — GitHub Actions (비유 없이 그대로)

이제 노트북을 열지 않아도 매일 아침 7시 30분에 저절로 돌게 할 차례예요. 필요한 건 셋이에요. 정해진 시각에 깨울 것, API 키를 안전하게 넘길 것, 돌았는지 확인할 방법. 셋째가 가장 자주 빠져요.

이 셋을 GitHub Actions7에 맡겨요. GitHub 저장소만 있으면 되고, 공개 저장소면 무료로 쓸 수 있고, 매 실행의 로그가 웹에 남아요. GitHub Actions가 무엇인지와 예약 실행의 첫 모양은 GitHub Actions 예약 발행 (5)에서 블로그 글 발행으로 먼저 다뤘어요.

저장소 구성 — 노트북을 파이썬 파일로

노트북(.ipynb)은 자동 실행에 맞지 않아요. 셀을 순서대로 눌러 줄 사람이 없거든요. 그래서 파일 몇 개로 옮겨요.

개념 설명용 코드 — 저장소 폴더 구조예요

옮길 때 손볼 곳이 셋이에요.

  1. ! pip install 줄은 requirements.txt로. 파이썬 파일에서는 !로 시작하는 명령을 쓸 수 없어요.
  2. 같은 이름을 두 번 정의했으면 마지막 것 하나만. build()·Brief는 최종 버전만 남겨요. 그리고 위에서 아래로, 정의가 먼저 오고 쓰는 곳이 뒤에 오게 놓아요. INIT만은 예외예요. 14편의 INIT = {**INIT, "verified": []}는 앞의 INIT을 읽어 칸을 더하는 줄이라, 11편 줄을 지우고 이 줄만 남기면 NameError: name 'INIT' is not defined가 나요. 두 줄을 차례로 두거나, "verified": []까지 든 사전 하나로 합쳐 적어요.
  3. 실습 셀에 있던 스키마를 빠뜨리지 않기. 13·14편은 코드 셀이 둘씩이에요. 앞 셀에서 Pick·Shortlist·Draft·SYS를 정의하는데, 노드 셀만 옮기면 NameError: name 'Shortlist' is not defined가 나요. 앞 셀에서는 클래스와 상수만 가져오고, 기사 제목을 훑어보던 실습용 반복문은 노트북에 두고 와요.

키를 코드에 직접 적었던 줄(os.environ["OPENAI_API_KEY"] = "sk-..." 같은 줄)도 반드시 지워요. 공개 저장소에 키가 한 번 올라가면 다음 커밋에서 지워도 예전 커밋에 그대로 남아요(AI가 짠 백엔드 코드에서 반드시 확인할 것들).

실행: 저장소에 run.py로 저장 — GitHub Actions가 python run.py로 실행해요. 내 컴퓨터에서 돌리면 OpenAI API 키 필요

# run.py
import os
from graph import run          # graph.py 에 있는 그 run()

if __name__ == "__main__":
    dry  = os.environ.get("DRY_RUN", "1") == "1"            # publish()와 같은 규칙으로 읽는다
    hook = bool(os.environ.get("DISCORD_WEBHOOK_URL"))      # 주소 자체는 찍지 않는다
    print("모드:", "dry-run" if dry else "발행", "· 웹훅 주소", "있음" if hook else "없음")
    out = run()
    for line in out["log"]:
        print(line)                        # 이 출력이 Actions 로그에 그대로 남는다

실행하는 코드를 run.py로 따로 둔 이유는 graph.py는 불러오기만 해도 안전해야 하기 때문이에요. graph.py 맨 끝에 run() 호출을 적어 두면 다른 코드에서 import graph를 하는 순간 브리핑이 발행돼요. if __name__ == "__main__": 아래는 이 파일을 python run.py로 직접 실행할 때만 돌아요.

첫 print는 이번 실행이 보내는 실행인지, 웹훅 주소가 들어왔는지를 로그 맨 위에 남겨요. 주소 값은 찍지 않고 "있음/없음"만 찍어요. 이 한 줄이 뒤에서 말할 "Actions는 초록인데 메시지가 안 오는" 날의 첫 단서예요. 내 컴퓨터에서 python run.py로 돌리면 DRY_RUN이 비어 있으니 기본값대로 보내지 않아요.

키는 Secrets에 — 코드에는 한 글자도

OPENAI_API_KEY와 DISCORD_WEBHOOK_URL은 코드나 설정 파일에 적지 않아요. 공개 저장소에 올라간 키는 몇 분 안에 긁어 가는 봇이 있어요. 대신 GitHub 저장소에 비밀값으로 등록해요.

  1. 저장소 Settings → Secrets and variables → Actions → New repository secret
  2. 이름 OPENAI_API_KEY, 값에 키를 넣고 저장. 같은 방법으로 DISCORD_WEBHOOK_URL도 등록해요.

등록한 값은 다시 열어 볼 수 없고 새 값으로 덮어쓰기만 돼요. 불편해 보여도 설계예요. 화면에 보이는 순간 유출 경로가 하나 더 생기거든요. 워크플로에서는 ${{ secrets.OPENAI_API_KEY }}로 꺼내 써요. 실수로 로그에 찍어도 GitHub가 ***로 가려 주지만, 앞 몇 글자만 잘라 찍는 식으로 값을 바꿔 찍으면 가려지지 않을 수 있어요. 이름을 잘못 적으면(예: DISCORD_WEBHOOK) 에러 없이 빈 문자열이 들어와요.

워크플로 파일 — 다섯 가지 결정

실행: .github/workflows/daily.yml로 저장 — GitHub Actions가 읽어요 — 들여쓰기가 틀리면 워크플로가 안 읽혀요

name: 매일 브리핑

on:
  schedule:
    - cron: "30 22 * * *"          # ① UTC 22:30 = KST 07:30
  workflow_dispatch:                # ② 손으로도 돌릴 수 있게
    inputs:
      dry_run:
        description: "발행하지 않고 로그만 남기기"
        type: boolean
        default: false

jobs:
  publish:
    runs-on: ubuntu-latest
    timeout-minutes: 20             # ③ 멈춰 있는 실행을 20분에서 끊는다

    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt

      - name: 브리핑 생성·발행
        run: python run.py
        env:                        # ④ 비밀값과 발행 스위치는 여기로만 들어간다
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
          DISCORD_WEBHOOK_URL: ${{ secrets.DISCORD_WEBHOOK_URL }}
          DRY_RUN: ${{ inputs.dry_run && '1' || '0' }}
          TZ: Asia/Seoul

      - name: 실행 기록 보관          # ⑤ 로그 말고 파일로 남은 것도 챙긴다
        if: always()
        uses: actions/upload-artifact@v6
        with:
          name: run-${{ github.run_number }}
          path: store/
          retention-days: 30

GitHub에서 돌려 보기 전에, 이 파일을 파이썬의 yaml.safe_load로 읽어 들여 들여쓰기가 의도대로 묶였는지만 확인했어요. schedule과 workflow_dispatch가 한 묶음, 단계 다섯 개가 steps 아래로 제대로 들어갔어요.

  1. ① 시각은 UTC로 적어요. cron8 줄의 다섯 칸은 분·시·일·월·요일이고, 기본은 UTC9 기준이에요. 한국 시각은 UTC보다 9시간 빠르니 KST 07:30은 전날 UTC 22:30이에요. 파이썬으로 UTC 2026-09-13 22:30을 한국 시각으로 바꿔 보면 2026-09-14 07:30이 나와요. 공식 문서에는 cron 아래에 timezone: "Asia/Seoul"을 함께 적어 한국 시각으로 쓰는 방법도 있어요(그때는 "30 7 * * *"). 정시 실행은 보장이 아니에요. GitHub가 붐비면 정해진 시각보다 늦게 돌고, 드물게 건너뛰기도 해요. UTC를 한국 시각으로 착각한 증상은 예약 발행 글의 의심 표에 있어요.
  2. ② 손으로도 돌릴 수 있게. 아래에서 따로 볼게요.
  3. ③ 20분에서 끊어요. timeout-minutes가 없으면 응답 없는 요청 하나에 매달린 실행이 기본 한도(360분)까지 살아 있어요. 비공개 저장소라면 그 시간이 무료 사용량에서 빠져요.
  4. ④ 비밀값과 스위치는 env로만. 키는 Secrets에서 꺼내 이 단계의 환경변수로만 넣어요. DRY_RUN 줄이 중요해요. 손으로 돌리면서 dry_run을 체크하면 '1', 체크를 끄거나 스케줄로 돌면 inputs가 비어 있어 '0'이 들어가요. TZ: Asia/Seoul은 시간대를 넘기지 않은 datetime.now()가 한국 시각을 돌려주게 해요. 발행 노드는 KST를 직접 넘겨서 이 줄이 없어도 한국 날짜가 찍히지만, 16편 실행 기록의 시각처럼 그냥 datetime.now()를 쓰는 곳은 이 줄이 없으면 UTC로 찍혀요.
  5. ⑤ 기록 파일도 챙겨요. 실행이 끝나면 그 서버는 통째로 사라지고, store/에 쓴 파일도 같이 사라져요. upload-artifact10가 실행 페이지에 파일을 30일간 올려 둬요. if: always()는 앞 단계가 실패해도 이 단계는 돌라는 뜻이에요. 실패한 회차의 기록이 가장 보고 싶은 기록이니까요. store/에 무엇을 쓰는지는 16편에서 채워요.

④의 DRY_RUN 줄이 없으면 어떻게 될까요. publish는 DRY_RUN이 비어 있으면 기본값 "1"로 읽어 보내지 않아요. 스케줄 실행에는 이 값을 넣어 주는 곳이 없으니 매일 아침 dry-run으로 돌아요. LLM·네트워크 자리를 가짜로 바꾼 그래프로 DRY_RUN 없이 돌려 보니, 에러 없이 끝나고 로그 끝에 ⑤ 발행 2건 · dry-run이 찍혔고 보내는 함수는 한 번도 불리지 않았어요. 실행 목록은 초록 체크인데 채널은 조용한 거예요. 같은 그래프에 DRY_RUN=0을 넣었을 때만 ⑤ 발행 2건 · 보냄이 찍혔어요.

손으로 돌리는 버튼이 먼저인 이유

workflow_dispatch를 넣으면 저장소의 Actions 탭에 Run workflow 버튼이 생기고, 누를 때 dry_run 체크박스가 같이 떠요. 이게 없으면 워크플로를 고칠 방법이 사실상 없어요. 파일을 한 줄 고칠 때마다 다음 날 아침 7시 30분까지 기다려야 결과를 알 수 있거든요. 버튼이 있으면 고친 즉시 dry-run으로 돌려 로그를 보고, 괜찮으면 체크를 끄고 한 번 더 눌러 실제 발행까지 확인해요.

이 줄을 넣는 이유를 다른 데서 찾으면 틀려요. schedule만 있어도 GitHub는 워크플로를 알아봐요 — 인식시키려고 넣는 게 아니에요. Secrets도 어떤 방식으로 시작하든 똑같이 읽혀요. 손으로 돌린다고 사용 시간이 공짜가 되지도 않아요. 수동 실행도 스케줄 실행과 똑같이 사용 시간이 쌓여요.

중요꼭 기억할 것

schedule 옆에 workflow_dispatch를 함께 넣는 이유는 손으로 즉시 돌릴 수 있어야 고칠 수 있기 때문이에요. 내일 아침을 기다리지 않고 dry-run으로 먼저 확인한 뒤 실제 발행까지 그 자리에서 해 봐요. 워크플로 인식·Secrets 읽기·사용량과는 상관없어요 — 자동화의 첫 단추는 손으로 돌릴 수 있게 만드는 거예요.

손으로 먼저 한 바퀴

  1. graph.py·run.py·requirements.txt·daily.yml을 커밋하고 푸시해요.
  2. 저장소 Actions 탭 → 왼쪽 목록의 매일 브리핑 → Run workflow → dry_run을 체크한 채 실행해요.
  3. 생긴 실행을 눌러 브리핑 생성·발행 단계를 펼쳐요. 맨 위에 모드: dry-run · 웹훅 주소 있음, 그 아래 로그 줄들이 보이면 정상이에요.
  4. dry_run 체크를 끄고 한 번 더 실행해요. 이번엔 모드: 발행이 찍히고, 디스코드에 브리핑이 오면 끝이에요. 다음 날 아침부터는 알림이 저절로 와요.

알아 둘 것 둘. 스케줄은 기본 브랜치(보통 main)에 있는 워크플로 파일로만 울려요. 다른 브랜치에서 시험 중이면 스케줄은 울리지 않아요. 또 공개 저장소에서 60일 동안 저장소 활동이 없으면 스케줄이 자동으로 꺼져요. 이때는 Actions 탭에서 다시 켜요.

돌았는지 확인하는 세 겹

매일 도는 자동화에서 가장 흔한 사고는 3주 전부터 멈춰 있었는데 아무도 몰랐다예요. 그래서 확인을 세 겹으로 둬요.

  1. 실패하면 GitHub가 메일을 보내요. 계정 알림 설정에서 Actions 알림이 켜져 있으면 실패한 실행마다 메일이 와요. 요란한 고장은 이걸로 잡혀요. 단, 실패가 실패로 끝나야 메일이 와요. 위의 send가 200·204가 아닌 응답에서 예외를 던지는 이유예요. 가짜 404 응답을 돌려주게 해서 돌려 보니 RuntimeError: 발행 실패 404 ...로 끝나고 종료 코드가 1이었어요. Actions에서는 이런 단계가 빨간 X로 표시돼요. 반대로 실패해도 False만 돌려주고 넘어갔다면 실행은 초록으로 끝나고 메일도 오지 않아요.
  2. 조용한 날에도 무언가를 보내요. "오늘은 조용합니다"의 두 번째 역할이에요. 소식이 없어서 조용한 날은 그 한 줄이 오고, 프로그램이 죽은 날은 아무것도 안 와요.
  3. 가끔 실행 목록을 봐요. Actions 탭에 날짜별로 초록·빨강 표시가 쌓여요.

셋 중 둘째가 가장 싸고 가장 잘 들어요. 코드가 "성공했다"고 말하는 걸 믿는 게 아니라, 받는 사람이 "오늘 왔나"를 직접 확인하는 방식이거든요.

정해진 시각에 사람 없이 돈다는 것

정리하면 스케줄 실행은 이런 구조예요. 크론 표현식으로 시각을 정하면, 그 시각에 스케줄러가 깨끗한 새 환경을 만들고, 코드를 내려받고, 비밀값을 넣고, 실행해요. 끝나면 환경은 통째로 사라져요. 남기고 싶은 건 우리가 명시적으로 밖에 내보내야 해요. 이 파이프라인에서는 artifact 업로드와 디스코드 메시지가 그 역할이에요.

그래서 주의할 것도 셋이에요. 정시는 최선의 노력일 뿐이고 조용한 저장소는 스케줄이 꺼져요. 환경이 매번 새것이라 지난 실행이 남긴 파일이 있다고 가정하면 안 돼요. 그리고 사용 시간 한도가 있으니 timeout-minutes로 끊어요.

사람이 매일 기억해서 하는 일은 오래가지 않아요. 자동화의 진짜 효과는 일을 덜어 주는 게 아니라 일을 보이지 않게 만드는 것이에요. 보이지 않는 일은 멈춰도 티가 나지 않아요. 그래서 자동화는 "돌았는지, 얼마나 걸렀는지"를 재는 장치와 짝을 이룰 때만 의미가 있어요. 그 짝이 16편의 실행 기록이에요.

나쁜 선택 vs 좋은 선택 — 보낼지 말지를 어디서 정하나

같은 파이프라인에서, 시험 실행과 진짜 발행을 가르는 스위치를 어디에 뒀는지 비교해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: send(..., dry_run=True)를 코드에 그대로 적어 두고, 진짜로 보낼 때마다 False로 고쳐 커밋했어요. 응답이 200이 아니면 실패로 보고 두 번 더 보내는 재시도도 붙였어요.

무슨 일이 생기나: 프롬프트를 고치며 시험하려고 True로 바꾼 채 푸시한 날부터, 매일 아침 실행은 초록인데 채널은 조용해요. 거꾸로 False인 채 노트북에서 시험하면 채널에 시험 브리핑이 쌓여요. 게다가 디스코드는 성공하면 204를 주니, 재시도 때문에 같은 브리핑이 세 장씩 올라가요.		 무엇을 했나: 코드의 기본값은 "안 보냄"으로 두고, 실제로 보내는 곳인 워크플로에서만 DRY_RUN을 '0'으로 명시했어요. run.py는 로그 첫 줄에 모드와 웹훅 주소 유무를 찍고, 응답은 200·204면 성공, 그 밖은 예외로 끝내요.

무슨 일이 생기나: 노트북·내 컴퓨터에서는 무엇을 돌려도 채널이 조용하고, 매일 아침 실행만 보내요. 안 왔다면 로그 첫 줄로 dry-run이었는지 바로 보이고, 발행이 실패한 날은 빨간 X와 메일이 와요. 재시도가 없으니 중복 발송도 없어요.

정리하면 되돌릴 수 없는 단계에서 물을 건 하나예요. "보냈는지, 안 보냈는지, 실패했는지가 로그에서 서로 다르게 보이는가?" 셋이 같은 초록으로 보이면 멈춘 날을 알아챌 수 없어요.

이럴 때 의심하세요 — 매일 아침 알림이 이상할 때

발행과 스케줄의 문제는 대부분 에러 없이 보여요. 실행 목록은 초록인데 채널이 조용하거나, 같은 카드가 두 번 떠 있거나, 기사 수가 로그와 달라요. 그래서 먼저 열 곳은 코드가 아니라 Actions 실행 로그의 브리핑 생성·발행 단계예요.

증상이 아직 없어도, AI에게 "매일 아침 디스코드로 보내게 자동화해 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

  • "실패하면 재시도하게 해 줘" — 성공 판정이 == 200만 보는지. 204를 실패로 보면 재시도가 곧 중복 발송이에요
  • "워크플로 파일 만들어 줘" — 발행 단계의 env에 발행 스위치(DRY_RUN 같은 값)가 들어가는지, 코드의 기본값과 맞는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
Actions 실행 목록은 매일 초록 체크인데 디스코드에는 아무것도 안 와요. 로그를 펼치면 마지막 줄이 ⑤ 발행 N건 · dry-run이에요 daily.yml의 브리핑 생성·발행 단계 env: 아래에 DRY_RUN 줄이 있는지, 그리고 publish()의 os.environ.get("DRY_RUN", "1") 기본값이에요. 웹훅 주소나 디스코드 설정은 범인이 아니에요 — 요청을 아예 안 보냈거든요 로그 첫 줄 모드:를 봐요. dry-run이면 워크플로에 DRY_RUN: ${{ inputs.dry_run && '1' || '0' }}을 넣고, Run workflow로 dry_run을 끈 채 돌려 ⑤ 발행 … · 보냄이 찍히는지 봐요. 모드: 발행 · 웹훅 주소 없음이 찍혔다면 이 줄의 증상이 아니에요. send가 RuntimeError를 내서 빨간 X로 끝나니, Secret 이름부터 봐요 (워크플로 파일)
같은 날짜의 브리핑 카드가 채널에 두 번 이상 올라와 있어요 send() 주변의 재시도 코드(for 반복, retry)와 성공 판정 조건이에요. 204를 실패로 보는 == 200이 흔한 범인이에요. Actions 실행 목록에서 그날 실행이 두 번 있었는지(스케줄 + 수동 실행)도 봐요 성공 판정이 in (200, 204)인지 보고, 재시도가 있으면 빼요. 중복을 막아 주는 장치는 웹훅 쪽에 없어요. 같은 날 손으로 한 번 더 돌릴 땐 dry_run을 체크해요 (204는 성공이다)
어느 아침 "오늘은 조용합니다"조차 안 왔는데 실행은 초록이에요. 로그가 ② 선별 0 → 0건에서 끝나고 ④·⑤ 줄이 없어요 fan_report 끝에 or "verify"가 남아 있는지(없으면 0건일 때 빈 리스트만 돌려줘요), build()의 add_conditional_edges("select", fan_report, [...]) 목록에 "verify"가 있는지 봐요. build_embeds의 조용한 날 분기는 범인이 아니에요 — 거기까지 가지도 못했어요 노트북에서 collect가 빈 리스트를 돌려주게 잠깐 바꿔 run()을 돌려요. 로그 끝에 ⑤ 발행 조용합니다 · dry-run이 나오면 길이 있는 거예요. 없으면 14편의 같은 증상 줄대로 고쳐요 (발행 노드)
로그에는 ⑤ 발행 5건인데 채널의 기사 카드는 3장이에요. 뒤쪽 순위 기사가 빠져 있어요 build_embeds()의 while 루프와 TOTAL_MAX, 그리고 요약이 유난히 긴 기사예요. 검수나 선별은 범인이 아니에요 — 로그 숫자가 이미 5건이에요 로그에서 [한도] 카드 N장을 빼고 줄을 찾아요. 이 줄을 찍는 코드가 없다면 흔적도 없으니, dry-run으로 돌려 embed N개 · M자를 봐요. M이 5800 가까우면 요약 길이를 줄여요 (카드로 나눠 담기)
며칠째 알림이 없고, Actions 실행 목록에 그 날짜들의 실행 자체가 없어요 Actions 탭의 그 워크플로 화면(꺼졌다는 안내가 있는지), 워크플로 파일이 기본 브랜치에 있는지, 마지막 커밋 날짜예요. 파이썬 코드는 범인이 아니에요 — 실행이 시작도 안 됐어요 Run workflow로 손으로 한 번 돌려요. 손으로는 도는데 스케줄만 안 울리면 브랜치·60일 비활동을 봐요. 엉뚱한 시각에 돌았다면 cron의 UTC 환산을 봐요 (손으로 먼저 한 바퀴)

첫 줄과 셋째 줄은 둘 다 초록인데 채널이 조용해요. 로그 마지막 줄이 · dry-run으로 끝나는지, ② 선별에서 끊겼는지로 갈라요.

이 저장소에서 디스코드로 발행하는 흐름을 점검해서 표로 보여 줘. 아직 코드는 고치지 마.
1. 웹훅으로 요청을 보내는 줄과, 성공으로 판정하는 상태 코드 조건, 재시도 코드가 있는지

3. 선별 결과가 0건일 때 그래프가 발행 노드까지 가는 길이 있는지 (조건부 엣지가 돌려주는 이름 목록)

  3. JSON — {"이름": 값} 모양으로 데이터를 적는 글자 형식으로, 프로그램끼리 데이터를 주고받을 때 가장 널리 써요. ↩
  4. HTTP 상태 코드 — 서버가 요청에 답할 때 붙이는 세 자리 숫자로, 첫 자리 2는 성공·4는 요청 쪽 문제·5는 서버 쪽 문제를 뜻하며 도메인·포트·HTTPS 글에서 표로 정리했어요. ↩
  5. embed — 디스코드 메시지 안에 제목·본문·링크·색·푸터를 칸별로 담아 카드처럼 보여 주는 구조화된 블록이에요. ↩
  6. dry-run — 실제 효과(발행·삭제·결제 등)를 일으키지 않고 무엇을 할지만 출력해 보는 시험 실행이에요. ↩
  7. GitHub Actions — 정해진 시각이나 푸시 같은 사건이 생기면 GitHub 서버가 저장소의 워크플로 파일대로 명령을 대신 실행해 주는 기능으로, GitHub Actions 예약 발행 (5)에서 처음 다뤘어요. ↩
  8. cron(크론 표현식) — 분 시 일 월 요일 다섯 칸으로 "언제 반복 실행할지"를 적는 표기법이에요. ↩
  9. UTC — 세계 표준시로, 한국 표준시(KST)는 UTC보다 9시간 빨라요. ↩
  10. artifact — GitHub Actions 실행이 끝난 뒤에도 그 실행 페이지에서 내려받을 수 있게 올려 두는 파일 묶음이에요. ↩
