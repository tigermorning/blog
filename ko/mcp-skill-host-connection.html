비유 — 신입 직원을 사내 전화번호부에 올리기

2편에서 회사 대표번호와 전화 교환대 이야기를 했고, 3편에서는 그 자료실 안에 앉은 신입 직원(서버 프로그램)을 만들었어요. 이번엔 그 사이를 잇는 일이에요.

자료실 직원은 이미 출근 준비를 마쳤어요. 책상도 있고, 옆에 캐비닛도 붙어 있고, 문 밖 안내판에 담당 업무도 적어 뒀죠. 그런데 교환대에는 이 직원의 존재가 아직 등록되지 않았어요. 그래서 손님이 대표번호로 전화를 걸어도 교환대는 자료실로 이어 줄 수 없어요.

그래서 교환대에 항목을 하나 추가해요. 거기 적히는 건 딱 세 가지예요. 부서 이름(weekly-records), 이 직원을 어떻게 부르는가(어떤 프로그램을 실행하는가), 그리고 어느 방으로 가서 부르는가(어느 폴더에서 실행하는가). 마지막 항목이 특히 중요해요 — "3층 자료실"이라고 적어야지 "여기서 왼쪽"이라고 적으면, 교환대가 어느 층에 있느냐에 따라 도착하는 방이 달라지니까요.

그리고 이 회사는 직원을 상시 대기시켜 두지 않아요. 교환대가 전화가 올 때 그 방에 가서 직원을 앉히고, 통화가 끝나면 정리해요. 그래서 제가 따로 자료실 문을 열어 두고 사람을 앉혀 둘 필요가 없어요.

--directory와 절대 경로 — 출발점을 못 박기

먼저 경로 두 종류를 갈라 둘게요. 절대 경로는 맨 위 폴더부터 목적지까지 전부 적은 위치예요(/Users/student/mcp-skill-practice). 상대 경로는 어떤 폴더를 출발점으로 삼고 거기서부터 적은 위치예요(weekly_records_server.py, data/week-one.json).

여기서 문제가 생겨요. 상대 경로는 출발점이 없으면 뜻이 안 정해져요. 그럼 그 출발점은 누가 정하느냐 — 프로그램이 실행될 때의 현재 작업 폴더7예요. PowerShell 명령어 실습에서 pwd를 칠 때마다 나오던 그 값이요.

그런데 제가 서버를 실행하는 게 아니라 호스트가 실행해요. 호스트가 어느 폴더를 현재 작업 폴더로 삼아 명령을 실행할지는 앱마다, 실행 방식마다 달라요. 제가 정하는 게 아니에요. 그래서 그냥 weekly_records_server.py만 적어 두면, 어떤 날은 되고 어떤 날은 "그런 파일 없음"이 나오는 상태가 돼요.

--directory는 uv가 명령을 실행할 작업 폴더를 지정해요. 이 한 조각이 두 가지를 동시에 못 박아요.

  • uv가 어느 프로젝트인지 찾을 때 기준이 되는 pyproject.toml의 위치
  • 뒤에 적은 상대 경로 weekly_records_server.py의 출발점

그래서 --directory에는 반드시 절대 경로를 적어요. 여기가 흔들리면 그 뒤의 모든 상대 경로가 같이 흔들리거든요. 한 지점만 못 박아 두면 나머지는 따라오는 구조예요.

그리고 여기서 끝이에요. data/week-one.json이나 data/week-two.json은 설정에 안 적어요. 3편에서 DATA_DIR = Path(__file__).with_name("data")로 만들어 뒀기 때문에, 서버 소스는 현재 작업 폴더가 아니라 자기 자신이 있는 폴더 옆에서 data를 찾아요. 설정은 소스 파일까지만 정확히 가리키고, 그다음은 소스가 알아서 하는 구조죠.

uv run --locked — 아까 그 환경으로만 돌리기

uv run은 3편에서 이미 한 번 봤어요. "이 프로젝트의 환경으로 뒤의 명령을 실행하라"는 뜻이에요. 실행 전에 프로젝트 환경이 준비돼 있는지 확인하고, 필요하면 맞춰 준 뒤에 명령을 돌려요.

--locked가 붙으면 조건이 하나 더 생겨요. "uv.lock8에 확정돼 있는 버전 조합을 그대로 쓰고, 이 파일을 새로 만들거나 고치지 말라"는 뜻이에요. 그리고 여기가 중요한데 — 잠금 파일이 없거나 pyproject.toml과 맞지 않으면, 알아서 고쳐서 진행하지 않고 오류로 멈춰요.

멈추는 게 왜 좋은 거냐고 하실 수 있어요. 조용히 버전을 갈아 끼우고 진행하면 어제 되던 게 오늘 다르게 도는데 이유를 알 수 없는 상태가 되거든요. 차라리 여기서 멈추면 "잠금 파일이 안 맞는다"는 한 가지 원인만 보면 돼요. 실패를 조용히 넘기지 않고 한 지점에서 확실히 드러내는 태도인데, 3편의 raise ValueError와 같은 결이에요.

또 하나. 터미널에서 가상환경을 따로 활성화할 필요가 없어요. uv가 --directory로 지정된 프로젝트의 .venv를 알아서 골라 주니까요. 이게 호스트에서 실행할 때 특히 고마운 점이에요 — 호스트가 터미널 설정을 물려받는다는 보장이 없거든요.

mcp run — 왜 python이 아닌가

마지막 조각이 mcp run weekly_records_server.py --transport stdio예요. 3편 끝에서 uv run --locked python weekly_records_server.py를 쳤더니 아무 일도 안 일어났던 거 기억나시죠? 수업에서 제공한 완성 예제에는 서버를 직접 시작하는 진입점9이 없어요. 그래서 파이썬으로 그냥 실행하면 함수와 서버 객체만 정의하고 파일 끝에 도달해 끝나요.

mcp run은 그 파일을 읽어 안에 있는 서버 객체를 찾아 직접 시작해 주는 명령이에요. 그래서 진입점이 없는 파일도 서버로 돌릴 수 있어요. --transport stdio는 2편에서 본 두 통로 중 stdio, 즉 표준 입력·출력으로 메시지를 주고받겠다는 지정이고요.

다만 여기엔 조건이 붙어요. AI와 함께 직접 만든 서버 파일이라면 진입점이 들어 있을 수도 있어요. 그 경우엔 python weekly_records_server.py로 등록해도 돌아가요. 그러니 "무조건 mcp run"이 아니라 "내 파일에 진입점이 있는가"에 따라 갈린다고 기억하는 게 맞아요. 수업에서 배포한 완성 예제를 그대로 쓰는데 python ...으로 등록됐다면, 그게 실패의 원인일 수 있어요.

나쁜 선택 vs 좋은 선택 — 번호부에 방을 적을 때

나쁜 선택좋은 선택
번호부에 "여기서 왼쪽 방"이라고 적는다 = 설정에 weekly_records_server.py만 적고 폴더를 지정하지 않는다 → 내가 실습 폴더에서 앱을 열었을 때는 잘 되다가, 다른 폴더에서 앱을 열자마자 "소스를 찾을 수 없다"로 실패한다. 번호부에 "3층 302호"라고 적는다 = --directory에 실습 폴더의 절대 경로를 적는다 → 앱을 어디서 열든 uv가 같은 프로젝트를 찾고, 그 폴더가 서버 파일 상대 경로의 출발점이 된다.
"버전은 알아서 맞춰 주세요"로 둔다 = --locked 없이 실행한다 → 잠금 파일이 조용히 갱신되고, 어제와 다른 패키지 조합으로 돌면서 원인 모를 차이가 생긴다. uv run --locked로 못 박는다 → 확정된 조합이 아니면 아예 시작하지 않고 오류로 멈춘다. 원인이 "잠금 파일 불일치" 하나로 좁혀진다.
답변 내용이 맞으니 연결도 됐다고 본다 → AI가 파일 읽기 도구로 week-one.json을 직접 읽었어도 내용은 맞을 수 있다. 확인하려던 MCP 경로는 한 번도 안 지나갔는데 성공으로 착각한다. 답변 위의 호출 기록을 펼쳐 어느 도구를 썼는지 본다 → MCP를 안 거쳤으면 "이번에는 weekly-records MCP 도구를 써서 읽어 줘"라고 다시 요청해 실제 경로를 관찰한다.

등록은 AI에게 맡겨도 돼요

설정 파일의 위치와 구조는 앱마다 다르고 버전에 따라서도 바뀌어요. 그래서 저는 직접 쓰기보다 이렇게 부탁했어요.

"바꾼 설정도 설명해 줘"를 꼭 붙이는 이유가 있어요. 설정이 만들어지고 나면 저는 네 가지를 눈으로 확인해요.

  • 서버 이름이 weekly-records인가
  • 실행 명령이 uv인가
  • --directory 뒤가 내 실습 폴더의 절대 경로가 맞는가
  • 기존에 쓰던 다른 MCP 연결이 지워지지 않고 남아 있는가

마지막 항목이 은근히 자주 깨져요. 설정 파일 전체를 새로 써 버리면서 원래 있던 항목이 사라지는 경우가 있거든요.

설정 파일의 뼈대는 대략 이렇게 생겼어요. 앱마다 감싸는 키 이름이 다르지만, 안쪽의 command와 args는 공통이에요.

실행: 호스트의 MCP 설정 파일로 저장 — Claude Code는 프로젝트 폴더의 .mcp.json, OpenCode는 버전에 따라 위치가 달라요

{
  "weekly-records": {
    "command": "uv",
    "args": [
      "--directory", "/Users/student/mcp-skill-practice",
      "run", "--locked",
      "mcp", "run", "weekly_records_server.py",
      "--transport", "stdio"
    ]
  }
}

이게 목업 데이터와 REST API에서 처음 봤던 JSON10이에요. 바깥 이름표가 서버 이름, command가 실행할 프로그램, args가 그 뒤에 이어 붙는 인자들의 목록이에요. 명령줄에서 빈칸으로 나뉘던 조각들이 여기서는 대괄호 안에 하나씩 따로 들어가는 거죠.

OpenCode를 쓴다면 한 가지 더 있어요. V1과 V2의 설정 구조가 달라요. V1은 mcp 바로 아래에, V2는 mcp.servers 아래에 서버를 등록해요. 그래서 이렇게 물어보는 게 안전해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

내 OpenCode 버전을 확인하고, 그 버전에 맞게 연결해 줘.

터미널에선 되는데 앱에서만 안 될 때 — PATH

이 상황을 만나면 꽤 당황스러워요. 터미널에서 uv --version은 멀쩡히 나오는데, 앱은 "uv를 찾을 수 없다"고 해요. 둘 다 같은 컴퓨터인데요.

원인은 PATH11예요. 터미널·셸·커널·프롬프트에서 다뤘던 그 "명령 이름만 듣고 실행 파일을 찾아볼 폴더 목록" 말이에요. 여기서 핵심은, 이 목록이 프로그램마다 따로 들려 있다는 점이에요. 앱이 켜지던 시점의 목록과, 제가 지금 연 터미널의 목록이 서로 다를 수 있어요. 그 글에서 "Node.js를 설치했는데 새 창에서만 인식되던" 일과 정확히 같은 종류예요.

해결은 간단해요. 이름 대신 절대 경로를 적어 주면 목록을 뒤질 필요 자체가 없어져요. 여기서도 아까 --directory와 똑같은 원리가 반복되는 거죠.

실행: 로컬 터미널

# macOS · Linux
command -v uv

# Windows PowerShell
(Get-Command uv).Source

여기 나온 경로를 설정의 command 자리에 uv 대신 넣으면 돼요. 이것도 AI에게 맡길 수 있어요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

앱에서 uv를 못 찾으니, 설치된 uv의 절대 경로를 확인해서 설정에 넣어 줘.

※ Claude Code와 OpenCode V1의 명령 형식은 Claude Code 2.1.258, OpenCode 1.18.27 기준이에요. 버전이 올라가면 설정 키 이름이나 위치가 달라질 수 있어요.

연결 확인 → 실제 호출 → 원본 대조

여기서부터가 이번 편의 진짜 목적이에요. 세 단계를 순서대로 밟아요. 한 단계씩 확인하는 이유는, 실패했을 때 어느 단계까지 갔는지가 그대로 원인을 가리키기 때문이에요.

단계무엇을 하나여기서 확인되는 것
① 연결 확인호스트의 MCP 목록에서 weekly-records를 찾고, 그 아래 도구에 get_weekly_records가 있는지 본다서버 프로세스가 떴고, tools/list로 도구 목록이 넘어왔다
② 실제 호출"연결한 MCP로 첫 주 업무 기록을 읽어 줘"라고 요청한다모델이 이 도구를 골랐고, tools/call이 실제로 오갔다
③ 원본 대조돌아온 결과를 data/week-one.json과 나란히 놓고 맞춰 본다도구가 원본을 고치지 않고 그대로 가져왔다

①에서 도구 이름을 볼 때 한 가지 알아 둘 게 있어요. 호스트가 서버 이름을 앞에 붙여 표시하는 경우가 있어요. 그래서 화면에 정확히 get_weekly_records라고만 안 나오고 앞에 뭔가 더 붙어 있을 수 있는데, get_weekly_records가 포함돼 있으면 맞아요. 이름이 조금 달라 보인다고 잘못된 게 아니에요.

그리고 ①이 됐다고 ②가 자동으로 되지는 않아요. 연결은 "이런 도구가 있다"까지고, 실제로 부를지는 그때그때 모델이 정하는 일이거든요. 2편에서 "도구를 연결한 것과 자료를 받은 것은 다른 상태"라고 갈라 뒀던 그 지점이 여기서 실습으로 나타나요.

호출 기록(trace)에서 볼 세 가지

AI의 최종 답변만 보면 ②를 확인할 수 없어요. 답변 바로 위에 접혀 있는 도구 사용 부분을 펼쳐야 해요. 이게 호출 기록(trace)이에요 — 어느 도구에 어떤 값을 보냈고 무엇을 받았는지 순서대로 남은 기록이죠.

볼 곳이번에 기대하는 값어긋나면 무슨 뜻인가
호출한 도구get_weekly_records가 포함된 이름다른 이름(예: 파일 읽기 도구)이면 MCP 경로를 안 지났다
보낸 입력week의 값이 week-one다른 값이면 모델이 '첫 주'를 다르게 옮긴 것
받은 결과첫 주의 날짜와 업무 기록 4건비었거나 오류면 서버 안에서 걸린 것

여기서 재미있는 지점이 하나 있어요. 제가 한 말은 "첫 주"인데, 도구에 실제로 간 값은 week-one이에요. 이 번역을 누가 했느냐 — 모델이에요. 그리고 모델이 그렇게 옮길 수 있었던 이유는, 3편에서 함수 설명(docstring)에 "week-one 또는 week-two"라고 지원하는 값을 적어 뒀기 때문이에요. 설명을 대충 썼다면 "1주차"나 "first" 같은 값이 갔을 거고, 그러면 서버의 허용 검사에서 막혔겠죠. 도구 설명이 실제로 일하는 순간이 여기예요.

그리고 자주 겪는 상황 하나. AI가 MCP 대신 자기 파일 읽기 도구로 week-one.json을 직접 열어 답할 수 있어요. 내용은 맞아요. 하지만 제가 확인하려던 경로는 아직 한 번도 안 지나간 상태예요. 이럴 땐 이렇게 다시 요청해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이번에는 weekly-records MCP 도구를 사용해서 읽어 줘.

원본과 대조하기 — 없는 값이 생기지 않았는가

③은 눈으로 하는 작업이에요. data/week-one.json을 옆에 열어 두고 맞춰 봐요. 특히 비어 있는 값을 집중해서 봐요.

개념 설명용 코드 — 실습 원본에서 대조에 쓸 부분만 잘라 온 발췌예요

{
  "week": "week-one",
  "report_date": "2026-09-04",
  "records": [
    {
      "id": "TASK-102",
      "title": "로그인 안내 문구 개선",
      "owner": "지우",
      "status": "개발 완료",
      "deployed_at": null,
      "verification": "미실시"
    }
  ]
}

실제 전체 결과에는 records에 TASK-101부터 TASK-104까지 네 건이 있어야 해요. 위는 대조용으로 한 건만 잘라 온 거예요.

이제 두 군데를 봐요.

  • TASK-102 — status는 '개발 완료'인데 deployed_at은 null이에요. 즉 배포 날짜가 기록에 없어요. 그런데 AI의 답변 문장에 배포 날짜가 등장했다면, 그게 원본에서 온 건지 문장을 만드는 과정에서 생긴 건지 구분해야 해요. 근거 없는 내용이 사실처럼 섞여 드는 것을 환각12이라고 하는데, 대조는 그걸 잡아내는 가장 단순한 방법이에요.
  • TASK-103 — owner가 null이에요. 담당자가 기록에 없는 상태죠. 이게 비어 있는 채로 돌아오는지 보세요. 누군가의 이름이 채워져 있으면 그건 원본에 없던 값이에요.

지금 이 도구는 기록을 읽어 전달하는 역할까지예요. 빈 값을 추정해 채우거나, '개발 완료'를 보고서에서 '완료'로 분류할지 정하는 일은 하지 않아요. 그 판정 기준을 정하는 이야기는 시리즈 뒤쪽 Skill 편의 몫이에요. 지금은 판정하지 않는 통로를 확보하는 게 목적이고, 그래야 나중에 우리 팀 기준으로 판정할 근거가 남아요.

오류가 알려 주는 연결 단계

정상 결과를 받았다면 일부러 한 번 실패시켜 봐요. 지원하지 않는 주를 요청하는 거예요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

같은 도구로 week-three 기록을 읽어 줘.

현재 서버는 week-one과 week-two만 허용하니까, 실제로 호출이 이루어지면 오류가 돌아와요. 그런데 이 오류는 서버가 안 뜨는 것과 완전히 다른 상태예요. 요청이 도구까지 도달했고, 함수가 입력을 확인한 뒤 거절한 거니까요. 3편의 WEEK_FILES 허용 검사가 실제로 도는 걸 눈으로 보는 순간이에요.

한 가지 갈림길이 있어요. 모델이 도구 설명을 먼저 읽고 호출도 안 해 보고 "지원하지 않는 주입니다"라고 답할 수도 있어요. 그건 실패가 아니라 모델의 사전 판단을 관찰한 것이에요. 호출 기록을 펼쳐 보면 둘을 바로 구분할 수 있어요 — 기록에 호출이 아예 없으면 후자예요.

이제 잘 안 될 때의 표예요. 증상마다 봐야 할 단계가 다르다는 게 핵심이에요.

증상먼저 볼 곳왜 거기인가
목록에 서버가 아예 없다설정을 저장한 프로젝트와 지금 앱에서 연 폴더프로젝트 단위 설정은 그 프로젝트를 열었을 때만 읽혀요
서버가 시작되지 않는다앱이 uv를 찾는지, 실습 폴더의 환경이 준비됐는지앱의 실행 파일 검색 목록(PATH)과 프로젝트 환경, 두 가지가 원인이에요
잠금 파일 관련 오류가 난다pyproject.toml과 uv.lock이 함께 있는지--locked는 잠금 파일을 새로 만들거나 고쳐서 진행하지 않아요
소스나 데이터를 찾지 못한다--directory의 절대 경로, 그 안의 서버 파일과 data 폴더작업 폴더가 정해져야 상대 경로인 서버 파일의 출발점도 정해져요
연결은 됐는데 MCP 호출이 없다호출 기록에서 모델이 고른 도구파일 직접 읽기 등 다른 행동을 골랐을 수 있어요
없는 주차 호출이 실패한다보낸 입력과 서버가 지원하는 주차고장이 아니라 입력 검사가 거절한 결과일 수 있어요
소스를 고쳐도 이전 동작이 계속된다실행 중인 서버를 다시 시작했는지디스크의 파일을 저장해도 이미 돌고 있는 프로세스는 새 소스를 다시 읽어야 해요

마지막 줄이 특히 허탈한 종류예요. 코드를 분명히 고쳤는데 결과가 그대로라 코드를 계속 들여다보게 되거든요. 그런데 원인은 코드가 아니라 메모리에 이미 올라가 있는 옛날 서버예요. 파일은 설계도고, 프로세스는 그 설계도로 이미 지어 놓은 건물이라 설계도만 고쳐서는 안 바뀌어요.

오류 메시지를 그대로 붙여넣고 이렇게 물어보면 단계부터 좁힐 수 있어요.

① 절대 경로를 상대 경로로 바꿔 보기. --directory의 값을 지우거나 상대 경로로 바꾸고 앱을 다시 시작해 보세요. 그리고 실습 폴더를 열었을 때와 전혀 다른 폴더를 열었을 때 결과가 어떻게 갈리는지 보세요. 한쪽에서만 되는 상태가 왜 위험한지 손에 잡혀요.

② 같은 질문을 두 가지 방식으로 물어보기. 먼저 "첫 주 업무 기록 읽어 줘"라고만 하고, 다음엔 "weekly-records MCP 도구로 읽어 줘"라고 해 보세요. 두 번의 호출 기록을 나란히 놓고 보면, 답변이 같아 보여도 지나온 길이 다를 수 있다는 걸 알게 돼요.

③ 서버를 고치고 다시 시작하지 않아 보기. 3편의 실험대로 @mcp.tool() 한 줄을 지우고 저장한 뒤, 앱을 다시 시작하지 않은 채로 도구 목록을 보세요. 그다음 다시 시작하고 또 보세요. 표 마지막 줄의 "실행 중인 프로세스가 새 소스를 다시 읽어야 한다"가 무슨 말인지 이때 확 와닿아요.

세 실험 다 정상 동작이 아니라 실패의 모양을 눈에 익히는 게 목적이에요. 이제 업무 데이터를 가져오는 통로 하나가 준비됐어요. 같은 방식으로 문서 검색·달력 조회·다른 팀 기록도 붙일 수 있고요. 그런데 여기서 새 문제가 생겨요 — 도구를 자꾸 붙이면 대화는 짧은데 문맥이 자꾸 커지거든요. 그 이야기는 다음 편에서 할게요.

  1. 호스트(host) — 내가 대화하는 AI 앱으로, 모델 사용과 서버 연결·실행 허용을 관리하는 쪽이며 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
  2. 절대 경로(absolute path) — 맨 위 폴더부터 목적지까지 빠짐없이 적어 어디서 읽어도 같은 곳을 가리키는 위치 표기. ↩
  3. 상대 경로(relative path) — 어떤 폴더를 출발점으로 삼아 거기서부터 적은 위치 표기라, 출발점이 바뀌면 가리키는 곳도 바뀌어요. ↩
  4. 프로세스(process) — 저장된 프로그램 파일이 실제로 실행되어 돌아가고 있는 상태로, 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
  5. 호출 기록(trace) — 어느 도구에 어떤 입력을 보내 무엇을 받았는지 순서대로 남겨 둔 기록. ↩
  6. 인자(argument) — 명령이나 함수를 실제로 실행할 때 이번 한 번을 위해 넣어 주는 값으로, 호스트·클라이언트·서버가 나누는 대화에서 처음 다뤘어요. ↩
  7. 현재 작업 폴더(current working directory) — 프로그램이 상대 경로를 풀 때 출발점으로 삼는 폴더로, PowerShell 명령어 실습의 pwd가 보여 주는 값이에요. ↩
  8. 잠금 파일(lock file) — 설치할 패키지들의 버전 조합을 확정해 적어 둔 파일로, 업무 기록 서버 직접 만들기의 uv.lock이 이것이에요. ↩
  9. 진입점(entry point) — 프로그램을 실행했을 때 가장 먼저 실행되도록 정해 둔 시작 지점. ↩
  10. JSON — 설정이나 데이터를 "이름: 값" 꼴로 중괄호 안에 적는 형식으로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  11. PATH — 명령 이름만 듣고 실행 파일을 찾아볼 폴더들의 목록이며, 터미널·셸·커널·프롬프트에서 처음 다뤘어요. ↩
  12. 환각(hallucination) — 모델이 근거 없는 내용을 사실인 것처럼 만들어 내는 현상으로, MCP — AI를 내 데이터에 꽂는 USB-C에서 처음 다뤘어요. ↩
