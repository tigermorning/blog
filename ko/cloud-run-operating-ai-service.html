배포한 AI 서비스가 말없이 틀리는 순간 — 타임아웃, 인스턴스, 비용, 로그 (3)

※ 이 글은 모두의연구소(모두연) 학습 자료를 제 나름의 말로 다시 정리한 글이에요.

AI 서비스를 운영한다는 것은 서버가 정상이라고 말해도 손님이 답을 못 받을 수 있다는 것을 알고, 타임아웃과 인스턴스 수와 비용 한도를 실제로 걸린 시간과 로그를 근거로 정하는 일이다.

이 글을 읽기 전에

이런 게 궁금했다면
  • 요청 타임아웃을 줄이면 답이 끊기고, 끊기면 사용자에게는 어떻게 보이나요?
  • 배포할 때마다 대화가 사라지는 이유는 뭔가요?
  • 인스턴스를 2개로 제한하면 비용도 막히나요?
  • 오류가 났을 때 터미널 메시지와 로그 중 어디를 믿어야 하나요?
읽고 나면 할 수 있는 것
  • 서버 기록과 사용자 화면이 서로 다른 말을 할 수 있다는 것을 사례로 말할 수 있어요.
  • 최대 인스턴스가 막는 것과 못 막는 것, 총액을 막는 장치를 구분할 수 있어요.
  • 터미널 메시지는 결과이고 원인은 앞선 로그에 있다는 것을 설명할 수 있어요.
어디에 쓰나
  • 2편에서 올린 서비스를 다른 사람이 써 보게 하기 전에. 주소를 아는 누구나 내 비용으로 서비스를 쓸 수 있어요.

← 이전 편 Cloud Run에 소스를 배포한다는 것 — 코드 폴더 하나가 공개 주소가 되기까지 (2)

2편에서 AI 친구 서비스를 Cloud Run(코드를 올리면 인터넷 주소를 만들어 주는 구글의 서비스)에 올려 공개 주소를 만들었어요. 올렸다고 끝이 아니에요. 주소를 아는 누구나 이 서비스를 쓸 수 있어요. 요청 하나하나에 내 키로 LLM(글을 만들어 주는 AI) 비용이 나가요. 이 글은 올린 서비스를 일부러 괴롭혀 보며 운영할 때 정해야 할 값을 직접 확인한 기록이에요. 확인하지 못한 것은 그렇게 적었어요. 비유는 1·2편의 식당을 이어 써요. 손님 한 명의 주문이 요청이고, 주방이 인스턴스1예요.

답이 끊긴다 — 요청 타임아웃

이 서비스는 답을 만드는 대로 조금씩 보내는 스트리밍으로 답해요. 그런데 대화 요청은 답을 다 보낸 뒤에도 끝나지 않아요. 같은 요청 안에서 방금 대화를 기억으로 정리해 저장하기 때문이에요. 요청이 요청 타임아웃2(기본 300초, 기다려 주는 최대 시간)을 넘으면 Cloud Run은 연결을 끊어요. 끊기는 곳이 두 군데예요.

  • 답을 보내는 중: "내일 서울은 맑다가"에서 멈춰, 뒤에 오던 비 소식이 사라져요.
  • 기억 정리 중: 답은 멀쩡한데 방금 말한 일정이 저장되지 않아요.

제 서비스에서 요청 하나는 약 5초(답 4초, 기억 정리 1초)가 걸렸어요. 타임아웃을 줄여 봤어요.

아래 한 줄은 요청 타임아웃을 1초로 줄이는 명령이에요. 직접 해 보는 실습이에요.

실행: 로컬 터미널 — 서비스 설정만 바꾸고 새 리비전이 하나 생겨요. 실습이 끝나면 300초로 되돌려요

gcloud run services update friend-agent --region us-central1 --timeout 1

3초로 줄였을 때는 끊기지 않았어요(4초짜리 요청이 정상 종료). 이유는 알 수 없었어요. 1초로 줄이자 화면에 "(답을 받지 못했어요)"와 "응답이 끝까지 오지 않았어요" 안내가 떴어요. 여기서 가장 중요한 것을 봤어요. 그 요청의 서버 기록은 200(정상)이었어요. 서버 로그(서버가 남기는 일기)만 봤다면 아무 일도 없었던 거예요. 그런데 사용자는 답을 못 받았어요. 이 앱은 스트림 종료 신호가 없으면 안내를 붙이게 만들어져 있어서 알 수 있었어요. 그런 확인이 없다면 사용자는 잘린 답을 그대로 믿어요. 끊김보다 "정상처럼 보이는 틀린 결과"가 진짜 위험이에요.

타임아웃은 짐작이 아니라 실제 걸린 시간으로 정해요. 콘솔(웹 관리 화면)의 측정항목은 50번째·99번째 백분위수3를 보여 줘요. 평균을 기준으로 삼지 말고 느린 쪽보다 넉넉하게 잡아요.

대화가 사라진다 — 인스턴스와 콜드 스타트

인스턴스는 지금 켜져 있는 주방 하나예요. 공개 주소라 누구나 부를 수 있으니 최대 인스턴스(동시에 켜 둘 주방 수)에 상한을 걸어요.

아래 한 줄은 최대 인스턴스를 2로 정하는 명령이에요. 직접 해 보는 실습이고, 실행하면 대화가 사라져요.

실행: 로컬 터미널 — 새 리비전이 생기고 그 순간 서버 메모리의 캐릭터와 대화가 사라져요

gcloud run services update friend-agent --region us-central1 --min-instances 0 --max-instances 2

실행해도 화면은 그대로였는데, 새로고침하자 캐릭터가 사라졌어요. 이 앱은 캐릭터와 대화를 인스턴스 메모리(주방이 켜져 있는 동안만 기억하는 곳)에만 둬요. 새 리비전(설정을 바꿔 새로 만든 버전)은 새 주방에서 시작해서 이전 장부가 이어지지 않아요. 열려 있는 화면은 받아 둔 내용을 보여 줄 뿐이에요. 서버에 다시 물어보는 순간(새로고침)에야 드러나요. 사라진 줄 모르고 있다가 한꺼번에 드러나는 것이 더 위험해요. 남겨야 할 데이터는 컨테이너 밖 데이터베이스에 둬야 해요.

최소 인스턴스를 0으로 두면 한가할 때 주방이 꺼져요. 다음 요청 때 새로 켜느라 첫 답이 늦어져요. 이것이 콜드 스타트예요. 15분 쉬었다 말을 걸었을 때는 못 봤고, 1시간 넘게 쉰 뒤에는 요청이 15.56초 걸렸어요(평소 2~5초). 같은 시각 로그에 "앱을 시작합니다."가 찍혀 있어서 콜드 스타트로 봐요. 다만 로그로 추정한 것이고, 인스턴스 수 그래프로 직접 확인한 것은 아니에요.

돈은 어디서 나가나 — 최대 인스턴스는 상한이 아니에요

최대 인스턴스를 2로 걸면 비용도 막힌다고 생각하기 쉬워요. 하지만 그렇지 않아요. 주방 하나는 동시성4(기본 80)만큼 주문을 한꺼번에 받아서, 주방 2개면 동시에 160건을 처리해요. 최대 인스턴스는 한 번에 처리하는 양(속도)만 제한할 뿐, 시간이 흐르며 쌓이는 호출 수는 막지 못해요.

설정막는 것막지 못하는 것
Cloud Run 최대 인스턴스한 번에 처리하는 요청 수쌓이는 호출 수
LLM 제공사의 월 사용 한도한 달 LLM 비용 총액Cloud Run 요금
Google Cloud 예산 알림없음(알려 주기만 해요)지출 자체

총액을 막는 것은 LLM 제공사의 월 사용 한도예요. 내 키로 운영한다면 배포 전에 월 한도를 작게 걸고 한도의 절반쯤에서 알림이 오게 하는 것이 첫 작업이에요. 돈은 대부분 LLM 쪽에서 나가요. 메시지 하나에 LLM을 세 번(도구 고르기, 답하기, 기억 정리) 불러요. 사용자가 자기 키를 넣는 방식은 요청 본문에 키가 실려 오니, 요청 본문 전체를 로그에 남기면 키가 그대로 새는 점을 조심해야 해요.

로그로 원인 찾기 — 터미널 메시지는 결과일 뿐이에요

Cloud Run 로그 탭에는 남기는 주체가 다른 세 종류가 섞여 나와요. 로그는 프로그램이 남기는 기록이에요. 요청 로그(Cloud Run이 요청마다 자동으로, 접수대 기록), 컨테이너 로그(내 앱이 직접, 주방장 메모), 시스템 로그(플랫폼이 주방을 켜고 끌 때, 관리실 기록)예요.

일부러 실패하는 배포를 만들었어요. 이 앱은 LLM_PROVIDER 값이 지원하는 것이 아니면 오류를 남기고 시작하지 않아요.

아래 한 줄은 앱이 모르는 설정값을 일부러 넣어 배포를 실패시키는 명령이에요. 직접 해 보는 실습이에요.

실행: 로컬 터미널 — 실패하는 것이 정상이에요. 실패한 리비전은 트래픽을 받지 않아 서비스는 이전 리비전으로 계속 답해요

gcloud run services update friend-agent --region us-central1 --update-env-vars LLM_PROVIDER=unknown

터미널은 "컨테이너가 포트 8080을 열지 못했다. 포트 설정이 틀렸거나 타임아웃이 짧을 수 있다"고 말했어요. 이것만 보면 포트나 타임아웃 설정을 의심하기 쉬워요. 여기서 헷갈리는 게 정상이에요. 로그를 시간순으로 모으니 순서가 보였어요. 새 인스턴스가 켜지고 → 앱이 "LLM_PROVIDER 값 'unknown' 를 알 수 없어 앱을 시작하지 않습니다"라는 ERROR를 남기고 꺼지고 → 플랫폼이 시작 실패를 기록하고 → 터미널에는 마지막 결과만 나왔어요. 터미널 메시지는 결과이고, 원인은 앞선 컨테이너 로그의 ERROR 줄에 있었어요. 환경변수를 지워 되돌렸고, 실패하는 동안에도 서비스는 이전 리비전으로 계속 답했어요.

원인을 코딩 에이전트와 고칠 때도 짐작이 아니라 근거(증상, 시간 범위, 리비전, 찾은 로그 줄)를 건네요.

다만 서버 로그는 요청이 성공했는지까지만 말해 줘요. 요청은 200으로 끝났는데 답이 엉뚱했다면, 요청 한 건 안에서 거친 단계를 따로 남겨야 해요. 그 이야기는 Langfuse로 에이전트 문제 찾기에서 이어 가요.

직접 해 본 기록 — 제 서비스 «루틴 도장»을 Cloud Run에 올려 운영해 보니

위 실습은 강의에서 쓴 «AI 친구» 서비스(friend-agent)로 했어요. 이어서 제 서비스 «루틴 도장»(루틴 만들기가 어려운 사람을 위한 앱에 붙인 AI 도우미, 서비스 이름 routine-coach)에도 같은 일을 해 봤어요. 배포하고 운영해 본 범위와, 하지 못한 범위를 나눠 적어요.

올린 서비스 — 리비전 9개를 만들었어요

  • Cloud Run에 소스를 배포했어요(서비스 이름 routine-coach). 배포 전에 세 가지를 점검했어요: 앱이 PORT 환경변수로 포트를 여는지, 코드 안에 키가 없는지, 라이브러리 목록이 맞는지. 키는 Secret Manager의 시크릿으로 연결했고, 최대 인스턴스는 2로 제한했어요.
  • 배포를 9번 해서 리비전이 9개 생겼어요(첫 배포, 말투 설정, 사용자 키 방식, 화면 개편, 대화 개선, 문구 정리 등). 이전 리비전은 롤백(옛 버전으로 되돌리기)에 쓰려고 남겨 뒀어요.
  • 이 도우미는 대화를 내 브라우저에만 저장하고 서버에는 저장하지 않아요. 그래서 위에서 본 «새 리비전이 뜨면 서버 메모리의 대화가 사라지는» 문제는 이 서비스에서는 다른 모양이에요.

요청 로그에서 읽은 것

요청 로그를 조회해서 /api/chat 요청의 상태 코드와 응답 시간을 읽었어요. 상태 코드는 200이었고, 응답 시간은 약 1.7~2.3초였어요. 최근 6시간 로그에서 대화와 도장 그림 요청은 모두 제 PC의 같은 IP에서 왔고, 다른 IP는 페이지를 열어 본 요청(GET) 3건뿐이었어요. 즉 다른 사람이 도우미와 대화한 기록은 아직 없어요. 콘솔의 요청 수 그래프에도 그날 오후에 작은 막대(최대 약 0.04건/초)만 있었어요.

롤백 — 주소가 이전 화면으로 돌아오는 것을 봤어요

이전 리비전(00007)에 트래픽 100%를 돌렸더니, 같은 주소가 이전 화면으로 응답했어요. 그다음 당시 최신 리비전(00008)으로 복귀했고, 복귀 후 트래픽이 100%인 것도 확인했어요. 걸린 시간은 약 1분이에요. 지금은 리비전 00009가 서비스 중이에요.

부하 테스트 — 동시성과 최대 인스턴스를 바꿔 가며

부하 테스트용으로 «2초 기다렸다 응답하는» 시험용 서비스(/slow, LLM은 부르지 않아요)를 따로 만들었어요. 설정마다 동시 요청 50개를 2번씩 보내고, 끝나면 서비스를 지웠어요. 시험용 서비스라서 LLM 비용은 나가지 않았어요.

설정결과알아 둘 것
A: 동시성 80, 최대 인스턴스 3200이 50/50개. 걸린 시간 중앙값 4.5초와 2.3초(2회). 인스턴스 1개인스턴스 1개가 50개를 한꺼번에 받았어요
B: 동시성 1, 최대 인스턴스 20200이 18/18개, 429가 32/32개최대를 20으로 뒀는데도 인스턴스는 3개까지만 떴어요. 다시 측정해도 같았고 원인은 못 찾았어요
C: 동시성 1, 최대 인스턴스 3200이 21/34개, 500이 29/16개. 로그 문구는 no available instance2회 결과가 달랐어요(200이 21개와 34개, 500이 29개와 16개)

읽는 법. 동시성이 높으면 인스턴스 1개가 요청 50개를 함께 받고, 동시성이 낮으면 요청이 거절(429)되거나 오류(500)가 나요. 여기까지는 직접 확인했어요. 이 서비스에는 앱 자체 제한도 있어서, 대화 요청을 20건만 통과시키고 나머지는 429로 돌려 보내는 시험을 따로 했고 그대로 동작했어요.

사용자 키 방식(BYOK) — 확인한 것과 못 한 것

BYOK는 «Bring Your Own Key», 사용자가 자기 API 키를 넣어 쓰는 방식이에요. 서버에는 BYOK 모드(BYOK_MODE)와 요청 헤더로 키를 받는 부분을 만들었고, 화면에는 설정의 «내 API 키» 칸을 만들어서 배포했어요.

  • 확인한 것: 형식이 틀린 키를 넣으면 대화와 도장 그림 요청 모두 안내 문구가 나오는 것을 배포 주소에서 확인했어요. 로그에 sk-로 시작하는 문자열이 없는 것도 확인했어요(위에서 말한 «요청 본문을 통째로 로그에 남기면 키가 샌다»는 점을 검사한 거예요).
  • 확인하지 못한 것: 맞는 키로 배포 주소에서 대화하는 것, 그리고 사용 한도 초과(keyLimit) 동작은 아직 확인하지 못했어요.

다른 사람이 써 보게 하기

다른 수강생의 서비스에 접속해서 대화해 봤고, 제 서비스에는 후기를 부탁하는 글을 남겼어요. 주소를 공유하면서 이렇게 적었어요: 제 API 키로 요청마다 비용이 나가니 가볍게 몇 번만 써 달라는 것, 오래 안 쓰다 깨어나면 첫 답이 느릴 수 있다는 것(콜드 스타트), 연구 근거 카드는 아직 출처 검수 전이라 조언은 참고용이라는 것. 후기로는 말투 설정이 대화에 반영되는 느낌이었는지, 끊기거나 이상한 답이 있었는지, 한 줄 평을 청했어요.

하지 못한 것

  • 맞는 키로 하는 BYOK 대화와 한도 초과(keyLimit) 동작 확인(위에 적은 대로).
  • 부하 테스트 B에서 최대 인스턴스를 20으로 뒀는데 3개까지만 뜬 이유.
