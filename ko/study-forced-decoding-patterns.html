로짓 마스킹 · 문법 — 강제 장치 두 가지

출력 형식을 "부탁"하는 것과 "강제"하는 것은 근본적으로 다르다 — 2장의 첫 두 패턴은 모두 강제 장치다. 저자 공식 코드 저장소의 실제 노트북(01_logits_masking, 02_grammar)을 근거로 확인했다.

학습 목표

  • 출력 형식을 "부탁"하는 것과 "강제"하는 것의 차이를 설명한다. 이 날의 두 패턴은 모두 강제 장치다.
  • 로짓 마스킹이 디코딩 시점에 개입한다는 사실이 왜 중요한지, 그래서 어떤 실패를 원천 봉쇄하는지 말한다.
  • 문법 기반 제약(정규표현식·CFG·JSON 스키마)이 로짓 마스킹과 어떻게 다른지, 구현 부담은 어느 지점에 생기는지 안다.
  • 두 패턴의 고려사항(tokenizer 의존성, 생성 속도 지연, 표현력 손실)을 우리 생산 환경의 실제 리스크로 엮는다.

M1

로짓 마스킹이 디코딩 시점에 개입한다는 게, 실제 코드에서는 정확히 어떤 모습인가?

📓 examples/01_logits_masking/0_logits_masking.ipynb 
class BrandLogitsProcessor(LogitsProcessor):
    def __call__(self, input_ids, input_logits):
        output_logits = input_logits.clone()
        num_matches = [0] * len(input_ids)
        for idx, seq in enumerate(input_ids):
            decoded = self.tokenizer.decode(seq)
            num_matches[idx] = evaluate(decoded, self.positives, self.negatives)
        max_matches = np.max(num_matches)
        for idx in range(len(input_ids)):
            if num_matches[idx] != max_matches:
                output_logits[idx] = -10000
        return output_logits
모범답

프롬프트에 "브랜드 단어만 써줘"라고 부탁하면, 모델이 안 들을 확률이 항상 남는다 — 확률적 지시 따르기일 뿐이다. 로짓 마스킹은 매 토큰이 뽑히기 직전, 이 __call__이 후보 시퀀스마다 점수(num_matches)를 다시 계산해서 최고점이 아닌 후보의 로짓을 -10000으로 뭉갠다 — 즉 애초에 고를 수 있는 후보에서 빼버린다. 부탁은 "안 지켜질 수 있는 요청"이고, 강제는 "지켜지지 않는 선택지 자체가 없어지는 것"이라는 차이가 이 15줄 코드 안에 그대로 들어있다.

직접 확인해볼 것

evaluate() 함수 정의를 찾아서, positives·negatives 판정이 어떤 기준으로 이뤄지는지 보라 — 의미(semantic)를 보는가, 아니면 다른 방식인가?

확인 포인트: num_positive = np.sum([1 for phrase in positives if phrase in descr]) — 문자열이 그대로 포함되는지만 본다. "의미"를 이해해서 판단하는 게 아니라 리터럴 문자열 매칭이다. 이게 K2(아래)의 답이기도 하다.

M2

규칙을 만족하는 후보가 하나도 안 남으면(막다른 길) 로짓 마스킹은 어떻게 하나?

모범답

ch2 본문 2.1.3의 이합체시(아크로스틱) 예제가 실제 사례다. 매 행을 만들 때마다 "지금까지 만든 행의 첫 글자를 이으면 목표 단어의 접두사가 되는가"를 검사하고, 만족하는 후보가 하나도 없으면 방금 만든 행을 지우고 그 이전 지점으로 되감는다 — 이게 역추적(backtracking)이다. 모든 행을 지워도 안 되면 아예 다른 시작 단어로 처음부터 다시 시작한다. 최대 시도 횟수를 넘기면 거절 메시지를 낸다.

직접 확인해볼 것

역추적이 "한 걸음 물러나기"라는 게 1장 D3(빔 탐색)과 어떻게 겹치는지 생각해보라 — 둘 다 "경로 여러 개를 미리 내다본다"는 점에서 같은 계열의 기법인가?

확인 포인트: 그렇다. 로짓 마스킹의 역추적도 내부적으로 빔 탐색처럼 여러 후보 경로를 동시에 유지하다가, 규칙을 어긴 경로를 가지치기(pruning)하는 방식으로 구현된다 — "여러 수를 미리 내다보다가 나쁜 수만 골라 지운다"는 원리가 1장부터 계속 반복되는 셈이다.

G1

문법 제약이 "형식은 맞는데 내용이 틀린" 답을 강제로 만들어내는 실제 사례가 있나?

📓 examples/02_grammar/1_applying_grammar.ipynb — 실제 실행 결과 
# 문법: root ::= (expr "=" ws term "\n")+   (등호(=)만 허용, 부등호 없음)
# 질문: "Bill·Mae 중 누가 사과가 오렌지보다 많은가?" (원래 ">" 비교가 필요한 문제)
1 +2 = 3 2 +4 = 6 3 = 3 6 = 6 3 = 6 3 = 6 3 = 6 ... (똑같은 "3 = 6" 무한 반복)
모범답

있다. 문법이 "등호(=)"만 허용하고 "초과(>)" 기호를 아예 문법에서 뺐기 때문에, 모델은 정답인 (3+2) > (2+4)를 구조적으로 쓸 수 없다. 그 결과 형식은 끝까지 완벽하게 지켜지면서(등호 형태 유지) 내용은 "3 = 6"이라는 명백히 틀린 문장을 반복해서 뱉는, 사실상 무한 루프에 가까운 실패가 난다. 형식 100% 보장이 정확도 향상을 보장하지 않는다는 걸 실제 실행 결과로 확인할 수 있는 사례다.

직접 확인해볼 것

이 문법에 "탈출구"를 하나 추가한다면 어떤 규칙을 더 넣어야 이 무한반복을 막을 수 있을까?

확인 포인트: 최소한 >·< 비교 연산자를 expr 규칙에 추가하거나, 2.2.4 고려사항에서 나온 것처럼 Literal["Unknown"]류의 "모르겠다/이 문법으로 표현 불가" 탈출 경로를 문법에 남겨둬야 한다. 탈출구가 없으면 모델은 끝까지 "그 안에서 제일 그럴듯한 틀린 답"을 억지로 계속 생성한다.

G2

BNF 문법·JSON 모드·데이터클래스 세 방식 중, 실무에서 기본값으로 삼아야 할 건 어느 쪽인가?

모범답
방식강제 위치강점약점
BNF 문법클라이언트(내 코드)임의로 복잡한 검증 규칙 표현 가능로그 확률 접근 필요, tokenizer에 직접 종속
JSON 모드서버구현 최소필드명·내용까지는 보장 못 함
데이터클래스/스키마서버쉬움·빠름·모델 호환성 넓음Enum 이상의 복잡한 검증은 어려움

데이터클래스(Pydantic 등)가 "실무의 90%"를 차지하는 기본값이다. BNF는 규칙이 동적이거나, DB·규칙엔진에서 그때그때 가져와야 하거나, Enum으로 못 담는 복잡한 검증(신용카드 번호 규칙 등)이 필요할 때만 꺼내 쓴다.

핵심질문 · 두 패턴을 엮어서 보기
K1

프롬프트에 "JSON으로만 답해"라고 쓰는 것과 로짓 마스킹은 무엇이 근본적으로 다를까?

모범답

"JSON으로만 답해"는 부탁이다 — 모델의 지시 따르기 능력에 기대는 확률적 요청이고, 모델 버전이 바뀌면 예고 없이 깨질 수 있다(2.2.1의 안티패턴 경고와 동일). 로짓 마스킹은 강제다 — M1에서 본 것처럼 규칙을 어기는 후보의 로짓을 -10000으로 만들어 애초에 선택 가능한 후보에서 제거한다. 전자는 "안 지킬 수도 있는 요청", 후자는 "지키지 않는 선택지 자체가 존재하지 않음"이라는 차이다.

K2

특정 토큰을 마스킹으로 막았을 때, 모델이 같은 의미를 다른 토큰으로 우회해 말할 수는 없는가?

모범답

있다 — 그리고 그게 코드 구조상 당연한 결과다. M1의 evaluate()가 확인해준 대로, 규칙 검사는 리터럴 문자열 포함 여부(phrase in descr)만 본다. 실제로 protein drink 예제에서 모델은 금지어 "품질(quality)"을 피하려고 "프리미엄 (premium)"이라는, 목록에 없는 동의어로 우회했다 — 책 예시에서 이건 "성공"으로 다뤄지지만, 뒤집어 보면 목록에 없는 단어라면 의미가 같아도 걸러지지 않는다는 한계이기도 하다. 진짜 의미(semantic) 기반 차단이 필요하면 임베딩 유사도 검사 등 별도 로직을 더해야 하고, 로짓 마스킹 하나만으로는 안 된다.

K3

문법 제약을 걸면 정확도가 같이 오를까? 형식만 맞고 내용 품질은 반대로 나빠질 수 있는가?

모범답

아니다, 나빠질 수 있다 — G1의 "3 = 6" 무한반복이 정확히 이 사례다. 문법은 형식(구조)만 보장할 뿐 내용의 진위나 논리적 타당성은 전혀 보장하지 않는다. 오히려 필요한 표현(예: 부등호)을 문법에서 빼먹으면, 모델은 그 문법 안에서 가장 그럴듯한 틀린 답을 억지로 만들어낸다 — "형식이 완벽해 보인다"는 인상이 오히려 내용 검증을 방해할 수 있다는 게 핵심 함정이다.

K4

모델을 다른 것으로 바꾸거나 tokenizer가 바뀌면 이 두 패턴 중 무엇이 먼저 깨지는가?

모범답

문법(BNF)이 먼저 깨진다. IncrementalGrammarConstraint(grammar_str, "root", pipe.tokenizer)는 문법 상태별로 허용되는 토큰 ID 집합을 그 토크나이저의 어휘집 기준으로 미리 계산해둔다 — 모델(토크나이저)을 바꾸면 이 매핑을 처음부터 다시 만들어야 한다. 반면 로짓 마스킹은 tokenizer.decode(seq)로 후보를 텍스트로 되돌린 뒤 규칙을 검사하므로, 토크나이저가 바뀌어도 apply_rules 검사 로직 자체는 거의 그대로 재사용된다. 텍스트 레벨 vs 토큰 레벨의 차이가 이식성의 차이로 이어진다.

K5

상용 API가 제공하는 구조화 출력 기능이 있는데도 이 패턴을 직접 구현해야 하는 상황은 언제인가?

모범답

G2 표의 BNF 쪽 조건과 같다 — ① 규칙이 Enum 수준을 넘는 복잡한 검증 로직일 때 (신용카드 번호 패턴 등) ② 규칙이 동적이거나 DB·규칙엔진에서 그때그때 가져와야 할 때 ③ 규칙이 사용자 입력에 의존할 때(자동완성처럼) ④ 외부 도구·API 호출 결과에 따라 마스킹 기준이 달라질 때. 이럴 땐 상용 API의 response_schema/json_object 같은 고정 스키마 기능으로는 표현이 안 되고, 로짓 마스킹이나 BNF를 직접 구현해야 한다 — 대신 로짓 접근권이 있는 모델(오픈AI·구글·자체 호스팅 오픈웨이트)로 제한된다는 대가가 따른다.

K6

형식이 100% 보장되면 다운스트림 검증 로직을 지워도 되는가? 지우면 생기는 새 위험은?

모범답

안 된다. 문법·로짓 마스킹이 보장하는 건 "이 모양이다"이지 "이 내용이 맞다"가 아니다 — K3의 "3 = 6" 사례가 그 증거다. 파싱 실패(형식 오류)에 대비한 방어 코드는 지워도 되지만, 값의 논리적 타당성·범위·업무 규칙 위반 여부를 확인하는 검증까지 지우면 안 된다. 새로 생기는 위험은 자동화 편향 (automation bias)이다 — "형식이 완벽하니 내용도 맞겠지"라고 사람이 방심해서, 형식은 멀쩡하지만 내용이 틀린 결과가 검증 없이 그대로 다운스트림으로 흘러가는 사고가 오히려 더 조용히 발생한다.

정리하면 — 부탁(프롬프트)은 확률적이고, 강제(로짓 마스킹·문법)는 결정적이다. 다만 강제가 보장하는 건 언제나 형식뿐이고 내용의 진실성은 여전히 사람 몫이다. 로짓 마스킹은 텍스트 레벨이라 이식성이 좋고 로직을 직접 짜야 하며, 문법은 토큰 레벨이라 모델 교체에 취약한 대신 서버가 대신 감시해준다 — 이 트레이드오프를 기억해두면 6개 핵심질문 어디서 막혀도 원리로 되짚어갈 수 있다.
