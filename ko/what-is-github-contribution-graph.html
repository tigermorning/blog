GitHub 잔디심기란 무엇인가

2026. 7. 12.

GitHub 잔디심기란 커밋·PR·이슈·코드 리뷰 기록이 프로필 화면의 1년치 달력에 초록색 칸으로 찍히는 그래프(Contribution graph)를, 잔디밭에 빗대어 하루 한 칸씩 채워 나가는 일이다.

뭐를 할 수 있나
GitHub 잔디(Contribution graph)가 정확히 뭘 기록하는지, 커밋·PR·이슈·코드 리뷰 중 뭐가 칸을 채우는지 설명할 수 있고, 잔디가 GitHub의 어느 화면에 있는지 찾아갈 수 있고, 분명 작업했는데 회색으로 남는 원인(비공개 저장소, 이메일 불일치)을 찾을 수 있어요.
왜 배우나
잔디를 "실력 성적표"로 오해하면 빈 커밋처럼 무의미한 방법으로 칸만 채우려는 함정에 빠지기 쉬운데, 도장판은 "했다"는 사실만 기록하지 "무엇을 했는지"는 기록하지 않는다는 걸 알아야 이 함정을 피할 수 있어요.
왜 중요한가
채용 담당자도 잔디 개수보다 어떤 저장소에 무슨 내용으로 기여했는지를 더 중요하게 본다는 걸 모르면, 정작 봐야 할 걸 안 보고 엉뚱한 지표에 시간을 쏟게 돼요.
어디에 쓰나
잔디가 안 보일 때 대시보드 말고 프로필 화면(github.com/아이디)으로 바로 찾아가기 · 내 GitHub 프로필에서 회색 칸이 이어지는 구간을 보고 실제로 손을 놓았던 시기를 확인하기 · "Include private contributions" 설정을 켜서 비공개 저장소 활동도 잔디에 반영하기 · 커밋한 이메일 주소와 계정 이메일이 같은지 확인해서 "잔디가 안 심기는" 문제 해결하기

이 블로그를 만들면서 GitHub를 매일 들여다보다가, 개발자들이 "오늘도 잔디 심었다"는 말을 쓰는 걸 봤어요. 처음엔 진짜 식물 얘기인 줄 알았어요. 알고 보니 GitHub 프로필에 붙어 있는 초록색 그래프를 가리키는 말이더라고요.

그런데 그래프라는 걸 안 뒤에도 궁금증이 남았어요. 그게 정확히 뭘 기록하는 그래프이고, 사람들은 왜 그렇게까지 신경 쓸까요. 이 질문에 답하려면 애초에 GitHub가 무엇을 기록해두는 곳인지부터 봐야 했어요.

GitHub는 "작업 기록이 날짜별로 남는 곳"이에요 — 그 기록을 도장으로 찍은 게 잔디

GitHub는 코드나 문서 파일을 인터넷에 올려두고 여러 사람이 함께 고칠 수 있게 해주는 서비스예요. 여기서 프로젝트 하나가 들어가는 폴더를 저장소(repository)라고 불러요. 이 블로그도 저장소 하나예요.

중요한 건 GitHub가 파일을 그냥 보관만 하는 게 아니라는 점이에요. 파일을 고칠 때마다 "누가, 언제, 무엇을 바꿨는지"를 한 줄씩 기록으로 남겨요. 이 기록 한 줄을 만드는 행위를 커밋(commit)이라고 해요. 저장 버튼을 누르는 것과 비슷한데, 저장 시점마다 날짜와 사람 이름이 도장처럼 같이 찍힌다는 게 달라요.

그러니까 GitHub 계정 하나에는 "이 사람이 며칠에 뭔가를 했다"는 날짜 기록이 이미 잔뜩 쌓여 있는 상태예요. 잔디는 그 쌓여 있는 기록을 가지고 만든 그림이에요.

GitHub 프로필 페이지에 가면 지난 1년치 날짜가 작은 네모 칸으로 쭉 늘어선 달력 모양 그래프가 있어요. 정식 명칭은 Contribution graph(기여 그래프)예요. 어떤 날에 활동 기록이 있으면 그날 칸이 초록색으로 칠해지고, 활동이 많았던 날일수록 초록색이 더 진해져요. 아무것도 안 한 날은 회색으로 남고요.

이게 잔디밭처럼 보인다고 해서 한국 개발자들 사이에서 "잔디심기"라는 별명이 붙었어요. 저는 어린이 출석 도장판을 떠올리면 제일 잘 맞았어요. 학원이나 도서관에서 오면 도장 하나 찍어주는 그 판이요. 하루에 한 칸씩 찍히고, 판 전체를 멀리서 보면 이 사람이 얼마나 꾸준히 왔는지가 한눈에 보이죠.

이 도장판 비유가 앞으로 이 글에서 계속 쓰일 거예요. 잔디의 장점도, 함정도 전부 "도장판이 무엇을 찍고 무엇을 안 찍는가"에서 나오거든요. 그런데 그 전에 — 저는 이 도장판이 어디에 붙어 있는지부터 한참 못 찾았어요.

도장판은 프로필 화면에만 붙어 있어요 — 제가 한참 못 찾은 이유

GitHub를 거의 매일 쓰면서도 저는 잔디를 한 번도 못 봤어요. "다들 있다는데 나는 왜 안 보이지?" 싶어서 찾아봤는데 이유가 허무했어요. 제가 평소에 들어가는 화면에는 잔디가 아예 없었던 거예요.

GitHub에 로그인하면 대시보드1라는 첫 화면이 떠요. 최근 소식과 내 저장소 목록만 모아둔 화면이에요. 거기서 저장소 이름을 눌러 들어가면 파일 목록이 나오고, 커밋도 전부 그 안에서 하고요. 그러니까 제가 GitHub에서 쓰는 화면은 이 두 개가 전부였고, 잔디가 붙어 있는 화면은 열어볼 일이 없었던 거예요.

화면주소잔디가 보이나
대시보드 — 로그인하면 처음 뜨는 화면github.com안 보여요
저장소 화면 — 파일 목록과 커밋 기록github.com/아이디/저장소이름안 보여요
프로필 화면 — 나를 소개하는 화면github.com/아이디여기에만 있어요

가는 방법은 두 가지예요. 주소창에 github.com/본인아이디를 직접 치거나, 화면 오른쪽 위의 내 프로필 사진을 누르고 "Your profile"을 고르면 돼요.

저도 그제야 열어봤는데, 지난 1년 동안 기여가 2,221개 찍혀 있었어요. 잔디가 없었던 게 아니라 제가 안 보고 있었던 거죠. 그런데 더 눈에 들어온 건 개수가 아니었어요. 초록 칸이 7~9월에만 몰려 있고 나머지 계절은 전부 회색이었거든요. 이 얘기는 글 뒤에서 다시 할게요.

프로필 화면까지 갔는데도 칸이 전부 회색이라면, 그건 위치 문제가 아니라 다른 문제예요 — 뒤에 나오는 "어떤 활동이 도장을 찍어주나요" 절에서 볼 두 가지 조건에 걸렸을 수 있어요.

나쁜 선택 vs 좋은 선택 — 잔디가 안 보일 때

나쁜 선택좋은 선택
무엇을 했나: 잔디가 안 보이니까 "내 커밋이 기록이 안 되고 있나?" 싶어서, 확인해 보려고 의미 없는 커밋을 몇 개 만들어 올렸어요.

무슨 일이 생기나: 화면을 잘못 보고 있었을 뿐이니 잔디는 여전히 안 보여요. 대신 저장소에는 아무것도 바꾸지 않은 커밋만 남죠. 원인을 찾기도 전에 기록부터 지저분해져요.		 무엇을 했나: 커밋을 더 만들기 전에 github.com/본인아이디 주소부터 열어서, 잔디가 있다는 그 화면을 직접 확인했어요.

무슨 일이 생기나: 30초면 끝나요. 잔디가 멀쩡히 있으면 "화면을 안 보고 있었던 것"이고, 프로필에서도 회색이면 그때 비공개 저장소·이메일 설정을 보면 돼요. 원인이 두 갈래로 깔끔하게 갈려요.

이 칸 그래프의 원래 이름은 "히트맵"이에요 — 그래서 다른 도구에서도 보여요

잔디를 두고 한 번쯤 헷갈리는 게 또 있어요. 잔디처럼 생긴 칸 그래프를 GitHub가 아닌 곳에서 먼저 보는 경우예요. 저는 터미널에서 쓰는 AI 코딩 도구인 Claude Code에서 제 사용 기록 화면을 열었다가, 잔디와 똑같이 생긴 칸 그래프를 봤어요. 색만 초록이 아니라 주황색이었고요. "잔디는 GitHub 거라며?" 싶었죠.

알고 보니 이 모양에는 원래 이름이 따로 있었어요. 히트맵(heatmap)2이라고 해요. 숫자를 색의 진하기로 바꿔서 보여주는 그림이라는 뜻이에요.

이름은 열화상 카메라에서 왔어요. 뜨거운 곳은 빨갛게, 차가운 곳은 파랗게 나오는 그 화면이요. 온도라는 숫자를 색으로 바꿔 보여주는 장치인데, 여기서 "열"만 빼고 원리만 가져온 게 히트맵이에요. 값이 크면 진하게, 작으면 옅게.

왜 굳이 색으로 바꾸는지는 나란히 놓고 보면 바로 느껴져요. 한 주치 활동 기록이라고 해볼게요.

월화수목금
숫자로 적으면051220
색으로 칠하면     

읽는 법: 위아래 두 줄은 똑같은 기록이에요. 아래 줄은 숫자를 지우고 색의 진하기로만 바꿔 칠한 것뿐이에요.

숫자 줄은 한 칸씩 읽고 머릿속에서 비교해야 하는데, 색 줄은 "수요일에 몰아서 하는구나"가 그냥 보여요. 다섯 칸이라 차이가 작아 보이지만 365칸이 되면 이 차이가 결정적이에요. GitHub가 1년치 기여 개수를 숫자표가 아니라 초록색 칸으로 보여주는 이유가 이거예요.

핵심 한 줄: 히트맵은 숫자를 읽게 하는 그림이 아니라, 패턴을 보게 하는 그림이에요.

그러니까 GitHub 잔디는 히트맵의 한 종류예요. 부품을 하나씩 맞춰보면 이렇게 돼요.

히트맵의 부품GitHub 잔디에서는
격자의 칸 하나하루 (1년치라서 365칸)
칸에 들어 있는 숫자그날의 기여 개수(커밋·PR·이슈·리뷰)
색의 진하기회색 → 연한 초록 → 진한 초록
색으로 읽어내는 것언제 몰아서 했고 언제 쉬었는지

히트맵이 워낙 잘 읽히는 방식이다 보니, 요즘은 "활동 기록"을 보여줘야 하는 도구들이 이 모양을 그대로 가져다 써요. 제가 Claude Code에서 본 주황색 칸도 그중 하나였고요. 다만 생긴 게 같다고 세는 것까지 같은 건 아니에요.

색초록주황 (도구마다 달라요)
어느 쪽이 먼저인가원조 — 2013년 1월부터이 모양을 빌려온 쪽

"잔디"라는 별명이 붙은 건 GitHub의 초록색 기여 그래프예요. 그러니 다른 도구에서 비슷한 칸 그래프를 먼저 봤다면, 그건 잔디를 따라 만든 것이라고 보시면 맞아요.

여기서 중요한 게 하나 따라 나와요. 같은 모양이라도 무엇을 세느냐에 따라 뜻이 완전히 달라진다는 거예요. 그럼 GitHub 도장판은 정확히 무엇을 셀까요.

어떤 활동이 도장을 찍어주나요 — 도장판이 안 찍는 것도 있어요

도장이 찍히는 활동은 정해져 있어요. 처음 보는 단어들이라 하나씩 풀어 쓸게요.

  • 커밋(commit): 앞에서 말한 그 기록 한 줄을 남기는 것. 가장 흔하게 잔디를 채우는 방법이에요.
  • Pull Request(PR) 생성: "제가 이렇게 고쳐봤는데, 원래 프로젝트에 반영해주실래요?"라고 정식으로 제안하는 것. 남의 프로젝트에 참여할 때 쓰는 절차예요.
  • 이슈(issue) 등록: "여기 이런 문제가 있어요", "이런 기능이 있으면 좋겠어요"라고 프로젝트 게시판에 글을 남기는 것. 코드를 못 짜도 할 수 있는 기여예요.
  • 코드 리뷰 참여: 남이 올린 PR을 읽고 의견을 달아주는 것.

실제로 걸려 넘어지기 쉬운 조건이 두 개 있어요. 첫째, 비공개(private) 저장소에서 한 활동은 기본적으로 잔디에 안 나와요. 프로필 설정에서 "Include private contributions"를 켜야 도장이 찍히는데, 이때도 내용은 감춰지고 개수만 반영돼요. 둘째, 커밋에 적힌 이메일 주소가 내 GitHub 계정에 등록된 이메일과 다르면, 분명히 커밋을 했는데도 잔디가 안 심겨요. "열심히 했는데 왜 회색이지?" 싶을 때 대부분 이 둘 중 하나예요.

여기까지가 도장이 찍히는 조건이에요. 그런데 이 목록을 다시 보면 이상한 점이 하나 보여요.

출석 도장판을 생각해보면 당연한 얘기예요. 도장은 왔다는 사실만 증명해요. 와서 세 시간을 집중했는지, 문 앞에서 도장만 찍고 나갔는지는 판에 안 남아요.

잔디도 똑같아요. 초록 칸 하나는 "그날 기록이 하나 생겼다"는 뜻이지, "그날 좋은 걸 만들었다"는 뜻이 아니에요. 그래서 빈 커밋(empty commit)이라는 게 문제가 돼요. 파일을 하나도 안 고치고 기록 한 줄만 만들어내는 커밋인데, 이걸 매일 자동으로 찍게 해두면 잔디밭은 새파랗게 채워지지만 실제로 만들어진 건 아무것도 없어요.

개발자 커뮤니티에서 "잔디 집착"을 두고 논쟁이 벌어지는 이유가 이거예요. 채우기 쉬운 지표는 언제나, 채우는 것 자체가 목적이 되는 순간 의미를 잃어요. 그래서 채용 담당자들도 잔디 개수보다 어떤 저장소에, 어떤 내용으로 기여했는지를 훨씬 중요하게 본다고 해요. 도장 개수가 아니라 그날 뭘 했는지를 보려고, 결국 저장소를 직접 열어본다는 뜻이에요.

그럼 잔디는 아예 볼 필요 없는 걸까요. 저는 그렇게까지는 아니라고 생각하게 됐어요.

그래도 도장판을 계속 보게 되는 이유, 그리고 정리

도장판이 "뭘 했는지"를 못 담는다는 건, 뒤집어 말하면 남에게 보여주는 성적표로는 약하지만 나에게 보여주는 습관 기록으로는 정확하다는 뜻이기도 해요. 실제로 제가 얻은 건 남에게 보이는 실적이 아니라 이런 것들이었어요.

  • 회색 칸이 며칠째 이어지면 내가 손을 놓고 있다는 사실이 눈에 보여요. 머릿속으로는 "요즘 계속하고 있는데"라고 생각하던 게 사실이 아니었다는 걸 알게 돼요.
  • "오늘 한 칸만 채우자"는 목표는 부담이 작아서, 큰 작업을 미루다가 아예 안 하는 것보다 낫더라고요.
  • 블로그 글 하나를 올릴 때마다 칸이 채워지니까, 글쓰기와 저장소 작업이 자연스럽게 같은 리듬으로 묶였어요.

다만 빈 커밋의 교훈은 그대로 가져가는 게 좋아요. 한 칸을 채우려고 무의미한 커밋을 만드는 순간, 이 도장판은 저를 속이는 도구가 돼요. 칸을 채우려고 일하는 게 아니라, 일했으니까 칸이 채워지는 순서를 지키는 것이 전부예요.

GitHub 잔디심기가 뭔가요. GitHub에 이미 날짜별로 쌓여 있는 작업 기록을, 1년치 달력에 초록색 도장으로 찍어서 보여주는 그래프(Contribution graph)예요. 커밋·PR·이슈·코드 리뷰를 하면 그날 칸이 채워지고, 많이 한 날일수록 진해져요.

그리고 사람들이 왜 신경 쓰는지, 왜 동시에 비판하는지도 같은 이유에서 나와요. 도장판은 "했다"는 사실만 기록하고 "무엇을 했는지"는 기록하지 않아요. 그래서 남에게 실력을 증명하는 자료로는 약하고, 나 자신의 꾸준함을 확인하는 거울로는 꽤 정확해요. 저는 이제 잔디를 성적표가 아니라 거울로 보고 있어요. 이 블로그 저장소에 커밋할 때마다 칸이 하나씩 채워지는데, 그게 자랑이 아니라 "이번 주에 실제로 손을 움직였다"는 확인으로 남는 게 더 쓸모 있더라고요.

직접 해보기: 본인 GitHub 프로필에 들어가서 잔디를 살펴보세요. 로그인하면 뜨는 대시보드가 아니라 github.com/본인아이디 주소, 즉 프로필 화면이에요. 회색 칸이 며칠째 이어지는 구간이 있다면, 그 주에 실제로 무슨 일이 있었는지 떠올려보면 도장판이 왜 거울에 가까운지 바로 느껴져요.
