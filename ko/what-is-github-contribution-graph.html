GitHub 잔디심기란 무엇인가

2026. 7. 12.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

이 블로그를 만들면서 GitHub를 매일 들여다보다가, 개발자들이 "오늘도 잔디 심었다"는 말을 쓰는 걸 봤어요. 처음엔 진짜 식물 얘기인 줄 알았어요. 알고 보니 GitHub 프로필에 붙어 있는 초록색 그래프를 가리키는 말이더라고요.

그런데 그래프라는 걸 안 뒤에도 궁금증이 남았어요. 그게 정확히 뭘 기록하는 그래프이고, 사람들은 왜 그렇게까지 신경 쓸까요. 이 질문에 답하려면 애초에 GitHub가 무엇을 기록해두는 곳인지부터 봐야 했어요.

GitHub는 "작업 기록이 날짜별로 남는 곳"이에요 — 그 기록을 도장으로 찍은 게 잔디

GitHub는 코드나 문서 파일을 인터넷에 올려두고 여러 사람이 함께 고칠 수 있게 해주는 서비스예요. 여기서 프로젝트 하나가 들어가는 폴더를 저장소(repository)라고 불러요. 이 블로그도 저장소 하나예요.

중요한 건 GitHub가 파일을 그냥 보관만 하는 게 아니라는 점이에요. 파일을 고칠 때마다 "누가, 언제, 무엇을 바꿨는지"를 한 줄씩 기록으로 남겨요. 이 기록 한 줄을 만드는 행위를 커밋(commit)이라고 해요. 저장 버튼을 누르는 것과 비슷한데, 저장 시점마다 날짜와 사람 이름이 도장처럼 같이 찍힌다는 게 달라요.

그러니까 GitHub 계정 하나에는 "이 사람이 며칠에 뭔가를 했다"는 날짜 기록이 이미 잔뜩 쌓여 있는 상태예요. 잔디는 그 쌓여 있는 기록을 가지고 만든 그림이에요.

GitHub 프로필 페이지에 가면 지난 1년치 날짜가 작은 네모 칸으로 쭉 늘어선 달력 모양 그래프가 있어요. 정식 명칭은 Contribution graph(기여 그래프)예요. 어떤 날에 활동 기록이 있으면 그날 칸이 초록색으로 칠해지고, 활동이 많았던 날일수록 초록색이 더 진해져요. 아무것도 안 한 날은 회색으로 남고요.

이게 잔디밭처럼 보인다고 해서 한국 개발자들 사이에서 "잔디심기"라는 별명이 붙었어요. 저는 어린이 출석 도장판을 떠올리면 제일 잘 맞았어요. 학원이나 도서관에서 오면 도장 하나 찍어주는 그 판이요. 하루에 한 칸씩 찍히고, 판 전체를 멀리서 보면 이 사람이 얼마나 꾸준히 왔는지가 한눈에 보이죠.

이 도장판 비유가 앞으로 이 글에서 계속 쓰일 거예요. 잔디의 장점도, 함정도 전부 "도장판이 무엇을 찍고 무엇을 안 찍는가"에서 나오거든요. 그럼 먼저, 무엇을 하면 도장이 찍힐까요.

어떤 활동이 도장을 찍어주나요 — 도장판이 안 찍는 것도 있어요

도장이 찍히는 활동은 정해져 있어요. 처음 보는 단어들이라 하나씩 풀어 쓸게요.

  • 커밋(commit): 앞에서 말한 그 기록 한 줄을 남기는 것. 가장 흔하게 잔디를 채우는 방법이에요.
  • Pull Request(PR) 생성: "제가 이렇게 고쳐봤는데, 원래 프로젝트에 반영해주실래요?"라고 정식으로 제안하는 것. 남의 프로젝트에 참여할 때 쓰는 절차예요.
  • 이슈(issue) 등록: "여기 이런 문제가 있어요", "이런 기능이 있으면 좋겠어요"라고 프로젝트 게시판에 글을 남기는 것. 코드를 못 짜도 할 수 있는 기여예요.
  • 코드 리뷰 참여: 남이 올린 PR을 읽고 의견을 달아주는 것.

실제로 걸려 넘어지기 쉬운 조건이 두 개 있어요. 첫째, 비공개(private) 저장소에서 한 활동은 기본적으로 잔디에 안 나와요. 프로필 설정에서 "Include private contributions"를 켜야 도장이 찍히는데, 이때도 내용은 감춰지고 개수만 반영돼요. 둘째, 커밋에 적힌 이메일 주소가 내 GitHub 계정에 등록된 이메일과 다르면, 분명히 커밋을 했는데도 잔디가 안 심겨요. "열심히 했는데 왜 회색이지?" 싶을 때 대부분 이 둘 중 하나예요.

여기까지가 도장이 찍히는 조건이에요. 그런데 이 목록을 다시 보면 이상한 점이 하나 보여요.

출석 도장판을 생각해보면 당연한 얘기예요. 도장은 왔다는 사실만 증명해요. 와서 세 시간을 집중했는지, 문 앞에서 도장만 찍고 나갔는지는 판에 안 남아요.

잔디도 똑같아요. 초록 칸 하나는 "그날 기록이 하나 생겼다"는 뜻이지, "그날 좋은 걸 만들었다"는 뜻이 아니에요. 그래서 빈 커밋(empty commit)이라는 게 문제가 돼요. 파일을 하나도 안 고치고 기록 한 줄만 만들어내는 커밋인데, 이걸 매일 자동으로 찍게 해두면 잔디밭은 새파랗게 채워지지만 실제로 만들어진 건 아무것도 없어요.

개발자 커뮤니티에서 "잔디 집착"을 두고 논쟁이 벌어지는 이유가 이거예요. 채우기 쉬운 지표는 언제나, 채우는 것 자체가 목적이 되는 순간 의미를 잃어요. 그래서 채용 담당자들도 잔디 개수보다 어떤 저장소에, 어떤 내용으로 기여했는지를 훨씬 중요하게 본다고 해요. 도장 개수가 아니라 그날 뭘 했는지를 보려고, 결국 저장소를 직접 열어본다는 뜻이에요.

그럼 잔디는 아예 볼 필요 없는 걸까요. 저는 그렇게까지는 아니라고 생각하게 됐어요.

그래도 도장판을 계속 보게 되는 이유, 그리고 정리

도장판이 "뭘 했는지"를 못 담는다는 건, 뒤집어 말하면 남에게 보여주는 성적표로는 약하지만 나에게 보여주는 습관 기록으로는 정확하다는 뜻이기도 해요. 실제로 제가 얻은 건 남에게 보이는 실적이 아니라 이런 것들이었어요.

  • 회색 칸이 며칠째 이어지면 내가 손을 놓고 있다는 사실이 눈에 보여요. 머릿속으로는 "요즘 계속하고 있는데"라고 생각하던 게 사실이 아니었다는 걸 알게 돼요.
  • "오늘 한 칸만 채우자"는 목표는 부담이 작아서, 큰 작업을 미루다가 아예 안 하는 것보다 낫더라고요.
  • 블로그 글 하나를 올릴 때마다 칸이 채워지니까, 글쓰기와 저장소 작업이 자연스럽게 같은 리듬으로 묶였어요.

다만 빈 커밋의 교훈은 그대로 가져가는 게 좋아요. 한 칸을 채우려고 무의미한 커밋을 만드는 순간, 이 도장판은 저를 속이는 도구가 돼요. 칸을 채우려고 일하는 게 아니라, 일했으니까 칸이 채워지는 순서를 지키는 것이 전부예요.

GitHub 잔디심기가 뭔가요. GitHub에 이미 날짜별로 쌓여 있는 작업 기록을, 1년치 달력에 초록색 도장으로 찍어서 보여주는 그래프(Contribution graph)예요. 커밋·PR·이슈·코드 리뷰를 하면 그날 칸이 채워지고, 많이 한 날일수록 진해져요.

그리고 사람들이 왜 신경 쓰는지, 왜 동시에 비판하는지도 같은 이유에서 나와요. 도장판은 "했다"는 사실만 기록하고 "무엇을 했는지"는 기록하지 않아요. 그래서 남에게 실력을 증명하는 자료로는 약하고, 나 자신의 꾸준함을 확인하는 거울로는 꽤 정확해요. 저는 이제 잔디를 성적표가 아니라 거울로 보고 있어요. 이 블로그 저장소에 커밋할 때마다 칸이 하나씩 채워지는데, 그게 자랑이 아니라 "이번 주에 실제로 손을 움직였다"는 확인으로 남는 게 더 쓸모 있더라고요.
