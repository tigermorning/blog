← 이전 편 갈림길을 밀어붙인다 — 세 갈래·라벨·끝나지 않는 반복 (3)

도구 루프란 조건부 엣지의 라우터 자리에 모델의 도구 요청을 읽는 tools_condition을 앉혀, 규칙이 고르던 갈림길을 모델이 다음 걸음을 고르는 반복으로 바꾼 LangGraph 그래프다.

어디쯤인가
8단계 › 에이전트 팀 꾸리기 — LangGraph — 4번째 글 (전 7편). 중간부터 보셨다면 1편부터 보시는 게 편해요.
뭐를 할 수 있나
LLM이 도구를 스스로 부르는 루프를 노드 두 개와 선 세 개로 조립할 수 있어요. 도구가 안 불릴 때 프롬프트가 아니라 독스트링부터 의심하게 되고, 계산처럼 틀리면 곤란한 일을 모델에게서 떼어 코드로 옮길 수 있어요.
왜 배우나
모델이 도구를 직접 돌린다고 착각하면, 도구가 안 불릴 때 어디를 고쳐야 할지 헷갈려요. 모델은 요청서만 쓰고 실행은 ToolNode가 해요.
왜 중요한가
도구 루프도 되돌아가는 선이에요. 몇 번까지 돌지 정해 두지 않으면 모델이 도구를 계속 부르는 동안 호출 요금이 그대로 쌓여요. 게다가 계산을 모델에게 맡기면 틀려도 에러 없이 그럴듯한 문장으로 나가요.
어디에 쓰나
재고나 일정을 조회하는 도구를 쥔 챗봇 · 사내 문서를 찾아 답하는 어시스턴트 · 틀리면 곤란한 계산을 코드로 떼어 놓기

2편에서 State·Node·Edge로 그래프를 만들고, 지난 편에서 그 갈림길을 세 문제로 밀어붙였어요. 거기까지 길을 고른 건 "소금이 세 숟갈 이상이면 내보낸다", "60자보다 짧으면 보류한다" 같은 규칙이었어요. 라우터가 if문이었으니까요.

이번 편에서는 그 라우터 자리에 모델을 앉혀요. 그러면 다음 걸음을 규칙이 아니라 모델이 고르게 돼요. 1편의 자율성 눈금자로 보면 왼쪽에서 오른쪽으로 한 칸 옮기는 거예요. 워크플로에서 에이전트 쪽으로 넘어가는 지점이고, 이 시리즈에서 처음으로 API 키가 필요한 편이기도 해요.

키를 넣다가 막히면 5편을 보세요. 강의 화면에서 .env가 안 읽혔던 네 겹의 이유를 따로 정리해 뒀어요.

비유 — 홀 직원의 창고 조회 요청서

2편의 주방에서는 검수대 직원이 맛을 보고, 싱거우면 전표를 화구로 되돌리고 간이 맞으면 홀로 내보냈어요. 이때 기준은 "소금 세 숟갈"이라는 정해진 규칙이었어요. 이번엔 손님을 직접 상대하는 홀 직원이 주인공이에요.

손님이 홀 직원에게 "계란말이 두 접시 돼요?" 하고 물어요. 홀 직원은 창고에 계란이 몇 개 남았는지 모르니, 창고 조회 요청서를 적어 주방의 창고 담당에게 넘겨요(도구 호출 글의 '주문표'와 같은 거예요). 창고 담당은 요청서대로 창고를 뒤져 "계란 4개"라고 적은 쪽지를 붙여 홀 직원에게 돌려줘요. 홀 직원은 쪽지를 읽고, 레시피가 더 궁금하면 요청서를 또 쓰고, 다 알았으면 손님에게 답해요. 그 사이 검수대는 한 가지만 봐요. 홀 직원이 요청서를 냈으면 전표를 창고로, 안 냈으면 홀로 내보내요.

비유 속 요소원래 개념
홀 직원이 창고 담당에게 넘기는 조회 요청서모델이 내놓는 도구 호출 요청(tool_calls) — 도구 이름과 넣을 값만 적힌 종이예요
창고 담당이 요청서대로 창고를 뒤지고, 결과 쪽지를 들고 늘 홀 직원에게 돌아가기ToolNode가 함수를 실제로 실행해 결과를 ToolMessage로 붙이고, add_edge("tools", "agent") 선을 따라 다시 모델에게 가요
홀 직원 손에 쥐여 준 창고 품목 안내문 — 홀 직원은 창고 안이 아니라 이 안내문만 봐요bind_tools로 모델에게 건네는 도구 설명 — @tool 함수의 독스트링으로 만들고, 모델은 파이썬 코드가 아니라 이것만 봐요
검수대가 "요청서가 있으면 창고로, 없으면 홀로" 가르기tools_condition — 모델의 마지막 답에 tool_calls가 있으면 tools로, 없으면 END로 보내는 미리 만들어진 라우터예요
검수대 직원이 동선표에 없는 조리대 이름을 외치기목적지 목록에 없는 이름을 돌려주는 라우터 — 그 갈래로 갈 입력이 처음 들어올 때 에러로 멈춰요 (갈림길 연습 ①)
검수대 직원이 전표에 몰래 적기라우터 안에서 State 고치기 — 적은 값이 사라지거나 몰래 새어 들어가요 (아래에서 직접 확인)

핵심 한 줄: 동선표 모양은 지난 편과 같고, 전표를 어디로 보낼지 정하는 기준만 규칙표에서 홀 직원의 요청서로 바뀌었어요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 홀 직원은 급하면 창고에 직접 들어갈 수도 있지만, 모델에게는 그런 손이 아예 없어요. 요청서를 적는 게 모델이 할 수 있는 전부예요. 정말 그런지는 아래 '요청서는 종이일 뿐'에서 코드로 확인해요.

전체 흐름 — 같은 모양, 바뀐 라우터

읽는 법: 왼쪽은 2편 ②의 간 맞추기 그래프를 줄인 그림이고(내보내기·셰프 호출 두 출구는 END 하나로 합쳤어요), 오른쪽은 이번 편 ③에서 조립할 도구 루프예요. 실선은 앞 노드가 끝나면 항상 지나가는 선, 점선은 라우터가 둘 중 하나만 고르는 선이에요. 두 그림 모두 아래 칸에서 위 칸으로 올라가는 실선이 반복이에요. 달라진 건 점선을 고르는 기준 하나예요. 왼쪽은 전표의 숫자를 보는 규칙이고, 오른쪽은 모델이 요청서를 냈는지예요.

계산은 코드에게 — 단순한 함수도 좋은 도구인 이유

갈림길 연습은 여기까지예요. 이제 라우터 자리에 모델을 앉힐 차례인데, 그 전에 모델에게 쥐여 줄 도구가 왜 필요한지부터 짚을게요.

강의가 짚어 준 설계 원칙 한 줄이 기억에 남아요. LLM이 약한 계산과 정밀 작업은 코드에 맡기고, LLM은 "언제 어떤 코드를 부를지" 판단하는 데 집중시킨다. 그래서 달력, 시간대 변환기, 단위 변환기처럼 단순한 함수도 훌륭한 도구가 돼요. 지난 편의 도구 종류 표에 나온 세 종류가 바깥에서 정보를 가져오거나 바깥을 바꾸는 도구라면, 이쪽은 LLM이 약한 계산을 대신 해 주는 도구예요.

처음엔 "오늘부터 100일 뒤가 무슨 요일인지 정도는 LLM이 그냥 풀면 되지 않나" 싶었어요. 그런데 LLM에게 직접 맡길 때와 함수로 뺄 때를 나란히 놓으면 차이가 분명해요.

비교 항목LLM이 직접 계산하면함수 도구로 빼면
정확한가계산을 하는 게 아니라 앞 글자들 다음에 올 그럴듯한 조각을 이어 쓰는 방식이라, 월말·윤년이 끼는 날짜나 자릿수가 긴 곱셈에서 틀린 답을 자신 있게 내놓을 수 있어요파이썬으로 "2026년 9월 11일 + 100일"을 계산하는 한 줄(date(2026, 9, 11) + timedelta(days=100))이면 언제 돌려도 2026-12-20(일요일)이 나와요
매번 같은가답을 확률적으로 뽑아서 같은 질문에도 실행마다 답이 달라질 수 있어요같은 입력엔 언제나 같은 결과가 나와요
지금 기준인가누가 알려 주지 않으면 오늘 날짜를 모르고, 학습이 끝난 뒤에 바뀐 서머타임 같은 시간대 규칙도 몰라요실행되는 순간의 컴퓨터 시계를 읽고, 시간대 규칙도 업데이트로 갱신되는 자료를 따라요
틀렸을 때 찾을 수 있나머릿속 계산이라 어디서 틀렸는지 흔적이 남지 않아요도구에 무엇을 넣고 무엇을 받았는지가 메시지로 남아요(아래 직접 만들기 ③에서 봐요). 함수는 테스트 코드로 따로 검사할 수도 있어요

정리하면 LLM은 "날짜 계산이 필요하니 이 도구를 이 값으로 부르자"까지만 판단하고, 계산은 코드가 맡아요. 이 역할 분담이 뒤에서 조립할 도구 루프의 출발점이에요. 다만 도구를 늘릴수록 모델이 읽어야 할 도구 설명도 함께 쌓이니(도구가 많아지면 생기는 문맥 부담 — Tool Search와 Code Mode), 틀리면 곤란한 계산부터 빼는 게 순서예요. 둘의 차이는 글 끝 직접 해보기 2번에서 재 볼 수 있어요.

중요2강에서 짚은 내용

단순한 계산도 LLM에게 맡기지 않고 도구로 빼는 이유는 세 가지로 모여요.

  • 틀려도 티가 안 나요. LLM이 틀린 날짜를 말할 때도 문장은 그럴듯해서, 사람이 읽어서는 잡아내기 어려워요.
  • 함수는 검사할 수 있어요. 같은 입력에 늘 같은 답을 내니(이런 성질을 '결정적'이라고 해요) 테스트 코드로 미리 확인해 둘 수 있어요.
  • 일을 나눠 맡겨요. LLM은 "지금 날짜 계산이 필요하다"는 판단을, 코드는 계산 자체를 맡아요. 강의 예제가 복습 문제의 형식 검사를 LLM 대신 파이썬 함수로 한 것도 같은 이유예요.

직접 만들기 ③ — 도구를 쥐여 주는 루프

이제 진짜 LLM을 넣어요. 여기서부터는 OpenAI API 키1가 필요해요. 키를 넣는 방법은 세 가지예요.

  • 내 컴퓨터 — 프로젝트 폴더의 .env 파일에 OPENAI_API_KEY=sk-...를 적고 from dotenv import load_dotenv; load_dotenv()로 읽어요. .env는 절대 깃에 올리지 않아요 (AI 코드 보안 기초에서 다룬 비밀 관리 그대로예요).
  • Colab — 왼쪽 열쇠 아이콘(보안 비밀)에 등록하고 google.colab.userdata로 읽어요.
  • 임시 — os.environ["OPENAI_API_KEY"] = "sk-..."로 직접 넣어요. 노트북 파일에 키가 그대로 남으니 저장하거나 공유하기 전에 꼭 지워요.

모두의연구소 강의 화면의 코드 셀에서 돌린다면 첫 번째 방법이 적힌 그대로는 안 통해요. 코드가 내 컴퓨터가 아니라 강의 서버에서 돌기 때문이에요. 제가 한참 막혔던 과정은 아래 '강의 화면에서 API 키 넣기'에 따로 적어 뒀어요.

도구는 함수에 @tool을 붙여 만들어요(지난 편의 식구 표에서 본 LangChain 쪽 부품이에요). 여기서 제일 중요한 건 독스트링2이에요. LangChain이 독스트링과 타입 힌트를 읽어 JSON 스키마3를 만들고, 모델은 우리 파이썬 코드가 아니라 이 스키마만 봐요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요 (호출마다 요금이 조금 나가요)

from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

@tool(parse_docstring=True)
def get_recipe(dish: str) -> str:
    """요리 한 접시에 들어가는 재료와 양을 알려 준다. 만들 수 있는지 답하기 전에 먼저 호출한다.

    Args:
        dish: 요리 이름. 예: "계란말이"
    """
    return {"계란말이": "계란 3개", "두부조림": "두부 1모"}.get(dish, "레시피 없음")

@tool(parse_docstring=True)
def check_stock(item: str) -> str:
    """창고에 재료가 몇 개 남았는지 조회한다.

    Args:
        item: 재료 이름. 예: "계란"
    """
    return f"{item} {({'계란': 4, '두부': 0}).get(item, 0)}개"

TOOLS = [get_recipe, check_stock]
llm = ChatOpenAI(model="gpt-4o-mini").bind_tools(TOOLS)   # 모델에게 메뉴판을 건넨다

def agent(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(TOOLS))                 # 요청서를 실제로 실행하는 노드
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)   # tool_calls가 있으면 "tools", 없으면 END
builder.add_edge("tools", "agent")                        # 결과를 들고 다시 모델에게
graph = builder.compile()

result = graph.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})
for m in result["messages"]:
    m.pretty_print()

한 줄씩 짚어 볼게요.

  • parse_docstring=True — 이걸 빼면 독스트링의 Args: 설명이 스키마에 안 들어가요. 성실하게 써 두고도 모델에게 전달이 안 되는 셈이라 꼭 확인할 값이에요. 제 컴퓨터에서 get_recipe의 스키마를 찍어 보니 "dish": {"description": "요리 이름. 예: \"계란말이\"", "type": "string"}처럼 타입 힌트는 type이, Args:는 description이 돼 있었어요.
  • MessagesState — messages 칸 하나짜리 미리 만들어진 State예요. 새 메시지가 오면 덮어쓰지 않고 뒤에 쌓이게 설정돼 있어서 대화 기록을 따로 관리할 필요가 없어요.
  • bind_tools는 도구를 실행하지 않아요. 모델 응답의 tool_calls 칸에 "이 도구를 이 값으로 불러 달라"는 요청만 담겨요. 실제 실행은 ToolNode가 하고, 결과를 ToolMessage로 메시지 목록에 붙여요. 정말 그런지 아래에서 직접 확인해요.
  • tools_condition — 마지막 메시지에 tool_calls가 있으면 "tools"를, 없으면 END를 돌려주는 미리 만들어진 라우터예요.

실행하면 이런 순서로 흘러가요. 사용자 질문을 받은 모델은 답 대신 레시피와 재고를 알려 달라는 도구 요청을 내놓고(모델에 따라 두 개를 한 번에 요청하기도, 하나씩 부르기도 해요), ToolNode가 두 함수를 실행해 "계란 3개", "계란 4개"를 붙이고, 다시 불려 온 모델이 그걸 읽고 "한 접시만 가능하다"는 최종 답을 써요. 더 부를 도구가 없으니 tools_condition이 END를 돌려주고 끝나요.

강의 실습에서도 똑같은 장면이 나왔어요. 노트 조회 도구와 출제 가능 판정 도구를 쥐여 주고 "이 노트로 문제를 낼 수 있나" 물었더니, 모델이 먼저 조회를 불러 208자·4문장이라는 값을 받고, 그 숫자를 그대로 판정 도구의 인자(함수 괄호 안에 넣는 값)로 넣었어요. 개발자가 "조회한 뒤 판정하라"고 코드에 순서를 박지 않았는데도요. 이렇게 관찰과 행동을 번갈아 하며 다음 행동을 스스로 정하는 게 ReAct4 루프예요. 도구 결과라는 확실한 기준을 받아 오니 모델 기억에만 기대는 것보다 지어낼 여지가 줄어들어요.

요청서는 종이일 뿐 — 도구는 누가 실행하나

처음 보면 가장 헷갈리는 게 이 대목이에요. 모델의 답을 찍어 보면 글(content)은 비어 있고, tool_calls에 도구 이름과 넣을 값만 들어 있어요. 이 순간 도구는 이미 돌았을까요? 확인하려고 모델이 돌려주는 답과 똑같은 모양의 메시지(AIMessage, 모델의 답 한 통을 담는 LangChain 자료형)를 손으로 만들고, 함수 안에는 실행되는 순간 한 줄을 찍게 해 뒀어요. 모델을 부르지 않으니 API 키도 필요 없어요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from langchain_core.tools import tool
from langchain_core.messages import AIMessage
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.prebuilt import ToolNode

@tool
def get_recipe(dish: str) -> str:
    """요리 한 접시에 들어가는 재료와 양을 알려 준다."""
    print(">>> get_recipe 함수가 지금 실행됨")
    return {"계란말이": "계란 3개"}.get(dish, "레시피 없음")

# bind_tools를 붙인 모델이 돌려주는 답과 똑같은 모양의 메시지를 손으로 만든다
ai = AIMessage(content="", tool_calls=[{"name": "get_recipe", "args": {"dish": "계란말이"}, "id": "call_1"}])
print("content:", repr(ai.content))
print("tool_calls:", ai.tool_calls[0]["name"], ai.tool_calls[0]["args"])
print("--- 여기까지 함수는 한 번도 안 돌았어요 ---")

b = StateGraph(MessagesState)
b.add_node("tools", ToolNode([get_recipe]))    # 요청서를 실제로 실행하는 노드
b.add_edge(START, "tools")
b.add_edge("tools", END)
last = b.compile().invoke({"messages": [ai]})["messages"][-1]
print(type(last).__name__, "|", last.content)

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

content: ''
tool_calls: get_recipe {'dish': '계란말이'}
--- 여기까지 함수는 한 번도 안 돌았어요 ---
>>> get_recipe 함수가 지금 실행됨
ToolMessage | 계란 3개

요청서만 있을 때는 아무것도 안 찍혔고, ToolNode를 거친 뒤에야 "실행됨"이 찍혔어요. 결과("계란 3개")도 요청서 안에 숨어 있던 게 아니라 ToolMessage라는 새 메시지로 따로 붙었고요. 주방으로 치면 홀 직원이 요청서를 막 적은 순간에는 아직 아무도 창고에 안 갔고, 창고 담당이 다녀와서 결과를 따로 적어 붙여 준 거예요.

중요5강에서 짚은 내용

LLM은 글자만 만들어요. 우리 컴퓨터에 있는 함수를 직접 실행할 손이 없어요. 그래서 bind_tools를 붙인 모델도 "이 도구를 이 값으로 불러 달라"는 요청서(tool_calls)만 써서 내밀어요. 요청서를 받아 함수를 실제로 돌리는 건 우리 쪽 코드인 ToolNode이고, 결과는 ToolMessage로 메시지 목록에 따로 붙어요. 어느 모델을 쓰든 똑같아요.

순서를 정해 준 적이 없는데 — 모델은 왜 조회부터 했을까

앞에서 본 강의 실습에서 모델이 조회부터 한 이유는 셋이에요.

  • 도구가 요구하는 값이 순서를 끌어내요. 판정 도구는 글자 수와 문장 수를 넣어야 부를 수 있어요. 모델은 처음에 그 숫자를 모르고, 알아낼 길은 조회뿐이라 조회를 먼저 할 수밖에 없어요. 서류에 모르는 칸이 있으면 먼저 알아보러 가는 것과 같아요.
  • 설명서에 적어 뒀어요. 조회 도구의 독스트링에 "판정하기 전에 반드시 먼저 호출한다"는 문장이 있었어요. 모델이 보는 건 이 설명이에요. 위 코드의 get_recipe에 "만들 수 있는지 답하기 전에 먼저 호출한다"를 넣어 둔 것도 같은 장치예요.
  • 결과를 보고 다시 고를 기회가 있어요. tools에서 agent로 되돌아가는 선 덕분에, 도구 결과가 붙은 뒤 모델이 다시 불려서 그걸 읽고 다음 행동을 골라요. 앞에서 말한 ReAct 루프예요.

다만 이건 모델의 판단이라 매번 같다는 보장이 없어요. 숫자를 지어내서 바로 판정을 부르거나, 조회를 건너뛸 수도 있어요.

중요5강에서 짚은 내용

도구 루프에서는 도구를 부르는 순서를 모델이 정해요. 그 판단은 도구가 요구하는 값, 독스트링의 안내, 결과를 보고 다시 고를 수 있는 루프에서 나와요. 이 순서를 더 확실히 지키게 하는 방법은 약한 것부터 셋이에요.

  1. 부탁을 또렷하게 — 모델에게 매번 맨 앞에 붙여 주는 기본 지시문(시스템 프롬프트)에 "조회한 뒤 판정한다"는 절차를 적어요. 여전히 모델의 판단이라 보장은 못 해요.
  2. 도구를 하나로 합치기 — 판정 도구가 노트 이름만 받아서 안에서 조회까지 하게 바꿔요. 순서가 함수 코드 안에 박혀서, 모델이 숫자를 옮겨 적을 일이 아예 없어져요.
  3. 워크플로로 바꾸기 — 조회 노드와 판정 노드를 고정 엣지(add_edge)로 이어요. 순서를 그래프가 정하니 가장 확실해요. 다음 편의 프롬프트 체이닝이 이 모양이에요.

이 agent ↔ tools 루프는 너무 자주 쓰여서 한 줄짜리 부품도 있어요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요, 위 코드의 TOOLS를 그대로 써요

from langchain.agents import create_agent

agent = create_agent("openai:gpt-4o-mini", tools=TOOLS)
agent.invoke({"messages": [("user", "계란말이 두 접시 만들 수 있어?")]})

이 부품의 draw_mermaid()를 찍어 보면 노드 이름만 model·tools로 다를 뿐, 손으로 조립한 것과 같은 모양이었어요. 그럼 왜 굳이 손으로 만들었을까요. 실무에서는 도구 호출 횟수에 상한을 두거나, 특정 도구를 부르기 전에 사람의 승인을 받는 식으로 흐름을 고치고 싶어져요. 단순한 도구 루프 하나면 create_agent, 흐름을 통제해야 하면 직접 그리는 쪽이 유리해요.

나쁜 선택 vs 좋은 선택 — 도구 순서를 모델에게만 맡길 때

같은 주방에서, 홀 직원(모델)이 "계란말이 몇 접시까지 돼요?"에 답하게 한다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 레시피 조회(get_recipe)와 재고 조회(check_stock) 도구만 쥐여 주고, "레시피를 보고, 재고를 보고, 나눗셈한다"는 순서와 계산을 모델의 판단에 맡겼어요.

무슨 일이 생기나: 대개는 두 도구를 차례로 부르겠지만 매번 그렇다는 보장이 없어요. 어느 날 모델이 레시피 조회를 건너뛰고 "한 접시에 계란 2개쯤"이라고 짐작하거나 나눗셈을 틀리면, 틀린 접시 수가 에러 없이 그럴듯한 문장으로 나가요.		 무엇을 했나: 틀리면 곤란한 순서와 계산은 코드에 박았어요. 요리 이름만 받아서 함수 안에서 레시피 조회 → 재고 조회 → 나눗셈까지 하는 도구 하나로 합쳤어요.

무슨 일이 생기나: 모델은 "접시 수를 알아봐야겠다"는 판단만 하고, 계산은 같은 입력에 늘 같은 답을 내는 함수가 해요. 부를 도구도 둘에서 하나로 줄고, 그 함수는 테스트 코드로 미리 검사해 둘 수 있어요.

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 강의 2·5강이 퀴즈로 다시 짚은 내용이에요. 1~2강 것은 1편, 3강 것은 2편, 4강 것은 3편, 6~12강 것은 6편과 7편의 같은 목록에 있어요.

  • 단순한 계산도 도구로 빼요 — 티 안 나는 오답, 검사할 수 있는 함수, 일 나눠 맡기기 (2강)
  • 모델은 요청서만 쓰고, 실행은 ToolNode가 해요 (5강)
  • 도구 루프에서는 순서를 모델이 정해요 — 확실히 하려면 코드로 박아요 (5강)

다른 예제로 복습하기 — 책 저장소의 날씨 에이전트

제가 따로 읽고 있는 책 Generative AI Design Patterns의 공개 저장소에도 LangGraph 예제가 있어요. examples/21_tool_calling/langgraph/lg_weather_agent.py인데, 지명을 좌표로 바꾸는 도구와 날씨를 조회하는 도구를 쥔 에이전트예요. 구조가 위 ③과 똑같아요. assistant 노드와 ToolNode가 조건부 엣지로 오가고, 도구 노드에서 다시 assistant로 돌아오는 선이 있어요. 시작점을 set_entry_point()로 지정한 건 add_edge(START, ...)와 같은 뜻의 예전 표기예요.

다만 그대로는 안 돌아가요. 제가 확인한 걸 적어 둘게요.

  • 모델 이름 gemini-1.5-flash는 이미 서비스가 끝난 모델이라 지금 쓰는 모델 이름으로 바꿔야 해요.
  • 날씨는 미국 기상청 API를 불러서 미국 지명만 돼요. 지명 변환에는 Google Maps 키도 필요해요.
  • 주석 처리된 MemorySaver·thread_id 줄이 바로 9/22 주제(상태 지속성)예요. 살릴 때는 import 경로를 지금 방식인 langgraph.checkpoint.memory로 바꿔야 해요.

직접 해보기

  1. 독스트링 망가뜨리기 — 바꿀 것: get_recipe의 독스트링을 """조회.""" 한 단어로 줄여요(Args:가 없으면 parse_docstring=True가 오류를 내니 함께 지워요). 측정할 것: 같은 질문에 모델이 그 도구를 부르는지, 인자는 맞는지. 비교할 것: 원래 독스트링일 때와 도구 호출 순서. 도구가 안 불리면 프롬프트보다 독스트링부터 의심하는 습관이 생겨요.
  2. 계산을 도구로 빼기 — 바꿀 것: "재고로 몇 접시까지 되는지" 나눗셈을 하는 도구를 하나 더해요. 측정할 것: 재고를 7개, 11개로 바꿔 가며 답이 맞는지. 비교할 것: 같은 질문을 도구 없이 물었을 때 계산이 틀리는 빈도.
  3. 도구 호출 횟수에 상한 걸기 — 바꿀 것: agent 노드에서 메시지 목록의 ToolMessage 개수를 세다가 5개를 넘으면 도구를 붙이지 않은 모델로 마무리하게 해요. 측정할 것: 상한에 걸렸을 때 최종 답에 그 사실이 드러나는지. 이게 create_agent 대신 직접 그리는 이유를 몸으로 느끼는 실험이에요.

정답은 없어요. 모델 답은 실행할 때마다 달라질 수 있으니, 제 조건에서 몇 번 돌려 보고 기록으로 비교하는 게 요령이에요.

함께 읽으면 좋은 글

  • 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동 — 오늘 조립한 루프의 뿌리예요.
  • 도구 하나가 호출되기까지 — 정의·파싱·구조화 요청 — bind_tools와 ToolNode 사이에서 무슨 일이 일어나는지 더 자세히 봐요.
  • 길을 누가 정하나 — LangGraph와 워크플로·에이전트 — 이 편이 눈금자에서 어디로 옮겨 간 건지를 그린 시리즈 첫 편이에요.
  • AI가 짠 백엔드 코드에서 반드시 확인할 것들 — API 키 같은 비밀값을 코드와 떼어 두는 원칙을 처음 다룬 글이에요.
  1. API 키 — 유료 AI 서비스를 내 계정으로 부를 때 쓰는 비밀 문자열이라, 남에게 보이면 내 요금으로 남이 쓸 수 있어요. ↩
  2. 독스트링(docstring) — 파이썬 함수 맨 위에 적는 설명 문자열로, LangChain은 이것을 읽어 모델에게 보낼 도구 설명을 만들어요. ↩
  3. JSON 스키마 — 데이터가 어떤 칸과 자료형을 가져야 하는지 적은 규칙서로, 도구 호출 글에서 메뉴판의 '주문 규칙'에 빗댔던 입력 스키마가 이것이에요. ↩
  4. ReAct(Reasoning + Acting) — 생각과 행동을 번갈아 하며 관찰 결과로 다음 행동을 정하는 루프로, ReAct 루프 글에서 그 뿌리를 다뤘어요. ↩
  5. LLM의 답은 확률적이라 같은 질문도 실행할 때마다 도구 호출 순서나 메시지 수가 달라질 수 있어서, 이 값은 강의 실습의 한 번 실행 결과로만 읽어야 해요. ↩
