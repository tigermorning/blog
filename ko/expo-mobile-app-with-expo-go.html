앞 편까지 만든 AI 친구 서비스는 웹 주소로만 열려요. 매일 말을 거는 서비스라면 사용자는 브라우저를 열고 주소를 찾는 대신 폰 홈 화면의 아이콘을 누르고 싶어 해요. 그런데 앱을 만들려면 언어를 새로 배우고 개발 도구를 깔아야 하고, 아이폰 앱은 맥에서만 만들 수 있다고들 해요. 이 글은 Windows 노트북으로, 코딩 에이전트와 함께, 지금 있는 백엔드를 그대로 쓰는 앱을 내 폰에 띄우는 데까지 가는 길을 정리한 거예요. 다른 사람 폰에 설치하고 출시를 준비하는 일은 이 글의 범위가 아니에요.

웹과 앱 — 코드가 어디서 실행되나

웹 서비스는 주소를 열 때마다 브라우저가 서버에서 화면 코드(HTML, JavaScript)를 받아 그 자리에서 실행하고, 탭을 닫으면 코드가 사라져요. 서버에 새 버전을 올리면 모든 사용자가 바로 새 화면을 봐요.

앱은 화면 코드, 이미지, 앱 이름과 권한 같은 설정을 앱 파일 하나에 담아 폰에 설치해 두고 실행해요. 화면 코드를 서버에서 받을 필요가 없고, 대화나 크레딧처럼 바뀌는 데이터만 백엔드 API로 받아요. 대신 화면을 고치면 앱 파일을 새로 만들어 스토어에 올리고 사용자가 업데이트해야 바뀌어요. 업데이트하지 않은 폰에는 옛 버전이 계속 남아요.

그래서 화면이 웹에서 앱으로 바뀌어도 백엔드는 그대로 써요. 달라지는 점 하나는 옛 버전 앱이 폰에 남는다는 거예요. 앱을 내놓은 뒤에는 옛 화면이 새 백엔드를 부르는 일이 생기므로, 앱이 읽는 API 응답의 모양은 함부로 바꾸지 않아요.

앱을 말할 때 나오는 낱말 — 플랫폼, 네이티브, 빌드

폰은 운영체제1 위에서 앱을 실행해요. 대부분은 애플의 iOS와 구글의 안드로이드(Android)예요. 앱 개발에서는 운영체제와 그 위에서 앱을 만드는 도구, 앱을 올리는 스토어를 묶어 플랫폼이라고 불러요.

네이티브2는 플랫폼이 기본으로 주는 언어와 부품으로 만든 것을 말해요. 아이폰 설정 앱의 스위치와 스크롤, 글자를 칠 때 올라오는 키보드가 그래요. 카메라·위치·알림처럼 운영체제가 열어 주는 기능은 사용자가 권한을 허락해야 쓸 수 있고, 그래서 앱이 처음 카메라를 쓸 때 «허용하시겠습니까» 창이 떠요.

빌드3는 사람이 쓴 소스 코드를 폰이 설치하고 실행할 수 있는 앱 파일로 만드는 과정이에요. 코드를 내려받고, 패키지를 설치하고, 코드를 파일 하나(번들)로 묶고, 네이티브 부분을 기계어로 바꾸고(컴파일), 만든 사람의 키로 서명하는 순서예요. 서명이 있어야 폰과 스토어가 «중간에 바뀌지 않았고, 같은 개발자가 낸 새 버전»이라고 확인해요. 한 번 내보낸 앱 파일은 사용자 수만큼의 폰에 설치되므로 되돌릴 수 없어요.

비유로 먼저 — 수업 시간의 칠판과 가방 속 교과서

앞 편들의 식당 비유는 «앱을 폰에 설치한다»는 장면을 설명하기에 어색해서, 이 편에서는 학교 수업으로 바꿔서 설명해요. 웹은 선생님이 수업 때마다 칠판에 적어 주는 것이에요. 학생(브라우저)은 수업에 들어갈 때마다 선생님(서버)이 적은 내용을 그 자리에서 읽고, 수업이 끝나면 칠판은 지워져요. 선생님이 내용을 고치면 다음 수업에 모든 학생이 새 내용을 봐요. 앱은 산 책을 가방에 넣고 다니는 교과서예요. 열면 바로 읽을 수 있지만, 선생님이 새 내용을 정해도 이미 가진 책은 옛 내용 그대로예요. 새 책을 구해야 바뀌고, 구하지 않은 학생은 옛 책으로 공부해요. 다만 «오늘의 급식 메뉴» 같은 매일 바뀌는 정보는 책에 적혀 있지 않고 «학교 게시판에서 확인하세요»라고만 안내돼 있어서, 학생은 그때그때 게시판을 봐요. 칠판 수업을 듣는 학생도 교과서를 든 학생도 급식 메뉴는 같은 게시판에서 확인해요.

어느 쪽이 좋은지는 상황마다 달라요. 스토어에 안 올려도 되고 웹 화면을 그대로 쓰고 싶으면 PWA가 가장 빨라요. 이미 잘 만든 웹 화면이 있고 맥과 빌드 도구를 갖춘 팀이면 웹 래핑도 해 볼 만해요. 그래픽이 무거운 게임이나 최신 운영체제 기능을 바로 써야 하면 네이티브가 맞아요.

이 글의 조건은 세 가지예요. 노트북은 대부분 Windows이고, 코딩 에이전트와 함께 만들며, 백엔드는 이미 있어서 화면만 새로 만들면 돼요. 이 조건에서 아이폰까지 다루면서 내 컴퓨터에 설치할 게 가장 적은 길이 Expo라서 Expo로 가요. 다만 앱 파일은 결국 컴파일해야 하므로 그 일을 클라우드 서비스에 맡기고, 무료 플랜의 빌드 횟수 제한을 감수해요.

Expo가 하는 일 — 도구들을 한 묶음으로

React Native는 JavaScript 코드로 네이티브 화면을 그리는 일까지만 맡아요. 그것만으로 앱을 만들면 화면 이동, 카메라 같은 기기 기능, 빌드와 서명에 쓸 도구를 하나씩 골라 맞춰야 해요. Expo는 이 도구들을 서로 버전이 맞는 한 묶음으로 줘요.

컴파일을 피하는 두 가지 방법

플랫폼 도구로 컴파일해야 하는 것은 앱의 네이티브 부분뿐이고, 내 코드는 묶기만 하면 돼요. Expo는 이 컴파일을 내 노트북 밖으로 옮겨요.

개발할 때는 Expo Go를 써요. Expo Go는 자주 쓰는 네이티브 부분을 미리 컴파일해 둔 앱이라서, 노트북의 개발 서버가 만든 번들을 와이파이로 받아 바로 실행해요. 코드를 저장하면 폰 화면이 몇 초 안에 바뀌어요. 다른 사람에게 줄 앱 파일은 EAS 빌드로 만들어요. 프로젝트를 Expo 클라우드에 올리면 안드로이드 도구가 깔린 서버와 Xcode가 깔린 맥 서버가 컴파일하고 서명해서 설치 링크를 돌려줘요.

Expo Go로 되는 것과 개발용 빌드가 필요한 것

Expo Go에는 미리 컴파일된 네이티브 기능만 들어 있어요. 그 밖의 라이브러리를 쓰려면 내 앱 전용으로 네이티브 부분까지 컴파일한 개발용 빌드를 만들어 폰에 설치해야 해요.

홈 화면 위젯, 애플워치 앱안 됨네이티브 코드를 따로 써야 함

이 글에서 만드는 대화 앱은 서버를 부르고 화면을 보여 주고 카메라와 사진첩을 쓰는 정도라 Expo Go로 충분해요. 코딩 에이전트가 새 라이브러리를 설치하자고 하면 그 라이브러리가 Expo Go에서 도는지부터 확인하게 해요. 패키지는 npx expo install로 설치하는데, 프로젝트의 SDK 버전에 맞는 버전을 골라 주기 때문이에요.

프로젝트의 SDK 버전은 package.json의 expo 버전으로 정해지고, 폰의 Expo Go가 그 SDK를 지원해야 앱이 열려요. 스토어의 Expo Go는 보통 최신 SDK 하나만 지원해요. 이 글에서는 SDK 58 기준으로 설명하고, Node.js는 22.13 이상이 필요해요.

앱과 백엔드가 주고받는 것 — 켜질 때부터 답을 받을 때까지

앱은 화면만 가지고, 데이터와 판단은 모두 백엔드에 있어요. 웹 화면이 하던 일을 폰 화면이 대신하는 것이라 백엔드 API는 하나도 바꾸지 않아요. 템플릿(앱 저장소)의 파일은 역할이 이렇게 나뉘어요.

파일하는 일
src/app/_layout.tsx앱 전체 틀. 로그인 상태를 모든 화면에 나눠 주고 화면을 쌓아 보여 줌
src/app/index.tsx대화 화면. 캐릭터가 없으면 캐릭터 화면으로 보냄
src/app/character.tsx캐릭터 화면
src/lib/api.ts백엔드 주소, API 호출, 답 스트리밍 읽기
src/lib/session.tsx, src/lib/supabase.ts앱이 켜질 때 설정 읽기와 익명 로그인

src/app/ 폴더는 Expo Router의 규칙을 따라서, 파일 이름이 곧 화면 주소예요. src/app/memories.tsx 를 만들면 /memories 화면이 생겨요. 화면 파일이 fetch를 직접 부르지 않고 api.ts를 거치게 한 이유는, 백엔드 주소와 로그인 토큰을 붙이는 일을 한곳에 모으기 위해서예요.

앱을 처음 켜서 메시지 하나의 답을 받을 때까지는 이런 순서예요.

순서누가 → 누구에게무엇을
1앱 → 백엔드/api/config로 Supabase 주소, publishable key, 캐릭터 화면 선택지를 요청
2앱 → Supabase익명 로그인으로 게스트 사용자를 만들고 토큰을 받아 기기에 저장
3앱 → 백엔드토큰을 붙여 내 정보, 캐릭터, 지난 대화를 요청. 백엔드는 토큰이 누구인지 Supabase에 확인하고 그 사용자의 데이터만 돌려줌
4앱 → 백엔드메시지를 /api/chat으로 보냄
5백엔드 → 앱답이 한 번에 오지 않고 한 줄에 이벤트 하나씩 흘러옴: 글자 조각 delta, 약속이 만들어졌을 때 reminder, 기억 정리 결과 memory, 끝을 알리는 done

React Native의 기본 fetch는 이렇게 조금씩 오는 응답을 읽지 못해서, 템플릿은 Expo의 expo/fetch로 줄 단위로 읽어 글자를 이어 붙여요. 앱에 넣는 설정은 백엔드 주소(EXPO_PUBLIC_API_URL) 하나뿐이에요.

앱에 넣으면 안 되는 값

EXPO_PUBLIC_으로 시작하는 환경변수7는 빌드할 때 앱 파일 안에 그대로 들어가요. 앱 파일은 누구나 내려받아 열어 볼 수 있으니 공개되는 값이에요. 백엔드 주소와 Supabase publishable key는 공개돼도 되는 값이라 괜찮지만, Supabase secret key나 LLM API 키를 넣으면 앱을 받은 누구나 그 키로 모든 사용자의 데이터를 읽거나 내 비용으로 LLM을 불러요. 비밀값은 백엔드에만 두고, 앱은 백엔드를 거쳐서만 써요.

같은 백엔드인데 대화가 달라 보이는 이유. 앱에서 저장한 캐릭터와 대화는 백엔드에 저장돼요(Supabase를 쓴다면 Table Editor의 messages 테이블에서 보여요). 앱을 닫았다 열어도 이어지는 건 앱이 익명 로그인 토큰을 기기에 저장했다가 같은 게스트로 다시 로그인하기 때문이에요. 그런데 같은 백엔드를 브라우저로 열면 앱의 대화가 안 보여요. 브라우저와 폰은 로그인 정보를 따로 저장해 서로 다른 게스트가 되고, 백엔드는 모든 조회에 그 사용자의 ID 조건을 붙이기 때문이에요. 같은 사람이 웹과 앱에서 같은 대화를 보려면 구글 로그인처럼 기기와 상관없이 같은 사용자로 알아보는 방법이 필요해요.

화면 고치고 사진으로 약속 만들기 — 구조를 먼저 정하고 에이전트에게

개발 서버를 켜 둔 채 src/app/index.tsx에서 대화가 없을 때 보이는 문구를 바꾸고 저장하면 몇 초 안에 폰 화면이 바뀌어요. 다시 빌드하거나 설치하지 않았는데 바뀌는 건 Expo Go가 개발 서버에서 바뀐 번들을 다시 받아 화면을 새로 그리기 때문이에요. 일부러 괄호 하나를 지우고 저장하면 폰에 빨간 오류 화면이 뜨고 어느 파일 몇째 줄인지 나와요. 에이전트가 고친 뒤 앱이 빨간 화면이 되면, 이 문구를 그대로 에이전트에게 붙여 주는 게 가장 빠른 해결 방법이에요.

웹 화면에는 있는데 앱에는 없는 정보를 더해 볼게요. 웹 화면은 답 아래에 «기억했어요», «약속 알림» 같은 작은 메모를 보여 주는데 앱은 답 글자만 보여 줘요. 에이전트는 시키는 대로 코드를 쓰지만 어떤 데이터를 어디에 보여 줄지는 대신 정해 주지 않아요. 그래서 구조부터 표로 정해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

대화 중에 나에 대한 걸 기억하거나 약속을 저장했을 때, 답 말풍선 아래에 회색 작은 글씨로 무엇을 기억했는지 같이 보여 주는 기능 만들어 줘.

구현이 끝나면 «나 고양이 두 마리 키워»를 보내 기억 메모가, «내일 아침 8시에 물 마시라고 알려 줘»를 보내 약속 메모가 붙는지 봐요. 앱을 닫았다 열면 지난 대화에는 메모가 없어요. 메모는 저장된 메시지가 아니라 그 턴에 흘러온 이벤트라서, 지난 대화에도 보이게 하려면 백엔드가 메시지와 함께 메모를 저장해 돌려줘야 해요. 이렇게 화면에 보이는 정보마다 어디서 오는지 알고 있으면, 무엇을 앱에서 고치고 무엇을 백엔드에 요청할지 나눌 수 있어요.

읽은 글을 바로 보내지 않는 데는 이유가 있어요. OCR은 손글씨·기울어진 사진·흐린 글자를 잘못 읽기 쉽고, 잘못 읽은 날짜로 약속이 저장되면 사용자는 틀린 시각에 알림을 받아요. 사람이 한 번 확인하는 단계가 오류를 보내기 전에 잡아 줘요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

일정표를 카메라로 찍거나 사진첩에서 골라서, 사진 속 글자를 읽어 입력창에 넣어 주는 기능 만들어 줘. 글자 읽기는 백엔드의 /api/ocr 을 쓰면 돼.

사진을 보냈는데 오류가 나면 상태 코드부터 봐요. 404이고 «사진 글자 읽기가 꺼져 있습니다»라면 백엔드에서 OCR이 꺼진 거예요(OCR_ENABLED=true와 OCR 프로그램 tesseract가 들어간 이미지인지 확인). 401이면 요청에 토큰이 안 붙은 거예요. 400대 오류로 사진이 없다는 내용이면 사진이 photo 필드로 가지 않은 건데, 공통 헤더의 JSON용 Content-Type이 OCR 요청에도 붙었는지 확인해요. multipart 폼은 경계 문자열이 들어간 Content-Type을 요청이 직접 만들어야 해서, 이 헤더를 손으로 지정하면 백엔드가 사진을 못 찾아요. 오류 없이 엉뚱한 글이 돌아오면 코드보다 사진 문제일 때가 많으니, 밝은 곳에서 글자가 화면을 가득 채우게 다시 찍어요.

이 기능에서 앱이 맡은 일은 사진을 받고 권한을 묻고 보내는 것까지고, 글자를 읽고 약속을 만드는 일은 백엔드가 해요. 그래서 OCR 엔진을 바꾸거나 약속을 만드는 방식을 고쳐도 앱은 다시 빌드할 필요가 없고, 카메라 화면이나 권한 문구를 바꿀 때만 앱을 고쳐요. 에이전트가 새 패키지를 설치하자고 하면 npx expo install로 설치하는지, Expo Go에서 도는지 확인하고, 작업이 끝나면 npx tsc --noEmit(타입 검사)과 npx expo-doctor(의존성·설정 검사)를 돌려 오류가 없는지 봐요.

나쁜 선택 vs 좋은 선택 — 같은 학교, 같은 상황

학교가 교과서를 만들어 나눠 주려는 장면이에요. 책에 무엇을 인쇄할지 정할 때 이렇게 갈려요.

나쁜 선택좋은 선택
학교 금고 열쇠(Supabase secret key, LLM API 키)를 교과서 안에 같이 인쇄해 나눠 준다 → 책을 받은 누구나 열쇠를 읽어 금고를 열고 학교 돈(내 비용)을 써요. 학교 게시판 주소(백엔드 주소)만 책에 적고 열쇠는 학교 사무실에만 둔다 → 책이 퍼져도 금고는 안전하고, 중요한 확인은 항상 사무실을 거쳐요.
받아 적은 신청서(사진에서 읽은 글)를 확인 없이 곧바로 접수한다 → 날짜를 잘못 받아 적으면 틀린 날짜로 접수돼요. 읽은 글을 입력창에 넣어 사용자가 확인·수정한 뒤 보낸다 → 오류가 접수 전에 잡혀요.

실무에서 이렇게 판단해요 — 자주 틀리는 8가지 상황

앱 만들기를 배우고 나서 가장 자주 틀리는 것은 개념이 아니라 «이 상황에서 어떻게 하겠는가»예요. 개념은 아는데 상황과 연결돼 있지 않으면, 현장에서는 «이거 앱을 다시 만들어야 하나?»에서 막혀요. 그래서 상황별로 판단 규칙 한 줄, 비유 한 줄, 사례표를 모았어요. 제 앱 «루틴 도장»(도장 세 칸을 누르면 도장이 바뀌는 작은 앱)을 Expo Go에서 직접 돌려 본 것은 사례표에 «직접 확인»이라고 적었어요.

유형 1. «이 수정, 앱을 다시 만들어야 하나?»

  • 판단 규칙: 고치려는 것이 앱 파일 안에 있으면 다시 빌드하고, 밖(서버)에 있으면 서버만 배포해요.
  • 비유: 이미 학생들에게 나눠 준 교과서 속 문장은 바꿀 수 없지만, 학교 게시판(오늘의 급식표)은 언제든 고칠 수 있어요.

유형 2. «옛 앱이 새 백엔드를 부를 때»

  • 판단 규칙: 사용자 중에는 업데이트하지 않은 폰이 항상 있어요. 백엔드가 옛 앱도 계속 처리해 주는 성질을 하위 호환10이라고 해요. 응답에 «더하는 것»은 안전하고, «이름을 바꾸거나 없애거나 모양을 바꾸는 것»은 옛 앱을 깨뜨려요.
  • 비유: 학교 게시판이 신청 양식의 칸 이름을 바꿨는데, 옛 교과서에는 옛 칸 이름으로 신청하는 방법이 적혀 있어요. 칸을 못 찾으면 신청이 접수되지 않아요.

  • 비유: 교정쇄 기계(Expo Go)에는 자주 쓰는 활자와 도구가 미리 들어 있어요. 그걸로 만든 쪽은 바로 확인되고, 특수한 활자(회사별 SDK)가 필요하면 내 전용 교정 기계(개발용 빌드)를 따로 마련해야 해요.

유형 6. «이 정보는 앱을 껐다 켜도 남나?»

  • 판단 규칙: 화면에 보이는 정보마다 어디서 오는지를 확인해요. 세 곳이에요. ① 백엔드에서 «조회»해서 오는 것, ② 그 순간 «스트리밍 이벤트»로만 오는 것, ③ 폰 안 저장소에 있는 것. 껐다 켰을 때 ①과 ③은 다시 불러올 수 있고 ②는 사라져요.
  • 비유: 게시판에 붙인 공지(①)와 내 필기 노트(③)는 다시 볼 수 있지만, 수업 시간에 선생님이 말로만 한 설명(②)은 기록이 없어요.

유형 7. «방법 고르기: PWA, 웹 래핑, 네이티브, Expo»

  • 판단 규칙: 세 가지 조건으로 골라요. ① 스토어에 올려야 하나, ② 내 컴퓨터에 어떤 도구가 있나, ③ 폰의 기능을 얼마나 쓰나.
  • 비유: 게시판에 붙여 두고 보는 인쇄물(PWA)은 책 없이 바로 보고, 칠판 수업에 표지만 씌워 교과서처럼 내는 방식(웹 래핑), 교과서를 처음부터 새로 집필하는 방식(네이티브), 한 원고로 인쇄소에서 두 가지 판형을 한꺼번에 찍는 방식(Expo)이 있어요.

혼자 풀어 보기 (섞어서)

먼저 생각해 보고 눌러서 답을 확인해요.

1. 서버에서 AI의 말투를 바꿨어요. 사용자에게 앱 업데이트를 부탁해야 하나요?

아니요. 서버의 프롬프트는 앱 파일 밖에 있어서 서버만 배포하면 모두에게 바로 적용돼요. (유형 1)

2. API의 날짜 필드 이름을 date에서 created_at으로 바꿨어요. 지난달 앱 버전을 쓰는 사용자는 어떻게 되나요?

옛 앱은 date를 찾는데 없어서 날짜가 빈칸이 되거나 오류가 나요. 한동안 두 이름을 함께 내려주는 것이 안전해요. (유형 2)

3. 앱에 카카오 로그인을 붙이려고 해요. Expo Go로 시험할 수 있나요?

없어요. 회사별 SDK는 Expo Go에 들어 있지 않아서 개발용 빌드가 필요해요. (유형 3)

4. 앱 설정에 OpenAI 키를 EXPO_PUBLIC_OPENAI_KEY로 넣었어요. 무엇이 문제인가요?

앱 파일 안에 그대로 들어가서, 앱을 받은 누구나 그 키를 꺼내 내 비용으로 LLM을 부를 수 있어요. 키는 백엔드에만 두고 앱은 백엔드를 거쳐서 써요. (유형 4)

5. 도장 기록을 화면 상태에만 두면, 앱을 종료했다 다시 열었을 때 도장은 어떻게 되나요?

사라져요. 제가 만든 루틴 도장은 폰 안 저장소(AsyncStorage)에 저장해서 남았어요. (유형 6)

6. OCR이 손글씨를 자꾸 틀려요. 앱 코드를 고쳐야 하나요?

글자를 읽는 일은 백엔드가 해서, 엔진을 바꾸는 것은 백엔드 쪽이에요. 앱에서 할 일은 «보내기 전에 사람이 확인·수정하게 하는» 정도예요. (유형 5)
