이 시리즈는 노드 아홉 개를 따라 도장판 앱(칸이 열리는 루틴 도장 앱)과 예제 앱을 서비스로 내보내는 과정을 글로 남겼어요. 이 글은 아홉 편을 요약하는 글이 아니에요. 각 글이 같은 세 질문의 서로 다른 칸이었다는 걸 보여 주려고 다시 묶었어요. 먼저 모듈에서 배운 것을 세 질문으로 정리하고, 가장 가볍게 넘어갔던 «무중단이라고 부르는 기준»을 계산으로 확장해 보고, 마지막에 내 앱에 적용해서 비어 있는 곳을 적을게요.

비유로 먼저 — 밀키트 상자를 가맹점에 보내는 본사

이 시리즈의 비유를 그대로 이어 갈게요. 본사(나)가 밀키트 상자를 만들어 가맹점(실제 서비스)에 보내요. 처음에는 사장이 상자를 직접 들고 갔지만, 지금은 배송 로봇이 가요. 보내기 전에 검수대에서 상자를 열어 보고, 시식 주방에서 맛을 본 뒤, 시식한 그 상자를 다시 포장하지 않고 보내요. 가맹점은 영업 중이어서, 새 상자는 뒤쪽 진열대에 먼저 차려 두고 손님 안내만 돌려요. 문제가 보이면 안내를 원래대로 돌려요.

핵심 한 줄: 상자를 보내는 일은 포장, 검수, 시식, 안내 교체가 이어진 한 줄이고, 줄 어디에서든 «지금 무엇이 나가고 있나»를 말할 수 있어야 해요.

다만 비유가 끊기는 점이 있어요. 가맹점 손님은 진열대 교체를 눈으로 보지만, 서비스 사용자는 교체가 일어났는지도 몰라요. 그래서 «사용자가 오류를 봤는지»는 눈이 아니라 숫자로 세어야 해요.

전체 흐름 — 변경 하나가 지나가는 칸과 세 질문

코드 변경 하나가 사용자에게 닿기까지 지나는 칸을 위에, 각 칸이 답해 주는 질문을 아래에 그렸어요. 칸 아래 숫자는 해당 노드 번호예요.

정리 — 아홉 노드, 아홉 키워드

노드 하나를 키워드 하나로 줄이고, 그 키워드가 막아 준 일과 도장판이나 예제 앱에서 제가 직접 본 값을 나란히 적었어요. 자세한 과정은 각 글에 있어요. 노드 1~3은 이 글에 옮길 수치를 이번에 다시 읽지 않아, 노드 목록의 소개 문장만 근거로 썼어요.

노드키워드막아 주는 일내가 본 것

이 표를 쓰면서 눈에 띈 건, 아홉 행이 모두 «증거를 남기는 방법»이라는 점이에요. 4번의 리비전 번호, 5번의 실패한 테스트 개수, 7번의 지문, 9번의 실패 건수는 전부 «말로는 안전하다고 하지만 숫자로 보여 주는» 방식이에요.

확장 — «무중단»에 숫자를 붙이면 하루에 몇 번 배포할 수 있나

9번 글에서 가장 가볍게 지나간 건, 기본 프로브 실험의 실패 구간이 약 29초(15:11:07~15:11:36)였다는 사실이었어요. 29초가 길다고 해야 할지 짧다고 해야 할지 기준이 없었어요. 8번 글의 가용성 표가 그 기준이 돼요. 가용성은 서비스가 정상으로 답한 시간의 비율이고, 1년에 허용되는 멈춤은 이렇게 계산돼요.

가용성 목표1년에 허용되는 멈춤계산
99%약 3.65일8,760시간 × 1%
99.9%약 8.8시간8,760시간 × 0.1% = 8.76시간
99.99%약 53분8,760시간 × 0.01% ≈ 52.6분
99.999%약 5분8,760시간 × 0.001% ≈ 5.3분

이제 «실패 구간 29초가 배포 한 번마다 생긴다»고 가정해 볼게요. 이 계산은 제가 세운 가정이에요. 실제 측정이 아니고, 실패 구간 29초 동안 모든 요청이 실패한 것으로 치는 보수적인 가정이에요(측정에서는 전체 389건 중 71건, 약 18%가 실패했어요).

배포 횟수1년에 잃는 시간99.9% 허용량(8.76시간) 대비
하루 1번29초 × 365 = 10,585초 ≈ 2.9시간약 34%를 배포가 써요
하루 3번약 8.8시간허용량을 거의 다 써서, 다른 사고가 나면 바로 목표를 넘어요
하루 1번, /health 프로브0초(측정에서 283건 중 0건 실패)대신 배포 한 번이 약 43초 더 걸려요(약 19초 → 약 62초)

제가 얻은 해석은 이래요. 배포가 자동화되면 «하루에 몇 번 내보내나»가 늘어나는데, 배포 한 번의 실패가 작아 보여도 횟수를 곱하면 가용성 예산을 크게 갉아먹어요. 그래서 9번 글의 /health 프로브는 «배포가 43초 늦어지는 대가»로 배포 횟수가 늘어도 예산을 쓰지 않는 구조를 사 오는 거예요. 이 해석은 계산에서 나온 추정이고, 실제 서비스의 가용성은 사용자가 몰리는 시간대나 다른 장애까지 포함해 따로 재야 해요.

활용 — 내 앱(도장판)에 세 질문을 대 보기

5번 글과 9번 글의 «비어 있는 곳», «해 보지 못한 것» 절에서 제가 스스로 적어 둔 한계를 세 질문 아래로 모았어요. 오른쪽 열의 다음 한 걸음은 지금 정한 제안이고, 아직 하지 않았어요.

질문지금 있는 증거비어 있는 곳(글에 적은 것)다음 한 걸음(제안)
무엇이 나갔나 화면 아래 커밋 7자리와 머지 기록 대조, 감사 로그의 저장소·브랜치 내 앱은 GitHub Pages가 저장소 전체를 공개해서 tests/와 package.json도 보여요. 공개 범위를 정리하지 않았어요. 공개 범위를 정리하고, 시험한 이미지의 지문을 배포 기록에 같이 남기는지 확인하기
사용자는 괜찮았나 9개 시나리오 테스트, /health·/version 확인, 요청 세기 프로브와 스모크 테스트는 /health와 /version만 봐서 앱의 답이 이상해졌는지는 몰라요. 도우미 답 품질은 사람이 같은 요청을 여러 번 보내 확인했고, 자동 평가는 없어요. 배포 뒤 대표 질문 몇 개를 보내 규칙을 어겼는지 세는 스크립트 하나 만들기
되돌릴 수 있나 Revert PR, 롤백 24초, 롤백 워크플로(버튼 한 번) 내 앱 main에는 브랜치 보호가 없어서 테스트가 실패해도 합치기가 막히지 않아요. 롤백 워크플로 실행 중 요청 실패 수는 측정이 끊겨 확인하지 못했어요. main에 필수 검사를 걸고, 롤백 중 요청 세기를 끊기지 않게 다시 재 보기

이 표를 만들고 보니 비어 있는 칸이 「사용자는 괜찮았나」에 몰려 있었어요. 자동으로 점검하는 도구가 «서비스가 떠 있는가»는 잘 보는데, «답이 맞는가»는 사람이 보고 있다는 뜻이에요. 다음에 코딩 에이전트에게 맡길 일을 고른다면 이 칸이에요.

나쁜 선택 vs 좋은 선택 — 배포가 끝난 뒤 "괜찮은가"를 확인할 때

비유로 돌아가서, 가맹점 영업 중에 시작이 늦는 새 진열대로 안내를 돌렸다고 해 볼게요.

나쁜 선택좋은 선택
배포 화면이 초록색이니 괜찮다고 보고 확인을 끝내요. → 기본 프로브는 포트가 열리자마자 통과시켜서, 30초 동안 503을 돌려주는 앱에 요청을 보냈고 389건 중 71건이 실패했어요. 배포 명령은 성공이었어요. 배포하는 동안 같은 주소에 0.2초마다 요청을 보내 실패 건수를 세요. → /health 프로브로 바꿔 요청 283건 중 0건 실패를 확인했어요. 배포가 약 43초 더 걸린 값도 같이 남겼어요.

이 글에 나온 숫자 — 배포 방식을 고르거나 점검표를 만들 때 다시 보는 값

앞의 각 글에서 직접 잰 값 가운데 다른 서비스에서도 기준으로 쓸 만한 것만 모았어요. 실험값은 한 번씩 잰 값이고 서비스마다 달라질 수 있어요. 가용성 계산은 이 글에서 제가 세운 가정 위의 값이에요.

무엇의 숫자인가값알아 둘 것

이런 증상이 보이면먼저 열어 볼 자리확인 방법
배포 워크플로는 초록색으로 끝났는데 배포 직후 사용자가 오류를 봤다고 해요. Cloud Run 서비스의 스타트업 프로브 설정(포트만 보는 기본값인지, /health 주소인지) 배포하는 동안 요청을 0.2초마다 보내 실패 건수를 세요. 실패가 배포 직후 몇십 초에 몰려 있으면 프로브를 의심해요. 이번에는 389건 중 71건이었어요.
배포는 성공했는데 서비스 주소는 여전히 옛 버전을 보여 줘요. Cloud Run 서비스의 트래픽 설정(특정 리비전이나 태그에 고정돼 있는지) 트래픽 설정을 조회해 «가장 최근 리비전 100%»인지 봐요. 롤백이나 카나리를 한 번 하면 트래픽이 특정 리비전에 고정돼 새 리비전이 0%로 남을 수 있어요. 풀려면 --to-latest를 써요.
테스트는 전부 통과했는데 실제 서비스에서는 AI가 규칙을 어겼어요. 테스트가 가짜 AI를 쓰는지, 실제 모델에 요청을 보내는지 가짜 AI를 쓴 테스트는 규칙이 프롬프트에 들어갔는지만 알아요. 5번 글에서는 같은 요청을 서비스에 4번 중 2번 → 8번 중 1번 → 12번 중 0번 규칙을 어겼다고 직접 보내 확인했어요. 표본이 작아서 «확인했다»는 기록이에요.
내 컴퓨터에서는 되는데 CI에서만 실패해요(No module named 'app', 종료 코드 2). pytest.ini의 pythonpath 줄, 시간대가 들어가는 테스트 CI는 내 컴퓨터가 우연히 맞춰 주던 것(시간대, 실행 위치)을 걷어 내요. pythonpath = .를 확인하고, 시각이 9시간 어긋나면 UTC를 의심해요.

  • 가용성 계산은 제가 세운 가정(배포마다 실패 구간 29초, 그 시간 동안 모든 요청 실패, 하루 배포 횟수)에서 나온 산술이에요. 실제 서비스에 적용한 측정이 아니에요.
  • 활용 표의 «다음 한 걸음»은 제안이고, 아직 하나도 하지 않았어요.
  • 9번 글의 실험은 staging에서만 했고, production에서 승인과 전환까지 돌려 보지는 못했어요.
