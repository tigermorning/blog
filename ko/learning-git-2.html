GitHub 계정과 SSH 연결 (2)

2026. 7. 12.

1편에서 제 컴퓨터에 Git을 설치하고, 커밋할 때 쓸 이름과 이메일까지 등록했어요. (Git은 파일이 바뀐 이력을 시점별로 기록해주는 프로그램이고, 커밋은 "지금 이 상태를 사진처럼 찍어 기록에 남기는 것"이에요.) 그런데 그 기록이 전부 제 컴퓨터 안에만 있으면 반쪽이에요. 인터넷에 올려둘 곳이 있어야 백업도 되고, 나중에 그 파일을 홈페이지로도 띄울 수 있거든요. 그래서 이번 2편에서는 그 "올려둘 곳"인 GitHub 계정을 만들고, 내 컴퓨터와 GitHub을 안전하게 연결하는 방법(SSH)을 다룹니다.

← 이전 편 (1) 개념과 기본 세팅

1. GitHub 계정 만들고, SSH가 왜 필요한지 알기

GitHub은 내 저장소(repository)를 인터넷에 올려두고 관리할 수 있는 사이트예요. 저장소는 "파일들이 모여 있는 폴더 + 그 파일들이 그동안 어떻게 바뀌어왔는지의 기록"을 한 덩어리로 묶은 것인데, 그걸 내 컴퓨터에만 두지 않고 인터넷에도 하나 더 올려두는 거예요. 그러니 제일 먼저 할 일은 그 자리를 마련해줄 계정 만들기예요.

  1. github.com 접속
  2. 우측 상단 Sign up 클릭
  3. 이메일, 비밀번호, 사용자 이름(아이디) 입력
  4. 이메일로 온 인증 코드 입력해서 가입 완료

여기서 정한 사용자 이름(아이디)은 나중에 홈페이지 주소에도 그대로 쓰이니, 신중하게 정하는 게 좋아요. (저는 tigermorning으로 정했어요.) 그런데 계정을 만들었다고 해서 제 컴퓨터가 곧바로 그 계정에 파일을 올릴 수 있는 건 아니에요. GitHub 입장에서는 "지금 파일을 올리겠다는 이 컴퓨터가 진짜 그 계정 주인이 맞나?"를 매번 확인해야 하거든요. 그때마다 아이디와 비밀번호를 치는 건 번거롭고 위험해서, 대신 쓰는 방식이 SSH예요.

SSH는 Secure Shell의 줄임말이에요. 여기서 셸(shell)은 원래 "껍데기"라는 뜻인데, 컴퓨터의 알맹이(핵심 부분)를 감싸고 있으면서 사람의 명령을 받아 안쪽으로 전달해주는 바깥층이라 붙은 이름이에요. 1편에서 쓴 PowerShell도 이름 끝에 이 단어가 붙어 있죠. 그러니까 SSH는 "명령을 주고받는 그 통로를 안전하게(Secure) 감싼 것"이라는 뜻이에요. 실제 인증은 비밀번호가 아니라 미리 만들어둔 열쇠 한 쌍이 대신해줍니다.

  • 개인키(private key): 내 컴퓨터에만 보관, 절대 공유 X (도장 그 자체)
  • 공개키(public key): GitHub 계정에 등록해두는 것 (도장의 인주 샘플)

어떻게 "나"라는 걸 증명하나요?

비밀번호처럼 값 자체를 주고받는 게 아니에요. 접속할 때마다:

  1. GitHub이 랜덤한 문제(데이터)를 하나 던짐 — "이거에 서명해봐"
  2. 내 컴퓨터가 개인키로 그 자리에서 즉석 서명을 만들어서 보냄
  3. GitHub이 등록된 공개키로 그 서명이 맞는지 검증

서명은 매번 새로 만들어지는 일회용이라 도청당해도 재사용이 안 되고, 개인키 자체는 절대 컴퓨터 밖으로 안 나가요.

비유하자면: 서버가 무작위 문서 한 장을 주면서 "여기 서명해봐"라고 함 → 나는 나만 가진 도장(개인키)으로 찍음 → 서버는 등록된 인주 샘플(공개키)과 대조해서 확인. 도장 자체는 보여주지 않고, 찍힌 자국만 보여주는 셈이에요.

2. SSH 키 만들고 GitHub에 등록하기

원리를 알았으니 이제 그 열쇠 한 쌍을 실제로 만들 차례예요. 개인키와 공개키는 따로따로 만드는 게 아니라, 명령어 한 번으로 짝을 이뤄 동시에 생겨나요. 이미 만들어둔 키가 있으면 그걸 그대로 쓰면 되고, 없으면 새로 만들면 됩니다.

🎨 바이브 코딩으로: Claude에게 "내 컴퓨터에 SSH 키가 있는지 확인하고, 없으면 새로 만들어줘"라고 말하면 알아서 확인·생성해줘요.

🔍 궁금하다면: 실제로 어떤 명령어일까?

ssh-keygen -t ed25519 -C "내 이메일"

몇 가지 질문이 나오는데(저장 위치, 비밀번호 설정 등) 그냥 Enter만 계속 눌러도 기본값으로 만들어져요.

이제 열쇠 한 쌍이 제 컴퓨터에 생겼어요. 그런데 GitHub은 아직 이 열쇠를 몰라요. 앞에서 본 것처럼 GitHub이 제 서명을 검증하려면 공개키를 미리 가지고 있어야 하니까, 두 개 중 공개키만 골라서 계정에 등록해줘야 합니다. (개인키는 절대 올리면 안 돼요. 둘 중 파일 이름 끝에 .pub가 붙은 쪽이 공개키예요.)

  1. 만들어진 공개키(파일 이름 끝에 .pub가 붙은 것) 내용을 복사
  2. GitHub 우측 상단 프로필 → Settings
  3. 왼쪽 메뉴에서 SSH and GPG keys
  4. New SSH key 클릭
  5. Title에는 아무 이름(예: "내 컴퓨터"), Key 칸에는 복사한 공개키 통째로 붙여넣기
  6. Add SSH key 클릭

3. 연결이 잘 됐는지 테스트하기

등록까지 마쳤으면 이론상 연결은 끝났어요. 그래도 여기서 한 번 확인하고 넘어가는 게 좋아요. 지금 확인해두면 문제가 있어도 원인이 "SSH 설정" 하나로 좁혀지는데, 그냥 넘어갔다가 나중에 파일을 올리는 단계에서 오류가 나면 무엇 때문인지 찾기가 훨씬 어려워지거든요.

🎨 바이브 코딩으로: Claude에게 "GitHub SSH 연결이 되는지 확인해줘"라고 말하면 테스트하고 결과를 알려줘요.

🔍 궁금하다면: 실제로 어떤 명령어일까?

ssh -T git@github.com

이런 메시지가 나오면 성공이에요.

Hi (내 아이디)! You've successfully authenticated, but GitHub does not provide shell access.

뒷부분의 "shell access"가 안 된다는 문구는 에러가 아니라 정상 응답이에요 — GitHub는 인증만 확인해주고, 실제 터미널 접속은 원래 안 시켜준다는 뜻이에요.

SSH가 어떻게 "나"라는 걸 증명하는지 원리가 더 궁금하다면, 아래 글에서 공개키·개인키·서명 개념을 더 깊게 다뤘어요.

참고 글 SSH는 어떻게 "나"를 증명할까?

이제 제 컴퓨터와 GitHub은 서로를 알아보는 사이가 됐어요. 그런데 열쇠는 준비됐는데 정작 열고 들어갈 방, 그러니까 파일을 담아둘 저장소는 아직 하나도 만들지 않았죠. 그래서 다음 3편에서는 실제로 저장소를 만들고, 그걸 내 컴퓨터로 가져와서(clone) 파일을 고치고 다시 올려보내는(commit, push) 한 바퀴를 돌아봅니다.
