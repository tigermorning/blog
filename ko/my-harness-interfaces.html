어디에 쓰나
작업 ID로 실행 하나하나 구별하기 · 도구의 성공·오류·제한을 계약으로 쓰기 · 모델 제공자마다 다른 응답을 어댑터로 흡수하기 · 승인 버튼을 두 번 눌러도 한 번만 실행되게 만들기.

3편에서 작업이 시작되고, 도구를 실행하고, 승인을 기다리거나 끝나는 흐름을 정했어요. 이번 편은 그 흐름의 각 부분이 어떤 정보를 주고받을지를 정합니다.

화면에는 "승인" 버튼이 하나뿐이에요. 그런데 프로그램에는 그것보다 훨씬 많은 게 필요해요. 어느 작업의 어떤 변경을 승인했는지 알아야 하고, 같은 승인이 두 번 들어왔을 때 어떻게 할지도 정해야 해요.

코드로 먼저 보기 — 함수 하나의 계약

비유로 들어가기 전에, 우리가 나중에 실제로 짤 코드가 어떤 모양일지 먼저 볼게요. 함수는 재료를 넣으면 요리가 나오는 조리기구라고 생각하면 편해요.

def add(a, b):
    return a + b

결과 = add(3, 5)   # 결과 = 8

a, b가 입력(재료)이고 return으로 돌려주는 값이 출력(요리)이에요. "숫자 두 개 넣으면 숫자 하나 나온다"는 게 이 함수의 계약이에요.

그럼 실패했을 땐 어떻게 알릴까요. 크게 두 가지 방식이 있어요.

# 방식 1: 예외(exception) — 경보음 울리고 그 자리에서 멈춤
def divide(a, b):
    if b == 0:
        raise ValueError("0으로 나눌 수 없음")   # 여기서 실행이 멈춰요
    return a / b

# 방식 2: 실패라고 적힌 값을 그냥 돌려줌 — 멈추지 않음
def divide(a, b):
    if b == 0:
        return {"error": "0으로 나눌 수 없음"}   # 프로그램은 계속 실행돼요
    return {"value": a / b}

하네스는 방식 2를 쓰기로 했어요. 도구 하나가 실패했다고 모델과의 대화 전체가 멈춰 버리면 안 되고, 모델이 그 실패 이유를 보고 스스로 다음 행동을 고를 수 있어야 하니까요.

비유 — 극장 예매번호

영화를 예매한다고 해 볼게요. 좌석을 고르고 결제 화면으로 넘어가면 예매번호가 하나 생겨요. 이 번호가 있어야 "내 예매가 어떻게 됐지?"를 물어볼 수 있어요. 번호 없이 "제 예매요"라고 하면 창구 직원은 아무것도 못 해요.

여기서 예매번호와 회원 계정은 다른 거예요. 같은 계정으로 이번 주에 세 번 예매했다면 예매번호는 세 개죠. 회원 계정은 "누구의 이력인가"를, 예매번호는 "그중 어느 건인가"를 가리켜요.

결제 버튼을 누를 때도 그냥 "네"가 아니에요. 화면에 영화·상영관·좌석·금액이 떠 있고, 제가 확인한 건 그 조합이에요. 그런데 결제 버튼이 늦게 반응해서 두 번 눌렀다고 표가 두 장 나오면 안 되죠. 그리고 제가 확인하는 사이에 그 좌석을 다른 사람이 가져갔다면, 조용히 옆자리로 바꿔 결제하면 안 되고 다시 확인을 받아야 해요.

마지막으로 조회할 때요. "좌석 목록이 비어 있음"과 "그런 예매번호가 없음"은 완전히 다른 대답이에요. 둘을 똑같이 빈 화면으로 보여 주면 저는 무슨 일이 일어난 건지 알 수 없어요.

비유 속 요소원래 개념
예매번호작업 ID — 실행 하나를 구별하는 이름표
회원 계정세션 ID — 이어지는 대화 맥락의 이름표
결제 화면의 영화·좌석·금액승인 요청에 담긴 대상과 제안된 변경
버튼 두 번 눌러도 표는 한 장멱등성1
확인하는 사이 좌석이 바뀜승인 대기 중 파일이 사람 손에 바뀐 상황
"좌석 목록 비어 있음" vs "그런 예매번호 없음"빈 결과와 오류를 구별하는 계약

핵심 한 줄: 화면의 버튼은 하나여도, 그 뒤에는 "어느 건의 무엇을 확정하는가"가 반드시 붙어 있어야 해요.

다만 비유가 끊기는 점이 있어요. 극장 예매는 결제가 한 번에 끝나지만, 하네스의 작업은 승인 뒤에도 여러 단계가 남아요. 그래서 "승인 ID를 붙였으니 중복 문제 해결"이 아니라, 처리 완료 여부를 언제 저장하는지와 실행 중 프로그램이 죽으면 어떻게 되는지까지 봐야 해요.

전체 그림 — 이름이 비슷한 세 개의 연결

하네스 안에는 이름이 비슷해 보이지만 책임이 다른 연결이 세 개 있어요. 읽는 법: 가운데 하네스를 기준으로 왼쪽은 사람이 쓰는 쪽, 오른쪽 위는 모델, 오른쪽 아래는 실제 작업이에요. 각 화살표마다 다른 계약이 붙습니다.

연결호출하는 쪽 → 받는 쪽계약의 예
① 앱의 작업 인터페이스터미널·웹 화면 → 작업 처리부요청을 시작하고 작업 ID 받기, 상태 조회, 변경 승인
② 모델 제공자 연결부하네스 → 모델 제공자대화와 도구 설명 전달, 응답과 도구 요청 해석
③ 도구 인터페이스하네스 → 파일 읽기·쓰기·검사경로와 내용을 받아 작업하고 결과 또는 오류 반환

여기서 어댑터2(adapter)가 나와요. 서로 다른 형태를 맞춰 주는 연결부예요. 제공자마다 요청과 응답의 세부 형태가 다르니까, 제공자별 연결부에서 그 차이를 처리하고 하네스에는 정해 둔 한 가지 형태로 돌려주도록 설계합니다. 이렇게 나눠 두면 나중에 모델 연결을 바꿀 때 파일 권한 코드까지 고치는 일이 생기지 않아요. 그런 일이 생긴다면 경계가 섞였다는 신호예요.

개념 설명용 코드 — 세 연결을 안 나누면 생기는 일

# 나쁜 예 — 도구 코드가 모델 제공자를 알아버림
def read_file(path):
    ...
    결과["tool_call_id"] = openai_response.tool_calls[0].id   # 이 줄 때문에
    return 결과                                                 # Ollama로 바꿀 때 여기도 고쳐야 해요

# 좋은 예 — 도구는 어떤 제공자인지 몰라도 됨
def read_file(path):
    ...
    return 결과   # tool_call_id는 여기서 전혀 몰라요

# 연결은 별도 위치(②번, 제공자 연결부)에서 붙여요
tool_result_message = {"tool_call_id": 요청받은_id, "content": read_file(path)}

그리고 API3가 꼭 인터넷 주소를 뜻하지는 않아요. CLI 안에서 작업을 시작하는 함수를 부르는 것도 입력과 반환값에 대한 계약이 필요합니다.

시작 · 조회 · 승인 · 결과 — 네 가지 약속

"회의 자료에서 결정 사항을 찾아 정리해 줘"라는 요청을 생각해 볼게요. 모델 응답을 기다리는 동안에도 사용자는 작업이 시작은 됐는지 알아야 해요. 시작과 완료 결과를 구별해 두면 CLI든 웹이든 같은 흐름을 표현할 수 있어요.

동작입력에서 정할 것출력에서 정할 것
작업 시작사용자 요청, 허용된 작업 폴더, 이어 갈 세션 여부작업 ID와 시작 상태
작업 조회작업 ID현재 상태, 진행 정보, 승인 대기 여부
승인 응답작업 ID, 승인 요청 ID, 허용 또는 거절반영 여부와 현재 상태
결과 확인작업 ID완료 결과 또는 종료 이유, 관련 실행 기록

함수 이름이나 필드 이름을 그대로 쓸 필요는 없어요. 중요한 건 각 칸이 비어 있지 않은 것이에요.

그리고 앞의 예매 비유에서 본 구분이 여기서 그대로 살아나요. 결과가 아직 없다와 결과가 빈 문자열이다는 다른 상태예요. 진행 중이면 진행 중이라고 알려 주고, 없는 작업 ID라면 찾을 수 없다는 오류를 돌려줘야 해요.

왜 지금 정하나 — 짜 보고 나중에 고치면 안 되나

당연히 들 수 있는 의문이에요. "일단 짜 보고, 문제 생기면 그때 고치면 안 돼?" 안 되는 이유는 한 곳만 고치면 끝나는 문제가 아니라서예요.

read_file 하나만 봐도 이걸 부르는 곳이 하네스 안에 최소 세 군데예요. ① 반복 루프에서 도구를 실행하는 곳, ② 세션 기록(JSONL)에 성공·실패를 남기는 곳, ③ 화면에 [3/20] read_file ... 한 줄을 출력하는 곳.

개념 설명용 코드 — 계약을 안 정하고 짰을 때 생기는 일

# 처음엔 이렇게 짰다고 해봐요
def read_file(path):
    if not 파일있음(path):
        return None   # "없다"를 None으로 표현

# 나중에 "빈 파일과 못 찾은 파일을 구별해야겠다"고 깨달으면
# 위 함수 하나만 고치는 게 아니라, None을 검사하던
# ①②③ 세 곳을 전부 찾아서 같이 고쳐야 해요.
# 하나라도 놓치면 그 부분만 조용히 잘못 판단해요.

미리 "실패하면 항상 {"error": "..."} 모양으로 돌려준다"고 문서에 못 박아 두면, ①②③을 짤 때부터 다 같은 모양을 기준으로 짜니까 나중에 어긋날 일이 없어요. 이번 편에서 계약부터 쓰는 이유가 이거예요 — 나중에 여러 곳을 두세 번 다시 고치는 일을 막기 위한 사전 작업인 거죠.

제공자 연결부 — 호출 ID와 파싱

②번 연결에서 정할 것은 이래요.

  • 일반 답변과 도구 요청을 어떻게 구별할지
  • 도구 요청과 실행 결과를 어떤 ID로 연결할지
  • 여러 도구 요청을 한꺼번에 받았을 때의 처리 순서
  • 지원하지 않는 응답이나 해석할 수 없는 입력을 받았을 때의 오류 처리

호출 ID는 도구 요청 한 건에 붙이는 이름표예요. 모델이 read_text로 notes.txt를 읽어 달라는 요청을 call_a라는 이름으로 보냈다면, 하네스는 실행 결과가 그 요청에 대한 것임을 연결해서 돌려줘요. 파일 두 개를 읽으라는 요청이 동시에 왔을 때 어느 내용이 어느 요청의 결과인지 섞이지 않게 하려는 거예요. (call_a는 설명용 이름이고, 실제 제공자가 요구하는 식별자와 반환 구조는 어댑터에서 맞춥니다.)

파싱4(parsing)은 응답을 프로그램이 다룰 구조로 해석하는 과정이에요. 여기서 꼭 갈라 둘 게 있어요. 응답을 해석할 수 있다는 것과, 그걸 실행해도 된다는 것은 다른 이야기예요. 해석한 뒤에도 도구 이름·인자의 종류·경로와 권한을 따로 검사해야 합니다.

그리고 OpenAI와 Ollama에 같은 필드를 보내면 같은 기능이 동작한다고 가정하지 않아요. 선택한 API의 공식 문서와 실제로 받은 응답으로 확인할 항목을 명세에 적어 둡니다. 도구 정의와 스키마를 설계하는 감각은 도구를 실제로 설계하기 — 정의서·스키마·MCP 실습 (2)에서 다뤘어요.

도구 계약 — 입력·성공·오류·제한

첫 읽기 도구부터 계약을 써 봅니다. 이름은 read_text로 정할 수 있지만, 이름보다 허용하는 동작이 중요해요.

구분파일 읽기 도구에서 정할 내용
입력작업 폴더를 기준으로 한 파일 경로, 허용할 파일 종류
성공 결과실제로 읽은 내용과, 그 내용을 식별할 경로
오류파일 없음 / 읽기 불가 / 허용 범위 밖 경로를 서로 구별
제한너무 큰 파일을 거절할지 일부만 읽을지, 일부라면 그 사실을 어떻게 표시할지

아래 예에서 쓰는 JSON은 "path" 같은 이름과 그 값을 짝지어 데이터를 표현하는 형식이에요. 그리고 스키마5(schema)는 그 데이터에 어떤 항목이 필요하고 값의 종류가 무엇인지 정한 규칙이고요 — "경로는 문자열이어야 한다" 같은 거예요. 경로가 허용 폴더 안인지 판단하는 건 스키마가 아니라 별도의 실행 검사입니다.

개념 설명용 코드 — 설계 문서에 적어 볼 가상의 입출력 예이고, 어떤 도구의 실제 반환값이 아니에요

정상 읽기
  입력  {"path": "notes.txt"}
  출력  {"ok": true, "path": "notes.txt", "text": "회의 자료"}

파일 없음
  입력  {"path": "missing.txt"}
  출력  {"ok": false, "error": {"code": "FILE_NOT_FOUND", "message": "파일을 찾을 수 없습니다."}}

여기서 확인할 게 하나 있어요. 정상 파일이 비어 있으면 성공 결과의 text가 빈 문자열일 수 있어요. 그게 파일을 못 찾은 오류와 구별되는지를 예제로 확인합니다. 그리고 이 도구는 파일을 바꾸지 않으니 "부작용 없음"으로 적고, 재시도하면 변경된 최신 내용을 읽게 된다는 점도 함께 기록해요.

나쁜 선택 vs 좋은 선택

같은 극장에서, 예매 조회에 실패했을 때의 두 가지 응답이에요.

나쁜 선택좋은 선택
무엇을 했나: 파일이 없을 때 오류 대신 빈 내용을 돌려주도록 만들었어요. 코드가 짧아지고 예외 처리도 안 해도 돼서요.

무슨 일이 생기나: 모델은 "빈 파일을 읽었구나"라고 해석해요. 그래서 "안내문에 준비물이 적혀 있지 않습니다"라는 사실과 반대인 답을 자신 있게 씁니다. 게다가 도구는 성공했으니 실행 기록에도 실패가 안 남아요.		 무엇을 했나: FILE_NOT_FOUND처럼 프로그램이 구별할 수 있는 오류 종류와 사람이 읽을 설명을 함께 돌려줬어요.

무슨 일이 생기나: 모델은 다른 경로를 확인하거나 사용자에게 되물어요. 나중에 기록을 볼 때도 "읽기가 실패했다"가 남아 있어서, 모델의 해석 문제인지 파일 문제인지가 갈립니다.

같은 원칙으로, 모델 제공자 연결 실패·도구 입력 오류·사용자 승인 거절도 서로 다른 사건으로 남겨요. 셋을 "실패"라는 한 단어로 뭉뚱그리면 원인을 못 찾습니다.

그리고 하나 더. 모델에게 보여 주는 도구 설명과 실제 함수의 검사는 같은 계약을 따라야 해요. 설명에는 "작업 폴더 안만 읽는다"고 써 놓고 실제 함수는 아무 경로나 읽게 두면, 설명만으로는 범위가 제한되지 않아요. 언어의 타입 검사도 허용 경로 판단을 대신하지 못하고요.

승인과 도구 실행을 잇는 정보

파일 수정 요청에는 "승인됨"이라는 값 하나로는 부족해요. 사용자가 확인한 변경과 실제로 실행할 변경이 같아야 하니까요. 그래서 승인 요청을 만들 때 대상 파일과 제안된 변경에 연결된 식별 정보를 남기고, 변경 내용이 달라지면 새 승인을 받도록 설계할 수 있어요.

승인 버튼을 두 번 눌렀다고 같은 작업이 두 번 실행되면 안 되겠죠. 같은 요청을 반복해도 의도한 효과가 추가로 생기지 않게 만드는 성질을 멱등성이라고 불러요. 이름을 외우기보다 "이미 처리한 승인인지 확인하고 다시 실행하지 않는다"는 동작으로 이해하면 충분해요. 다만 승인 ID를 추가했다고 모든 중복 문제가 끝난 건 아니에요 — 처리 완료를 언제 저장하는지, 실행 도중 중단되면 어떻게 되는지까지 봐야 합니다.

승인 대기 중에 사람이 그 파일을 손으로 고쳤다면 어떻게 할까요. 처음에는 "파일이 달라졌으면 멈추고 새 변경안을 다시 확인받는다"로 범위를 잡을 수 있어요. 구현하지 않은 충돌 처리까지 갖춘 것처럼 명세에 쓰지 않고, 고른 처리와 검증할 상황만 적습니다.

화면 선택에 계약 연결하기

CLI를 골랐다면 터미널 입력을 읽는 코드가 작업 시작 함수를 부르고, 진행 정보를 글자로 출력해요. 승인 대기가 생기면 제안된 변경을 출력하고 입력을 기다립니다. 내부 함수를 쓴다는 이유로 입력 검사나 오류 계약이 없어지지는 않아요.

로컬 웹을 골랐다면 같은 동작을 HTTP6에 연결해요. 작업 시작 요청·상태 조회 요청·승인 응답 요청을 각각 웹 경로에 대응시키는 식이죠. 구체적 경로와 형식은 제 앱에서 정하고, CLI만 만들 거라면 이 부분은 건너뛰어도 됩니다.

웹에서 하나만 더 짚을게요. 버튼을 눌렀다는 사실과 서버가 요청을 받았다는 사실은 달라요. 통신이 끊겼을 때 화면이 무조건 작업 시작을 다시 보내면 같은 요청이 두 개 생겨요. 첫 설계부터 모든 통신 장애를 해결할 필요는 없지만, 재시도할 때 기존 작업을 조회할지 새 작업을 만들지는 정하고 그 한계를 기록해 둡니다.

모델이 더 좋아지면 — 이 계약도 필요 없어질까

수업 중에 이런 질문이 나왔어요. "강력한 범용 에이전트를 쓰면, 이런 인터페이스 설계는 점점 필요 없어지지 않을까요?" 곧이어 "토큰이 무제한이면 필요 없을지도"라는 의견이 붙었고, 다른 학생은 "모델이 아무리 뛰어나도 방향성을 안 주거나 길을 안 열어주면 아무것도 못 한다"고 답했어요.

이 대화가 이번 편 내용과 바로 이어져요. "토큰 무제한이면 필요 없다"는 쪽은 하네스가 존재하는 이유를 비용과 자원 제약으로 보는 거예요. 승인을 거치고, 도구가 다룰 범위를 좁히고, 실패를 구분해서 기록하는 일이 전부 "낭비를 막으려는" 장치라면, 그 낭비 자체가 사라질 때 장치도 함께 필요 없어지겠죠.

그런데 이번 편에서 정한 것들 — 작업 ID로 어느 실행인지 구별하기, 빈 결과와 오류를 구별하기, 승인 요청과 실제로 실행할 변경이 같은지 확인하기 — 은 모델 성능이나 토큰 비용과 무관해요. 모델이 지금보다 훨씬 똑똑해져도 "이 요청이 어느 파일의 어떤 변경을 승인한 것인지"는 여전히 누군가 미리 정해 둬야 하는 약속이에요. 모델은 그 약속 안에서 판단할 뿐, 약속 자체를 대신 정해 주지는 않아요.

그래서 뒤에 나온 학생 말이 더 정확한 방향이라고 생각해요. 하네스가 하는 일은 모델의 부족함을 메우는 게 아니라, 모델에게 무엇을 맡길지와 그 결과를 어떻게 확인할지에 대한 방향을 정하는 거예요. 그 방향은 모델이 아무리 좋아져도 사람이 대신 정해 줘야 하는 몫으로 남아요.

선택한 플랫폼에 맞춰 작업 시작·조회·승인과 첫 읽기 도구의 계약을 정리해 줘.
정상 요청과 잘못된 요청 예를 넣고, 아직 결정이 필요한 부분은 남겨 줘. 코드는 아직 만들지 마.
  1. 바꿀 것 — INTERFACES.md에 세 연결의 책임과 구체적 계약 한 개(정상 예 + 오류 예)를 적어요.
  2. 측정할 것 — AI가 만든 예제를 호출하는 쪽과 받는 쪽 두 입장에서 각각 읽어요. ①입력만 보고 실행 대상을 알 수 있는가 ②결과만 보고 성공·실패·대기를 구별할 수 있는가.
  3. 비교할 것 — "빈 결과"와 "오류"가 같은 모양으로 돌아오는 칸이 있는지 찾아요. 있으면 거기가 나중에 6편에서 헤맬 자리예요.

마지막으로 못 박을 것. 예제 응답은 설계를 설명하는 가상 데이터이지 실행 증거가 아니에요. 다음 편에서는 이 계약을 실제로 지켰다고 판단할 완료 조건을 씁니다.

함께 읽으면 좋은 글

  • 도구를 실제로 설계하기 — 정의서·스키마·MCP 실습 (2) — 도구 정의서와 스키마를 처음 써 본 글이에요.
  • 도구 하나가 호출되기까지 — 정의·파싱·구조화 요청 (1) — 도구 호출이 파싱되는 과정을 뜯어본 글이에요.
  • API란 무엇인가, AI와 차이 — API라는 말이 낯설면 여기부터요.
  1. 멱등성(冪等性, idempotency) — 같은 요청을 여러 번 보내도 의도한 효과가 추가로 생기지 않는 성질이에요. 한자어라 한국어가 맞긴 한데 수학·전산에서만 쓰는 낯선 말이라 처음 보면 외국어처럼 느껴져요. 단어 자체를 외우기보다 "이미 처리한 승인인지 확인하고 다시 실행하지 않는다"는 동작으로 기억하면 충분해요. ↩
  2. 어댑터(adapter) — 제공자마다 다른 요청·응답 형태를 하네스 내부의 공통 형태로 맞춰 주는 연결부예요. ↩
  3. API(Application Programming Interface) — 프로그램이 다른 기능을 호출할 때 쓰는 인터페이스이며 인터넷 주소만을 뜻하지는 않는데, API란 무엇인가에서 정리했어요. ↩
  4. 파싱(parsing) — 받은 응답이나 문자열을 프로그램이 다룰 수 있는 구조로 해석하는 과정이에요. ↩
  5. 스키마(schema) — 데이터에 어떤 항목이 필요하고 각 값의 종류가 무엇인지 정해 둔 규칙으로, 도구를 실제로 설계하기에서 다뤘어요. ↩
  6. HTTP — 브라우저와 서버가 요청과 응답을 주고받는 방식이에요. ↩
