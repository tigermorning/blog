플러그인과 명세 주도 개발

2026. 7. 27.

※ 이 글은 모두의연구소(모두연) 학습 자료를 제 나름의 말로 다시 정리한 글이에요.

플러그인은 스킬·MCP·명령을 한 꾸러미로 묶은 것이고, 명세 주도 개발은 코드보다 먼저 의도를 문서로 적고 시키는 방법이에요.

여기부터는 당장 필요하진 않은, '한 걸음 더' 나가는 이야기였어요. 스킬·MCP(먼저 읽으면 좋은 글)에 익숙해지면 만나게 되는 흐름이에요. 지금은 이런 게 있다는 감만 잡아도 충분했어요.

스킬·도구를 통째로 나누기 — Claude 플러그인

스킬 하나, MCP 연결 하나, 자주 쓰는 명령 하나. 이렇게 낱개로 쌓다 보면 남한테 "내 세팅 그대로 써봐"라고 넘기기가 번거로워요. 그래서 Claude Code(AI에게 코드 작업을 시키는 도구)에는 이걸 하나로 묶는 '플러그인(plugin)'이 있었어요. 한 꾸러미에 이런 것들을 담아요. 스킬, 서브에이전트(특정 일만 맡는 보조 AI), 자주 쓰는 슬래시 명령(/로 시작하는 단축 명령), 자동화 훅(특정 순간에 자동으로 실행되는 동작), MCP 연결이에요. 그러면 명령 한 줄로 통째로 설치돼요.

아래 두 줄은 플러그인 모음을 등록하고, 그중 하나를 설치하는 명령이에요. 읽기만 해도 되고, 직접 해 볼 수도 있어요. 처음 보면 낯설어서 막히는 게 정상이에요.

실행: Claude Code 안에서 실행 — 터미널이 아니라 Claude Code 채팅창에 입력

# 마켓플레이스(플러그인 모음)를 하나 등록하고
/plugin marketplace add anthropics/claude-plugins-community
# 거기서 원하는 플러그인을 설치
/plugin install <플러그인이름>@claude-community

Anthropic이 직접 고른 공식 모음과 사람들이 올린 커뮤니티 모음이 있어요. 깃허브(코드를 올려 두는 인터넷 창고) 주소나 내 폴더에서 바로 설치할 수도 있어요. 많이 켤수록 AI가 읽어야 할 맥락이 늘어 느려져요. 그래서 '지금 쓸 것만' 켜는 게 좋았어요.

플러그인이 진짜 빛나는 건 팀에서였어요. 보통 좋은 세팅은 잘하는 한 사람 머릿속에만 있어요. 플러그인으로 묶어 두면 "우리 팀 코드 리뷰는 이렇게", "배포(만든 것을 실제로 내보내는 일)는 이 순서로" 같은 노하우가 설치 한 번으로 모두의 것이 돼요. 버전이 붙어 있어서, 만든 사람이 고치면 다 같이 업데이트돼요. 문제가 생기면 이전 버전으로 되돌릴 수도 있었어요.

에이전트 팀을 통째로 얹기

여기서 더 나아가면, 여러 전문 에이전트와 스킬·명령을 한꺼번에 얹어 Claude Code를 '지휘자'로 만드는 오픈소스(만드는 방법이 공개돼 누구나 쓸 수 있는) 레이어도 있어요. 큰 일이 들어오면 지휘자가 조사·구현·검증 담당에게 나눠 맡겨요. 그리고 그 일들을 동시에(병렬로) 굴려요. 앞서 본 서브에이전트를 아예 '팀' 규모로 키운 셈이었어요.

이름어떤 레이어인가
oh-my-claudecodeClaude Code에 플러그인으로 얹는 '팀 우선' 오케스트레이션(여러 에이전트에게 일을 나눠 맡기는 지휘) 레이어예요. 마켓플레이스에 저장소를 등록하고 설치하면 수십 개의 전문 에이전트와 스킬이 한 번에 딸려와요
oh-my-openagent(omo)모델을 가리지 않아요. Claude든 GPT든 Gemini든 한 인터페이스(하나의 창구) 뒤에 묶어, "이 잔일엔 값싼 모델, 이 판단엔 제일 똑똑한 모델"처럼 골라 쓰게 해 줘요. opencode(AI 코딩 도구의 하나)에서 쓰는 쪽은 혼자 일하던 에이전트를 팀으로에서 자세히 다뤄요

첫날부터 손댈 도구는 아니었지만, 알아 둘 값어치는 있었어요. "AI 하나에게 다 시키기"에서 "여러 전문 AI를 지휘하기"로 넘어가는 흐름이 있어요. 그 끝에 이런 레이어가 있고, 이건 스킬·플러그인·서브에이전트를 차곡차곡 쌓아 올린 결과예요. 익숙해지면 자연스레 이쪽으로 올라오게 된다는 게 흥미로웠어요.

'먼저 적고 시키는' 명세 주도 개발

스킬과 AGENTS.md(AI가 지켜야 할 규칙을 적어 둔 파일)에는 공통점이 하나 있었어요. 시키기 전에 '무엇을, 어떻게'를 먼저 글로 적어 둔다는 것이에요. 이 발상을 프로젝트 전체로 키운 게 요즘 부쩍 뜨는 명세 주도 개발(spec-driven development)이에요. 한마디로 "코드가 정답이 아니라, 내 의도(명세)가 정답이다"로 무게중심을 옮기는 거였어요. 예전에 다룬 PRD(만들 것을 적은 요구사항 문서)가 바로 그 '명세'의 출발점이었고요.

나쁜 선택좋은 선택
아무 설명 없이 "만들어줘"만 던진다(이른바 바이브 코딩 — AI에게 말로 시켜 만드는 방식) → 빠르지만 AI가 슬금슬금 의도에서 벗어나거나 없는 기능을 지어내기 십상이에요. 코드를 짜기 전에 요구사항·설계·할 일 목록을 먼저 문서로 정하고, AI가 그 문서를 보며 단계대로 만들게 한다 → 의도 안에서 만들어지고, 결과도 고쳐 쓰기 좋아요.

도구도 이미 많았어요.

도구성격
Spec Kit깃허브가 내놓은 오픈소스예요. '원칙 → 명세 → 계획 → 할 일 → 구현'을 정해진 순서로 밟게 해주는데, 깃허브 별이 12만 개를 넘을 만큼 인기예요
Kiro아마존이 내놓은, 명세부터 쓰게 만드는 편집기예요
OpenSpec더 가볍게 시작하고 싶을 때 많이 쓰인대요. 이미 굴러가는 프로젝트를 조금씩 고쳐 나갈 때 편하다는 평이었어요

방식은 조금씩 달라도 뿌리는 같았어요. 짧게라도 먼저 적고 시키면 AI가 덜 헤매고, 결과도 고쳐 쓰기 좋다는 것이에요. 다만 직접 써 본 사람들 얘기를 들어 보면 이게 만능은 아니었어요. 그래서 요즘 굳어지는 결론은 '섞어 쓰기'였어요. 가볍게 탐색하거나 시제품을 만들 땐 그냥 대화로(바이브 코딩), 오래 유지할 중요한 걸 제대로 지을 땐 명세로요. 명세 주도 개발의 진짜 값어치는 도구 자체가 아니라 '만들기 전에 한 번 더 생각하게 만든다'는 데 있었어요. 다음 글에서는 이 경험을 계속 쌓아 다음 작업이 더 수월해지게 만드는 컴파운드 엔지니어링(일할수록 도구와 규칙이 쌓여 다음 일이 쉬워지게 하는 방식)과, 프롬프트(AI에게 적어 주는 부탁 글) 대신 루프(같은 일을 되풀이하는 흐름)를 설계하는 흐름을 볼게요.

이럴 때 의심하세요 — 세팅이 늘고 앱이 커지면서 결과가 흔들릴 때

플러그인과 명세의 문제는 처음 며칠은 안 보여요. 사람이 늘거나, 켜 둔 게 늘거나, 고친 횟수가 늘 때 조금씩 드러나죠. 그래서 "원래 되던 게 사람마다, 날마다 다르다"는 느낌이 드는 순간이 의심할 때예요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
같은 저장소에서 일하는데 동료가 "그 슬래시 명령이 제 화면엔 없어요"라고 하거나, 같은 리뷰 부탁에 사람마다 AI가 다른 기준으로 답해요 각자 컴퓨터에 설치된 플러그인 목록과 버전이에요. Claude Code라면 채팅창에 /plugin을 넣어 플러그인 관리 화면에서 볼 수 있어요. 한 사람만 낱개로 깔아 둔 스킬·명령이 차이를 만드는 경우가 많아요 결과가 좋은 사람의 목록과 내 목록을 나란히 놓고, 빠진 것과 버전이 다른 것을 찾아요. 낱개로 깔린 게 원인이라면 그걸 플러그인 하나로 묶어 모두가 같은 걸 설치하게 해요
"만들어줘"로 여러 번 고쳐 온 앱에 부탁한 적 없는 기능(로그인 버튼, 설정 화면 같은)이 생겼거나, 처음에 정한 기능이 슬쩍 빠져 있어요 코드보다 먼저 처음에 정한 걸 적어 둔 문서(PRD나 명세 파일)예요. 그런 문서가 없다면, 비교할 기준이 없다는 게 문제의 시작이에요 문서의 항목마다 실제로 되는지 하나씩 눌러 보고, 문서에 없는데 생긴 것도 따로 적어요. 문서가 없으면 지금이라도 짧게 적고, 다음 부탁부터 "이 문서 기준으로"를 붙여요. 출발점은 바이브 코딩 글의 PRD예요
플러그인을 여러 개 설치한 뒤로 새 대화의 첫 답부터 느리고, 사용 한도도 전보다 빨리 차요 대화 내용이 아니라 켜 둔 플러그인에 딸려 온 것들이에요. 플러그인 하나에 MCP 연결과 에이전트·스킬이 여러 개씩 들어 있을 수 있어요. Claude Code라면 새 대화에서 /context로 무엇이 창을 차지하는지 봐요 지금 작업에 안 쓰는 플러그인을 끄고 같은 화면을 다시 봐요. 줄어든 만큼이 그 플러그인들의 몫이에요(MCP로 같은 확인을 하는 줄). 여러 에이전트를 한꺼번에 굴리는 팀형 레이어라면 토큰이 몇 배로 느는 쪽도 같이 봐요

둘째 줄은 문서가 있어야만 잡혀요. 기억에 기대서 "이런 기능 정했었나?"를 따지면 AI의 결과물이 곧 기준이 돼 버리거든요. 문서가 있다면 비교를 에이전트에게 맡겨도 되는데, 이때도 고치기 전에 표로 먼저 보여 달라고 해요. 다만 표에 파일과 줄 번호가 적혔다는 건 코드가 있다는 뜻일 뿐 돌아간다는 뜻은 아니에요. 그래서 중요한 항목은 직접 눌러 봐요.

아래 글은 AI에게 그대로 붙여 넣어 시키는 부탁이에요. 대괄호 자리에는 내 문서 이름을 넣어요. 읽기만 해도 괜찮고, 내 프로젝트에서 직접 해 봐도 돼요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 명세 문서와 코드가 함께 있는 프로젝트 폴더에서

이 프로젝트의 명세 문서([파일 이름], 예: PRD.md)를 읽고 아래를 표로 보여 줘. 아직 코드는 고치지 마.
1. 명세의 항목마다: 그 기능을 만드는 코드가 있는 파일 이름과 줄 번호. 못 찾으면 "없음"
2. 명세에는 없는데 코드에 들어 있는 기능: 파일 이름과 줄 번호, 언제부터 들어왔는지 짐작 가는 커밋이 있으면 그것도
3. 확실하지 않은 칸은 추측으로 채우지 말고 "확인 못 함"이라고 적어 줘
