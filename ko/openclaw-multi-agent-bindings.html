OpenClaw의 멀티에이전트는 챗봇을 여러 개 만드는 일이 아니라, 게이트웨이 하나 안에서 들어온 대화를 담당 역할에게 나르는 작은 라우터를 설계하는 일이다.

지금까지는 에이전트 하나를 다뤘어요. 실무에서는 역할이 갈려요. 문의를 받는 역할, 코드를 고치는 역할, 자료를 조사하는 역할이 다른 시간에 다른 일을 해요. OpenClaw는 이 차이를 게이트웨이1 프로세스 하나 안에 서로 격리된 에이전트 여럿을 두는 것으로 풀어요. 이 편은 설치 없이 공식 문서의 설정 예시를 읽으며 구조를 이해하는 편이에요. 멀티 에이전트가 애초에 득인지 실인지, 어떤 구조가 있는지는 나누면 좋아질까와 네 가지 구조와 맞는 과업에서 다뤘어요. 이 편은 그중 OpenClaw가 택한 한 가지 구조를 실제 설정으로 보는 거예요.

비유 — 회사 대표번호와 내선

회사 대표번호로 전화가 오면 교환원이 받아요. "청구서 문의"면 회계팀 내선으로, "제품 고장"이면 기술지원 내선으로 돌리고, 어디로 보낼지 모르겠으면 총무팀으로 보내요. 각 팀은 자기 서류함과 자기 통화 기록을 따로 갖고, 다른 팀 서류함은 열지 않아요. 교환원이 하는 일은 딱 "어느 내선으로 돌리나"까지예요. 누가 회사에 전화를 걸 수 있는지는 교환원이 아니라 건물 경비가 정하죠.

비유 속 요소원래 개념
대표번호 교환원게이트웨이
"청구서 문의는 회계팀으로"라는 규칙binding — 채널 계정을 특정 에이전트에 잇는 규칙
모르겠으면 총무팀으로default: true인 기본 에이전트
팀마다 따로 있는 서류함에이전트별 workspace(작업 폴더)
팀마다 따로 있는 통화 기록에이전트별 SQLite 세션 기록
누가 전화 걸 수 있는지 정하는 건물 경비채널 설정의 페어링·허용 목록 (4편)

핵심 한 줄: 교환원(binding)은 갈 길만 정하고, 문지방의 기준(누가 걸 수 있나)은 경비(채널 설정)가 따로 가져요.

전체 흐름

읽는 법: 왼쪽에서 메시지가 들어오면 가운데 게이트웨이 안의 binding이 어느 에이전트로 보낼지 골라요. 맞는 binding이 없으면 기본 에이전트로 가요. 오른쪽 두 에이전트는 각자 자기 폴더와 자기 기록만 써요. 강의가 눈여겨보라고 한 그림이 바로 이거예요.

binding — 채널 계정을 역할에 잇는다

binding(바인딩)은 채널 계정을 특정 에이전트에 연결하는 규칙이에요. 채널 계정이란 슬랙 작업공간 하나, 왓츠앱 번호 하나처럼 채널이 구분하는 단위예요. 공식 문서의 가장 짧은 예시는 에이전트 둘과 binding 하나예요.

{
  agents: {
    entries: {
      main: {
        default: true,
        workspace: "~/.openclaw/workspace",
      },
      support: {
        workspace: "~/.openclaw/workspace-support",
      },
    },
  },
  bindings: [
    {
      channel: "discord",
      account: "support",
      agent: "support",
    },
  ],
}

읽어 볼게요. agents.entries에 에이전트 둘(main, support)이 각자 다른 workspace를 갖고 있어요. bindings에 "디스코드의 support 계정에서 온 메시지는 support 에이전트로"라는 규칙 하나가 있고요. 이 설정 형식은 3편에서 본 openclaw.json에 들어가는 JSON2이에요.

main에 붙은 default: true가 중요해요. 어떤 binding에도 해당하지 않는 대화가 도착하면 기본 에이전트가 받아요. 기본 에이전트를 정하지 않으면 갈 곳이 없어진 메시지가 조용히 사라지는 사고가 날 수 있어요. 오류도 안 뜨고 그냥 없어져요. 여러 역할을 두기로 했다면 누가 남은 대화를 받을지 반드시 정해 둬요.

binding이 하는 일은 딱 "받을 에이전트를 고르는 것"까지예요. 5편에서 본 페어링 승인이나 허용 목록처럼 누가 말을 걸 수 있는지를 정하는 규칙은 채널 설정이 따로 가져요. 라우터가 갈 길을 정할 뿐, 문지방의 기준을 대신 정하지 않아요.

에이전트마다 분리되는 것

에이전트 하나가 감싸는 범위를 "페르소나 하나의 전체"라고 불러요. 역할의 성격, 쓰는 규칙, 작업 폴더, 대화 기록이 한 단위로 묶여요. 공식 문서는 에이전트마다 분리되는 것으로 셋을 적어요.

분리되는 것무엇인가어디에
workspace (작업 폴더)에이전트가 기본으로 일하는 폴더. main과 support가 다른 폴더를 쓰니 만지는 파일이 처음부터 갈림설정의 workspace 값
상태 폴더인증 프로필과 에이전트별 설정~/.openclaw/agents/<agentId>/
대화 기록에이전트마다 따로인 SQLite 파일~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite

기억과 기록은 기본으로 섞이지 않아요. 한 에이전트의 기본 메모리는 다른 에이전트의 기록을 검색하지 않아요. 함께 써야 하는 자료는 두 에이전트가 모두 읽는 공유 문서를 명시적으로 둬요. 서로 다른 두 파이썬 프로젝트가 폴더를 나눠 쓰는 것과 같은 이치예요. 연구 담당과 코딩 담당이 한 테이블에서 일하면 서류가 섞이니, 폴더를 나누고 필요한 문서만 복사해 두는 규칙이 있어야 서로의 기록을 실수로 건드리지 않아요.

문서가 분명히 적은 경계도 있어요. 상태 폴더를 에이전트끼리 재사용하면 인증과 세션 상태가 충돌해요. 그리고 작업 폴더는 기본 작업 경로일 뿐 단단한 격리 장치가 아니에요. 폴더 밖의 경로를 막아야 한다면 sandbox3를 따로 둬야 해요. "폴더를 나눴으니 안전하다"는 착각을 여기서 한 번 걷어 내요.

delegate — 자기 계정으로 대신 행동한다

역할이 늘어나면 사람을 대신해 일하는 에이전트가 필요해져요. delegate(델리게이트)는 조직 안에서 자기 이메일 주소와 표시 이름을 가지고 일하는 에이전트예요. 공식 문서가 정체성을 한 문장으로 못 박아요. 사람으로 가장하지 않고, 자기 자격 증명으로, 정해진 권한 안에서 대신 행동한다. 내 계정을 빌려주는 자동화가 아니라, 권한 범위를 정해 둔 보조 구성원을 추가하는 설계예요.

권한은 작은 것에서 시작해요. 문서가 권하는 첫 등급은 읽고, 초안만 만들고, 사람의 검토를 받는 단계예요. 아무것도 승인 없이는 밖으로 나가지 않아요. 발송과 일정 생성처럼 밖으로 나가는 행동은 다음 등급에서 delegate 자신의 이름으로 이뤄져요. 넓힐 때는 도구 제한, sandbox, 감사 기록4을 먼저 갖추는 순서를 지켜요. delegate 문서가 다루는 권한은 조직의 이메일과 캘린더인데, 넓은 위임 열쇠 하나가 새면 모든 사서함과 캘린더가 열리는 구조라 문서 스스로 최소 권한을 권해요. 수업에서는 실제 메일 권한을 연결하지 않고, 역할과 승인 규칙을 설계하는 것까지만 다뤘어요.

standing orders와 병렬 전문가 레인

역할이 여럿이면 맡긴 일을 언제 어떻게 하는지 규칙이 필요해요. standing orders(스탠딩 오더)는 항상 적용되는 지시예요. 무엇을 해도 되는지, 무엇은 승인을 받아야 하는지, 무엇이 보이면 멈추는지를 에이전트에게 미리 적어 두는 규칙이에요. 허용·승인·중단 세 칸을 채우는 셈이고, 5편 끝의 "직접 해보기"에서 쓴 권한 기준 메모와 같은 문양이에요. 규칙을 파일로 미리 적어 두는 발상은 스킬과 규칙 파일에서 봤어요.

병렬 작업은 에이전트를 많이 만드는 일이 아니라 역할 설계가 먼저예요. 공식 문서의 병렬 전문가 레인은 연구, 제작, 검토처럼 역할이 겹치지 않게 나누고, 동시에 돌릴 개수를 정해 두는 구성을 권해요. 예시 설정의 해당 부분이에요.

{
  agents: {
    defaults: {
      maxConcurrent: 4,
      subagents: { maxConcurrent: 8, delegationMode: "prefer" },
    },
  },
  messages: {
    queue: { mode: "collect", cap: 20, drop: "summarize" },
  },
}

동시 실행 수에 한도를 두고(maxConcurrent), 몰리는 메시지는 모아 두었다가(collect) 한도를 넘으면 요약해서 넘기는(summarize) 규칙까지가 설계 대상이에요. 에이전트를 늘리는 일보다 역할 겹침과 용량을 먼저 정하는 편이 사고를 줄여요.

에이전트끼리 직접 대화하는 길은 기본으로 닫혀 있어요. 켜려면 명시적 활성화와 허용 목록이 필요해요.

{
  tools: {
    agentToAgent: {
      enabled: false,
      allow: ["home", "work"],
    },
  },
}

명령줄에서 특정 에이전트에게 한 번 실행을 시키는 openclaw agent도 별개의 도구예요. --agent, --session-id처럼 대상을 지정해 한 번의 실행을 요청할 뿐, 에이전트 사이의 대화를 여는 장치가 아니에요. 역할 간 전달은 서로의 대화를 모두 보는 것이 아니라, 누구에게 무엇을 넘길지 명시하는 작업이에요. 이건 네 가지 구조에서 본 "문맥을 공유할지 말지"의 선택을 OpenClaw가 기본 닫힘으로 정해 둔 셈이에요.

나쁜 선택 vs 좋은 선택 — 교환원 규칙을 짤 때

나쁜 선택좋은 선택
support와 research 두 에이전트를 만들고 binding도 둘 다 적었지만 default: true를 아무에게도 안 붙인다 → 새로 붙인 텔레그램에서 온 메시지가 어느 binding에도 안 맞아 오류 없이 조용히 사라진다. 에이전트를 둘 이상 두는 순간 하나에 default: true를 붙이고, "남은 대화는 여기로 간다"를 설정에 적어 둔다 → 예상 못 한 입구의 메시지도 어딘가에는 도착한다.
설정을 줄이려고 두 에이전트가 같은 상태 폴더를 쓰게 한다 → 인증 프로필과 세션 상태가 충돌해 한쪽 로그인이 다른 쪽을 덮어쓴다. workspace·상태 폴더·기록을 에이전트마다 따로 두고, 같이 봐야 할 자료만 공유 문서 하나로 명시한다 → 서로의 기록을 실수로 건드리지 않는다.

직접 해보기

설치하지 않고 종이에 해 보는 연습이에요. 내가 맡기고 싶은 역할을 두 개 고르고(예: "기사 요약", "코드 검토"), 각각에 대해 네 줄을 적어요. ① 어느 채널 계정에서 오는 대화가 이 역할로 가나(binding), ② 이 역할의 작업 폴더는 어디인가(workspace), ③ 둘 중 누가 default인가, ④ 허용·승인·중단 세 칸(standing orders). 네 줄이 다 채워지면 위 JSON 예시에 그대로 옮길 수 있어요. 역할이 늘면 다음 질문이 자연히 따라와요. "역할마다 토큰을 얼마나 쓰나?" 그 답은 3편의 사용량 화면에 있어요.

  1. 게이트웨이 — 여러 입구에서 오는 연결을 한 곳에서 받아 어디로 보낼지 조정하는 프로그램으로, 1편에서 처음 다뤘어요. ↩
  2. JSON — 설정이나 데이터를 "이름: 값" 꼴로 중괄호 안에 적는 형식으로, 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  3. sandbox — 프로그램이 정해진 울타리 밖의 파일이나 네트워크에 닿지 못하게 격리하는 실행 환경. ↩
  4. 감사 기록 — 누가 언제 무엇을 승인하고 실행했는지 나중에 확인할 수 있게 남기는 이력. ↩
  5. 서브에이전트 — 주 에이전트가 일부 작업을 떼어 맡기는 보조 에이전트로, 네 가지 구조와 맞는 과업에서 다뤘어요. ↩

"OpenClaw로 내 에이전트 운영하기" 시리즈

(1) 새 껍데기, 같은 바닷가재 — OpenClaw는 무엇이고 어디서 왔나 (2) 연습 폴더에 들이기 — 설치·온보딩·첫 대화 (3) 답변이 아니라 흔적을 본다 — 세션 기록과 사용량 (4) 폰에서 부리기 — 텔레그램 채널과 페어링 (5) 어디까지 해도 되는가 — 권한 모드·입구·인젝션·공개 권고

(6) 한 게이트웨이에 여러 역할 — 바인딩·델리게이트·스탠딩 오더 (이 글)

(7) 사람이 기억하지 않도록 — 자동화 예약과 cron (8) 뼈대와 손 — pi 코어와 확장 기능 투어 다음 편 → 사람이 기억하지 않도록 — 자동화 예약과 cron
