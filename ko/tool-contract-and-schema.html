← 이전 편 에이전트가 도구를 쥔다는 것 — 모델·하네스·루프

1편에서 모델·도구·에이전트·하네스라는 낱말과, 요청이 하네스를 거쳐 실행되고 돌아오는 순환을 봤다. 그리고 도구 설명 문장이 곧 모델이 읽는 프롬프트라는 것도 확인했다. 이번 편은 그 설명 문장을 실제로 표 형식으로 써보는 실습이다 — "설명을 잘 쓴다"가 구체적으로 뭘 하는 건지 손으로 직접 채워본다.

1. 도구 정의서 — 여섯 칸을 채우는 표

계약을 실제로 쓸 때는 여섯 칸을 한 표에 채운다. 이 여섯 칸을 흔히 도구 정의서(tool definition)라 부른다. 재고 조회 도구를 예로 채우면 이렇다.

항목내용
① 이름get_inventory — 동사+대상 형태로 짓는다
② 하는 일 (한 문장)승인된 창고의 특정 SKU 가용 수량을 읽기 전용으로 조회한다
③ 쓰는 때 · 안 쓰는 때수량 질문에는 쓰고, 수량 변경이나 창고 미지정에는 쓰지 않는다
④ 인자 스키마sku: 문자열(3~32자), warehouse_id: SEOUL-01 또는 BUSAN-02
⑤ 반환 형식SKU, 창고, 가용 수량, 확인 시각
⑥ 실패 정의와 뒤 행동오류 코드별로 한 번 재시도, 허용 창고 재질문, 또는 중단

도구 설계에서 중요한 원칙 하나를 짚으면, 도구 하나는 동작 하나여야 한다. 재고 조회와 수량 변경을 같은 함수 안에 넣지 않는다. 반환값도 원본 데이터를 통째로 주지 않고 available_quantity, checked_at처럼 답의 근거가 될 필드만 남긴다 — 반환을 줄이는 일은 정보를 숨기는 게 아니라, 모델이 다음에 봐야 할 것을 명확히 가리키는 일이다. 예를 들어 재고 데이터베이스 안에는 원가·공급업체 연락처 같은 정보도 함께 있을 수 있는데, 이런 값까지 그대로 돌려주면 모델이 답변에 실수로 인용해버릴 위험이 생긴다.

2. 스키마란 무엇인가

여섯 칸 중 가장 낯설게 느껴졌던 건 ④번의 스키마(schema)였다. 스키마는 어떤 값이 들어갈 칸의 모양과 범위를 미리 정해 둔 규격이다. 회원가입 양식에서 "우편번호" 칸이 숫자 5자리만 받게 정해져 있는 것과 같은 원리를, 도구의 입력 칸에 그대로 적용한 것이다. 있을 때와 없을 때를 나란히 두면 왜 필요한지 바로 보인다.

모델이 보낼 수 있는 값결과
스키마 없이 (자유 텍스트로 받음)warehouse_id: "부산 아무 창고나"존재하지 않는 창고 이름이 그대로 하네스까지 넘어간다
스키마로 제한warehouse_id: enum["SEOUL-01","BUSAN-02"] (enum은 "이 목록 중 하나만" 이라는 뜻)이 두 값 이외의 입력은 실행 전에 하네스가 기계적으로 걸러낸다

즉 스키마는 "설명을 얼마나 친절히 썼는가"와는 다른 층의 안전장치다. 설명 문장(위 표의 ②③)은 모델에게 부탁하는 것이고, 스키마(④)는 하네스가 실행 전에 기계적으로 검사하는 규칙이다. 모델이 아무리 설명을 잘못 읽어도, 스키마를 벗어난 값은 애초에 통과하지 못한다. 부탁과 규칙, 이 두 층이 함께 있어야 안전하다는 게 이번 절의 핵심이다.

3. 실습 — 설명 문장 하나만 바꿔서 결과가 달라지는지 본다

이 실습이 증명하려는 것을 한 줄로 요약하면 이렇다. "도구 설명 = 모델이 읽는 지시"라는 말을 눈으로 직접 확인하는 대조 실험이다. 같은 모델·같은 요청·같은 스키마를 고정해두고 설명 문장 딱 하나만 바꿔서(짧은 minimal 버전 vs 자세한 contextual 버전), 결과가 실제로 달라지는지 본다.

실습 순서와 각 단계의 이유는 다음과 같다.

  1. 먼저 채점 기준(scorecard)을 저장한다. 결과를 보기 전에 "무엇을 통과로 칠지"를 미리 파일에 적어둔다. 이유는 간단하다 — 결과를 본 뒤에 기준을 만들면, 마음에 드는 결과 쪽으로 기준을 슬쩍 끼워 맞추게 된다(이걸 확증 편향이라 부른다). 채점 기준을 먼저 못 박아야 봐주기 판정을 막을 수 있다.
  2. 정상 요청과 애매한 요청, 두 가지를 각각 두 설명 버전에 넣는다. 정상 요청은 "BUSAN-02 창고 A-17 재고 알려줘"처럼 창고와 상품을 정확히 지정한 것이고, 애매한 요청은 일부러 창고를 빼고 "어느 창고든 SKU A-17 재고를 알려 주세요"라고 묻는 것이다. 왜 이런 애매한 요청을 일부러 넣을까? warehouse_id가 빠졌을 때 모델이 "허용된 창고를 물어봐야지" 하고 멈추는지, 아니면 아무 창고나 지어내서 호출하는지를 갈라보려는 것이다. 1편에서 본 "잘못 고름" 실패를 일부러 유도해서, 설명 문장이 그 실패를 막아주는지 시험하는 것이라 보면 된다.
  3. 결과를 pass/fail로 기록한다. 아래 네 항목으로 채점한다.
    채점 항목통과 기준
    도구 선택요청에 맞는 도구(get_inventory)를 골랐는가
    스키마 준수인자가 허용된 이름·형식·범위 안에 있는가
    반환 근거최종 답이 실제 반환값을 근거로 삼았는가
    실패 처리애매한 요청에서 추측 대신 정해진 대로(재질문 등) 행동했는가

실패 사례를 정의서 칸으로 되돌리기

실습을 실제로 돌리면 minimal 설명 쪽에서 몇 가지 실패가 관측된다. 이때 하는 일은 "이상하다"에서 멈추지 않고, 실패를 위 여섯 칸 표 중 정확히 몇 번이 비어서 생겼는지 되짚고, 그 칸을 한 문장으로만 보완하는 것이다. 아래는 실제로 강의에서 관측된 세 사례다.

실패 사례비어 있던 정의서 항목보완 문장
존재하지 않는 창고 코드를 임의로 넣어 WAREHOUSE_NOT_ALLOWED를 반복 호출했습니다③, ⑥허용되지 않은 창고면 허용 코드를 질문하고 재호출하지 않습니다
SKU 없이 가장 비슷한 상품을 골라 조회했습니다④, ⑥SKU는 필수이며 없으면 상품 식별자를 질문합니다
응답의 내부 원가까지 최종 답에 인용했습니다⑤가용 수량과 확인 시각만 반환하고 답의 근거로 씁니다

이 표를 읽는 방법은 언제나 같다. 나쁜 결과 하나를 보면 → "여섯 칸 중 몇 번이 비었길래 이런 일이 생겼지?"를 되묻고 → 그 칸만 한 문장으로 채운다. 한 번에 여러 칸을 동시에 고치면, 나중에 어느 수정이 실제로 효과가 있었는지 구별할 수 없게 된다. 한 번에 한 곳만 고친다는 이 원칙은 3편에서 다룰 회귀 판정과도 그대로 이어진다.

4. 하네스 상자를 열면 여섯 결정이 있다

1편에서 본 하네스 상자는 사실 하나의 결정이 아니라 여섯 개가 겹쳐 있다. 계약(위 정의서)만 잘 써도 실패가 남는 이유가 여기 있다 — 나머지 다섯이 비면 여전히 실패한다.

지점정하는 것비면 생기는 문제
① 시스템 지시역할, 우선순위, 금지 행동을 정하는 전역 안내문"조회 뒤 검증하라"가 빠지면 모델이 추측으로 답한다
② 도구(계약)위에서 채운 여섯 칸모델이 변경 도구를 대신 부르거나, 빈 반환을 성공으로 오해한다
③ 권한계약상 가능한 일 중 실제로 허용하는 범위읽기 전용이어야 할 자리에서 쓰기 호출이 통과된다
④ 실행 환경작업 폴더, 네트워크, 접속 자격, 시간·비용 한계넓은 접속 권한은 유출 범위를, 무제한 시간은 낭비 비용을 키운다
⑤ 관찰(기록)도구명·입력·판정·반환값·후속 판단을 남기는 실행 기록기록이 없으면 어디서 잘못 읽었는지 되짚을 수 없다
⑥ 중단같은 오류가 반복될 때 멈추고 사람에게 넘기는 조건없으면 위 "같은 실수 반복"이 브레이크 없이 계속된다

강의에서 든 사례도 흥미로웠다. 연구용 코딩 에이전트 SWE-agent는 이 여섯 지점을 정교하게 설계했고, 반대로 mini-swe-agent는 도구를 명령줄 하나로, 기록을 단순한 목록 하나로 줄인 약 100줄짜리 최소 구성으로도 준수한 성적을 냈다. 다만 여기서 나온 점수는 모델의 성능이 아니라 "모델+하네스" 조합의 성능이라는 점은 짚어야 한다 — 같은 모델이라도 하네스가 다르면 다른 에이전트가 된다.

하네스는 어떤 방식으로 목표 수행능력을 끌어올리는가

여섯 지점을 늘어놓고 보면 각자 다른 일을 하는 것 같지만, 한 문장으로 묶으면 결국 하나의 원리로 수렴한다. 1편에서 본 루프의 정의 — "관찰이 다음 선택을 바꿀 때 비로소 의미가 생긴다" — 가 그것이다. 검증·실행·재입력이 이 순환을 한 바퀴 돌리는 장치라면, 관찰과 중단은 그 순환이 같은 자리에서 헛돌지 않게 잡아주는 장치다.

그래서 "하네스가 에이전트의 목표 수행능력을 어떤 방식으로 개선하는가"라는 질문에는 이렇게 답할 수 있다 — 여섯 지점을 1편의 세 가지 실패에 하나씩 되돌려보면 된다.

하네스의 장치막는 실패
검증(허용목록·스키마)① 잘못 고름 — 엉뚱한 도구·값이 실행 전에 걸러진다
실행 + 결과 재입력② 잘못 읽음 — 추측이 아니라 실제 반환값을 근거로 판단하게 한다
관찰(기록) + 중단③ 같은 실수 반복 — 실패를 기록해 되짚고, 반복되면 멈춰 사람에게 넘긴다

즉 여섯 지점은 낱개로 존재하는 목록이 아니라, 검증→실행→관찰→재입력이라는 피드백 순환 하나를 안전하게 돌리기 위한 세부 장치들이다. 권한과 실행 환경은 이 순환이 도는 범위 자체를 좁혀 피해를 제한하는 역할을 한다. 이 순환이 없으면 모델은 매번 같은 추측을 반복할 뿐이고, 순환이 있어야 실행 결과가 다음 판단에 실제로 반영된다 — 그 반영이 곧 "목표 수행능력이 올라간다"는 말의 실체다.

5. 직접 만들어 실행해보기

지금까지는 이론이었다면, 여기서는 실제로 코드를 돌려 확인한다. Python으로 짠 get_inventory 도구를 모델에 연결해, 요청→실행→최종 답 세 단계를 그대로 찍어본다.

[1] 모델의 요청: get_inventory(sku='A-17', warehouse_id='BUSAN-02')
[2] 하네스의 실행 결과: {"sku": "A-17", "warehouse_id": "BUSAN-02",
    "available_quantity": 7, "checked_at": "2026-08-27T01:55:00+09:00"}
[3] 결과를 읽은 최종 답: 승인된 창고(BUSAN-02)에서 상품 A-17의
    현재 가용 재고는 7개입니다.

이 세 줄이 각각 누구의 책임인지 다시 짚으면, [1]은 모델의 소관, [2]는 하네스의 소관, [3]은 다시 모델의 소관이다. [1]이 그럴듯해도 [2]가 없으면 재고를 읽었다고 말할 수 없고, [2]가 성공해도 [3]이 수량을 바꿔 말하면 실패다. 이 세 줄을 텍스트 파일 하나에 순서대로 남기는 걸 트레이스(trace)라 부르는데 — 요청부터 최종 답까지 무슨 일이 있었는지 남기는 실행 기록이다 — 나중에 계약을 수정했을 때 "이번 수정이 실제로 무엇을 바꿨는지" 비교할 근거가 된다.

6. 남이 만든 도구 붙이기 — MCP와 RAG

여기서 한 단계 더 나아가, 자기가 만든 도구가 아니라 남이 만든 도구를 붙이는 실습도 했다. 문서 검색 서버인 Qdrant(문서 조각을 의미 기반으로 찾아 돌려주는 오픈소스 검색 엔진)를 1편에서 설명한 MCP 방식으로 등록하는 실습이다.

이 방식을 RAG(Retrieval-Augmented Generation, 검색 증강 생성)라 부르는데, 모델이 답을 순전히 기억에서 지어내는 대신 관련 문서를 먼저 찾아 그 내용을 근거로 답하게 만드는 구조다. RAG를 왜 쓰는지, 무엇을 근거로 넣을지 정하는 법은 무엇을 넣을지 정하는 법 — RAG에 따로 자세히 정리해 뒀으니 여기서는 이 실습에서 새로 나온 두 낱말만 짚는다.

  • 임베딩(embedding) — 문장을 컴퓨터가 "의미가 비슷한지"를 계산할 수 있는 숫자 배열로 바꾸는 과정. "재고 확인 방법"과 "재고 조회하는 법"처럼 표현은 달라도 뜻이 비슷한 문장을 찾아낼 수 있게 해준다.
  • 벡터 데이터베이스(vector database) — 이렇게 숫자로 바꾼 값들을 모아두고, 새 질문이 들어오면 의미가 가장 비슷한 것을 빠르게 찾아주는 저장소. Qdrant가 이 역할을 한다.

등록은 설정 파일 하나로 끝난다. Claude Code는 프로젝트 루트의 .mcp.json에 이렇게 등록한다.

{
  "mcpServers": {
    "qdrant": {
      "command": "uvx",
      "args": ["mcp-server-qdrant"],
      "env": { "QDRANT_URL": ":memory:", "QDRANT_COLLECTION": "policies" }
    }
  }
}

여기서 헷갈리기 쉬운 게 하나 있다. 이 설정 파일 안의 내용이 모델에게 그대로 보이는 건 아니다. command, args, env(QDRANT_URL 같은 값들)는 전부 "이 서버를 어떻게 켜고 어디에 접속할지"를 정하는 값이고, 이건 하네스만 안다 — 모델은 이 값들을 아예 보지 못한다.

모델에게 실제로 넘어가는 건 서버가 켜진 뒤 내놓는 도구 목록뿐이다. 이 예시라면 qdrant-store, qdrant-find 두 도구 각각의 이름 · 설명 · 인자 규칙(스키마) 세 가지만 모델에게 전달된다. 즉 "어떻게 접속하는가"는 하네스만 알고 있고, "무엇을 할 수 있는가"만 모델에게 넘어간다 — 도구 정의서 6칸으로 치면 ①이름·②하는 일·④인자 스키마에 해당하는 부분만 모델 몫이고, 나머지는 하네스가 붙잡고 있는 셈이다.

opencode라는 다른 에이전트 도구는 같은 서버를 opencode.json에 mcp라는 다른 키 이름으로 등록하지만, 결국 같은 mcp-server-qdrant 실행 줄을 가리킨다. 등록만 하면 qdrant-store(문장을 저장)와 qdrant-find(비슷한 문장을 검색) 두 도구가 모델의 도구 목록에 자동으로 나타나고, 모델은 이 중 어느 것을 부를지 스스로 고른다. 1편에서 본 "M×N 문제를 표준 하나로 줄인다"는 게 실제 설정 파일에서는 이렇게 짧은 몇 줄로 끝나는 걸 확인한 것이 이 실습의 핵심이었다.

3편에서는 이렇게 만든 도구를 실제로 안전하게 쓰기 위한 권한 설계, 그리고 과제로 이어지는 평가 방법을 다룬다.
