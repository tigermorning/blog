PR 병목 고치기 — 에이전트 PR을 사람이 다 읽지 않아도 되는 조건

2026. 10. 4.

※ 이 글은 원본 강연 "Fixing the PR Bottleneck"(Matt Pocock, AIHero · AI Engineer Paris 2026, AI Engineer 채널)과 이 강연을 한국어로 풀어 준 해설 영상 "에이전트 PR을 사람이 전부 리뷰하지 않아도 되는 기준"(AgentOS)을 보고 제 나름의 언어로 정리한 것입니다. 슬라이드 화면은 확인하지 못해, 말로 나온 내용만 옮겼어요.

PR 병목은 에이전트가 만든 코드 변경 요청(PR)이 사람의 검토를 기다리며 쌓여서, 사람이 읽는 속도가 개발 전체의 속도를 정해 버리는 상태다.

  • 에이전트에게 맡긴 일이 "확인해 주세요"로 줄지어 돌아올 때. 밤새 맡겨 둔 고칠 거리들이 아침에 PR 여러 개로 와 있고, 다 읽기도 전에 다음 PR이 또 와요.
  • 내 저장소의 PR 본문 양식에 무엇을 적게 할지 정할 때
  • 같은 지적을 두 번째로 하고 있을 때 — 검사나 규칙으로 옮길 때라는 신호예요

코딩 에이전트에게 일을 맡기면 결과는 보통 PR1로 돌아와요. "이렇게 고쳤으니 원래 코드에 합쳐도 될지 봐 주세요"라는 요청이에요. 사람이 읽고 승인하면 원래 코드에 합쳐지고(머지2), 아니면 고칠 점을 돌려보내요. 에이전트는 이 요청을 밤새 몇 개든 만들 수 있지만, 읽는 사람은 그대로 한 명이에요.

발표자 맷 포콕은 이게 AI 때문에 새로 생긴 문제가 아니라고 짚으며 시작해요. 아무도 안 본 PR이 쌓여 있는 건 원래 흔한 풍경이었고, AI는 그 압력을 크게 키웠을 뿐이라는 거예요. 강연 영상 설명란은 문제를 더 정확하게 적어요. 에이전트는 PR을 여는 일은 아주 쉽게 만들었지만, 리뷰할 가치가 있는 PR을 여는 일은 조금밖에 쉽게 만들지 못했다는 거예요.

여기에 소프트웨어 팩토리가 겹쳐요. 발표자의 정의로는 일의 시작을 사람이 아니라 에이전트나 정해진 규칙대로 도는 코드에 넘기는 것이에요. 오류 알림이나 느린 쿼리 보고서가 뜨면, 사람이 보기 전에 에이전트가 먼저 고치기 시작하는 식이에요. 일을 빠르게 만드는 쪽만 있고 품질을 지키는 장치가 없으면 품질 낮은 PR이 끝없이 쏟아져요. 발표자는 이 상태를 "slop cannon"이라고 불러요 — 저품질 코드를 쏘아 대는 대포라는 뜻이에요. 그래서 그는 빠르게 만드는 쪽을 가속장치, 품질을 지키는 장치를 브레이크라고 나눠 불러요.

코드는 에이전트가 일하는 환경이기도 해요. 나쁜 코드 위에서 일한 에이전트는 더 나쁜 코드를 내요. 그래서 설명란은 사람 개발자의 작업 환경(DX)을 따지는 만큼 에이전트의 작업 환경(AX3)도 엄밀하게 다뤄야 한다고 말해요. 병목을 푸는 길은 PR을 더 빨리 쓰는 게 아니라, PR 주변 — 검사·리뷰·PR 본문·회고 — 을 고치는 거예요. 한국어 해설 영상은 이 문제를 한 줄로 정리해요. 사람이 느려서가 아니라, 사람에게 도착하는 PR의 품질이 낮아서 생기는 병목이라고요.

브레이크 세 겹 — 자동 검사 · 자동 리뷰 · 사람 리뷰

발표자가 세우는 브레이크는 세 겹이에요. PR이 사람에게 오기 전에 앞의 두 겹을 먼저 지나요.

겹무엇을 하나드는 비용
① 자동 검사린트4·테스트·타입 검사5·품질 지표를 정해진 규칙대로 돌려요CPU 시간 — 가장 싸요
② 자동 리뷰에이전트가 변경 내용을 읽고, 테스트가 못 잡은 것과 구조 문제를 봐요토큰
③ 사람 리뷰마지막으로 판단하고 머지를 승인해요사람 시간 — 가장 비싸요

목표는 앞 두 겹에 기대서 세 번째 겹을 빠르게 만드는 거예요. 내보내는 코드의 품질이 오르면 사람이 끼어들 일이 줄어요. 자동 검사는 CPU만 쓰니 더 많이, 더 창의적으로 늘려도 돼요. 그런데 문제가 하나 있어요. 자동 검사는 거짓말을 해요. 그 이야기는 아래에서 이어 가고, 먼저 세 겹 전체를 익숙한 장면에 대 볼게요.

비유로 먼저 — 신문사 편집국의 원고

신문사 편집국을 떠올려 봐요. 기자가 편집부에 원고를 넘기면 맞춤법 검사기가 먼저 훑고, 교정 담당이 읽으며 틀린 곳을 직접 고쳐 놓은 뒤 확신이 안 서는 대목에만 기자에게 묻는 쪽지를 붙여요. 편집장은 내일 아침 종이 신문 1면에 찍혀 나갈 기사는 한 줄씩 읽고, 나중에 고칠 수 있는 웹 기사 정정은 훑고 승인해요. 교정 담당은 같은 지적이 자꾸 나오면 그걸 편집국 표기 규칙집에 옮겨 적어요.

비유 속 요소원래 개념
기자가 편집부에 — 원고를 넘김에이전트가 사람에게 — PR을 올림
맞춤법 검사기가 원고를 자동으로 훑음① 자동 검사 — 린트·테스트·타입 검사가 정해진 규칙대로 돎
교정 담당이 원고를 직접 고쳐 놓고, 확신 없는 곳만 기자에게 쪽지로 물음② 자동 리뷰 — 리뷰 에이전트가 고쳐서 커밋6하고, 확신 없는 것만 PR 댓글로 물음
편집장이 마지막으로 읽고 승인③ 사람 리뷰 — 사람이 머지를 승인
찍으면 회수 못 하는 종이 신문 1면 · 나중에 정정할 수 있는 웹 기사one-way door(합친 뒤 되돌릴 수 없는 변경) · two-way door(되돌릴 수 있는 변경)
교정 담당이 반복되는 지적을 표기 규칙집에 옮겨 적음retro — 반복된 리뷰 지적을 새 자동 검사·코딩 규칙으로 옮김

핵심 한 줄: 편집장이 더 빨리 읽게 만드는 대신, 편집장 책상에 오는 원고를 미리 걸러 둔다.

다만 여기서 비유가 끊기는 점이 있어요. 맞춤법 검사기는 틀린 곳을 놓칠 수는 있어도, 통과할 수밖에 없게 짜인 채로 오지는 않아요. 에이전트가 쓴 테스트는 그런 채로 올 수 있어요.

전체 흐름 — PR 하나가 머지되기까지

읽는 법: 윗줄을 왼쪽에서 오른쪽으로 읽으면 PR 하나가 지나가는 순서예요. 오른쪽으로 갈수록 한 번 보는 비용이 비싸져요. 코딩 규칙 파일이 ②에만 화살표로 이어진 게 이 강연의 핵심 배치예요 — 코드를 짜는 에이전트는 이 파일을 안 읽어요. 점선은 되먹임이에요. 사람이 리뷰하다 같은 지적을 두 번째로 하게 되면, 그 지적은 retro를 거쳐 ①의 검사나 ②가 읽는 규칙으로 내려가요. 그다음부터는 사람에게 오기 전에 걸러져요.

초록불은 거짓말을 한다 — 에이전트가 쓴 테스트의 세 함정

CI7에서 테스트가 전부 통과하면 초록불이 떠요. 그런데 초록불이 곧 "합쳐도 된다"는 뜻은 아니에요. 발표자는 에이전트가 쓴 테스트에서 자주 보이는 거짓말 세 가지를 들어요.

테스트 종류생김새왜 믿으면 안 되나
되받아쓰기 테스트구현 코드에 적힌 상수(예: 글자 수 제한 280)를 테스트가 그대로 다시 적어 확인해요동작을 확인한 게 아니라 구현을 베낀 거예요. 이름만 바꿔도 깨져요
구조 민감 테스트화면을 실제로 그려 보지 않고, 소스 파일을 글자로 읽어 "A가 B보다 뒤에 있나"를 확인해요코드 모양에 묶여 있어서, 정작 화면이 제대로 나오는지는 모르는 채 통과해요
실패할 수 없는 테스트오류가 날 수 있는 실제 API 호출을 목8(가짜 메서드)으로 바꿔 버려요테스트에서는 절대 실패하지 않으니, 오류는 운영에서만 터져요

에이전트가 나쁜 뜻으로 이러는 건 아니에요. 시킨 대로 테스트를 쓰다 보니 구현 구조에 너무 묶인 테스트가 나오는 거예요. 그래서 나머지 두 겹, 자동 리뷰와 사람 리뷰는 거짓말 탐지기 역할을 해요. 한국어 해설 영상은 이런 거짓 테스트를 체중계에 올라가지 않고 공책에 적힌 숫자만 읽는 검사에 빗대요.

테스트 통과 여부 하나로 판정하지 않고, 에이전트가 실제로 무엇을 했는지 기록을 따로 읽어 판정하는 방법은 통과했다는 말로는 부족하다 — 두 층 채점에서 다뤘어요.

처방 ① 깊은 모듈 — 작은 입구에서만 테스트하게

첫 처방은 코드베이스 설계예요. 깊은 모듈9은 바깥에 드러난 사용법(인터페이스10)은 작고, 그 뒤에 복잡한 동작을 숨긴 코드 묶음이에요. John Ousterhout의 책 A Philosophy of Software Design에서 온 개념이에요. 테스트를 이 작은 인터페이스에서만 하게 하면, 안쪽 구현을 바꿔도 테스트가 버텨요. 앞의 세 함정은 모두 테스트가 안쪽 구현을 들여다봐서 생긴 거예요.

그래서 할 일은 에이전트가 내부를 파고들지 않고 작은 인터페이스로 테스트하게 강제하는 거예요. 발표자는 이걸 팀이 함께 이야기하려면 공용 어휘가 필요하다며 세 낱말을 들어요.

  • locality — 한 가지를 바꿀 때 고칠 곳이 한곳에 모이는가
  • leverage — 모듈을 부르는 쪽이 작은 사용법으로 얼마나 많은 일을 얻는가
  • seam — 다른 구현으로 갈아 끼울 수 있는 이음매가 어디인가

발표자의 공개 스킬 모음(2026-10-04 확인)에는 이 일을 맡는 스킬이 둘 있어요. improve-codebase-architecture는 깊게 만들 기회를 찾아 HTML 보고서로 정리하고, codebase-design은 깊은 모듈·작은 인터페이스·seam을 기준으로 설계를 다뤄요.

처방 ② 코딩 규칙은 리뷰 에이전트에게

코딩 규칙(이름 짓는 법, 함수 크기, 피할 패턴 같은 것)을 어디에 적을까요? 흔히 CLAUDE.md나 AGENTS.md 같은 규칙 파일에 넣어요. 그러면 코드를 짜는 에이전트가 세션마다 그걸 읽어요. 발표자는 이게 거꾸로라고 봐요.

  • 구현 에이전트는 이미 과부하예요. 코드를 찾아보고, 고치고, 디버깅하는 일을 한 컨텍스트 창 안에서 다 해요. 여기에 규칙까지 얹으면 성능이 떨어져요(넣은 내용이 많을수록 덜 읽히는 현상은 길게 넣어도 안 읽힐 수 있다에 있어요).
  • 리뷰 에이전트는 여유가 있어요. 바뀐 부분(diff11)을 받고 조금 찾아볼 뿐, 구현도 디버깅도 안 해요. 별도 서브에이전트12로 띄우면 컨텍스트도 따로예요.

그래서 규칙은 매번 읽히는 전역 지시 파일이 아니라 별도의 코딩 규칙 파일에 두고, 리뷰 서브에이전트만 읽게 해요.

중요꼭 기억할 것

구현과 리뷰를 두 단계로 나눠요. 구현 단계는 되게 만들기(red-green13)만 하고, 리뷰 단계가 다른 컨텍스트에서 좋게 만들기(refactor)를 맡아요. 코딩 규칙은 뒤쪽 단계의 도구예요.

검토하는 에이전트에게 무엇을 덜 줄지 고민하는 건 이 블로그의 에이전트 안티패턴 다섯 가지에도 나와요. 거기서는 검토 에이전트에게 작성자의 생각 과정을 빼고 주장과 근거만 넘겼어요.

처방 ③ 자동 리뷰는 직접 만들고, 댓글 대신 커밋

범용 자동 리뷰 서비스를 붙이면 되지 않을까요? 발표자는 외주보다 직접 만들기를 권해요. 범용 도구는 규칙이 너무 일반적이면 문제가 아닌 것을 문제라고 짚는 일(오탐)이 많고, 너무 구체적이면 다른 팀에는 안 맞아요. 대신 우리 팀의 코딩 규칙을 시간을 두고 쌓아 공유해요. 아무도 안 읽던 팀 문서가 있다면 바로 여기, 리뷰 에이전트가 읽는 자리에 두면 돼요.

두 번째는 리뷰 에이전트의 기본 동작이에요. 댓글만 달면 사람이 읽을 게 늘 뿐이에요. 그래서 기본은 직접 고쳐 커밋하고, 확신이 없는 것만 질문 댓글로 남겨요. 한 번에 좋은 코드를 뽑으려는 시도는 그만두고, 되게 만든 뒤 리뷰 단계에서 좋게 만드는 흐름으로 가는 거예요.

공개 저장소와 다른 점(2026-10-04 확인). 발표자의 공개 저장소 mattpocock/skills의 code-review 스킬은 서브에이전트 둘이 동시에 봐요.

  • Standards — 저장소의 규칙 문서(CODING_STANDARDS.md·CONTRIBUTING.md)와 Martin Fowler의 코드 냄새 기준에 맞는가
  • Spec — 이슈와 명세에 충실한가

그런데 이 스킬은 찾은 것을 보고만 해요. 커밋도, PR 줄마다 다는 댓글도 하지 않아요. 리뷰어가 고쳐서 커밋하라는 강연의 권고와는 다른 모양이에요(고치는 일을 다른 스킬이 맡는지는 확인하지 못했어요). 강연에서 말로 나온 코딩 규칙 파일 이름은 저장소에서 CODING_STANDARDS.md로 적혀 있어요.

사람이 읽기 좋은 PR — 세 원칙

앞의 두 겹을 지나 사람에게 온 PR도, 본문이 어떻게 생겼느냐에 따라 읽는 시간이 크게 달라져요. 발표자가 새로 낸 pr 스킬은 세 원칙 위에 서 있어요.

1. 리뷰 중요도는 PR마다 다르다. 기준은 합친 뒤에 되돌릴 수 있느냐예요.

  • two-way door — 합친 뒤에도 되돌릴 수 있는 변경이에요. 대부분의 PR이 여기에 들어요.
  • one-way door — 되돌릴 수 없는 변경이에요. 비싼 데이터 이전(마이그레이션), 데이터 손실, 그리고 코드로는 한 줄짜리라도 6만 명에게 메일이 나가는 변경이 그 예예요.
  • blast radius — 잘못됐을 때 피해가 어디까지, 얼마나 번지는가예요.

이 판단을 PR 맨 아래 Merge Danger 칸에 적어 두면, 사람은 그 칸부터 보고 얼마나 꼼꼼히 읽을지 정해요. 한국어 해설 영상은 one-way·two-way door라는 말이 아마존 베이조스의 주주 서한에서 왔다고 덧붙여요. 어떤 요청에서 사람을 부를지를 계산 가능한 기준으로 적는 법은 멈출 기준을 정하고 승인 화면을 설계한다에서 다뤘어요. 같은 질문을 PR 단위로 묻는 셈이에요.

2. 무엇을 하는지 그림으로 보여 준다. 긴 글 대신 의사코드, 호출 순서를 적은 트리, 바뀐 파일 트리, mermaid14 도식처럼 가장 작은 그림으로 "왜"를 빨리 이해시켜요. 발표자는 이 발상에 대해 Dex Horthy의 show-me 스킬에 고마움을 전해요.

3. 코드가 아니라 코드를 만든 시스템을 리뷰한다. 같은 지적을 두 번 쓰지 않아요. 두 번째 쓰게 된 지적은 이 PR이 아니라 PR을 만든 쪽(검사·규칙·스킬)을 고쳐야 한다는 신호예요. 이게 다음 절의 retro로 이어져요.

공개 저장소의 pr 스킬(2026-10-04 확인)은 PR 본문을 Summary → Evidence → Merge Danger 순서로 써요. Summary는 위 2번의 가장 작은 그림이고, Evidence는 되는지 보여 주는 증거인데 스크린샷을 가장 높게(S급), 실행 결과를 그다음(A급)으로 쳐요. Merge Danger에는 Door(one-way/two-way)와 Blast Radius(한 단어)를 적어요. 이 순서를 본떠 내 저장소의 PR 양식으로 만들면 이래요.

retro — 오늘의 리뷰를 다음 리뷰의 검사로

발표자가 함께 낸 retro 스킬은 3번 원칙을 실제로 굴리는 도구예요. 이 스킬의 원문은 확인하지 못해, 강연에서 말한 내용만 옮겨요. 입력으로는 셋 중 하나를 넣어요.

  • 에이전트 세션 하나
  • PR 하나와 그 PR을 만든 세션
  • 지난주의 PR과 리뷰 전부

그러면 아래를 제안해요.

  • 새 자동 검사와 코딩 규칙 파일 갱신 — 사람이 반복한 지적을 ①·②로 내려보내요.
  • 탐색 길잡이 — 에이전트가 필요한 정보를 쉽게 찾았는지 보고, 못 찾았다면 agents.md에 길잡이를 둘지 물어요.
  • 도구 경제성 — 토큰을 덜 쓰는 도구로 바꿀 수 있는지 봐요.
  • 비대해진 파일 — 에이전트 행동을 이끄는 지시 파일(steering 파일)이나 스킬이 너무 커져서 결과를 망치고 있지 않은지 봐요.

효과는 복리예요. 오늘 사람이 한 리뷰가 검사와 규칙으로 남아, 다음 리뷰를 가볍게 만들어요. 한국어 해설 영상은 retro를 설명하며 같은 맞춤법을 매번 빨간 펜으로 고치는 선생님을 비유로 들어요. 지난 실패를 다음에 바꿀 행동으로 압축해 두는 일반적인 방법은 성공은 자산으로, 실패는 설명으로 — 경험·스킬 축적과 반성에 있어요.

정리 — two-way는 다 보지 않아도, one-way는 다 본다

강연의 결론은 짧아요. two-way door PR은 전부 읽을 필요가 없어요. one-way door PR은 전부 읽어요. 그리고 사람이 리뷰를 빨리 읽는 요령을 찾기보다, 사람에게 오기 전에 걸러지는 겹을 쌓는 쪽에 힘을 써요. 자동 검사는 싸니까 늘리고, 그 검사의 거짓말은 깊은 모듈과 리뷰 에이전트로 잡고, 사람은 Merge Danger 칸을 보고 힘을 쓸 곳을 골라요.

나쁜 선택 vs 좋은 선택 — 리뷰 에이전트를 붙일 때

에이전트가 올리는 PR 뒤에 리뷰 에이전트를 하나 붙인다고 해 볼게요. 편집국으로 치면 교정 담당을 새로 들이는 장면이에요.

나쁜 선택좋은 선택
코딩 규칙을 전부 CLAUDE.md에 넣어 구현 에이전트가 매번 읽게 하고, 리뷰 에이전트는 찾은 문제를 PR 댓글로만 달게 한다 → 구현 에이전트는 규칙까지 떠안아 결과가 흐려지고, 사람은 PR마다 댓글 수십 개를 읽은 뒤 직접 고치거나 다시 시켜야 한다. 코딩 규칙을 별도 파일(CODING_STANDARDS.md 같은)로 옮겨 리뷰 서브에이전트만 읽게 하고, 기본 동작은 고쳐서 커밋, 확신 없는 것만 질문 댓글로 남기게 한다 → 구현 에이전트는 되게 만드는 데만 집중하고, 사람은 커밋 목록과 질문 몇 개, 맨 아래 Merge Danger만 보고 얼마나 읽을지 정한다.

이 글에 나온 숫자 — 원본을 찾아보거나 스킬을 직접 쓰기 전에

두 영상과 공개 저장소에서, 이 강연을 직접 찾아보거나 발표자의 스킬을 가져다 쓸 때 다시 확인할 값만 모았어요. 저장소는 이 글을 쓴 날 한 번 대조한 것이라, 그 뒤에 바뀌었을 수 있어요.

이럴 때 의심하세요 — 에이전트 PR을 받아 합치는 흐름에서

PR 병목의 문제들은 코드 줄보다 머지한 뒤의 사고나 늘어난 읽을거리로 먼저 보여요. 아래 증상이 보이면 PR을 하나 더 꼼꼼히 읽기 전에 이 자리부터 열어 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "이 기능 테스트도 같이 짜 줘" — 테스트가 구현의 숫자를 베꼈거나 실제 호출을 가짜로 바꿨는지
  • "PR마다 자동으로 리뷰해 주게 만들어 줘" — 리뷰 결과가 댓글로만 쌓이는지, 고쳐서 커밋하는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
CI는 초록인데 운영에서만 오류가 나요. 또는 함수 이름 하나 바꿨을 뿐인데 테스트가 줄줄이 빨개져요 테스트 파일이에요. 실제 호출을 가짜로 바꾸는 줄(jest.mock, unittest.mock 같은), 구현에 적힌 숫자를 그대로 다시 적은 확인, 소스 파일을 글자로 읽어 들이는 줄. 구현 코드는 범인이 아닐 때가 많아요 구현의 핵심 줄을 잠깐 망가뜨리고 테스트를 돌려 봐요. 그래도 초록이면 그 테스트는 아무것도 지키지 않아요. 작은 인터페이스에서 동작을 확인하는 테스트로 바꿔요(세 함정, 깊은 모듈)
자동 리뷰를 붙였더니 PR마다 댓글이 수십 개 달리고, 사람이 읽을 게 오히려 늘었어요 리뷰 에이전트에게 주는 지시(스킬 파일이나 리뷰 프롬프트)에서 찾은 것을 어떻게 남기라고 했는지 적힌 부분 지난 PR의 리뷰 댓글 가운데 사람이 그대로 받아 고친 것이 몇 개인지 세어 봐요. 그런 지적은 리뷰 에이전트가 직접 고쳐 커밋하게 바꾸고, 질문만 댓글로 남기게 해요(처방 ③)
CLAUDE.md에 코딩 규칙을 적을수록 구현 에이전트가 규칙도 어기고, 원래 시킨 기능까지 엉성해져요 세션마다 자동으로 읽히는 규칙 파일(CLAUDE.md·AGENTS.md)의 코딩 스타일 부분 코딩 규칙을 별도 파일로 옮기고 리뷰 단계에서만 읽히게 한 뒤, 같은 일을 다시 시켜 결과를 비교해요(처방 ②)
"단순 변경"이라 훑고 머지했는데, 메일이 대량으로 나갔거나 지워진 데이터를 되살릴 수 없어요 PR이 건드린 파일 가운데 데이터베이스 마이그레이션, 메일·알림 발송, 결제 호출 부분. 그리고 PR 본문의 Merge Danger 칸 이런 파일을 건드렸는데 Door가 비어 있거나 two-way로 적힌 PR이면 one-way로 다시 분류하고 줄마다 읽어요. 코드 줄 수는 위험도와 상관없어요(세 원칙)

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

이 저장소의 테스트 파일을 훑어서 아래에 해당하는 테스트를 찾아 파일·줄 번호로 표로 보여 줘. 아직 코드는 고치지 마.
1. 구현 코드에 적힌 상수나 문자열을 그대로 다시 적어 확인하는 테스트
2. 소스 파일을 텍스트로 읽어 코드의 순서나 내용을 확인하는 테스트
3. 실패할 수 있는 실제 호출(API·DB·파일)을 가짜(mock)로 바꿔서, 실패하는 경우를 한 번도 확인하지 않는 테스트
항목마다 왜 그렇게 봤는지 한 줄씩 적어 줘.

함께 보기

  • 에이전트 안티패턴 다섯 가지 — 같은 발표 노트 묶음의 글이에요. 검토 에이전트에게 무엇을 빼고 줄지, CI에서 에이전트를 어떻게 부를지가 이 글과 맞닿아 있어요.
  • 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정 (4) — 초록불 하나로 판정하지 않는 방법을 실제 실험으로 보여 줘요.
  • AGENTS.md와 캐싱 경제학 (5) — 매 세션 읽히는 규칙 파일에 무엇을 실어도 되는지 따져요. 코딩 규칙을 거기서 빼는 이유와 이어져요.
  • 멈출 기준을 정하고 승인 화면을 설계한다 (2) — 어떤 요청에서 사람이 승인할지를 기준으로 적는 법이에요. one-way door를 고르는 일과 같은 질문이에요.
  • 성공은 자산으로, 실패는 설명으로 (3) — retro처럼 지난 실패를 다음 행동으로 바꾸는 일반적인 방법이에요.
  • 켄트 벡 — 기능 사이에서 멈춰 여지를 되찾는 법 — 에이전트가 쏟아내는 결과의 병목을 사람 쪽이 아니라 만드는 방식에서 푸는 또 다른 시각이에요. 사람 없는 공장이 왜 탈선하는지도 다뤄요.
  1. PR(pull request, 풀 리퀘스트) — 내가 고친 코드를 원래 코드에 합쳐 달라고 GitHub 같은 곳에 올리는 요청으로, 다른 사람이 바뀐 부분을 읽고 승인하거나 고칠 점을 돌려보내요. ↩
  2. 머지(merge) — 따로 고친 코드를 원래 코드에 합치는 일이며, Git의 갈래(브랜치)와 합치기는 Git 브랜치·병합 실습에서 직접 해 봤어요. ↩
  3. AX(agent experience) — 에이전트가 코드베이스 안에서 일하기 얼마나 편한지를 사람의 개발자 경험(DX)에 빗대 부르는 말로, 실험이 남긴 네 문제와 도구들에서 쓴 AX(AI 전환)와는 다른 말이에요. ↩
  4. 린트(lint) — 코드를 실행하지 않고 읽기만 해서 문법 실수나 팀이 정한 스타일 위반을 자동으로 찾아 주는 검사예요. ↩
  5. 타입 검사 — 숫자가 들어갈 자리에 글자를 넣는 것처럼 값의 종류가 맞지 않는 곳을 실행 전에 찾아내는 검사예요. ↩
  6. 커밋(commit) — 지금까지 고친 상태를 확정해 기록으로 남기는 Git 동작으로, Git 커밋이란 무엇인가에서 처음 다뤘어요. ↩
  7. CI — 코드를 올릴 때마다 테스트·검사를 사람 손 없이 자동으로 돌리는 장치로, 에이전트 안티패턴 다섯 가지에서 CI/CD로 다뤘어요. ↩
  8. 목(mock) — 테스트할 때 실제 API·데이터베이스 대신 끼워 넣는 가짜 객체로, 정해 둔 답만 돌려줘요. ↩
  9. 깊은 모듈(deep module) — 사용법은 작고 단순한데 그 뒤에서 많은 일을 해 주는 코드 묶음을 가리키는, John Ousterhout의 설계 용어예요. ↩
  10. 인터페이스 — 코드 묶음을 바깥에서 쓸 때 부르는 함수 이름·받는 값·돌려주는 값처럼 겉으로 드러난 사용법이에요. ↩
  11. diff — 고치기 전과 후의 코드를 줄 단위로 비교해 바뀐 부분만 보여 주는 결과예요. ↩
  12. 서브에이전트 — 메인 에이전트가 일의 한 조각을 맡기려고 따로 띄우는 하위 에이전트로, 멀티 에이전트의 득실에서 나눌지 말지를 따져 봤어요. ↩
  13. red-green-refactor — 실패하는 테스트를 먼저 쓰고(빨강), 그 테스트가 통과하게 만든 뒤(초록), 동작은 그대로 두고 코드를 다듬는(리팩터) 테스트 주도 개발의 순서예요. ↩
  14. mermaid — 몇 줄의 글로 순서도·흐름도를 그려 주는 도식 문법으로, GitHub의 PR 본문에서도 그림으로 보여 줘요. ↩
