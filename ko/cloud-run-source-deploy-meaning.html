Cloud Run에 소스를 배포한다는 것 — 코드 폴더 하나가 공개 주소가 되기까지 (2)

2026. 10. 20.

※ 이 글은 모두의연구소(모두연) 학습 자료를 제 나름의 말로 다시 정리한 글이에요.

내 컴퓨터에서만 돌던 앱을 동료에게 보여 주면 "나도 써 보게 주소 좀 줘"라는 말이 돌아와요. 그런데 줄 주소가 없어요. 앱은 내 컴퓨터 안에서만 돌아가고, 컴퓨터를 끄면 함께 멈춰요. 1편에서 정한 설계(키는 서버에만, 데이터는 서버 밖에)도 일단 서버가 있어야 지킬 수 있어요. 이 글은 그 첫 단계, 코드를 서버에 올려 공개 주소를 만드는 일을 다뤄요. 서버를 직접 사지 않고 Google Cloud의 Cloud Run1을 쓰고, 오늘 제가 실제로 올린 아주 작은 앱의 로그를 따라가며 설명할게요.

명령 한 줄 — 폴더를 넘기면 서버가 돼요

소스 배포는 터미널에서 gcloud2로 이 한 줄을 실행하는 것이 전부예요. 여기서 소스(source)는 내가 짠 코드가 든 폴더를 뜻해요.

실행: 로컬 터미널 — 코드가 든 폴더(my-hello) 안에서 실행해요. 미리 gcloud 설치·로그인과 프로젝트 선택이 끝나 있어야 해요

gcloud run deploy hello --source . --region us-central1 --allow-unauthenticated
부분뜻
gcloud run deploy hellohello라는 이름의 서비스를 Cloud Run에 배포해요
--source ."지금 있는 폴더(.)의 코드를 올려라"예요. 이미지를 따로 만들어 올리는 게 아니라 폴더를 그대로 넘겨요
--region us-central1서비스가 실행될 데이터센터 위치(리전3)예요
--allow-unauthenticated로그인 없이 누구나 이 주소를 부를 수 있게 해요. 연습용 앱은 괜찮지만, 호출마다 AI 비용이 나가는 서비스라면 한도를 함께 걸어야 해요

비유로 먼저 — 1편의 식당에서 포장 가게로

1편의 식당을 이어 쓸게요. 사장인 내가 요리사에게 가게를 맡기는 대신, 이번엔 본사에 레시피 폴더를 통째로 보내요. 본사는 레시피를 읽고 필요한 재료와 조리 도구를 알아서 맞춰 밀키트 상자로 포장하고, 그 상자를 가맹점에 보내 가게를 열어 주고, 가게 주소까지 붙여 줘요. 이게 소스 배포예요. 이미 포장한 상자를 내가 직접 만들어 보내는 방식도 있는데, 이건 아래에서 비교해요.

핵심 한 줄: 본사에 레시피 폴더만 보내면, 본사가 재료와 도구까지 한 상자로 포장해 가게를 열고 주소를 붙여 준다.

다만 여기서 비유가 끊기는 점이 있어요. 식당 상자는 한 번 포장하면 끝이지만, 배포는 할 때마다 새 상자와 새 개정판(리비전)이 쌓여요. 그래서 문제가 생기면 이전 개정판으로 되돌릴 수 있어요. 이건 아래에서 다시 볼게요.

전체 흐름 — 코드 폴더가 공개 주소가 되기까지

읽는 법: 윗줄은 왼쪽에서 오른쪽으로 읽어요. ④에서 아랫줄로 내려와 ⑤ 인스턴스가 켜지고, 왼쪽으로 가서 서비스 주소가 붙어요. 점선은 일이 아니라 상태나 선택이에요. 요청이 없으면 인스턴스가 0개로 줄고, 문제가 생기면 트래픽을 이전 리비전으로 돌려요.

왜 한 묶음으로 포장할까 — 서버에는 내 컴퓨터의 환경이 없어요

내 컴퓨터에서 main.py가 도는 건 코드가 좋아서만이 아니에요. 그 컴퓨터에 파이썬이 깔려 있고, 코드가 쓰는 라이브러리도 이미 설치돼 있어서예요. 코드는 그 환경 위에서 돌고 있을 뿐이에요.

서버에는 그런 환경이 아무것도 없어요. 코드만 받으면 "어떤 파이썬으로, 어떤 라이브러리와 함께 돌려야 하는지"를 알 수 없어요. 서버마다 환경이 다르면 "내 컴퓨터에서는 되는데 서버에서는 안 된다"가 생기고요. 그래서 코드, 코드를 실행하는 파이썬(런타임9과 그 버전), 코드가 가져다 쓰는 라이브러리(의존성10)를 한 묶음으로 포장하면, 어디서 열어도 같은 환경으로 돌아요. Cloud Run은 그 묶음을 받아 그대로 실행만 해요.

이 포장이 실제로 쓰였다는 건 제 배포에서도 보여요. 제 컴퓨터의 파이썬은 3.14인데, 폴더의 .python-version 파일에는 3.13이라고 적어 뒀어요. 포장할 때 이 파일이 적용되니, 서버는 제 컴퓨터와 다른 버전으로 돌아요. 파일에 적지 않았다면 어느 버전이 쓰일지 제가 알 수 없었을 거예요.

소스 배포 (--source .)이미지 배포

이미지는 누가 만드나Google이 대신 만들어요(Cloud Build + buildpacks)내가 직접 만들어 저장소에 올려 둬요

어울리는 때코드와 라이브러리만으로 충분한 작은 서비스운영체제에 직접 설치해야 하는 프로그램이 필요할 때 등

이 글에서는 앞쪽(소스 배포)만 다뤄요. 이미지를 직접 만드는 방법은 6편 로컬에서는 되는데 서버에서만 안 되는 이유 — Dockerfile로 실행 환경 정하기에서 이어 가요. 이미지와 컨테이너라는 말이 낯설다면 도커(Docker)란 무엇인가를 먼저 보고 와도 좋아요.

단계마다 남는 흔적 — 제 배포 로그와 콘솔에서 찾을 곳

제가 연습용 앱 hello를 처음 배포했을 때 터미널에 이런 줄이 순서대로 찍혔어요. 전체는 약 2분이 걸렸어요. 배포 명령 하나가 만든 흔적을 단계별로 찾아볼 수 있어요.

로그에 찍힌 줄일어난 일콘솔에서 찾을 곳
Creating Container Repository…done이미지를 보관할 저장소 cloud-run-source-deploy를 만들었어요. 이 프로젝트에서 처음 소스 배포를 할 때만 한 번 나와요Artifact Registry › 저장소 목록
Uploading sources…done폴더의 파일을 올렸어요(터미널에서만 보여요)
Building Container…donebuildpacks가 폴더를 보고 파이썬과 라이브러리를 설치해 이미지로 만들었어요. 로그에서 가장 오래 걸린 줄이에요Cloud Build › 기록(History). 리전을 us-central1로 맞춰야 보여요

Creating Revision…done이미지와 설정을 묶어 첫 리비전(hello-00001-…)을 만들었어요Cloud Run › 서비스 › 리비전 탭
Routing traffic…done → Service URL: …들어오는 요청의 100%를 이 리비전으로 보내고 공개 주소를 발급했어요같은 화면의 리비전 탭(트래픽 칸), 인스턴스 수는 측정항목 탭, 요청 기록은 로그 탭

이 순서는 위 흐름도의 ②~⑤와 같아요. 배포가 막혔을 때 이 표가 어디서 끊겼는지 찾는 지도가 돼요. 빌드가 실패했다면 Cloud Build 기록을, 빌드는 됐는데 주소가 안 열리면 리비전과 로그 탭을 먼저 열어요.

다음은 처음 보는 말 몇 가지예요.

  • buildpacks — 폴더 안 파일을 보고 "이건 파이썬 앱이네" 하고 알아내, 파이썬과 라이브러리를 설치해 이미지로 묶는 도구예요. 그래서 파일 이름이 정확해야 해요.
  • 리비전 — 배포할 때마다 남는 버전이에요. 이미지뿐 아니라 환경변수, 요청 타임아웃, 인스턴스 수 같은 설정도 함께 기록돼요. 그래서 코드를 다시 빌드하지 않고 이전 리비전으로 되돌릴 수 있어요(롤백11).
  • 인스턴스 — 리비전을 지금 실행 중인 컨테이너예요. 요청이 많으면 늘고, 한동안 요청이 없으면 0개로 줄어 실행 요금이 나가지 않아요.
  • 콜드 스타트 — 0개였다가 첫 요청이 와서 인스턴스를 새로 켜느라 첫 응답이 늦어지는 현상이에요. 그다음 요청부터는 빨라요.

폴더에 두는 파일 네 개 — buildpacks가 읽는 것들

연습용 hello 앱은 파일 네 개로 충분해요. 이 앱을 먼저 올리는 이유는, 처음부터 큰 서비스를 올리면 실패했을 때 원인이 배포 과정인지 코드인지 가리기 어렵기 때문이에요. 네 파일 모두 폴더 바로 아래에 둬요.

실행: my-hello/main.py로 저장 — Cloud Run에서 앱이 시작될 때 이 파일을 읽어요

from fastapi import FastAPI
from fastapi.responses import HTMLResponse

app = FastAPI()

@app.get("/", response_class=HTMLResponse)
def home():
    return "<h1>안녕하세요, 첫 배포입니다</h1>"

@app.get("/health")
def health():
    return {"status": "ok"}

@app.get("/")는 "누가 주소 /를 열면 아래 함수를 실행하라"는 표시예요. /health는 서비스가 살아 있는지 알려 주는 헬스 체크12 주소예요.

실행: my-hello/requirements.txt로 저장 — buildpacks가 이 목록을 보고 라이브러리를 설치해요

fastapi>=0.115
uvicorn>=0.30

fastapi는 앱의 틀이고, uvicorn은 그 앱을 실제로 켜서 요청을 받는 서버 프로그램이에요.

실행: my-hello/Procfile로 저장 — 컨테이너가 켜질 때 이 줄의 명령으로 앱을 시작해요. 확장자 없이 대문자 P로 시작해요

web: uvicorn main:app --host 0.0.0.0 --port $PORT
부분뜻
main:appmain.py 파일 안의 app을 켜라는 뜻이에요(파일이름:앱이름). 둘 중 하나라도 바꾸면 앱을 못 찾아요
--host 0.0.0.0컨테이너 밖에서 오는 요청도 받아요. 127.0.0.1이면 컨테이너 안에서만 응답해서 바깥에서는 연결이 안 돼요
--port $PORT포트를 숫자로 고정하지 않고, Cloud Run이 환경변수 PORT로 알려 주는 번호(기본 8080)를 써요

실행: my-hello/.python-version으로 저장 — buildpacks가 이 버전의 파이썬을 준비해요

3.13

배포 전에는 Google 계정과 결제 정보(무료 체험), 프로젝트, gcloud 설치와 로그인이 필요하고, 소스 배포가 거치는 Cloud Run·Cloud Build·Artifact Registry 세 서비스의 API를 프로젝트에서 켜 둬야 해요. 먼저 내 컴퓨터에서 돌려 보고 싶다면 이렇게 해요.

실행: 로컬 터미널 — my-hello 폴더 안에서 실행하고, 끝낼 때는 Ctrl+C예요

python -m uvicorn main:app --port 8080

브라우저에서 http://localhost:8080을 열면 같은 화면이 나와요.

왜 Vercel이 아니라 Cloud Run일까 — 런타임을 누가 정하느냐

Vercel은 저장소를 연결하고 버튼을 누르면 주소가 생겨서 편해요. 화면(프론트엔드)만 있는 서비스라면 그렇게 올리면 돼요. 제가 배운 설명으로는 둘의 차이는 서버를 관리하느냐가 아니라 런타임과 의존성을 누가 정하느냐예요. 두 방식 모두 요청이 없으면 서버가 0개로 줄고, 요청이 늘면 알아서 늘려 주는 서버리스예요.

VercelCloud Run (소스·이미지 배포)
내가 올리는 것코드코드 + 런타임 + 의존성(+ 시스템 패키지)을 묶은 이미지
런타임·의존성Vercel이 준비한 범위 안에서 골라요내가 정해요(.python-version, requirements.txt)
요청 타임아웃13무료 플랜 함수는 최대 5분기본 5분, 최대 60분까지 늘릴 수 있어요
배포 과정빌드·버전·서버 수를 알아서 처리하고 과정을 보여 주지 않아요이미지·리비전·인스턴스·트래픽·로그를 하나씩 보고 다뤄요

AI 서비스에서 이 차이가 중요한 이유는 시간과 도구예요. 여러 문서를 읽고 정리하는 에이전트 작업은 5분을 넘기기 쉽고, 플랫폼이 준비해 두지 않은 프로그램이 필요할 때도 많아요. 실무에서는 프론트엔드는 Vercel에 두고 백엔드만 컨테이너로 올리는 구성도 흔해요. Cloud Run이 Vercel보다 낫다는 말이 아니에요. 대신 런타임과 의존성을 내가 정하니, 이미지에 빠진 게 있으면 원인도 내가 찾아야 해요. 이 두 서비스를 어떻게 나눠 쓰는지는 배포, 무료 호스팅, 집 컴퓨터를 서버로와 어디서 돌리고 무엇에 연결할까에서도 이어 볼 수 있어요.

AI가 대신 배포해 주는 시대에 — 왜 단계를 눈으로 볼까요

코딩 에이전트에게 "배포해 줘"라고 말하면 명령을 대신 실행해 주기도 해요. 그래도 단계를 알아야 하는 이유는, 손으로 매번 하기 위해서가 아니라 맡긴 결과를 검증하고 사고가 났을 때 원인을 찾으려면 지도가 머릿속에 있어야 해서예요.

  • 실패했을 때 원인이 어디 있는지 알아요. 키 없이 배포하면 터미널은 "컨테이너가 포트에서 시작하지 못했다"고 하는데, 진짜 원인은 앱이 시작하자마자 "키가 없다"는 오류를 남기고 스스로 꺼진 것이에요. 메시지는 결과고 원인은 앞선 로그에 있어요. 이걸 모르면 에이전트가 멀쩡한 포트 설정을 고치자고 해도 알아채지 못해요. 자세한 과정은 아래 키는 서버로 따라가지 않아요에서 봐요.
  • 위험한 지름길을 걸러요. 서비스 계정 키 파일을 만들거나 프로젝트 전체에 편집 권한을 주는 명령은 문제를 빨리 풀어 주기 때문에 에이전트가 지름길로 내놓기 쉬워요. 실행 전에 "이 명령이 무엇을 만들고, 바꾸고, 지우고, 공개하는가"를 읽는 일은 사람 몫이에요. 저도 오늘 배포 전에 "저장소가 새로 생기고 로그인 없는 공개 주소가 붙는다"를 읽고 승인했어요.
  • 에이전트에게 근거를 건네요. "안 돼요"만 말하면 에이전트는 짐작으로 고치기 시작하고 멀쩡한 곳을 바꾸기도 해요. 증상, 시각, 서비스와 리비전, 내가 찾은 로그 줄을 건네려면 그 부품이 무엇인지 알아야 해요.
  • 되돌리는 수단을 알아요. 리비전과 트래픽이 롤백 수단이에요. 모르면 문제가 생길 때 코드를 고쳐 다시 빌드할 생각만 하게 돼요.
  • 다른 곳에서도 써요. 이미지·리비전·인스턴스·트래픽·로그는 AWS나 Azure 같은 다른 클라우드에도 거의 같은 이름으로 있어요. 반대로 다 숨겨 주는 곳은 편하지만 그 과정을 보여 주지 않아요.

리비전 사이로 트래픽 나누기 — 새 버전을 일부에게만 먼저 보여 줘요

리비전은 한 번 만들면 바뀌지 않아서, 서비스에는 리비전이 여러 개 함께 남아 있어요. 요청을 어느 리비전이 받을지는 트래픽 설정이 정해요. 이 설정으로 요청을 비율로 나누는 일을 트래픽 분할14이라고 해요. 새 버전을 모두에게 한꺼번에 보여 주지 않고 일부에게만 먼저 보여 주면, 문제가 있어도 영향이 작게 끝나요.

설정만 바꿔서도 새 리비전이 생겨요

리비전은 이미지와 설정을 함께 기록한 버전이라고 했죠. 그렇다면 이미지는 그대로 두고 설정만 바꿔도 새 리비전이 생겨야 해요. 앱이 시작할 때 읽는 설정값(환경변수) 하나를 읽어서 화면의 문구와 색을 바꾸도록 만들어 두고, 이 값만 바꿔 리비전을 하나 더 만들어 봤어요.

실행: 로컬 터미널 — 다시 빌드하지 않고 설정(환경변수)만 바꿔 새 리비전을 만들어요. 서비스는 이미 배포돼 있어야 해요

gcloud run services update hello --region us-central1 --update-env-vars STAGE=second --tag second --no-traffic
부분뜻
--update-env-vars STAGE=second환경변수 STAGE의 값을 second로 바꿔요. 나머지 설정은 그대로예요
--tag second이 리비전에만 닿는 전용 주소(second---서비스주소 꼴)를 붙여요. 일반 주소와 따로 열어 볼 수 있어요
--no-traffic일반 주소의 트래픽은 이 리비전으로 보내지 않아요. 확인한 뒤에 옮기려는 거예요

결과로 has been deployed and is serving 0 percent of traffic이 찍혔어요. 로그에는 Creating Revision…done만 나오고 Building Container는 나오지 않았어요. 이미지는 그대로이고 설정만 달라진 새 리비전이 만들어진 거예요. 전용 주소로 열면 일반 주소와 다른 화면이 나와서, 같은 서비스 안에 화면이 다른 리비전 두 개를 동시에 놓고 볼 수 있었어요.

비율로 나누고, 실제로 세어 보기

실행: 로컬 터미널 — 값 전체를 큰따옴표로 감싸고, 쉼표 앞뒤에 공백을 넣지 않아요. PowerShell은 따옴표가 없으면 쉼표를 값 목록으로 읽어서 "정수가 아니다"라는 오류가 나요

gcloud run services update-traffic hello --region us-central1 --to-revisions "hello-00005-7t9=50,hello-00006-l7h=50"

이 명령은 몇 번을 실행해도 50% hello-00005-7t9, 50% hello-00006-l7h만 출력해요. 그건 설정이에요. 실제로 나뉘었는지는 주소로 요청을 여러 번 보내서 어느 화면이 나왔는지 세어 봐야 보여요. 직접 세어 봤어요.

실험설정요청 수결과
A리비전 셋에 34 · 33 · 3330번10 · 12 · 8번
B리비전 둘에 50 · 5020번11 · 9번

기대한 값(10 · 10 · 10, 10 · 10)과 정확히 같지는 않지만 가까워요. 요청마다 독립적으로 추첨하기 때문에 이 정도 차이는 자연스럽고, 요청을 늘릴수록 비율에 가까워져요. 한 번만 보내면 어느 쪽으로 갔는지만 알 뿐 비율은 알 수 없어요.

주의: 화면 하나를 여는 데에도 요청이 여러 개 들어가요. 화면 본문을 받는 요청과, 그 화면이 서버의 값을 가져오는 요청이 따로 추첨될 수 있어요. 실제로 화면은 한 리비전에서 왔는데 그 안에 보인 "응답한 리비전"은 다른 리비전의 이름인 적이 있었어요. 새 버전과 옛 버전이 화면과 값을 따로 만드는 서비스라면, 나누는 동안 이 어긋남이 생길 수 있어요.

되돌리기와 정리

하고 싶은 일명령의 모양
롤백 — 이전 리비전에 100%update-traffic 서비스 --to-revisions 리비전이름=100
복구 — 최신 리비전에 100%update-traffic 서비스 --to-latest

한 가지 더, 트래픽을 직접 지정해 두면 그 뒤에 새로 배포한 리비전은 트래픽을 자동으로 받지 않아요. 새 리비전이 0%로 만들어져서 일반 주소에는 아직 옛 화면이 나올 수 있어요. 새 버전이 맞게 올라갔는지는 전용 주소(--tag)로 먼저 확인하고, 트래픽은 따로 옮겨요.

키는 서버로 따라가지 않아요 — .env와 Secret Manager

AI 서비스는 시작할 때 LLM 키를 확인해요. 내 컴퓨터에서는 키를 .env 파일에 적어 두면 앱이 그걸 읽어서 잘 돌아가요. 그런데 이 파일은 서버로 가지 않아요. 예제 AI 친구 앱(하루친구)으로 확인한 내용을 따라가 볼게요.

키 없이 배포하면 — 같은 실패에 메시지가 둘

.env는 .gitignore와 .gcloudignore에 적혀 있어서 GitHub에도, 소스 배포 업로드에도 빠져요. 그래서 키 없이 배포하면 빌드는 되는데 마지막 단계에서 실패해요. 터미널과 로그가 말하는 내용은 달라요.

내용성격
터미널container failed to start and listen on the port … PORT=8080결과(증상)
로그LLM_API_KEY 환경변수가 없어 앱을 시작하지 않습니다원인

출력: 서비스의 로그 탭 — 직접 입력하는 게 아니라 실패한 리비전의 로그에서 읽는 줄이에요

06:41:41  Starting new instance.
06:41:46  ERROR  LLM_API_KEY 환경변수가 없어 앱을 시작하지 않습니다.
06:41:47  Container called exit(1).
06:41:47  STARTUP TCP probe failed … on port 8080. The instance was not started.

순서가 중요해요. 앱이 먼저 꺼지고, 그 결과로 포트가 안 열린 거예요. 포트 메시지만 보고 포트를 고쳤다면 같은 실패가 반복됐을 거예요. 같은 구조의 앱이 앞서 멀쩡히 올라갔다는 것도 포트 설정이 원인이 아니라는 단서예요. 이 앱은 키가 없으면 일부러 시작하자마자 꺼지게 만들었어요. 그러면 실패한 리비전은 트래픽을 받지 않으니, 키 없는 서비스가 열려서 사용자에게 오류를 돌려주는 일이 없어요.

키를 이름으로만 연결하기

서버에 키를 전달하는 곳이 Secret Manager15예요. 키 값은 이곳에 한 번 넣어 두고, 서비스에는 값이 아니라 이름만 알려 줘요.

순서한 일누가
1콘솔의 Secret Manager에서 llm-api-key라는 이름으로 시크릿을 만들고 키 값을 넣어요내가 직접. 명령이나 대화로 넣으면 키가 그 기록에 남아요
2서비스가 실행될 때 쓰는 계정(서비스 계정16)에 이 시크릿 하나만 읽을 수 있는 권한(secretAccessor)을 줘요명령 실행
3서비스의 LLM_API_KEY가 이 시크릿의 최신 버전을 가리키게 설정해요명령 실행

실행: 로컬 터미널 — 설정만 바꾸므로 다시 빌드하는 deploy 대신 update를 써요. 시크릿과 권한(1, 2번)이 먼저 있어야 해요

gcloud run services update friend-agent --region us-central1 --update-secrets LLM_API_KEY=llm-api-key:latest

연결하자 새 리비전이 만들어져 트래픽 100%를 받았고, 로그에는 STARTUP TCP probe succeeded after 1 attempt가 찍혔어요. 서비스 설정에는 키 값 대신 LLM_API_KEY → llm-api-key : latest만 남았어요.

"번거로우니 --update-env-vars LLM_API_KEY=키값으로 바로 넣자"는 유혹도 있어요. 앱은 어느 쪽이든 잘 도는데, 키가 어디에 남는지가 달라요.

환경변수에 값을 넣기시크릿을 이름으로 연결하기
넣는 것값 그 자체시크릿의 이름
서비스 설정 화면키 값이 그대로 보여요이름만 보여요
리비전 기록예전 키가 남아요이름만 남아요
명령·대화 기록명령에 키가 들어가요이름만 오가요
키를 읽을 수 있는 쪽프로젝트를 볼 수 있는 모든 사람읽기 권한을 받은 계정만

한계도 하나 있어요. 권한을 준 기본 서비스 계정은 같은 프로젝트의 다른 서비스도 함께 쓰는 계정이라, 그 서비스들도 이 시크릿을 읽을 수 있어요.

서버에서도 같은 화면, 시간은 얼마나 걸릴까

하루친구에는 한 번의 답이 어떻게 만들어졌는지 보여 주는 개발용 패널이 있어요. 같은 조건(새로 켠 서버, 첫 턴, 같은 날씨 질문, 도구 1개)으로 내 컴퓨터와 Cloud Run에서 한 번씩 쟀어요.

구간내 컴퓨터Cloud Run
도구 선택1.7초1.4초
첫 글자4.4초2.6초
답 전체4.8초2.9초
요청 전체5.7초3.8초

서버가 더 빨랐지만 각각 한 번만 쟀고, 모델이 답하는 시간은 매번 달라서 서버가 더 빠르다고 말할 수는 없어요. 도구를 둘 쓴 내 컴퓨터의 한 턴은 7.2초였어요. 요청 타임아웃을 정할 때는 여러 번 재서 느린 쪽을 기준으로 삼는 것이 안전해요.

나쁜 선택 vs 좋은 선택 — 요리사에게 가게를 열어 달라고 할 때

식당으로 치면 사장이 요리사에게 "가게 문 열어 줘"라고 맡기는 장면이에요. 아래는 상황을 가정한 예시예요.

나쁜 선택좋은 선택
"이 앱 Cloud Run에 올려 줘"라고만 맡기고, 끝났다는 메시지만 보고 넘어간다 → 에이전트가 로그인 없는 공개 접근을 켜고 저장소를 만들었는데 모르고 지나간다. 폴더 안에 비밀 파일이 있어도 알아채지 못한다. 실패하면 터미널 메시지만 보고 멀쩡한 설정을 고친다 실행 전에 "이 명령이 무엇을 만들고 공개하는지"를 설명하게 하고, 서비스 이름·리전·공개 여부를 확인한 뒤 승인한다. 끝나면 콘솔에서 빌드·이미지·리비전·로그의 흔적을 직접 찾아본다 → 무엇이 생겼는지 알고, 실패해도 원인을 로그에서 찾는다

이 글에 나온 숫자 — 배포 설정을 정할 때 다시 보는 값

배포 설정을 정할 때 다시 보게 되는 기본값과 상한을 모았어요. 제가 이 글을 쓴 2026년 10월에 배운 값이라 바뀔 수 있으니, 정할 때는 각 서비스의 공식 문서로 한 번 더 확인해요.

무엇의 숫자인가값알아 둘 것
Cloud Run 요청 타임아웃기본 5분 · 최대 60분요청 하나가 이 시간을 넘으면 연결이 끊겨요. 오래 걸리는 AI 작업은 이 값을 넉넉히 정하거나 비동기로 바꿔요
Vercel 무료 플랜 함수 요청 타임아웃최대 5분여러 문서를 읽는 에이전트 작업이 5분을 넘기면 다른 방식을 찾아요
인스턴스 하나의 동시 처리 요청 수(동시성)기본 80요청이 이보다 많아지면 인스턴스가 늘어요. 늘어나는 수에는 상한을 걸어 둘 수 있어요
인스턴스 최대 개수(설정이 없을 때)100개까지호출마다 비용이 나가는 서비스라면 처음부터 작게 제한해요. 이 설정은 다음 글에서 다뤄요
요청이 없을 때의 인스턴스0개실행 요금이 안 나가는 대신 첫 요청에서 콜드 스타트가 생겨요
Google Cloud 무료 체험가입 후 90일, 300달러 크레딧기간이 끝난 뒤 직접 유료로 전환하지 않으면 자동 결제는 되지 않지만, 만들어 둔 서비스가 멈춰요
트래픽 분할 실험(리비전 둘에 50 · 50)20번 중 11 · 9번요청마다 따로 추첨해서 정확히 반반이 되지 않아요. 한 번에 보면 알 수 없고 여러 번 세어야 비율이 보여요
예제 앱의 한 번 답(날씨 질문, 도구 1개, 첫 턴)내 컴퓨터 5.7초 · Cloud Run 3.8초각각 한 번만 쟀어요. 도구를 둘 쓴 한 턴은 7.2초였어요. 타임아웃은 느린 쪽을 기준으로 정해요
이미지 저장소의 무료 저장 공간월 0.5GB배포할 때마다 이미지가 쌓이니, 연습으로 쓴 서비스는 이미지(패키지)까지 지워요. 저장소 자체를 지우면 다른 서비스의 이미지도 사라져요

이럴 때 의심하세요 — 소스 배포가 막힐 때

배포 문제는 터미널 메시지 한 줄로 먼저 보이는데, 그 메시지가 원인을 말해 주지 않는 경우가 많아요. 아래 증상이 보이면 메시지를 고치려 들기 전에 이 자리를 열어 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "이 앱 Cloud Run에 올려 줘" — 올려진 것(저장소, 공개 접근)과 폴더 안 비밀 파일이 같이 올라가지 않았는지
  • "배포 실패했어, 고쳐 줘" — 에이전트가 로그를 읽었는지, 아니면 메시지만 보고 설정을 바꾸려는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
배포 명령이 빌드 단계에서 실패해요 Cloud Build › 기록의 빌드 로그예요. 빌드 로그는 서비스의 로그 탭이 아니라 여기에 따로 남아요 로그에서 오류 줄을 찾아 어느 파일·어느 패키지인지 봐요. requirements.txt 철자와 파일 위치(폴더 바로 아래)를 먼저 확인해요
"컨테이너가 PORT에서 시작하지 못했다"는 메시지로 끝났는데 포트 설정은 멀쩡해요 터미널이 아니라 서비스의 로그 탭(심각도 오류 필터)이에요. 앱이 시작하자마자 남기고 꺼진 오류 줄을 찾아요. 예를 들어 필요한 키가 없어 스스로 종료한 경우예요 오류 줄이 가리키는 원인(환경변수 누락 등)을 고쳐요. 에이전트에게 맡길 때는 "로그를 근거로"와 "아직 고치지 마"를 같이 말해요
서버에서 키를 못 읽어요, 또는 키 값이 서비스 설정 화면에 그대로 보여요 서비스의 리비전 상세 › 컨테이너 › 변수 및 보안 비밀(Variables & Secrets)이에요. .env는 서버로 가지 않으니 서버의 키는 따로 연결해야 해요 LLM_API_KEY 옆에 값 대신 시크릿 이름과 latest가 보이면 맞게 연결된 거예요. 값이 보이면 환경변수에 직접 넣은 거예요
트래픽을 나눠 놨는데 한 화면에서 버전이 섞여 보이거나 값이 비어 보여요 트래픽 설정(Cloud Run › 서비스 › 리비전 탭)과, 화면이 값을 가져오는 요청이 어느 리비전으로 갔는지예요 화면과 값을 따로 요청하는 구조면 요청마다 다른 리비전이 답할 수 있어요. 나누는 동안만 생기는 현상인지 보고, 전용 주소(--tag)로 리비전 하나만 먼저 열어 확인해요
배포는 성공했는데 주소를 열면 오류 화면이나 빈 화면이 나와요 Procfile의 시작 명령 줄(main:app의 파일·앱 이름, $PORT)과 서비스의 로그 탭이에요 로그에서 요청 줄의 상태 코드를 읽고, /health로 앱이 응답하는지 먼저 확인해요
내 컴퓨터에서는 되는데 서버에서만 안 돼요 requirements.txt와 .python-version이에요. 목록에 없는 라이브러리는 내 컴퓨터에 우연히 깔려 있으면 통과하고, 서버에서 처음 터져요 새 가상환경을 만들어 pip install -r requirements.txt만 하고 앱을 실행해 봐요. 거기서 안 되면 목록이 빠진 거예요
한동안 안 쓰다 열었더니 첫 응답만 느려요 Cloud Run › 서비스 › 측정항목 탭의 컨테이너 인스턴스 수 그래프예요 0에서 1로 올라오는 구간이 있으면 콜드 스타트예요. 고장이 아니고, 줄이는 방법은 요금과 맞바꾸는 설정이라 다음 글에서 다뤄요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

서비스 hello 배포가 실패했어. 실패한 리비전의 Cloud Run 로그를 읽고, 로그에 적힌 내용을 근거로 원인을 설명해 줘.
원인이라고 본 로그 줄은 시각과 함께 그대로 보여 줘. 아직 아무것도 고치지 마.

함께 보기

  • AI 기능을 서비스로 설계한다는 것 — 코딩 에이전트에게 맡기기 전에 정할 것 (1) — 이 글에서 올린 서버가 지켜야 할 설계(키 위치, 저장소, 소유자, 실패 처리)를 먼저 정하는 글이에요.
  • 도커(Docker)란 무엇인가 — 이미지와 컨테이너, 상자에 뭘 담느냐 — 이 글의 "한 묶음"인 컨테이너 이미지가 무엇인지 따로 풀어요.
  • 배포, 무료 호스팅, 집 컴퓨터를 서버로 — 올리는 곳을 고르는 선택지를 넓게 훑어요.
  • 왜 화면 뒤에 서버가 필요할까 — 서버가 있어야 하는 이유를 처음부터 풀어요.
  • .env가 안 읽혔던 네 겹의 이유 — 원격 주피터에서 API 키 넣기 (5) — 키를 환경변수로 넣을 때 막히는 곳을 봐요.
  1. Cloud Run — Google Cloud가 제공하는 서비스로, 컨테이너 이미지를 받아 실행하고 공개 주소를 붙여 줘요. ↩
  2. gcloud — 콘솔 화면에서 누르던 일을 터미널 명령으로 하게 해 주는 Google Cloud의 명령줄 도구예요. ↩
  3. 리전(region) — 서비스가 실제로 실행되는 데이터센터의 지역으로, 리전마다 요금이 달라요. ↩
  4. buildpacks — 폴더 안 파일을 보고 무엇을 설치할지 스스로 정해 이미지를 만들어 주는 도구라서, 도커 파일을 따로 쓰지 않아도 돼요. ↩
  5. 컨테이너 이미지 — 코드와 파이썬 버전, 라이브러리를 한 묶음으로 포장한 꾸러미로, 플랫폼은 이 묶음을 그대로 실행해요. 도커란 무엇인가에서 이미지와 컨테이너를 자세히 다뤘어요. ↩
  6. 리비전(revision) — 배포할 때마다 남는 버전으로, 어떤 이미지를 쓰는지와 환경변수·요청 타임아웃·인스턴스 수 같은 설정을 함께 기록해요. ↩
  7. 인스턴스 — 리비전의 이미지와 설정으로 지금 실행되면서 요청을 처리하는 컨테이너로, 요청이 없으면 0개로 줄어요. ↩
  8. 콜드 스타트(cold start) — 꺼져 있던 인스턴스를 새로 켜느라 첫 응답이 늦어지는 현상이에요. ↩
  9. 런타임(runtime) — 내 코드를 읽고 실제로 실행해 주는 프로그램으로, 파이썬 코드라면 파이썬과 그 버전을 뜻해요. ↩
  10. 의존성(dependencies) — 내 코드가 가져다 쓰는 라이브러리로, requirements.txt에 목록으로 적어요. ↩
  11. 롤백(rollback) — 새 버전에 문제가 생겼을 때 이전 버전으로 되돌리는 일이에요. ↩
  12. 헬스 체크(health check) — 서비스가 살아 있는지 확인하려고 만들어 두는 주소로, 보통 /health에서 짧은 응답을 돌려줘요. ↩
  13. 요청 타임아웃(request timeout) — 요청 하나를 처리할 수 있는 최대 시간으로, 넘으면 플랫폼이 연결을 끊어요. ↩
  14. 트래픽 분할(traffic splitting) — 들어오는 요청을 비율로 나눠 여러 리비전에 보내는 설정으로, 새 버전을 일부에게만 먼저 보여 주는 카나리 배포의 바탕이에요. ↩
  15. Secret Manager — API 키 같은 비밀 값을 암호화해 보관하고, 권한을 받은 계정만 읽게 해 주는 Google Cloud의 서비스예요. 서비스 설정에는 값이 아니라 이름만 연결해요. ↩
  16. 서비스 계정(service account) — 사람이 아니라 프로그램이 쓰는 Google Cloud 계정이에요. 서비스가 실행되는 동안 이 계정의 권한으로 다른 서비스(예: 시크릿)를 읽어요. ↩

"AI 서비스로 내놓기" 시리즈

(1) AI 기능을 서비스로 설계한다는 것 — 코딩 에이전트에게 맡기기 전에 정할 것

(2) Cloud Run에 소스를 배포한다는 것 — 코드 폴더 하나가 공개 주소가 되기까지 (이 글)

(3) 배포한 AI 서비스가 말없이 틀리는 순간 — 타임아웃, 인스턴스, 비용, 로그 (4) 코드를 머지하면 서비스가 저절로 바뀌는 길 — GitHub Actions로 자동 배포하기 (5) 합치기 전에 테스트하고 내보내기 전에 먼저 본다 — CI 테스트와 staging 환경 (6) 로컬에서는 되는데 서버에서만 안 되는 이유 — Dockerfile로 실행 환경 정하기 (7) 시험한 이미지와 내보낸 이미지가 같다는 증거 — 이미지를 한 번만 만들어 그대로 보내기 (8) 새 버전으로 바뀌는 몇 초 동안 — 로드밸런서로 무중단 배포 구성하기 (9) 배포하는 동안 사용자는 오류를 봤을까 — Cloud Run으로 무중단 배포하기 (10) 아홉 개 노드를 한 번에 — AI 서비스를 프로덕션에 올리기까지 돌아보기 (11) 발표용 한 장 요약 — 코드를 사용자에게 내보내는 아홉 날을 다섯 장으로
