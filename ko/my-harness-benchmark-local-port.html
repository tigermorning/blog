벤치마크란 정해진 문제와 실행 조건, 그리고 남이 정한 평가 기준으로 시스템의 동작을 비교하는 방법이다.

지금까지는 제가 만든 실습 자료로 하네스를 확인했어요. 회의록도 제가 썼고, 기대 결과도 제가 정했죠. 이번에는 다른 사람이 정한 작업과 채점 기준에 연결합니다. 제 프로그램이 낯선 파일을 읽고, 코드를 쓰고, 결과를 확인하며 작업을 끝낼 수 있는지 보는 거예요.

비유 — 학교 운동장에서 잰 기록

학교에서 체력 측정을 한다고 해 볼게요. 종목은 제가 고르는 게 아니에요. 팔굽혀펴기, 오래달리기, 유연성처럼 이미 정해져 있고, 몇 개를 몇 초에 해야 몇 등급인지도 남이 만든 표에 적혀 있어요.

여기서 두 가지가 갈려요. 종목과 채점표는 공식 그대로예요. 그런데 재는 장소는 학교 운동장이에요. 공식 경기장의 우레탄 트랙이 아니라 흙바닥이고, 그날 바람도 불었고, 신발도 제 운동화죠.

그래서 결과를 이렇게 적어야 해요. "공식 종목·공식 채점표로, 우리 학교 운동장에서 잰 기록"이요. 이걸 "공식 기록"이라고 적으면 거짓말이 되고, 그렇다고 "우리끼리 만든 놀이"라고 적으면 종목과 채점표가 공식이라는 사실을 버리는 거예요.

그리고 채점하는 사람도 따로 있어요. 체육 선생님이 "잘했어!"라고 말한 건 기록이 아니에요. 스톱워치에 찍힌 숫자가 기록이죠. 뛴 사람과 잰 사람이 다르다는 것, 이게 채점의 핵심이에요.

핵심 한 줄: 종목과 채점표는 남의 것을 그대로 쓰되, 잰 곳이 학교 운동장이라는 사실도 기록에 같이 적어요.

다만 비유가 끊기는 점이 있어요. 체력 측정은 종목을 다 통과하는 게 목표지만, 이 과제는 열 문제를 다 통과하는 게 완료 조건이 아니에요. 통과 못 한 문제의 실패 기록을 읽고 한 군데를 고쳐 다시 재는 것이 과제예요.

그리고 easy라고 해서 작은 모델이 반드시 푼다는 뜻이 아니에요. 난도는 원본 메타데이터의 분류일 뿐, 이 로컬 환경에서 새로 측정한 난도가 아니에요.

Docker 없이 돌리는 구조

기본 실습에는 Docker가 필요하지 않아요. 압축을 푼 프로젝트에서 Python으로 문제 파일을 준비하고, 문제마다 새 작업 폴더를 만들어 실행합니다. 실행 코드는 제 컴퓨터에서 동작해요.

원본 문제는 컨테이너 안의 /app, /protected 같은 절대 경로를 써요. 로컬 실행에서는 이 경로를 각 시행의 workspace/app, workspace/protected 등으로 바꿔요. 문제의 입력 자료·요구사항·원본 Python 채점 코드는 그대로 쓰되 경로와 Python 실행 파일 선택만 로컬에 맞추는 것 — 이게 이식(port)이에요. 풀이를 단순한 함수 문제로 바꾼 게 아닙니다.

예외가 하나 있어요. 자격정보 복구 문제의 원본 이미지에 들어 있던 정답 목록은 평가자 전용 캐시에 두고 모델 작업 폴더에는 복사하지 않아요. 채점기는 같은 원본 정답 목록을 쓰고, 이 노출 보정도 manifest의 변경 기록에 남깁니다.

읽는 법: 아래 그림에서 왼쪽 캐시는 건드리지 않는 원본이고, 가운데는 시행마다 새로 만드는 작업 폴더예요. 오른쪽 채점은 에이전트가 끝난 뒤에 별도로 돌아요.

세 역할이 나뉘어 있다는 게 핵심이에요. Agent는 다음 행동을 결정하고, 도구는 파일을 읽거나 Python 코드를 실행하고, verifier는 결과를 검사해요. 모델이 "완료했습니다"라고 말했는지가 아니라 원본의 검사 조건을 충족했는지를 봅니다.

파일별로는 7편에서 본 그대로예요 — benchmark_source.py가 고정 원본을 준비하고, local_agent.py가 같은 Agent 반복을 평가용 도구에 연결하고, grading.py가 원본 tests/test_outputs.py를 실행해요. 바둑 문제의 원본 검사에서 부르는 mypy와 flake8(각각 타입과 코드 형식을 검사하는 도구예요)도 잠금 파일에 포함돼요.

여기서 한 번 더 못 박아 둘게요. 원본 검사 자체가 모든 요구를 엄격하게 판정하는 건 아니에요. 통과 점수를 제품 품질 전체의 증명으로 해석하지 않습니다.

7편에서 쓰던 harness-lab 폴더를 그대로 씁니다. pyproject.toml과 run.py가 보이는 위치예요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

README를 보고 로컬 벤치마크를 준비해 줘. 실제 문제 10개와 난도가 맞는지 확인하고, 실행 전 설정을 보여 줘.

문제는 내려받은 원본을 보관하는 캐시와 실제로 풀 작업 폴더로 나뉘어요. 시행마다 입력 파일을 새로 복사하니 직전 문제의 수정 결과가 다음 문제로 넘어가지 않아요.

다만 작업 폴더를 나눴다고 운영체제 수준의 격리가 생긴 건 아니에요. 실행한 Python은 제 계정 권한으로 돌아요. 그래서 실습용 자료와 코드만 쓰고, 제 컴퓨터의 민감한 자료를 평가 작업에 섞지 않습니다. 원본 풀이와 채점 파일은 모델 작업 폴더에 주지 않지만, 이 로컬 방식이 악의적인 코드의 접근까지 막는 보안 샌드박스는 아니에요.

첫 기준 실행 — baseline

Baseline6은 개선 전 비교 기준이에요. 기본 실행은 고정 열 문제를 한 번씩 순서대로 시도해요. 첫 점수가 낮아도 괜찮아요 — 실패 기록이라는 읽을 재료가 생기니까요.

실행 전에 모델과 단계·시간 한도를 정하고, 기준 실행과 개선 실행에 똑같이 적용합니다.

현재 하네스로 고정 10문제를 baseline으로 실행해 줘. 점수 화면도 열고, 실패와 실행 오류를 따로 남겨 줘.

실행할 때 하네스는 당시의 소스를 별도 사본에 저장하고 그 사본으로 실행해요. 기준 실행 도중에 작업 중인 소스를 고쳐도 그 실행에 새 코드가 섞이지 않게 하려는 거예요. 그리고 run-metadata.json에 문제 버전, 코드와 manifest 해시, 모델, 실행 한도, 운영체제와 Python 버전 등이 남아요.

다만 로컬 실행은 원본 컨테이너의 CPU·메모리 제한을 강제하지 않아요. 이 차이도 조건에 포함해 기록합니다.

나쁜 선택 vs 좋은 선택

같은 체력 측정에서, 결과를 제출하는 두 가지 방식이에요.

나쁜 선택좋은 선택
무엇을 했나: 제 하네스를 만들긴 했는데, 평가는 기본 명령이 실행하는 제공 Python 구현으로 돌렸어요. 명령 한 줄이면 됐고 점수도 잘 나왔거든요. 그 점수를 제 구현의 점수로 제출했어요.

무슨 일이 생기나: 보고서의 숫자가 제 코드와 아무 관계가 없어요. 개선 실험도 성립하지 않아요 — 제가 고친 곳이 그 점수에 반영될 리가 없으니까요. 그리고 이건 실수라기보다 측정 대상 자체를 바꿔치기한 것이에요.		 무엇을 했나: 평가기가 제 하네스를 호출하도록 연결부를 바꿨어요. 문제 설명과 작업 폴더를 전달하고, 종료 상태와 사용량을 돌려받게요.

무슨 일이 생기나: 점수가 낮게 나올 수 있어요. 대신 그 숫자가 제 코드의 숫자예요. 실패 기록도 제 하네스의 기록이라 다음 편의 개선 가설로 곧장 이어집니다.

평가기가 내 하네스를 실행하도록 연결해 줘. 문제 설명과 작업 폴더를 전달하고, 종료 상태와 사용량을 돌려주게 해 줘.

이 점수를 뭐라고 부를까

결과 이름을 정확히 붙이는 게 이번 편의 마지막 일이에요. 이건 Terminal-Bench Pro 고정 10문항의 로컬 이식판 결과예요.

  • 난도는 실제 벤치마크의 표기가 맞아요.
  • 문제와 채점 코드도 고정된 원본이 맞고요.
  • 다만 실행 환경이 다르므로 공식 컨테이너 점수나 전체 순위와 직접 비교할 수 없어요.

더 다양한 시스템 도구가 필요한 문제를 다루거나, 여러 사람의 실행 환경을 더 일관되게 맞추고 싶다면 Docker를 쓸 수 있어요. 이번 과제에서는 설치나 사용을 요구하지 않습니다.

그리고 이 태도는 이 블로그가 계속 지켜 온 것이기도 해요 — 결과와 궤적을 함께 본다 — 평가 루프와 일곱 하네스 비교 (5)에서 남의 하네스 점수를 읽을 때 썼던 그 기준을, 이번엔 제 점수에 적용하는 거예요.

직접 해보기

  1. 바꿀 것 — 평가기 연결부를 제 하네스로 바꾸고, 고정 10문항을 한 번씩 baseline이라는 이름으로 실행해요.
  2. 측정할 것 — 결과에서 통과·실패·실행 오류·미완료를 각각 몇 개인지 세요. 넷을 뭉뚱그리지 않는 게 중요해요.
  3. 비교할 것 — run-metadata.json에 모델·한도·문제 커밋·코드 해시가 남았는지 확인해요. 이게 없으면 다음 편의 비교 실험이 성립하지 않아요.

첫 실행과 개선 실행 모두 같은 열 문제를 시도한 기록을 남깁니다. 성공한 문제만 모으거나 실패한 문제를 쉬운 문제로 바꾸지 않아요. 다음 편에서는 아직 끝나지 않은 문제까지 포함해 점수를 읽고, 변경 한 가지가 어떤 결과로 이어졌는지 비교합니다.

함께 읽으면 좋은 글

  • 결과와 궤적을 함께 본다 — 평가 루프와 일곱 하네스 비교 (5) — 남의 하네스 점수를 읽는 기준이에요.
  • 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정 (4) — 자기 실험을 채점하는 두 층 구조요.
  • 내 불편을 가설로 — 개선 실험 설계와 제출 (6) — 다음 편으로 이어지는 실험 설계 감각이요.
  1. 검증기(verifier) — 에이전트가 만든 산출물을 에이전트와 무관하게 별도로 검사해 통과 여부를 판정하는 채점 프로그램이에요. ↩
  2. Docker — 프로그램과 그 실행 환경을 하나로 묶어 어디서든 같은 조건으로 실행하게 해 주는 도구로, 이번 기본 실습에서는 쓰지 않아요. ↩
  3. 이식(port) — 원본의 입력 자료·요구사항·채점 코드는 그대로 두고 경로와 실행 환경만 다른 곳에 맞춰 옮기는 작업이에요. ↩
  4. 시행(trial) — 한 문제를 새 작업 상태에서 한 번 풀고 채점하는 단위예요. ↩
  5. Manifest — 실험에 쓸 문제와 조건(저장소·커밋·문제 이름·난도·파일 해시)을 적어 둔 목록이에요. ↩
  6. Baseline — 개선 전후를 비교하기 위해 먼저 재 두는 기준 실행이에요. ↩
