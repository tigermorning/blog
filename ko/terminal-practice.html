안전한 연습 폴더에서 시작하기

실습에 들어가기 전에 안전 규칙부터 정하고 시작했어요 — 삭제 명령은 실제 파일이 아니라 연습 폴더 안에서만 씁니다. 바탕화면의 진짜 파일 대신, 이번에 새로 만들 terminal-practice라는 연습 전용 폴더 안에서만 손을 대는 거예요.

이 규칙이 왜 필요한지는 3편의 실수를 떠올리면 바로 이해가 돼요. 그때 저는 ~를 몰라서 폴더를 엉뚱한 곳에 만들었는데, 그건 폴더가 하나 잘못 생긴 것뿐이라 지우면 그만이었어요. 그런데 똑같은 착각을 삭제 명령에서 하면요? 터미널에는 휴지통이 없어서 되돌릴 수가 없어요. 그러니까 위치를 확실히 읽을 줄 알게 되기 전까지는, 실수해도 아무것도 잃지 않는 방에서만 연습하는 게 맞았어요. (이름에 공백이 들어가면 따옴표로 감싸는 것도 같은 이유예요. 안 감싸면 컴퓨터가 한 이름을 두 개로 잘라 읽거든요.)

오늘 쓸 명령어는 이 일곱 개예요.

명령하는 일
pwd지금 내가 있는 폴더의 전체 경로를 출력합니다.
ls현재 폴더 안의 파일·폴더 이름을 보여줍니다.
cd 폴더이름지정한 폴더로 이동합니다. cd ..는 한 단계 위로 갑니다.
mkdir 폴더이름새 폴더를 만듭니다.
New-Item 파일이름빈 파일을 만듭니다. (별명 ni)
rm 파일이름기존 파일을 삭제합니다. (오늘 실습에서는 쓰지 않아요)
mv 원본 대상파일·폴더를 이동하거나 이름을 바꿉니다. 실행 전 원본과 대상을 꼭 다시 읽어요.

수업 자료의 원래 명령어는 touch였는데, 3편에서 이미 겪었듯 PowerShell에는 touch가 없어서 New-Item(별명 ni)을 써요. 다행히 pwd, ls, cd, mkdir, mv, rm은 PowerShell에서도 이름이 그대로 통해요. 폴더 여러 개를 한 번에 만들 때는 mkdir ideas, assets, archive처럼 쉼표로 구분해요.

1~2단계 — 연습 공간을 만들고 파일을 옮겨보기

가장 먼저 할 일은 폴더를 만드는 게 아니라 지금 내가 어디 서 있는지 확인하는 것이에요. 3편에서 이 단계를 건너뛰었다가 폴더가 엉뚱한 데 생겼으니까요. 위치를 확인하고, 거기가 맞으면 그때 연습 폴더를 만들어요.

실행: 로컬 터미널

pwd
ls
mkdir terminal-practice
cd terminal-practice
mkdir ideas, assets, archive
ls

pwd 출력에서 지금 내 위치를 노트에 적어두고, ls로 ideas, assets, archive 세 폴더가 보이는지 확인해요. 이미 같은 이름의 폴더가 있다는 에러가 나오면, 지우지 말고 그냥 ls로 확인한 뒤 다음 단계로 넘어가면 돼요.

빈 방 세 개를 만들었으니, 이번엔 그 안에 실제로 뭔가를 넣고 옮겨볼 차례예요. 폴더를 만드는 것보다 옮기는 것이 한 단계 더 조심스러운 일이라서 여기서 연습해두는 게 중요해요. 만들기는 잘못돼도 새 폴더가 하나 생길 뿐이지만, 옮기기는 원래 있던 자리에서 파일이 사라지는 일이거든요.

실행: 로컬 터미널

ni ideas/landing-page.txt
mkdir assets/images
mv ideas/landing-page.txt assets/images/landing-page.txt
ls assets/images
cd ..
pwd

빈 메모 파일을 하나 만든 뒤 이미지 폴더로 옮겨봤어요. mv 다음의 ls assets/images 출력에 landing-page.txt가 실제로 보일 때만 성공이에요. 명령을 쳤다는 사실이 아니라, 그 다음 출력으로 확인하는 것이 중요해요 — 이건 4편에서 다뤘던 "판단" 단계와 똑같은 습관이에요.

3단계 — 길을 잃었을 때 돌아오기, 그리고 명령어의 정체

2단계를 하면서 실제로 불편한 게 하나 생겼어요. cd로 폴더를 몇 번 들어갔다 나왔더니, 지금 제가 어느 층에 있는지 헷갈리기 시작한 거예요. 화면에는 마지막 명령의 결과만 남아 있어서 눈으로는 알 수가 없었어요. 그래서 3단계는 일부러 깊이 들어갔다가 되돌아 나오는 연습이에요.

실행: 로컬 터미널

cd terminal-practice
cd assets
pwd
cd ..
ls

cd ..는 "한 단계 위 폴더로 가라"는 명령이에요. 화면에 스쳐 지나가는 이름만 믿지 말고, 이동할 때마다 pwd와 ls를 번갈아 확인하는 습관을 들이면 좋아요. 지금 위치가 불안하면 일단 pwd부터 실행하고, mv는 원본·대상 경로를 한 글자씩 눈으로 확인한 뒤에 실행해요. 실제로 중요한 파일에는 이 연습이 끝난 뒤에나 적용해요.

실습을 하다가 걸리는 게 하나 있었어요. touch는 PowerShell에서 안 통했는데, 왜 pwd랑 ls는 똑같은 유닉스 명령어인데도 멀쩡히 통했을까요? 이상해서 찾아봤더니 답이 나왔어요.

5편에서 Get-Location이 PowerShell의 내장 cmdlet(커맨드릿, PowerShell에 처음부터 들어 있는 진짜 명령어)이라는 걸 다뤘는데, 사실 오늘 쓴 pwd, ls, cd, mkdir, mv, rm은 하나도 진짜 이름이 아니었어요. 전부 그 cmdlet들에 붙여둔 별명(alias)이었어요. PowerShell을 만든 쪽에서 유닉스에 익숙한 사람들이 헤매지 않도록 미리 짧은 이름을 달아둔 거예요.

  • pwd → Get-Location
  • ls → Get-ChildItem
  • cd → Set-Location
  • mkdir → New-Item(폴더 만들기)
  • mv → Move-Item
  • rm → Remove-Item

이걸 직접 확인해볼 수도 있어요. 5편에서 node가 어디 있는지 찾을 때 썼던 Get-Command를 여기에 그대로 쓰면 돼요. Get-Command ls를 입력하면 "Alias, ls -> Get-ChildItem"처럼 별명과 진짜 이름이 한 줄에 나와요. touch가 안 통했던 이유도 이걸로 설명이 되더라고요 — 그건 별명 목록에 아예 없는 이름이었던 거예요. 없는 이름이라 못 알아들은 것뿐이지, PowerShell이 빈 파일을 못 만드는 게 아니었고요.

오늘 손에 남은 것

새 개념은 거의 없는 시간이었는데도, 손으로 반복하고 나니 읽어서 아는 것과 다른 게 두 가지 남았어요.

하나는 순서예요. 3편에서는 명령을 먼저 치고 결과가 이상해서 뒤늦게 pwd를 봤어요. 오늘은 반대로 했어요 — 움직이기 전에 pwd, 옮기고 나서 ls. 명령어 목록을 외운 것보다, 위험한 명령 앞뒤를 확인으로 감싸는 이 순서가 실제로 손에 남은 것 같아요.

다른 하나는 이름은 껍데기일 수 있다는 감각이에요. 제가 ls라고 친 것이 사실은 Get-ChildItem이었다는 걸 알고 나니, 명령어가 안 통할 때 "이 컴퓨터는 안 되나 보다"라고 포기하는 대신 "이 환경에서는 이걸 뭐라고 부르지?"를 먼저 묻게 됐어요. 3편의 touch도, 오늘의 ls도 결국 같은 이야기였어요.

이럴 때 의심하세요 — 폴더를 옮기고 지우는 명령 앞뒤에서

이 편의 실수는 대부분 에러 없이 지나가요. 명령이 멀쩡히 끝났는데 파일이 엉뚱한 데 가 있거나, 지우고 나서야 위치가 틀린 걸 알게 되죠. 그래서 증상을 기다리기보다, 명령이 끝난 직후의 출력과 명령을 치기 직전의 경로를 봐야 해요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
파일 정리를 맡겼더니 AI가 rm·Remove-Item·del이 든 명령을 실행해도 되냐고 물어요. 문서에서 복사해 온 줄에 이런 명령이 들어 있을 때도 같은 순간이에요 명령 뒤에 붙은 경로와 옵션이에요. -Recurse나 -rf는 폴더 안의 것까지 전부, -Force는 숨김·읽기 전용 파일까지 지워요. 경로가 .이나 *, 폴더 이름 하나뿐이면 "지금 서 있는 곳" 기준이에요 허락하기 전에 거절하고 "작업 폴더 경로와 이 명령으로 지워질 파일 목록부터 보여 줘"라고 해요. 직접 칠 때는 pwd와 ls 경로로 같은 걸 봐요. 터미널에서 지운 건 휴지통에 안 가서, 허락한 뒤에는 확인할 기회가 없어요
mv가 에러 없이 끝났는데 옮긴 폴더 안에 파일이 없어요. 대신 대상 폴더 이름을 단 확장자 없는 파일이 하나 생겼어요 mv 줄의 대상 경로 철자예요. 대상으로 적은 폴더가 실제로 없으면, 옮기기가 아니라 이름 바꾸기로 처리돼요 옮긴 폴더에 ls를 쳐서 파일 이름이 보이는지 봐요. 안 보이면 그 한 칸 위에서 ls로 낯선 파일을 찾아 mv 낯선이름 원래이름.txt로 되돌린 뒤, 폴더 철자를 고쳐 다시 옮겨요
책이나 AI가 알려 준 touch, which 같은 명령이 인식할 수 없다는 빨간 에러로 끝나요. 따로 설치하는 프로그램도 아닌데요 컴퓨터가 아니라 이 환경에서 그 일을 부르는 이름이에요. 에러 난 이름으로 Get-Command 이름을 쳐서 PowerShell이 아는 이름인지 봐요 못 찾으면 없는 이름이라, 하려는 일을 적어 AI에게 "Windows PowerShell에서는 이걸 뭐라고 불러?"라고 물어요. 이름이 아니라 문법이 달라서 막히는 경우는 5편의 이 줄에 있어요
cd나 mkdir에 공백이 든 이름을 줬더니, 이름 뒷부분 낱말을 받아 줄 매개 변수를 찾을 수 없다는 에러가 나요 명령 줄에서 공백이 들어간 이름이에요. 에러에 찍힌 낱말이 이름의 뒷부분(예: my project의 project)이면 그거예요 이름 전체를 따옴표로 감싸 다시 쳐요(예: cd "my project"). bash 같은 다른 셸에서는 에러 없이 my와 project 두 폴더가 따로 생기기도 하니, 만든 뒤 ls로 한 번 더 봐요

첫째 줄만은 뒤늦게 알아채면 늦어요. 나머지는 ls로 찾아 되돌릴 수 있지만, 지운 파일은 되돌릴 자리가 없으니 허락하기 직전이 확인할 유일한 때예요. 파일 정리를 AI에게 맡길 때 실제로 옮기기 전에 계획부터 받는 방법은 다음 편에 있어요.

참고한 자료: 실습 절차와 안전 규칙(연습 폴더 사용, 삭제 명령 자제)은 오늘 수업 자료를 바탕으로 정리했어요. PowerShell 별명(alias) 대응 관계는 수업 자료에는 없는 내용이라, 제 윈도우 환경에 맞춰 AI와 함께 직접 확인한 것이에요. 다음 실습(7편)에서는 이 폴더 정리를 Claude Code에게 맡기고, 결과를 검토하는 방법을 다뤄볼게요.
