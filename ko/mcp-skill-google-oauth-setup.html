OAuth 준비란 비밀번호를 프로그램에 넘기는 대신 "이 앱이 내 표를 읽는 것까지만 허용한다"고 내가 Google 화면에서 직접 눌러 줄 수 있도록, 앱과 허용 범위를 미리 등록해 두는 일이다.

어디쯤인가
6단계 › MCP와 Skill로 업무 맡기기 — 11번째 글 (전 14편). 중간부터 보셨다면 첫 글부터 보시는 게 편해요.
뭐를 할 수 있나
Google Cloud Console에서 프로젝트를 만들고 Sheets API를 켜고 동의 화면과 읽기 전용 범위를 설정해, credentials.json 파일 하나를 손에 쥘 수 있게 돼요. 실제 로그인과 표 읽기는 다음 편 몫이에요.
왜 배우나
브라우저에 로그인해 있다는 사실이 새로 만든 프로그램에게 자동으로 접근 권한을 넘겨주지 않는다는 걸 모르면, 왜 코드가 표를 못 읽는지 원인을 못 찾고 헤매게 돼요.
왜 중요한가
준비 단계에서 scope를 필요 이상으로 넓게 잡거나 credentials.json을 저장소에 커밋하면, 실수로 표를 고칠 권한까지 열리거나 인증 정보가 새어 나가는 실제 사고로 이어져요.
어디에 쓰나
팀 업무 기록을 Google 스프레드시트에서 읽는 MCP 도구를 만들 때 · 개인 계정으로 실습용 프로젝트를 등록할 때 · Desktop app과 Web application 중 맞는 클라이언트 종류를 고를 때 · 인증 파일을 대화창에 노출하지 않고 안전하게 다룰 때

10편 끝에서 이런 예고를 했어요. Colab에 로그인해 있다는 사실이 다른 앱의 접근 동의까지 대신해 주지는 않는다고요. 이번 편이 바로 그 이야기예요.

상황은 이렇습니다. 팀이 주간 기록을 Google 스프레드시트에 모으기 시작했어요. 저는 브라우저에서 그 표를 잘 보고 있고요. 그런데 Python 프로그램에서 같은 표를 읽으려고 하면 아무것도 안 돼요. 브라우저에 로그인한 사실이 방금 새로 실행한 프로그램에게 자동으로 전달되지는 않기 때문이에요. 프로그램은 Google에게 어떤 앱이 · 어느 사용자의 동의를 받아 · 어떤 작업을 하려는지 스스로 밝혀야 합니다.

여기서 말하는 Google Docs·Sheets·Drive·Gmail·Calendar를 묶어 Google Workspace1라고 불러요. 문서·표·파일·메일·일정 서비스 묶음이에요. 그리고 미리 하나 짚어 둘게요 — 8편에서 만든 SKILL.md 같은 Skill 문서를 쓰는 것 자체에는 인증이 전혀 필요 없어요. 인증이 필요해지는 건 그 Skill이 부르는 MCP 서버나 스크립트가 Google API를 실제로 호출할 때예요.

참고로 이번 인증 경로는 10편의 Colab MCP와는 완전히 별개예요. Colab이 연결돼 있다고 이게 따라오지 않고, 반대도 마찬가지예요.

비유 하나 — 회사 로비의 방문증 데스크

어느 회사 건물을 그려 볼게요. 저는 사원증이 있어서 게이트를 통과해 3층 사무실에 앉아 있어요. 그런데 오늘 외부 업체 기사 한 명이 와서, 3층 캐비닛에 있는 서류 한 부를 복사만 해 가야 해요.

제가 안에 있다고 해서 그 기사가 저절로 들어오지는 않죠. 순서가 있어요. 먼저 어느 업체 소속인지가 로비 데스크에 등록돼 있어야 하고, "3층 서류 열람만, 촬영·반출은 안 됨"이라고 적힌 신청서가 있어야 하고, 마지막으로 제가 데스크 앞에서 "네, 이 기사에게 그것만 허용합니다"라고 직접 확인해야 방문증이 나와요. 그 방문증에는 유효 시간이 있고, 시간이 지나면 재발급 티켓을 내밀어 새 방문증을 받아요.

비유 속 요소원래 개념
내 사원증으로 이미 건물 안에 있는 상태브라우저에 Google 계정으로 로그인해 있는 상태
서류를 복사해 가야 하는 외부 업체 기사내 컴퓨터에서 새로 실행한 프로그램 — 아직 아무 자격이 없어요
데스크에 등록된 업체 정보OAuth 클라이언트 — 다운로드하면 credentials.json
업체마다 붙는 등록 번호클라이언트 ID — "어떤 앱인가"를 나타내는 값
신청서에 적힌 "3층 서류 열람만"scope(범위) — 허용할 작업의 종류
제가 데스크에서 직접 확인하는 순간Google 동의 화면 — 사용자가 직접 허용을 누르는 자리
발급된 방문증(유효 시간 있음)접근 토큰 — API를 부를 때 붙이는 값
시간이 지나면 쓰는 재발급 티켓갱신 토큰 — 새 접근 토큰을 받아 오는 값
방문증을 넣어 둔 기사의 주머니token.json — 내 컴퓨터에 저장되는 파일
아직 시범 운영이라 명단에 적힌 사람만 받는 데스크Testing 상태 + Test users 등록
애초에 내가 열쇠를 못 받은 캐비닛나에게 공유되지 않은 다른 사람의 표

핵심 한 줄: 로그인은 "내가 누구인가"를 밝히는 일이고, OAuth는 "이 프로그램이 내 것 중 무엇까지 만져도 되는가"를 따로 정하는 일이에요 — 그래서 로그인해 있어도 준비 절차가 통째로 한 번 더 필요해요.

다만 여기서 비유가 끊기는 점이 하나 있어요. 진짜 로비 데스크는 등록 안 된 업체가 와도 사람이 보고 융통성을 발휘할 수 있죠. 그런데 Google 쪽은 앱이 미리 등록돼 있지 않으면 데스크 자체가 열리지 않아요. 그래서 이번 편은 "먼저 데스크를 만드는 일"만 하고, 실제로 기사가 방문증을 받으러 가는 건 다음 편이에요.

말부터 정리 — 인증 정보와 토큰은 어떻게 다른가

절차에 들어가기 전에 이번 편에 계속 나올 말 여섯 개를 한 표에 모아 둘게요. 지금 다 외울 필요는 없고, 아래에서 헷갈릴 때 여기로 돌아오면 돼요.

말한 줄로방문증 비유에서는
credential2 (인증 정보)앱이나 사용자를 식별·인증하는 데 쓰는 정보를 통틀어 부르는 말데스크에서 오가는 증빙 서류 전부
OAuth3비밀번호를 도구에 넘기는 대신, Google 화면에서 허용할 접근을 내가 고르는 절차데스크 앞에서 내가 직접 확인하는 방식 자체
클라이언트 ID4"어떤 앱인가"를 나타내는 값업체 등록 번호
접근 토큰5 (access token)동의한 범위 안에서 API를 호출할 때 붙이는 값방문증 — 유효 시간이 있어요
갱신 토큰6 (refresh token)새 접근 토큰을 받는 데 쓰일 수 있는 값재발급 티켓
scope7 (범위)'표 읽기', '일정 읽기'처럼 허용할 작업의 범위신청서에 적힌 "3층 서류 열람만"

제일 자주 헷갈리는 건 클라이언트 ID와 토큰의 차이예요. 클라이언트 ID는 앱에 붙는 이름표라 사용자가 누구든 그대로고, 토큰은 특정 사용자가 동의한 결과라서 사람마다·기기마다 달라요. 이 구분이 이따 credentials.json과 token.json을 가르는 기준이 됩니다.

전체 흐름 그림 — 이번 편은 위 절반까지

준비부터 실제 호출까지 한 장에 그렸어요. 이번 편에서 하는 건 위쪽 다섯 칸이고, 아래쪽은 다음 편에서 할 일이에요. 지금 아래쪽까지 같이 보여 주는 이유는, "지금 밟는 이 단계가 나중에 어디에 쓰이는지"를 알고 하면 헷갈릴 일이 확 줄어들기 때문이에요.

읽는 법: 가로 화살표는 순서예요 — 앞 칸을 건너뛰면 뒤 칸에서 막혀요. 위아래를 가르는 점선이 이번 편과 다음 편의 경계고, 그 사이에 낀 결과물 상자가 두 편을 잇는 유일한 물건이에요. 즉 이번 편의 목표는 딱 하나 — credentials.json 파일 하나를 손에 쥐는 것이에요.

그림에서 눈여겨볼 건, 동의(⑧)가 맨 아래에 있다는 점이에요. 위쪽 다섯 칸을 다 밟아도 내 표에 대한 접근 허가는 아직 하나도 나오지 않았어요. 준비와 동의는 끝까지 별개의 일입니다.

그 전에 갈림길 하나 — 인증 방식 세 갈래

Google 쪽 인증을 검색하면 서비스 계정이니 API 키니 하는 말이 같이 나와서 처음엔 뭘 골라야 할지 막막해요. 하려는 일에 따라 출발점이 다릅니다.

하려는 일인증 방식이번 실습에서는주의할 점
내가 로그인해 내 자료를 다루기사용자 동의를 받는 OAuth 클라이언트✅ 이걸 씁니다사람이 브라우저에서 한 번은 직접 허용해야 해요
프로그램 전용 계정에 공유한 자료 다루기서비스 계정8이번엔 안 씀공유한 파일 등의 접근 범위를 따로 설정해야 해요
지원되는 공개 데이터 조회API 키9이번엔 안 씀API 키를 지원하는 API인지 먼저 확인해야 해요

핵심: API 키 하나로 내 Gmail이나 비공개 문서 전체에 접근할 수 있는 건 아니에요. API 키는 "누구든 볼 수 있는 자료를 부를 때 쓰는 표"에 가깝고, 내 개인 자료에는 내 동의가 따로 필요해요. 프록시 서버 글에서 API 키를 코드에 그대로 두면 안 된다고 했던 그 API 키가 바로 이 API 키예요.

서비스 계정은 이름에 '계정'이 들어가지만 사람이 로그인하는 개인 계정과는 다른 물건이에요. 예를 들어 매일 자동으로 도는 서버에 전용 계정을 하나 마련해 두고, 그 계정에 연습용 표를 공유해 주는 구성이 가능해요. 사람이 매번 브라우저에서 허용을 눌러 줄 수 없는 상황에 맞는 방식이죠. 다만 이번 편에서는 내 계정으로 로그인하는 사용자 OAuth 한 가지만 실제로 구현합니다.

이번 실습의 조합을 한 줄로 못박아 둘게요 — 개인 Google 계정 · 별도의 실습 프로젝트 · Google Sheets API · Desktop app · spreadsheets.readonly. 회사 계정이 없어도 개인 Gmail 계정으로 이 API를 쓸 수 있어요.

① 실습 프로젝트 만들기

Google Cloud Console에 들어가면 먼저 화면 오른쪽 위의 계정부터 확인하세요. 브라우저에 계정을 여러 개 로그인해 뒀다면 엉뚱한 계정으로 프로젝트를 만들게 되고, 나중에 로그인 단계에서 계정이 안 맞아 막혀요.

Cloud 프로젝트11는 API 설정과 앱 인증 정보를 묶어 관리하는 단위예요. 폴더 하나라고 생각하면 편해요. 이 안에 "어떤 API를 켰는지", "어떤 앱을 등록했는지"가 함께 들어갑니다.

프로젝트 생성 화면에서 Project name에 목적이 드러나는 이름을 적어요 — 예를 들어 Workspace OAuth Practice처럼요. 그리고 Create.

화면에서 확인할 것: 생성이 끝나면 상단 프로젝트 선택기에 방금 만든 이름이 표시돼요. 여기가 다른 이름으로 돼 있으면 이후 설정이 전혀 다른 프로젝트에 들어가니, 다음으로 넘어가기 전에 꼭 맞춰 두세요.

② 표 API 켜기

APIs & Services → Library로 가서 Google Sheets API를 찾아 Enable을 누릅니다. API는 "정해진 형식으로 물어보면 결과를 돌려주는 창구"였죠. 그 창구를 이 프로젝트에서 쓸 수 있게 열어 두는 작업이에요.

여기서 오해하기 쉬운 점 하나. 이 작업은 "우리 프로그램에서 표 API를 사용할 준비"일 뿐이고, 어느 사용자의 어느 표를 읽을지는 아직 하나도 정하지 않은 단계예요. API를 켰다고 제 표가 읽히기 시작하는 게 아니에요.

나중에 다른 걸 읽고 싶어질 때를 위해, 하려는 일과 켜야 할 API를 표로 정리해 둘게요.

하려는 작업확인할 API
표의 셀 읽기Google Sheets API

파일 이름 검색·목록 조회Google Drive API

다시 한 번 — API 사용 설정과 사용자 동의는 별개예요. 이 표의 API를 다 켜 놔도, 동의 화면에서 허용하지 않은 범위는 여전히 못 씁니다.

③ 동의 화면과 테스트 사용자

이제 Google Auth platform → Branding → Get started로 갑니다. 여기서 만드는 건 나중에 내가 직접 보게 될 그 허용 화면이에요.

App name에는 Sheets Practice처럼 이름을 적어요. 그리고 이메일 칸이 두 개 나오는데 역할이 달라요.

  • 지원 이메일 — 동의 화면을 본 사용자가 문의할 연락처
  • 연락 이메일 — 앱 설정 관련 안내를 받을 주소

External을 고른다고 곧바로 세상에 공개된다는 뜻이 아니에요. 앱을 Testing 상태로 두고, Test users에 등록한 계정으로만 개발 중인 앱을 시험하는 게 기본값이에요. 방문증 비유로 치면 "아직 시범 운영이라 명단에 적힌 사람만 받는 데스크"죠.

프로젝트 설정 마지막에는 Google API 사용자 데이터 정책을 읽고 동의하는 단계가 있어요. 여기까지 하면 동의 화면의 뼈대가 완성됩니다.

Test users에 내 계정 등록하기

Audience의 Test users → Add users에서 실제로 로그인할 자기 이메일을 넣고 Save를 누릅니다.

화면에서 확인할 것: 저장이 끝나면 화면에 1 user (1 test, 0 other) 같은 집계가 표시돼요. 계정 하나만 등록했다면 이 문구가 나오는 게 정상이에요. 이 숫자가 0이면 나중에 로그인 단계에서 거절당하니, 넘어가기 전에 눈으로 확인하세요.

여기서 흔한 오해 하나 — Testing 상태를 벗어나야 실습이 되는 게 아니에요. Testing을 그대로 유지한 채로 실제 인증과 표 읽기까지 성공할 수 있어요. 게시(Publish)는 남들에게 쓰게 할 때의 이야기입니다.

④ 읽기 범위 정하기

Data Access 화면에서 요청할 scope를 정합니다. 이번 실습에서 쓸 범위는 딱 하나예요.

실행: Google Cloud Console의 Data Access 화면에 붙여넣기 — Manually add scopes 칸에 넣는 값이에요

https://www.googleapis.com/auth/spreadsheets.readonly

주소처럼 생겼지만 브라우저로 열어 보는 주소가 아니라, 범위를 가리키는 이름표예요. 끝의 readonly가 핵심이고, 읽기 전용이라는 뜻이에요. 이 범위로는 표를 고칠 수 없어요.

같은 값이 다음 편에서 코드에도 등장해요. 미리 눈에 익혀 두면 좋아요.

개념 설명용 코드 — 다음 편에 나올 코드를 미리 보는 것이라 지금 실행하지 않아요

SCOPES = ["https://www.googleapis.com/auth/spreadsheets.readonly"]

콘솔의 Data Access → Add or remove scopes에서 목록에 있는 spreadsheets.readonly를 고르거나, Manually add scopes 칸에 위 문자열을 직접 넣고 Add to table → Update → Save까지 누르면 끝이에요.

scope와 파일 공유 권한은 다른 조건이다

이게 이번 편에서 제일 헷갈리는 지점이라 따로 떼어 놓을게요. scope와 파일 공유 권한은 서로 다른 두 개의 잠금장치예요. 둘 다 열려야 읽을 수 있어요.

상황scope는파일 공유 권한은결과
내 표를 읽으려 함표 읽기 동의함 ✅내 표라 접근 가능 ✅읽힘
공유받지 않은 남의 비공개 표표 읽기 동의함 ✅애초에 접근 불가 ❌못 읽음 — 열쇠 없는 캐비닛
편집 권한이 있는 표를 고치려 함읽기 전용 토큰 ❌편집 권한 있음 ✅수정 못 함 — 방문증에 촬영 금지

핵심: 내 계정이 '표 읽기'에 동의했다고 공유받지 않은 남의 표까지 읽히지는 않고, 반대로 편집 권한이 있는 표라도 읽기 전용 토큰으로는 수정 API를 부를 수 없어요.

마지막으로 동의 화면에 뜨는 문구도 한 번 짚어 둘게요. "See all your Google Sheets spreadsheets"라고 표시되는데, 이건 내가 접근할 수 있는 표 전체에 대한 읽기 권한이라는 뜻이에요. 예제 표 하나만 허용하는 범위가 아니에요. 실습이니 그대로 진행하되, 이 문구가 무슨 뜻인지는 알고 넘어가는 게 좋아요.

⑤ OAuth 클라이언트 만들고 JSON 내려받기

이제 마지막 칸이에요. Google Auth platform → Clients → Create client로 갑니다.

앱 종류에서 Desktop app을 고르세요. 이번 실습은 내 컴퓨터에서 도는 로컬 프로그램이 브라우저 로그인 결과를 돌려받는 구조라서 그래요. Web application을 고르면 redirect URI 입력란이 나오는데, 이 칸을 임의로 채우지 마세요. 나중에 redirect_uri_mismatch 오류로 되돌아옵니다.

이름을 정하고 생성하면 곧바로 Download JSON 버튼이 보여요. 여기서 받는 파일이 흔히 말하는 credentials.json이에요.

화면에서 확인할 것: 콘솔은 이 창을 닫으면 client secret을 다시 보거나 다운로드할 수 없다고 안내해요. "나중에 받지 뭐"가 안 되는 자리라서, 생성 직후에 바로 내려받으세요.

파일 두 개를 구분하기

앞에서 "클라이언트 ID는 앱 이름표, 토큰은 사용자 동의의 결과"라고 했죠. 그 구분이 그대로 파일 두 개로 나뉩니다.

credentials.jsontoken.json
언제 생기나지금 — Cloud 콘솔에서 앱 클라이언트를 만들고 다운로드다음 편 — 프로그램 실행 후 사용자가 로그인하고 동의하면
무엇인가어떤 앱이 로그인을 요청하는지 식별하는 설정동의한 사용자로 API를 요청하고 인증을 갱신하는 정보
비유에서는데스크에 등록된 업체 정보기사 주머니 속 방문증과 재발급 티켓
사람마다 다른가아니요 — 앱에 하나네 — 동의한 사람·기기마다

보관은 프로젝트 코드 밖의 개인 설정 폴더에 하고 경로만 기억합니다. 예제에서는 ~/.config/google-workspace/credentials.json에 뒀어요. 다음 편의 인증 프로그램은 같은 폴더에 token.json을 만들어요.

이 두 파일을 다루는 규칙

AI가 짠 백엔드 코드에서 확인할 것들에서 "비밀값을 코드에 그대로 두지 말라"고 했던 이야기가 여기서 그대로 되풀이돼요. 규칙은 세 줄이에요.

  • 실습 ZIP이나 Git 저장소에 넣지 않는다 — 둘 다요.
  • 다운로드한 내용이나 토큰을 에이전트 대화에 붙여넣지 않는다 — 대화 기록에 남아요.
  • 저장소 안에 둘 수밖에 없다면 .gitignore로 버전 관리에서 제외한다.

실행: 프로젝트에 .gitignore로 저장 — Git이 이 목록에 적힌 파일을 커밋 대상에서 빼요

credentials.json
token.json

그래서 도구에 경로를 알려 줄 때도 부탁하는 말을 조금 다듬는 게 좋아요.

실행: 코딩 에이전트에 붙여넣기 — 파일을 내려받아 개인 폴더에 옮긴 다음에요

인증 JSON은 준비했어.
이 도구가 사용할 경로를 설정해 줘.
내용은 출력하지 말아 줘.

마지막 줄이 중요해요. 1편에서 봤듯 에이전트는 도구를 부르고 그 결과를 대화에 담아 돌려주는데, 파일 내용을 읽어서 보여 달라고 하면 비밀값이 대화 기록에 그대로 남아요. "경로만 설정하고 내용은 출력하지 마"라고 미리 못박는 편이 안전합니다.

나쁜 선택 vs 좋은 선택 — 방문증 데스크에서

나쁜 선택좋은 선택
"내가 안에 있잖아"라며 기사를 그냥 들여보내려 한다 = 브라우저에 로그인돼 있으니 프로그램도 되겠지 하고 코드부터 짠다 → 프로그램에는 아무 자격이 없어서 호출이 통째로 거절된다. 기사 몫의 방문증을 따로 신청한다 = OAuth 클라이언트를 등록하고 동의를 따로 받는다 → 프로그램이 자기 자격으로 API를 부른다.
"3층 전체 + 금고까지" 적힌 신청서를 낸다 = 편하라고 쓰기까지 포함된 넓은 scope를 고른다 → 읽기만 하면 되는데 표를 실수로 고칠 수 있는 권한까지 열린다. "3층 서류 열람만"으로 적는다 = spreadsheets.readonly 하나만 요청한다 → 코드가 잘못 돌아도 표는 바뀌지 않는다.
명단에 이름을 안 올린 채 데스크로 간다 = Test users에 내 계정을 등록하지 않고 로그인부터 시도한다 → 다음 편에서 access_denied로 막히고 원인을 못 찾는다. 먼저 명단에 이름을 올린다 = Audience → Test users에 로그인할 계정을 등록하고 → 1 user (1 test, 0 other) 표시를 눈으로 확인한다.
다른 회사 양식으로 신청서를 낸다 = 로컬 프로그램인데 Web application을 고르고 redirect URI를 아무 주소나 적는다 → redirect_uri_mismatch가 뜨는데 어디를 고쳐야 할지 모른다. 쓰려는 도구에 맞는 양식을 고른다 = Desktop app을 선택하고 → redirect URI 칸은 임의로 채우지 않는다.
방문증을 로비 게시판에 붙여 둔다 = credentials.json을 저장소에 커밋하거나 에이전트 대화창에 붙여넣는다 → 값이 기록에 남고, 회수하기도 어렵다. 주머니에만 넣고 다닌다 = 프로젝트 밖 개인 설정 폴더에 두고 경로만 알려주며 → "내용은 출력하지 말아 줘"까지 함께 말한다.

직접 해보기

이번 연습의 목적은 표를 읽는 게 아니라, 표를 읽을 자격을 만드는 자리를 이해하는 것이에요.

① 두 문장을 내 말로 구분해 보기. "나는 지금 Google에 로그인해 있다"와 "내 프로그램은 지금 내 표를 읽을 동의를 받았다" — 이 둘이 왜 다른 이야기인지 한 문장씩 적어 보세요. 이 구분이 안 잡히면 이후 오류 메시지가 전부 똑같아 보여요.

② 세 갈래 중 내 경우를 골라 보기. 앞으로 내가 진짜 하고 싶은 일(내 표 읽기 / 서버가 매일 자동으로 읽기 / 공개 데이터 조회)을 하나 정하고, 세 갈래 표에서 어느 줄인지 짚어 보세요. 다른 줄을 골랐다면 준비 절차가 어디서부터 달라지는지도요.

③ 다섯 단계를 안 보고 순서대로 적기. 흐름 그림을 덮고 ①~⑤를 순서대로 적어 보세요. 순서가 헷갈린 자리가 이따 막혔을 때 제일 먼저 의심할 자리예요.

④ scope 문자열을 소리 내 읽어 보기. spreadsheets.readonly에서 readonly를 빼면 무엇이 달라지는지 한 줄로 적어 보세요. 그리고 "scope가 넓다"와 "파일 공유 권한이 넓다"가 어떻게 다른지도요.

⑤ 파일 두 개의 자리를 미리 정해 두기. credentials.json을 어느 폴더에 둘지 지금 정하고, 그 폴더가 Git 저장소 밖인지 확인하세요. 안이라면 .gitignore부터 만들고요.

⑥ 동의 화면 문구 예상해 보기. 다음 편에서 진짜 동의 화면을 보게 되는데, 그 전에 "거기에 어떤 문구가 뜰까"를 먼저 적어 두세요. 실제로 뜬 "See all your Google Sheets spreadsheets"와 비교하면, 내가 요청한 범위가 생각보다 넓은지 좁은지가 확 드러나요.

여기까지 하면 credentials.json 하나가 손에 남아요. 다음 편에서는 이 파일로 실제 로그인을 해 봅니다. 프로그램이 브라우저를 열고, 제가 계정을 고르고 허용을 누르면 token.json이 생기고, 그 토큰으로 Google 공식 예제 표의 첫 세 줄을 실제로 읽어 오는 데까지 가요. 그리고 그 읽기 함수를 2편에서 배운 MCP 방식으로 감싸서, 3편에서 서버를 만들었던 것처럼 에이전트가 부를 수 있는 도구로 내놓습니다.

  1. Google Workspace — Google Docs·Sheets·Drive·Gmail·Calendar처럼 문서·표·파일·메일·일정을 다루는 Google 서비스 묶음을 부르는 이름이에요. ↩
  2. credential(인증 정보) — 앱이나 사용자가 누구인지 식별하고 인증하는 데 쓰는 정보를 통틀어 부르는 말이에요. ↩
  3. OAuth — 비밀번호를 도구에 직접 넘기는 대신, Google 같은 서비스의 화면에서 사용자가 허용할 접근 범위를 직접 골라 주는 인증 절차예요. ↩
  4. 클라이언트 ID — "어떤 앱이 요청하는가"를 나타내는 값으로, 사용자가 누구든 앱마다 고정돼 있어요. ↩
  5. 접근 토큰(access token) — 사용자가 동의한 범위 안에서 API를 호출할 때 요청에 붙이는 값이며 유효 기간이 있어요. ↩
  6. 갱신 토큰(refresh token) — 접근 토큰의 유효 기간이 끝났을 때 새 접근 토큰을 받는 데 쓰일 수 있는 값이에요. ↩
  7. scope(범위) — '표 읽기', '일정 읽기'처럼 앱에 허용할 작업의 종류를 가리키는 이름표예요. ↩
  8. 서비스 계정 — 사람이 로그인하는 계정이 아니라 프로그램 전용으로 만드는 계정이며, 다룰 자료를 그 계정에 따로 공유해 줘야 해요. ↩
  9. API 키 — 일부 API에서 공개 데이터를 조회할 때 쓰는 식별값이며, 이것만으로 내 비공개 자료 전체에 접근할 수는 없어요(프록시 서버 글에서 키를 코드에 두면 안 되는 이유를 다뤘어요). ↩
  10. redirect URI — 로그인과 동의가 끝난 뒤 그 결과를 돌려받을 주소로, Web application 형태의 클라이언트에서는 이 주소를 정확히 등록해야 해요. ↩
  11. Cloud 프로젝트 — Google Cloud에서 API 설정과 앱 인증 정보를 한 덩어리로 묶어 관리하는 단위예요. ↩
