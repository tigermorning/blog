데이터는 어디에 남는가 — 학습에 안 쓴다는 안 남는다는 다른 말

2026. 8. 7.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

← 이전 편 로컬이냐 API냐는 틀린 질문 — 세 갈래와 품질 격차

세 갈래를 배웠으니 첫 번째 축, 데이터를 자세히 봤어요. 같은 질문을 API로 보냈다면 결과는 비슷했을지 몰라도, 그 문장이 지나간 경로는 완전히 달라요. 제 키보드에서 출발해 회선을 타고, 어느 나라의 어느 리전에 있는 서버로 들어가고, 그곳에서 계산되고, 다시 돌아와요. 응답 화면은 똑같아 보이지만 지나온 길이 다르고, 그 길 위에 남는 것도 달라요.

"학습에 쓰지 않는다"와 "남지 않는다"는 다른 말

API 제공자 문서를 열면 거의 항상 같은 문장이 먼저 눈에 들어와요. "API로 보낸 입력과 출력은 기본적으로 모델 학습에 사용하지 않습니다." 이 문장은 사실이고, 중요해요. 그런데 이 문장은 궁금한 것의 절반만 답해요. 학습에 쓰지 않는다는 건 "내 문장이 다음 모델의 재료가 되지 않는다"는 뜻이에요. 데이터가 남지 않는다는 건 "내 문장이 어딘가에 저장되어 있지 않다"는 뜻이에요. 이 둘은 다른 통제 장치이고, 실제로 따로 설정돼요.

2026년 7월에 확인한 바로는, OpenAI는 2023년 3월 1일 이후 API로 보낸 데이터를 모델 학습에 사용하지 않으며 사용하려면 명시적으로 동의해야 한다고 밝혀요. 그런데 같은 문서에서 남용 모니터링 로그는 최대 30일 보관된다고 적혀 있어요. Anthropic도 API 입력과 출력을 수신·생성 후 30일 이내에 자동 삭제한다고 밝히지만, 안전 시스템이 위반으로 표시한 대화는 최대 2년, 신뢰·안전 분류 점수는 최대 7년까지 남을 수 있다고 적어요. 이 숫자들을 검색해보면 서로 다른 값을 적어둔 요약 글이 여럿 나오는데, 정책이 계속 바뀌기 때문이에요. 그래서 실무 규칙은 단순해요 — 요약 글이 아니라 공급자의 공식 문서를 열고, 확인한 날짜를 함께 적어두는 것.

제로 데이터 보관은 문자 그대로 0이 아니다

보관 자체를 없애는 선택지도 있어요. 흔히 ZDR이라고 부르는 제로 데이터 보관 계약이에요. 이름만 들으면 콘솔 어딘가의 토글처럼 들리지만, 실제로는 그렇지 않았어요. 첫째, 신청해서 승인받아야 해요 — 표준 종량제 카드 결제만으로 얻는 상태가 아니에요. 둘째, 적용 범위에 구멍이 있어요. 파일 API, 배치 처리, 코드 실행처럼 본질적으로 상태를 저장하는 기능은 ZDR 대상이 아니고, 특정 모델 자체가 30일 보관을 요구해 ZDR을 적용할 수 없는 경우도 있어요. 셋째, 제로에도 예외가 있어요. 법적 요구나 안전 시스템의 판단이 있으면 ZDR 상태에서도 데이터가 남을 수 있다고 적혀 있어요.

이건 사업자가 약속을 어긴다는 이야기가 아니었어요. 안전 의무와 법적 의무가 계약보다 위에 있다는 이야기였어요. 그리고 감사 자리에서 설명해야 할 건 "ZDR을 켰습니다"가 아니라 "이런 조건에서 이만큼 남고, 이런 경우에는 이렇게 남습니다"였어요. 웹이나 앱에서 쓰는 소비자용 챗 인터페이스는 API와 정책이 완전히 다르다는 것도 챙길 점이었어요. 팀원이 "회사에서 승인한 AI"라고 생각하며 개인 계정 챗 창에 고객 문서를 붙여넣는 상황은, 계약과 무관한 완전히 다른 경로였던 거예요.

확인해야 할 여섯 가지

아래 표에서 하위 처리자(subprocessor)란 AI 회사가 데이터 처리를 다시 맡기는 다른 업체를 말하고, 데이터 처리 부속 계약(DPA)이란 개인정보를 어떻게 다룰지 구체적으로 못 박아 표준 약관에 덧붙이는 별도 계약이에요.

확인 항목구체적으로 물어야 할 것
학습 사용입력과 출력이 훈련에 기본으로 쓰이는가, 명시적 동의가 필요한가
로그 보관모니터링·보안·장애 대응을 위해 무엇이 며칠 남는가, 예외 조건은
처리 리전어느 나라, 어느 리전에서 처리되는가, 지정할 수 있는가
하위 처리자사업자가 다시 쓰는 클라우드나 외부 서비스는 어디인가
계약 형태표준 약관인가, 데이터 처리 부속 계약인가, 협상된 기업 계약인가
삭제와 감사삭제 요청이 가능한가, 감사 때 제출할 자료가 있는가

로컬 실행은 이 목록의 상당 부분을 없애줘요. 문장이 사업자 경계를 넘지 않으니 리전도, 하위 처리자도, 보관 기간 협상도 사라져요. 여기까지는 분명한 이점이에요.

로컬이 자동으로 안전한 건 아니다

그런데 로컬이 자동으로 안전한 건 아니었어요. 통제 지점이 밖에서 안으로 들어왔을 뿐이고, 그 안쪽을 관리할 사람은 이제 저였어요. 실제로 사고가 나는 지점은 대개 이런 곳이었어요. 노트북을 잃어버리면 그 안의 모델 파일과 함께 그동안 입력한 프롬프트 기록도 같이 나가요. 디스크 암호화가 꺼져 있었다면 잠금화면은 아무 의미가 없어요. 사내 서버에 모델을 올려두고 접근을 편하게 하려고 인증 없이 포트를 열어두면, 그 서버는 사내망에 있는 누구에게나 열린 창구가 돼요. 클라우드 백업이 켜진 폴더에 프롬프트 로그를 쌓아두면, 로컬로 옮긴 이유가 조용히 무효가 되고요. 회의 중 화면 공유로 민감한 프롬프트가 그대로 녹화되는 경우도 흔했어요.

그러니 로컬을 고를 때도 문서로 남길 게 있었어요 — 누가 이 장비에 접근하는가, 로그는 어디에 얼마나 쌓이는가, 백업은 어디로 가는가, 장비를 폐기할 때 디스크는 어떻게 처리하는가. 밖에 물어보던 질문을 이제 안에다 묻는 거였어요. 어느 쪽도 자동으로 안전하지 않고, 통제해야 할 지점이 옮겨갈 뿐이라는 게 이 축의 핵심이었어요. 다음 글에서는 두 번째와 세 번째 축, 비용과 통제권을 볼게요.
