에이전트가 도구를 쥔다는 것 — 모델·하네스·루프 (1)

2026. 8. 27.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

오늘 배운 것은 "AI 에이전트에게 재고 조회 도구 하나를 쥐여준다"는, 언뜻 단순해 보이는 상황이다. 그런데 이 하나의 상황을 계속 파고들었더니 계약·스키마·하네스·MCP 처럼 낯선 낱말이 계속 나왔다. 강의 자료는 이 낱말들을 당연히 아는 것처럼 훅 지나가는데, 프로그래밍을 전공하지 않은 나는 그때마다 멈춰서 "그게 정확히 뭔데?"를 되물어야 했다. 이 시리즈는 그 되물음의 기록이다. 부산 창고(BUSAN-02)에서 상품 A-17의 재고를 묻는 예시 하나를 시리즈 끝까지 붙잡고, 새 용어가 나올 때마다 그 자리에서 바로 정의하면서 따라간다. 1편은 가장 기초가 되는 낱말 네 개 — 모델·도구·에이전트·하네스 — 를 다룬다.

0. 시작하기 전에 — "도구를 준다"는 게 뭘 뜻하는가

AI 챗봇에게 "부산 창고에 A-17 재고 있어?"라고 물었다고 하자. 챗봇 뒤에서 움직이는 대규모 언어 모델(LLM)은 인터넷에 있던 방대한 글을 학습해서 다음 문장을 그럴듯하게 만들어내는 프로그램이다. 문제는 이 모델이 지금 이 순간 부산 창고에 실제로 몇 개가 쌓여 있는지 알 방법이 없다는 점이다. 학습할 때 본 데이터가 아니니까. 그런데도 질문을 받으면 모델은 "7개 남았습니다" 같은 그럴듯한 문장을 만들어낼 수 있다 — 근거 없이 지어낸, 틀린 답이다. 이런 현상을 흔히 환각(hallucination)이라 부른다.

이 문제를 푸는 방법이 "도구를 준다"는 것이다. 진짜 재고 데이터베이스에 접속해서 숫자를 가져오는 함수(function) — 정해진 값을 넣으면 정해진 규칙대로 결과를 돌려주는 작은 프로그램 조각 — 를 모델이 호출할 수 있게 연결해주면, 모델은 더 이상 추측하지 않고 그 함수가 돌려준 진짜 숫자를 가지고 답할 수 있다. 이런 함수를 흔히 API(Application Programming Interface)를 통해 부르는데, API가 정확히 뭔지 궁금하면 API란 무엇인가에 도서관 사서 비유로 따로 정리해 뒀다. 이 글에서는 "정해진 형식으로 요청하면 정해진 형식으로 답을 돌려주는 창구" 정도로만 알고 있어도 충분하다.

그런데 "함수를 연결한다"는 이 단순해 보이는 한 문장 안에 실은 여러 결정이 숨어 있다. 그 결정들을 낱말 하나씩 뜯어보는 게 이 시리즈다.

1. 네 낱말부터 구분하자 — 모델, 도구, 에이전트, 하네스

먼저 이 넷을 구분해야 뒷이야기가 헷갈리지 않는다. 처음 봐서는 다 비슷해 보이지만, 서로 완전히 다른 역할을 맡는다.

  • 모델(model) — 입력된 텍스트를 보고 다음에 올 텍스트를 확률적으로 예측하는 프로그램 그 자체다. ChatGPT나 Claude를 만드는 핵심 엔진이라 생각하면 된다. 이 모델은 재고 창고와 아무런 직접 연결이 없다.
  • 도구(tool) — 모델이 "이걸 실행해줘"라고 요청할 수 있는 외부 기능. 여기서는 get_inventory(sku, warehouse_id)처럼 재고를 실제로 조회해 오는 함수다. sku는 상품을 구분하는 코드(예: A-17)를 뜻한다.
  • 에이전트(agent) — 모델이 과업의 경계를 스스로 판단해 진행하는 구성 전체를 말한다. 같은 모델이라도 질문 한 번에 한 줄 답하고 끝나면 에이전트라 부르지 않고, 도구를 고르고 결과를 보고 다음 행동을 정하는 구성 안에 있을 때만 이 이름이 붙는다. "에이전트"라는 말 자체를 부동산 중개인 비유로 더 자세히 풀어본 글이 AI 에이전트란 무엇인가에 있다.
  • 하네스(harness) — 모델과 도구 사이에서 요청을 검증하고 실제로 실행한 뒤 결과를 모델에 되돌려주는 프로그램. 이 시리즈에서 가장 낯설고 가장 중요한 낱말이라 바로 아래에서 그림으로 풀어본다.

이 넷은 나열이 아니라 포함 관계다. 모델이 에이전트라는 구성 안에 들어가고, 에이전트는 하네스를 통해 도구와 이어진다. 그리고 이 요청-실행-응답을 계속 되풀이하는 순환을, 루프(loop)라 부른다.

실제 강의 자료에 나온 원본 도식으로 이 넷을 한 번에 겹쳐보면 이렇다. "모델과 에이전트, 하네스, 루프는 각각 어떻게 다른 의미인가요?"라는 질문에 답할 때 이 그림 하나로 설명이 된다.

이 그림에 네 낱말을 하나씩 겹쳐보면 다음과 같다.

  • 모델은 ②(요청 JSON 생성)와 ④⑤(결과를 받아 답을 완성)만 담당한다. 판단만 하고, 절대 스스로 실행하지 않는다.
  • 하네스는 ③(검증·실행)을 담당한다. 그림에 "하네스·앱"이라고 함께 적힌 이유는, ①에서 도구 정의를 요청에 챙겨 넣는 일도 결국 같은 프로그램(예: Claude Code)이 하기 때문이다 — 실무에서는 앱과 하네스가 같은 프로그램인 경우가 많다.
  • 에이전트는 이 낱말 하나에 대응하는 상자가 없다. ①~⑤ 전체 순환이 함께 일어나는 구성 자체를 가리키는 이름이기 때문이다.
  • 루프는 맨 아래 점선 화살표다. ⑤에서 답을 완성한 뒤 끝나는 게 아니라, 다시 ②로 돌아가 새 요청을 만드는 이 "연쇄 호출" 구조가 루프다.

2. 하네스가 뭔지 그림으로 보기

"하네스는 모델과 도구 사이의 실행 장치다"라는 문장만 읽으면 뭔지 감이 잘 안 온다. 실제로 무슨 일이 벌어지는지, 부산 창고 재고를 묻는 요청 하나가 처음부터 끝까지 어떻게 흘러가는지를 그대로 그려보면 이렇다.

말로 다시 풀면 이렇다. 사용자가 "부산 창고에 A-17 재고 있어?"라고 물으면,

  1. 모델은 직접 창고에 접속하지 못한다. 대신 "get_inventory라는 도구를 sku=A-17, warehouse_id=BUSAN-02라는 값으로 불러줘"라는 요청 문장만 만든다. 이게 그림의 ①이다.
  2. 이 요청을 받은 하네스가 두 가지를 확인한다 — 이 도구가 정말 써도 되는 도구인지(허용목록), 인자값 형식이 맞는지(스키마). 통과하면 그제서야 실제로 함수를 실행해 진짜 재고 데이터베이스에 접속한다. 이게 ②다.
  3. 실행 결과(예: {"available_quantity": 7})를 하네스가 다시 모델의 입력으로 넣어준다. 이게 ③이다.
  4. 모델은 이 실제 숫자를 받아들고 나서야 "A-17 재고는 7개입니다"라는 최종 문장을 만든다. 이게 ④다.

여기서 핵심은 모델은 절대 직접 실행하지 않는다는 점이다. 모델이 하는 일은 오직 "이 도구를, 이 값으로 불러줘"라는 요청 문장을 쓰는 것뿐이다. 실제로 데이터베이스에 접속하고, 값을 확인하고, 결과를 돌려주는 모든 실행은 하네스라는 별도의 프로그램이 담당한다. 이 분리가 왜 중요한지는 다음 절에서 바로 드러난다.

3. 이 순환 위에서 실패가 나는 자리는 딱 셋뿐이다

모델이 직접 실행하지 않고 요청만 쓴다는 사실을 알고 나면, 어디서 문제가 생길 수 있는지도 자연히 세 자리로 좁혀진다.

  1. 잘못 고름 — 재고를 확인해야 하는데, 이름이 비슷한 "주문 조회" 도구를 잘못 고르는 경우. 위 그림 ①에서 생긴다. 예를 들어 이런 식이다. 
    사용자: 부산 창고에 A-17 재고 있어?
모델(잘못된 선택): get_order_status(order_id="A-17") 호출  ← 재고 조회가 아니라 주문 조회를 부름
  2. 잘못 읽음 — 도구가 {"available_quantity": 7, "warehouse_id": "BUSAN-02"}를 정확히 돌려줬는데도, 모델이 warehouse_id 값을 놓치고 다른 창고 재고인 것처럼 답하는 경우. 그림 ③에서 생긴다. 도구는 제대로 일했는데 결과를 읽는 마지막 단계에서 새는 실패라는 점이 첫 번째 실패와 다르다.
  3. 같은 실수 반복 — 위 두 실패 중 하나가 일어났는데도 그걸 기록하고 판정하는 절차가 없으면, 다음 요청에서도 같은 인자로 같은 실패가 되풀이된다. 순환이 다시 처음(①)으로 돌아갈 때 생긴다.

이 세 자리를 미리 알아두면, 시리즈 뒤에서 다룰 도구 정의서·하네스 여섯 지점·권한 설계가 전부 "이 세 실패 중 무엇을 막으려는 장치인가"로 정리된다. 낯선 용어가 나올 때마다 "이건 ①·②·③ 중 어느 걸 막으려는 거지?"라고 되물으면 시리즈 전체가 훨씬 덜 막막해진다.

4. 도구 설명은 모델이 실제로 읽는 문장이다

도구를 하나 준다는 건 코드를 연결하는 일처럼 보이지만, 모델 입장에서는 다르다. 모델은 함수의 실제 코드를 보지 못하고, 이 도구가 뭘 하는지 설명하는 문장만 읽는다. 이 문장을 프롬프트(prompt)라 부르는데 — 프롬프트가 뭔지 처음이라면 프롬프트 엔지니어링이란?을 먼저 봐도 좋다 — 도구 설명도 결국 이 프롬프트의 일부로 모델에게 전달된다. 이 설명 문장을 계약(contract)이라 부른다. 이름, 하는 일, 인자 형식, 반환 형식, 실패했을 때의 행동까지 묶어 정한 약속이라는 뜻이다. 계약이 모호하면 모델은 빈 자리를 그럴듯한 추측으로 채운다.

실제로 얼마나 그대로 들어가는지, 강의 실습에서 직접 확인한 결과가 있다. 구글 코랩 연결 도구 하나를 등록하고 모델에게 전달되는 최종 입력을 그대로 꺼내 보면 이렇다.

<|im_start|>system
# Tools
You have access to the following functions:
<tools>
{"type": "function", "function": {"name": "open_colab_browser_connection",
  "description": "Opens a connection to a Google Colab browser session...",
  "parameters": {"properties": {}, "type": "object"}}}
</tools>
...
<|im_end|>
<|im_start|>user
구글 코랩을 브라우저로 연결해 줘<|im_end|>

중괄호 { }로 감싸인 부분은 JSON이라는, 컴퓨터 프로그램끼리 데이터를 주고받을 때 흔히 쓰는 정해진 형식이다 ("이름": 값 쌍을 콤마로 나열한다 정도로만 알아도 충분하다). 여기서 눈여겨볼 건 description이라는 자리에 적힌 문장 — 도구 설명 문장이 시스템 프롬프트(모델이 매 요청마다 가장 먼저 읽는 전역 안내문) 안에 토큰 그대로 박혀 들어간다는 점이다. "도구 설명을 잘 쓴다"는 게 사실은 "프롬프트를 잘 쓴다"와 같은 말이라는 뜻이다.

도구를 건네는 방식은 세 시대를 거쳤다

이 문장을 모델에 전달하는 방식 자체도 계속 바뀌어 왔다. 왜 바뀌어 왔는지 알면 지금 방식이 왜 이런 모양인지도 자연히 이해된다.

  • 텍스트 규약 — 초기에는 "Action: 검색"처럼 모델이 문장을 직접 짓고, 개발자가 그 문장을 프로그램으로 직접 해석했다. 추론과 행동을 번갈아 적는 ReAct가 이 계열의 대표적인 방식이다. 이 루프 구조와 그로부터 파생된 AutoGPT라는 프로젝트가 어떤 소동을 일으켰는지는 에이전트의 ReAct 루프와 AutoGPT 소동에, 프롬프트 기법이 역사적으로 어떻게 발전해왔는지는 프롬프트 기법의 역사에 각각 더 다뤄 뒀다. 문제는 표기법이 회사마다 달라 한 모델의 출력을 다른 프로그램이 그대로 읽는다는 보장이 약했다는 점이다.
  • 네이티브 함수 호출(function calling) — 2023년 6월 OpenAI가 도입했고 Anthropic의 tool use도 같은 계열이다. 도구를 위 예시 같은 JSON 스키마로 선언해 보내면, 모델은 구조가 보장된 함수 호출 응답을 돌려준다. "모델이 문장을 지어내고 개발자가 해석"하던 데서 "회사가 만든 프로그램(API)이 호출 구조를 아예 보장"하는 방식으로 넘어간 것이다.
  • MCP(Model Context Protocol) — 2024년 11월 Anthropic이 공개한 표준이다. 함수 호출 API가 나온 뒤에도, 챗봇 앱이 M개 있고 붙이고 싶은 도구·서비스가 N개 있으면 각 조합마다 따로 연결 코드를 짜야 하는 M×N개의 작업이 남아 있었다. 앱마다 도구를 선언하는 방식, 접속 인증 방식, 결과 해석 방식도 제각각이었다. MCP는 이 문제를 규칙 하나로 묶어 M×N을 M+N으로 줄인다. 이 규격을 흔히 USB-C에 빗대는데, 기기마다 다른 충전 단자를 쓰던 시절과 단자 규격 하나로 통일된 지금을 떠올리면 된다. MCP를 더 깊이, 실제 사례와 함께 다룬 글이 MCP — AI를 내 데이터에 꽂는 USB-C에 따로 있다.

여기서 헷갈리기 쉬운 게 하나 있다. MCP는 하네스가 아니다. MCP는 "도구 목록과 사용법을 이런 형식으로 알려준다"는 통신 규격일 뿐이고, 그 요청을 실제로 확인하고 실행하고 결과를 돌려주는 일은 여전히 하네스가 한다. 그림으로 보면 이렇다.

실습에서는 이 셋 중 MCP로, 문서 검색 서버를 실제로 등록해봤다. 그 실습과, 도구 설명 계약을 실제로 표 형식으로 채우는 방법은 다음 편에서 이어간다.

한 걸음 더: 여기서 정의한 모델·도구·에이전트·하네스라는 낱말을, 이번엔 Claude Code·opencode·Aider 같은 실제 하네스 여러 개를 나란히 놓고 비교하는 시리즈가 에이전트 하네스 톺아보기예요. "이 도구가 뭘 지원하나"라는 기능표보다 "내 일이 어디서 막히는가"부터 관찰하는 법을 다뤄요.
