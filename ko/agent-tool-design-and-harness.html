오늘 배운 건 "AI 에이전트(스스로 일을 이어 가는 AI)에게 재고 조회 도구 하나를 쥐여 준다"는 상황이에요. 얼핏 단순해 보여요. 그런데 이 상황을 계속 파고들었더니 계약·스키마·하네스·MCP 같은 낯선 낱말이 계속 나왔어요. 이런 낱말은 보통 다들 아는 것처럼 휙 지나가요. 프로그래밍을 전공하지 않은 저는 그때마다 멈춰서 "그게 정확히 뭔데?"를 되물어야 했어요. 이 시리즈는 그 되물음의 기록이에요. 부산 창고(BUSAN-02)에서 상품 A-17의 재고를 묻는 예시 하나를 시리즈 끝까지 붙잡고 가요. 새 용어가 나오면 그 자리에서 바로 풀어요. 1편은 가장 기초가 되는 낱말 네 개, 모델·도구·에이전트·하네스를 다뤄요.

0. 시작하기 전에 — "도구를 준다"는 게 뭘 뜻하는가

AI 챗봇에게 "부산 창고에 A-17 재고 있어?"라고 물었다고 해 볼게요. 챗봇 뒤에서 움직이는 대규모 언어 모델(LLM)은 인터넷의 방대한 글을 학습해서, 다음에 올 문장을 그럴듯하게 만들어 내는 프로그램이에요. 문제는 이 모델이 지금 이 순간 부산 창고에 실제로 몇 개가 쌓여 있는지 알 방법이 없다는 거예요. 학습할 때 본 데이터에는 없으니까요.

나쁜 선택좋은 선택
"부산 창고에 A-17 재고 있어?"를 모델에게 그대로 묻는다 → 모델은 "7개 남았습니다" 같은 그럴듯한 문장을 만들어낼 수 있다. 근거 없이 지어낸, 틀린 답이다. 이런 현상을 흔히 환각(hallucination)이라 부른다. 진짜 재고 데이터베이스에 접속해서 숫자를 가져오는 함수를 모델이 호출할 수 있게 연결해 준다 → 모델은 더 이상 추측하지 않고, 그 함수가 돌려준 진짜 숫자를 가지고 답한다.

이 문제를 푸는 방법이 "도구를 준다"는 거예요. 여기서 함수(function)는 정해진 값을 넣으면 정해진 규칙대로 결과를 돌려주는 작은 프로그램 조각이에요. 이런 함수는 흔히 API(Application Programming Interface)를 통해 불러요. API가 궁금하면 API란 무엇인가에 도서관 사서 비유로 정리해 뒀어요. 이 글에서는 "정해진 형식으로 요청하면 정해진 형식으로 답을 돌려주는 창구" 정도로만 알아도 충분해요.

그런데 "함수를 연결한다"는 한 문장 안에는 여러 결정이 숨어 있어요. 그 결정들을 낱말 하나씩 뜯어보는 게 이 시리즈예요.

1. 네 낱말부터 구분하자 — 모델, 도구, 에이전트, 하네스

먼저 이 넷을 구분해야 뒷이야기가 헷갈리지 않아요. 처음에는 다 비슷해 보여요. 하지만 서로 완전히 다른 역할을 맡아요.

  • 모델(model) — 입력된 글을 보고 다음에 올 글을 확률로 예측하는 프로그램 그 자체예요. ChatGPT나 Claude를 만드는 핵심 엔진이라고 보면 돼요. 이 모델은 재고 창고와 직접 이어져 있지 않아요.
  • 도구(tool) — 모델이 "이걸 실행해 줘"라고 요청할 수 있는 바깥 기능이에요. 여기서는 get_inventory(sku, warehouse_id)처럼 재고를 실제로 조회해 오는 함수예요. sku는 상품을 구분하는 코드(예: A-17)를 뜻해요.
  • 에이전트(agent) — 모델이 일의 범위를 스스로 판단해 진행하는 구성 전체를 말해요. 같은 모델이라도 질문 한 번에 한 줄 답하고 끝나면 에이전트라고 부르지 않아요. 도구를 고르고, 결과를 보고, 다음 행동을 정하는 구성 안에 있을 때만 이 이름이 붙어요. "에이전트"라는 말을 부동산 중개인 비유로 더 자세히 풀어 본 글이 AI 에이전트란 무엇인가에 있어요.
  • 하네스(harness) — 모델과 도구 사이에서 요청을 검증하고, 실제로 실행하고, 결과를 모델에 되돌려 주는 프로그램이에요. 이 시리즈에서 가장 낯설고 가장 중요한 낱말이라 바로 아래에서 그림으로 풀어 봐요.

이 넷은 나란히 놓인 목록이 아니라 포함 관계예요. 모델이 에이전트라는 구성 안에 들어가고, 에이전트는 하네스를 통해 도구와 이어져요. 그리고 이 요청-실행-응답을 계속 되풀이하는 순환을 루프(loop)라고 불러요.

이 넷을 한 장에 겹쳐 보면 아래 그림이에요. "모델과 에이전트, 하네스, 루프는 각각 어떻게 다른가요?"라는 질문에 이 그림 하나로 답할 수 있어요.

이 그림에 네 낱말을 하나씩 겹쳐 보면 이래요. JSON은 아래 4절에서 풀어요. 지금은 "데이터를 적는 정해진 형식" 정도로만 알아 두세요.

  • 모델은 ②(요청 JSON 만들기)와 ④⑤(결과를 받아 답 완성하기)만 맡아요. 판단만 하고, 스스로 실행하지 않아요.
  • 하네스는 ③(검증·실행)을 맡아요. 그림에 "하네스·앱"이라고 같이 적힌 이유가 있어요. ①에서 도구 정의를 요청에 챙겨 넣는 일도 같은 프로그램(예: Claude Code)이 하기 때문이에요. 실제로는 앱과 하네스가 같은 프로그램인 경우가 많아요.
  • 에이전트는 대응하는 상자가 없어요. ①~⑤ 전체 순환이 함께 일어나는 구성 자체를 가리키는 이름이기 때문이에요.
  • 루프는 맨 아래 점선 화살표예요. ⑤에서 답을 완성하고 끝나는 게 아니에요. 다시 ②로 돌아가 새 요청을 만드는 이 "연쇄 호출" 구조가 루프예요.

2. 하네스가 뭔지 그림으로 보기

여기서 나눈 모델·도구·에이전트·하네스라는 네 낱말을 실제 코드로 구현해 보는 이야기는 내 손으로 만드는 에이전트 하네스 시리즈에서 이어가요.

"하네스는 모델과 도구 사이의 실행 장치다"라는 문장만 읽으면 감이 잘 안 와요. 부산 창고 재고를 묻는 요청 하나가 처음부터 끝까지 어떻게 흘러가는지 그려 보면 아래와 같아요.

말로 다시 풀면 이래요. 사용자가 "부산 창고에 A-17 재고 있어?"라고 물으면,

  1. 모델은 창고에 직접 접속하지 못해요. 대신 "get_inventory라는 도구를 sku=A-17, warehouse_id=BUSAN-02라는 값으로 불러 줘"라는 요청 문장만 만들어요. 이게 그림의 ①이에요.
  2. 이 요청을 받은 하네스가 두 가지를 확인해요. 이 도구가 정말 써도 되는 도구인지(허용목록), 값의 형식이 맞는지(스키마 — 입력 칸의 모양과 범위를 미리 정해 둔 규격)예요. 통과하면 그때서야 함수를 실행해서 진짜 재고 데이터베이스(자료 보관함)에 접속해요. 이게 ②예요.
  3. 실행 결과(예: {"available_quantity": 7})를 하네스가 다시 모델의 입력으로 넣어 줘요. 이게 ③이에요.
  4. 모델은 이 실제 숫자를 받고 나서야 "A-17 재고는 7개입니다"라는 최종 문장을 만들어요. 이게 ④예요.

핵심은 모델은 직접 실행하지 않는다는 점이에요. 모델이 하는 일은 "이 도구를, 이 값으로 불러 줘"라는 요청 문장을 쓰는 것뿐이에요. 데이터베이스에 접속하고, 값을 확인하고, 결과를 돌려주는 모든 실행은 하네스라는 별도의 프로그램이 해요. 이렇게 나눈 게 왜 중요한지는 다음 절에서 드러나요.

3. 이 순환 위에서 실패가 나는 자리는 딱 셋뿐이다

모델이 직접 실행하지 않고 요청만 쓴다는 걸 알면, 문제가 생길 수 있는 자리도 세 곳으로 좁혀져요.

  1. 잘못 고름 — 재고를 확인해야 하는데, 이름이 비슷한 "주문 조회" 도구를 잘못 고르는 경우예요. 위 그림 ①에서 생겨요. 아래는 읽기만 해도 되는 예시예요.

    개념 설명용 코드 — 직접 실행하는 코드 아니에요

    사용자: 부산 창고에 A-17 재고 있어?
모델(잘못된 선택): get_order_status(order_id="A-17") 호출  ← 재고 조회가 아니라 주문 조회를 부름
  2. 잘못 읽음 — 도구가 {"available_quantity": 7, "warehouse_id": "BUSAN-02"}를 정확히 돌려줬는데도, 모델이 warehouse_id 값을 놓쳐서 다른 창고 재고인 것처럼 답하는 경우예요. 그림 ③에서 생겨요. 도구는 제대로 일했는데 결과를 읽는 마지막 단계에서 새는 실패라서, 첫 번째 실패와 달라요.
  3. 같은 실수 반복 — 위 두 실패 중 하나가 일어났는데 그걸 기록하고 판정하는 절차가 없으면, 다음 요청에서도 같은 값으로 같은 실패가 되풀이돼요. 순환이 다시 처음(①)으로 돌아갈 때 생겨요.

이 세 자리를 미리 알아 두세요. 시리즈 뒤에서 다룰 도구 정의서·하네스 여섯 지점·권한 설계가 모두 "이 세 실패 중 무엇을 막으려는 장치인가"로 정리돼요. 낯선 용어가 나오면 "이건 잘못 고름·잘못 읽음·같은 실수 반복 중 어느 걸 막으려는 거지?"라고 되물어 보세요. 시리즈 전체가 훨씬 덜 막막해져요.

4. 도구 설명은 모델이 실제로 읽는 문장이다

도구를 하나 준다는 건 코드를 연결하는 일처럼 보여요. 하지만 모델 입장에서는 달라요. 모델은 함수의 실제 코드를 보지 못해요. 이 도구가 뭘 하는지 설명하는 문장만 읽어요. 이 문장은 프롬프트(prompt, 모델에게 주는 지시 글)의 일부로 모델에게 전달돼요. 프롬프트가 처음이라면 프롬프트 엔지니어링이란?을 먼저 봐도 좋아요. 이 설명 문장을 계약(contract)이라고 불러요. 이름, 하는 일, 값의 형식, 돌려주는 형식, 실패했을 때의 행동까지 묶어 정한 약속이라는 뜻이에요. 계약이 모호하면 모델은 빈 자리를 그럴듯한 추측으로 채워요.

실제로 얼마나 그대로 들어가는지 직접 확인해 봤어요. 구글 코랩 연결 도구 하나를 등록하고, 모델에게 전달되는 최종 입력을 그대로 꺼내 봤어요. 아래 글은 읽기만 해도 돼요.

중괄호 { }로 감싼 부분은 JSON이에요. 컴퓨터 프로그램끼리 데이터를 주고받을 때 흔히 쓰는 정해진 형식이에요. "이름": 값 짝을 쉼표로 늘어놓는다고만 알아도 충분해요. 여기서 눈여겨볼 곳은 description 자리에 적힌 문장이에요. 도구 설명 문장이 시스템 프롬프트(모델이 매 요청마다 가장 먼저 읽는 전체 안내문) 안에 글자 그대로 들어가요. 그래서 "도구 설명을 잘 쓴다"는 말은 사실 "프롬프트를 잘 쓴다"와 같은 말이에요.

도구를 건네는 방식은 세 시대를 거쳤다

이 문장을 모델에 전달하는 방식도 계속 바뀌어 왔어요. 왜 바뀌었는지 알면 지금 방식이 왜 이런 모양인지 이해돼요.

  • 텍스트 규약 — 초기에는 "Action: 검색"처럼 모델이 문장을 직접 짓고, 개발자가 그 문장을 프로그램으로 읽어 해석했어요. 생각과 행동을 번갈아 적는 ReAct가 이 계열의 대표 방식이에요. 이 루프 구조와, 여기서 나온 AutoGPT라는 프로젝트가 일으킨 소동은 에이전트의 ReAct 루프와 AutoGPT 소동에 있어요. 프롬프트 기법이 어떻게 발전해 왔는지는 프롬프트 기법의 역사에 있어요. 문제는 표기법이 회사마다 달라서, 한 모델의 출력을 다른 프로그램이 그대로 읽을 수 있다는 보장이 약했다는 점이에요.
  • 네이티브 함수 호출(function calling) — 2023년 6월 OpenAI가 도입했고 Anthropic의 tool use도 같은 계열이에요. 도구를 위 예시 같은 JSON 스키마로 적어 보내면, 모델은 모양이 보장된 함수 호출 응답을 돌려줘요. "모델이 문장을 지어내고 개발자가 해석"하던 방식에서 "회사가 만든 프로그램(API)이 호출 모양을 아예 보장"하는 방식으로 넘어간 거예요.
  • MCP(Model Context Protocol) — 2024년 11월 Anthropic이 공개한 표준(모두가 따르기로 한 약속)이에요. 함수 호출 API가 나온 뒤에도 일이 남아 있었어요. 챗봇 앱이 M개, 붙이고 싶은 도구·서비스가 N개라면 짝마다 따로 연결 코드를 짜야 하는 M×N개의 작업이 생겨요. 앱마다 도구를 적는 방식, 접속 인증 방식, 결과 해석 방식도 제각각이었어요. MCP는 이걸 규칙 하나로 묶어서 M×N을 M+N으로 줄여요. 이 규격을 흔히 USB-C에 빗대요. 기기마다 다른 충전 단자를 쓰던 시절과, 단자 하나로 통일된 지금을 떠올리면 돼요. MCP를 더 깊이 다룬 글은 MCP — AI를 내 데이터에 꽂는 USB-C에 따로 있어요.

여기서 헷갈리기 쉬운 게 하나 있어요. MCP는 하네스가 아니에요. MCP는 "도구 목록과 사용법을 이런 형식으로 알려 준다"는 통신 규격일 뿐이에요. 그 요청을 실제로 확인하고, 실행하고, 결과를 돌려주는 일은 여전히 하네스가 해요. 그림으로 보면 이래요.

실습에서는 이 셋 중 MCP로 문서 검색 서버를 실제로 등록해 봤어요. 그 실습과, 도구 설명 계약을 표로 채우는 방법은 다음 편에서 이어가요.

이럴 때 의심하세요 — 도구를 붙인 AI가 엉뚱하게 답하거나 멋대로 실행할 때

도구를 붙인 뒤의 문제는 대부분 "AI가 이상하다" 한마디로 먼저 느껴져요. 그런데 모델이 쓴 요청, 하네스가 실행한 결과, 최종 답을 한 줄씩 떼어 보면 어느 자리에서 샜는지 거의 바로 갈려요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
재고를 물었는데 챗봇이 도구를 부른 흔적 없이 "7개 남았습니다"처럼 숫자를 바로 말해요. 실제 재고와 안 맞아요 모델에 보낸 요청과 모델이 돌려준 원본 응답이에요. 요청에 도구 목록(tools)이 실렸는지, 응답에 도구 호출 요청(OpenAI는 tool_calls, Anthropic은 tool_use 블록)이 있는지 봐요 요청에 도구 목록이 없으면 앱이 안 실은 거예요. 목록은 있는데 호출 요청이 없으면 모델 쪽이라 설명 문장을 봐요. 호출 요청은 있는데 결과가 안 돌아왔다면 하네스 쪽이라, 요청을 받아 함수를 실행하는 코드를 봐요
실행 기록을 보니 재고 질문인데 get_order_status(order_id="A-17")처럼 이름이 비슷한 다른 도구가 불렸어요 함수 코드가 아니라 두 도구의 설명 문장(description)이에요. 모델은 코드를 못 보고 이 문장만 읽어요 두 설명을 나란히 놓고, 설명만 읽어서 재고 수량 질문엔 어느 쪽인지 가를 수 있는지 봐요. 내가 못 가르면 모델도 못 가르는 거예요. 설명마다 쓰는 때와 안 쓰는 때를 한 문장씩 적어요(2편의 여섯 칸 중 ③)
도구는 {"available_quantity": 7, "warehouse_id": "BUSAN-02"}를 제대로 돌려줬는데, 최종 답은 다른 창고 이야기처럼 말하거나 수량을 바꿔 말해요 도구 코드가 아니라 실행 결과와 최종 답 사이예요. 실행 기록에서 모델에 되돌려 넣은 결과 원문과 최종 답을 나란히 봐요 결과 원문에는 맞는 값이 있는데 답이 다르면 읽는 단계에서 샌 거예요. 결과에 답과 상관없는 필드가 많으면 봐야 할 값만 남기게 줄여요(2편의 ⑤ 반환 형식). 결과가 기록되지 않아 나란히 볼 수 없다면 기록부터 남겨요
코딩 에이전트에 남이 만든 MCP 서버를 붙였더니, AI가 그 서버 도구로 파일 삭제나 메시지 전송 같은 일을 묻지 않고 실행해요 MCP 연결이 아니라 하네스의 허용 설정이에요. Claude Code라면 /permissions에서 그 도구가 묻지 않고 허용하는 목록에 들어 있는지 봐요. 예전 확인 창에서 다시 묻지 말라는 쪽을 고른 적이 있으면 거기 남아 있어요 쓰기·삭제·전송 도구는 허용 목록에서 빼서 매번 묻게 해요. 넘어온 값을 검사하는지는 MCP가 아니라 그 서버의 코드가 정해요. 무엇을 검사하는지 확인하기 전에는 조회 도구만 열어 둬요(3편의 서버 쪽 검증)

둘째·셋째 줄을 가르려면 요청, 실행 결과, 최종 답이 한 줄씩 남아 있어야 해요. 기록이 없으면 세 실패가 모두 "답이 이상하다" 하나로 뭉쳐 보여요. 그래서 도구를 붙이는 첫날부터 이 세 줄을 파일로 남기게 해 둬요. 남기는 모양은 2편의 트레이스에 있어요.

한 걸음 더: 여기서 정의한 모델·도구·에이전트·하네스라는 낱말을, 이번엔 Claude Code·opencode·Aider 같은 실제 하네스 여러 개를 나란히 놓고 비교하는 시리즈가 에이전트 하네스 톺아보기예요. "이 도구가 뭘 지원하나"라는 기능표보다 "내 일이 어디서 막히는가"부터 관찰하는 법을 다뤄요.
