에이전트 툴은 마법 상자가 아니라 "작은 코어 위에 무엇을 얹을지"를 고르는 층위이고, 손을 하나 늘릴 때마다 입구·상태·권한이 함께 늘어난다.

마지막 편은 강의의 두 절을 묶었어요. 하나는 OpenClaw의 뼈대였던 pi라는 작은 도구를 들여다보는 절, 다른 하나는 OpenClaw에 더 붙일 수 있는 확장 기능을 지도처럼 둘러보는 절이에요. 둘 다 같은 질문이에요. "무엇이 코어에 있고, 무엇이 바깥에 얹히는가." 오늘은 아무것도 켜지 않아요. 무엇이 있는지, 무엇을 조심해야 하는지 읽고 다음에 열어 볼 지점을 정하는 편이에요.

비유 — 뼈대만 있는 집과 증축

작은 집을 하나 지었어요. 기둥과 지붕, 방 하나, 현관 하나. 필요해지면 증축해요. 차고를 붙이면 차가 드나드는 새 입구가 생기고, 창고를 붙이면 물건이 쌓이는 새 공간이 생기고, 2층을 올리면 계단 열쇠를 누구에게 줄지 정해야 해요. 증축 하나마다 입구·보관·열쇠가 함께 늘어요. 그리고 이 집의 기둥은 원래 다른 건축가가 만든 작은 규격 기둥이었는데, 나중에 자기 기둥으로 바꿨어요.

전체 그림 — 코어와 확장의 층

읽는 법: 안쪽 굵은 상자가 코어예요. 모델을 만나고, 도구를 부르고, 기록을 남기는 가장 작은 부분이죠. 그 바깥 상자가 이 시리즈에서 본 OpenClaw 본체이고, 점선 바깥이 오늘 둘러볼 확장이에요. 안쪽으로 갈수록 바꾸기 어렵고, 바깥으로 갈수록 붙였다 뗐다 해요.

pi — 작은 코어에서 내 도구를 만든다

pi는 터미널에서 쓰는 작은 코딩 에이전트 CLI1예요. 모델과 도구를 연결해 코딩 작업을 돕고, 스크립트로 확장할 자리를 열어 둬요. 강의가 pi를 소개한 까닭은 하나예요. pi를 기반으로 내 필요에 맞춘 에이전트 툴을 만들 수 있기 때문이에요. 완성된 서비스를 그대로 쓰는 데서 멈추지 않고, 필요한 입구와 기능을 코어 위에 얹는 선택도 가능해요.

이 선택은 이미 일어난 일이에요. 1편에서 본 Warelay는 WhatsApp 게이트웨이였고, Clawdbot은 npm 패키지 설명에서 "Pi RPC agent" 위에 만든 WhatsApp 게이트웨이로 소개됐어요. pi가 에이전트 코어가 되고, 그 위에 메시지를 받는 입구가 더해져 다른 도구가 된 모습이에요. 초기 버전은 pi를 프로그램 안에 넣어(임베디드) 엔진으로 썼고, 이후 자체 코어를 갖추면서 pi 의존을 걷어냈어요. 지금 OpenClaw의 내장 런타임 이름은 openclaw예요. 이름은 바뀌어도 "코어 위에 채널과 기능을 조립한다"는 생각은 이어져요.

없는 것도 설계다

pi에는 내장 MCP6 클라이언트가 없어요. 내장 서브에이전트도 없고, 반복 작업을 정해진 시각에 돌리는 내장 스케줄러도 없어요. 이 빈자리는 "부족한 목록"으로 끝나지 않아요. 무엇을 코어에 두고 무엇을 확장으로 둘지 고르는 경계예요. MCP 연결은 확장으로 더할 수 있고, 여러 pi를 함께 다루는 방식도 확장이나 별도 구성으로 설계할 수 있고, 반복 실행은 운영체제의 예약 기능이나 별도 확장이 맡을 수 있어요.

핵심: OpenClaw는 이 기능들을 하나의 도구에 품었고, pi는 기본으로 다 품지 않는 대신 바깥에서 조립할 여지를 남겼어요. 기능이 있는지뿐 아니라 어느 층에 놓였는지도 살펴야 해요. 이 관점은 에이전트가 도구를 쥔다는 것 — 모델·하네스·루프에서 본 "하네스" 개념과 같아요. OpenClaw에서 본 게이트웨이, 채널, 권한은 pi 위에 내 도구를 만들 때도 다시 묻게 돼요. 어디서 메시지를 받을지, 무엇을 할 수 있게 둘지, 어느 행동에 승인을 둘지.

확장 기능 투어 — 손을 늘리면 입구·상태·권한이 는다

여기까지가 OpenClaw의 기본 몸이에요. 게이트웨이가 있고, 채널이 붙고, 권한이 있고, 사용량을 봐요. 이제 여기에 손을 더 붙이는 기능들을 지도처럼 둘러봐요. 둘러보는 기준은 셋이에요. 손이 하나 늘면 그 손이 닿는 곳이 늘고(입구), 손이 남기는 기록이 늘고(상태), 손에게 허락해야 하는 권한이 늘어요(권한).

확장무엇을 하나새로 생기는 입구주의할 권한
브라우저 조작페이지 열기, 탭, 스크린샷, 클릭, 입력, PDF 저장을 하나의 서비스로웹이 통째로 새 접촉면방문하는 페이지의 문장은 명령이 아니다 — 5편의 "읽은 내용과 실행 요청 분리"가 더 자주 적용됨
카메라·위치 노드연결한 폰·컴퓨터의 카메라로 사진, 위도·경도·고도·속도·위치 출처물리 세계가 에이전트의 입력이 됨권한 거부·기능 꺼짐·시간 초과 시의 오류까지 문서화됨. 허용과 연결이 먼저, 기능은 그다음
Talk mode로컬 음성 인식과 합성으로 화면 없이 이어서 대화음성 입구소리로 듣는 승인은 흘러가기 쉬움 — 위험도 큰 작업은 발화로 정확히 다시 승인
IMAP7 메일 감시메일함을 지켜보다 인증된 메일을 분리되고 제한된 읽기 전용 reader agent에 넘김메일함 — 검증할 수 없는 입력이 들어오는 입구임의의 메일을 주 에이전트에 바로 넣는 기능이 아님. 입구에 처음 닿는 것을 권한이 가장 작은 별도 역할로 격리
모델 페일오버지금 모델에 문제가 생기면 같은 제공자 안에서 인증 프로필을 바꿔 본 뒤 설정해 둔 다음 모델로—실패를 없애는 장치가 아니라 실패 뒤 시도할 순서. 다음 모델을 정해 두지 않으면 넘어갈 곳이 없음
ClawHub스킬을 찾아 설치하는 배포처 — openclaw skills search, openclaw skills install남이 만든 코드가 들어오는 입구설치할 수 있다 ≠ 안전하다. 악성 표시 배포판은 거부하지만, 감사 내용을 보여 주며 설치를 이어 가는 배포판도 있음 — 문서를 읽는 습관이 조건
모바일 앱iOS·Android 앱이 노드로 연결되어 폰의 감각과 알림이 에이전트와 이어짐주머니 속 입구4편의 텔레그램 연결과 같은 원리가 앱이라는 다른 옷을 입은 것

IMAP 감시 항목이 특히 오늘의 원칙을 그대로 보여 줘요. 문 같은 곳에는 문지기가 따로 서 있는 구조예요. 스킬 마켓의 "설치할 수 있다와 안전하다는 다르다"는 스킬과 규칙 파일에서 스킬이 뭔지 봤던 독자라면 "남이 쓴 스킬을 그대로 믿을 수 있나"라는 질문으로 이어져요.

함께 붙는 주의점 둘

  1. 실험 단계 표시가 붙은 기능은 안정적인 기본값이나 장기 계약을 보장하지 않는 미리 보기예요. 형태가 빨리 바뀔 수 있으니, 같은 일을 하는 안정 경로가 있다면 그쪽이 먼저예요.
  2. 카메라, 위치, 음성, 기기 조작은 권한을 주고 연결된 노드가 있어야 움직여요. 켜는 순서가 아니라 허용의 근거를 먼저 묻는 습관이 이 시리즈의 결론이에요.

나쁜 선택 vs 좋은 선택 — 증축할 때

나쁜 선택좋은 선택
"메일 정리를 시키고 싶다"며 메일함 전체를 주 에이전트에 바로 연결한다 → 스팸 메일 안의 "첨부 링크를 열고 계정 정보를 보내라"는 문장이 실행 권한 있는 에이전트에 그대로 닿는다. IMAP 감시가 설계한 대로, 읽기 전용 reader agent가 먼저 받고 실행이 필요한 것만 별도 승인으로 넘긴다 → 검증 안 된 입력이 실행 권한과 만나지 않는다.
ClawHub에서 별점 높은 스킬을 문서도 안 읽고 설치한다 → 그 스킬이 어떤 도구를 쓰고 어디로 데이터를 보내는지 모른 채 내 에이전트의 손이 하나 늘어난다. 설치 전 스킬 문서에서 "무슨 도구를 쓰나, 무슨 권한을 요구하나"를 읽고, 감사 표시가 있으면 그 내용을 본다 → 늘어나는 입구·상태·권한을 알고 늘린다.

위 확장 표에서 "다음에 켜 보고 싶은 것" 하나를 골라 세 줄을 적어 보세요. 이 손이 새로 닿는 입구는 어디인가, 새로 남기는 상태는 무엇인가, 새로 허락해야 하는 권한은 무엇인가. 세 줄이 채워지지 않으면 아직 켤 때가 아니에요. 그리고 여덟 편을 되돌아보면 질문은 계속 같았어요. 어디서 메시지를 받을지(채널), 무엇을 할 수 있게 둘지(권한), 어느 행동에 승인을 둘지(스탠딩 오더), 모델을 어떻게 만날지(인증 경로), 기록이 어디에 남는지(세션·워크스페이스). 작은 코어 위에 무엇을 얹을지 정할 때마다 편리함과 경계를 함께 설계하게 돼요. 도구를 업무에 붙일지 말지의 판단 자체는 도구에서 시작하면 아무도 안 씁니다에서 다뤘어요.

  1. CLI — 터미널에서 글자 명령으로 프로그램을 다루는 방식으로, 터미널·셸·커널·프롬프트 차이에서 처음 다뤘어요. ↩
  2. TUI — 마우스 없이 터미널 안에서 글자로 그린 화면을 움직이는 인터페이스. ↩
  3. OAuth — 비밀번호를 직접 주지 않고 "이 앱이 내 계정을 이만큼 쓰게 허락한다"는 방식으로 로그인 권한을 맡기는 표준. ↩
  4. JSONL — 한 줄마다 JSON 객체 하나를 넣어 기록을 쌓는 형식으로, JSON 자체는 목업 데이터와 REST API에서 처음 다뤘어요. ↩
  5. 표준입출력 — 프로그램이 글자를 받고 내보내는 기본 통로로, 다른 프로그램과 파이프로 이어 붙일 수 있어요. ↩
  6. MCP — AI가 외부 도구와 데이터에 표준 방식으로 연결되는 규약으로, MCP — AI를 내 데이터에 꽂는 USB-C에서 처음 다뤘어요. ↩
