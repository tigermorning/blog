시작은 오해였어요

강사님 화면을 봤는데, 모델 이름 옆에 sisyphus라는 글자가 붙어 있었어요. 저는 당연히 "저것도 모델 이름인가? 내가 저걸 안 깔아서 1편에서 찾던 모델이 안 보이는 건가?" 싶었죠.

아니었어요. Sisyphus는 모델이 아니에요. 모델을 여러 개 부려 먹는 쪽이에요. oh-my-opencode라는 플러그인1을 깔면 생기는 지휘자 역할의 이름이고, 화면에 그 이름이 뜨는 건 "지금 이 플러그인이 켜져 있다"는 표시예요.

이름은 그리스 신화에서 따왔어요. 바위를 산 위로 계속 밀어 올리는 시시포스처럼, 사람이 옆에서 봐 주지 않아도 끝까지 계속 미는 에이전트를 만들겠다는 뜻이에요. 실제로 이 플러그인의 문서는 "작업 도중 사람이 끼어들어야 했다면 그건 실패 신호"라는 문장을 대놓고 내세워요.

이 발상 자체는 제가 실험이 남긴 네 문제와 도구들 — Agent Teams·Workflows·oh-my-claudecode·herdr에서 본 oh-my-claudecode와 같은 계보예요. 거기서 "모델을 나눌 수 없는 문제"를 푸는 도구로 소개했던 그것이, opencode 쪽에서는 이 Sisyphus로 나타나는 거예요.

비유 — 신문 편집국

기자 한 사람이 신문 한 부를 통째로 만든다고 생각해 볼게요. 기획도 혼자, 취재도 혼자, 사진도 혼자, 교열도 혼자. 가능은 하지만 밤을 새워도 얇은 신문 한 장이 나와요. 무엇보다 자기가 쓴 글을 자기가 검수하니까 빠뜨린 걸 못 찾아요.

실제 편집국은 그렇게 안 돌아가요. 아침에 기획 회의를 해서 오늘 낼 기사 목록을 짜고, 데스크가 "이 각도가 빠졌다"고 지적하고, 편집장이 누구에게 뭘 맡길지 배분해요. 취재기자·사진기자·자료조사원은 각자 다른 사람이고, 원고가 돌아오면 교열부가 한 번 더 훑어요.

편집국에서는Sisyphus에서는
기획 회의에서 오늘의 기사 목록을 짠다Prometheus — 무엇을 어떤 순서로 할지 계획서를 만든다
데스크가 "이 각도가 빠졌다"고 짚는다Metis — 계획에서 빠진 부분을 찾아낸다
내보내도 되는지 최종 확인한다Momus — 계획이 말이 되는지 검증한다
편집장이 배분하고 돌아온 원고를 검수한다Atlas — 작업을 나눠 주고 결과를 따로 확인한다
취재기자 / 사진기자 / 자료조사원Sisyphus-Junior(일반 작업) / Frontend(화면) / Librarian(문서 조사) · Explore(코드 탐색)
인쇄 넘기기 전 교열부가 훑는다주석 검사기, 미완 작업 감시 장치
마감까지 아무도 안 멈춘다"사람 개입 = 실패 신호" 철학

핵심 한 줄: 사람 한 명이 취재·촬영·교열을 다 하지 않듯, 에이전트도 역할을 쪼개면 역할마다 그 일에 맞는 모델을 붙일 수 있어요.

다만 여기서 비유가 끊기는 점은 — 편집국 기자들은 서로 대화하며 조율하지만, 이 에이전트들은 대부분 서로 직접 말하지 않아요. 전부 편집장(Atlas)을 거쳐요. 이건 여러 에이전트를 엮는 방식 중 오케스트레이터-워커라는 특정 구조인데, 다른 구조들과의 차이는 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업에 정리돼 있어요.

전체 흐름 — 3층 구조와 역할별 모델

읽는 법: 위에서 아래로 한 번 흐르고, 맨 아래 화살표가 다시 ②로 돌아가는 순환이에요. 세로선이 갈라지는 지점은 "여기서 여러 명이 동시에 일한다"는 뜻이고, 작업층 상자 아래 붉은 글씨는 그 역할에 기본으로 붙는 모델 계열이에요 — 한 회사 모델로만 다 하지 않는다는 게 이 도구의 핵심 주장이에요.

왜 굳이 모델을 섞나

이게 처음엔 제일 안 와닿았어요. 좋은 모델 하나면 되지 왜 여러 개를 섞나 싶었죠.

이유는 두 가지예요. 하나는 잘하는 게 다르기 때문이에요. 화면 디자인 감각이 좋은 모델과 긴 로그를 뒤져 원인을 찾는 모델이 꼭 같지는 않아요. 다른 하나는 같은 모델은 같은 실수를 하기 때문이에요. 내가 쓴 글을 내가 검수하면 오타를 못 찾는 것과 같아요 — 계획을 세운 모델이 그 계획을 검증하면 자기 논리의 빈틈은 그대로 통과시켜요.

그래서 이 플러그인은 계획을 세우는 쪽과 검증하는 쪽을 아예 다른 역할·다른 모델로 갈라놨어요. 다만 나눈다고 항상 좋아지는 건 아니고 손해도 같이 생기는데, 그 득실을 재는 법은 나누면 좋아질까 — 멀티 에이전트의 득실과 판정표에 있어요.

두 가지 사용 모드

깔고 나면 쓰는 방법이 크게 둘이에요. 초보자는 두 번째부터 쓰는 걸 권해요.

모드어떻게 부르나어떤 상황에 맞나
ultrawork — "그냥 알아서 다 해"부탁하는 문장 안에 ultrawork 또는 ulw라는 단어를 넣는다실패해도 상관없는 연습 폴더. 조사·구현·검증까지 멈추지 않고 혼자 간다
계획 먼저 — Prometheus계획 명령으로 시작해 질문에 답하고, 나온 계획서를 읽은 뒤 /start-work로 실행실제로 쓰는 코드. 내가 읽고 승인한 다음에 손대게 만든다

이 "계획서를 먼저 뽑고 사람이 읽은 뒤 실행"이라는 순서가 바로 플러그인과 명세 주도 개발에서 본 그 방식이에요. 이름만 다르지 같은 얘기예요.

이 밖에 완료될 때까지 스스로 반복하는 /ralph-loop, 검증을 붙여 구조를 정리하는 /refactor 같은 명령이 더 있어요. 반복 루프 자체를 설계 대상으로 보는 관점은 컴파운드 엔지니어링과 루프, 그리고 MCP 다음은 CLI에서 다뤘어요.

나쁜 선택 vs 좋은 선택

편집국 비유를 그대로 이어서 — "새 편집장을 채용한 첫날".

나쁜 선택좋은 선택
첫날부터 오늘 인쇄할 진짜 신문 전체를 맡기고 퇴근한다 → 설치하자마자 실제 업무 저장소에서 ultrawork로 전권을 준 격이에요. 여러 에이전트가 동시에 파일을 고치는데 커밋2을 안 해 뒀다면, 뭐가 원래 코드였는지 되돌릴 방법이 없어요. 사람 한 명이 어질러도 힘든데 넷이 동시에 어지르면 추적이 훨씬 어려워요. 연습용 신문을 한 부 만들어 보게 한다 → 빈 연습 폴더를 만들고, 시작 전에 커밋을 한 번 찍어 되돌릴 지점을 만들어 둬요. 첫 실행은 ultrawork 말고 계획 모드로 — 계획서만 뽑아서 읽어 보고, 납득이 가면 그때 실행시켜요. 나중에 이상해지면 커밋 지점으로 되돌리면 끝이에요.

"에이전트에게 어디까지 맡길 것인가"를 권한의 문제로 정리한 글이 덜어내기와 경계 긋기 — 미니멀과 권한·보안이에요. 에이전트가 여럿이 되면 이 경계 긋기가 훨씬 더 중요해져요.

처음 세팅하는 순서

"쓰는 법"은 알겠는데 "어떻게 해 놓고 써야 하는지"가 막막한 부분인데, 순서만 지키면 어렵지 않아요. ①~③은 플러그인과 무관하게 먼저 해 두는 준비고, ④부터가 설치예요.

① 연습 폴더를 하나 만들고, 되돌릴 지점을 찍어 둔다. 이게 제일 중요해요. 이 안전장치가 없으면 뒤에 뭘 하든 불안해서 제대로 못 시켜요. Git이 처음이면 Git 초보자 가이드 (1)부터 보고 오세요.

실행: 로컬 터미널

mkdir agent-practice
cd agent-practice
git init
git commit --allow-empty -m "start"

② 모델 창구를 먼저 정한다. 이 플러그인은 역할마다 다른 모델을 부르기 때문에, 붙어 있는 제공자가 없으면 반쪽만 돌아요. 이미 쓰는 구독(Claude Pro/Max, ChatGPT Plus, GitHub Copilot 등)이 있으면 그걸 연결하고, 없으면 창구 하나로 시작하면 돼요 — 1편에서 다룬 부분이에요.

③ opencode 버전을 확인한다. 이 플러그인은 opencode 1.4.0 이상을 요구해요. 낮으면 설치가 되더라도 기능이 빠져요.

실행: 로컬 터미널

opencode --version

④ 설치한다. 프로젝트 이름이 oh-my-opencode에서 oh-my-openagent로 넓어졌어요(opencode 말고 다른 도구도 지원하게 되면서요). 설치 명령은 새 이름을 써요. 실행하면 대화형 화면이 떠서 어떤 구독을 연결할지 물어봐요.

실행: 로컬 터미널 — Bun3이 설치돼 있어야 해요

bunx oh-my-openagent install

설정 파일을 직접 만들 필요는 없어요. 설치 도구가 ~/.config/opencode/ 아래에 에이전트 설정 파일을 만들고, 프로젝트의 opencode.json에 플러그인을 등록해 줘요.

⑤ 제대로 붙었는지 확인한다. 여섯 항목을 자동으로 점검해 줘요.

실행: 로컬 터미널

bunx oh-my-openagent doctor

⑥ 첫 실행은 계획 모드로. ultrawork는 익숙해진 다음에 쓰세요. 첫 판은 계획서를 뽑아서 사람이 읽는 것이 목적이에요 — 이 도구가 내 프로젝트를 어떻게 이해했는지가 거기 다 드러나거든요.

⑦ 프로젝트 규칙 파일을 하나 써 둔다. 에이전트가 여럿이 되면 각자 다르게 해석하는 일이 생겨요. "이 프로젝트는 이런 규칙이다"를 파일 하나에 적어 두면 전원이 같은 전제로 시작해요. 쓰는 법은 스킬과 규칙 파일 — 반복 작업을 AI에게 외워 두기에 있어요.

실행: 프로젝트에 AGENTS.md로 저장 — opencode 등 AI 코딩 도구가 세션마다 자동으로 읽어요

# 이 프로젝트

- 정적 HTML 사이트. 빌드 도구 없음.
- 커밋 메시지는 한국어 한 줄로.
- node_modules와 build 폴더는 절대 건드리지 않는다.

⑧ 원치 않으면 사용 통계 전송을 끈다. 익명 사용자 수 집계4가 기본으로 켜져 있어요. 끄는 스위치가 공개돼 있으니 원하면 꺼 두세요.

실행: 로컬 터미널 — 셸 설정 파일(.bashrc 등)에 넣어 두면 매번 적용돼요

export OMO_DISABLE_POSTHOG=1

알아두면 좋은 것들

깔면 무조건 좋아지는 건 아니에요. 역할이 나뉜다는 건 같은 일에 모델을 여러 번 부른다는 뜻이고, 그만큼 토큰이 더 나가요. 짧고 명확한 작업(오타 고치기, 파일 하나 수정)은 오히려 기본 상태가 빠르고 싸요. 이 도구는 "혼자 시키면 중간에 길을 잃는 크기의 일"에 값을 하는 물건이에요.

남이 만든 확장을 켠다는 건 그 사람의 지시문을 내 컴퓨터에서 실행한다는 뜻이에요. 플러그인은 결국 "에이전트에게 주는 지시 + 실행 코드"라서, 안에 뭐가 들었는지 한 번은 열어보고 쓰는 게 안전해요. 이 주의점은 스킬과 규칙 파일에서도 같은 이유로 짚었어요.

같은 발상이 Claude Code 쪽에도 있어요. Claude Code를 쓰신다면 oh-my-claude-sisyphus처럼 같은 구조를 옮겨 놓은 것들이 있어요. 도구 이름만 다르고 "계획을 세우는 쪽과 실행하는 쪽을 나눈다"는 뼈대는 똑같아요. 이런 이식이 가능한 건 Claude Code 자체를 라이브러리로 쓸 수 있게 포장한 것(Claude Agent SDK)이 따로 있기 때문이에요 — 모델 API를 부르는 SDK와 이름이 비슷해 헷갈리는데, 둘의 차이와 "루프를 누가 짜는가"라는 네 갈래는 루프란 무엇인가 — 그리고 그 루프를 누가 짜는가에 갈라 뒀어요.

화면에 뭐가 도는지 보이게 해 두세요. 에이전트를 여럿 돌리면 가장 답답한 게 "지금 뭐 하는 중인지 모르겠다"예요. 그래서 이 계열 도구들이 상태 표시줄(HUD)을 같이 제공해요 — 강사님 화면의 sisyphus 글자도 그 표시줄의 일부예요. 상태가 안 보이는 문제를 도구로 푸는 이야기는 실험이 남긴 네 문제와 도구들에 정리돼 있어요.

직접 해보기

깔자마자 성능을 판단하려 들면 십중팔구 "잘 모르겠다"로 끝나요. 대신 이렇게 재 보세요.

바꿀 것: 플러그인 켬/끔, 딱 하나만.
시킬 것: 파일 서너 개를 건드려야 끝나는 과제 하나 — 예를 들어 "이 정적 사이트에 다크 모드 토글을 붙여 줘". 한 파일로 안 끝나는 크기여야 의미가 있어요.
잴 것: ⓐ 사람이 중간에 끼어들어 방향을 고쳐 준 횟수, ⓑ 총 토큰 사용량, ⓒ 결과물이 한 번에 돌아갔는지.
비교할 것: ⓐ가 줄었는데 ⓑ가 크게 늘지 않았다면 그 크기의 과제에는 값을 하는 거예요. 반대로 ⓐ가 그대로면, 그 과제는 아직 이 도구가 필요한 크기가 아닌 거고요.

"통과했다"만으로는 부족하고 두 층으로 채점해야 한다는 이야기는 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정에 있어요.

함께 읽으면 좋은 글

한 걸음 더: 여기 나온 Prometheus·Atlas 같은 역할이 사실 마크다운 파일 하나로 정의된다는 이야기는 실험이 남긴 네 문제와 도구들의 서브에이전트6 정의 파일 부분에 있어요.

한 걸음 더: 에이전트가 "스스로 반복한다"는 게 원래 어떤 루프인지는 에이전트는 어떻게 스스로 반복할까 — ReAct 루프와 AutoGPT 소동에서 봐요. /ralph-loop가 하는 일이 그 루프의 후손이에요.

  1. 플러그인 — 이미 있는 프로그램에 나중에 끼워 넣어 기능을 늘리는 부품으로, AI 코딩 도구에서의 쓰임은 플러그인과 명세 주도 개발에 있어요. ↩
  2. 커밋 — 지금 상태를 되돌아올 수 있게 저장해 두는 지점으로, 개념은 Git 커밋(commit)이란 무엇인가에 있어요. ↩
  3. Bun — 자바스크립트로 만든 프로그램을 설치하고 실행해 주는 도구이고, bunx는 설치 없이 한 번만 실행할 때 쓰는 명령이에요. ↩
  4. 사용 통계 전송(텔레메트리) — 누가 몇 명 쓰는지 같은 익명 정보를 개발자에게 자동으로 보내는 기능이에요. ↩
  5. 훅(hook) — "이런 일이 생기면 자동으로 저걸 실행하라"고 미리 걸어 두는 장치예요. ↩
  6. 서브에이전트 — 주 에이전트가 일부 작업을 떼어 맡기는 별도의 작은 에이전트로, 여러 구조 비교는 네 가지 구조와 맞는 과업에 있어요. ↩
