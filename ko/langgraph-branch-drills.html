지난 편에서 조건부 엣지로 간 맞추기 그래프를 만들었어요. 강의에는 그 실습 뒤에 "더 해보기" 문제가 세 개 붙어 있었는데, 이번 편은 그 세 문제를 푸는 편이에요. 셋 다 갈림길을 한 번씩 더 밀어붙이는 문제예요. 갈래를 늘리면 어디까지 되는지, 화살표에 이유를 적을 수 있는지, 되돌아가는 선을 아무 데나 그으면 어떻게 되는지요.

이번 편도 API 키 없이 돌아가요. 길은 전부 글자 수를 세는 규칙이 골라요. 라우터 자리에 모델을 앉히는 건 다음 편이에요.

세 문제가 왜 필요한지부터 짚을게요. 갈래를 늘리는 건 6편의 라우팅(입력 종류마다 다른 담당에게 보내기)의 뼈대이고, 되돌아가는 선은 7편의 평가자-최적화자(통과할 때까지 고쳐 쓰기)의 뼈대예요. 여기서 손으로 그어 보는 선이 나중에 패턴이라는 이름으로 다시 나와요.

비유 — 검수대에 갈래가 하나 더 생긴 날

지난 편의 그 주방이에요. 검수대 직원은 원래 두 가지만 했어요. 간이 맞으면 홀로 내보내고, 싱거우면 화구로 되돌려요.

어느 날 세 번째 경우가 생겼어요. 간은 맞는데 한 접시에 담기엔 양이 너무 많은 요리가 올라온 거예요. 사장님은 소분대를 새로 놓고, 검수대에서 그리로 가는 화살표를 동선표에 하나 더 그었어요. 그런데 동선표의 화살표에 아무 글자도 없으니 나중에 보는 사람은 어느 선이 무슨 경우인지 몰라요. 그래서 화살표마다 '통과', '보류', '양 많음'이라고 이유를 적어 뒀어요.

마지막으로 사고가 하나 있었어요. 검수대가 싱거운 요리를 화구로 되돌려 보내면서 전표에 아무것도 안 적었어요. 화구 담당은 똑같은 접시를 똑같은 상태로 받아 그대로 다시 올려 보내고, 검수대는 또 싱겁다고 되돌려 보내요. 둘 다 성실히 일하는데 접시는 영원히 홀로 못 나가요.

비유 속 요소원래 개념
검수대가 고를 수 있는 목적지 목록 (홀 · 화구 · 소분대)add_conditional_edges의 목적지 목록 — 라우터가 돌려줄 수 있는 이름은 이 안에 있어야 해요
소분대를 새로 놓고 화살표를 하나 더 긋기갈래 늘리기 — 노드를 더하고 목적지 목록에 이름을 더해요 (문제 ①)
화살표마다 '통과'·'보류'·'양 많음'이라고 이유 적기라벨 — 목적지를 딕셔너리로 주면 그림의 화살표에 이유가 찍혀요 (문제 ②)
검수대가 화구에게 — 전표에 아무것도 안 적고 되돌려 보내기State가 안 바뀌는 되돌아가기 선 — 끝나지 않는 반복 (문제 ③)
검수대 직원이 전표에 직접 판정을 적으려 하기라우터가 State를 고치려는 시도 — 적은 값이 사라져요 (아래)

핵심 한 줄: 검수대는 어디로 보낼지만 고르고, 전표에 적는 일도 요리를 바꾸는 일도 조리대(노드)의 몫이에요 — 그래서 되돌려 보낼 때는 조리대가 무언가를 바꿔 줘야 반복이 끝나요.

다만 여기서 비유가 끊기는 점이 있어요. 사람 직원이라면 세 번째로 같은 접시를 받았을 때 "어, 아까 그거네" 하고 알아채지만, 그래프는 몇 바퀴째인지 스스로 세지 않아요. 바퀴 수를 세는 칸을 State에 두고 사람이 직접 세든지, 상한을 걸든지 해야 해요.

전체 흐름 — 노트 분량 검사 그래프

아래에서 만들 그래프를 먼저 볼게요. 학생이 올린 공부 노트를 받아 복습 문제를 낼 만할지 가르는 그래프예요. 읽는 법: 점선은 라우터(triage)가 셋 중 하나만 고르는 선이고, 실선은 앞 노드가 끝나면 항상 지나가는 선이에요. 회색 상자 둘과 점선 하나는 문제 ①에서 새로 더할 것이고, 맨 아래 굵은 선은 문제 ③에서 일부러 그어 볼 되돌아가기 선이에요.

갈래 셋 가운데 accept와 flag_too_short만 있는 상태가 출발점이에요. 거기서 하나씩 밀어붙여 볼게요.

갈림길 더 밀어붙이기 — 세 갈래, 라벨, 일부러 만든 무한 반복

강의에는 조건부 엣지 실습(지난 편의 간 맞추기) 뒤에 "더 해보기" 문제가 세 개 붙어 있었어요. 처음엔 강의 코드를 통째로 베껴 넣었더니 실행은 되는데, 무엇을 확인했는지는 하나도 남지 않았어요. 50줄 가운데 문제마다 실제로 바뀌는 건 두세 줄뿐인데, 그 두세 줄이 나머지 속에 묻혀 버렸거든요. 그래서 지난 편의 합치기 규칙 확인하기 때처럼 한 번에 몇 줄만 바꾸고, 돌리기 전에 결과를 먼저 예상한 뒤 실행하는 식으로 다시 풀었어요.

출발점 — 노트 분량 검사 그래프

강의 예제는 학생이 올린 공부 노트를 받아, 복습 문제를 낼 만큼 내용이 충분한지 가르는 그래프였어요. 60자보다 짧으면 보강해 달라고 보류하고, 아니면 출제 대기열로 보내요. 구조는 그대로 두고 코드를 제 식으로 줄여 다시 짰어요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Note(TypedDict):
    text: str       # 올라온 노트 원문
    verdict: str    # 판정 결과

def receive(state: Note):
    print(f"[receive] {len(state['text'])}자 노트 접수")
    return {}                          # 바꾸는 칸이 없으면 빈 딕셔너리

def triage(state: Note) -> str:        # 라우터: 글자 수만 보고 다음 노드 이름을 돌려준다
    if len(state["text"].strip()) < 60:
        return "flag_too_short"
    return "accept"

def flag_too_short(state: Note): return {"verdict": "보류 — 60자 미만이라 보강 필요"}
def accept(state: Note):         return {"verdict": "출제 가능"}

builder = StateGraph(Note)
builder.add_node("receive", receive)
builder.add_node("flag_too_short", flag_too_short)
builder.add_node("accept", accept)
builder.add_edge(START, "receive")
builder.add_conditional_edges("receive", triage, ["flag_too_short", "accept"])
builder.add_edge("flag_too_short", END)
builder.add_edge("accept", END)
graph = builder.compile()

for text in ["State는 딕셔너리다.",
             "State는 노드들이 함께 쓰는 딕셔너리다. 노드는 바꾼 칸만 돌려주고, 나머지 칸은 LangGraph가 그대로 남겨 둔다.",
             "State는 딕셔너리다. " * 250]:        # 같은 문장 250번 = 3500자짜리 긴 노트
    out = graph.invoke({"text": text})
    print(" →", out["verdict"])

돌리기 전에 예상해 보세요. 세 번째 노트(3500자)는 어떻게 판정될까요?

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

[receive] 13자 노트 접수
 → 보류 — 60자 미만이라 보강 필요
[receive] 69자 노트 접수
 → 출제 가능
[receive] 3500자 노트 접수
 → 출제 가능

3500자짜리 노트도 '출제 가능'이에요. 갈래가 둘뿐이라 짧지만 않으면 무조건 통과예요. 문항 하나로는 다 덮을 수 없는 긴 노트를 걸러 낼 길이 그래프에 아예 없는 거예요. 첫 문제는 여기서 출발해요.

① 세 번째 갈래 — 너무 긴 노트는 쪼개기

3000자를 넘는 노트는 따로 빼서 1000자씩 쪼개기로 해요. 바꿀 곳은 네 군데예요. ⓐ 조각을 담을 칸, ⓑ 라우터의 판단 하나, ⓒ 새 노드 둘, ⓓ 목적지 목록의 이름 하나요.

실행: 로컬 파이썬 — 위 코드에서 이 부분만 더하거나 바꿔요

class Note(TypedDict):
    text: str
    verdict: str
    parts: list     # ⓐ 새 칸: 쪼갠 조각

def triage(state: Note) -> str:
    n = len(state["text"].strip())
    if n < 60:
        return "flag_too_short"
    if n > 3000:                       # ⓑ 판단 하나 추가
        return "flag_too_long"
    return "accept"

def flag_too_long(state: Note): return {"verdict": "분할 필요 — 3000자 초과"}   # ⓒ 새 노드 둘
def split_note(state: Note):
    t = state["text"]
    return {"parts": [t[i:i + 1000] for i in range(0, len(t), 1000)]}     # 1000자씩 자르기

builder.add_node("flag_too_long", flag_too_long)
builder.add_node("split_note", split_note)
builder.add_conditional_edges("receive", triage,
                              ["flag_too_short", "accept", "flag_too_long"])   # ⓓ 기존 줄을 이걸로 바꿔요
builder.add_edge("flag_too_long", "split_note")    # 판정 다음엔 항상 쪼개기
builder.add_edge("split_note", END)

# 맨 아래 for 문: 목록은 그대로 두고 print 줄만 이렇게 바꾼 뒤, 그래프 그림을 찍는 줄을 더해요
    print(" →", out["verdict"], "| 조각 길이:", [len(p) for p in out.get("parts", [])])
print(graph.get_graph().draw_mermaid())

flag_too_long과 split_note를 둘로 나눈 데는 이유가 있어요. 목적지를 리스트로 주면 라우터가 돌려준 글자가 곧 노드 이름이어야 해요. 그래서 "flag_too_long"을 돌려주려면 같은 이름의 노드가 있어야 하고, 그 노드가 판정을 적은 뒤 실선을 따라 split_note로 넘겨요. 출력 줄의 .get("parts", [])는 지난 편에서 본 대로, 짧은 노트처럼 parts 칸이 아예 생기지 않은 경우에 빈 목록을 대신 쓰려는 거예요.

개념 설명용 코드 — 제 화면에 찍힌 출력에서 긴 노트의 결과와 화살표 줄만 옮겼어요

[receive] 3500자 노트 접수
 → 분할 필요 — 3000자 초과 | 조각 길이: [1000, 1000, 1000, 500]

__start__ --> receive;
flag_too_long --> split_note;
receive -.-> accept;
receive -.-> flag_too_long;
receive -.-> flag_too_short;
accept --> __end__;
flag_too_short --> __end__;
split_note --> __end__;

receive에서 나가는 점선이 셋이 됐어요(실선·점선 읽는 법은 지난 편 ②에서 봤어요). 목적지 목록에 이름을 더하는 만큼 갈래가 늘어나요. 그리고 flag_too_long --> split_note는 실선이에요. 라우터가 고르는 길은 점선, 판정 뒤에 무조건 가는 길은 실선이라는 게 그림에 그대로 드러나요.

이름을 한 군데라도 안 맞추면 어떻게 되는지도 일부러 틀려 봤어요.

일부러 한 실수나온 에러언제 드러나나
라우터에만 "flag_too_long"을 추가하고, 목적지 목록과 새 노드는 그대로 둠KeyError: 'flag_too_long'실행 도중, 긴 노트가 실제로 들어왔을 때만이에요. 짧은 노트와 보통 노트는 멀쩡히 판정돼요
목적지 목록에는 적었는데 add_node("flag_too_long", ...)를 빠뜨림ValueError: At 'receive' node, 'triage' branch found unknown target 'flag_too_long'1compile()하는 순간이에요. 노트를 하나도 넣기 전에 멈춰요

무서운 건 첫 번째예요. 테스트 삼아 짧은 노트와 보통 노트만 넣어 보면 아무 문제 없이 돌아가다가, 긴 노트가 처음 들어오는 날에야 터져요. 게다가 트레이스백 맨 아래에 During task with name 'receive'라고 찍혀서 receive 노드를 의심하게 되는데, 범인은 receive에 붙어서 도는 라우터예요. 라우터가 돌려줄 수 있는 이름과 목적지 목록이 한 글자도 다르지 않은지는 사람이 맞춰야 해요.

② 라벨 붙이기 — 화살표에 이유 적기

이번엔 라우터가 노드 이름 대신 "보류"·"통과"·"분할" 같은 라벨을 돌려주게 하고, 목적지를 리스트 대신 딕셔너리로 줘요. 딕셔너리는 "이 라벨이 오면 이 노드로"라는 번역표예요.

실행: 로컬 파이썬 — ①까지 고친 코드에서 라우터와 add_conditional_edges 줄만 바꿔요

def triage(state: Note) -> str:
    n = len(state["text"].strip())
    if n < 60:
        return "보류"                  # 노드 이름 대신 라벨을 돌려준다
    if n > 3000:
        return "분할"
    return "통과"

builder.add_conditional_edges("receive", triage,
    {"보류": "flag_too_short", "통과": "accept", "분할": "flag_too_long"})   # 라벨 → 노드 이름 번역표

개념 설명용 코드 — 제 화면에 찍힌 draw_mermaid() 출력 중 점선 세 줄이에요

receive -. &nbsp;통과&nbsp; .-> accept;
receive -. &nbsp;분할&nbsp; .-> flag_too_long;
receive -. &nbsp;보류&nbsp; .-> flag_too_short;

판정 결과는 ①과 똑같은데, 점선 화살표 가운데에 라벨이 끼어들었어요. &nbsp;는 HTML에서 띄어쓰기 한 칸을 뜻하는 기호라서, 이 글자를 GitHub나 Notion에 붙여 그림으로 그리면 화살표 위에 '보류', '통과', '분할'만 보여요. ①에서 화살표에 라벨이 없었던 건 라벨과 노드 이름이 같아서 생략됐기 때문이에요. 노드 이름은 영문으로 두고, 사람이 읽을 라벨만 한국어로 다는 절충이에요.

여기서 두 가지에 걸려 넘어지기 쉬워요.

  • 갈림길을 두 번 붙이기. 주피터나 Colab처럼 코드를 칸 단위로 나눠 돌리는 노트북에서, 원래 코드를 이미 돌린 뒤 바뀐 add_conditional_edges 한 줄만 새 칸에 붙여 실행하면 ValueError: Branch with name `triage` already exists for node `receive`가 나요. 같은 builder의 같은 출발 노드에 같은 라우터로 갈림길을 두 번 붙였다는 뜻이에요. builder = StateGraph(Note)부터 다시 만드는 칸 전체를 돌려야 해요.
  • 번역표에 없는 라벨. 라우터가 번역표에 없는 "합격"을 돌려주게 해 봤더니, ①의 첫 번째 실수와 같은 KeyError: '합격'이 났어요. 라벨을 바꿀 땐 라우터와 딕셔너리를 같이 고쳐요.

③ 일부러 무한 반복 — 되돌아가는데 아무것도 안 바뀌면

flag_too_short에서 END로 가던 선을 receive로 돌려요. 짧은 노트를 '다시 접수'시키는 거예요. 돌리기 전에 예상해 보세요. 13자 노트를 넣으면 몇 번 만에 끝날까요?

실행: 로컬 파이썬 — ②까지 고친 코드에서 엣지 한 줄을 바꾸고, 맨 아래 for 문을 이 한 줄로 바꿔요

그런데 지난 편의 간 맞추기 그래프도 되돌아가는 선이 있었는데 그건 끝났잖아요. 차이는 한 바퀴 돌 때마다 State가 바뀌느냐예요. 간 맞추기에서는 add_salt가 돌 때마다 salt를 1씩 올려서 언젠가 3에 닿아요. 여기서는 되돌아가는 동안 text를 고치는 노드가 하나도 없어요. 똑같은 13자 노트를 똑같은 라우터가 똑같이 판정하니, 몇 바퀴를 돌아도 같은 길이에요. 되돌아가는 선이 의미가 있으려면 소금이든, 시도 횟수든, 고쳐 쓴 초안이든 매 바퀴 무언가가 달라져야 해요.

recursion_limit을 빼고 기본값으로 돌려 봤더니 receive가 5,004번, flag_too_short가 5,003번 돈 뒤에야 10007스텝에서 멈췄어요. 이 노드들이 LLM을 부르는 노드였다면 호출이 만 번 가까이 쌓였을 거예요. 아래 '나쁜 선택 vs 좋은 선택'의 정상 출구가 왜 필요한지 이 숫자가 말해 줘요.

라우터는 길만 고른다 — 전표에 직접 적으면?

이 꼭지는 앞의 세 문제와 달리 코드를 늘리는 게 아니라 줄여서 봐요. 먼저 여태 쓴 말이 코드의 어디를 가리키는지 맞추고 갈게요.

이 글에서 부르는 말코드에서 어디인가
전표 (State)class Note(TypedDict): 아래에 적은 칸 목록이에요. 노드들이 돌려 가며 같이 쓰는 딕셔너리 하나예요
verdict 칸판정 결과를 적어 두는 칸이에요. LangGraph가 아는 이름이 아니라 제가 지은 이름이라, result든 판정이든 아무 이름이어도 똑같이 돌아가요
노드def accept(state):처럼 일을 하는 함수예요. 위에서 return {"verdict": "출제 가능"}처럼 전표에 적는 쪽이었어요
라우터def triage(state):처럼 갈 곳 이름만 돌려주는 함수예요. 여태 return "accept"처럼 글자 하나만 돌려줬어요

그럼 라우터가 길을 고르는 김에 verdict 칸에 판정까지 적어 두면 안 될까요? 강의가 던진 질문인데 답을 몰라서 직접 해 봤어요. 위의 노트 분량 검사 그래프는 이걸 보기엔 너무 커서, 노드 한 개짜리 제일 작은 그래프를 따로 만들었어요. 글자 수를 세는 판단도, 갈래도 없어요. 라우터가 전표를 고쳐 보는 것만 남겼어요.

실행: 로컬 파이썬 — 위 코드와 이어지지 않는 새 파일이에요. 그대로 복사해 돌리면 돼요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Note(TypedDict):                       # ① 전표에 칸 두 개만 둔다
    text: str
    verdict: str

def accept(state: Note):                     # ② 노드는 하나뿐
    print("accept가 본 verdict:", state.get("verdict"))
    return {}

def triage(state: Note) -> str:              # ③ 라우터
    state["verdict"] = "라우터가 적은 판정"   # ④ 실험 1: 라우터가 전표에 직접 적어 본다
    return "accept"                          # ⑤ 갈 곳 이름

builder = StateGraph(Note)
builder.add_node("accept", accept)
builder.add_conditional_edges(START, triage, ["accept"])   # ⑥ 시작하자마자 라우터를 한 번 태운다
builder.add_edge("accept", END)
print("최종 전표:", builder.compile().invoke({"text": "아무 노트"}))   # ⑦

줄마다 무슨 일을 하는지 풀면 이래요. 조립하는 순서는 지난 편과 같아요.

줄하는 일
①전표에 text·verdict 두 칸이 있다고 선언해요. 값을 넣는 게 아니라 칸 이름표를 붙이는 줄이에요
②노드가 받는 state가 전표예요. state.get("verdict")는 그 칸을 꺼내 보되 칸이 없으면 None을 내놔요. return {}는 "전표에 적을 건 없다"는 뜻이에요
③-> str는 이 함수가 글자를 돌려준다는 표시예요. 노드가 아니라 라우터라는 신호이기도 해요
④이번 실험의 한 줄이에요. 노드처럼 돌려주는 게 아니라, 받은 전표의 verdict 칸에 그 자리에서 적어요
⑤돌려주는 글자는 다음에 갈 곳의 이름이에요. 여기선 갈 곳이 accept 하나뿐이라 늘 같은 값이에요
⑥출발점이 START라서, 노드를 거치기도 전에 라우터부터 돌아요. 뒤의 ["accept"]가 목적지 목록이에요
⑦invoke(...)에 넣은 딕셔너리가 처음 전표예요. 다 돌고 난 마지막 전표가 그대로 돌아와요

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

accept가 본 verdict: None
최종 전표: {'text': '아무 노트'}

라우터가 적은 글씨가 어디에도 없어요. 바로 다음에 도는 accept도 못 봤고(None), 마지막에 돌아온 전표에는 verdict라는 칸 자체가 안 생겼어요. 라우터 함수 안에서 분명히 적었는데요.

이유는 이래요. LangGraph는 노드나 라우터를 부를 때마다 전표를 새 딕셔너리로 떠서 건네줘요. 그리고 그 사본에서 값을 거둬 가는 통로는 딱 하나, 노드가 return으로 돌려주는 딕셔너리예요. 라우터가 돌려준 "accept"는 갈 곳 이름으로만 읽히니, 사본에 적은 글씨는 함수가 끝나는 순간 같이 버려져요.

그럼 칸에 리스트가 들어 있으면 어떨까요. 위 코드에서 네 군데만 고쳐요.

실행: 로컬 파이썬 — 위 파일에서 이 줄들만 바꿔요

class Note(TypedDict):
    text: str
    verdict: str
    history: list                        # 바꾼 곳 1: 리스트가 든 칸을 하나 더 둔다

def accept(state: Note):
    print("accept가 본 history:", state["history"])   # 바꾼 곳 2: 찍어 볼 칸을 바꾼다

def triage(state: Note) -> str:
    state["history"].append("router")    # 바꾼 곳 3: 칸에 새로 적는 대신, 칸에 든 리스트 '안'을 고친다

처음전표 = {"text": "아무 노트", "history": ["시작"]}      # 바꾼 곳 4: 시작값을 변수에 담아 넣고

이번엔 'router'가 남았어요. 같은 라우터 안의, 비슷하게 생긴 한 줄인데 실험 1과 결과가 정반대예요. 마지막 줄은 더 이상해요. 그래프 바깥에 있는 제 변수 처음전표의 리스트까지 바뀌어 있어요. 그래프에 넣기만 했는데요.

이건 LangGraph가 정한 규칙이 아니라 파이썬이 딕셔너리를 복사하는 방식이에요. 사본을 뜰 때 칸은 새로 만들지만, 칸에 든 값까지 새로 만들지는 않아요. 글자나 숫자가 든 칸에는 값이 그대로 찍히고, 리스트가 든 칸에는 그 리스트가 놓인 자리가 찍혀요. langgraph 없이 여섯 줄로 재현돼요.

실행: 로컬 파이썬 — langgraph도, API 키도 필요 없어요

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

원본에는 verdict가 없는데 'router'는 들어가 있어요. 마지막 줄의 True가 이유예요. 두 딕셔너리의 history 칸은 같은 리스트 하나를 가리키고 있어서, 어느 쪽으로 열어 고치든 같은 곳이 바뀌어요. 반대로 verdict는 사본에만 생긴 칸이라 원본은 그런 칸이 있었다는 것도 몰라요. 그래프에서도 마찬가지라, 라우터는 전표에 적는 통로를 쓴 게 아니라 리스트를 옆에서 직접 고친 거예요. 그래서 'router'가 누구 손에 언제 들어갔는지는 그래프 어디에도 안 남아요.

마지막으로, 라우터를 아예 노드처럼 만들면 어떻게 될까요. 실험 1의 코드에서 라우터 본문 두 줄을 한 줄로 바꿔요.

실행: 로컬 파이썬 — 실험 1의 파일에서 triage 본문만 바꿔요

def triage(state: Note):
    return {"verdict": "라우터가 적은 판정"}   # 노드처럼 딕셔너리를 돌려준다

개념 설명용 코드 — 제 화면에 찍힌 트레이스백의 마지막 세 줄이에요

    r if isinstance(r, Send) else self.ends[r] for r in result
                                  ~~~~~~~~~^^^
TypeError: unhashable type: 'dict'

이 트레이스백2은 LangGraph 안쪽 코드라 우리가 쓴 줄이 아니에요. 그래도 가운데 줄의 물결과 화살표가 어디서 터졌는지 짚어 줘요. self.ends가 목적지 번역표이고, [r]의 r이 라우터가 돌려준 값이에요. 우리가 돌려준 딕셔너리가 대괄호 안, 열쇠 자리에 들어간 거예요. 파이썬은 열쇠로 쓸 값에서 짧은 번호를 하나 뽑아 두고 그 번호로 찾아가는데, 리스트와 딕셔너리는 나중에 안이 바뀔 수 있어서 번호를 못 뽑아요. 그게 unhashable이라는 말이에요.

이 실험은 목적지를 ["accept"]라는 리스트로 줬는데도 번역표에서 터졌어요. LangGraph가 리스트를 받으면 속으로 {"accept": "accept"}처럼 이름이 열쇠이자 값인 번역표로 바꿔 두기 때문이에요. 목적지를 리스트로 주든 ②처럼 딕셔너리로 주든, 라우터가 돌려준 값은 결국 열쇠로 쓰여요.

세 실험을 한 표로 모으면 이래요.

라우터 안에서 한 일결과왜 그런가
실험 1 — state["verdict"] = ...로 칸에 새 값 적기사라짐. 다음 노드도, 최종 전표도 verdict가 없어요라우터가 받은 전표는 매번 새로 뜬 사본이라, 사본에 적은 글씨는 원본으로 안 가요
실험 2 — state["history"].append(...)로 리스트 안을 고치기남음. 'router'가 끼어들었어요사본의 리스트 칸이 원본과 같은 리스트를 가리켜서, 그 안을 고치면 원본까지 바뀌어요. LangGraph가 받아 준 변경이 아니라 새어 들어간 거예요
실험 3 — {"verdict": ...} 딕셔너리를 돌려주기멈춤. TypeError: unhashable type: 'dict'라우터의 반환값은 목적지 번역표에서 이름을 찾는 열쇠로 쓰이는데, 딕셔너리는 열쇠가 될 수 없는 자료형이에요

중요꼭 기억할 것

라우터가 돌려주는 값은 '다음에 갈 곳의 이름'으로만 읽혀요. 전표에 값을 적는 통로는 노드가 돌려주는 딕셔너리 하나뿐이에요. 그래서 라우터 안에서 전표를 고치면 적은 값이 사라지거나(실험 1), 기록 없이 몰래 새어 들어가거나(실험 2), 목적지를 못 찾고 멈춰요(실험 3). 라우터는 읽기만 하고, 적는 일은 노드에게 맡겨요.

셋 중 제일 위험한 건 실험 2예요. 되는 것처럼 보여서 믿고 쓰게 되는데, verdict 같은 글자 칸은 리스트처럼 제자리에서 고칠 방법이 없어서 결국 실험 1처럼 새 값을 적게 되고, 그 값은 조용히 사라지거든요. 판정 결과를 남기고 싶으면 판정을 적는 노드를 따로 두면 돼요. 문제 ①의 flag_too_long이 딱 그런 노드예요. 라우터는 "flag_too_long"이라는 이름만 돌려주고, 전표에 "분할 필요 — 3000자 초과"를 적는 건 같은 이름의 노드가 했어요.

세 문제에서 남은 것

문제바꾼 곳확인한 것
① 세 번째 갈래라우터에 판단 하나, 목적지 목록에 이름 하나, 노드 둘갈래는 필요한 만큼 늘릴 수 있어요. 대신 라우터가 돌려줄 이름과 목적지 목록은 사람이 맞춰야 해요
② 라벨라우터의 반환값, 목적지를 리스트에서 딕셔너리로라벨이 노드 이름과 다르면 그림의 화살표에 갈래의 이유가 적혀요
③ 무한 반복선 하나를 END에서 receive로되돌아가는 선은 매 바퀴 State가 바뀌어야 끝나요. 상한은 기본값에 맡기지 말고 직접 걸어요
라우터가 전표에 적기라우터 안에서 State 고치기적은 값은 사라지거나 몰래 새어 들어가요. 전표에 적는 건 노드의 일이에요

나쁜 선택 vs 좋은 선택 — 되돌아가는 선을 그을 때

같은 주방에서, 검수대가 퇴짜 놓은 요리를 화구로 되돌려 보내는 선을 그린다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: flag_too_short에서 END로 가던 선을 receive로 돌려 "다시 접수"시켰어요. 되돌아가는 동안 text를 고치는 노드는 하나도 두지 않았고, 멈추는 건 상한에 맡겼어요.

무슨 일이 생기나: 똑같은 13자 노트를 똑같은 라우터가 똑같이 판정하니 몇 바퀴를 돌아도 같은 길이에요. 기본값으로 돌리면 receive 5,004번, flag_too_short 5,003번을 돈 뒤 10007스텝에서 GraphRecursionError로 끊겨요. 그 노드가 LLM을 부르는 노드였다면 호출이 만 번 가까이 나갔고, 결과는 예외와 함께 사라져요.		 무엇을 했나: 되돌리기 전에 무엇이 바뀌는지부터 정했어요. "보강 요청을 보내고 학생이 고쳐 올린 text를 받는 노드"를 사이에 두거나, 그게 없으면 tries 칸을 세는 노드를 두고 상한을 넘으면 사람에게 넘기는 정상 출구를 그렸어요.

무슨 일이 생기나: 매 바퀴 State가 달라지니 언젠가 판정이 바뀌고, 안 바뀌어도 정상 출구로 빠져 결과가 돌아와요. verdict 칸에 "보강 요청 3회 초과"가 남아서 왜 덜 끝났는지가 드러나요.

정리하면 되돌아가는 선을 그을 때 물을 건 하나예요. "이 바퀴에서 전표의 무엇이 바뀌나?" 답이 "없음"이면 그건 반복이 아니라 무한 루프예요.

이 글에 나온 숫자 — 반복을 그리기 전에 볼 것

이 편에서 다른 그래프를 짤 때도 그대로 쓰이는 숫자만 모아 뒀어요. 예제가 몇 자를 몇 조각으로 잘랐는지 같은 실행 기록은 본문에 있는 그대로가 전부라 여기 옮기지 않았어요. 남은 세 줄은 전부 되돌아가는 선을 그릴 때 물리는 값이에요.

무엇의 숫자인가값알아 둘 것

내 파이프라인에 대입하면 — 스텝 하나를 받았을 때의 세 갈래

이 편의 세 문제가 블로그 글 만들기에서는 이렇게 나와요.

① 세 갈래. 강의 스텝 하나를 받으면 갈 곳이 셋이에요. 짧고 얕으면 합치기(다음 스텝과 한 편으로), 알맞으면 그대로, 길고 빽빽하면 쪼개기(두 편으로). 위의 짧은 노트·보통 노트·긴 노트와 같은 모양이에요.

② 이름 어긋남. 판정하는 쪽이 "쪼개기"를 돌려주는데 목적지 목록에는 "분할"로 적어 뒀다면, 짧은 스텝과 보통 스텝만 넣어 본 날은 멀쩡히 지나가요. 처음으로 긴 스텝이 들어오는 날에야 터져요. 갈래를 늘렸으면 그 갈래로 실제로 가는 입력을 한 번은 넣어 봐야 하는 이유예요.

③ 끝나지 않는 반복. 이 블로그에는 "비유가 그 편 내용에 안 맞으면 다시 쓴다"는 규칙이 있어요. 이걸 되돌아가는 선으로 그려 놓고, 다시 쓰는 쪽이 지난번 지적을 못 받아 보면 같은 비유를 또 써요. 전표가 안 바뀌니 같은 자리를 계속 돌아요. 바퀴 수를 적는 칸과 빠져나가는 출구가 필요한 게 이 자리예요.

여기까지는 길을 전부 규칙이 골랐어요. 글자 수를 세는 if문이 라우터였으니까요. 다음 편에서는 그 라우터 자리에 모델을 앉혀요. 모델이 "이 질문에 답하려면 재고를 조회해야겠다"고 판단하면 도구를 부르는 쪽으로, 다 알았으면 답을 쓰는 쪽으로 가는 루프를 조립해요. 1편의 자율성 눈금자에서 한 칸 오른쪽으로 옮기는 거예요.

함께 읽으면 좋은 글

  • 흐름을 그림으로 짠다 — LangGraph의 State·Node·Edge — 이 편이 밀어붙이는 조건부 엣지를 처음 그은 앞 편이에요.
  • 코딩 에이전트에게 흐름을 맡기고, IF 노드로 갈림길 만들기 — 같은 갈림길을 n8n 화면에서 만든 글이라, 코드와 화면을 나란히 보면 좋아요.
  • 끝날 때까지 따라가기 — 실행 흐름·상태·승인과 종료 조건 — "중단을 완료로 표시하지 말라", 즉 반복의 정상 출구를 설계하는 이야기를 먼저 다룬 글이에요.
  1. ValueError — 값의 자료형은 맞지만 그 내용이 허용되지 않을 때 파이썬이 내는 에러로, 여기서는 목적지 목록에 적힌 노드 이름이 그래프에 없다는 뜻이에요. ↩
  2. TypeError — 그 자리에 쓸 수 없는 자료형의 값이 들어왔을 때 파이썬이 내는 에러예요. ↩
