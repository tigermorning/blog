과거에 쓰던 스크립트(컴퓨터에게 시킬 일을 적어 둔 파일)를 그대로 실행하려다 보니, 그 경로가 BGE(예전에 쓰던 임베딩 모델 이름)의 384차원 벡터를 남긴다는 걸 알게 됐어요. 차원이란 숫자 목록의 칸 수예요. 화면의 숫자 배열은 정상처럼 보여요. 하지만 질문이 다른 공간에서 만들어졌다면 가깝다는 판단 자체가 성립하지 않아요. 문서와 질문의 출발점부터 맞춰야 한다는 게 오늘의 핵심이었어요.

1. 문장을 숫자로 바꾸는 이유

컴퓨터는 글자의 뜻을 바로 비교하지 못해요. 그래서 모두콘 문서를 검색할 수 있게 하려면, 문장을 숫자 목록(벡터)으로 바꿔 두어야 해요. 뜻이 비슷한 문장은 비슷한 숫자 목록이 되어, 지도 위에서 가까운 점처럼 찾을 수 있어요. 쓰는 모델(숫자 목록을 만들어 주는 프로그램)은 onnx-community/embeddinggemma-300m-ONNX예요. 이 모델이 각 문장과 질문을 768차원 벡터 하나로 바꿔요.

첫 방문에서는 모델 파일 약 200MB를 받아야 하고, 첫 로드는 5~15초가 걸릴 수 있어요. 화면이 멈춘 것처럼 보이지 않게 진행 상태와 캐시(한 번 받은 파일을 저장해 두는 곳) 여부를 보여줘야 해요. 한 가지는 꼭 기억해 두세요. 임베딩은 답을 만드는 과정이 아니라, 답의 근거 후보를 찾기 위한 색인(찾아보기 목록을 만드는) 과정이에요.

2. 캐시는 성능 장식이 아니라 재방문 경험의 계약

모델 파일을 질문할 때마다 다시 받으면, 검색을 시작하기도 전에 사용자가 기다려요. 브라우저가 알아서 해 주는 HTTP 캐시만 믿기는 어려워요. Hugging Face(AI 모델을 모아 둔 사이트)의 주소가 서명된 CDN(파일을 빨리 나눠 주는 서버) 주소로 넘어가면서, 저장해 둔 파일을 못 찾을 수 있기 때문이에요.

그래서 원래 주소(URL)를 이름표(키)로 삼아 Cache Storage(브라우저 안의 저장 공간)에 직접 보관해요. 이미 저장돼 있으면 완료 상태와 캐시 사용 여부를 바로 알려 주는 편이 좋아요. Cache Storage 저장이 실패할 수도 있어요. 한 번 다시 시도해도 실패하면 다운로드를 계속하는 길을 남겨 두세요. 브라우저에 따라 저장이 보장되지 않을 수 있다는 점도 기억해 두세요.

3. 기본 파이프라인이 멈추는 지점을 우회하기

브라우저에서 pipeline()을 곧바로 부르면 코드는 짧아 보여요. 하지만 기본으로 q4/q8(용량을 줄인 모델 형식)이 선택되면 실패할 수 있어요. WASM(브라우저 안에서 빠르게 도는 실행 형식) 위의 ONNX Runtime(ONNX 형식 모델을 실행하는 엔진)이 GatherBlockQuantized라는 계산을 지원하지 않기 때문이에요. 여기서 막히는 게 정상이에요.

해결은 모델 전체를 포기하는 게 아니라 역할을 나누는 것이에요. 토크나이저(문장을 낱말 조각 번호로 쪼개는 도구)는 transformers.js의 AutoTokenizer를 써요. 추론 세션(모델에 입력을 넣고 결과를 받는 한 번의 실행 창구)은 model_no_gather_q4.onnx와 데이터 파일을 ONNX Runtime에 직접 넘겨서 만들어요. 이때 WASM 실행 공급자(계산을 맡을 방식)를 지정해요.

아래 코드는 읽기만 해도 돼요. 토크나이저를 불러오고, 추론 세션을 WASM 방식으로 만드는 두 단계를 보여 줘요.

개념 설명용 코드 — 앱 내부 구현 일부, 직접 실행하는 코드 아니에요

// rag.ts의 핵심 경로를 짧게 확인합니다.
const tokenizer = await AutoTokenizer.from_pretrained(modelId);
const session = await ort.InferenceSession.create(modelUrl, {
  executionProviders: ["wasm"],
});

이 우회는 문서 임베딩과 브라우저 질문 임베딩이 같은 모델 계열의 계산을 거치게 하는 조건이기도 해요. 에이전트(코딩을 맡기는 AI)에게 오류 문구만 던지면 부족했어요. 토크나이저와 ORT 세션을 나눠야 하는 이유, 그리고 no_gather_q4 파일을 써야 하는 조건을 함께 요구해야 했어요.

4. 평균을 만들고 길이를 맞춰야 비교가 공정해진다

모델은 낱말 조각(토큰)마다 숫자 목록을 하나씩 내놓아요. 이 출력이 last_hidden_state예요. 그런데 우리에게 필요한 건 문장 하나당 벡터 하나예요. 그래서 하나로 줄이는 규칙이 필요해요.

먼저 attention_mask(진짜 낱말과 빈칸 채우기를 구분하는 표시)가 가리키는 실제 토큰만 평균 내요. 이걸 mean pooling이라고 해요. 그다음 벡터의 길이가 1이 되도록 맞춰요. 이걸 L2 정규화라고 해요. 이 순서를 빼면 패딩(길이를 맞추려고 채운 빈 토큰)이 문장 표현에 섞여요. 문장 길이 차이가 점수에 너무 크게 영향을 줄 수도 있어요.

정규화한 벡터끼리는 내적(같은 칸끼리 곱해 더한 값)이 곧 코사인 유사도(두 벡터가 얼마나 같은 방향인지 나타내는 점수)가 돼요. 그래서 검색 단계에서 길이를 또 맞출 필요가 없어요.

구현을 맡기는 에이전트에게는 세 가지를 분명히 말해야 해요. 출력 텐서의 첫 값만 쓰지 말 것, 마스크를 분모와 분자에 함께 반영할 것, 0으로 나누는 경우를 막을 것이에요. 작은 생략 하나가 검색 결과 전체를 한쪽으로 치우치게 할 수 있어요.

5. 차원이 같아도 공간이 다르면 소용없다

과거 BGE 경로는 384차원 벡터를 만들었어요. 지금 코퍼스(검색 대상 문서 모음)는 Gemma의 768차원 벡터를 써요. 이 둘을 섞으면 이런 일이 생겨요.

이렇게 섞으면생기는 일
384차원(BGE)과 768차원(Gemma)계산 자체가 실패하거나 의미 없는 거리를 만든다
차원이 우연히 같아도 서로 다른 모델의 공간 (더 위험한 경우)숫자가 나오더라도 가까움의 뜻이 보장되지 않는다

그래서 문서 벡터를 만들 때 쓴 모델, pooling 방식, 정규화 규칙을 질문 임베딩에도 똑같이 적용해요. 그리고 벡터스토어(벡터를 모아 둔 파일)에는 어떻게 만들었는지 확인할 수 있는 경로를 남겨 두세요.

6. 실습 — 문서 벡터스토어를 에이전트와 함께 만들기

embed-docs-browser-path.mjs는 Node(내 컴퓨터에서 자바스크립트를 실행하는 도구)에서 같은 모델의 feature-extraction pipeline(문장에서 숫자 특징을 뽑는 흐름)을 써요. dtype:"q4", pooling:"mean", normalize:true 조건으로 문서 벡터를 만들어서 app/public/moducon-docs.json에 둬요. 아래 글은 직접 코딩 에이전트에 붙여 넣는 요청문이에요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

모두콘 공개 문서 청크 배열을 읽어 브라우저 RAG용 벡터스토어를 만드는
embed-docs-browser-path.mjs를 작성합니다. onnx-community/embeddinggemma-300m-ONNX를

벡터 길이를 확인했으면, 과거 스크립트가 만든 결과를 새 파일에 섞지 않아요. 문서와 질문이 모두 같은 Gemma 경로를 지나게 한 뒤에야 검색 점수를 읽어요. 이제 남는 질문은 파일이 만들어졌는지가 아니에요. 실제 질문에서 관련 청크(문서를 잘라 놓은 조각)가 위로 올라오는지예요.

7. 검색 결과를 스팟체크로 읽기

생성 명령이 성공했다는 메시지만으로는 벡터스토어가 맞는지 알 수 없어요. 스팟체크(몇 군데를 골라 직접 확인하기)를 해요. check_retrieval.py 같은 점검 도구에 예상 질문을 넣고, top-1(1등)과 top-3(3등까지)에 어떤 청크가 놓이는지 읽어요.

문서에 근거가 있는 질문은 관련 청크가 위에 나오는지 봐요. 문서 범위 밖 질문은 엉뚱한 청크가 정답처럼 보이지 않는지도 함께 봐요. 1등이 기대와 다르면 곧바로 임계값(통과 기준 점수)을 바꾸지 마세요. 질문과 문서가 같은 임베딩 경로를 지났는지, 청크의 경계가 알맞은지를 뒤에서부터 차례로 점검해요. 아래 한 줄은 직접 실행해 보는 명령이에요.

실행: 로컬 터미널

python3 check_retrieval.py

정리

임베딩은 답을 만드는 단계가 아니라 근거 후보를 찾는 색인 단계예요. 이걸 자꾸 잊기 쉬워요. 질문과 문서가 같은 공간에 있어야 거리가 뜻을 가져요. 오늘 배운 걸 한 문장으로 줄이면 이거였어요. 다음 편에서는 이렇게 만든 벡터스토어에서 가까운 청크를 고르는 하이브리드 검색으로 넘어가요.

이럴 때 의심하세요 — 벡터는 만들어졌는데 검색이 이상할 때

임베딩 단계의 실수는 대부분 에러 없이 지나가요. 숫자 배열은 정상처럼 보이고 "생성 완료" 메시지도 떠요. 그래서 이상함은 한참 뒤 검색 결과에서 처음 드러나요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
검색 결과가 질문과 아무 관계없는 조각만 올라온다. 또는 점수 계산에서 길이가 안 맞는다는 오류로 멈춘다 문서 벡터를 만든 스크립트와 질문을 임베딩하는 코드, 두 곳의 모델 이름이다. 검색 함수나 임계값이 아니다 두 곳의 모델 이름이 글자까지 같은지 본다. 그리고 벡터 파일에서 배열 길이를 센다 — 예전 BGE 경로의 384와 지금 Gemma의 768이 섞여 있으면 그거다. 길이가 우연히 같아도 모델이 다르면 "가깝다"의 뜻이 보장되지 않는다
어떤 질문은 되고 어떤 질문은 이상한데 규칙이 안 보인다. 상위 결과가 질문을 크게 바꿔도 거의 그대로다 pooling과 정규화 규칙이다. 문서 쪽은 pooling:"mean"·normalize:true로 만들었는데 질문 쪽은 출력 텐서를 그대로 쓰고 있지 않은지 본다 같은 문장 하나를 문서 경로와 질문 경로에 각각 넣어, 나온 두 벡터를 앞 몇 개 값만 비교한다. 같은 문장인데 값이 다르면 경로가 갈린 것이다. 이때는 임계값을 만질 게 아니라 임베딩을 다시 만들어야 한다
질문을 하려는데 화면이 몇 초씩 멈춘 것처럼 있고, 새로고침할 때마다 똑같이 그런다. 개발자 도구 네트워크 탭에 큰 모델 파일 내려받기가 매번 새로 뜬다 모델 파일을 받는 코드에서 Cache Storage에 저장하는 부분과, 저장할 때 쓰는 키다 개발자 도구의 저장소 화면에서 Cache Storage에 그 URL이 들어가 있는지 본다. 비어 있으면 저장이 안 되고 있는 것이고, 원래 주소가 서명된 CDN 주소로 넘어가며 키가 매번 달라지는 경우를 먼저 의심한다. 첫 로드는 원래 200MB·5~15초가 걸리니, 두 번째 방문부터도 그러면 캐시 문제다
벡터 생성 명령이 성공했다고 나왔는데 검색은 계속 이상하다 만들어진 벡터 파일 자체다. 명령의 출력 메시지가 아니다 모든 vector의 길이가 768인지 세고, 예상 질문 몇 개를 넣어 top-1·top-3에 무엇이 올라오는지 읽는다. 문서에 근거가 있는 질문에서 관련 조각이 위로 올라오지 않으면, 파일이 생겼다는 사실은 아무것도 보장하지 않는다

네 줄 모두 임계값을 만지기 전에 보는 자리다. 결과가 기대와 다를 때 먼저 손이 가는 건 점수 기준이지만, 이 단계가 어긋났으면 기준을 아무리 옮겨도 순서가 제자리로 돌아오지 않는다.
