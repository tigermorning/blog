프레임워크 고르는 법과 AI와 기획하기

2026. 7. 16.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

← 이전 편 추상화·모듈화·가상 DOM

지난 글까지 프레임워크가 뭐고 왜 필요한지 알았으니, 이제 진짜 질문이 남았어요. "그래서 나는 뭘 골라야 하지?" 결론부터 말하면, 다 배울 필요는 없어요. 대신 판단할 수 있어야 해요.

"많이 쓴다"와 "나한테 맞다"는 다른 말이었다

Stack Overflow의 2025년 개발자 설문(4.9만 명)을 보면 프런트엔드 사용률은 React 44.7%로 1위(2위 Angular 18.2%, 3위 Vue 17.6%)였고, 메타프레임워크인 Next.js는 21.5%였어요. 그런데 같은 조사에서 개발자 만족도는 완전히 다르게 나왔어요. State of JS 2024 기준으로 만족도 1위는 Svelte(약 74%)였고, 오히려 React 만족도는 62%로 내려가는 중이었어요.

이 숫자가 알려주는 건 하나예요. 많이 쓰는 것과 내 조건에 맞는 것은 다른 질문이라는 거죠. 그럼 공식 문서가 스스로를 어떻게 설명하는지 보면 각자 뭘 다르게 풀고 싶은지가 보여요.

  • React — "UI를 렌더링하는 JavaScript 라이브러리." 컴포넌트 사고를 널리 퍼뜨렸어요.
  • Vue — "UI를 만들기 위한 JavaScript 프레임워크." 점진적으로 도입할 수 있는 구조를 앞세워요.
  • Angular — Google이 유지하며, 라우팅·폼·업데이트 도구 묶음이 강해서 큰 조직의 장기 운영 서비스에 자주 쓰여요.
  • Svelte — 컴파일러로 브라우저가 할 일을 미리 줄여둬요.
  • Solid — 반응형 UI 성능을 극한까지 밀어붙여요.
  • Qwik — 서버에서 만든 상태를 브라우저가 이어받는 resumability를 강조해요.

여기서 헷갈렸던 것 하나 — React(UI 라이브러리) → Next.js(React 기반 메타프레임워크)라는 관계였어요. Next.js는 React에 라우팅·서버 렌더링·배포까지 하나로 묶어준 도구고, Vite는 이들과 경쟁하는 대안이 아니라 개발·빌드 도구라서 아예 다른 범주였어요.

2026년의 새 판단 기준 — "AI가 이 프레임워크로 정확히 짜주는가"

여기서부터가 제일 흥미로웠어요. "문법은 AI가 다 짜주니 아무거나 골라도 되지 않나?"라고 생각했는데, 오히려 정반대였어요. AI가 프레임워크마다 코드를 짜는 정확도가 실제로 다르다는 근거가 있었거든요.

프런트엔드 코드 생성을 평가한 학술 벤치마크 DesignBench(arXiv:2506.06251, 2025)에서, 최신 AI 모델들은 React·Vue로는 컴파일 성공률이 83%를 넘겼지만 Angular는 69~76%로 눈에 띄게 낮았어요. AI 코딩 벤치마크들이 기준 프레임워크로 React를 자주 고르는 이유도 "학습 데이터에 가장 많이 담겨 있어서"였고요. 즉 공개 자료가 많은 프레임워크일수록 AI의 첫 코드가 정확했어요. 여기에 하나 더 — "이건 이렇게 하는 게 정석"이라는 규칙이 강한 프레임워크는 AI가 매번 비슷한 구조로 코드를 내지만, 자유도가 아주 높은 도구는 부를 때마다 구조가 달라져서 제가 검토하고 고칠 게 많아져요.

그래서 정리하면 이래요. 자료와 AI 지원을 최우선으로 친다면 React 계열이 무난한 출발점이고, 코드 간결함이나 개발 경험을 중시한다면 Svelte 같은 선택도 충분히 합리적이에요. 직접 확인하는 법도 배웠는데, 후보가 정해졌으면 AI에게 같은 요청("상품 목록 화면 만들어줘")을 세 번 시켜보면 돼요. 세 번 다 구조가 비슷하면 그 프레임워크는 AI와 궁합이 좋은 거고, 매번 딴판이면 나중에 고치기 어려워져요.

판단 축 6가지 — 정답 하나가 아니라 근거 비교

AI 친화도AI가 정확한 코드를 잘 짜나요?첫 코드 품질과 리뷰 부담을 가장 크게 좌우

정답 하나를 찾으려 하면 금방 지쳐요. 후보를 2~3개로 좁히고 근거를 비교하는 편이 훨씬 현실적이었어요.

"뭐가 좋아요?" 대신 — AI를 인터뷰어로 쓰는 3단계

좋은 개발은 "○○ 만들어줘" 한 방으로 시작하지 않았어요. 무엇을 만들지 AI와 주고받으며 정하는 게 훨씬 좋은 결과를 냈어요.

1단계 — AI에게 나를 인터뷰하게 하기. 한 번에 다 설명하려 하지 말고 AI가 되묻게 만들어요.

내가 만들고 싶은 건 [수제 디저트 온라인 가게]인데,
[선물 사는 사람이 편하게 고르도록] 하고 싶어.
구체적인 PRD를 짜기 위해 정해야 할 것들을, 한 번에 하나씩 나에게 물어봐줘.

이러면 AI가 "주 사용자는 누구인가요? 상품은 어떻게 분류되나요?"처럼 되물어와요. 모르는 항목은 "아직 모르겠어, 네가 제안해줘"라고 답해도 괜찮았어요.

2단계 — 프레임워크를 추천받기.

이제 이 서비스를 만들기에 어떤 프레임워크가 좋을지,
3개 이상 장단점과 함께 추천해줘.

여기서 나온 답은 곧이곧대로 받아들이지 않고, "왜 이걸 추천했는지", "내 조건에서도 정말 맞는지"를 한 번 더 되물었어요.

3단계 — PRD로 정리받기.

지금까지 정한 내용을 PRD로 작성해줘.
추후 백엔드(로그인·저장·결제) 기능을 추가할 것도 고려해서 정리해줘.

이 PRD가 오늘 만들 것의 뼈대이자, 나중에 백엔드 기능을 붙여나갈 때의 길잡이가 됐어요. 강의에서 강조한 게 인상 깊었는데, 지금 단계에서는 문법을 파고드는 것보다 AI와 함께 만든 이 PRD를 꼼꼼히 읽는 게 훨씬 좋은 공부였어요. 코드가 무엇을, 왜 하려는지 위에서 내려다보는 눈이 생겨야, AI가 만든 결과도 판단할 수 있으니까요.

정리

프레임워크는 "제일 좋은 거 하나"를 찾는 게 아니라, 내 조건(AI 친화도·러닝커브·생태계·자료·유지보수·트레이드오프)에 맞는 후보를 좁히고 근거를 비교하는 문제였어요. 그리고 그 조건 자체도 AI와 대화하며 인터뷰-추천-PRD 3단계로 정리할 수 있었고요. 프레임워크와 기획이 끝났으니, 이제 실제로 화면을 만들 때 부딪히는 첫 벽 — 백엔드가 아직 없는데 어떻게 화면을 채우느냐 — 을 다음 글에서 다뤄볼게요.
