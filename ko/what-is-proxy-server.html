프록시 서버란 무엇인가 — API 키를 대신 들어주는 서버

2026. 8. 28.

지난 글에서 API 키를 프론트 코드에 넣으면 개발자 도구로 다 보인다고 했었죠. 그럼 이 키를 대체 어디에 둬야 하나 궁금했는데, 답은 의외로 간단했어요 — 브라우저가 아니라 서버가 대신 들고 있으면 돼요. 이 역할을 하는 서버를 프록시(proxy) 서버라고 불러요.

안내 데스크를 거치는 이유

회사 로비를 생각해보면 이해가 쉬워요. 방문객은 사원증이 없어서 사무실 문을 직접 못 열어요. 대신 안내 데스크에 용건만 말하면, 안내 데스크 직원이 자기 사원증으로 문을 열고 다녀와서 필요한 걸 갖다 줘요. 방문객은 그 사원증을 만져볼 일도, 구경할 일도 없어요. 프록시 서버가 정확히 이 안내 데스크 역할이에요. 브라우저(방문객)는 프록시 서버(안내 데스크)에만 요청하고, 진짜 출입증(API 키)은 프록시 서버만 들고 있다가 외부 서버에 대신 전달해요.

코드로 보면 이렇게 바뀐다

프록시가 없으면 브라우저 코드가 이런 모양이에요 — 키가 그대로 코드 안에 박혀요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

// ❌ 브라우저에서 직접 호출 — 키가 그대로 노출됨
const res = await fetch('https://sam.example.com/v1/generate', {
  method: 'POST',
  headers: { Authorization: `Bearer sk-abc123...` },
  body: JSON.stringify({ npc: '김민준', situation: '주방에서 마주침' }),
});

이 코드가 배포되는 순간, 누구나 개발자 도구 네트워크 탭에서 sk-abc123...을 그대로 복사해 갈 수 있어요. 프록시 서버를 세우면 브라우저 코드는 이렇게 바뀌어요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

// ✅ 우리 프록시 서버에만 요청 — 키는 안 보임
const res = await fetch('/api/npc-line', {
  method: 'POST',
  body: JSON.stringify({ npc: '김민준', situation: '주방에서 마주침' }),
});

그리고 그 /api/npc-line을 받아주는 프록시 서버 쪽 코드는 이래요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

// server.js — 프록시 서버 (Node.js + Express)
app.post('/api/npc-line', async (req, res) => {
  const upstream = await fetch('https://sam.example.com/v1/generate', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${process.env.SAM_API_KEY}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(req.body),
  });
  res.json(await upstream.json());
});

키는 process.env.SAM_API_KEY, 그러니까 지난 글에서 다룬 환경변수 안에만 있어요. 브라우저는 이 서버 코드를 아예 받아볼 일이 없으니, 개발자 도구를 아무리 열어봐도 진짜 키는 나오지 않아요.

바뀐 건 위치 하나뿐

프록시를 세워도 "브라우저가 요청하고 서버가 응답한다"는 기본 구조는 그대로예요. 딱 한 가지, 키가 어디 있느냐만 바뀌었어요. 이 서버는 딱 이 중계 역할만 하기 때문에 만들기도 어렵지 않아요 — 위 예시처럼 20~30줄이면 충분해요. 다만 이 프록시 서버도 아무 주소에서나 오는 요청을 다 받아주면 안 되는데, 그걸 정하는 규칙이 다음 번외편인 CORS예요.

이럴 때 의심하세요 — 외부 AI를 부르는 기능을 배포하기 전

키가 노출된 코드도 화면은 똑같이 잘 돌아가요. 그래서 대개 요금이나 사용량으로 처음 알게 되는데, 그때는 키가 이미 남의 손에 있어요. 배포한 사이트의 네트워크 탭에 무엇이 찍히는지를 방문자 눈으로 먼저 봐요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
배포한 사이트의 네트워크 탭에서 AI를 부르는 요청을 눌렀더니, 요청 주소가 우리 서버가 아니라 외부 AI 회사 주소예요. 요청 헤더에 Authorization: Bearer sk-...도 보여요 화면 코드에서 외부 AI 주소로 직접 fetch하는 줄이에요. 에디터 전체 검색에 그 회사 주소나 Authorization을 넣어 봐요 보였다면 이미 누구나 복사할 수 있던 키라, 먼저 보안 편의 이 줄대로 키를 새로 발급받아요. 그다음 호출을 프록시 서버로 옮기고 새 키는 서버 환경변수에만 넣어요
요청 주소는 /api/...로 우리 서버를 향하는데, 그 요청의 보내는 내용(Payload)이나 헤더에 키가 여전히 실려 있어요 화면 코드가 키를 어디서 꺼내는지예요. VITE_나 NEXT_PUBLIC_이 붙은 환경변수에서 키를 읽어 서버로 보내고 있는지 봐요 키는 화면이 보내는 게 아니라 서버가 자기 환경변수에서 꺼내야 해요. 공개 접두사가 붙어 있었다면 그 키도 이미 브라우저에 실렸던 거라 새로 발급받아요 (연결 편의 이 줄)
프록시로 바꿨더니 배포한 사이트에서만 404가 떠요. 요청 주소를 보면 화면이 올라간 주소 뒤에 /api/npc-line이 붙어 있어요 화면 코드의 fetch('/api/...') 줄이에요. 앞에 서버 주소가 없는 짧은 주소는 화면이 올라간 곳으로 가요 프록시 서버가 화면과 다른 주소(예: ...onrender.com)에 있다면 그 서버 주소를 붙여야 해요. 주소는 환경변수로 빼 두면 개발과 배포에서 따로 넣을 수 있어요 (연결 편의 이 줄)
프록시를 거치게 바꾼 뒤 AI가 입력을 못 받은 것처럼 엉뚱하게 답하거나 에러를 내요. 서버에서 req.body를 찍어 보면 undefined나 {}예요 화면 쪽 fetch의 headers와, 서버 파일 위쪽의 app.use(express.json()) 줄이에요 화면 쪽에 'Content-Type': 'application/json'이 빠져 있거나 서버에 express.json()이 없으면, 서버가 보낸 내용을 JSON으로 읽지 못해 빈 채로 넘겨요. 둘 다 있는지 봐요
키는 안 보이는데, AI 회사의 사용량 화면에 우리 화면이 쓰지 않는 모델이나 유난히 긴 요청이 찍혀요 프록시 서버 코드에서 받은 내용을 외부로 넘기는 줄이에요. 위 예시의 JSON.stringify(req.body)처럼 받은 걸 통째로 넘기는지 봐요 통째로 넘기면 프록시를 부르는 누구나 모델과 길이를 마음대로 정해 우리 키로 쓸 수 있어요. 서버가 필요한 칸(예: npc, situation)만 꺼내 요청을 직접 만들게 해요. CORS로 허용 주소를 좁히는 것도 필요하지만, 브라우저 밖에서 직접 부르는 건 못 막아요 (CORS 편의 이 줄)

둘째 줄이 제일 헷갈려요. 주소가 /api/...로 바뀌어서 프록시를 세운 것처럼 보이는데, 키는 그대로 브라우저에 있거든요. 그래서 요청 주소만 보지 말고 보내는 내용까지 열어 봐요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 화면과 프록시 서버 코드가 있는 프로젝트 폴더에서

이 프로젝트에서 외부 AI API를 부르는 흐름을 전부 찾아서, 한 곳마다 파일 이름과 줄 번호를 표로 보여 줘.
1) 화면(브라우저) 코드에서 외부 AI 주소로 직접 요청하는 곳
2) 화면 코드가 API 키를 읽거나 요청에 실어 보내는 곳 (키 값은 보여 주지 마)
3) 프록시 서버가 받은 요청 본문을 그대로 외부 API로 넘기는 곳
4) 프록시 서버의 CORS 허용 주소 설정
