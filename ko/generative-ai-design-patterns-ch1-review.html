1.1 · 설계 패턴
Q1

이 책이 "설계 패턴"이라는 틀을 쓰는 이유는? 신입사원 매뉴얼 비유가 정확히 뭘 짚어주나?

생성형 AI를 실제 서비스에 넣으면 같은 문제(문체 이탈, 환각, 내부 지식 부재 등)가 반복해서 생긴다. 그때마다 바닥부터 고민하지 말고, 이미 검증된 해법 32개를 "문제 → 해법 → 예시 → 고려사항" 형태로 참고서처럼 찾아 쓰라는 게 이 책의 구성이다. 회사가 신입사원을 새로 뽑을 때마다 "자주 겪는 문제 대응 매뉴얼"을 서랍에서 꺼내 주는 것과 같다 — 매번 바닥부터 대응법을 새로 고민하지 않아도 된다는 뜻이다.

추가문제

3장 RAG 패턴은 이 틀에서 "어떤 문제"의 해법인가?

회사 내부 문서를 모르는 모델이 환각(있지도 않은 사실을 그럴듯하게 지어냄)을 일으키는 문제. 질문에 답하기 전에 실제 문서를 먼저 찾아보게 만드는 게 해법이다.

04_reverse_neutralization/  05_content_optimization/  06_basic_rag/  ...
...  31_self_check/  32_guardrails/

확인 포인트: 정확히 맞는다. "패턴집" 구조가 책 텍스트뿐 아니라 저장소 폴더 구조 자체로 구현돼 있다 — 06_basic_rag가 바로 RAG 패턴의 실행 가능한 코드다.

1.2 · 기초 모델로 앱 만들기
Q2

시스템 프롬프트와 사용자 프롬프트는 뭐가 다른가?

시스템 프롬프트는 "너는 이런 역할, 이런 태도로 답해"라고 한 번 정해두는 규칙이고, 사용자 프롬프트는 그때그때 실제로 부탁하는 내용이다. prompt라는 말 자체가 연극 무대에서 배우에게 다음 대사를 귀띔해주는 "프롬프터"에서 왔다.

📓 examples/00_introduction/agentic_ai.ipynb 
agent = Agent(f"anthropic:{MODEL_ID}",
              system_prompt="You are an inventory manager who orders just in time.",
              result_type=list[Reorder])

result = agent.run_sync(f"Identify which of these items need to be reordered this week.\n{items}")
직접 검증해볼 것

system_prompt와 run_sync(...) 인자에 들어간 문자열의 성격이 어떻게 다른지 비교해보라.

확인 포인트: system_prompt엔 매번 안 바뀌는 역할("재고 관리자")이, run_sync엔 그때그때 바뀌는 실제 요청(재고 데이터)이 들어간다 — 책 예제 코드가 이 구분을 그대로 지킨다.

Q3

모델을 클라우드 API로 쓰는 것과 내 컴퓨터(로컬)로 돌리는 것, 로컬이 가능해지는 조건은 뭔가?

API는 인터넷 너머 회사 서버로 질문을 보내는 방식이고, 로컬은 그 "알맹이"(가중치)를 내 컴퓨터로 통째로 내려받아 직접 돌리는 방식이다. 로컬이 가능하려면 회사가 그 알맹이를 공개(오픈웨이트)해둔 경우여야 한다 — 알맹이가 안 열린 프런티어 모델은 API로만 접근할 수 있다.

후속질문

"오픈웨이트"와 "로컬호스팅 가능"이 왜 서로 다른 축인가?

오픈웨이트는 라이선스상 가중치를 공개했는지의 문제고, 로컬호스팅 가능은 그걸 실제로 내 컴퓨터 사양으로 돌릴 수 있는지의 문제다. 공개돼 있어도 모델이 너무 크면 내 GPU로는 못 돌릴 수 있다.

📓 저장소 비교 — 00_introduction vs 15_adapter_tuning 
# 00_introduction: 클라우드 API만 있으면 됨
agent = Agent(f"anthropic:{MODEL_ID}", ...)   # ANTHROPIC_API_KEY만 필요

# 15_adapter_tuning: 오픈웨이트를 통째로 로컬 GPU에 로드
model_id = "google/gemma-3-4b-pt"
model = AutoModelForImageTextToText.from_pretrained(model_id, **model_kwargs)
# README: "Step 4: Get a sufficiently large machine with a GPU.
#          We used a NVIDIA L4 with 32 GB of memory"
직접 검증해볼 것

두 폴더의 keys.env/README 요구사항을 비교해보라 — 오픈웨이트 모델이라고 항상 가볍게 로컬에서 돌아가는가?

확인 포인트: Gemma는 오픈웨이트지만 README가 NVIDIA L4 32GB GPU를 명시한다 — "가중치 공개"와 "내 컴퓨터에서 실제로 돌아감"이 다른 축이라는 걸 실제 하드웨어 요구사항으로 확인할 수 있다.

Q4

기초 모델은 왜 성능과 비용을 저울질해서 골라야 하나?

프런티어 모델(성능 최고, 알맹이 비공개), 증류 모델(가볍고 저렴), 오픈웨이트 모델(공개돼서 내려받아 쓸 수 있음)로 대략 나뉘는데, 일반적으로 성능이 좋을수록 비용도 올라간다. 모든 작업에 제일 비싼 모델을 쓸 필요는 없고, 작업 난이도에 맞춰 골라야 가성비가 맞는다.

직접 검증해볼 것

lmarena.ai/leaderboard에서 지금 상위권 모델과, 같은 회사의 경량(증류) 라인업을 나란히 찾아보라.

확인 포인트: 리더보드 등수는 계속 바뀌지만, 상단(프런티어)과 경량 라인업(하이쿠·플래시류)이 항상 같이 존재하는 구조는 그대로다 — 작업 난이도에 맞춰 등급을 낮추는 습관이 실제 비용을 좌우한다.

1.3 · 에이전트형 AI
Q5

"자율성"이 정확히 뭔가? 재고 관리 예시로 설명하면?

"재고가 100개 밑이면 300개 주문해"처럼 세세한 규칙을 사람이 미리 프로그래밍하지 않고, "재고 부족 없게 적시에 주문해줘"라는 목표만 주는 것. 에이전트는 최근 판매량·배송 기간을 스스로 살펴보고 필요한 수량을 계산해서 이유까지 설명한다. 규칙을 사람이 적어두는 게 아니라, 에이전트가 그 규칙 자체를 그때그때 만들어낸다는 게 핵심이다.

📓 examples/00_introduction/agentic_ai.ipynb — 책의 재고 예시 원본 
items = [
    InventoryItem("itemA", 300, [50, 70, 80, 100], 2),
    InventoryItem("itemB", 100, [70, 80, 90, 70], 2),
    InventoryItem("itemC", 200, [80, 70, 90, 80], 1)
]
agent = Agent(f"anthropic:{MODEL_ID}",
              system_prompt="You are an inventory manager who orders just in time.",
              result_type=list[Reorder])
직접 검증해볼 것

이 셀 어디에도 "재고 100개 밑이면 300개 주문" 같은 if문이 없다는 걸 코드에서 직접 확인해보라.

확인 포인트: 정말 없다. 판단은 전부 system_prompt 한 줄과 result_type=list[Reorder](출력 형식 강제)에서 나온다 — 목표·형식만 정해주고 판단 로직 자체는 프롬프트+모델에 위임했다는 뜻이다.

Q6

에이전트에게 기대되는 네 가지 능력과, 이게 순환 구조라는 말은 무슨 뜻인가?

① 목표 지향성(반응만 안 하고 목표를 향해 움직임) ② 계획 및 추론(단계를 스스로 쪼갬) ③ 인지 및 행동(데이터를 읽고 외부 함수를 호출함) ④ 적응 및 학습(자기 산출물이 맞는지 스스로 점검하고 고침 — 6장 Reflection·9장 Self-Check). 이 넷이 인지→계획→행동→적응→다시 인지로 한 바퀴 돌 때마다, 에이전트는 자기 결과를 스스로 검증해서 조금씩 나아진다.

직접 검증해볼 것

Q5의 agentic_ai.ipynb를 다시 보라 — @agent.tool 데코레이터나 실제 주문 API 호출 코드가 있나? items 데이터는 어디서 오나?

확인 포인트: 없다. items는 노트북에 하드코딩된 파이썬 리스트일 뿐이다. 이 예제는 ②계획·추론까지만 구현됐고, ③인지·행동(실제 재고 DB 조회, 진짜 주문 API 호출)은 빠져 있다 — 그건 7장 도구 호출 패턴(21_tool_calling)부터 채워진다.

Q7

비결정성과 환각은 둘 다 "AI가 틀리는 문제"처럼 보이는데, 원인이 어떻게 다른가?

비결정성은 모델이 다음 단어·숫자 후보마다 매긴 점수(로짓)를 확률로 바꿔서 그 확률대로 제비뽑기하기 때문에 생긴다 — 1등(예: 300개)이 뽑힐 확률이 제일 높아도, 2등(280개)이 가끔 뽑힐 수 있다. 이건 계산이 틀린 게 아니라 원래 설계가 그렇게 되어 있는 것(창의성을 위해 일부러 넣은 무작위성)이다.

환각은 확률 뽑기와 무관하게, 모델에게 애초에 "이게 사실인지 확인하는 절차"가 없어서 생긴다. 모델은 "다음에 올 말로 그럴듯한 게 뭔가"만 계산하므로, 실제 데이터가 없어도 문법·맥락상 자연스러운 답(예: 존재하지 않는 배송업체 이름)의 점수가 높으면 그냥 뽑아버린다.

후속질문

그럼 온도(T)를 0으로 낮추면 환각도 같이 사라지나?

아니다. T=0은 매번 1등 후보만 고르게 해서 비결정성은 거의 없앨 수 있지만, 그 1등 후보 자체가 사실 확인 없이 매겨진 점수라서 환각은 그대로 남을 수 있다. 둘은 서로 다른 층위의 문제라 하나를 고친다고 다른 게 같이 고쳐지지 않는다.

📓 examples/00_introduction/building_on_apis.ipynb — 실제 출력 기록 
for T in [0, 0.2, 0.5, 0.8, 1.0]:
    agent = Agent('anthropic:claude-3-7-sonnet-latest',
                  model_settings={"temperature": T}, ...)
    result = agent.run_sync("The trade war caused")
0 : The trade war caused significant disruptions to global supply chains... (T=0을 여러 번 돌려도 토씨까지 똑같은 문장이 반복됨)
직접 검증해볼 것

이 반복문을 T=0만 남겨서 3번 재실행해보라. 문장이 똑같이 나오는가?

확인 포인트: 그렇다 — 비결정성은 거의 사라진다. 하지만 그 문장이 사실인지는 T값과 무관하다. 온도는 "얼마나 다양하게 뽑을지"만 건드릴 뿐, "그 내용이 진짜인지"는 건드리지 못한다.

1.4 · 세밀한 제어
Q8

로짓·소프트맥스·온도(T)는 각각 뭘 하는 개념인가?

모델의 마지막 계층은 다음 단어 후보마다 로짓(순위용 원점수)을 매긴다. 소프트맥스는 이 로짓을 0~100% 확률로 바꾸는 계산이다. 온도(T)는 이 확률을 재분배하는 손잡이 — T를 0에 가깝게 두면 1등만 거의 항상 뽑히고(안전, 뻔함), T를 높이면 순위 낮은 후보도 뽑힐 기회가 생긴다(창의적, 대신 말이 안 될 위험도 커짐).

📓 examples/00_introduction/building_on_apis.ipynb 
def logits_to_probs(logits):
    probs = { word: np.exp(logit) for word, logit in logits.items() }
    sigma = np.sum(list(probs.values()))
    return { word: value/sigma for word, value in probs.items() }

def scale_logits(logits, T):
    return { word: logit/T for word, logit in logits.items() }
직접 검증해볼 것

위 두 함수(순수 파이썬, API 호출 없음)를 그대로 돌려서 scale_logits(logits, 0.01)과 scale_logits(logits, 1.0)의 확률 분포가 어떻게 달라지는지 직접 계산해보라.

확인 포인트: T=0.01은 1등 단어 확률이 거의 100%로 몰리고, T=1.0은 5개 후보에 확률이 훨씬 고르게 퍼진다 — "온도가 로짓을 나눈 뒤 소프트맥스에 넣는다"는 정의를 숫자로 직접 확인할 수 있다.

Q9

상위K 표집과 상위P 표집은 둘 다 "안전장치"라는데, 방식은 어떻게 다른가?

상위K는 점수 순으로 줄 세운 뒤 고정된 개수 K개만 남기고 나머지는 후보에서 아예 제외한다. 상위P는 개수를 미리 안 정하고, 누적 확률이 P(예: 90%)를 넘는 지점까지만 후보로 남긴다 — 그래서 남는 후보 개수가 상황(점수 분포)에 따라 달라진다. 목적은 둘 다 같다 — 말이 안 되는 단어가 뽑힐 가능성을 후보에서 미리 잘라내는 것.

📓 examples/00_introduction/building_on_apis.ipynb — 실제 출력 
for top_k in [1, 10, 100]:
    agent = Agent('anthropic:claude-3-7-sonnet-latest',
                  model_settings={"temperature": 0.95, "top_k": top_k}, ...)
    result = agent.run_sync("The spaceship")
1 : The spaceship zoomed through the vast expanse of space... 10 : The spaceship glided silently through the vast emptiness of space... 100 : The spaceship soared through the starry expanse, its gleaming hull...
직접 검증해볼 것

저장소의 apply_top_p(probs, top_p) 함수를 {"the":5.2,"a":3.8,"an":2.1,"this":1.5,"that":0.9} 같은 뾰족한 분포에 top_p=0.3으로 돌려서 몇 개가 남는지 세어보라.

확인 포인트: the·a 정도만 남고 나머지는 확률 0으로 잘린다 — top_k=1이 그리디 선택과 같아지는 것도 위 출력에서 확인된다.

1.5 · 컨텍스트 내 학습
Q10

퓨샷 학습에서 모네 그림 예시 하나로 전혀 다른 르누아르 그림까지 맞히는 게, 왜 "지식 주입"이 아니라는 증거인가?

모델은 르누아르 그림에 대한 정보를 예시에서 받은 적이 없다. 모네 그림 예시 하나가 가르친 건 "설명 → 작품·화가·연도·의의" 순서(패턴)뿐이고, 르누아르·1881년·벨 에포크 같은 실제 내용은 모델이 사전훈련 때부터 이미 알고 있던 지식이다. 즉 퓨샷 학습은 새 지식을 넣는 게 아니라, 이미 아는 지식을 원하는 형식으로 꺼내 쓰게 하는 것이다. 그래서 모델이 원래 모르는 지식이면 예시를 아무리 줘도 소용없다.

📓 examples/00_introduction/prompt_engineering.ipynb 
agent = Agent(MODEL_ID, system_prompt=
    "You are an expert on art history. I will describe a painting. You should identify it")

result = agent.run_sync("""
Example:
Description: shows two small rowboats in the foreground and a red Sun.
Answer:
   Painting: Impression, Sunrise
   Artist: Claude Monet
   ...
Description: [새로운 그림 설명]
""")
직접 검증해볼 것

마지막 Description을 실존하지 않는 그림("보라색 하늘 아래 로봇 세 대가 체스를 두는 그림")으로 바꿔 재실행해보라. 모델이 "모른다"고 하는지, 형식만 맞춰 지어내는지 확인하라.

확인 포인트: 십중팔구 "모른다"고 하는 대신 형식(Painting/Artist/Year)은 정확히 맞춘 채 존재하지 않는 화가·연도를 지어낸다 — 퓨샷이 형식만 가르쳤다는 걸 역으로 증명하는 동시에, 이게 Q7의 환각이 실제로 발생하는 순간이다.

1.6 · 사후훈련
Q11

가진 데이터 모양에 따라 CPT·SFT·RLHF(DPO·GRPO) 중 뭘 골라야 하나?

데이터 모양방법가르치는 것
순수 텍스트 뭉치CPT(계속 사전훈련)새 어휘·개념 자체

추가문제

블룸버그의 BloombergGPT 사례는 이 표에서 무엇을 경고하나?

2023년 금융 문서로 CPT를 돌려 만든 특화 모델(BloombergGPT)이, 몇 달 뒤 나온 범용 기초 모델에 아무 특화 훈련 없이 성능을 추월당했다. "특화 훈련(CPT)이 항상 남는 장사는 아니다"는 실제 사례 — 표의 첫 줄(CPT)을 고르기 전에 정말 필요한지부터 따져봐야 한다는 경고다.

Q12

LoRA는 왜 쓰고, 파국적 망각은 왜 생기나?

LoRA는 수천억 개 매개변수 전체를 다시 훈련하는 대신, 원본은 그대로 두고 작은 "추가 메모" 층만 새로 학습시키는 방식이다(포스트잇 비유). 학습 파라미터가 최대 1만 배, GPU 메모리가 최대 3배까지 줄면서도 성능은 전체 재훈련과 비슷하다.

파국적 망각은 좁은 데이터로 너무 집중해서 재훈련하면 원래 잘하던 다른 일을 잊어버리는 현상이다. 컴퓨터 파일과 달리, 모델의 가중치는 여러 능력이 같은 숫자 자리를 겹쳐서 공유하기 때문에 생긴다 — "이 능력 버려"라고 누가 결정한 게 아니라, 좁은 데이터의 오차를 줄이려고 가중치를 계속 밀어붙이는 계산 과정에서 다른 능력이 걸려 있던 같은 숫자까지 원치 않게 같이 바뀌는 것이다.

📓 examples/15_adapter_tuning/3_adapter_tuning.ipynb 
from peft import LoraConfig
peft_config = LoraConfig(
    lora_alpha=16, lora_dropout=0.05, r=16,          # 어댑터(포스트잇 층) 크기
    target_modules="all-linear", task_type="CAUSAL_LM",
    modules_to_save=["lm_head", "embed_tokens"],
)
직접 검증해볼 것

r=16이 뭘 뜻하는지, modules_to_save가 왜 명시돼 있는지 찾아보라.

확인 포인트: r은 LoRA 어댑터의 랭크(포스트잇 크기)다. lm_head·embed_tokens까지 modules_to_save로 일반 파라미터처럼 함께 학습시킨 이유는 Gemma가 원래 모르던 방사선 용어를 새로 익혀야 해서다 — 이 층까지 건드리며 좁은 데이터로 오래 학습시키면 파국적 망각이 더 쉽게 생긴다.

1.7 · 이 책의 구성
Q13

1장이 왜 나머지 8개 챕터(32개 패턴)보다 먼저 와야 하나?

2장부터 다루는 32개 패턴(문체 제어·RAG·추론·신뢰성·도구 호출·비용·안전·프로덕션)은 전부 1.2~1.6에서 다진 개념 위에서만 말이 되는 해법이다. 예를 들어 7장 도구 호출 패턴은 1.3의 "인지·행동" 능력을 실제로 구현하는 방법이고, RAG는 1.5 컨텍스트 내 학습의 응용이다. 기초 없이 패턴만 외우면 "왜 이게 해법인지"를 이해할 수 없다.

한 장 지도로 정리하면 — 채용(1.2)·배치(1.3)·조율(1.4)·즉석교육(1.5)·정식재교육(1.6)·실전투입(1.7). 이 여섯 칸 순서를 뼈대로 잡아두면, 위 열세 개 문답의 세부 내용은 "이 칸에서 걸리는 지점을 채워 넣는 것"으로 자연스럽게 정리된다.
