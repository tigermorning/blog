  • git push origin main에서 뒤의 두 단어는 뭔가요?
읽고 나면 할 수 있는 것
  • 저장소를 만들고 내 컴퓨터로 가져와 고치고 올려보내는 한 바퀴를 혼자 돌립니다.
  • 세 단계가 각각 뭘 하는지 압니다 — add는 이번 기록에 포함시킬 파일 표시, commit은 그 상태를 사진처럼 한 장 찍기, push는 찍어둔 기록을 서버로 밀어 올리기.
  • origin과 main이 뭔지 압니다. origin은 클론해온 그 저장소에 Git이 붙여준 별명이고, main은 기록이 쌓이는 기본 줄기 이름이에요.
모르면 이런 일이 생겨요
  • 이 한 바퀴를 못 돌리면 작업물이 내 컴퓨터 안에만 갇힙니다. 고장 나면 통째로 사라지고, 어제 상태로 되돌아갈 수도 없어요. 언제 의심하나 ↓
  • .html 파일을 더블클릭하면 고치는 화면이 아니라 완성된 웹페이지가 브라우저에 열려버립니다.
  • 빈 저장소를 클론하면 빈 폴더만 생겨서 제대로 받아진 건지 확인이 안 돼요. 언제 의심하나 ↓
어디에 쓰나
  • 내 컴퓨터에서 고친 파일을 인터넷에 올려야 할 때. clone·commit·push 세 단어가 각각 무슨 동작인지 알면 그다음부터 혼자 한 바퀴 돌 수 있어요.
  • 저장소를 만들 때 README 파일을 하나 넣어 클론이 잘 됐는지 눈으로 확인하기
  • 클론 주소는 HTTPS 탭 말고 SSH 탭에서 복사하기
  • 파일을 고칠 때 오른쪽 클릭 → 연결 프로그램 → 메모장으로 열기
  • 관련 있는 변경만 골라 한 묶음으로 커밋하고, 정리되면 한꺼번에 push하기

2편까지 하고 나니 제 컴퓨터와 GitHub 계정은 서로를 알아보게 됐는데, 정작 주고받을 물건이 하나도 없었어요. 그래서 이번 3편에서는 실제로 저장소를 만들고, 내 컴퓨터로 가져오고(clone), 파일을 고쳐서 GitHub로 올려보내는(commit, push) 한 바퀴를 처음부터 끝까지 돌려봅니다. 앞으로 뭘 하든 계속 반복하게 되는 Git의 기본 동작이 바로 이 한 바퀴예요.

1. GitHub에서 저장소 만들기

첫 단추는 저장소(repository)를 만드는 거예요. 저장소는 "파일들을 모아두는 폴더 + 그 파일들의 변경 이력"을 한 덩어리로 묶은 것이라고 생각하면 돼요. repository라는 단어 자체가 원래 "보관소, 창고"라는 뜻이에요. 앞으로 하는 작업이 전부 이 창고 하나를 기준으로 돌아가기 때문에, 이걸 먼저 만들어야 합니다.

저는 내 컴퓨터가 아니라 GitHub 쪽에서 먼저 만들었어요. 그래야 다음 단계에서 그걸 통째로 내려받기만 하면 되거든요.

  1. GitHub 우측 상단 + 클릭 → New repository
  2. 저장소 이름 입력
  3. "Add a README file" 체크(선택)
  4. Create repository 클릭

중간의 "Add a README file"은 저장소를 설명하는 README.md 파일을 처음부터 하나 넣어줄지 묻는 항목이에요. 저는 체크했는데, 설명을 적고 싶어서만은 아니었어요. 파일이 하나도 없는 완전히 빈 저장소는 다음 단계에서 내려받아도 빈 폴더만 생겨서 제대로 된 건지 확인이 안 되거든요. 파일이 한 개라도 들어 있으면 "아, 잘 받아졌구나"를 눈으로 바로 알 수 있어요. 저장소 이름은 나중에 파일 안에 쓰이지는 않지만, 폴더 이름이자 주소의 일부가 되기 때문에 처음부터 알아보기 쉽게 짓는 게 좋아요. 저는 나중에 봐도 뭘 위한 저장소였는지 한눈에 떠오르도록, 목적이 드러나는 짧은 영어 단어로 지었어요.

2. 내 컴퓨터로 가져오기 (clone)

저장소는 GitHub 서버 위에만 있어서, 내 컴퓨터에서 직접 파일을 수정하려면 먼저 통째로 복사해와야 해요. 이걸 클론(clone)이라고 해요.

clone은 "복제본"이라는 뜻인데, 그냥 다운로드가 아니라서 이런 이름이 붙었어요. 파일만 내려오는 게 아니라 그동안 쌓인 변경 이력까지 통째로 함께 따라와서, 제 컴퓨터 안에도 GitHub에 있는 것과 똑같은 저장소가 하나 생기는 거예요. 그래서 클론은 처음 딱 한 번만 하면 돼요. 그다음부터는 계속 이 폴더에서 작업하면 됩니다.

클론하려면 "어느 저장소를"인지 알려줘야 하니, 먼저 주소를 챙겨야 해요. 저장소 페이지의 초록색 Code 버튼 → SSH 탭에서 주소를 복사해두세요. (2편에서 SSH로 연결해뒀기 때문에 HTTPS 탭 대신 SSH 탭 주소를 쓰는 거예요.) SSH 탭 주소는 git@github.com:...처럼 시작하고, HTTPS 탭 주소는 https://github.com/...처럼 시작해요. 겉보기엔 둘 다 같은 저장소를 가리키는 주소라 비슷해 보이지만, HTTPS는 GitHub 로그인(계정 비밀번호가 아니라 브라우저 로그인이나 토큰)을 따로 한 번 더 거쳐야 하는 반면 SSH는 2편에서 이미 등록해둔 열쇠로 바로 인증되기 때문에, 2편을 따라온 지금은 SSH 쪽이 맞았어요.

🎨 바이브 코딩으로: 복사한 주소를 Claude에게 붙여넣으며 "이 저장소를 내 문서 폴더에 클론해줘"라고 말하면 알아서 받아와줘요.

🔍 궁금하다면: 실제로 어떤 명령어일까?

실행: 로컬 터미널

git clone git@github.com:내아이디/저장소이름.git

3. 파일은 실제로 어디서, 어떻게 여나요?

클론이 끝나면 제 문서 폴더 안에 저장소 이름과 똑같은 폴더가 하나 생겨 있어요. 여기서 저는 잠깐 멈칫했어요. 여태 Claude에게 말로만 시켰는데, 정작 "그럼 그 파일은 내가 어떻게 열어보지?"가 막막했거든요. 알고 보니 특별한 프로그램이 필요한 게 아니라, 평소 쓰던 파일 탐색기와 메모장으로 그냥 열면 되는 거였어요. GitHub Desktop이나 Claude Code처럼 저장소 폴더를 곧바로 열어주는 도구도 있다는 걸 나중에 알게 됐지만, 저는 일단 파일 탐색기부터 손에 익혀두기로 했어요. 원리를 알아두면 나중에 어떤 도구를 쓰든 지금 배운 게 그대로 통하니까요.

  1. 파일 탐색기 열기: 윈도우 키 + E
  2. 주소 입력창에 저장소 경로 입력 후 Enter
  3. 수정하고 싶은 파일을 마우스 오른쪽 클릭 → 연결 프로그램 → 메모장
  4. 원하는 문장만 고치기. <p>, <h1>처럼 꺾쇠괄호로 된 부분은 건드리지 않기

⚠️ 파일을 더블클릭하면 안 돼요. .html 파일을 더블클릭하면 수정할 수 있는 화면이 아니라, 완성된 웹페이지가 브라우저에 열려버려요. 반드시 마우스 오른쪽 클릭 → 연결 프로그램 → 메모장으로 열어야 글자를 고칠 수 있어요.

수정을 마쳤으면 Ctrl + S로 저장하세요. 저장하지 않고 바로 닫기(X)를 누르면 안 돼요 — 메모장이 "변경 내용을 저장하시겠습니까?" 하고 물어보긴 하지만, 헷갈리지 않게 항상 닫기 전에 먼저 저장하는 습관을 들이는 게 좋아요.

4. 기록 남기고(commit) → 올려보내기(push)

여기까지는 아직 내 컴퓨터 안에서만 바뀐 상태예요. 실제 GitHub에 반영하려면 이 상태를 기록으로 남기고(commit), 온라인에 올려야(push) 해요.

🎨 바이브 코딩으로: 파일만 고쳐서 저장해두고, Claude에게 "방금 바꾼 내용을 커밋하고 push해줘"라고 말하면 나머지는 대신 처리해줍니다.

🔍 궁금하다면: 실제로 어떤 명령어일까?

실행: 로컬 터미널

git add 파일이름
git commit -m "무엇을 바꿨는지 메시지"
git push origin main

세 단계로 굳이 나뉘어 있는 게 처음엔 번거로워 보였는데, 각 단계가 하는 일을 표로 정리해보니 왜 나뉘어 있는지 이해가 됐어요.

단계명령어하는 일
①git add 파일이름이 파일을 이번 기록에 포함시키겠다고 표시
②git commit -m "메시지"표시해둔 상태를 사진처럼 한 장 찍어 남기기
③git push origin main찍어둔 기록을 GitHub 서버로 실제로 밀어 올리기

commit이라는 말은 원래 "맡기다, 확정해서 넘기다"라는 뜻이라, "이 상태를 확정해서 기록에 넘긴다"는 느낌으로 받아들이면 이해가 쉬워요. 파일을 열 개 고쳤어도 그중 서로 관련 있는 것만 골라 ①에서 add해서 한 묶음으로 커밋할 수 있고, 커밋을 여러 번 쌓아둔 다음 정리가 됐을 때 한꺼번에 ③에서 push할 수도 있어요. 기록을 남기는 일(②)과 남에게 공개하는 일(③)이 분리되어 있는 거예요.

여기서 헷갈렸던 것: origin main이 뭐예요?

git push origin main에서 뒤에 붙은 두 단어가 무슨 뜻인지 몰라 찾아봤어요. origin은 "내가 클론해온 그 GitHub 저장소"에 Git이 자동으로 붙여준 별명이에요. 밀어 올릴 때마다 긴 주소를 다시 적지 않아도 되게 하려고 붙여둔 이름이죠. main은 기록이 쌓이고 있는 기본 줄기의 이름이고요. 그러니까 이 명령은 "내 컴퓨터의 main에 쌓인 기록을, origin이라 부르는 그 저장소로 올려보내라"는 뜻이에요.

이럴 때 의심하세요 — 고친 파일이 GitHub에 안 올라갈 때

clone·commit·push를 Claude에게 맡기면 한 바퀴 중 어느 칸에서 멈췄는지가 잘 안 보여요. Claude는 "했어요"라고 답하는데 GitHub 화면은 그대로인 식이죠. 이럴 때는 다시 시키기 전에 git status 한 줄로 어느 칸인지부터 가려요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
클론이 끝났다는데 폴더를 열어 보면 아무것도 없어요. 터미널 결과에는 warning: You appear to have cloned an empty repository.가 찍혀 있어요 내 컴퓨터가 아니라 GitHub의 저장소 페이지예요. 클론 명령은 대개 범인이 아니에요 저장소 페이지에 파일 목록 대신 Quick setup으로 시작하는 안내만 보이면 원래 빈 저장소예요. 받기는 제대로 된 거라, 파일을 하나 넣고 커밋·push하면 돼요
push를 시켰더니 GitHub 로그인 창이 뜨거나 아이디·비밀번호를 물어요. 2편에서 SSH를 연결해 뒀는데도요 저장소에 붙은 원격 주소예요. 저장소 폴더에서 git remote -v를 넣으면 origin 옆에 주소가 나와요 주소가 https://github.com/...로 시작하면 HTTPS 탭 주소로 받은 거예요. git remote set-url origin git@github.com:내아이디/저장소이름.git으로 바꾸면 2편의 열쇠로 들어가요. 바꾼 뒤 Permission denied (publickey)가 나오면 2편의 이 줄을 봐요
파일을 고치고 커밋을 부탁했더니 Claude가 바뀐 게 없대요. 결과에 nothing to commit, working tree clean이 찍혀요 고친 파일의 저장 여부와 위치예요. 메모장에서 Ctrl + S를 안 눌렀거나, 클론으로 생긴 폴더가 아닌 다른 곳의 같은 이름 파일을 고쳤을 때 이렇게 돼요 메모장에서 Ctrl + S를 한 번 더 누르고, 파일 탐색기에서 그 파일이 저장소 폴더 안에 있는지 봐요. 그다음 git status에 modified:와 파일 이름이 나오면 커밋할 준비가 된 거예요
Claude가 "커밋했어요"라고 했는데 GitHub 저장소 페이지를 새로고침해도 그대로예요. 에러는 하나도 없어요 커밋이 아니라 push예요. 저장소 폴더에서 git status를 넣어 봐요 Your branch is ahead of 'origin/main' by 1 commit.처럼 앞서 있다는 줄이 나오면 기록은 아직 내 컴퓨터에만 있어요. git push origin main까지 해야 GitHub에 올라가요

넷째 줄이 제일 놓치기 쉬워요. 에러가 안 나니 다 끝난 줄 알고 컴퓨터를 끄게 되거든요. 커밋과 push를 부탁한 뒤에는 GitHub 저장소 페이지를 새로고침해서, 파일 목록 위에 방금 쓴 커밋 메시지가 보이는지 봐요.

Claude에게 점검을 맡길 때는 올리기 전에 보여만 달라고 해요. 파일이 안 바뀐 건지, 커밋이 안 올라간 건지 내 눈으로 가려 봐야 다음에 같은 일이 생겼을 때 어느 칸부터 볼지 알아요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 클론한 저장소 폴더에서

이 저장소의 상태를 점검해서 표로 보여 줘. 아직 아무것도 add·commit·push하지 마.
1. git remote -v 로 본 origin 주소, 그리고 그게 SSH(git@github.com:)인지 HTTPS(https://)인지
2. git status 로 본, 저장은 됐지만 커밋 안 된 파일 목록
3. git log origin/main..main --oneline 으로 본, 커밋은 됐지만 아직 push 안 된 커밋 목록

커밋이 "저장"과 정확히 뭐가 다른지 더 궁금하다면 아래 글도 함께 보세요.

참고 글 Git 커밋이 뭔가요?

이걸로 만들기 → 가져오기 → 고치기 → 기록하기 → 올려보내기까지 한 바퀴가 완성됐어요. 그런데 지금 GitHub에 올라간 제 파일은 아직 "코드가 적힌 문서"로만 보여요. 똑같은 파일이 주소만 치면 열리는 진짜 웹페이지로 보이게 하려면 한 단계가 더 필요한데, 그게 다음 4편에서 다룰 GitHub Pages예요.

다음 편 → (4) GitHub Pages로 진짜 홈페이지 만들기
