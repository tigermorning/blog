비유로 먼저 — 점심 장사 중에 주방 팀을 바꾸는 식당

손님이 가득한 점심시간에 주방 팀을 새 팀으로 바꾼다고 해 볼게요. 새 팀을 바로 주방에 세우면 아직 불을 못 올린 새 팀 때문에 주문이 막혀요. 그래서 사장은 새 팀을 손님 주문은 받지 않는 상태로 먼저 불러 놓고, 새 팀이 "준비됐습니다" 하고 종을 울릴 때까지 기다려요. 그다음 사장이 새 팀 전용 시식 창구로 요리 하나를 시켜 먹어 보고, 정말 맞는 메뉴판대로 나오는지 봐요. 통과하면 홀 안내 직원에게 "이제 손님을 새 팀으로 보내세요"라고 하고, 문제가 생기면 "다시 옛 팀으로"라고 말해요. 옛 팀은 아직 퇴근시키지 않았으니 바로 돌아올 수 있어요.

다만 여기서 비유가 끊기는 점이 있어요. 식당의 손님은 한 번 자리를 정하면 같은 팀에게 계속 서빙받지만, Cloud Run은 요청 하나하나마다 어느 리비전이 답할지 고르기 때문에 같은 사용자도 번갈아 다른 리비전의 답을 받을 수 있어요.

말부터 구분 — 이미지, 컨테이너, 인스턴스, 리비전

이 글에서 자주 쓰는 말을 먼저 갈라 둘게요. 이미지는 앱과 실행에 필요한 것을 담아 둔 설계도(파일)이고, 컨테이너는 이 이미지로 만든 실행 환경이에요. 인스턴스는 같은 컨테이너를 "몇 개 떠 있나"로 셀 때의 이름이라서, Cloud Run에서는 컨테이너를 인스턴스라고도 불러요. 리비전은 Cloud Run 용어로, 배포할 때마다 저장되는 배포 한 벌이고 옛 리비전은 지워지지 않아요. 구글 문서의 "버전 기록"에서 저장된 버전 하나하나가 리비전이고, "현재로 지정된 버전"이 트래픽 100%를 받는 리비전이라고 보면 돼요. 담는 순서는 서비스 안에 리비전이 있고, 리비전 안에 인스턴스(컨테이너)가 있어요. 이미지는 리비전의 재료예요. 이미지와 컨테이너가 처음이라면 도커(Docker)란 무엇인가를 먼저 읽어도 좋아요.

전체 흐름 — 머지 한 번에 도는 아홉 칸

제가 루틴 도장 저장소의 deploy.yml(staging 브랜치에 push하면 실행)을 이렇게 바꿨어요. 아래 그림에서 칸 ⑤와 ⑦이 새 버전이 전환되기 전에 지나는 두 관문이에요. 어느 관문에서든 걸리면 그 뒤 칸은 건너뛰고, 사용자가 쓰는 100%는 그대로예요.

두 관문 — 스타트업 프로브와 스모크 테스트

새 리비전은 전환되기 전에 관문을 두 번 지나요. 첫 관문은 ⑤ 안쪽에서 Cloud Run이 자동으로 하는 스타트업 프로브이고, 둘째 관문은 ⑦에서 내 워크플로가 하는 스모크 테스트예요.

스타트업 프로브는 헬스 체크의 일종이에요. 헬스 체크는 앱이 정상인지 확인하는 일을 두루 가리키는 말이고, 스타트업 프로브는 그중 Cloud Run이 새 인스턴스가 시작될 때 하는 헬스 체크예요. 앞 편의 Nginx에서 하던 능동 헬스체크에 해당해요. 프로브는 앱의 주소(/health)를 불러 200이 오는지 보고, 주소를 정하지 않은 기본 프로브는 포트가 열렸는지만 확인해요. 스모크 테스트는 프로브가 아니라 내 워크플로가 따로 하는 확인이에요.

스모크 테스트는 원래 서비스 주소가 아니라 태그 URL로 해야 해요. 원래 서비스 주소에는 지금 사용자 요청을 받는 이전 리비전이 대답하므로, 새 리비전이 망가져 있어도 "정상"으로 통과하기 때문이에요. 검사하는 대상이 틀리면 가짜로 통과해요.

rollback.yml — 버튼 한 번으로 이전 리비전에

  • Run workflow 버튼(workflow_dispatch)으로 실행해요. 승인은 두지 않았어요. 롤백은 이미 정상이었던 리비전으로 트래픽만 옮기는 일이라 피해 범위가 작고, 장애 중에 승인을 기다리는 위험이 더 크다고 판단했어요.
  • 입력은 되돌릴 서비스(staging 또는 production)와 되돌아갈 리비전이고, 리비전을 비워 두면 "지금 100%인 리비전보다 먼저 만들어진 정상(Ready) 리비전 중 가장 최근 것"을 자동으로 골라요.
  • update-traffic --to-revisions <대상>=100으로 이미지를 다시 만들지 않고 트래픽만 바꾸고, 롤백 전후의 100% 리비전을 실행 요약 표로 남겨요.

① 준비가 늦은 앱: 기본 프로브와 /health 프로브

② 새 리비전을 0%로 배포하고, 전환하고, 롤백하기

문제. 새 버전을 사용자에게 보내기 전에 먼저 확인하고 싶어요. "리비전을 0%로 올린다"는 "새 리비전을 트래픽 0%로 배포한다"를 줄인 말이에요. 배포는 새 리비전을 만들어 실행할 수 있는 상태로 두는 것이고, 트래픽 0%는 사용자 요청을 그 리비전에 한 건도 보내지 않는 것이에요. 이전 리비전이 계속 100%를 받아요. 서비스 주소는 하나이고, Cloud Run이 트래픽 설정의 비율대로 요청마다 확률로 리비전을 고르므로, 전환은 서비스 주소는 그대로 두고 뒤에서 누가 대답할지 비율만 바꾸는 일이에요. 롤백10은 구글 문서의 "버전 기록"에서 저장된 이전 버전을 "현재로 지정"하는 것과 같아서, 이미 남아 있는 이전 리비전에 100%를 지정하면 되고 새로 만들 것이 없어요.

내가 한 일.

  • --no-traffic --tag green으로 새 리비전 00016-gur를 트래픽 0%로 배포했어요. 서비스 주소는 계속 이전 리비전 00014-j9m이 답했고, 태그 URL(green)은 00016-gur가 답했어요. 서비스가 비공개라 인증 없이 태그 URL을 부르면 403이에요.
  • update-traffic --to-tags green=100으로 전환했어요.
  • update-traffic --to-revisions <이전 리비전>=100으로 롤백했어요.

결과.

  • 전환하는 동안 요청 127건 중 실패 0건이었어요. 응답한 리비전이 00014-j9m에서 00016-gur로 바뀌었어요.
  • 롤백하는 동안 요청 156건 중 실패 2건(ReadTimeout, 제한 2초)이었어요. 원인은 "이전 리비전의 인스턴스가 0개로 줄어 있어 콜드 스타트가 2초를 넘었을 것"이라는 추정이고 확인하지는 못했어요.
  • 롤백은 프로브를 다시 돌리지 않고 DB 같은 바깥 의존성도 확인하지 않아요. 돌아갈 곳이 지금도 정상인지는 사람이 직접 확인해야 해요.

③ 일부에게만 먼저 보내기: 카나리

블루그린11이 비율을 0%에서 100%로 한 번에 바꾼다면, 카나리12는 중간 값(10%, 50%)에 두고 일부 요청만 새 리비전으로 보내요. 비율은 순서가 아니라 요청마다 확률로 적용돼요. 앞 편의 Nginx에서 쓴 weight=3은 "요청 4개 중 3개"를 보내는 순서 규칙이었어요. 이번에는 비율을 10%, 50%, 100%로 바꿀 때마다 요청을 200번씩 보내 응답한 리비전을 셌어요.

새 리비전 비율 설정이전 리비전 00014-j9m이 받음새 리비전 00016-gur가 받음
10%188건12건
50%89건111건
100%0건200건

50%로 설정했는데 정확히 반반이 아닌 건 요청마다 확률로 나누기 때문이에요. 같은 사용자의 요청도 요청마다 다른 리비전으로 갈 수 있어서 서버가 상태를 갖지 않아야(무상태)13 해요. 그리고 요청이 적으면 "실패 0건"이 아무것도 증명하지 못해요. 10%에서 새 리비전이 받은 요청은 12건뿐이었어요. 하루 요청이 수십 건 정도라면 블루그린이 더 맞아요.

④ 롤백 뒤에는 트래픽이 한 리비전에 고정돼요

문제. 배포는 성공했는데 사용자는 옛 리비전을 봐요. 트래픽 설정의 지정 방식은 두 가지예요. "가장 최근 리비전 100%"는 새 배포를 따라가고(항상 최신 문서를 가리키는 링크), "특정 리비전 100%"는 새 배포가 와도 그대로 남아요(v14로 고정한 링크). 0% 배포나 태그 전환, 롤백을 하면 지정이 고정 방식으로 바뀌어요.

내가 한 일과 결과. --no-traffic으로 0% 배포를 하자 그때까지 "최신 따름"이던 100%가 00010-62w에 고정되는 것을 콘솔에서 확인했어요. 다음으로 00016-gur에 100%가 고정된 상태에서 새 설정으로 배포하자 새 리비전 00016-lpx가 만들어졌지만, 트래픽은 00016-gur 100% 그대로였고 서비스 주소도 계속 00016-gur가 답했어요. --to-latest로 고정을 풀자 00016-lpx가 100%(최신 따름)를 받고 서비스 주소가 00016-lpx로 답했어요. 그래서 자동 배포는 전환 단계에서 태그를 지정해 100%를 직접 옮겨요.

  • 스모크 테스트는 원래 서비스 주소가 아니라 태그 URL로 해야 해요. 원래 주소로 하면 이전 리비전이 대답해서 망가진 새 리비전도 통과해요.
  • 롤백이나 카나리 뒤에는 트래픽이 한 리비전에 고정되어 새 배포가 0%로 남아요. 그래서 전환 단계에서 태그를 지정해 100%를 직접 옮겨요.
  • 롤백 대상을 "지금 100%가 아닌 가장 최근 Ready"에서 "지금 100%보다 먼저 만들어진 Ready"로 고쳤어요. 앞의 방식은 방금 올린 검증 전 0% 리비전으로 되돌아갈 수 있었어요(PR #28).
  • 서비스가 비공개이면 스모크 테스트가 서비스 계정 토큰으로 호출해야 하고, 그러려면 IAM 권한이 따로 필요해요.

참고: 테이블 구조를 바꾸는 배포 — 실행하지 않고 생각만 한 것

새 버전이 테이블의 열 이름 하나를 바꾸는 마이그레이션을 한다면 어떻게 될까요? 예를 들어 예제 앱의 reminders 테이블에서 due_at을 remind_at으로 바꾼다고 해 볼게요. 실행하지 않고 생각만 했어요.

  • 바로 바꾸면: 전환하는 동안 이전 리비전이 받는 요청은 due_at을 찾지 못해 오류가 나고, 롤백해도 이전 리비전이 바뀐 테이블을 읽지 못해 깨져요. 스모크 테스트는 /health와 /version만 확인하므로 이 문제를 잡지 못해요.
  • 확장-축소 패턴으로 나누면: ① 새 열 remind_at을 추가하고 기존 값을 복사한다. ② 두 열을 함께 쓰는 버전을 배포한다(이전 버전도 새 버전도 정상 동작한다). ③ 이전 버전이 모두 내려가고 롤백할 일이 없어진 뒤에 옛 열 due_at을 지운다.
  • 그래서 스키마를 바꾸는 배포는 여러 번에 나눠서 하고, 카나리보다 "두 버전이 함께 도는 시간이 짧은" 블루그린이 더 안전해요.

서비스 주소를 부르면 태그 URL을 부르게 바꾸는 방법만 제안하고, 아직 파일은 고치지 마.
그리고 새 리비전을 배포하는 단계에 no_traffic 과 tag 가 들어 있는지, 시작 프로브 경로가 /health 인지도 알려 줘.

확인 범위와 해 보지 못한 것

  • 워크플로는 production도 대상으로 만들었지만 실행은 staging에서만 했어요(main 머지와 production 승인 없음). main에 반영하면 production 서비스에도 서비스 호출 권한이 필요해 스모크가 실패할 수 있다고 추정해요.
  • 스모크 테스트가 몇 번 실패한 뒤 재시도로 통과하는 경우는 보지 못했어요(이번에는 첫 시도에 통과). 망가진 버전은 스모크 테스트까지 가지 못하고 시작 프로브에서 먼저 멈췄어요.
  • 스모크 테스트와 프로브는 /health와 /version만 확인하므로 앱의 답이 이상해졌는지는 알 수 없어요.
  • 전환 단계가 33초 걸린 이유, 롤백 때 ReadTimeout 2건의 원인(콜드 스타트 추정), 리비전 번호 00015가 비어 있는 이유, 카나리 첫 시도가 실패한 원인은 확인하지 못했어요.
  • 망가진 버전을 Actions의 deploy.yml로 직접 배포해 본 것은 없어요(gcloud로만 시험).
  • 롤백 워크플로 실행 중 요청 실패 수(측정이 끊김), Run workflow 버튼 화면(main에 파일이 없음), 태그 URL의 브라우저 화면(인증이 필요해 열지 않음)은 확인하지 못했어요.
  • 단계별 선택 과제(알림, 카나리 자동 승격)와 "서로 보여 주기"는 하지 않았어요.
  • 하루친구의 production Supabase가 서유럽(West EU) 리전이라 생기는 지연은 측정하지 않았어요.
  • 원본 기록의 "오늘의 회고" 중 처음 답(1강 시작 질문)과 비교하는 칸은 아직 작성 전이라 이 글에 옮기지 못했어요.
  • 콘솔과 로그 화면 캡처는 프로젝트 번호와 프로젝트 ID가 보이는 부분을 가려서 기록했고, 이 글에는 화면 캡처를 싣지 않았어요.

  5. 스모크 테스트(smoke test) — 새 버전이 최소한의 일을 하는지 빠르게 한 번 확인하는 시험이에요. ↩

  9. 콜드 스타트(cold start) — 인스턴스가 0개로 줄어 있다가 첫 요청이 오면 새로 띄우느라 그 요청이 느려지는 일로, 3편에서 직접 확인했어요. ↩
  10. 롤백(rollback) — 문제가 생긴 배포를 이전 버전으로 되돌리는 일이에요. ↩

  13. 무상태(stateless) — 요청을 처리하는 데 필요한 상태(대화, 약속)를 서버 안에 두지 않고 밖의 저장소에 두는 방식이에요. ↩
  14. Supabase — PostgreSQL 데이터베이스와 로그인 기능을 함께 주는 관리형 서비스예요. ↩
