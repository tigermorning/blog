비유 — 장부와 레시피 카드

비유 없이 먼저 적으면, 이 편에서 더하는 건 두 가지예요. 하나는 실행이 끝날 때마다 "수집 몇 건, 선별 몇 건, 취재 몇 건, 검수 통과 몇 건"을 파일 끝에 한 줄로 적는 코드예요. 다른 하나는 선별·취재 프롬프트 안에 박혀 있던 "누구를 위해, 무엇을 고르고 무엇을 버릴지" 문장을 따로 떼어 둔 파일이에요. 노드와 그래프 코드는 그대로 두고요.

11편부터 이어 온 그 식당 주방은 이제 매일 아침 '오늘의 한 상'(다섯 접시)을 내요. 마감할 때마다 장부에 한 줄이 적혀요. 사장님이 영업 전에 정해 둔 칸대로요 — 들어온 재료 몇, 골라 둔 재료 몇, 접시에 담은 것 몇, 시식을 통과해 나간 것 몇. 몇 주 뒤 사장님이 장부를 거래처별로 다시 세어 보면 "이 거래처 재료는 한 번도 접시에 오른 적이 없네"가 보여요. 벽에는 레시피 카드가 걸려 있어요. 어떤 손님을 위한 상인지, 무엇을 먼저 올리고 무엇은 빼는지가 적힌 카드예요. 손님층이 바뀌는 날 메뉴를 정하는 사람은 카드만 갈아 끼우고, 조리대 직원들은 늘 하던 순서대로 손질하고 담고 시식에 넘겨요.

비유 속 요소원래 개념
마감 때마다 장부에 한 줄 — 사장님이 정해 둔 칸(들어온 재료 → 골라 둔 재료 → 담은 접시 → 시식 통과)을 채워 적기run()이 끝날 때마다 store/metrics.jsonl에 — 개발자가 정해 둔 키(collected → picked → drafted → published)를 JSON 한 줄로 덧붙이기
사장님이 몇 주치 장부를 거래처별로 다시 세기개발자가 쌓인 기록의 by_source를 더해 소스별 성적표 만들기
메뉴를 정하는 사람이 레시피 카드를 갈아 끼우기편집 방향을 정하는 사람이 audience.yaml의 독자·기준 문장을 고치기 — 파이썬 파일은 안 열어요
조리대 직원은 카드가 바뀌어도 같은 순서로 손질 → 담기 → 시식노드 다섯 개와 그래프는 그대로, 실행할 때 설정 파일에서 기준 문장만 읽어 씀

핵심 한 줄: 장부는 지난 영업을 거슬러 볼 수 있게 해 주고, 레시피 카드는 메뉴가 바뀌어도 주방 동선을 다시 긋지 않게 해 줘요.

다만 여기서 비유가 끊기는 점이 있어요. 실제 레시피 카드에는 조리 순서도 적히지만, 이 글의 설정 파일에는 순서가 없어요. "누구를 위해 무엇을 고를지"만 적히고, 순서는 끝까지 코드에 남아요.

전체 흐름

가운데 줄은 11편에서 세우고 15편까지 하나씩 채운 노드 그대로예요. 위 상자는 코드 밖에서 고치는 파일이고, 아래 상자는 이번 편에서 run()이 새로 남기는 한 줄이에요. 네 개의 건수가 왼쪽에서 오른쪽으로 줄어드는 모양을 보는 게 이 편의 절반이에요.

내린 결정을 재 볼 수 있어야 한다

돌아보면 11편부터 열 번 넘게 갈림길에서 한쪽을 골랐어요. 수집은 RSS 피드로, 매체는 관문 세 개로, 본문 기준선은 600자로(12편), 예선 묶음은 40건, 발행 목표는 다섯 건으로(13편). 그런데 근거를 들여다보면 대부분 한 번 재 본 값이에요. 매체마다 기사가 몇 건 오는지 한 번, 후보 12건으로 비교 한 번, 전체 실행 한 번. 그것만으로 "이 구조가 맞다"고 말하긴 어려워요.

설계 결정이 취향과 다른 점은 나중에 재어 볼 수 있다는 데 있어요. 재려면 먼저 기록이 있어야 하고요. 그래서 마지막으로 채우는 건 노드가 아니라, 매 실행을 기록으로 남기는 일이에요.

실행마다 한 줄 — store/metrics.jsonl

기록을 쌓는 데 데이터베이스나 대시보드는 필요 없어요. 파일 하나를 정해 두고, 실행이 끝날 때마다 그 끝에 한 줄을 덧붙이면 돼요. 한 줄에 기록 하나씩 JSON(파이썬 딕셔너리처럼 "이름": 값을 적는 글자 형식)으로 쌓는 이 방식을 JSONL1이라고 불러요. 메모장으로도 열리고, 줄 하나만 읽어도 그 실행이 보여요.

15편까지의 셀을 먼저 실행해 둔 노트북에서 이어 가요. 이번엔 노드를 바꾸지 않고, 11편에서 만든 run()을 같은 이름으로 다시 정의해요. 그래프를 돌린 뒤 결과에서 건수를 세어 한 줄로 적는 일까지 하게요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 앞 편에서 채운 노드가 LLM을 부르니 OpenAI API 키 필요 (DRY_RUN 기본값이면 디스코드로는 안 나가요)

import json, pathlib
from datetime import datetime

METRICS = pathlib.Path("store/metrics.jsonl")

def run():                                          # 돌리고, 한 줄 남긴다
    out = build().compile().invoke(INIT)
    row = {"run_id":    datetime.now().strftime("%Y-%m-%d %H:%M"),
           "collected": len(out["collected"]),      # ① 수집한 건수
           "picked":    len(out["picked"]),         # ② 선별이 남긴 건수
           "drafted":   len(out["drafted"]),        # ③ 취재를 마친 건수
           "published": len(out["verified"]),       # ④ 검수를 통과해 발행으로 넘긴 건수
           "hours":     out["hours"],
           "by_source": {},
           "log":       out["log"]}
    for a in out["verified"]:
        row["by_source"][a["source"]] = row["by_source"].get(a["source"], 0) + 1
    METRICS.parent.mkdir(exist_ok=True)
    with METRICS.open("a", encoding="utf-8") as f:  # 인코딩을 꼭 적는다
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
    return out

out = run()
last = json.loads(METRICS.read_text(encoding="utf-8").splitlines()[-1])
print(json.dumps({k: v for k, v in last.items() if k != "log"},
                 ensure_ascii=False, indent=2))

처음 보는 부분만 짚을게요. METRICS.parent.mkdir(exist_ok=True)는 store 폴더가 없으면 만들고 있으면 그냥 넘어가요. open("a")의 a는 덧붙이기(append)라서, 이미 있는 줄은 두고 끝에만 붙여요. "w"로 열면 실행할 때마다 앞의 기록이 지워져요. ensure_ascii=False는 한글 "수"를 \uc218 같은 기호 대신 글자 그대로 적게 해요. 사람이 메모장으로 열어 볼 파일이라 이쪽이 낫고, 그 대신 파일 인코딩을 코드에서 정해 줘야 해요(바로 아래에서 이유를 봐요).

저는 API 키 없이 확인하려고, 노드 다섯 개를 정해진 값을 돌려주는 가짜 함수로 바꾸고 위 코드를 그대로 돌렸어요. 가짜 수집 노드가 98건을 내고, 취재에서 한 건이 본문 부족으로 빠지고, 검수에서 한 건이 떨어지게 꾸몄어요.

개념 설명용 코드 — 노드를 가짜 함수로 바꿔 키 없이 돌렸을 때 제 화면에 찍힌 출력이에요. 숫자는 꾸민 값이에요. 15편 발행 노드를 그대로 두면 이 위에 [dry-run] 줄이 먼저 찍혀요

{
  "run_id": "2026-09-14 12:54",
  "collected": 98,
  "picked": 5,
  "drafted": 4,
  "published": 3,
  "hours": 24,
  "by_source": {
    "TechCrunch": 1,
    "AI타임스": 2
  }
}

실제로 돌리면 숫자는 날마다 달라요. 봐야 할 건 값이 아니라 어떤 항목을 남겼는가예요.

  • collected → picked → drafted → published — 줄어드는 네 숫자예요. picked와 drafted가 다르면 취재에서 빠진 기사가 있다는 뜻이고(본문이 600자에 못 미친 경우, 14편), drafted와 published가 다르면 검수에서 떨어진 거예요. 14편에서 기사가 조용히 빠진 채 합쳐질 수 있다고 했던 자리가 이제 숫자로 남아요.
  • hours — 그 실행이 몇 시간 치 기사를 모았는지예요. 발행이 자꾸 적어서 24를 48로 늘렸다면, 언제부터 바꿨는지를 기록에서 되짚을 수 있어요.
  • by_source — 검수까지 통과한 기사가 어느 매체에서 왔는지예요. 아래 성적표의 재료이고, 몇 주째 한 건도 못 올리는 매체는 이 숫자로만 드러나요.
  • log — 실행 중에 노드들이 찍은 줄 그대로예요. 응답 없는 매체, 본문이 짧아 빠진 기사가 여기 남아서 "오늘 왜 그 기사가 안 실렸지?"에 답해 줘요. 출력에서만 빼고 파일에는 들어 있어요.

이름 하나는 조심해서 읽어야 해요. published는 실제로 디스코드에 나간 건수가 아니라 검수를 통과해 발행 노드로 넘긴 건수예요. 15편의 dry-run으로 돌려 아무것도 안 보낸 날에도 같은 값이 적혀요. 실제로 보냈는지는 log의 마지막 줄(보냄 / dry-run)에서 봐요.

한 줄이 이만큼을 말해요. 운영 상태를 들여다보는 데 필요한 건 새 도구가 아니라 무엇을 남길지 정하는 일이에요. 이 형식은 기록으로 판정하는 멀티 에이전트 실험과 하네스 채점 보고서에서도 실행 기록을 남기는 데 썼어요.

윈도우에서는 인코딩을 꼭 적는다

위 코드의 encoding="utf-8" 두 군데를 빼고 쓰는 경우가 많아요. Colab이나 GitHub Actions처럼 리눅스에서 도는 곳에서는 빼도 아무 일이 없어서요. 파일에 글자를 저장할 때 어떤 바이트로 바꿀지 정한 규칙을 인코딩2이라고 하는데, 파이썬은 인코딩을 안 적으면 운영체제의 기본값을 써요. 리눅스의 기본값은 UTF-8이지만, 한국어 윈도우의 기본값은 cp9493예요.

제 윈도우 노트북(파이썬 3.12)에서 encoding을 빼고 같은 코드를 돌려 확인해 봤어요. 세 가지가 나왔어요.

  • 쓰고 읽는 게 같은 컴퓨터라 셀은 멀쩡히 끝났어요. 그런데 만들어진 파일을 UTF-8로 읽어 보니 'utf-8' codec can't decode byte 0xc0로 실패했어요. 파일이 UTF-8이 아니라 cp949로 저장돼 있었던 거예요. 이 파일을 저장소에 올리면 리눅스에서 도는 Actions가 못 읽어요.
  • 반대로 UTF-8로 저장된 파일(Actions가 쌓아서 git pull로 받아 온 기록이 이쪽이에요)을 인코딩 없이 read_text()로 읽으니 UnicodeDecodeError: 'cp949' codec can't decode byte 0xed ... illegal multibyte sequence로 멈췄어요.
  • 쓰는 쪽도 안전하지 않아요. 로그에 줄표(—)처럼 cp949에 없는 글자가 섞이면 UnicodeEncodeError: 'cp949' codec can't encode character '\u2014'로 기록 셀이 멈춰요.

그래서 파일을 열고 읽는 모든 줄에 encoding="utf-8"을 적어요. 어느 컴퓨터에서 돌리든 같은 바이트로 쓰고 같은 규칙으로 읽게요.

이 파일은 어디에 생길까

store/metrics.jsonl은 코드가 실행된 컴퓨터의 작업 폴더에 생겨요. 같은 코드라도 어디서 돌렸느냐에 따라 기록의 운명이 달라요.

Colab 같은 원격 주피터그 원격 컴퓨터의 작업 폴더런타임이 끝나면 파일도 함께 사라져요
GitHub Actions그 회차만을 위해 빌린 임시 서버실행이 끝나면 서버째 사라져요

그러니 Actions로 매일 돌린 결과는 내 노트북 파일에 한 줄도 추가되지 않아요. 서로 다른 컴퓨터니까요. 15편에서 붙인 upload-artifact로 실행 페이지에서 store/를 내려받을 수는 있지만, 그건 그 회차 한 줄짜리 파일이고 회차끼리 이어지지 않아요. 누적하려면 실행 끝에 그 파일을 저장소에 커밋해서 되돌려 놓아야 해요. 15편의 워크플로 파일에 두 군데를 더해요.

실행: .github/workflows/daily.yml에 추가 — GitHub Actions가 읽어요. 15편 파일의 해당 자리에 끼워 넣어요

permissions:
  contents: write                  # 저장소에 되써 넣으려면 필요하다

jobs:
  publish:
    steps:
      # ... 15편의 단계들은 그대로 ...
      - name: 기록 커밋
        if: ${{ !inputs.dry_run }}
        run: |
          git config user.name "newsroom-bot"
          git config user.email "bot@users.noreply.github.com"
          git add store/
          git diff --cached --quiet || (git commit -m "metrics: $(TZ=Asia/Seoul date +%F)" && git push)
  • permissions: contents: write — Actions는 기본으로 저장소를 읽기만 할 수 있어서, 커밋을 올리려면 쓰기 권한을 열어야 해요. 권한이 없을 때 어떤 에러가 나는지는 예약 발행 글의 권한 오류에 정리해 뒀어요.
  • if: ${{ !inputs.dry_run }} — 손으로 돌리면서 dry_run을 체크한 회차는 커밋하지 않아요. 시험 삼아 돌린 기록이 섞이지 않게요. 매일 아침 스케줄 실행에는 이 입력 자체가 없어서 조건이 참이 되고, 기록 커밋이 들어가요.
  • git diff --cached --quiet || — 올릴 변경이 없으면 커밋을 건너뛰어요. 변경이 없는데 git commit을 부르면 그 단계가 실패로 끝나거든요. 커밋과 푸시 자체는 클론·커밋·푸시 글에서 본 그 명령이에요.
  • TZ=Asia/Seoul date +%F — 15편은 TZ를 브리핑 생성 단계에만 넣어서, 이 단계의 date는 UTC로 돌아요. 그대로 두면 한국 시각 아침 7시 반 실행이 UTC로는 전날 22시 반이라 커밋 메시지에 전날 날짜가 적혀요.

이제 git pull을 할 때마다 그날의 기록이 노트북으로 내려와요. 캐시나 artifact와 달리 커밋은 기간이 지나도 지워지지 않고, 언제 무엇이 발행됐는지가 git 이력에 함께 남아요. 알아 둘 게 두 가지 있어요. 로컬에서도 같은 파일에 기록을 쌓으면 양쪽이 같은 파일 끝에 한 줄씩 붙여서 충돌이 날 수 있어요. 한 줄씩 덧붙이기만 하는 파일이라, 충돌이 나면 두 쪽 줄을 위아래로 둘 다 남기면 돼요. 그리고 store/에 API 응답 원문 같은 걸 함께 저장하면 공개 저장소에선 그것까지 공개돼요. 커밋할 파일은 지표 정도로만 둬요.

개념: 깔때기 관측

여러 단계를 거치며 건수가 좁혀지는 파이프라인에서, 단계마다 들어간 수와 나온 수를 같은 줄에 나란히 적어 두는 것을 깔때기 관측이라고 해요. 우리 경우엔 수집 → 선별 → 취재 → 검수 통과, 네 숫자예요.

이게 없으면 고장 난 단계를 모르게 돼요. "오늘 뉴스레터가 부실하다"는 사실만으로는 매체가 죽었는지, 선별 기준이 빡빡한지, 취재에서 본문이 안 뽑혔는지 구분이 안 돼요. 네 숫자를 나란히 두면 갑자기 크게 줄어든 자리가 범인 후보로 떠올라요.

이때 절대 건수보다 비율을 함께 봐요. 수집 건수는 그날 뉴스 양에 따라 출렁이지만, 단계별 통과 비율은 비교적 안정적이에요. 예를 들어 취재까지 온 기사가 늘 거의 다 검수를 통과하다가 어느 주부터 절반만 통과한다면, 검수 기준이나 바로 앞 단계인 취재 프롬프트 가운데 무언가가 바뀐 거예요.

한계도 분명해요. 깔때기는 어디가 문제인지는 알려 주지만 무엇이 문제인지는 안 알려 줘요. 그래서 건수와 함께 탈락 사유를 남겨요. 12편 수집 노드의 응답 없음 목록, 14편 취재 노드의 "본문 N자" 로그가 그 사유예요. 그리고 하루치 숫자는 우연일 수 있어서, 며칠은 쌓여야 의미가 생겨요.

중요꼭 기억할 것

단계를 거치며 좁혀지는 파이프라인은 단계마다 남은 건수를 한 줄에 나란히 남겨요. 결과가 부실한 날 갑자기 줄어든 자리가 고장 난 단계를 가리키고, 건수보다 비율의 변화가 더 믿을 만해요. 다만 건수는 어디인지만 알려 주니, 무엇이 문제인지 알려면 탈락 사유 로그를 같이 남겨요.

소스별 성적표 — 쌓인 기록을 매체 기준으로 다시 세기

깔때기가 파이프라인 전체를 본다면, 12편의 관문은 매체 하나하나를 봤어요. 쌓인 기록을 매체 기준으로 다시 세면 성적표가 돼요. 새 도구는 필요 없고, 줄마다 by_source를 더하기만 하면 돼요. API 키도 필요 없어요. 기록 파일만 읽거든요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키 없이 돌아가요. 12편의 SOURCES와 위에서 쌓은 기록 파일을 읽어요

import json, pathlib
from collections import Counter

path = pathlib.Path("store/metrics.jsonl")
rows = [json.loads(l) for l in path.read_text(encoding="utf-8").splitlines() if l.strip()] \
       if path.exists() else []

if not rows:
    print("아직 기록이 없습니다. 위 셀을 한 번 이상 돌린 뒤 다시 실행하세요.")
else:
    print(f"쌓인 실행 기록: {len(rows)}줄\n")
    pub = Counter()
    for r in rows:
        pub.update(r["by_source"])
    print(f"{'소스':<12}{'발행 기여':>9}")
    print("-" * 23)
    for name, _ in SOURCES:                         # 기여가 0인 소스도 보여야 한다
        print(f"{name:<12}{pub.get(name, 0):>9}")

    print("\n수집 → 선별 → 취재 → 검수 통과")
    for r in rows[-5:]:
        print(f"  {r['collected']:>4} → {r['picked']:>3} → {r['drafted']:>3}"
              f" → {r['published']:>3}")

Counter는 이름별로 개수를 세어 주는 딕셔너리예요. update()에 {"TechCrunch": 3} 같은 딕셔너리를 넣으면 기존 값에 더해요. 매체 목록을 by_source가 아니라 SOURCES에서 도는 게 핵심이에요. by_source에는 한 건이라도 올린 매체만 들어 있어서, 그걸로 돌면 0인 매체는 표에 아예 안 나타나요.

제 기록은 가짜 실행 한 줄뿐이라, 모양을 보려고 꾸민 기록 세 줄을 파일에 넣고 위 코드를 돌렸어요.

개념 설명용 코드 — 꾸민 기록 세 줄로 위 코드를 돌렸을 때 제 화면에 찍힌 출력이에요. 실제 매체 성적이 아니에요

쌓인 실행 기록: 3줄

소스              발행 기여
-----------------------
OpenAI              1
DeepMind            0
TechCrunch          8
The Verge           1
AI타임스               1

수집 → 선별 → 취재 → 검수 통과
    96 →   5 →   5 →   5
    88 →   5 →   4 →   4
   104 →   5 →   3 →   2

한글이 든 줄(제목 줄과 AI타임스 줄)만 칸이 밀린 건, 화면에서 한글은 두 칸을 차지하는데 파이썬 서식은 한 칸으로 세기 때문이에요. 숫자는 맞아요. 성적표에서 보이는 건 세 가지예요.

  • 기여가 0인 매체 — DeepMind처럼 수집은 되는데 발행까지는 한 번도 못 간 매체예요. 며칠치로는 우연일 수 있지만 몇 주째 0이라면, 그 매체는 매일 요청 시간과 선별 토큰을 쓰면서 아무것도 기여하지 않고 있어요. 뺄 매체를 숫자가 지목해 주는 게 성적표의 쓸모예요.
  • 기여가 한쪽으로 몰림 — 11건 중 8건이 TechCrunch예요. 한 매체가 매일 다섯 자리 중 서너 자리를 가져가면, 나머지 매체 기사는 본선 후보에조차 못 드는 상태일 수 있어요. 그렇다면 다음 수는 매체별 상한을 코드로 거는 거예요.
  • 깔때기의 어느 쪽이 줄었나 — 수집 → 선별의 낙폭과 취재 → 검수 통과의 낙폭을 따로 봐요. 앞쪽이 큰 건 정상이에요, 그게 선별이 하는 일이니까요. 뒤쪽이 커지고 있다면 본문 추출이나 검수에서 기사가 조용히 빠지고 있는 거예요. 마지막 줄의 3 → 2가 그 모양이에요.

실제 값은 매체 목록과 돌린 횟수에 따라 전부 달라요. 요점은 새 도구 없이, 이미 남긴 기록만으로 이 표가 나온다는 거예요.

실전 적용기 — 북한 뉴스 첫 기록 두 줄

12편의 잣대로 잰 북한 뉴스 4곳의 값을 이 편의 방식으로 store/metrics.jsonl에 남겼어요. 실제 첫 두 줄을 줄여 적으면 이래요.

1줄: g2_14d {Yonhap-NK: 90, DailyNK: 10, 38North: 6} / g3 38North 전부 false / elapsed 2.1초
2줄: g2_14d 동일 / g3 전부 true / elapsed 2.2초 / g1 기존 통과율 0.778

첫 줄의 38North false 아홉 개는 오판이었어요. 기록을 읽는 코드가 파이썬 기본 이름표로 robots.txt를 요청했더니 403이 왔고, 파서가 조용히 전부 금지로 돌아갔거든요(12편 실전 적용기의 함정). 첫 줄을 지우지 않고 남긴 건, 나중에 "왜 다시 쟀나"를 설명해 주는 감사 기록이 되기 때문이에요. 분석에는 둘째 줄을 써요.

두 줄이 말해 주는 건 하나예요. 38North의 14일 기여가 6건이라는 숫자예요. 일간 브리핑 매체로 쓰기엔 모자라지만 주간지로 두기엔 충분하다는, 주간枠 결정의 근거가 기록에 박힌 거예요. 성적표가 "쓸모"를 재는 방식 그대로예요.

관문을 다 통과한 매체가 몇 주째 0이라면

성적표를 보다 보면 헷갈리는 장면이 나와요. 12편에서 본문·생존·접근 관문을 전부 통과했고 본문도 넉넉히 뽑히던 매체인데, 발행 기여가 몇 주째 0이에요. 이건 그 매체가 기술적으로는 쓸 수 있지만, 우리 독자 기준에서 중요한 기사를 내놓지 않는다는 뜻이에요.

관문과 성적표는 다른 것을 재요. 관문은 "이 매체를 쓸 수 있나"를 묻고, 성적표는 "이 매체가 쓸모 있나"를 물어요. 흔히 떠올리는 다른 해석들은 이 장면과 안 맞아요.

  • "본문 추출이 사실은 실패하고 있다" — 그랬다면 관문 검사와 추출 성공률에서 이미 드러났어요. 취재 로그의 "본문 N자" 줄에도 그 매체 이름이 찍혔을 거고요.
  • "모델이 그 매체를 싫어해서 뽑지 않는다" — 근거가 없는 짐작이에요. 확인하려면 짐작 대신 선별에서 왜 떨어졌는지, 탈락 사유를 봐야 해요.
  • "그냥 우연이다" — 며칠이면 모를까, 몇 주는 우연으로 넘길 기간이 아니에요.

중요꼭 기억할 것

관문은 매체를 쓸 수 있는지(본문이 뽑히나, 살아 있나, 막히지 않았나)를, 성적표는 쓸모 있는지(우리 독자 기준에서 뽑힌 적이 있나)를 재요. 관문을 다 통과했는데 몇 주째 발행 기여가 0이면, 기술 문제가 아니라 그 매체의 기사가 우리 기준에 안 맞는다는 신호라 목록에서 뺄 후보예요.

이 결정을 검증하는 법

확인할 것은 "정한 매체 목록과 예선·본선 선별 구조가 제 몫을 하고 있나"예요. 세 가지를 봐요.

  • 매체별 발행 기여 — by_source 누적. 몇 주 내내 0인 매체는 뺄 후보예요.
  • 깔때기 단계별 비율 — 네 숫자를 실행마다 비율로 바꿔 봐요. 한 단계의 비율이 갑자기 변하면 그 단계나 바로 앞 단계가 바뀐 거예요.
  • 발행 건수의 분포 — 매일 몇 건이 나갔는지, 0건인 날까지 세요. 0건이나 1~2건인 날이 잦으면 시간 창이 좁거나 매체 수가 모자란 거예요.

셋 다 이미 화면에 출력하던 값을 파일에 남기기만 한 거예요. 특히 매체별 기여는 밖에서 잴 방법이 없고, 우리 기록으로만 알 수 있어요.

이걸 안 남기면 벌어지는 일은 요란하지 않아요. 결정을 되돌릴 수 없게 돼요. 몇 달 뒤 "이 매체는 왜 넣었지?"라는 질문에 기록이 없으면 답은 "그때 괜찮아 보여서"뿐이고, 뺄 근거도 없으니 쓸모없는 매체가 계속 남아요. 기록이 없으면 결정은 쌓이기만 하고 정리되지 않아요.

구조는 그대로, 내용만 바꾸기 — 설정 파일

11편부터 세운 구조를 늘어놓아 볼게요. 수집 경로를 칸별로 고르기, 관문으로 매체 거르기, 예선·본선, 부탁 대신 코드로 강제하기, 노드를 잇는 그래프, 깔때기 기록. 이 중에 AI 뉴스에만 해당하는 건 하나도 없어요. 채용 공고를 모아도, 논문을 모아도 같은 구조가 그대로 맞아요.

그런데 코드 곳곳에는 AI 뉴스가 박혀 있어요. 13편 선별 프롬프트의 "독자는 AI를 실제 제품에 붙이는 국내 개발팀", "이번 주 일하는 방식이 바뀔 만한가", 14편 취재 프롬프트의 "국내 개발팀을 위한 AI 뉴스레터 기자" 같은 문장이요. 구조는 일반적인데 내용이 특수한 거예요. 이걸 떼어 두지 않으면 다른 분야로 옮길 때 파이썬 파일을 전부 열어 문자열을 찾아 고쳐야 해요. 어디에 무엇이 박혀 있는지 기억하는 사람만 할 수 있고, 그 사람이 떠나면 아무도 못 옮겨요.

분야마다 바뀌는 문장을 어디에 둘까

정할 것은 "독자·기준·토픽처럼 분야마다 달라지는 내용을 어디에 두나"예요. 선택지는 넷이고, 아래로 갈수록 고치기는 쉬워지지만 만들 게 늘어요.

둘 곳얻는 것포기하는 것
① 프롬프트 문자열 안에 그대로
SYS = "당신은 국내 개발팀을 위한..."		가장 빨라요. 프롬프트만 읽어도 맥락이 한눈에 보여 프로토타입에 맞아요같은 내용이 여러 프롬프트에 흩어져 한 곳만 고치는 사고가 나요. 고칠 때마다 파이썬 파일을 열어야 해서 개발자가 아니면 못 고쳐요
② 파이썬 상수 모듈
config.py에 AUDIENCE = "..."		흩어짐은 해결돼요. 편집기 자동완성과 타입 검사도 받아요여전히 파이썬 파일이라 따옴표·들여쓰기를 다뤄야 하고, 한 글자만 틀려도 프로그램이 아예 안 돌아요
③ 설정 파일(YAML·TOML) — 고른 것
audience.yaml을 코드가 읽어 씀		프로그래밍을 몰라도 고칠 수 있고, 주석으로 작성 요령을 적어 둘 수 있어요. 무엇이 설정이고 무엇이 코드인지 경계가 파일로 드러나고, git 이력으로 "왜 기준이 바뀌었나"를 추적해요검증 없이 읽으면 오타가 실행 중에 터져요. 파일이 커지면 아무도 전체를 안 읽어요
④ 데이터베이스 + 관리자 화면뉴스레터 여러 개를 동시에 운영하고, 고치는 사람이 여럿일 때 맞아요화면·권한·수정 이력까지 만들 게 급격히 늘어요. 뉴스레터 하나에는 과해요

고른 기준은 "누가 이것을 고칠 것인가"예요. 독자 정의와 중요도 기준은 개발자가 아니라 편집 방향을 정하는 사람이 고쳐야 하는 문장이에요. 그 사람에게 파이썬 파일을 열라고 하면, 실제로는 아무도 안 고쳐요. 고치는 사람이 여럿으로 늘어나는 날이 ④로 넘어갈 때예요.

③의 약점인 "검증 없음"은 설정을 읽는 순간 한 번 검사하는 것으로 줄여요. 13편에서 모델 응답의 모양을 강제할 때 쓴 pydantic 같은 도구로 설정 파일의 칸 모양을 검사하면, 오타가 새벽 실행 한가운데가 아니라 프로그램이 시작하자마자 드러나요. 물론 조건이 달라지면 다른 선택지가 답이에요. 혼자 쓰는 실험용이면 ①로도 충분해요.

audience.yaml 만들고 읽기

13편의 CRITERIA 문자열을 파일로 옮겨요. 파일 형식은 YAML4이에요. 이름: 값을 줄마다 적고, 들여쓰기로 소속을 나타내고, -로 목록을 적어요. 먼저 YAML을 읽는 패키지를 설치해요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 노트북 셀에서, 맨 앞의 !가 터미널 명령으로 실행해 줘요

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 이 셀을 실행하면 노트북 폴더에 audience.yaml이 생겨요. API 키 없이 돌아가요

%%writefile audience.yaml
독자:
  누구: "AI를 실제 제품에 붙이는 국내 개발팀(개발자와 기획자)"
  이미_아는_것: "LLM API 사용법, 프롬프트 기본, RAG 개념"

# 선별 프롬프트(예선·본선)에 그대로 들어간다. 위에 있을수록 우선.
# 기사 하나를 보고 예/아니오로 답할 수 있는 질문이어야 한다.
중요도_기준:
  - "이번 주 우리가 일하는 방식이 바뀔 만한가"
  - "지금 쓰는 도구·API의 가격·한도·정책이 실제로 변했나"

# 추상어("홍보성") 말고 구체적인 표현으로.
버릴_것:
  - "발표 예정·로드맵만 있고 지금 쓸 수 없는 것"
  - "MOU·업무협약·투자유치·수상 등 당사자 홍보성 소식"

이제 이 파일을 읽어 13편의 CRITERIA와 14편의 SYS를 다시 만들어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키 없이 돌아가요. 13·14편의 셀을 실행해 둔 노트북에서 이어 가요

import pathlib, yaml

CFG = yaml.safe_load(pathlib.Path("audience.yaml").read_text(encoding="utf-8"))

def build_criteria(cfg):                            # 설정 → 프롬프트 문단
    out = [f"독자는 {cfg['독자']['누구']}입니다.",
           f"이미 아는 것: {cfg['독자']['이미_아는_것']}",
           "", "중요도 기준 (위에 있을수록 우선):"]
    out += [f"- {x}" for x in cfg["중요도_기준"]]
    out += ["", "버릴 것:"]
    out += [f"- {x}" for x in cfg["버릴_것"]]
    return "\n".join(out)

CRITERIA = build_criteria(CFG)                      # ← 13편에서 만든 그 상수를 덮어쓴다
SYS = (f"당신은 뉴스레터 기자입니다. 독자는 {CFG['독자']['누구']}입니다.\n"
       "아래 기사 본문을 읽고 헤드라인·요약·왜 중요한지를 쓰세요.\n"
       "반드시 한국어로 쓰고, '주목된다·기대를 모은다' 같은 기자체 표현은 쓰지 마세요.")

print(CRITERIA)

이미 아는 것: LLM API 사용법, 프롬프트 기본, RAG 개념

중요도 기준 (위에 있을수록 우선):
- 이번 주 우리가 일하는 방식이 바뀔 만한가
- 지금 쓰는 도구·API의 가격·한도·정책이 실제로 변했나

버릴 것:
- 발표 예정·로드맵만 있고 지금 쓸 수 없는 것
- MOU·업무협약·투자유치·수상 등 당사자 홍보성 소식

파일 내용이 문단 하나로 조립돼 찍혔어요. 이 문단이 그대로 선별 프롬프트가 돼요. yaml.safe_load는 YAML 글자를 파이썬 딕셔너리와 리스트로 바꿔 주는 함수고, 그래서 cfg['독자']['누구']처럼 꺼내 쓸 수 있어요.

기존 노드 코드는 한 줄도 안 고쳤어요. 13편의 ask_picks는 함수가 불릴 때마다 그 시점의 전역 CRITERIA를 읽어 프롬프트를 만들고, 14편의 draft도 불릴 때 전역 SYS를 읽어요. 그래서 값을 바꿔 두면 다음 run()부터 새 기준으로 돌아요. 반대로 노트북에서 audience.yaml만 고치고 이 셀을 다시 실행하지 않으면 CRITERIA는 옛 문장 그대로예요.

15편의 graph.py로 옮길 때는 13편의 CRITERIA 문자열과 14편의 SYS 문자열을 지우고 그 자리에 이 셀 내용을 둬요. 옛 문자열이 아래쪽에 남아 있으면 같은 이름의 나중 정의가 이겨서 설정 파일이 무시돼요. 셀 끝의 print(CRITERIA)는 옮기지 않아요. 앞의 기록 셀도 마찬가지로, METRICS와 새 run()만 11편 run() 자리에 두고 셀 끝의 out = run() 아래 줄들은 옮기지 않아요. 남겨 두면 run.py가 graph.py를 불러오는 순간 한 번 더 돌아요. 새 run()이 graph.py에 없으면 Actions에서 store/가 생기지 않아 위 "기록 커밋" 단계의 git add store/가 실패해요. requirements.txt에는 pyyaml을 한 줄 더하고, audience.yaml도 저장소에 함께 커밋해요.

없으면 멈출 칸, 없으면 기본값을 쓸 칸

위 코드에는 "파일이 없으면 기본 문장으로 만들어 두기" 같은 줄이 없어요. 일부러요. 설정을 못 읽은 채 기본 문장으로 조용히 돌면, 그게 12편에서 본 조용한 실패예요. 편집자가 기준을 바꿨는데 파일 이름이 틀려 옛 기준으로 몇 주째 돌고 있어도 아무도 모르죠.

그런데 "설정에는 기본값이 있어야 한다"는 말도 자주 들어요. 두 말은 칸의 성격으로 나누면 부딪히지 않아요.

  • 필수 칸 — 독자·중요도_기준·버릴_것. 이게 없으면 선별이 무엇을 기준으로 고르는지 자체가 사라지니, 빈 채로 돌기보다 시작하자마자 멈추는 게 맞아요. 위 코드는 검사 줄을 따로 넣지 않아도 그렇게 돼요. 파일이 없으면 FileNotFoundError가 나고, 제가 버릴_것 칸을 지우고 돌려 보니 build_criteria에서 KeyError: '버릴_것'로 그 셀이 멈췄어요. graph.py에서는 이 줄들이 파일을 불러오는 순간 실행되니, 수집이 시작되기도 전에 멈춰요.
  • 선택 칸 — 없어도 결과의 뜻이 바뀌지 않는 꾸밈이에요. 15편의 카드 색이 그런 예예요. 토픽 이름이 색 목록에 없으면 기본색으로 칠하죠. 이런 칸이 비었다고 멈추면, 설정으로 뺀 게 오히려 약점이 돼요.

토픽별 작성 지침("가격 변화는 반드시 숫자로") 같은 문장도 같은 파일로 옮길 수 있어요. 다만 그 칸을 읽어 쓰는 코드가 생기기 전에는 넣지 않아요. 아무도 안 읽는 설정은 고쳐도 아무 일이 안 일어나서, 고친 사람에게 오해만 남기거든요.

배울 것은 YAML 문법이 아니라 주석 세 줄

설정 파일에서 정말 중요한 건 값이 아니라 #으로 시작하는 주석이에요. 셋 다 "이 칸을 어떻게 채워야 하나"를 적어 둔 거예요.

  • "기사 하나를 보고 예/아니오로 답할 수 있는 질문이어야 한다" — 중요도 기준을 쓰는 규칙이에요. "좋은 기사인가"처럼 예/아니오가 안 갈리는 문장이면 모델이 매번 다르게 해석해요. 문장의 모양을 제약하는 거예요.
  • "추상어('홍보성') 말고 구체적인 표현으로" — 바로 아래에서 자세히 봐요.
  • "위에 있을수록 우선" — 기준끼리 부딪힐 때 무엇이 이기는지를 미리 정해 둬요. 안 적으면 그 판단도 모델이 매번 새로 해요.

"버릴 것: 홍보성 기사" 대신 "MOU·업무협약·투자유치·수상 등 당사자 홍보성 소식"이라고 적은 이유는, '홍보성'이 사람마다 판정이 다른 추상어라서예요. 사람끼리도 어디까지가 홍보성인지 갈리니, 모델도 실행마다 다르게 해석해요. "MOU·업무협약·투자유치·수상"처럼 구체적인 유형을 늘어놓으면 해석할 여지가 거의 없어요. 문장을 짧게 만들려는 것도 아니고(오히려 길어졌어요), 한국어라서 모델이 '홍보성'을 못 알아듣는 것도 아니고, YAML이 추상어를 금지하는 것도 아니에요. 판정이 흔들리지 않게 하려는 거예요.

중요꼭 기억할 것

모델에게 주는 기준은 추상어 대신 구체적인 유형으로 적어요. "홍보성 기사를 버려라"는 사람마다, 실행마다 판정이 달라지지만 "MOU·업무협약·투자유치·수상 소식을 버려라"는 거의 안 틀려요. 기준 문장은 기사 하나를 보고 예/아니오가 갈리는 모양이어야 해요.

그러니 설정 파일을 잘 만든다는 건 값을 옮겨 놓는 일이 아니라, 그 값을 어떻게 채워야 하는지를 파일 안에 적어 두는 일이에요. 주석이 없으면 다음 사람은 빈칸 앞에서 무엇을 적어야 할지 몰라요.

영어 기사는 제목만 보고 넘겨서 중요한 걸 놓친다기준 문장이 아니에요 — 한국어 요약을 만드는 14편 취재 단계의 몫이에요없음

세 번째 줄처럼 모든 번거로움이 기준 문장이 되지는 않아요. "무엇을 고를까"의 문제인지, "어떻게 전할까"의 문제인지 먼저 갈라 봐요. 첫째 줄의 "이미 고른 기사와 같은 발표"는 다른 기사를 함께 봐야 답할 수 있는 문장이라, 후보를 한 화면에 모아 비교하는 본선에서만 제대로 먹혀요. 확실히 막으려면 13편에서 본 것처럼 사건 라벨을 코드로 세는 쪽이 낫고요.

나쁜 예도 같이 봐 둘게요. "좋은 기사", "의미 있는 소식", "업계에 영향이 큰 발표" 같은 문장은 기사 하나를 앞에 두고 예/아니오를 가를 수가 없어요. 모델은 이런 문장을 받으면 매번 자기 식으로 채워 넣어요.

중요꼭 기억할 것

기준 문장은 머릿속 인상이 아니라 내가 실제로 겪은 번거로움에서 뽑아요. "같은 발표를 여러 번 읽는다"를 "같은 회사의 같은 발표를 다룬 기사는 버린다"로 바꾸듯, 기사 하나를 보고 예/아니오가 갈리는 문장으로 옮기고, 선별로 풀 문제가 아니면 기준 문장에 넣지 않아요.

개념: 설정과 코드의 경계

설정은 같은 프로그램을 다른 상황에 쓰려고 바꾸는 값이고, 코드는 상황이 바뀌어도 그대로인 절차예요. 우리 경우 "중요도 기준 문장들"은 설정이고, "예선에서 묶음별로 뽑고 본선에서 한 화면에 비교한다"는 코드예요.

경계가 흐리면 재사용이 안 돼요. 다른 분야로 옮길 때 고칠 곳이 코드 전체에 흩어져 있으면, 옮기기보다 새로 만드는 게 빨라요. 그렇게 같은 구조를 여러 번 다시 만들고, 각각이 조금씩 다르게 낡아 가요.

경계를 긋는 질문은 둘이에요. "분야가 바뀌면 이 값이 바뀌나?", 그리고 "이걸 고칠 사람이 개발자인가?" 첫째가 예면 설정 후보이고, 둘째가 아니오면 코드 밖 설정 파일로 빼요. audience.yaml의 문장들은 둘 다 해당해요. 반면 13편의 BATCH(예선 묶음 크기 40)와 TARGET(발행 목표 5)은 분야에 따라 바뀔 수는 있지만 고칠 사람이 개발자예요. 이런 값은 독자 문장과 섞지 말고 따로 둘 수 있어요.

그렇다고 모든 걸 설정으로 빼면 아무것도 이해할 수 없게 돼요. 항목이 많을수록 실제 동작을 알려면 코드와 설정을 함께 읽어야 하고, 설정 조합이 늘어나 테스트도 어려워져요. 그래서 판단 기준은 "바뀔 수 있는가"보다 "실제로 바뀐 적이 있는가"에 가까워요.

나쁜 선택 vs 좋은 선택 — "요즘 브리핑이 좀 심심하다"는 말을 들었을 때

매일 아침 알림은 빠짐없이 오는데, 몇 주 전부터 실린 기사가 시시하다는 말을 들은 같은 상황이에요.

나쁜 선택좋은 선택
무엇을 했나: Actions 실행 목록이 매일 초록불이니 파이프라인은 멀쩡하다고 보고, 느낌대로 선별 프롬프트의 기준 문장부터 이리저리 고쳤어요.

무슨 일이 생기나: 매체가 조용히 죽었는지, 한 매체가 자리를 독차지하는지, 검수에서 기사가 빠지는지 모른 채 엉뚱한 곳을 고쳐요. 고친 뒤 나아졌는지 비교할 기록도 없어서 "좋아진 것 같다"로 끝나고, 같은 말을 몇 주 뒤에 또 들어요.		 무엇을 했나: 실행마다 네 건수와 by_source·log를 한 줄씩 남겨 두었고, 이 말을 듣자 성적표부터 뽑았어요.

무슨 일이 생기나: 몇 주째 0인 매체, 한쪽으로 몰린 기여, 낙폭이 커진 단계가 숫자로 드러나 고칠 곳이 하나로 좁혀져요. 기준 문장을 고쳤다면 고친 날 앞뒤의 기록을 나란히 놓고 정말 나아졌는지 볼 수 있어요.

정리하면 매일 도는 자동화에서 물을 건 "잘 되고 있다는 말을 숫자로 할 수 있나?"예요. 초록불은 "멈추지 않았다"까지만 말해 줘요.

다른 분야로 옮길 땐 단계마다 "분야가 바뀌면 이 단계의 무엇이 바뀌나"를 물어요. 소스가 달라지는 수집이 대개 가장 크게 바뀌고, 선별 기준은 설정 파일의 문장만 고치면 되고, 뼈대·발행·실행 기록은 그대로 써요. 구조와 내용을 떼어 둔 만큼 옮기는 비용이 줄어요.

다루지 않은 것

  • 평가셋과 회귀 검사 — 이 시리즈에서는 프롬프트를 고친 뒤 "좋아진 것 같다"로 판단했어요. 제대로 하려면 기사 30~50건에 사람이 정답을 붙인 평가셋을 만들고, 고칠 때마다 그 위에서 점수를 다시 재야 해요. 그래야 한 곳을 고쳤더니 다른 곳이 나빠지는 회귀6를 잡아요.
  • 사람이 끼어드는 자리 — 지금은 사람 승인 없이 발행해요. 발행 전에 사람이 한 번 보게 하려면 그래프를 멈췄다가 승인 뒤 다시 이어 가는 기능이 필요해요. 이게 HITL7이에요.
  • 비용·지연 최적화 — 모든 단계에 같은 모델을 썼어요. 예선처럼 판단이 단순한 곳은 더 싼 모델로 바꿀 여지가 있어요.
  • 소스 확장과 스크래핑 — 12편 사다리의 맨 아래 칸은 "안 쓴다"로 닫았어요. 위 칸이 없는 분야라면 필요해지고, 그땐 robots.txt 확인과 화면 구조 변경 감지가 통째로 따라와요.

  • "실행할 때마다 기록을 파일로 남겨 줘" — 파일을 열고 읽는 줄마다 encoding="utf-8"이 붙었는지, 덧붙이기("a")로 여는지
  • "기준 문장을 설정 파일로 빼 줘" — 옛 CRITERIA·SYS 문자열 정의가 코드 어딘가에 남아 있지 않은지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
수집 건수는 평소와 비슷한데 브리핑이 며칠째 두세 건만 와요. 에러는 하나도 없어요 성적표 아래 깔때기 줄이에요. 수집 → 선별의 낙폭은 원래 커서 대개 범인이 아니고, 취재 → 검수 통과 쪽 낙폭을 봐요 그날 기록의 log에서 "③ 취재 제외 … 본문 N자" 줄이 많으면 본문 추출(14편), "④ 검수" 줄 끝의 "불합격" 목록이 길면 검수 쪽이에요. 하루치만 보지 말고 며칠의 비율을 나란히 봐요 (깔때기 관측)
성적표에서 한 매체만 몇 주째 발행 기여 0이에요. 수집 로그의 응답 없음 목록에는 안 떠요 관문과 본문 추출은 대개 범인이 아니에요(채택할 때 통과했어요). 그 매체 기사가 어느 단계에서 사라지는지를 봐요 먼저 그 매체 피드 주소를 브라우저로 열어 새 글이 실제로 올라오는지 봐요(12편). 올라오는데 몇 주치 log의 "③ 취재" 줄(취재 노드는 성공해도 제외돼도 매체 이름을 한 줄씩 남겨요)에 이름이 한 번도 안 보이면 선별에서 떨어지는 거라 뺄 후보예요. 이 시리즈 코드는 선별에서 떨어진 기사의 매체를 따로 적지 않아서, 여기까지는 "안 보인다"로 추정하는 거예요 (관문을 다 통과한 매체가)
윈도우 로컬 주피터에서 성적표 셀이 UnicodeDecodeError: 'cp949' codec can't decode byte …로 멈춰요. git pull로 Actions 기록을 받은 직후에 흔해요. 기록 셀이 UnicodeEncodeError: 'cp949' codec can't encode character …로 멈추기도 해요 파일을 여는 open("a")와 읽는 read_text() 줄이에요. JSON 내용이나 로그 문장은 범인이 아니에요. Colab·Actions에서는 안 나고 윈도우에서만 보여요 두 줄에 encoding="utf-8"을 붙여요. 인코딩 없이 이미 써 둔 파일은 encoding="cp949"로 한 번 읽어서 encoding="utf-8"로 다시 저장해요 (윈도우에서는 인코딩을 꼭)
Actions는 매일 초록불인데, git pull을 해도 노트북의 store/metrics.jsonl 줄 수가 그대로예요 워크플로 파일의 "기록 커밋" 단계와 permissions: 줄, 그리고 저장소의 Commits 화면이에요 Commits에 newsroom-bot이 올린 "metrics: 날짜" 커밋이 있는지 봐요. 없으면 단계가 빠졌거나 조건에 걸린 거예요(dry_run을 체크해 손으로 돌린 회차는 원래 커밋하지 않아요). 그 단계가 빨간 X에 403이면 쓰기 권한 문제예요 (권한 오류)
audience.yaml의 기준 문장을 고쳤는데, 다음 실행에서 고른 기사 성격이 전혀 안 달라져요 노트북이면 설정을 읽는 셀을 다시 실행했는지, graph.py면 13편 CRITERIA·14편 SYS 문자열 정의가 아래쪽에 남아 덮어쓰고 있지 않은지예요 print(CRITERIA)로 새 문장이 찍히는지 봐요. 옛 문장이면 셀 재실행이나 옛 정의 삭제가 답이에요. 새 문장이 찍히는데도 결과가 같다면, 그땐 설정이 아니라 모델이 부탁을 확률적으로만 지키는 쪽(13편)을 의심해요 (audience.yaml 만들고 읽기)

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 뉴스레터 에이전트 코드가 있는 프로젝트 폴더에서

이 프로젝트에서 실행 기록과 설정 파일을 다루는 곳을 찾아서 파일·줄 번호로 표로 보여 줘. 아직 코드는 고치지 마.
1. 파일을 열거나 읽고 쓰는 곳(open, read_text, write_text) 전부와, 각각 encoding을 적었는지
2. CRITERIA와 SYS가 정의되는 곳이 몇 군데인지, audience.yaml을 읽는 코드보다 뒤에 옛 문자열 정의가 남아 있는지
3. 워크플로 파일에 store/를 커밋하는 단계가 있는지, permissions에 contents: write가 있는지

함께 읽으면 좋은 글

  • 안전하게 쓰고 평가하기 — 권한·회귀·과제 제출 — 여기서 다루지 않은 평가셋과 회귀 검사를 전후 판정으로 풀어 본 글이에요.
  • 통과했다는 말로는 부족하다 — 두 층 채점과 채택·축소·폐기 판정 — JSONL 실행 기록을 근거로 결과를 판정하는 과정을 다룬 글이에요.
  • GitHub Actions 예약 발행 — Actions가 저장소에 커밋하려면 필요한 쓰기 권한과 UTC cron을 정리한 글이에요.
  • 완성한 판단을 SKILL.md로 남기기 — YAML의 속성: 값 모양을 처음 설명한 글이에요.
  • JSON Lines — 한 줄에 JSON 하나씩 쌓는 형식의 공식 설명이에요.
  1. JSONL(JSON Lines) — 한 줄에 JSON 기록 하나씩 쌓는 텍스트 파일 형식으로, 두 층 채점 글에서 세션 전사를 담을 때도 나왔어요. ↩
  2. 인코딩(encoding) — 글자를 파일에 저장할 바이트로 바꾸고 다시 글자로 읽어 들이는 규칙이에요. ↩
  3. cp949 — 한국어 윈도우가 기본으로 쓰는 한글 인코딩으로, 세계 표준인 UTF-8과 같은 한글을 서로 다른 바이트로 저장해요. ↩
  4. YAML — 속성: 값 형태로 정보를 줄 단위로 적는, 사람이 읽기 쉬운 표기 형식으로 SKILL.md로 남기기 글에서 처음 다뤘어요. ↩
  5. 매직 명령(magic command) — 주피터 셀 맨 앞에 %나 %%로 붙여 파이썬 코드 대신 파일 저장 같은 특별한 동작을 시키는 명령이에요. ↩
  6. 회귀(regression) — 한 곳을 고친 뒤 예전엔 잘 되던 곳이 도리어 나빠지는 현상으로, 권한·회귀 글에서 전체 문항을 다시 돌려 잡는 법을 봤어요. ↩
  7. HITL(Human-in-the-loop) — 자동으로 도는 흐름 중간에 사람이 확인하거나 승인하는 단계를 끼워 넣는 설계예요. ↩
