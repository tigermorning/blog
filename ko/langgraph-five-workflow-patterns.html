앞 편에서 State·Node·Edge와 조건부 엣지로 갈림길과 반복을 만들었어요. 강의 후반부는 그 재료로 흔히 쓰이는 흐름 모양 다섯 가지를 하나씩 조립하는 시간이었어요. 출처는 Anthropic의 글 "Building Effective Agents"이고, 실습 데이터는 '모두런'이라는 가상 온라인 강의 플랫폼의 강의 노트와 녹취였어요. 그래프 구조에 집중하려고 일부러 더미 데이터를 썼대요.

다섯 모두 개발자가 경로를 그려 두는 워크플로예요. 가장 확실하고 통제하기 쉬운 모양부터 차례로 자율성을 조금씩 늘려 가는 순서예요. 모두 LLM을 여러 번 부르고, ②에서는 LLM이 입력을 분류하고, ④에서는 워커 수까지 LLM이 정하는데도 에이전트가 아닌 이유는 앞 편에서 정리한 기준 그대로예요. 호출 횟수나 도구 사용 여부가 아니라, 갈 수 있는 길을 개발자가 미리 다 그려 뒀는가가 기준이거든요. 에이전트 프레임워크인 LangGraph로 그렸다는 것도 기준이 아니에요. n8n 같은 워크플로 자동화 도구와 카테고리가 갈리는 건 제품이 무엇을 하려고 만들어졌느냐의 이야기고, 그걸로 무엇을 그리느냐는 따로예요(앞 편의 n8n 비교).

비유 — 식당 주방의 하루, 다섯 장면

앞 편의 주방으로 다시 가 볼게요. 하루 동안 이런 장면들이 벌어져요.

점심엔 코스 요리가 나가요. 손질, 조리, 플레이팅을 순서대로 하되 단계 사이에 검수대가 있어서 덜 된 접시는 다음 단계로 못 넘어가요. 주문이 몰리면 매니저가 주문서를 읽고 한식·양식·디저트 담당 중 한 명에게 넘겨요. 새 메뉴를 내기 전엔 맛·온도·모양 담당 셋이 한 접시를 동시에 검사하고 검수표 한 장에 각자 한 줄씩 적어요. 저녁엔 단체 예약이 들어와서 헤드셰프가 인원을 보고 메뉴 수를 정한 뒤 요리사 한 명 한 명에게 쪽지로 맡겨요. 마감 직전엔 시식 담당이 신메뉴를 맛보고 "간이 약해"라며 조리사에게 되돌리는데, 세 번 넘게 퇴짜 나면 사장님을 불러요.

핵심 한 줄: 다섯 장면 모두 "누가 무엇을 언제 할지"가 동선표에 미리 그려져 있어요 — 요리사가 알아서 동선을 바꾸는 장면은 하나도 없고, 그게 바로 에이전트와의 차이예요.

다만 여기서 비유가 끊기는 점이 있어요. 사람은 검수표에 줄을 더하는 걸 당연하게 하지만, LangGraph는 "합치는 법"을 선언하지 않으면 동시에 들어온 두 값을 에러로 막아요. ③에서 직접 봐요.

전체 흐름 — 다섯 모양을 한 장에

읽는 법: 줄마다 하나의 패턴이에요. 실선은 항상 지나가는 선, 점선은 조건에 따라 고르거나 실행 중에 개수가 정해지는 선이에요. 빨간 테두리가 각 패턴의 핵심 장치예요. 위에서 아래로 내려갈수록 흐름을 LLM에게 조금씩 더 맡겨요.

① 프롬프트 체이닝 — 순서대로, 사이에 검사

큰 작업을 순서가 정해진 여러 단계로 쪼개고, 각 단계의 LLM 호출이 앞 단계의 결과를 받아 처리하는 모양이에요. 강의 실습은 구어체 강의 녹취를 받아 (1) 학습자가 읽을 3문장 노트로 다듬고, (2) 다듬는 동안 핵심 용어가 사라지지 않았는지 파이썬 문자열 검사로 확인하고, (3) 통과하면 학습 목표 문장을 뽑는 파이프라인이었어요.

개념 설명용 코드 — State 선언과 LLM 노드 함수는 생략한 뼈대예요

KEY_TERMS = ["State", "리듀서"]               # 다듬는 동안 사라지면 안 되는 용어

def gate_check(state) -> str:                  # 게이트: LLM이 아니라 코드가 검사한다
    missing = [t for t in KEY_TERMS if t not in state["note"]]
    return "pass" if not missing else "fail"

builder.add_edge(START, "polish_note")         # LLM ①: 녹취를 3문장 노트로
builder.add_conditional_edges("polish_note", gate_check,
                              {"pass": "write_objectives", "fail": "fix_note"})
builder.add_edge("fix_note", "write_objectives")
builder.add_edge("write_objectives", END)      # LLM ②: 학습 목표 뽑기

"이걸 한 번에 시키면 안 되나?" 싶은데, 한 호출로 몰면 세 가지 문제가 생겨요.

  • 요구가 많으면 모델이 일부를 흘려요. 셋을 시켰는데 둘만 하거나, 학습 목표에 집중하다 노트에서 용어를 빠뜨려요.
  • 어디서 틀렸는지 알 수 없어요. 단계를 쪼개 두면 중간 결과가 State에 남아서 result["note"]만 꺼내 봐도 어느 단계까지 멀쩡했는지 보여요.
  • 중간에 끼어들 틈이 없어요. 단계 사이가 열려야 그 틈에 우리 코드를 끼울 수 있어요.

LLM의 출력은 확률적이라 같은 프롬프트에도 결과가 달라요. 그 사이에 결정적2인 코드 검사를 끼우면 전체 시스템의 신뢰도가 올라가요. 앞 편에서 날짜 계산을 LLM 대신 함수에 맡기던 것과 같은 이유예요. 다만 이 게이트는 누락만 잡아요. 용어가 들어 있기만 하면 그 용어를 틀리게 설명해도 통과해요. 이게 실제로 어떤 모습인지는 아래에서 노트 두 개로 확인해요.

하나 더. Anthropic 원문 그림은 게이트에서 떨어지면 그냥 종료하는데, 강의는 보정 노드로 보냈어요. 어느 쪽이 맞는지는 상황에 달렸어요. 학습 자료를 배포하는 일이라면 용어가 뭉개진 노트를 내보내느니 멈추고 사람을 부르는 게 나을 수도 있어요.

맞는 일: 단계에 자연스러운 순서가 있고, 단계마다 품질을 중간 확인할 수 있는 작업. 안 맞는 일: 단계끼리 독립적이면 병렬화가, 어떤 단계를 밟을지가 입력마다 다르면 라우팅이 나아요.

게이트가 못 보는 것 — 결정적 검사의 한계

강의는 체이닝 설명 끝에서 결정적인 계산에도 한계가 있다는 걸 알아 두라고 짚고 넘어갔어요. 처음엔 무슨 말인지 감이 안 왔는데, 위 gate_check의 검사 줄에 노트 두 개를 직접 넣어 보니 바로 보였어요.

실행: 로컬 파이썬 — 아무 환경 OK, 따로 설치할 것 없어요

KEY_TERMS = ["State", "리듀서"]

note_a = "리듀서는 State에서 오래된 값을 지워 주는 기능이다."
note_b = "state의 한 칸에 값이 여럿 오면 리듀서가 합치는 법을 정한다."

for note in [note_a, note_b]:
    missing = [t for t in KEY_TERMS if t not in note]
    print("통과" if not missing else f"실패 (누락: {missing})")

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

통과
실패 (누락: ['State'])

판정이 거꾸로 나왔어요.

  • 틀린 설명이 통과했어요. note_a에는 두 용어가 다 들어 있으니 게이트를 지나가요. 그런데 리듀서는 값을 지우는 장치가 아니라, 같은 칸에 여러 값이 들어올 때 어떻게 합칠지 정하는 장치예요(아래 ③ 병렬화에서 봐요). 게이트는 글자가 있는지만 볼 뿐, 그 글자가 들어간 문장이 맞는 말인지는 몰라요.
  • 맞는 설명이 떨어졌어요. note_b는 뜻이 맞는데 State를 소문자 state로 적었어요. 파이썬의 in은 대소문자까지 똑같아야 같은 글자로 쳐서 "State가 빠졌다"며 떨어뜨려요. 사람이라면 같은 말로 읽었을 텐데요.

앞 편에서 날짜 계산을 함수에 맡긴 것처럼, 결정적인 검사는 정해 둔 규칙 안에서는 절대 흔들리지 않아요. 대신 규칙 밖의 일은 아예 못 봐요. 그래서 검사를 이렇게 나눠 맡겨요.

둘은 서로를 대신하는 게 아니라 겹쳐 쓰는 관계예요. "용어가 빠지지 않았나"처럼 확실하게 걸 수 있는 건 코드로 걸고, 그 위에 뜻을 보는 검사를 얹어요. ⑤ 평가자-최적화자에서 LLM 평가자를 따라 고쳐 쓰다가 주제가 엉뚱하게 흘러간 장면이 나오는데, 그때 "무엇을 잃으면 안 되는가"를 붙잡아 주는 것도 결국 이 코드 게이트예요.

게이트를 두는 진짜 이유와, 코드로 못 하는 검사

중요6강에서 짚은 내용

게이트를 두는 이유는 하나예요. 답이 매번 조금씩 달라지는 LLM 단계들 사이에 늘 같은 판정을 내리는 코드 검사를 끼워서, 틀린 중간 결과가 다음 단계로 흘러가지 못하게 막는 거예요. 한 단계의 실수가 뒤 단계 전체로 번지기 전에 문 앞에서 끊는 셈이에요.

반대로 게이트가 호출 수나 시간을 줄여 주지는 않아요. 검사에서 떨어지면 보정 노드가 LLM을 한 번 더 부르니 호출은 오히려 늘 수 있고, 여러 단계를 동시에 돌려 시간을 줄이는 건 ③ 병렬화의 일이에요. 다음 걸음을 LLM에게 스스로 고르게 하는 것도 게이트가 아니라 에이전트 쪽 이야기고요.

그런데 바로 위에서 본 것처럼 코드 게이트는 규칙으로 적을 수 있는 것만 봐요. "처음 배우는 사람이 이해할 수 있는 노트인가?"를 검사하고 싶다면요? 이건 어떤 단어가 들어 있는지로는 판단할 수 없어요. 용어를 풀어 설명했는지, 설명 순서가 자연스러운지 같은 뜻을 읽어야 알 수 있어서 if문 규칙으로는 못 적어요.

중요6강에서 짚은 내용

뜻을 읽어야 하는 검사는 LLM을 게이트로 써서 만들어요. 평가 기준을 프롬프트에 구체적으로 적고, LLM이 "통과/실패"와 그 이유를 정해진 형식으로 답하게 한 뒤, 그 답으로 조건부 엣지를 갈라요. 실패하면 그 이유를 보정 노드에 넘겨 다시 고치게 하고요. "정해진 형식"은 바로 다음 ② 라우팅의 구조화 출력이 맡아요. 이렇게 하면 '늘 같은 판정'은 포기하는 대신 뜻을 볼 수 있어요. 그래서 둘 중 하나를 고르는 게 아니라, 확실하게 걸 수 있는 건 코드 게이트로 먼저 걸고 그 위에 LLM 게이트를 얹어요.

채점하는 LLM도 틀릴 수 있다는 한계는 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge에서 다뤘고, 떨어진 이유를 되돌려 고쳐 쓰는 반복은 ⑤ 평가자-최적화자로 이어져요.

② 라우팅 — 먼저 분류하고, 한 갈래로

앞 편의 간 맞추기에서도 갈림길을 만들었지만 그땐 "소금 3숟갈 이상" 같은 규칙이 판단했어요. 라우팅은 그 판단을 LLM이 해요. 강의 노트를 개념설명·코드예제·실습과제로 나누는 일은 글자 수나 키워드로 안 되거든요. "직접 해 보면 알 수 있듯이…"로 시작하는 개념설명도 있으니까요. 규칙으로 가르는 갈래를 셋 이상으로 늘리거나 화살표에 한국어 라벨을 다는 연습은 앞 편의 갈림길 더 밀어붙이기에서 해 봤어요. 판단하는 쪽이 규칙에서 LLM으로 바뀔 뿐, 목적지 목록과 라우터의 반환값을 맞춰야 하는 건 똑같아요.

그래프로 보면 라우팅은 세 조각이에요.

  1. 분류 노드 — LLM이 입력을 읽고 "주문·예약·불만 중 무엇인가"를 하나 골라 State에 적어요. 주방에서 주문서를 읽는 매니저예요.
  2. 조건부 엣지 — 적힌 값을 보고 다음에 갈 노드 이름을 골라요. 매니저가 체크한 칸에 따라 주문서가 담당 요리사에게 가는 길이에요.
  3. 처리 노드들 — 갈래마다 하나씩 있고, 자기 종류만 처리해요. 셋 중 한 곳만 실행돼요.

조건부 엣지는 분류 노드가 적은 값을 그대로 받아 길을 찾아요. 그러니 분류 노드의 답은 반드시 정해 둔 세 값 중 하나여야 해요.

문제는 LLM 답이 자유 문장이라는 거예요. "이 노트는 코드 예제로 보입니다"라고 답하면 그 문장을 우리가 해석해서 갈라야 하고, 표현이 조금만 달라져도 깨져요. 이걸 막는 게 구조화 출력3이에요.

실행: 로컬 파이썬 — OPENAI_API_KEY 환경변수 필요

from typing import Literal
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class Route(BaseModel):
    category: Literal["주문", "예약", "불만"] = Field(description="손님 메시지의 종류")
    reason: str = Field(description="그렇게 분류한 근거 한 문장")

router = ChatOpenAI(model="gpt-4o-mini").with_structured_output(Route)
r = router.invoke("다음 주 토요일 저녁 6시에 네 명 자리 되나요?")
print(r.category, "/", r.reason)
  • with_structured_output(Route) — Pydantic4 클래스를 JSON 스키마로 바꿔 "이 모양으로만 답하라"고 모델에게 전달해요. 앞 편에서 독스트링이 도구 스키마가 되던 것과 같은 원리라서, Field(description=...)을 성실하게 쓰는 게 분류 품질로 이어져요.
  • Literal[...]이 핵심이에요. 제 컴퓨터에서 스키마를 찍어 보니 "enum": ["주문", "예약", "불만"]으로 들어가 있었어요. 모델이 고를 수 있는 답의 범위 자체가 이 세 값으로 좁아지는 거예요. 그래서 {"주문": "take_order", "예약": "book_table", "불만": "apologize"} 같은 매핑을 조건부 엣지에 안심하고 쓸 수 있어요. 강의 코드도 HANDLER[state["category"]]처럼 분류 값으로 딕셔너리에서 다음 노드 이름을 찾았어요. 값이 셋으로 보장되지 않으면 "예 약"(띄어쓰기)이나 "reservation" 같은 변형이 왔을 때, 딕셔너리에 없는 키라서 KeyError가 나고 그래프가 그 자리에서 멈춰요.
  • reason 칸을 같이 받아요. 분류가 틀렸을 때 왜 그렇게 봤는지 들여다볼 창이에요. 근거는 Literal이나 구조화 출력이 알아서 붙여 주는 게 아니라, 이렇게 칸을 따로 선언했기 때문에 채워져요. 칸이 없으면 모델은 분류 값만 내놓아요.

Literal이 막아 주는 것, 못 막는 것

여기서 헷갈리기 쉬운 말이 하나 있어요. "Literal은 파이썬 타입 힌트일 뿐이라 실행에는 아무 영향이 없다." 보통은 맞는 말이에요. 업무 기록 서버 직접 만들기에서 봤듯이 타입 힌트는 값의 종류를 적어 두는 표시일 뿐이라, 함수에 x: int라고 적어 두고 글자를 넘겨도 파이썬은 막지 않아요. 그런데 with_structured_output은 이 힌트를 읽어서 모델에게 보낼 스키마를 만들어요. 그래서 여기서는 힌트 한 줄이 모델의 실제 답을 바꿔요. ③에서 볼 Annotated도 파이썬은 무시하고 LangGraph가 읽어 쓰는 같은 경우예요.

그렇다고 Literal이 분류를 맞게 해 주는 건 아니에요. 지켜 주는 건 답의 형식이고, 답이 맞는지는 별개예요. 답의 모양과 채점법에서 본 "형식은 강제해도 사실까지 강제하지는 못한다"와 같은 이야기예요.

Literal이 막아 주는 것못 막는 것
세 값 밖의 답 — "예 약", "reservation", "기타"세 값 안에서 고른 틀린 답 — 예약 문의를 "주문"으로
매핑에서 KeyError가 나 그래프가 멈추는 일에러 없이 멀쩡히 돌면서 엉뚱한 처리 노드로 가는 일

주방으로 옮기면, 매니저가 쓰는 주문서에 체크 칸이 세 개뿐이라 "기타: 애매함"이라고 휘갈길 수는 없어요. 하지만 예약 전화를 받고 '주문' 칸에 체크하는 실수는 여전히 할 수 있어요. 오른쪽 칸이 더 무서운 건 에러가 안 나서 아무도 모르고 지나가기 때문이에요.

중요7강에서 짚은 내용

라우팅에서 Literal["개념설명", "코드예제", "실습과제"]가 중요한 이유는, 모델이 이 세 값 말고는 답할 수 없게 묶어 주기 때문이에요. 분류 값으로 다음 노드 이름을 찾을 때 뜻밖의 값이 와서 KeyError로 멈추는 일을 구조부터 막아 줘요. 여기서 타입 힌트는 장식이 아니에요. with_structured_output이 읽어서 모델에게 보내는 규칙이 돼요. 다만 막아 주는 건 답의 형식뿐이고, 세 값 중 맞는 것을 골랐는지는 따로 확인해야 해요. 분류 근거도 저절로 붙지 않으니 reason 칸을 따로 둬요.

그 오른쪽 칸이 강의 실습에서 실제로 벌어졌어요. 정답 라벨을 붙인 노트 6건을 분류시켰더니 4건만 맞았어요(67%). 모두 세 값 중 하나로 답했으니 에러는 한 번도 안 났는데 말이에요. 여기서 reason 창이 제 몫을 했어요. 틀린 2건의 reason을 보니 둘 다 "원리를 설명하고 있어서 개념설명"이라고 했고, 원문을 보면 코드 한 줄과 그 코드를 설명하는 문장이 함께 있었어요. 모델이 틀렸다기보다, 개념설명과 코드예제가 서로 배타적인 부류가 아니라 한 노트가 동시에 가질 수 있는 두 성질이었던 거예요. 이런 라벨로 하나만 고르게 하면 프롬프트를 아무리 다듬어도 정확도가 안 올라가요. 해법은 "코드가 있으면 코드예제 우선" 같은 판정 우선순위를 정하거나, 여러 라벨을 허용하고 해당 처리를 동시에 돌리는 병렬화로 바꾸는 거예요.

라우팅을 쓰면 각 처리 노드는 자기 일만 알면 돼요. 용어 카드 노드의 프롬프트엔 용어 카드 얘기만 있으니 짧고 선명해지고, 채점 기준 양식이 바뀌면 그 노드 하나만 고치면 돼요. 모델도 라우팅할 수 있어요. 쉬운 일은 싸고 작은 모델로, 어려운 일만 비싼 모델로 보내면 품질을 크게 잃지 않고 비용을 줄일 수 있어요.

③ 병렬화 — 동시에 돌리고, 합친다

강의는 이 패턴을 일부러 에러로 시작했어요. 저도 따라 해 봤어요. 검사 노드 셋이 같은 checks 칸에 동시에 쓰는 그래프를, 합치는 법 없이 한 번, 합치는 법을 붙여서 한 번 돌려요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class BadPlate(TypedDict):
    checks: list                                   # 리듀서 없음: 기본은 덮어쓰기

class Plate(TypedDict):
    checks: Annotated[list, operator.add]          # 여러 값이 오면 + 로 이어 붙인다
    verdict: str

def check_taste(state): return {"checks": [("맛", 4)]}
def check_temp(state):  return {"checks": [("온도", 2)]}
def check_look(state):  return {"checks": [("모양", 5)]}

def aggregate(state):
    low = [name for name, score in state["checks"] if score < 3]
    return {"verdict": f"총 {len(state['checks'])}건, 다시 할 것: {low or '없음'}"}

def build(schema):
    b = StateGraph(schema)
    for name, fn in [("taste", check_taste), ("temp", check_temp), ("look", check_look)]:
        b.add_node(name, fn)
        b.add_edge(START, name)          # START에서 세 갈래로 동시에 (팬아웃)
        b.add_edge(name, "aggregate")    # 세 갈래가 한곳으로 (팬인)
    b.add_node("aggregate", aggregate)
    b.add_edge("aggregate", END)
    return b.compile()

try:
    build(BadPlate).invoke({"checks": []})
except Exception as e:
    print(type(e).__name__, "|", str(e).splitlines()[0])

print(build(Plate).invoke({"checks": []}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

InvalidUpdateError | At key 'checks': Can receive only one value per step. Use an Annotated key to handle multiple values.
{'checks': [('모양', 5), ('맛', 4), ('온도', 2)], 'verdict': "총 3건, 다시 할 것: ['온도']"}

에러 문장은 "한 스텝에 이 키로 값을 하나만 받을 수 있으니, 여러 값을 받으려면 Annotated 키를 쓰라"는 뜻이에요. 왜 이런 일이 생기는지는 LangGraph의 실행 단위를 알면 풀려요.

  • 슈퍼스텝5 — LangGraph는 노드를 하나씩 도는 게 아니라, 실행 준비가 된 노드를 한 스텝에 모두 동시에 돌리고, 스텝이 끝나면 반환값을 한꺼번에 State에 합쳐요. 세 검사 노드는 같은 스텝에서 돌았어요.
  • 기본 규칙은 덮어쓰기예요. 노드가 돌려준 키만 새 값으로 바뀌고 돌려주지 않은 키는 그대로 남는다는 건 앞 편의 합치기 규칙 확인하기에서 직접 봤어요. 그런데 같은 스텝에 같은 키로 값이 셋 오면 무엇을 남길지 정할 수 없어요. LangGraph는 아무거나 고르지 않고 에러를 내요.
  • 리듀서6로 합치는 법을 알려 줘요. Annotated[list, operator.add]는 "이 칸은 리스트이고, 여러 값이 오면 +로 이어 붙여라"예요. Annotated는 타입에 덧붙임 정보를 다는 파이썬 표준 문법인데, 파이썬은 무시하고 LangGraph가 읽어서 합치는 규칙으로 써요. 앞 편의 MessagesState가 메시지를 쌓아 올리던 것도 이 장치 덕분이었어요.

고친 쪽 출력을 보면 세 결과가 다 살았고, aggregate는 셋이 다 모인 뒤에 한 번만 돌았어요("총 3건"). 이렇게 한 노드에서 여러 갈래로 펼치는 걸 팬아웃, 여러 갈래가 하나로 모이는 걸 팬인이라고 해요. 그런데 checks의 순서가 모양·맛·온도예요. 코드에 적은 순서(맛·온도·모양)와 달라요. 병렬 결과의 순서는 보장되지 않아요. 그래서 항목마다 이름표를 붙여 두는(("맛", 4)) 게 안전해요.

강의 실습은 성의 없이 쓴 노트 초안을 정확성·명확성·예시 세 축으로 동시에 평가했어요. 점수가 축마다 다르게 나오고 각 코멘트가 자기 축 이야기만 했대요. 한 호출에 기준을 다 몰아넣는 것보다 나은 점은 셋이에요. 모델의 주의가 가장 눈에 띄는 결함 하나로 쏠리지 않고, 한 축의 프롬프트만 고치거나 축을 하나 더하는 게 쉽고, 세 번 연달아 부를 시간에 한 번 부르는 시간이면 끝나요. 다만 시간은 줄어도 호출 수와 요금은 그대로예요. 같은 검사를 여러 번 돌려 다수결로 판정하는 투표 방식도 같은 모양으로 만들 수 있어요.

에러의 진짜 원인 — 병렬 실행이 아니라 한 칸에 동시에 쓰기

이 수업은 병렬로 돌리자마자 에러가 나는 장면으로 시작해서, 저는 처음에 "LangGraph는 병렬로 돌리면 에러가 난다"고 읽었어요. 그런데 에러는 병렬 실행 자체가 아니라 한 칸에 동시에 쓴 것 때문이에요. 근거가 셋 있어요.

  • 에러 문장이 고치는 법을 알려 줘요. "여러 값을 받으려면 Annotated 키를 쓰라"고 했죠. 병렬 실행을 지원하지 않는 거라면 고칠 방법도 없어야 해요.
  • 위 코드의 두 번째 실행이 반례예요. 세 갈래는 그대로 두고 리듀서만 붙인 Plate는 에러 없이 돌아서 "총 3건"을 찍었어요.
  • 칸을 따로 두면 리듀서도 필요 없어요. 아래처럼 검사마다 자기 칸에 쓰게 하면 셋이 동시에 돌아도 에러가 안 나요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

class Scores(TypedDict):          # 리듀서 없음. 대신 검사마다 칸을 따로 둔다
    taste: int
    temp: int
    look: int

def check_taste(state): return {"taste": 4}
def check_temp(state):  return {"temp": 2}
def check_look(state):  return {"look": 5}

b = StateGraph(Scores)
b.add_node("check_taste", check_taste)
b.add_node("check_temp", check_temp)
b.add_node("check_look", check_look)
for name in ["check_taste", "check_temp", "check_look"]:
    b.add_edge(START, name)       # 세 갈래가 동시에
    b.add_edge(name, END)
print(b.compile().invoke({}))

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

{'taste': 4, 'temp': 2, 'look': 5}

정리하면 에러는 같은 스텝, 같은 칸, 리듀서 없음 세 조건이 모두 겹칠 때만 나요. 하나만 빠져도 안 나요.

그래프 모양실행 결과
동시에, 같은 칸, 리듀서 없음InvalidUpdateError
동시에, 같은 칸, 리듀서 있음셋 다 이어 붙어 남아요 (위 Plate)
동시에, 칸을 따로각자 자기 칸에 들어가요 (바로 위 코드)
순서대로, 같은 칸, 리듀서 없음에러 없이 덮어써서 마지막 값만 남아요

마지막 줄이 LangGraph가 동시 쓰기에서만 에러를 내는 이유예요. BadPlate의 세 검사를 맛, 온도, 모양 순서로 이어 돌리면 에러 없이 {'checks': [('모양', 5)]}만 남아요. 순서대로 돌 때는 뒤 노드가 앞 노드의 값을 보고 돌았으니, 덮어쓴 것도 뒤 노드가 고른 결과예요. 동시에 돈 노드들은 서로의 값을 못 본 채 썼으니, 하나만 골라 남기면 나머지가 소리 없이 사라져요. 그래서 LangGraph는 조용히 틀리는 대신 눈에 띄게 멈춰요.

비슷하게 오해하기 쉬운 것도 둘 있어요. 노드를 가르는 건 함수 이름이 아니라 add_node에 준 노드 이름이라서, 같은 함수를 두 노드에 붙여도 괜찮아요(노드 이름이 겹치면 실행하기도 전에 add_node에서 ValueError로 막혀요). 그리고 State에 리스트를 못 쓰는 것도 아니에요. 위 Plate의 checks도, 앞 편의 MessagesState도 리스트 칸이에요.

중요8강에서 짚은 내용

동시에 도는 두 노드가 같은 칸에 값을 돌려주면 InvalidUpdateError가 나요. State의 기본 규칙이 덮어쓰기라서, 같은 스텝에 같은 칸으로 값이 둘 오면 무엇을 남길지 정할 수 없거든요. LangGraph는 아무거나 골라 하나를 몰래 버리는 대신 에러로 알려 줘요. 고치는 법은 그 칸에 합치는 규칙(리듀서, 예: Annotated[list, operator.add])을 달거나, 노드마다 칸을 따로 두는 거예요.

④ 오케스트레이터-워커 — 몇 갈래일지 LLM이 정한다

병렬화에는 숨은 전제가 있었어요. 하위 작업(나눠 맡길 일 하나하나)의 개수와 종류를 개발자가 코드를 쓸 때 이미 알아야 해요. 평가 축이 셋이라 검사 노드도 셋을 미리 그렸죠. 주방으로 치면 검사 담당 셋을 영업 전에 동선표에 그려 둔 거예요.

그런데 단체 예약이 들어오면 사정이 달라요. 손님 수를 봐야 메뉴가 몇 개일지 정해지니, 요리사가 몇 명 필요할지 영업 전에는 몰라요. 학습 가이드도 같아요. "이 주제로 가이드를 만들어 줘, 섹션 수는 알아서"라고 하면 섹션이 3개일 수도 7개일 수도 있어요. 그렇다고 영업 중에 동선표에 조리대를 새로 그려 넣을 수도 없어요. 노드를 등록하는 add_node는 compile() 전에만 부를 수 있거든요.

그래서 요리사 자리는 동선표에 하나만 그려 두고, 헤드셰프가 메뉴를 정한 다음 "이 쪽지 들고 요리사 한 명 더!"를 메뉴 수만큼 외쳐요. 이 외침이 Send예요.

개념 설명용 코드 — 아래 전체 코드에서 한 줄만 떼어 뜯어본 거예요

Send("cook", {"dish": d})
     ^^^^^^  ^^^^^^^^^^^
     (1)     (2)
# (1) 부를 노드 이름   (2) 그 요리사에게만 건넬 쪽지

아래 코드의 assign은 메뉴 목록에서 요리를 하나씩 꺼내(for d in state["menu"]) Send를 하나씩 만들어 목록으로 돌려줘요. 메뉴가 셋이면 Send도 셋이고, 같은 cook 노드가 쪽지를 한 장씩 들고 세 번 동시에 돌아요. 보통 라우터는 "다음은 이 노드" 하고 이름 하나를 돌려주는데, 여기서는 Send 목록을 돌려줘서 "이 노드를 이 쪽지로 N번"이라고 지시하는 거예요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class Party(TypedDict):
    guests: int
    menu: list
    plates: Annotated[list, operator.add]   # 워커들의 결과를 모으는 칸

class CookInput(TypedDict):                  # 요리사 한 명이 받는 전용 쪽지
    dish: str

def plan(state: Party):                      # 실제로는 LLM이 메뉴 수를 정하는 자리
    menu = ["전", "잡채", "갈비", "나물", "떡", "식혜"][: state["guests"] // 2]
    return {"menu": menu}

def assign(state: Party):
    return [Send("cook", {"dish": d}) for d in state["menu"]]   # 메뉴 수만큼 요리사 복제

def cook(state: CookInput):
    return {"plates": [f"{state['dish']} 완성"]}

def serve(state: Party):
    return {}

b = StateGraph(Party)
b.add_node("plan", plan)
b.add_node("cook", cook)
b.add_node("serve", serve)
b.add_edge(START, "plan")
b.add_conditional_edges("plan", assign, ["cook"])
b.add_edge("cook", "serve")
b.add_edge("serve", END)
g = b.compile()

for n in (6, 12):
    out = g.invoke({"guests": n, "plates": []})
    print(n, "명 →", len(out["plates"]), "접시:", out["plates"])

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

6 명 → 3 접시: ['전 완성', '잡채 완성', '갈비 완성']
12 명 → 6 접시: ['전 완성', '잡채 완성', '갈비 완성', '나물 완성', '떡 완성', '식혜 완성']

같은 그래프인데 한 번은 요리사가 3명, 한 번은 6명 불렸어요. draw_mermaid()로 찍어 보면 cook 노드는 여전히 하나고 plan -.-> cook 점선 하나뿐이에요. 그림에는 요리사 자리가 하나, 실행할 때 필요한 만큼 불려 나오는 거예요. 요리사들이 돌려준 plates는 리듀서(operator.add)를 단 칸이라, 세 명이 동시에 적어도 에러 없이 한 목록으로 모여요(③ 병렬화의 그 장치예요). 이렇게 펼쳐서 각자 처리하고 하나로 모으는 구조를 맵-리듀스7라고도 불러요.

요리사는 전표를 못 봐요 — 쪽지만 받아요

여기서 가장 중요한 성질이 있어요. Send로 불린 요리사는 주방의 전표(State) 전체를 받는 게 아니라 자기 쪽지만 받아요. 확인하려고 cook이 받은 걸 찍고, 쪽지에 없는 손님 수(guests)까지 읽어 보게 했어요.

실행: 로컬 파이썬 — 위 코드에서 cook 함수와 맨 아래 실행 줄만 이렇게 바꿔요

def cook(state: CookInput):
    print("요리사가 받은 것:", dict(state))
    print("손님 수를 읽으면:", state["guests"])   # 쪽지에 없는 칸을 읽어 본다
    return {"plates": [f"{state['dish']} 완성"]}

try:
    g.invoke({"guests": 6, "plates": []})
except Exception as e:
    print("에러:", type(e).__name__, e)

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

요리사가 받은 것: {'dish': '전'}
요리사가 받은 것: {'dish': '잡채'}
요리사가 받은 것: {'dish': '갈비'}
에러: KeyError 'guests'

요리사 셋이 받은 건 요리 이름 하나짜리 쪽지뿐이었고, 손님 수를 읽으려는 순간 KeyError로 멈췄어요. cook의 타입을 Party로 바꿔 적어도 결과는 같았어요. 타입 힌트는 표시일 뿐이고, 실제로 들어오는 건 Send에 담은 딕셔너리 그대로거든요.

왜 이렇게 만들었을까요? 요리사 셋이 동시에 서로 다른 요리를 맡아야 하는데, 전표의 한 칸에는 값을 하나만 적을 수 있어요. "지금 만들 요리" 칸을 전표에 두면 세 명에게 서로 다른 값을 줄 수가 없죠. 그래서 한 명씩 개인 쪽지를 주는 거예요.

중요9강에서 짚은 내용

Send("노드 이름", {...})의 두 번째 인자(괄호 안에 넣는 두 번째 값)는 그 워커 실행 한 번에만 건네는 전용 상태예요. 이 쪽지는 전표(State)에 옮겨 적히지 않고 그 워커에게만 가요. 워커가 받는 건 이 딕셔너리 그대로라서, 메인 State의 다른 칸(주제, 섹션 목록 등)은 볼 수 없어요. 워커가 알아야 하는 건 전부 이 쪽지에 담아 줘야 해요. 워커가 쓴 결과는 쪽지가 아니라 워커의 반환값으로 따로 돌아와 리듀서가 단 칸에 모여요.

강의 실습에서는 "LangGraph의 리듀서와 병렬 실행"이라는 주제를 주고 프롬프트에 "섹션은 3~5개"라는 범위만 줬더니 오케스트레이터가 5개를 골랐어요. 그런데 결과물을 읽어 보면 한계가 드러났대요.

  • 지어내기 — 쪽지에 섹션 제목만 받은 워커는 주제가 LangGraph라는 걸 몰라요(바로 위에서 본 성질이에요). 그래서 'LangGraph의 리듀서' 대신 학습 데이터에 훨씬 흔한 자바스크립트 Redux의 useReducer를 설명해 버렸어요. 해법은 프롬프트를 다듬는 게 아니라 주제와 근거 노트를 쪽지에 같이 넣어 주는 것이에요. Send("write_section", {"section": s, "topic": state["topic"]})처럼요.
  • 중복 — 계획할 때 섹션의 경계를 안 그어 주면 워커 두 명이 거의 같은 내용을 써요. "이 섹션에서 다루지 않을 것" 칸을 쪽지에 넣는 식으로 막아요.
  • 격리 — 워커끼리는 서로 뭘 썼는지 몰라요.

병렬화와 뭐가 다른가

두 패턴은 실행될 때 여러 갈래로 갈라졌다가 한곳에 모이는 모양이 닮았어요(개념도로 그리면 거의 같고, draw_mermaid() 그림에서는 오케스트레이터-워커의 워커 노드가 하나뿐이지만요). 차이는 갈래가 몇 개인지 누가, 언제 정하느냐 하나예요.

비교 항목③ 병렬화④ 오케스트레이터-워커
갈래 수를 정하는 쪽개발자LLM(오케스트레이터)
정하는 때코드를 쓸 때, compile() 전실행 중에, 입력을 본 뒤
그래프 모양갈래마다 노드를 미리 그려 둠워커 노드 하나 + Send로 필요한 만큼 불러냄
주방에서검사 담당 셋을 동선표에 미리 그려 둠헤드셰프가 그날 메뉴 수를 보고 요리사를 부름

대가도 분명해요. 계획이 나쁘면 아래 워커 전부가 나빠지고(단일 실패 지점8), 워커 수를 LLM이 정하니 비용도 미리 알 수 없어요. 오케스트레이터가 섹션 20개를 계획하면 호출이 21번이에요. 그래서 state["menu"][:4](목록에서 앞의 4개만 남기기)처럼 워커 수에 상한을 두고, 잘린 게 있으면 결과에 표시해 둬요.

중요9강에서 짚은 내용

병렬화와 오케스트레이터-워커의 가장 큰 차이는 하위 작업의 개수와 종류를 누가, 언제 정하느냐예요. 병렬화는 개발자가 코드를 쓸 때 고정해서 노드를 미리 그려 두고, 오케스트레이터-워커는 LLM이 실행 중에 정해서 Send로 워커를 불러내요.

그래서 "평가 축 3개로 노트 검수하기"처럼 어떤 입력이 와도 할 일이 늘 같은 작업에 오케스트레이터-워커를 쓰면, 얻는 것 없이 대가만 커져요. 계획용 LLM 호출이 한 번 더 들어 비용과 기다리는 시간이 늘고, 계획이 틀리면(축을 둘만 만들거나 엉뚱한 축을 넣으면) 검수 전체가 망가지고, 실행마다 축이 달라져 결과를 서로 비교할 수도 없어요. 미리 알 수 있는 건 미리 정해 두는 게 맞아요(아래 나쁜 선택 vs 좋은 선택).

이 모양은 코딩(몇 개 파일을 어떻게 고칠지 요청마다 다름)이나 여러 출처 검색에 잘 맞아요. 멀티 에이전트 네 가지 구조에서 본 오케스트레이터-워커가 에이전트 여럿의 이야기라면, 여기서는 한 그래프 안의 LLM 호출로 같은 모양을 만든 거예요.

⑤ 평가자-최적화자 — 통과할 때까지 고쳐 쓰기

앞의 넷은 데이터가 앞에서 뒤로만 흘렀어요. 이번엔 처음으로 되돌아가는 순환이 생겨요. 한 LLM 호출이 결과를 만들고, 다른 호출이 평가해서 피드백을 주고, 기준을 넘을 때까지 반복해요. 순환에는 앞 편에서 본 위험이 따라와요. 끝나지 않을 수 있다는 거요. 앞 편의 무한 반복 실험에서는 되돌아가는 동안 State가 하나도 안 바뀌어서 영원히 돌았는데, 이 패턴은 매 바퀴 초안을 고쳐 쓰니 그 점은 달라요. 대신 고쳐 써도 기준을 영영 못 넘을 수 있어서 상한은 여전히 필요해요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요 (LLM 자리는 규칙으로 흉내 냈어요)

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

MAX_ROUNDS = 3
RULES = ["용어 정의", "예시"]

class Draft(TypedDict):
    text: str
    feedback: str
    rounds: int
    passed: bool

def evaluate(state: Draft):                  # 실제로는 LLM 평가자 자리
    missing = [r for r in RULES if r not in state["text"]]
    return {"passed": not missing,
            "feedback": f"빠진 것: {missing}" if missing else "통과",
            "rounds": state["rounds"] + 1}

def optimize(state: Draft):                  # 실제로는 LLM 작성자 자리
    missing = [r for r in RULES if r not in state["text"]]
    return {"text": state["text"] + f" +{missing[0]}"}

def hand_over(state: Draft):                 # 상한에 닿으면 사람에게 넘기는 정상 출구
    return {"feedback": state["feedback"] + " (사람에게 넘김)"}

def decide(state: Draft) -> str:
    if state["passed"]:
        return "통과"
    if state["rounds"] >= MAX_ROUNDS:
        return "포기"
    return "재작성"

b = StateGraph(Draft)
b.add_node("evaluate", evaluate)
b.add_node("optimize", optimize)
b.add_node("hand_over", hand_over)
b.add_edge(START, "evaluate")
b.add_conditional_edges("evaluate", decide,
                        {"통과": END, "재작성": "optimize", "포기": "hand_over"})
b.add_edge("optimize", "evaluate")
b.add_edge("hand_over", END)
g = b.compile()

for step in g.stream({"text": "리듀서는 값을 합친다.", "rounds": 0}):
    print(step)

{'evaluate': {'passed': False, 'feedback': "빠진 것: ['용어 정의', '예시']", 'rounds': 1}}
{'optimize': {'text': '리듀서는 값을 합친다. +용어 정의'}}
{'evaluate': {'passed': False, 'feedback': "빠진 것: ['예시']", 'rounds': 2}}
{'optimize': {'text': '리듀서는 값을 합친다. +용어 정의 +예시'}}
{'evaluate': {'passed': True, 'feedback': '통과', 'rounds': 3}}
  • 반복 상한은 그래프 안에. 상한에 닿으면 GraphRecursionError로 멈추는데, 이건 예외(실행을 그 자리에서 끊는 에러)라서 그동안 고쳐 온 중간 결과가 다 날아가요(바로 아래에서 직접 확인해요). 게다가 langgraph 1.2 이후의 기본 상한은 25가 아니라 10007스텝이라(앞 편에서 직접 확인), 기본값만 믿으면 멈추기 전에 호출 요금부터 쌓여요. 그래서 rounds를 세다가 hand_over로 빠지는 정상 종료 경로를 두고, recursion_limit은 이중 안전망으로 남겨요.
  • stream()과 invoke() — invoke()는 끝날 때까지 기다렸다가 최종 State만 줘요. stream()은 스텝이 끝날 때마다 "어느 노드가 무엇을 바꿨는지"를 하나씩 내보내요. 루프가 몇 바퀴 돌았는지, 피드백이 어떻게 바뀌었는지는 stream()으로만 보여요. 디버깅엔 stream(), 서비스에서 결과만 필요하면 invoke()예요.
  • 비용은 곱절로 늘어요. 한 바퀴에 생성 1번 + 평가 1번이니, 3바퀴면 6번이에요. 바퀴를 늘리면 품질이 정말 오르는지 재 보고 상한을 정해요.

상한에만 맡기면 왜 결과를 못 받을까

"예외라서 결과가 날아간다"는 말이 처음엔 잘 와닿지 않았어요. 그래서 채점이 늘 불합격을 주는 최악의 경우를 두 가지 방식으로 돌려 봤어요. A는 멈추는 걸 recursion_limit에만 맡기고, B는 위 코드처럼 rounds를 세다가 3이 되면 hand_over로 빠지는 정상 출구를 둬요.

실행: 로컬 파이썬 — langgraph 설치 후, API 키 없이 돌아가요

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import GraphRecursionError

class Draft(TypedDict):
    text: str
    rounds: int

def evaluate(state: Draft):                 # 늘 불합격을 주는 채점 (최악의 경우를 흉내)
    return {"rounds": state["rounds"] + 1}

def optimize(state: Draft):
    return {"text": state["text"] + " +고침"}

def hand_over(state: Draft):
    return {"text": state["text"] + " (사람에게 넘김)"}

def build(decide, with_exit):
    b = StateGraph(Draft)
    b.add_node("evaluate", evaluate)
    b.add_node("optimize", optimize)
    b.add_edge(START, "evaluate")
    if with_exit:
        b.add_node("hand_over", hand_over)
        b.add_conditional_edges("evaluate", decide, ["optimize", "hand_over"])
        b.add_edge("hand_over", END)
    else:
        b.add_conditional_edges("evaluate", decide, ["optimize"])
    b.add_edge("optimize", "evaluate")
    return b.compile()

# A. 멈추는 걸 recursion_limit에만 맡긴다
a = build(lambda s: "optimize", with_exit=False)
result = "아직 아무것도 안 들어옴"
try:
    result = a.invoke({"text": "초안", "rounds": 0}, {"recursion_limit": 8})
except GraphRecursionError as e:
    print("A 에러:", type(e).__name__)
print("A result:", result)

# B. rounds를 세다가 3이 되면 hand_over로 빠지는 정상 출구를 둔다
b = build(lambda s: "hand_over" if s["rounds"] >= 3 else "optimize", with_exit=True)
print("B result:", b.invoke({"text": "초안", "rounds": 0}, {"recursion_limit": 8}))

처음 보는 문법 둘만 짚을게요. lambda s: ...는 한 줄짜리 이름 없는 함수라서 여기서는 라우터 역할을 해요. try: 아래에서 에러가 나면 프로그램이 멈추는 대신 except 아래 줄로 넘어가요.

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

A 에러: GraphRecursionError
A result: 아직 아무것도 안 들어옴
B result: {'text': '초안 +고침 +고침 (사람에게 넘김)', 'rounds': 3}

핵심은 result = a.invoke(...) 한 줄이에요. =는 오른쪽 일이 끝까지 성공해야 왼쪽 result에 값을 넣어요. A는 채점과 수정이 번갈아 8번 돈 뒤 한도에 걸려, invoke가 결과를 돌려주기 전에 에러로 끝났어요. 그래서 result에는 처음에 넣어 둔 "아직 아무것도 안 들어옴"이 그대로 남았고, 네 번이나 고친 초안은 받을 길이 없어요. B는 세 번째 채점에서 hand_over로 빠져 평범하게 끝났고, 고쳐 온 초안을 그대로 받았어요.

A가 멈춘 지점도 눈여겨볼 만해요. 노드마다 실행 횟수를 따로 세어 보니 채점 4번, 수정 4번, 모두 8번 실행한 뒤 멈췄어요. 노드는 두 종류뿐인데 한도 8에서 멈췄다는 건, recursion_limit이 노드 개수가 아니라 실행된 단계 수를 센다는 뜻이에요. 한도는 invoke()에 두 번째 값으로 {"recursion_limit": 8}처럼 넘겨서 얼마든지 바꿀 수 있고요.

중요10강에서 짚은 내용

되돌아가는 선이 있는 그래프를 recursion_limit 하나로만 멈추게 하면 안 돼요. 한도에 닿으면 GraphRecursionError라는 예외로 끝나서, 그때까지 만든 중간 결과를 하나도 돌려받지 못해요. 그래서 반복 횟수를 State에 세다가 정해 둔 횟수에서 "사람에게 넘기기" 같은 정상 출구로 빠지게 그래프 안에 그려 두고, recursion_limit은 그 설계가 실패했을 때를 대비한 비상용으로만 남겨요.

강의 실습에서 인상 깊었던 장면이 있어요. 성의 없는 노트 초안을 이 루프에 넣었더니, 평가 규칙("용어 정의가 있나", "예시 코드가 있나" 등)을 채우는 쪽으로 고쳐 쓰는 동안 주제가 LangGraph 리듀서에서 자바스크립트 reduce로 옮겨 가 버렸대요. 평가자는 규칙 목록만 채우는 방향으로 글을 바꿀 뿐, 원래 무엇을 지켜야 했는지는 몰라요. 그래서 "무엇을 잃으면 안 되는가"를 ①의 게이트처럼 코드 검사로 걸어 두는 게 필요해요.

평가 기준이 흐리면 피드백이 "더 좋게 써 보세요" 수준으로 겉돌고 반복해도 안 나아져요. 규칙부터 구체적으로 적는 게 먼저예요. 그리고 평가자가 결정적일 수 있다면 그편이 훨씬 나아요. 코드를 쓰게 하고 테스트를 돌려 실패 메시지를 피드백으로 돌려주는 루프가 대표적이에요. LLM이 채점하는 방식의 장단점은 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge에서, 에이전트 여럿이 같은 모양을 만드는 경우는 네 가지 구조의 비평-수정에서 봤어요.

패턴이럴 때그래프의 핵심치르는 값
① 프롬프트 체이닝단계에 순서가 있고 중간 점검이 필요할 때일렬 노드 + 코드 게이트단계 수만큼 기다리는 시간(지연 시간9)이 늘어요

표를 실제 요구에 대 볼게요. "회의록을 받아, 거기서 나온 할 일 개수만큼(3개일 수도 10개일 수도) 할 일마다 담당자 배정 초안을 만든다." 요약하고, 할 일을 뽑고, 배정하는 순서가 있어 보여서 ① 체이닝을 떠올리기 쉬워요. 하지만 체이닝은 단계가 고정이라 마지막 단계 한 번에 할 일을 몰아서 처리하게 되고, 할 일마다 따로 초안을 만드는 구조가 아니에요. ③ 병렬화는 처리 노드 개수를 미리 알아야 하는데 할 일 개수는 회의록마다 달라요. ② 라우팅은 여러 갈래 중 하나만 고르니 할 일 여러 개를 동시에 다루지 못해요.

중요11강에서 짚은 내용

하위 작업의 개수가 입력을 받아 봐야 정해진다면 ④ 오케스트레이터-워커예요. 회의록에서 할 일을 뽑는 계획 단계가 개수를 정하고, Send로 할 일마다 워커를 하나씩 불러 담당자 초안을 써요. "개수를 미리 아나?" 한 질문이 병렬화와 오케스트레이터-워커를 가르는 갈림길이에요.

그럼 언제 워크플로를 넘어 에이전트로 가야 할까요. 기준은 하나예요. 필요한 단계의 조합을 개발자가 미리 늘어놓을 수 없을 때. 사내 문서로 퀴즈를 만드는 일은 경로가 뻔하니 워크플로가 낫고, "이 저장소의 버그를 찾아 고쳐 줘"는 어떤 파일을 몇 번 읽을지 경우의 수가 끝이 없으니 도구를 쥔 자율 에이전트가 필요해요. 대신 비용을 미리 계산할 수 없고, 같은 입력에 다른 길로 가서 테스트가 어렵고, 틀렸을 때 어디가 틀렸는지 짚기 어려워요. 그래서 워크플로로 먼저 해 보고, 안 된다는 증거가 나왔을 때만 옮겨요.

"워크플로로는 안 된다"는 증거는 어떤 모습일까

"증거가 나왔을 때만"이라는 말은, 뒤집으면 그 증거를 알아볼 수 있어야 한다는 뜻이에요. 강의는 구체적인 모습을 스스로 적어 보라고만 했고, 아래는 제가 떠올린 신호예요. 기준이 "필요한 단계의 조합을 미리 늘어놓을 수 없을 때"였으니, 증거도 결국 미리 그린 길로는 감당이 안 되는 장면이에요. 아래 LangSmith 같은 실행 기록에서 이런 모습이 되풀이되면 신호로 봐요.

  • 갈래를 계속 덧대고 있어요. 새로운 종류의 입력이 올 때마다 라우터에 갈래를 하나씩 더하고, 예외를 처리하는 노드가 끝없이 늘어나요. 길을 미리 다 그릴 수 없다는 뜻이에요.
  • 중간 결과를 보고 다음 걸음을 바꿔야 해요. 실패한 건을 모아 보니 "한 번 더 조회했어야 했는데 그래프에 그 길이 없어서" 틀린 경우가 대부분이에요. 몇 번, 어떤 순서로 조회할지가 매번 달라요.
  • 계획 한 번으로 끝나지 않아요. 오케스트레이터가 처음 짠 계획대로 워커를 돌렸는데, 결과를 보고 계획을 다시 짜야 하는 일이 잦아요. ④ 오케스트레이터-워커는 계획을 한 번만 세우는 모양이에요.
  • 사람이 자주 끼어들어 길을 바꿔 줘요. 흐름이 막힐 때마다 사람이 "이번엔 이걸 먼저 해"라고 손으로 경로를 바꿔 주고 있다면, 그 판단을 LLM에게 맡길 후보예요.

강의가 참고 자료로 건 칩 후옌(Chip Huyen)의 글 Agents는 에이전트가 실패하는 모습을 계획 오류·도구 오류·효율 문제로 나눠 정리해요. 에이전트로 옮긴 뒤 무엇을 지켜봐야 하는지 알고 싶을 때 이어서 읽기 좋아요.

에이전트로 옮기는 근거는 "더 똑똑해 보여서"가 아니라 기록으로 확인한 실패 모습이어야 해요. 갈래가 끝없이 늘어나거나, 중간 결과에 따라 다음 걸음이 매번 달라져 고정된 길로는 실패하는 일이 되풀이될 때가 그 증거예요. 에이전트는 비용을 미리 알 수 없고 테스트와 원인 찾기가 어려운 만큼, 증거 없이 먼저 가지 않아요.

내 일에는 어떤 모양이 맞을까 — 고르는 질문 순서

강의는 마지막에 첫 질문으로 돌아가요. 첫 편에서 적어 본 '맡기고 싶은 반복 작업'과 그 조회·행동 목록을 다시 꺼내, 다섯 모양 중 무엇이 맞는지 골라 보라는 거예요. 저는 위 표를 질문 순서로 바꿔서 위에서부터 차례로 물어요.

  1. 할 일의 단계와 순서가 늘 같고, 단계 사이에 확인할 게 있나? → ① 프롬프트 체이닝
  2. 들어오는 입력의 종류에 따라 처리 방법이 완전히 달라지나? → ② 라우팅
  3. 서로 독립인 일을 여러 개 동시에 할 수 있고, 그 개수를 미리 아나? → ③ 병렬화
  4. 그 개수를 입력을 받아 봐야 알 수 있나? → ④ 오케스트레이터-워커
  5. 좋고 나쁨의 기준이 뚜렷하고, 피드백대로 고쳐 쓰면 나아지나? → ⑤ 평가자-최적화자
  6. 필요한 단계의 조합을 아예 미리 늘어놓을 수 없나? → 그때만 에이전트

한 가지 일에 여러 모양이 섞여도 돼요. 첫 편 예시였던 식당 예약 변경에 대 보면, 할 일은 늘 "예약 찾기 → 빈자리·수수료 확인 → 예약 바꾸기 → 확인 문자" 순서라 ① 프롬프트 체이닝이 뼈대예요. 빈자리가 없으면 멈추는 코드 게이트를 확인 단계 뒤에 두고, 되돌리기 어려운 '예약 바꾸기' 앞에는 사람의 확인을 끼워요. 그런데 문의가 예약 변경·취소·불만으로 섞여 들어온다면 맨 앞에 ② 라우팅을 붙여 종류별로 나눠 보내요.

패턴은 이름을 외우는 게 아니라 내 일의 모양에 대 보는 것이에요. 순서가 정해져 있나, 종류별로 갈리나, 개수를 미리 아나, 고쳐 쓰면 나아지나를 차례로 묻고, 맞는 것 중 가장 단순한 모양을 골라요. 여러 모양을 섞어도 되지만, 길을 미리 그릴 수 있는 한 워크플로로 먼저 해요.

나쁜 선택 vs 좋은 선택 — 신메뉴를 세 기준으로 검사할 때

주방에서 신메뉴를 낼 때마다 맛·온도·모양 세 가지로 검사하는 흐름을 만든다고 해 볼게요.

나쁜 선택좋은 선택
무엇을 했나: "유연해 보여서" 오케스트레이터-워커로 짰어요. 헤드셰프 역할 LLM이 매번 접시를 보고 검사 항목을 정한 뒤 Send로 검사원을 불러요.

무슨 일이 생기나: 계획 호출이 매번 1번 더 들고, 어떤 날은 항목이 4개로 늘고 어떤 날은 '모양'이 빠져요. 요금은 들쑥날쑥하고, 메뉴끼리 점수를 비교할 수도 없어요.		 무엇을 했나: 검사 항목이 항상 셋이니 병렬화로 짰어요. 노드 셋을 고정하고 checks 칸에 리듀서를 달았어요.

무슨 일이 생기나: 호출은 늘 3번이고 비용이 예측돼요. 같은 기준의 점수가 쌓이니 메뉴끼리 비교도 돼요. 반대로 "회의록에서 나온 할 일 개수만큼 담당자 초안 만들기"처럼 개수가 입력마다 다를 때가 오케스트레이터-워커의 자리예요.

LangSmith로 안을 들여다보기

오늘 만든 그래프는 노드가 서너 개라 stream()으로도 충분했어요. 하지만 서비스에서는 하루 수천 건이 흐르고 그중 몇 건이 이상한 답을 내요. 그 몇 건을 찾아 "어느 노드에서 어떤 프롬프트로 무엇을 받았는지" 보려면 print()로는 안 돼요. 게다가 LLM은 같은 입력에도 다르게 답하니, 문제가 난 그 순간의 기록이 없으면 재현조차 못 해요.

LangSmith는 이 기록을 남기고 보여 주는 웹 서비스예요. 환경 변수만 넣으면 LangChain·LangGraph의 모든 호출이 자동으로 기록돼요. 코드는 안 고쳐요. 실행 한 번이 하나의 트레이스10로 남고, 그 안에 노드별 입력·출력, 모델에게 간 프롬프트 전문, 토큰 사용량, 걸린 시간이 계층으로 쌓여요.

실행: 프로젝트의 .env 파일에 저장 — load_dotenv()로 읽으면 LangChain·LangGraph가 알아서 기록을 보내요

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...
LANGSMITH_PROJECT=langgraph-study
  • smith.langchain.com에서 가입하면 개인 무료 요금제로 월 5,000 트레이스까지 쓸 수 있어요(강의 시점 기준). 오늘 실습 분량은 한참 못 미쳐요. 켜지 않아도 공부에는 지장 없어요.
  • 옛 자료에 LANGCHAIN_TRACING_V2, LANGCHAIN_API_KEY가 보이면 예전 이름이에요.
  • LangChain을 안 쓰는 함수는 langsmith 패키지의 @traceable 데코레이터를 붙이면 같이 기록돼요.
  • 주의: 추적을 켜면 프롬프트와 입력·출력이 전부 LangSmith 서버로 가요. 개인정보나 밖으로 나가면 안 되는 자료로 실습할 땐 끄거나 조심해야 해요. 키는 .env에만 두고 깃에 올리지 않아요. 모두의연구소 강의 화면에서 셀을 돌린다면 이 .env는 내 컴퓨터가 아니라 강의 서버에 둬야 하고, 읽어 줄 python-dotenv가 설치돼 있는지도 먼저 봐야 해요(1편의 API 키 막힘 기록).

켜고 나서 앞의 그래프를 다시 돌리면 이런 게 보인대요. 평가자-최적화자 루프는 evaluate · optimize · evaluate가 계층으로 펼쳐지고, 각 evaluate를 누르면 그 순간 모델이 실제로 받은 프롬프트 전문과 돌려준 JSON이 보여요. stream()은 State의 변화만 보여 줬지만, LangSmith는 모델이 본 것 자체를 보여 줘요. 병렬화 그래프는 세 평가 노드가 시간축에서 겹쳐 그려져서, 전체 시간이 가장 느린 노드에 가깝다는 걸 눈으로 확인할 수 있어요. 에이전트 기록을 "답변이 아니라 흔적으로" 보는 감각은 답변이 아니라 흔적을 본다 — 세션 기록과 사용량에서 처음 다뤘어요.

이 편에서 꼭 기억할 것

본문에 중요 표시를 단 곳만 모았어요. 강의 6~12강이 퀴즈로 다시 짚은 내용이에요. 1~5강 것은 첫 편의 같은 목록에 있어요.

  • 게이트는 LLM 단계 사이에서 틀린 중간 결과를 막는 코드 검사 (6강)
  • 뜻을 읽어야 하는 검사는 LLM을 게이트로 (6강)
  • Literal은 답을 정한 값으로 묶어 KeyError를 막아요 — 맞는지는 별개 (7강)
  • 동시에 같은 칸에 쓰면 에러, 리듀서로 합치는 법을 알려 줘요 (8강)
  • Send로 불린 워커는 자기 쪽지만 봐요 (9강)
  • 병렬화와 오케스트레이터-워커는 "개수를 누가, 언제 정하나"로 갈려요 (9강)
  • 반복은 상한에만 맡기지 말고 정상 출구를 그래프 안에 (10강)
  • 개수를 입력을 봐야 알면 오케스트레이터-워커 (11강)
  • 에이전트로 옮기는 근거는 기록으로 확인한 실패 모습 (11강)
  • 패턴은 내 일의 모양에 대 보고, 가장 단순한 것부터 (12강)

직접 해보기

  1. 라벨 우선순위로 정확도 되찾기 — 바꿀 것: 분류 프롬프트에 "코드나 API 호출이 있으면 설명이 붙어 있어도 코드예제, 학습자에게 무언가를 시키면 실습과제"처럼 우선순위를 못 박아요. 측정할 것: 같은 6건의 정확도. 비교할 것: 표현만 다듬었을 때와 우선순위를 정했을 때의 차이. 67%가 어떻게 변하는지 기록해요.
  2. 병렬의 이득을 숫자로 — 바꿀 것: 세 평가를 병렬 그래프와 for문 순차 실행 두 가지로 돌려요. 측정할 것: time.perf_counter()로 걸린 시간, usage_metadata로 토큰 수. 비교할 것: "시간은 줄고 비용은 그대로"가 제 환경에서도 맞는지.
  3. 기준을 흐리게 해 보기 — 바꿀 것: 평가 규칙을 "좋은 학습 노트로 써라" 한 문장으로 바꿔요. 측정할 것: 바퀴 수와 피드백 문장의 구체성. 비교할 것: 원래 규칙 목록일 때. 평가 기준의 구체성이 곧 루프의 성능이라는 걸 확인하는 실험이에요.

함께 읽으면 좋은 글

  • 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업 — 오케스트레이터-워커·팬아웃·비평-수정을 에이전트 여럿의 구조로 본 글이에요.
  • 답의 모양과 채점법 — 구조화 출력이 형식은 강제해도 사실까지 강제하지는 못한다는 이야기요.
  • 답변 뒤에 심사위원 하나를 더 둔다 — LLM-as-a-Judge — ⑤의 평가자를 LLM으로 둘 때의 한계예요.
  1. 게이트(gate) — LLM 단계 사이에 끼워 두고 중간 결과가 조건을 만족할 때만 다음 단계로 보내는 검사 지점이에요. ↩
  2. 결정적(deterministic) — 같은 입력을 넣으면 언제나 같은 결과가 나오는 성질로, 파이썬 문자열 검사는 결정적이고 LLM 답은 그렇지 않아요. ↩
  3. 구조화 출력(structured output) — 모델의 답을 미리 정한 칸과 자료형의 JSON으로만 나오게 강제하는 기능으로, 답의 모양과 채점법에서 strict schema라는 이름으로 처음 다뤘어요. ↩
  4. Pydantic — 파이썬 클래스로 데이터의 칸과 자료형, 설명을 선언해 두면 검사와 JSON 스키마 변환을 해 주는 라이브러리예요. ↩
  5. 슈퍼스텝(super-step) — 실행 준비가 된 노드를 한꺼번에 돌리고 그 반환값을 모아 State에 한 번에 반영하는 LangGraph의 실행 단위예요. ↩
  6. 리듀서(reducer) — 같은 State 칸에 여러 값이 들어올 때 어떻게 합칠지 정해 두는 함수로, operator.add를 쓰면 리스트를 이어 붙여요. ↩
  7. 맵-리듀스(map-reduce) — 일을 여러 갈래로 펼쳐 각각 처리한 뒤 결과를 하나로 접는 데이터 처리 방식이에요. ↩
  8. 단일 실패 지점(single point of failure) — 그 한 곳이 잘못되면 시스템 전체 결과가 망가지는 지점이에요. ↩
  9. 지연 시간(latency) — 요청을 보낸 뒤 결과를 받기까지 기다리는 시간이에요. ↩
  10. 트레이스(trace) — 요청부터 최종 답까지 무슨 일이 있었는지 단계별로 남긴 실행 기록으로, 도구를 실제로 설계하기에서 처음 다뤘어요. ↩
  11. 강의는 이 수치를 "라벨 정의가 배타적이지 않아서 생긴 한계"의 예로 들었으니, 모델 성능 자체의 점수로 읽으면 안 되고 LLM 답은 실행마다 달라질 수도 있어요. ↩
