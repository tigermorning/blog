시험용 서버(staging)에서 확인한 이미지를 새로 만들지 않고 그 이미지의 지문(다이제스트)으로 가리켜 실제 서버(production)에 그대로 보내면, "시험한 것과 내보낸 것이 같다"를 증거로 말할 수 있다.

앞의 편에서 Dockerfile로 실행 환경을 정해 도장판 앱을 staging(운영 서버에 올리기 전에 먼저 확인하는 시험용 서버)과 production(실제 사용자가 쓰는 서버)에 올렸어요. 이번에는 그 다음 질문이에요. production에서 신고가 들어왔다고 해 볼게요. 이때 세 가지를 바로 답할 수 있어야 해요. ① 지금 도는 코드가 어느 커밋1인가, ② 정상이던 이전 버전으로 되돌릴 수 있나, ③ 지금 production 이미지가 staging에서 확인한 그 이미지가 맞나. 저는 이 세 질문에 답이 안 나오는 상태에서 시작해, 이미지를 GitHub Actions2에서 한 번만 만들고 그대로 보내는 구조로 바꿨어요. 이미지와 컨테이너가 낯설다면 도커(Docker)란 무엇인가를 먼저 보고 와도 좋아요. 비유는 1편부터 쓰던 식당을 이어 써요.

비유로 먼저 — 시식하고 나서 상자를 다시 포장하는 가게

사장인 내가 가맹점에 보낼 밀키트 상자를 만든다고 해 볼게요. 먼저 시식 주방(staging)에서 상자를 열어 맛을 봐요. 그런데 가맹점(production)에 보낼 때 상자를 다시 포장하면 어떨까요? 같은 레시피로 다시 포장해도, 그 사이 시장에 새 재료가 나와 있으면 가맹점 상자에는 다른 재료가 들어갈 수 있어요. 시식한 상자와 가맹점에 간 상자가 다르면, 시식은 의미가 없어져요. 해결은 간단해요. 시식한 그 상자를 그대로 가맹점에 보내면 돼요. 그러려면 상자에 "이 상자가 어느 레시피 판에서 나왔는지"를 적은 이름표와, 상자 내용에서 나온 지문이 있으면 확인이 쉬워져요.

핵심 한 줄: 시식한 상자를 다시 포장하지 말고 그 상자를 그대로 가맹점에 보내야, 시식이 가맹점 상자의 증거가 된다.

다만 여기서 비유가 끊기는 점이 있어요. 밀키트는 가맹점에서 뜯으면 없어지지만, 이미지는 production이 실행해도 저장소에 그대로 남아 있어요. 그래서 같은 상자를 두 곳에 보낼 수 있어요.

전체 흐름 — 한 번 만든 이미지가 커밋에서 production까지

글 전체를 한 장으로 먼저 보면 이래요. 이미지는 ②에서 한 번만 만들어지고, ③ 이미지 저장소에서 태그와 다이제스트를 갖고 있다가, ④ staging에서 시험한 뒤 ⑤ production으로 다이제스트 주소 그대로 가요.

왜 한 번만 만드나 — 같은 코드여도 두 이미지는 같지 않을 수 있어요

"같은 코드로 이미지를 두 번 만들면 같은 이미지겠지"라고 생각하기 쉬워요. 그런데 이미지에는 내가 쓴 코드만 들어가지 않아요. 남이 만든 라이브러리도 빌드할 때 인터넷에서 내려받아 넣어요. 도장판 앱의 requirements.txt(가져다 쓸 라이브러리의 목록, 7줄)에는 fastapi>=0.115처럼 「0.115 이상이면 어느 버전이든 괜찮다」는 범위만 적혀 있어요. 이 줄은 버전 하나를 못 박은 것이 아니라서, pip(파이썬 라이브러리 설치 도구)는 빌드하는 순간 저장소에 올라와 있는 가장 새 버전을 골라요. 제 빌드 로그에는 fastapi 0.162.0이 설치됐어요. 며칠 뒤 새 버전이 나온 다음에 다시 빌드하면 더 높은 버전이 들어갈 수 있어요.

여기서 정확히 짚어야 할 것이 있어요. 한 번 만든 이미지 하나 안의 라이브러리는 바뀌지 않아요. 이미지는 만든 뒤 바뀌지 않으니까요. 문제는 이미지를 다시 만들 때 생겨요. staging용으로 한 번, production용으로 또 한 번 만들면 두 이미지가 서로 다를 수 있어요. 버전을 fastapi==0.162.0처럼 하나로 못 박으면 이 차이는 줄지만, 이 앱은 그렇게 적지 않았어요. 날짜를 달리해 같은 커밋을 두 번 빌드해 비교해 본 적은 없어요. 그래서 이 글의 결론은 "이미지를 두 번 만들면 달라질 수 있으니, 아예 한 번만 만들자"예요.

제 실습에서 직접 본 차이도 있어요. 승격으로 바꾸기 전에 production이 쓰던 이미지(소스 배포로 만든 것, 다이제스트 앞 12자리 6d29e8d854f1)와 staging 이미지(64c25be3bf9d)는 서로 달랐어요. 다만 이 둘은 만드는 방법이 달랐던 것이라, 같은 코드를 두 번 빌드해서 생긴 차이를 잰 것은 아니에요.

production 이미지가 시험한 이미지와 같은지는 믿을 수밖에 없다두 환경의 다이제스트가 64자리까지 같은지로 확인한다

이미지를 누가 만드나 — Cloud Build에서 GitHub Actions 러너로

2편에서 쓴 소스 배포는 폴더째 넘기면 GCP의 Cloud Build가 이미지를 만들어 주는 방식이었어요. 그 이미지는 자동으로 만들어진 저장소(cloud-run-source-deploy)에 태그 없이 남았어요. 이번에는 GitHub Actions의 러너(작업을 실행하는 컴퓨터)가 docker build로 직접 만들고, 내가 만든 이미지 저장소에 올린 뒤 Cloud Run에는 만들어진 이미지를 넘겨요. 둘 다 GitHub Actions가 배포를 시작하는 것은 같고, 달라지는 것은 이미지를 누가 만드느냐예요.

좋은 점설정이 적다검토·테스트를 거친 커밋으로만 만들어지고, 누가 언제 만들었는지 기록이 남는다

기록이 남는 것이 왜 좋을까요? 문제가 생겼을 때 이미지에서 커밋을 찾아 어느 코드인지 알고, 되돌릴 대상을 정할 수 있어요. 내 컴퓨터에서 만들어 올린 이미지는 어느 코드로 만들었는지, 누가 만들었는지 기록이 남지 않아 같은 이미지를 다시 만들 수도 없어요. 이 부분은 배운 내용이고, 이번 실습에서 실제 사고로 써 본 것은 아니에요.

워크플로 파일(deploy.yml)에서 바뀐 곳은 아래와 같았어요.

실행: .github/workflows/deploy.yml로 수정 — GitHub Actions가 이 파일을 읽어요

-          source: .
+          image: ${{ env.IMAGE }}
-          flags: ... --build-service-account=... --clear-base-image
+          flags: --no-allow-unauthenticated --service-account=${{ vars.RUNTIME_SA }}
+      - name: 이미지 만들기와 올리기
+        run: |
+          docker build --tag "$IMAGE" .
+          docker push "$IMAGE"

이 변경을 PR로 올려 staging에 머지하니 CI 두 개가 통과하고 배포가 성공했어요. 이미지 저장소(Artifact Registry7)에는 이미지 1개(태그 fc01d21e2bea…, 다이제스트 sha256:64c25be3bf9d…)가 생겼고 staging 리비전8 00005-5rh가 그 이미지를 썼어요. 한계도 있어요. 소스 배포 때 넣던 --build-service-account와 --clear-base-image를 빼도 되는지는 "배포가 성공했다"는 것으로만 확인했어요.

태그와 다이제스트 — 이름표와 지문은 다른 것이에요

이미지 이름은 저장 위치/프로젝트/저장소/이미지이름:태그로 이루어져 있어요. 맨 끝 태그는 이미지에 붙인 이름표로, 다른 이미지로 옮겨 붙일 수 있어요. 반면 다이제스트는 이미지 내용에서 계산되는 sha256:로 시작하는 64자리 값이라, 내용이 같아야 같고 내용이 바뀌면 달라져요. 그래서 사람이 찾아갈 때는 태그를 쓰고, 실제로 무엇이 실행 중인지는 다이제스트로 확인해요.

태그다이제스트

모양(제가 확인한 값)92d2c86647dd… (커밋 SHA를 그대로 씀)sha256:61e4310e0460… (64자리)

자주 헷갈리는 점이 하나 있어요. 커밋 SHA와 태그는 글자가 같고, 다이제스트는 글자가 달라요. 태그는 커밋 SHA9를 그대로 복사해서 이미지에 붙인 이름표라서 글자가 같아요. 반면 다이제스트는 이미지 내용에서 따로 계산하니까 SHA와 글자가 전혀 달라요.

커밋에서 화면까지 — 다섯 칸을 한 줄로 잇기

이미지를 Actions에서 만들고 커밋 SHA를 태그로 붙이자, 커밋 → 이미지 태그 → 다이제스트 → 리비전 → 화면이 같은 값으로 이어졌어요. 이 다섯 칸을 채우면 "지금 도는 코드는 어느 커밋인가"에 화면 몇 개로 답할 수 있어요. 제가 production에서 읽은 값이에요.

한 줄 요약: 이름이 비슷한 SHA 두 개는 대상이 달라요. 커밋 SHA는 코드, 다이제스트는 이미지예요. 그리고 리비전 이름(00011-vgr)만으로는 어느 커밋인지 알 수 없어요. 리비전 상세에서 다이제스트를 찾고 Artifact Registry에서 그 다이제스트의 태그를 찾아야 커밋이 나와요.

화면 구석의 v 92d2c86는 어떻게 생기나

노드는 "앱이 /version 주소로 지금 커밋을 알려 준다"고 가정해요. /version은 앱 주소 뒤에 붙여 여는 페이지인데, 앱 개발자가 그 주소를 처리하는 코드를 만들어야 생겨요. 도장판 앱에서 version, COMMIT_SHA, K_REVISION을 코드에서 검색해 보니 일치하는 것이 없었고, 서버가 가진 주소는 /, /health, /api/ocr 세 개뿐이었어요. 그 대신 앱 화면 구석에 작은 글씨 v 92d2c86이 보여요. 이 글자는 배포할 때 컴퓨터가 자동으로 넣은 커밋 앞 7자리예요.

원리는 간단해요. index.html에 var v='__COMMIT__'이라는 자리 표시를 적어 두고, 배포 때 sed10(글자를 찾아 바꾸는 명령)가 그 자리 표시를 커밋 앞 7자리로 바꿔요.

개념 설명용 코드 — 배포 워크플로 안에서 자동으로 도는 줄이에요

sed -i "s/__COMMIT__/${GITHUB_SHA::7}/" index.html
var v='__COMMIT__'   →   var v='92d2c86'

바뀐 파일이 이미지 안에 들어가기 때문에, 앱을 열면 화면에 v 92d2c86이 보여요. staging은 서비스가 비공개라서 로그인 없이는 열 수 없었고, 신원 토큰(내가 누구인지 증명하는 임시 값)을 붙여 한 번만 요청해 var v= 값을 읽었어요. 토큰은 출력하거나 저장하지 않았어요.

승격 — 새로 만들지 않고 그대로 보내기

승격은 staging에서 확인한 이미지를 새로 만들지 않고 그대로 production으로 보내는 것이에요. 저는 두 단계로 했어요. 먼저 손으로 staging 리비전의 이미지를 다이제스트 주소 그대로 production에 배포해서 두 환경의 다이제스트를 맞췄어요. 그 다음 배포 워크플로가 main에서는 이미지를 만들지 않고 staging의 이미지를 찾아 보내도록 바꿨어요.

개념 설명용 코드 — 형태만 보여 주는 명령이라 자리 표시를 그대로 둔 거예요

gcloud run deploy production서비스 --image 저장소/이미지@sha256:다이제스트 --update-env-vars COMMIT_SHA=커밋번호

여기서 --set-env-vars가 아니라 --update-env-vars를 쓴 이유가 있어요. 앞의 것은 기존 환경변수를 모두 지우기 때문이에요. 실제로 승격한 뒤에 환경변수(ENV, OCR_ENABLED)와 접근 권한(IAM)이 그대로인지 전후로 읽어 비교했어요.

워크플로로 바꾼 뒤, main에 머지하면 무슨 일이 일어나나

  • 「이미지 만들기와 올리기」 단계를 건너뛰어요. main에서는 새 이미지를 만들지 않아요.
  • 대신 「staging 이미지 찾기」 단계가 staging에서 확인한 이미지를 찾아 다이제스트 주소 그대로 production에 배포해요.
  • production 배포는 승인 대기로 멈춰요. 승인하면 진행돼요.
승격 전 방식승격 워크플로
main 머지 때production용 이미지를 새로 빌드이미지 만들기를 건너뜀
production이 쓰는 이미지새로 만든 이미지(staging과 다이제스트가 다를 수 있음)staging 이미지 그대로
제가 확인한 것–PR #23 머지 뒤 production 리비전 00010-bv7의 다이제스트 5d64baf7278c가 staging과 같고 환경변수·IAM이 그대로. PR #25 머지 뒤 00011-vgr의 61e4310e0460도 staging과 64자리가 같음

한 가지는 실행해 보고서야 알 수 있었어요. main에서 도는 워크플로가 staging 서비스를 조회할 권한이 있는지는 코드만 봐서는 몰랐는데, 실제로 돌려 보니 성공했어요. 그리고 한계도 있어요. production에서 실제로 되돌려 본 적은 없고, 되돌리기 훈련은 staging에서만 했어요.

배포 끝에는 「배포 기록 남기기」 단계도 더했어요. 환경·서비스·커밋·리비전·다이제스트(앞 12자리)를 Actions 실행 요약에 표로 남기는 단계예요. 표의 값(production | routine-stamp-trial | 92d2c86647dd | routine-stamp-trial-00011-vgr | 61e4310e0460)이 Cloud Run 값과 일치했어요. 표의 커밋 칸에는 머지 커밋이 아니라 이미지를 만든 staging 커밋이 적혀요(의도한 동작이에요).

롤백 — 옛 리비전으로 「복귀」하는 것이 아니에요

문제가 생긴 배포를 이전 이미지로 돌리는 일을 롤백11이라고 해요. 저는 staging에서 손으로 롤백 훈련을 했어요. 결과는 "옛 리비전으로 복귀"가 아니라 이전 이미지로 새 리비전을 만드는 것이었어요. 승격도, 롤백도 새 리비전을 만들어서 번호는 계속 올라가요.

단계리비전다이제스트화면배포 시간
시작00006-ppb5d64baf7278c0304f99–
롤백(이미지 주소 + COMMIT_SHA를 함께 변경)00007-jrz64c25be3bf9dfc01d2124초
복구(최신)00008-fnl5d64baf7278c0304f9936초

롤백 중에는 다이제스트와 화면이 한 커밋 전의 값이 되고, 복구하면 최신 값으로 돌아왔어요. 환경변수와 IAM은 그대로였고 production과 main은 변하지 않았어요. 롤백할 때는 이미지 주소와 COMMIT_SHA 환경변수를 함께 바꿔야 해요. 환경변수는 이미지와 따로 남기 때문이에요. 시간은 배포 명령이 걸린 시간이고 조사하고 확인한 시간은 빠졌어요. COMMIT_SHA를 안 바꿨을 때 어떻게 보이는지는 시험해 보지 않았어요.

저장 공간 정리 — 롤백에 쓸 이미지를 남기는 기준으로

이미지는 배포할 때마다 쌓이고, 노드가 알려 준 무료 저장 공간은 0.5GB예요. 그래서 오래된 이미지를 지우는 정리 정책12을 정해요. 노드의 예시는 「7일 넘으면 삭제, 최근 10개 유지」예요. 두 조건이 겹치면 어떻게 될까요? 이미지가 15개이고 그중 6개가 7일보다 오래됐다고 해 볼게요.

번호(오래된 순)7일 넘음(삭제 조건)최근 10개(유지 조건)결과
1~5✓✕삭제
6✓✓유지(둘에 걸리면 유지)
7~15✕✓유지

그래서 지워지는 것은 1~5번의 5개예요(제 계산이고, 노드의 제출 해설은 보지 못했어요). 「최근 10개」는 저장소 전체가 아니라 패키지(이미지 이름)마다 센다는 점도 공식 문서에서 확인했어요. 남기는 수는 롤백으로 되돌릴 이미지가 남는지를 기준으로 정해요.

실제로 정책을 걸 때는 드라이런13부터 했어요. 정책 파일(7일 삭제, 최근 10개 유지)을 저장소가 아니라 임시 폴더에 만들어 문법을 통과시키고, 두 저장소에 --dry-run으로 적용했어요. 상태가 「Dry run is disabled」에서 「Dry run is enabled」로 바뀌었고 이미지는 2개와 60개 그대로였어요. 지금 데이터에 대입한 삭제 후보는 0개로 계산돼요(제 계산). 드라이런이 실제로 무엇을 지웠을지는 하루 뒤 감사 로그로만 알 수 있어서 오늘은 확인하지 못했고, --no-dry-run은 쓰지 않았어요.

이미지 크기 — FROM 한 줄이 크기를 3.8배로

이미지가 쌓이는 속도는 이미지 크기에도 달려 있어요. 4편의 Dockerfile 첫 줄 FROM python:3.13-slim-bookworm의 slim은 실행에 꼭 필요한 파일만 남긴 가벼운 베이스 이미지14예요. 이 한 줄만 python:3.13-bookworm(전체판)으로 바꿔 빌드해 봤어요.

측정값
slim 기반 이미지(로컬)431MB
전체판 기반 이미지(로컬)1.63GB (+약 1.2GB, 약 3.8배)
Artifact Registry에 저장된 slim 기반 이미지(압축)약 106MiB (111,483,083바이트)
전체판 베이스만 내려받은 양(압축)약 383MB (빌드 로그의 레이어 크기 합)

로컬 크기는 압축을 푼 값이고, Artifact Registry는 압축해서 저장해요. 전체판 이미지가 무료 0.5GB의 상당 부분을 차지할 것으로 짐작하지만 올려 보지 않아서 실제 값은 몰라요. 전체판 베이스 이미지 자체의 크기는 이 환경의 Docker가 따로 남기지 않아 재지 못했어요.

고장 난 Dockerfile 고쳐 보기 — 증상에서 줄 하나로

같은 노드에서 일부러 고장 낸 Dockerfile을 증상만 보고 찾는 실습도 했어요. 저장소는 건드리지 않고 임시 복사본에서만 했고 이미지는 올리지 않았어요. 정상 이미지는 431MB, 실행 사용자 appuser, /app에 .env 없음이었어요. 그중 두 문제는 아래와 같았어요.

문제고장증상원인

두 문제 모두 이미지 크기로는 알 수 없고, 이미지를 열어 파일과 사용자를 직접 봐야 드러났어요. 문제 C에서는 지운 줄 위의 주석(「관리자가 아닌 사용자로 실행한다」)이 남아 거짓 주석이 됐어요. 문제 A(OCR 안 됨)와 D(포트 고정)는 템플릿의 고장 파일이 다른 앱 기준이라 제 앱에 맞는지 비교가 필요해서 하지 않았어요.

식당으로 치면 사장이 요리사에게 "가맹점에 보낼 상자를 준비해 줘"라고 맡기는 장면이에요. 아래는 상황을 가정한 예시예요.

이럴 때 의심하세요 — 이미지를 환경마다 다르게 만들 때

이런 문제는 코드를 읽어서는 보이지 않고, 시험할 때는 되던 것이 실제 서버에서만 이상해지는 모습으로 먼저 나타나요. 아래 증상이 보이면 코드를 고치려 들기 전에 이 자리를 열어 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "배포 설정을 고쳐 줘" — production 배포에서 docker build가 새로 도는 줄이 생겼는지
  • "정리 정책 넣어 줘" — --dry-run으로 먼저 걸었는지, 남기는 개수가 롤백에 충분한지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
staging에서는 되던 것이 production에서 다르게 동작해요 (같은 커밋인데 버전이 다른 것 같아요) 두 서비스 리비전 상세의 이미지 다이제스트예요. 범인이 코드가 아니라 production 이미지가 따로 만들어진 것일 수 있어요 두 환경 리비전의 다이제스트가 64자리까지 같은지 비교해요. 다르면 production 배포 설정에서 docker build가 도는지 봐요
사용자 신고가 왔는데 지금 어느 커밋이 돌고 있는지 몰라요 앱 화면 구석의 v … 값, 그리고 Cloud Run 리비전 상세의 다이제스트예요. 리비전 이름만으로는 알 수 없어요 화면의 7자리로 먼저 커밋을 찾고, 다이제스트에서 Artifact Registry의 태그를 찾아 서로 맞는지 봐요
롤백했는데 화면의 커밋 값이 그대로예요 리비전의 COMMIT_SHA 환경변수예요. 환경변수는 이미지와 따로 남아요 롤백할 때 이미지 주소와 COMMIT_SHA를 함께 바꿨는지 봐요. 이 글에서는 함께 바꿨고, 안 바꿨을 때의 모습은 시험하지 않았어요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

production과 staging의 Cloud Run 리비전에서 이미지 다이제스트를 읽어서 64자리까지 같은지 비교해 줘.
다르면 production 배포 설정 파일에서 이미지를 새로 만드는 줄이 있는지 찾아 줄 번호로 보여 줘.
아직 아무것도 고치지 마.

확인 범위와 해 보지 못한 것

  • 정리 정책의 드라이런 결과(실제로 무엇이 지워질지)는 하루 뒤 감사 로그로만 알 수 있어서 확인하지 못했어요.
  • production에서 실제로 되돌려 보기는 하지 않았어요. 롤백 훈련은 staging에서만 했어요.
  • 같은 커밋을 날짜를 달리해 두 번 빌드해서 라이브러리 버전이 실제로 달라지는지는 확인하지 못했어요.
  • 노드는 내 컴퓨터에서 만든 이미지가 CPU 종류가 달라 Cloud Run에서 실행되지 않을 수 있다고 알려 줬어요. 제 컴퓨터는 x86_64라 Apple Silicon에서의 arm64 실패는 해 보지 못했어요.
  • 전체판 베이스 이미지를 올렸을 때의 압축 크기와 무료 저장 공간 대비 비율은 재지 못했어요.
  • 노드의 과제 2(태그 덮어쓰기 막기)는 하지 않았어요. 표의 커밋 칸은 앞 12자리만 비교했어요.

  • 로컬에서는 되는데 서버에서만 안 되는 이유 — Dockerfile로 실행 환경 정하기 (6) — 이 글에서 쓴 Dockerfile과 레이어 캐시가 어떻게 만들어졌는지 봐요.
  • Cloud Run에 소스를 배포한다는 것 (2) — 소스 배포와 리비전이 무엇인지 풀어요.
  • 도커(Docker)란 무엇인가 — 이미지와 컨테이너, 상자에 뭘 담느냐 — 이미지와 컨테이너를 따로 풀어요.
  • 배포한 AI 서비스가 말없이 틀리는 순간 (3) — 서버 로그로 원인을 찾는 순서를 봐요.
  1. 커밋(commit) — 코드를 한 번 저장한 시점으로, 시점마다 번호가 붙어요. ↩
  2. GitHub Actions — GitHub 저장소에 코드가 올라올 때 정해 둔 작업을 자동으로 실행하는 기능으로, 4편의 배포도 이것이 시작했어요. ↩
  3. 이미지 태그 — 이미지 이름 끝에 붙이는 이름표로, 다른 이미지로 옮겨 붙일 수 있어요. ↩
  4. 다이제스트(digest) — 이미지 내용에서 계산되는 sha256:로 시작하는 64자리 지문이에요. ↩
  5. 승격(promotion) — 시험한 환경에 올린 이미지를 새로 만들지 않고 그대로 다음 환경으로 보내는 일이에요. ↩
  6. 라이브러리 — 남이 미리 만들어 둔 기능 묶음으로, 직접 다 만들지 않고 가져다 써요. ↩
  7. Artifact Registry — GCP에서 이미지를 보관하는 저장소로, 2편의 소스 배포가 이미지를 맡기던 곳이기도 해요. ↩
  8. 리비전 — 이미지와 설정을 함께 적은 Cloud Run의 배포 기록으로, 2편에서 다뤘어요. ↩
  9. 커밋 SHA — git이 코드 내용으로 자동으로 만드는 커밋의 고유 번호예요. ↩
  10. sed — 파일 속 글자를 찾아 다른 글자로 바꿔 주는 명령어예요. ↩
  11. 롤백(rollback) — 문제가 생긴 배포를 이전 버전의 이미지로 돌리는 일이에요. ↩
  12. 정리 정책(cleanup policy) — 저장소에서 오래된 이미지를 자동으로 지우는 규칙이에요. ↩
  13. 드라이런(--dry-run) — 실제로 바꾸지 않고 무엇이 바뀔지만 계산해 보는 실행이에요. ↩
  14. 베이스 이미지(base image) — Dockerfile이 출발점으로 삼는 이미지로, 4편에서 FROM 줄로 다뤘어요. ↩
