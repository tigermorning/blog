hcom — 서로 다른 코딩 AI끼리 메시지를 주고받게 하기

2026. 9. 16.

※ 이 글은 제가 hcom을 제 윈도우 노트북에 직접 설치해 돌려 보고 정리한 것입니다. 본문에 나오는 실행 기록과 실패 사례는 모두 2026년 9월 16일에 제가 직접 잰 값이에요.

hcom은 각자 다른 터미널 창에서 돌고 있는 코딩 AI들이 서로에게 메시지를 보내고 서로의 상태를 볼 수 있게 해 주는 명령어 도구예요.

무엇을 해결하는 도구인가

코딩을 AI에게 맡기다 보면 창이 여러 개가 돼요. 한쪽에는 Claude Code1를 띄워 놓고, 다른 쪽에는 OpenCode를 띄워 놓는 식이죠. 그런데 이 둘은 서로의 존재를 몰라요. 한쪽이 만든 코드를 다른 쪽에게 검토시키려면, 제가 답을 긁어서 옮겨 붙여야 해요.

hcom은 그 옮겨 붙이는 일을 없애 주는 도구예요. 정확히는 명령줄 도구2라서, 평소 쓰던 명령 앞에 hcom만 붙여 실행하면 그때부터 그 AI가 다른 AI와 말을 주고받을 수 있게 돼요.

식당 주방에 창구를 내면 — 비유로 먼저

작은 식당을 떠올려 볼게요. 홀에서 주문을 받는 사람, 주방에서 요리하는 사람, 디저트를 맡은 사람이 있어요. 셋은 서로 안 보이는 자리에서 일해요. 창구가 없으면 사장이 주문서를 들고 홀과 주방을 계속 왕복해야 해요. 사장이 자리를 비우면 그 순간 전달이 멈춰요.

주방 벽에 창구를 하나 내고 호출 벨을 달면 달라져요. 홀 직원이 주문서를 창구에 꽂고 벨을 누르면 주방이 바로 받아요. 주방장은 "3번 테이블 주문 받았습니다" 하고 복창해요. 사장은 이제 왕복하지 않고, 창구를 힐끗 보기만 하면 지금 어느 주문이 걸려 있는지 알아요.

핵심 한 줄: hcom은 AI에게 새로운 능력을 주는 게 아니라, 사람이 손으로 하던 전달을 없애 주는 창구예요.

다만 여기서 비유가 끊기는 점은, 복창을 안 하는 주방장이 실제로 있다는 거예요. 제가 처음 돌렸을 때 OpenCode 쪽은 답을 자기 화면에만 쓰고 끝냈어요. 창구에 도로 꽂지를 않은 거죠. 이 문제는 아래에서 다시 다뤄요.

메시지가 실제로 지나가는 길

hcom은 서버에 연결하지 않아요. 제 컴퓨터 안에 작은 저장소를 하나 만들어 두고, 거기에 메시지와 상태를 적었다 꺼내요. 이 저장소를 읽고 쓰는 일은 훅4이 맡아요.

읽는 법: 위쪽 진한 화살표(①②)가 부탁이 가는 방향, 아래쪽 흐린 화살표(③④)가 답이 오는 방향이에요. 두 터미널은 서로를 직접 부르지 않고 가운데 저장소에만 쓰고 읽어요. 그래서 한쪽이 Claude Code이고 다른 쪽이 OpenCode여도 이어져요 — 저장소 입장에서는 둘 다 그냥 기록 한 줄이거든요.

설치

여러 방법이 있는데 제 경우 파이썬 도구 설치기로 깔았어요. 맥이라면 brew install aannoo/hcom/hcom 한 줄로도 돼요.

실행: 로컬 터미널

uv tool install hcom

설치가 끝나면 상태를 확인해요. 이 명령은 지금 컴퓨터에 어떤 코딩 도구가 깔려 있는지, hcom이 그것들과 이어졌는지를 보여 줘요.

실행: 로컬 터미널

hcom status

여기서 command not found가 나오면 설치는 됐는데 PATH5에 등록이 안 된 거예요. 터미널을 껐다 켜면 대개 풀려요.

다음으로 훅을 붙여요. 이걸 해야 메시지가 자동으로 배달돼요. 쓰는 도구에 대해서만 하면 돼요.

실행: 로컬 터미널

hcom hooks add claude

되돌리고 싶으면 hcom hooks remove all로 전부 떼어 낼 수 있어요. hcom을 안 쓰는 동안에는 이 훅이 아무 일도 하지 않아요.

띄우면 각 AI에게 이름이 하나씩 자동으로 붙어요. 제 경우 kira와 luna였어요. 사람이 고르는 게 아니라 무작위로 배정되는 호출부호 같은 거예요. 지금 누가 떠 있는지는 이 명령으로 봐요.

실행: 로컬 터미널

hcom list

이제 한쪽 창에 평소처럼 한국어로 부탁하면 돼요. "@luna한테 이 파일 검토를 맡기고 결과를 받아 와"처럼요. 제가 실제로 돌려 보니 Claude Code 쪽이 OpenCode 쪽에 질문을 보내고, 답을 받아서 저에게 돌려주기까지 23초가 걸렸어요. 그 사이에 제가 한 일은 없어요.

첫 시도는 실패했어요

사실 처음에는 안 됐어요. 부탁은 잘 전달됐는데 답이 안 왔어요. 기록을 열어 보니 이렇게 적혀 있었어요.

개념 설명용 코드 — 직접 실행하는 코드 아니에요

silo went idle without responding to your request

"요청에 답하지 않고 작업을 끝냈다"는 뜻이에요. 상대 AI의 화면을 열어 보니, 답은 제대로 써 놨더라고요. 다만 자기 화면에만 썼어요. 창구에 도로 꽂는 명령을 실행하지 않은 거예요.

이건 hcom의 고장이 아니라 예상해야 하는 기본 상태예요. AI 입장에서는 "물어봤으니 답을 썼다"로 할 일이 끝난 거니까요. 그래서 답장까지가 일이라고 미리 못 박아 둬야 해요. 아래 명령은 앞으로 띄우는 모든 AI에게 그 규칙을 한 번씩 알려 줘요.

실행: 로컬 터미널

hcom config notes "누가 물어보면 반드시 hcom send 로 답해라. 자기 화면에만 답하면 상대는 못 본다."

이 한 줄을 넣고 다시 돌리니 답장이 돌아왔어요. 같은 구조인데 결과가 갈린 건 규칙을 적어 뒀느냐 아니냐 하나뿐이었어요.

나쁜 선택좋은 선택
주방장에게 "재고 좀 봐 줘"라고만 말한다 → 주방장은 재고를 확인하고 자기 수첩에 적는다. 홀에서는 아무리 기다려도 대답이 없고, 사장은 결국 주방까지 걸어가 확인한다. "확인해서 창구로 도로 알려 줘. 안 알려 주면 확인 안 한 걸로 친다"까지 말한다 → 주방장이 창구에 답을 꽂는다. 홀은 걸어가지 않고 받는다.

역할을 어떻게 나눠야 요금이 덜 나오나

여기가 이 도구에서 가장 조심할 자리예요. hcom에서는 메시지 한 건이 상대 AI의 작업 한 번을 통째로 발동시켜요. 그러니까 "잘 부탁드립니다" 같은 인사도 요금으로는 일감 하나와 같아요. 둘이 예의 바르게 주고받기 시작하면 한 일은 없는데 요금만 올라가요.

제가 돌려 보면서 정리한 규칙은 넷이에요.

  • 한 명만 지휘하게 해요. 지휘하는 AI 하나를 정하고 나머지는 그 하나에게만 보고하게 해요. 전원이 전원과 이야기하게 두면 주고받는 횟수가 인원수의 제곱으로 늘어요. 구조를 고르는 이야기는 여럿이라는 말만으론 부족하다 — 네 가지 구조와 맞는 과업에서 더 자세히 다뤘어요.
  • 담당 파일을 미리 갈라 놓아요. 누가 어느 폴더를 맡는지 먼저 정하면 같은 파일을 겹쳐 고치는 일이 안 생겨요. hcom은 두 AI가 30초 안에 같은 파일을 고치면 양쪽에 경고를 보내는데, 이 경고도 각자를 한 번씩 깨워요.
  • 보고는 끝났을 때 한 번만 하게 해요. "시작합니다", "절반 했습니다" 같은 중계를 금지하면 왕복이 확 줄어요.
  • 긴 내용을 메시지 본문에 붙여넣지 않게 해요. 코드나 로그를 통째로 붙이면 보낸 쪽과 받은 쪽 양쪽에 같은 내용이 두 번 쌓여요. 파일 경로만 알려 주고 상대가 직접 읽게 하는 편이 싸요.

그리고 규칙 자체를 어디에 적느냐도 요금에 영향을 줘요. hcom에는 규칙을 적는 자리가 둘 있어요.

일이 끝났는지 알기

메시지보다 오히려 더 쓸모 있었던 건 상태를 보는 쪽이었어요. hcom list는 각 AI가 지금 작업 중인지, 기다리는 중인지, 승인 화면에서 멈춰 있는지를 보여 줘요.

마지막 항목이 특히 유용해요. AI에게 일을 맡겨 놓고 다른 걸 하다가 돌아와 보면, 실은 30분 내내 "이 명령 실행해도 될까요?" 화면에서 멈춰 있던 경우가 있잖아요. 제가 실험할 때도 띄운 AI가 승인 대기에 걸렸는데, hcom이 곧바로 launch_blocked라는 기록을 남겼어요.

끝났을 때만 알림을 받고 싶으면 이렇게 걸어 둬요.

실행: 로컬 터미널

hcom events sub --idle kira

상대 AI의 화면을 그대로 들여다볼 수도 있어요. 창을 옮겨 다니지 않고 확인할 때 써요.

실행: 로컬 터미널

hcom term kira

보고를 믿지 말고 검증하게 만들기

AI가 "다 했습니다"라고 보내 와도 그 말만으로는 확인이 안 돼요. 그래서 저는 보고할 때 커밋 번호를 같이 적게 했어요. 커밋은 코드를 저장한 시점마다 붙는 고유 번호예요.

이렇게 시키면 보고가 완료: 803548b 같은 모양으로 와요. 그러면 제가 그 번호를 직접 확인할 수 있어요 — 진짜 있는 번호인지, 어느 갈래에 들어갔는지, 파일을 몇 개나 건드렸는지요. AI의 말을 믿는 게 아니라 흔적을 보는 거죠.

제가 실제로 해 본 실험에서는 AI를 별도 작업 폴더에 띄워 놓고 파일 하나를 만들어 저장하게 시켰는데, 띄운 시점부터 완료 보고가 올 때까지 35초가 걸렸고 그동안 제가 손댄 건 화면을 한 번 들여다본 것뿐이었어요. 받은 번호를 확인해 보니 실제로 존재했고, 제 원래 작업 내용은 건드려지지 않았어요.

덧붙임 — Claude 안에서 대화창끼리는 잘 안 통해요

hcom을 쓰다 보면 자연스럽게 드는 생각이 있어요. "굳이 다른 도구끼리 이을 것 없이, 같은 Claude 안에서 대화창 여러 개를 띄우면 그건 서로 알지 않나?"

제가 확인해 보니 잘 안 통해요. 대화창마다 각자의 기억만 갖고 있어서, 옆 창이 무슨 작업을 했는지 기본적으로 몰라요. 지난 대화를 찾아보는 기능이 있긴 한데, 글자를 붙어 있는 그대로 찾는 방식이라 띄어쓴 표현으로는 잘 안 걸려요. 제가 같은 내용을 두고 소스 선정으로 찾으면 0건, 붙어 있는 낱말인 소스당으로 찾으면 3건이 나왔어요. 내용은 분명히 있는데 검색어 모양 때문에 못 찾는 거예요.

그래서 저는 대화창끼리 이어 붙이려고 애쓰는 대신, 작업 상태를 프로젝트 폴더 안의 파일 한 장에 적어 두는 쪽으로 정리했어요. 파일은 검색 방식에 영향을 안 받고, 새 대화를 시작해도 그냥 열어 보면 되니까요. 이 이야기는 나중에 따로 정리해 볼게요.

이 글에 나온 숫자 — 설치하거나 설정할 때 다시 볼 값

본문에서 나온 값 가운데 제 실습 기록이 아니라 다른 사람이 써도 그대로 통하는 값만 모았어요. 설치가 막히거나 설정을 손볼 때 이 표를 보면 돼요.

이럴 때 의심하세요 — AI 둘을 이어 놓고 뭔가 안 돌 때

아래 문제들은 에러 창이 뜨지 않고 조용히 지나가는 편이라, 뭐가 잘못됐는지 알아채기가 어려워요. 기다리는 시간이 길어지거나 요금이 예상보다 나오면 이 표부터 봐요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "둘이 상의해서 결정해 줘" — 왕복 횟수에 제한을 뒀는지 확인해요.
  • "이 폴더 전체를 둘이 나눠서 고쳐 줘" — 누가 어느 파일을 맡는지 정해 줬는지 확인해요.
이런 증상이 보이면먼저 열어 볼 자리확인 방법
부탁은 전달됐는데 답이 영영 안 와요. 부른 쪽 AI는 계속 기다린다고만 해요 상대 AI의 화면. 부른 쪽은 범인이 아니에요 hcom term <이름>으로 상대 화면을 봐요. 답이 화면에만 적혀 있으면 답장 규칙을 안 넣은 거예요. hcom config notes로 넣어요
한 일은 별로 없는데 요금이 평소의 몇 배로 나와요 주고받은 기록 — hcom events --type message "알겠습니다", "확인했습니다" 같은 내용 없는 왕복이 있는지 세어 봐요. 있으면 "답장이 필요 없는 알림은 답하지 마라"를 규칙에 넣어요
AI를 띄웠는데 창이 3초 만에 꺼져요. 화면에는 이유가 안 남아요 도구별 기본 설정값 — hcom config에서 _args로 끝나는 항목 거기에 hcom 전용 설정을 넣었는지 봐요. 그 자리는 도구 자신이 아는 설정만 받아요. hcom 전용 설정은 띄울 때 직접 붙이거나 notes에 넣어요
일을 맡겼는데 한참 지나도 아무 변화가 없어요 hcom list의 상태 칸 작업 중이 아니라 승인 대기로 멈춰 있는지 봐요. 그렇다면 그 창을 열어 승인해 줘야 이어져요
설치했다는데 command not found가 떠요 PATH — 설치할 때 마지막 줄에 나온 경고 터미널을 껐다 켜 봐요. 그래도 안 되면 설치기가 알려 준 폴더를 PATH에 넣어요
