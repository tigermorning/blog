바이브 코딩의 첫 문장 — PRD를 스스로에게 묻기

2026. 8. 28.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

어제 지도를 봤으니 오늘은 첫 걸음이다. 그런데 그 첫 걸음이 코드가 아니라는 게 의외였다. 에이전트한테 "챗봇 화면 만들어줘"라고 바로 시키는 게 아니라, 그 전에 내가 스스로에게 질문지를 채우는 자리부터였다.

1. 왜 코드보다 질문이 먼저인가

바이브 코딩은 말하면 에이전트가 화면과 파일을 만들어주는 경험이다. 근데 그 요청 자체가 "무엇을 성공으로 볼지" 비워둔 채 길어지면, 결과물은 빨리 생겨도 검증할 대상이 사라진다. 화면이 떴다는 사실만으로는 성공 여부를 판정할 수 없다는 뜻이다.

PRD(제품 요구사항 문서)는 에이전트에게 넘길 답안을 미리 써두는 문서가 아니다. 오히려 내가 아직 결정하지 못한 경계를 스스로 발견하는 질문지다. 모두콘 챗봇처럼 공개 정보에만 답해야 하는 제품에서는 "답할 수 있는 질문"과 "답하지 않아야 하는 질문"이 같은 무게를 가진다.

2. 여덟 개의 질문

강의에서 준 질문 목록을 모두콘 예시에 맞춰 채우면 이렇다.

#스스로에게 묻는 질문모두콘에서 확인한 답
①누구의 어떤 불편을 다룹니까행사 정보를 찾는 방문자가 공개 사실에 접근하도록 돕습니다
②사용자가 끝내 무엇을 할 수 있어야 합니까질문 뒤 답변의 근거와 원문 출처를 확인합니다
③제품의 한 문장 목표는 무엇입니까소개와 RAG를 연결해 근거 있는 안내를 제공합니다
④이번 범위에서 하지 않을 일은 무엇입니까로그인과 전문 DB 검색을 포함하지 않습니다
⑤어떤 자료를 사실로 삼습니까공개 원문과 그 URL을 함께 보관합니다
⑥답하지 못할 때 어떤 행동을 합니까근거 부족을 드러내고 보수적으로 제한합니다
⑦사용자가 성공을 어떻게 알아봅니까스트리밍 답과 출처 칩, 판정 배지를 확인합니다
⑧어떤 관찰로 수용 여부를 판정합니까수용 기준의 질문과 화면 상태를 하나씩 확인합니다

이 여덟 질문은 정답을 채우는 양식이 아니다. 아직 판단할 근거가 없는 칸에는 "모른다" 혹은 [결정 필요]로 남기는 게 오히려 맞는 답이다. 그 표식이 나중에 추가 조사나 에이전트에게 물어야 할 위치를 그대로 보여주기 때문이다. 목표가 넓어지면 비목표가 없을 때 검색 범위도 무한히 넓어지고, 판정 기준이 없으면 완성된 화면을 보고도 뭐가 빠졌는지 말할 수 없다.

3. 목표는 기능 목록이 아니라 사용자의 변화

"모두콘 챗봇을 만든다"는 작업 목록으로는 쓸 수 있어도 제품 요구로는 부족하다. 사용자가 행사 소개를 읽고 역대 정보를 찾으며, 답의 출처를 열어본다는 변화까지 적어야 소개 페이지, 청크, 검색, 생성 UI가 하나의 목표를 향한다.

비목표는 목표를 축소하는 사과가 아니라 이번 구현이 약속하지 않는 것을 선언하는 안전장치다. 로그인, 전문 DB 검색, 다국어, 모바일 최적화, 서버 수집을 비목표로 적으면 에이전트가 계정 시스템이나 서버 동기화를 필요한 것처럼 구조를 부풀리지 않는다. 정적 브라우저 앱이라는 선택과도 맞물린다 — 공개 문서를 정적 파일로 두고 브라우저에서 검색하며 로컬 Ollama를 부르는 구조에서, 서버 쪽 계정 관리와 비공개 데이터 검색을 섞는 건 목표 확장이 아니라 다른 제품의 시작이다.

4. 수용 기준 — "좋은 챗봇"을 관찰 가능한 문장으로

수용 기준은 해석이 갈리는 표현("좋은 챗봇")을 화면에서 확인 가능한 문장으로 바꾸는 장치다. 모두콘 기준에는 이런 게 들어간다.

  • 소개에 출처를 표시할 것
  • "모두콘이 뭐야?"에는 [ID] 근거를 가진 스트리밍 답변을 보일 것
  • "내일 날씨"처럼 도메인 밖 질문에는 refusal=true로 제한할 것
  • 모든 답변에 판정 배지를 보일 것
  • API 키 없이도 로컬 자기평가를 시도할 것
  • 판정에 실패해도 기존 UI를 무너뜨리지 않을 것
  • 상대시간 질문은 질문 시점의 KST로 해석할 것
  • 출처 칩에서 원문을 열 수 있을 것
  • Ollama가 꺼졌을 때 배너와 재시도를 보일 것
  • CORS 설정 뒤 github.io 환경에서도 동작할 것

여기서 로컬 judge는 같은 2B 모델이 답과 판정을 모두 다루므로 독립 평가가 아니다. 교육용의 거친 신호로 읽어야 한다는 단서도 기준에 함께 적어둔다. 기준 하나는 기능 하나를 추가하라는 명령이 아니라, 실패해도 사용자가 아무것도 없는 상태를 겪지 않게 하는 관찰 가능성의 약속이다.

5. 자기 도메인의 PRD 초안 만들기

  1. 모두콘을 기준점으로 삼되, 안내하고 싶은 도메인을 하나 정한다. 자료를 공개 URL로 확인할 수 있어야 하고, 확신 없으면 그 불확실성 자체를 조사 항목으로 남긴다.
  2. 앞의 여덟 질문에 한 문장씩 답한 뒤, 답을 목표·비목표·수용 기준의 세 제목 아래로 재배열한다.
  3. 수용 기준은 실제로 입력할 질문과 관찰할 화면 상태를 포함한 문장으로 바꾼다.

"정확한 정보를 제공한다"보다 "소개 정보에 출처가 표시된다", "행사 밖 질문에는 근거 부족 또는 거절 상태가 드러난다"가 검증 가능한 기준이다. 반대로 자료가 없는 주제를 그럴듯하게 답하게 한다는 문장은 RAG의 목표와 애초에 맞지 않는다.

6. 에이전트에게 맡길 첫 대화 — 구현 전에 반박부터

PRD 초안이 생긴 뒤에야 에이전트에게 첫 요청을 보낸다. 목적은 즉시 모든 파일을 만들게 하는 게 아니라, 에이전트가 PRD의 모순과 빠진 판정 기준을 먼저 찾아내게 하는 것이다.

당신은 브라우저 기반 RAG 안내 챗봇의 제품 설계 검토자입니다.
아래 PRD 초안을 읽고 구현을 시작하지 말고 먼저 검토합니다.

도메인: [내 도메인]
목표: [사용자가 할 수 있어야 하는 일]
비목표: [이번 범위에서 하지 않을 일]
공개 자료 후보: [URL 또는 자료 종류]
수용 기준: [질문과 관찰 가능한 결과]

반드시 다음 순서로 답합니다.
1. 목표와 비목표가 충돌하거나 모호한 지점을 질문으로 제시합니다.
2. 공개 자료만으로 검증할 수 없는 수용 기준을 표시합니다.
3. 도메인 밖 질문, 근거 부족, 판정 실패의 처리 기준을 제안합니다.
4. 수정된 PRD 목차를 작성하되, 확인되지 않은 사실과 수치를 추가하지 않습니다.
5. 파일 생성이나 코드 작성은 제가 명시적으로 요청할 때까지 하지 않습니다.

마지막 문장은 속도를 늦추는 장식이 아니다. 설계와 구현을 분리해서, 검토 결과가 코드에 의해 덮이지 않게 막는 경계다. PRD 문장 하나하나가 나중에 채점 문항이 된다고 생각하니, 오늘 빈칸으로 남긴 [결정 필요]들이 갑자기 무겁게 느껴졌다.

정리

오늘 배운 건 결국 하나다 — 빠른 코드보다 먼저, 무엇을 성공으로 볼지와 무엇을 하지 않을지를 문장으로 고정하는 일. 다음 편에서는 이 PRD를 실제 검색 가능한 자료로 바꾸는 첫 단계, 청크 설계로 넘어간다.
