Git 브랜치·병합 실습 (6)

2026. 7. 12.

5편까지 오는 동안 저는 파일을 고치면 곧바로 기록을 남기고(커밋), 그대로 GitHub에 올려보냈어요(푸시). 기록이 쌓이는 줄이 딱 하나뿐이었던 셈이에요. 이 기본 줄의 이름이 main이에요. (커밋은 "지금 이 상태를 사진처럼 찍어 기록에 남기는 것", 푸시는 "그 기록을 GitHub 서버로 밀어 올리는 것"이에요.)

그런데 자동 발행 시스템까지 만들고 나니 문제가 생겼어요. 실험 삼아 뭘 고쳤다가 잘못되면, 이미 잘 돌아가던 블로그가 그대로 망가진다는 거예요. 줄이 하나뿐이니 커밋하는 순간 그게 곧 main이니까요. 바로 이 상황을 위해 Git이 처음부터 갖고 있던 장치가 브랜치(branch)와 병합(merge)이에요. 마지막 6편에서는 이 둘을 직접 실습해본 이야기를 정리했습니다.

← 이전 편 (5) GitHub Actions로 예약 발행 만들기

1~2. 브랜치와 병합이 뭔가요?

브랜치(branch)는 원래 나뭇가지라는 뜻이에요. 이 이름이 개념을 거의 다 설명해줘요. 나무는 줄기 하나에서 가지가 갈라져 나오고, 가지는 각자 다른 방향으로 자라지만 뿌리는 같잖아요. Git의 브랜치도 똑같아요. 지금까지 쌓인 커밋 기록(줄기)의 어느 시점을 골라 새 가지를 하나 뻗어내고, 그 가지 위에만 새 커밋을 쌓는 거예요.

그래서 그 가지에서 파일을 아무리 뒤집어놓아도, 줄기인 main은 갈라져 나온 그 시점 그대로 멀쩡히 남아 있어요. 문서를 고칠 때 원본은 두고 사본에 마음껏 낙서해보는 것과 비슷한데, 다른 점이 하나 있어요. 사본에 한 낙서는 나중에 원본에 옮기려면 손으로 다시 옮겨 적어야 하지만, 브랜치는 합치는 방법이 이미 준비되어 있다는 거예요. 그게 바로 다음에 나올 병합이에요.

가지에서 해본 작업이 마음에 들면, 그 결과를 다시 줄기(main)에 합쳐 넣어요. 이걸 병합(merge)이라고 해요. merge는 "여럿이 하나로 합쳐진다"는 뜻의 영어 단어 그대로예요. 갈라졌던 두 갈래의 기록을 Git이 비교해서 한 줄기로 다시 이어붙여줍니다.

그러니까 브랜치와 병합은 따로 외울 두 개가 아니라 한 세트예요. 갈라져 나와서(branch) → 그 안에서 마음껏 해보고 → 괜찮으면 다시 합친다(merge). 결과가 별로면 합치지 않고 가지째 버리면 되고, 그동안 main은 단 한 번도 위험해지지 않아요.

중요한 오해 하나: 브랜치는 "거쳐가는 임시 과정"이 아니라, 그 안의 커밋은 진짜로 저장돼요. 다만 main과는 분리되어 있어서, 병합하기 전까지는 실제 결과(예: 배포되는 웹사이트)에 반영이 안 될 뿐이에요.

3~4. 브랜치 만들고 그 안에서 작업하기

개념을 알았으니 직접 해봤어요. 여기서 한 가지 짚고 갈 게 있는데, 브랜치는 만드는 것과 그 브랜치로 옮겨 가는 것이 별개예요. 가지를 뻗어놓기만 하고 제가 여전히 줄기에 서 있으면, 파일을 고쳐도 그 기록은 그대로 main에 쌓이거든요. 그래서 보통 이 둘을 한꺼번에 처리합니다.

🎨 바이브 코딩으로: Claude에게 "새 브랜치를 만들어서 그쪽으로 이동해줘"라고 말하면 돼요.

🔍 궁금하다면: 실제로 어떤 명령어일까?

git checkout -b practice-branch

checkout -b는 "브랜치 만들기"와 "그 브랜치로 이동하기"를 한 번에 해주는 명령어예요.

이 상태에서 파일을 수정하고 커밋하면, 그 기록은 practice-branch에만 남아요. 신기하게도 다시 main으로 돌아가서 확인해보면, 방금 수정한 내용이 안 보여요 — 브랜치가 서로 격리되어 있다는 증거예요.

처음엔 이게 좀 무서웠어요. 파일 탐색기로 폴더를 열어봐도 내용이 진짜로 예전 상태로 돌아가 있으니까, 작업한 게 날아간 것처럼 보이거든요. 알고 보니 Git은 브랜치를 옮길 때마다 폴더 안의 파일들을 그 브랜치 시점의 모습으로 통째로 바꿔놓아요. 사라진 게 아니라, 그 기록이 지금 제가 서 있는 가지에는 없는 것뿐이에요. 다시 practice-branch로 옮겨 가면 그대로 돌아옵니다. 이걸 눈으로 확인하고 나서야 "여기서는 뭘 해도 main은 안전하겠구나" 하고 마음이 놓였어요.

5~6. main으로 돌아가 병합하기, 그리고 왜 필요한가

실험한 내용이 마음에 들었으니, 이제 이걸 줄기에 옮겨 붙일 차례예요. 여기서 순서가 중요해요. 병합은 "받을 쪽"에 서서 하는 작업이라, 먼저 main으로 돌아간 다음에 "저 브랜치를 여기로 합쳐줘"라고 시켜야 해요.

🎨 바이브 코딩으로: Claude에게 "main으로 돌아가서 이 브랜치를 합쳐줘"라고 말하면 돼요.

🔍 궁금하다면: 실제로 어떤 명령어일까?

git checkout main
git merge practice-branch
git branch -d practice-branch

merge로 합친 다음, branch -d로 다 쓴 브랜치를 정리했어요. 여기서 또 헷갈렸던 게, "브랜치를 지우면 그 안의 커밋 기록도 같이 지워지는 거 아니야?"였는데 — 아니에요. branch -d는 그냥 "브랜치 이름표(책갈피)"만 떼는 거고, 이미 main에 합쳐진 커밋 기록은 그대로 남아있어요.

여기까지 해보고 솔직히 든 생각은 "그래서 이게 왜 필요하지?"였어요. 합치고 나니 결과가 그냥 main에서 바로 고친 것과 똑같았거든요. 실제로 혼자서 간단한 수정만 할 때는 결과가 다르지 않아요. 브랜치의 값어치는 결과물이 아니라 중간 과정의 안전함에 있더라고요. 그래서 브랜치가 진가를 발휘하는 건 이런 때예요.

  • 실험적인 기능을 만들다가 잘못돼도 main은 안전하게 유지하고 싶을 때
  • 여러 사람이 동시에 각자 다른 부분을 작업할 때

특히 5편에서 만든 자동 발행 시스템처럼 이미 잘 돌아가고 있는 것을 건드릴 때가 그래요. 브랜치에서 먼저 해보고 확인된 것만 합치면, 최악의 경우에도 잃는 건 그 가지 하나뿐이에요. 제가 이 편을 마지막에 배운 건 순서가 그렇게 흘러갔기 때문이지, 사실은 뭔가를 고치기 시작하는 순간부터 필요한 개념이었어요.

이번 6편을 끝으로, "Git이 뭔지도 몰랐던 내가 하루 만에 블로그를 만들기까지" 시리즈를 마칩니다. 처음엔 "Git이 뭐예요?"부터 시작했는데, 여기까지 오게 됐네요.

돌아보면 여섯 편이 결국 한 줄로 이어져요. 파일이 바뀐 시점을 기록해두는 도구가 Git이고(1편), 그 기록을 인터넷에 올려둘 곳이 GitHub이고(2편), 실제로 주고받는 동작이 클론·커밋·푸시이고(3편), 올려둔 파일을 웹사이트로 보여주는 게 GitHub Pages이고(4편), 그 위에서 정해진 시각에 사람 없이 일하게 만든 게 GitHub Actions이고(5편), 그 모든 걸 망가뜨리지 않고 실험할 수 있게 해주는 게 브랜치와 병합(6편)이에요.

하루 전만 해도 저는 검은 명령창을 무서워하던 사람이었어요. 지금도 명령어를 다 외운 건 아니고 대부분 Claude에게 말로 시키지만, 적어도 지금 무슨 일이 일어나고 있는지는 알게 됐어요. 시작하는 데 필요했던 건 재능이 아니라 "일단 한 번 해보기"였다는 게, 이 시리즈에서 제가 얻은 제일 큰 소득이에요.
