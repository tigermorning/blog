합치기 전에 테스트하고 내보내기 전에 먼저 본다 — CI 테스트와 staging 환경 (5)

이 글에 나오는 말부터 풀어 둘게요. PR1은 "이 변경을 합쳐 주세요"라는 요청이고, main은 진짜 서비스가 되는 본줄기 코드(여러 갈래로 고치던 코드가 모이는 줄기)예요. 변경을 main에 넣는 것을 합친다(머지, merge)2고 해요. CI3는 PR마다 서버가 자동으로 돌리는 테스트고, 리비전4은 서비스를 배포할 때마다 붙는 버전 번호예요.

비유로 먼저 — 가맹점에 상자를 보내기 전의 검수대

이 시리즈는 비유를 하나만 써요. 7편에서 세운 밀키트 가게를 이어 갈게요. 사장인 내가 밀키트 상자를 만들어 시식 주방(staging)에서 맛을 보고, 가맹점(production)에 보내요. 그런데 상자가 하루에도 여러 번 나가면 사고가 나기 시작해요. 사장 집 주방에서는 멀쩡한데 가맹점 주방에서만 안 되는 레시피가 나가고, 포장이 덜 된 상자가 그대로 나가고, 시식용 상자가 가맹점 진열대에 올라가요. 그래서 상자가 가맹점으로 가기 전에 검수대를 세워요. 검수대는 사장이 바빠서 못 볼 때도 자동으로 상자를 살펴요.

핵심 한 줄: 검수대는 상자를 만든 사람이 아니라 문에 서 있어서, 사장도 불합격 상자를 통과시킬 수 없다.

다만 여기서 비유가 끊기는 점이 있어요. 검수 기계는 "정해 둔 항목"만 살펴요. 사장이 미처 생각하지 못한 맛 문제는 기계가 모르듯이, 테스트도 내가 적어 둔 것만 확인해요. 이 글의 마지막 사례가 바로 그 이야기예요.

전체 흐름 — PR에서 production까지 네 관문

변경이 PR로 올라오면 ① 서버가 테스트를 돌려요. 통과해야만 ② main이나 staging으로 합칠 수 있고(브랜치 보호), 합쳐지면 staging에는 자동으로 나가요. production은 ③ 사람의 승인을 기다리며 멈춰요. 실패하면 문 앞에서 돌아와요.

막고 싶었던 사고 — 세 가지와 네 관문의 짝

혼자서든 여럿이서든 코드를 서비스에 올리다 보면 이런 일이 생겨요.

  • 서버에서만 틀리는 일. 내 컴퓨터에서는 테스트가 통과하는데 서버에 올리면 실패해요. 컴퓨터마다 설치된 것, 설정, 시간대가 다르기 때문이에요. 이번 예는 시간대였어요. 내 컴퓨터(한국 시간)에서는 통과했어요. 그런데 서버가 쓰는 세계 표준시(UTC)5로 돌리니 오전 8시가 오후 5시(17:00)로 저장됐어요.
  • 망가진 코드가 합쳐지는 일. 실수로 망가진 코드가 main에 합쳐지고, 그대로 서비스까지 올라가요.
  • 연습과 진짜가 섞이는 일. 연습으로 올린 것이 진짜 서비스를 바꿔 버려요.

관문 1. 자동 테스트(CI) — PR마다 서버가 대신 돌려요

연습용 템플릿 저장소(friend-agent-template)에서 세 번에 나눠 만들었어요. 1~3번째 PR의 화면은 처음에 저장하지 못했어요. 그래서 같은 PR과 실행 기록을 나중에 다시 열어 확인했어요.

(1) 테스트 하나 넣기 (PR #1)

"내일 아침 8시에 물 마시라고 알려 줘"라고 하면 약속 시각이 한국 시간 08:00으로 저장되는지 보는 테스트예요. PR #1로 올려 합쳤어요(합친 커밋 d9512eb). 내 컴퓨터에서 pytest6(파이썬 코드를 시험해 주는 도구)를 돌리면 11개가 통과해요.

(2) 첫 CI가 실패하고, 고치기 (PR #2)

PR마다 서버가 테스트를 돌리게 하는 설정 파일(ci.yml)을 PR #2로 올렸어요. 그런데 첫 실행이 빨간불이었어요. 오류는 No module named 'app'(종료 코드 2)였어요. 서버에서는 pytest가 앱 폴더를 찾지 못한 거예요. 내 컴퓨터에서는 python -m pytest로 실행해서 현재 폴더가 경로에 들어갔어요. 그래서 몰랐던 것으로 보여요(추정). 이런 오류에서 막히는 게 정상이에요. 해결은 한 줄이었어요.

아래 한 줄은 "현재 폴더에서도 코드를 찾으세요"라고 pytest에 알려 주는 설정이에요. 그대로 따라 저장하면 돼요.

실행: 프로젝트에 pytest.ini로 저장 — pytest가 실행할 때마다 자동으로 읽어요

pythonpath = .

그러자 두 번째 실행은 초록불이었어요(합친 커밋 cea1536). 한 PR의 커밋 목록에 첫 커밋의 빨간 ✗와 고친 커밋의 초록 ✓가 같이 보여요.

(3) 서버에서만 틀리는 시간대 버그 (PR #3)

저장소에 미리 준비된 「일부러 망가뜨린 변경」 중 reminder-timezone을 PR #3으로 올렸어요. 이 변경은 약속 시각에서 시간대 정보를 지워요. 그러면 서버가 자기 시간대로 시각을 읽게 돼요.

  • 내 컴퓨터(한국 시간)에서는 11개가 모두 통과해요.
  • 서버처럼 UTC로 돌리면 약속 시각이 08:00이 아니라 17:00으로 저장되어 1개가 실패해요. 한국과 UTC의 시차인 9시간이 어긋난 거예요.

내 컴퓨터에서만 테스트했다면 못 잡았을 오류를 서버의 CI가 잡았어요. 같은 상황을 내 컴퓨터에서 TZ=UTC로 다시 돌려 보니 17:00으로 1개가 실패했고, CI 로그의 pytest 단계에서도 17:00이 찍혀 있었어요. PR #3은 원인을 읽는 것이 목적이어서 합치지 않고 닫았어요.

한 줄 정리 내 컴퓨터에서만 테스트했다면 못 잡았을 오류를 서버의 CI가 잡았어요.

관문 2. 환경 분리 — staging과 production

▼ 자세히 보기

GitHub에 staging(연습용)과 production(진짜 서비스) 환경7을 만들었어요. 환경마다 따로 값을 둬서(서비스 이름 변수와 환경 이름 변수) 같은 배포 파일이 환경에 맞게 움직여요. staging용 AI 키도 production과 따로 만들었어요. 서비스 실행 계정이 읽을 수 있는 시크릿(비밀 값)8도 그 키 하나로 제한했어요. 설정 화면에는 production(보호 규칙 1개)과 staging이 있고 각각 변수가 2개씩 있어요.

배포 중 한 번 막혔어요. 빌드 단계에서 PERMISSION_DENIED(기본 계정을 빌드에 쓸 권한이 없음)가 났어요. 빌드에 쓸 계정을 환경 변수로 지정하고 배포 명령에 빌드 계정 옵션을 추가해서(PR #5) 풀었어요. staging으로 합치자 테스트(19초)와 배포(2분 17초)가 모두 초록불이었어요.

관문 3. 승인 대기 — 사람이 누르기 전에는 안 나가요

▼ 자세히 보기

production 환경에는 「내 승인」이 있어야만 배포가 진행되도록 지정했어요. staging을 main으로 올리는 PR #6을 합치자, 테스트는 통과했지만 production 배포는 「승인 대기(Waiting)」에서 멈췄어요. 사람이 승인하기 전에는 진짜 서비스가 바뀌지 않는다는 것을 화면으로 확인했어요.

이 배포는 승인하지 않고 취소했어요. 확인해 보니 production 서비스의 설정(환경 값, 실행 계정, 시크릿 권한)이 설계와 맞지 않았어요. 맞지 않는 상태 그대로 승인을 눌러 진짜 서비스를 바꾸지 않으려는 판단이었어요.

관문 4. 브랜치 보호 — 관리자인 나도 못 합쳐요

▼ 자세히 보기

main과 staging에 규칙을 걸었어요. 규칙은 세 가지예요. PR 없이는 합칠 수 없어요. test라는 검사가 통과해야만(필수 검사9) 합칠 수 있어요. 관리자(나)에게도 똑같이 적용했어요. 조회 명령으로 규칙이 걸린 것을 확인했고, main에 직접 push(코드를 바로 올리기)를 시도하니 GH006(보호된 브랜치라 거절)으로 막혔어요. 이렇게 걸어 두는 것을 브랜치 보호10라고 해요.

저장소에 미리 준비된 「일부러 망가뜨린 변경」 세 개(safety-exact-match, weather-keyword, reminder-timezone)도 차례로 PR로 올렸어요. 모두 test가 빨간불이 되었고 합치기 버튼이 회색으로 막혔어요. 합치기 방식 메뉴를 열어 봐도 「검사를 건너뛰고 합치기」 같은 항목이 없어요. 관리자에게도 규칙이 적용되도록 했기 때문이에요.

실전 사례 — 테스트는 통과했는데 AI는 규칙을 어겼다

오늘 이 흐름을 내 앱의 실제 문제에 그대로 써 봤어요. 문제는 도우미(루틴 코치 챗)가 오후 4시에도 「아침 먹기」를 권한 것이었어요. 고친 것들을 PR로 하나씩 올려 CI를 통과시키고 합친 뒤 배포했어요. 배포할 때마다 서비스에는 새 리비전 번호가 붙어요.

핵심은 네 번째 단계(00017)를 배포한 뒤예요. 테스트와 CI는 모두 통과했어요. 그런데 배포한 서비스에 같은 상황을 실제로 보내 보니 지난 칸을 또 권했어요. 테스트는 가짜 AI로 하기 때문이에요. 「프롬프트(AI에게 주는 지시문)12에 규칙이 들어갔다」까지만 확인할 수 있어요. 그래서 서비스에 같은 요청을 여러 번 보내 세어 봤어요. 여섯 번째 단계에서 빠져나간 이유는, 한 문장 뒤쪽의 「내일의 루틴」이 앞쪽 권유를 가려서였어요. 서버의 검사는 답을 읽어요. 지난 칸을 권했으면 다시 쓰게 해요. 세 번 모두 어기면 정해 둔 답을 써요.

한 줄 정리 테스트는 가짜 AI로 하기 때문에 「프롬프트에 규칙이 들어갔다」까지만 확인할 수 있어요.

나쁜 선택 vs 좋은 선택 — 에이전트에게 "배포 전에 테스트 붙여 줘"라고 할 때

밀키트 가게로 치면 사장이 검수대를 세우고도 "기계가 합격시켰으니 끝"이라고 여기느냐 아니냐의 장면이에요. 아래는 이 글의 사례를 바탕으로 가정한 예시예요.

나쁜 선택좋은 선택
가짜 AI로 도는 테스트가 초록불이면 안심하고 배포를 끝낸다 → 테스트는 「프롬프트에 규칙이 들어갔다」까지만 아는데, 배포한 서비스는 오후 4시에도 지난 칸을 계속 권한다. 테스트가 통과한 뒤 배포한 서비스에 같은 요청을 여러 번 보내 세어 본다 → 4번 중 2번, 8번 중 1번, 12번 중 0번처럼 빠져나가는 정도가 보이고, 서버의 답 검사를 한 단계씩 더해 간다.

이 글에 나온 숫자 — 오류 메시지를 읽거나 CI를 처음 붙일 때 다시 보는 값

이 글에서 직접 확인한 값 중 다른 프로젝트에서도 쓸 만한 것만 모았어요. 시간은 이 템플릿 저장소에서 한 번 잰 값이라 서비스마다 달라요.

이럴 때 의심하세요 — 관문을 세운 뒤에도 문제가 지나갈 때

이런 문제는 코드를 읽어서는 보이지 않고, 초록불인데 서비스가 이상하거나, 빨간불인데 합쳐지는 모습으로 먼저 나타나요.

증상이 아직 없어도, AI에게 이런 부탁을 한 직후라면 한 번 확인하고 넘어가요.

  • "테스트를 붙여 줘" — 서버에서 도는 실행 환경(시간대, 실행 위치)을 내 컴퓨터와 다르게 두고 돌려 봤는지
  • "main을 보호해 줘" — 관리자에게도 적용되는지, 필수 검사 이름이 실제 검사 이름과 같은지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
내 컴퓨터에서는 통과인데 CI만 빨간불이에요 (No module named …이나 시각이 몇 시간 어긋남) CI 실행 로그의 pytest 단계, pytest.ini, 시간대가 걸린 코드예요. 범인이 테스트 코드가 아니라 서버와 내 컴퓨터의 환경 차이일 수 있어요 내 컴퓨터에서 TZ=UTC로 다시 돌려 같은 실패가 나는지 봐요. 앱 폴더를 못 찾으면 pythonpath = .를 확인해요
테스트는 전부 초록불인데 배포한 AI 서비스의 답이 규칙을 어겨요 테스트가 가짜 AI를 쓰는지, 규칙이 프롬프트에만 들어 있는지예요. 실제 모델의 행동은 테스트가 보지 못해요 배포한 서비스에 같은 요청을 여러 번 보내 몇 번 어기는지 세어 봐요. 숫자가 작으면 늘려서 다시 봐요
검사가 실패했는데도 합치기가 막히지 않아요 저장소의 브랜치 보호 규칙이에요. 이 글의 내 앱 main에는 보호를 걸지 않아서 이런 상태였어요 브랜치 보호 규칙을 조회해서 필수 검사와 관리자 적용 여부를 봐요
합쳤는데 production 배포가 「승인 대기」에서 멈춰 있어요 GitHub 실행 화면의 production 환경 승인 요청이에요. 고장이 아니라 설정한 대로의 동작이에요 누르기 전에 production 서비스의 환경 값, 실행 계정, 시크릿 권한이 설계와 맞는지 봐요. 맞지 않으면 승인하지 않고 취소해요

만든 것

  • PR마다 도는 테스트(CI)와, 통과해야만 합치게 하는 필수 검사(템플릿).
  • staging과 production 분리, production 승인 대기, staging 전용 키.
  • 내 앱 칸 열림 일정 테스트 9개와 CI, 일부러 깨뜨린 PR이 막히는 것 확인.
  • 배포 후 실제 서비스에 같은 요청을 보내 확인하는 습관(서비스 설정의 배포 전후 비교 포함).

비어 있는 곳

  • 내 앱 main에는 브랜치 보호를 걸지 않았어요(조회 결과 보호 없음). 테스트가 실패해도 합치기가 막히지 않아요. 지금은 제가 확인하고 합칠 뿐이에요.
  • 내 앱의 CI는 화면 테스트(webtests)만 돌려요. 서버 테스트(190여 개)는 내 컴퓨터에서만 돌렸어요.
  • 내 앱은 GitHub Pages가 저장소 전체를 공개해요. tests/와 package.json도 보이는 상태예요(저장소가 공개이고 비밀 값은 없어요). 공개 범위는 아직 정리하지 않았어요.
  • 도우미의 답 품질은 사람이 같은 요청을 여러 번 보내 확인했어요. 자동으로 점검하는 평가(실제 모델 대상)는 아직 없어요.
  • production 서비스(템플릿)의 설정이 설계와 맞지 않는 점은 손대지 않았어요. 승인 대기 배포는 취소했어요.
  • 도우미 재현 숫자(4번 중 2번, 8번 중 1번, 12번 중 0번)는 표본이 작아서, 개선의 정도가 아니라 「실제로 확인했다」는 기록이에요.

  • 과제 2(예시를 테스트로)와 3(메신저 알림)은 하지 않기로 하고, 1과 4에 집중했어요.
  • 템플릿의 시간대 버그 PR #3은 합치지 않고 닫았어요. 목적이 「원인을 읽는 것」이었기 때문이에요.
  • staging AI 키를 처음에는 Claude 키로 만들었다가, 이 프로젝트가 쓰는 OpenAI 키로 다시 바꿨어요. 바꾼 뒤 이전 버전은 폐기해서, staging 키에 버전이 여러 개 남지 않게 했어요.
  • production 배포가 승인 대기에서 멈췄을 때 승인하지 않고 취소했어요(관문 3).

배운 점

  • 테스트는 「통과했다」가 아니라 「무엇을 확인했는가」가 중요해요. 가짜 AI를 쓴 테스트는 규칙이 프롬프트에 들어갔는지만 알아요. 실제 모델의 행동은 배포한 서비스에 직접 보내 봐야 알아요.
  • CI는 내 컴퓨터가 우연히 맞춰 주는 것(시간대, 실행 위치)을 걷어 내요. 시간대 버그와 pythonpath 오류가 같은 종류였어요.
  • 관문은 사람의 부주의를 막는 장치이지, 사람의 판단을 대신하지 않아요. production 승인 대기에서 멈춘 것을 승인하지 않고 취소한 것이 그 예예요.
  • 한 번에 크게 고치지 않고 PR 단위로 작게 나누면, 무엇이 문제였는지(프롬프트만으로는 부족했다)가 리비전 번호와 함께 남아요.
