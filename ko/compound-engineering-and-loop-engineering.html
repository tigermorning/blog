쌓일수록 강해지기 — 컴파운드 엔지니어링

앞서 본 AGENTS.md·스킬에는 숨은 힘이 하나 있었어요. 한 번 적어두면 다음 작업이 더 수월해진다는 것. 이 아이디어를 아예 하나의 작업 방식으로 만든 게 컴파운드 엔지니어링(compound engineering)이에요. compound는 '쌓인다'는 뜻이에요. 일할 때마다 그 경험을 규칙·스킬로 남겨서, 다음 일이 이전 일 위에 쌓이게 하는 거예요.

나쁜 선택좋은 선택
버그를 고치고 대화에서만 설명하고 끝낸다 → 새 대화는 그 교훈을 몰라서, 다음에 같은 버그를 또 만들어요. 버그를 한 번 고치면 그 교훈을 AGENTS.md에 한 줄 적어 둔다 → AI가 다음부터 자동으로 지켜요.

개발사 Every가 이 방식으로 소수 인원이 여러 제품을 굴린다고 알려졌고, 같은 이름의 Claude Code 플러그인도 인기래요.

이걸 도구로 구현한 예가 Nous Research의 Hermes였어요. 보통 AI는 대화창을 닫으면 배운 걸 잊어요. Hermes는 기억을 남기고 스스로 스킬을 만들어서, 오래 쓸수록 똑똑해지도록 설계됐대요(모델은 갈아 끼울 수 있고요). 만든 쪽은 '진짜 열쇠는 더 똑똑한 모델이 아니라 모델을 감싸는 더 똑똑한 껍데기(하네스)'라고 말해요. 하네스는 AI 모델을 감싸서 일하게 해 주는 도구와 규칙 묶음이에요. 앞서 배운 '모델 + 하네스'의 하네스를 끝까지 밀어붙인 셈이었어요.

한 걸음 더: 이 "경험을 남겨 다음 작업이 쌓이게 한다"는 아이디어를 ExpeL·Voyager·WikiSkill 같은 실제 연구와 함께 훨씬 깊게 다룬 글이 성공은 자산으로, 실패는 설명으로예요. 여기 나온 Hermes를 "경험을 재사용하는 도구" 관점에서 다시 살펴보고, 반대로 반성(Reflexion)이 항상 성능을 높이진 않았다는 반전 사례도 다뤄요.

프롬프트를 넘어 루프로 — 'Ralph'

앞에서 본 "계획-실행-관찰-반복" 루프를, 요즘은 사람이 직접 설계하는 흐름이 뜨고 있대요. 대표가 개발자 제프리 헌틀리가 퍼뜨린 'Ralph'예요. 이름은 심슨 캐릭터 랠프 위검에서 땄어요. '단순해 보이는데 진짜 되더라'는 뜻으로 붙였대요. 방법은 놀랄 만큼 단순했어요.

  1. 같은 지시(스펙 = 앞서 본 명세 파일)를 계속 다시 줘요.
  2. 한 번에 한 가지만 하고 커밋(바뀐 내용을 되돌아올 수 있게 저장하는 일)해요.
  3. 목표를 이룰 때까지 반복해요. 진행 상황은 대화 기억이 아니라 파일과 git(변경 기록을 쌓는 도구)에 쌓아두고요.

왜 하나의 긴 대화 대신 이렇게 할까 궁금했는데, 앞서 본 '컨텍스트 부패'를 떠올리면 이해가 됐어요. 컨텍스트 부패란 대화가 길어질수록 AI가 앞부분을 놓치고 헤매는 일이에요. 그래서 상태를 대화 기억에 쌓지 않고, 스펙·AGENTS.md 같은 고정 파일과 git에 두는 거예요. 그러면 어느 바퀴에서 시작하든 AI가 같은 안내 파일을 근거로 삼아요.

2023년 AutoGPT는 '무한 반복'으로 실패했어요. 그 자리를 '멈출 기준(스펙) + 파일에 쌓는 진행'으로 다시 푼 셈이에요. 헌틀리는 이 방식으로 프로그래밍 언어 하나를 약 300달러어치 호출로 만들어 화제가 됐대요.

이 흐름이 굳어져 이제 도구에 아예 들어왔어요. Claude Code에는 목표만 주면 알아서 도는 /goal 명령이 생겼어요. Anthropic과 OpenAI는 '루프 만드는 법'을 공식 문서로 냈어요. Claude Code를 만든 보리스 체르니는 "나는 이제 프롬프트하지 않는다, 루프를 돌리고 그 루프가 대신 프롬프트한다"고까지 말한대요. 다만 안전장치가 없으면 무한 반복·엉뚱한 목표·요금 폭발이 흔해요. 그래서 멈출 기준과 검토는 여전히 사람 몫이라는 걸 잊지 않아야 했어요.

요즘 흐름 — MCP에서 '스킬 + CLI'로

MCP는 편하지만 공짜는 아니었어요. 연결해두면 AI가 그 도구 설명서를 미리 통째로 읽어두는데, 이게 컨텍스트(기억 공간)를 꽤 잡아먹어요. 그래서 2026년 들어 재미있는 반작용이 생겼어요. 무거운 MCP 서버 대신, AI가 원래 알고 있는 명령줄 도구(CLI)를 그냥 쓰게 하자는 흐름이에요. 명령줄 도구란 글자로 명령을 입력해 쓰는 프로그램이에요.

방식어떻게 일하나한 벤치마크에서 같은 일에 쓴 토큰
MCP 서버연결해 둔 도구 설명서를 미리 통째로 읽어요. 서버 몇 개만 붙여도 대화를 시작하기도 전에 수만 토큰이 날아가곤 한대요약 4만
CLIAI가 학습으로 이미 아는 명령을 그때그때 불러요. 예를 들어 깃허브 작업은 gh라는 공식 CLI가 이미 있어서, GitHub용 MCP 서버를 세우는 대신 "gh로 이슈 목록 가져와"라고 시키면 돼요약 1천

여기에 "이럴 땐 이 명령을 써" 정도를 담은 짧은 스킬 파일 하나만 얹으면 더 빠르고 정확해진다고 해요.

게다가 이 '무겁다'는 문제 자체도 도구 쪽에서 이미 손보고 있었어요. 요즘 Claude Code는 연결된 MCP 도구를 처음부터 다 읽지 않아요. 필요할 때 검색해서 그때그때 불러오는 방식(툴 서치)을 기본으로 써요. 그래서 MCP를 잔뜩 붙여둬도 예전처럼 대화를 시작하자마자 컨텍스트가 꽉 차진 않아요. 결국 'MCP는 무거우니 피하라'가 아니라, 무거운 부분은 도구가 알아서 덜어주는 쪽으로 가고 있는 거였어요. 그렇다고 MCP가 한물간 것도 아니었어요. 그래서 요즘 정리는 "셋 중 하나가 아니라, 스킬·MCP·CLI를 함께"였어요.

이런 상황이면이걸 써요
혼자 작은 걸 만들 때이미 있는 CLI + 짧은 스킬 — 가볍고 빨라요
여러 사람이 같이 쓰고 접근 권한·기록이 중요한 회사 환경MCP — 표준화된 관리가 여전히 강했어요

이 바닥은 정말 빠르게 바뀐다는 것도 기억해야 했어요. AI 코딩 도구의 이름·가격·무료 정책·회사는 짧은 기간에도 바뀌어요. 그래서 특정 도구가 인수됐는지, 중단됐는지, 대체됐는지는 외우지 않는 편이 안전했어요. 고르기 직전에 공식 공지와 현재 저장소 상태를 확인할 정보로 다뤄요. 도구 이름을 외우는 건 의미가 적었어요. 대신 이번 시리즈에서 배운 개념을 잡아두면 돼요. 에이전트 = 모델 + 하네스, MCP(연결), 스킬(반복 자동화), 루프(반복 실행)예요. 그러면 어떤 새 도구가 나와도 "아, 이건 하네스가 이렇구나, MCP 되나?"로 빠르게 판단할 수 있었어요. 이 도구들 안쪽에서 AI가 어떻게 "배우는지"는 3단계 AI는 어떻게 '배울까'에서 이어지고, 먼저 다음 편에서는 opencode로 모델을 고르는 법을 봐요.

이럴 때 의심하세요 — 같은 실수가 돌아오거나 루프가 안 끝날 때

경험이 안 쌓이는 문제와 루프가 새는 문제는 둘 다 대화창 밖에 흔적이 남아요. 규칙 파일에 무엇이 적혔는지, git에 어떤 커밋이 쌓였는지를 보면 AI가 기억하는 척하는지, 실제로 앞으로 가고 있는지가 드러나요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
지난주에 고친 버그와 똑같은 에러를 AI가 다른 기능을 만들다가 또 만들어요. 그때 한 설명을 다시 하고 있어요 그 교훈이 규칙 파일에 적혀 있는지예요. 대화에서만 설명하고 끝냈다면 새 대화는 몰라요. 전에 무엇을 고쳤는지는 그때의 커밋에 남아 있어요 전에 고친 커밋을 찾아 무엇을 바꿨는지 보고, 그 교훈을 한 줄 규칙으로 AGENTS.md(Claude Code라면 CLAUDE.md)에 적어요. 적어 뒀는데도 되풀이한다면 파일이 읽히고 있는지부터 봐요 (스킬·규칙 글의 이 줄)
루프를 돌려 두고 돌아왔더니 커밋이 수십 개 쌓였는데 스펙의 할 일은 그대로거나, 같은 파일을 고쳤다 되돌렸다 한 흔적이 보여요. 사용량도 크게 늘어 있어요 대화 화면이 아니라 git 기록과 스펙 파일이에요. 최근 커밋 메시지들이 같은 말을 되풀이하는지, 스펙에서 끝난 항목이 실제로 늘었는지 봐요 터미널(명령을 글자로 입력하는 창)에서 git log --oneline을 입력하면 최근 커밋이 한 줄씩 나와요. 직접 해 보는 명령이에요. 진전 없이 같은 말만 반복되면 루프를 멈추고, 스펙에 "무엇이 되면 끝"인지와 최대 몇 바퀴까지인지를 적은 뒤 다시 돌려요. 멈추는 법은 토큰 글의 이 줄에 있어요
MCP 서버를 여러 개 붙인 뒤로 대화를 막 시작했는데도 컨텍스트가 꽤 차 있거나, 짧은 부탁에도 한도가 빨리 줄어요 연결된 MCP 도구들의 설명이에요. 다만 툴 서치(필요할 때만 도구 설명을 불러오는 방식)를 쓰는 도구에서는 이 몫이 훨씬 작아서, 원인이 다른 데 있을 수도 있어요 안 쓰는 서버를 끄고 비교해요(컨텍스트 창 글의 이 줄). 깃허브 작업처럼 공식 CLI가 있는 일이라면, 그 서버를 끄고 "gh로 이슈 목록 가져와"처럼 명령을 쓰게 해 봐요. gh가 설치되고 로그인돼 있어야 해요

둘째 줄은 시간과 사용량이 이미 나간 뒤에야 보여요. 그래서 루프를 켜기 직전에, 스펙 파일에 끝 조건과 최대 바퀴 수가 적혀 있는지부터 봐요.
