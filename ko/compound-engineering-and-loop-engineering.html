컴파운드 엔지니어링과 루프, 그리고 MCP 다음은 CLI

2026. 7. 28.

※ 이 글은 모두의연구소 AI AIFFEL 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

쌓일수록 강해지기 — 컴파운드 엔지니어링

앞서 본 AGENTS.md·스킬에는 숨은 힘이 하나 있었어요. 한 번 적어두면 다음 작업이 더 수월해진다는 것. 이 아이디어를 아예 방법론으로 밀어붙인 게 컴파운드 엔지니어링(compound engineering)이에요. 핵심은 '일할 때마다 그 경험을 규칙·스킬로 남겨, 다음 일이 이전 일 위에 쌓이게' 하는 거예요. 버그를 한 번 고치면 그 교훈을 AGENTS.md에 적어두고, AI가 다음부터 자동으로 지키게 하는 식이죠. 개발사 Every가 이 방식으로 소수 인원이 여러 제품을 굴린다고 알려졌고, 같은 이름의 Claude Code 플러그인도 인기래요.

이걸 도구로 구현한 예가 Nous Research의 Hermes였어요. 보통 AI는 대화창을 닫으면 배운 걸 잊지만, Hermes는 기억을 남기고 스스로 스킬을 만들어 오래 쓸수록 똑똑해지도록 설계됐대요(모델은 갈아 끼울 수 있고요). 만든 쪽은 '진짜 열쇠는 더 똑똑한 모델이 아니라 모델을 감싸는 더 똑똑한 껍데기(하네스)'라고 말하는데, 앞서 배운 '모델 + 하네스'의 하네스를 끝까지 밀어붙인 셈이었어요.

프롬프트를 넘어 루프로 — 'Ralph'

앞에서 본 "계획-실행-관찰-반복" 루프를, 요즘은 사람이 직접 설계하는 흐름이 뜨고 있대요. 대표가 개발자 제프리 헌틀리가 퍼뜨린 'Ralph'예요(이름은 심슨 캐릭터 랠프 위검에서 땄고, '단순해 보이는데 진짜 되더라'는 뜻으로 붙였대요). 방법은 놀랄 만큼 단순했어요. 같은 지시(스펙 = 앞서 본 명세 파일)를 계속 다시 주고, 한 번에 한 가지만 하고 커밋하기를 목표를 이룰 때까지 반복해요. 진행 상황은 대화 기억이 아니라 파일과 git에 쌓아두고요.

왜 하나의 긴 대화 대신 이렇게 할까 궁금했는데, 앞서 본 '컨텍스트 부패'를 떠올리면 이해가 됐어요. 대화가 길어질수록 AI가 헤매니, 상태를 대화 기억에 쌓지 않고 스펙·AGENTS.md 같은 고정 파일과 git에 두는 거예요. 그러면 어느 바퀴에서 시작하든 AI가 같은 안내 파일을 근거로 삼아요. 2023년 AutoGPT가 '무한 반복'으로 실패했던 자리를, '멈출 기준(스펙) + 파일에 쌓는 진행'으로 다시 푼 셈이에요. 헌틀리는 이 방식으로 프로그래밍 언어 하나를 약 300달러어치 호출로 만들어 화제가 됐대요.

이 흐름이 굳어져 이제 도구에 아예 들어왔어요. Claude Code에는 목표만 주면 알아서 도는 /goal 명령이 생겼고, Anthropic과 OpenAI가 '루프 만드는 법'을 공식 문서로 냈어요. Claude Code를 만든 보리스 체르니는 "나는 이제 프롬프트하지 않는다, 루프를 돌리고 그 루프가 대신 프롬프트한다"고까지 말한대요. 다만 안전장치가 없으면 무한 반복·엉뚱한 목표·요금 폭발이 흔하니, 멈출 기준과 검토는 여전히 사람 몫이라는 걸 잊지 않아야 했어요.

요즘 흐름 — MCP에서 '스킬 + CLI'로

MCP는 편하지만 공짜는 아니었어요. 연결해두면 AI가 그 도구 설명서를 미리 통째로 읽어두는데, 이게 컨텍스트(기억 공간)를 꽤 잡아먹어요. 서버 몇 개만 붙여도 대화를 시작하기도 전에 수만 토큰이 날아가곤 한대요. 그래서 2026년 들어 재미있는 반작용이 생겼어요 — 무거운 MCP 서버 대신, AI가 원래 알고 있는 명령줄 도구(CLI)를 그냥 쓰게 하자는 흐름이에요. 예를 들어 깃허브 작업은 gh라는 공식 CLI가 이미 있고 AI는 이 명령을 학습으로 알고 있어서, GitHub용 MCP 서버를 따로 세우는 대신 "gh로 이슈 목록 가져와"라고 시키면 돼요. 한 벤치마크에서는 같은 일을 하는 데 CLI가 약 1천 토큰, MCP가 약 4만 토큰을 썼대요. 여기에 "이럴 땐 이 명령을 써" 정도를 담은 짧은 스킬 파일 하나만 얹으면 더 빠르고 정확해진다고 해요.

게다가 이 '무겁다'는 문제 자체도 도구 쪽에서 이미 손보고 있었어요. 요즘 Claude Code는 연결된 MCP 도구를 처음부터 다 읽지 않고, 필요할 때 검색해서 그때그때 불러오는 방식(툴 서치)을 기본으로 써요. 그래서 MCP를 잔뜩 붙여둬도 예전처럼 대화를 시작하자마자 컨텍스트가 꽉 차진 않아요. 결국 'MCP는 무거우니 무조건 피하라'가 아니라, 무거운 부분은 도구가 알아서 덜어주는 쪽으로 가고 있는 거였어요. 그렇다고 MCP가 한물간 것도 아니었어요 — 여러 사람이 같이 쓰고 접근 권한·기록이 중요한 회사 환경에서는 MCP의 표준화된 관리가 여전히 강했거든요. 그래서 요즘 정리는 "셋 중 하나가 아니라, 스킬·MCP·CLI를 함께"였어요. 혼자 작은 걸 만들 땐 '이미 있는 CLI + 짧은 스킬'이 가볍고, 여럿이 쓰고 권한을 챙겨야 하면 MCP를 쓰는 거예요.

이 바닥은 정말 빠르게 바뀐다는 것도 기억해야 했어요. AI 코딩 도구의 이름·가격·무료 정책·회사는 짧은 기간에도 바뀌니, 특정 도구의 인수·중단·대체 여부는 고정 사실로 외우기보다 선택 직전에 공식 공지와 현재 저장소 상태를 확인할 정보로 다루는 편이 안전했어요. 그래서 도구 이름을 외우는 건 의미가 적었어요. 대신 이번 시리즈에서 배운 개념 — 에이전트 = 모델 + 하네스, MCP(연결), 스킬(반복 자동화), 루프(반복 실행) — 을 잡아두면, 어떤 새 도구가 나와도 "아, 이건 하네스가 이렇구나, MCP 되나?"로 빠르게 판단할 수 있었어요. 다음엔 AI가 도구를 넘어 실제로 어떻게 "배우는지" — 데이터에서 규칙을 찾아내는 학습의 원리로 이어져요.
