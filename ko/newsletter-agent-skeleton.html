무엇을 만드나 — 하루 100건 남짓에서 다섯 건

매일 쏟아지는 AI 소식을 여러 사이트에서 찾아 읽기는 번거로워요. 그래서 최신 기사를 자동으로 모아 중요한 것만 골라 요약해 매일 아침 보내 주는 AI 뉴스레터 에이전트를 만들어요.

기사는 TechCrunch·The Verge·OpenAI 블로그·DeepMind 블로그 같은 해외 매체와 AI타임스·전자신문 같은 한국어 매체의 RSS1, 그리고 Hacker News의 공개 API2까지 11곳에서 가져와요. 최근 24시간이면 대략 50~120건인데, 실시간 소스라 돌리는 시각마다 달라요. 가져오는 건 매체가 공개한 제목·짧은 소개글·원문 링크뿐이고, 본문 전체를 다시 퍼뜨리지는 않아요. 그중 다섯 건만 남겨 내보내는 게 목표예요.

"뉴스레터 에이전트"를 한 덩어리로 보면 어디부터 손댈지 안 보여요. 다섯 단계로 쪼개면 단계마다 무엇을 받아 무엇을 내놓는지가 한 줄로 적혀요. 이 다섯 단계가 그래프의 노드3 다섯 개가 돼요.

③ 요약(취재)

실행 기록을 재고 설정을 파일로 빼는 운영은 16편이에요. 단계마다 방법이 여럿이라, 선택지를 늘어놓고 하나를 고르며 무엇을 포기했는지를 같이 적어요. 도구는 1편부터 써 온 LangGraph이고, 6~10편의 워크플로 패턴을 곳곳에 가져다 써요.

시작 전에 적어 두기 — 내가 매일 챙겨 보는 소식

코드를 쓰기 전에 매일 챙겨 보는 분야 소식, 그걸 접하는 경로, 가장 번거로운 점 하나를 적어 보세요. 1편에서 맡길 일을 조회와 행동으로 나눠 적어 본 것과 같은 결의 준비예요. "뉴스가 너무 많다"처럼 뭉뚱그리지 말고 장면으로 적어요.

  • "AI 소식을 X·뉴스 사이트·해외 블로그 세 군데서 따로 봐서, 같은 발표를 매체만 바꿔 서너 번 읽는다."
  • "영어 기사는 제목만 보고 넘겨서, 중요한 걸 놓친 줄도 모른다."

적은 번거로움은 다섯 단계 가운데 한 곳에 떨어져요. 여러 사이트를 도는 건 ① 수집, 같은 발표를 여러 번 읽는 건 ② 선별에서 겹치는 기사 거르기, 영어라 안 읽는 건 ③ 요약을 한국어로 받기, 매일 들어가 봐야 하는 건 ⑤ 발행이 풀어요. 적어 둔 문장은 16편에서 "무엇을 중요하게 볼지, 무엇을 버릴지"를 적는 설정 파일(audience.yaml)의 문장으로 옮겨요.

비유 — 개업 전 리허설, 빈 접시로 한 바퀴

1편에서 세운 뒤 10편까지 이어 온 그 식당 주방이에요. 저녁 영업만 하던 주방이 이제 매일 아침 "오늘의 한 상"을 내기로 했어요. 장보기·재료 고르기·조리·시식·내보내기 다섯 자리가 새로 생겨요.

사장님은 재료부터 사지 않고 전표 양식의 칸(장 본 재료·고른 재료·완성 접시·거쳐 간 자리)부터 정해 인쇄해요. 그다음 직원들에게 빈 접시를 들려 장보기 자리부터 내보내는 창구까지 한 바퀴 돌게 해요. 직원은 자리마다 아무것도 조리하지 않고 '거쳐 간 자리' 칸에 한 줄만 적어 넘겨요. 리허설이 끝나면 자리마다 진짜 담당을 세우지만, 벽의 동선표는 그대로 둬요.

비유 속 요소원래 개념
사장님이 매일 아침 다섯 접시짜리 "오늘의 한 상"을 내기로 정하기뉴스레터 에이전트 — 하루 100건 남짓에서 다섯 건을 골라 요약해 발행해요

자리마다 직원이 전표 '거쳐 간 자리' 칸에 한 줄만 적고 넘기기빈 노드 — 노드가 진짜 결과 없이 log에 한 줄만 돌려줘요
사장님이 자리 하나에 진짜 담당을 세우기 (동선표는 그대로)노드 갈아 끼우기 — 개발자가 같은 이름으로 함수를 다시 정의하면 build()가 그 함수를 붙여요

핵심 한 줄: 요리가 하나도 없어도 동선이 끝까지 돌면, 어느 자리에서 전표 칸이 어긋나는지는 개업 첫날이 아니라 리허설 날에 드러나요.

다만 여기서 비유가 끊기는 점이 둘 있어요. 사람 직원은 칸 이름이 조금 달라도 알아듣지만 그래프는 선언에 없는 이름의 값을 에러 없이 버리고, 리허설은 한 번으로 끝나지만 뼈대는 자리 하나를 바꿀 때마다 다시 돌려요.

전체 흐름 — 빈 노드 다섯 개와 State 하나

읽는 법: 가운데 상자 다섯 개가 노드이고 화살표 순서대로 한 번씩 실행돼요. 맨 위 점선 상자는 모든 노드가 함께 읽고 쓰는 State, 노드 아래 첫 줄은 그 노드가 값을 적는 칸, 둘째 줄은 진짜 코드로 바꾸는 편이에요. 맨 아래 log에는 노드마다 한 줄씩 쌓여요.

뒤 편은 선을 그대로 두고 상자 속만 바꿔요. 취재를 기사 수만큼 펼치는 14편에서만 select → report 선 하나를 손봐요.

만드는 순서 고르기 — 선택지 넷

가장 흔한 순서는 수집·선별·요약 함수를 차례로 완성한 다음 마지막에 이어 붙이는 거예요. 그러면 끝까지 가기 전에는 실제로 도는 물건이 하나도 없고, 붙이는 날에야 "이 함수가 돌려주는 모양과 저 함수가 받는 모양이 다르네"를 발견해요. 순서를 네 가지로 놓고 비교해 봐요.

만드는 순서얻는 장점치르는 대가
① 부품을 다 만들고 마지막에 조립한 번에 한 가지만 생각하고, 함수마다 따로 시험하기 좋아요조립하는 날까지 도는 물건이 없고, 단계 사이 규격 어긋남이 가장 늦게 한꺼번에 드러나요
② 빈 노드로 뼈대를 세우고 하나씩 채우기 (고른 순서)로그만 남기는 스텁5 다섯 개를 먼저 이어요. 첫날부터 도는 물건이 있고, 규격(State 칸)이 맨 처음 정해지고, 어디까지 만들었는지 로그에 보여요뒤에 무엇이 필요할지 다 모르는 채로 State를 처음에 설계해야 하고, 중간에 칸이 늘면 앞 노드를 다시 봐야 해요
③ 노드 하나를 완성할 때마다 그래프를 새로 그리기그때 필요한 만큼만 State를 정의해요그래프 정의를 매번 다시 쓰고 무엇이 바뀌었는지 대조해야 해요. 비슷한 코드가 여러 벌 생겨요
④ 그래프 없이 노트북6 셀을 순서대로 실행가장 단순하고, 이것저것 시험해 보는 탐색 단계에 맞아요되돌아가기나 여러 갈래로 펼치기를 표현하지 못하고, 매일 자동으로 도는 프로그램으로 옮길 때 전부 다시 써야 해요

여기서는 ②를 골라요. 매번 전체를 돌리니 "지금 어디까지 왔나"가 로그로 보이고, 12편의 수집 결과가 13편 선별의 입력이 되는 것도 보여요. 약점인 State 미리 설계도 부담이 작아요. 다섯 단계를 나눌 때 단계마다 받는 것과 내놓는 것을 이미 적었고, State의 칸은 그걸 코드로 옮긴 것뿐이거든요.

조건이 달라지면 다른 순서가 맞아요. 소스 하나를 이리저리 찔러 보는 날이면 ④가 가장 빠르고, 하루 만에 끝낼 작은 스크립트면 ①도 괜찮아요. 무엇을 포기했는지 알고 고르면 돼요.

State부터 정한다 — 기사 한 건의 모양과 칸 다섯

노드를 쓰기 전에 기사 한 건을 어떤 모양으로 들고 다닐지부터 정해요. 소스마다 기사를 가리키는 값을 link·url·id처럼 다른 이름으로 주고, 시각 형식도 제각각이에요. 한 모양으로 바꿔 두지 않으면 뒤 코드마다 if source == "hackernews": ... 같은 분기가 붙어요. 그래서 기사 한 건은 어느 소스에서 왔든 다섯 칸짜리 딕셔너리로 통일해요. title(제목) · url(원문 주소) · source(매체 이름) · at(발행 시각) · summary(매체가 붙인 짧은 소개글, 12편 수집 코드는 앞 300자까지)예요.

14편에서는 모델이 쓴 요약 칸(headline·summary·why)이 붙는데, summary는 이름이 같아서 소개글 자리를 모델의 요약이 덮어써요.

그다음이 그래프 전체가 함께 쓰는 State인데, 칸을 고르는 기준은 하나예요.

중요꼭 기억할 것

State에는 단계 사이를 실제로 건너가는 값만 올려요. 처음에 넣어 수집 노드가 읽는 설정값 hours와, 단계의 결과물(collected·picked·drafted·log)이에요. 프롬프트 문자열이나 인터넷 연결 세션처럼 한 노드 안에서만 쓰는 것까지 올리면 모든 노드가 들고 다니게 되어, 무엇이 어디서 쓰이는지 추적할 수 없어요.

빈 노드 다섯 개로 세우기

11~16편의 코드는 노트북 하나에 이어 붙여 가요. 12편은 이 편의 셀을 실행해 둔 노트북에서 시작하니, 새 노트북에 여기서부터 차례로 붙여 넣으세요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 노트북 첫 셀에서 한 번만. 맨 앞 !는 셀 안에서 터미널 명령을 돌린다는 표시예요

! pip install -q langgraph

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키 없이 돌아가요

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class Brief(TypedDict):
    hours:     int                              # 수집 시간 창(시간)
    collected: list                             # ① 수집한 기사
    picked:    list                             # ② 선별해 남긴 다섯 건
    drafted:   Annotated[list, operator.add]    # ③ 취재한 초안 — 워커들이 나눠 채운다
    log:       Annotated[list, operator.add]    # 무슨 일이 있었는지

def collect(s: dict) -> dict:                  # ① 자료 수집  — 12편에서 채운다
    return {"collected": [], "log": [f"① 수집   {s['hours']}시간 창 · 0건 (빈 노드)"]}

def select(s: dict) -> dict:                   # ② 중요도 선별 — 13편에서 채운다
    return {"picked": [], "log": [f"② 선별   {len(s['collected'])} → 0건 (빈 노드)"]}

def report(s: dict) -> dict:                   # ③ 요약       — 14편에서 채운다
    return {"drafted": [], "log": [f"③ 취재   {len(s['picked'])}건 (빈 노드)"]}

def verify(s: dict) -> dict:                   # ④ 검수       — 14편에서 채운다
    return {"log": [f"④ 검수   {len(s['drafted'])}건 (빈 노드)"]}

def publish(s: dict) -> dict:                  # ⑤ 발행       — 15편에서 채운다
    return {"log": [f"⑤ 발행   {len(s['drafted'])}건 (빈 노드)"]}

def build():                                    # 노드를 이름으로 찾아 붙인다
    g = StateGraph(Brief)
    for name in ("collect", "select", "report", "verify", "publish"):
        g.add_node(name, globals()[name])
    g.add_edge(START, "collect")
    g.add_edge("collect", "select")
    g.add_edge("select", "report")
    g.add_edge("report", "verify")
    g.add_edge("verify", "publish")
    g.add_edge("publish", END)
    return g

INIT = {"hours": 24,
        "collected": [], "picked": [], "drafted": [], "log": []}

def run():
    return build().compile().invoke(INIT)

for line in run()["log"]:
    print(line)

① 수집   24시간 창 · 0건 (빈 노드)
② 선별   0 → 0건 (빈 노드)
③ 취재   0건 (빈 노드)
④ 검수   0건 (빈 노드)
⑤ 발행   0건 (빈 노드)

아무것도 안 했는데 다섯 줄이 순서대로 찍혔어요. 이 다섯 줄이 앞으로의 진행 표시예요.

class Brief(TypedDict)는 TypedDict7로 State의 칸 이름을 적어 둔 거예요(2편의 전표와 같은 방식). f"...{s['hours']}..."는 중괄호 안의 값을 글자 속에 끼워 넣는 문자열이고, INIT은 그래프에 처음 넣는 State예요.

코드에서 짚을 세 가지

노드는 자기가 바꾼 칸만 돌려준다

verify와 publish는 log 하나만 돌려줘요. 돌려주지 않은 칸은 앞의 값이 그대로 남아요(2편의 부분 업데이트). 덕분에 State에 칸을 하나 더해도 기존 노드를 고칠 필요가 없어요. 14편에서 검수 통과분을 담을 칸이 새로 생겨도, 그 칸을 모르는 collect·select는 한 줄도 안 바뀌어요.

리듀서는 drafted와 log 두 칸에만 붙인다

Annotated[list, operator.add]가 붙은 칸은 다섯 중 둘뿐이에요. 이게 리듀서8로, 새 값이 오면 덮어쓰지 말고 +로 이어 붙이라는 표시예요. 왜 두 칸에만 붙였는지는 그 칸에 누가, 몇 번 쓰나를 보면 풀려요.

  • drafted — 14편에서 취재 워커 다섯이 동시에 이 칸에 한 건씩 넣어요(9편의 Send). 리듀서 없이 동시에 쓰면 8편의 InvalidUpdateError가 나고, 다섯 건이 다 남아야 하니 합쳐야 해요.
  • log — 다섯 노드가 모두 한 줄씩 보태요. 덮어쓰면 마지막 한 줄만 남아요.
  • collected·picked — 한 노드가 쓰고 다음 노드가 읽어요. 이런 칸은 덮어쓰는 게 맞아요.

리스트가 긴 칸이라서 붙이는 게 아니에요. 가장 긴 collected(100건 남짓)엔 안 붙였어요. TypedDict에 Annotated를 두 개까지만 쓸 수 있어서도 아니고(그런 제한은 없어요), 실행이 느려져서 아껴 쓰는 것도 아니에요. 덮어써야 할 칸에 붙이면 생기는 문제는 속도가 아니라 틀린 결과예요. 9건을 적는 노드 뒤에 그 9건을 읽어 5건만 같은 칸에 돌려주는 노드를 두고, 리듀서 없이 한 번, 붙여서 한 번 돌려 봤어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키 없이 돌아가요. 뼈대 셀 아래에 붙여도 뼈대는 안 바뀌어요

class Right(TypedDict):
    collected: list                              # 리듀서 없음 → 덮어쓰기

class Wrong(TypedDict):
    collected: Annotated[list, operator.add]     # 리듀서를 잘못 붙임 → 이어 붙이기

def fetch_nine(s):                               # 기사 9건을 적는다
    return {"collected": [f"기사{i}" for i in range(1, 10)]}

def keep_five(s):                                # 9건을 읽어 5건만 남겨 같은 칸에 돌려준다
    return {"collected": s["collected"][:5]}

def demo(schema):
    g = StateGraph(schema)
    g.add_node("fetch_nine", fetch_nine)
    g.add_node("keep_five", keep_five)
    g.add_edge(START, "fetch_nine")
    g.add_edge("fetch_nine", "keep_five")
    g.add_edge("keep_five", END)
    out = g.compile().invoke({"collected": []})
    print(schema.__name__, len(out["collected"]), out["collected"])

demo(Right)
demo(Wrong)

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

Right 5 ['기사1', '기사2', '기사3', '기사4', '기사5']
Wrong 14 ['기사1', '기사2', '기사3', '기사4', '기사5', '기사6', '기사7', '기사8', '기사9', '기사1', '기사2', '기사3', '기사4', '기사5']

Wrong은 5건으로 줄이는 노드를 지났는데 14건이 됐어요. keep_five가 돌려준 5건이 칸을 바꾸지 못하고 이미 있던 9건 뒤에 이어 붙어서 9 + 5 = 14예요. 기사1~기사5가 두 번 나오는데, 에러는 한 줄도 없어요.

더 곤란한 건 빈 뼈대에서는 이 실수가 아예 안 보인다는 점이에요. 뼈대의 collected·picked에도 리듀서를 붙여 돌려 봤는데, 로그 다섯 줄이 한 글자도 다르지 않았어요. 빈 리스트끼리 이어 붙여도 빈 리스트거든요. 칸을 읽어 줄여서 다시 쓰는 노드가 생겨야 드러나는데, 이 시리즈에서는 14편 검수가 그 자리예요. 그래서 통과분은 리듀서가 붙은 drafted가 아니라 리듀서 없는 새 칸에 담아요.

리듀서가 곧 operator.add는 아니다

규칙 자체는 한 줄이에요. Annotated[타입, 함수]의 두 번째 자리에 넣은 함수가 그 칸의 리듀서가 되고, LangGraph는 그 칸에 새 값이 올 때마다 함수(기존 값, 새 값)을 불러 돌아온 값을 칸에 적어요. 바로 위 Wrong을 이 규칙으로 한 줄씩 되짚으면 14건이 어디서 나왔는지 보여요.

지나는 노드LangGraph가 부르는 것칸에 남는 값
시작 전—[]
fetch_nine
9건을 돌려줌		operator.add([], 9건)9건
keep_five
5건을 돌려줌		operator.add(9건, 5건)14건

keep_five가 "이 5건으로 해 달라"고 돌려줘도, 그 값은 함수의 두 번째 인자로 들어갈 뿐이에요. 칸에 적히는 건 언제나 함수가 돌려준 값이고요.

그런데 여기 불린 operator.add는 LangGraph 기능이 아니에요. 파이썬에 원래 있는 함수로, 하는 일이 + 기호와 같아요.

개념 설명용 코드 — 주석은 실행했을 때 나온 값이에요

import operator
operator.add(3, 5)                # 8                 (3 + 5)
operator.add(["a"], ["b", "c"])   # ['a', 'b', 'c']   (리스트 + 리스트 = 이어 붙이기)

리스트끼리 +하면 이어 붙으니까, 리듀서 자리에 넣었을 때 "이어 붙이기"로 동작한 거예요. 바꿔 말하면 리듀서는 역할의 이름이고, operator.add는 그 역할을 맡을 수 있는 함수 중 하나예요. 주방으로 치면 리듀서는 "전표 칸에 새 내용이 오면 어떻게 적을지 정하는 담당" 자리이고, operator.add는 그 자리에 앉은 "아래에 이어 적는 직원" 한 명이에요. 그 자리에는 다른 직원도 앉힐 수 있어요.

두 번째 자리에 넣는 것새 값이 오면

직접 만든 함수(기존 값, 새 값)을 받아 돌려준 값이 칸에 적혀요

직접 만든 리듀서도 위 실험에 그대로 끼워 볼 수 있어요. 이미 있는 항목은 빼고 새 항목만 보태는 함수예요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 바로 위 Right·Wrong 셀을 실행해 둔 노트북에서. demo()를 다시 써요

def merge_unique(old, new):                      # 기존에 없는 항목만 뒤에 보탠다
    return old + [x for x in new if x not in old]

class Unique(TypedDict):
    collected: Annotated[list, merge_unique]

demo(Unique)

중요꼭 기억할 것

리듀서를 붙일지는 칸이 긴지, 실행이 느려지는지가 아니라 "그 칸에 여러 곳이 쓰거나, 쓸 때마다 쌓아야 하나"로 정해요. drafted는 취재 워커 여럿이 동시에 쓰고 log는 모든 노드가 한 줄씩 보태니 operator.add로 합쳐요. collected·picked처럼 한 노드가 쓰고 다음 노드가 읽는 칸에 붙이면, 9건을 5건으로 줄였는데 14건이 되는 틀린 숫자가 에러 없이 나와요.

build()는 노드를 이름으로 찾는다

build() 안의 globals()[name]이 이 뼈대의 교체 장치예요. globals()는 지금 노트북에 정의된 이름과 그 이름이 가리키는 값을 묶은 딕셔너리라, globals()["collect"]는 지금 그 이름에 붙어 있는 함수를 꺼내요. 그래서 뒤 편에서 collect를 같은 이름으로 다시 정의하고 run()만 다시 부르면, 조립 코드는 한 줄도 안 고치고 새 함수가 붙어요. 기사 9건짜리 가짜 collect로 확인해 봤어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — API 키 없이 돌아가요. 12편에서 진짜 collect로 다시 덮어쓰니 그대로 둬도 괜찮아요

def collect(s: dict) -> dict:                  # 같은 이름으로 다시 정의한다
    fake = [{"title": f"기사 {i}", "url": f"https://example.com/{i}",
             "source": "test", "at": "", "summary": ""} for i in range(1, 10)]
    return {"collected": fake,
            "log": [f"① 수집   {s['hours']}시간 창 · {len(fake)}건 (가짜 기사)"]}

for line in run()["log"]:
    print(line)

개념 설명용 코드 — 위 코드를 실행했을 때 제 화면에 찍힌 출력이에요

① 수집   24시간 창 · 9건 (가짜 기사)
② 선별   9 → 0건 (빈 노드)
③ 취재   0건 (빈 노드)
④ 검수   0건 (빈 노드)
⑤ 발행   0건 (빈 노드)

첫 줄이 0에서 벗어났고, 둘째 줄의 9 → 0건이 수집 결과가 선별로 건너갔다는 증거예요. 다섯 칸 모양을 따른 고정 가짜 값도 뼈대에서는 괜찮은 껍데기예요.

두 가지는 조심해요. 하나, 교체가 되는 건 run()이 매번 build()부터 다시 하기 때문이에요. 조립할 때 함수 자체를 붙여 두니, app = build().compile()을 변수에 담아 두고 app.invoke(INIT)를 되풀이하면 collect를 고쳐도 반영이 안 돼요. 제가 그렇게 해 보니 app.invoke의 첫 줄은 옛 로그 그대로였고, run()을 부르자 새 로그가 찍혔어요. 둘, 이름 목록에 "colect"처럼 오타가 있으면 조립 단계에서 KeyError: 'colect'로 멈춰요. 그 이름의 함수가 딕셔너리에 없다는 뜻이에요.

뼈대를 그림으로 뽑는다 — draw_mermaid와 mermaid.live

빈 노드 다섯 개가 선언한 순서대로 이어졌는지는 build() 코드를 눈으로 따라가는 대신, 그래프에게 직접 그리게 해서 확인해요. 주방으로 치면 사장님이 동선표를 손으로 다시 그리지 않고, 실제로 쓰는 전표 규칙에서 동선표를 뽑아 벽에 붙이는 거예요. 선언에서 뽑은 그림이라 선언과 어긋날 수가 없어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 뼈대 셀을 실행해 둔 노트북에서

그림이 아니라 글자가 나와요. 이 글자가 Mermaid9 문법이에요. 위아래 --- 사이는 선 모양 같은 설정 구역, graph TD는 위에서 아래로 그리라는 뜻, A --> B는 A에서 B로 가는 화살표예요. report --> verify가 select --> report보다 먼저 적혀 있는데, 그림은 적힌 순서가 아니라 화살표 연결대로 그려져서 괜찮아요.

이 글자를 그림으로 바꾸는 가장 쉬운 곳이 Mermaid 공식 온라인 편집기 mermaid.live예요. 무료이고 로그인도 필요 없어요.

  1. mermaid.live를 열면 왼쪽 Code 칸에 샘플 코드가 들어 있어요. 칸을 누르고 Ctrl+A, Delete로 전부 지워요.
  2. 위 출력을 --- 첫 줄부터 끝까지 통째로 복사해 붙여 넣어요.
  3. 저장이나 실행 버튼은 없어도 돼요. 오른쪽에 __start__ → collect → … → publish → __end__가 세로 한 줄로 이어진 그림이 바로 나와요.

이름이 비슷한 mermaid.ai는 계정으로 들어가는 다른 편집기라 화면 구성이 달라요. 처음에는 mermaid.live가 단순해요.

붙였는데 그림이 안 바뀌면 복사한 글자부터 봐요. 제가 첫 줄 ---만 빼고 붙여 보니, 오른쪽에는 원래 있던 샘플 그림이 그대로 남고 왼쪽 코드 칸 아래에만 Syntax error와 UnknownDiagramError: No diagram type detected가 떴어요. 여는 ---가 없으니 Mermaid가 config:를 그림 문법으로 읽으려다 실패한 거예요. 그림이 그대로라 아무 일도 안 일어난 것처럼 보여요.

  • 첫 줄이 빠졌거나 --(대시 2개)로 잘렸으면 ---(대시 3개)로 고쳐요. 설정 구역은 그림에 꼭 필요하지 않아서, ---부터 두 번째 ---까지 지우고 graph TD;부터 붙여도 돼요.
  • Mermaid는 그림 문법만 읽어요. 노트북에서 실행할 파이썬 코드(from typing import ...)를 Code 칸에 붙이면 같은 오류가 나요. 파이썬은 주피터 셀에서 실행하고, Code 칸에는 draw_mermaid()가 출력한 글자만 붙여요.

복사하기 번거로우면 노트북 안에서 바로 그림으로 볼 수도 있어요.

실행: Colab 같은 원격 주피터 또는 로컬 주피터 — 인터넷이 열린 환경에서. 그림을 만들 때 Mermaid 글자를 외부 서비스 mermaid.ink로 보내요

그림은 뼈대에서 끝나지 않아요. 14편에서 취재를 여러 워커로 펼친 뒤 같은 줄로 다시 뽑아 이 그림과 나란히 두면, 구조가 바뀐 자리만 눈에 들어와요.

중요꼭 기억할 것

draw_mermaid()는 그래프 선언에서 그림 글자를 뽑으니, 그림과 선언은 늘 같아요. 엣지를 바꿀 때마다 다시 뽑아 전후를 대조해요. mermaid.live에 붙였는데 그림이 그대로면 코드 칸 아래 Syntax error부터 보고, 첫 줄 ---가 온전한지 확인해요.

어차피 지울 코드인데 왜 만들까 — 걸어 다니는 뼈대

위 collect·select의 몸통은 12편, 13편에서 통째로 지워져요. 그런데도 먼저 만드는 이 방식을 걸어 다니는 뼈대(walking skeleton)라고 불러요. 단계마다 입출력 모양만 맞춘 껍데기(빈 값이나 고정 가짜 값 + 로그 한 줄)를 만들어 → 전부 잇고 → 하나씩 진짜 구현으로 바꾸는 방식이에요. 그러니 "어차피 지울 코드"는 반만 맞아요. 지워지는 건 함수의 안쪽뿐이고, 빈 노드가 세운 네 가지는 16편까지 남아요.

  1. 규격을 고정해요. 주고받을 칸(State)과 실행 순서(엣지)가 첫날 Brief 선언과 build() 한 곳에 적히고, 뒤의 노드는 모두 그 규격을 보고 만들어져요. 부품을 따로 만들면 이 어긋남을 대개 마감 직전에야 알아요.
  2. 늘 도는 상태를 지켜요. 노드 하나를 진짜로 바꿀 때마다 전체를 돌려 다른 데가 안 깨졌는지 바로 봐요.
  3. 진행도가 보여요. 가짜 collect를 넣자 첫 줄만 9건으로 바뀐 것처럼, 0에서 벗어난 줄 수가 곧 "어디까지 왔나"예요.
  4. 교체 비용이 0이에요. 같은 이름의 함수만 다시 정의하면 끼워져요.

주의할 게 둘 있어요. 첫째, 뼈대가 두꺼워지면 의미가 없어요. 껍데기에 조건 분기나 임시 로직을 넣으면 걷어낼 일이 또 생겨요(아래 나쁜 선택 vs 좋은 선택). 둘째, State를 처음에 완벽하게 설계하려 들지 마세요. 필요한 칸을 지금 다 모르는 것도, 14편처럼 중간에 칸이 느는 것도 정상이에요. 미리 정할 건 칸 목록이 아니라 어느 단계가 어느 단계에 무엇을 넘겨주는지예요.

중요꼭 기억할 것

빈 노드에서 지워지는 건 함수 안쪽뿐이에요. 첫날 고정한 규격(State 칸·실행 순서), 늘 끝까지 도는 상태, 로그로 보이는 진행도, 같은 이름으로 갈아 끼우는 장치는 끝까지 남아요.

나쁜 선택 vs 좋은 선택 — 빈 노드 속을 무엇으로 채우나

빈 노드는 리허설이에요. 접시에 뭘 담을지는 나중이고, 지금은 접시가 제자리에 있는지와 나오는 순서만 맞춰 한 바퀴 돌아보는 거죠. 그런데 빈 접시가 허전해서 "대충 비슷한 반찬"이라도 올려 두고 싶어져요. 코드에서는 몇 줄짜리 임시 규칙이 그 반찬이에요. 앞의 가짜 collect가 기사 9건을 채워 둔 상태에서, select 자리를 두 가지로 채워 볼게요.

나쁜 선택좋은 선택
무엇을 했나: 빈 select에 s["collected"][:5], 즉 "앞에서 다섯 건"이라는 임시 규칙을 한 줄 넣었어요. 들어온 값을 읽어서 결과를 만드는 코드예요.

무슨 일이 생기나: 로그가 ② 선별 9 → 5건으로 찍혀요. 바로 앞에서 "0에서 벗어난 줄 수가 곧 진행도"라고 했는데, 이 줄은 아직 안 만든 선별을 다 만든 것으로 세요. 게다가 picked에는 "그냥 앞에서 다섯 건"이 담기는데, 뒤쪽 노드를 만들 때는 그게 골라진 다섯 건인 줄 알고 짜게 돼요. 13편에서 진짜 선별로 바꾸면 picked의 성격이 달라지니, 이 한 줄만 지우는 게 아니라 그 한 줄을 믿고 짠 곳을 찾아다녀야 해요.		 무엇을 했나: picked를 빈 리스트로 두고 (빈 노드) 꼬리표가 붙은 로그 한 줄만 남겼어요. 모양 확인이 꼭 필요하면 고정 가짜 값을 쓰되, 어느 쪽이든 들어온 값을 읽지 않아요. 무엇이 들어오든 늘 같은 값이 나와요.

무슨 일이 생기나: 로그가 ② 선별 9 → 0건 (빈 노드)으로 찍혀요. 9건이 들어왔는데 0건이 나갔으니 안 채운 자리라는 게 줄에 그대로 보여요. 결과가 그럴듯하지 않으니 뒤쪽 노드도 이 값을 믿고 짤 수가 없고요. 13편에서는 같은 이름으로 함수를 통째로 다시 정의하면 끝이라, 걷어낼 임시 코드가 한 줄도 없어요.

두 선택을 가른 건 "가짜냐 진짜냐"가 아니라 들어온 값을 읽느냐예요. 읽지 않는 껍데기는 결과가 늘 같아서 아무도 진짜로 착각하지 않고, 지울 때도 함수 하나로 끝나요. 읽는 순간 결과가 그럴듯해지고, 그 그럴듯함에 뒤쪽 코드가 기대기 시작해요. 껍데기는 얇을수록 제 역할을 해요.

증상이 아직 없어도, AI에게 "이 노드를 진짜로 구현해 줘"라고 부탁한 직후라면 한 번 확인해요.

  • "collect를 RSS에서 기사 가져오게 바꿔 줘" — 돌려주는 키 이름이 Brief 선언과 같은지, 함수 이름이 collect 그대로인지
  • "여러 개를 동시에 처리하게 바꿔 줘" — collected나 picked에 Annotated[..., operator.add]가 덧붙지 않았는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
줄이는 단계를 지났는데 건수가 오히려 늘었어요. 9건을 5건으로 줄였을 텐데 14건이고, 목록 뒤쪽에 앞의 항목이 한 번 더 붙어 있어요. 에러는 없어요 class Brief에서 그 칸의 선언 줄이에요. 줄이는 노드의 [:5]는 범인이 아니에요. 함수는 5건을 제대로 돌려줬어요 그 칸의 len()을 찍고 앞부분이 뒤에서 반복되는지 봐요. 한 노드가 쓰고 다음이 읽는 칸이면 리듀서를 떼요 (리듀서는 두 칸에만)
노드가 돌았고 로그 줄도 찍혔는데, 다음 단계가 읽는 칸이 빈 리스트예요. 에러 문장은 한 줄도 없어요 그 노드의 return 딕셔너리 키 이름이에요. "picked"를 "pickd"처럼 한 글자만 틀려도 선언에 없는 이름이라, 제가 돌려 보니 에러 없이 버려지고 picked는 빈 채로 남았어요 print(run())으로 State 전체를 찍어 칸마다 건수를 보고, return의 키를 Brief 선언과 한 글자씩 대조해요 (State부터 정한다)
함수를 고쳐 다시 정의했는데 로그가 옛날 그대로라, 고친 함수만 계속 들여다보게 돼요 함수가 아니라 그래프를 부르는 줄이에요. app = build().compile()을 변수에 담아 두고 app.invoke()를 되풀이하는 셀이 있는지 봐요 run()을 불러 build()부터 다시 조립해요. 새 로그가 찍히면 함수는 멀쩡했던 거예요 (이름으로 찾는다)
draw_mermaid() 출력을 mermaid.live에 붙였는데 오른쪽 그림이 샘플 그대로예요. 저장·실행 버튼을 찾게 돼요 붙여 넣은 글자의 첫 줄이에요. ---가 빠졌거나 --로 잘렸는지, 출력 대신 파이썬 코드를 붙이지 않았는지 봐요 왼쪽 코드 칸 아래에 Syntax error가 떠 있는지 봐요. 첫 줄을 ---로 고치거나 설정 구역을 지우고 graph TD;부터 다시 붙여요 (그림으로 뽑는다)
실행하다가 TypeError: can only concatenate list (not "str") to list가 나요 노드가 log에 돌려주는 값이에요. [f"..."]처럼 대괄호로 감싸야 하는데 f"..." 글자만 돌려준 노드가 있어요. log는 리스트끼리 +로 잇는 칸이라 멈춘 거예요 노드마다 "log": 바로 뒤가 [로 시작하는지 훑어요. 제가 verify 하나만 대괄호를 빼고 돌렸을 때 이 문장이 그대로 나왔어요. 방금 새로 정의한 노드부터 봐요

이 프로젝트의 LangGraph State 선언과 노드 함수를 찾아서 표로 보여 줘. 아직 코드는 고치지 마.

  7. TypedDict — 딕셔너리에 어떤 키가 들어갈지 미리 적어 두는 파이썬 문법으로, 2편에서 State 선언에 처음 썼어요. ↩
  8. 리듀서(reducer) — 같은 칸에 값이 여러 번 들어올 때 덮어쓰지 않고 어떻게 합칠지 정한 규칙으로, 8편에서 처음 다뤘어요. ↩
  9. Mermaid — 상자와 화살표를 A --> B 같은 글자로 적으면 도구가 그림으로 바꿔 주는 다이어그램 문법이에요. ↩
