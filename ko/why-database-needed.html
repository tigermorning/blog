지난 시리즈에서 백엔드(눈에 안 보이는 주방)가 요청을 받아 처리하는 걸 봤어요. 그런데 한 가지가 빠져 있었어요 — 처리한 데이터를 대체 어디에 두는 걸까요? 지금까지 다뤘던 목업 데이터는 컴퓨터의 잠깐 기억(메모리)에만 있었어요. 그래서 껐다 켜거나 새로고침하면 사라졌어요. 서비스가 되려면 데이터가 남아 있어야 하는데, 그 "영구 창고"가 바로 오늘 다룰 데이터베이스(DB)예요.

도서관, 그리고 마법 장난감 상자

데이터베이스가 뭔지는 두 가지 그림이면 충분했어요. 첫째는 도서관이에요. 도서관에는 책이 수만 권 있지만 원하는 책을 금방 찾을 수 있어요. 데이터베이스 = 도서관, 데이터 = 책, 그걸 관리하는 소프트웨어 = 사서인 셈이에요. 둘째는 마법 장난감 상자예요. 장난감을 마구 넣어도, "파란색 자동차만 다 꺼내 줘"라고 하면 정리해서 딱 그것만 꺼내 줘요.

핵심은 이거예요 — 데이터베이스는 그냥 쌓아 두는 곳이 아니라, 원하는 것만 빠르게 찾아 주는 곳이라는 것. 저장 자체보다 "필요할 때 정확히 꺼낼 수 있다"는 게 진짜 가치였어요.

그럼 엑셀·메모장이랑 뭐가 다른가요

좋은 질문이었어요. 작을 때는 엑셀로도 충분해요. 하지만 데이터베이스는 세 가지가 달랐어요.

구분엑셀데이터베이스
규칙(스키마)아무 칸에나 아무 값이나 넣을 수 있음"이 표에는 이름·가격·분류가 들어간다"처럼 모양을 미리 정해 강제 — 데이터가 뒤죽박죽 섞이는 걸 막음
검색 속도데이터가 커지면 느려지고 멈춤수만 건에서도 순식간에 찾도록 애초에 설계됨
동시 사용여러 사람이 동시에 쓰면 충돌·덮어쓰기 위험여러 사람이 동시에 안전하게 씀 — 서비스에는 필수 조건

여기서도 마찬가지였어요. DB에 넣고 꺼내는 코드는 AI가 써줘요. 제가 판단할 건 "무엇을 어떤 모양으로 저장할지"와 "어떤 DB를 고를지"뿐이었어요.

세상에서 가장 큰 데이터베이스는 얼마나 클까

"데이터베이스가 크다"는 게 얼마나 큰 건지 감이 잘 안 왔는데, 두 가지 사례를 보고 확 와닿았어요. 미국 의회도서관은 세계에서 가장 큰 도서관으로, 책·사진·지도·녹음·필름 등 1억 7,800만 점 이상을 소장해요. 책장을 늘어놓으면 약 838마일이라고 하니, 서울에서 부산을 몇 번 왕복할 거리예요. 매일 약 1만 5천 점을 받아 1만여 점을 새로 소장하고, 디지털로 보존하는 자료만도 페타바이트(PB) 단위라고 해요.

CERN(유럽입자물리연구소)의 사례는 더 인상적이었어요. LHC 입자가속기의 검출기에서는 초당 약 10억 번의 입자 충돌이 일어나서, 이론상 초당 1페타바이트의 데이터가 쏟아진다고 해요. 그런데 이걸 다 저장하는 게 아니라 '트리거'라는 장치가 의미 있는 극소수(1%도 안 되는 양)만 골라 저장해요. 그렇게 걸러 저장해도 CERN의 데이터 저장 용량은 2023년에 1엑사바이트(100만 테라바이트)를 넘어섰대요. 여기서 제가 배운 건, 데이터가 클수록 "무엇을 저장할지 고르는 일"이 저장장치 크기만큼 중요해진다는 거였어요.

재미있는 건, 예전엔 "얼마나 크냐"로 기술력을 자랑했지만 요즘은 클라우드 덕분에 저 같은 비전공자도 이런 거대한 기술을 무료로 조금씩 빌려 쓸 수 있다는 점이에요. 규모의 문제가 아니라, 이제는 누구나 쓸 수 있는 도구가 된 거예요. 다음 글에서는 이 데이터베이스가 왜 이렇게 종류가 많은지, 60년에 걸친 역사를 따라가볼게요.

이럴 때 의심하세요 — AI가 만든 저장 기능에서 데이터가 사라지거나 뒤섞일 때

데이터를 어디에 어떻게 두느냐의 문제는 혼자 테스트할 때 거의 안 드러나요. 서버를 다시 켜는 날, 두 사람이 동시에 쓰는 날, 데이터가 쌓여 정렬해 보는 날에 드러나요. AI에게 "저장되게 해 줘"라고만 하면 DB 없이 변수나 파일에 담는 코드가 나오기도 해서, 저장이 "된다"는 것만으로는 안심하기 일러요.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
새로고침해도 잘 남던 데이터가 서버를 껐다 켜거나 다시 배포한 뒤 전부 사라져요. 무료 호스팅에서는 한동안 안 쓴 뒤에 사라지기도 해요 서버 코드에서 받은 데이터를 넣는 줄이에요. 파일 위쪽의 let posts = [] 같은 변수에 push하고 있는지 봐요 내 컴퓨터에서 서버 터미널을 Ctrl + C로 끄고 다시 켜 봐요. 사라지면 잠깐 기억(메모리)에만 둔 거예요. 무료 서버가 잠들었다 깨는 것도 다시 켜는 것과 같아요 (배포 편의 이 줄)
두 사람이 거의 동시에 등록했는데 하나만 남아요. 혼자 테스트할 때는 한 번도 안 생겨요 저장 코드가 data.json 같은 파일이나 시트를 통째로 읽고 → 고치고 → 통째로 다시 쓰는 모양인지 봐요 그런 모양이면 두 요청이 같은 옛 내용을 읽고 서로 덮어썼을 수 있어요. 혼자서는 재현하기 어려우니 코드 모양으로 판단하고, 여러 사람이 쓰는 기능이면 동시 사용을 처리해 주는 데이터베이스로 옮겨요
가격순으로 정렬했더니 10,000원이 2,000원보다 앞에 와요. 합계가 안 맞거나 날짜 모양이 제각각인 줄도 보여요 저장된 원래 값이에요. 시트나 JSON 파일을 열어 같은 칸에 10000, 1만, 10,000원처럼 모양이 섞였는지 봐요 숫자 칸에 글자가 섞이면 글자 순서로 정렬돼서 이렇게 돼요. 입력받을 때 숫자만 들어가게 막고, 데이터베이스로 옮길 땐 칸마다 모양(숫자·날짜)을 정해 달라고 해요 (표 설계 편)

새로고침만 해도 사라진다면 서버까지 가지도 않았을 수 있어요. 그때는 목업 편의 이 줄부터, 다른 브라우저에서만 안 보인다면 서버 편의 이 줄부터 봐요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 서버 코드가 있는 프로젝트 폴더에서

이 프로젝트에서 사용자가 입력한 데이터를 저장하는 곳을 전부 찾아서 표로 보여 줘.
한 곳마다 파일 이름, 줄 번호, 어떤 데이터인지, 어디에 저장하는지(서버 코드 안의 변수, JSON 같은 파일, 스프레드시트, 데이터베이스) 적어 줘.
파일이나 시트를 통째로 읽고 다시 쓰는 곳, 숫자나 날짜여야 할 값을 글자로 저장하는 곳은 따로 표시해 줘. 아직 코드는 고치지 마.
