정적 Pages에 배포한 챗봇 주소에서 질문을 보내면, 화면은 공개돼도 Ollama(내 컴퓨터에서 모델을 돌려 주는 로컬 실행 프로그램) 호출이 막힐 수 있다. "정적 파일을 배포하면 서버가 로컬 모델 호출을 대신할 것"이라는 짐작은 틀렸다. 배포된 앱은 사용자 컴퓨터의 브라우저에서 실행되고, 브라우저는 여전히 그 컴퓨터의 로컬 엔진을 직접 호출한다. 이 실행 경계를 먼저 확인한 뒤에야 프롬프트가 어떤 근거로 답해야 하는지도 정할 수 있었다.

1. buildPrompt() — 근거 원칙을 문장으로 고정하기

검색된 청크를 단순히 이어 붙이는 것만으로는 모델이 자료 밖 내용을 보태지 않도록 제한할 수 없다. buildPrompt()는 먼저 자료가 모두콘의 공개 문서 청크라는 소개를 두고, 이어서 근거 원칙을 명시하며, 답 안에 근거 청크의 [ID]를 표시하도록 요구한다. 상대 시각을 묻는 질문을 해석할 수 있도록 KST 현재 시각을 넣고, 그 뒤에만 [자료]와 [질문]을 배치한다.

개념 설명용 코드 — buildPrompt()가 조립하는 프롬프트 구조 예시, 직접 실행하는 코드 아니에요

다음 자료는 모두의연구소의 컨퍼런스 '모두콘'에 대한 공개 문서에서 뽑은 조각입니다.
주의: 검색된 조각의 유사도가 낮습니다. 질문과 완전히 맞는 근거가 아닐 수 있으니, 근거에 있는 내용만 짧게 답하고 자료에 없는 부분은 없다고 말합니다.
근거가 된 조각의 [ID]를 답 안에서 표시합니다.
현재 시각은 [KST 시각]입니다. '지금', '올해', '다음 주' 같은 상대 표현은 이 시각을 기준으로 해석합니다.

[자료]
[MC-... | 섹션] 청크 텍스트

[질문]
사용자 질문

이 순서는 모델의 능력을 높이는 주문이 아니라, 모델이 어떤 범위에서 답하고 무엇을 인용해야 하는지를 문장으로 고정하는 계약이다. 청크마다 MC-xxx 형식 ID와 section을 보존하면 사용자는 답변 문장을 원문 청크까지 되짚을 수 있고, 모델도 막연한 "자료에 따르면" 대신 검토 가능한 근거를 남긴다. 최고 검색 점수가 0.55보다 낮을 때는 더 엄격한 분기 문구가 필요하다 — 검색 결과가 존재한다는 사실과 질문에 맞는 근거라는 사실을 구별해, 모델이 빈틈을 상식으로 메우지 못하게 한다.

2. Ollama 응답은 한 번에 받지 않고 조각으로 읽는다

로컬 엔진은 POST http://localhost:11434/api/chat으로 qwen3.5:2b에 요청하며, 본문에는 stream:true와 think:false를 담는다. 스트리밍 응답은 한 개의 완성 JSON이 아니라 줄바꿈으로 구분된 JSON 조각이라, ReadableStream을 읽어 남은 문자열을 보관하고 줄 단위로 파싱한 뒤 각 조각의 텍스트를 화면 답변에 이어 붙여야 한다.

개념 설명용 코드 — 앱 내부 구현 일부, 직접 실행하는 코드 아니에요

await fetch("http://localhost:11434/api/chat", {
  method: "POST",
  signal: controller.signal,
  body: JSON.stringify({
    model: "qwen3.5:2b", stream: true, think: false, messages,
  }),
});

이 구조에서는 토큰당 약 50ms라는 응답 감각을, 사용자가 빈 화면이 아니라 자라나는 문장으로 경험할 수 있다. 네트워크 오류와 JSON 파싱 실패는 답변 상태와 분리해 표시하고, 요청을 취소할 때는 AbortSignal을 전달해 이미 시작한 스트림을 멈춘다. 스트리밍은 속도 과시가 아니라, 생성 중이라는 상태와 취소할 권리를 사용자에게 드러내는 인터페이스다.

3. 연결 상태와 CORS를 배포 환경까지 확인한다

채팅을 시작하기 전 GET /api/tags로 Ollama 상태를 확인하면, 모델이 꺼진 상황을 생성 실패처럼 보이지 않게 안내 배너와 재시도 동작으로 분리할 수 있다. 로컬 개발 서버에서 되던 요청도 GitHub Pages 배포 뒤에는 자동으로 해결되지 않는다. 정적 페이지가 서버를 대신해 호출하는 게 아니라 사용자 브라우저가 계속 자신의 localhost:11434로 요청하기 때문에, Ollama의 OLLAMA_ORIGINS 설정이 필요하다.

실행: 로컬 터미널

# macOS
launchctl setenv OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# Windows
setx OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# systemd 환경
systemctl set-environment OLLAMA_ORIGINS="https://YOUR_ID.github.io"

운영체제별 설정 뒤에는 앱을 재시작해야 하고, 실제 Pages 주소에서 상태 확인과 스트리밍을 함께 점검해야 한다. Chrome과 Edge를 권장하고, Safari에서는 Ollama 연결과 임베딩 WASM이 불안정할 수 있음을 시작 화면에 명시하는 편이 좋다. 연결 상태 배너와 재시도 동작을 남겨두면, 사용자 컴퓨터에서 로컬 엔진이 꺼져 있거나 출처 허용이 빠졌을 때 이를 검색이나 프롬프트 실패로 오해하지 않게 된다. 배포 주소와 로컬 엔진 사이의 경계를 화면에 드러내는 일은 사용자가 자신의 환경에서 점검할 조건을 알게 하는 제품의 책임이다.

4. 실습 — 챗봇 UI의 상태를 에이전트에게 명세하기

UI는 입력창과 답변 말풍선만으로 완성되지 않는다. 로컬 엔진 선택 상태, Ollama 연결 여부, 임베딩 준비 상태, 검색 진행 상태, 생성 중지 동작, 출처 칩, 약한 근거 경고를 통해 사용자가 현재 답이 어느 단계에 있는지 읽을 수 있어야 한다. 스트리밍이 중단되어도 이미 받은 답변 청크를 지우지 않고, 출처 칩은 ID·section·검색 방법·점수를 보여주며 원문으로 연결할 수 있게 요구했다.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

Vite, React, TypeScript로 모두콘 RAG 챗봇 UI 골격을 만듭니다.
로컬 qwen3.5:2b 엔진 선택, GET /api/tags 연결 상태 배너와 재시도,
임베딩·하이브리드 검색·생성 단계 표시, 스트리밍 답변과 AbortSignal 중지 버튼을 구현합니다.
각 답변에는 출처 칩을 표시하고 칩에는 MC ID, section, vector 또는 bm25 방법, 점수를 보입니다.
최고 유사도가 0.55보다 낮으면 약한 근거 경고를 보이며, 스트리밍 오류가 나도
이미 받은 답변과 출처는 유지합니다. Chrome과 Edge 권장, Safari 불안정 안내도 포함합니다.

이 구조는 답변의 신뢰를 배지 하나에 맡기지 않고, 사용자가 근거와 과정을 직접 확인할 수 있게 만든다.

정리

오늘 확인한 건 결국 두 층의 분리였다 — 배포 환경의 연결 조건(어디서 Ollama를 부르는가)과 답변 근거의 조건(무엇을 근거로 답할 수 있는가)은 서로 다른 층에서 검증해야 한다는 것. 다음 편에서는 이렇게 나온 답변을 사람이 매번 읽지 않고도 판정할 수 있게, 답변 뒤에 심사위원 하나를 더 두는 LLM-as-a-Judge로 넘어간다.

이럴 때 의심하세요 — 배포한 챗봇이 답을 안 주거나 엉뚱하게 답할 때

이 단계의 문제는 두 층으로 갈린다. 답이 아예 안 오는가(연결 층), 아니면 답은 오는데 자료 밖 이야기를 하는가(근거 층). 두 층은 열어 볼 자리가 전혀 다르니, 증상부터 어느 쪽인지 가르고 들어간다.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
로컬에서는 잘 되던 챗봇이 배포한 주소에서만 답을 못 받아 온다. 콘솔에는 요청이 막혔다는 메시지가 뜨는데 다른 화면은 멀쩡하다 앱 코드가 아니라 Ollama를 켜는 쪽의 환경 변수 OLLAMA_ORIGINS다. 배포해도 서버가 대신 호출해 주는 게 아니라 사용자 브라우저가 계속 자기 localhost:11434를 부르기 때문이다 배포 주소를 OLLAMA_ORIGINS에 넣고 앱을 재시작한 뒤 실제 배포 주소에서 다시 연다. 로컬 개발 서버에서 되던 건 아무 증거가 안 된다. Safari는 연결과 임베딩이 불안정할 수 있으니 Chrome·Edge로 먼저 확인한다
질문을 넣으면 답이 영영 안 나오거나 생성 실패처럼 보이는데, 검색과 프롬프트를 아무리 고쳐도 그대로다 채팅을 시작하기 전 GET /api/tags로 연결을 확인하는 부분과, 그 결과를 보여주는 배너다 먼저 Ollama가 켜져 있는지 본다. 꺼져 있었다면 코드 문제가 아니다. 그리고 연결 실패를 생성 실패와 같은 화면으로 보여주고 있지 않은지 확인해, 배너와 재시도로 갈라 놓는다 — 안 그러면 다음에도 검색·프롬프트부터 뒤지게 된다
답변 안에 자료에 없는 날짜나 설명이 자연스럽게 섞여 있다. 출처 표시가 없거나 엉뚱한 ID가 붙어 있다 buildPrompt()가 조립한 최종 문자열이다. 자료를 붙이기 전에 근거 원칙과 [ID] 표시 규칙이 문장으로 들어가 있는지 본다 실제로 모델에 보낸 프롬프트를 그대로 찍어 읽는다. 청크만 이어 붙어 있고 "근거에 있는 내용만 답한다", "근거 조각의 [ID]를 표시한다" 같은 문장이 없으면 모델을 탓할 일이 아니다. 자료를 붙이는 것만으로는 범위가 안 잠긴다
자료 범위 밖 질문에도 챗봇이 자신 있게 답한다. 화면에 약한 근거 경고는 안 뜬다 최고 유사도를 0.55와 비교하는 분기와, 그때 프롬프트에 덧붙이는 문구다 자료와 상관없는 질문("내일 날씨")을 넣고 그때의 최고 점수를 찍어 본다. 0.55보다 낮은데 프롬프트가 평소와 똑같다면 보수화 분기가 안 걸린 것이다. 검색 결과가 있다는 사실과 질문에 맞는 근거다는 사실은 다르다

위 두 줄은 연결 층, 아래 두 줄은 근거 층이다. 답이 아예 안 오는데 프롬프트를 고치거나, 답이 이상한데 OLLAMA_ORIGINS를 만지는 게 이 단계에서 시간을 가장 많이 먹는 길이다.
