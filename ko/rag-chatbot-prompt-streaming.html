프롬프트는 근거의 경계다 — 프롬프트 조립과 로컬 LLM 스트리밍

정적 Pages(파일만 그대로 내려 주는 무료 호스팅)에 챗봇을 올린 주소에서 질문을 보내 볼게요. 화면은 누구에게나 보이지만, Ollama(내 컴퓨터에서 모델을 돌려 주는 로컬 실행 프로그램)를 부르는 일은 막힐 수 있어요. "파일을 올리면 서버가 로컬 모델 호출을 대신해 주겠지"라는 짐작은 틀렸어요. 배포된 앱은 사용자 컴퓨터의 브라우저에서 실행되고, 브라우저는 여전히 그 컴퓨터의 로컬 엔진을 직접 호출한다. 이 실행 경계를 먼저 확인한 뒤에야 프롬프트가 어떤 근거로 답해야 하는지도 정할 수 있었다.

1. buildPrompt() — 근거 원칙을 문장으로 고정하기

검색된 청크(자료를 잘라 놓은 조각)를 이어 붙이기만 해서는 모델이 자료 밖 내용을 보태는 걸 막을 수 없다. 그래서 buildPrompt()(프롬프트, 곧 모델에게 보낼 글을 만드는 함수)는 순서를 정해 쓴다. 먼저 자료가 모두콘의 공개 문서 청크라고 소개한다. 다음으로 근거 원칙을 쓰고, 답 안에 근거 청크의 [ID]를 표시하라고 요구한다. 그리고 "지금", "다음 주" 같은 말을 풀 수 있도록 KST(한국 표준시) 현재 시각을 넣는다. 맨 뒤에 [자료]와 [질문]을 놓는다.

아래 상자는 읽기만 해도 돼요. 이 함수가 만들어 내는 글의 모양이에요.

개념 설명용 코드 — buildPrompt()가 조립하는 프롬프트 구조 예시, 직접 실행하는 코드 아니에요

다음 자료는 모두의연구소의 컨퍼런스 '모두콘'에 대한 공개 문서에서 뽑은 조각입니다.
주의: 검색된 조각의 유사도가 낮습니다. 질문과 완전히 맞는 근거가 아닐 수 있으니, 근거에 있는 내용만 짧게 답하고 자료에 없는 부분은 없다고 말합니다.
근거가 된 조각의 [ID]를 답 안에서 표시합니다.
현재 시각은 [KST 시각]입니다. '지금', '올해', '다음 주' 같은 상대 표현은 이 시각을 기준으로 해석합니다.

[자료]
[MC-... | 섹션] 청크 텍스트

[질문]
사용자 질문

이 순서는 모델의 능력을 높이는 주문이 아니라, 모델이 어떤 범위에서 답하고 무엇을 인용해야 하는지를 문장으로 고정하는 계약이다. 청크마다 MC-xxx 형식 ID와 section을 보존하면 사용자는 답변 문장을 원문 청크까지 되짚을 수 있고, 모델도 막연한 "자료에 따르면" 대신 검토 가능한 근거를 남긴다. 최고 검색 점수가 0.55보다 낮을 때는 더 엄격한 문구를 덧붙인다. 검색 결과가 있다는 것과 질문에 맞는 근거라는 것은 다른 사실이기 때문이다. 이렇게 해서 모델이 빈틈을 상식으로 메우지 못하게 한다.

2. Ollama 응답은 한 번에 받지 않고 조각으로 읽는다

로컬 엔진에는 POST http://localhost:11434/api/chat 주소로 qwen3.5:2b 모델에게 요청을 보낸다(localhost는 "지금 쓰는 내 컴퓨터"라는 뜻의 주소예요). 요청 본문에는 stream:true(답을 조금씩 보내 달라)와 think:false(생각 과정은 빼 달라)를 담는다.

스트리밍 응답(답이 만들어지는 대로 조금씩 도착하는 응답)은 완성된 JSON(데이터를 적는 약속된 글 모양) 하나가 아니다. 줄바꿈으로 나뉜 JSON 조각이 이어서 온다. 그래서 ReadableStream(조금씩 도착하는 데이터를 읽는 도구)으로 읽는다. 먼저 줄이 덜 끝난 남은 글자를 보관한다. 다음으로 한 줄씩 해석한다. 마지막으로 각 조각의 글자를 화면 답변 뒤에 이어 붙인다.

아래 코드는 요청을 보내는 부분이에요. 읽기만 해도 돼요.

개념 설명용 코드 — 앱 내부 구현 일부, 직접 실행하는 코드 아니에요

await fetch("http://localhost:11434/api/chat", {
  method: "POST",
  signal: controller.signal,
  body: JSON.stringify({
    model: "qwen3.5:2b", stream: true, think: false, messages,
  }),
});

이렇게 하면 토큰(모델이 글을 세는 작은 단위) 하나에 약 50ms라는 속도를, 사용자가 빈 화면이 아니라 자라나는 문장으로 보게 된다. 네트워크 오류와 JSON 해석 실패는 답변과 따로 표시한다. 요청을 취소할 때는 AbortSignal("그만" 신호)을 넘겨 이미 시작한 스트림을 멈춘다. 스트리밍은 속도 과시가 아니라, 생성 중이라는 상태와 취소할 권리를 사용자에게 드러내는 인터페이스다.

3. 연결 상태와 CORS를 배포 환경까지 확인한다

CORS는 다른 주소의 웹페이지가 내 컴퓨터의 Ollama를 부르는 걸 브라우저가 기본으로 막는 규칙이다(자세한 설명). 채팅을 시작하기 전에 GET /api/tags로 Ollama가 켜져 있는지 먼저 물어본다. 그러면 모델이 꺼진 상황을 생성 실패와 따로 보여 줄 수 있다. 안내 배너와 재시도 버튼으로 알려 주는 식이다.

로컬 개발 서버에서 되던 요청도 GitHub Pages에 올린 뒤에는 저절로 해결되지 않는다. 서버가 대신 호출해 주는 게 아니라, 사용자 브라우저가 계속 자기 localhost:11434로 요청하기 때문이다. 그래서 Ollama 쪽에 OLLAMA_ORIGINS(이 주소에서 오는 요청은 받아 달라는 설정값, 환경 변수)를 넣어야 한다. 여기서 막히는 게 정상이에요.

아래 명령은 내 컴퓨터의 터미널에서 직접 해 보는 거예요. 자기 운영체제에 맞는 한 줄만 쓰면 돼요.

실행: 로컬 터미널

# macOS
launchctl setenv OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# Windows
setx OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# systemd 환경
systemctl set-environment OLLAMA_ORIGINS="https://YOUR_ID.github.io"

운영체제별 설정 뒤에 확인할 것은 세 가지다.

  • 설정이 적용되도록 앱을 재시작한다.
  • 실제 Pages 주소에서 상태 확인과 스트리밍을 함께 점검한다.
  • Chrome과 Edge를 권장한다. Safari에서는 Ollama 연결과 임베딩(문장을 숫자 좌표로 바꾸는 일) WASM(브라우저 안에서 빠르게 도는 프로그램 형식)이 불안정할 수 있다. 이 내용을 시작 화면에 적어 두는 편이 좋다.

연결 상태 배너와 재시도 버튼을 남겨 두면, 로컬 엔진이 꺼져 있거나 출처 허용이 빠졌을 때 사용자가 이를 검색이나 프롬프트 실패로 오해하지 않는다. 배포 주소와 로컬 엔진 사이의 경계를 화면에 드러내는 일은 사용자가 자신의 환경에서 점검할 조건을 알게 하는 제품의 책임이다.

4. 실습 — 챗봇 UI의 상태를 에이전트에게 명세하기

UI(화면)는 입력창과 답변 말풍선만으로 끝나지 않는다. 사용자가 지금 답이 어느 단계에 있는지 읽을 수 있어야 한다. 그래서 아래 상태를 화면에 보이게 했다.

  • 로컬 엔진 선택 상태, Ollama 연결 여부
  • 임베딩 준비 상태, 검색 진행 상태
  • 생성 중지 버튼, 출처 칩(근거를 알려 주는 작은 표), 약한 근거 경고

스트리밍이 중단돼도 이미 받은 답변은 지우지 않는다. 출처 칩은 ID·section·검색 방법·점수를 보여 주고 원문으로 이어지게 요구했다.

아래 글은 코딩 에이전트에게 그대로 붙여 넣는 부탁 글이에요. 직접 해 보세요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등

Vite, React, TypeScript로 모두콘 RAG 챗봇 UI 골격을 만듭니다.
로컬 qwen3.5:2b 엔진 선택, GET /api/tags 연결 상태 배너와 재시도,
임베딩·하이브리드 검색·생성 단계 표시, 스트리밍 답변과 AbortSignal 중지 버튼을 구현합니다.
각 답변에는 출처 칩을 표시하고 칩에는 MC ID, section, vector 또는 bm25 방법, 점수를 보입니다.
최고 유사도가 0.55보다 낮으면 약한 근거 경고를 보이며, 스트리밍 오류가 나도
이미 받은 답변과 출처는 유지합니다. Chrome과 Edge 권장, Safari 불안정 안내도 포함합니다.

이 구조는 답변의 신뢰를 배지 하나에 맡기지 않고, 사용자가 근거와 과정을 직접 확인할 수 있게 만든다.

정리

오늘 확인한 건 결국 두 층의 분리였다 — 배포 환경의 연결 조건(어디서 Ollama를 부르는가)과 답변 근거의 조건(무엇을 근거로 답할 수 있는가)은 서로 다른 층에서 검증해야 한다는 것. 다음 편에서는 이렇게 나온 답변을 사람이 매번 읽지 않고도 판정할 수 있게, 답변 뒤에 심사위원 하나를 더 두는 LLM-as-a-Judge로 넘어간다.

이럴 때 의심하세요 — 배포한 챗봇이 답을 안 주거나 엉뚱하게 답할 때

이 단계의 문제는 두 층으로 갈린다. 답이 아예 안 오는가(연결 층), 아니면 답은 오는데 자료 밖 이야기를 하는가(근거 층). 두 층은 열어 볼 자리가 전혀 다르니, 증상부터 어느 쪽인지 가르고 들어간다.

이런 증상이 보이면먼저 열어 볼 자리확인 방법
로컬에서는 잘 되던 챗봇이 배포한 주소에서만 답을 못 받아 온다. 콘솔에는 요청이 막혔다는 메시지가 뜨는데 다른 화면은 멀쩡하다 앱 코드가 아니라 Ollama를 켜는 쪽의 환경 변수 OLLAMA_ORIGINS다. 배포해도 서버가 대신 호출해 주는 게 아니라 사용자 브라우저가 계속 자기 localhost:11434를 부르기 때문이다 배포 주소를 OLLAMA_ORIGINS에 넣고 앱을 재시작한 뒤 실제 배포 주소에서 다시 연다. 로컬 개발 서버에서 되던 건 아무 증거가 안 된다. Safari는 연결과 임베딩이 불안정할 수 있으니 Chrome·Edge로 먼저 확인한다
질문을 넣으면 답이 영영 안 나오거나 생성 실패처럼 보이는데, 검색과 프롬프트를 아무리 고쳐도 그대로다 채팅을 시작하기 전 GET /api/tags로 연결을 확인하는 부분과, 그 결과를 보여주는 배너다 먼저 Ollama가 켜져 있는지 본다. 꺼져 있었다면 코드 문제가 아니다. 그리고 연결 실패를 생성 실패와 같은 화면으로 보여주고 있지 않은지 확인해, 배너와 재시도로 갈라 놓는다 — 안 그러면 다음에도 검색·프롬프트부터 뒤지게 된다
답변 안에 자료에 없는 날짜나 설명이 자연스럽게 섞여 있다. 출처 표시가 없거나 엉뚱한 ID가 붙어 있다 buildPrompt()가 조립한 최종 문자열이다. 자료를 붙이기 전에 근거 원칙과 [ID] 표시 규칙이 문장으로 들어가 있는지 본다 실제로 모델에 보낸 프롬프트를 그대로 찍어 읽는다. 청크만 이어 붙어 있고 "근거에 있는 내용만 답한다", "근거 조각의 [ID]를 표시한다" 같은 문장이 없으면 모델을 탓할 일이 아니다. 자료를 붙이는 것만으로는 범위가 안 잠긴다
자료 범위 밖 질문에도 챗봇이 자신 있게 답한다. 화면에 약한 근거 경고는 안 뜬다 최고 유사도를 0.55와 비교하는 분기와, 그때 프롬프트에 덧붙이는 문구다 자료와 상관없는 질문("내일 날씨")을 넣고 그때의 최고 점수를 찍어 본다. 0.55보다 낮은데 프롬프트가 평소와 똑같다면 보수화 분기가 안 걸린 것이다. 검색 결과가 있다는 사실과 질문에 맞는 근거다는 사실은 다르다

위 두 줄은 연결 층, 아래 두 줄은 근거 층이다. 답이 아예 안 오는데 프롬프트를 고치거나, 답이 이상한데 OLLAMA_ORIGINS를 만지는 게 이 단계에서 시간을 가장 많이 먹는 길이다.
