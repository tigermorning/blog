맡길 일부터 관찰까지 — 하네스 보는 법 (1)

2026. 9. 2.

※ 이 글은 모두의연구소 학습 과정에서 배운 내용을 제 나름의 언어로 재구성한 것입니다.

예전 시리즈에서 모델은 요청 문장만 쓰고, 그 요청을 검증·실행하는 프로그램이 하네스라는 걸 봤어요. 이번엔 그 하네스를 실제로 여러 개 놓고 어떻게 비교할지를 다뤘어요. Claude Code, opencode처럼 이미 익숙한 도구를 놓고, "이 도구가 뭘 지원하나"를 기능표로 비교하기 전에 "내가 맡길 일이 어디서 막히는가"부터 화면에서 직접 관찰하는 법이에요.

도구 이름부터 고르면 안 되는 이유

"이 도구가 반성 기능이 있나, 저 도구는 컨텍스트 관리가 되나" — 기능 목록부터 비교하면 그럴듯한 표는 만들어지지만, 정작 내가 맡길 일에 맞는지는 안 보여요. 예를 들어 "반복되는 오류 원인을 모으는 일"을 맡긴다고 하면, 그 안에도 서로 다른 위험이 섞여 있어요. 요청을 받고 관련 파일을 읽는 일과, 읽은 내용을 바탕으로 실제 변경을 실행하는 일은 전혀 다른 위험이에요. 그런데 "오류 원인을 정리해줬다"는 결과 문장만 보면 이 둘의 차이가 사라져요. 그래서 도구 이름보다 먼저, 내가 맡길 일이 어디서 막히는지부터 물어야 한다는 걸 배웠어요.

하네스가 감싸고 있는 건 결국 하나의 순환이다

모델의 답변 능력만으로는 도구 사이의 차이를 설명할 수 없어요. 같은 모델이라도 행동을 적는 형식, 남겨 둘 문맥, 허용된 권한이 다르면 전혀 다른 결과를 내거든요. 그 차이가 나는 자리를 그림으로 그리면 이래요.

일곱 가지 병목 질문 — 기능 지도

이 순환 위에서 맡긴 일이 막힐 수 있는 자리는 크게 일곱이었어요. 등급표가 아니라, 내 일이 왜 막혔는지 되짚는 질문 목록이라고 보면 돼요.

병목물어야 할 질문
행동 포맷모델이 행동을 적고 도구가 그걸 읽는 문법이, 실패하기 어렵게 짜여 있나?
컨텍스트 관리긴 작업에서 무엇을 남기고 무엇을 줄일지 정해져 있나?
경험·스킬 축적한 번 해결한 일을 다음 작업에 다시 쓸 수 있나?
반성(Reflexion)실행 결과를 보고 다음 행동을 고치되, 틀린 교훈까지 쌓지는 않나?
단순성필요한 구성만 남아서 운영 부담이 적나?
권한과 보안읽기·수정·실행의 경계와 승인 방식이 정해져 있나?
평가 루프결과가 맞았는지 무슨 근거로 확인하나?

순서도 정해져 있어요. 먼저 내 일이 어디서 막히는가(행동이 애매한가, 문맥이 넘치는가, 경험이 재사용 안 되는가, 승인이 많은가, 결과를 증명할 길이 없는가)를 묻고, 그다음 그 병목을 줄일 기능이 뭔가를 묻고, 마지막으로 그 기능이 실제로 작동했다는 기록을 어디서 볼 수 있나를 물어요. 제품 소개 문구를 읽기 전에 이 세 질문을 먼저 던지면, 맡길 일의 경계가 먼저 드러나요.

여섯 칸 관찰 카드 — 같은 잣대로 기록하기

기능 지도가 "무엇이 문제인가"를 묻는 질문이라면, 관찰 카드는 화면과 문서를 같은 틀로 기록하는 도구예요. 기능 지도에서 컨텍스트 관리가 중요하다고 판단했더라도, 카드에는 그게 실제 화면에서 어떻게 보이는지를 적어요.

칸관찰할 내용
입구요청이 들어가는 화면, 명령, 연결 지점
상태세션·대화·작업 기록이 남는 위치
대표 행동읽기·검색·수정·실행 가운데 화면에서 실제로 확인한 행동
권한 경계읽기 밖의 행동 전에 승인이나 제한이 보이는지
1차 근거실행 기록·설정·공식 문서처럼 나중에 다시 열 수 있는 근거
한계이번 관찰만으로는 확인하지 못한 범위

화면에서 찾아야 할 다섯 신호

실습은 읽기 전용 과업 하나면 충분해요 — 작업 폴더의 파일 목록을 읽거나 공개 문서 한 건을 요약하는 정도로요. 결과가 잘 나왔는지를 보는 시간이 아니라, 요청이 들어가는 입구와 실행의 경계를 화면에서 찾는 시간이라는 게 핵심이에요.

관찰에 쓸 자료는 매번 같은 것이어야 해요. 자료가 바뀌면 화면에서 달라진 게 도구 때문인지 자료 때문인지 구분할 수 없거든요. 그래서 내용이 알려진 작은 텍스트 파일 한 건처럼, 시험할 때마다 똑같이 준비해 둔 자료(fixture)를 씁니다. 비밀값이나 실제 저장소는 이 관찰의 대상이 아니에요.

이 조건 위에서 화면에 나타나는 다섯 신호를 찾아요.

  1. 입력 위치 — 요청 문장이 들어가는 자리
  2. 도구 호출 표시 — 파일 읽기·검색 같은 행동을 화면이 알리는 방식
  3. 관측 축약 — 긴 출력 일부를 접거나 요약하는 표시가 있는지
  4. 기록 위치 — 대화·세션 목록·로그 가운데 실행 결과가 실제로 남는 곳
  5. 승인 신호 — 읽기 밖의 행동 전에 뜨는 승인 창, 허용 선택지, 권한 안내

①·②는 행동 포맷이 화면에서 어떤 순서와 단위로 드러나는지를, ③·④는 컨텍스트 관리와 경험·반성에 남을 흔적을, ⑤는 권한과 보안의 경계를 보여줘요. 화면에 실제로 보이지 않으면 "확인하지 못했다"고 남기고, 넘겨짚지 않아요.

시범 — Claude Code 화면 한 바퀴

강의가 든 시범은 이래요. Claude Code CLI로 새 작업 폴더를 열고, 그 안에는 공개 문서 하나를 받아 둔 텍스트 파일 한 건만 넣어요. 이 상태에서 "이 폴더의 파일 목록을 보여 줘"라고 요청하면 네 단계가 화면에 순서대로 남아요.

  1. 요청 — 입력한 문장이 대화 흐름 안에, 응답 본문과 구분되어 표시된다.
  2. 도구 호출 — 응답이 만들어지는 동안 어떤 도구를 불렀는지가 화면에 뜬다. 이 시범에서는 공식 문서가 안내하는 전용 파일탐색 도구 대신, 셸 명령(ls -la)이 화면에 나타났다 — 즉 도구를 고른 주체가 모델의 판단이었다는 게 드러난 것이다.
  3. 결과 — 명령의 원본 출력이 그대로 돌아와, 이후 세션 기록에 남는다.
  4. 요약 — 모델이 그 원본 결과를 읽고 사람이 읽을 문장으로 정리한다.

이 요청은 읽기만 했기 때문에 승인 창은 뜨지 않았어요. 이걸 그대로 관찰 카드에 옮기면 이런 한 줄 기록이 나와요.

칸이번 관찰
입구대화창 — 요청과 응답이 구분되어 표시됨
대표 행동셸 명령(ls -la)으로 파일 목록 조회 — 도구는 모델이 골랐다
1차 근거세션에 요청부터 요약까지 순서대로 남음
권한 경계이 읽기 요청에는 승인 창이 없었음
한계설정 파일의 허용 규칙은 열어 보지 않아 미확인

사실과 해석을 가르는 법

여기서 아직 쓰면 안 되는 문장이 하나 있어요. "이 도구는 읽기가 안전하다"는 문장이에요. 안전을 판정하려면 권한 규칙까지 열어봐야 하는데, 이번 관찰은 화면에 보인 것만 봤을 뿐 그 규칙까지는 확인하지 않았거든요. 그래서 기록에는 "파일 목록 요청에 승인 없이 읽기가 실행되었다. 관측한 사실: 화면의 파일 목록. 미확인: 설정 파일의 권한 규칙"처럼, 본 것과 아직 못 본 것을 나눠 적어요. 짧은 실행 한 번으로 도구 전체를 판정하지 않고, 어디까지 확인됐고 어디부터 비어 있는지를 구분하는 게 이 관찰의 결과예요.

이 두 걸음은 모두의연구소의 "에이전트 하네스 톺아보기" 프로젝트 열두 강 가운데 앞 두 강이에요. 도구 이름부터 고르지 않고 막히는 자리부터 본다는 원칙 하나만 챙겨도, 다음에 새 에이전트 도구를 써 볼 때 무엇부터 확인해야 할지가 한결 또렷해져요. 다음 편부터는 이 틀 위에서 일곱 병목을 하나씩 실제 연구와 도구 사례로 깊이 들어가요.

함께 읽으면 좋은 글: 에이전트가 도구를 쥔다는 것 — 모델·하네스·루프, 안전하게 쓰고 평가하기 — 권한·회귀·과제 제출, AI 코딩 도구 고르기 — 터미널이냐 편집기냐 클라우드냐, AI에게 컴퓨터를 맡길 때 — 권한, 로컬 모델, 토큰 비용.
