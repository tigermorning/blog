이번 편에서 하는 일 — 한 편을 완성하고, 내 일로 바꾸기

앱을 만들고 질문 대기까지 붙였으면, 이제 실제로 'AI 최신소식'을 넣어 카드뉴스 한 편을 완성해요. 출발점은 정해 둔 모델이나 오래된 발표가 아니에요. 앱이 실행한 시점을 기준으로 최근 7일의 소식을 검색하고, 그중 설명할 가치가 있는 1~3개를 사용자가 골라요. 앱의 제작 에이전트가 조사부터 이미지와 원고까지 이어서 하고, 나는 선택이 필요한 지점과 최종 결과만 확인해요. 그다음 이 흐름을 내가 자주 하는 작업으로 바꿔 확장해요.

비유 — 요리와 메뉴 카드를 따로 두고, 포장을 열어 보기

이 시리즈는 비유를 하나만 써요. 1편에서 세운 식당 주방 그대로예요. 손님은 카드뉴스를 만드는 사용자이고, 받는 사람은 그 카드뉴스를 읽을 사람이에요.

주방은 도시락 접시마다 요리와, 그 옆에 꽂는 메뉴 카드를 따로 만들어요. 메뉴 카드에 오타가 있으면 카드만 다시 인쇄하고 요리는 그대로 둬요. 손님이 "세 번째 접시 요리가 별로예요"라고 하면 그 접시의 요리만 다시 해요. 그리고 손님에게 보내기 전에는 진열대에 놓은 시식 사진이 아니라, 포장을 실제로 열어 접시 수·순서·메뉴 카드의 글씨를 확인해요.

접시에 올리는 요리글자가 없는 생성 이미지 (글자를 올릴 여백만 남겨요)

손님이 주방에게 — "세 번째 메뉴 카드가 너무 길어요" → 주방이 카드만 다시 인쇄사용자가 앱에게 — 3번 카드 본문을 줄여 달라고 요청 → 글만 고치고 이미지는 유지

주방이 포장을 열어 접시 수·순서·글씨를 직접 확인내보낸 카드 파일을 모두 열어 순서·수량·글자 잘림·출처 점검

핵심 한 줄: 요리와 메뉴 카드를 따로 두면 글씨 하나 고치려고 요리를 다시 하지 않고, 포장을 열어 봐야 손님이 받을 것을 알 수 있다.

다만 여기서 비유가 끊기는 점이 있어요. 식당의 요리는 다시 하면 재료와 시간이 들 뿐이지만, 앱에서는 이미지를 다시 만드는 것이 곧 외부 도구를 다시 부르는 일이에요. 제가 읽은 한 참고 구현은 제목이나 본문을 바꾸면 이미지 생성 요청도 달라져서 그 카드의 삽화가 다시 만들어질 수 있었어요. 그래서 "글만 고치면 그림이 유지되는지"는 내 앱에서 따로 확인해야 해요.

전체 흐름 — 한 카드를 고칠 때 무엇이 다시 만들어지나

읽는 법: 왼쪽 상자는 카드 한 장을 이루는 두 겹이에요. 사용자가 고칠 것을 지정하면 오른쪽 두 갈래 중 하나로 가고, 어느 쪽이든 끝에는 기존의 최종 승인이 풀리고 새 버전을 다시 검토해 승인해요.

한 편을 만드는 여섯 걸음 — 단계마다 직접 확인할 것

아래는 앱이 자동으로 이어 가야 할 동작이에요. 사용자는 주제를 입력하고 필요한 선택과 승인만 해요. 인용한 요청 문장은 단계를 손으로 진행하라는 뜻이 아니라, 앱에 동작이 빠졌거나 고쳐야 할 때 코딩 에이전트에게 전할 참고예요.

1~3. 후보 → 심층 검증 → 독자와 후킹

단계앱이 해야 할 것직접 확인할 것
① 후보 찾기검색 기준 시각·시간대·시작일·종료일을 화면에 보여요. 가능하면 서로 다른 후보 7~12개(모델·제품·연구·개발 도구 등)를 내놓고, 같은 발표를 다룬 기사는 묶어요. 후보마다 제목·원문 링크·게시일·실제 발표나 변경일(확인되는 경우)·선택할 가치·불확실성을 달아요. 확인 못 한 날짜는 '미확인'으로 두고, 최근에 쓴 소개 글이라고 오래된 발표를 새 소식으로 분류하지 않아요후보의 공식 원문을 하나 직접 열어 제목과 날짜를 대조해요. 검색 결과 요약만 있고 원문을 읽지 못했으면 '검증 완료'로 넘어가면 안 돼요. 후보 목록에는 '미확인'으로 남겨도 되지만, 카드의 핵심 사실로 쓰기 전에 근거를 확인하거나 그 주장을 빼요
② 심층 검증공식 발표뿐 아니라 제품 문서·변경 기록도 확인해요. 무엇이 달라졌는지, 누가 언제부터 쓸 수 있는지, 지역·계정·요금제 같은 조건이 있는지를 나눠요. 성능이나 효과는 발표한 쪽의 주장인지, 독립적으로 확인한 사실인지 구별해요. 자료끼리 날짜나 조건이 안 맞으면 원고를 확정하기 전에 보여 줘요'모두 사용 가능', '무료', '성능 향상'처럼 뜻이 큰 문장을 골라 근거와 대조해요. 모르는 부분을 그럴듯한 문장으로 채우지 않는지 봐요
③ 독자·후킹검증을 마친 뒤에 표지 문장을 만들어요. 소식과 조사 결과로 받는 사람을 판단하고 추천 이유를 보여 줘요. 받는 사람이나 편집 방향에 따라 결과가 크게 달라질 때만 짧은 객관식을 내고(예: 일반 사용자·개발자·교육자), 선택의 차이를 한 줄로 설명하고 자유 입력도 허용해요. 이미 목적을 입력했으면 같은 질문을 되풀이하지 않아요표지만 읽었을 때 원문보다 기능이나 혜택을 크게 받아들이게 되지 않는지 봐요. 궁금증을 만드는 문장과 사실을 부풀리는 문장을 구별해요

기간 안에 확인 가능한 소식이 부족하면 앱은 실제로 찾은 수를 알리고, 검색 기간을 30일로 넓힐지 사용자가 고르게 해요. 코딩 에이전트에게 단계를 고치게 할 때는 이렇게 말해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 앱에 이 동작이 빠졌을 때

실행한 시점 기준 최근 7일의 AI 소식을 찾아 줘. 가능하면 서로 다른 후보를 7~12개 보여 주고, 후보마다 원문 링크·게시일·선택할 가치·불확실성을 달아 줘. 부족하면 실제로 찾은 만큼만 알려 줘.

표지 문구는 한 번에 쓰지 않고 순서를 둬요. 제가 읽은 참고 구현은 첫 카드의 후킹을 별도 호출로 먼저 설계했어요. 받는 사람의 관심 → 서로 다른 후보 문구 두 개 → 근거와 과장 위험 비교 → 하나 선정 → 그 문구로 첫 카드 작성 순서예요. 뒤 카드는 첫 카드가 만든 궁금증을 실제 자료로 풀어 줘야 해요. 기획 화면에서는 텍스트로 피드백을 주면 다시 쓰고, 수정안을 확인한 뒤 제작을 승인할 수 있어요.

4. 스토리보드를 확정하고 이미지를 만든다

선택한 형식으로 보통 5~8장의 스토리보드를 만들고 내용에 맞게 조정해요. 예를 들어 표지 → 달라진 점 → 활용 상황 → 사용 조건·한계 → 요약과 출처 순서로 짤 수 있어요. 장마다 핵심 문장 하나, 짧은 본문, 이미지의 역할, 근거 링크를 달아요. 공개 예정인 기능이면 제목과 본문에도 '예정'임을 남겨요. 모든 장에 같은 정보를 되풀이하거나 이미지로 설명할 수 없는 추상적인 지시만 들어 있지 않은지 확인해요.

스토리보드를 확정하면 앱의 제작 에이전트가 Antigravity CLI(agy)로 이미지 생성을 요청해요. 요청에는 장면, 공통 색감, 구도, 글자를 올릴 여백을 넣고 '이미지 안에 글자 없음'을 분명히 적어요. 실제 제품 화면이나 발표 장면이 아닌 그림은 설명용 생성 이미지로 기록해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 스토리보드를 확정한 뒤 이미지 연결을 요청할 때

이 스토리보드에 맞는 설명용 이미지를 agy로 만들어 줘. 장마다 색감과 그림체를 통일하고, 제목을 올릴 여백을 남겨 줘. 이미지 안에는 글자를 넣지 말고, 실제로 저장된 파일을 열어서 확인해 줘.

여기서 가장 흔한 실수는 "요청을 보냈다"와 "파일이 만들어졌다"를 같은 일로 보는 것이에요. 생성 결과 파일이 실제로 존재하고 이미지로 열리는 걸 확인한 뒤에만 완료로 표시해야 해요. 실패하면 그 카드에 오류와 다시 시도 버튼을 보여 주고, 확정한 스토리보드와 다른 카드의 결과는 그대로 둬요. 이미지 요청을 헤드리스2로 실행하면 필요한 도구 권한을 대화형으로 받을 수 없어 작업이 거부될 수 있어요. 그래서 종료 코드나 응답 문장만으로 성공이라고 보지 말고 결과 파일까지 검증해요. 인증 실패는 대화형 화면에서 로그인을 확인하고, 권한 거부는 필요한 도구의 허용 규칙을 정한 뒤 다시 시도해요.

한 가지 주의가 있어요. 별도 작업 폴더에서 승인한 작업을 시험할 때 --dangerously-skip-permissions를 붙이는 방법도 있지만, 이건 이미지 도구에만 권한을 주는 것이 아니라 그 실행의 모든 도구 요청을 자동으로 승인해요. 웹 서비스에 연결할 때는 필요한 도구만 허용하는 규칙을 먼저 써요. 참고로 제가 읽은 설명은 이미지 생성을 에이전트가 가진 이미지 생성·편집 도구로 다루고, agy image generate 같은 별도 명령으로 부르는 것은 아니라고 했어요. 제가 확인해 본 것은 아니에요. 원본 생성 이미지의 예는 1024×1024 PNG3였고, 앱에서는 선택한 최종 카드 크기에 맞춰 배치하고 제목·본문을 별도로 얹어요.

5. 글자를 따로 넣고 미리보기를 고친다

생성한 이미지는 배경이나 삽화로 놓고, 제목·본문·출처는 앱에서 편집할 수 있는 별도 텍스트로 올려요. 그래야 맞춤법이나 사실관계를 고칠 때 이미지를 다시 만들지 않아도 돼요. 모바일 크기로 카드를 넘겨 보면서 글자 크기, 줄바꿈, 여백, 명암 대비, 카드 사이의 이어짐을 확인해요. 글자를 이미지와 따로 두면 한국어 줄바꿈과 읽기 쉬움을 앱에서 조정할 수 있어요.

수정을 요청할 때는 카드와 문제를 구체적으로 지목해요. "더 예쁘게"보다 "3번 카드의 본문이 길어. 핵심 조건은 유지하고 두 문장으로 줄여 줘"가 확인하기 쉬워요. 그림이 부적절하면 그 카드만 다시 만들고, 글만 고칠 때는 기존 이미지를 유지하게 구현해요. 수정한 뒤에는 기존 최종 승인을 풀고 새 버전을 검토해 다시 승인하게 해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 앱에 글자 분리와 부분 수정이 아직 없을 때

생성 이미지 위에 제목과 본문을 별도 텍스트로 올려 줘. 모바일 크기 미리보기를 보여 주고, 글자가 잘리거나 배경과 겹치는 부분을 고칠 수 있게 해 줘. 한 카드의 글만 고쳐도 그 카드의 이미지는 다시 만들지 마.

6. 내보낸 파일로 최종 검수한다

미리보기가 괜찮아도 내보낸 결과는 따로 확인해요. 카드 이미지 파일을 모두 열어 순서와 수량, 글자 잘림, 한글 표시, 출처와 조사 기준일을 점검해요. 자료를 다시 확인할 수 있게 원문 링크와 이미지 생성 기록도 함께 보관해요. 카드별 PNG, 전체 ZIP4, 출처와 이미지 사용 기록을 내려받게 하고, 자동 게시까지는 하지 않고 검수한 파일을 결과물로 삼아요. 통과 기준은 이래요.

검수 대상통과 기준
최신성과 사실조사 기간이 표시되고, 핵심 문장의 날짜·기능·사용 조건을 원문에서 확인할 수 있어요
독자와 흐름표지가 받는 사람에게 필요한 이유를 전하고, 각 카드가 서로 다른 메시지를 이어 가요
생성 결과이미지 파일이 실제로 열리고, 생성한 그림을 실제 제품 화면이나 보도 사진처럼 설명하지 않아요
편집과 가독성제목·본문을 따로 고칠 수 있고, 모바일 크기에서도 글자가 읽혀요
실패와 재시도인증·권한·생성 실패가 완료로 표시되지 않고, 실패한 작업을 다시 시도할 수 있어요
내보내기확정한 카드가 빠짐없이 같은 순서로 저장되고, 출처와 조사 기준일이 남아요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 내려받은 파일이 있는 폴더에서

내보낸 파일을 기준으로 빠진 카드, 글자 잘림, 출처, 날짜를 확인해 줘. 확인하지 못한 항목은 통과로 처리하지 말고, 내가 직접 확인할 부분을 알려 줘.

혼자 만들었더라도 짝이나 시간 간격을 둔 나에게 한 번 더 맡겨요. 원문 링크·완성 카드 파일·실행 기록을 보여 주고, 핵심 문장 하나의 날짜와 조건을 원문과 대조하고, 모바일 크기에서 읽기 어려운 카드 하나를 지목해요. 피드백 한 가지를 반영한 뒤 같은 항목을 다시 확인해요. 혼자라면 시간을 두고 같은 두 항목을 직접 점검해요.

참고 사례 하나만 적어 둘게요. 2026년 9월 8일에 돌린 기록에서는 후보 10개 가운데 WeatherNext 3를 골라 일반 AI 뉴스 독자용 카드 5장을 완성했고, 마지막 카드의 수치 설명을 검토한 뒤 고쳤고, 고치지 않은 4장의 PNG가 그대로 남는 것까지 확인했다고 해요. 다만 이 기록은 카드마다 삽화를 만들기 전, 배경 한 장을 나눠 쓰던 버전의 것이라 지금 구현의 모든 기능을 검증한 예시가 아니고, '최신'이라는 말도 그 실행 당시에만 맞아요.

나만의 워크플로로 확장하기 — 가져올 것과 바꿀 것

카드뉴스 한 편의 검수까지 끝냈으면 이 흐름을 자주 하는 작업에 옮겨 봐요. 반복해서 겪는 불편 하나와 확인할 수 있는 결과물 하나를 고르면 시작하기 쉬워요. 회의 기록을 실행 항목으로 정리하기, 학습 자료에서 복습 문제 만들기, 여러 공고를 비교해 지원 준비 목록 만들기가 예가 돼요. 먼저 카드뉴스 PRD5에서 무엇을 가져오고 무엇을 바꿀지 정해요. 자료를 조사하고, 후보를 비교하고, 선택에 따라 결과물을 만드는 흐름은 그대로 쓸 수 있고, 카드 수나 이미지 배치처럼 카드뉴스에만 필요한 조건은 내 작업에 맞게 바꿔요.

설계할 부분내 작업에서 정할 내용
입력사용자가 무엇을 넣는가? 자료·목적·조건 중 결과를 만드는 데 필요한 것만 정해요
AI 판단AI가 어떤 정보를 추리고, 어떤 후보를 비교하고, 무엇을 제안하는가? 판단의 근거도 결과에서 확인할 수 있게 해요
사람 결정목표나 취향에 따라 결과가 달라지는 지점은 어디인가? 이미 입력한 조건은 다시 묻지 않고, 꼭 필요한 선택만 요청해요
도구 행동선택 뒤 실제로 무엇을 검색·작성·저장하는가? 외부에 보내거나 게시하는 일이 있으면 실행 전에 검토할 결과와 실행 조건을 정해요
검수와 산출물어떤 상태면 쓸 수 있는 결과인가? 원문과의 일치, 빠진 내용, 형식을 확인하고 고칠 수 있게 해요

예를 들어 '학습 자료로 복습 문제 만들기'라면 이렇게 짤 수 있어요. 자료와 학습 범위를 입력받고, AI가 핵심 개념과 문제 후보를 제안해요. 학생은 복습할 개념이나 난도를 고르고, 앱은 문제와 해설을 써요. 마지막에는 해설의 근거가 자료에 있는지 확인하고, 고친 문제를 저장해요. 선택 화면은 모든 단계에 두지 않고 학생의 결정이 필요한 곳에만 둬요. 설계가 정해지면 수정한 PRD 전체를 코딩 에이전트에게 넘겨 구현해요.

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 수정한 PRD가 들어 있는 폴더에서

카드뉴스 PRD를 '학습 자료로 복습 문제를 만드는 워크플로'로 바꿔서 구현해 줘. 핵심 개념을 제안하고 내가 고르면, 근거가 있는 해설과 함께 문제를 만들어 줘. 자료가 부족하면 어느 부분이 부족한지 표시해 줘.

첫 실행에서 원하는 결과가 안 나오면 코드 설명을 길게 요청하지 말고 실제 입력, 기대한 결과, 나온 결과의 차이를 알려 주고 다시 실행해요. 완성한 뒤에는 내 자료로 한 번 돌리고, 자료가 부족하거나 요청이 모호한 경우도 확인해요. 오류를 숨기거나 그럴듯한 내용으로 채우지 말고, 현재 상태를 보여 주고 입력을 보완하거나 다시 실행하는 쪽으로 이어지는지 봐요. 새 앱을 처음부터 크게 만들기보다 입력·판단·결과 중 필요한 부분만 바꿔 정상 입력 한 번과 자료 부족 입력 한 번을 실행하는 정도면 돼요. 확장이 끝나지 않았다면 카드뉴스의 완료 범위와 확장의 미완료 범위를 따로 기록해 둬요.

기록으로 남길 것은 네 가지예요. 실행할 수 있는 결과와 간단한 실행 방법, 해결할 불편과 기대 산출물과 사람이 결정하는 지점을 반영한 PRD, 실제 입력부터 선택과 결과까지 보이는 화면·기록·산출물, 기대와 달랐던 사례 하나와 바꾼 점·다시 실행한 결과예요. 아직 풀지 못했다면 남은 문제와 다음 수정 방향을 적어요. 기능 수를 늘리기보다 다음 작업에서도 다시 쓸 수 있는 흐름을 완성하는 데 집중해요.

나쁜 선택 vs 좋은 선택 — 이미지 요청을 보낸 뒤

주방이 요리 주문서를 요리사에게 보낸 상황이에요. 도시락 접시 다섯 개 가운데 하나의 요청이 인증 문제로 거부됐어요.

나쁜 선택좋은 선택
무엇을 했나: 요청을 보냈고 종료 코드가 정상이라는 이유로 다섯 장을 모두 '완료'로 표시했어요.

무슨 일이 생기나: 한 카드는 이미지가 비어 있는데 화면에는 완료로 보여요. 내려받은 파일에서야 한 장이 빠졌다는 걸 알고, 어느 요청이 왜 실패했는지 기록도 없어요.		 무엇을 했나: 저장된 파일이 실제로 있고 이미지로 열리는 카드만 완료로 표시하고, 실패한 카드에는 오류와 다시 시도 버튼을 보여 줬어요.

무슨 일이 생기나: 실패한 한 장만 다시 시도하면 돼요. 확정한 스토리보드와 성공한 네 장은 그대로 남아요.

이 글에 나온 숫자 — 만들고 검수할 때 볼 것

한 편을 만드는 여섯 걸음과 확장하기에서 다른 작업에도 다시 쓰는 값만 모았어요.

무엇의 숫자인가값알아 둘 것
한 번에 보여 주는 후보 수가능하면 7~12개실제로 그만큼 못 찾으면 못 찾은 대로 알려야 해요. 숫자를 맞추려고 오래된 소식을 채우지 않아요
조사 기간 확대7일 → 30일기간 안에 소식이 부족할 때 사용자가 넓힐지 고르는 값이에요. 넓히면 '최신'의 기준이 바뀌니 화면에 다시 표시해요
카드 한 편의 장수보통 5~8장내용에 맞게 조정해요. 장마다 핵심 문장은 하나만 둬요
생성 이미지 원본과 최종 카드 크기1024×1024 PNG → 최종 1080×1350원본 이미지는 글자를 올리기 전의 배경이에요. 다른 비율이 필요하면 PRD에 적고 구현해요
최종 검수 항목6가지최신성과 사실·독자와 흐름·생성 결과·편집과 가독성·실패와 재시도·내보내기예요. 확인하지 못한 항목은 통과로 세지 않아요
교차 검수에서 보는 것핵심 문장 1개의 날짜·조건 + 읽기 어려운 카드 1개 + 피드백 1가지 반영많이 보려 하지 말고 같은 항목을 고친 뒤 다시 확인하는 데까지 가요
확장의 첫 실행정상 입력 1번 + 자료 부족 입력 1번잘 풀리지 않는 경우도 함께 돌려 봐야 오류를 숨기는지 알 수 있어요

이럴 때 의심하세요 — 만든 카드를 믿어도 되는지 흔들릴 때

카드뉴스의 문제는 에러 문장 없이 파일을 열어 봐야 보이는 모습으로 나타나는 경우가 많아요.

증상이 아직 없어도, 코딩 에이전트에게 "카드를 내보내게 해 줘"라고 부탁한 직후라면 한 번 확인하고 넘어가요.

  • "카드를 PNG로 저장해 줘" — 내려받은 파일을 모두 열었을 때 장수와 순서가 미리보기와 같은지
  • "이미지를 생성해 줘" — 카드 칸마다 저장된 파일이 정말 있는지
이런 증상이 보이면먼저 열어 볼 자리확인 방법
미리보기는 멀쩡한데 내려받은 파일에서 글자가 잘리거나 카드 순서나 장수가 달라요 내보내기 코드가 글자를 얹는 부분이에요. 미리보기와 내보내기가 서로 다른 경로로 그려질 수 있어요. 미리보기 화면은 범인이 아닐 수 있어요 내려받은 PNG를 전부 열어 순서·수량·글자 잘림·출처를 직접 봐요(최종 검수). 모바일 크기에서도 읽히는지 봐요
카드 상태는 '완료'인데 이미지 칸이 비었거나 열리지 않는 파일이에요 이미지 생성을 부른 뒤 성공을 판정하는 줄이에요. 종료 코드나 응답 문장만 보고 성공으로 두었을 수 있어요 저장 폴더에서 그 카드의 파일이 실제로 있고 이미지로 열리는지 봐요. 없으면 그 카드만 다시 시도해 앞 카드가 유지되는지 확인해요 (이미지 만들기)
카드에 '모두 사용 가능'·'무료' 같은 말이 있는데 원문에서 그 문장을 찾을 수 없어요 핵심 사실의 근거 링크와 '확인한 사실 / 발표한 쪽의 주장 / 미확인' 구분이에요. 검색 요약만 읽고 쓴 문장일 수 있어요 뜻이 가장 큰 문장 하나를 골라 공식 원문과 제품 문서에서 찾아요(심층 검증). 없으면 그 문장을 빼거나 '미확인'으로 바꿔요
카드 하나의 글만 고쳤는데 그림이 달라졌어요. 이미지가 다시 생성된 것 같아요 글을 고쳤을 때 이미지 생성 요청에 제목·본문이 같이 들어가는 부분이에요. 글을 바꾸면 요청도 달라지게 짜여 있을 수 있어요 한 카드의 글만 고쳐 나머지 카드와 그 카드의 이미지가 그대로인지 비교해요. 달라지면 이미지 요청에 글을 넣지 않게 고쳐 달라고 해요(글자 따로 넣기)
카드를 고쳤는데 화면에는 고치기 전의 '최종 승인'이 그대로 남아 있어요 수정 뒤 승인 상태를 되돌리는 코드예요 카드 하나를 고친 직후 승인 표시가 풀리고, 새 버전을 다시 승인해야 내려받기가 열리는지 확인해요

실행: 코딩 에이전트에 붙여넣기 — Claude Code 등 — 카드뉴스 앱 프로젝트 폴더에서

이 프로젝트의 이미지 생성과 내보내기 코드를 찾아 표로 보여 줘. 아직 코드는 고치지 마.
1. 이미지 생성이 성공했다고 판정하는 조건(종료 코드·응답 문장·저장된 파일 확인 중 무엇을 보는지)과 파일 줄 번호
2. 카드의 제목·본문을 고쳤을 때 이미지 생성 요청이 다시 만들어지는지
3. 카드를 고친 뒤 '최종 승인' 상태를 풀어 주는 코드가 있는지
4. 미리보기와 내보내기가 같은 그리기 코드를 쓰는지

직접 해보기

  1. 원문과 날짜 대조 — 바꿀 것: 앱이 내놓은 후보 중 하나를 골라 공식 원문 링크를 직접 열어요. 측정할 것: 화면의 제목·게시일이 원문과 같은지. 비교할 것: 요약만 읽었을 때와 원문까지 읽었을 때 달라지는 문장이 있는지.
  2. 글만 고치기 — 바꿀 것: 한 카드의 본문을 두 문장으로 줄여 달라고 요청해요. 측정할 것: 나머지 카드와 그 카드의 이미지 파일이 그대로인지. 비교할 것: 이미지를 다시 만들었을 때 걸리는 시간과 비교해요.
  3. 내 작업 PRD 다섯 칸 — 바꿀 것: 위 다섯 칸 표를 내 반복 작업 하나로 채워요. 측정할 것: 사람이 정하는 칸이 몇 개인지. 비교할 것: 전부 AI에게 맡겼을 때와 결과가 달라지는 곳.

정답은 하나가 아니에요. 어디서 사람에게 묻고 어디서 AI에게 맡길지는 일마다 달라서, 내 작업으로 한 번 돌려 보고 정하는 게 요령이에요.

확인 범위 — 읽은 것과 못 읽은 것

  • 이 글은 한 편을 만드는 여섯 걸음, 검수 기준, 확장 설계에 대한 설명 글을 읽고 재구성한 것이에요. 제가 'AI 최신소식'을 넣어 카드를 만들거나 내보낸 파일을 열어 본 것이 아니에요.
  • agy와 헤드리스 권한 이야기, 이미지 생성 도구에 대한 설명은 공식 문서를 직접 열어 대조하지 않았어요. 구현할 때 해당 도구의 공식 문서로 확인해요.
  • 2026년 9월 8일 사례는 설명 글에 적힌 요약을 옮긴 거예요. 그 실행의 결과 ZIP과 검증 기록은 읽지 못했어요.
  • 접혀 있던 보조 설명(이미지 요청을 손으로 해 보는 방법)과 화면 이미지는 읽지 못했어요.

이 시리즈는 여기까지예요. 여기서 발견한 사용자 결정, 도구 권한, 실패 사례는 내 업무 자동화를 설계할 때 그대로 반영할 수 있어요. 사람이 승인하는 자리의 기준은 HITL 2편, 같은 'AI 소식'을 사람 손 없이 매일 보내는 쪽은 뉴스레터 에이전트의 발행·예약 편이 이어져요.

함께 읽으면 좋은 글

  • 고르고 승인하며 완성하는 카드뉴스 — 일곱 단계 흐름과 독자·형식 정하기 (1) — 이 편의 단계가 어디에 놓이는지 먼저 정리한 글이에요.
  • PRD로 시작해 질문과 재개를 붙인다 — 실행 엔진과 대기 상태 (2) — 질문 대기와 새로고침 뒤 이어 가기를 다룬 글이에요.
  • 요약을 세 칸으로 받고 원문과 대조한다 (14) — 요약이 원문과 다른 말을 하지 않는지 확인하는 방법을 다룬 글이에요.
  • 만들기 전에 합격선을 긋는다 — 완료 조건과 검증 시나리오 (5) — 통과 기준을 미리 적어 두는 방식이에요.
  1. 텍스트 레이어 — 이미지 위에 겹쳐 놓는 글자만의 층으로, 이미지를 건드리지 않고 글만 고칠 수 있게 해요. ↩
  2. 헤드리스(headless) — 화면과 대화 없이 요청을 실행하는 방식이라, 실행 중에 도구 권한을 사람에게 물어볼 수 없어요. ↩
  3. PNG — 화질 손실 없이 저장하는 이미지 파일 형식이에요. ↩
  4. ZIP — 여러 파일을 하나로 묶고 압축한 파일 형식이에요. ↩
  5. PRD(Product Requirements Document) — 만들 앱이 무엇을 해야 하는지 요구사항을 적은 문서로, PRD를 스스로에게 묻는 글에서 처음 다뤘어요. ↩
